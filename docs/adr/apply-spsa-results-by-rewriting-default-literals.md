# SPSAの結果は係数表の既定値のリテラルだけを書き換えて反映する

## ステータス

承認済み。決定日は2026年9月22日。

## コンテキスト

SPSAの係数は`crates/minase/src/search/alphabeta/params.rs`の`parameters!`の表に1行1係数で並び、通常ビルドはその既定値を定数として使う（[調整用ビルドのADR](expose-tunable-coefficients-only-in-tuning-builds.md)）。
当初の手引きは、セッションの最終値を人手で四捨五入して表へ書き写すことにしていた。
この転記には、書き写しの誤り、丸め規則の揺れ、途中で止まったセッションや事前確認のセッションの値の誤用、および開始時と異なる表への適用の余地があった（[SPSAの結果を反映するコマンド](../plans/spsa-apply.md)）。
やねうら王の`tune.py`、fishutils、およびapeironも同種の自動反映を持ち、いずれもソース中の定数の行を独自の規則で探して数値を置き換える（[反映の先行例の調査](../research/spsa-parameter-application.md)）。
同じ調査で、Hobbes、akimbo、Reckless、Viridithas、およびapeironは、いずれも係数の定義をRustのソースに置いていた（[反映の先行例の調査](../research/spsa-parameter-application.md)）。

## 決定

`minase spsa apply`は、完了したセッションの実行ディレクトリから更新則を再計算して最終のθを復元し、`f64::round`で丸めた整数で、表の各宣言の既定値のリテラルだけを書き換える。
表は1行1宣言の文法として標準ライブラリの文字列操作で解析し、宣言として認識できない行があれば何も書かずに失敗する。
表の既定値がセッションの開始値と厳密に一致し、セッションの範囲が表の範囲に含まれる場合だけ書き込み、検査と書き換えの詳細は`apply`モジュールのdocコメントに従う。

## 検討した代案

表をTOMLやJSONへ移して`build.rs`でアクセサを生成する案は、コード生成の処理と依存が増え、係数ごとのdocコメントを保てず、表の構文をrustcがマクロで検査している保証を手放すので採らなかった。
pest、nom、winnowなどの構文解析ライブラリを使う案は、入れ子も再帰もない文法に対して依存とビルド時間を増やすだけなので採らなかった。
表を構造から生成し直す案はdocコメントと並び順を保てず、やねうら王のように周辺のコードを目印に数値を探す案は目印の保守が要るので採らなかった。
runnerの標準出力から最終値を読む案は、保存記録の検査を経ないので採らなかった。
開始値の不一致を上書きで許すオプションと、差分の表示だけを行う`--dry-run`は、検査と書き換えの経路を2つにするので設けなかった。
ブランチの作成やコミットを`apply`に行わせる案は、gitの状態を読む機構を足すことになるので採らなかった。

## 結果

候補のコミットが調整対象のコミットと係数の値だけで異なることは、`apply`ではなく、調整対象からブランチを切って`git diff`を確かめる手順が保証する（[SPSAの手引き](../guides/spsa.md)）。
`apply`はエンジンをビルドしないので、書き換えた値が調整用ビルドの宣言へ反映されたことは`minase spsa params`の出力で確かめる。
解析の規則は`parameters!`マクロが受け付ける書き方より狭いので、表に新しい書き方を加えると、実際の`params.rs`を解析する単体テストが失敗して検出する。
`apply`はrunnerより新しいバイナリで動かすことを前提にし、runnerのSHA-256も作業ツリーのコミットも照合しない。

# 各ファイル形式の版を1つにし、過去のファイルを読み続けない

## ステータス

置き換え済み。決定日は2026年10月13日。[保存するファイル形式の版は1つにし、実行専用の一時ファイルだけは独自の配置を認める](../keep-one-version-per-saved-format-and-allow-run-private-scratch-files.md)によって置き換えられた。

## コンテキスト

2026年10月13日の時点で、minaseのコードがディスクに読み書きするファイル形式のうち、`MN`で始まる独自のマジック（ファイル先頭の識別バイト列）を持つバイナリ形式は7種類あった。
重みの形式MNPTはPSTだけの版2とPSTとFMの版3を併存させ、対局ハーネスの集計`minase match report`は、実行ディレクトリの記録形式の版4と版5を読み分けていた。
独自形式の仕様は、読み書きするモジュールのdocコメント、凍結した設計書、および廃止した`docs/reference/`に分かれ、一部は実装と食い違っていた。
エンジンの開発者は、同じ形式に複数の版があることと、過去のファイルを読み続けるための保守が過剰であることを指摘した。
形式や版が多いと、変更のたびに書き込み処理、読み込み処理、検査、および文書をそろえる手間が増え、そろわなかった箇所が不具合や古い記述として残る。

## 決定

各形式の版は1つだけにし、読み手は現行の配置だけを受け付ける。
版番号の欄は、古いファイルを誤読せずにエラーで止めるためだけに使う。
形式を変えるときは変換コマンドを作らず、読めなくなったファイルは必要になったときに生成し直し、使えなくなったファイルは一覧を示して確認を得てから削除する。
`crates/minase/nets/`に埋め込む重みのように、その時点でコードが必要とするファイルだけは、コードに残さない使い捨ての手順で書き直して同じコミットに含める。
`MN`の独自形式は、エンジンが読む重み（MNUEとMNPT）と、学習器が読む教師データ（MNSD）に限り、学習器の内部だけで使うファイルにはNPZとJSONを使う。
各形式の仕様は、その形式を書き出すモジュールのdocコメントに書き、形式の一覧と仕様の所在だけを[ファイル形式の一覧](../../guides/file-formats.md)に置く。

この原則に従い、MNPTは版3だけにし、FMを持たない重みはFM節の次元を0とする。
`minase match report`は記録形式の版5だけを受け付ける。

## 検討した代案

MNPTの版2と版3を併存させる案は、原則に反するので採らなかった。
PSTだけの重みを廃止してNNUEの重みへ統合する案は、PSTとPST＋FMの評価関数をソースコードに残すという2026年10月9日の決定に反するので採らなかった。
旧版を新版へ書き換える変換コマンドを用意する案は、変換器そのものが保守の対象として残るので採らなかった。
仕様を設計書や専用の参照文書に置く案は、完了後に保守されずに実装と食い違うことが、廃止した`docs/reference/`と凍結した設計書で起きていたので採らなかった。

## 結果

`MN`の独自形式はMNSD、MNUE、MNPTの3つになった。
形式を変えるコミットでは、読めなくなる過去のファイルの扱いを、変換ではなく再生成か削除で決める。
過去の測定の再現には、その測定を行ったコミットのバイナリを使う。
対局ハーネスの実行ディレクトリは測定記録の根拠なので、版4のものも削除せずに残し、集計が必要なら当時のコミットの`minase`で行う。
形式を追加、変更、または廃止するコミットでは、書き手のdocコメントとファイル形式の一覧を同じコミットで直す。

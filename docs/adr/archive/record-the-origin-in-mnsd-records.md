# 教師データの由来をMNSDのレコードに置き、来歴ファイルと全体の検査和をやめる

## ステータス

置き換え済み。[教師データを対局単位の連鎖で記録するMNSDの1形式にまとめる](../record-teacher-data-as-chained-games.md)によって置き換えられた。

## コンテキスト

[教師データを来歴ファイルで分類する決定](classify-teacher-data-by-provenance-files.md)では、MNSDの形式を変えずに、教師の探索条件、局面の由来、混合比λ、および棋譜との対応を各MNSDに添えるJSONの来歴ファイルへ記し、学習器にMNSD全体のSHA-256を来歴と照合させていた。
その後、[付け直しと実戦棋譜を教師に加えない決定](../keep-deep-rescoring-and-human-games-out-of-the-teacher.md)により、付け直しの出力と棋譜IDによる検証分割は学習に使われなくなった。
2026年10月13日にエンジンの開発者は、教師データの照合が将棋の教師形式に比べて過剰であること、1つのデータを2つのファイルで表していることを指摘した。
将棋のhcpe（38バイト）とPackedSfenValue（40バイト）は、ヘッダも検査和も持たない固定長レコードの列である（cshogi 1.0.4の`cshogi/_cshogi.pyx`）。
MNSDのレコードには、0に固定された未使用の4バイトがあった。

## 決定

MNSDのレコードのオフセット156の1バイトを由来の欄とし、乱数開始の自己対局0、実戦開始の自己対局1、実戦対局2、合成3を書く。
学習器は、ヘッダの生成コミット、重みの検査和、ノード上限、規則セット、ファイルの由来、先読みの条件、および適用したλの組で教師の分類を決め、検証集合を由来によらずヘッダのシードと対局番号のハッシュで決める。
λは教師値を作るコマンドの必須の引数`--lambda`で与え、自己対局の由来にだけ適用し、実戦対局には常に0を使う。
来歴ファイル、付け直し（MNRS形式）、実戦棋譜の詳細の付随ファイル`.games.json`、およびMNSD全体の検査和の計算と照合は廃止する。
仕様は`crates/minase/src/training/records.rs`と`crates/minase-trainer/src/data/mnsd.rs`のdocコメントにある。

## 検討した代案

来歴ファイルから全体の検査和だけを外す案は、ヘッダの写しを来歴と突き合わせる重複と、1つのデータを2つのファイルで表す構造が残るので採らなかった。
ビット化けの検出のために全体の検査和を残す案は、hcpeとPackedSfenValueも検出しないので採らなかった。
切り詰めはファイル長の検査で、同じファイルの重複指定は正規化したパスの比較で検出できる。
実戦に由来するデータの検証分割を棋譜IDで決める方式を残す案は、棋譜IDの対応表を要し、それが来歴ファイルの存在理由になるので採らなかった。
この方式の利点（同じ棋譜に由来するデータがファイルをまたいで同じ集合に入ること）が効くのは、実戦対局のデータと実戦開始の自己対局のデータを同時に学習する場合だけである。
λを来歴から読み、引数で上書きする方式は、値の出どころが2つになるので採らなかった。
引数の既定値で補う方式は、プロジェクトの方針が禁じるフォールバックに当たる。

## 結果

MNSDは1ファイルで完結し、版と配置は変わらない。
既存の乱数開始の自己対局のデータはバイト156が0なので、そのまま新しい定義に合う。
変更の前後で、乱数開始の自己対局の2ファイルによるNNUEとPSTの学習の局面数、教師用K、通し番号、および各エポックの損失がビット単位で一致した（[照合の記録](../../measurements/file-format-consolidation/file-format-consolidation-equivalence.md)）。
実戦対局のデータと、その棋譜から始めた自己対局のデータを同時に学習すると、同じ棋譜に由来する局面が訓練集合と検証集合に分かれ得る。
その組み合わせで学習する計画は、検証損失が実際より良く見えるおそれを考慮して設計する必要がある。
学習器の診断（`minase-trainer diag pst-compare`）が対局を数える単位は、入力ファイルの番号と対局番号の組になった。
来歴を持たなかった過去のMNSDのうち、診断の標本や派生データは、由来を表せないので削除した。

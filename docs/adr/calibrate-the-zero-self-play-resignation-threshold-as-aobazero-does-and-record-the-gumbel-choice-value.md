# AlphaZero型探索の自己対局は、最後の選択の手の値を記録して投了の判定に使い、閾値はAobaZeroの方式で自動で較正し、10局に1局は投了させずに終局まで指させる

## ステータス

承認済み。決定日は2026年11月15日。
[勝率1%で投了させるADR](archive/resign-zero-self-play-games-below-one-percent-after-bounding-false-resignations.md)を置き換える。

## コンテキスト

置き換えたADRは、Sequential Halvingが最後に残した手のQが1%を下回った側を投了させ、同じQを学習データの価値に記録すると定めた。
投了は、誤った投了（投了しなければ負けなかった対局）の割合の片側95%上限（Clopper–Pearson法）が5%以下と確かめたサイクルの次から有効にし、有効なサイクルでは20%の対局を投了させずに終局まで指させ、誤った投了の割合が5%を超えたサイクルでは投了の対局を学習から外して生成し直していた。
1%の固定の閾値と有効化の手順は、minaseが補ったものである。
2026年11月15日に学習の設定を先行実装のソースと論文で照合したところ、AlphaGo Zeroは「誤った投了の割合が5%未満になるよう閾値を自動で選び、10%の対局では投了させずに終局まで指させる」とし、AobaZeroはこれを具体的な推定の式として実装していた（[学習レシピを先行実装に揃える設計書](../plans/archived/zero-recipe-precedents.md)）。
投了させない10%の対局はAobaZeroとCrazyAraに共通し、KataGoとGumbel dlshogiは投了を使わない。
エンジンの開発者は同じ日に、投了の閾値を自動で較正し、10%の対局では投了させずに終局まで指させると決めた。

教師データに記録する価値は、dlshogiとAobaZeroのどちらも、確定した勝ちを1、確定した負けを0とする（DeepLearningShogi、コミットa9e7e5fの`selfplay/self_play.cpp`の`best_wp`、AobaZero、コミット5eb9441の`src/usi-engine/bona/ysszero.cpp`の`best_v01`）。
AobaZeroは、序盤の抽選の前に選んだ最良の子の値を記録する。
置き換えたADRのQは確定した勝敗で上書きしないので、勝ちが確定した手の値が投了の閾値を下回ることがあった。

## 決定

各局面で、Gumbel AlphaZeroの最後の選択の手eの値u(e)を、教師データに記録する価値と、投了の判定に使う値vの両方に使う。
u(e)は、eの先が手番側の勝ちに確定していれば1、負けに確定していれば0とする。
勝敗が確定していなければ、eが訪問済みならその平均価値Qとし、未訪問ならGumbel AlphaZeroの方式で未訪問の手に与える混合価値とする。
序盤の30手で訪問回数による抽選が実際に指す手を決めても、記録する価値とvはeの値とする（[序盤の抽選のADR](start-zero-self-play-from-the-initial-position-and-sample-the-first-30-moves-by-root-visit-counts.md)）。

投了の較正は、AobaZeroの方式（コミット5eb9441の`server.cfg`と`src/server/datakeep.cpp`の`EMAKeep`）を写す。
サイクルの中で1から数えた対局番号gについて、(g−1)を10で割った余りが0の対局は投了させずに終局まで指させる。
それ以外の対局では、初期局面からの手数pが10以上の局面で、vが閾値θより小さく、かつ根の部分木に、同一局面の反復の規則を近似して打ち切った節点がなければ、手番側を投了させる。
θを求めるため、64個の候補t_u＝0.005×(u＋1)（u＝0〜63）ごとに、投了させなかった対局のうち勝った側のvが一度でもt_u以下になった割合の指数移動平均e_u（初期値0.10、分母5,000、つまり1局あたりの重み1/5,000）を求める。
e_uが0.05を超える最小のuをkとしてθ＝0.005×kとし、どのe_uも0.05を超えなければθ＝0.32とする。
引き分けの対局では、勝った側のvの代わりに、両者のvの最小値のうち小さいほうで判定する。
AobaZeroは対局が1局終わるたびに閾値を配り直すが、minaseはサイクルの中で閾値を固定する。
サイクルcの閾値は、サイクル1からc−1までに採用した対局のうち投了させなかったものを、サイクルの順、サイクルの中では対局番号の順に推定の更新へ適用して、実行器が求める。
推定は別のファイルに保存せず、サイクルごとに過去の生成の集計から計算し直す。

## 検討した代案

1%の固定の閾値、Clopper–Pearson法による有効化、20%の対局を投了させずに終局まで指させる設定、および誤った投了の多いサイクルの生成し直しを保つ案は採らなかった。
どれもminaseが補った値と手順であり、チェスと将棋のエンジンに先例がないからである。

KataGoとGumbel dlshogiのように投了を使わない案は採らなかった。
エンジンの開発者が、AlphaGo Zeroの記述とAobaZeroの実装による自動の較正を選んだからである。

較正の推定をサイクルをまたいで状態のファイルに保存する案は採らなかった。
推定は記録した集計から決まる関数なので、計算し直せば中断と再開で同じ対局を2回取り込む心配がなく、別の状態を照合する手順も要らないからである。

閾値の判定に、置き換えたADRと同じく最後に選んだ手が訪問済みであることを求める案は採らなかった。
AobaZeroの方式にない条件だからである。
確定していない最後の選択の手が未訪問になるのは、訪問した候補がすべて負けに確定し、最後の選択がそれらを除いた場合である。

## 結果

最初のサイクルはすべてのe_uが0.10なのでθは0になり、投了は起きない。
最も小さい候補t_0で誤りが1度も起きなければ、e_0が0.05以下になるのは投了させなかった対局が3,466局たまった後であり、1サイクル約2,250局なら約15サイクルの後になる（推論）。
pが0〜9の局面で投了しないことは、AobaZeroの「開始局面から10手を超えたら投了を許す」条件（同じコミットの`src/autousi/play.cpp`）と同じである。
投了した対局も、ほかの対局と同じ教師データのファイルに書いて学習に使う。
生成器は、投了させなかった対局の対局番号、結果、および両者のvの最小値を、塊（一定数の対局をまとめた生成の単位）ごとの集計に記録し、実行器が閾値を求めてサイクルの記録に残す。
実装は`crates/minase/src/bin/minase/zero_selfplay/game.rs`と、実行器の較正の`tools/train/zero/minase_zero/rl.py`にある。

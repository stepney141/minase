# 探索の起動と停止を対局状態機械に入れず、プロトコルの各モジュールが直接呼ぶ

## ステータス

承認済み。決定日は2026年8月14日。

## コンテキスト

[プロトコル層](../plans/protocol-layer.md)は、エンジン本体を標準入出力から切り離し、プロトコルに依存しない状態機械`Engine`に、コマンド`EngineCommand`と応答`EngineReply`だけを扱わせる構造を採った。
この構造は、Rust製のチェスエンジンRusticの通信設計に倣ったものである（[プロトコル層の参考資料](../plans/protocol-layer.md#参考資料)）。
プロトコル層の時点では探索がなかったので、入出力は受信順に1行ずつ処理する同期の実装とした。
[ブラウザGUI向けUSI照会](../plans/browser-gui.md)は、読み取り専用の照会`moves`と`state`のために列挙子を加えず、USIのモジュールが`Engine`を直接読む整理を採った。
[外部対局接続](../plans/engine-connectivity.md)では、探索の起動、停止、および結果の受領をどこに置くかを決める必要が生じた。
探索が返した手の扱いは、USIとCECPで異なる。
USIでは`go infinite`と先読みの探索が`bestmove`を保留し、CECPでは探索の手をエンジン自身が対局へ適用して`move`行で送る。

## 決定

`EngineCommand`と`EngineReply`は対局状態を変える操作の境界に保ち、探索のための列挙子を加えない。
探索の起動、停止、結果の受領、および探索中に届いた入力の扱いは、USIとCECPのモジュールが探索の呼び出し境界を直接使って行う。
実行ファイルは標準入力を専用のスレッドで読み、各モジュールの`run_channel`が入力と探索の通知を1つのループで処理する。

## 検討した代案

探索の開始と停止、思考情報、および着手を`EngineCommand`と`EngineReply`の列挙子にする案は、結果の保留と着手の適用がプロトコルごとに異なり、状態機械がプロトコルごとの分岐を持つことになるので採らなかった。
探索のない段階で、入力と出力のスレッドを先に用意する案は、用途のない機構を置くことになるので採らなかった。

## 結果

CECPのGUIは着手を1手ずつ送り全着手列を再送しないので、CECPだけが探索の手を`EngineCommand::ApplyMove`で現局へ適用する。
USIで探索の手を適用しない理由は、[USI経路では探索の手を対局へ適用せず、局面の同期に失敗した後は着手を返さない](keep-searched-moves-out-of-the-usi-game.md)にある。
テストは同じ処理を逐次に進める`Protocol::run`を使うので、標準入力のスレッドと`run_channel`の経路は台本テストでは覆えない。
この経路を変えたときは、実バイナリで、時計つきの`go`と`stop`、`go infinite`と`stop`、および探索中の`quit`を確かめる必要がある。

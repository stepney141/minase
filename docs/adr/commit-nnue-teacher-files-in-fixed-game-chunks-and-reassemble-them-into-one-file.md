# NNUEの教師ファイルは、対局数で決めた塊ごとに確定させ、全塊がそろったら1つのファイルへ組み直す

## ステータス

承認済み。決定日は2026年11月14日。

## コンテキスト

NNUEの教師は、生成器`minase data selfplay generate`が自己対局から作る。
1回の学習に使う教師（1世代の教師）は37個の教師ファイルからなり、教師ファイル1つは、基本シードと対局番号1〜7,500で決まる対局のうち、手数の上限までに終局したものを収めたMNSDファイルである。
これまでの生成器は、全局を書き終えてからMNSDヘッダの対局数と項目数を確定させていたので、生成の途中で計算機が止まると、生成中の教師ファイルを最初から作り直す必要があった。

教師生成の計算料金は、いつ止められてもよい代わりに安い計算機を使えば下げられる見込みがある（[GCPでのNNUE教師生成の費用の調査](../research/nnue-teacher-gcp-cost.md)）。
同じ調査が例にした30 vCPUの機械では、教師ファイル1つに約135分かかると見込まれ、止まる間隔がこれより短いと教師ファイルは完成しない。
そうした計算機での料金は、止まる頻度と止まるたびに失う量で決まるので、中断に強い生成器がなければ測ることもできない。

学習器と、生成から学習までを順に動かすスクリプト`scripts/vast/generation_chain.py`（以下、生成チェーン）は、教師ファイルを単位として扱う。
学習器は、乱数の序盤から始めた自己対局のファイルどうしでシードが重なると入力を拒み、学習器の`--train-subsample`は局面の抽出にファイルの番号を使う。
対局を訓練用と検証用に分ける割り振りも、シードと対局番号で決まる。

AlphaZero型探索の自己対局の生成器`minase data zero-selfplay`は、対局数で決めた塊を一時ファイルに書いてから確定させ、同じ出力先で起動し直すと欠けた塊だけを生成する（[ADR](commit-zero-self-play-in-fixed-game-chunks-up-to-the-first-prefix-reaching-the-target-positions.md)）。
先行実装では、囲碁のKataGoが自己対局の学習データを決まった行数ごとに一時ファイルへ書いてから改名し、Stockfishのtoolsブランチが教師生成で決まった局面数ごとに書き先のファイルを切り替える。
この2つはいずれも、強制終了で止まるとまだ書き出していないデータを失い、起動し直すと新しいファイルを足すだけで、同じ位置からは再開しない。

この決定は、[NNUEの教師生成を中断の後に再開できるようにする設計書](../plans/archived/resumable-nnue-teacher-generation.md)で下した。

## 決定

生成器は、教師ファイル1つ分の対局番号を固定の局数ごとの塊に分け、塊ごとに一時ファイルへ書いてから確定させる。
同じ引数で同じ出力先を指定して起動し直すと、確定済みの塊を飛ばして未確定の塊の対局だけを指し、全塊がそろったら、件数を合計したヘッダの後に塊の本体を番号順に連結して1つの教師ファイルへ組み直す。
教師ファイルの数、基本シード、および対局番号は変えないので、組み直した教師ファイルは、同じ機械で同じバイナリと生成条件を使う限り、中断のない生成と同じバイト列になる。

出力先には、各局の内容または塊の配置を変える生成条件だけを`config.json`に保存し、起動し直したときに照合する。
照合するのは、規則セット、生成コミット、ネットのチェックサム、基本シード、総対局数、塊の局数、ノード数、ランダム着手の上限、手数上限、置換表の容量、および開始局面一覧のSHA-256であり、同時対局数とファイルのパスは照合しない。
作業ツリーに未コミットの変更があるまま始めた生成は再開させず、出力先に記録した起動か今回の起動のどちらかに未コミットの変更があれば、確定済みの塊がある出力先での起動を拒否する。

## 検討した代案

未完成の教師ファイルへ追記して再開する案は採らなかった。
ヘッダの件数を途中で書き戻す処理、書きかけの末尾を切り詰める処理、およびファイルから復元できない統計を別に保存する仕組みが要るからである。
復元できない統計は、手数上限で破棄した局数、探索ノード数、ランダム着手の数などである。

教師ファイルを小さくするだけの案は採らなかった。
教師ファイルの末尾では最後の長い対局を待つ間に計算資源が遊ぶので、同じ局数を生成するのに、ファイルの数だけ遊休が増えるからである。
同じ理由で、塊を1つずつ順に生成する案も採らず、生成器のスレッドは塊をまたいで次の対局を取る。

停止の通知を受けてファイルを確定させて閉じる案は採らなかった。
GCPのSpot VMでは終了処理の猶予が最大30秒のベストエフォートであり、強制終了やホストの障害では閉じる機会がないからである。

塊を学習器へ直接渡す案は採らなかった。
学習器がシードの重なるファイルを拒み、抽出にファイルの番号を使うので、学習器の変更が要り、抽出される局面も変わるからである。
1世代の教師全体を1つのシードの通し番号にする案も、生成する対局と、訓練用と検証用の割り振りが変わるので採らなかった。

組み直しで、塊を復号して書き込み器へ1局ずつ渡し直す案は採らなかった。
書き込み器は各局を再生して検査するので、統計を求めるための全塊の復号に加えて、再生による検査と全局の書き直しがもう一度かかるからである。
MNSDの書き込み器は、ヘッダの後に各局のバイト列を順に追記し、最後にヘッダの件数を書き戻すので、件数以外のヘッダと対局の順が同じなら、連結は書き込み器の出力と同じバイト列になる。
直接連結すると書き込み器の検査を経ないので、統計を求める復号のときに、件数以外のヘッダが生成条件と一致すること、保存した対局の番号がその塊の担当範囲にあること、および保存した局数と破棄した局数の和が担当の局数になることを確かめる。

塊ごとの重複局面数を足して教師ファイルの重複局面数とする案は採らなかった。
塊をまたぐ重複を数えられないからである。
重複局面数、得点の分布、および保存した対局の除外件数は、組み直しのときに全塊を復号して教師ファイル全体から求め、塊の集計には加算できる統計だけを置く。

ネットのファイル全体のSHA-256を照合に足す案は採らなかった。
ネットはリポジトリ内の重みをバイナリに埋め込んだものなので、作業ツリーに変更がなければ生成コミットがネット全体を決めるからである。

異なる機械の間で同じ対局になることを再開の条件にする案も採らなかった。
探索には浮動小数点の計算を含む処理があり、ビルドは機械のCPUに合わせた命令を使うので、異なる機械の間で同じ対局になるとは言えない。
各局は同じ条件で指した対局であり、教師としての価値は、止まる前と同じバイト列を再現できるかには依存しない。

未コミットの変更がある状態での生成を許す引数`--allow-dirty`を廃止する案は採らなかった。
この引数は、未コミットの変種の生成の速さを測るために使われてきた。
同じコミットのまま未コミットの変更で探索を変えて再ビルドすると、生成コミットの照合を通り抜けて異なるコードの塊が1つの教師ファイルに混ざるが、この問題は再開でだけ生じるので、再開を禁じれば足りる。

再開専用の引数を設ける案は採らなかった。
初回と再開でコマンドが変わり、呼ぶ側が出力先の状態を調べなければならなくなるからである。

## 結果

1回の停止で失うのは、確定していない塊ですでに終えた対局と、実行中の対局だけになる。
学習器と生成チェーンは、教師ファイルを単位とする扱いのまま使える。
作業機での確認の結果は、[出力の一致と組み直しの時間の測定記録](../measurements/resumable-nnue-teacher-generation/resumable-nnue-teacher-generation-equivalence.md)にある。

出力先の`config.json`、確定済みの塊の集計JSON、およびそのMNSDファイルを別の機械の出力先へ写せば、同じコマンドでそこから続きを生成できる。
写した先の機械が異なる場合は、異なる機械で生成した塊が1つの教師ファイルに混ざる。
塊を生成に使う機械の外へ退避して別の機械へ復元する仕組みは、この決定には含まれず、計算機の借り先を決める設計書で定める。

生成コミットと未コミットの変更の有無は、生成器が起動のたびに作業ツリーから`git`で調べた値であり、バイナリをビルドした時点の値ではない。
このため、ソースを変えてビルドし直した後にソースだけを元へ戻して再開すると、照合を通り抜けて異なるコードの塊が混ざる。
MNSDヘッダの生成コミットも同じ方法で記録してきたので、この制約は教師ファイルの来歴にもともとあるものであり、生成は対象のコミットを固定したworktreeのバイナリで行う規則（[教訓](../lessons/pin-generation-binary-to-worktree.md)）で防ぐ。

塊の局数は生成の引数であり、変えても教師の内容は変わらない。
ただし、塊の局数は照合する条件なので、生成の途中では変えられない。
排他ロック、原子的なJSONの保存、および同期と改名の部品は`minase::datagen`に置き、`zero-selfplay`と共有する。
出力先の構成と各ファイルの欄は、`crates/minase/src/bin/minase/selfplay_gen/`のdocコメントにある。

# AlphaZero型探索の自己対局は、対局数で決めた塊ごとに確定させ、訓練局面数が目標に届いた最初の塊まででサイクルを締める

## ステータス

承認済み。決定日は2026年10月31日。

## コンテキスト

強化学習（RL）の自己対局は、Google ColabのColab機またはvast.aiとRunpodのレンタル機で生成する。
Colab機はセッションの上限時間、残高の枯渇、およびColab側の都合で、レンタル機は貸し手の都合で止まり得る（[Colab機の操作の手引き](../guides/alphazero-machines.md)）。
止まった機械で生成した結果は、作業機へ転送していなければ失われる。
借りた機械は`git archive`で作ったソースの書庫からminaseをビルドするので、リポジトリを持たない。
隣接する基本シードを使うと、1局ずれた同じ対局列ができる（[隣接する基本シードの教訓](../lessons/derive-seed-adjacent-collision.md)）。
投了の誤りを判定する割合は、サイクルの対局がすべて終わるまで決まらない（[投了のADR](resign-zero-self-play-games-below-one-percent-after-bounding-false-resignations.md)）。

2026年10月27日の[前のADR](archive/commit-zero-self-play-cycles-in-fixed-game-chunks.md)は、1サイクルの生成量を対局数で与え、決まった対局数の塊に分けて確定させると決めた。
100万局面に要る対局数は、[強化学習の実行](../plans/alphazero-rl.md)が、前のサイクルの1局あたりの訓練局面数から見積もる。
前のADRは、生成量を局面数で与える案を、塊の数が生成の結果で決まり、再開時にどの塊が欠けているかを定められなくなるとして採らなかった。

2026年10月31日に学び直した本線では、サイクル2の1局あたりの訓練局面数が14.4で、サイクル3の対局数は69,581局と見積もられた。
サイクル2のネットが3手以内の詰みをすぐには食らわなくなったので、サイクル3の対局は1局平均70手から349手に伸び、1局の訓練局面数は81.5になった。
このまま全塊を生成すると、サイクル3は目標の約5.7倍の約570万局面になり、生成に約4.4時間かかる見込みであった。
初期のサイクルほど、少ないデータでネットをこまめに更新するほうが学習が進むので、エンジンの開発者は、目標の局面数に届いたところでサイクルを締めると決めた。

先行実装も、生成の量を局面数で区切る。
dlshogiの自己対局（`selfplay/self_play.cpp`）は、量を局面数の引数`nodes`だけで受け取り、書き出した局面数が目標に届くと生成を止め、終わっていない対局は書き出さずに捨てる。
KataGoは、小規模の同期ループでは生成を対局数で区切るが、学習の量は新しく生成した局面数に比例させる。

## 決定

生成器は、総対局数の上限と塊の対局数に加えて、訓練局面数の目標を受け取る。
対局番号、各局のシード、塊の数、および各塊が担当する対局番号の範囲は、総対局数の上限と塊の対局数だけから決め、前のADRと同じく塊ごとに一時ファイルへ書いてから確定させる。
サイクルに含める塊は、塊0からkまでがすべて確定済みで、それらの訓練局面数の累計（投了で終えた対局の分を含む）が初めて目標以上になる最小のkを選び、塊0からkまでとする。
全塊を確定しても目標に届かなければ、全塊を含める。

生成器は、塊を確定するたびにこの条件を調べ、kが決まった時点で生成を止め、書きかけの塊の一時ファイルを削除する。
kより後の塊が先に確定していても、サイクルには含めず、そのファイルは削除せずに残す。
同じ出力先で起動し直したときは、確定済みの塊だけでkが決まれば推論器を作らずに集計を書き、決まらなければ欠けた塊だけを生成する。
目標は生成条件の`config.json`には入れず、サイクルの集計に記録する。

出力先には生成条件を記録し、同じ出力先で起動し直すと、条件が記録と一致する場合に限って生成を続ける。
照合する条件は各対局の内容を変えるものに限り、推論の実行プロバイダは含め、スレッド数、スレッドごとの同時対局数、およびGPUの種類は含めない。
出力先は排他的にロックし、MNSDのヘッダに書く生成コミットは起動引数で受け取る。

## 検討した代案

総対局数を与えずに、局面数だけで生成量を与える案は採らなかった。
塊の数が生成の結果で決まり、再開時にどの塊が欠けているかを定められなくなるからである。
本決定では、塊の配置は総対局数の上限で先に決まるので、局面数の目標は、決まった塊の列のどこで締めるかだけを決める。
kは確定済みの塊の集計だけから求まるので、止まった機械を替えて再開しても同じ塊の列になる。

止めた時点で確定していた塊をすべて含める案は採らなかった。
塊は番号順に確定するとは限らず、止めた時点で確定している塊の集合は、スレッドの進み方と推論の速さで変わるからである。
本線のサイクル2でも、塊2が塊1より先に確定した。

dlshogiのように、局面数が目標に届いた時点で終わっていない対局を捨てる案は採らなかった。
止めた時点で終わっているのは短い対局に偏るので、残るデータも短い対局に偏るからである。
塊の境目で締めれば、含める対局は対局番号の範囲だけで決まり、対局の長さに左右されない。

判定に、誤った投了で終えた対局を除いた後の訓練局面数`training_positions`を使う案は採らなかった。
除外するかどうかはサイクルに含める塊全体の誤りの割合で決まるので、含める塊を決める判定が、含める塊に依存してしまうからである。

目標を`config.json`に入れて再開時に照合する案は採らなかった。
目標は各対局の内容を変えず、どの塊までをサイクルとするかだけを変えるからである。

投了で終えた対局を他の対局と同じファイルに書き、誤った投了の割合が上限を超えたら確定済みの塊を書き換える案と、生成コミットを`git rev-parse HEAD`で求める案は、前のADRと同じ理由で採らなかった。
確定した塊を書き換えると転送済みのファイルと検査和が食い違い、また借りた機械にはリポジトリがないからである。

## 結果

1サイクルの訓練局面数が目標を超える分は、最後に含めた塊1つの局面数より小さい。
1サイクルを約20個の塊に分けているので、超過は見積もりどおりの対局の長さなら目標の約5%以内である。
総対局数の上限は、対局が前のサイクルより短くなったときに働き、そのサイクルは目標に届かずに終わる。
kより後に確定した塊の生成は無駄になるが、その対局は対局番号の範囲としてシードの台帳に登録済みなので、別の生成と重ならない。
サイクル3は、この決定の前の生成器で塊0から6までを生成した後に止めたので、新しい生成器で塊0から3までの113.5万局面として締めた。
出力先の構成と各ファイルの欄は、`crates/minase/src/bin/minase/zero_selfplay/`のdocコメントにある。

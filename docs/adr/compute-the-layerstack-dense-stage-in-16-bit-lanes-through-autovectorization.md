# A型の後段を16ビットのレーンで計算し、SIMD命令は自動ベクトル化だけで得る

## ステータス

承認済み。決定日は2026年11月27日。

## コンテキスト

A型のNNUEの後段（第1層の累算値から評価値を計算する、要素積、16出力のL1、32出力のL2、および1出力の層）は、[第3期の高速化の試作](../measurements/adhoc/nnue-dense-safe-vectorization-20261127.md)の時点で`bench`の深さ16の探索時間の17.7%を占めていた。
当時の後段は、要素積の一部を添字の範囲検査つきのスカラーのループで計算し、L1とL2では8ビットの重みと入力を32ビットへ広げてから掛けていた。
エンジンとライブラリのクレートは`unsafe`を使わない（[unsafeのADR](allow-unsafe-only-in-the-trainer-gpu-code.md)）。`#[target_feature]`を付けた関数は`unsafe`なしでは呼べず、標準ライブラリの`std::simd`は安定版にない。
エンジンの開発者は、[第3期の高速化の設計書](../plans/archived/movegen-speedup-3.md)で、後段を「要素積とL1」と「L2と出力層」の2つの測定単位に分け、固定の仕事量での探索の結果を変えないことを確かめたうえで、サイクル数の対比較で採否を決めた。

要素積とL1の単位は、`bench`の深さ16で速度比1.061倍、教師生成2局で1.060倍だった（[測定記録](../measurements/movegen-speedup-3/movegen-speedup-3-stage1-pair-l1.md)）。L2と出力層の単位は、その上でさらに1.034倍と1.036倍だった（[測定記録](../measurements/movegen-speedup-3/movegen-speedup-3-stage1-l2.md)）。
採用後の後段は、探索時間の約9.2%を占める（[段階5の診断](../measurements/movegen-speedup-3/movegen-speedup-3-stage5-diagnosis.md)）。

## 決定

後段は標準のRustの反復子と配列で書き、LLVMの自動ベクトル化でSIMD命令を得る。
要素積は16ビットで求め、L1は8ビットの重みを読み込み時に16ビットへ広げた行優先の複製との積和にし、L2は重みを入力ごとに32出力を並べた16ビットの複製へ組み替えて、入力2つ分の積の和を16ビットのまま求めてから32ビットの和へ足す。
元の8ビットの重みはネットのファイルの表現の正本として残し、複製は検査を通った後の値から1回だけ作る。

## 検討した代案

`unsafe`の組み込み関数でAVX-VNNIの`vpdpbusd`を使う版は、試作で`bench`の毎秒ノード数を1.185倍にしたが、エンジンで`unsafe`を使わない方針に反するので採らない。
safe_arch、wide、pulp、fearless_simd、およびarchmageは、利用側に`unsafe`を書かずに使えるが、クレートの内部またはマクロの展開に`unsafe`を持つので採らない。

Stockfishの、8ビットの重みを入力4つずつの塊ごとに全出力ぶん並べる配置は、組み込み関数で4バイトの入力を全レーンへ複製する経路のための配置であり、自動ベクトル化ではマイクロベンチマークで現行より遅かったので採らない。0の入力を飛ばす書き方も、飛ばさない16ビットの書き方に及ばなかった（[試作の記録](../measurements/adhoc/nnue-dense-safe-vectorization-20261127.md)）。

L1を、隣接する2つの積の和を固定の個数ずつ作る形にして256ビット幅の積和を得る変種は、3通りの書き方のどれでも、主ループが32個の積を256ビット幅の積和2命令で処理する形にならず、後段の命令数も650から677〜736に増えたので採らない。L2の対の積を32ビットの積和の形で足す変種も、L2の命令数が増えたので採らない（[段階5の診断](../measurements/movegen-speedup-3/movegen-speedup-3-stage5-diagnosis.md)）。

L1の15出力の2乗の活性化を、絶対値を8,160で制限してから`i32`のレーンで計算する変種は、後段の命令数を0.8%減らしたが、サイクル数の対比較で速くならなかったので採らない（[測定記録](../measurements/movegen-speedup-3/movegen-speedup-3-stage5-activation.md)）。

## 結果

後段の速さはコンパイラの自動ベクトル化に依存する。rustcでは、版の更新で自動ベクトル化が外れた例（rust-lang/rust#142519、#166207）がある。
ビルドに使うrustcとLLVMの版が変わったときは、同じコミットを新旧のコンパイラでビルドし、後段の型、ループ、またはビルド設定を変えたときは、親と候補を同じコンパイラでビルドして、[第3期の高速化の準備の記録](../measurements/movegen-speedup-3/movegen-speedup-3-baseline.md)の対比較の手順で比べ直す。
命令名ごとの出現数は単体テストやCIの合否にしない。CIは`-C target-cpu=x86-64`でビルドするので測定機と命令の集合が違い、より良い命令が出るようになれば出現数が減るからである。
入力の配列は2,048バイトを0で埋めており、標準のネットが使うのはその半分である。`unsafe`なしで使う長さだけを埋める方法は見つかっていない。
HalfKP_vmの後段`SimpleNetwork::out`は書き換えていない。HalfKP_vmのネットで教師を作る計画を立てるときに、その負荷で後段の時間を測ってから、同じ書き直しを試すかを決める。

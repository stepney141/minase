# 探索統計を既定で無効のフィーチャ`search-stats`で数え、固定の項目だけを常設する

## ステータス

承認済み。決定日は2026年9月27日。

## コンテキスト

探索の改良を調べるときの回数の計測は、測定のたびにmasterへ入れない一時的な計測コードとして書き直されてきた。
計測コードをパッチとして残した`diagnostic.patch`を持つ測定記録のディレクトリは、2026年9月27日の時点で9件あった。
その多くは特定の改良の発動率を数えたものだが、ノードの種類や置換表の一致率のように、どの改良の前後比較にも使う回数もあった。
回数を数えるカウンタは探索の最内ループに置くので、既定のビルドに含めると探索速度が変わる。
共有のカウンタは、複数のワーカーの探索速度を歪める（[教訓](../lessons/shared-probe-counter-distorts-threads.md)）。
この判断は[デバッグ機能の整備](../plans/debugging-tools.md)で下した。

## 決定

探索統計は、既定では無効のCargoフィーチャ`search-stats`を有効にしたビルドだけで、ワーカーごとに数えて探索の後に合算する。
常設する項目は、ノードの種類、置換表、βカット、および最善手の順位の4群に限り、出力は`minase dev bench`だけが行ってUSIの`info`行には出さない。
各項目の加算の条件は`SearchStats`の各欄のdocコメントにある。

## 検討した代案

カウンタを既定のビルドに含める案は、対局に使うバイナリの探索速度を変えるので採らなかった。
Stockfishの`dbg_hit_on`のような汎用の集計関数を置く案は、Stockfish自身のソースにも呼び出し箇所がなく（[調査メモ](../research/engine-debugging-survey.md)）、必要になるまで書かない方針に反するので採らなかった。

## 結果

フィーチャを有効にしないビルドの探索木とノード数は変わらないので、このフィーチャの追加に棋力測定は要らなかった。
改良の採否に使う速度はフィーチャなしのバイナリで測り、フィーチャを有効にした実行からは回数の比だけを読む。
固定の項目にない回数は、項目の宣言へ項目を1つ足すパッチで数え、パッチは測定記録に残してmasterへは入れない（[デバッグの手引き](../guides/debugging.md)の「探索」）。

# 上位N手の読み筋を出すUSIオプション`MultiPV`は、USIの層が宣言して保持し、値が2以上のときだけ`info`行に順位を付ける

## ステータス

承認済み。決定日は2026年11月17日。

## コンテキスト

minaseは、探索が最善と見た手とそれに続く双方の応手の列である読み筋（主変化、PV）を1本だけ出していた。
対局や棋譜の検討では、最善手に次ぐ手がどれだけ劣るかを知りたい。
minaseは、評価関数NNUEで読むαβ探索と、方策と価値を出すネットで木を広げるAlphaZero型のモンテカルロ木探索PV-MCTSの2つの探索方式を持つ。
NNUEやPV-MCTSのネットが特定の局面で候補手をどう順位づけるかを診断するときも、上位N手の評価値の並びが要る。
将棋エンジンのやねうら王とdlshogi、およびチェスエンジンのStockfishは、上位N手の読み筋を同時に出す機能MultiPV（multiple principal variations）を備える。

USIの原典は予約名として`USI_MultiPV`を定めるが、やねうら王、ふかうら王（dlshogiのPV-MCTSをやねうら王の枠組みへ移したエンジン）、およびdlshogiは、どれも`MultiPV`の名前で宣言する。
USIの原典は、複数の読み筋を出すときは最善の読み筋へ`multipv 1`を付け、k本をk行でまとめて送ると定め、1本だけの場合に`multipv`を求めていない。
対局ハーネスは、`bestmove`の前の最後の評価値つきの`info`行の値を、その手の評価値として記録していた。
判断の詳細と先行実装の行番号は、[MultiPVの設計書](../plans/archived/multipv.md)の「設計判断」の節にある。

## 決定

USIの層がspin型のオプション`MultiPV`（既定値1、最小1、最大35,856）を、探索の方式によらず宣言して保持し、`go`のときに探索の入力`SearchSnapshot`へ渡す（2026年11月17日のエンジンの開発者の決定）。
最大値の35,856は、PV-MCTSのネットの方策の要素数であり、合法手から方策の要素への写像が単射であることを試験で確かめてあるので、1局面の合法手の数の上界になる。
探索が読む本数Nは、設定値と、探索を始める局面（根）の候補手の数の小さい方とする。
`info`行の`depth`の直後に`multipv <k>`を付けるかどうかはNではなく設定値だけで決め、設定値が2以上のときだけ付ける。
`bestmove`は1本目の読み筋の1手目、予想手は1本目の読み筋の2手目とし、投了は1本目の値で判定する。
探索からUSIやCECPの通信層へ渡すイベント`SearchEvent`は、読み筋を順位の順に並べた列`lines`を持つ。
対局ハーネスは、`multipv`を含まない行と`multipv 1`の行の評価値だけを記録する。

## 検討した代案

原典の予約名`USI_MultiPV`で宣言する案は採らなかった。
GUIが送るオプション名はエンジンの宣言に従うので、実績のあるエンジンと同じ名前にすれば、それらのエンジン向けの検討の設定をそのまま使える。
2つの名前を両方とも宣言する案は、同じ設定に2つの入口ができ、後に送った方で値が決まるので採らなかった。

最大値を256（チェスの合法手の上界を使うStockfish）、600（将棋の合法手の最大数593に余裕を加えたやねうら王）、または593（dlshogi）のような値にする案は採らなかった。
先行実装も最大値を合法手の数の上界から決めており、中将棋の合法手の最大数はまだ証明されていないので、証明済みの上界である方策の要素数を使う。

2つの探索方式にそれぞれオプションを宣言させる案は採らなかった。
探索が返す読み筋が1本だけのとき、設定値が1なのか根の候補手が1つしかないのかは、読み筋の本数からは分からない。
USIの層が設定値を知っていれば、根の候補手が1つしかなくても設定値が2以上なら`multipv 1`を付けられるが、探索器に宣言させると、USIの層が出力の形を決めるために探索器へ設定値を問い合わせることになる。
引き分けの評価値`DrawValueBlack`と`DrawValueWhite`も、USIの層が保持して`SearchSnapshot`で探索へ渡している。

Stockfishとやねうら王のように、`MultiPV`の値によらず`multipv 1`を付ける案は採らなかった。
既定値でも出力が変わり、行の文字列を照合しているUSIの層の試験の期待も書き換えることになる。
dlshogiも、`MultiPV`が1のときは`multipv`を付けない。

`bestmove`のために最善手を読み筋とは別に保持して返す案は採らなかった。
1本目の読み筋の1手目は探索が選んだ最善手と常に一致するので、別に保持すると同じ値の入口が2つになる。

対局ハーネスが最後の評価値つきの行を記録する規則を保つ案は採らなかった。
`MultiPV`が2以上のエンジンでは、N番手の値を最善手の評価値として記録してしまう。
原典が最善の読み筋へ`multipv 1`を付けると定めるので、新しい規則はminase以外のエンジンにも当てはまる。

## 結果

既定値1では、`usi`への応答に`MultiPV`の宣言が1行加わることを除き、探索も出力も変わらない（[イベントの変更の一致の記録](../measurements/multipv/multipv-events-default-equivalence.md)）。
棋力測定は既定値で行うので、ハーネスの記録の規則の変更は測定の記録を変えない。
`SearchEvent`のフィールドを変えたので、ライブラリの公開APIの互換性を壊す変更として扱った。
xboard系の通信規約CECPの層は探索のオプションを宣言せず、最善手だけを使うので、CECPでの探索は1本のまま動く。
自己対局と教師の生成器も同期版の探索を直接呼び、Nは常に1である。
開発用GUIで複数の読み筋を表示する変更は、別リポジトリ`minase-gui`で別に計画する。
各探索方式がN本をどう求めるかは、[αβ探索のMultiPVのADR](search-alphabeta-multipv-by-repeating-the-root-search-and-keep-only-complete-iterations.md)と[PV-MCTSのMultiPVのADR](rank-pv-mcts-root-edges-by-the-best-move-rule-for-multipv-and-leave-unvisited-edges-unscored.md)にある。

# 役目を終えたAlphaZero型探索の測定用の道具を削除し、1サイクルの見積もりは実際に1サイクル回して行う

## ステータス

承認済み。決定日は2026年11月2日。

## コンテキスト

`tools/train/zero/feasibility/`は、[実現性の実測](../measurements/alphazero-environment/alphazero-feasibility.md)のために作った独立のcrateであり、その後のマイルストーンで道具が追加された。
実装がそろった段階で各道具を調べると、現行のコードと合わないか、役目を終えたものが大半であった。

推論の速さを測る`trt_bench`は入力を95面に固定し、現行の159面のネットと合わない。
探索の速さを測る`sim_cost`は本番の駆動部`Driver`を使わず、独自の探索を測っている。
学習の速さを測る`train_bench.py`は現行の学習器が学ぶ補助目標の計算を通らない。
`make_nets.py`と`nn_torch_reference.py`の役目は、`minase_zero init`と`minase_zero fixture-eval`が担っている。
`batch_probe`、`driver_cost`、および`mate_cost`は、それぞれの測定の目的を果たしている。
毎サイクル使うのは`teacher_stats`だけであり、これは独立のcrateにあるので、強化学習の前に別のビルドが必要であった。

[借りる機械の操作の手引き](../guides/alphazero-machines.md)は、これらの道具で処理ごとの速さを測り、式で1サイクルの時間を見積もる手順を定めていた。
同じ手引きは、この見積もりに並列化の効率、推論との受け渡し、および記録の書き込みが含まれないことを認め、確定の判定を試走に委ねていた。
[学習技法の導入の試走](../measurements/alphazero-restart-techniques/alphazero-restart-techniques-trial.md)では、学習の更新が見積もりの約1.9倍の1,063秒かかった。

エンジンの開発者は2026年11月2日に、内容が古い道具は残さないと決めた。

## 決定

`tools/train/zero/feasibility/`と`tools/train/zero/nn_torch_reference.py`を削除する。
`teacher_stats`だけを`minase data teacher-stats`へ移し、`minase_zero run-cycles`は`--minase`で受けた実行ファイルからこれを呼ぶ。
1サイクルの所要時間とColabの計算単位（compute unit、CU）の見積もりは、まだ測っていない機械の構成で`minase_zero run-cycles`の1サイクルを実際に回し、その時間と料金から求める。

## 検討した代案

名前を`measure`などへ改めて残す案は採らなかった。
残してもその道具を使う予定がなく、残すと開発者が現行の手順と誤解し、保守の対象も増える。
必要になれば、測定記録が示すコミットから取り出せる。

`teacher_stats`を測定用のcrateに残す案は採らなかった。
毎サイクル使う道具の置き場所として合わず、古いビルドや未ビルドのまま機械を借りた後で初めて失敗が判明する原因になった。

`teacher_stats`をPythonで書き直す案は採らなかった。
教師データの形式MNSDを読む実装が増える。

処理ごとの測定と式の手順だけを新しいネットに合わせて保守する案は採らなかった。
式に含まれない要素が大きく、判定には結局試走が要るので、保守の費用に見合わない。

## 結果

毎サイクルの集計は`minase`の実行ファイルだけで行え、学習の前に別のビルドが必要ない。
実行器は学習を始める前に、作業機の実行ファイルのサブコマンドと、借りた機械に展開したソースの固定局面集を確かめる。
見積もりには実際に機械を借りる費用がかかるが、その1サイクルは本線とは別の系列（`--cycles-dir`で分けた出力）の実データであり、処理ごとの測定よりも判定に直接使える。
削除した道具を呼ぶ過去の測定スクリプトは、測定に使ったコミットのソースで動く。
推論の速さの比較のように部品の速さが要る問いが再び現れたら、そのときの現行のネットと駆動部に合わせて道具を作り直す。

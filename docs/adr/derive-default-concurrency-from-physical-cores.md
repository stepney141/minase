# 同時対局数の既定値を物理コア数から計算する

## ステータス

承認済み。決定日は2026年9月1日。

## コンテキスト

[棋力測定の段階ゲート](../plans/archived/match-staged-gate.md)より前は、測定者が手順書にある手計算の規則に従って`--concurrency`を毎回指定していた。
その規則は、同時に動く探索スレッドの合計を物理コア数以下に抑え、OSとハーネスのために1コア以上を残すというものだった。
手順書に測定機ごとの数値が残り、別の測定機では書き換える必要があった。
旧案は、同時対局数8、12、16、19の4点を各100ペアで掃引して既定値を決める計画を持っていた。
時間制御の対局では、CPUの競合が探索量を変えるので、同時対局数は対局の条件の一部である。

## 決定

`--concurrency`を省いた場合、`minase match run`は物理コア数から1を引き、候補と基準の`Threads`の大きい方で割った商を同時対局数とし、先読みを対局条件に含める測定では両エンジンが同時に探索するので除数を2倍にする。
物理コア数またはどちらかの`Threads`が取得できない場合と、商が1未満になる場合は、既定値を推測せずにエラーで終了する。
算出または指定された値は`manifest.json`に記録し、再開ではこの値を使い、計算の詳細は`default_concurrency`のdocコメントに従う。

## 検討した代案

4点の掃引で既定値を決める案は、見込める差が回転率の数%にとどまる一方で、測定と判定基準の文書化が重いので廃止した。
1コアを残さずに物理コア数まで対局させる案は、利得が小さいうえに時計の管理が遅れて時間切れが起こる危険を増やすので、[棋力測定の所要時間削減](../plans/archived/match-cost-reduction.md)で採らなかった。
取得できない値に既定値を補う案は、記録と異なる構成で黙って対局することになるので採らなかった。

## 結果

物理20コアの測定機で両エンジンが`Threads=1`なら、同時対局数は19になる。
`Threads`を報告しないCECPエンジンとの測定では、`--concurrency`を明示する必要がある。
計算は物理コアだけを見るので、置換表容量が大きい測定では、測定者がメモリ量から同時対局数を下げて明示する（[HaChuとの条件格子測定](../plans/archived/hachu-condition-grid.md)）。
再開の前後で同時対局数を変えないので、物理コア数の少ない測定機で再開すると同時対局数がコア数を超えることがあり、その影響は`time_forfeits`に現れる（[再開のADR](resume-from-the-manifest-and-accept-rebuilt-tuning-commits.md)）。

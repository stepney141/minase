# AlphaZero型探索のネットの入力は、手番側から見た盤の95面に駒種ごとの利きと利き数の64面を足した159面とし、履歴と左右反転による水増しを入れない

## ステータス

承認済み。決定日は2026年10月31日。
[95面の入力のADR](archive/encode-zero-network-inputs-as-95-planes-from-the-side-to-move.md)を置き換える。

## コンテキスト

AlphaZero型探索のネットの入力の定義は、対局用のMCTS、自己対局生成器、およびPythonの学習器の3者が共有する。
初版の入力は、手番側と相手側の47種類の駒の状態（成った駒を元の駒と区別した状態）の94面と、先獅子の升（直前の着手で獅子以外の駒が相手獅子を取った升、RULES.md第15条）の1面からなる95面であった。
初版は利きと利き数の面を採らなかった。
学習器のPython側で計算するには中将棋の規則の判定をPythonにも実装し直す必要があり、Rust側で計算して教師データに書くと1局面あたり数百バイト増えるからである。
dlshogiは、駒種ごとの利き14面と利き数3面が学習の短縮に有効だったと報告している（[調査](../research/alphazero-rl-training-efficiency.md)）。
学習器は既にMNSDをRustの拡張モジュールで読んでいるので、Rustの1つの関数を推論と学習の両方から呼べる。
利用者は2026年10月31日に、利きと利き数の入力面を含む9つの技法をまとめて採ると決めた。

## 決定

入力は、今までの95面（手番側から見た盤の駒の状態94面と先獅子の升1面）に、次の64面を足した159面とする。
手番側と相手側のそれぞれについて、29の駒種（動きで区別した駒の種類で、成駒は成った後の駒種）のそれぞれの駒の利きが届く升を1にする29面と、その陣営の利きの本数がそれぞれ1以上、2以上、3以上の升を1にする3面である。
利きは`Position::piece_control_with_occupancy`の疑似利きとし、走り駒の利きは最初に駒がある升まで、獅子、角鷹、および飛鷲は2段階の到達範囲を含み、味方の駒がある升も含め、獅子の捕獲の制限は判定しない。
利き数は、同じ升へ疑似利きが届く駒の数であり、`Position::attackers_to_by`の返す駒の数に一致する。
後手番の盤は、今までの95面と同じく180度回転する。
64面は`crates/minase/src/nn/control.rs`の1つの関数で作り、推論の符号化はこの関数を直接呼び、学習器は拡張モジュールを通してバッチごとに盤の配列から同じ関数を呼ぶ。
教師データには面を書かない。
履歴の面を入れないこと、反復の回数を入れないこと、および左右反転で水増ししないことは、置き換えたADRと同じ理由で変えない。

## 検討した代案

47の駒の状態ごとに利きの面を作る案は採らなかった。
同じ動きの駒（成った金将と元からの飛車など）は利きが同じなので、駒種ごとで足り、面の数も29に収まる。

利き数の面だけを足す案は採らなかった。
dlshogiが駒種ごとの利きと利き数の両方を入れており、どちらが効くかを比べない方針（技法をまとめて採る）に合わせた。

教師データに面を書く案は採らなかった。
1局面あたり64面×144升のビットで約1.2 KB増え、学習窓の転送の時間が延びるからである。

## 結果

推論と学習器の159面の一致は、Rustが書き出した固定局面集`tools/train/zero/fixtures/nn-positions.jsonl`の288局面で、Pythonの試験が全面について確かめる。
利きの面が各升で`attackers_to_by`の駒種と本数に一致することは、獅子の跳び、角鷹と飛鷲の2段階、走りの遮蔽、味方の駒、成駒、および後手番の回転を含む局面でRustの試験が確かめる。
入力の面の数が変わったので、95面のネットは使えない。
ネットのパラメータ数は、入力の畳み込みで約7万増える。
NNキャッシュの鍵が局面だけで決まることと、成り権を保留するP1、P2、P5の規則セット（RULES.md第30条）で学習するには保留の升を示す面が要ることは、置き換えたADRと同じである。
配置の詳細は`crates/minase/src/nn/encoding.rs`と`control.rs`のdocコメントにある。

# 探索内の反復検出は、対局履歴のビットフィルタを通してから線形走査で行う

## ステータス

承認済み。決定日は2026年11月5日。

## コンテキスト

探索は着手を適用するたびに、子局面のキーが探索経路または対局履歴に現れているかを調べる。
[以前のADR](archive/check-repetition-by-linear-scan.md)では、対局履歴を`HashSet`へ変換する案に効果がなかったので線形走査を選び、再提案するときは現行の評価関数と長い履歴で測り直すことを条件にしていた。
[教師生成の高速化](../plans/teacher-generation-speedup.md)の完全な対局のプロファイルでは、この走査が全サイクルの約5%を占めた。
呼び出しは報告ノードあたり0.73回で、走査する履歴は平均342件であり、対局が長いほど費用が増える。
教師生成の対局は最長4,000手まで続く。

## 決定

探索開始時に対局履歴のキーの下位15ビットから4 KiBのビットフィルタを作り、全ワーカーで共有する。
探索経路に一致がなく、フィルタのビットが立っていない場合は、対局履歴を走査しない。
ビットが立っている場合は従来どおり線形走査で最も新しい出現を探すので、衝突があっても結果は変わらない。
R2とR3の禁止手の判定は出現回数を数えるので、フィルタを使わず従来の走査のままとする。

## 検討した代案

`HashSet`は照会ごとにハッシュの計算とメモリの読み出しが必要であり、大半の照会が不一致である用途ではビットフィルタより重い。
走査そのものを残すのは、衝突の処理を複雑にせず、最も新しい出現を返す契約をそのまま保てるからである。
出現回数を差分更新する案は、以前のADRのとおりNPSを下げたので採らない。

## 結果

[測定記録](../measurements/teacher-generation-speedup/teacher-generation-speedup-engine.md)のとおり、200手で打ち切る比較でも命令数が1.49%減り、探索結果は変わらない。
完全な対局では、`find_repetition`の包含サイクルが全体の4.7%から0.5%へ減った。
1回の探索につき4 KiBの初期化と履歴の長さに比例するキーの登録が増えるが、1探索2万ノードの処理量に対して無視できる。

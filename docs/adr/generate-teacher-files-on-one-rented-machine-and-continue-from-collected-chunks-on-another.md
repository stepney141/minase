# NNUEの教師ファイルは、作業機の制御スクリプトが借りた1台に生成させ、止まったら回収済みの塊から別の機械で続ける

## ステータス

承認済み。決定日は2026年11月14日。

## コンテキスト

NNUEの教師は、生成器`minase data selfplay generate`が自己対局から作る。
生成器は、7,500局の教師ファイル1つを250局ずつの塊に分けて確定させ、確定済みの塊と生成条件の`config.json`を別の機械の出力先へ写せば、同じコマンドで続きを生成できる（[ADR](commit-nnue-teacher-files-in-fixed-game-chunks-and-reassemble-them-into-one-file.md)）。
教師生成は、計算機を時間単位で借りられる市場vast.aiで、生成から学習までを順に動かす連続生成スクリプト`scripts/vast/generation_chain.py`が、止められない借り方（オンデマンド）の機械を1台借りて行ってきた。
vast.aiの中断可能インスタンスは、入札で安く借りる代わりに、より高い入札が入るといつでも止められる。
止まったときに続きを別の機械で生成する仕組みがなければ、中断可能インスタンスでの生成は、止まるたびに教師ファイルを作り直すことになる。

[中断可能な計算機での教師生成の設計書](../plans/archived/interruptible-teacher-generation.md)では、手元の作業機で動く制御スクリプトを作り、[候補の機械の速さ](../measurements/interruptible-teacher-generation/interruptible-teacher-generation-candidates.md)を測って借りる機種を決め、[復旧試験](../measurements/interruptible-teacher-generation/interruptible-teacher-generation-recovery.md)と[2つの借り方の比較](../measurements/interruptible-teacher-generation/interruptible-teacher-generation-trial.md)を行った。

## 決定

生成専用の制御スクリプト`scripts/vast/teacher_generation.py`が、借りた生成機1台で、連続生成スクリプトと同じ作業プロセス`scripts/vast/generation_worker.py`を改修せずに動かして教師ファイルを生成させ、確定した塊と教師ファイルを60秒おきにSSHのrsyncで作業機へ回収する。
生成機が止まったと判定したら、旧機の削除を確かめてから別の機械を借り、塊のMNSDファイルと集計JSONの両方がそろった塊と`config.json`を送って、同じ教師ファイルの続きを生成させる。
出品は、借りた後のcpusetとcgroupの検査に通るEPYC 7B13かEPYC 9654の256スレッド以上の機械から、時間単価を見込みの探索速度で割った値で選び、同時対局数はcpusetの論理スレッド数とする。

## 検討した代案

連続生成スクリプトに機械の移行を加える案は採らなかった。
連続生成スクリプトは、生成、学習、補正、および世代のコミットを1つの再開の手順で扱っており、移行を加えると扱う状態の組み合わせが大きく増えるからである。
制御スクリプトは、受け入れた教師ファイルを連続生成スクリプトが読むのと同じ配置に置くので、学習には、連続生成スクリプトで作業機を使って学習する設定をそのまま使える。

作業プロセスは、教師ファイルを完成させて公開すると、生成機の上の塊を消す。
この作業プロセスを変えて、公開した教師ファイルの塊を作業機が受け取るまで生成機に残す案は採らなかった。
公開の後に機械が止まっても、作業機に回収済みの塊から再開できるので、塊を残しても失う量は減らないからである。

生成機からクラウドのストレージへ押し出す案は採らなかった。
認証情報を借りた機械へ置く必要があり、vast.aiのストレージとの同期機能は信頼済みのデータセンターに限られるからである。
停止中の機械からも取り出せる`vastai copy`は、貸し手の機械によって失敗することが、探索の係数を対局の結果から調整する手法SPSAの[手引き](../guides/spsa.md)に記録されているので使わず、停止した機械の未回収の塊は捨てる。

止まった機械の自動の再開を待つ案は採らなかった。
中断可能インスタンスは優先順位が戻ると自動で再開し、待ち時間は文書にないので、停止のまま残すと2台が同じ教師ファイルを生成して二重に課金されるからである。
復旧試験では、制御スクリプトが停止を1分49秒で検知し、6分27秒後に別の機械で生成を再開した。

確定した塊の数やログの更新で停滞を判定する案は採らなかった。
長い対局とビルドの間は塊もログも増えないので、正常な生成を停滞と誤認するからである。
停止の判定では、インスタンスの状態の照会、SSH、回収の成否、作業プロセスの生存、およびそのセッションのCPU時間の条件を、決めた順に調べる。
照会が認証の失効や通信の失敗で失敗したときは、稼働中の機械を残したまま別の機械を借りないように、新しい機械を借りずに止まる。
照会の頻度の上限（HTTPの状態コード429）の応答だけは、60秒待って5回まで再試行する。

出品の表示だけで機械を選ぶ案は採らなかった。
候補の測定では、表示が384スレッドで、使えるスレッド数の欄も384のEPYC 9B45機が、cpusetで48スレッド、cgroupで46.08 CPU分しか使えなかった。
復旧試験でも、条件を満たすはずのEPYC 7B13機が借りた後の検査に落ちた。

時間単価の最も安い出品を選ぶ案は採らなかった。
機種によって1スレッドあたりの探索速度が異なり、記録局面あたりの費用は時間単価を探索速度で割った値で決まるからである。
機種を7B13と9654に限るのは、候補の測定で表示どおりのスレッド数を使え、探索速度あたりの費用が安い順に1位と2位だったからであり、256スレッド以上に限るのは、192スレッドのEPYC 7643機では1世代37本の換算が約24.2時間となり、再検討の条件とした24時間を超えたからである。
同時対局数を物理コア数にする案は、候補の4台すべてで論理スレッド数の方が1.13〜1.35倍速かったので採らなかった。

複数台へ教師ファイルを配布する案は採らなかった。
比較の試行では1台で1世代37本の換算が約17.2時間であり、24時間に収まったからである。
GCPのSpot VMは、vCPUの枠が全リージョン合計64と小さく、[予備測定](../measurements/adhoc/gcp-spot-teacher-generation-speed.md)の1ファイル約0.25米ドルがvast.aiより高いので使わない。

止められるたびに入札額を上げる案は採らなかった。
費用の見込みが借りている途中で変わり、一定の入札額での中断の頻度も測れなくなるからである。

費用の上限を機械ごとの期限だけで抑える案は採らなかった。
移行を繰り返すたびに期限が延びて費用が際限なく増えるので、実行全体の絶対期限、累計費用の上限、借りる回数の上限、および時間単価の上限を必須の引数とし、実行ディレクトリに保存して再実行でも初期化しない。

## 結果

中断可能インスタンスが止められても、作業機に回収済みの塊からその教師ファイルの続きを生成できる。
1回の移行では、止まった機械で確定していなかった対局と回収していなかった塊を失い、復旧試験では1,343局分、比較の試行では964局分と1,216局分と推定された。
塊が番号順に確定するとは限らないので、損失は、塊が順に確定すると仮定して塊の局数、回収の間隔、および同時対局数から見積もった値の約3倍になることがある。
口座の操作には2段階認証のログインが要るので、ログインが切れると移行できず、制御スクリプトは機械を借りずに止まる。

# 勝率尺度を重みファイルの1定数とし、教師の勝率尺度は較正コマンドで求めて学習の引数で与える

## ステータス

承認済み。決定日は2026年10月16日。[学習する評価関数の出力Kを初期値の重みファイルの値に固定し、データから推定し直さない](archive/fix-the-output-k-of-trained-weights.md)を置き換える。

## コンテキスト

評価関数の学習は、評価値（センチポーン、cp）を勝率へ換算する尺度を2つ持っていた。
1つは、ネットの出力をロジット（シグモイド関数に入れる前の実数）へ換算する尺度で、重みファイルのヘッダに書かれた1072.6529541015625という定数である。
もう1つは、教師の探索値を勝率へ換算する尺度で、教師の分類（生成コミット、重みの検査和、探索の規模、規則セット、局面の由来、先読み条件の組）ごとに、学習のたびに訓練集合から推定していた。
2つの量は同じ単位（1ロジットあたりのcp）だが、前者は評価値の単位を定める取り決め、後者は各教師の探索値が勝率とどう対応するかの測定値である。
コードは両方を`k`と呼び、文書は「出力K」「出力用K」「教師K」「教師尺度」などと場所ごとに呼び分けていたので、2つの量の違いが名前から読み取れなかった。
2026年10月15日にエンジンの開発者は、勝率への換算尺度を学習で獲得するのはおかしいこと、`k`という名前では理解できないこと、および2つの値は1つにまとめられるはずであることを指摘した。

学習のたびに推定する方式には、教師値の定義が訓練集合の分割や間引き方に左右されるという問題もあった。
[学習率スケジュールの設計書](../plans/archived/nnue-lr-schedule.md)は、訓練局面を間引く比較実験で教師値が変わらないように、間引く前の集合から推定する特則を置いていた。
既存実装の調査（[評価値を勝率へ換算する尺度の決め方](../research/win-rate-scale-k-prior-art.md)）では、調べた13件のうち学習のたびに推定するのはEtherealのチューナーとdlshogiの`--use_evalfix`の2件だけであり、残りは手で決めた定数か、一度推定して定数化した値だった。

一方、分類ごとの値には根拠がある。
記録された教師の勝率尺度は、1局面10万ノードで生成した世代2と世代3で758と766、1局面2万ノードの教師で1218であり、浅い探索の教師ほど大きい。
同じcpの探索値が分類ごとに違う勝率を意味するので、分類ごとの値を1つの値にまとめると教師値が変わり、棋力への影響を測定せずには採用できない。

## 決定

勝率尺度`cp_per_logit`は、重みファイル（MNPT、MNUE）のヘッダが持つ値を唯一の定数とし、学習の初期値に与えた重みファイルの値を、学習中および書き出す重みにもそのまま使う。
教師の探索値は、分類ごとの教師の勝率尺度`teacher_cp_per_logit`で勝率へ換算する。
両者の比`cp_per_logit / teacher_cp_per_logit`を尺度補正係数`teacher_score_multiplier`と呼び、教師の探索値をこの係数で勝率尺度の単位へ換算したものとして、文書の説明と学習の記録を整理する。
実装の計算式は`σ(v / teacher_cp_per_logit)`のまま変えず、補正係数は無次元の導出量として記録だけに使う。
補正係数を先に掛けてから勝率尺度で割る計算は実数では同じ値だが、浮動小数点では丸めが変わり得るからである。

教師の勝率尺度は、学習、および教師値を使う診断の必須の引数`--teacher-cp-per-logit`で与え、既定値を置かない。
値は、この学習の訓練集合から分類ごとに推定させる`calibrate`か、較正コマンド`minase-trainer data calibrate`が書き出す較正ファイル（JSON）のパスのどちらかである。
較正の計算は、訓練集合の探索値から終局結果を予測する二値交差エントロピーを区間`[50, 4000]`の黄金分割探索で最小化するもので、`calibrate`指定の学習と較正コマンドは同じ1つの関数を呼ぶ。
較正ファイルは分類ごとに、生成コミット、重みの検査和、探索の規模、規則セット、局面の由来、先読み条件、訓練局面数、教師の勝率尺度、および推定値が探索範囲の端に達したかどうかを持ち、学習器はこれらの属性で学習の分類と突き合わせる。
混合比λは較正の計算に入らないので突き合わせに使わない。
λが0でない分類に対応する項目がない、項目に対応する分類がない、または同じ分類に複数の項目がある場合は、学習を始めずにエラーで終了する。
入力ファイルの一覧は突き合わせない。
教師値を固定したい比較では、較正に使ったファイルの集合と学習に用いるファイルの集合が異なっていてもよいためである。

学習の記録`config.json`には、`calibrate`と較正ファイルのどちらを使ったか、較正ファイルの内容、分類ごとの教師の勝率尺度、および導出した補正係数を記録し、再開の照合に含める。
あわせて、Rustの識別子、`config.json`のキー、チェックポイントの配列名、CLIの引数、および現行の文書の名前を、`cp_per_logit`、`teacher_cp_per_logit`、`teacher_score_multiplier`、および教師の探索の規模を表す`teacher_search_budget`に統一する。
仕様は`crates/minase-trainer/src/data/`のdocコメントにある。

## 検討した代案

勝率尺度を学習の引数で与える案は、重みが既にその単位で書かれているので、再学習なしに変えると評価値のcpを基準に調整した探索係数の前提が崩れる。
ヘッダの値を単位の定義として残すのが最も単純である。

補正係数を持たない1定数化（tanuki-の方式）は、現行の教師の分類間で勝率尺度が最大で約1.6倍（1218対758）異なるので、棋力への影響を測定せずには採用できない。
測るなら別の設計書で段階ゲートにかける。

常に推定する現行の方式だけにする案は、教師値を固定したい比較のたびに「間引く前の集合で推定する」といった特則を書き続けることになる。
較正ファイルだけにする案は、通常の学習でも較正と学習の2段階の手順を要し、別の条件で作った較正ファイルを渡す誤りの余地を増やす。
生成器が生成の終了時に推定してMNSDヘッダへ書く案は、形式の版を上げて既存の30ファイル（約43時間分）を再生成する必要があり、生成器が検証集合を含む全局面で推定する点も学習器の推定と一致しない。

較正ファイルの代わりに`<検査和の先頭8桁>@<ノード数>=<値>`のような短い鍵を手で書く案は、同じ重みのまま探索コードだけを更新した世代（検査和とノード数が同じで生成コミットが違う分類）を区別できない。
鍵なしの値を入力順に並べる案は、`--data`の順序を変えると対応がずれる。
単一の値だけを受ける案は、世代の異なる教師を混ぜる学習を不可能にする。

較正ファイルに補正係数（例: 0.88）を持たせる案は、勝率尺度の異なる重みを初期値にすると同じ教師でも値が変わり、較正の記録と突き合わせにくいので、教師自身の勝率尺度を持たせた。
旧キー名や旧配列名を読む互換経路は作らなかった。
改名前の実行ディレクトリとチェックポイントは新しい学習器で再開できなくなるが、過去の記録との互換の維持は不要と判断した。

## 結果

学習が計算する値と書き出す重みは変わらない。
改名の前後で、NNUE、PST、FM、同時学習、および教師値を使う診断において、局面数、教師の勝率尺度、通し番号、各エポックの損失、ならびに書き出した重みが文字列として一致し、較正コマンドの出力は改名前の学習器が記録した値と一致した（[照合の記録](../measurements/win-rate-scale-equivalence.md)）。
通常の学習は`calibrate`を使い、訓練集合の間引きや分割の変更のように教師値を固定したい比較では較正ファイルを使う。
較正ファイルを与えた学習は推定し直さず、別のファイルの集合で求めた値かどうかも検出しないので、較正ファイルを使う学習の記録には較正ファイルの内容を記録する。
[out-of-coreシャッフルの設計書](../plans/out-of-core-shuffle.md)が前提とする学習時の推定は、`calibrate`指定の学習として保たれる。

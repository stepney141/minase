# AlphaZero型探索の推論は、ortのrc.15を使い、ONNX Runtimeの環境をプロセスの終了まで保持する

## ステータス

承認済み。決定日は2026年11月11日。

## コンテキスト

AlphaZero型探索のネットの推論は、ONNX RuntimeのRustバインディングであるortクレートで行う（[推論の方式のADR](run-zero-network-inference-through-ort-load-dynamic.md)）。
ortは`=2.0.0-rc.13`に固定していた。rc.14以降は`rust-version = "1.92"`を宣言しており、minaseの`rust-version`を1.88のまま保つためである。

推論を使う`minase dev nn-eval`と自己対局の生成器は、出力を書き終えた後の終了処理で、glibcがヒープの破壊（`corrupted double-linked list`）を検出して異常終了することがあった。
ONNX Runtimeの実行時ライブラリを1.28.3から1.31.1へ上げると回数は減ったが、借りた機械の一部では残った（[ONNX Runtimeの版のADR](load-onnx-runtime-1-31-1-through-ort-rc13-for-zero-inference.md)）。
強化学習の1サイクル（自己対局の生成、学習、および書き出したネットの照合）を順に起動する実行器は、これらのコマンドの0以外の終了コードを失敗として止まるので、異常終了が起きる機械ではサイクルを回せない。

[原因の調査](../measurements/adhoc/zero-teardown-abort-root-cause.md)は、手元の作業機で異常終了を再現し、原因を次のとおり特定した。
ortのrc.13は、ONNX Runtimeの環境（プロセスに1つの共有の設定）を解放する`ReleaseEnv`を、実行ファイルの`.fini_array`から呼ぶ。
minaseはONNX Runtimeの共有ライブラリを実行中に読み込み、ONNX RuntimeはCUDAの実行プロバイダの共有ライブラリを実行中に読み込む。glibcでは、`.fini_array`の関数は、実行中に読み込んだ共有ライブラリの静的デストラクタより後に走る。
ONNX RuntimeのCUDAの実行プロバイダは、演算の実装の登録表を静的な`std::shared_ptr`に持ち、環境の破棄から呼ばれる`Shutdown()`でこれを手放す。
このため、終了時に、登録表は静的デストラクタで解放された後にもう一度手放され、解放済みの領域の参照カウントが1減る。
この書き込みは実行のたびに起きており、異常終了になるかどうかは、その領域がglibcのどのリストにあるかというヒープの配置で決まる。異常終了のスタックの先頭にはNVIDIAのドライバのライブラリが現れるので、ドライバの版が疑われていたが、ドライバは破壊を検出する引き金になっただけで、原因ではない。

ortは、rc.14でこの仕組みを取り除いた。rc.14以降は、環境を作る関数`build()`が返す値として環境を利用者に持たせ、利用者の値と、その環境から作ったすべてのセッション（1つのネットを読み込んだ推論の単位）が破棄された時点で解放する。
rc.14以降の`build()`は、環境を1回作ったプロセスでは、その環境が解放された後でも、2回目の作成をエラーにする。
エンジンの開発者は、2026年11月11日に、ortをrc.15へ上げる方針で直すと決めた。

## 決定

ortを`=2.0.0-rc.15`に固定し、minaseの`rust-version`を1.92にする。
Cargoの機能（feature）の指定は変えず、`api-28`のまま、ONNX Runtime 1.31.1の実行時ライブラリを読み込む。
規則のライブラリである`minase-core`クレートはortに依存しないので、`rust-version`を1.88のままとする。

推論器の初期化が作った環境は、プロセスに1つの静的変数に保持し、プロセスの終了まで解放しない。
環境は、`build()`が成功した直後、セッションの作成より前に、静的変数へ入れる。

## 検討した代案

rc.13のまま、環境への参照を`std::mem::forget`で捨てて`ReleaseEnv`を呼ばせない案は採らなかった。
ortが公開していない内部の持ち方に頼る回避策であり、開発元が同じ仕組みを取り除いた版がすでにあるからである。

推論器ごとに環境を持ち、最後の推論器の破棄で解放する案は採らなかった。
USIエンジンは、実行プロバイダやバッチの大きさの設定が変わると推論器を破棄して作り直すので、同じプロセスで環境を2回作ることになり、rc.15がこれを拒むからである。

実行ファイルの入口が環境を持ち、推論器へ渡す案は採らなかった。
`process::exit`で終わる経路では環境が解放されないので、経路によって終了処理が変わる。また、推論器を作るすべての呼び出しに引数が増える。

`minase dev nn-eval`の終了処理を飛ばす案と、出力が完全なら異常終了を成功とみなす案は、ONNX Runtimeの版のADRがすでに棄却している。

## 結果

`ReleaseEnv`はプロセスの終了時に呼ばれなくなり、登録表は静的デストラクタで1回だけ解放される。
作業機では、gdbの下で、CUDAとTensorRTの`minase dev nn-eval`、入出力の形が合わないネットを拒んで終わる経路、および自己対局の生成器の4つの経路のすべてで、`exit`に入った後に登録表を手放す関数が呼ばれなかった。変更前の実行ファイルでは、4つの経路のすべてで呼ばれた。
推論の出力と、同じシードで生成した64局の訓練データは、変更の前後でバイト列が一致し、生成の速さも変わらなかった。USIエンジンは、同じプロセスで推論器を4回作り直せた（[作業機での確認](../measurements/alphazero-teardown-abort/alphazero-teardown-abort-workstation.md)）。

環境が持つメモリは、プロセスの終了とともにOSが回収する。
ONNX Runtimeの側には環境を解放する静的デストラクタがないので、環境が生きたままプロセスが終わっても、終了処理の中で環境が解放されて登録表がもう一度手放されることはない。

借りた機械での異常終了が同じ原因であることは、メッセージ、検出された箇所、およびライブラリの構成の一致から推定したものであり、借りた機械では確かめていない。
借りた機械で終了処理の異常終了がまた起きたら、原因の調査の記録の手順で、壊れる番地への書き込みを調べ直す。

minaseのビルドには、Rust 1.92以降が要る。
ONNX Runtimeの実行時ライブラリを上げるときは、原因の調査の記録の`find_registry_reset.py`と`probe.py`で、終了時に登録表を手放す関数が呼ばれないことを確かめ直せる。
ortをさらに上げるときは、環境の解放の仕組みが変わっていないことをソースで確かめる。

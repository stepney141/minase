# NNUEのネットを、読み込んだファイル全体のSHA-256で識別する

## ステータス

承認済み。決定日は2026年11月17日。

## コンテキスト

αβ探索のNNUEのネットは、実行ファイルに埋め込まず、USIのオプション`EvalFile`で指定した外部のファイルから読むようになった（[外部ファイル化のADR](archive/use-an-nnue-read-from-evalfile-as-the-only-search-evaluation.md)）。
埋め込んでいた間は、生成コミットがネットを決めていたので、ネットを別に識別する必要はなかった。
外部のファイルでは、同じコミットに別々のネットを渡せるので、エンジンの報告、対局の実行器の記録、および教師ファイルのヘッダに、ネットを特定する値が要る。

重みのファイルの形式MNUE（版5）のヘッダは、本体（192バイト目以降）のSHA-256をチェックサムとして持つ。
しかし、ヘッダには評価値の換算に使う勝率尺度（評価値と勝率を結ぶ実数）と規則セットの名前もあり、本体のチェックサムの計算範囲にはこれらが含まれない。
勝率尺度は、復号のときに非線形の経路の出力をセンチポーンへ換算する整数の係数になるので、本体が同じでも、勝率尺度が違えば評価値が変わる。
学習器は、学習の出発点として読み込む前の世代のネットから勝率尺度と規則セットの名前を引き継ぐので、ヘッダの値も含めてネットを識別する必要がある。
PV-MCTSの`NnModel`は、ONNXのファイル全体のSHA-256を`isready`で報告していた。
この判断は[NNUEの外部ファイル化の設計書](../plans/archived/nnue-external-network-file.md)で下した。

## 決定

`isready`（または教師生成の`--eval-file`）で読み込んだファイル全体のバイト列のSHA-256を、ネットの唯一の識別子とする。
ファイルは1回だけ読み、復号に渡すのと同じバイト列から識別子を求める。
エンジンは`readyok`の直前に`info string network_sha256 <64桁の16進数>`で報告する。
対局の実行器と係数調整はこの報告値を記録して照合し、教師生成は生成条件`config.json`と教師ファイル（形式MNSD）のヘッダの`network_checksum`に書く。
MNUEのヘッダのチェックサムは、復号のときに本体の破損を見つける検査として残すが、識別子には使わない。

## 検討した代案

MNUEの本体のチェックサムを識別子にする案は、ヘッダだけが違う2つのネットを区別できないので採らなかった。
MNUEのチェックサムの範囲をヘッダまで広げて版を上げる案は、重みのファイルの形式をtataraの形式（チェックサムを持たない）へ揃える計画（[tatara化とHalfKP_vmの設計書](../plans/archived/nnue-tatara-framework-and-halfkp-vm.md)）があり、すぐに捨てる変更になるので採らなかった。
ファイル全体のSHA-256とMNUEのチェックサムを両方とも識別子として記録する案は、同じネットに2つの識別子を持たせ、同じ対象を二重に照合することになるので採らなかった。
2026年10月13日にエンジンの開発者は、同じ対象のチェックサムを二重に照合しないと決めている。

教師ファイルの形式MNSDの版を上げる案は採らなかった。
欄の配置は変わらず、`network_checksum`に入れる値の意味だけが変わる。
既存の教師ファイルの値はMNUEの本体のチェックサムであり、同じネットでもファイル全体のSHA-256とは一致しないので、教師生成の再開の照合で新旧を取り違えることはない。

## 結果

識別子と実際に使うネットは、同じ読み取りのバイト列から得るので食い違わない。
ファイルを書き換えれば識別子も変わるので、同じパスのファイルを差し替えた測定や再開は照合で止まる。
識別子の求め方は、αβ探索のNNUEとPV-MCTSのONNXで同じになった。
重みのファイルの形式をtataraの形式へ揃えた後も、識別子の定義は形式によらず変わらない。
読み込みの関数の契約は`crates/minase/src/eval/nnue/`のdocコメントにある。

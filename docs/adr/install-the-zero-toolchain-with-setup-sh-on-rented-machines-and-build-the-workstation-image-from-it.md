# AlphaZero型探索の実行環境は、借りる機械では導入スクリプトで導入し、作業機の開発用のコンテナは同じスクリプトから作る

## ステータス

承認済み。決定日は2026年11月13日。

## コンテキスト

AlphaZero型探索の学習と自己対局は、Google Colabで借りる機械（以下、Colab機）、vast.aiで借りる機械、および開発に使う作業機で動かす。
[前の決定](archive/install-the-zero-toolchain-from-one-lock-on-every-machine.md)は、独自のコンテナイメージを作らず、どの機械でも`tools/train/zero/setup.sh`を実行して、uvのロックファイルとスクリプトが固定する版のツールとパッケージを導入すると決めていた。

この方式には、気になる点が2つあった。
1つ目は、vast.aiの機械では、導入の結果と時間が、機械や借りた日によって変わることである。
導入のたびに、apt、PyPI、NVIDIAのパッケージインデックス、GitHub、およびrustupの配布元から大きなパッケージを取得していた。
aptのパッケージは版を固定していないので、借りた日によって中身が変わり得る。時間も、[複数GPU化の測定](../measurements/alphazero-multi-gpu/alphazero-multi-gpu-vast.md)では、導入に3分52秒かかった機械と11分50秒かかった機械があった。
2つ目は、作業機（Arch Linux、glibc 2.44）で通った試験や、ニューラルネットワーク（以下、ネット）の推論の出力の照合が、借りた機械（Ubuntu 24.04、glibc 2.39）で通るとは限らないことである。
作業機の環境は手で更新していたので、版のずれも起きていた。

[Dockerイメージの設計書](../plans/archived/docker-environment.md)は、`setup.sh`を実行して作る1つのイメージを、作業機の開発用のコンテナとvast.aiの機械の両方で使う案を試した。
作業機では、イメージのビルドからコンテナの中の検査、GPUの試験、およびネットの出力の照合までが通った（[作業機での確認](../measurements/docker-environment/docker-environment-workstation.md)）。
vast.aiでは、GitHubのコンテナレジストリ（GHCR）に置いたイメージで機械を6回借りたが、起動して、自己対局の生成と学習の1サイクルを回せたのは1回であった（[vast.aiでの確認](../measurements/docker-environment/docker-environment-vast.md)）。
エンジンの開発者は2026年11月13日に、この結果を見て、vast.aiではイメージを使わないと決めた。

## 決定

借りる機械（Colab機とvast.aiの機械）では、今までどおり`tools/train/zero/setup.sh`で実行環境を導入する。
作業機には、リポジトリの直下の`Dockerfile`が同じ`setup.sh`を実行して作るイメージ`minase-dev`と、それをdocker composeで起動する開発用のコンテナを用意する。
導入するツールとパッケージの版は、環境の入力（`tools/train/zero/`の`setup.sh`、`env.sh`、`pyproject.toml`、`uv.lock`、`.python-version`）と、`Dockerfile`が指定するベースのイメージのダイジェストだけに書く。

この決定には、次の4つの取り決めが伴う。

- `setup.sh`は、uv、rustup、Rustのツールチェーン、Pythonの本体、仮想環境、およびONNX Runtimeを、すべて`env.sh`が置かれたディレクトリの下の`.runtime/`と`.venv/`に導入する。このディレクトリは、`Dockerfile`が環境の入力を写して`setup.sh`を実行するイメージでは`/opt/minase-zero`であり、ソースから`setup.sh`を実行する借りる機械と作業機のホストでは、作業ツリーの`tools/train/zero`である。導入先と環境変数は、`env.sh`を読み込めば決まる。
- `setup.sh`は外部のパッケージだけを入れる。学習器が教師ファイルを読む拡張モジュール`mnsd_reader`は、動かす機械で`sync-env.sh`が対象のコミットのソースからビルドする。minase本体も、動かす機械でビルドする。
- イメージは、作ったときの環境の入力の写しを`/opt/minase-zero`に持つ。`check-env-inputs.sh`は、作業ツリーの環境の入力がこの写しとバイト列で一致することを検査する。検査は、開発用のコンテナの起動時と、仮想環境を同期する`sync-env.sh`の最初に行う。開発用のコンテナでは、`uv run`が仮想環境を自動で書き換えないように`UV_NO_SYNC=1`を設定し、同期を`sync-env.sh`だけに限る。借りる機械では、導入先が作業ツリーそのものなので、この検査は常に通る。
- 開発用のコンテナは、1つの作業ツリーをホストからマウントして扱う。ホストでビルドした実行ファイルをコンテナで使わないように、作業ツリーごとのDockerの名前つきボリュームを、ビルド出力の`target/`と`mnsd_reader/target/`にかぶせる。

## 検討した代案

vast.aiの機械もイメージで借りる案は、測定の結果から採らなかった。
イメージは圧縮後で7.1 GBあり、機械はこれをGHCRから取得する。
GHCRからの取得は1接続あたり毎秒約15 MBで頭打ちになり、借りた機械では、取得がHTTP 500で失敗する、接続が切れて取得がやり直しになる、という失敗が続いた。
取得のやり直しで失う量を減らすためにイメージの層を8つに分け、起動を待つ上限を45分へ延ばして起動できた機械でも、機械の作成から準備の完了までに40分37秒かかった。これは、今までの方式で2台の機械の起動と導入にかかった5分13秒と14分53秒より長い。
回線の遅い機械での結果なので、同じ機械での比較ではないが、イメージにすれば速くなることは示せなかった。
イメージにしても、`mnsd_reader`のビルドのときにPyPIとcrates.ioからの取得が残り、この機械ではそこに15分かかった。
Pythonの依存、ONNX Runtime、およびRustの版は、もともとロックファイルとチェックサムで固定されており、イメージで新しく固定されるのは、aptで入れる10個のパッケージだけである。
一方で、環境の入力を変えるたびにイメージを作り直して登録する手間と、レジストリのトークンの管理が加わる。

作業機でも`setup.sh`だけを使い、コンテナを用意しない案は、コンテキストの2つ目の点が残るので採らなかった。

Dockerfileに版を書き、`setup.sh`とは別の手順でイメージを作る案は、借りる機械の`setup.sh`と版が食い違い得るので採らなかった。

uvやRustのツールチェーンを今までどおり`$HOME`の下に導入し、機械にuvやrustupがあればそれを使う案は採らなかった。
開発用のコンテナはホストの利用者のUIDで動くので、イメージを作ったときの`$HOME`と使うときの`$HOME`が同じにならない。
また、機械にあるツールを使う作りでは、導入が機械にもとからあるツールに左右される。Colab機には、uvとPythonがもとから入っている。

minaseと`mnsd_reader`をイメージに入れる案は、2つの理由で採らなかった。
`.cargo/config.toml`が`target-cpu=native`を指定しているので、実行ファイルはビルドした機械のCPUに特化する。
また、`mnsd_reader`はminaseのクレートにパスで依存するので、イメージがソースの特定のコミットに結び付く。

環境の入力を検査しない案は、作業ツリーの`uv.lock`がイメージのものと違うときに、uvがイメージの仮想環境のパッケージを黙って入れ替えるので採らなかった。

開発用のコンテナのビルド出力を、`CARGO_TARGET_DIR`でホストと分ける案は採らなかった。
エンジン同士を対局させる対局ハーネスが、指定されたコミットをビルドした後、そのソースの直下の`target/release/minase`を読むからである。

Colab機でイメージを使う案は、Colabの規約がコンテナ化を禁じ、コンテナの実行環境もないので採れない（[Colab機の借り方のADR](rent-colab-gpus-through-the-cli-and-keep-state-on-the-nas.md)）。

## 結果

借りる機械の導入の手順は、`setup.sh`の後に`sync-env.sh`を実行する形に変わる（[借りる機械の操作の手引き](../guides/alphazero-machines.md)の3節）。
導入したものはすべて`tools/train/zero/`の下の`.runtime/`と`.venv/`に入り、`$HOME`には何も置かれない（[Colab機での確認](../measurements/docker-environment/docker-environment-colab.md)）。
vast.aiの機械で、導入の時間が機械によって変わる点は残る。

作業機では、vast.aiで機械を借りるときに指定するベースのイメージの上で、借りる機械と同じ`setup.sh`を実行して作った環境の中で、マージ前の検査、GPUの試験、およびネットの出力の照合を実行できる。
手順は[開発用のコンテナの手引き](../guides/dev-container.md)にある。
環境の入力を変えたときは、その作業ツリーでイメージを作り直す。作業ツリーの環境の入力がイメージのものと違えば、開発用のコンテナは起動しない。

作業機のホストで`env.sh`を読み込んで学習器や推論を動かすには、その作業ツリーで`setup.sh`を実行し直す必要がある。
`env.sh`が指すuvとRustのツールチェーンが、`$HOME`の下のものから、作業ツリーの`tools/train/zero/.runtime/`の下のものに変わったからである。

GPUドライバは機械ごとに異なるので、推論の結果が機械によって変わらないことは、今までどおり出力の照合で確かめる（[ネットの出力の照合の手引き](../guides/alphazero-network-check.md)）。

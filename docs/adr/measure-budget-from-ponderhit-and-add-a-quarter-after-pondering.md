# 先読みが的中したら同じ探索を続けて時間予算を的中の時点から測り、秒読みのない時計では、先読みの探索を始めた後の、先読みでない探索の目安時間を25%増やす

## ステータス

承認済み。決定日は2026年10月23日。

## コンテキスト

USIの先読みでは、エンジンが`bestmove X ponder Y`で相手の次の手の予想Yを添え、GUIはXとYを指した局面で`go ponder`を送る。
相手の実際の着手がYなら`ponderhit`が届き、異なれば`stop`が届く。
[USI先読み](../plans/archived/ponder.md)は、的中した後の探索の続け方と、時間予算を測る起点を決める必要があった。
Stockfish、やねうら王、およびHaChuは経過時間を探索の起点から測り、先読みの時間を予算に全額算入する（[設計書の参考資料](../plans/archived/ponder.md#参考資料)）。
この方式では長い先読みの後に的中と同時に指すことになるので、各エンジンは目標時間の25%増しや先読み時間の残り時間への足し戻しなどの別の機構で目減りを補っている（[同じ参考資料](../plans/archived/ponder.md#参考資料)）。
当時のminaseの予算は加算と秒読みの項が大半を占め、残り時間の項は88手以上で割っていたので、先読みで節約した時間は後の手の予算へほとんど戻らなかった。

[旧ADR](archive/continue-search-and-measure-budget-from-ponderhit.md)は、2026年9月21日に、的中しても同じ探索を続け、時間予算を的中の時点から測ると決めた。
旧ADRは、予算を探索の起点から測る方式を採らないので、目減りを補う別の機構も持たないとした。
先読みは、STCが有効208ペアでLLR 2.9505、LTCが有効215ペアでLLR 2.9512の`H1`だった（[STC](../measurements/ponder/ponder-stc.md)、[LTC](../measurements/ponder/ponder-ltc.md)）。
測定は評価関数がPSTとFMだった時期の構成で行ったので、旧ADRは、起点や再判定の方式を変える提案には現行の構成での再測定が要るとしていた。

Stockfishは、`Ponder`オプションが有効なら、上限時間を決めた後で、すべての探索の目安時間に4分の1を足す（`src/timeman.cpp:164-165`）。
Stockfishは先読みの探索の経過時間を探索の開始から数えるので、的中した手では相手の手番中に使った時間まで目安時間から差し引かれ、時計に対して時間を使い残す。
25%増しは、その使い残しを他の手で使う働きを持つ。
YaneuraOuも、`USI_Ponder`が有効で`Stochastic_Ponder`が無効なら目安時間を25%増やし（`yaneuraou-timeman.cpp:283-286`）、秒読みつきの時計を区別しない。
Stockfishは、先読み中に目安時間の超過か短い詰みの条件を満たしても止めず、印`stopOnPonderhit`を立てて的中か`stop`を待つ（`src/search.cpp:626-629`）。
この印は、aspiration windowsの窓が評価値の低下で外れると消える（同`444`）。

[持ち時間の伸縮の設計書](../plans/time-instability-scaling.md)は、2026年10月17日のエンジンの開発者の決定に従い、Stockfishの時間管理の項目をminaseへ入れた。
エンジンの開発者は、先読みを使う対局での25%増しも入れると決め、設計書はその対象を、minaseが的中の時点から予算を測ることに合わせて絞った。
同じ設計書は、完了反復ごとに目安時間を伸縮させる4因子と、短い詰みでの早期停止を入れた（[伸縮のADR](scale-the-soft-limit-by-search-instability-and-keep-the-stable-best-move-rule.md)）。
これらは先読みから続く探索の判定にも関わる。

## 決定

`ponderhit`を受けても探索を止めず、同じ探索のまま時間の制限を有効にして、1手の目安時間softと打ち切りの上限hardを的中の時点から測る。
次の反復を始める判定と、的中の時点で進行中だった反復を続けるかの1回だけの再判定は、探索の起点からの累積時間に固定比を掛けた予測完了時刻を、的中までの時間と予算の和と比べて行う。
4因子を使う探索では、的中前の先読みでも完了反復ごとに4因子を求め、的中後の判定と再判定には、最新の完了反復で伸縮させたsoftを持つ予算を渡す。

対局内で次の探索へ持ち越す`HistoryTables`に先読みの印を置く。
印は、探索チームが先読みとして探索を始めるときに、ワーカー数の不一致による表の作り直しを終えた後で立て、`HistoryTables`の初期化で消す。
印が立っていれば、4因子を使う探索（時計の秒読みが0で、`movetime`がない探索）のうち、先読みとして始めなかった探索では、基礎予算のsoftを`soft + ⌊soft / 4⌋`に増やしてhardで抑え、そのうえで4因子を掛ける。
先読みとして始めた探索には、的中してそのまま続いた場合も含めて、この増分を掛けない。
秒読みが正の時計の探索には、持ち時間を使い切る前の手も含めて、この増分を掛けない。

4因子を使う探索の的中前の先読みでは、短い詰みの条件を満たしても止めず、最新の完了反復が条件を満たすかを記録し、次の完了反復が満たさなければ記録を消す。
的中の後は、反復を始める前の判定と、探索中の時計の検査で記録を調べて止める。
時計の検査はhardを先に調べ、詰みの記録は予測の再判定とは独立に調べる。
再判定は的中より前に始めた反復だけを対象にするからである。

詳細は`SearchHandle::ponderhit`、`iteration_prediction_fits`、`Searcher::check_time`、および`ponder_bonus_time_budget`のdocコメントにある。

## 検討した代案

`ponderhit`で探索を止め、置換表を使って時計つきの探索をやり直す案は、進行中の反復を捨て、置換表の世代を1つ余分に進め、浅い反復からやり直す時間を自分の持ち時間から使うので採らなかった。
予算を探索の起点から測る案は、先読みの時間を予算に全額算入して先読みの利益を捨てるので採らなかった。
的中からの経過時間に固定比を掛けて次の反復を予測する案は、次の反復の所要時間が探索全体の累積時間に比例するので所要時間を過小に見積もり、完了できない反復を毎回始めてhardで打ち切られるので採らなかった。
的中の時点で進行中の反復を無条件に続ける案は、長い先読みの後の的中でhardまで使ってその反復を捨てる手が増えるので採らなかった。

Stockfishと同じく、先読みを使う対局のすべての探索に25%増しを掛ける案は採らなかった。
minaseは的中の時点から予算を測るので、的中した手では使い残しが生じない。
的中の時点から測ることで目減りはすでに補われているので、的中した手にも25%を足すと、同じ目減りを2回補うことになる。

25%増しを持たない旧ADRの形は、Stockfishにある項目を入れるというエンジンの開発者の決定により採らなかった。

増分の対象を`USI_Ponder`の値で決める案は採らなかった。
minaseの予算は`USI_Ponder`に依存しないので、minaseは`USI_Ponder`を宣言せず、受け取っても無視する。
先読みの印は、Stockfishの`Ponder`オプションの代わりに、25%増しを掛ける探索を決める。

印の寿命を新規対局だけに結びつける案は採らなかった。
プロトコル層は、新規対局と、規則、置換表容量、引き分けの評価値、またはワーカー数の変更とを区別せずに`HistoryTables`を初期化するので、新規対局だけで消すには、プロトコル層で両者を区別する変更が要る。
Stockfishの`Ponder`オプションは対局をまたいで保たれるが、minaseの印はそれより短く、対局の途中で置換表容量やワーカー数を変えると消える。
lishogiのBotは対局の途中でこれらを変えないので、この差は運用に影響しない。

Stockfishと同じく、増やしたsoftがhardを超えることを許す案は採らなかった。
Stockfishは上限時間を決めた後に目安時間を増やすので、増やした目安時間が上限時間を超え得る。
minaseは、softをhard以下に保つ契約（[残り手数の見積りのADR](estimate-moves-to-go-from-ply.md)）を守るため、増やした基礎予算のsoftをhardで抑えてから4因子を掛ける。

25%という増分をSPSAで調整する案は採らなかった。
SPSAとSTCの対局は先読みを使わないので、この値は調整できない。

秒読みつきの時計の持ち時間期にも増分を掛ける案は、測ったうえで採らなかった。
設計書はSPSAまでをこの形で進めたが、SPSAの最終値を反映した候補は秒読みつきの短い条件で起点に対して`H1`とならず、2026年10月22日のエンジンの開発者の決定（設計書の案1）により、4因子とともに秒読みが0の時計に限った（[伸縮のADR](scale-the-soft-limit-by-search-instability-and-keep-the-stable-best-move-rule.md)）。
YaneuraOuは秒読みつきの時計を区別せずに25%を足す。

Stockfishの`stopOnPonderhit`と同じく、的中前に目安時間の超過を満たした状態も保持する案は採らなかった。
minaseは的中の時点から予算を測るので、的中前の目安時間の超過は的中後の判定に意味を持たない。
保持するのは短い詰みの条件だけとした。

的中前に短い詰みの条件を満たしたら探索を止める案は採らなかった。
Stockfishも先読み中は止めず、的中か`stop`を待つ（`src/search.cpp:626-629, 2154-2156`）。

## 結果

先読みでない探索では的中までの時間が0なので、判定は先読みのない式と一致する。
固定深さのbenchは時間予算を使わないので、設計書の全13コミットで探索ノード数、評価値、および最善手が変わらなかった（[benchの記録](../measurements/time-instability-scaling/time-instability-scaling-bench.md)）。
旧ADRの先読みの測定では、的中率はSTCで49.5%、LTCで52.0%であり、先読みを使う候補は相手の手番中にもCPUを使うので、CPU時間の合計は先読みを使わない基準の約2.0倍だった。
この測定が示すのは同じ時計の下での強さである。

本決定は、予算を測る起点と再判定の方式を変えず、秒読みが0の時計では、再判定に渡す予算を伸縮させたsoftに替え、先読みでない探索に増分を加える。
SPSA、事前対局、およびSTCは先読みを使わないので、先読みを対局条件に含めた測定（`--ponder`）は行っておらず、増分と、先読み中の詰みの記録の働きは単体テストと結合テストで確かめた。
先読みの印は先読みの探索そのものを始める前に立つが、その探索の予算には使わないので、印が働くのは、先読みが外れた後の探索のように、先読みとして始めなかった次以降の探索である。
秒読みが正の時計の探索には増分を掛けず、`ponder_bonus_time_budget`は秒読み期の予算を受け取らないことを表明（`assert!`）で検査する。
印の記録と増分の適用は`crates/minase/src/search/alphabeta/team.rs`の`run_search_team`に、増分を掛ける探索かの判定は同じファイルの`uses_instability_scaling`に、印そのものは`time.rs`の`PreviousSearch`にある。

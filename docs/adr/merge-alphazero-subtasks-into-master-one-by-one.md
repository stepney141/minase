# AlphaZero型探索のサブタスクは統合ブランチに集めず、1本ずつmasterへマージする

## ステータス

承認済み。決定日は2026年10月27日。

## コンテキスト

[AlphaZero型探索の統括計画](../plans/alphazero.md)は、作業を6本のサブタスクに分ける。
2026年10月26日の計画では、サブタスクの実装をmasterから切った統合ブランチ`alphazero`に集め、到達の判定で`H0`となったネットとともに、数か月後にmasterへ一括で統合するとしていた。
理由は、[ランダム初期化の評価関数では探索が止まらない](../lessons/random-init-net-stalls-search.md)の教訓に従い、推論のコードを学習済みの重みより先にmasterへ入れないことであった。
この教訓は、既定の評価関数をランダム初期化のネットに替えた結果、既定の探索のbenchとテストが止まった事例から得たものである。

サブタスク1を統合ブランチへマージした時点で、統合ブランチを保つ負担が明らかになった。
設計書と測定記録はmaster、コードと手引きは統合ブランチに分かれて、設計書から手引きへリンクを張れなかった。
サブタスクの設計書は、最後の一括統合まで数か月の間、凍結できなかった。
統合ブランチを保つには、masterの変更を取り込み続ける必要があった。

## 決定

各サブタスクは、masterからブランチを切って実装し、完了時にmasterへマージして、設計書を凍結する。
masterへマージする前に、αβ探索の深さ6のbench（起動引数`--search`の実装後は`--search alphabeta`）の局面ごとのノード数、最善手、および評価値が、直前のmasterと一致することを確かめる。

## 検討した代案

統合ブランチに集めて最後に一括で統合する案は、上の負担に見合う利点がないので廃止した。
MCTSは起動引数`--search mcts`と`--nn-model`を指定したときだけ動き、既定の探索はαβ探索のままなので、学習済みの重みがない段階のコードがmasterにあっても、既定の探索のbenchとテストは変わらない。
MCTSの試験は一様評価器で行うので、教訓の事例のような既定の探索の停止は起きない。

## 結果

サブタスクの成果は、完了のたびにmasterで使え、設計書もそのたびに凍結できる。
到達の判定に使うネットを埋め込むコミットだけは、判定で`H0`となったときにmasterへマージする。
学習済みの重みがない期間も、MCTSと推論のコードはmasterにある。
このコードは、既定の探索のbenchの一致で既存の動作を変えないことを確かめてからマージする。

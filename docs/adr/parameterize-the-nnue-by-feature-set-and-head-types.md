# NNUEを入力特徴集合と出力部の型引数で組み立てる

## ステータス

承認済み。決定日は2026年10月12日。

## コンテキスト

入力特徴集合とは、局面と視点から第1層のどの行を発火させるかを定める規則であり、出力部とは、両視点の第1層の出力から評価値を計算する部分である。
基底特徴は駒状態、陣営、および升の組に先獅子の対象升を加えた13,680個の特徴であり、文脈は視点ごとに特徴の番号付けを決める値である。
[NNUEによるPST＋FMの完全代替](../plans/archived/nnue-replacement.md)を始めた時点のNNUEの推論は、王の位置で条件付けないP型の入力特徴集合に固定されていた。
同計画は、P型と自玉の位置で条件付けるHalfKP-hm-b8の2つを比べる必要があり、後続の計画も別の入力特徴集合や出力部を試す可能性があった。
入力特徴集合を変えるたびに、推論、重みファイルの形式、および学習器を作り直すと、比較のたびに実装の誤りが入り得る。
[設計書の参考資料](../plans/archived/nnue-replacement.md#参考資料)に挙げたtataraは、入力特徴集合を1つの仕様として表し、重みファイルのヘッダに構造を表す文字列（構造記述文字列）を入れて読み込み時に照合する。

## 決定

NNUEの型を、入力特徴集合の`FeatureSet`トレイトと出力部の`Head`トレイトの2つの型引数で総称化し、探索は`ActiveFeatureSet`と`ActiveHead`の型の別名で具体化した1つの組だけを使う。
特徴番号は、どの入力特徴集合でも「文脈の区分番号×13,680＋文脈に応じて写した基底特徴の番号」の形にそろえ、重みファイルは構造記述文字列を型から組み立てた文字列と照合し、一致しなければ拒否する。
トレイトの契約は`FeatureSet`と`Head`のdocコメントに、照合の規則は`Network::decode`のdocコメントにある。

## 検討した代案

v0、PST、NNUEなどの評価関数を実行時に切り替えるトレイトの抽象化は採らなかった。
本決定は1つのNNUEの内部をコンパイル時に組み立てるだけであり、どのコミットでも探索が使う評価関数は1つで、型の組合せどうしの比較はコミット対コミットの対局で行う。
入力特徴集合ごとに推論と重みファイルの形式を別々に書く案は、比較のたびに作り直しが要るので採らなかった。
学習器に特徴の番号付けを別に実装する案は、推論と学習の番号付けがずれる危険があるので採らなかった。

## 結果

特徴番号の形をそろえたので、差分更新は文脈が変わらなければ基底特徴の増減を写すだけで済み、学習時の特徴分解（区分によらない共通の行を各特徴の行に足す手法）とPSTからの初期化も入力特徴集合によらず同じ手順になる。
テストは型の別名によらず、すべての組を具体化して復号と推論を検査できる。
埋め込んだ重みファイルが探索の組と一致しなければ、起動時の検証で停止する。
学習器は、`minase::eval::features`と`FeatureSet`の実装を推論と共有する。

# PV-MCTSの根の候補手ごとの統計は、既定で無効のUSIオプション`VerboseMoveStats`で、探索の終わりに1回だけ出す

## ステータス

承認済み。決定日は2026年11月17日。

## コンテキスト

PV-MCTSは、`--search mcts`で起動したminaseの探索方式であり、探索の終わりに最善手、評価値、および読み筋だけを出す（[MCTSの対局の探索のADR](search-mcts-games-by-puct-with-virtual-loss-batches.md)）。
このため、対局でPV-MCTSが不自然な手を指しても、ほかの候補手を何回読んだか、どの手で探索の平均の勝率Qとネットの1回の評価が食い違っていたかが分からなかった。
対局サイトlishogiのBotや対局ハーネスでの探索は時間で区切られるので、同じ探索を後から再現することもできない。

[エンジン開発のデバッグ手法の調査](../research/engine-debugging-survey.md)は、チェス、囲碁、および将棋の7つのPV-MCTSエンジンのうち6つが、根の候補手ごとの統計を出す専用の表示を持つことを確かめた。
探索に付随して自動で出す方式は、チェスのlc0の`VerboseMoveStats`とMontyの`report_moves`、将棋のdlshogiの`DebugMessage`の3つのオプションにある。
探索の後に送るコマンドで照会する方式は、チェスのCeresの`dump-move-stats`だけにある。
表の列は、着手、訪問回数、およびQを4つのエンジンが、ネットの方策から求めた事前確率を3つが、確定した勝敗を3つが出し、子の局面のネットの価値Vと、手を選ぶ式PUCTの探索項U、Qに探索項を足した選択の得点S、および評価を待っている訪問の数はlc0だけが出す。
判断の詳細は[PV-MCTSのデバッグ道具の設計書](../plans/archived/mcts-debugging-tools.md)の「設計判断」の節にある。

## 決定

MCTSだけが真偽値のUSIオプション`VerboseMoveStats`（既定値false）を宣言し、有効なときは、探索が終わるたびに1回だけ、最後の`info`の行の後、`info string stop`の行の前に、根の要約1行と根の全候補手の表を`info string movestats`の行で出す（2026年11月17日のエンジンの開発者の決定）。
表の列は、着手、訪問回数、勝率の和、Q、事前確率、V、および確定した勝敗とし、行は最善手を選ぶ規則と同じ比較の降順に並べる。
要約は、今回のシミュレーション数、前の探索から持ち越した訪問数、根の辺の訪問回数の和、根の局面のV、根の確定した勝敗、探索木の使用量と容量、経過時間、および時間の予算を含む。
浮動小数点の値は、往復変換で同じ値に戻る最短の10進表記で出す。

## 検討した代案

探索の後に送る独自コマンドで探索木を照会する案（Ceres）は採らなかった。
対局中に時間で区切られた探索には、後からコマンドを送る機会がないからである。
オプションなら、起動引数`--io-log`で記録した対局のログに、その探索の統計が残る。
オプションとコマンドの両方を作る案も、同じ情報に入口を2つ作り、探索木を保持する期間の仕様まで要るので採らなかった。

探索項U、選択の得点S、および評価待ちの訪問数の列は加えなかった。
UとSを出すには、シミュレーションのたびに経路の各節点で呼ばれる手の選択の関数から、得点だけを計算する関数を切り離す必要があり、1つのエンジンの先例のために探索の最も頻繁に通る処理を変えることになる。
評価待ちの訪問数は、探索のループが集めた葉を評価してから停止を判定するので、探索の終わりには常に0である。
1つのエンジンにしか先例のない列のうち、Vは探索木の節点に保存済みの値を取り出すだけで済むので加えた。
先例のない勝率の和は、Qが一致しても勝率の和が一致するとは限らないので、固定局面の探索による回帰の検出（[`bench`のADR](run-bench-with-the-launched-search-and-detect-pv-mcts-regressions-with-a-hash-evaluator.md)）のために加えた。

方策のlogit（正規化する前の値）の列は加えなかった。
探索木が持つlogitは方策の温度（確率の偏りを調整する定数）で割った後の値なので、ネットの生のlogitを出す独自コマンド`eval`の値と食い違って誤読を招く。
各候補手の読み筋は、上位N手の読み筋を出すMultiPVの設計書（[multipv.md](../plans/multipv.md)）が扱う。
評価値（cp）の列は、勝率を評価値へ換算する勝率尺度がセッションの設定に依存するので加えず、勝率だけを出す。

根より下の部分木を指定して表示する案と、木の全節点を書き出す案（Ceresの`dump-store`）は採らなかった。
チェスと将棋のエンジンでは1つにしか先例がなく、新しい出力の仕様が要るので、根の表では調べられない具体的な不具合が出たときに別に計画する。
探索中に統計を定期的に出す案（lc0の`LogLiveStats`）は、PV-MCTSは探索の終わりにだけ`info`を出すという規則を保つために採らなかった。

## 結果

オプションが無効なら、出力と探索の結果は変わらない。
有効にしても、`bestmove`、`info`の行、および次の探索での木の付け替えの結果は変わらない。
対局ハーネスは`info string stop`のような既知の語の行だけを読むので、`movestats`の行は対局の記録を乱さない。
持ち越した訪問数は新しいフィールドを足さずに、根の辺の訪問回数の和Rと今回のシミュレーション数Sから R − (S − 1) で求めるので、この式が成り立たない探索の終わり方を加えるときは、式と出力を見直す。
各欄の定義と出力の順は`crates/minase/src/search/mcts/move_stats.rs`と`crates/minase/src/protocol/usi.rs`のdocコメントにあり、使い方は[USIの独自拡張の手引き](../guides/usi-extensions.md)の「オプション」の節と[デバッグの手引き](../guides/debugging.md)にある。
行を並べる関数`Node::ranked_edges`は、MultiPVもPV-MCTSの候補手を並べるときに使う。

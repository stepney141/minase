# AlphaZero型探索の学習器は、規則セットlishogiのMNSDだけを訓練に受け付け、Rustの拡張モジュールで読み、利きの面を拡張モジュールで作り、駒の面と方策のラベルはPythonでバッチごとに作る

## ステータス

承認済み。決定日は2026年11月16日。
[規則`JCSA`のファイルを訓練に受け付けていたADR](archive/read-mnsd-into-the-zero-trainer-and-build-control-planes-in-a-rust-extension.md)を置き換える。

## コンテキスト

強化学習の教師データは形式MNSDで記録され、局面の復元には中将棋の着手の適用と合法手の生成が要るので、PyTorchの学習器はMNSDを単体では読めない。
置き換えたADRは、PyO3の拡張モジュール`minase_mnsd_reader`で訓練局面を読み、入力の利きの面を拡張モジュールで作ると定め、訓練に受け付ける規則を日本中将棋連盟の規則に基づく`JCSA`（規則コードL0＋P0＋R1＋E0）としていた。
2026年11月13日に、2回目の学習の自己対局を、オンライン対局サイトlishogiの実装に近い規則セット`lishogi`（L1＋L2＋P0＋P3＋R1＋E1＋E3、[競技規則](../rules/chu-shogi.md)第33条第6項）で行うと決まった（[規則のADR](play-self-play-and-judge-trained-networks-under-the-lishogi-rule-set.md)）。
2回目の学習の自己対局の生成器は、これに従って教師データのヘッダに`lishogi`の規則コードを書く。
入力の159面だけで次の合法手が決まるのは、成り権の保留を追跡する規則P1、P2、P5と、対局の経過によって着手を禁じる反復の規則R2、R3を、どれも含まない規則セットに限られる（[入力のADR](encode-zero-network-inputs-as-159-planes-with-pseudo-control-from-the-side-to-move.md)）。
`lishogi`はこの5つの規則をどれも含まないので、`lishogi`の教師も同じ入力と拡張モジュールで読める。

## 決定

MNSDは、`minase::training::records::Reader`を包むPyO3の拡張モジュール`minase_mnsd_reader`（`tools/train/zero/mnsd_reader/`）で読む。
拡張モジュールは、除外の印がなく、価値と方策の候補の両方を記録した項目を訓練局面として選ぶ。
返すのは、局面ごとの盤の駒コード、手番、先獅子の升、価値、対局結果、根の総訪問回数、方策の候補、および全合法手である。
着手は正準形（移動元、経由升、移動先、成り）の列と局面ごとの区切りの位置で返し、Pythonの`minase_zero.encoding`が方策のラベルに直す。
全合法手は、学習の更新には使わず、最終の重みの診断（合法手の確率質量と方策の一致率）と固定の検証用データの診断に使う。
入力のうち駒の95面はPythonがバッチごとにGPUの上で作り、利きの64面は拡張モジュールが盤の配列から、推論器と同じRustの関数を呼び出して作る。
拡張モジュールは、学習器の環境定義におけるuvのpath依存としてmaturinでビルドし、PyO3への依存はCargoのフィーチャ`python`を有効にしたときだけ入れる。

学習器は、教師の種類がMCTS、由来が乱数開始の自己対局、規則が`lishogi`であるファイルだけを訓練に受け付け、リプレイバッファに同じパスまたは同じ（基本シード、対局番号）の対局が2回現れたらエラーとする。
規則の照合は、ヘッダの規則の文字列ではなく、解釈した規則コードの組で行うので、規則名`lishogi`とそのコード列のどちらで書いたファイルも受け付ける。
受け付ける規則は引数で選ばない。
拡張モジュールは、解釈した規則が`lishogi`と一致するかを返し、`JCSA`と一致するかは返さない。

## 検討した代案

受け付ける規則を引数で選べるようにする案は採らなかった。
2回目の学習の全サイクルが同じ規則を使い、別の規則で学習する予定がないので、引数を足しても、実行器と起動スクリプトの受け渡しが増えるだけである。

`JCSA`と`lishogi`の両方を受け付ける案も採らなかった。
2つの規則の教師が1つのリプレイバッファに混ざると、ネットは学んだ規則とは別の規則で強さを測られる。

利きの面をPythonで計算する案と、利きの面をMNSDに書く案は、置き換えたADRと同じ理由で採らなかった。
前者は推論の符号化との一致をPythonの側で保つ必要を生み、後者は1局面あたり約1.2 KB増え、符号化を変えるたびに教師データを作り直すことになる。
159面を拡張モジュールの中で実体化して返す案も、置き換えたADRと同じく採らなかった。
リプレイバッファから抽出した局面を159面の単精度で展開すると、1局面あたり約92 KBになるので、盤の配列のまま保持してバッチごとに展開する。

## 結果

1回目の学習の`JCSA`の教師データは、この学習器では訓練に読めない。
学習器の試験が読む固定データ`tools/train/zero/fixtures/zero-selfplay-small.mnsd`も`JCSA`で作ったものだったので、`lishogi`で生成する生成器で作り直した（作り方は[ファイル形式の手引き](../guides/file-formats.md)）。
拡張モジュールが返す局面の列が固定局面集の入力と一致することは、Rustの試験とPythonの試験で確かめる。
探索なしで記録した固定の検証用データを読むときは、拡張モジュールが指した手を確率1の候補として、訓練のファイルと同じ形の局面を返す。
成り権の保留を追跡する規則セットで学習する場合は、入力の面と拡張モジュールの受け入れの検査を変える必要がある。

# AlphaZero型探索の学習器は、MNSDをRustの拡張モジュールで読み、利きの面と対局全体から決まる教師を拡張モジュールで作り、駒の面と方策のラベルはPythonでバッチごとに作る

## ステータス

承認済み。決定日は2026年10月31日。
[拡張モジュールで読むADR](archive/read-mnsd-into-the-zero-trainer-through-a-rust-extension.md)を置き換える。

## コンテキスト

強化学習の教師データは形式MNSDの版2で記録され、局面の復元には中将棋の着手の適用と合法手の生成が要るので、PyTorchの学習器はMNSDを単体では読めない。
初版は、PyO3の拡張モジュール`minase_mnsd_reader`で価値を持つ項目を読み、入力の95面と方策のラベルはPythonでバッチごとに作った。
[学習技法の導入の設計書](../plans/archived/alphazero-restart-techniques.md)で、入力に駒種ごとの利きと利き数の64面を足し、方策を記録しない速い探索の手番を加え、対局全体を見て決まる補助目標（短期の価値、相手の次の手）を学ぶことにした。
利きの判定は中将棋の規則そのものであり、Pythonで実装し直すと推論との不一致を生む。
補助目標の教師は、抽出した局面より後の手番の記録から決まり、学習器は窓のファイルを先頭から再生しながら抽出した局面だけを残す。

## 決定

MNSDは、`minase::training::records::Reader`を包むPyO3の拡張モジュール`minase_mnsd_reader`（`tools/train/zero/mnsd_reader/`）で読む。
拡張モジュールは、除外の印がなく、価値と方策の候補の両方を記録した項目を訓練局面として選ぶ。
返すのは、局面ごとの盤の駒コード、手番、先獅子の升、価値、対局結果、根の総訪問回数、方策の候補、全合法手に加え、短期の価値の目標3つ、次の手番の方策の候補、および次の手番の局面の全合法手である。
短期の価値の目標は、対局ごとに項目を末尾から先頭へたどって求め、速い探索の項目の価値も使う。
着手は正準形（移動元、経由升、移動先、成り）の列と局面ごとの区切りの位置で返し、Pythonの`minase_zero.encoding`が方策のラベルに直す。
次の手番の着手は、手番tの側を指定してラベルに直すことで、手番tの側から見た座標になる。
入力のうち駒の95面はPythonがバッチごとにGPUの上で作り、利きの64面は拡張モジュールの関数が盤の配列から推論と同じRustの関数で作る。
拡張モジュールは学習器の環境定義のuvのpath依存としてmaturinでビルドし、PyO3への依存はCargoの機能`python`を有効にしたときだけ入れる。
学習器は、教師がMCTSで、由来が乱数開始の自己対局で、規則が`engine-default`と同じファイルだけを訓練に受け付け、学習窓に同じパスまたは同じ（基本シード、対局番号）の対局が2回現れたらエラーとする。

## 検討した代案

利きの面をPythonで計算する案は採らなかった。
中将棋の利き（獅子、角鷹、飛鷲の2段階と走りの遮蔽）を再実装すると、推論の符号化との一致をPythonの側で保つ必要が生じる。

利きの面と補助目標の教師をMNSDに書く案は採らなかった。
利きの面は1局面あたり約1.2 KB増え、教師の作り方を変えるたびに教師データを作り直すことになる。

159面を拡張モジュールの中で実体化して返す案は採らなかった。
学習窓の抽出の約400万局面を単精度で展開すると約370 GBになるので、盤の配列のまま保持してバッチごとに展開する。

## 結果

拡張モジュールが返す局面の列が固定局面集の入力と一致することは、Rustの試験とPythonの試験が確かめる。
相手の次の手の候補と全合法手が加わったので、データセットのメモリは1局面あたり28＋4C＋2Lバイト（Cは相手の候補数、Lは相手の局面の合法手数）増える。
αβ探索の教師データ（固定の検証用棋譜）は、全項目が指した手を確率1とする印を持つので、選別の定義を改めた後も同じ局面を返す。
成り権の保留を追跡する規則セットで学習する場合は、入力の面と拡張モジュールの受け入れの検査を変える必要がある。

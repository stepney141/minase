# 対局ハーネスと係数調整は、エンジンがisreadyで返すネットのチェックサムを実行条件に記録し、対局の開始時と再開時に照合する

## ステータス

承認済み。決定日は2026年11月17日。[対局ハーネスは、エンジンが`isready`で返すネットのチェックサムを実行条件に記録し、対局の開始時と再開時に照合する](archive/record-and-verify-the-network-checksum-reported-by-match-engines.md)を置き換える。

## コンテキスト

対局ハーネス`minase match run`は、比べる2つのエンジン（候補と基準）の同一性を、実行条件の記録`manifest.json`に残す。
[以前の決定](archive/record-and-verify-the-network-checksum-reported-by-match-engines.md)は、エンジンが`isready`から`readyok`までの間に`info string network_sha256 <64桁の16進数>`で返すネットのチェックサムを、エンジンごとの欄`network_sha256`に記録し、対局の開始時と再開時に照合すると定めた。
当時この行を返したのは、ONNXのネットをオプション`NnModel`で受け取るPV-MCTSのエンジンだけだった。
係数調整`minase spsa`は、ネットを埋め込んだαβ探索の調整用のビルドだけを対局させていたので、記録に欄を足していなかった。

その後、αβ探索もNNUEのネットをオプション`EvalFile`で外部のファイルから読み、同じ行でファイル全体のSHA-256を返すようになった（[外部ファイル化のADR](archive/use-an-nnue-read-from-evalfile-as-the-only-search-evaluation.md)、[識別子のADR](identify-nnue-networks-by-the-sha256-of-the-whole-file.md)）。
係数調整でも、同じパスのネットのファイルを調整の途中や再開の前に書き換えると、記録と実際に対局したネットの対応が失われる。
CECPで起動するminaseも`option EvalFile=`でネットを受け取るので、対局ハーネスはCECPのエンジンにも追加のオプションを送るようになった。
この改訂は[NNUEの外部ファイル化の設計書](../plans/archived/nnue-external-network-file.md)で下した。

## 決定

対局ハーネスと係数調整は、エンジンが`isready`から`readyok`までの間に返すチェックサムを、`manifest.json`の欄`network_sha256`に保存し、行を返さないエンジンでは明示的に`null`を書く。
係数調整は、全対局で固定するUSIオプション（引数`--option <名前>=<値>`）の列も`manifest.json`に保存し、各対局で調整する係数の`Tune_*`の列の前に送る。
どちらも、設定と同一性を確かめるためにエンジンを1回ずつ起動し（以下、事前の起動）、測定の開始時には事前の起動で得た値を記録する。
再開時の事前の起動と各対局の開始時には、得た値を記録と照合し、異なれば測定をエラーで止める。
欄の定義と照合の規則は、`crates/minase/src/harness/`、`crates/minase/src/bin/minase/match_runner/`、および`crates/minase/src/bin/minase/spsa_runner/`のdocコメントにある。

## 検討した代案

パスだけを記録して、ファイルを上書きしない運用に頼る方式は、書き換えを検出できないので採らなかった。
ハーネスがオプションの値をパスとして読み、自分でチェックサムを計算する案は、どのオプションがネットを指すかをハーネスが知ることになるので採らなかった。
エンジンが返す値は、探索や推論に実際に使うバイト列から計算した値でもある。

不一致をその側の反則負けにする案は採らなかった。
不一致は、エンジンの異常ではなく、測定の条件が崩れたことを表し、反則負けにすると条件の崩れを勝敗の統計に混ぜてしまう。

事前の起動を握手だけにとどめ、最初の対局で得た値を記録する案は採らなかった。
同時に始まる複数の対局のどれを正とするかが決まらず、測定の開始より前に条件を確定できないからである。

係数調整で、固定のオプションをネットのパスの引数`--eval-file`に限る案は採らなかった。
PV-MCTSの係数を調整するときには`NnModel`と勝率尺度の`NnCpPerLogit`も渡す必要があり、同じ仕組みを2度作ることになる。

## 結果

同じパスのネットのファイルを書き換えると、次の対局の開始時、または再開時に測定が止まる。
止まった測定は、それまでに終わったペア（同じ開始局面で先後を入れ替えた2局）の記録を保ち、ファイルを元に戻せば再開できる。
エラーで終わった測定には、正常に終わらなかった起動があることを示す印が付き、`minase match report`が測定の所要時間を見積もるために行う校正用の集計には使えない。

事前の起動は、対局の開始時と同じ初期化の列を送って`isready`まで進める。
このため、PV-MCTSのエンジンでは、測定の開始時と再開時に推論器の作成が1回ずつ増える。
作成にかかる時間は応答の期限（`--response-timeout`）に含まれるので、TensorRT（NVIDIAのGPU向けの推論の基盤）が初回にネットをGPU向けに最適化する処理が期限を超える場合は、期限を延ばして実行し直す。
CECPで起動するエンジンも、事前の起動で対局の開始時と同じ初期化の列を送り、`ping`への`pong`を受けるまで進めるので、`EvalFile`の誤りや、エンジンが宣言していないオプションは最初の対局より前に見つかる。
CECPにはチェックサムを報告する手段がないので、CECPのエンジンと、事前の起動を行わない校正用のランダム着手エンジンの欄は`null`になる。
係数調整の`manifest.json`に欄を足したので、それより前の形式の`manifest.json`からは再開できない。

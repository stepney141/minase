# 対局ハーネスは、エンジンが`isready`で返すネットのチェックサムを実行条件に記録し、対局の開始時と再開時に照合する

## ステータス

承認済み。決定日は2026年11月12日。

## コンテキスト

対局ハーネス`minase match run`は、比べる2つのエンジン（候補と基準）の同一性を、実行条件の記録`manifest.json`に残す。
`commit:<コミット>`で指定したエンジンについては、実行ファイルのチェックサム（SHA-256）を記録し、再開のときに照合している。
一方、AlphaZero型探索のMCTSが使うニューラルネット（以下ネット）は、ファイルのパスだけが記録に残っていた。
同じパスのファイルを測定の途中や再開の前に書き換えると、記録と実際に対局したネットの対応が失われる。
これまでは、ネットをサイクル番号つきのファイル名で保持して上書きしない運用で防いでいた。

ネットの指定が起動引数からUSIのオプション`NnModel`へ移り（[ネットをオプションで指定する決定](select-zero-networks-by-the-usi-option-nnmodel.md)）、エンジンは`isready`で読み込んだネットのチェックサムを`info string network_sha256 <64桁の16進数>`の行で返すようになった。
この判断は[起動引数と診断ツールをUSIへ移す計画](../plans/archived/cli-to-usi.md)で下した。

## 決定

ハーネスは、エンジンが`isready`から`readyok`までの間に返すチェックサムを、`manifest.json`のエンジンごとの記録の欄`network_sha256`に保存する。
行を返さないエンジンでは、欄に明示的に`null`を書く。
ハーネスは、対局を始める前に、設定と同一性を確かめるためにエンジンを1回ずつ起動する（以下、事前の起動）。
測定の開始時には、事前の起動で得た値を記録する。
再開時の事前の起動と各対局の開始時には、得た値を記録と照合し、異なれば測定をエラーで止める。
欄の定義と照合の規則は、`crates/minase/src/harness/`と`crates/minase/src/bin/minase/match_runner/`のdocコメントにある。

## 検討した代案

パスだけを記録して、ファイルを上書きしない運用に頼る方式は続けなかった。
書き換えを検出できないからである。

ハーネスがオプションの値をパスとして読み、自分でチェックサムを計算する案は採らなかった。
どのオプションがネットを指すかを、ハーネスが知ることになるからである。
エンジンが返す値は、推論に実際に使うバイト列から計算した値でもある。

不一致をその側の反則負けにする案は採らなかった。
不一致は、エンジンの異常ではなく、測定の条件が崩れたことを表す。
反則負けにすると、条件の崩れを勝敗の統計に混ぜてしまう。

事前の起動を握手だけにとどめ、最初の対局で得た値を記録する案は採らなかった。
同時に始まる複数の対局のどれを正とするかが決まらず、測定の開始より前に条件を確定できないからである。

## 結果

同じパスのネットのファイルを書き換えると、次の対局の開始時、または再開時に測定が止まる。
止まった測定は、それまでに終わったペア（同じ開始局面で先後を入れ替えた2局）の記録を保ち、ファイルを元に戻せば再開できる。
エラーで終わった測定には、正常に終わらなかった起動があることを示す印が付き、`minase match report`が測定の所要時間を見積もるために行う校正用の集計には使えない。

事前の起動は、対局の開始時と同じ初期化の列を送って`isready`まで進める。
このため、MCTSのエンジンでは、測定の開始時と再開時に推論器の作成が1回ずつ増える。
作成にかかる時間は応答の期限（`--response-timeout`）に含まれるので、TensorRT（NVIDIAのGPU向けの推論の基盤）が初回にネットをGPU向けに最適化する処理が期限を超える場合は、期限を延ばして実行し直す。
事前の起動を行わない校正用のランダム着手エンジンと、CECPで起動するエンジンは、欄が`null`になる。
係数調整`minase spsa`は、調整用のビルドのαβ探索だけを対局させるので、記録に欄を足していない。

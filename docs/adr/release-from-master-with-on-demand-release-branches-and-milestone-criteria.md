# masterへのトランクベース開発を維持し、必要時だけrelease/*ブランチを切り、出口条件でリリースする

## ステータス

承認済み。決定日は2026年11月21日。

## コンテキスト

従来の運用では、すべての変更を`master`へ統合し、エンジンの開発者が区切りのよいと感じた時点でタグを打ってリリースしていた。
`v2.6.0`（2026年10月25日）の後、`master`には起動引数の廃止、`EvalFile`の外部ファイル化、およびtatara形式への移行など10件以上の破壊的変更が積み上がり、NNUEの世代反復が終わるまでエンジンが一時的に弱くなる期間も生じた。
一方で別リポジトリの`minase-lishogi-bot`は`v2.6.0`を固定して公開運用しており、`master`から`v2.6.1`の不具合修正を直接出せない状態になっていた。
また、リリース時期の基準が明文化されていなかったため、変更の滞留や途中撤回コミットの混在が起きやすかった。

## 決定

日常の開発は`master`を中心とするトランクベース開発を維持し、常設の`develop`ブランチは作らない。
既公開版のパッチ保守または次期版の安定化が必要なときだけ`release/*`ブランチを切り、`release.toml`の`allow-branch`で`master`と`release/*`の両方を許可する。
リリースの判断はクレートごとの出口条件で行い、`minase`の正式版は互換性変更の確定、検査と手動確認の通過、および探索・評価変更時の棋力確認を必須とし、途中の検証には`-alpha.N`と`-rc.N`を使い分ける。

## 検討した代案

`main`と`develop`を常設するGit Flowを採る案は、個人開発の規模に対して常設ブランチ間の統合と同期の手間が増え、計画書ごとのworktree運用とも二重管理になるため採らなかった。

毎月など固定の暦でリリースを切る定期リリース（リリース列車方式）を採る案は、NNUEやAlphaZero型探索の学習周期が一定ではなく、学習途中で一時的に弱い状態のまま正式版を出す恐れがあるため採らなかった。

## 結果

日常の統合手順を変えずに、旧版へのパッチ提供（例: `release/2.6`からの`v2.6.1`）と次期版の安定化（例: `release/3.0`での`-rc.N`検証）を`master`の研究開発と分離できるようになった。
また、正式版の変更履歴は公開前に要約を添えて途中撤回コミットを整理する運用とし、利用者が変更点の全体像を把握しやすくした。
具体的な手順と手動確認一覧は[リリースの手引き](../guides/release.md)にある。

# 規則セットを排他群ごとの列挙型で表し、着手規則と対局規則の2層に分ける

## ステータス

承認済み。決定日は2026年8月25日。

## コンテキスト

規則コードは、獅子、成り、反復、および駒枯れの4つの排他群と、群に付け加える修飾規則に分かれる（RULES.md第33条第2項）。
[規則集合の代数的データ型化](../plans/rules-type.md)の前の`Rules`は規則コードのビット集合であり、群の中の排他は`from_codes`が排他の組の表で実行時に検査していた。
反復規則の欠落は対局の構築時に別のエラーとして検査されたので、反復規則を持たない標準規則の値は、作ることはできても対局を構築できない値として存在していた。
規則セットは起動引数`--rules`で実行時に切り替える必要がある。

## 決定

排他群を列挙型で、修飾規則を真偽値のフィールドで表し、不正な組合せを構築できない値型にする。
獅子規則と成り規則だけを持つ着手規則`MoveRules`と、それに反復規則、駒枯れ規則、およびE1を加えた対局規則`Rules`の2層に分ける。
規則コード列の意味の検証は`Rules::from_codes`だけが行い、報告するエラーの種類は`RulesError`のdocコメントにある。

## 検討した代案

規則を型パラメータにしてtypestateやconst genericsで表す案は採らなかった。
規則は実行時に切り替えるので、全組合せを単相化するのは測定なしの最適化にあたるからである。
ビット集合を残し、コードの採否を問う`contains`を互換の層として残す案も採らなかった。
`match`の網羅性の検査が効かず、ビット集合の時代の書き方が残るからである。
構築のためのビルダーやセッターは、構造体リテラルと定数で足りるので設けなかった。

## 結果

`Position`、`MoveGenerator`、探索、局面表記、および直前局面生成器は`MoveRules`だけを受け取り、反復規則と駒枯れ規則を参照できない。
`Game`は反復規則が型で保証されるので失敗しない構築関数を持ち、反復規則の欠落を表すエラー型は不要になった。
規則コード列は各群から1つを明示する必要があるが、規則コードP0とE0を導入する前の過去のコミットは、全群を明示したコード列を拒否する。
このため、新旧のコミットを対局させる対局ハーネスは`--rules`の入力原文を両エンジンへそのまま渡し、各コミットが自分の語彙で解釈する（[SPRTの手引き](../guides/sprt.md)の「エンジンの指定方法」）。

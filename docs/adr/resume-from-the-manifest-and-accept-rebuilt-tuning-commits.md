# 再開は実行条件を`manifest.json`だけから読み、SPSAではコミット指定の調整対象のビルドし直しを受け入れる

## ステータス

承認済み。決定日は2026年10月18日。[再開は実行条件を`manifest.json`だけから読み、runnerと測定機を照合しない](archive/resume-from-the-manifest-without-checking-the-runner.md)（2026年10月5日）を置き換える。

## コンテキスト

`minase match run`と`minase spsa`は、中断した実行を`--resume`で再開できる。
2026年10月5日の旧ADRは、再開の実行条件をすべて`manifest.json`から読み、対局を進める実行ファイル（runner）と測定機は照合せず、対局するエンジンの実行ファイルのSHA-256だけを照合すると決めた。
runnerを照合しない理由は、[補助ツールのサブコマンド化](../plans/archived/cli-subcommands.md)でrunnerがエンジンと同じ`minase`になり、探索や評価だけの変更でもrunnerのSHA-256が変わるからである。
fishtest、fastchess、cutechess-cli、およびAyaneも、再開時にrunner自身のハッシュを照合しない（[再開条件の簡素化の参考資料](../plans/archived/match-resume-simplification.md#参考資料)）。

2026年10月18日、[探索の関数形の見直しの統括計画](../plans/archived/search-forms.md)で、SPSAをvast.aiで借りる計算機（以下、調整機）で実行することにした（[調整機のADR](run-spsa-on-rented-machines-with-nps-scaled-time-controls.md)）。
調整用ビルドは`.cargo/config.toml`の`target-cpu=native`で機械ごとにビルドされるので、同じコミットでも実行ファイルのSHA-256は機械ごとに変わる。
旧ADRのままでは、調整機が途中で失われたときに、最初の調整機の実行ファイルを持ち込める同じCPU型の機械でしか再開できない。
エンジンの開発者は、SPSAを完遂できればよく、新しい機械では都度ビルドし直せばよいと判断した。

## 決定

`--resume`は実行条件をすべて`manifest.json`から読み、再開時に条件を変える引数は、`minase match run`でペア数の目標を引き上げる`--target-pairs`だけとする。
runnerの版とSHA-256、および測定機は照合せずに、起動ごとに`invocations.json`へ記録する。
対局するエンジンは、次のとおり照合する。

- `minase spsa`の調整対象を`commit:`の形式で指定した場合は、記録したコミットのハッシュと、再開時に解決したコミットのハッシュの一致だけを確かめる。実行ファイルのSHA-256が記録と違えば、両方の値を標準エラーへ1行で通知して再開する。
- `minase spsa`の調整対象を起動コマンドの形式で指定した場合と、`minase match run`のエンジンは、実行ファイルのSHA-256を照合する。
- 合法手から一様ランダムに指す`random`は、SHA-256を照合せずに指定の種類だけで同一とみなす。

記録形式の版4の実行ディレクトリは、集計などの読み取りだけに受け付け、再開は拒む。
手順の詳細は、`RunStore::resume`、`match_runner`の`resume`モジュール、および`spsa_runner`の`engine`モジュールの`restore_engine`のdocコメントに従う。

## 検討した代案

`minase spsa`でも実行ファイルのSHA-256を照合し続け、最初の調整機の実行ファイルを同じCPU型の機械へ持ち込んで再開する案は、再開できる機械が出品の状況に左右され、エンジンの開発者の判断にも合わない。
コミット指定の調整対象のSHA-256の照合を`minase match run`でも外す案は、測定機での採否の測定で、ツールチェーンの更新などによるビルド結果の変化を見逃すので採らない。
起動コマンドの形式で指定した調整対象の照合を外す案は、その実行ファイルが何であるかを確かめる手段がSHA-256しかないので採らない。

旧ADRで棄却した案は、この決定でも棄却したままとする。
runnerが自分の実行ファイルをハッシュをキーにした置き場へ保存し、ハッシュが異なる再開ではそのパスを示して止める案は、先行例のない照合を保つために保存と手順を増やすので採らない。
対局の進行を統括するrunnerをPythonのスクリプトへ移す案は、スクリプトが呼ぶ`minase`の同一性の照合が残るので、問題を解消しない。
再開時に同時対局数を測定機に合わせて変える案は、時間制御の対局でエンジンが受けるCPUの競合が再開の前後で変わるので採らない。
版4の実行ディレクトリへ版5の起動の記録を書き足す案は、1つの実行ディレクトリに2つの形式が混ざるので採らない。

## 結果

作業ツリーの`minase`を再ビルドした後でも、測定とSPSAを再開できる。
起動の記録に複数のrunnerが現れた測定とセッションは、そのことを測定記録に書く。
`minase spsa`の`commit:`指定のセッションは、別のCPU型の調整機でビルドし直して再開できる。
その代わり、セッションの途中で調整用ビルドの実行ファイルが変わり得るので、再開の通知が出たセッションは、再開の回数と各機械を測定記録に書く。
`minase match run`では、ツールチェーンの更新などでコミットのビルド結果が変わるとエンジンの照合が失敗し、その測定は元のエンジンでなければ再開できない。
物理コア数の少ない測定機で再開すると同時対局数がコア数を超えることがあり、過剰な競合による時間切れは`time_forfeits`に現れる。
`minase match report`の校正用の指標は測定機ごとに意味が変わるので、全起動の測定機の記録が一致しない実行ディレクトリの集計は拒否する。
SPSAの総反復数は利得の式に入るので、`minase spsa --resume`には延長の引数を設けない。

# `bench`は起動した探索の方式で固定局面を探索し、PV-MCTSでは文字列のハッシュで方策と価値を決める評価器で固定回数だけ探索して、2つのコミットの出力の一致で回帰を検出する

## ステータス

承認済み。決定日は2026年11月17日。

## コンテキスト

αβ探索では、探索の結果を変えないはずの変更を、USIの独自コマンド`bench`の局面ごとのノード数が2つのコミットで一致することで確かめる。
PV-MCTSには同じ役割の道具がなく、`--search mcts`で起動したminaseの`bench`も、診断をUSIの独自コマンドにした時点（[診断のコマンドのADR](run-engine-diagnostics-as-usi-commands-and-keep-experiment-tools-as-subcommands.md)）から変わらずαβ探索を測っていた。
手を選ぶ式PUCTの係数の調整（[mcts-puct-spsa.md](../plans/mcts-puct-spsa.md)）と、上位N手の読み筋を出すMultiPV（[multipv.md](../plans/multipv.md)）のように、PV-MCTSのコードに触れる計画が控えている。

同じコマンドの名前で、起動した探索を測る形は、先行エンジンに共通する。
将棋エンジンやねうら王の`bench`は、局面ごとのコマンドの列をビルドしたエンジン自身の`go`に流すので、dlshogi系のふかうら王としてビルドするとPV-MCTSを測る。
チェスのlc0とCeresの`benchmark`、およびMontyの`bench`も、それぞれのエンジン自身の探索を測る。
調べたエンジンに、探索の方式ごとに別の名前の固定局面の探索のコマンドを持つものはない。
minaseの`eval`も、αβ探索で起動すれば評価関数NNUEの評価の内訳を、MCTSで起動すればネットの価値と方策を出す。
回帰の検出には、チェスのlc0がネットの入力のハッシュから方策と価値を決める評価器`random`を持ち、チェスのMontyが固定条件のbenchの総ノード数をコミットの本文の署名と照合する。
判断の詳細は[PV-MCTSのデバッグ道具の設計書](../plans/archived/mcts-debugging-tools.md)の「設計判断」の節にある。

## 決定

`bench`は起動した探索の方式に従う（2026年11月17日のエンジンの開発者の決定）。
αβ探索で起動したminaseの`bench`は変えない。
`--search mcts`で起動したminaseの`bench [nodes <N>] [batch <N>]`は、αβ探索の`bench`と同じ15局面を、規則セット`JCSA`、探索木の容量256 MiB、引き分けの勝率0.5、および新しく作ったMCTSと同じPUCTの係数と方策の温度で、対局と同じ探索のループに上限回数（既定800回）だけを与えて探索する。
評価器には、局面の文字列表記である拡張SFENから手数の欄を除いた局面の鍵と、USIの着手の表記から、64ビットのハッシュ関数FNV-1aで価値とlogitを決めるハッシュの評価器を使う。
出力は、探索の条件の行、局面ごとの最善手、停止理由、主変化、および根の全候補手の統計（[根の統計のADR](print-pv-mcts-root-move-statistics-once-at-the-end-of-search-through-verbosemovestats.md)と同じ書式）であり、同じ機械と同じ設定でビルドした2つのコミットの出力が、経過時間と速度の欄を除いて全行一致すれば、その変更は探索の結果を変えていないと判定する。

## 検討した代案

別の名前の独自コマンド（`mcts-bench`）を加え、`bench`をαβ探索だけに残す案は採らなかった。
同じ役割の診断に2つの名前ができ、先行エンジンにその形の先例がないからである。

学習済みのネットをCPUで推論して探索する案は採らなかった。
ONNX Runtimeとネットのファイルを要し、比較の結果がネットの選び方に依存するからである。
既存の一様な試験用の評価器を使う案は、全局面に価値0.5と一様な方策を返すため、訪問済みの辺の平均の勝率Qが0.5に揃い、ネットの評価の差による分岐を十分に試せないので採らなかった。

ハッシュの評価器をフィーチャ`test-util`の中に置く案は、αβ探索の`bench`と同じ通常のreleaseビルドで比べられなくなるので採らなかった。
推論の実行先を選ぶオプション`NnBackend`の選択肢にする案は、対局で選べる評価器が増えるので採らなかった。
ハッシュの入力を、局面を乱数の表で要約したZobristキーやネットの入力の符号化（lc0）にする案は採らなかった。
これらは表やネットの入力の変更で値が変わる内部の値であり、比べるコミットの間で評価器の出力が変わってしまう。
拡張SFENとUSIの着手の表記は、文法を[USIの独自拡張の手引き](../guides/usi-extensions.md)が定める外部の表記なので、探索の処理を変えるコミットでも変わらない。

期待出力をリポジトリにコミットして照合する案（KataGo）は、現在の出力を丸ごと保存して比べる試験を書かないという方針（[テストの手引き](../guides/testing-minase-rules.md)の「期待値の根拠」）に反するので採らなかった。
総ノード数をコミットの本文の署名と照合し、選択の経路の平均の深さで探索を止める案（Monty）も採らなかった。
根の全候補手の訪問回数と勝率の和を比べれば、上限の回数で止めても、木のどの深さでの配分の違いも、打ち消し合わない限り検出できるので、新しい停止条件は要らない。
比べるための専用のスクリプトは、出力の全行の比較で足りるので作らなかった。

## 結果

PV-MCTSの`bench`は、ネットもGPUもない機械で、規則の設定も`isready`も要らずに動く。
`bench`を呼ぶ既存のスクリプトは、どれもαβ探索で起動したminaseに送るので影響を受けない。
探索はsoftmax、対数、および平方根の浮動小数点の計算を含むので、機械をまたいだ出力の一致は求めない。
PUCTの係数や方策の温度の既定値を変えるコミットは出力も変えるので、最初の行に探索の条件を記録し、差が条件によるものか探索の処理によるものかを区別できるようにした。
ハッシュの評価器は通常のビルドに入るが、PV-MCTSの`bench`だけが使い、対局では選べない。
引数と出力の定義は`crates/minase/src/diagnostics/bench_mcts.rs`、評価器の契約は`crates/minase/src/nn/hash_evaluator.rs`のdocコメントにあり、比較の手順は[デバッグの手引き](../guides/debugging.md)にある。

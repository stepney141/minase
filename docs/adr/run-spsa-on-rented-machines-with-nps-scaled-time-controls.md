# SPSAは借りた計算機で、負荷時の速度の比で伸ばした持ち時間で実行する

## ステータス

承認済み。決定日は2026年10月18日。

## コンテキスト

SPSAの標準の規模は30,000ペアである（[利得と規模のADR](decay-spsa-gains-over-30000-pair-sessions.md)）。
開発と棋力測定に使う手元の機械（以下、測定機）は、lishogiのBotと共用するので同時対局数が16に限られ、30,000ペアに約75時間かかる。
[探索の関数形の見直しの統括計画](../plans/search-forms.md)は7本のサブタスクごとにSPSAを行うので、測定機だけでは約1か月を要する。

計算機を時間単位で借りられる市場vast.aiでは、物理96〜192コアの機械が1時間1〜2米ドル前後で出品されている。
以下、vast.aiで借りてSPSAを実行する計算機を調整機と呼ぶ。
サーバー向けのCPUは多数のコアを測定機より低いクロックで動かすので、調整機では同じ持ち時間でも1手に読む局面の数が減る。
浅い探索に合う係数を選ぶと、採否を測定機のSTCで判定するときに不利になる。
Stockfishの分散テスト基盤fishtestは、各ワーカーで同時対局数と同じ本数のbenchを走らせ、1スレッドあたりの速度と基準の速度の比を、持ち時間の基本時間と加算の両方に掛けている（fishtestのコミット5a8a229a、`worker/games.py`の`get_bench_nps`と`adjust_tc`）。

2026年10月17日から18日の[試走](../measurements/vast-spsa-trial.md)では、Threadripper PRO 9995WXの調整機で換算係数`f`が1.46となり、30,000ペアを約20時間、約25米ドルで実行できる見込みを得た。
換算した持ち時間では、調整機は測定機より約0.3手深く読んだ。

## 決定

SPSAの時間切れの事前確認と本番のセッションは、vast.aiで借りる調整機で実行し、採否のための対局（事前対局と段階ゲート）は測定機で行う。
持ち時間は、測定機のSTC`time=10000+100`の基本時間と加算の両方に換算係数`f`を掛けた値とする。
`f`は、測定機で16本、調整機でその機械の同時対局数と同じ本数の`dev bench`を同時に走らせ、測定機の平均NPSを調整機の平均NPSで割った比であり、セッションの開始時に調整対象のコミットの調整用ビルドで測る。
同時対局数は、調整機の物理コア数から1を引いた数と、実メモリを1局あたりの最大常駐メモリの1.25倍で割った数の小さい方とする。
調整機は、CPUの世代ではなく、実測の負荷時の速度から見込む所要時間と時間単価による1回の費用で選び、所要時間の見込みが24時間を超える機械では本番を始めない。
事前確認の反復数は、同時対局数と同じ数のペアが入れ替わる回数（巡の数）が同時対局数16での手引きの13反復と同じになるよう、`⌈13 × 同時対局数 ÷ 16⌉`とする。

再開時には負荷時の速度を照合せず、別のCPU型の機械でもビルドし直して再開する（[再開のADR](resume-from-the-manifest-and-accept-rebuilt-tuning-commits.md)）。
2026年10月18日、利用者は、SPSAは係数の最適化であり、調整機の速さの違いによる1手あたりの探索量の小さなずれにはこだわらないと判断した。
試走で見た約0.3手の深さの差も、同じ判断により`f`の測り方を変えずに受け入れた。

手順は[SPSAの手引き](../guides/spsa.md)の第8節と`scripts/vast-spsa/`の各スクリプトの冒頭の説明に従い、vast.aiの操作のうち教師生成と共通する処理は`scripts/vast/common.sh`に置く。

## 検討した代案

測定機でSPSAを回し続ける案は、1本あたり約75時間、7本で約1か月、測定機を占有する。
手元の別の計算機（Threadripper 2990WX、物理32コア）は、1コアが測定機より遅く、測定機の数倍の処理量に届かない。
規模を3,000ペアへ戻す案は、利得と規模のADRに反する。

測定機と同じ持ち時間で調整機の対局をさせる案は、1手の探索量が測定機の約2分の1から3分の1になり、深さに依存する係数を浅い探索の条件で選ぶので採らない。
1手のノード数を固定する案は、時間管理の係数を調整できない。
fishtestのように基準の速度を定数にする案は、探索の形を変えるたびに速度が変わるので、定数が実際の測定機からずれる。

CPUの世代（Zen 4以降など）で機械を選ぶ案は、持ち時間を速度の比で換算するので1コアの速さは`f`に吸収され、所要時間は機械全体の速さだけで決まるという関係に合わない。
公開ベンチマークの値で速さを見込む案は、PassMarkの値が試走の実測と合わなかった（統括計画の設計判断）。

調整機からの実行ディレクトリの取得に`vastai copy`だけを使う案は、貸し手の機械のrsyncを通るので、試走と検証で貸し手によって失敗した（[スクリプトの検証の記録](../measurements/vast-spsa-scripts.md)）。
動いている調整機からはコンテナのSSHを通したrsyncで取得し、`vastai copy`は停止した調整機からの取得にだけ使う。

## 結果

1本のSPSAは約20時間、約25米ドルで終わり、測定機の占有は事前対局と段階ゲートの時間だけになる。
調整機での1手あたりの探索量は測定機と完全には一致せず、試走の機械では約0.3手深い。
段階ゲートは測定機で行うので、このずれは係数の選び方にだけ影響し、採否の基準は変わらない。
停止した調整機からの取得は貸し手によって失敗するので、調整機が止まった場合に失うのは、最後の取得（10分ごと）以後の反復である。

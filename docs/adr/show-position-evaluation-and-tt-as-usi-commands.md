# 局面、評価、置換表の表示をUSIの独自コマンドにする

## ステータス

承認済み。決定日は2026年9月27日。

## コンテキスト

不具合の調査では、現局面、評価値の内訳、および置換表の項目を表示する手段が要る。
置換表は、探索が終わった後もUSI層の`UsiProtocol`が保持し、次の探索へ引き継ぐ。
置換表を照会し、探索の後に手を進めながら木を辿ると、ある手が捨てられた理由と反駁手を調べられる（[調査メモ](../research/engine-debugging-survey.md)）。
StockfishとYaneuraOuも、局面の表示`d`と評価の表示をプロトコルのコマンドとして持ち、YaneuraOuの現行版では評価値だけを出す`e`がその役を担う（[調査メモ](../research/engine-debugging-survey.md)）。
minaseのUSI層には、lishogiのBotブリッジ、開発用GUI、および対局ハーネスが接続する。
この判断は[デバッグ機能の整備](../plans/debugging-tools.md)で下した。

## 決定

局面を表示する`d`、評価の内訳を表示する`eval`、および現局面と全子局面の置換表の項目を表示する`tt`を、`position`の後に受け付けるUSIの独自コマンドとし、置換表の照会は表を書き換えない。
`eval`と`tt`の各行は`info string`で始めて`info string end`で終え、`d`だけは端末で読む表示として素の行で出力する。
USI層は未知のコマンドに`info string error: unknown command <先頭の語>`を返し、出力の細目は`UsiProtocol::handle_diagnostic`のdocコメントにある。

## 検討した代案

表示を別の実行ファイルにする案は、探索を実行したプロセスの置換表を照会できないので採らなかった。
デバッグビルドで置換表の項目に手ごとの延長、削減、および枝刈りの判断を記録する案は、2語16バイトの固定形式の項目をフィーチャで切り替えることになり、置換表の実装が2系統になるので採らなかった。
置換表の不具合を表面化させるためにMTD(f)の探索を併設する案は、2系統の探索を保守する費用に見合う具体的な不具合がないので採らなかった。
局面を段反転して陣営を交換する`flip`コマンドは、評価がこの変換で不変であることをテストが検査しており、任意の局面を手で確かめるよりテストの局面を増やすほうが再現性が高いので置かなかった。
CECPの独自コマンドは、開発用GUIと対局ハーネスがUSIで接続するので置かなかった。

## 結果

接続するクライアントは`info string`の行を注釈として扱うので、`eval`と`tt`の出力が誤って届いても状態機械は乱れない。
`d`は端末で人が打つコマンドであり、接続するクライアントは`d`を送らない。
未知のコマンドに応答を返すので、`d`や`tt`の打ち間違いと出力のない成功を区別できるが、USIの原典にある`debug`と`register`は従来どおり応答なしで無視する。
評価関数がNNUEへ置き換わった後の`eval`は、線形の経路の升ごとの寄与に加えて非線形の経路の出力を表示する。

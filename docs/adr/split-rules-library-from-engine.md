# 規則と表記をライブラリ`minase-core`に置き、探索と評価をエンジン`minase`に置く

## ステータス

承認済み。決定日は2026年10月4日。

## コンテキスト

minaseは、中将棋の合法手生成ライブラリと対局エンジンの2つを目的とする。
2026年8月10日の[src構成の整理](../plans/src-layout.md)は、外部の利用者が現れる、crates.ioへ公開する意思が生じる、またはビルド時間が問題になるまで、1つのcrateのまま保つと決めていた。
[ライブラリとエンジンのcrate分割](../plans/crate-split.md)は、2つの目的に別々のライセンスを与えて両方を公開するために、crateを2つに分けた。
分ける境界は、モジュールの依存の向きから決まる。
盤、局面、合法手生成、規則セット、および審判は、表記と乱数のほかに他のモジュールを参照せず、探索、評価、およびプロトコルはこれらを参照するが、逆向きの参照はない。
局面のZobristハッシュの初期化は実行時に乱数を使い、整合検査の診断は局面をSFENで出力する。

## 決定

ライブラリ`minase-core`には、RULES.mdの規則を実装するモジュールと、SFENとUSI・CECPの指し手表記、決定的な乱数、および試験用の局面の標本を置く。
探索、評価、プロトコル、対局ハーネス、学習データの形式と生成、統計、および実行ファイルは、エンジン`minase`に置く。
各crateが持つモジュールの一覧は、`minase_core`と`minase`のcrateのdocコメントにある。

## 検討した代案

表記をエンジン側に置く案は、ライブラリの整合検査がSFENを出力するために依存が循環するうえ、SFENを読み書きできない規則のライブラリは外部の利用者に使いにくいので採らなかった。
探索と評価を含むエンジン一式を中核のcrateとする構成は、rshogiの`rshogi-core`が採る（[crate分割の参考資料](../plans/crate-split.md#参考資料)）。
この構成は、製品がエンジンでありライブラリの境界がフロントエンドを分けるためにある場合の形であり、ライブラリから「規則の実装」という意味が失われるので採らなかった。
試験用の局面の標本をエンジン側にも複製する案は、2つの複製が乖離する危険があるので採らず、ライブラリのフィーチャ`test-util`で公開した。

## 結果

規則と表記だけを使うプログラムは、探索と評価の依存を負わずにライブラリを組み込める。
乱数のモジュール`rng`は、実行ファイルと試験が共有する道具であり、ライブラリの安定した公開面ではないので`#[doc(hidden)]`で公開している。
`test_util`は、ライブラリ自身の試験では`cfg(test)`により、エンジンの試験では開発依存で有効にした`test-util`によりコンパイルされる。
エンジンは型を`minase_core::`のパスで参照し、ライブラリの型をエンジンのルートから再公開しない（[移動した項目を旧パスで再公開しない](do-not-re-export-moved-items-at-old-paths.md)）。

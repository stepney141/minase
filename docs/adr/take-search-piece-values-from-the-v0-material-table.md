# 探索用駒価値はv0の駒割から作る固定の表とし、エンジンと学習器で共有する

## ステータス

提案。[探索用駒価値は学習PSTから導いた値に固定する](derive-search-piece-values-from-the-learned-pst.md)を置き換える案である。[tatara化とHalfKP_vmの設計書](../plans/nnue-tatara-framework-and-halfkp-vm.md)で載せ替えたP型が、載せ替えの確認のSTCで前のP型に約64 Elo負けたので、その原因の切り分けの結果を見てP型の扱いを決めるまで、決定しない。

## コンテキスト

探索は、静的交換評価、捕獲の手の並べ替え、静止探索の余裕値、歩兵の価値を単位とする枝刈りの幅、および成りの得の最大値に、47の駒状態ごとの駒価値を使う。
[以前の決定](derive-search-piece-values-from-the-learned-pst.md)は、学習したPST（駒と升ごとの点数だけの、NNUEより前の評価関数）から導いた47個の値を重みのファイルに格納し、評価関数を学び直しても導き直さない固定値とした。
NNUEの重みのファイルも、この値を写して持っていた。

tataraの形式には駒価値の欄がない（[入力特徴集合と構造のADR](represent-nnue-feature-sets-and-structures-as-enums-and-select-the-structure-from-the-tatara-file.md)）。
P型とHalfKP_vmの世代反復は、どちらも手書きの評価関数v0から始め、v0の書き出しはこれまでも探索用駒価値にv0の駒割を書いていた。
v0の駒割は、`crates/minase/src/eval/handcrafted.rs`の`piece_value`が駒種ごとに定める値である。

## 決定

探索用駒価値は、v0の駒割から作る47状態の固定の表`crates/minase/src/eval/piece_values.rs`とし、エンジンと学習器はこの1つの定義を使う。
状態が0〜28なら駒種番号と同じ駒種の値とし、29〜46なら成れる18種のうち成っていない駒を駒種番号順に並べた状態なので、その駒種の値とする。
v0の駒割は駒種ごとの値なので、成った駒は成った後の駒種の値になり、たとえば歩兵が成った金将は金将の値になる。
王駒の値は、v0の値（2,600）であり、非王駒の最大値（獅子の2,500）に成っていない歩兵の値を足した値に等しい。
固定値の出どころを学習したPSTからv0の駒割に替える点で以前の決定を置き換え、評価関数を学び直しても導き直さない点は引き継ぐ。

## 検討した代案

表を設定ファイルから読む案は、値を実行のたびに替える用途がないうえ、探索の振る舞いを決める外部の入力が増え、`EvalFile`と同じく必須の設定、測定の記録への識別子の記載と照合、借りた計算機への転送、およびGUIとBotの対応が要るので採らなかった。
チェスエンジンのStockfish（`src/types.h`）と将棋エンジンのやねうら王（`source/eval/evaluate.h`）も、駒価値をコードの定数で持つ。
学習したPSTから導いた値を表に写す案は、新しい世代反復がv0から始めることと合わず、PSTを使わなくなった後も古い評価関数に値を縛るので採らなかった。
ネットの書き出しのたびに駒価値を導き直す案は、評価関数の変化と静的交換評価や枝刈りの変化を切り分けられなくなるので、以前の決定と同じく採らなかった。

## 結果

成りの得の最大値は麒麟（385）から獅子（2,500）への2,115であり、この値を定数として持つ。
盤上に現れ得る非王駒の値がすべて正であることと王駒の式は、表の試験で確かめる。
いまのmasterのネットの駒価値（学習したPSTから導いた値）から探索用駒価値が変わるので、探索の結果も変わる。
その影響は、載せ替える前と後のP型の比較の対局に含めて測った。
駒価値を調整するときは、探索の係数と同じく`crates/minase/src/search/params.rs`の仕組み（通常のビルドでは定数、調整用のビルドではUSIのオプション`Tune_<名前>`）に載せ、段階ゲートで測る。

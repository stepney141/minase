# AlphaZero型探索の学習は、Lightning FabricのDDPで、GPUの枚数によらず全体のバッチ1,024をミクロバッチ256の勾配累積で学び、BatchNormの移動統計を最初のミクロバッチだけで更新する

## ステータス

承認済み。決定日は2026年11月10日。

## コンテキスト

学習器はGPUを1枚だけ使い、自前の学習ループで再開をバイト単位で保証していた（[再開の方式のADR](archive/resume-zero-training-from-the-update-count-over-a-seeded-permutation.md)）。
エンジンの開発者は、2026年11月9日に学習器をPyTorch Lightningへ移して複数GPUで学ぶと決め、11月10日に全体のバッチをGPUの枚数によらず固定し、GPUが少ない機械では勾配累積で補うと決めた。
LightningのTrainerは、2.6.6では状態を保存できないローダーでの途中からの再開、標本の並びの分配、およびautocastの範囲の3点で今の保証と食い違う（[複数GPU化の設計書](../plans/alphazero-multi-gpu.md)の「学習器の枠組み」の節）。
dlshogiの開発者は、全体のバッチを4,096に固定した2枚のGPUの学習が1枚の0.53倍の時間で同じ損失になったと報告し、GPUごとのバッチを固定して枚数を増やすと損失が上がったと報告している（設計書の「全体のバッチと勾配累積」の節）。
具体の方式はClaudeが提案し、設計書の承認で決まった。

## 決定

学習器は`torchrun`が起動したプロセスでだけ動き、Lightning Fabricに分散データ並列（DDP）と集団通信を受け持たせ、学習ループ、抽出の列、チェックポイント、および再開の照合は自前のまま保つ。
GPUの枚数をN、全体のバッチBを1,024、ミクロバッチmを256とし、k番目の更新は抽出の列sの区間s[kB:(k+1)B]の局面で行い、これをK=B/m個のミクロバッチ（0から数えた番号j）に分ける。
0から数えたGPU rは、j mod N = rとなるミクロバッチを順に処理して各損失にN/Kを掛け、自分の最後のミクロバッチの逆伝播だけで勾配を平均する。
BatchNormの移動統計は各更新の最初のミクロバッチ（j=0、いつもGPU 0）だけで更新し、ほかのミクロバッチでは逆伝播の後に元の値へ書き戻し、DDPの`broadcast_buffers`は切る。
DDPの`find_unused_parameters`を`True`にして、最初の更新の後の勾配のバケットの組み替えを止める。
各GPUのプロセスは自分のミクロバッチに入る局面だけを保持する。
診断の局面の保持と、保存、診断、および書き出しは、GPU 0のプロセスだけが行う。

## 検討した代案

LightningのTrainerに学習ループを任せる案は採らなかった。
再開、標本の分配、およびautocastの範囲を、Trainerの拡張の仕組みの上で作り直すことになるからである。

PyTorchのDDPを直接使う案（KataGoの方式）は採らなかった。
行数はFabricと大きく変わらないが、Lightningの導入はエンジンの開発者の決定であり、Fabricはその範囲で今の保証を最も多く残すからである。

全体のバッチを256のまま各GPUに64ずつ分ける案は採らなかった。
20ブロック256チャネルでは1回の更新ごとに約112 MBの勾配を平均し、GPUごとに64局面では通信が計算と同程度の時間になると見込まれ、BatchNormの統計も64局面で取ることになるからである。

GPUごとのバッチを256に固定して全体のバッチを枚数とともに変える案（KataGoとdlshogiの既定）は採らなかった。
借りた機械によって学習の規則が変わるからである。

全GPUで統計を同期するSyncBatchNormと、各GPUのすべてのミクロバッチで移動統計を更新するDDPの既定は採らなかった。
どちらも、1枚の勾配累積と同じ移動統計にならないからである。

DDPの既定（`find_unused_parameters=False`）でバケットを組み替えさせる案は採らなかった。
vast.aiの4枚の機械で、強制終了して再開した学習が、再開した直後の区間から、途中で止めない学習と食い違ったからである（[vast.aiの測定](../measurements/alphazero-multi-gpu/alphazero-multi-gpu-vast.md)）。
再開したプロセスは、再開した直後の1回だけ組み替える前のバケットで勾配を平均するので、4つの値を足す順序が変わると考えられる（推論）。
`True`にすると同じ4枚で再開の一致が保たれ、学習の時間の差は塊0の189回の更新で約2%であった。

## 結果

1回の更新の式は、重みの更新も保存する移動統計の更新もGPUの枚数Nによらず、Nによる違いは浮動小数点の加算の順序だけになる。
その丸めの差は学習の間に育つので、Nを変えて学んだネットの出力は一致しない。
vast.aiの測定では、N=1とN=4で学んだネットの出力の差は、同じN=4のまま抽出のシードだけを変えたネットどうしの差と同じ大きさで、検証の損失は同じ程度であった。
4枚の機械の学習は、1枚の2.59倍の速さであった（vast.aiの測定）。
作業機の試験は、CPUの1プロセスと2プロセスで5回学んだ重み、最適化器の状態、および記録が、float32の既定の許容誤差で一致することを確かめる。
Nは1、2、4に限られ、8枚の機械は、ミクロバッチの大きさか全体のバッチを変えない限り使えない。
各プロセスの再生のスレッド数は必須の引数`--replay-threads`で受け取る。
実行器は、使えるCPUの数をNで割った値をこれに渡す。
リプレイバッファのファイルは全プロセスが読み直すので、読み込みの時間はNを増やしても縮まない。
実装は`tools/train/zero/minase_zero/train.py`と`data.py`にあり、学習率は[学習率のADR](warm-up-the-zero-learning-rate-from-a-base-of-0-04-for-a-global-batch-of-1024.md)が定める。

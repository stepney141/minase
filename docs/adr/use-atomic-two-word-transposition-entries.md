# 置換表のエントリを2語の原子値にする

## ステータス

承認済み。決定日は2026年8月23日。

## コンテキスト

[Lazy SMP](../plans/lazy-smp.md)では、複数の探索ワーカーが1つの置換表を共有する。
それまでの置換表は`Vec<Entry>`を`&mut`で操作しており、複数のワーカーから共有できなかった。
Stockfishとやねうら王は、共有置換表への競合する読み書きを通常のメモリアクセスのまま許容している。
同じ競合をRustの通常のメモリアクセスで再現すると、未定義動作になる。
置換表の値のうち、評価値によるカットオフに要るのは検証キー、評価値、深さ、およびバウンドである。
記録手は指し手順序付けと減深の判断にしか使わず、着手として使う前に現局面の合法手との一致を確かめる。
世代は置換の優先度にしか使わない。

## 決定

1エントリを2個の`AtomicU64`からなる16バイトとし、評価値によるカットオフに要る検証キー、評価値、深さ、およびバウンドを1語目のcriticalに、記録手と世代を2語目のadvisoryに置く。
書き込み側はadvisoryを書いた後にcriticalをReleaseで公開し、読み取り側はcriticalをAcquireで読んでからadvisoryを読み、置換の可否は既存値を読んでから判定して競合を待たずに書き込む。
64ビットの原子値を使えないコンパイル対象は、コンパイル時に拒否する。

## 検討した代案

StockfishやC++版のやねうら王と同じく、競合を通常のメモリアクセスで許容する案は、Rustでは未定義動作になるので採らなかった。
置換の可否を比較交換で判定し直す案は採らなかった。
競合で浅い結果が後から公開されても、最後に公開されたcriticalは1回の書き込みに由来する探索値であり、カットオフの正しさは損なわれないからである。

## 結果

カットオフに使う値は1回の原子的な読み取りで得るので、別々の書き込みの値が混ざらない。
記録手と世代だけは、criticalと異なる書き込みに由来することがあり、これを助言的な情報として許容する。
設計書は、原子型への置き換えの前後で`Threads=1`の探索結果とbenchの総ノード数が一致することを、次の段階へ進む条件とした。
ThreadSanitizerによる競合試験は、Lazy SMPの完了時点では実施していない。
1スロットに複数のエントリを置くクラスタ化は、[置換表を1スロット1エントリの直接マップのまま保つ](keep-transposition-table-direct-mapped.md)が扱う。
実装は`crates/minase/src/search/alphabeta/tt.rs`にあり、ビット配置とメモリ順序の詳細は`TranspositionTable`の`probe`と`store`のdocコメントにある。

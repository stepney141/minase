# 探索部の不具合監査（2026年9月28日）

探索部`src/search/`を読み、設計書に記載のない不具合を3件確認した。
3件とも再現例または計数で裏づけた。
第1は静止探索のdelta pruningが捕獲を伴う成りの成り益を無視すること、第2は手番側の王駒がすべて相手の利きにある局面で静止探索がstand-patを下限として返すこと、第3は探索内の反復検出がnull moveをまたぎ、null move直後の相手のじっとを引き分けとして扱うことである。
このほか、影響の小さい指摘が2件あり、設計書に既知の近似として記載済みの指摘は対象から除いた。
いずれの不具合も、修正による棋力の変化は測定していない。
修正は設計書[探索部の不具合修正](../plans/search-bug-fixes.md)として起案する。

## 対象と方法

監査対象は2026年9月28日時点の`master`、コミット`b59e616720757a17228a689831e3a6acea20cf14`の`src/search/`以下の全ファイルである。
評価関数、合法手生成、および対局管理層は、探索部から呼ばれる範囲だけを確認した。
調査は2系統で独立に行い、結果を照合した。
1系統はClaudeが全ファイルを読んだもの、もう1系統はCodexに同じ範囲を読み取り専用でレビューさせたものである。
静止探索の2件はCodexが先に報告し、Claudeが単体テストで再現した。
null moveの件はClaudeが見つけ、計数で確かめた。

計数には、探索部に一時的な計数器を入れた`bench`を使った。
計数器と再現テストは[probe.patch](search-bugs-2026-09-28/probe.patch)に保存してあり、基準コミットへ`git apply`で適用できる。
計数時には別の時間制御の測定が同時対局数19で動いていたので、`bench`は`nice -n 19`で1本ずつ実行した。
報告する値はノード数と件数だけであり、CPUの負荷には依存しない。

## 不具合1：delta pruningが成り益を無視する

静止探索のdelta pruningは、stand-patに取る駒の価値と余裕値（歩兵価値の258%）を加えてもαに届かない捕獲を展開しない。
判定に使うのは取る駒の価値だけであり、捕獲と同時に成る手の成り益を含めない。
該当箇所は`src/search/alphabeta/quiesce.rs`の63行の閾値、326・342・355行の候補生成時の除外、および119行のループ内の枝刈りである。
候補生成時の除外は升単位で行うので、閾値以下の駒がある升は、その升へ成りながら取る手も含めて生成されない。

再現局面`11k/12/6p5/12/6O5/12/12/12/12/12/12/K11 b`では、先手の麒麟が歩兵を取って獅子に成る`6e6c+`が合法である。
着手前の静的評価は874、着手後の静的評価は先手から見て2846である。
空の置換表で静止探索を呼ぶと、探索窓が(−30001, 30001)と(1074, 1075)では2846を返し、(1300, 1301)では874を返した。
窓(1300, 1301)では閾値が1300 − 874 − 258 = 168となり、歩兵の価値100がこれを下回るため、`6e6c+`は生成されない。
真の値がβ以上であるのに、β未満の上界を返したことになる。

頻度は、`bench`の15局面を深さ7で探索して数えた。
stand-patで打ち切られなかった静止探索ノード1,418,523のうち70,266（5.0%）に、取る駒の価値だけでは閾値以下だが、成り益を加えると閾値を超える捕獲成りがあった。

[探索部の設計書](../plans/search.md)の「静止探索」節は、捕獲を伴う成りが静止探索に自然に含まれると定めており、実装はこの意図に反する。
主探索のSEE（静的交換評価）による枝刈りは成り益の上限を考慮しているので、この件は静止探索のdelta pruningに限られる。

## 不具合2：王駒がすべて狙われていてもstand-patを下限にする

静止探索は、手番側の静的評価をstand-patとして探索値の下限に使い、β以上なら即座に返す（`quiesce.rs`57行）。
β未満の場合も、捕獲の結果を`let mut best = stand_pat`から始めて比べる（同102行）。
手番側の王駒がすべて相手の利きにある局面でも、この扱いは変わらない。
その局面で捕獲以外の手を指しても王駒を守れなければ、相手は次の手で最後の王駒を取れる。
stand-patは「何も悪化させずに現在の評価を確保できる」という仮定に立つが、この局面ではその仮定が成り立たない。

再現局面`11k/12/12/12/12/12/12/3b8/12/r2n8/P11/KP10 w`では、後手の`12j12k+`が先手の最後の王駒を詰める。
深さ1の探索はこの手を評価値4661と評価し、深さ2で初めて詰みの値29997を返した。
深さ1では、`12j12k+`の後の先手の静止探索がstand-patで返るので、王駒を取られることが評価に現れない。

頻度は同じ`bench`の条件で数えた。
静止探索ノード2,252,752のうち、手番側の王駒がすべて相手の利きにあるノードは66,610（3.0%）であった。
そのうち5,813はstand-patがβ以上で即座に返ったノード、60,797はβ未満のまま捕獲だけを調べたノードである。

[探索部の設計書](../plans/search.md)224行は、王手放置が合法な中将棋ではチェスの「王手中はstand-pat禁止」の特例が不要であると述べる。
しかし、チェスがこの特例を置く理由は着手の合法性ではなく、王を取られる脅威がstand-patの下限の仮定を壊すことにある。
中将棋でも最後の王駒を失えば負けなので、この理由は同じように当てはまる。
この件は実装と設計書の食い違いではなく、設計上の前提の誤りである。

## 不具合3：反復検出がnull moveをまたぐ

主探索は、着手後の局面キーが対局履歴または探索経路にあれば引き分けの値を返す（`src/search/alphabeta/negamax.rs`296行）。
null move pruningは手番だけを相手へ渡し、探索経路へ局面キーを積まない（同81〜115行）。
null moveの直後に相手がじっとを指すと、盤面は変わらずに手番が戻り、局面キーはnull moveの前の局面と一致する。
null moveの前の局面は探索経路にあるので、じっとは反復として引き分けの値を受ける。
その結果、null moveの前の局面で手番側が有利でβが正の場合、相手はじっとで実在しない引き分けを得る。
null moveの探索値はβに届かなくなり、打ち切りが起こらない。

Stockfishは反復の検出を直近のnull moveより前へ遡らせない（`src/position.cpp`の`do_move`が、直前のnull moveと50手規則の手数の小さい方までを遡る。[反復の先行実装の調査](../research/search-repetition-prior-art.md)参照）。
ElephantEyeも遡りをnull moveで止める（同）。
ところが[探索内の反復負け回避](../plans/search-repetition.md)86行は、周回の区間にnull moveが含まれる場合を引き分けとし、その根拠にElephantEyeの遡りの停止を挙げている。
遡りを止めれば反復は検出されず、引き分けにはならないので、この記述は引用した先行実装と逆の結論になっている。
既存のテスト`src/search/alphabeta/tests/contracts.rs`47行は、null move後の実着手による反復を参照に含める現行の挙動を固定している。

計数は、null move以後の探索経路にない局面キーとの一致を「null moveをまたぐ反復」として数えた。
`bench`を深さ9で探索すると、null moveをまたぐ反復は1,986件あり、うち1,980件はnull move直後の1手目で起きた。
1手で盤面を元へ戻せる着手はじっとだけなので、この1,980件はすべてじっとである。
null moveをまたぐ一致を反復と扱わないようにすると、総ノード数は16,519,597から15,199,132へ8.0%減った。
深さ7では該当が54件で、総ノード数の差は0.05%であった。
null moveの子が通常探索になるのは残り深さ5以上のノードだけなので、影響は深い探索ほど大きい。

## 軽微な指摘

静止探索は、捕獲の候補がなければstand-patを返し、非捕獲手を含めた合法手の有無を調べない（`quiesce.rs`73行）。
このため、RULES.md第23条の「合法手がない側の負け」を静止探索の局面では検出しない。
Codexは局面`KP10/LL10/12/12/12/12/12/12/12/12/12/10k1 w`で、深さ1が`-601`、深さ2が`mate +0`を返すことを再現した。
[探索部の設計書](../plans/search.md)が述べるとおり、中将棋ではこの局面がほとんど現れないので、影響は小さい。

置換表は、評価値の絶対値が`MATE_THRESHOLD`（29,744）以上であることだけで詰みの値を判定し、手数を補正する（`src/search/alphabeta/tt.rs`395〜416行）。
詰みの値を格納時より深い位置で読み出し、根からの手数と詰みまでの手数の和が256を超えると、読み出した値が詰みの帯から外れ、以後は通常の値として補正されない。
算術上は起こり得るが、実際の探索深さと静止探索の長さでは和が256に届かないので、実害は確認していない。

## 既知の近似として除いた指摘

Codexは次の2件も再現した。
1件は、反復による引き分けの値が親局面の置換表項目を通じて別の経路で再利用されるgraph history interactionである。
もう1件は、R1、R2、R3の反復規則を探索の木の中で一律に引き分けとして扱うことである。
どちらも[探索部の設計書](../plans/search.md)の「探索内の終局と規則処理」節と[探索内の反復負け回避](../plans/search-repetition.md)に既知の近似として記載されているので、本報告の不具合には含めない。

## 問題が見つからなかった観点

次の観点は2系統とも確認し、不具合を見つけなかった。
評価値の符号の反転、最後の王駒の捕獲と合法手がない場合の詰みの値、置換表の詰みの値の手数補正は正しい。
置換表の照合キー、評価値、深さ、および境界は同じ64ビットの原子値に入っており、並列書き込みで混ざらない。
別の原子値にある置換表の指し手は、通常探索と静止探索の双方で合法手と照合してから使っている。
探索の中断は値を返さずに伝わり、盤面と探索経路を復元してから戻るので、未完成の値を置換表へ書かない。
aspiration windowsの読み直しは外れた側だけを広げるので、必ず終わる。
探索深さは256以下に検証されており、通常探索は深さを延長しないので、ply単位の配列の範囲外参照は起こらない。
killer表、history表、および静的評価の補正表の添字と加算幅に、到達可能な範囲の整数のあふれはない。
SEEは経由升を持つ手を枝刈りせず、獅子の跳び越しを占有に依存しない利きとして扱っている。
先獅子の状態と成りの保留状態は探索局面キーに含まれ、null moveは先獅子の状態を正しく消す。
調整用の係数は`go`の後に変更できないので、1回だけ生成するLMRの減深量表が古い係数のまま残ることはない。

## 再現資料

[probe.patch](search-bugs-2026-09-28/probe.patch)は、次の3つを基準コミットへ加える。
1つ目は`bench`の計数器であり、各局面の後にnull moveと静止探索の累積件数を出力する。
環境変数`PROBE_Q`を設定すると静止探索の件数を数え、`PROBE_SKIP_CROSS_NULL`を設定するとnull moveをまたぐ一致を反復と扱わない。
2つ目と3つ目は、不具合1と不具合2の再現局面を探索して値を出力する単体テスト`probe_bugs`である。

```console
git apply docs/audits/search-bugs-2026-09-28/probe.patch
cargo build --release --bin bench
./target/release/bench --depth 9
PROBE_SKIP_CROSS_NULL=1 ./target/release/bench --depth 9
PROBE_Q=1 ./target/release/bench --depth 7
cargo test --release --lib probe_ -- --nocapture --test-threads=1
```

2026年9月29日時点のmaster、コミット`c76eaeae1b419f22e72e267a8ef0cb9ab92a81eb`を基準に、`src/search/`の終了性とスレッド生成失敗時の処理を監査し、未修正の欠陥を2件確認した。
本報告は、[先行監査](search-bugs-2026-09-29.md)の6件を同じ確度の不具合とした分類を改め、受理済み入力に対する探索の進行と、失敗時の停止通知を根拠に判定できるものを記録する。
探索の近似による読み落としは、その存在だけを根拠に欠陥とは判定しない。

1. 受理された評価重みでも探索窓の幅が0になり、深さ5の反復を完了できない。

   [評価ファイルの検証](../../src/eval/pst/format.rs#L207)は、歩兵価値が1または2の重みを受理する。
   一方、[探索窓の初期半幅](../../src/search/alphabeta/root.rs#L65)は、歩兵価値に既定係数46を掛け、100で整数除算して求めるため、どちらも0になる。
   深さ5以降で直前の評価値が詰みの範囲外なら、[窓の初期化](../../src/search/alphabeta/root.rs#L23)によって`alpha == beta`となる。

   [公開入力の検証契約](../plans/rust-design-audit-remediation.md#検証契約)は、外部バイト列から復号した有効な評価重みを、同期探索と非同期探索の両方で使用できると定めている。
   また、[探索窓の設計](../plans/strength-stage6.md#設計判断)は、窓の外に出た場合には窓を広げ、有限回の再探索でその反復を完了すると定めている。
   受理された重みで窓が広がらない処理は、これらの契約を満たさない。

   幅0の窓は再探索を何回行っても広がらない。
   両端の更新量が0であり、半幅の拡大も整数演算で`0 × 201 / 100 = 0`となる。
   [反復の正常完了条件](../../src/search/alphabeta/root.rs#L92)は`alpha < score < beta`なので、この状態ではどの評価値を返しても完了できない。
   時間上限、ノード上限、外部停止のいずれもなければ、この反復から戻らない。
   これは読み落としではなく、終了条件に到達できない制御上の欠陥である。

   再現では、埋め込み評価ファイルの歩兵価値を100、1、2に設定した3組を用意し、王駒価値とチェックサムもファイル形式の制約に合わせて更新した。
   3組とも`Pst::decode`を通過することを確認したうえで、王駒2枚の局面`k11/12/12/12/12/12/12/12/12/12/12/11K b`を公開関数`search`で探索した。
   条件は1ワーカー、深さ5、ノード上限10,000、時計なし、各探索で空の置換表である。
   歩兵価値100では132ノードで深さ5を完了したが、1と2では10,000ノードを使い切り、深さ4の結果を返した。
   探索とは別に、直前の評価値を0と置いて深さ5の窓を構成し、両端を1回ずつ広げても、`(alpha, beta, delta) = (0, 0, 0)`のままだった。
   この3つ組は、探索中の内部状態を直接記録した値ではない。
   [再現ログ](search-control-defects-2026-09-29/aspiration.log)のノード上限は検査を終了させるために設けており、上限なしで正常完了しないという結論は、上記の不変条件から導く。

   [追加の比較検査](search-control-defects-2026-09-29/review-extra.log)では、初期半幅が1になる歩兵価値3と4は103ノードで深さ5を完了した。
   歩兵価値1では、ノード上限を100,000へ増やしても深さ4までしか完了しなかった。
   同じ重みで深さ4までを探索すると64ノードで完了し、評価値は0だった。
   歩兵価値は枝刈りの余裕値にも影響するため、これらの観測は不変条件による論証の補助として扱う。

   初期半幅が0になる条件は、正の歩兵価値と[探索係数AspirationDelta](../../src/search/alphabeta/params.rs#L71)の積が100未満となることであり、既定値46では歩兵価値1と2が該当する。
   通常の埋め込み評価の歩兵価値100では、この条件は発生しない。
   ただし、任意の検証済み評価重みを受け取る公開関数には到達可能であり、外部停止手段のない[同期探索](../../src/search/handle.rs#L141)で深さだけを指定すると、呼び出しを完了できない。
   時間制限がある場合も、幅0の反復へ入ると完了結果を更新できず、探索中の時間上限の検査などによる中断を待つ。
   修正後には、受理する評価重みの全範囲で探索窓に正常完了可能な幅があり、窓外の結果に対する再探索が進行することを確認する必要がある。

2. 補助スレッドの部分的な生成失敗が、開始済みワーカーへ停止として通知されない。

   [探索チームの生成処理](../../src/search/alphabeta/team.rs#L254)は、補助スレッドを順に生成してから主ワーカーの探索を始める。
   `scope.spawn`の生成失敗によるパニックは、ワーカー本体を保護する`run_worker_guarded`の外で発生する。
   そのため、[パニック時に共有停止状態を更新する処理](../../src/search/alphabeta/team.rs#L287)を通らず、`thread::scope`が開始済み補助スレッドの終了を待つ。

   [並列探索の設計](../plans/lazy-smp.md#探索チーム)が明記するのは、生成失敗時にチームを失敗させ、チャネル切断と`join`エラーへ接続することであり、この要求自体は開始済みワーカーの終了後に満たされる。
   生成失敗時の停止通知は明文化されていない。
   一方、[ワーカーパニック時の検証契約](../plans/rust-design-audit-remediation.md#検証契約)と[start_searchの文書](../../src/search/handle.rs#L82)は、残るワーカーへ停止を通知してから失敗を返すと定めている。
   本監査では、生成失敗の経路には同じ停止通知がなく、開始済みワーカーの探索が終了するまで失敗通知を待たせる点を、異常終了処理の欠陥と判定する。
   この判定は、ワーカーパニック時に明文化された停止方針との整合性を根拠とする。

   発生には、少なくとも1本の補助スレッドの生成成功後に、後続の生成が失敗する必要がある。
   したがって、この欠陥の対象となる指定スレッド数は3以上である。
   失敗後も開始済みワーカーが探索を続けるため、終了イベントの受信だけで完了を待つ利用側への失敗通知は、そのワーカーの自然終了または別途の停止要求まで遅れる。
   実際の遅延時間は残りの探索量と停止条件に依存し、本監査では測定していない。

   再現では`run_worker_team`を3ワーカーで呼び、第2補助スレッドに相当する`pthread_create`の呼び出しを資源不足エラー`EAGAIN`で失敗させた。
   これは検査実行用スレッドを含めて3回目の生成であり、失敗注入は検査プロセス内に限定した。
   検査用ワーカーは共有停止状態が立つまで待ち、停止通知が欠けても検査を終了できるよう100 msの期限を設けた。
   [再現ログ](search-control-defects-2026-09-29/spawn-failure.log)は`spawn_failed=true team_stop=false watchdog_expired=true`となり、生成失敗後も共有停止状態が更新されず、第1補助スレッドが検査用期限に達するまで残ったことを示す。
   この100 msは製品の応答期限ではなく、公開関数からの通知遅延を測った値でもない。

   この欠陥は、スレッドを回収できなくなることを意味しない。
   [SearchHandleの終了処理](../../src/search/handle.rs#L54)では、`request_stop`が外部停止を要求し、`join`と`Drop`もその停止要求を行ってから終了を待つ。
   これらが呼ばれれば、開始済みワーカーを停止できる。
   欠けているのは、利用側の追加操作を待たず、部分的な生成失敗そのものを契機として残るワーカーへ停止を通知する処理である。

2件の再現資料は、この基準コミットに固定した[実行スクリプト](search-control-defects-2026-09-29/reproduce.py)、[検査用パッチ](search-control-defects-2026-09-29/repro.patch)、および[スレッド生成の失敗注入](search-control-defects-2026-09-29/fail_pthread_create.c)として保存した。
Linux上でPython 3.12以降、Rust、およびCコンパイラを使い、リポジトリのルートから次のコマンドを実行する。

```sh
python3 docs/audits/search-control-defects-2026-09-29/reproduce.py
```

スクリプトは対象コミットを一時ディレクトリへ展開し、テストだけを追加してビルドする。
欠陥を検出する2件のテストは期待する挙動を満たさないため失敗し、追加の比較検査は正常終了する。
スクリプトはそれぞれの終了コードと観測値を確認して正常終了する。
今回の記録はLinux x86_64、`rustc 1.98.0`、通常機能構成、最適化レベル0、ビルド1ジョブ、テスト実行1スレッドで取得した。
スレッド生成失敗の検査内では、別途、補助スレッドを生成する。

先行監査のほかの指摘は、今回の未修正の確定欠陥には含めない。
手番を仮に相手へ渡すnull moveをまたいだ反復判定は、[修正計画の完了記録](../plans/search-bug-fixes.md)と基準コミットのコードから、修正済みであることを確認した。

成り益を含めない静止探索の枝刈りは、[既存の修正計画](../plans/search-bug-fixes.md#設計判断)で不具合として記録されている。
修正版との[対局測定](../measurements/search-bug-fixes-delta-promotion-diag-stc.md#結果)は判定未了で、修正前の版が強い方向の結果となり、利用者の決定で修正が取り込まれなかった。
この既存の分類を記録したうえで、終了性と失敗処理を対象とする本監査では再判定しない。

補助ワーカーが指定深さを完了した際の停止方針は、設計書の間で記述が一致しない。
[並列探索の設計](../plans/lazy-smp.md#探索チーム)は、いずれかのワーカーが深さ上限を完了した時点でチームを停止すると定めている。
一方、[Rust設計監査の修正計画](../plans/rust-design-audit-remediation.md#設計判断)は、主ワーカーの進捗が空になる競合を避けるため、固定深さの完了通知を主ワーカーだけに限ると定めており、コミット`8b48929`でも補助ワーカーからの停止通知が削除されている。
したがって、現在の処理には意図的な変更の根拠があり、実装の変更が必要かは、この文書不整合を解消したうえで判断する。

合法手がない通常探索ノードでの枝刈りは、null moveによる近似の許容範囲や探索費用を含めた設計判断を要するため、判定を保留する。

追加の比較検査も再現資料へ収録し、同じ基準コミットで再実行した。

本監査は探索本体を変更しておらず、修正後の棋力も測定していない。
2件の欠陥が存在することから、その修正が棋力を上げることや、棋力を下げないことは導けない。
修正の実装を採用する際は、上記の機能上の確認と棋力への影響の確認を分けて扱う必要がある。

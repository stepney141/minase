# M1〜M4候補の絞り込みと判定

本書は、`m1_hits.tsv` から `m4_hits.tsv` までの機械的候補を再現可能な規則で絞り込み、上位候補を両側のソースで読んだ結果を記録する。
判定は `../review/rubric.md` の4段階に従い、既知の5件（K1〜K5）は再調査せず、各手法が検出したかどうかだけを確認した。
スクリプトは `triage_work/` にあり、読み込むのは本ディレクトリの成果物と `sources/` の保存済みソースだけである。

## 共通の規則

同梱ライブラリの除外には、コーパス側のパスに対する正規表現 `triage_work/common.py` の `VENDOR` を用いた。
対象は nlohmann、third_party、external、vendor、gaviota、zlib、packages/、idna、pyrrhic、Fathom、syzygy/tbprobe、googletest などである。
minase 側のテストは、パス（`tests/`、`tests.rs`、`_test.py`、`test_*.py`）に加え、Rust では `#[cfg(test)]` の直後に `mod 名前 {` が続くインラインのブロックの範囲と、直前4行に `#[test]` がある関数をテストとみなした。
当初は最初の `#[cfg(test)]` 以降をすべてテストとみなしたが、`#[cfg(test)] pub(crate) mod tests;` や `#[cfg(test)]` 付きの補助関数を冒頭に置くファイル（`see.rs`、`tt.rs`、`ordering.rs`、`movegen/mod.rs`、`adjudication.rs` などの各版）の本体を取りこぼすことが分かったため、ブロック単位に改めて M2 から M4 を再実行した。
minase 側がテストでコーパス側がテストでない候補は、テスト固有のデータとして除いた。
重複は (minase のパス, コーパスのリポジトリ, コーパスのパス) で1件にまとめ、基準版 `a05478a` に存在する版を優先した。
コーパスの Stockfish タグ群のように同一ファイルの版違いは、リポジトリ名の括弧書きを外して同一視した。

これらの規則を各手法に適用した結果、次の節のとおり候補は数十件まで減った。

## M1 注釈と文字列

絞り込みは次の順に行った。
まず、既存の除外理由（プロトコル、RULES引用、ライセンス定型文）か偽陽性注記のある行を除いた。
希少度には `corpus_occurrences` ではなく、同じ窓を含むコーパスのリポジトリ系統の数を用いた。
`corpus_occurrences` は blob ごとに数えるため、Stockfish の sf_10〜sf_19 と研究用複製やファイル単位の写しにまたがる注釈は十数回と数えられ、最も重要な比較先の一致が先に落ちるからである。
系統数が3以上の窓を除いた。
次に、同じ (minase の行, コーパスの行) に属する5語窓または12文字窓を束ね、`m1_texts.jsonl` の正規化文から最長共通部分列を再計算した。
採用条件は英語8語以上、日本語16文字以上、または英語語数と日本語文字数の半分の和が8以上である。

候補数は 1,006,656行（候補 820,797）から、窓単位の約18.3万行、行対の 80,298組、長さ条件を満たす 1,377組を経て、ファイル対 72件になった。
この72件に、条件の一段下（和が6以上8未満）から SFEN 文字列を除いた27件を加えた99件を読んだ。
72件の内訳は、中将棋の SFEN 局面文字列（lishogi 形式の初期局面と試験局面）が scalashogi と shogiops を相手に57件、tatara の1文が10件、rshogi と Gikou の日本語の定型説明が各2件、lishogi API の URL が1件である。
一段下の27件は、一般的な言い回し24件、数字列2件、Linux sysfs のパス1件であった。
例として、「開始局面から現局面までの手数を返す」は Gikou の手数関数の説明、「同一ディレクトリの一時ファイルへ」は原子的書き込みの定型説明、「探索スレッドの終了を待ってから」と「反復による引き分けとなる」は YaneuraOu の注釈との一致であり、いずれも周辺のコードに一致はない。
系統数による希少度へ切り替えても、Stockfish と minase の `src/search`、`src/eval` の組は長さ条件に届かず、K1 の注釈レベルの一致も現れなかった。
`short` と `identifier` の別枠（出現2回以下の 8,456行、異なる文字列339種）も一覧で確認し、gsprt、worktree、futility margin1 などの一般語彙だけであった。

新規1件は、minase の `the working tree is dirty; commit changes or pass --allow-dirty` と tatara の `working tree is dirty; commit changes or pass --allow-dirty (the report records dirty=true)` の一致である。
minase 側の導入は 6bc33e1（2026-08-26、`src/bin/selfplay_gen.rs`）であり、tatara 側は ce8ba9c（2026-07-19）が先行する。
導入時点で同時に変更した設計書 `docs/plans/evaluation.md` は tatara を挙げておらず、tatara への言及は後の `docs/plans/strength-stage9.md` と `docs/plans/relative-pair-eval.md` に設計の参考として現れるだけである。
一致は1文だけで、フラグ名 `--allow-dirty` は cargo の慣行でもあり、両ファイルの他のコードには M4 でも一致がない。
したがって判定は「2 標準的な方式で説明可能」とし、tatara は MIT なので仮に由来があっても表示義務は1文の範囲にとどまる。

M1 の結果は注釈と文字列の短い一致が主であり、次の M2 では数値の組に視点を移す。

## M2 数値の組

コーパス側の文書頻度は、値を含む関数集合の数ではなく、値を含むリポジトリの数で数えた（Stockfish の10タグを1回と数えるため）。
自明値は16以下の整数、2の冪、1/2、1/4、3/4、1/10 とした。
採用条件は次のいずれかである。

1. 文書頻度3以下の非自明値が3個以上ある。
2. 小数第2位以下を持つ非自明な小数が2個以上ある。
3. 非自明な共通値の idf（log2(50/文書頻度)）の和が15以上である。

条件3は、提案規則だけでは K5 を落とすため追加した。
非自明値が300種を超えるコーパス側集合（lc0 の方策表、syzygy 表、ctg 表など）は、条件2を満たさない限り除いた。

候補数は 492,346行から、同梱除外 56,838行、minase テスト 260,774行、巨大表 5,896行、条件不成立 165,085行を除いて 3,753行、ファイル対 501件になった。
上位80件を読んだ結果は、K1 が1件、K5 が2件、12×12盤の升番号列（11〜85、144）10件、SPSA の Spall 推奨値 α=0.602、γ=0.101 と fishtest 既定値18件、GSPRT 境界 log 19＝2.944 が1件、丸め値、分位点、微小量などの偶然の一致48件であった。
新規の候補はない。
テスト判定の修正で新たに対象となった `see.rs`、`tt.rs`、`ordering.rs` などは、絞り込み後の M2 には現れなかった。
K1 以外に Stockfish または YaneuraOu の探索・評価関数と minase の `src/search`、`src/eval` が組になる候補は残らなかった。

数値の組の次は、配列としての並びを比べる M3 を扱う。

## M3 配列

既存注記のうち「定数が2種類以下の反復表」136,469行と「小さな連番の表」51,643行を除いた。
さらに、同梱除外、minase テスト（コーパス側が非テストの場合）、倍率が {1, 2, 3, 4, 5, 8, 10, 16, 100, 1000, 3/2, 5/2 とその逆数} にない16要素未満の一致、一致範囲の異なる値が4種未満、全要素の絶対値8以下、単調列を除いた。
候補数は 199,405行から 172行、ファイル対13件になった。
13件は K4（HaChu の駒価値表に対する倍率5/2の並べ替え部分一致、4ファイル）と、8近傍の方向ベクトル（規則上の語彙）9件である。
13件では上位30件に満たないため、「2種類以下」と同梱だけを除いた緩い条件で単調列、等差列、小整数列を外し、異なる値の多い順に30件を追加で読んだ。
追加分はすべて升番号、探索既定値、テスト用の表と他リポジトリの無関係な表との倍率付き偶然一致であり、新規の候補はない。

M3 で残ったのが既知の K4 だけだったため、最後に構文上の局所一致である M4 を調べた。

## M4 トークン列

長さ40トークン以上、既存注記なし、minase 側が非テスト（コーパス側がテストなら残す）、同梱除外の条件で、5,034,236行から 4,802行、断片対 796件（ファイル対762件）になった。
796件すべてについて、両側の該当行を `sources/` から切り出し、正規化前のトークン列の最長共通部分列（以下、生一致長）を計算した。
生一致長の分布は 0〜9 が327件、10〜19 が269件、20〜29 が124件、30以上が76件である。
30以上の76件は全件読み、パターンごとにまとめた。
内容は Display と Error の実装、io::Error の変換、OpenOptions によるロック、Command の出力検査、SHA-256 の読み込みループなどの Rust の慣用句70件、USI の `info` 行分解4件、SplitMix64 の公開定数2件（Vigna の公開アルゴリズム）である。
生一致長30未満の720件は、識別子を正規化した構造だけが一致する候補であり、長さ上位30件を読んで、列挙値から文字列への match、Display 実装、SFEN 解析の骨格などの構造一致だけであることを確認した。
既存注記で除かれた40トークン以上の 14,271断片対も生一致長を計算し、最大は82（use 宣言の並び）で、上位はすべて import 列と0の配列であった。

apery_rust、rshogi、shakmaty、Reckless、viridithas、fishtest、nnue-pytorch などの GPL、AGPL、ライセンスなしのコーパスとの間に、新規の候補はない。

akimbo との一致はどの手法にもなかった。
手法ごとの生の再現率は、M1 が0/5、M2 が5/5（K2 は弱い）、M3 が1/5、M4 が0/1（比較可能な K5 だけ）である。
絞り込み後の和集合は K1、K4、K5 の3/5であり、K2 と K3 のように公知の数式や広く使われる定数を含む由来は、希少度による絞り込みでは原理的に残らない。

## 出力

`triage_m1.tsv` から `triage_m4.tsv` は、読んだ候補の順位、両側の位置、ライセンス、指標、分類（FP、KNOWN、NEW）、理由または判定を示す。
再実行は、本ディレクトリで次を順に実行する。

```sh
python3 triage_work/m1.py && python3 triage_work/m1_pairs.py
python3 triage_work/m2.py && python3 triage_work/m2_show.py 80
python3 triage_work/m3.py && python3 triage_work/m3_loose.py 60
python3 triage_work/m4.py && python3 triage_work/m4_raw.py
python3 triage_work/write_tsv.py
python3 triage_work/calib.py M2   # K1〜K5の生の検出（M1〜M4 を引数に取る）
```

## 限界

絞り込みは希少度と長さに基づくため、公知の定数や短い慣用句に埋もれた翻案は残らない。
M4 は Rust 同士と Python 同士だけを比べており、C、C++ との翻訳は検出できない。
テスト判定は括弧の数によるブロック検出であり、文字列やコメント中の括弧で範囲がずれる可能性がある。
M1 の `short` と `identifier` の別枠は既存の `corpus_occurrences` のまま確認したため、版違いの多い注釈を取りこぼしている可能性がある。

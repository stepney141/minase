# M5 対照レビューの判定基準

## 前提
- 対象: minase リポジトリ（以下 `<minase-repo>`）の基準コミット a05478a（`git -C <repo> show a05478a:<path>` で読む。作業ツリーは他の人が編集中の可能性があるので、ファイルを変更しない）。削除済みファイルは `git log --all -- <path>` で最終版を探して `git show <commit>:<path>` で読む。
- コーパス: corpus/manifest.tsv（列: repo, local_path, head_commit, head_date, license_spdx, license_evidence, language, source_lines, category）。Stockfish と YaneuraOu は主要リリースタグ（sf_10〜sf_19、YaneuraOu V5.00〜v9.40）を `git -C <clone> show <tag>:<path>` で読める。minase の文書が固定コミットのリンクで参照している版があれば、その版も読む（`git -C <minase-repo> grep -n '<repo名>' a05478a -- docs` で探す）。
- クローンは読むだけで変更しない。

## 判定の4段階
1. **複製または翻案を支持する証拠あり**: 実装固有の一致が複数あり、独立実装では説明しにくい。
2. **標準的な方式または仕様で説明可能**: 一致は、公知のアルゴリズム、数式、プロトコル（USI、CECP）、中将棋の規則、または言語の慣用で説明でき、実装固有の一致がない、または偶然の範囲にとどまる。
3. **判定保留**: 実装固有の一致があるが、1の判定には足りない。
4. **未確認**: 対照を読めなかった（理由を書く）。

## 一致の2種類を分ける
- **必須の一致**（証拠にしない）: 同じアルゴリズム・数式・仕様から必然的に同じになる部分。例: fishtest と同じLLRを出すための式、USIのコマンド名、alpha-betaの骨格、PVSの再探索条件、公知の枝刈りの存在そのもの。
- **実装固有の一致**（証拠になる）: 別の書き方が自然にあり得るのに同じ選択をしている部分。例: 同じ変数名・フィールド名の組、同じ補助関数の分割、同じ特異な分岐順、同じ調整済み定数の組（例: 係数の組、閾値の組）、同じ特異な条件の組合せ、コメントの対応、同じ誤り・癖。
- 必須の一致だけを根拠に1と判定しない。一方、「標準的なアルゴリズム」という理由だけで周辺の実装固有の一致を除外しない。

## 記録すること（判定ごと）
- minase 側の path:行範囲（a05478a時点。削除済みなら commit:path:行）と対照側の repo@commit/tag:path:行範囲。
- 実装固有の一致の一覧と、それぞれ別の書き方があり得た理由。
- 反証（同じ機能で異なる選択をしている箇所）。
- minase 側の導入コミット（`git log --format='%h %ad %s' --date=short -S'<特徴的な文字列>' -- <path>` など）と、その時点の設計書が参照先としてどこを挙げているか。
- 対照側のライセンス（manifest.tsv の値。ファイル単位の例外があればそれ）。

## 出力
- 各 reviewer は review/ の担当範囲名のファイル（search.md、infrastructure.md、core.md、harness-and-statistics.md、training-and-evaluation.md）に、上の記録を判定ごとに書く。
- 最後に、担当範囲の各モジュールについて、判定と一言の理由を表にする。
- 報告（返信）は日本語で、判定の表と、1または3の判定の詳細だけを800語以内で書く。

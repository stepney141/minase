# SPRTによる棋力測定の手引き

本書は、Minaseのエンジン変更の効果を自己対局で測定する標準手順を定める。
本書は、測定の実行者（人間およびエージェント）向けの運用規約と手順だけを記す。
仕組みの詳細は設計書に書かれている。
測定基盤の成立過程と対局の進め方は [plans/match-harness.md](../plans/match-harness.md) にある。
保存、再開、および集計の基盤は [plans/match-harness-efficiency.md](../plans/match-harness-efficiency.md) と [plans/match-resume-simplification.md](../plans/match-resume-simplification.md) にある。
統計方式は [plans/search.md](../plans/search.md) の測定基盤の節に、機能採否の段階ゲートの設計判断は [plans/match-staged-gate.md](../plans/match-staged-gate.md) にある。

## 原則

測定はfishtestと同じメタ的な構造に従う。
テストは「旧エンジンのコミット」と「新エンジンのコミット」の2つで定義し、対局ハーネス`minase match run`は差分の内容（どの機能が追加されたか）を一切知らずに、勝敗だけから効果を判定する。
したがって、探索、評価、時間管理など棋力に影響し得る変更は、機能ごとの比較スイッチをハーネスへ追加するのではなく、変更をコミットとして確定させたうえでコミット対コミットの対局にかける。

## 測定の種類と標準コマンド

### 機能採否の段階ゲート（STCとLTC）

新機能の採否は、機能実装コミットと直前コミットの対等条件GSPRTを、短時間の選別と長時間の最終測定の2段階で実行して判定する。
短時間条件`time=10000+100`を**STC**（short time control）と呼ぶ。
長時間条件`time=60000+200`を**LTC**（long time control）と呼ぶ。
どちらも秒読みは使わない。
STCはfishtestの標準値と同じであり、LTCの加算0.2秒は片側の総思考時間をfishtestのLTCと同程度にする値である（選定理由は [plans/match-cost-reduction.md](../plans/match-cost-reduction.md)）。
思考制限は`--each`で両エンジンに同一条件を与える。
固定深さと固定ノード数は、探索速度を除いた診断に限定し、採否の根拠には使わない。
STCとLTCは別の測定として扱い、測定名と実行ディレクトリを接尾辞`-stc`と`-ltc`で分ける。

STCの標準コマンドは次のとおりである。

```console
cargo run --release --bin minase -- match run \
  --run-dir data/matches/<測定名>-stc --seed <シード> \
  --candidate commit:<新コミット> --baseline commit:<旧コミット> \
  --each time=10000+100 gsprt --max-pairs 3000
```

STCの判定は、次の振分け規則で扱う。

- `decision: H1`（候補が有意に強い）は、候補をLTCへ進める。
- `decision: H0`（elo=10の改善があるとは言えない）は、候補を採用しない。
- 上限3,000ペアに達した`decision: pending`は、停止時点の対数尤度比LLRが0以上ならLTCへ進め、負なら進めない。

候補の棄却はSTCでもLTCでも起こるが、採用の決定はLTCの判定だけが下し、STCの通過を採用の根拠にしない。

LTCの標準コマンドは次のとおりである。

```console
cargo run --release --bin minase -- match run \
  --run-dir data/matches/<測定名>-ltc --seed <シード> \
  --candidate commit:<新コミット> --baseline commit:<旧コミット> \
  --each time=60000+200 gsprt
```

LTCのシードは、STCの基本シードからペア数以上離れた未使用の値とする（[隣接シードで対局が重複する教訓](../lessons/derive-seed-adjacent-collision.md)）。
`decision: H1`であり、かつエンジン異常、時間切れ、および拒否着手が0件の場合だけ採用する。
拒否着手とは、審判層が合法とした相手の着手を、エンジンが受け付けなかった反則である。
LTCの`decision: pending`は、同じ実行ディレクトリを`--resume`で再開し、`--target-pairs`でペア数上限だけを引き上げて対局列を延長する（再開手順は後述）。

時間管理の変更、`Threads`の変更、STCの到達深さでは発火しない機構のように、短時間条件では効果が原理的に現れない変更は、省略の理由を測定開始前に設計書へ記録したうえで、STCを省略してLTCへ直行できる。
結果を見た後の経路変更は認めない。

採否の判定では、次の規則を守る。

- 判定保留の候補を裁量で採用しない。`pending`の扱いは、STCでは振分け規則、LTCでは`--resume`による延長だけとする。
- シードを変えて再試行しない。
- STCとLTCの結果を合算しない。
- 信頼区間または固定局数Eloを、採用の根拠として読み替えない。
- 完了済みの測定に遡って規則を適用しない。
- 同じ着想のパラメータ違いを、LTCの結果を見てから同じ主張へ追加しない。パラメータ違いはSTCまでに1つへ絞る。

段階ゲートの時間制御で開始する最初の測定で、時間切れ、エンジン異常、または拒否着手が1件でも出た場合は、測定を停止して原因を調査する。

### 完了基準ゲート

探索部マイルストーンの完了基準は、凍結ベースラインへの有意な勝ち越しである。
凍結ベースラインは**コミット0045833のバイナリにdepth=1を指定したもの**に固定されている（確定の経緯は [plans/match-harness.md](../plans/match-harness.md)）。

```console
cargo run --release --bin minase -- match run \
  --run-dir data/matches/<測定名> --seed <シード> \
  --candidate commit:<測定対象> \
  --baseline commit:0045833 --baseline-limit depth=1 \
  --each depth=4 gsprt
```

ベースライン側だけ`--baseline-limit`で深さ1へ上書きする非対称条件が、このゲートの定義である。

### 外部エンジンとの強さ比較

HaChuのような外部エンジンとの比較は、対等な時間制御のGSPRTで行う。
深さ固定では探索1段の意味がエンジンごとに異なるため、強さの比較には使わない。
規則はHaChuの既定設定（RULES.md第33条第7項、`L1,L3,P0,P5,P6,R2,E1,E2`）に合わせ、審判層とminase側の双方へ同じ規則を与える。

```console
cargo run --release --bin minase -- match run \
  --run-dir data/matches/<測定名> --seed <シード> \
  --candidate commit:<測定対象> --baseline "cecp:../hachu-debian/hachu" \
  --rules L1,L3,P0,P5,P6,R2,E1,E2 --each time=60000+1000 gsprt
```

HaChuは`usermove`で受けた着手を自前の規則で検査し、不合法と判定すると`Illegal move`を返す。
審判層が合法とした着手を相手エンジンが拒否した場合は、拒否した側の反則負け（`rejected_moves`）として算入する。
HaChuが自玉の詰みを判定して着手を返さずに結果行だけを出した場合は、投了として当該局の負けに算入し、`engine_failures:`には数えない。
判定の採用前に、`rejected_moves`が0であることを必ず確認する。
0でない場合は規則の不一致が疑われるため、当該局の着手列を再現して原因を調べる。

### 進捗記録の固定局数Elo

各フェーズ完了時の強さの積み上がりは、固定ペア数のEloと95%信頼区間で記録する。
固定200ペアのEloは95%信頼区間の幅が約65 Eloあり、個々の変更の効果量を測る精度はない。
このため、変更ごとのEloは測らず、段階ごとの固定局数Eloだけを進捗指標とする。

```console
cargo run --release --bin minase -- match run \
  --run-dir data/matches/<測定名> --seed <シード> \
  --candidate commit:<新> --baseline commit:<旧> \
  --each depth=4 elo --pairs 200
```

全勝または全敗の標本ではロジスティックEloの点推定が無限大になる。
その場合は勝率と局数をそのまま記録し、必要なら1局あたり期待スコアの95%下限（rule of three）による下界を併記する。

### 先読みを対局条件に含める測定（`--ponder`）

`--ponder`は、USIの先読み（ponder）を対局進行に含める対局条件である。
ハーネスは予想手を返したエンジンにだけ相手の手番中の先読みをさせ、候補と基準に同じ手順を適用するので、`--ponder`は時間制御と同じ対局条件であり、機能比較のスイッチではない（送受信の手順は [plans/ponder.md](../plans/ponder.md) の「対局ハーネスの対局進行」）。
`--ponder`は両エンジンが時間制御（`time=`）の場合にだけ指定でき、`depth`または`nodes`の制限、および`cecp:`のエンジンとの併用はエラーになる。
外れた先読みを止める時間は、先読みをした側の消費時間に含まれる。
不合法な予想手は反則負けにせず、先読みをさせずに件数だけを数える。

最終サマリの`ponder candidate:`行と`ponder baseline:`行は、予想手の出力数、不合法な予想手の数、`go ponder`の送信数、的中数、および着手数を出力する。
先読みの実装を変更する候補の採否では、候補の`illegal_predictions`が0であることも採用の条件にし、両者のCPU時間、`go ponder`の送信数、および的中数を測定記録へ残す。

`--ponder`の測定が示すのは「同じ時計の下で、相手の手番中の計算も使える実装の強さ」であり、同じCPU時間あたりの効率ではない。
段階ゲートの標準コマンドは`--ponder`を含まない。
`--ponder`は、先読みの挙動を変える変更の採否と、先読みを使う運用条件での強さの確認に使う。

## 実行ディレクトリと再開

`minase match run`は、新しい測定では`--run-dir`、保存済み測定の再開では`--resume`のどちらか一方を必須とする。
`--run-dir`には存在しないパスを指定し、測定ごとに別のディレクトリを使う。
ハーネスはそのディレクトリに、実行条件の`manifest.json`、累計実行時間と中断状態の`summary.json`、起動ごとのrunnerと測定機の`invocations.json`、および確定した各ペアの`pairs/`を保存する。
実行中のディレクトリは排他的にロックされるので、同じディレクトリを指定した別のrunnerまたは`minase match report`は起動に失敗する。
再開と監査には実行ディレクトリ全体が必要なので、個別のJSONを編集しない。

中断した測定は、`--resume`に実行ディレクトリを指定して再開する。
実行条件はすべて`manifest.json`から読むので指定し直さず、`--resume`と条件の引数を同時に指定すると引数のエラーで終了する。

```console
cargo run --release --bin minase -- match run \
  --resume data/matches/<測定名>
```

確定済みペアは再計算せず、欠番だけを実行して、ペア番号順に同じ統計へ取り込む。
GSPRTのペア数上限または固定局数Eloのペア数を増やして対局列を延長する場合は、`--target-pairs <N>`を加える。
`N`は直前の起動の目標より大きくなければならない。

再開時には対局するエンジンの同一性を照合し、記録と異なれば明示的なエラーで終了する（照合の項目は [plans/match-resume-simplification.md](../plans/match-resume-simplification.md)）。
runnerと測定機は照合しないので、作業ツリーの`minase`を再ビルドした後でも再開できる。
起動の記録に複数のrunnerが現れた測定は、そのことを測定記録に書く。
記録形式の版4（起動の記録を持たない形式）の実行ディレクトリは、変更後の`minase`では再開できない。
この場合は、その測定を開始したrunnerを使う。

時間制御の対局結果と逐次検定は再開後も有効だが、強制終了した測定は処理停止から記録更新までの時間を確定できないため、スループット校正には使わない。
同様に、起動ごとの測定機が異なる測定も、校正用の指標の意味が定まらないので`minase match report`の集計対象外とする。

## 保存記録の集計

`minase match report`は、同一時間制御の固定局数Eloで完了した実行ディレクトリから、Elo、95%信頼区間、異常件数、CPU時間、局時間、最大常駐メモリ、および校正用の2主指標をJSONで再計算する。
GSPRT、候補と基準で時間制御が異なる測定、実行中の測定、強制終了を含む測定、および起動ごとの測定機が異なる測定は集計対象外であり、条件を満たさなければエラーで終了する。
記録形式の版4の実行ディレクトリも読み取れる。
エンジン異常などで資源を取得できない局があっても得点と異常件数は再集計され、欠測した資源に依存する指標だけが`null`になる（欠測の扱いの詳細は [plans/match-harness-efficiency.md](../plans/match-harness-efficiency.md) の「保存記録の集計」）。
集計を読む側も、欠測を0で補完したり、欠測局を除外して最大値または校正指標を計算したりしてはならない。
校正測定はLinux上で行い、両エンジンの`Threads`、各局のCPU時間と最大常駐メモリ、物理コア数、および実メモリ容量が保存されていることを前提とする。

```console
cargo run --release --bin minase -- match report \
  --run-dir data/matches/<測定名>
```

時間制御の比較と校正用の2主指標は、機能採否の標準手順には含まれない診断用途であり、測定条件そのものを調べるときにだけ使う。
`--ponder`の測定では先読みの探索時間もプロセスのCPU時間に含まれるので、CPU時間に依存する校正用の指標は`--ponder`なしの測定と比較できない。
時間制御を比較する場合は、比較対象に候補時間制御の実行ディレクトリ、`--compare-to`に基準時間制御の実行ディレクトリを指定する。
両方の実行は、時間制御を除く実行条件、測定機、および保存済みペア番号が一致していなければならない。

```console
cargo run --release --bin minase -- match report \
  --run-dir data/matches/<候補時間制御> \
  --compare-to data/matches/<現行時間制御>
```

## エンジンの指定方法

`--candidate`と`--baseline`には、エンジンを次の4つの形式で指定する。

標準の測定では、`commit:<hash>`の形式でコミットを指定する。
ハーネスは当該コミットを`git archive`で展開して`cargo build --release --bin minase`を実行し、成果物を`target/match-cache/`へキャッシュする。
キャッシュの検証と再ビルドの規則は、[plans/match-harness-efficiency.md](../plans/match-harness-efficiency.md) の「履歴バイナリのキャッシュ」にある。
作業ツリーにある未コミットの変更は、この形式のビルドには含まれない。
起動引数`--protocol usi --rules <マッチ規則>`は自動で付与される。
`--rules`の値は入力原文のまま両エンジンへ渡され、各コミットのバイナリがそれぞれの版の規則コードとして解釈する。
規則コードP0とE0を導入する前のコミットを対戦相手とする測定では、規則コードを列挙した指定を旧版のバイナリが拒否するので、`engine-default`などのプリセット名で指定する。

未コミットの作業ツリーや外部のUSIエンジンを測る場合は、パスと空白区切りの引数からなる起動コマンドで指定する。
たとえば`"target/release/minase --protocol usi --rules engine-default"`のように書く。
minase本体は`--protocol`と`--rules`の指定が必須なので、この形式では両方の引数を必ず書く。

ハーネス自体の煙試験には`random`を指定する。
この指定では同一ビルドの`minase dev usi-random`が起動され、合法手から一様ランダムに着手する校正用エンジンとして動く。
`random`同士の対局は、真のElo差が0であると分かっている唯一の対戦カードである。

HaChuのようにUSIに対応していない外部エンジンとの比較には、`cecp:<起動コマンド>`の形式を使う。
この形式は、CECP（XBoardプロトコル）で対局するエンジンを起動する。
指定例は`"cecp:../hachu-debian/hachu"`である。
接続時のハンドシェイクと毎手の同期の手順は、[plans/match-harness.md](../plans/match-harness.md) の「CECPセッション管理」にある。
指定できる思考制限は、`depth`、秒単位の時間制御、および1手固定時間の3種類である。
1手固定時間は、基本時間と加算が0で秒読みが整数秒の時間制御として指定する。
`nodes`、基本時間や加算を伴う秒読み、および秒未満の値は指定できない。
HaChuは1手固定時間を指定すると、指定値より短い時間で着手する。
測定の詳細は[HaChu対minaseの条件格子測定](../plans/hachu-condition-grid.md)にある。
規則はエンジン側の設定に委ねられるため、`--rules`にはそのエンジンが実装する規則を指定する。

置換表容量は`--candidate-hash`と`--baseline-hash`にMB単位で指定し、USIエンジンには`setoption name USI_Hash`、CECPエンジンには`memory`で伝える。
省略時はエンジンの既定値（minaseは`USI_Hash`の既定256 MB、CECPエンジンは`memory 256`）で走り、解決後の容量は`manifest.json`の`hash_mb`に記録され、再開時にはこの値で対局する。
HaChuは受けた容量を2の冪へ丸めるため、CECPエンジンには2の冪だけを指定できる。

ハーネスは、USIエンジンの起動時に`setoption name ResignValue value 99999`を候補と基準の両方へ無条件に送り、エンジンの投了を無効にして対局を規則上の終局まで指させる（理由は [USI投了](../plans/usi-resignation.md)）。
このオプションを持たないコミットは、USIの慣例どおり未知のオプション名を無視する。

## 統計的手続き

判定はペンタノミアルGSPRTによる。
同一開始局面で先後を入れ替えたペア対局は2局間に相関があるため、局単位ではなく候補側のペア得点合計（0、0.5、1、1.5、2）の5分類度数で対数尤度比（LLR）を計算する。
LLRの計算方式と、fishtestの参照値による単体テストは、[plans/search.md](../plans/search.md) の「GSPRTと固定局数Elo」が定める。

仮説と誤り率は次のとおり固定する。
Eloの写像はロジスティック（`s = 1/(1+10^(-elo/400))`）、H0はelo=0、H1はelo=10、α=β=0.05である。
H1を採用する境界は`log((1-β)/α) ≈ +2.944`、H0を採用する境界は`log(β/(1-α)) ≈ -2.944`である。
ハーネスは1ペア取り込むごとにLLRを再計算する。
停止は原則としてLLRの境界交差によって起こる。ペア数上限（`--max-pairs`、既定100,000）はfishtestと同様の暴走保険であり、到達時は判定保留として報告する。
ただしSTCで指定する上限3,000ペアは暴走保険ではなく段階ゲートの振分け規則であり、到達時の判定保留は停止時点のLLRの符号によってLTCへ進むかどうかを決める。
H1を5 Eloとしていた時期の測定は、`manifest.json`の`h1_elo`で識別できる（変更の経緯は [棋力測定の所要時間削減](../plans/match-cost-reduction.md)）。
H1=10は恒久の値ではなく、新境界のLTCで`H0`となった候補が連続して3件出た時点、または段階計画が完了した時点で再検討する。

必要標本数の目安は次のとおりである。
判定までの期待ペア数は、実測のペア得点分散をσ²=0.10に固定したWald近似では、真のElo差がH0とH1の中間（5 Elo）にある場合に約4,200ペア、H1と同じ10 Eloの場合に約2,600ペア、20 Eloの場合に約950ペア、40 Eloの場合に約410ペアとなる。
一方、置換表や静止探索のような数十Elo以上の効果は数十〜数百ペアで決着する。
計算方法と効果量別の表は[棋力測定の所要時間削減](../plans/match-cost-reduction.md#仮説h1を10-eloへ広げる)が定める。

検定全体の健全性は、合成結果によるモンテカルロ検証で確認する。
固定シードで各仮説を3,000回反復し、elo=0での誤採用率が8%以下、elo=10での検出率が90%以上であることを検査する。
この検証は通常のテスト実行から外し、検定式、仮説、正則化、判定境界、または停止規則を変更したときに、次のコマンドで実行する。
通常実行の外部参照値と境界判定だけでは、参照点以外での累積的な統計誤りを検出できないため、変更時にはモンテカルロ検証も完了させる。

```sh
cargo test --lib stats::tests::gsprt_monte_carlo_error_rates_match_documented_thresholds -- --ignored --exact
```

固定局数Eloモードは、正規化ペア得点の平均と分散からEloの点推定と95%信頼区間を計算する。観測単位はペアであり、分散はペンタノミアル度数から推定する。

## ペア対局と再現性

開始局面は、ペア番号ごとに決定的に派生したシードで初期局面から8〜12手（一様選択）をランダムに進めて作る。
同一開始局面で先後を入れ替えて2局対戦し、手番差のバイアスを除去する。
エンジンプロセスは局ごとに起動し直すため、置換表などの内部状態が局間に持ち越されることはない。

両エンジンを`Threads=1`で動かし、同じ`--seed`と引数を与えれば、出力（経過時間の行を除く）、ペンタノミアル度数、LLR、判定、および停止ペア番号は完全に再現される。
`Threads=1`はエンジンの既定値である。
`--concurrency N`のペア並列実行でも、LLRへの取り込みと出力はペア番号順に整列されるため、判定は並列度に依存しない。
この完全再現契約は、`Threads=1`かつ`depth`または`nodes`制限の対局に限る。
`Threads>1`では、共有置換表へのアクセス順がOSのスケジューリングに依存するため、固定深さまたは固定ノード数でも完全再現を保証しない。
時間制御対局も着手時間の実測に依存するため、完全再現の対象外である。
時間制御対局では、最終サマリの`time_forfeits`を必ず記録する。
シードを省略すると時刻から生成されるので、記録に残す測定では`--seed`を明示し、出力先頭の`seed:`行とともに保存する。

同時対局数は、`--concurrency`の省略時に`minase match run`が「物理コア数から1を引き、候補と基準の`Threads`の大きい方で割った商」として自動計算する。
`--ponder`のときは両エンジンが同時に探索するので、除数を「`Threads`の大きい方の2倍」とする。
物理コア数またはどちらかの`Threads`が取得できない場合、および計算結果が1未満になる場合は、既定値を推測せずに明示エラーで終了するため、`--concurrency`を明示する。
解決後の同時対局数は`manifest.json`へ記録され、再開時にはこの値を使う。

## 異常時の裁定

エンジンの不正着手（`bestmove`が審判層の合法手にない）、クラッシュ（プロセス終了またはパイプ切断）、応答タイムアウト（`--response-timeout`、既定120秒）は、いずれも起こしたエンジンの当該局の反則負けとして統計へ算入される。
時間制御対局では、ハーネスが両エンジンの時計を管理して毎手`go btime`などで残り時間を送り、着手時間が残り時間と秒読みの和を超えた場合も同様に反則負け（`time_forfeits`）として算入する。
バグで落ちるエンジンは弱いエンジンとして測るというfastchessおよびfishtestと同じ思想である。
最終サマリの`engine_failures:`行に理由別件数が出るため、測定結果を採用する前に必ず確認し、0でない場合はまず異常の原因を調査する。
手数上限（`--max-ply`、既定4096）への到達だけは実力と無関係な打ち切りとして、当該ペアごと破棄され件数報告される。

## 測定結果の記録

測定は、終了した時点で直ちに`docs/measurements/<測定名>.md`へ1測定1ファイルで記録し、設計書からは測定名でリンクする（見出しの順序は docs/plans/README.md が定める）。
記録には、シードを含むコマンドライン全体、両エンジンのコミットハッシュ、ペンタノミアル度数、LLRと判定、破棄ペア数と異常件数、および経過時間を含める。
固定局数Eloの測定では、LLRと判定の代わりにEloと信頼区間を記録する。
実行条件とエンジンバイナリのSHA-256は`manifest.json`、起動ごとのrunnerと測定機は`invocations.json`、確定済みの結果と異常分類は`pairs/`、再開を含む累計実行時間は`summary.json`を正とする。
標準出力の`elapsed`は当該起動だけの経過時間であり、再開した測定の累計時間には`summary.json`の`active_wall_time_ns`を使う。
固定局数の時間制御測定では`minase match report`のJSONを保存記録から再計算した集計値として使い、標準出力の最終サマリだけに依存しない。

並列測定では、CPU型、物理コア数、論理コア数、候補と基準のワーカー数、`USI_Hash`、同時対局数、時間制御、および`time_forfeits`も記録する。
外部エンジンを含む測定では、そのエンジンの版（ソースのコミットとビルド手順）と規則オプションの設定も記録する。

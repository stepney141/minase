# minaseのテストの手引き

本書は、minaseのテストを書く人間とエージェントに向けて、書く範囲、検証の層、期待値の根拠、決定性、および運用の規則を定める。
テストの配置、命名、および個々の契約はコードとそのdocコメントが定める。
規則の理由とテスト一般の原則は[テストの一般原則](testing-general-principles.md)にあり、食い違う場合は本書が優先する。
個別の判断に迷ったときは、「テストの条件」と「書く範囲」に戻る。

## テストの条件

テストは、次の5条件を満たすように書く。
理由と例は[テストの一般原則](testing-general-principles.md#良いテストの条件)にある。

1. 守りたい挙動が壊れたら必ず失敗する。
2. 挙動を検証し、実装の呼び出し方を検証しない。
3. 失敗するのは本物の誤りのときだけである。
4. 速く、決定的である。
5. テストの通過やカバレッジの高さを、品質の保証と勘違いしない。

条件2の例外は、相互作用そのものが仕様である場合である。
エンジンとGUIの通信プロトコルUSIで送受信する行、自己対局ハーネス`minase match run`が書く記録ファイルの内容、および外部エンジンへ送る着手の表記は、相手との契約なので、送った内容を検証してよい。
検証は内部の補助関数ではなくモジュールの公開関数を通して行い、内部関数を直接検証している既存のテストは、改修の機会に公開関数を通した検証へ順次移す。

条件3を満たさないテストは、挙動に基づく形へ書き直す。
通らないからといって検証を消す、または緩めるのは改ざんであり、書き直しではない。
仕様が変わったためにテストを更新するのは、正当な保守である。

条件5に関して、カバレッジには目標値を設けず、数値の低い領域で理由を確かめてテストの欠落を探す、診断用の二次的な指標にとどめる（[ADR](../adr/derive-test-expectations-from-normative-documents.md)の「検討した代案」）。
何をテストするかは「書く範囲」の表で決め、検出力は「運用」の節の変異による確認で確かめる。

## 書く範囲

目指す水準は「このテストがあれば、手で確かめずにリリースしてよい」状態である。
ただし、何を心配するかは人によって違うので、実際に書くかどうかは次の観測できる条件で判定する。
いずれかに当てはまれば書く。

| 条件 | どの層で | 何を検証するか |
|---|---|---|
| 分岐がある（`if`、`match`、エラー経路） | ユニット | 各分岐を通す |
| 外部入力を解析、検証、または変換する。USIの行、局面の文字列表記SFEN、起動引数、ファイル形式、USIオプションの値がこれに該当する | ユニット | 受理する入力と拒否する入力の両方。空、欠落、非ASCII、桁あふれ、未対応の版を含む。規則は[外部入力でパニックしない](../lessons/no-panic-on-external-input.md)と[エラーを文字列へ失わない](../lessons/typed-errors-over-strings.md)にある |
| 規則の条文または規則コード（chu-shogi.md第33条のローカルルールの識別子）に対応する挙動を実装する | ユニット | 条文から導いた期待値。テスト名に条番号を含める |
| 誤ると対局または測定の結果が変わる（終局の裁定、反復の判定、時計の管理、反則の算入、統計の計算） | ユニット。プロセス境界を越える部分は統合 | 正しく裁定、算入、計算されること。統計は外部の参照値と照合する |
| 内部状態を保持して更新する（置換表、時計、局面の履歴、測定の再開） | ユニット。再開はプロセス境界を越えるので統合 | 操作の列に対する状態遷移と派生値。再実行に対する冪等性 |
| ファイルを上書き、削除、または移動する経路（実行ディレクトリ、重み、教師データ） | 判定はユニット。実際の消去と既存パスの拒否は統合 | 消してよい条件で消え、消してはならない条件で拒否されること。この検証は省略できない |
| 自分が所有するファイル形式の読み書きを変える | 統合 | 実ファイルに書いて読み直し、内容が等しいこと |
| 複数の呼び出し元を持つ共有関数を変更した | その関数の層。影響先は呼び出し元の層 | 関数の挙動を網羅する。呼び出し元は、戻り値を次の処理へ渡すだけのものを除き、分岐や計算に使うものに絞って確かめる |
| 別の場所の判定ロジックを複製した | 複製先の層 | 複製先にも同じ事例を置く。複製元のテストは複製先を守らない |
| 外部エンジン、GUI、保存形式、またはライブラリ`minase-core`の公開APIとの境界を変える | ユニットまたは統合 | 送受信する行、記録の形、および公開APIの契約。相手の実物との疎通は記録済みの棋譜または手動で確かめる |
| 不具合を修正した | 不具合が現れた層 | 不具合を再現する最小の事例。修正を外すと失敗することを確かめる（[教訓](../lessons/confirm-regression-test-fails-without-fix.md)） |

共有関数と外部との境界は、変更の波及が大きいので、変更したときに限らず細かい事例を厚く保つ。
ある挙動をどの層で守るかは書きやすさで決めてよく、テスト全体でいずれかの層が守っていれば、複数の層で重ねて書く必要はない。

守るべき挙動（分岐、変換、仕様上の判断）を持たないものは書かなくてよい。
型と定数の定義、分岐のない初期化、モジュール宣言と`pub use`だけのファイル、条件分岐のない出力の整形、入出力を変換せず委譲するだけの関数、および`test_util`と`fixtures/`のようなテスト支援の資産がこれに当たる。
委譲するだけの薄い関数の、委譲先との境界は、委譲先の実物を使う層で担保する。
「別の層で担保する」を理由に省くときは、その層にある具体的なテストを特定して確かめ、棚卸しで実在を再確認する。
「書きにくい」は省く理由にならず、[設計を疑う](testing-general-principles.md#テストしにくいコードは設計を疑う)。

境界値は、1つずれると実害になる、境界で挙動が変わる箇所だけを書き、型の最大値やオーバーフローを機械的に並べない。
ただし、明示された上限と下限（深さの範囲、置換表容量の上限など）と外部入力の桁あふれは、入力の検証なので必須である。
迷ったときは、上の表の条件を優先する。

組合せの網羅は前の層で行い、後の層は代表的な事例に絞る。
たとえば、ローカルルールの組合せごとの裁定は規則の判定のユニットテストで網羅し、プロセスを起動する統合テストと保存棋譜の再生は代表的な規則セットだけで行う。
内部で組み立てた中間表現の文字列は部分一致で検証せず、その中間表現を使った結果で検証する。
部分一致は取り違えを検出できず、整形の変更で偽陽性を出すからである。

仕様が未確定な部分があっても、確定した振る舞いのテストは後回しにしない。
未確定なのは多くの場合、表示や出力の形であって振る舞いではなく、テストはエージェントが安く書けるので、費用も先送りの理由にしない。
変わりやすい出力の形式に依存するテストは、形式が決まるまで待ってよい。
待つ場合は、確定後に追加するテストを設計書の残作業に書いて追跡し、目安として1か月以内に決まる見込みがなければ、暫定の形式に対して書く。
長期間テストがない状態のほうが、多少の書き直しより危険だからである。

## 検証の層

minaseの検証は、次の6層からなる。
層1から層4は自動テストであり、番号の小さい層で検証できるものはその層で確かめ、そこで原理的に検証できないものだけを後の層へ回す。
層5と層6は測定であり、合否を決めるテストの代わりではないので、この順序の対象に入れない。

1. ユニットテスト。各モジュールの`#[cfg(test)] mod tests`に置き、プロセス内で完結する挙動を検証する。合法手生成、規則の判定、表記の変換、探索の契約、統計の式がここに当たる。
2. 統合テスト。各crateの`tests/`に置き、crateの公開APIを外から使う挙動と、プロセス境界を越える挙動を検証する。エンジンのcrateでは`CARGO_BIN_EXE_minase`で実際のバイナリを起動し、USIの往復、`--io-log`の記録、および対局ハーネスの実行ディレクトリを検証する。バイナリの起動は、CLIのサブコマンドのようにライブラリのAPIをプロセス内で呼んでも検証できない場合に限る。
3. 記録済みの外部オラクル（正解を与える外部の実装や資料）との照合。オンライン対局サイトLishogiの公開棋譜を1手ずつ再生して合法手判定と終局の裁定を突き合わせる統合テスト、Stockfishの測定基盤fishtestの参照値による検定式の照合、および中将棋エンジンHaChuの駒文字表との対応の検証がここに当たる。外部の挙動は保存したテストデータ（fixture）としてだけテストに入れ、実ネットワークへは出ない。棋譜の取得は`scripts/`の別のスクリプトが担う。
4. ランダム対局による不変条件の検査。`minase dev random-play`は、ランダムな合法手で対局を進めて毎手`Position::validate`で局面の不変条件を検査し、失敗した局をシードと局番号で再現できる（[デバッグの手引き](debugging.md)）。条文ごとの事例では網羅できない相互作用を、ここで広く検査する。
5. benchによる速度の測定。`minase dev bench`は決まった局面の集合を探索してノード数と時間を測る診断であり、探索木を変えない変更の確認と速度の比較に使う。
6. SPRTによる棋力の測定。棋力に影響し得る変更の採否は自己対局の逐次検定で判定する（[SPRTによる棋力測定の手引き](sprt.md)）。

層を選ぶときは、ユニットテストでは原理的に検証できないか、プロセス内でライブラリのAPIを呼ぶ統合テストでは検証できないか、プロセスを起動しなければ検証できないか、自動化できないかを順に問う。
前の問いで検証できるなら、そこで書く。

### 後の層のテストを足す条件

テストの本数は、層1を厚く、後の層ほど薄くする。
後の層へテストを足す必要条件は、複数のプロセスまたは境界をまたいで初めて壊れる挙動であることの1点に限られ、満たさないものは前の層で書く。
満たす挙動は[4類型](testing-general-principles.md#どの層で書くか)に分かれる。
USIの往復と探索の停止要求は層2の統合テストが、外部システムとの結合は層3の保存棋譜の再生が、遷移をまたぐ状態の保持は測定の再開の統合テストが守る。
後の層のテストを足すときは、どの類型に当たるかを設計書に書き、要否は実装の後ではなく設計書を書く時点で決める。

後の層の代表事例は、GUIからの対局、LishogiのBotとしての対局、`match run`による測定という実際の利用経路から選ぶ。
後の層のテストでは、検証対象の経路を通して状態を準備しない。
局面はUSIで着手を送って作らず、SFENや`test_util`で直接組み立て、`--io-log`や実行ディレクトリの記録に特定の行や項目が出ること、または出ないことを検証する。

### 依存の差し替え

実物が使えるなら実物を使い、使いにくいときだけ代替物に差し替える。
自分が完全に制御し、外部から観測されない依存は差し替えず、実物に書いて読み直し、結果の状態で検証する。
minaseでは、自分が所有するファイル形式と測定の実行ディレクトリがこれに当たる。
外部から観測される依存（外部エンジン、GUI、対局サイト）は代替物に差し替えて構わないが、相手へ送った内容は契約なので検証の対象になる。

差し替えが要るときは、呼び出しを記録するだけのモックより、`Vec<u8>`や`Cursor`による入出力、合法手から一様に着手する校正用エンジン`random`のような、実際に動く軽量な代替実装を優先する。
上位の処理の分岐だけを見るユニットテストでは書き込み先をメモリ上にしてよいが、実ファイルでの往復は別のテストで必ず検証する。

minaseのコードの大半は、合法手生成、規則の判定、探索、および統計というドメインモデルとアルゴリズムなので、ユニットテストが主力になる。
ユースケースの層に当たるUSIの会話の処理と`match run`の対局の進行は、統合テストで検証する。

### 外部との境界

minaseの境界は、USI、CECP、ファイル形式、実行ディレクトリの記録、および別リポジトリのminase-guiとminase-lishogi-botである。
ワークスペース内のcrate間の契約のずれは、共有の型でコンパイル時に検出する。
USIとCECPの契約は、プロトコルの調査メモ（[research/protocols/](../research/protocols/README.md)）と保存棋譜で固定する。
ファイル形式は版の欄を持ち、読み手がヘッダから期待する長さを導いて検査する（[ファイル形式の一覧](file-formats.md)）。
minase-guiとminase-lishogi-botは別の周期でリリースされるが、USIと規則コードだけを使い、その互換性を壊す変更は[CONTRIBUTING.md](../../CONTRIBUTING.md)の規約で`BREAKING CHANGE`として知らせるので、契約テストの道具は置かず、USIの調査メモを正本とする。

minaseにはデータベースも外部サービスもないので、差し替えの対象はほぼ外部エンジンに限られ、その境界は記録済みの棋譜（層3）と手動の疎通確認で担保する。
保存棋譜は実物から採取したものに限り、相手側（LishogiやHaChu）の版が変わったら、再採取するか手動で確かめる。

自動テストで担保しきれない範囲は手動で確かめる。
minaseでは、GUIおよび対局サイトとの実際の接続と、外部エンジンとの疎通がこれに当たる。
手動の確認は、設計書の完了条件を基準に、手元のGUIとBotの配備環境のそれぞれで、リリースの前と接続の形を変えたときに行い、リリース前の項目は[リリースの手引き](release.md)に一覧で置く。
手動の確認は層ではなく最終の確認であり、自動化できるものを手動に残さない。

### 整合検査とperft

`cargo test`では、フィーチャ`invariants`が常に有効になり、着手のたびに局面を全検査し、探索中の評価のたびに差分更新の値を全計算と照合する（[重い整合検査をフィーチャ`invariants`に置く](../adr/enable-invariant-checks-in-tests-by-feature.md)）。
したがって、テストの中で指した着手と探索も、全検査を受ける。

perftは、ある局面から指定した深さまでの合法手の列を数え上げる手法である。
その数値は合法手生成の正しさの基準にしない（[ADR](../adr/verify-movegen-without-perft-counts.md)）。
合法手生成は、条文ごとの境界局面のテスト、ランダムな局面に対する性質のテスト、および保存棋譜の再生で検証する。
性質のテストは、先後の180度回転対称や着手の適用と取消しの往復のように、どの局面でも成り立つ関係を層1と層4で確かめる。

## 期待値の根拠

テストの期待値は、[規範文書から導き、現在の実装から導かない](../adr/derive-test-expectations-from-normative-documents.md)。
証拠は次の3種類である。

1. [chu-shogi.md](../rules/chu-shogi.md)と各領域の規範文書（手引き、プロトコルの調査メモ、コードのdocコメント、ADR）。
2. 外部のプロトコルおよび実装との互換性の契約（fishtestの参照値、Lishogiの棋譜、HaChuの駒文字表）。
3. 確認済みの過去の不具合と境界事例。

現在の実装の出力は、正しさの証拠として使わない。
現在の出力を丸ごと保存して比較するテスト（スナップショット）も実装の写しなので書かない。
ただし、保存棋譜や参照値のような外部契約の固定は、実装の写しではないので除く。

規則に関わるテストは、`article_14_1_...`のように根拠の条番号を名前に含める。
規範文書から期待値を確定できない挙動は、テストの名前またはコメントで実装の契約であることを明示してから書く。
規範文書の欠落が原因なら、先にその挙動を定めるべき規範文書へ最小限の規範文を追記し、その文言に基づくテストを書く。
仕様の裏付けがない期待値は書かない。
閾値や境界のような数値は、コードを正本として持ち、手引きに写すときはコードの該当箇所を参照する。

## 決定性

実行のたびに通ったり落ちたりする不安定なテストは、原因がほぼ決まっている。
原因と防ぎ方の一覧は[テストの一般原則](testing-general-principles.md#不安定なテストの扱い)にあり、minaseでは次のように書く。

- 完了は固定時間で待たず、条件が満たされるまで待つ。エンジンの応答は`bestmove`などの行を読むまで待ち、スレッドの終了はjoinで待ち、ファイルの出現や状態の反映は上限つきのポーリングで待つ。
- プロセスの起動や`usiok`の受信を準備完了とみなさない。USIでは`isready`に対する`readyok`、XBoard系の通信プロトコルCECPでは[ハンドシェイクの手順](../research/protocols/README.md)の完了まで待つ。
- 対局ハーネスの統合テストは、プロセスIDと連番から一意な実行ディレクトリを作る。書き込む資源にはテストごとに一意な名前を使い、固定の名前は読むだけの fixture に限る。共有が避けられないテストは専用のテストバイナリに集めて直列化し、全体の並列実行は止めない。
- 一時領域は失敗時にも残骸が残らない形で作り、残ったものは棚卸しで掃除する。
- 新しく書く処理では、時刻や経過時間を引数で受け取る形にしてテストから値を与える。時間予算は式に対する数値例で検証し、実測の経過時間に閾値を置かない。
- 乱数生成器またはシードを引数で渡し、テストでは固定する。minaseの乱数は`XorShift64`で、`--seed`と局番号から決定的に派生する。
- 実ネットワークへ接続するテストと、外部エンジンを要するテストは置かない。外部の挙動は保存した fixture で与える。
- 局面や設定は、テストごとに文字列で直書きせず、`test_util`の構築関数で組み立てる。
- 浮動小数点は許容誤差で比較する。ただし、GPUとCPUの一致のように加算順まで定義して一致を要求する契約は、その契約どおり厳密に比較する。
- 競合状態の修正は、回帰テストを10回以上連続で通して確かめる（[教訓](../lessons/repeat-concurrency-regression-tests.md)）。

結果が決定的でない機能は、テストではなく測定で評価する。
持ち時間と加算で進める時間制御の対局は着手時間の実測に、`Threads>1`の探索は共有置換表へのアクセス順に、GPUでの学習はカーネルの実行順に依存するので、設計上、完全な再現の対象外である。
時間制御の挙動は、テストで厳密な値を要求せず、固定深さまたは固定ノード数の決定的な条件と、時間予算の式に対する数値例で検証する。
学習は、シードを明示して走らせ、検証損失の記録で評価する。
SPRTの再現性の契約は[棋力測定の手引き](sprt.md)の「ペア対局と再現性」の節にある。

### 評価値と探索結果に依存するテスト

評価値、最善手、読み筋、およびノード数は、重みファイル、探索の係数、枝刈り、置換表の状態、およびスレッド数に依存する。
これらを具体的な値で固定すると、重みの再学習や探索の改良という正当な変更で落ちるので偽陽性の原因になり、`Threads>1`では同じ入力でも結果が変わるので不安定にもなる。
落ちたときに期待値を新しい出力へ置き換えるだけの更新は、テストが実装を追認しているだけの兆候であり、「期待値の根拠」の節に反する。

探索と評価のテストは、次の形で書く。

- 具体的な値ではなく、満たすべき契約を検証する。最善手が合法手に含まれること、読み筋の先頭が最善手と一致すること、同じ入力で同じ結果が返ること、指定した深さやノード数で止まること、停止理由が正しいことがその例である。
- 規則で値が決まるものだけを厳密に比較する。詰みの値、引き分けの値`DRAW_SCORE`、および裁定の結果がこれに当たる。
- 探索のテストは、学習で変わる埋め込みの重みを読まず、[固定ネットの教訓](../lessons/search-tests-use-a-fixed-net.md)のとおり学習前の重み`crates/minase/nets/nnue-epoch0.bin`から作る`test_nnue()`の固定ネットで書く。探索の分岐を作りたいときは、このネットのまま置換表に値を仕込む。
- 最善手を期待値として検証したいときは、一方的な捕獲や詰みのように評価関数によらず結論が決まる局面を選び、特定の重みに依存する局面は避ける。
- 探索以外のテストで実際の重み`eval::weights()`を読むときは契約の検証にとどめ、具体的な評価値や最善手を期待値として固定しない。
- ノード数と速度は、テストで固定せずbenchで比較する。

重みを更新したときは、実際の重みを使うテストの差分をレビューし、値を写し直すだけの変更があれば、そのテストを契約の検証へ書き直す。

### 時間管理のテスト

「n秒で止まる」という契約を、実際にn秒待って確かめるテストは書かない。
そのテストは遅く、測定機の負荷で結果が変わり、しかもエンジンの判断ではなくOSの時計を検証している。
時間管理は、方針と機構に分けてテストする。

- 方針とは、残り時間、加算、秒読み、手数、および経過時間から予算を決める計算と、予測した次の反復が予算に収まるかの判断である。これらは純粋関数なので、経過時間を値として与えて瞬時に検証する。既存のテストは、探索の開始時刻を過去へずらして経過時間を作る。
- 機構とは、時計を読んで停止フラグを立て、探索がそれに従う仕組みである。これは数十ミリ秒の小さな予算で動かし、予算に余裕を足した上限までに止まることだけを検証する。停止した時刻の厳密な値は検証しない。
- 実際の時間制御の下で時間切れを起こさないことは、テストではなくスモークテストで確かめる。[打ち切り上限の教訓](../lessons/cap-hard-limit-by-remaining-fraction.md)のとおり、採否の測定と同じ負荷で時間切れ0件を確かめる。

## 運用

### マージ前の検査

minaseには継続的インテグレーション（CI）の環境もgitのフックによる強制もないので、検査はマージする人またはエージェントが手順として手元で実行する。
masterへマージする前に、次の4つを通す。

```console
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo test -p minase --lib --features search-stats,tuning
```

4つ目は、フィーチャ`search-stats`と`tuning`を有効にしたときだけコンパイルされるテストを実行する。
これらは既定のビルドに含まれないので、`cargo test --workspace`では走らない。
複数のworktreeのブランチを順にmasterへマージするので、マージの後にはマージ後の状態で`cargo test --workspace`を再実行する。

`scripts/`のPythonスクリプトのテストは、この4つの検査に含まれない。
Lishogiの棋譜を取得する`scripts/fetch_lishogi_games.py`、およびvast.aiの調整機でSPSAを実行する`scripts/vast/`と`scripts/vast-spsa/`を変更したときは、マージの前にリポジトリのルートで該当するテストを実行する。
調整機のPythonは3.11なので、後者のテストは手元のPythonに加えて3.11でも実行する。

```console
PYTHONPATH=. python3 scripts/test_fetch_lishogi_games.py
python3 scripts/vast/test_common.py
python3 scripts/vast-spsa/test_spsa.py
```

遅い層は速い層と分けて単独に実行できるようにし、`cargo test -p <crate>`や`--test <名前>`で一部だけを回せる形を保つ。
遅いテストを足したときは検査全体の所要時間を測り、目標の10分を超えたら、まず固定の費用の分離と削減を検討し、本数の削減は最後にする。
固定の費用とは、テストバイナリのビルドとリンク、プロセスの起動、および対局ハーネスがコミット指定（`commit:`）のエンジンを用意するためのビルドである。
影響を受けるテストだけの実行、マージ前とマージ後の分離、不安定なテストの自動検出、およびマージキューは今は置かず、結果のキャッシュはビルドの成果物を`target/`と`target/match-cache/`に持つ範囲にとどめる。
棋力測定に使う計算機（測定機）で測定が走っている間は、[測定中の負荷の教訓](../lessons/check-running-measurements-before-cpu-load.md)に従って`nice -n 19`と`-j`で負荷を抑える。

### masterが赤くなったとき

masterのテストが失敗する状態（赤）になったら、原因の変更を直すか戻す。
赤のmasterの修正は、機能の開発より優先する。
赤にした変更をマージした者（委任ならClaudeなどの委任元）が、戻すか直す責任を持つ。

### テスト専用のコードの置き場所

本番の型のフィールド、本番の関数の中の分岐、および本番の型のメソッドに`#[cfg(test)]`を付けず、`#[cfg(not(test))]`も使わない。
テストと本番で異なるコードがコンパイルされ、テストが本番の挙動を確かめていない部分が生じるからである。
`#[cfg(test)]`を付けるのは、`#[cfg(test)] mod tests;`や`#[cfg(test)] mod test_support;`のようなテスト用の子モジュールの宣言だけとする。
テストだけが使う補助関数は、その子モジュール（`X/tests.rs`または`X/test_support.rs`）に置く。
Rustの子モジュールは親モジュールの非公開のフィールドを読めるので、子モジュールに`impl`を書けば、本番の可視性を広げずに済む。
別の実行ファイルのテストから使う補助の項目は、フィーチャ`test-util`で公開する`test_util`モジュールに置き、自分自身を指す開発依存でこのフィーチャを有効にする。
理由と棄却した代案は[ADR](../adr/keep-test-only-code-out-of-production-types-and-functions.md)にある。
αβ探索と評価関数には、この規則を定める前に書かれた`#[cfg(test)]`の項目が残っている。

### `#[ignore]`で除外するテスト

GPUを要するテスト、直前局面の生成器の全列挙、および検定式を変えたときだけ回すモンテカルロ検証は、`#[ignore]`で通常の実行から外している。
除外するテストには、理由の文字列と、実行する条件および標準コマンドを記した手引きの両方を要する。
現在の例は、[NNUEの学習の手引き](nnue-training.md)の`gpu_`テストと、[SPRTの手引き](sprt.md)のモンテカルロ検証である。
直前局面の生成器の全列挙は、直前局面の生成器または合法手生成を変えたときに次のコマンドで実行する。
releaseビルドでの所要時間は、前者が約6分、後者が約9分であり、後者は最大で約6 GBのメモリを使う（[計測記録](../measurements/predecessor-generator/predecessor-generator-profile.md)）。

```console
cargo test -p minase-core --release predecessor_completeness -- --ignored --test-threads=1
cargo test -p minase-core --release predecessor_oracle -- --ignored --test-threads=1
```

理由も実行手順もない`#[ignore]`は、見かけだけの成功であり、有効化するか削除する。
GPUやファイルがないときに早期に`return`して成功させる書き方は、実質的に飛ばしたテストを成功に見せるので書かず、`#[ignore]`か失敗にする。
除外の対象でも、純粋なロジックを抽出した部分は通常のユニットテストで守る。
除外を解くときは、除外の原因になった方式のまま戻さず、原因を取り除いた形で戻す。

### 不安定なテスト

不安定なテストは再実行で隠さず、原因を特定して書き直す。
`cargo test`を再実行したら通った、という形で見つかった場合も不安定なテストとして記録する。
再試行で通すしくみは置かない。
不安定な失敗が出たら、シード、`--io-log`、およびテストの出力を保存してから再実行し、原因の分析に使う。
すぐに直せないときは、理由を書いた`#[ignore]`で通常の実行から外して直す。
同じテストが3回以上不安定になったら、必ず隔離する。
隔離したまま放置した除外は、前項の規則に従い、理由と実行手順を備えて残すか、削除する。

### 回帰テストとレビュー

修正の後に書いたテストは、修正がなくても通る危険がある。
修正対象の処理を一時的に外してテストが失敗することを確かめ、その後で修正を戻して採用する（[教訓](../lessons/confirm-regression-test-fails-without-fix.md)）。
ロジックを変えたのにテストの差分がない変更は疑い、レビューで指摘して最低限の正常系と異常系を足す。

### 変異による検出力の確認

新しい領域のテストを書き終えたら、条件の反転、`<`と`<=`の入替、境界定数の変更、必須の副作用の除去、もっともらしい誤った戻り値の返却、検証分岐の省略といった意味を変える変異を実装へ一時的に加え、テストが検出することを確かめる。
生き残った変異は、検証の弱さか未カバーの挙動かを判定してテストを補強し、再び適用する。
意味を変えない変異と判定したときは、その根拠を記録する。
変異を自動生成する道具は補助にとどめ、判定の主体は手で選んだ代表的な変異とする。
既存のテストの強さを測りたいときは、`cargo-mutants`を変更の差分に限って1回走らせてよい。

### 棚卸し

テストは定期的に棚卸しする。
狙いは速度ではなく、陳腐化と重複の除去、および欠落の発見である。
削る対象は、機能が削除されて不要になった陳腐化したテストと、後から追加されたテストと検証内容が重なる重複したテストの2つに限る。
重複のうち、前の層で検証できるのに後の層に残っているものは優先して外し、利用経路の確認用に代表の1〜2事例は残す。
消す前に、その挙動が別のテストで検証されているかを確かめる。
「最近落ちていない」は削除の理由にならず、落ちないのは守れている証拠である。
棚卸しでは、次も確かめる。

- `#[ignore]`の一覧と、「別の層で担保する」を理由に省いたテストについて、除外の理由が今も事実か、その層のテストが実在するかを照合する。
- テストを持たないモジュールとcrateを列挙する。数えるときは`target/`、`data/`のworktree、およびシンボリックリンク（minase-gui、minase-lishogi-bot）を除外する。
- 見つけた未テストの領域は、誤ったときの影響（対局の結果、測定の結果、学習の結果）で順位を付けて記録し、直さないと決めた領域もその理由とともに記録する。
- 層ごとのテストの本数と所要時間を数え、層2で済む検証が層3以降に回っていないかを確かめる。
- 差し替え用の型や、呼び出しの記録を検証するテストが増えていないかを数える。増えていれば、実装の詳細への結合が進んでいる兆候である。
- 手引きが述べるコマンドと検査が実在し、動くことを確かめる。

### 方針を変えたとき

本書の方針に合わない既存のテストを見つけても、一括では書き直さず、機能の追加と修正で触ったファイルから順に直す。
ただし、実装を写したテストが大半を占めて安全網として働いていない場合は例外であり、2026年8月のspec-first再構築は、この理由で全面的に書き直した（[ADR](../adr/derive-test-expectations-from-normative-documents.md)）。

## エージェントへの委任

minaseでは、Claudeが計画と設計を担い、codexなどのサブエージェントが実装を担う（[codexへの実装委任の手引き](codex-delegation.md)）。
テストは設計者が仕様に基づいて作り、実装から独立した検証の基準とする。
実装者が人間でもエージェントでも同じである。
委任は次の手順で行う。

1. 委任する前に、期待する挙動を規範文書から固定する。条文、ADR、または契約の内容を指示書に書き、期待値を実装から導かせない。
2. テストと実装は、仕様から別々に導く。設計者がテストの事例と期待値を指示書で与え、実装者はそれを満たす実装を書く。既存の同種のテストがあれば、ひな形として指示書で示す。
3. 固定したテストに対して実装させる場合、テストの失敗と成功を反復させてよいが、実装者にテストを書き換えさせない。通らないからと検証を緩める変更は、報告に書かせて設計者が判断する。
4. テストが通った後に、例示した事例だけを通す実装になっていないかを設計者が確かめる。確認の手段は、指示書に書かなかった事例の追加と、「運用」の節の変異による確認である。
5. 委任元は、回収した変更に対して「運用」の節のマージ前の検査を自分で実行し、委任先の報告だけで完了と扱わない。

委任の有無にかかわらず、テストが通っていることを仕様を正しく写し取っている証明とせず、仕様に照らしてテスト自体を読み直し、必要なら強める。

## 棋力と速度はテストで判定しない

テストが通ることは、エンジンが強いことも速いことも意味しない。
探索、評価、および時間管理の変更が棋力を上げるかどうかは、[SPRTによる棋力測定](sprt.md)の段階ゲートだけが判定する。
速度は[benchの比較](debugging.md)で測り、テストに速度の閾値を書かない。
検定の境界と仮説の値は`crates/minase/src/stats.rs`のコードを正本とする。
探索、評価、および時間管理の変更にもテストは要り、探索の停止条件、置換表の契約、時間予算の式、評価の差分更新と全計算の一致といった契約を検証する。
契約のテストと棋力の測定は混同せず、両方を行う。

決定的に検査できる部分は先に固め、残る部分だけを測定に回す。
合法性、記録の形、損失が有限であること、時間切れが0件であることは、テストとスモークテストで先に固める。
合法性と裁定は条文と保存棋譜で決まるので、測定では判定せず、残る強さだけをSPRTに回す。
ハーネスのスモークテストには、`random`同士の短い対局を使う。
置換表が空のまま測ると誤解を生むので、置換表に依存する指標は対局を再生して置換表を保持した状態で測る。

測定の記録では、Eloや損失といった主指標と、時間切れ、反則、CPU時間、最大常駐メモリといった副次的な指標を分けて記録する。
時間管理のスモークテストや学習の再現確認のように、K回の試行がすべて成功することを基準にする判定では、Kを明示して記録する。
Botの秒読み余裕を3,000 msにした後に、秒読みつきの対局51局で時間切れ0件を確かめた記録がその例である（[Botの記録](../measurements/byoyomi-time-usage/bot-byoyomi-margin-3000.md)）。
評価は、SPRT、bench、詰み探索の問題集のように開発時に手元で行うものを先に、LishogiのBotの実対局での時間切れと反則のように運用の記録によるものを後に行う。
benchの局面集合や詰み探索の問題集のような固定の評価集合は、少数の良質な事例から始めて段階的に増やし、版を管理する。

# テストの手引き

本書は、minaseのテストを書く人間とエージェントに向けて、テストの目的、良いテストの条件、書く範囲、検証の層、および運用の規則を定める。
テストの配置、命名、および個々の契約はコードとそのdocコメントが定めるので、本書はそれらを繰り返さず、判断の規則だけを書く。
本書の方針の多くは、テストの一般的な原則（末尾の参考資料）をminaseの事情に当てはめたものであり、既に[ADR](../adr/README.md)と[教訓](../lessons/README.md)で決まっている事項は、本文から該当する文書へリンクする。

本書は、まず「原則」で目的を、「良いテストの条件」で質を、「書く範囲」で判断基準を示し、その後に層、決定性、運用の各論を置く。
個別の判断に迷ったときは、最初の3節に戻る。

## 原則

テストは次の3つの目的のために書く。
カバレッジの数字はこれらの結果であって、目的ではない。

1. 新しい実装が仕様を満たすことを、実行できる形で示す。設計者が仕様から固定した期待値が、実装の正しさを外から証明する基準になる。
2. 既存の挙動が意図せず壊れたときに気づく。
3. 正しいリファクタリング（挙動を変えない内部の書き換え）では、テストが誤って失敗しない。

### エージェントが実装する開発での重み付け

minaseでは、Claudeが計画と設計を担い、codexなどのサブエージェントが実装を担う（[codexへの実装委任の手引き](codex-delegation.md)）。
エージェントは「動いて見える」時点で手を止めやすいので、設計者が仕様からあらかじめ固定したテストが、実装の正しさを客観的に証明する唯一の拠り所になる。
この証明が成り立つには2つの性質が要る。
テストが仕様を正しく写し取っている性質を妥当性と呼ぶ。
妥当性は、仕様の条件を取りこぼさないことと、弱い検証に頼らないことの2つからなる。
テストが実装から独立していることを客観性と呼ぶ。
実装の出力を写して作ったテストは、通っても何も証明しない。

この2つの性質を守るために、次を徹底する。

- テストは設計者が仕様に基づいて作り、実装から独立した検証の基準として位置づける。実装者が人間でもエージェントでも同じである。
- テストと実装は、仕様から別々に導く。テストを実装から生成せず、実装をテストの例に過剰適合させない。同じエージェントに同じ文脈で両方を書かせると、テストが実装の写しになり、同義反復になる。
- 固定したテストに対してエージェントに実装させるときは、テストの失敗と成功を反復させてよい。失敗を赤、成功を緑と呼ぶ。ただし、エージェントにテストを書き換えさせず、緑になった後に、例示した事例だけを通す実装になっていないかを設計者が確かめる。
- テストの妥当性は、委任の有無にかかわらず継続的に疑う。「通っている」ことは妥当性の証明ではない。仕様に照らしてテスト自体を読み直し、必要なら強める。

この考え方は、[テストの期待値を規範文書から導き、現在の実装から導かない](../adr/derive-test-expectations-from-normative-documents.md)というADRとして既に決まっており、本書の各節はこの決定を前提にする。
委任の具体的な手順は「エージェントへの委任」の節にある。

## 良いテストの条件

量より先に質を定める。
次の5条件を満たさないテストは、何本書いても安心にはつながらない。
各条件は、規則、例、理由、注意の順で書く。
本書の他の節は、条件を(1)から(5)の番号で参照する。

**(1) 守りたい挙動が壊れたら必ず失敗する。**
テストの第一の仕事は、壊れたら気づくことである。
たとえばRULES.md第14条第2項（足のある獅子は隣接しない獅子で取れない）を守るテストは、条文から導いた合法手の集合と、生成した合法手の集合が等しいことを検証する。
合法手生成器が呼ばれたことや、結果が空でないことだけを見るテストは、条件の不等号を取り違えても通るので、何も守っていない。
テストを書いたら「この処理にわざと誤りを入れたら、このテストは落ちるか」と自問する。
落ちないなら、そのテストは弱い。
この自問を手順にしたものが、(5)で述べる変異による検証である。

**(2) 挙動を検証し、実装の呼び出し方を検証しない。**
検証するのは、入力に対する出力、状態の変化、および外部へ送った内容である。
内部でどの関数を何回呼んだかは、原則として見ない。
たとえば重みファイルの保存では、書き出し関数が呼ばれたことを検証するのではなく、ファイルへ書いて読み直し、読み戻した内容が元と等しいことを検証する。
呼び出し方を検証すると、実装を書き換えただけで失敗し、しかも呼んだ事実だけでは結果の正しさを示せない。
実装の形にテストが張り付くほど、リファクタリングの費用が上がる。
ただし、相互作用そのものが仕様である場合は例外である。
エンジンとGUIの通信プロトコルUSIで送受信する行、自己対局ハーネス`minase match run`が書く記録ファイルの内容、および外部エンジンへ送る着手の表記は、相手との契約なので、送った内容を検証してよい。

依存先を差し替えるかどうかの判断は、依存の種類によって分かれる。
自分が完全に制御し、外部から観測されない依存は差し替えず、実物に書いて読み直し、結果の状態で検証する。
minaseでは、自分が所有するファイル形式と測定の実行ディレクトリがこれに当たる。
外部から観測される依存は代替物に差し替えて構わないが、相手へ送った内容は契約なので検証の対象になる。
外部エンジン、GUI、および対局サイトがこれに当たる。
この区別の根拠は付録Dにある。
差し替えが要るときは、呼び出しを記録するだけのモックより、実際に動く軽量な代替実装を優先する。
`Vec<u8>`や`Cursor`による入出力や、合法手から一様に着手する校正用エンジン`random`がその例である。
上位の処理の分岐だけを見るユニットテストでは、書き込み先をメモリ上にしてよい。
ただし、実ファイルでの往復は別のテストで必ず検証する。

**(3) 失敗するのは本物の誤りのときだけである。**
挙動を変えない正しいリファクタリングでテストが失敗するなら、それはテスト側の欠陥である。
こうした失敗を偽陽性と呼ぶ。
たとえば、SFENの解析器の内部の補助関数を改名しただけで落ちるテストは偽陽性を出す。
不正なSFENに対して解析がエラーを返すことを検証するテストは、内部をどう変えても通る。
偽陽性を放置すると「また誤検知か」と扱われ、テストが信用されなくなり、最後は無視または削除されて安全網が失われる。
偽陽性を出すテストは、挙動に基づく形へ書き直す。
通らないからといって検証を消す、または緩めるのは改ざんであり、書き直しではない。
一方、仕様が変わったためにテストを更新するのは偽陽性ではなく、正当な保守である。

**(4) 速く、決定的である。**
同じコードなら毎回同じ結果になるテストを決定的という。
実行のたびに通ったり落ちたりするテストを不安定なテストと呼ぶ。
不安定なテストは「再実行すれば通る」と扱われ、本物の失敗まで覆い隠す。
Googleの報告では、不安定なテストの割合が1%台に達するだけで、スイート全体の信頼と費用に大きく響くとされる。
遅いテストは回されなくなる。
ただし速さは層ごとに相対的に判断する。
プロセスを起動する統合テストがユニットテストより遅いのは当然であり、避けるべきなのは、ユニットテストに固定時間の待機や実ネットワークを混ぜるような不要な遅さと非決定性である。
不安定なテストの原因と予防は、「決定性」の節にまとめる。

**(5) テストの通過やカバレッジの高さを、品質の保証と勘違いしない。**
次のテストはどれも成功するが、何も証明していない。
`#[ignore]`で実行されていないテスト、環境が欠けると早期に`return`して成功扱いになるテスト、`is_some()`程度しか見ない弱い検証、および実装から期待値を逆算したテストである。
最後のものは、実装が`x = a + b`のときに期待値にもそのまま`a + b`と書いてしまうパターンである。
実装の式が誤っていれば期待値も連動して誤るので、誤りを検知できずに通る。
エージェントが生成したテストで特に起こる。
現在の出力を丸ごと保存して比較するテスト（スナップショット）も実装の写しなので書かない。
ただし、保存棋譜や参照値のような外部契約の固定は、実装の写しではないので除く。
カバレッジは「コードを実行したか」を示すだけで「検証したか」を示さない。
検証が1つもなくても行カバレッジ100%は達成でき、80%を満たしていても肝心の箇所を一切検証していないことがあり得る。
測定値を目標にすると、数字を埋めるための質の低いテストが増える（Goodhartの法則）。
minaseはカバレッジに目標値を設けず、数値の低い領域で理由を確かめてテストの欠落を探す、診断用の二次的な指標にとどめる（上記ADRの「検討した代案」）。
何をテストするかはカバレッジではなく「書く範囲」の表で決め、検出力は、実装へ意味を変える変異を一時的に加えてテストが気づくかで確かめる（付録E）。

### テストしにくいコードは設計を疑う

テストが極端に書きにくい（準備する状態が複雑、差し替える依存が多い）ときは、テストではなく設計を疑う。
テストを省いたり弱いテストで妥協したりせず、責務の分離と依存の向きを直してテストしやすい形にする。
判断を含むロジックは、できる限り入力だけから出力が決まる純粋関数へ寄せる。
純粋関数のテストは準備が少なく、リファクタリング耐性も高い。
テストに頼る以前の設計として、不正な状態を型で作れなくすることも重要である（教訓[不正状態を作れる公開型を避ける](../lessons/checked-constructors-for-public-types.md)）。
検証は、内部の補助関数ではなくモジュールの公開関数を通して行う。
内部関数を直接検証している既存のテストは、改修の機会に公開関数を通した検証へ順次移す。

## 書く範囲

目指す水準は「このテストがあれば、手で確かめずにリリースしてよい」状態である。
ただし、何を心配するかは人によって違うので、この水準だけでは判定できない。
実際に書くかどうかは、次の観測できる条件で判定する。
いずれかに当てはまれば書く。

| 条件 | どの層で | 何を検証するか |
|---|---|---|
| 分岐がある（`if`、`match`、エラー経路） | ユニット | 各分岐を通す |
| 外部入力を解析、検証、または変換する。USIの行、局面の文字列表記SFEN、起動引数、ファイル形式、USIオプションの値がこれに該当する | ユニット | 受理する入力と拒否する入力の両方。空、欠落、非ASCII、桁あふれ、未対応の版を含む。規則は[外部入力でパニックしない](../lessons/no-panic-on-external-input.md)と[エラーを文字列へ失わない](../lessons/typed-errors-over-strings.md)にある |
| 規則の条文または規則コード（RULES.md第33条のローカルルールの識別子）に対応する挙動を実装する | ユニット | 条文から導いた期待値。テスト名に条番号を含める |
| 誤ると対局または測定の結果が変わる（終局の裁定、反復の判定、時計の管理、反則の算入、統計の計算） | ユニット。プロセス境界を越える部分は統合 | 正しく裁定、算入、計算されること。統計は外部の参照値と照合する |
| 内部状態を保持して更新する（置換表、時計、局面の履歴、測定の再開） | ユニット。再開はプロセス境界を越えるので統合 | 操作の列に対する状態遷移と派生値。再実行に対する冪等性 |
| ファイルを上書き、削除、または移動する経路（実行ディレクトリ、重み、教師データ） | 判定はユニット。実際の消去と既存パスの拒否は統合 | 消してよい条件で消え、消してはならない条件で拒否されること。この検証は省略できない |
| 自分が所有するファイル形式の読み書きを変える | 統合 | 実ファイルに書いて読み直し、内容が等しいこと |
| 複数の呼び出し元を持つ共有関数を変更した | その関数の層。影響先は呼び出し元の層 | 関数の挙動を網羅する。呼び出し元は、戻り値を次の処理へ渡すだけのものを除き、分岐や計算に使うものに絞って確かめる |
| 別の場所の判定ロジックを複製した | 複製先の層 | 複製先にも同じ事例を置く。複製元のテストは複製先を守らない |
| 外部エンジン、GUI、保存形式、またはライブラリ`minase-core`の公開APIとの境界を変える | ユニットまたは統合 | 送受信する行、記録の形、および公開APIの契約。相手の実物との疎通は記録済みの棋譜または手動で確かめる |
| 不具合を修正した | 不具合が現れた層 | 不具合を再現する最小の事例。修正を外すと失敗することを確かめる（[教訓](../lessons/confirm-regression-test-fails-without-fix.md)） |

共有関数と外部との境界は、変更の波及が大きいので、変更したときに限らず細かい事例を厚く保つ。

ある挙動をどの層で守るかは、書きやすさで決めてよい。
スイート全体でいずれかの層が守っていればよく、同じ挙動を複数の層で重ねて書く必要はない。

守るべき挙動（分岐、変換、仕様上の判断）を持たないものは書かなくてよい。
型と定数の定義、分岐のない初期化、モジュール宣言と`pub use`だけのファイル、出力の整形だけを行う層、および入出力を変換せず委譲するだけの関数がこれに当たる。
`test_util`と`fixtures/`のようなテスト支援の資産そのものも対象外である。
ただし、整形の中に条件分岐があれば整形だけの層ではなく、表の「分岐がある」に当たる。
委譲するだけの薄い関数はユニットテストを省いてよいが、その委譲先との境界は、委譲先の実物を使う層で担保する。
「別の層で担保する」を理由に省くときは、その層にある具体的なテストを特定して確かめ、棚卸しで実在を再確認する。
「書きにくい」は省く理由にならず、「テストしにくいコードは設計を疑う」に従う。
境界値も網羅的には列挙せず、境界で挙動が変わる箇所だけを書く。
型の最大値やオーバーフローを機械的に並べるのは不要であり、書くのは1つずれると実害になる境界である。
ただし、明示された上限と下限（深さの範囲、置換表容量の上限など）は入力の検証なので必須であり、外部入力の桁あふれも表の「外部入力」に従って必須である。
迷ったときは、上の表の条件を優先する。

組合せの網羅は前の層で行い、後の層は代表的な事例に絞る。
たとえば、ローカルルールの組合せごとの裁定は規則の判定のユニットテストで網羅し、プロセスを起動する統合テストと保存棋譜の再生は代表的な規則セットだけで行う。
規則セットの一覧に1行足すだけで統合テストが増えるため、組合せは最も膨らみやすい。
内部で組み立てた中間表現の文字列を部分一致で検証せず、その中間表現を使った結果で検証する。
部分一致は取り違えを検出できず、整形の変更で偽陽性を出すからである。

仕様が未確定な部分があっても、確定した振る舞いのテストを後回しにしない。
未確定なのは多くの場合、表示や出力の形であって振る舞いではない。
テストはエージェントが安く書けるので、費用を先送りの理由にしない。
変わりやすい出力の形式に依存するテストは、暫定の形式に対して書くと変更のたびに偽陽性で失敗するので、形式が決まるまで待ってよい。
待つ場合は、確定後に追加するテストを設計書の残作業に書いて追跡する。
待機には期限を設け、目安として1か月以内に決まる見込みがなければ、暫定の形式に対して書く。
長期間テストがない状態のほうが、多少の書き直しより危険だからである。

## 検証の層

minaseの検証は、次の層からなる。
層1から層4は自動テストであり、番号の小さい層で検証できるものはその層で確かめ、そこで原理的に検証できないものだけを後の層へ回す。
前の層で書けるものを後の層で書くのは費用の無駄であり壊れやすく、後の層でしか検証できないものを前の層で書くと、差し替えた依存が増えて実装の詳細に結合し、本番とのずれを検出できなくなる。
層5と層6は測定であり、合否を決めるテストの代わりではない。
そのため、前の層で検証できないかを検討する順序の対象にも入れない。

1. ユニットテスト。各モジュールの`#[cfg(test)] mod tests`に置き、プロセス内で完結する挙動を検証する。合法手生成、規則の判定、表記の変換、探索の契約、統計の式がここに当たる。
2. 統合テスト。各crateの`tests/`に置き、crateの公開APIを外から使う挙動と、プロセス境界を越える挙動を検証する。エンジンのcrateでは`CARGO_BIN_EXE_minase`で実際のバイナリを起動し、USIの往復、`--io-log`の記録、および対局ハーネスの実行ディレクトリを検証する。バイナリの起動は、CLIのサブコマンドのようにライブラリのAPIをプロセス内で呼んでも検証できない場合に限る。
3. 記録済みの外部オラクル（正解を与える外部の実装や資料）との照合。オンライン対局サイトLishogiの公開棋譜を1手ずつ再生して合法手判定と終局の裁定を突き合わせる統合テスト、Stockfishの測定基盤fishtestが計算した参照値による検定式の照合、および中将棋エンジンHaChuの駒文字表との対応の検証がここに当たる。外部の挙動は保存したテストデータ（fixture）としてだけテストに入れ、テストから実ネットワークへは出ない。棋譜の取得は`scripts/`の別の道具が担う。
4. ランダム対局による不変条件の検査。`minase dev random-play`は、ランダムな合法手で対局を進めて毎手`Position::validate`で局面の不変条件を検査し、失敗した局をシードと局番号で再現できる（[デバッグの手引き](debugging.md)）。条文ごとの事例では網羅できない相互作用を、ここで広く検査する。
5. benchによる速度の測定。`minase dev bench`は決まった局面の集合を探索してノード数と時間を測る診断であり、探索木を変えない変更の確認と速度の比較に使う。
6. SPRTによる棋力の測定。棋力に影響し得る変更の採否は自己対局の逐次検定で判定する（[SPRTによる棋力測定の手引き](sprt.md)）。

層を選ぶときは、段階ごとに次の問いを順に立てる。
ユニットテストでは原理的に検証できないか。
プロセス内でライブラリのAPIを呼ぶ統合テストでは検証できないか。
プロセスを起動しなければ検証できないか。
自動化できないか。
前の問いで検証できるなら、そこで書く。

テストの本数は、層1を厚く、後の層ほど薄くする。
『Software Engineering at Google』第11章は、おおむね小さいテスト80%、中くらいのテスト15%、大きいテスト5%を目安とする。
後の層へテストを足す必要条件は、複数のプロセスまたは境界をまたいで初めて壊れる挙動であること、この1点に限る。
満たさないものは前の層で書く。
満たすものの類型は付録Bにあり、後の層のテストを足すときは、どの類型に当たるかを設計書に書く。
後の層のテストの要否は、実装の後ではなく設計書を書く時点で決める。
後の層の代表事例は、GUIからの対局、lishogiのBotとしての対局、`match run`による測定という実際の利用経路から選ぶ。
後の層のテストでは、検証対象の経路を通して状態を準備しない。
局面はUSIで着手を送って作らず、SFENや`test_util`で直接組み立て、`--io-log`や実行ディレクトリの記録に特定の行や項目が出ること、または出ないことを検証する。

層の選択では、実物が使えるなら実物を使い、使いにくいときだけ代替物に差し替える。
minaseにはデータベースも外部サービスもないので、差し替えの対象はほぼ外部エンジンに限られる。
外部エンジンとの境界は、記録済みの棋譜（層3）と手動の疎通確認で担保する。
保存棋譜は実物から採取したものに限り、相手側（LishogiやHaChu）の版が変わったら、再採取するか手動で確かめる。

自動テストで担保しきれない範囲は手動で確かめる。
minaseでは、GUIおよび対局サイトとの実際の接続と、外部エンジンとの疎通がこれに当たる。
手動の確認は、設計書の完了条件を基準に、手元のGUIとBotの配備環境のそれぞれで、リリースの前と接続の形を変えたときに行う。
リリースの前に手動で確かめる項目は、一覧にしてリリース手順に置く。
手動の確認は層ではなく最終の確認であり、自動化できるものを手動に残さない。

`cargo test`では、フィーチャ`invariants`が常に有効になり、着手のたびに局面を全検査し、探索中の評価のたびに差分更新の値を全計算と照合する（[重い整合検査をフィーチャ`invariants`に置く](../adr/enable-invariant-checks-in-tests-by-feature.md)）。
したがって、テストの中で指した着手と探索も、全検査を受ける。

perftは、ある局面から指定した深さまでの合法手の列を数え上げる手法である。
その数値は合法手生成の正しさの基準にしない（[ADR](../adr/verify-movegen-without-perft-counts.md)）。
合法手生成は、条文ごとの境界局面のテスト、ランダムな局面に対する性質のテスト、および保存棋譜の再生で検証する。
性質のテストは、先後の180度回転対称や着手の適用と取消しの往復のように、どの局面でも成り立つ関係を層1と層4で確かめる。

## 期待値の根拠

テストの期待値は、次の証拠から導く。

1. [RULES.md](../rules/RULES.md)と各領域の規範文書（手引き、プロトコルの調査メモ、コードのdocコメント、ADR）。
2. 外部のプロトコルおよび実装との互換性の契約（fishtestの参照値、Lishogiの棋譜、HaChuの駒文字表）。
3. 確認済みの過去の不具合と境界事例。

現在の実装の出力は、正しさの証拠として使わない。
規則に関わるテストは、`article_14_1_...`のように根拠の条番号を名前に含める。
規範文書から期待値を確定できない挙動は、テストの名前またはコメントで実装の契約であることを明示してから書く。
規範文書の欠落が原因なら、先にその挙動を定めるべき規範文書へ最小限の規範文を追記し、その文言に接地したテストを書く。
仕様の裏付けがない期待値は書かない。
閾値や境界のような数値は、コードを正本として持ち、手引きに写すときはコードの該当箇所を参照する。

## 決定性

不安定なテストは運任せではなく、原因がほぼ決まっている。
次の書き方を避ければ、作らずに済む。

| こう書くと不安定になる | こう書けば防げる |
|---|---|
| 完了を固定時間で待つ（一定時間待機してから検証する） | 条件が満たされるまで待つ。エンジンの応答は`bestmove`などの行を読むまで待ち、スレッドの終了はjoinで待つ。ファイルの出現や状態の反映は、上限つきのポーリングで待つ |
| 準備完了の代理信号を信じる（プロセスの起動や`usiok`の受信を準備完了とみなす） | 実際に使う応答まで待つ。USIでは`isready`に対する`readyok`、XBoard系の通信プロトコルCECPでは[ハンドシェイクの手順](../research/protocols/README.md)の完了まで待つ。代理信号は早すぎる成功を返し得る |
| テスト間で状態を共有する（同じ一時ディレクトリ、グローバル変数、環境変数） | 各テストで用意して片付け、実行順序と並列実行に依存させない。対局ハーネスの統合テストは、プロセスIDと連番から一意な実行ディレクトリを作る |
| 検証の結果が現在時刻に依存する | 時刻に依存しない形で検証する。新しく書く処理では、時刻や経過時間を引数で受け取る形にしてテストから値を与える。時間予算は式に対する数値例で検証し、実測の経過時間に閾値を置かない |
| 乱数をシードなしで使う | 乱数生成器またはシードを引数で渡し、テストでは固定する。minaseの乱数は`XorShift64`で、`--seed`と局番号から決定的に派生する |
| 順序の定まらない集合を順序込みで比較する | 順序を検証するなら整列し、順不同なら集合として比較する |
| 実ネットワークまたは手元にない外部エンジンへ接続する | 外部の挙動は保存した fixture で与える。外部エンジンを要するテストは置かない |
| 並列に走るテストが同じ資源を奪い合う（固定のパス、同じポート） | 書き込む資源にはテストごとに一意な名前を使い、固定の名前は読むだけの fixture に限る。共有が避けられないテストは専用のテストバイナリに集めて直列化し、スイート全体の並列実行は止めない |
| 局面や設定をテストごとに文字列で直書きする | `test_util`の構築関数で組み立てる。形式の変更が1か所で済む |
| 異常終了で一時ディレクトリが残る | 一時領域は失敗時にも残骸が残らない形で作り、残ったものは棚卸しで掃除する |
| 浮動小数点を厳密に比較する | 許容誤差で比較する。ただし、GPUとCPUの一致のように加算順まで定義して一致を要求する契約は、その契約どおり厳密に比較する |
| 競合状態の修正を1回の通過で確認する | 回帰テストを10回以上連続で通す（[教訓](../lessons/repeat-concurrency-regression-tests.md)） |
| 評価値、最善手、読み筋、ノード数を具体的な値で固定する | 契約で検証する。詳細は次の「評価値と探索結果に依存するテスト」にある |

結果が決定的でない機能は、テストではなく測定で評価する。
持ち時間と加算で進める時間制御の対局は着手時間の実測に依存し、`Threads>1`の探索は共有置換表へのアクセス順に依存し、GPUでの学習はカーネルの実行順に依存する。
これらは設計上、完全な再現の対象外である。
したがって時間制御の挙動は、テストで厳密な値を要求せず、固定深さまたは固定ノード数の決定的な条件と、時間予算の式に対する数値例で検証する。
学習は、シードを明示して走らせ、検証損失の記録で評価する。
SPRTの再現性の契約は[棋力測定の手引き](sprt.md)の「ペア対局と再現性」の節にある。

### 評価値と探索結果に依存するテスト

評価値、最善手、読み筋、およびノード数は、重みファイル、探索の係数、枝刈り、置換表の状態、およびスレッド数に依存する。
これらを具体的な値で固定したテストは、重みの再学習や探索の改良という正当な変更で落ちるので、実装が正しいのに失敗する偽陽性（条件(3)）の原因になる。
`Threads>1`では、同じ入力でも結果が変わるので不安定でもある。
こうしたテストが落ちたときに期待値を新しい出力へ置き換えるだけの更新は、テストが実装を追認しているだけの兆候であり、「期待値の根拠」の節に反する。

探索と評価のテストは、次の形で書く。

- 具体的な値ではなく、満たすべき契約を検証する。最善手が合法手に含まれること、読み筋の先頭が最善手と一致すること、同じ入力で同じ結果が返ること、指定した深さやノード数で止まること、停止理由が正しいことがその例である。
- 規則で値が決まるものだけを厳密に比較する。詰みの値、引き分けの値`DRAW_SCORE`、および裁定の結果がこれに当たる。
- 探索の分岐を決めたいときは、重みに頼らず、学習前の重み`crates/minase/nets/nnue-epoch0.bin`に差し替えるか、置換表に値を仕込んで分岐を作る。既存の探索のテストはこの2つの手段を使っている。
- 最善手を期待値として検証したいときは、一方的な捕獲や詰みのように評価関数によらず結論が決まる局面を選び、特定の重みに依存する局面は避ける。
- 実際の重み`eval::weights()`を使うテストは契約の検証にとどめ、具体的な評価値や最善手を期待値として固定しない。
- ノード数と速度は、テストで固定せずbenchで比較する（「棋力と速度はテストで判定しない」）。

重みを更新したときは、実際の重みを使うテストの差分をレビューし、値を写し直すだけの変更があれば、そのテストを契約の検証へ書き直す。

### 時間管理のテスト

「n秒で止まる」という契約を、実際にn秒待って確かめるテストは書かない。
そのテストは遅く、測定機の負荷で揺れ、しかもエンジンの判断ではなくOSの時計を検証している。
時間管理は、方針と機構に分けてテストする。

- 方針とは、残り時間、加算、秒読み、手数、および経過時間から予算を決める計算と、予測した次の反復が予算に収まるかの判断である。これらは純粋関数なので、経過時間を値として与えて瞬時に検証する。既存のテストは、探索の開始時刻を過去へずらして経過時間を作る。
- 機構とは、時計を読んで停止フラグを立て、探索がそれに従う配線である。これは数十ミリ秒の小さな予算で動かし、予算に余裕を足した上限までに止まることだけを検証する。停止した時刻の厳密な値は検証しない。
- 実際の時間制御の下で時間切れを起こさないことは、テストではなく煙試験で確かめる。[打ち切り上限の教訓](../lessons/cap-hard-limit-by-remaining-fraction.md)のとおり、採否の測定と同じ負荷で時間切れ0件を確かめる。

## 運用

書いたテストは資産であると同時に負債でもある。
テストスイート（テストの集合全体）を健全に保つために、次の規則に従う。

**マージの前にローカルの検査を通す。**
minaseには継続的インテグレーションの環境がなく、検査はマージする人またはエージェントが手元で実行する。
masterへマージする前に、次の4つを通す。

```console
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo test -p minase --lib --features search-stats,tuning
```

4つ目は、フィーチャ`search-stats`と`tuning`を有効にしたときだけコンパイルされるテストを実行する。
これらは既定のビルドに含まれないので、`cargo test --workspace`では走らない。

一般には、マージ前の検査は手動の申し合わせではなく仕組みで止めるのが原則である（付録G）。
minaseはCIを持たず、gitのフックによる強制も置いていないので、この規則は手順として守る。
複数のworktreeのブランチを順にmasterへマージするので、マージの後にはマージ後の状態で`cargo test --workspace`を再実行する。
遅い層は速い層と分けて単独に実行できるようにし、`cargo test -p <crate>`や`--test <名前>`で一部だけを回せる形を保つ。
混ぜると、速い層まで遅い層の準備に引きずられ、片方だけを実行できなくなる。
遅いテストを足したときは、検査全体の所要時間を測る。
目標は10分以内である。
超えたら、まず固定の費用の分離と削減を検討し、本数の削減は最後にする（付録K）。
固定の費用とは、テストバイナリのビルドとリンク、プロセスの起動、および対局ハーネスがコミット指定（`commit:`）のエンジンを用意するためのビルドである。
棋力測定に使う計算機（測定機）で測定が走っている間は、[測定中の負荷の教訓](../lessons/check-running-measurements-before-cpu-load.md)に従って`nice -n 19`と`-j`で負荷を抑える。

masterのテストが赤くなったら、原因の変更を直すか戻す。
赤のmasterの修正は、機能の開発より優先する。
30分で直せなければ、原因のコミットを戻してから調べる。
赤にした変更をマージした者（委任ならClaudeなどの委任元）が、戻すか直す責任を持つ。
壊れたまま積み上げると、修正の費用が増え続ける。
赤を放置すると全員が止まり、やがて赤が普通になって安全網として働かなくなる。

**`#[ignore]`は保証ではない。**
GPUを要するテスト、約100秒かかる全列挙、および検定式を変えたときだけ回すモンテカルロ検証は、`#[ignore]`で通常の実行から外している。
除外するテストには、理由の文字列と、実行する条件および標準コマンドを記した手引きの両方を要する。
現在の例は、[NNUEの学習の手引き](nnue-training.md)の`gpu_`テストと、[SPRTの手引き](sprt.md)のモンテカルロ検証である。
直前局面の生成器の全列挙も除外の例であり、直前局面の生成器または合法手生成を変えたときに次のコマンドで実行する。
releaseビルドでの所要時間は、前者が約6分、後者が約9分である。
後者は最大で約6 GBのメモリを使う（[計測記録](../measurements/predecessor-generator-profile.md)）。

```console
cargo test -p minase-core --release predecessor_completeness -- --ignored --test-threads=1
cargo test -p minase-core --release predecessor_oracle -- --ignored --test-threads=1
```

理由も実行手順もない`#[ignore]`は、見かけだけの成功であり、有効化するか削除する。
GPUやファイルがないときに早期に`return`して成功させる書き方は、実質的に飛ばしたテストを成功に見せるので書かず、`#[ignore]`か失敗にする。
除外や`#[ignore]`の対象でも、純粋なロジックを抽出した部分は通常のユニットテストで守る。
除外を解くときは、除外の原因になった方式のまま戻さず、原因を取り除いた形で戻す。

**不安定なテストは再実行で隠さず、直す。**
不安定なテストを見つけたら、「決定性」の表のどの原因かを特定して書き直す。
`cargo test`を再実行したら通った、という形で見つかった場合も不安定なテストとして記録する。
再試行で通すしくみは置かない。
不安定な失敗が出たら、シード、`--io-log`、およびテストの出力を保存してから再実行し、原因の分析に使う。
すぐに直せないときは、理由を書いた`#[ignore]`で通常の実行から外し、担当と期限を決めて直す。
同じテストが3回以上不安定になったら、必ず隔離する。
隔離中のテストには上限の件数を決め、超えたら新規の開発より修正を優先する。
隔離したまま放置した除外は、前項の規則に従い、理由と実行手順を備えて残すか、削除する。

**回帰テストは修正を外して失敗を確かめる。**
修正の後に書いたテストは、修正がなくても通る危険がある。
修正対象の処理を一時的に外してテストが失敗することを確かめ、その後で修正を戻して採用する（[教訓](../lessons/confirm-regression-test-fails-without-fix.md)）。

**新しい領域のテストは、変異で検出力を確かめる。**
領域のテストを書き終えたら、条件の反転、`<`と`<=`の入替、境界定数の変更、必須の副作用の除去、もっともらしい誤った戻り値の返却、検証分岐の省略といった意味を変える変異を実装へ一時的に加え、テストが検出することを確かめる。
生き残った変異は、検証の弱さか未カバーの挙動かを判定して補強し、再び適用する。
意味を変えない変異と判定したときは、その根拠を記録する。
変異を自動生成する道具は補助にとどめ、判定の主体は手で選んだ代表的な変異とする。
既存のスイートの強さを測りたいときは、`cargo-mutants`を変更の差分に限って1回走らせてよい。

**ロジックを変えたのにテストの差分がない変更は疑う。**
レビューで指摘し、最低限の正常系と異常系を足す。

**定期的に棚卸しする。**
棚卸しの狙いは速度ではなく、陳腐化と重複の除去、および欠落の発見である。
削る対象は主観的な重要性ではなく、客観的に不要になったものに限る。
対象の機能が削除されて不要になった陳腐化したテストと、後から追加されたテストと検証内容が重なる重複したテストの2つに限る。
重複のうち、前の層で検証できるのに後の層に残っているものは、費用が高いので優先して外し、利用経路の確認用に代表の1〜2事例は残す。
消す前に、その挙動が別のテストで検証されているかを確かめ、勘で消さない。
「最近落ちていない」は削除の理由にならず、落ちないのは守れている証拠である。
棚卸しでは、次も確かめる。

- `#[ignore]`の一覧と、「別の層で担保する」を理由に省いたテストについて、除外の理由が今も事実か、その層のテストが実在するかを照合する。除外の設定と実態が食い違うと、回帰が見えなくなる。
- テストを持たないモジュールとcrateを列挙する。数えるときは`target/`、`data/`のworktree、およびシンボリックリンク（minase-gui、minase-lishogi-bot）を除外する。
- 見つけた未テストの領域は、誤ったときの影響（対局の結果、測定の結果、学習の結果）で順位を付けて記録し、直さないと決めた領域もその理由とともに記録する。
- 層ごとのテストの本数と所要時間を数え、層2で済む検証が層3以降に回っていないかを確かめる。
- 差し替え用の型や、呼び出しの記録を検証するテストが増えていないかを数える。増えていれば、実装の詳細への結合が進んでいる兆候である。
- 手引きが述べるコマンドと検査が実在し、動くことを確かめる。

**方針を変えたときは、触った箇所から順に直す。**
本書の方針に合わない既存のテストを見つけても、一括では書き直さず、機能の追加と修正で触ったファイルから順に直す。
ただし、実装を写したテストが大半を占めて安全網として働いていない場合は例外であり、2026年8月のspec-first再構築は、この理由で全面的に書き直した（[ADR](../adr/derive-test-expectations-from-normative-documents.md)）。

## エージェントへの委任

「原則」の節の重み付けを、委任の手順に落とすと次のようになる。

1. 委任する前に、期待する挙動を規範文書から固定する。条文、ADR、または契約の内容を指示書に書き、期待値を実装から導かせない。
2. テストと実装は、仕様から別々に導く。設計者がテストの事例と期待値を指示書で与え、実装者はそれを満たす実装を書く。既存の同種のテストがあれば、ひな形として指示書で示す。
3. 固定したテストに対して実装させる場合、赤と緑を反復させてよいが、実装者にテストを書き換えさせない。通らないからと検証を緩める変更は、報告に書かせて設計者が判断する。
4. テストが通った後に、例示した事例だけを通す実装になっていないかを設計者が確かめる。確認の手段は、指示書に書かなかった事例の追加と、「運用」の節の変異による検証である。
5. 委任元は、回収した変更に対して「運用」の節のローカルの検査を自分で実行し、委任先の報告だけで完了と扱わない（[codexへの実装委任の手引き](codex-delegation.md)）。

## 棋力と速度はテストで判定しない

テストが通ることは、エンジンが強いことも速いことも意味しない。
探索、評価、および時間管理の変更が棋力を上げるかどうかは、[SPRTによる棋力測定](sprt.md)の段階ゲートだけが判定する。
速度は[benchの比較](debugging.md)で測り、テストに速度の閾値を書かない。
一方で、これらの変更にもテストは要る。
テストが守るのは、探索の停止条件、置換表の契約、時間予算の式、評価の差分更新と全計算の一致といった、変更が守るべき契約である。
契約のテストと棋力の測定を混同せず、両方を行う。

順序は、決定的に検査できる部分を先に固め、残る部分だけを測定に回す。
合法性、記録の形、損失が有限であること、時間切れが0件であることは決定的に検査できるので、テストと煙試験で先に固める。
合法性と裁定は条文と保存棋譜で決まるので、測定では判定しない。
残る強さだけをSPRTに回す。
測定の記録では、Eloや損失といった主指標と、時間切れ、反則、CPU時間、最大常駐メモリといった副次的な指標を分けて記録する。
時間管理の煙試験や学習の再現確認のように、K回の試行がすべて成功することを基準にする判定では、Kを明示して記録する。
Botの秒読み余裕を3,000 msにした後に予定している、秒読みつきの対局20局で時間切れ0件を確かめる記録がその例である（[秒読みつき時計の活用](../plans/byoyomi-time-usage.md)）。
評価は、SPRT、bench、詰み探索の問題集のように開発時に手元で行うものを先に、lishogiのBotの実対局での時間切れと反則のように運用の記録によるものを後に行う。
benchの局面集合や詰み探索の問題集のような固定の評価集合は、少数の良質な事例から始めて段階的に増やし、版を管理する。

## 付録　参考にする一般原則

本付録では、本文の規則の根拠になった一般原則と出典を整理して示す。
本文と異なり、付録は規則ではなく参考情報であり、本文と食い違う場合は本文が優先する。
原則の多くはウェブサービスの開発で確立したものなので、minaseに当てはめるときの読み替えを各節の末尾に書く。
読み替えのうちminaseの現状を述べる部分は、2026年10月15日時点の確認に基づく。

### A. どの層で書くかの判断順序

層は前から順に検討し、その層で検証できないものだけを後の層へ回す。
前の層で書けるものを後の層で書くのは、費用の無駄であり、かつ壊れやすい。
逆に、後の層でしか検証できないものを前の層で書くと、差し替えた依存が増えて実装の詳細に結合し、本番とのずれを検出できない。
minaseの層の並びと、段階ごとの問いは本文の「検証の層」にある。

### B. 後の層のテストを増やす判断基準

必要条件は1つで、複数のプロセスまたは境界をまたいで初めて壊れるかである。
満たさないなら前の層で書く。
満たすものは、次の4類型に分類される。

| 類型 | 例 | なぜ前の層では守れないか |
|---|---|---|
| プロセス境界をまたぐ状態の受け渡し | GUIからUSIで受けた局面が探索スレッドへ渡り、`bestmove`で戻る経路 | 前の層は両側を差し替えるので、契約のずれを原理的に検出できない |
| 非同期と時間をまたぐ挙動 | 完了の通知、ポーリング、再試行、探索の停止要求 | 前の層は同期的に呼ぶだけなので、タイミングに起因する破綻を再現しない |
| 外部システムとの結合 | 外部エンジン、対局サイト | 差し替えは「自分が思っている相手の仕様」しか検証できない。各1事例で結合を担保する |
| 遷移をまたぐ状態の保持 | 中断した測定の`--resume`による再開、局をまたぐ`usinewgame`、`setoption`の値の保持 | 前の層は単位ごとに作って壊すので、遷移をまたぐ状態が再現しない |

増やすべきでないものは、組合せの網羅、単一の入力の検証、および表示だけの確認である。
組合せの網羅は、一覧に1行足すだけで増えるので最も膨らみやすい。
網羅は前の層で行い、後の層は代表的な1〜2事例に留める。
後の層のテストは、検証対象の経路を通さずに固定したデータで状態を準備し、速く決定的に動くようにする。
そのうえで、複数の構成要素をまたぐ挙動を、記録の有無のような細かい観測点で検証する形に寄せる。
外部の実物を動かす方式は遅く壊れやすく、最後には無効化される。
無効化したテストを戻すときは、同じ方式に戻さず、固定データの方式で作り直す。

minaseでは、層2の統合テスト（USIの往復、探索の停止要求）が第1と第2の類型に、層3の保存棋譜の再生が第3の類型に、測定の再開の統合テストが第4の類型に当たる。

### C. 良いユニットテストの4本柱

Khorikovは、良いユニットテストの条件を退行の検出、リファクタリング耐性、速いフィードバック、および保守性の4本柱で説明し、このうちリファクタリング耐性を最重要とする。
実装の詳細に結合したテストは偽陽性を量産し、テストが変更を邪魔するものに変わる。
偽陽性を減らす唯一の方法は、テストを実装の詳細から切り離し、観測できる振る舞いを検証することである。
何をするかという契約を検証し、どうやるかという内部は検証しない。
本文の「良いテストの条件」は、この4本柱を本書の5条件へ組み替えたものである。

### D. 依存の使い分け

プロセスの外にある依存は2種類に分かれ、扱いが逆になる。

| 種類 | 定義 | 扱い |
|---|---|---|
| managed | 自分が完全に制御し、外部から観測されない。典型はアプリケーション自身のデータベース | 実物を使い、差し替えない。データベースは実装の詳細である |
| unmanaged | 外部から観測される。メール送信、メッセージバス、決済、サードパーティのAPI | 差し替える。送った内容は後方互換性の対象なので検証してよい |

managedな依存を差し替えると、2つの害がある。
保存形式やスキーマのずれを検出できなくなり、関数の形を変えるたびに多数のテストが落ちる。
この区別から、ユースケースの層は統合テストで検証し、ユニットテストはドメインモデルとアルゴリズムに使う、という指針が導かれる。
Fowlerの古典派（classicist）の立場も同じ方向であり、実物が使えるなら使い、使いにくいときだけ代替物を使う。

minaseのコードの大半は、合法手生成、規則の判定、探索、および統計というドメインモデルとアルゴリズムなので、ユニットテストが主力になる。
ユースケースの層に当たるのは、USIの会話の処理と`match run`の対局の進行であり、統合テストで検証する。
managedに当たるのは自分が所有するファイル形式と実行ディレクトリ、unmanagedに当たるのは外部エンジン、GUI、および対局サイトである。

### E. カバレッジの限界と変異テスト

カバレッジは、測定値が目標になった瞬間に価値を失うGoodhartの法則の典型例である。
検証が1つもなくても行カバレッジ100%は達成でき、80%は広く使われる基準だが、80%を満たしても肝心の箇所を一切検証していないことがあり得る。
目標にすると、数値を満たす最も簡単な手段である低品質なテストの量産に流れる。
規則が「書いてあるが強制されない」状態は最も価値が低いので、強制するか、目標から外すかを決める。

代わりの指標が変異テストである。
意図的にコードを壊してテストが気づくかを測り、ある事例ではカバレッジ30%のスイートが変異に対して実質3%しか検出しなかった。
実践では全部に当てず、重要な箇所から、または差分だけに当てることが推奨される。
道具には、JavaScript向けのStryker、Python向けのmutmut、Rust向けのcargo-mutantsがある。
minaseでは、カバレッジを目標から外し、本文の「運用」のとおり、手で選んだ代表的な変異を判定の主体とし、道具は差分に限った測定の補助にとどめる。

### F. 不安定なテストの扱い

不安定なテストの主因は、テスト間の共有状態、素の待機による非同期のタイミング、外部サービスへの依存、時刻と乱数の直接使用、および資源の漏れである。
自動の再試行は問題を隠すので、根本の修正を優先し、再試行は一時的な緩和に限る。
Playwrightの公式の指針は、CIでは2回まで再試行して初回の再試行で実行の記録を取り、根本を分析することであり、手元では再試行しない。
隔離（quarantine）の手順では、同じテストが3回以上不安定になったら別のスイートに隔離し、上限の件数と期限を設けて修正を強制し、放置しない。
CIの再試行は、実行基盤の障害だけを対象にして、テストの失敗と切り分ける。
決定性のために、テストで時刻と乱数を直接呼ばない。

minaseにはCIがなく、再試行の設定を置く場所もない。
ユニットテストも統合テストも再試行せず、不安定なテストは本文の「運用」のとおり隔離して直す。

### G. 緑の維持

Kent Beckの言葉によれば、壊れたビルドの修正より優先度の高い作業はない。
壊れたビルドはチーム全員を止めるので最優先で直す。
短時間で直せないなら、原因のコミットを戻してから調査する（revert first）。
壊れたまま積み上げると修正の費用が指数的に増える。
壊した本人が、影響を最小にする責任を持つ。
マージ前の検査が通らない限りマージせず、手動の申し合わせではなく仕組みで止める。
フィードバックは10分以内を目標にし、速い段階を先に走らせる。
DORAの研究によれば、速度と安定性はトレードオフではなく、小さい単位で頻繁に統合するほどビルドは安定する。
不安定なテストを緑の維持の言い訳にせず、失敗を許容する設定を恒久化しない。

minaseでは、マージ前の検査は本文の「運用」の3コマンドであり、仕組みで止める手段を置いていないので、実行する人またはエージェントが手順として守る。
30分で直せなければ戻し、検査の所要時間が10分を超えたら、まず固定の費用の分離と削減を検討する。

### H. 性能テスト

通常の容量を測る負荷試験、限界点を探る限界試験、急な増加に対する試験、および資源の漏れを探す長時間試験は目的が別であり、実行の頻度も分ける。
サービス水準の目標（SLO）は、文書ではなくコードに閾値を定義し、閾値を超えたら自動で失敗するハードゲートにし、警告の閾値と失敗の閾値を分ける。
煙試験は毎回、負荷試験は夜間のように、軽い試験を頻繁に、重い試験を定期に回す。
煙試験は、接続性と正しさの回帰を小さな負荷で拾う。
空のデータで測ると、インデックスとキャッシュが温まっていないので誤解を生む。
代表的なデータ量を投入してから測る。

minaseでは、速度はbench、棋力はSPRTで測り、どちらもテストに閾値を書かない（本文「棋力と速度はテストで判定しない」）。
検定の境界と仮説の値は`crates/minase/src/stats.rs`のコードを正本とする。
ハーネスの煙試験には、`random`同士の短い対局を使う。
時間管理の変更では、採否の測定と同じ負荷の煙試験で時間切れ0件を確かめてから測定へ進む（[打ち切り上限の教訓](../lessons/cap-hard-limit-by-remaining-fraction.md)）。
置換表が空のまま測ると誤解を生むので、置換表に依存する指標は対局を再生して置換表を保持した状態で測る。

### I. テストデータ

テストデータの組み立てには、固定データ、生成器、および組み立て器の3つの型がある。
固定データ（fixture）は、静的で不変な参照データに向く。
生成器（factory）は、テストが所有する可変データに向き、項目の上書きができる。
組み立て器（builder）は、複雑なオブジェクトグラフに向く。
生成器や組み立て器がないと、リテラルがテストに散在し、形式を変えたときの保守の費用が高くなる。
参照データには決定的な固定の識別子を使い、人が読める形にする。
固定の識別子は並列実行で衝突し得るので、読むだけの参照データに限り、テストが書き込む資源には実行ごとに生成した接頭辞を付ける。
各スイートがデータのライフサイクルを所有し、開始時に作成して終了時に削除する。
異常終了で残った資源は、期限を決めて掃除する。
managedの実物は使い、unmanagedは差し替える。
共有された永続的な保存先を分離しないことが、不安定なテストの最大の要因である。

minaseでは、局面は`test_util`のプログラム的な構築で組み立て、外部のデータは`fixtures/`の固定ファイルで与え、実行ディレクトリはテストごとに一意に作る。

### J. 契約テスト

契約テストは、提供側と利用側の間のインターフェースとスキーマの互換性を守る仕組みである。
最初に、すべての境界を列挙し、それぞれに正となる定義があるかを判定する。
独立して配備され、リポジトリとリリースの周期が別のときは、利用側主導の契約テスト（Pactなど）が最適である。
仕様を先に書いてコードを生成する方式（OpenAPIなど）は、仕様を唯一の正本にして並行保守の問題を消す。
非同期のメッセージはスキーマをリポジトリに置き、両側で検証する。
単一のリポジトリなら、共有の型を両側が取り込むことが軽量な代替であり、ずれがコンパイルエラーになる。
メッセージにはスキーマの版を持たせ、利用側が解析の前に確かめる。
版を黙って捨てず、未対応の版は不明瞭な解析エラーではなく「未対応の版」として明示的に拒否する。
同じ形式を2か所で独立に解釈するなら、同じ固定データで両方をテストする。

minaseの境界は、USI、CECP、ファイル形式、実行ディレクトリの記録、および別リポジトリのminase-guiとminase-lishogi-botである。
ワークスペース内のcrate間の契約は共有の型でコンパイル時に検出され、USIとCECPの契約はプロトコルの調査メモ（[research/protocols/](../research/protocols/README.md)）と保存棋譜で固定される。
ファイル形式は版の欄を持ち、読み手がヘッダから期待する長さを導いて検査する（[ファイル形式の一覧](file-formats.md)）。
minase-guiとminase-lishogi-botは別リポジトリで別の周期でリリースされ、独立配備の条件に当たる。
ただし両者はUSIと規則コードだけを使い、その互換性を壊す変更は[CONTRIBUTING.md](../../CONTRIBUTING.md)の規約で`BREAKING CHANGE`として知らせるので、契約テストの道具は置かず、USIの調査メモを正本とする。

### K. 大規模化に向けたテストの維持

テスト資産が増えても回り続けるための手筋は、大規模開発で確立している。
検査の所要時間は、おおむね可変の費用を並列の区画数で割った値に、区画ごとの固定の費用を足したものになる。
本数を減らしても固定の費用は減らないので、棚卸しは速度にほとんど効かない。
速度は、まず実行時間に基づいて並列の区画を均衡化し、次に固定の準備費用を削り、最後に並列度を増やす、という順で進める。
均衡化は費用がかからない。
並列度を増やしても固定費用が下限になり、効果は逓減し、直列化が必要なテストは並列化できない。

| 技法 | 内容 | minaseでの要否 |
|---|---|---|
| 影響を受けるテストだけ実行する | 依存グラフから、変更が波及するテストだけ走らせる | 将来 |
| 結果のキャッシュ | 入力が変わらないテストは前回の結果を再利用する | 一部。ビルドの成果物は`target/`と`target/match-cache/`に既にある |
| 密閉（hermetic）なテスト | 外部依存がなく再現できる。依存の使い分けと不安定なテストの予防に等しい | 現行。本書の中核 |
| ピラミッドを守る | 前の層を厚く、後の層を薄くする | 現行 |
| マージ前とマージ後の分離 | 速い検査は毎回、遅い検査は定期に回し、壊れたら自動で二分探索する | 将来 |
| 不安定なテストの自動検出 | 再実行の統計で自動判定し、隔離して追跡する | 将来。今は手動 |
| マージキュー | 合流後の状態でテストしてからmasterへ入れ、「単体では緑、合流すると赤」を防ぐ | 将来。今はマージ後の手元での再実行で代える |
| 継続的な整理 | 陳腐化したテストを一括で除く | 現行。本文の棚卸し |
| 壊れて困る挙動にはテストを置く | 「壊れて困るならテストを置くべきだった」という標語で、GoogleでBeyoncéルールと呼ばれる規則 | 現行。本文の「書く範囲」と同義 |

minaseの固定の費用は、テストバイナリのビルドとリンク、プロセスの起動、および`commit:`指定のビルドである。
`--test-threads=1`で直列化するテストは、並列化の下限になる。

## 参考資料

本書の一般的な原則は、次の資料の整理に基づく。
ウェブ資料は2026年10月15日に参照した。

**良いテスト、依存の使い分け、カバレッジ（本文、付録C、D、E）**

- [Vladimir Khorikov, *Unit Testing Principles, Practices, and Patterns* (Manning, 2020)、第4章「The four pillars of a good unit test」](https://livebook.manning.com/book/unit-testing/chapter-4)。良いテストの4本柱と、リファクタリング耐性を最重視する根拠。
- [Vladimir Khorikov, “Don't mock your database, it's an implementation detail”](https://vkhorikov.medium.com/dont-mock-your-database-it-s-an-implementation-detail-8f1b527c78be)。managedな依存を差し替えない根拠。
- [Vladimir Khorikov, “What exactly is an unmanaged dependency?”](https://khorikov.org/posts/2021-11-29-unmanaged-dependencies-explained/)。unmanagedな依存の定義。
- [Enterprise Craftsmanship, “When to Mock”](https://enterprisecraftsmanship.com/posts/when-to-mock/)。差し替えの判断基準。
- [Martin Fowler, “UnitTest”](https://martinfowler.com/bliki/UnitTest.html)。実物が使えるなら実物を使い、使いにくいときだけ代替物に差し替える古典派の立場。
- [Kent C. Dodds, “Write tests. Not too many. Mostly integration.”](https://kentcdodds.com/blog/write-tests)および[“The Testing Trophy and Testing Classifications”](https://kentcdodds.com/blog/the-testing-trophy-and-testing-classifications)。層の比率に関する別の立場。
- [ThinkingLabs, “The Fallacy of the 100% Code Coverage”](https://thinkinglabs.io/articles/2022/03/19/the-fallacy-of-the-100-code-coverage.html)。カバレッジを目標にする弊害。
- [Codecov, “Mutation Testing: How to Ensure Code Coverage Isn't a Vanity Metric”](https://about.codecov.io/blog/mutation-testing-how-to-ensure-code-coverage-isnt-a-vanity-metric/)。変異による検出力の測定。
- [drizz, “Test Coverage Metrics that Actually Tell you Something”](https://www.drizz.dev/post/test-coverage-metrics)。カバレッジの読み方。
- [Stryker Mutator](https://stryker-mutator.io/)および[cargo-mutants](https://github.com/sourcefrog/cargo-mutants)。変異テストの道具。

**不安定なテストと緑の維持（本文、付録F、G）**

- [Martin Fowler, “Eradicating Non-Determinism in Tests”](https://martinfowler.com/articles/nonDeterminism.html)。不安定なテストの主因と、再試行で隠さない原則。
- [Martin Fowler, “Continuous Integration”](https://martinfowler.com/articles/continuousIntegration.html)。壊れたビルドを最優先で直す原則と、Kent Beckの言葉の出所。
- [Google Testing Blog, “Flaky Tests at Google and How We Mitigate Them”](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html)。不安定なテストが全体の信頼を損なう実測。
- [Playwright, “Test Retries”](https://playwright.dev/docs/test-retries)。再試行と記録の取り方。
- [trunkbaseddevelopment.com, “Continuous Integration”](https://trunkbaseddevelopment.com/continuous-integration/)。マージ前の検査で止める運用。
- [GitHub Docs, “About protected branches”](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)。仕組みで止める手段の例。
- [DORA, “DORA Metrics: the Four Keys”](https://www.dora.dev/guides/dora-metrics-four-keys/)。速度と安定性がトレードオフでないことの根拠。

**非決定的な結果の評価（本文「棋力と速度はテストで判定しない」）**

- [Hamel Husain, “Your AI Product Needs Evals”](https://hamel.dev/blog/posts/evals/)。決定的な検査を先に置き、少数の良質な評価集合から始め、開発時の評価を運用の評価より先に行う指針。

**性能、テストデータ、契約、大規模化（付録H、I、J、K）**

- [k6, “Test types”](https://k6.io/docs/test-types/)、[k6, “Thresholds”](https://k6.io/docs/using-k6/thresholds/)および[Grafana, “Automated performance testing”](https://grafana.com/docs/k6/latest/testing-guides/automated-performance-testing/)。性能試験の種類、閾値のハードゲート、および自動化の指針。
- [Pact docs](https://docs.pact.io/)および[Pactflow, “What is contract testing?”](https://pactflow.io/blog/what-is-contract-testing/)。契約テストの定義と適用条件。
- [JSON Schema, “Getting started”](https://json-schema.org/learn/getting-started-step-by-step)。メッセージのスキーマ検証。
- Titus Winters, Tom Manshreck, Hyrum Wright (eds.), *Software Engineering at Google* (O'Reilly, 2020)、第11章「Testing Overview」。テストの規模の比率、壊れて困る挙動には必ずテストを置く規則、および大規模化の技法。

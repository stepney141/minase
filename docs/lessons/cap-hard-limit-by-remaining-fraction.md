# 打ち切り上限は残り時間の割合でも抑える

## 症状

時間管理の候補（[持ち時間の効率的な使用](../plans/time-management-efficiency.md)の最終コミット）は、加算つきのSTC（10秒＋0.1秒）で1,330局中2局を時間切れで落とした。
どちらも候補側で、着手前の残り時間が120〜130 ms、hardが安全上限（残り時間−30 ms）の91〜96 msに拘束された局面であり、エンジン自身の経過時間は91〜97 msでhardどおりに止まっていたが、ハーネスの計測は127〜133 msで、探索の外の遅れが36 msに達していた。
静かな測定機での固定費の確認は最大13 msで通っていた。

## 原因

候補のhardは`5·(remaining / moves_to_go + 0.7·increment)`で、残り時間に比例する項が小さい（`moves_to_go`が100〜225）ため、局面が不安定な手が続くと加算の3.5倍を1手で使い、持ち時間を序盤で使い切る。
その後は残り時間が加算の1〜1.3倍の帯で推移し、毎手hardが安全上限に拘束されて、30 msの余裕が探索の外の遅れ（物理コア数を超える負荷でのスケジューリング）を吸収できなくなった。
現行の式が持っていた`remaining / 4`の項は、残り時間が少ない局面で1手の消費を残り時間の25%に抑え、時計を端まで使い切らせない働きをしていた。

## 以後の規則

打ち切り上限には、残り時間の一定割合（現行は`remaining / 4`）による項を必ず残し、安全上限−30 msだけに頼らない。
時間管理の変更は、静かな測定機での固定費の確認に加えて、採否測定と同じ同時対局数と負荷の下で時間切れが0件であることを煙試験で確かめてから採否測定へ進む。

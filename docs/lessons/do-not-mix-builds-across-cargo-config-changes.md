# ビルド設定を変えた後はコミットのビルドを混ぜて比べない

## 症状

教師生成の高速化で、`.cargo/config.toml`の`rustflags`に`-C llvm-args=-inline-threshold=1000`を加えた。この指定だけでサイクル数が10.3%減る。
変更を世代反復のブランチへ統合した後は、統合後の作業ツリーから統合前のコミットを`minase match run`でビルドすると、指定のないコミットにもインライン閾値が適用される。
探索のコードが同じでネットだけが違う2つのコミットを比べるとき、基準がキャッシュ済みで候補が新しいビルドだと、候補の側だけが約10%速くなる。
世代反復の第1世代の見直しでは、統合前の作業ツリーから対局を実行して、このビルド設定の混入を避けた。

## 原因

次の3つの要因が重なっている。

- `minase match run`は、`commit:`で指定したコミットを、実行した作業ツリーの`target/match-cache/`の下へ展開してビルドする。
- cargoは親ディレクトリの`.cargo/config.toml`も読み、`rustflags`を連結する。cargo 1.98.0で最小限の構成を試すと、内側の設定が`-C target-cpu=native`だけのクレートをビルドしても、rustcには親の指定も渡った。
- キャッシュのキーはコミットのハッシュとfeature名だけで、ビルド設定を含まない。

そのため、同じコミットでも、どの作業ツリーからいつビルドしたかで実行ファイルが変わる。
設定変更前のコミットと変更後のコミットをキャッシュなしで比べると、両方に新しい指定が適用されるので、指定そのものの効果は比較結果に現れない。
`data/worktrees/`の下の作業ツリーはリポジトリのルートの設定も継承するので、masterへ統合した後は、リポジトリの中に変更前の設定でビルドできる場所がなくなる。

## 以後の規則

`.cargo/config.toml`のビルド設定が変わった後は、キャッシュ済みのビルドと新しいビルドを混ぜて比べない。変更前の設定のビルドが要るときは、親ディレクトリの設定が届かないリポジトリの外にworktreeを作ってビルドする。

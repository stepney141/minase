# ヒープの破壊は、検出された場所ではなく書き込んだ場所を監視点で探す

## 症状

ONNX Runtimeで推論するプロセスが、終了処理でglibcの`corrupted double-linked list`を出して異常終了することがあった。
異常終了のスタックで`free`を呼んでいたのがNVIDIAのドライバの`libcuda.so.1`だったので、借りた機械でドライバの版、共有ライブラリの読み込みの順序、およびヒープの検査の方式を変えて異常終了の回数を数えたが、原因を特定できなかった。
ONNX Runtimeの実行時ライブラリの版を上げると回数は減ったが、一部の機械では残った。
作業機では起きないと見なしていたが、過去の測定記録には、作業機の古いコミットで起きた回が残っていた。

## 原因

glibcは、ヒープの管理情報が壊れた時点ではなく、後の`free`か`malloc`がその領域に触れた時点で破壊を検出する。
検出時のスタックは壊した側を示さず、検出されるかどうかはヒープの配置で決まる。
このため、条件を変えて異常終了の回数を比べても、配置の違いを数えているだけで、書き込んだコードには届かなかった。
実際の原因は、解放済みの領域の参照カウントを減らす1命令による書き込みであり、この書き込みは異常終了しない機械でも実行のたびに起きていた。

## 以後の規則

glibcがヒープの破壊を検出して異常終了したら、次の順で調べる。

1. 過去の記録にある構成を含めて、手元の機械で高い割合で再現する構成を探す。古いコミットや、不正な入力を拒んで終わる経路のように、本番と違う構成でもよい。
2. その構成をgdbの下で動かす。gdbはアドレス空間の配置のランダム化を切るので、壊れる番地が毎回同じになるかを確かめる。
3. 同じ番地なら、壊れる8バイトにハードウェア監視点を置き、書き込みのたびにスタックを記録して、glibcの外からの書き込みを探す。
4. 修正は、異常終了の回数ではなく、その書き込みが起きないことで確かめる。

AddressSanitizerの実行時ライブラリを先に読み込ませて異常終了が消えても、原因がないことの根拠にしない。
計装していない共有ライブラリの書き込みは報告されず、割り当て器が替わって検出されなくなるだけだからである。

# 採否測定の条件で改良が発動することを実装前に確認する

## 症状

探索部フェーズ6でaspiration windowsを設計どおり実装しレビューまで行ったが、採否測定にかけられずに見送りとなり、実装とレビューの工数が無駄になった。

## 原因

aspiration windowsは深さ5以上の反復で発動する設計であった。
一方、静止探索後のbenchではdepth=4に局面あたり約30万ノードを要し、第2層の採否測定の対等条件nodes=100000では反復深化が深さ5へ届かない。
発動する水準（局面あたり数百万ノード）での測定は1回が半日以上になり、マイルストーンの予算に見合わなかった。
実装の前に、測定条件でその改良が1度でも発動するかを確かめていなかった。

## 以後の規則

探索改良を実装する前に、採否測定に使う思考制限（ノード数、深さ、時間）の下でその改良が発動するかをbenchの到達深さや発動回数で確認し、発動しないなら測定条件を変えるか改良を先送りする。
先送りした改良のコードは残さず、設計本文と再開条件だけを設計書に保持する。

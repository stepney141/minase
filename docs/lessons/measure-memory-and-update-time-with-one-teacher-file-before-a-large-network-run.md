# パラメータの大きな構造を学ぶ前に、教師1本で保存と再開のメモリと1回の更新の時間を測る

## 症状

2026年11月18日、[tatara化とHalfKP_vmの設計書](../plans/archived/nnue-tatara-framework-and-halfkp-vm.md)で、HalfKP_vmのSimple（第1層の幅256）を教師37本で学び始めたところ、2つの問題が本番の学習の中で初めて表に出た。

1つ目はメモリである。
メモリの上限を18 GiBにしたサービスで動かすと、最初の検証の直後に、cgroupのメモリが上限の18 GiBに達して、メモリ不足（OOM）で止められた。
同じ教師で同じ上限のもとP型のLayerStackを学んだときの最大は12.4 GiBで、その大部分は教師の常駐だった。
教師を1本にして同じ命令を走らせ、cgroupの`memory.stat`の`anon`を0.3秒ごとに読むと、教師の常駐は約0.3 GiBなのに、チェックポイントの保存と書き出しのたびに`anon`が約9.4 GiB増え、最大9.69 GiBになった。
Simpleの重みと最適化器の2つのモーメントは合わせて約2.76 GiBであり、増分はその約3.4倍だった。

2つ目は1回の更新の時間である。
メモリを直して学び直すと、1 superbatch（6,104更新）が55分たっても終わらなかった。
学習を止めて、GPUをほかの処理と分け合わない状態で`nnue bench-step simple --profile`を測ると、1回の更新は逆伝播が453.38 ms、最適化器が145.57 ms、順伝播が4.99 msの計約604 msであり、64 superbatch（390,656更新）を学び終えるのに約2.7日かかる見込みだった。
同じGPU（RTX 3060 Ti）で、P型のLayerStackの1回の更新は約60 msだった。
それより前に、P型の学習とGPUを分け合っていた間の短い学習で1回の更新を約1.3秒と測っていたが、この値はGPUの共用で膨らんでいたので、見積もりには使えなかった。

## 原因

チェックポイントの保存は、GPUから取り出した配列を、バイト列への変換、NPYの符号化、伸長するZIPのバッファの順に複製してから書いていた。
読み込みもファイル全体を1つのバッファに読んでから、配列ごとに複製していた。
最適化器は約2.5億個の要素ごとに倍精度で計算しており、[GPUカーネルの内側のループで倍精度を使わない](no-f64-in-gpu-kernel-inner-loops.md)の規則から外れていた。
逆伝播は、964,224行の第1層の全ての行に計算のブロックを割り当て、同じwarpのレーンが別々の局面の行を読んでいた。
P型のLayerStackの配列は小さいので、どちらの費用も教師の常駐や他の計算に比べて目立たず、チェックポイントの大きさで比べてパラメータが約140倍に増えたHalfKP_vmで、初めて上限と所要時間を大きく超えた。
学習器の実装の段階では、GPUのメモリの使用量は標準のバッチで測っていたが、ホストのメモリと1回の更新の時間は本番と同じ大きさで測っていなかった。

cgroupの`MemoryCurrent`と`MemoryPeak`には、書き出したファイルのページキャッシュも数えられる。
3.0 GBのチェックポイントを書いた直後は、プロセスの確保したメモリが減ってもキャッシュの分だけ値が残るので、これらの値だけでは複製の大きさを読み分けられなかった。

## 以後の規則

パラメータの大きな構造や入力特徴集合を学習器に足したら、本番の教師で学ぶ前に、本番と同じ幅とバッチで次の2つを測る。

第1に、教師1本、少ない更新数、および検証と保存を毎superbatchにした学習と、その再開を走らせ、保存、再開、書き出しの間の`anon`の最大を測る。
教師の常駐は教師の本数に比例し、保存と再開の増分はパラメータの大きさで決まるので、2つを足して本番の上限に収まるかを見積もる。
cgroupの値は`memory.stat`の`anon`と`file`を分けて読み、`MemoryCurrent`と`MemoryPeak`だけで判断しない。
大きな配列の保存と読み込みは、借用した配列からファイルへ直接書き、ファイルから配列へ直接読む形にし、中間のバイト列を作らない。

第2に、GPUをほかの処理と分け合わない状態で、`nnue bench-step <構造> --profile`で1回の更新の区間ごとの時間を測り、本番の更新回数を掛けて所要時間を見積もる。
最適化器の時間は、要素ごとの読み書きのバイト数をGPUの帯域で割った下限と比べ、大きく離れていれば要素ごとの計算の精度と並べ方を疑う。

修正の後は同じ条件で測り直して記録する。
このときは、保存で3.20 GiB、再開で4.01 GiBになり、1回の更新は逆伝播が24.33 ms、最適化器が16.84 ms、順伝播が4.97 msになった。

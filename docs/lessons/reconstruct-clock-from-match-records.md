# 時間管理を変える前に保存記録から時計を再構成する

## 症状

上位計画は時間管理の欠陥を「残り時間が加算の約3倍を下回るとhard limitがsoft limitより短くなる」と診断し、発生域を旧時間制御の913msと記していた。
外部レビューはこの数値の不整合を指摘したが、欠陥の規模は「時間切れは出ていないので緊急ではない」と見積もった。
段階1のSTCとLTCの保存記録から各手の時計を再構成すると、診断した領域に入る局は3%以下だった一方、100手目以降は7〜9割の手がhard limitで打ち切られ、1局の3分の2が深さ4〜6の拘束状態で指されていた。

## 原因

予算式の境界条件だけを机上で解析し、実際の対局で時計がどの残り時間に落ち着き、各手がどの停止理由で終わっているかを数えていなかった。
時間切れが0件であることは、持ち時間が最善手に反映される計算へ使われていることを意味しない。

## 以後の規則

時間管理を変更する前に、保存済みの実行ディレクトリの手ごとの思考時間から両側の時計を再構成し（`scripts/clock_profile.py`）、手数帯ごとの到達深さ、残り時間、および停止理由の分布を数えてから設計する。

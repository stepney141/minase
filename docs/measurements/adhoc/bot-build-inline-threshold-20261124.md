# lishogiのBotのビルドにLLVMのインライン閾値を渡したときの探索速度

## 目的

lishogiのBotを動かす別リポジトリ`minase-lishogi-bot`のDockerイメージは、環境変数`RUSTFLAGS`を`-C target-cpu=native`だけにしてminaseをビルドしていた。
本測定は、このフラグによるビルドとminase本体のリポジトリの設定どおりのビルドの速さを比べ、Botのビルドに[LLVMのインライン閾値の設計判断の記録（ADR）](../../adr/raise-the-llvm-inline-threshold-to-1000.md)の設定が入っていないことによる損失を確かめる。
比較は2つ行った。1つ目は、minase本体のmasterを2通りのフラグでビルドしたバイナリどうしの比較（以下、ビルドの比較）であり、2つ目は、Botのイメージを修正の前と後でビルドし、それぞれから取り出したバイナリどうしの比較（以下、Botのイメージの比較）である。
あわせて、本体のリポジトリの設定でビルドしたバイナリを高効率コアで動かしたときの速さを記録する。

## コマンドライン

負荷は、固定の15局面を深さ16で探索するコマンド`bench`である。`bench`は、将棋エンジンの通信プロトコルUSIでエンジンへ送るminase独自のコマンドである。次の5行をファイル`bench16.usi`に書き、標準入力から与えた。`<ネット>`は評価関数NNUEの重みのファイルであり、規則セット`JCSA`は日本中将棋連盟の規則である。

```console
setoption name RuleSet value JCSA
setoption name EvalFile value <ネット>
isready
bench depth 16 threads 1 repetitions 1
quit
```

ビルドの比較では、2つのバイナリを交互に5回ずつ、性能コアの論理CPU 3に固定して実行し、性能コアのサイクル数と命令数のイベント（`cpu_core/cycles/u`と`cpu_core/instructions/u`）を数えた。

```console
taskset -c 3 perf stat -x, -e cpu_core/cycles/u,cpu_core/instructions/u <バイナリ> --protocol usi < bench16.usi
```

高効率コアの値は、リポジトリの設定のバイナリを論理CPU 15に固定し、高効率コアのサイクル数のイベント`cpu_atom/cycles/u`を数えて1回だけ測った。

Botのイメージの比較では、稼働中のコンテナから取り出したバイナリ（修正前）と、修正したDockerfileで`docker compose build`したイメージから取り出したバイナリ（修正後）を、論理CPU 3に固定して交互に3回ずつ実行し、サイクル数だけを数えた。

## エンジン

ビルドの比較では、minaseのmasterのコミット`f9b56d03`を次の2通りでビルドした。

| 名前 | ビルド |
|---|---|
| リポジトリの設定 | `cargo build --release --locked -p minase --bin minase`（`.cargo/config.toml`の`-C target-cpu=native -C llvm-args=-inline-threshold=1000`が入る） |
| Botと同じフラグ | `RUSTFLAGS="-C target-cpu=native" cargo build --release --locked -p minase --bin minase` |

環境変数`RUSTFLAGS`は`.cargo/config.toml`の`rustflags`を置き換えるので、後者にはインライン閾値が入らない。
Botのイメージは、Rust 1.98で`cargo install minase --version =3.0.0`を実行してminaseをビルドする。
crates.ioのパッケージには`.cargo/config.toml`が含まれないので、Botのビルドには`RUSTFLAGS`の値だけが入る。
修正前のイメージは`RUSTFLAGS="-C target-cpu=native"`、修正後のイメージは`RUSTFLAGS="-C target-cpu=native -C llvm-args=-inline-threshold=1000"`であり、修正は`minase-lishogi-bot`のコミット`710f0d75`である。
取り出したバイナリのSHA-256の先頭16文字は、修正前が`c8aa5b7eba02ebaf`、修正後が`0d03b883b8b79a86`である。
Botのイメージのバイナリは、ビルドの比較のバイナリとminaseの版もコンパイラの版も違うので、2つの比較の値どうしは比べない。

どの比較でも、ネットは第3世代のネットのファイル（SHA-256は`cbbccf6f5ee7097fd890086d2cf4bca72ed969da28353cb0c4a2f4d781acc244`）を使った。このファイルは、ネットの構造を表す文字列の中の入力特徴集合の名前を`P`から`A`へ改める前のものであり、改めた後のファイルとは名前だけが違う。

## 環境

測定機はIntel Core Ultra 7 265KF（性能コア8、高効率コア12、スレッドは計20、メモリ30 GiB）で、Linux `6.18.63-3-lts`、リポジトリのビルドはRust `1.100.0`、perf `7.3.6`である。
探索スレッドは1、置換表は`bench`の既定の容量である。
測定は2026年11月24日に行った。
測定中は、lishogiのBotのエンジン2つが探索を続けており、合わせて約8スレッドの負荷があった。
同じ機械で行うことのある自己対局の測定、探索の係数の自動調整（SPSA）、および教師の生成は動いていなかった。

## 結果

ビルドの比較で5回測った値の最小と最大は次のとおりである。
探索ノード数は両方とも2,094,622で、15局面の局面別のノード数、最善手、および評価値は一致した。

| ビルド | 毎秒ノード数 | サイクル数 | 命令数 |
|---|---:|---:|---:|
| リポジトリの設定 | 824,742〜826,092 | 14,597,767,035〜14,642,898,102 | 44,663,025,936〜44,663,031,571 |
| Botと同じフラグ | 787,298〜789,382 | 15,396,608,556〜15,472,334,933 | 47,603,237,243〜47,603,238,011 |

Botと同じフラグのビルドは、リポジトリの設定のビルドより毎秒ノード数が約4.5%低く、命令数が約6.6%多かった。

リポジトリの設定のバイナリを高効率コアの論理CPU 15で動かすと、毎秒ノード数は616,751、`cpu_atom`のサイクル数は17,378,878,313であり、毎秒ノード数は性能コアの約75%だった。

Botのイメージの比較で3回測った値の最小と最大は次のとおりである。
15局面の局面別のノード数、最善手、および評価値は一致した。

| バイナリ | 毎秒ノード数 | サイクル数 |
|---|---:|---:|
| 修正前 | 846,437〜862,317 | 14,663,913,636〜14,782,279,386 |
| 修正後 | 892,667〜901,909 | 13,766,986,753〜13,962,587,751 |

修正後のバイナリは、毎秒ノード数が約5%高かった。

## 結論

Botのビルドはインライン閾値が入らないために約5%遅く、`RUSTFLAGS`に閾値を加えた修正で、探索の結果を変えずにその分を取り戻せた。
また、同じバイナリでも、高効率コアで動かすと毎秒ノード数は性能コアの約75%に下がった。

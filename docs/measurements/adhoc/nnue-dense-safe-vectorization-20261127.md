# NNUEの後段の計算を`unsafe`なしで自動ベクトル化させる試作の速さ

## 目的

本測定は、A型のNNUE（着手ごとに差分で更新できる小さなニューラルネットの評価関数）の後段の計算`LayerStackNetwork::dense`が探索時間に占める割合と、その機械語の形を調べ、`unsafe`を使わずにLLVMの自動ベクトル化が効く形へ書き直した試作を、現行の版と、探索の結果の一致とサイクル数で比べる。
比較の上限の目安として、`unsafe`の組み込み関数でAVX-VNNI命令（8ビット整数の積を32ビットの和へ足す命令）を使う版も、コミット`f9b56d03`でだけ測った。
この版は、エンジンとライブラリで`unsafe`を禁じる方針（[ADR](../../adr/allow-unsafe-only-in-the-trainer-gpu-code.md)）に反するので、採用の候補ではない。

## コマンドライン

`bench`の負荷は、固定の15局面を深さ16で探索するUSIの独自コマンドであり、次の5行を標準入力から与えて、性能コアの論理CPU 3に固定して実行した。

```console
setoption name RuleSet value JCSA
setoption name EvalFile value <ネット>
isready
bench depth 16 threads 1 repetitions 1
quit
```

教師生成の負荷は、自己対局の各局面を2万ノードで探索する2局であり、変更のない基準のworktreeを作業ディレクトリにして、同じ論理CPU 3で実行した。

```console
taskset -c 3 <バイナリ> data selfplay generate --eval-file <ネット> --output-dir <空の出力先> --chunk-games 2 --games 2 \
  --seed 9010200000 --nodes 20000 --random-moves 0 --concurrency 1 --hash-mb 16
```

関数別の内訳は、フレームポインタを残したビルド（`CARGO_PROFILE_RELEASE_DEBUG=1`、`RUSTFLAGS`にリポジトリの2つのフラグと`-C force-frame-pointers=yes`）で`perf record --call-graph fp -e 'cpu_core/cycles,period=500009/u'`を採取し、[教師生成の高速化の付属資料](../teacher-generation-speedup/teacher-generation-speedup-engine/)の`inline_prof.py`で集計した。
`dense`の機械語は、同じビルドを`objdump -d -M intel`で逆アセンブルし、命令名ごとの出現数を数えた。

マイクロベンチマークは、[付属のcrate](nnue-dense-safe-vectorization-20261127/microbench.rs)（`Cargo.toml`は[付属のファイル](nnue-dense-safe-vectorization-20261127/microbench-Cargo.toml)、ビルドフラグはリポジトリと同じ`-C target-cpu=native -C llvm-args=-inline-threshold=1000`）で、`dense`の各変種を同じ入力に対して呼び、1回あたりの時間を測った。
入力は乱数の累算値10万件であり、全変種の出力が現行の書き方と一致することを確かめてから時間を測った。
このcrateより前に、`bench`の深さ16の探索中に`dense`へ渡された累算値を16回に1回ずつ書き出した102,826件を入力に使う版でも測ったが、その版のソースは保存していない。

現行のmasterでの比較は、基準と試作を1回ずつ実行した組を、組ごとに実行の順序を入れ替えながら、`bench`で20組、教師生成で10組繰り返し、サイクル数、命令数、および分岐予測ミスを`perf stat -x, -e cpu_core/cycles/u,cpu_core/instructions/u,cpu_core/branch-misses/u`で数えた。
実行に使ったスクリプトは[付属のファイル](nnue-dense-safe-vectorization-20261127/paired-run.sh)、組ごとの値は[付属の結果](nnue-dense-safe-vectorization-20261127/paired-results.txt)にある。
各組から、試作のサイクル数を基準のサイクル数で割った値の自然対数（対数比）を求め、その平均とt分布による両側95%信頼区間を計算し、速度比は対数比の平均の符号を変えて指数を取った値とした。

## エンジン

内訳、機械語、マイクロベンチマーク、および`unsafe`の版は、minaseのmasterのコミット`f9b56d03`で測った。
ネットは第3世代のネットのファイル（SHA-256は`cbbccf6f5ee7097fd890086d2cf4bca72ed969da28353cb0c4a2f4d781acc244`）である。

現行のmasterでの比較は、コミット`f2eb2fbf`を基準とし、試作はその上に[安全な書き直しの差分](nnue-dense-safe-vectorization-20261127/safe-dense.patch)を当てたものである。
`f2eb2fbf`は、`f9b56d03`の後に第3世代のネットに合わせて探索の係数を調整し直し、入力特徴集合の名前をP型からA型へ改めた版であり、`dense`の計算は`f9b56d03`と同じである。
ネットは、同じ第3世代のネットについて、ネットの構造を表す文字列の中の入力特徴集合の名前を`P`から`A`へ改めたファイル（SHA-256は`415020879b9086772acb168397dfa406a1432350c151f87b635b3f271153d1a9`）である。
ビルドはリポジトリのrelease設定（`target-cpu=native`、インライン閾値1000、LTO有効、`codegen-units=1`）で、バイナリのSHA-256は基準が`e6b4e704ef50ff54…`、試作が`957b8f91873b9953…`である。

`dense`は、両視点の累算値から要素積256個を作り、全結合層L1とL2、および出力層を順に計算する。現行の版は、L1とL2の8ビットの重みを、出力ごとに入力を並べた行優先の配列で持つ。
安全な書き直しは、次の3点を変える。

1. 要素積は、各視点の累算値を`split_at`で前半と後半に分けて`zip`で対にし、0から127へ切り詰めた2つの値の積を16ビット整数のまま求めて7ビット右シフトする。積の上限は127×127＝16,129なので16ビットに収まる。
2. L1（入力256、出力16）は、読み込みのときに8ビットの重みを16ビットへ広げた行優先の複製を持ち、16ビットの入力との積を32ビットで足す。
3. L2（入力30、出力32）は、読み込みのときに重みを入力ごとに出力を並べた配列（30×32）へ組み替え、入力2つ分の積の和を16ビットのまま求めてから32ビットの和へ加える。入力は0から127、重みは−128から127なので、2つの積の和の絶対値は2×127×128＝32,512以下であり、16ビットに収まる。

`unsafe`の版は[参考の差分](nnue-dense-safe-vectorization-20261127/unsafe-avxvnni-reference.patch)であり、第1層の幅が256の場合に限って、要素積をAVX2で計算し、L1とL2を、入力4バイトを全レーンへ複製して`vpdpbusd`で計算する。

## 環境

測定機はIntel Core Ultra 7 265KF（性能コア8、高効率コア12、スレッドは計20、メモリ30 GiB）で、Linux `6.18.63-3-lts`、Rust `1.100.0`、perf `7.3.6`である。
探索ワーカーは1、`bench`の置換表は既定の容量、教師生成の置換表は16 MiBである。
`f9b56d03`での測定は2026年11月24日と25日に、現行のmasterでの比較は2026年11月27日の0時3分から0時13分に行った。
どの測定の間も、lishogiのBotのエンジン2つが探索を続けており、合わせて約8スレッドの負荷があった。
現行のmasterでの比較の間は、同じ機械で別のエージェントが逆アセンブルとビルドを行っていた。
対局の測定、SPSA、および教師生成は動いていなかった。

## 結果

### `f9b56d03`での内訳と機械語

`bench`の深さ16の標本のうち、静的評価`evaluate_at`とその呼び出し先は20.9%、後段の計算`dense`は17.7%だった。
`dense`の中では、L1の積和`affine`が9.3%、L2の計算（`dense::{closure#0}`）が3.6%、要素積`pair`が2.3%だった。
`dense`の外では、累算値の差分更新`ensure_accumulator`が3.2%だった。
上位の関数の全体は[付属の集計](nnue-dense-safe-vectorization-20261127/profile-bench16-f9b56d03.txt)にある。

`dense`の機械語は、要素積をスカラー命令で1成分ずつ計算していた。
L1は、8ビットの重みと入力を`vpmovsxbd`と`vpmovzxbd`で32ビットへ広げてから`vpdpwssd`で積を足しており、1命令で8個の積しか扱っていなかった。16出力のそれぞれで、最後に水平加算をしていた。
命令名ごとの出現数は[付属の集計](nnue-dense-safe-vectorization-20261127/dense-opcode-counts-f9b56d03.txt)にある。

### マイクロベンチマーク

探索中の累算値102,826件を入力にした版では、要素積の値の69.9%が0だった。ただし、0の入力を4つずつまとめて飛ばす方式で飛ばせる、連続する4バイトがすべて0の組は23.5%だった。
1回あたりの時間は次のとおりである。
ソースを保存していない版の値なので、変種の書き方は名前だけを記す。範囲は、同じ版を2回から4回実行して得た値の最小と最大であり、1つの値は、実行どうしの差が1 ns未満だった変種の値である。

| 変種 | 1回あたりの時間 |
|---|---:|
| 現行 | 336〜398 ns |
| 安全な書き方：8ビットのまま、L1の重みを入力4つずつ転置 | 317〜331 ns |
| 同上で、4バイトがすべて0の入力の組を飛ばす | 280〜296 ns |
| 安全な書き方：8ビットのまま、L1を16レーンの部分和に分ける | 286 ns |
| `unsafe`：AVX2とAVX-VNNI（`vpdpbusd`） | 75〜87 ns |
| `unsafe`：同上で、0の入力の組を飛ばす | 81〜91 ns |

付属のcrateの値は次のとおりである。
「入力ごと」は、出力ごとに入力を並べる行優先ではなく、入力ごとに出力を並べた配置をいう。

| 変種 | 1回あたりの時間 |
|---|---:|
| 現行 | 376〜386 ns |
| 要素積とL1を16ビット、L1は行優先、L2は行優先 | 380〜382 ns |
| 要素積とL1を16ビット、L1は入力2つずつ転置、L2は行優先 | 457〜460 ns |
| 要素積とL1を16ビット、L1は行優先、L2は入力ごと（安全な書き直し） | 199 ns |
| 要素積とL1を16ビット、L1とL2の両方を入力ごと | 531 ns |

安全な書き直しは、L1を行優先のまま16ビットへ広げ、L2を入力ごとの並びにした組み合わせでだけ速くなった。

### `f9b56d03`でのエンジンの試作

`bench`の深さ16を、基準と試作で交互に5回ずつ実行した範囲は次のとおりである。
どの版も探索ノード数は2,094,622で、15局面の局面別のノード数、最善手、および評価値は基準と一致した。

| 版 | 毎秒ノード数 | サイクル数 | 命令数 |
|---|---:|---:|---:|
| 基準 | 825,860〜828,961 | 14,570,249,153〜14,627,970,173 | 44,663,025,675〜44,663,031,880 |
| 安全な書き直し | 917,962〜923,100 | 13,173,468,210〜13,255,893,674 | 38,599,372,788〜38,599,373,240 |
| `unsafe`のAVX-VNNI（参考） | 975,082〜980,063 | 12,462,673,932〜12,522,879,644 | 33,831,867,432〜33,831,873,014 |

安全な書き直しの試作で、L1を16レーンの部分和に分けて書いた変種は、3回の毎秒ノード数が829,050〜835,521、サイクル数が14,379,593,575〜14,507,017,253であり、ほとんど速くならなかった。

`perf report`で`dense`のシンボルに付いた標本の割合は、安全な書き直しで全標本の17.7%から9.3%へ下がった。
機械語では、要素積が`vpmullw`、L1が`vpmaddwd`へベクトル化されたが、L1の`vpmaddwd`は128ビット幅であり、16出力それぞれの水平加算は残った。
`eval::nnue`の単体テストは37件すべて通った。

### 現行のmasterでの対比較

| 負荷 | 組数 | 速度比 | 速度比の両側95%信頼区間 | 組ごとの対数比の標準偏差 |
|---|---:|---:|---:|---:|
| `bench`深さ16 | 20 | 1.104 | 1.099〜1.110 | 0.0103 |
| 教師生成2局 | 10 | 1.156 | 1.065〜1.256 | 0.1154 |

`bench`の探索ノード数は基準と試作のどちらも3,371,474で、20組すべてで15局面の局面別のノード数、最善手、および評価値が一致した。
教師生成は、基準と試作の10回ずつ、計20回のすべてで、探索ノード数の合計が16,400,000、教師のファイルのSHA-256が`63f6f5b011560e83…`で一致した。

サイクル数の範囲は、`bench`で基準が22,361,797,329〜24,098,289,784、試作が20,228,564,601〜22,041,885,822、教師生成で基準が102,743,071,444〜143,809,797,863、試作が92,443,440,468〜105,348,937,432だった。
教師生成の基準の最大値は、他の基準の実行の最大値より約30%大きく、同じ機械で動いていた別の処理の影響と考えられる。この組を含めたので、教師生成の区間は広い。
試作の中央値を基準の中央値で割った比は、教師生成のサイクル数で0.895（速度比で約1.118）だった。
命令数の同じ比は、`bench`で0.870、教師生成で0.879であり、分岐予測ミスはどちらも約1.8%減った。

## 結論

`dense`を`unsafe`なしで自動ベクトル化が効く形に書き直すと、探索の結果を変えずに、現行のmasterでサイクル数を`bench`の深さ16で約9.4%（速度比1.104、95%信頼区間1.099〜1.110）減らせ、教師生成でも速度比の区間の下端が1.065だった。

# 第3世代のネットに合わせた探索係数の再調整のSPSA

## 目的

v3.0.0で探索の測定の標準のネットが第3世代のネットへ替わったので、探索と時間管理の103係数をこのネットに合わせてSPSAで30,000ペア調整し、採否の測定にかける候補の値を得る。
どの設計書も計画していない調整なので、記録を`adhoc/`に置く。
SPSAの対局結果は強さの根拠にしない。
最終値は、この予算と設定で得た候補の値であり、最適値とは呼ばない。

## コマンドライン

vast.aiで借りた計算機（以下、調整機）で、`scripts/vast/spsa/remote.py`が[時間切れの事前確認](nnue-gen3-search-retune-safety.md)を通した後に次を実行した。

```console
minase spsa --run-dir /workspace/job/nnue-gen3-search-retune --seed 7100000000 \
  --engine commit:f9b56d03904716b22b3e1f88734a76ea5167c590 --params /workspace/job/params \
  --rules lishogi --each time=8700+87 --concurrency 95 \
  --iterations 3750 --pairs-per-iteration 8 \
  --option EvalFile=/workspace/job/network.bin
```

パラメーターファイルは`data/vast-spsa/nnue-gen3-search-retune/params`（103行）である。
`minase spsa params`が調整用ビルドから生成した104行から、NNUEの探索では使われない`FmScale`（FMの補正の倍率）の行を除いたものである。
範囲、`c_end`、および`r_end`は、[前回の全係数のセッション](../time-instability-scaling/time-instability-scaling.md)のファイルとすべて一致し、開始値だけがそのセッションの後の係数の表の既定値である。
`r_end`はすべて0.002であり、利得の指数はα = 0.602とγ = 0.101、学習率の安定化の定数はA = 375である。
持ち時間`time=8700+87`（基本時間8,700ミリ秒、1手ごとの加算87ミリ秒）は、STCの`time=10000+100`に換算係数`f` = 0.87を掛けた値である。換算係数の求め方は[事前確認の記録](nnue-gen3-search-retune-safety.md)にある。
実行ディレクトリの内容は、`scripts/vast/spsa/fetch.py`が10分ごとに手元の測定機の`data/vast-spsa/nnue-gen3-search-retune/`へ取得した。全反復がそろった時点で`fetch.py`が記録を検査し、終了後に`data/spsa/nnue-gen3-search-retune`へ移した。

## エンジン

調整対象は`f9b56d03904716b22b3e1f88734a76ea5167c590`の調整用ビルドであり、調整機でビルドした実行ファイルのSHA-256は`8f758ac2fa48953c343f2c570230bcd16089606745d79075c1ba61be3c96bbe1`である。
runnerは、調整機で同じコミットをビルドした通常のminase（版3.0.0）であり、そのSHA-256は`64d6b625c7f3791bbbf39a8340444d32f2222f92ff6a4d7cbdfe4f518bf23226`である。
`invocations.json`の起動の記録は1件であり、セッションは中断なく1回の起動で終えた。
ネットは、当時の標準だった第3世代のネット（SHA-256は`cbbccf6f5ee7097fd890086d2cf4bca72ed969da28353cb0c4a2f4d781acc244`）である。
セッションの後に入力特徴集合の名前が`P`から`A`へ改められ、同じ重みのネットは名前だけを書き換えたファイル（SHA-256は`415020879b9086772acb168397dfa406a1432350c151f87b635b3f271153d1a9`）になった。改名の判断は[改名のADR](../../adr/rename-the-p-type-input-features-to-a.md)にある。
規則セットは`lishogi`（`L1,L2,P0,P3,R1,E1,E3`）である。このネットの教師の生成と学習に使った規則であり、lishogiのBotが対局する規則でもあるので、2026年11月24日に利用者が選んだ。過去のセッションは、日本中将棋連盟の規則に準拠する`JCSA`（旧名`engine-default`）で行っている。

runnerが記録したCPUの数は、物理96コア、論理184スレッドである。
`Threads`は1、`USI_Hash`は既定の256 MB、同時対局数は95である。
開始時に見込んだ所要時間は11.05時間だった。
インスタンスは2026年11月24日23時18分（日本時間）に作成し、本番は23時40分ごろに始まり、2026年11月25日9時21分ごろに終わった。
`fetch.py`は9時27分にインスタンスを削除した。
vast.aiの残高の減少から求めた費用は、事前確認と本番を合わせて約13.82米ドルである。

### クラッシュ

反復2（適用6、ペア番号14）と反復2732（適用2730、ペア番号21852）で、θを負の向きへ摂動した設定θ−の側のエンジンが1局ずつ異常終了した。
どちらも、エンジンの標準エラーには`thread '<unknown>' has overflowed its stack`と`fatal runtime error: stack overflow, aborting`が出ていた。
どちらの局も長く（開局を含めて474手と1,191手）、異常終了したのは優勢な側が自分の手番で探索している最中だった。

反復2の局の474手目の局面を、記録したθ−の値と`go depth 30`で探索させると、深さ19の反復の途中で毎回同じ異常終了が起きた。
`Threads`は1なので、同じ入力で同じノード数をたどる。
gdbで取得した異常終了時のスタックは、`negamax`と`search_move`の組が約245組（約490フレーム）重なっており、1組あたり約8.2 KiBを使っていた。
探索は`MAX_PLY`（256）の近くまで延長されることがあり、そのとき約2.1 MiBのスタックを要して、Rustのスレッドの既定の容量2 MiBを超える。
同じ局面を係数の既定値で探索すると深さ30まで異常終了しないので、θ−の値は延長の深い経路を通りやすくしただけであり、原因は探索スレッドのスタック容量である。
主ワーカーを含む全ワーカーを8 MiBのスタックを持つスレッドで動かす修正（masterのコミット`b74f11c4`）の後は、同じ入力で異常終了は起きず、既定値での探索のノード数と最善手は修正前と一致した。
修正後も、θ−の値でのこの局面の深さ19の反復は、終わるまでに約125秒と約8,800万ノードを要した。対局では持ち時間で打ち切られる。
2件のクラッシュは異常終了した側の負けとして係数の更新に使われたが、約30,000ペアのうちの2ペアなので、最終値への影響は小さいと見る。

## 結論

最終値を、修正を含むmasterのコミット`b74f11c4`の係数の表へ`minase spsa apply`で反映し、候補のコミット`2b4bbbcb`とした。
候補の調整用ビルドが宣言する既定値は、103係数すべてで最終値（整数）と一致した。
採否は、候補を新、`b74f11c4`を旧として、規則セット`lishogi`の段階ゲートで判定する。

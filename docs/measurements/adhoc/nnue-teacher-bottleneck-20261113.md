# NNUE教師生成の律速箇所の測定

## 目的

2026-11-13に、現行の教師生成を同じ局面列で実行し、探索、初期化、出力、および並列実行時の待ち時間のうち、どこが生成速度を制約するかを調べた。
差分更新型評価関数NNUEの学習済みネットを使い、実際の`data selfplay generate`を完局まで測定した。
クラウドでの費用比較に先立つローカル測定であり、Google Cloud上の性能や大規模並列時のメモリ帯域は測定していない。

## コマンドライン

全試行でシードを`9010200000`、1局面の探索上限を20,000ノード、手数上限を4,000手、ランダム着手を0手、置換表を16 MiBに固定した。
2局の試行を通常版と工程別計時用の診断版で3回ずつ実行した後、8局を1並列と4並列で生成した。
計測用の[実行スクリプト](nnue-teacher-bottleneck-20261113/measure.py)は、生成引数、標準出力、性能カウンタ、プロセスの使用CPU時間とスレッド数、および生成物のSHA-256を保存する。
1並列での標本採取は、リポジトリ直下から次の引数で実行した。

```sh
python3 docs/measurements/adhoc/nnue-teacher-bottleneck-20261113/measure.py \
  --binary target/teacher-profile-20261113/bin/minase-baseline \
  --source /tmp/minase-teacher-profile-20261113-source \
  --output target/teacher-profile-20261113/runs/samples-validated-c1 \
  --games 8 --concurrency 1 --seed 9010200000 --cpus 3 --mode record
```

生成コマンドの引数全体は次のとおりである。
診断用の計時コードを加えた作業ツリーから実行できるよう`--allow-dirty`を指定し、引数を揃えるために通常版でも指定した。

```sh
minase-baseline data selfplay generate \
  --output samples-validated-c1.mnsd \
  --seed 9010200000 --games 8 --concurrency 1 --nodes 20000 \
  --random-moves 0 --max-ply 4000 --hash-mb 16 --allow-dirty
```

標本は`perf record --user-callchains --call-graph lbr`で採取し、サイクルに`-e 'cpu_core/cycles,period=4000037/u'`、L3キャッシュのロードミスに`-e 'cpu_core/mem_load_retired.l3_miss,period=4009/upp'`を指定した。
CPUの命令処理枠を分類するTop-down測定には、実行スクリプトの`--mode topdown`を使った。
4並列では`--concurrency 4 --cpus 0-3`へ変更した。
各試行の完全な引数と出力は[実行記録](nnue-teacher-bottleneck-20261113/runs/)にある。

## エンジン

通常版のコミットは`c1c84466476eb36cf43abc529792469862b8e856`である。
同梱ネットの構成は`features=P;ft=256;linear=tapered2;head=pairwise-l16-l32`、SHA-256は`987f060d545c09f0a42b4c668ea8b24cbf83c1770d11d663a94e4b82601274cd`で、規則セットは日本中将棋連盟準拠の`L0,P0,R1,E0`とした。
ネットの属性は[network.json](nnue-teacher-bottleneck-20261113/network.json)に保存した。

ビルドには固定コミットの外部worktreeを使い、リポジトリのrelease設定と`target-cpu=native`、リンク時最適化、`codegen-units=1`を適用した。
次のコマンドで通常版をビルドし、実行ファイルを`bin/minase-baseline`へ複製してから、診断版を別名の`bin/minase-stages`として保存した。

```sh
git worktree add --detach /tmp/minase-teacher-profile-20261113-source \
  c1c84466476eb36cf43abc529792469862b8e856
cd /tmp/minase-teacher-profile-20261113-source
CARGO_PROFILE_RELEASE_DEBUG=1 \
CARGO_TARGET_DIR=/home/stepney141/board-games/minase/target/teacher-profile-20261113/build \
  nice -n 19 taskset -c 0,1 cargo build --release --locked -p minase --bin minase -j2
```

診断版には[計時差分](nnue-teacher-bottleneck-20261113/diagnostic.patch)だけを加えた。
各対局の初期化、探索用局面の複製、探索呼び出し、完了した対局の書き出し、統計、および最後の同期処理を計時した。
探索ノードごとの共有カウンタは追加していない。
工程別の計時には診断版を使い、性能カウンタと処理別の標本採取には通常版を使った。

## 環境

測定機はIntel Core Ultra 7 265KF、20物理コア・20論理CPU、メモリ約30 GiBである。
高性能コアに固定し、1並列では論理CPU 3、4並列では論理CPU 0–3を使った。
教師生成は1ワーカーが1局ずつ逐次探索し、別スレッドが完了した対局を集計する。
Rust 1.98.0、LLVM 22.1.8、Linux 6.18.57-2-lts、perf 7.2.11-1を使用した。
バイナリの検査和と詳細は[environment.json](nnue-teacher-bottleneck-20261113/environment.json)にある。

同じ機械では別の4並列の対局測定が進行していた。
固定ノード数で動くモンテカルロ木探索（MCTS）対αβ探索の測定が終了した後、MCTS対HaChuの固定深さ測定へ移ったため、他の処理からの干渉や動作周波数の変動は残る。
この条件では小さな速度差を最適化の効果と判定せず、工程ごとの時間配分と、同じ出力を得るための処理量を調べる。

## 結果

### 探索が対局処理のほぼ全体を占める

2局の試行では1,150局面を探索して955局面を保存し、通常版の所要時間は中央値23.546秒、範囲23.269–23.990秒だった。
診断版3回の工程比率は次のとおりで、分母は対局処理にかかった経過時間の合計である。

| 工程 | 比率の範囲 |
|---|---:|
| 探索呼び出し | 98.52–98.68% |
| 対局の初期化 | 1.24–1.39% |
| 探索用局面の複製 | 0.056–0.058% |

別スレッドによる書き出しは合計4.4–12.8 ms、終了時の同期処理は2.1–10.2 msだった。
書き出し時間は各試行の生成時間の0.02–0.06%に相当し、探索と重なるため、上表へ加算する比率ではない。
8局・4並列でも探索は各ワーカーの対局処理時間の99.64%を占め、書き出しは27.9 msだった。
この負荷では、出力処理や局面の複製を速めても生成速度への効果は小さい。

診断版2局の所要時間は22.550–23.721秒だった。
通常版より短い試行もあるが、計時コードによる配置変化と測定時の揺れを含むので、両者の速度差を改善量として扱わない。
診断版は工程の比率を調べるために使い、通常版との生成物の完全一致を別に確認した。

### 探索内では手生成と順位付けの負荷が大きい

8局の通常版から105,336個のサイクル標本を採取し、インライン展開情報まで解決して各標本を1区分へ分類した。
以下の分母は採取周期で重み付けしたサイクル標本の合計であり、実時間の割合や変更によって短縮できる割合ではない。

| 処理 | 構成比 |
|---|---:|
| 手生成、利き計算、および盤面のビット集合演算 | 32.1% |
| 手の順位付け、整列、および関連する履歴参照 | 21.8% |
| NNUE評価と累積値更新 | 14.7% |
| 置換表 | 8.8% |
| 評価値の補正履歴 | 4.2% |
| その他の探索制御 | 11.4% |
| 局面の着手・取消しなど | 2.8% |
| 駒の取り合いの評価のうち、上の利き計算を除く部分 | 2.0% |
| 初期化、メモリ確保、および未分類など | 2.2% |

手の順位付けの区分には、捕獲手の履歴、直前までの着手に対応する履歴、および歩の配置に対応する履歴を含めた。
利き計算を呼ぶ取り合いの評価や王手判定では、呼び出し先で実行した命令を利き計算側へ分類しているため、呼び出し元の関数全体の負荷とは異なる。
NNUE評価の内訳は非線形出力、累積値更新、およびその他の評価処理であり、教師生成がNNUEの推論だけで占められているわけではない。
分類規則と集計は[解析スクリプト](nnue-teacher-bottleneck-20261113/analyze_samples.py)、[標本集計](nnue-teacher-bottleneck-20261113/validated-samples-summary.json)、および[総合集計](nnue-teacher-bottleneck-20261113/summary.json)で確認できる。

### 改善候補が対象とする処理の範囲

2026-11-14に、同じ記録の呼び出し履歴と機械語を調べ、攻撃駒の存在判定、静かな手の採点、および置換表の照会が対象とする範囲を確かめた。
`attackers_to_by`の本体に帰属する11,309標本について、CPUの分岐履歴から記録された直近の呼び出し元を取り出し、戻り番地の直前をインライン展開情報まで解決した。
全105,336サイクル標本を分母とした内訳は次のとおりであり、呼び出し元のフレームが欠けた標本は0件だった。

| 呼び出し元 | サイクル標本の構成比 |
|---|---:|
| 駒の取り合いの評価`see_prunes` | 8.46% |
| 王手判定`CheckContext::gives_check` | 1.24% |
| 王駒への攻撃判定`royal_under_attack` | 0.71% |
| 獅子の足の判定`lion_has_foot_after_capture` | 0.31% |
| その他 | 0.01% |

この内訳は呼び出し先の本体だけの標本であり、呼び出す前の準備と、戻った後の処理を含まない。
その他の8標本は、呼び出し箇所の行を特定できなかった`search_move`の7標本と、反復の攻撃判定の1標本である。
取り合いの評価は攻撃駒の集合を使うため、存在だけを返す照会への置き換えはできない。
王手、王駒への攻撃、および獅子の足の判定が合計2.27%に相当し、このうち返された集合を加工しない`royal.rs:16`と`gives_check.rs:63`は合計1.12%だった。
これらは現在のコードで候補が対象にする範囲であり、変更後の速度差の予測や、短縮率の厳密な上限ではない。
集計は[呼び出し元の記録](nnue-teacher-bottleneck-20261113/attack-callers.json)に保存し、次の手順で再生成できる。

```sh
python3 docs/measurements/adhoc/nnue-teacher-bottleneck-20261113/analyze_attack_callers.py \
  --binary target/teacher-profile-20261113/bin/minase-baseline \
  --data target/teacher-profile-20261113/runs/samples-validated-c1.data \
  --output target/teacher-profile-20261113/attack-callers.json
```

静かな手の線形評価差分`quiet_move_pst_delta`を含むインライン階層の標本は全体の1.44%だった。
機械語では、駒数の係数とその補数を`0xadef96`と`0xadefa1`で保存し、各手の採点では`0xae32e9`と`0xae32f2`でその値を再利用していた。
一方、移動元の特徴番号の計算と、移動元の重みを読む`0xae3b78`と`0xae3b7d`は各手の処理に残っていた。
したがって、係数の計算をループの外へ移すことによる追加の高速化は見込めないが、移動元側の共通化を検討する根拠は残る。

置換表の照会では、静止探索内の`0xae8ec2`で記録を読み、予約領域などを検査してから、`0xae8f1e`でキーを比較していた。
順序を変える余地はあるが、復号関数に帰属したサイクル標本の大半はロード直後の命令に集中していた。
この配置はロードの待ちが後続命令へ帰属することと整合し、復号関数の標本全体を復号の演算費用とは扱えない。
これらの機械語は、測定時のバイナリに次のコマンドを使って確認できる。

```sh
objdump -d --start-address=0xadef91 --stop-address=0xadefa9 \
  target/teacher-profile-20261113/bin/minase-baseline
objdump -d --start-address=0xae32d0 --stop-address=0xae3bae \
  target/teacher-profile-20261113/bin/minase-baseline
objdump -d --start-address=0xae8ec2 --stop-address=0xae8f33 \
  target/teacher-profile-20261113/bin/minase-baseline
```

### メモリ待ちだけでは負荷を説明できない

Top-down測定では、メモリ待ちに加えて、命令供給と投機実行の失敗に対応する割合も大きかった。
表の値はCPUの命令処理枠を分母とする指標であり、実時間の割合ではない。
「演算資源側の制約」は実行側全体の制約からメモリ待ちを差し引いた値で、メモリ待ちを二重に加算していない。

| 分類 | 1並列 | 4並列 |
|---|---:|---:|
| 正常に完了した命令 | 37.5% | 35.8% |
| 分岐予測の失敗などの投機損失 | 11.6% | 12.9% |
| 命令供給側の制約 | 23.6% | 24.8% |
| 演算資源側の制約 | 16.0% | 15.0% |
| メモリ待ち | 10.9% | 11.9% |

別途採取した18,996個のL3ロードミス標本のうち、置換表に70.3%、補正履歴の1区分に13.5%、着手の履歴参照に5.6%が帰属した。
これは発生したミスの内訳であり、表を参照したときのミス率や、各表による停止時間ではない。
また、履歴表が他のデータをキャッシュから追い出す影響も、この分類だけでは判定できない。
したがって、置換表はキャッシュミスを調べる候補だが、今回の結果からメモリ帯域の飽和を断定することはできない。

### 少数対局の並列実行では終了時にワーカーが余る

8局の試行では4,204局面、84,080,000ノードを探索して3,532局面を保存した。
通常版の1並列では82.751秒、4並列の2試行では25.849秒と27.323秒で、保存局面数の処理速度は約3.0–3.2倍になった。

| 試行 | 経過時間 | 保存局面数/秒 | 使用可能CPU時間に対する使用率 |
|---|---:|---:|---:|
| 1並列、Top-down測定 | 82.751秒 | 42.68 | 95.4% |
| 4並列、通常カウンタ測定 | 27.323秒 | 129.27 | 76.6% |
| 4並列、Top-down測定 | 25.849秒 | 136.64 | 79.0% |

使用率は`/proc`を0.25秒間隔で読んだCPU時間の差分を、観測した経過時間と指定コア数で割って求めた。
4並列では、終了前の約8.0–8.5秒は探索ワーカーが2本だけ残っていた。
1局にかかる時間が異なるうえ、残りの対局がなくなったワーカーは終了するため、実行の末尾では指定した4コアを使い切れなくなる。
診断版でも各局の終了時刻とスレッド数の減少が対応していた。

1ノード当たりのサイクル数は1並列で4,984、4並列で5,055と約1.4%の差だった。
この4並列の試行では、CPU使用率の低下をメモリ競合だけで説明するより、末尾のワーカー不足を含めて説明する方が測定と整合する。
ただし、8局を4並列に割り当てた短い試行であり、この損失率を数千局・数百並列の生成へ外挿することはできない。

### 生成物と測定記録の検証

同じ局数の試行では、通常版、診断版、1並列、および4並列の生成ファイルがバイト単位で一致した。
2局の6試行のSHA-256は`b6d613da28573642870bbc8bcc1dfea1a12e9038a10adae5d252917a409d3dfb`、8局の5試行は`c1bf2af7e9a5f898b2d2882744970ca3355b6a40db2fae5f4053202354cfe78c`である。
時間と並列数を除く生成統計も一致し、手数上限による破棄と実行異常は0件だった。
これは生成負荷の診断であり、棋力差、レーティング差、および対局の時間切れは測定対象にしていない。

標本採取の初回には、イベントごとに意図した採取周期が適用されていなかったため、その記録を処理別内訳から除外して取り直した。
採用した記録は[イベント定義](nnue-teacher-bottleneck-20261113/validated-events.txt)で周期を確認し、[欠落と採取抑制の検査](nnue-teacher-bottleneck-20261113/validated-record-health.json)はいずれも0件だった。
この注意点は[perfの採取周期に関する教訓](../../lessons/set-perf-sampling-period-per-event.md)に残した。

集計は`python3 docs/measurements/adhoc/nnue-teacher-bottleneck-20261113/summarize.py`で再生成できる。
実行バイナリ、生成ファイル、および生のperfデータは`target/teacher-profile-20261113/`に保存した。
診断用の差分は付属資料として残し、専用worktreeは測定後に削除した。
本体のソースコードには計時処理を残していない。

## 結論

この機械と探索条件では、教師生成は探索処理が律速であり、改善調査では負荷の大きい手生成・利き計算と手の順位付けを優先し、クラウド選定では同じ負荷の保存局面数/秒と料金を実測して比較する。

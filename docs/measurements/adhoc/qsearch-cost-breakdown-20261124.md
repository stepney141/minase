# 静止探索の時間の内訳、枝刈りの免除をやめたときのノード数、および置換表の容量とスレッド数による探索速度

## 目的

本測定は、探索時間の約4割を占める静止探索（quiescence search、読みの末端で駒を取る手だけを読み進める探索）について、時間の内訳と1ノードあたりの費用を通常探索と比べ、探索の結果を変えずに減らせる処理と、探索木を変えて調整する候補を切り分ける。
静止探索は、駒を取る候補手を、読む順番による手数制限、取る駒の価値に余裕値を足してもαに届かない手を読まないdelta pruning、および静的交換評価（SEE、到達升での駒の取り合いの損得の見積り）の閾値で枝刈りし、直前の手の到達升で取る手（取り返し）、成る手、および王手になる手をこれらの枝刈りから免除している。
あわせて、成る手と王手になる手の免除をやめたときの探索ノード数と探索速度、および置換表（探索済み局面の結果を保存する表）の容量とスレッド数による探索速度を記録する。
棋力は測っていない。

## コマンドライン

基本の負荷は、固定の15局面を深さ16で探索するUSIの独自コマンド`bench`であり、次の5行を標準入力から与え、性能コアの論理CPU 3に固定して実行した。

```console
setoption name RuleSet value JCSA
setoption name EvalFile value <ネット>
isready
bench depth 16 threads 1 repetitions 1
quit
```

関数別の内訳は、フレームポインタを残したビルドを次の形で採取し、[教師生成の高速化の付属資料](../teacher-generation-speedup/teacher-generation-speedup-engine/)の`inline_prof.py`でインライン展開まで解決して、静止探索の呼び出し先の木を集計した。

```console
CARGO_PROFILE_RELEASE_DEBUG=1 RUSTFLAGS="-C target-cpu=native -C llvm-args=-inline-threshold=1000 -C force-frame-pointers=yes" \
  cargo build --release --locked -p minase --bin minase
taskset -c 3 perf record -o bench.data --user-callchains --call-graph fp -e 'cpu_core/cycles,period=500009/u' -- <バイナリ> --protocol usi < bench16.usi
python3 inline_prof.py bench.data <バイナリ> --tree 'Searcher>::quiesce$' --tree-depth 3 --tree-min 0.3
```

枝刈りと免除の発動回数は、`cargo build --release --locked -p minase --bin minase --features search-stats`のビルドで同じ`bench`を実行し、最後に出力される`stats:`行から全15局面の合計を読んだ。

免除をやめる変種は、環境変数`QX`で動作を切り替える診断用の変更を`crates/minase/src/search/alphabeta/quiesce.rs`に加えたビルドで測り、各変種で`bench`の深さ12と深さ16を1回ずつ実行した。
この変更の差分は保存していない。
`QX=0`では、現行と同じく動作する。
`QX=1`では、取り返しと成る手を枝刈りから免除する条件`is_recapture || mv.promote`を`is_recapture`だけにして、成る手を免除の対象から除く。
`QX=2`では、`QX=1`の変更に加えて、王手になる手の免除を判定する`checking_move_exempts_qsearch_pruning`が王手の判定を呼ばずに常に偽を返すようにして、王手になる手も免除の対象から除く。

置換表の容量とスレッド数による探索速度は、`bench`の15局面の1つである`game-6-ply-77`（下の`position sfen`の行の局面）を、オンライン対局サイトlishogiの実装に近い規則セット`lishogi`で10秒間探索し、最後の`info`行の毎秒ノード数を読んだ。
各条件を2回ずつ測った。

```console
setoption name RuleSet value lishogi
setoption name EvalFile value <ネット>
setoption name Threads value <1または4>
setoption name USI_Hash value <256または2048>
isready
usinewgame
position sfen l1c1gekgsc1l/3st2t1b1a/1vr1dq1dhrv1/a2p1poxp1fm/1p2h1ppippp/p4n6/1PFbf7/PN3PPPIPPP/MC1P1OC1P3/2RHD1Q1HRVM/A1B1T1DT1B1A/LV1SGKEGS1FL w - 1
go movetime 10000
```

1スレッドは論理CPU 4に、4スレッドは論理CPU 4から7に固定した。

これとは別に、4つの性能コアを同時に使ったときの減速の有無を見るため、`bench`の深さ16を1スレッドで、論理CPU 4から7に1つずつ固定した4つのプロセスとして同時に実行する測定と、論理CPU 4に固定した1つのプロセスだけを実行する測定を、それぞれ2回行った。

## エンジン

対象はminaseのmasterのコミット`f9b56d03`である。
このコミットの後に、第3世代のネットに合わせて探索の係数を自動調整（SPSA）し直した版がmasterへ入り、静止探索の係数のうち、delta pruningとSEEの閾値に使う余裕値`DeltaMargin`、SEEの下限を決める`QsearchSeeMargin`、および手数制限の上限`QsearchMoveLimit`は、78、83、8から57、42、5へ変わったので、本測定の件数とノード数は現行のmasterとは異なる。
ネットは第3世代のネットのファイル（SHA-256は`cbbccf6f5ee7097fd890086d2cf4bca72ed969da28353cb0c4a2f4d781acc244`）である。このファイルは、ネットの構造を表す文字列の中の入力特徴集合の名前を`P`から`A`へ改める前のものである。
ビルドはリポジトリのrelease設定（`target-cpu=native`、インライン閾値1000、LTO有効、`codegen-units=1`）である。

## 環境

測定機はIntel Core Ultra 7 265KF（性能コア8、高効率コア12、スレッドは計20、メモリ30 GiB）で、Linux `6.18.63-3-lts`、Rust `1.100.0`、perf `7.3.6`である。
`bench`の探索ワーカーは1、置換表は`bench`の既定の容量である。
2026年11月24日と25日に測った。
測定中、lishogiのBotのエンジン2つが探索を続けており、合わせて約8スレッドの負荷があった。
対局の測定、SPSA、および教師生成は動いていなかった。

## 結果

### 静止探索の時間の内訳

静止探索とその呼び出し先は、全標本の41.5%を占めた。
下表は、全標本に対する割合と、静止探索の41.5%に対する割合である。
呼び出しの木の全体は[付属の集計](qsearch-cost-breakdown-20261124/profile-quiesce-tree.txt)にある。

| 処理 | 全標本に対する割合 | 静止探索の中での割合 |
|---|---:|---:|
| 静的評価（`evaluate_at`） | 16.1% | 39% |
| うちNNUEの後段を含む評価（`evaluate_accumulator`） | 13.9% | 34% |
| うち累算値の差分更新（`ensure_accumulator`） | 1.9% | 4% |
| 捕獲の候補の初期化（`QsearchBuffers::initialize`） | 6.7% | 16% |
| 置換表の照会（`probe`） | 6.1% | 15% |
| 静的交換評価SEE（`see_prunes`） | 4.5% | 11% |
| 候補の群の生成と取り出し（`QsearchBuffers::next`） | 2.5% | 6% |
| 王手になる手の免除の判定（`checking_move_exempts_qsearch_pruning`） | 1.4% | 3% |
| 静的評価の補正の読み出し（`correction_weighted_sum_at`） | 1.3% | 3% |

### 1ノードあたりの費用

`search-stats`のビルドで数えた全15局面の合計は、通常探索のノードが818,856、静止探索のノードが1,584,412であり、静止探索はノードの65.9%を占めた。
この2つの和の2,403,268は、`bench`が出力する探索ノード数2,094,622より大きい。2つは数え方が違うが、差の内訳は調べていない。
発動回数の全体は[付属の集計](qsearch-cost-breakdown-20261124/search-stats-bench16.txt)にある。
フレームポインタのビルドの標本で、探索全体（`search_root`）は89.6%、静止探索は41.5%だったので、通常探索の処理（静止探索を除く）は48.1%である。
探索ノード100万あたりの標本の割合は、静止探索が26.2%、通常探索が58.7%であり、静止探索の1ノードの費用は通常探索の約0.45倍だった。

### 枝刈りと免除の発動回数

| 項目 | 回数 |
|---|---:|
| 手数制限で枝刈りした候補 | 227,454 |
| SEEの閾値で枝刈りした候補 | 307,653 |
| SEEの下限で枝刈りした候補 | 331,229 |
| 取り返しとして免除した候補 | 193,858 |
| 成る手として免除した候補 | 186,219 |
| 王手になる手として免除した候補 | 131,172 |
| 王手の判定の呼び出し | 1,401,539 |

免除の回数は、免除がなければ手数制限、delta pruning、またはSEEの閾値で枝刈りされた候補の数である。
SEEの下限による枝刈りは、免除の後にも、免除した候補を含めて働く。
王手の判定は静止探索の1ノードあたり0.88回呼ばれ、そのうち免除になったのは9.4%だった。

### 免除をやめたときの探索ノード数と探索速度

| 変種 | 深さ12のノード数 | 深さ16のノード数 | 深さ16の毎秒ノード数 |
|---|---:|---:|---:|
| `QX=0`（現行） | 448,594 | 2,094,622 | 818,866 |
| `QX=1`（成る手の免除をやめる） | 411,265 | 2,285,211 | 829,672 |
| `QX=2`（成る手と王手になる手の免除をやめる） | 414,781 | 2,270,717 | 850,355 |

成る手の免除をやめると、探索ノード数は深さ12で8.3%減り、深さ16で9.1%増えた。
王手になる手の免除もやめると、深さ16の毎秒ノード数は現行より3.8%高かった。
深さによってノード数の増減の向きが変わるので、固定の深さのノード数からは強さへの影響を判断できない。

### 置換表の容量とスレッド数による探索速度

| 条件 | 1回目（到達深さ、毎秒ノード数） | 2回目（到達深さ、毎秒ノード数） |
|---|---:|---:|
| 1スレッド、置換表256 MB | 深さ29、782,444 | 深さ29、784,028 |
| 1スレッド、置換表2,048 MB | 深さ29、791,779 | 深さ28、788,417 |
| 4スレッド、置換表2,048 MB | 深さ31、3,195,340 | 深さ34、3,150,747 |

毎秒ノード数は、置換表の容量を256 MBから2,048 MBへ増やしてもほとんど変わらず、4スレッドでは1スレッドの約4倍だった。

`bench`の深さ16を4つのプロセスとして同時に実行したときの毎秒ノード数は、1回目が818,824〜827,085、2回目が819,015〜824,958であり、論理CPU 4で1つのプロセスだけを実行したとき（827,071と830,369）と比べて、目立った減速はなかった。

## 結論

静止探索は、1ノードの費用が通常探索の約0.45倍と小さいが、探索ノードの約3分の2を占めるので、探索時間の約4割に達する。
その時間の約4割は静的評価が占めるので、探索の結果を変えずに静止探索を速くするには、静的評価、特にNNUEの後段の計算を速くするのが最も効く。
成る手と王手になる手の免除をやめると、深さ16の毎秒ノード数は最大で3.8%上がるが、ノード数の増減の向きが深さで変わるので、強さへの影響は対局で測る必要がある。
置換表の容量は毎秒ノード数をほとんど変えず、4スレッドの毎秒ノード数は1スレッドの約4倍だった。

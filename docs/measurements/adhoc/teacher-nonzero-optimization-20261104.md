# 学習済みNNUEでの教師生成の高速化調査

## 目的

2026-11-04に、学習済みの非ゼロNNUEを使い、探索結果を保ちながら教師生成の処理量を減らす方法を調べた。
[先行測定](teacher-single-thread-profile-20261104.md)で負荷が大きかった利き計算と手の順位付けから候補を選び、生成0だけに適用できる評価計算の省略は対象に含めなかった。

## コマンドライン

性能比較は、同一CPUに固定した自己対局生成を版ごとに5回ずつ実行し、回ごとに版の実行順を反転した。
各試行は2対局、1手20,000ノード、上限200手、同時対局1、置換表16 MiBとした。
すべて375局面、7,500,000ノードを処理し、2対局とも手数上限で破棄された。
この条件は同じ探索量で速度を比べるためのもので、教師レコードの保存速度を測るものではない。

```sh
python3 target/teacher-optimization/compare.py \
  --directory target/teacher-optimization --tag individual \
  --versions base attackers continuation see-reuse --rounds 5
```

各試行で実行した生成部分の引数は次のとおりである。
`perf stat` はサイクル、命令、L1からL3のロードミス、分岐予測ミスをユーザーモードで計測した。

```sh
taskset -c 3 <binary> data selfplay generate --output <output.mnsd> \
  --seed 9010200000 --games 2 --concurrency 1 --nodes 20000 \
  --random-moves 0 --max-ply 200 --hash-mb 16 --allow-dirty
```

探索結果の照合は、固定15局面の `dev bench --depth 9 --threads 1 --repetitions 1` と、上記を `--max-ply 4000` にした完局までの自己対局で行った。
前者は局面ごとのノード数、最善手、評価値を、後者は生成ファイル全体のSHA-256を基準版と比較した。
速度比較に診断用カウンタの追加は行っていない。

個別測定後に3つの変更を組み合わせ、探索結果の照合を終えてから、同じ条件で基準版と交互に5回ずつ測定した。

```sh
python3 target/teacher-optimization/compare.py \
  --directory target/teacher-optimization --tag combined \
  --versions base combined --rounds 5
```

各実行の引数、カウンタ、集計値、検証結果、試作差分と再現スクリプトは [付属資料](teacher-nonzero-optimization-20261104/) に保存した。
再現スクリプトは `target/teacher-optimization/` に置き、同名のworktreeと `bin/` 内のバイナリを使う。
生のperfデータと全実行ログも同ディレクトリに残した。

## エンジン

基準版はmasterの `9380aa7fcdee6a70003260dff4edac547728bf4e` で、規則セットは全版とも `L0,P0,R1,E0` である。
同梱ネットは `features=P;ft=256;linear=tapered2;head=pairwise-l16-l32` で、SHA-256は `987f060d545c09f0a42b4c668ea8b24cbf83c1770d11d663a94e4b82601274cd` だった。
入力重み3,502,080要素のうち2,417,882要素が非ゼロで、本体の検査和も一致した。
全候補で同一のネットを使い、評価器は変更していない。

候補はそれぞれ基準版から分けた専用worktreeに置き、次の3つの変更を試した。

| 版 | 変更 | 探索結果を保つ理由 |
|---|---|---|
| `attackers` | 利きの逆引きで、走りの利き線全体を作る処理を、最初の遮蔽升の取得に置き換える。 | 最初の占有升が自駒かを判定し、従来と同じ駒種と方向の検査を行う。 |
| `continuation` | 静かな手の採点前に、5つの過去文脈に対応する履歴表の行先頭を計算する。 | 各候補手では現在駒種と到達升の部分だけを加える。履歴値を読む順序と時点は保つ。 |
| `see-reuse` | 静止探索で、同じ捕獲手に対する駒取り評価の再判定を条件付きで省く。 | 厳しい閾値で枝刈りしないと分かった場合は、それ以下の閾値でも枝刈りしない。 |

`attackers` は両陣営を含む占有から最初の遮蔽を選ぶため、敵駒や仮想の占有升を飛び越えない。
`continuation` は添字を分配則で分解しただけで、表の容量、参照する要素、更新方法を変えていない。
`see-reuse` は最初の評価を実際に通過し、その閾値が最終下限以上だった場合だけ省略し、取り返し、成り、王手による免除では従来どおり最終判定を行う。

ビルドは `CARGO_PROFILE_RELEASE_DEBUG=1` を付けた通常のrelease設定で、`target-cpu=native`、LTO有効、`codegen-units=1` とした。
共有ビルドディレクトリを使うため、版を切り替える際には `minase` と `minase-core` の成果物を消して再ビルドし、各バイナリのハッシュとデバッグ情報のソースディレクトリを確認した。
ビルドはCPU 12と13で並列数2に制限し、性能測定とは同時に実行しなかった。

## 環境

Intel Core Ultra 7 265KFの高性能コアである論理CPU 3に、探索ワーカー1スレッドを固定した。
測定機は20物理コア、20論理CPUを持ち、対象コアのL1データキャッシュは48 KiB、L2は3 MiB、共有L3は30 MiBである。
Linux `6.18.57-2-lts`、Rust `1.98.0 (88d9e12ae 2026-08-18)`、perf `7.2.11-1` を使用した。

同じPCでは各4スレッドのBot探索2プロセスも動作していた。
測定対象をCPUに固定しても、動作周波数や共有キャッシュの影響は残るため、探索速度に加えて1ノード当たりの命令数とサイクル数を比較した。
個別測定と組合せ測定の全イベントのカウンタ稼働率は100%だった。

## 結果

### 学習済みネットの負荷

基準版の375局面のサイクル標本では、手生成と利き計算が40.2%、その他の手の順位付けと整列が12.8%、continuation historyの添字計算が3.7%を占めた。
割合は生成プロセス全体の標本を周期で重み付けした構成比であり、処理を省いた場合の速度改善率ではない。
採取は3,001 Hzを指定したが、perfはカーネルの上限に合わせて2,700 Hzへ制限し、34,038サンプルを記録した。

### 個別の変更

履歴表の添字を分離する案が、命令数とサイクル数を最も大きく減らした。
下表は各版5回の中央値と基準版との差であり、各変更を単独で適用した結果である。

| 版 | 探索速度 | 速度差 | サイクル/ノードの差 | 命令数/ノードの差 |
|---|---:|---:|---:|---:|
| 基準版 | 640,375ノード/秒 | 0% | 0% | 0% |
| 履歴表の添字の分離 | 665,889ノード/秒 | +3.98% | −3.91% | −6.07% |
| 最初の遮蔽升の直接取得 | 653,685ノード/秒 | +2.08% | −2.14% | −3.28% |
| 駒取り評価の再利用 | 645,816ノード/秒 | +0.85% | −0.79% | −0.85% |

基準版の探索速度は597,192〜641,531ノード/秒で、最大値と最小値の差を中央値で割った幅は6.92%だった。
個別の速度差はこの幅を超えていないため、上表だけから改善率を確定することはできない。
サイクル数と命令数の減少を確認したうえで、3つの変更を組み合わせた版を別途基準版と比較した。

### 3つの変更を組み合わせた結果

組合せ版は基準版に対して探索速度の中央値が7.33%高く、差は両版の試行間の幅を上回った。
この比較は個別測定とは別の時間帯に行ったため、直前の表の絶対速度とは直接比較できない。

| 指標 | 基準版 | 組合せ版 | 基準版との差 |
|---|---:|---:|---:|
| 探索速度の中央値 | 596,166ノード/秒 | 639,866ノード/秒 | +7.33% |
| 探索速度の範囲 | 595,877〜596,565ノード/秒 | 638,918〜640,797ノード/秒 | 該当なし |
| 最大値と最小値の差/中央値 | 0.12% | 0.29% | 該当なし |
| サイクル/ノード | 8,688.72 | 8,097.00 | −6.81% |
| 命令数/ノード | 31,783.85 | 28,581.73 | −10.07% |

削減したのは主に重複計算であり、履歴表の容量と精度は維持した。
この結果は当該PCの単独スレッドでの改善を示すもので、生成機での384並列の速度改善率は測っていない。
先行測定の旧版に対する約2倍の計算コスト差を、この変更だけで解消するものでもない。

### 探索結果の一致

個別の3版と組合せ版はいずれも、固定15局面の深さ9の探索でノード数、最善手、評価値が基準版と一致した。
完局までの2対局では各版とも23,000,000ノードを探索し、生成した8,713 Bの教師データが基準版とバイト単位で一致した。
生成ファイルのSHA-256は `0474f011c52257cfed93f74a803de03b597304572df15c35a859c057d9ebd64d` である。

既存テストは、利き計算を含む手生成112件、履歴と手の順序29件、静止探索12件、駒取り評価18件が成功した。
この検証は有限の局面に対するもので、棋力の検定や多スレッドでの速度評価は行っていない。

### 次の調査候補

手の整列には、採点済みの静かな手をヒープから順に取り出す案が残る。
全件整列の代わりに、候補数をn、実際に取り出す手数をkとして、構築O(n)と取り出しO(k log n)へ変えられる。
ただし全候補を読む局面では遅くなる可能性があり、採点自体を遅らせると子探索中の履歴更新を拾って順番が変わるため、候補数と取り出し数を先に測る必要がある。
根の整列キーの一度だけの計算と、捕獲情報を採点と履歴参照で共用する変更も候補だが、今回の速度比較には含めていない。

384並列でのメモリ対策には、continuation historyを行ごとに遅延確保する案がある。
現行表は16,704行、1行8,352 Bで計133.049 MiBを持ち、全要素の初期値は−586である。
未更新の行をこの初期値で表現し、初回更新時に行を確保すれば学習情報を捨てずに容量を減らせるが、参照時の分岐とポインタ参照が増える。
対局終了までの使用行数と更新行数を測っていないため、メモリ削減量と速度への効果は未確定である。

## 結論

学習済みネットで3つの変更を併用すると、照合した探索結果と教師データを保ったまま、単独スレッドの探索速度が中央値で7.33%向上した。

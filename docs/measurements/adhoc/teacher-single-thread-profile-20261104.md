# NNUE教師生成の単独スレッド測定

## 目的

2026-11-04に、生成0の教師生成エンジンと旧版を同じPCの1スレッドで比較し、速度低下とcontinuation history、continuation correction historyの負荷を調べた。
測定対象は実際の `data selfplay generate` であり、棋力や教師データの品質は判定していない。

## コマンドライン

速度比較では、両版を交互に3回ずつ実行した。
各試行を4対局、上限200手にそろえ、探索した748局面、14,960,000ノードを処理する時間とハードウェアカウンタを比較した。
生成0の第1試行は次のコマンドで実行した。
`profile_root` はリポジトリ直下で設定し、実行時のカレントディレクトリは対応するクリーンなworktreeとした。

```sh
profile_root="$PWD/target/teacher-bottleneck"
cd "$profile_root/source-gen0"
taskset -c 3 perf stat -x, \
  -o "$profile_root/results/gen0-baseline-1.stat" \
  -e cpu_core/cycles/u,cpu_core/instructions/u,cpu_core/mem_load_retired.l1_miss/u,cpu_core/mem_load_retired.l2_miss/u,cpu_core/mem_load_retired.l3_miss/u,cpu_core/branches/u,cpu_core/branch-misses/u \
  -- "$profile_root/bin/gen0" data selfplay generate \
  --output "$profile_root/results/gen0-baseline-1.mnsd" \
  --seed 9010200000 --games 4 --concurrency 1 --nodes 20000 \
  --random-moves 0 --max-ply 200 --hash-mb 16
```

処理別の内訳を得るため、同じシードとノード予算で `--games 2 --max-ply 4000` に変更し、完局まで測定した。
サイクル標本は `perf record -e cpu_core/cycles/u -F 3001`、ロードミス標本は `-c 1009` と `cpu_core/mem_load_retired.l{1,2,3}_miss/upp` の3イベントで採取した。
呼び出し元の補助測定には `-F 499 --user-callchains --call-graph lbr` を使った。
実行引数の全体は [速度比較の記録](teacher-single-thread-profile-20261104/baselines.json) と [完局測定の記録](teacher-single-thread-profile-20261104/profile-commands.json) に保存した。

探索回数の診断では、既存の `search-stats` 機能を有効にし、探索終了時に統計とNNUEの累積値更新回数を出力した。
差分は [旧版](teacher-single-thread-profile-20261104/old-stats.patch) と [生成0](teacher-single-thread-profile-20261104/gen0-stats.patch) に保存した。
診断版の速度は比較に用いず、各版で通常版と診断版の生成ファイルのSHA-256が一致することを確認した。

## エンジン

旧版は過去の教師生成速度との比較に使われた版、生成0は生成機で実行されていた版である。
比較には各コミットに同梱されたネットを用いたため、探索実装と評価器の両方が異なる。

| 対象 | コミット | 同梱ネットの構成 |
|---|---|---|
| 旧版 | `9f393ecce304ba2b8aa83abdf624562224c879b5` | P、幅128、direct-screlu |
| 生成0 | `6f874692fb91544c94394ca0e8df25299ef2e02d` | P、幅256、pairwise-l16-l32 |

両版の規則セットは `L0,P0,R1,E0` とした。
バイナリとネットのSHA-256は [集計値](teacher-single-thread-profile-20261104/baseline-summary.json) に記録した。
各worktreeで次の設定によりビルドし、完成したバイナリを版ごとに保存した。

```sh
CARGO_PROFILE_RELEASE_DEBUG=1 \
CARGO_TARGET_DIR="$profile_root/build" \
  taskset -c 12,13 cargo build --release --locked -p minase --bin minase -j2
```

最適化はリポジトリのrelease設定を使用し、`target-cpu=native`、LTO有効、`codegen-units=1` とした。
診断版だけは別worktreeで小変更を適用し、`--features search-stats` を指定してビルドした。

## 環境

測定機はIntel Core Ultra 7 265KFで、20物理コア、20論理CPUを持つ。
全試行を高性能コアの論理CPU 3に固定した。
このコアのL1データキャッシュは48 KiB、L2は3 MiB、共有L3は30 MiBである。
両版とも探索ワーカー1、同時対局1、置換表16 MiBとし、ビルドと性能測定は同時に実行しなかった。

OSはLinux `6.18.57-2-lts`、Rustは `1.98.0 (88d9e12ae 2026-08-18)`、perfは `7.2.11-1` を使用した。
速度比較の全カウンタの稼働率は100%だった。
測定時の詳細は [環境記録](teacher-single-thread-profile-20261104/environment.json) に残した。

## 結果

### 単独スレッドの速度差

生成0の速度中央値は旧版の50.1%であり、384並列での競合がない環境でも速度低下が再現された。
1ノード当たりの命令数は1.75倍、サイクル数は2.04倍だった。
各指標は3試行の中央値で、速度には生成処理が報告する経過時間を用いた。

| 指標 | 旧版 | 生成0 | 生成0 / 旧版 |
|---|---:|---:|---:|
| 探索速度 | 1,293,024ノード/秒 | 647,304ノード/秒 | 0.501 |
| 経過時間 | 11.570秒 | 23.111秒 | 1.998 |
| 命令数/ノード | 17,104 | 29,882 | 1.747 |
| サイクル数/ノード | 4,014 | 8,177 | 2.037 |
| L1ロードミス数/ノード | 5.206 | 31.639 | 6.078 |
| L2ロードミス数/ノード | 0.528 | 2.221 | 4.207 |
| L3ロードミス数/ノード | 0.413 | 1.046 | 2.529 |
| 分岐予測ミス数/ノード | 16.130 | 40.357 | 2.502 |

探索速度の範囲は旧版1,292,767〜1,375,781ノード/秒、生成0は627,570〜671,818ノード/秒だった。
全試行で4対局とも200手の上限に達して破棄されているため、この比較は教師レコードの保存速度を測るものではない。
同じノード予算でも到達局面と探索木は異なるので、命令数の差を特定の機能だけに帰属させることはできない。

### 完局までの処理別負荷

完局測定では、旧版は17,700,000ノード、724レコード、生成0は13,940,000ノード、575レコードを処理した。
サイクル採取時の生成時間は旧版11.781秒、生成0は19.468秒で、各2対局とも上限による破棄はなかった。
下表の割合は、生成プロセス全体のサイクル標本を周期で重み付けした構成比であり、実時間の割合や最適化による短縮率ではない。
命令アドレスをインライン展開情報まで解決し、各標本を1区分に分類した。

| 処理 | 生成0の構成比 | 旧版の標本サイクル/ノード | 生成0の標本サイクル/ノード |
|---|---:|---:|---:|
| 手生成と利き計算 | 37.3% | 1,433 | 2,844 |
| その他の手の順位付けと整列 | 11.6% | 338 | 883 |
| NNUEの非線形出力 | 7.8% | 106 | 595 |
| 置換表 | 6.6% | 241 | 506 |
| continuation historyの添字計算と参照など | 6.1% | 0 | 461 |
| NNUEの累積値更新 | 3.8% | 240 | 287 |
| continuation correction historyの添字計算と参照 | 0.9% | 0 | 66 |

手生成と利き計算は両版とも最大の区分で、生成0では1ノード当たりの負荷が約2倍になった。
呼び出し元の補助測定では、周期で重み付けした標本の12.1%に駒の取り合いを評価する `see` が、6.2%に王手判定の `gives_check` が含まれた。
これらは呼び出し先も含み、上表の利き計算などと重複するため、構成比へ加算できない。
静止探索から呼ばれた枝刈り免除の王手判定は3.3%だった。

### キャッシュミスの発生箇所

生成0のL3ロードミス標本は、置換表を参照する命令で発生したものが77.8%を占めた。
continuation historyは4.8%、continuation correction historyは5.2%で、両表への直接帰属は約10.0%だった。
L1ロードミスではNNUEの累積値更新が35.3%、continuation historyが11.1%だった。
これらは発生したミスの構成比であり、各表を参照したときのミス率ではない。

IntelのTop-down指標では `tma_memory_bound` は12.4%、`tma_core_bound` は20.3%、`tma_frontend_bound` は15.7%、`tma_bad_speculation` は9.3%、`tma_retiring` は42.3%だった。
分母はCPUの命令処理枠であり、「実時間の12.4%がメモリ待ち」という解釈はできない。
また、巨大な履歴表が置換表やNNUEのデータをキャッシュから追い出す間接的な影響は、ミスした命令の分類からは判定できない。

両履歴表は教師生成の各対局が個別に持ち、384対局が1枚の表を書き換えている構造ではない。
1対局当たりの配列容量はcontinuation historyが133.049 MiB、continuation correction historyが34.409 MiBで、384対局なら計62.797 GiBになる。
共有キャッシュやメモリ帯域を圧迫する余地は残るが、このPCの単独スレッド測定から生成機の帯域飽和は判定できない。

### 探索回数と評価器

報告ノード数は着手を適用した回数で、探索関数の呼び出し回数とは異なる。
この計数方式は両版で共通だが、完局測定では、報告ノード当たりの探索関数呼び出し回数と置換表照会回数が増えていた。

| 指標 | 旧版 | 生成0 |
|---|---:|---:|
| 通常探索の呼び出し | 7,159,149回 | 4,788,070回 |
| 静止探索の呼び出し | 11,299,512回 | 11,708,284回 |
| 合計呼び出し/報告ノード | 1.043 | 1.183 |
| 置換表照会/報告ノード | 0.642 | 1.183 |
| NNUEの累積値更新/報告ノード | 1.030 | 1.172 |

生成0の静止探索は枝刈り免除のために10,722,774回の王手判定を行った。
通常探索と静止探索を合算した呼び出し/報告ノードは13.5%増え、置換表照会/報告ノードは約1.84倍だった。
旧版では静止探索の一部が置換表照会より先に終了していたため、両版の置換表ヒット率の単純比較は避ける。
これらは完局測定の値であり、200手で打ち切った速度比較の命令数増加から機械的に差し引くことはできない。

生成0のネットでは非線形部分の全重みとバイアスが0だった。
[ネットの検査結果](teacher-single-thread-profile-20261104/network-audit.json) では、入力重み3,502,080要素を含む全区画を読み、本体の検査和も確認した。
一方、`evaluate_accumulator` は評価のたびに非線形出力を計算しており、その処理が上表の7.8%に当たる。
生成0に限って同じ評価値を保ちながらこの計算を省く余地はあるが、学習後の非ゼロネットには適用できないため、教師生成を継続して速める改善策には含めない。
この計算を省いた場合の速度改善量は未測定である。

改善調査では、負荷の大きい利き計算と手の順位付けを優先し、学習済みの非ゼロネットで効果を確認する。
履歴表については直接参照の負荷に加え、ほかのデータをキャッシュから追い出す影響と並列時の帯域競合を切り分ける必要がある。

### 検証と再現資料

各版で診断版と通常版の生成ファイルは完全一致し、生成0ではサイクル、ロードミス、Top-down、呼び出し元の各測定でも一致した。
サイクル標本は旧版35,365個、生成0は58,372個、生成0のL3ロードミス標本は11,082個だった。
呼び出し元の補助測定では9,749個の標本を用いた。
先に試したDWARFによる呼び出し元の復元は大半の標本で失敗したため、結果の解釈には使用していない。

集計JSON、コマンド、診断差分、解析スクリプトは [付属資料](teacher-single-thread-profile-20261104/) に保存した。
生のperfデータ、実行バイナリ、診断用worktreeは `target/teacher-bottleneck/` にある。
`network-audit.py` は同ディレクトリへ置いて実行し、`analyze_perf.py` と `analyze_callgraph.py` は入力と出力を引数で指定する。
棋力の検定、対局ペアの破棄数、時間切れ負けの評価は本測定の対象外で、自己対局生成の異常終了はなかった。
製品コードの変更はなく、診断用の変更は専用worktreeだけに置いた。

## 結論

生成0の速度低下は単独スレッドでも再現し、命令量、利き計算、手の順位付けの負荷増加を確認したが、両履歴表と384並列での帯域競合が速度低下に寄与する割合は未確定である。

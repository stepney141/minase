# AlphaZero型探索の実現性の実測（フェーズ0）

## 目的

[AlphaZero型探索と深層強化学習](../plans/alphazero.md)のフェーズ0として、作業機と候補のレンタル機で、ネットの推論速度、1シミュレーションあたりのCPUの費用、既存の自己対局の対局長と合法手数の分布、および教師生成の速度を測り、強化学習の1サイクルの所要時間と費用を一次見積もりする。本記録は項目ごとに測れた時点で書き足し、未測定の項目は「未測定」と明記する。

## 環境

作業機は、CPUがIntel Core Ultra 7 265KF（20コア、ハイパースレッディングなし）、メモリ30 GiB、GPUがNVIDIA GeForce RTX 3060 Ti（8 GiB、ドライバ615.71.09）、CUDA 13.4、Linux 6.18.53である。
NVIDIA Container Toolkit 1.20.0は2026年10月9日に利用者が導入した。Docker 29.8.1では`--gpus all`がToolkitのCDI経由で動き、`daemon.json`へのランタイム登録は不要だった。コンテナイメージ`minase-zero:dev`（`tools/train/zero/Dockerfile`、CUDA 13.4.2、cuDNN 9.26、ONNX Runtime 1.28.0、TensorRT 10.14.1.48、PyTorch 2.13.0）は同日に作業機でビルドし、展開後24 GBである。
レンタル機の環境は、借りた時点でここに書く。

## 第1項　ネットの推論速度

### 作業機

まずコンテナイメージの外の `tools/train/zero` のuv環境（onnxruntime-gpu 1.28.0、tensorrt-cu13 10.14.1.48、PyTorch 2.13.0、CUDA 13.4）で測り、次にコンテナイメージ`minase-zero:dev`の中で同じコマンドを実行した。
10ブロック128チャネルのTensorRT FP16は、イメージの中でバッチ64から512の順に毎秒23,800、25,666、27,466、28,233評価であり、外の値と0.2%以内で一致した。
イメージの中の実行で`--verbose`により出したTensorRTの詳細ログには、`trt_fp16_enable: 1`、`FP16 mode is enabled`、および`ampere_fp16_s16816gemm`系のカーネルの選択が記録されており、FP16で動いていることを設計書の求める方法で確かめた（ログは`data/alphazero-feasibility/bench-image-b10-c128-verbose.log`）。
下の表はイメージの中の値であり、CUDA実行プロバイダの行だけは外の環境で測った。外の環境のTensorRTの値は、10ブロック128チャネルのFP16で28,205、FP32で11,545、6ブロック96チャネルで38,814、15ブロック192チャネルで12,817（いずれもバッチ512）であり、イメージの中の値と3%以内で一致する。
ネットはランダム初期化で、`python -m minase_zero.export` でONNXへ出力し、`python -m minase_zero.bench --provider tensorrt --batches 64,128,256,512` でウォームアップ20回の後に100回の推論を測った。
GPUメモリは `nvidia-smi` の使用量であり、計測前の基準値は53 MiBである。

| ネット | 実行プロバイダ | バッチ64 | バッチ128 | バッチ256 | バッチ512 | GPUメモリ（バッチ512） |
|---|---|---|---|---|---|---|
| 10ブロック128チャネル | TensorRT FP16 | 23,800 | 25,666 | 27,466 | 28,233 | 943 MiB |
| 10ブロック128チャネル | TensorRT FP32 | 10,939 | 11,350 | 11,590 | 11,846 | 977 MiB |
| 10ブロック128チャネル | CUDA（FP32、イメージの外） | 6,261 | 7,856 | 8,499 | 8,825 | 1,239 MiB |
| 6ブロック96チャネル | TensorRT FP16 | 34,755 | 37,634 | 39,532 | 40,015 | 935 MiB |
| 15ブロック192チャネル | TensorRT FP16 | 11,633 | 12,457 | 12,358 | 12,812 | 961 MiB |

値は毎秒の評価局面数である。
FP16の設定を外すと10ブロック128チャネルの速度が2.4分の1に落ち、CUDA実行プロバイダはさらに遅くTensorRT FP16の3.2分の1なので、FP16の設定は有効に働いている（設計書が求めるTensorRTの詳細ログによる確認は、イメージの中の計測で行う）。
バッチ64から512への増加で速度は2割弱しか上がらず、バッチ64でも最大値の85%に達する。
`nvidia-smi` の使用量にはTensorRTの作業領域とCUDAのコンテキストが含まれ、ネットの大きさによる差は数十MiBに留まる。

### 学習の速度（作業機）

学習器 `python -m minase_zero.train` を、24局6,514局面の見本MNZT（300ノードの自己対局、`data/alphazero-feasibility/step.mnzt`）に対して作業機のGPUで試走し、学習の処理速度を測った。
条件は10ブロック128チャネル、バッチ1,024、単精度（混合精度なし）、SGD、データ読み込みのワーカー4、イメージの外のuv環境である。

| 項目 | 値 |
|---|---|
| 学習の処理速度（バッチ1,024） | 毎秒約3,070局面（40ステップの中央値3,067、最大3,078） |
| 1ステップの時間 | 約0.33秒 |

この速度では、学習窓の最大幅である4サイクル分400万局面を1回読む学習は約22分、SLの5,000万局面を2エポック読む学習は約9時間になる。
推論（TensorRT FP16で毎秒28,000評価）に対して学習は約9分の1の速さであり、順伝播と逆伝播を単精度で行うためである。
混合精度の導入で2倍前後の短縮が見込めるが、設計書の初版の範囲外とし、必要になった時点で測る。

## 第2項　1シミュレーションあたりのCPUの費用

使い捨ての試作（scratchpadに置き、リポジトリには入れない。mimallocとLTOはエンジンと同じ設定）で、1スレッドの1シミュレーションあたりの時間を測った。
1シミュレーションは、初期局面から8〜12手進めた100局面を根とし、深さ4まで各段で合法手を生成して擬似PUCTで1手を選び、`make_move_unchecked`で進め、葉で合法手生成と95面の入力の符号化を行い、`unmake_move`で戻して経路の訪問回数とQを更新する操作である。
30万シミュレーションを性能コア1つ（`taskset -c 2`）に固定して3回測った。機械は他の負荷のない状態（ロードアベレージ1.2）だった。

| 区間 | 1シミュレーションあたり（ns、3回の範囲） |
|---|---|
| 合計 | 4,993〜5,074 |
| 合法手生成（5回） | 3,692〜3,744 |
| 着手の適用と戻し（4手） | 141〜144 |
| 入力の符号化 | 575〜592 |
| 選択 | 525〜536 |
| 逆伝播 | 57〜59 |
| 合法手生成1回あたり | 738〜749 |

実時間（ループ全体を回数で割った値）は5,017〜5,099 nsで、区間の和と1%以内で一致する。
設計書の定義（合法手生成は葉の1回だけ。展開済みの節点は子の列を保持する）に換算すると、合計から葉以外の4回分を引いた2,040〜2,079 nsになる。
葉の平均合法手数は48.3であり、教師データの平均73.6より少ないので、中盤では合法手生成の費用が1.5倍程度まで増え得る。
これを織り込んでも1シミュレーションあたりのCPUの費用は3 µs前後、1スレッドで毎秒30万シミュレーション程度であり、GPUの推論速度（第1項、毎秒数千〜数万評価の見込み）より1桁以上速い。
したがってRLの生成の律速はGPUであり、CPUのコア数は数本で足りる見込みである。

## 第3項　対局長と合法手数の分布

### 生成記録から読める値

2026年10月3日に生成した教師（`data/gen3/generate-1100000.log` から `generate-1500000.log` までの5件、コミット44ae7cb、10万ノード、乱択手なし、手数上限4,000）の集計行は次のとおりである。

| 項目 | 値 |
|---|---|
| 対局数 | 37,500 |
| 手数上限4,000に達して除いた対局 | 1,194（3.2%） |
| 平均手数（上限に達した対局を含む） | 603〜628 |
| 詰みによる終局 | 32,466（86.6%） |
| 反復による勝敗 | 2,396 |
| 反復による引き分け | 1,264 |
| 駒枯れによる勝敗と引き分け | 70 |
| 王駒の捕獲 | 110 |

手数上限4,000に達した対局が3.2%あるので、対局長の99パーセンタイルは4,000以上である。
設計書は、強化学習の手数の上限を「対局長の分布の99パーセンタイル以上」と定めているが、この分布ではその規則が上限を4,000以上に置くことになり、上限に達した対局を学習から除く設計と合わせると、生成時間の相当な割合を除かれる対局に費やすことになる。
ヒストグラムとパーセンタイルの詳細は、下の「分布の計測」で確定し、上限の決め方は設計書の改訂で扱う。

### 分布の計測

同じ5件の教師データ（`data/gen3/generated-1100000.bin` から `generated-1500000.bin`、計15,150,946局面）を、使い捨ての集計ツール（scratchpadに置き、リポジトリには入れない）で数えた。
対局長は、ファイルと対局番号の組ごとに記録された最大の手数であり、MNSDが戦術的な局面と詰みの帯の局面を記録しないため、実際の対局長の下界である。
手数上限に達して除かれた1,194局は教師データに含まれないので、この分布にも含まれない。

| 対局長（下界） | 値 |
|---|---|
| 局数 | 36,195 |
| 平均 | 499 |
| 50パーセンタイル | 414 |
| 90パーセンタイル | 708 |
| 95パーセンタイル | 989 |
| 99パーセンタイル | 2,633 |
| 99.9パーセンタイル | 3,810 |
| 最大 | 3,989 |

分布は300〜450手に山があり、1,000手を超える裾が全体の約5%、上限到達の3.2%を合わせると約8%の対局が1,000手を超える。
2,000手の対局1局は400手の対局5局分の生成時間を使うので、上限の置き方が生成の費用に直接響く。

合法手数は20件ごとに1件を抽出した757,548局面について、規則セット`engine-default`で数えた。

| 合法手数 | 値 |
|---|---|
| 平均 | 73.6 |
| 50パーセンタイル | 76 |
| 90パーセンタイル | 109 |
| 99パーセンタイル | 133 |
| 最大 | 207 |

設計書の「中将棋の合法手は1局面で100手を超えることが多い」と「合法手が平均300手」という見積もりはどちらも過大であり、平均は約74手、100手を超える局面は約18%である。
MNZTの1局面は、方策の組4バイト×74手に局面の表168バイトを加えて約0.5 KBになり、RLの1サイクル100万局面で約0.5 GB、100サイクルで約50 GBとなる（設計書の見積もり130 GBの約4割）。
Gumbel方式の候補数m＝16は、平均74手の約2割に当たる。

## 第4項　教師生成の速度

現行の生成器の速度は、新たに測らず、2026年10月3日の生成記録で確定する。
`data/gen3/generate-1500000.log`（コミット44ae7cb、`minase data selfplay generate`、10万ノード、同時対局数16、置換表16 MB、規則`L0,P0,R1,E0`）の`searched_positions_per_second`は369.97であり、同じ条件の5件の記録では311〜370の範囲にある。
教師5,000万局面の生成には、毎秒370局面で約37.5時間（約1.6日）、毎秒311局面なら約44.7時間（約1.9日）を要する。
設計書の見込み（約1.3日）より長く、同時対局数を19に上げてもCPUの物理コア数（20）の制約から1.4日程度が下限である。

## フェーズ1の付随する実測

ortの依存を加えたコミットで、`cargo build --release --bin minase`のバイナリは5.1 MB（master）から19.5 MBへ増えた。
増分のうち約14 MBは埋め込んだ10ブロック128チャネルのONNXであり、ortのコード自体の増分は約0.4 MBである。
`ORT_DYLIB_PATH`を設定しない環境でもビルドは通り、`--search mcts`で`isready`を送ると専用のエラーを出して終了する。
1.88のツールチェーンでは`cargo +1.88 check -p minase --lib --bins`が通る。`--all-targets`は、本マイルストーン以前から存在する`search/alphabeta/tests/time.rs`の一時値の寿命の問題で1.88では通らない。

ランダム初期化の10ブロック128チャネルのネットを埋め込んだ`--search mcts`のエンジンを、コンテナイメージの中でビルドしてUSIで起動し、初期局面から`go nodes 3000`を実行した。
TensorRT FP16（`NnBatchSize`64）では3,000シミュレーションを164 msで終え（毎秒約18,200シミュレーション）、CPU実行プロバイダでは2,085シミュレーションの時点で毎秒222シミュレーションだった。
どちらも合法な`bestmove`を返し、`info string`でノード数の定義を1回告げた。
TensorRTの推論速度（バッチ512で毎秒28,000評価）に対して探索は約65%の速度であり、バッチ64の推論速度（毎秒23,800評価）に対しては約76%である。
GPUのない環境でCPU実行プロバイダを使う対局は、速度が2桁落ちるので診断にだけ使える。

対局ハーネスの煙試験として、同じコンテナの中で`minase match run`に、起動コマンド形式で指定した`--search mcts`のエンジン（TensorRT、1手800シミュレーション）と乱択エンジン`random`を、固定2ペア（シード20261009、手数上限1,200）で対局させた。
4局とも王駒の捕獲で終局し、`engine_failures`（不正着手、クラッシュ、タイムアウト、時間切れ、拒否着手）はすべて0件、手数上限への到達も0件で、所要時間は6.8秒だった。
ランダム初期化のネットでも探索が王駒の捕獲を見つけるので全勝したが、この結果は強さの指標ではなく、USIの対局進行と推論の経路が通ることの確認である。

## 一次見積もり

### 作業機のGPUで生成する場合の参考値

設計書の式「1日あたりの学習局面数 ＝ min(GPUの毎秒の評価数, CPUの1スレッドの毎秒のシミュレーション数 × スレッド数) × 86,400 ÷ 32」に、作業機の値を入れる。
10ブロック128チャネルのGPUの毎秒の評価数は28,233（バッチ512、イメージの中）、CPUは1スレッドで毎秒約30万シミュレーションなので、律速はGPUである。

| 項目 | 10ブロック128チャネル | 6ブロック96チャネル |
|---|---|---|
| 1日あたりの学習局面数 | 約7,600万 | 約1億500万 |
| 100万局面の生成時間 | 約19分 | 約14分 |
| 進捗測定（200ペア、1手800シミュレーション、1局500手と仮定）の時間 | 約1.6時間 | 約1.1時間 |
| 同、サイクルあたり（10分の1） | 約9分 | 約7分 |

学習時間は、上の「学習の速度」の値から、学習窓の最大幅4サイクル分400万局面を1回読む場合で約22分である。
したがって作業機では、生成約19分、学習約22分、進捗測定約9分を合わせて1サイクル約50分となり、設計書の上限8時間に対して約10倍の余裕がある。
バッチの充填率、NNキャッシュ、木の再利用、記録の書き込み、および上限到達で除く対局は数えていない。
この値は、RTX 3060 Tiより速いレンタル機ではさらに短くなる一方、作業機のGPUそのものでもRLを1日に20サイクル以上回せる速度であることを示す。
作業機でRLを回す場合はαβ探索の測定とGPUと数コアを奪い合うが、レンタル機の費用と転送の手間は要らなくなる。
レンタル機を使うかどうかの判断材料として、レンタル機の実測の前にこの参考値を残す。

### レンタル機

## 結論

作業機（RTX 3060 Ti）の実測では、10ブロック128チャネルの強化学習の1サイクルは生成約19分、学習約22分、進捗測定約9分の合計約50分と見積もられ、設計書のフェーズ0の完了条件のうち所要時間の条件（8時間以内）を作業機自身が満たす。
費用の条件（100サイクルで1万8,000円以内）は、RTX 3060 Ti以上の性能を持つ候補のレンタル機なら1サイクル1時間以内となり、時間単価0.5ドル以下の機種では100サイクルで約7,500円以下に収まる見込みであるため、レンタル機の実測は実現性ではなく機種と事業者の選択を決めるものになる。
同時に、この見積もりは作業機のGPUだけで強化学習を回せることも示しており、レンタル機を使うかどうかは、作業機のαβ探索の測定との資源の競合と、レンタルの費用と手間を比べて利用者が決める。
いずれの場合も、律速はGPUの推論であり、CPUは数コアで足りる。

# 推論の転送を減らす候補の、自己対局の生成の速さ

## 目的

[推論の転送を減らす設計書](../../plans/archived/alphazero-inference-transfer.md)のフェーズ5のうち、借りた機械で行う測定の記録である。
設計書は、ニューラルネットワーク（以下、ネット）の推論でホストとGPUの間の転送を減らす4つの候補を、共通の準備のコミットSの上に1つずつ積み重ねる。
候補は、出力をピン留めメモリで受け取るA、入力をuint8で送るB、方策をFP16で返すC、および方策の出力を35,856ラベルから固定の表で16,108ラベルへ詰めるDである。
以下では、SとA〜Dを合わせて5つの変種と呼ぶ。
この測定では、5つの変種の自己対局の生成の速さを、順番を1周ごとに逆にしながら繰り返し測り、各候補を積み重ねた列の直前の変種（以下、相手）と比べて採否を決めた。
採否は、ホストとGPUの間の帯域が狭く、転送が生成を律速していると考えられる機械（以下、遅い機械）で決める。
帯域の広い機械（以下、速い機械）と、GPUを1枚だけ積んだ機械では、採った候補が生成を遅くしないことを確かめる。
作業機で行った出力の照合などの確認は、[作業機での確認の記録](alphazero-inference-transfer-workstation.md)にある。

## コマンドライン

測定日は2026年11月11日である。
vast.aiで、RTX 4090を4枚積んだ機械を3台と、RTX PRO 6000 Blackwell Server Editionを1枚積んだ機械を1台借りた。

| 役割 | インスタンス | 出品 | CPU | 出品の`pcie_bw` | 1時間の料金 | 稼働 |
|---|---|---|---|---|---|---|
| 遅い機械 | 60152887 | 59828256 | AMD EPYC 7543の仮想マシン（cgroupの割当て34 CPU） | 10.5 GB/s | 2.054米ドル | 2.59時間 |
| 速い機械 | 60155802 | 48665697 | AMD EPYC 7663（cgroupの割当て107 CPU） | 20.9 GB/s | 2.034米ドル | 1.37時間 |
| 使えなかった機械 | 60152886 | 59863168 | Intel Xeon Gold 6330（cgroupの割当て53 CPU） | 24.1 GB/s | 1.978米ドル | 0.62時間 |
| GPU 1枚の機械 | 60166474 | 53838806 | Intel Xeon Platinum 8559C（cgroupの割当て15 CPU） | 52.9 GB/s | 1.561米ドル | 0.58時間 |

遅い機械は、[複数GPU化のvast.aiの測定](../alphazero-multi-gpu/alphazero-multi-gpu-vast.md)の機械Hと同じ出品であり、速い機械は同じ測定の機械BとCと同じ出品である。
`pcie_bw`は、vast.aiが出品ごとに測ってCPUとGPUの間の帯域として載せる値である。
GPU 1枚の機械のGPUは、ColabのG4と同じ機種である。設計書は起案のときにこの確認をColabのG4で行うとしていたが、測定の日にG4の割り当てが「Service Unavailable」で断られたので、開発者の決定で、同じGPUを積んだvast.aiの機械に替えた。
3台目は、4枚のGPUのうち1枚だけメモリの表示が違い（49,140 MiBが3枚と46,068 MiBが1枚）、minaseが「同じ機種と同じメモリのGPUであること」の検査で起動を拒んだので、測定に使わずに削除した。

各機械には、5つの変種のコミットの書庫、変種ごとに書き出した初期ネット、作業機で作った照合の参照（学習器が同じネットで計算した出力）、および変種の一覧を`/workspace/in/`へ送った。
初期ネットは、[2回目の強化学習の実行](../../plans/alphazero-rl-2.md)がサイクル1の生成に使う、ランダム初期化の20ブロック256チャネルのネットである。
導入は[vast-setup.sh](../alphazero-multi-gpu/vast-setup.sh)で行い、続けて[vast-measure.sh](vast-measure.sh)のサブコマンドを次の順に実行した。

```console
bash vast-measure.sh build S A B C D
bash vast-measure.sh bandwidth 4
bash vast-measure.sh check logits S A B
bash vast-measure.sh check fp16-logits C D
bash vast-measure.sh warm 4
bash vast-measure.sh run 4 0 5
bash vast-measure.sh summarize 0 5
```

`bandwidth`は、[copy-bandwidth.py](../alphazero-multi-gpu/copy-bandwidth.py)で、バッチ128の方策の出力と同じ大きさ（約18 MB）の領域の転送を、GPUを1枚ずつ使う場合と4枚を同時に使う場合で測る。
`check`は、各変種の`minase dev nn-eval`を、CPUとTensorRTのそれぞれでバッチの大きさ7で実行し、その出力を作業機で作った参照と比べる。
`warm`は、各変種で16局を生成し、最大バッチ128のTensorRTのエンジンを作る。
`run`は、[measure-generation.py](measure-generation.py)で、次の生成を5周測る。1、3、5周目（スクリプトの周の番号は0、2、4）はS、A、B、C、Dの順、2、4周目は逆の順である。

```console
minase data zero-selfplay --output-dir <出力先> --nn-model <変種のネット> --nn-backend tensorrt \
  --generation-commit <変種のコミット> --seed 9100000000 --start-position shuffled-setup --games 4096 \
  --target-positions 1000000000 --chunk-games 256 --simulations 32 --playthrough-percent 100 \
  --threads 16 --devices 4 --games-per-thread 128
```

生成の速さは、訓練局面の数を、生成器が自分で測った経過時間で割った値である。
`summarize`は、変種ごとに5回の中央値と、最大と最小の差を中央値で割った値（以下、幅）を求め、候補の中央値を相手の中央値で割って1を引いた値（以下、増分）を、候補と相手の幅の大きいほうと比べる。

測定の途中で、測定のスクリプトを1回直した。
遅い機械の1周目で、変種Bの生成器が、全対局を生成して集計を書いた後、プロセスの終了処理で異常終了し（終了コード−6）、スクリプトがその回を記録せずに止まったからである。
生成器が測る経過時間は終了処理を含まないので、集計がすべて揃った回は終了コードとともに記録する形に改め（コミット`dbc117b0`）、2台とも1周目から測り直した。
本書の値は、すべて測り直した後のものである。

GPU 1枚の機械では、SとDだけを同じ手順で測った。
GPUの枚数は1、生成のスレッドは4、周回は3周である（周回の数は開発者の決定による）。

```console
bash vast-measure.sh build S D
bash vast-measure.sh bandwidth 1
bash vast-measure.sh check logits S
bash vast-measure.sh check fp16-logits D
bash vast-measure.sh warm 1
bash vast-measure.sh run 1 0 3
bash vast-measure.sh summarize 0 3
```

## エンジン

| 変種 | コミット | 内容 | 初期ネットのONNXのSHA-256 |
|---|---|---|---|
| S | `353ef0ff` | チェックポイントからONNXを書き出し直すサブコマンドと、測定のスクリプト | `8be01e2e…` |
| A | `0b87abe7` | TensorRTとCUDAで、出力をピン留めメモリで受け取る | `8be01e2e…`（Sと同じファイル） |
| B | `2f7b02f4` | 入力をuint8で送り、グラフの中でfloat32へ変換する | `94e589da…` |
| C | `15b0f1d1` | 方策をFP16で返す | `7b764285…` |
| D | `43441d00` | 方策を16,108ラベルへ詰める | `7a9f3ec7…` |

ネットは、上の初期ネットを、各変種のコミットの学習器で作業機のチェックポイントから書き出し直したものである。
測定のスクリプトと`vast-measure.sh`は、4枚の機械では、導入にコミット`30bc5239`のものを使い、測り直しからは`measure-generation.py`だけをコミット`dbc117b0`のものに差し替えた。GPU 1枚の機械では、初めからコミット`dbc117b0`のものを使った。

## 環境

どの機械も、コンテナのイメージは`nvidia/cuda:13.0.3-base-ubuntu24.04`で、PyTorch 2.11.0（CUDA 13.0）、ONNX Runtime 1.31.1、TensorRT 10.14.1、および`ort` 2.0.0-rc.13を使った。
NVIDIAのドライバは、遅い機械が610.57.04、速い機械が580.159.03、GPU 1枚の機械が595.71.05である。

## 結果

### 転送の帯域

次の表は、GPU 1枚あたりの帯域（GB/s）の最小と最大である。

| 転送 | 遅い機械、1枚ずつ | 遅い機械、4枚で同時 | 速い機械、1枚ずつ | 速い機械、4枚で同時 |
|---|---|---|---|---|
| ページング可能なメモリ、GPU→ホスト | 5.8〜6.3 | 1.8〜2.0 | 11.8〜12.4 | 4.2〜12.1 |
| ページング可能なメモリ、ホスト→GPU | 8.9〜9.7 | 2.6〜3.6 | 19.8〜20.4 | 9.6〜20.2 |
| ピン留めメモリ、GPU→ホスト | 16.6〜18.2 | 5.7〜9.9 | 25.7〜26.0 | 20.0〜26.0 |
| ピン留めメモリ、ホスト→GPU | 13.0〜13.6 | 4.6〜8.2 | 25.8〜25.9 | 17.5〜25.9 |

ページング可能なメモリを通るGPU→ホストの転送は、4枚で同時に使うと、遅い機械が合計で約7.8 GB/s、速い機械が合計で約26.6 GB/sであった。
遅い機械の値は、複数GPU化の測定の機械Hの値（合計で約7 GB/s）と同じ水準である。
これで、設計書が遅い機械に求める2つの条件のうち、帯域が速い機械を下回ることを確かめた。
もう1つの条件であるSの生成が速い機械より遅いことは、後の「遅い機械の生成の速さ」と「速い機械の生成の速さ」の節の値（毎秒426局面と1,171局面）で確かめた。

GPU 1枚の機械の帯域は、ページング可能なメモリのGPU→ホストが17.2 GB/s、ホスト→GPUが22.6 GB/s、ピン留めメモリのGPU→ホストが55.0 GB/s、ホスト→GPUが53.2 GB/sであった。

生データは[alphazero-inference-transfer-generation-speed/](alphazero-inference-transfer-generation-speed/)の`slow-copy-bandwidth.txt`、`fast-copy-bandwidth.txt`、および`single-gpu-copy-bandwidth.txt`にある。

### 出力の確認

4枚の2台では5つの変種のすべてで、GPU 1枚の機械ではSとDで、CPUとTensorRTのバッチの大きさ7の出力が照合の許容誤差に収まった。
CPUのlogitの差の最大は、S、A、Bが5.1×10⁻⁷以下、CとDが1.2×10⁻⁴であり、TensorRTの確率の差の最大は3.3×10⁻⁵以下、価値の差の最大は2.6×10⁻⁴以下であった。
`warm`の16局の生成は、2台とも5つの変種のすべてが4枚のGPUで終わった。
これにより、GPUが1枚の作業機では確かめられなかった機器番号1以上のGPUでも、ピン留めメモリへの出力の結び付けが動くことを確かめた。

生データは`slow-check.tsv`、`fast-check.tsv`、`single-gpu-check.tsv`、`slow-warm.jsonl`、`fast-warm.jsonl`、および`single-gpu-warm.jsonl`にある。

### 遅い機械の生成の速さ

5つの変種を5周ずつ測った25回の生成は、どれも4,096局で、手数上限で破棄した対局は0局であった。
訓練局面はS、A、B、Cが150,461、Dが150,148であった。
Dの対局が違うのは、ネットの入力と出力の型と形を変える候補では、ネットごとに作るTensorRTのエンジンが変わり、推論の値が照合の許容誤差の中で変わるからである。設計書は、そのような候補に対局の一致を求めていない。
表の値は、1秒あたりの訓練局面数である。

| 変種 | 1周目 | 2周目 | 3周目 | 4周目 | 5周目 | 中央値 | 幅 |
|---|---|---|---|---|---|---|---|
| S | 417.5 | 425.7 | 419.5 | 431.7 | 428.7 | 425.7 | 3.3% |
| A | 597.5 | 592.8 | 583.7 | 609.0 | 594.4 | 594.4 | 4.3% |
| B | 1,016.2 | 981.7 | 993.2 | 1,007.8 | 1,005.4 | 1,005.4 | 3.4% |
| C | 1,241.9 | 1,228.3 | 1,246.5 | 1,214.0 | 1,225.9 | 1,228.3 | 2.7% |
| D | 1,311.0 | 1,305.9 | 1,307.7 | 1,264.0 | 1,276.8 | 1,305.9 | 3.6% |

各候補の増分は、次のとおり、どれも候補と相手の幅の大きいほうを超えた。

| 候補 | 相手 | 増分 | 幅の大きいほう | 判定 |
|---|---|---|---|---|
| A | S | +39.6% | 4.3% | 採る |
| B | A | +69.2% | 4.3% | 採る |
| C | B | +22.2% | 3.4% | 採る |
| D | C | +6.3% | 3.6% | 採る |

4つを積んだDの生成の速さは、Sの約3.07倍である。
増分が最も大きいのは入力をuint8で送るBで、方策の出力だけでなく、入力の転送もこの機械の生成を律速していたことになる。

### 速い機械の生成の速さ

5つの変種を5周ずつ測った25回の生成は、どれも4,096局、訓練局面150,461で、手数上限で破棄した対局は0局であった。
表の値は、1秒あたりの訓練局面数である。

| 変種 | 1周目 | 2周目 | 3周目 | 4周目 | 5周目 | 中央値 | 幅 |
|---|---|---|---|---|---|---|---|
| S | 1,082.4 | 1,200.8 | 1,173.0 | 1,158.5 | 1,171.0 | 1,171.0 | 10.1% |
| A | 1,193.4 | 1,249.3 | 1,274.8 | 1,239.9 | 1,278.9 | 1,249.3 | 6.8% |
| B | 1,401.2 | 1,383.0 | 1,405.8 | 1,356.4 | 1,398.3 | 1,398.3 | 3.5% |
| C | 1,450.7 | 1,430.6 | 1,440.3 | 1,417.7 | 1,435.4 | 1,435.4 | 2.3% |
| D | 1,385.9 | 1,432.6 | 1,437.4 | 1,419.0 | 1,424.3 | 1,424.3 | 3.6% |

| 候補 | 相手 | 増分 | 相手の幅 | 相手の幅を超えて遅いか |
|---|---|---|---|---|
| A | S | +6.7% | 10.1% | いいえ |
| B | A | +11.9% | 6.8% | いいえ |
| C | B | +2.6% | 3.5% | いいえ |
| D | C | −0.8% | 2.3% | いいえ |

速い機械で設計書が求めるのは、採った候補が相手の幅を超えて遅くならないこと、つまり負の増分の大きさが相手の幅を超えないことである。
負の増分はDの−0.8%だけで、相手のCの幅2.3%の内側なので、4つの候補のどれもこの条件を満たした。
4つを積んだDの生成の速さは、Sの約1.22倍である。
速い機械でも、AからCまでは生成が速くなっており、転送の時間は速い機械でも無視できる大きさではなかった。

### GPU 1枚の機械の生成の速さ

6回の生成は、どれも4,096局で、手数上限で破棄した対局は0局であった。
訓練局面はSが151,589、Dが152,409であった。
表の値は、1秒あたりの訓練局面数である。

| 変種 | 1周目 | 2周目 | 3周目 | 中央値 | 幅 |
|---|---|---|---|---|---|
| S | 580.9 | 582.3 | 579.7 | 580.9 | 0.5% |
| D | 710.5 | 711.8 | 711.8 | 711.8 | 0.2% |

Dの中央値は、Sの中央値より22.5%高かった。
設計書がこの機械に求めるのは、最終のコミットの中央値がSの中央値から幅を超えて下がらないことであり、Dはこの条件を満たした。
4,096局の生成の時間は、約261秒から約214秒へ、約18%短くなった。

生データは`slow-runs.jsonl`、`fast-runs.jsonl`、`single-gpu-runs.jsonl`、`slow-summary.json`、`fast-summary.json`、および`single-gpu-summary.json`にある。

### 終了処理での異常終了

遅い機械とGPU 1枚の機械では、プロセスの終了処理で`corrupted double-linked list`を出して異常終了する回があった。
どの回も、出力や集計をすべて書き終えた後に起きている。

| 機械 | 処理 | 回数 | 異常終了した回 |
|---|---|---|---|
| 遅い機械 | TensorRTのエンジンを新しく作った`nn-eval` | 4回（S、B、C、D。AはSと同じネットなので作らない） | 2回（S、B） |
| 遅い機械 | 5周の生成 | 25回 | 9回（S 2回、A 0回、B 3回、C 2回、D 2回） |
| GPU 1枚の機械 | 3周の生成 | 6回 | 2回（S 2回、D 0回） |

速い機械では、同じ処理で1回も起きなかった。GPU 1枚の機械の`nn-eval`でも起きなかった。
変種Sはmasterと同じ推論のコードなので、この異常終了は候補の変更が原因ではなく、変種による回数の差も、この回数の範囲では見分けられない。
ONNX Runtime 1.28.3で見られた終了処理の異常終了は、1.31.1では10回中0回であったが（[ONNX Runtimeの版のADR](../../adr/load-onnx-runtime-1-31-1-through-ort-rc13-for-zero-inference.md)）、今回の遅い機械では1.31.1でも起きた。
起きた2台のNVIDIAのドライバは610.57.04と595.71.05、起きなかった速い機械は580.159.03である。ただし、作業機（RTX 3060 Ti、ドライバ615.78.08）では、同じ日の確認で、エンジンを新しく作った`nn-eval`の36回と生成の18回のどれも正常に終わったので、ドライバの版だけでは説明できない。原因は調べていない。

`nn-eval`の異常終了のログは`slow-nn-eval-aborts.txt`に、生成の終了コードは`slow-runs.jsonl`と`single-gpu-runs.jsonl`の`exit_code`の欄にある。

### 費用

4台の費用は、遅い機械が5.31米ドル、速い機械が2.79米ドル、使えなかった機械が1.23米ドル、GPU 1枚の機械が0.90米ドルで、転送料を含めた口座の残高の減少は10.83米ドルであった。
遅い機械では、GitHubからのONNX Runtimeの取得が毎秒約80 KBしか出なかったので、作業機から同じ書庫を送ってSHA-256を照合し、導入をやり直した。

## 結論

遅い機械で、A、B、C、Dの4つの候補のすべてが、直前のコミットに対する増分で測定の幅を超えた。
速い機械では、どの候補も相手の幅を超えて遅くならなかった。
GPU 1枚の機械では、4つを積んだDがSより22.5%速かった。
4つの候補は、すべて採る。
4つを積むと、生成の速さは遅い機械で約3.07倍（毎秒426局面から1,306局面）、速い機械で約1.22倍（毎秒1,171局面から1,424局面）になり、2台の差は約2.75倍から約1.09倍に縮まった。
複数GPU化の測定で機械H（今回の遅い機械と同じ出品）の生成が遅かった原因はホストとGPUの間の転送であるという仮説は、この結果で裏づけられた。

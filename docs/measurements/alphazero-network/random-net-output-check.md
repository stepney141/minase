# ランダム初期化のネットの出力の照合

## 目的

[ネットの入出力と推論の設計書](../../plans/archived/alphazero-network.md)のフェーズ2として、ランダムに初期化した10ブロック128チャネルのネットについて、PyTorchの出力を基準に、ONNX RuntimeのCPU、TensorRTのFP16、およびCUDAの出力がバッチの大きさ1、7、および256で一致するかを作業機で確かめる。
あわせて、TensorRTのエンジンのキャッシュの作成と読み込み、および各実行プロバイダでのプロセスの終了処理を確かめる。

## コマンドライン

```console
# <wt> は alphazero-network の worktree（コミット 982d772d）、<out-dir> は出力先
cargo build --release --bin minase
bash docs/measurements/alphazero-network/random-net-output-check/run.sh <wt> <out-dir>
```

`run.sh`は、`tools/train/zero/env.sh`で環境を設定し、`feasibility/make_nets.py`でネットを作り、固定局面集の288局面を`minase dev nn-eval`で推論する。
推論は、CPUではバッチ1、7、256で各1回、TensorRTではバッチ1、7、256でエンジンの作成と読み込みの各1回、CUDAではバッチ7で4回行う。
続いて`nn_torch_reference.py`でPyTorchの出力を求め、`nn_compare.py`で各出力をPyTorchの出力と照合する。
許容誤差は、CPUが1×10⁻⁴、TensorRTのFP16とCUDAが1×10⁻²である。
標準出力は同じディレクトリの`run.log`にある。

## エンジン

minaseはブランチ`alphazero-network`のコミット982d772dからビルドした。
規則セットは`engine-default`（L0＋P0＋R1＋E0）で、合法手は固定局面集の生成と同じ`MoveGenerator`の順に並べる。
ネットは`make_nets.py`がシード0で作る`zero-b10c128.onnx`（重み3,462,524個、SHA-256 `61a62a62…01600`）であり、[実現性の実測](../alphazero-environment/alphazero-feasibility.md)で使ったファイルとバイト単位で一致した。

## 結果

PyTorchの出力との照合の結果は次のとおりである。
差は、288局面の合法手のlogitと価値についての差の絶対値の最大である。
最大のlogitを持つ手を、以下では最大の手と呼ぶ。
最大の手の不一致は、PyTorchの最大の手と候補の最大の手が異なる局面の数である。

| 候補 | 許容誤差 | logitの差の最大 | 価値の差の最大 | 最大の手の不一致 | 判定 |
|---|---|---|---|---|---|
| CPU、バッチ1 | 1×10⁻⁴ | 1.7×10⁻⁷ | 8.8×10⁻⁸ | 0 | 合格 |
| CPU、バッチ7 | 1×10⁻⁴ | 1.6×10⁻⁷ | 8.8×10⁻⁸ | 0 | 合格 |
| CPU、バッチ256 | 1×10⁻⁴ | 1.6×10⁻⁷ | 8.8×10⁻⁸ | 0 | 合格 |
| TensorRT FP16、バッチ1 | 1×10⁻² | 4.8×10⁻⁴ | 2.5×10⁻⁴ | 0 | 合格 |
| TensorRT FP16、バッチ7 | 1×10⁻² | 3.5×10⁻⁴ | 2.4×10⁻⁴ | 2 | 合格 |
| TensorRT FP16、バッチ256 | 1×10⁻² | 4.4×10⁻⁴ | 2.5×10⁻⁴ | 2 | 合格 |
| CUDA、バッチ7 | 1×10⁻² | 6.1×10⁻⁵ | 1.7×10⁻⁶ | 0 | 合格 |

TensorRTのエンジンをキャッシュから読んだ3回の出力は、作成した回の出力とバイト単位で一致した。
最大の手が入れ替わった4局面（バッチ7の53番と209番、バッチ256の102番と277番）では、PyTorchの最大のlogitと、候補が最大とした手のPyTorchのlogitの差が、それぞれ6.4×10⁻⁵、3.2×10⁻⁴、1.1×10⁻⁵、および8.2×10⁻⁵であった。
288局面のうち、PyTorchで1位と2位のlogitの差が1×10⁻³未満の局面は27局面あった。

ランダム初期化のネットの出力の散らばりは次のとおりである。
各局面の合法手のlogitの標準偏差は0.046〜0.071、最大と最小の差は0.18以上であった。
各局面で、合法手の列の隣の着手のlogitを読み違えたとすると、差の最大は局面ごとに0.15以上になる。
価値は288局面すべてで0.5155〜0.5186の範囲にあった。

セッションの作成と288局面の推論にかかった時間は次のとおりである。

| 実行プロバイダ | バッチ | セッションの作成 | 推論 |
|---|---|---|---|
| CPU | 1 | 0.06秒 | 0.72秒 |
| CPU | 7 | 0.06秒 | 0.40秒 |
| CPU | 256 | 0.05秒 | 0.15秒 |
| TensorRT（エンジンの作成） | 1 | 7.1秒 | 0.088秒 |
| TensorRT（エンジンの作成） | 7 | 7.6秒 | 0.028秒 |
| TensorRT（エンジンの作成） | 256 | 9.6秒 | 0.020秒 |
| TensorRT（キャッシュの読み込み） | 1 | 0.36秒 | 0.090秒 |
| TensorRT（キャッシュの読み込み） | 7 | 0.40秒 | 0.028秒 |
| TensorRT（キャッシュの読み込み） | 256 | 0.41秒 | 0.020秒 |
| CUDA | 7 | 0.18〜0.20秒 | 0.27秒 |

キャッシュの親ディレクトリの下には、最大バッチ1、7、256に対応する3つのディレクトリができた。
3つのディレクトリのエンジンのファイル名は、どれも`TensorrtExecutionProvider_TRTKernel_graph_main_graph_1514624461933310472_0_0_fp16_sm86.engine`で同じであった。

プロセスの終了コードは、CPUの3回とTensorRTの6回がすべて0であった。
CUDAは4回中2回が終了コード134（SIGABRT）で終わり、標準エラーにglibcの`corrupted double-linked list`が出た。
異常終了した回も、出力のJSONは288局面すべてを書き終えていた。
`coredumpctl`で見たスタックによれば、異常終了は、`exit`から呼ばれた`libcuda.so.1`の終了処理が呼んだglibcの`free`の中で起きていた。
本記録の前に同じネットと同じバイナリで行った予備の実行では、CUDAの5回のうち2回が同じ形で異常終了し、TensorRTの9回はすべて正常に終了した。
CUDAの予備の実行のうち1回は、glibcのデバッグ用のmalloc（`LD_PRELOAD=/usr/lib/libc_malloc_debug.so.0 MALLOC_CHECK_=3`）を読み込んで行い、異常終了も破壊の検出も起きなかった。
前日に[実現性の実測](../alphazero-environment/alphazero-feasibility.md)の道具`trt_bench`（mimallocを使わない）をCUDAの実行プロバイダで作業機で動かした際のコアダンプにも、同じ`libcuda.so.1`の終了処理のスタックが残っていた。

## 結論

PyTorch、ONNX RuntimeのCPU、TensorRTのFP16、およびCUDAの出力は、すべてのバッチの大きさで許容誤差に収まり、作業機でのTensorRTの推論とエンジンのキャッシュは設計どおりに動いた。
設計書は最大の手がすべての入力で一致することも求めていた。
しかし、各logitの差が許容誤差t以下なら、候補の最大の手の基準のlogitは基準の最大から2t以内に収まるので、この条件は要素ごとの検査に含まれる。
独立の条件として課すと、正しい実装でもほぼ同点の局面で不合格になるだけなので、本測定の結果を見た後に合否の条件から外し、件数と差を報告するだけにした。
FP16の許容誤差1×10⁻²は、隣の着手のlogitとの差（0.15以上）より十分小さいので読み出しのずれを検出できるが、価値の局面間の散らばり（0.003）より大きいので価値のずれは検出できず、価値のずれはCPUの1×10⁻⁴の照合が検出する。
CUDAの実行プロバイダは、ONNX Runtime 1.28.3と作業機の環境で、出力を書き終えた後の終了処理で非決定的に異常終了するので、既定のTensorRTの代わりに使う場合はこの点を前提にする。

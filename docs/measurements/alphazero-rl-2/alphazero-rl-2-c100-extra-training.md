# 2回目の強化学習のサイクル100のネットの追加学習

## 目的

2回目の強化学習の系列`cycles-rl2-az`は、固定の検証用データ（lishogiの人間同士の棋譜811局）の診断で、作った局面の累計が同じ時点の1回目の系列より伸びが遅い（[系列のページ](../../training/alphazero-rl-2/README.md)）。
1回目は1サイクルで新しく作った局面の約3.8倍をリプレイバッファから抽出して学んだが、2回目は先行実装に倣って約1倍しか学んでいない。
2回目は、ネットも10ブロック128チャネルから20ブロック256チャネルへ大きくしている。
そのため、作ったデータの量に比べて学習の量が足りないことが、伸びの遅さの原因である可能性がある。
本書では、新しく自己対局を行わずに、サイクル100のネットに同じリプレイバッファで学習を追加し、強さが上がり診断の値が良くなるかを確かめる。
この実験は、2026年11月17日の利用者の決定で行った。

## コマンドライン

追加学習は、vast.aiで借りた機械で、学習器`minase_zero train`を3回続けて走らせた。
各回の出発点は、1回目がサイクル100のチェックポイント（`cycles-rl2-az/cycle-0100/train/checkpoint.pt`）、2回目と3回目が直前の回のチェックポイントである。
引数は、抽出の数を指定する`--samples`、シード、および出力先を除いて、2回目の系列のサイクル100の学習と同じである。

```bash
uv run --frozen --project /workspace/src/tools/train/zero torchrun --standalone --nproc-per-node 4 -m minase_zero train \
  --init <出発点のcheckpoint.pt> --data-list cycles-rl2-az/cycle-0100/train-data.json \
  --latest-data <サイクル100の20個の教師ファイル> --out-dir experiments/rl2-c100-extra/run-<回>/train \
  --cycle 100 --seed <シード> --batch-size 1024 --micro-batch-size 256 --lr 0.04 --momentum 0.9 \
  --weight-decay 0.0001 --clip-grad-norm 10 --value-lambda 0.333 --precision bf16 --checkpoint-steps 50 \
  --device cuda --replay-threads 26 --trainer-commit 94b3a82726422577c849078869b6d9a4bc9e3eee --samples <抽出の数>
```

リプレイバッファには、サイクル1〜100の訓練局面がT＝90,429,193局面あり、各回の抽出の数とシードは次のとおりである。
3回の合計はTであり、2回目の系列がサイクル100までに学んだ局面の延べ数（同じく90,429,193）と同じだけを追加で学んだことになる。

| 回 | 抽出の数 | 累計の追加量 | シード |
|---|---|---|---|
| 1 | 22,607,298（0.25T） | +25% | 20261701 |
| 2 | 22,607,298（0.25T） | +50% | 20261702 |
| 3 | 45,214,597（0.5T） | +100% | 20261703 |

各回の後に、学習した機械で`minase_zero fixture-eval`を実行して出力の照合の基準を作り、作業機で`check_outputs.py`による出力の照合と、`minase_zero external-eval`による固定の検証用データの診断を行った。
対局は作業機で、定例の測定に使うMCTSを固定した作業ツリー`data/worktrees/alphazero-rl-2-routine`（コミット`8e419486`、以下`$R`）のスクリプトで行った。

```bash
M=8e419486e7cf5c93bbefb4f856bc203f2213cd21
F=$R/docs/measurements/mcts-fixed-opponents/mcts-fixed-opponents-scripts
S=$R/docs/measurements/alphazero-rl-2/alphazero-rl-2-routine-scripts
python3 -I $F/run_match.py alphabeta --harness $R/target/release/minase --mcts-commit $M \
  --net <ネット> --nodes 500 --name <測定名> --seed 2026111811 --pairs 100 --concurrency 4
python3 -I $S/run_rl2_match.py versus --harness $R/target/release/minase --mcts-commit $M \
  --net <追加100%のネット> --baseline-net <サイクル100のネット> --name alphazero-rl-2-c100-extra-r3-vs-c100 \
  --seed 2026111812 --pairs 100
```

固定のαβ探索との対局は、サイクル100のネット（測定名`alphazero-rl-2-c100-extra-base-ab500`）と、3回目の後の追加100%のネット（`alphazero-rl-2-c100-extra-r3-ab500`）で同じシードを使い、同じ開始局面から指させた。
この2つの対局と、2つのネットの直接対局を合わせた3つの対局の実行ディレクトリは、本体のリポジトリの`data/matches/<測定名>.tar.zst`へ圧縮して残した。
固定の相手との対局の集計は[summary.json](alphazero-rl-2-c100-extra-training/summary.json)、各回の学習の要点は[training.json](alphazero-rl-2-c100-extra-training/training.json)、固定の検証用データの診断は同じディレクトリの`validation-run-<回>.json`にある。

## エンジン

学習器は、抽出の数を指定する`--samples`を加えたコミット`94b3a827`（ブランチ`alphazero-rl-2`）である。
`--samples`のほかは、2回目の系列のサイクル100を学習したコミットと計算の内容が同じである。
学習率は0.04のまま変えなかった。最初の250回の更新で学習率を上げるウォームアップは累計の更新数で決まり、追加学習の出発点はすでにその期間を過ぎているので働かない。
学習したネットのSHA-256は、1回目が`913c931a…`、2回目が`9a01a3bb…`、3回目が`55d7be4d…`である。

対局のMCTSは、作業ツリー`$R`の`minase`に`--search mcts`を指定したものであり、1手800シミュレーション、`NnBatchSize`は16、推論はTensorRTのFP16である。
固定のαβ探索はコミット`45d5db54`のminaseと、そのコミットに埋め込まれたNNUEであり、1手500ノード、規則セット`lishogi`、手数の上限4,096手で対局させた（[強さを測る固定の相手の設計書](../../plans/archived/mcts-fixed-opponents.md)）。

## 環境

追加学習は、vast.aiで借りた台湾の機械（RTX 4090を4枚、AMD EPYC 7663、使えるCPUは107個、インスタンス61080134）で、2026年11月17日23時8分から11月18日1時52分（日本時間）に行った。
リプレイバッファの1,869ファイル（3.81 GB）は、zstdで圧縮しながら551秒で送った。
3回の学習は、毎秒13,461〜13,645局面で進み、それぞれ約36分、約35分、約70分かかった。
料金は、口座の残高の減少額で5.82米ドルであった。

評価は、作業機（Intel Core Ultra 7 265KF、NVIDIA GeForce RTX 3060 Ti 8 GB）で、11月18日2時から5時に行った。
作業機は11月17日23時34分にNVIDIAドライバの版が615.78から620.70へ上がっていたので、再起動してから評価した。
ドライバを上げる前に作ったTensorRTのエンジンのキャッシュは、警告が出たので使わずに作り直した。
対局はノード数とシミュレーション回数で制限したので、指し手と勝敗は負荷の影響を受けない。

## 結果

### 出力の照合

3つのネットとも、作業機での照合の6つの組（ONNX RuntimeのCPUとTensorRTのFP16を、それぞれバッチの大きさ1、7、256で照合する組）がすべて合格した。
PyTorchの出力に対するTensorRTのFP16の合法手の確率の差の最大は、1回目が0.036、2回目が0.022、3回目が0.019であり、許容誤差5×10⁻²に収まった。

### 固定のαβ探索との対局

| ネット | ペンタノミアル度数 | 得点率 | Elo（95%信頼区間） | 手数の中央値（最大） |
|---|---|---|---|---|
| サイクル100 | [87, 0, 13, 0, 0] | 6.5% | −463 [−592, −386] | 250.5手（1,034手） |
| 追加100%（3回目の後） | [61, 2, 34, 0, 3] | 20.5% | −235 [−299, −183] | 262手（2,829手） |

ペンタノミアル度数は、MCTSから見たペアの得点（0、0.5、1、1.5、2）ごとのペア数である。
どちらの対局も、手数の上限で破棄したペアはなく、エンジンの異常終了、時間切れ、および反則は0件であった。
2つの対局は同じ開始局面で指したので、ペアごとに比べられる。
追加100%のネットのほうが得点の高かったペアが34、低かったペアが7、同じペアが59であり、ペアあたりの得点の差は平均+0.56点（標準誤差0.12点）であった。

### 2つのネットの直接対局

追加100%のネットとサイクル100のネットを1手800シミュレーションで対局させたが、1局の手数の中央値が912.5手と長く、6ペアに約56分かかったので、6ペアで止めた。
6ペアのうち1ペアは、1局が手数の上限4,096手に達したので破棄した。
残る5ペアのペンタノミアル度数は追加100%のネットから見て[0, 0, 2, 1, 2]であり、得点率は75%（10局で7.5点）であった。1局は千日手による引き分けであった。
100ペアを指すには約14時間かかる見込みであった。

### 固定の検証用データの診断

| ネット | 追加の量 | 価値の損失 | 人間の手との一致率 |
|---|---|---|---|
| サイクル100 | 0 | 0.6634 | 8.16% |
| 1回目の後 | +25% | 0.6489 | 9.38% |
| 2回目の後 | +50% | 0.6612 | 10.04% |
| 3回目の後 | +100% | 0.6683 | 8.44% |

### 学習器の診断

各回の学習器が最後の重みで診断した方策の損失は、1回目、2回目、3回目の順に、リプレイバッファ全体から取った訓練の標本で2.650、2.641、2.643であり、サイクル100の自己対局の検証局面で2.991、3.001、2.999であった。
サイクル100の学習の診断では、同じ検証局面の方策の損失が3.008であった。
価値の損失は、訓練の標本で0.524、0.526、0.517、検証局面で0.555、0.550、0.549であった（サイクル100は検証局面で0.551）。

## 結論

サイクル100のネットに、それまでと同じだけの学習を同じデータで追加すると、固定のαβ探索に対する得点率が6.5%から20.5%に上がり、Eloの点推定は−463から−235へ約230上がった。
同じ開始局面のペアごとの比較でも差は標準誤差の約4.5倍あり、偶然では説明しにくい。
新しく自己対局を行わずに強くなったので、2回目の系列は、作ったデータの量に比べて学習の量が足りなかったとみられる。

一方、固定の検証用データの診断と学習器の損失は、追加の量に応じて良くならなかった。
人間の棋譜での価値の損失と一致率は追加の量に対して単調には変わらずに上下し、学習器の方策の損失は訓練の標本でも検証局面でもほぼ一定であった。
これらの値は今回の強さの変化を捉えなかったので、学習の設定の採否は対局で判断する必要がある。
学習率を0.04で一定にしたまま損失が下がらなかったことから、学習率の高さが損失の低下を妨げている可能性もある（推論）。

追加学習した途中の2つのネット（+25%と+50%）は、対局では測っていない。
サイクル100のネットと追加100%のネットの直接対局は有効な5ペアしか指しておらず、追加100%のネットの優勢を示すものの、それだけでは差を判断できない。

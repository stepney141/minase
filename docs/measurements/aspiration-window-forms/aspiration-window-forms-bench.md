# aspiration windowsの形の変更による探索ノード数と探索速度

## 目的

[aspiration windowsの幅と窓の移し方の見直しの設計書](../../plans/archived/aspiration-window-forms.md)のフェーズ1で入れたコミットを対象とする。
挙動を変えない2つの移行のコミット（M1とM2）については、探索ノード数、評価値、および最善手が直前のコミットと同じになることを確かめる。
探索を変えるコミット（A1からA5）については、`minase dev bench`の探索ノード数の変化を記録する。
あわせて、探索速度、最大常駐メモリ、および係数の既定値を動かしたときのテストの結果を記録する。
棋力測定ではない。新しい係数と、開始値を置き直した2つの係数は、Stockfishの値を換算した開始値のままである。強さの変化は、SPSAで調整した後に、事前対局と短時間条件（10秒＋1手0.1秒）の逐次検定STCで記録する。

## コマンドライン

ノード数は、各コミットの`cargo build --release --bin minase`によるminaseで、次のコマンドを深さ3、5、7について1回ずつ実行して数えた。
`dev bench`は固定の15局面を固定の深さで探索し、局面ごとに置換表と履歴の表を初期化するので、同じバイナリなら出力は毎回同じになる。

```console
minase dev bench --depth <深さ>
```

探索速度と最大常駐メモリは、比べる2つのminase（M1とM2、および起点と最後のコミット）を交互に3回ずつ、性能コアのCPU 3に固定して測った（[速度比較のbenchは性能コアへ固定して測る](../../lessons/pin-bench-to-performance-core.md)）。
各回の値は、計測外のウォームアップ1回の後に3回探索した中央値である。最大常駐メモリは`/usr/bin/time -f %M`で取得した。

```console
/usr/bin/time -f %M taskset -c 3 minase dev bench --depth 9 --repetitions 3
```

1局あたりの最大常駐メモリは、最後のコミットの調整用ビルド同士の1ペア（2局）をSTCの持ち時間で指して測った。

```console
<最後のコミットのminase> match run \
  --run-dir data/matches/aspiration-window-forms-rss --seed 4780000000 \
  --candidate "<調整用ビルド> --protocol usi --rules engine-default" \
  --baseline "<調整用ビルド> --protocol usi --rules engine-default" \
  --each time=10000+100 --concurrency 2 elo --pairs 1
```

## エンジン

起点はコミット`03f5d79d`（サブタスク5の完了後のmaster）、最後のコミットは`7631da34`である。各コミットは結果の表に挙げる。
`7631da34`はA5の`6795cce6`の後のコミットであり、2ワーカーの反復のテストの深さ上限を直しただけで、探索の挙動は変えていないので、benchの出力はA5と同じである。
規則セットは`engine-default`、探索のワーカーは1、置換表は既定の256 MBである。

## 環境

測定機はIntel Core Ultra 7 265KF（性能コア8個と高効率コア12個、20スレッド）である。
ほかの対局測定、SPSA、教師生成、および学習は動いていなかった。lishogiのBotは止めておらず、探索速度はBotのエンジンが動いていない間にだけ測った。

## 結果

### 探索ノード数

15局面の合計は次のとおりである。

2つの移行のコミットは、全15局面の3つの深さで直前のコミットと一致した。

### 探索速度

M2で加えた根の手ごとの記録の更新が探索速度に与える影響を分けて測るため、M1とM2を交互に3回ずつ測った。あわせて、起点と最後のコミットを同じ方法で測った。
各回の前にBotのエンジンが3秒間CPUを使っていないことを確かめ、各回の間にBotのエンジンが使ったCPU時間がすべて0秒だったことを確かめた。
NPSは1秒あたりの探索ノード数、所要時間は深さ9で全15局面を読み終える時間である。

| 回 | M1のNPS | M1の所要時間 | M2のNPS | M2の所要時間 |
|---:|---:|---:|---:|---:|
| 1 | 862,277 | 0.206956秒 | 861,329 | 0.207183秒 |
| 2 | 859,906 | 0.207526秒 | 859,818 | 0.207547秒 |
| 3 | 864,268 | 0.206479秒 | 862,183 | 0.206978秒 |

M1とM2の深さ9の探索ノード数はどちらも178,453であり、中央値のNPSはM1が862,277、M2が861,329で、M2は約0.1%低かった。根で手を読むたびに記録を更新することによる速度の低下は、この測り方では測定の繰り返しのばらつきと同じ程度である。

| 回 | 起点のNPS | 起点の所要時間 | 最後のNPS | 最後の所要時間 |
|---:|---:|---:|---:|---:|
| 1 | 862,095 | 0.206999秒 | 847,840 | 0.179317秒 |
| 2 | 861,199 | 0.207215秒 | 842,472 | 0.180460秒 |
| 3 | 857,637 | 0.208075秒 | 841,545 | 0.180658秒 |

深さ9の探索ノード数は、起点が178,453、最後のコミットが152,032であり、14.8%少ない。
最後のコミットは、起点に比べてNPSが約2.2%下がり、深さ9を読み終える時間が約12.9%短くなった。

### 最大常駐メモリ

探索速度と同じ実行で取得した最大常駐メモリは、起点が約509.5 MB、最後のコミットが約507.4 MBであり、ほぼ変わらなかった。
調整用ビルド同士の1ペアをSTCの持ち時間で指したときの1局あたりの最大常駐メモリ（2局のそれぞれで2つのエンジンの最大常駐メモリを足し、その大きい方）は1,004,732,416バイトであり、[サブタスク5の記録](../qsearch-forms/qsearch-forms-bench.md)の1,003,966,464バイトとほぼ同じだった。

### 係数の既定値に依存するテスト

調整係数の既定値を範囲の1/3と2/3の位置に置いた一時的な`params.rs`で、`cargo test --workspace --no-fail-fast`と`cargo test -p minase --lib --features search-stats,tuning --no-fail-fast`を実行した。
1/3と2/3のどちらの表でも、すべてのテストが通った。

最後のコミットの前に、A5のコミットで4つの検査を実行し直したところ、2つのワーカーでR1の経路の反復を10回評価するテストが、10回のうち1回だけ、2手先の反復を読めずに失敗した。
A5では、fail highの後に読み直しの窓の深さが減る。このため深さ上限3では、最後の窓の深さが1になる回が生じ、どの回でそうなるかは2つのワーカーが置換表を共有する順序によって変わる。
1ワーカーで各窓を調べると、深さ2の反復の最初の窓でfail highが起きて窓の深さが1に減り、深さ3の反復は持ち越しのために窓の深さ2で読んでいた。
深さ上限を4にすると、深さ3でfail highがもう1回増えても、深さ4の反復の窓の深さは2以上になり、2手先の反復を読める。
テストの深さ上限を4に直し（コミット`7631da34`）、そのテストを通常ビルドと調整用ビルドで20回ずつ繰り返して、すべて通ることを確かめた。

## 結論

2つの移行のコミットは探索を変えず、A1からA5のコミットは3つの深さの合計で探索ノード数を28.8%減らした。
最後のコミットは起点に比べて、深さ9の探索ノード数が14.8%少なく、NPSが約2.2%低く、深さ9を読み終える時間が約12.9%短い。
M2の根の手ごとの記録による速度の低下は約0.1%であり、1プロセスの最大常駐メモリは変わらなかった。

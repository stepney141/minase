# aspiration windowsの形の変更の時間切れの事前確認

## 目的

[aspiration windowsの幅と窓の移し方の見直しの設計書](../../plans/archived/aspiration-window-forms.md)のフェーズ2として、SPSAの本番の前に、時間管理の4係数を思考時間が最も長くなる側の範囲の端に置いても、換算した持ち時間で時間切れとエンジン異常が起きないことを確かめる。
棋力測定ではない。

## コマンドライン

パラメーターファイル`aspiration-window-forms-safety.params`は、本番の91係数のファイルの写しで、開始値を`HardRemainingShare` = 50、`HardSoftRatio` = 800、`MinMoves` = 40、および`IterationRatio` = 150へ書き換えたものである。`HardRemainingShare`は、本番の開始値もすでに範囲の上端の50である。
反復数156は、[統括計画](../../plans/search-forms.md)が定める`⌈13 × 同時対局数 ÷ 16⌉`（同時対局数191）である。
持ち時間は、測定機のSTC`time=10000+100`に、この調整機で測った換算係数1.37を掛けた値である。
換算係数は、測定機の負荷時の速度467,260 NPSを、調整機で191本の`dev bench`を同時に走らせた負荷時の速度340,521 NPSで割った比を、小数第2位に丸めた値である。
測定機の値は、調整用ビルドを16本同時に`minase dev bench --depth 9 --repetitions 3`で走らせた平均NPSを5回測った中央値であり、5回の値は470,331、453,675、467,260、477,536、および459,882 NPSだった。
測定の間、lishogiのBotは通信対局を指し続けていたので、各回の前にBotのエンジンが3秒間CPUを使っていないことを確かめ、各回の間にBotのエンジンが使ったCPU時間が0.5秒未満の回だけを採用した。採用した5回はいずれも0秒であり、最初の1回はBotのエンジンが12.13秒のCPU時間を使ったので捨てた。
測定機の負荷時の速度は、[サブタスク5の記録](../qsearch-forms/qsearch-forms-safety.md)の377,413 NPSより高い。サブタスク5の値は、同書の形の変更の最後のコミットの開始値で測ったものであり、本書の起点はその後にSPSAの最終値を反映した版である。
コマンドは、調整機の`scripts/vast-spsa/remote.py`が起動した。

```console
minase spsa \
  --run-dir /workspace/job/aspiration-window-forms-safety --seed 4700000000 \
  --engine commit:7631da34 --params /workspace/job/safety.params \
  --rules engine-default --each time=13700+137 --concurrency 191 \
  --iterations 156 --pairs-per-iteration 8
```

## エンジン

調整対象は、形の変更の最後のコミット`7631da34e28b906ed876cfa6c228c7838a924682`の調整用ビルドであり、調整機でビルドした実行ファイルのSHA-256は`aeea5725…`である。
runnerは同じコミットの通常ビルド（版2.4.0、SHA-256`ffaf3f22…`）である。
調整機では、測定機で作った`git bundle`からブランチを取り込み、`cargo build --release --locked --bin minase`でrunnerを、`minase spsa params --engine commit:7631da34 --rules engine-default`で調整用ビルドを作った。
このコマンドが出力した既定のパラメーターファイルから`FmScale`の行を除いたものは、測定機で作った91係数のファイルと一致した。
規則は`engine-default`（`L0,P0,R1,E0`）、置換表は既定の256 MB、探索のワーカーは1である。

## 環境

調整機は、vast.aiのインスタンス57080553（出品57006540、機械のID 49339、AMD EPYC 9K84の2基構成、物理192コア、論理384スレッド（runnerが記録した論理CPUは368）、`cpu_ram`は773,540 MB、ベトナム、1時間約1.88米ドル）である。
同時対局数は、物理コア数から1を引いた191であり、メモリによる制限（調整機の実メモリを、1局あたりの最大常駐メモリ約1,005 MBの1.25倍で割った数）は受けなかった。
1局あたりの最大常駐メモリは、測定機で調整用ビルド同士の1ペアをSTCの持ち時間で対局させ、2局それぞれについて2つのエンジンの最大常駐メモリを足した値のうち、大きい方（1,004,732,416バイト、[benchの記録](aspiration-window-forms-bench.md)）とした。
`launch.py`の条件による選択はメモリを条件に含めないので、メモリの少ない出品で同時対局数が下がって費用が残高を超えないよう、`cpu_ram`が260,000 MB以上で、1時間2.1米ドル以下の出品だけを測定機で照会し、見つかった出品を`launch.py`に出品のIDで渡して作成した。
2026年10月22日1時07分（日本時間）に照会を始め、1時17分に作成できた。

## 結果

156反復をすべて適用し、1,248ペアのうち有効ペアは1,228、手数上限で破棄したペアは20だった。
異常件数は、不正着手、クラッシュ、応答タイムアウト、時間切れ（`time_forfeits`）、および拒否着手のいずれも0だった。
所要時間は1,685秒だった。

## 結論

時間管理の4係数を思考時間が最も長くなる側の範囲の端に置いても、換算した持ち時間で時間切れとエンジン異常は起きなかったので、本番のSPSAへ進む。

# 段階Bの煙試験（難しさで重み付けした持ち時間期の配分）

## 目的

[秒読みつき時計での持ち時間と秒読みの活用](../plans/byoyomi-time-usage.md)の段階Bの3候補（B0、B1、B2）を段階Aの採用構成と秒読みつきの2条件で対局させ、フェーズ4の判定条件（時間切れ0件、持ち時間が尽きる手数が予測から50%以内、深さ6に達した手が50%以上、信号が真だった手が10%以上）を確かめる。

## コマンドライン

各候補について、短い条件と長い条件で次を実行した。シードは2033100000から100000ずつ増やし、B1の短い条件、B1の長い条件、B0の短い条件、B0の長い条件、B2の短い条件、B2の長い条件の順に割り当てた。

```console
cargo run --release --bin minase -- match run --run-dir data/matches/byoyomi-<候補>-smoke-<条件> --seed <シード> \
  --candidate commit:<候補> --baseline commit:72fb0ce --each time=<6000または45000>+0,byoyomi=300 --concurrency 11 elo --pairs 10
```

深さ6への到達率と信号の発動率は、短い条件の対局記録から候補の持ち時間期の手を200局面選び、記録から再現した持ち時間で候補のエンジンに探索させて数えた。

```console
python3 scripts/lishogi_byoyomi_usage/signal_probe.py data/matches/byoyomi-<候補>-smoke-short <候補のエンジン> 200 100
```

## エンジン

候補はB0がec9bed6、B1がe5af46e、B2がf630519であり、基準は72fb0ce（段階Aの採用構成に、挙動を変えない信号の計算と検査の修正を加えたもの）である。規則セットは`engine-default`、両者とも`Threads=1`、`USI_Hash`は256 MB、`ByoyomiMargin`は既定の30 msである。

## 環境

CPUはIntel Core Ultra 7 265KF（物理20コア、論理20コア）、同時対局数は11である。同じ測定機ではlishogiのBotが動いていた。

## 結果

| 候補 | 条件 | ペンタノミアル度数 | Eloの点推定（95%信頼区間） | 破棄 | 時間切れ | 持ち時間が尽きる手数（予測→実測の中央値） |
|---|---|---|---|---:|---:|---|
| B1 | 短い | [2, 0, 5, 0, 2] | 0.0（−162.2〜＋162.2） | 1 | 0 | 40 → 53.5 |
| B1 | 長い | [2, 2, 5, 0, 1] | −70.4（−212.4〜＋50.8） | 0 | 0 | 154 → 184 |
| B0 | 短い | [1, 1, 7, 0, 0] | −58.5（−140.8〜＋17.8） | 1 | 0 | 58 → 76.5 |
| B0 | 長い | [2, 0, 5, 2, 1] | 0.0（−133.6〜＋133.6） | 0 | 0 | 204 → 264 |
| B2 | 短い | [5, 0, 5, 0, 0] | −190.8（−391.5〜−66.9） | 0 | 0 | 198 → 199 |
| B2 | 長い | [2, 1, 3, 0, 2] | −21.7（−222.8〜＋164.4） | 2 | 0 | 198 → 208.5 |

エンジン異常、拒否着手はすべての条件で0件だった。
短い条件の持ち時間期の局面で、深さ6の反復を完了した手の割合と、最後の完了反復で信号が真だった手の割合は、B1が1.000と0.215、B0が1.000と0.215、B2が0.800と0.200だった。

## 結論

3候補とも判定条件を満たしたので、選別の測定へ進む。10ペアの成績はいずれも段階Aを上回らず、B2の短い条件は信頼区間の上端も負であるが、煙試験の成績は採否の根拠にしない。

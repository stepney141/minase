# correction historyの表の追加と持ち越しによる探索ノード数、探索速度、およびメモリ

## 目的

[correction historyの表の追加と持ち越しの設計書](../../plans/correction-history-tables.md)のフェーズ1で入れたコミットを対象とする。
探索を変えない移行のコミットについては、探索ノード数、評価値、および最善手が起点と同じになることを確かめる。
探索を変えるコミット（材料表の値の形と更新を改めるC4、局面の配置の4表を加えるC2、continuation correction historyを加えるC3、LMRの減深量に補正量の項を加えるC5）については`minase dev bench`の探索ノード数の変化を記録し、表を持ち越して共有するC1については、`Threads=1`のbenchがC3と同じになることを確かめる。
あわせて探索速度と最大常駐メモリを測る。
棋力測定ではない。新しい係数はStockfishの値を換算した開始値のままであり、SPSAで調整した後に、事前対局と短時間条件（10秒＋1手0.1秒）の逐次検定STCで強さの変化を記録する。

## コマンドライン

ノード数は、各コミットの`cargo build --release --bin minase`によるminaseで、次のコマンドを深さ3、5、7について1回ずつ実行して数えた。
`dev bench`は固定の15局面を固定の深さで探索し、局面ごとに`HistoryTables`を初期化するので、同じバイナリなら出力は毎回同じになる。

```console
minase dev bench --depth <深さ>
```

探索速度と最大常駐メモリは、起点と最後のコミットのminaseを交互に3回ずつ、性能コアのCPU 3に固定して測った（[速度比較のbenchは性能コアへ固定して測る](../../lessons/pin-bench-to-performance-core.md)）。
各回の値は、計測外のウォームアップ1回の後に3回探索した中央値である。最大常駐メモリは`/usr/bin/time -f %M`で取得した。

```console
/usr/bin/time -f %M taskset -c 3 minase dev bench --depth 9 --repetitions 3
```

1局あたりの最大常駐メモリは、最後のコミットの調整用ビルド同士の1ペア（2局）をSTCの持ち時間で指して測った。

```console
<最後のコミットのminase> match run \
  --run-dir data/matches/correction-history-tables-rss --seed 4260000000 \
  --candidate "<調整用ビルド> --protocol usi --rules engine-default" \
  --baseline "<調整用ビルド> --protocol usi --rules engine-default" \
  --each time=10000+100 --concurrency 2 elo --pairs 1
```

## エンジン

起点はコミット`e21b7655`（サブタスク3の完了後のmaster）、最後のコミットは`e695176a`である。各コミットは結果の表に挙げる。
`e695176a`はC5の`e10ddf52`の後のコミットであり、テストを直し、そのために補正表の更新の処理を関数へ切り出した。探索の挙動は変えていないので、benchの出力はC5と同じである。
規則セットは`engine-default`、探索のワーカーは1、置換表は既定の256 MBである。

## 環境

測定機はIntel Core Ultra 7 265KF（性能コア8個と高効率コア12個、20スレッド）である。
ほかの対局測定、SPSA、教師生成、および学習は動いていなかった。lishogiのBotは止めておらず、探索速度はBotのエンジンが動いていない間にだけ測った。

### 探索速度

起点と最後のコミットを交互に3回ずつ測った。測定の間、Botは通信対局を指していたが、各回の前にBotのエンジンが3秒間CPUを使っていないことを確かめ、各回の間にBotのエンジンが使ったCPU時間がすべて0秒だったことを確かめた。

NPSは1秒あたりの探索ノード数、所要時間は深さ9で全15局面を読み終える時間である。

| 回 | 起点のNPS | 起点の所要時間 | 最後のNPS | 最後の所要時間 |
|---:|---:|---:|---:|---:|
| 1 | 899,572 | 0.322846秒 | 837,292 | 0.365069秒 |
| 2 | 897,459 | 0.323606秒 | 839,096 | 0.364284秒 |
| 3 | 899,739 | 0.322786秒 | 839,495 | 0.364111秒 |

深さ9の探索ノード数は、起点が290,423、最後のコミットが305,669であり、5.2%多い。
最後のコミットは、起点に比べてNPSが約6.7%下がり、深さ9を読み終える時間が約12.8%延びた。
ノードごとに読む表は、材料表1つから局面の5表とcontinuation correction historyの3区画になり、着手ごとに差分更新する鍵もminorと先手と後手のnon-pawnの3つが増えたが、NPSの低下の内訳は測っていない。

### 最大常駐メモリ

同じ実行で取得した最大常駐メモリは、起点が約470 MB、最後のコミットが約509 MBであり、約39 MB増えた。
増分は、設計書の見込み（ワーカーごとのcontinuation correction historyの約36 MBと、局面の5表の約1.3 MB）とほぼ一致する。

調整用ビルド同士の1ペアをSTCの持ち時間で指したときの1局あたりの最大常駐メモリ（2局のそれぞれで2つのエンジンの最大常駐メモリを足し、その大きい方）は1,002,328,064バイトであり、[サブタスク3の記録](../history-forms/history-forms.md)の926,187,520バイトより約76 MB多い。
2つのエンジンがそれぞれ約38 MB増やした量に当たる。

### 係数の既定値に依存するテスト

調整係数の既定値を範囲の1/3と2/3の位置に置いた一時的な`params.rs`で、`cargo test --workspace --no-fail-fast`と`cargo test -p minase --lib --features search-stats,tuning --no-fail-fast`を実行した。
補正表のテスト5件とreverse futility pruningのテスト1件が失敗した（1/3では6件、2/3では5件）。
テストは、更新量を固定の値で与えて確かめるか、更新の向きと初期値からの変化で確かめるか、局面の補正を0にして確かめたい境界だけを分けて確かめるように直した（コミット`e695176a`）。
最後のコミットでは、1/3と2/3のどちらの表でもすべてのテストが通った。

## 結論

移行のコミットは探索を変えず、C1は単一ワーカーのbenchを変えず、C4からC5までは3つの深さの合計で探索ノード数を1.5%増やした。
最後のコミットは起点に比べて、深さ9の探索ノード数が5.2%多く、NPSが約6.7%低く、深さ9を読み終える時間が約12.8%長い。
1プロセスの最大常駐メモリは約39 MB増え、設計書の見込みどおりだった。

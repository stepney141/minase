# historyの形の変更の時間切れの事前確認

## 目的

[historyの更新量の形とcontinuation historyの設計書](../../plans/archived/history-forms.md)のフェーズ2として、SPSAの本番の前に、時間管理の4係数を思考時間が最も長くなる側の範囲の端に置いても、換算した持ち時間で時間切れとエンジン異常が起きないことを確かめる。
棋力測定ではない。

## コマンドライン

パラメーターファイル`history-forms-safety.params`は、本番の82係数のファイルの写しで、開始値を`HardRemainingShare` = 50、`HardSoftRatio` = 800、`MinMoves` = 40、および`IterationRatio` = 150へ書き換えたものである。`MinMoves`はもともと範囲の下限40なので、この係数の値は変わらない。
反復数156は、[統括計画](../../plans/archived/search-forms.md)が定める`⌈13 × 同時対局数 ÷ 16⌉`（同時対局数191）である。
持ち時間は、測定機のSTC`time=10000+100`に、この調整機で測った換算係数1.45を掛けた値である。
換算係数は、測定機の負荷時の速度542,019 NPSを、調整機で191本を同時に走らせた負荷時の速度373,782 NPSで割った比を小数第2位に丸めた値である。
測定機の値は、調整用ビルドを16本同時に`minase dev bench --depth 9 --repetitions 3`で走らせた平均NPSを、lishogiのBotが対局していない間に5回測った中央値であり、5回の値は538,549、540,517、542,019、546,379、および557,886 NPSだった。
Botが2局を対局している間に測った6回の値は352,024〜376,105 NPS（中央値363,331 NPS）であり、Botの思考と重なると約3割低く出るので、前のサブタスクと条件をそろえて、Botが対局していない間の値を使った。
コマンドは、調整機の`scripts/vast-spsa/remote.py`が起動した。

```console
minase spsa \
  --run-dir /workspace/job/history-forms-safety --seed 3800000000 \
  --engine commit:b2cae818 --params /workspace/job/safety.params \
  --rules engine-default --each time=14500+145 --concurrency 191 \
  --iterations 156 --pairs-per-iteration 8
```

## エンジン

調整対象は、形の変更の最後のコミット`b2cae818cc8c7b912a087017c9ae8781172fa909`の調整用ビルドであり、調整機でビルドした実行ファイルのSHA-256は`8b5e0208…`である。
runnerは同じコミットの通常ビルド（版2.4.0、SHA-256`39fc5882…`）である。
調整機では、測定機で作った`git bundle`からブランチを取り込み、`cargo build --release --locked --bin minase`でrunnerを、`minase spsa params --engine commit:b2cae818 --rules engine-default`で調整用ビルドを作った。
このコマンドが出力した既定のパラメーターファイルから`FmScale`の行を除いたものは、測定機で作った82係数のファイルと一致した。
規則は`engine-default`（`L0,P0,R1,E0`）、置換表は既定の256 MB、探索のワーカーは1である。

## 環境

調整機は、vast.aiのインスタンス56723270（出品56499914、機械のID 51088、AMD EPYC 9K84の2基構成、物理192コア、論理384スレッド（runnerが記録した論理CPUは368）、`cpu_ram`は773,514 MB、ベトナム、1時間1.87米ドル）である。
同時対局数は、物理コア数から1を引いた191であり、メモリによる制限（調整機の実メモリを、1局あたりの最大常駐メモリ約926 MBの1.25倍で割った数）は受けなかった。
1局あたりの最大常駐メモリは、測定機で調整用ビルド同士の1ペアをSTCで指し、2局のそれぞれで候補と基準の最大常駐メモリを足し、大きい方の値（926,187,520バイト）とした。

この調整機の前に、出品56041192（AMD Eng Sampleの100-000000894-04の2基構成、論理384スレッド、ルーマニア、1時間1.74米ドル）でインスタンス56680581を作った。
このコンテナに割り当てられたCPUは論理208個（`cpuset`は88〜191と280〜383、CPUの割り当ての上限も208個）だけであり、`remote.py`は物理コアを`lscpu`のソケット数とコア数の積の192と数えて同時対局数を191とした。
191本の負荷時の速度は71,596 NPS、換算係数は7.57、見込みの所要時間は約47.8時間となり、上限の24時間を超えたので、`remote.py`は事前確認の前に止まり、`fetch.py`が調整機を削除した。費用は約0.35米ドルだった。
その後、vast.aiのAPIキーが口座の操作に2要素認証でのログインを求めて拒否される時期があり、利用者が認証し直してから2台目を作った。

## 結果

156反復をすべて適用し、1,248ペアのうち有効ペアは1,238、手数上限で破棄したペアは10だった。
異常件数は、不正着手、クラッシュ、応答タイムアウト、時間切れ（`time_forfeits`）、および拒否着手のいずれも0だった。
所要時間は1,728秒だった。

## 結論

時間管理の4係数を思考時間が最も長くなる側の範囲の端に置いても、換算した持ち時間で時間切れとエンジン異常は起きなかったので、本番のSPSAへ進む。

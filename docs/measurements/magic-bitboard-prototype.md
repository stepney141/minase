# Magic bitboard試作の実現可能性と速度

## 目的

横線の小表と斜線の乗算magicを実際に組み込み、定数生成、正しさ、表容量、および探索速度から採用候補に進めるかを判定する。
今回の試作は両方式とも速度向上を示さなかったため、現行方式を維持する。

## コマンドライン

試作はmasterの固定コミットから作った独立cloneのブランチで行い、本体リポジトリのRustソースは変更していない。
変更の全体は[横線の差分](magic-bitboard-prototype/horizontal.patch)、[斜線の差分](magic-bitboard-prototype/diagonal.patch)、[強制インライン化の差分](magic-bitboard-prototype/force-inline.patch)に保存した。
斜線の差分には、生成器と生成した定数を含む。
既存の計測スクリプトの出力解析を使う[比較スクリプト](magic-bitboard-prototype/compare.py)で、実装ごとに別バイナリを実行した。

3組の探索速度の比較は、リポジトリのルートで次の1コマンドから再現できる。
指定する作業ディレクトリは未作成のものとし、CPU番号は測定機の性能コアに合わせる。
このコマンドは6個のバイナリを先にビルドし、ビルド終了後に速度を測る。

```sh
python3 docs/measurements/magic-bitboard-prototype/reproduce.py \
  --work-dir /tmp/minase-magic-rerun --cpu 0
```

各バイナリのビルドは`cargo build --release --locked --bin bench`、コンパイル対象は`target-cpu=native`である。
探索は`bench --depth <5または6> --threads 1 --repetitions 5`を使い、実行ごとに1回ウォームアップした後の5反復の中央値を得る。
各組で実行順を入れ替えながら6または8ラウンド測り、ラウンドごとの中央値の中央値を比較した。
全て`taskset -c 0`で固定し、ビルド、別のベンチマーク、自己対局は同時に実行しなかった。

全ラウンドの順序と測定値は[初回の深さ5](magic-bitboard-prototype/depth5-initial.json)、[インライン化を指定した深さ5](magic-bitboard-prototype/depth5-forced.json)、[確認用の深さ6](magic-bitboard-prototype/depth6-forced.json)に保存した。
3者の6ラウンドでは全順列を1回ずつ使う。
4者の8ラウンドは全実行位置を均等には割り当てていないが、現行方式の強制インライン版と斜線の強制インライン版は同じ位置の頻度で比較される。
深さ6ではこの2者と現行版を全位置で均等に比較した。

## エンジン

基準は`1633f534cf0e8c96738b11158e68f31f0f144f01`、minase v1.1.0である。
規則セットは`engine-default`、置換表は256 MiB、ワーカーは1個であり、15局面を固定深さで探索する。
置換表の確保と局面ごとのクリアは探索時間に含めない。
実装とビルドの対応は次のとおりで、完全なハッシュは[コミット一覧](magic-bitboard-prototype/commits.json)にある。

| 版 | コミット | 変更内容 |
|---|---|---|
| 現行版 | `1633f534` | 比較の基準とする。 |
| 横線版 | `6e8a789` | 横線2方向を共通の24 KiB表で計算する。 |
| 斜線版 | `8075224` | 斜め4方向を片方向ごとの乗算magicで計算する。 |
| 現行方式の強制インライン版 | `44d0282` | 現行の`sliding_control`に`#[inline(always)]`だけを加える。 |
| 横線の強制インライン版 | `e05a1cf` | 横線版に同じ属性を加える。 |
| 斜線の強制インライン版 | `92813d1` | 斜線版に同じ属性を加える。 |

通常の`#[inline]`だけを加えた3版も作ったが、候補の呼び出しは消えず、該当関数の機械語も変わらなかったため、別の速度測定は行わなかった。
強制インライン版は、表方式の変更によるインライン化の有無を切り分ける試作である。
本番の属性や実装は変更していない。

## 環境

2026年9月21日に、Intel Core Ultra 7 265KF、20物理コア、20論理コア、rustc 1.98.0で測った。
性能コアのCPU 0へ固定し、通常のrelease最適化、リンク時最適化、および1コード生成単位を使った。
速度測定にはプロファイラや呼び出しカウンタを組み込んでいない。
同じ固定局面、深さ、および単一スレッドでの比較であり、他のCPUや局面分布での結果は測っていない。

## 結果

### 定数生成と容量

斜線のmagic定数は、必要な占有ビット数と同じ幅の添字で全て生成できた。
144始点×4方向の576マスクのうち400個が非空で、176個は関連ビット数0なので定数探索を要しない。
固定シード`52f1804bb57c183d`と1マスク当たり1,000,000候補の上限を使い、合計443,393候補、最大23,427候補で全て成功した。
生成器内で測った時間は0.017281秒であり、再実行でも定数ファイルはバイト単位で一致した。
探索上限に達した場合は終了する実装であり、表の拡大や別方式への切り替えは行っていない。
元の数値は[生成記録](magic-bitboard-prototype/generation.json)にある。

| 版 | 追加するデータ | 容量 |
|---|---|---:|
| 横線版 | 12始点×1,024占有の`u16`表を持つ。 | 24,576バイト |
| 斜線版 | 24,568エントリの24バイト利き表を持つ。 | 589,632バイト |
| 斜線版 | 生インデックス用の768個のマスク、定数、オフセットを持つ。 | 36,864バイト |
| 斜線版の合計 | 上記2表を持つ。 | 626,496バイト、約612 KiB |

両試作とも現在の36 KiBの利き線表を残す。
斜線版は各語に対象線のマスクを掛けてから論理和を取り、乗算とシフトで直接24バイトの出力を引く。
横線版は内側10升の占有を取り出し、`u16`の利きを元の段へ戻して片方向の利き線と交差させる。
いずれも`unsafe`を使わず、仮想占有を含む現在の引数だけで計算する。

### 正しさ

横線版は144始点×4,096占有×2方向の1,179,648入力で、規則第7条4項と5項に従う逐次走査と一致した。
斜線版は全レイ占有に加え、終端、始点の占有、および線外を全て埋めた場合を含む196,176入力で一致した。
さらに定数を別のプログラムで読み、全関連占有の添字と利きの衝突を独立に検査した。
最初の遮蔽升を除く誤実装と、斜線のマスクをOR前に掛けない誤実装を入れた場合には、参照との一致検査が失敗した。

両試作のライブラリテストは584件成功し、書式検査とClippyも通った。
斜線版の最初の並列テストでは、ビルドが並行していた環境で既存のUSIテストが5秒の待機上限に達した。
同テストの単独10反復と、単一テストスレッドでのライブラリ全体の再実行は成功した。
この結果からタイムアウトの原因を実装へ特定したわけではない。

探索では、比較した全ての版で15局面それぞれの深さ、ノード数、最善手、探索値が一致した。
合計ノード数は深さ5で598,014、深さ6で1,813,911だった。
初期局面の`perft`も深さ1から順に36、1,296、48,315で一致した。
この一致は棋力や固定時間での指し手の一致を意味しない。

### 探索速度

初回の試作は、横線版が現行比で11.26%、斜線版が9.26%遅くなった。
各版の1秒あたりの探索ノード数（NPS）の中央値は、現行版2,124,413.5、横線版1,885,219.5、斜線版1,927,698.5だった。
基準のラウンド間の幅は1.97%であり、両試作の退行はその幅を超えた。
ここで幅は、NPS中央値の最大と最小の差を、その中央値で割った値である。

逆アセンブルでは、現行版には`sliding_control`の独立関数がなく、両試作では呼び出しが残っていた。
通常駒の捕獲先を求める呼び出し元のスタック確保も、現行版の40バイトから両試作の120バイトへ増えた。
したがって、この比較には表引きの費用だけでなく、変更対象外の方向も含めた関数呼び出しとレジスタ退避の増加が含まれる。
関数のシンボルと大きさは[機械語の記録](magic-bitboard-prototype/codegen-symbols.json)にある。

`#[inline(always)]`では両候補の関数呼び出しを除けたので、同じ属性を現行方式へ加えた対照も測った。
深さ5の8ラウンドの結果は次のとおりである。

| 版 | NPS中央値 | 現行版に対する変化 | 同じ属性の現行方式に対する変化 |
|---|---:|---:|---:|
| 現行版 | 2,142,810.5 | 基準とする。 | |
| 現行方式の強制インライン版 | 2,128,062.5 | −0.69% | 基準とする。 |
| 横線の強制インライン版 | 1,785,697.0 | −16.67% | −16.09% |
| 斜線の強制インライン版 | 2,088,249.5 | −2.55% | −1.87% |

斜線版は関数呼び出しを除くことで最初の退行を縮めたが、同じ属性の現行方式との同ラウンド比較でも8回全てで遅かった。
横線版ではインライン展開後の呼び出し元が大きくなり、スタック確保も168バイトとなった。
そのため、インライン化を強制すれば表方式の追加費用を全て取り除けるとは扱わない。
表容量だけで候補の速度を判断できない結果である。

斜線版について深さ6でも6ラウンド確認したところ、同じ傾向が続いた。
基準の幅は0.55%、同じ属性の対照の幅は0.51%だった。

| 版 | NPS中央値 | 現行版に対する変化 | 同じ属性の現行方式に対する変化 |
|---|---:|---:|---:|
| 現行版 | 2,080,093.5 | 基準とする。 | |
| 現行方式の強制インライン版 | 2,065,976.5 | −0.68% | 基準とする。 |
| 斜線の強制インライン版 | 2,037,676.5 | −2.04% | −1.37% |

各組の中央値はその組の基準と比較し、測定時刻が異なる組同士の絶対NPSを直接比べない。
ラウンド内の5反復は中央値を安定させるための反復であり、全反復を独立な統計標本とは扱っていない。
今回の判断は改善を示さなかった試作を採用候補へ進めないことであり、全CPUで同じ退行率になるとの推定ではない。

### 実際の入力による単体計測

別ビルドで現行版の深さ5を実行し、探索中の13,368,286回の利き照会から固定の混合関数で約32回に1回を採取した。
採取した420,119件は、始点、方向、および仮想占有を含む3語の入力をそのまま保持する。
計測用の変更を加えた版も、15局面の探索結果は基準と一致した。
[採取差分](magic-bitboard-prototype/trace.patch)、[方向別の件数](magic-bitboard-prototype/trace-counts.txt)、[入力のSHA-256](magic-bitboard-prototype/queries.sha256)を保存した。

採取した入力を、独立の逐次走査と1件ずつ照合したうえで、各版の最初の試作へ繰り返し与えた。
結果は[単体計測の差分](magic-bitboard-prototype/probe.patch)と[集計値](magic-bitboard-prototype/probe-summary.json)で確認できる。
全方向を混ぜた1照会当たりの中央値は、現行版6.21ナノ秒、横線版7.68ナノ秒、斜線版7.09ナノ秒だった。
最後に現行版を測り直した値は6.31ナノ秒である。
これらは呼び出しが残る最初の試作の値であり、強制インライン版の値ではない。

この単体計測では探索中の他のデータとのキャッシュ競合や呼び出し元での最適化が再現されないため、採用判断には探索全体の値を使う。
初回の利き表構築時間も同じ単体計測で観測し、現行版約0.263ミリ秒、横線版約0.320ミリ秒、斜線版約1.131ミリ秒だった。
これは各1回の初期化の参考値であり、定常速度の比較区間には含めていない。

## 結論

斜線のmagic定数は小さな探索費用で生成でき、約612 KiBの追加データで現在の盤表現と規則を維持した実装を作れた。
実装可能性の未確定点だった定数生成と正しさは、今回の範囲で確認できた。
一方、表参照、追加の方向分岐、および呼び出し元の機械語の変化を含む全体費用では、現在の算術方式を上回らなかった。

今回の2方式は速度比較で改善を示さなかったため、採用候補に進めず、自己対局による逐次確率比検定（SPRT）は実施しない。
別の表配置や利きの圧縮が速くなる可能性は未検証であり、この結果をmagic方式一般の否定や棋力の評価へ広げない。
前回の[プロファイル](magic-bitboard-profile-depth5.md)の4.26%も、今回変わった呼び出し元の命令配置やキャッシュへの影響を拘束する改善上限には使わない。

# HaChu対minaseの等時間GSPRT（60秒＋1秒）

## 目的

CECPエンジン指定の初回運用として、minase（CECP対応を加えたコミットa49bd46）とHaChuを対等な時間制御60秒＋1秒加算で対局させ、どちらが強いかを判定する。

## コマンドライン

```console
match_runner --seed 20260824 --candidate commit:a49bd46 \
  --baseline "cecp:../hachu-debian/hachu" --rules L1,L3,P5,P6,R2,E1,E2 \
  --each time=60000+1000 --concurrency 8 gsprt --max-pairs 200
```

## エンジン

候補はコミットa49bd46（探索部とLazy SMP完了後、評価関数v0）で、`Threads=1`である。
基準はHaChuのDebianパッケージ収録のオリジナル版（コミットdf26f4a）を`gcc -O2`でビルドしたもので、規則オプションは既定（"Okazaki rule"無効、"Promote on entry"有効、"Allow repeats"無効）のままである。
規則セットはHaChuの既定設定に合わせた`L1,L3,P5,P6,R2,E1,E2`（RULES.md第13版当時の表記）であり、第14版以後に同じ条件を指定する場合は`L1,L3,P0,P5,P6,R2,E1,E2`を用いる。

## 環境

CPUはIntel Core Ultra 7 265KF（物理20コア、論理20、SMTなし）である。
候補は`Threads=1`、基準は単一スレッドのHaChu、`USI_Hash`とHaChuの`memory`はともに256 MB、同時対局数は8、時間制御は両者とも60秒＋1秒加算である。
測定日は2026年8月24日である。

## 結果

200ペア（破棄0）を消化し、ペンタノミアル度数は[125, 0, 74, 0, 1]、LLRは−2.8536584430、判定は上限ペア数到達によるpendingだった。
minaseの得点は400局中76勝（勝率19%）で、固定局数Elo換算は−252、95%信頼区間は[−294, −216]である。
LLRがH0境界−2.944に僅かに届かなかったのは、elo0=0とelo1=5の狭い仮説帯に対して真の差が桁違いに大きく、1ペアあたりの尤度差が飽和するためであり、仮説の順序を入れ替えた仮想LLR（+2.81）も同様に境界手前にとどまる。
異常は`crashes=2`、`rejected_moves=1`、`time_forfeits=0`だった。
クラッシュ2件はいずれもHaChuが2,001〜2,002手目で落ちたもので、hachu.cの棋譜配列上限`MAXMOVES 2000`が原因である。
拒否1件（ペア85第2局304手目）は、敵陣入域時に不成を選んだ歩兵が非捕獲で最奥段へ到達する成りをHaChuが拒否したもので、RULES.md第30条P5の典拠欄に注記した既知の規則差である。
3件はいずれも当該局のHaChuの負けとして算入されており、3件をすべてHaChuの勝ちへ振り替えた感度計算でもペンタノミアルは[128, 0, 71, 0, 1]、Elo −260、95%信頼区間[−303, −223]で結論は変わらない。
経過時間は26,852秒だった。

## 結論

95%信頼区間が0から大きく離れているため、この対局条件ではHaChuがminaseより明確に強い（−252 Elo）と結論する。

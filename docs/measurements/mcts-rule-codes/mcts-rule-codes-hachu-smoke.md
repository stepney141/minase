# HaChuの既定の規則でのMCTSとHaChuの対局の確認

## 目的

[対局用MCTSを全部の規則コードで探索できるようにする設計書](../../plans/archived/mcts-rule-codes.md)のフェーズ3として、成りの保留を理由とする拒否を外したminaseのMCTSと、中将棋の外部エンジンHaChuを、HaChuの既定の規則で10ペア対局させ、対局が異常なく成り立つかを確かめる。
MCTSは、AlphaZero型の対局用のモンテカルロ木探索であり、ニューラルネットワーク（以下、ネット）で局面を評価する。
成りの保留は、成れる着手で成らなかった駒が後で成れるかどうかを決める状態であり、HaChuの既定の規則が含む規則コードP5は、歩兵の成りの保留を追跡する。
変更の前のMCTSは、P5を含む規則セットを探索の前に拒否していたので、この規則ではHaChuと対局できなかった。
この対局は強さの測定ではない。確かめるのは、MCTSの探索のエラー、エンジンの異常終了、および時間切れが0件であることと、着手の拒否や不正着手があった場合に、その原因が成りの保留の扱いにないことである。

## コマンドライン

測定日は2026年11月13日である。
`<wt>`は後述のコミットの作業ツリー、`<net>`は後述のネットのファイル、`<キャッシュの親>`はTensorRTのエンジンのキャッシュを置くディレクトリの親である。
コマンドは、minaseのリポジトリのルートで実行した。
`minase match run`は、2つのエンジンを対局させて結果を集計する対局ハーネスであり、HaChuとはCECP（XBoardプロトコル）で通信する。
合法手と終局は、minaseの審判層（対局を管理して合法手と終局を裁定する層）が裁定する。

```console
source tools/train/zero/env.sh   # bashで実行する
export XDG_CACHE_HOME=<キャッシュの親>
<wt>/target/release/minase match run \
  --run-dir data/matches/mcts-rule-codes-hachu-smoke --seed 20261113 \
  --candidate commit:bc8fdee0cad64e0bcb54b442a29badcf897587ec --candidate-args '--search mcts' \
  --candidate-option NnModel=<net> --candidate-option NnBatchSize=16 \
  --candidate-limit nodes=800 \
  --baseline cecp:../hachu-debian/hachu --baseline-limit depth=2 \
  --rules L1,L3,P0,P5,P6,R2,E1,E2 --max-ply 1900 --concurrency 2 elo --pairs 10
```

1ペアは、ハーネスが初期局面から8〜12手を乱択で指した同じ開始局面で、先後を入れ替えた2局である。
手数の上限に達した局があると、ハーネスはそのペアを2局とも統計から除く（破棄ペア）。
HaChuは棋譜の配列の上限が2,000手で、それを超えると異常終了するので、手数の上限`--max-ply`を1,900手にした。

対局の前に、[外部エンジンは接続前に棋譜照合と着手転送で検証する](../../lessons/verify-external-engine-before-cecp-match.md)に従って、次の2つを確かめた。

- `scripts/hachu_selfplay.py`でHaChuの自己対局を3局（312手、931手、234手の計1,477手）生成し、`scripts/hachu_replay.py`で変更の後のminaseに読ませて再生した。審判層は、規則`L1,L3,P0,P5,P6,R2,E1,E2`で全手を合法と判定した。
- 2つのHaChuのプロセスに交互に指させ、着手をCECPのコマンド`usermove`で相手のプロセスへ80手転送した。どちらのプロセスも着手を拒否せず、同じ80手を審判層で再生すると、全手が合法であった。

## エンジン

候補（`--candidate`）は、ブランチ`mcts-rule-codes`のコミット`bc8fdee0cad64e0bcb54b442a29badcf897587ec`のバイナリに、起動引数`--search mcts`を渡して起動したMCTSであり、ハーネスがビルドしたバイナリのSHA-256は`03df4327e6bc3868de2a79caec3e80c7f35e307decd5dcf12937d383140ab34a`である。
思考の制限は1手800回のシミュレーションで、手の選択には対局用のPUCT（方策を探索項に使う上側信頼限界による手の選択）を既定の係数で使った。
ネットは、1回目の強化学習のサイクル32で得た10ブロック128チャネルのネットを、推論器が今受け付ける入出力の形のONNX形式のファイルへ書き出し直したものであり、SHA-256は`cdc64e02fbd3ff54a935775c1bfe7610e33b02e498d41270a55bc705792d76a6`である（書き出しの手順は[出力の一致の記録](mcts-rule-codes-invariance.md)にある）。

基準（`--baseline`）は、HaChu（Debianパッケージ収録のオリジナル版、コミットdf26f4a、`../hachu-debian`で`gcc -O2`によりビルド、バイナリのSHA-256は`10db1299f95626fe58875b1c24a1cee6acce0eee5fb42ed8b17ce1373a9dcbdf`）である。
規則オプションは既定の設定（“Okazaki rule” 無効、“Promote on entry” 有効、“Allow repeats” 無効）であり、思考の制限は深さ2（CECPの`sd 2`）である。
深さ2は、対局が成り立つことを確かめるために選んだ値であり、強さを測るときの深さは、[強さを測る固定の相手の設計書](../../plans/archived/mcts-fixed-opponents.md)で別に選ぶ。

規則は、HaChuの既定の設定に対応する`L1,L3,P0,P5,P6,R2,E1,E2`（[競技規則](../../rules/chu-shogi.md)第33条第7項）を、審判層とMCTSの双方に与えた。

## 環境

作業機（Intel Core Ultra 7 265KF、物理20コア、論理20コア、NVIDIA GeForce RTX 3060 Ti、ドライバ615.78.08）で、ONNX Runtime 1.31.1とTensorRT 10.14.1を使った。
候補の`Threads`は1、推論はTensorRT（FP16）、`NnBatchSize`は16である。HaChuは探索のスレッド数を報告しない。
候補の`USI_Hash`は既定の256 MB（MCTSは使わない）、HaChuの`memory`は256 MB、同時対局数は2、応答タイムアウトは120秒である。
測定のあいだ、ほかの棋力測定は走っていなかった。

## 結果

10ペア20局を実行し、有効ペアは9、破棄ペアは1であった。
破棄したのはペア2であり、第1局が手数の上限の1,900手に達した。第2局は終局まで指された。
MCTSの探索のエラー、クラッシュ、応答タイムアウト、時間切れ（`time_forfeits`）、および拒否着手（`rejected_moves`）はすべて0件であった。拒否着手は、審判層が合法とした相手の着手をエンジンが拒否した件数である。
審判層がエンジンの着手を合法手にないと判定した不正着手（`illegal_moves`）は、HaChuの側に1件あった。
経過時間は244.5秒である。

20局の終わり方は、HaChuの投了が14局、HaChuによる王駒の捕獲が4局、手数の上限が1局、HaChuの不正着手が1局であった。
1局の手数は271〜1,900手であった。
成りの保留のある局面は、20局の開始局面以後の12,657局面のうち、3局の11局面に現れ、そのうち4局面ではMCTSが手番であった。

強さの測定ではないが、記録の項目として得点も書く。
候補のペア得点（0、0.5、1、1.5、2）ごとの度数であるペンタノミアル度数は[1, 0, 2, 0, 6]、Eloの点推定は+217.6（95%信頼区間の下限は+37.7、上限は推定できない）であった。
不正着手のあったペア7（得点1）を除くと、度数は[1, 0, 1, 0, 6]になる。

### HaChuの不正着手の原因

不正着手は、ペア7の第2局（HaChuが先手）の1,155手目に起きた。
HaChuの入出力を記録する中継を挟んで同じシードで再実行すると、同じ対局が再現し、HaChuが返した着手は、獅子が動かずに手番を渡すじっと（CECPの表記で`@@@@`）であった。
この局面の先手の獅子には隣接する空升があるので、じっとは駒の動きとしては成立する（競技規則第12条第10項）。
しかし、1,155手目のじっとの後の局面（同じ盤面で後手の手番）は、953手目の後の局面と、駒の配置、手番、および先獅子の状態（直前の着手で獅子以外の駒が獅子を取ったかどうか）が同じであり、審判層は、既出の局面を再現する着手を禁じる規則R2によって、この着手を合法手から除いていた。

HaChuがこの着手を指した原因は、HaChuが反復の判定に使う対局の履歴が直近の200局面に限られることである。
HaChuは、300要素の配列`repStack`のうち先頭の200要素に対局の局面のハッシュ値を持ち、着手のたびに1つずつ前へ詰めて、最も古い要素を捨てる（`hachu.c` 171行、2547〜2550行）。
反復の判定は、可逆な着手が続いた手数`cnt50`まで2手刻みでこの配列をさかのぼるが、200手より前にあたる添字は負になって配列の外を指し、そこには対局の局面が入っていない（2287行）。
再現した局面は953手目の後の局面であり、1,155手目の後の局面から数えて202手前であった。
したがって、HaChuは、既定の設定（“Allow repeats” 無効）でも、200手より前の局面を再現する着手を指すことがある。

この食い違いは反復の規則R2の判定の差であり、成りの保留の扱いとは関係がない。
当該局には成りの保留のある局面が現れておらず、不正着手の局面にも成りの保留はなかった。
これまでに知られていたHaChuと審判層の反復の判定の差は、HaChuが局面の同一を駒の配置だけで判定するために、審判層の認めた着手をHaChuが拒否するものであった（[記録](../hachu-condition-grid/hachu-grid-time1of4.md)）。
今回の差は向きが逆で、審判層の禁じる着手をHaChuが指す。
ハーネスはこれをHaChuの反則負けとして数えるので、HaChuとの対局で強さを測るときは、不正着手（`illegal_moves`）の件数も確かめる必要がある。

## 結論

成りの保留を理由とする拒否を外したMCTSは、HaChuの既定の規則でHaChuと20局を最後まで対局し、MCTSの側の異常は0件であった。
HaChuの側の不正着手1件の原因は、HaChuの反復の判定が直近の200局面しか見ないことであり、成りの保留の扱いには原因がない。

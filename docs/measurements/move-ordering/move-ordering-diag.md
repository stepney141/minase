# move-ordering-diag

## 目的

[手の順序付けの改善](../../plans/archived/move-ordering.md)のフェーズ1として、現行masterで、βカットした手より前に読んだ手の部分木ノード数の和（先行費用W）を残り深さ別・先頭手の種別別に測り、候補1から候補6までの発動率（同じ判断の時点で現行と候補の判断を並べて比べ、判断が変わった割合）を数えて、各候補を進めるか見送るかと候補2の対象の変種を決める。

## コマンドライン

計測は本番の経路へ入れず、現行masterのコミット`b784fe5`へ計測差分を当て、フィーチャ`search-stats`を有効にしたビルドで行った。
差分は[ordering-diag.patch](move-ordering-diag/ordering-diag.patch)にあり、`search-stats`を無効にした構成では一切コンパイルされない。
計数はワーカーごとに保持し、探索の判断には使わない。
`bench`は環境変数`MINASE_ORDERING_DIAG`にパスを与えると全局面の合算をJSONへ書き、USIエンジンは同じ環境変数が設定されていると`bestmove`の直前に対局内の累計を`info string diag scope=game ...`で出す。

```console
git apply docs/measurements/move-ordering-diag/ordering-diag.patch
cargo build --release --bin minase
cargo build --release --features search-stats --bin minase --target-dir target/diag

# 項目1〜5（bench、深さ6を判定に使い、深さ8を補助として併記する）
MINASE_ORDERING_DIAG=bench-depth6.json taskset -c 3 target/diag/release/minase dev bench --depth 6
MINASE_ORDERING_DIAG=bench-depth8.json taskset -c 3 target/diag/release/minase dev bench --depth 8
python3 docs/measurements/move-ordering-diag/summarize_bench.py bench-depth6.json bench-depth8.json

# 項目6〜7（対局再生。引数は記録、対局数、シード、1手のノード数、並列数、出力）
export MINASE_ORDERING_DIAG=1
python3 docs/measurements/move-ordering-diag/replay_diag.py target/diag/release/minase \
  data/matches/fm-scale-spsa-stc 20 20271001 223000 8 replay-stc-223k.json --baseline target/release/minase
python3 docs/measurements/move-ordering-diag/replay_diag.py target/diag/release/minase \
  data/matches/fm-scale-spsa-ltc 10 20271002 574000 8 replay-ltc-574k.json --baseline target/release/minase
```

`bench`の出力全文は[bench-depth6.txt](move-ordering-diag/bench-depth6.txt)と[bench-depth8.txt](move-ordering-diag/bench-depth8.txt)、計数のJSONは[bench-depth6.json](move-ordering-diag/bench-depth6.json)と[bench-depth8.json](move-ordering-diag/bench-depth8.json)、集計表の印字は[summarize_bench.py](move-ordering-diag/summarize_bench.py)が行う。
再生の集計は[replay-stc-223k.log](move-ordering-diag/replay-stc-223k.log)と[replay-ltc-574k.log](move-ordering-diag/replay-ltc-574k.log)にある（各手の結果を含むJSONは12 MBを超えるので保存しない）。
再生スクリプトは[段階12の再生スクリプト](../strength-stage12/strength-stage12-activation-diag/replay_diag.py)の診断キーと集計を本診断のものへ改めたものである。

対局記録は、直近のLTCである[fm-scale-spsa-ltc](../fm-scale-spsa/fm-scale-spsa-ltc.md)の保存記録と、同じ測定のSTCである[fm-scale-spsa-stc](../fm-scale-spsa/fm-scale-spsa-stc.md)の保存記録から、固定シードで無作為に選んだ。
設計書は「直近のLTCの保存記録からSTC相当20局とLTC相当10局」と定めるが、1手のノード数を「その記録の思考時間の中央値」から決めるので、段階12の前例と同じく、STC相当はSTCの記録、LTC相当はLTCの記録から選んだ。
1手のノード数は、候補側の思考時間の中央値（STC 121.1ミリ秒、LTC 312.3ミリ秒。[records_profile.py](../strength-stage12/strength-stage12-activation-diag/records_profile.py)による）に、計測なしの現行masterの`bench`の毎秒探索ノード数（`taskset -c 3`、深さ6、5回の中央値1,838,818）を掛け、STC相当を223,000、LTC相当を574,000とした。
再生は、各局の初手から最終手まで、その手までの着手列を与えて探索し、`usinewgame`の後は1プロセスで表を保持する。

## エンジン

現行masterのコミット`b784fe5`に計測差分を当てたビルドである。
規則は`L0,P0,R1,E0`、`Threads`は1、`USI_Hash`は既定の256 MB、`bench`の置換表も既定の256 MBである。
対局ではないので、候補と基準の区別はない。

計測が受動的であることは、次の3点で確かめた。
計測ビルドの`bench`は、深さ6と深さ8の15局面すべてで、到達深さ、ノード数、最善手、および評価値が計測なしの現行masterのビルドと一致した（総ノード数は深さ6で715,206、深さ8で3,423,994）。
再生では、同じ対局を計測なしのビルドで再生して各手の`bestmove`と最終の`info`行のノード数を比べ、STC相当の20局9,528手とLTC相当の10局（手数は後述）で不一致は0件だった。
`cargo test --features search-stats`は570件、フィーチャなしは548件が通った。

## 環境

測定機はIntel Core Ultra 7 265KF（物理20コア、論理20コア）、`rustc 1.98.0`であり、2026年10月9日に測った。
同じ機械でlishogi Botのminaseが2プロセス動いていた。
`bench`はCPU 3へ固定した1スレッドの逐次実行、再生はSTC相当とLTC相当を8プロセスずつ、合計16プロセスで同時に実行した。
対局は行っていないので、ペンタノミアル度数、判定、破棄ペア数、異常件数、および`time_forfeits`は該当しない。
再生は固定ノード数なので経過時間は使わない。

### 項目2　候補1（静かな手のβカット時の捕獲履歴の減点）

| 指標 | 深さ6 | 深さ8 |
|---|---:|---:|
| 発動率（影の表で順序が変わる段／置換表の記録手を除いた捕獲手が2手以上ある段） | 12,636／76,711 = **16.47%** | 144,269／403,918 = **35.72%** |
| 更新の機会率（先に捕獲手を探索していた静かな手のカット／静かな手のカット） | 18,107／26,400 = 68.59% | 87,868／120,901 = 72.68% |
| 捕獲段のカット手の順位の変化（件数、前進、後退） | 52,114件、前進441（幅計451）、後退1,223（幅計1,437） | 282,751件、前進3,102（幅計4,082）、後退6,030（幅計8,917） |

影の表は、本番の捕獲履歴と同じ更新（置換表の記録手の捕獲によるカットを含む）に、静かな手がβカットしたときの探索済み捕獲手への`−min(depth², 上限)`の減点を加えたものである。
発動率は基準の5%を満たす。
ただし、実際にβカットを起こした捕獲手の順位は、影の順序では前進より後退の方が多く（深さ6で441対1,223、深さ8で3,102対6,030）、減点が成功する捕獲手を後ろへ動かす場合の方が多い。
この差は設計書が判定に使わない補助の指標であるが、採否の測定の前に知っておくべき不利な兆候である。

### 項目3　候補2（先頭の捕獲手のSEE判定によるkiller手の前置）

零窓ノードを残り深さと置換表の記録手の有無（置換表の記録手を先頭で探索したか）で分けた（深さ6）。

| d | 置換表の記録手 | 零窓ノード | 先頭がSEE負 | 先頭がSEE負で枝刈りされた | 先頭がSEE負かつ合法なkiller手あり（発動率） | killer手ありの先頭の部分木ノード数の合計（平均） | 同、現行では静かな手を生成する前にカットしたノード |
|---|---|---:|---:|---:|---:|---:|---:|
| 1 | なし | 72,810 | 16,413（22.5%） | 0 | 16,164（**22.20%**） | 37,718（2.3） | 4,881（30.2%） |
| 1 | あり | 9,092 | 776（8.5%） | 774 | 722（7.94%） | 2（0.0） | 40（5.5%） |
| 2 | なし | 5,441 | 1,454（26.7%） | 0 | 1,446（**26.58%**） | 8,462（5.9） | 229（15.8%） |
| 2 | あり | 7,295 | 1,338（18.3%） | 1,206 | 1,320（18.09%） | 272（0.2） | 99（7.5%） |
| 3 | なし | 350 | 134（38.3%） | 0 | 134（**38.29%**） | 365（2.7） | 6（4.5%） |
| 3 | あり | 4,994 | 543（10.9%） | 540 | 540（10.81%） | 3（0.0） | 2（0.4%） |

深さ8の発動率は、置換表の記録手がないノードで残り深さ1から順に25.88%、22.92%、39.41%、あるノードで13.79%、10.33%、12.01%であり、置換表の記録手があるノードではSEE負の先頭捕獲手の97〜99%が現行のSEE pruningで既に枝刈りされている。
したがって候補2が回避できる費用は、置換表の記録手がないノードにほぼ集中する。

費用の見積りには、診断で呼んだ`see_prunes(…, 0)`と`generate_quiets`の所要時間を`Instant`で測った値を使った。
深さ8の`bench`で、SEEは441,575回で1回あたり100ナノ秒、静かな手の生成は122,086回で1回あたり1,285ナノ秒、1ノードの費用は計測なしのビルドの毎秒探索ノード数1,838,818から544ナノ秒である。
候補2の費用は、対象ノードの捕獲段の先頭1手へのSEEと、先頭がSEE負で合法なkiller手があるのに現行では捕獲段のうちにカットしていたノードでの静かな手の生成の前倒しとし、回避できる見込みの費用は、その先頭の捕獲手単独の部分木ノード数の合計とした（深さ8）。

| 対象 | 回避できる見込みの費用 | 追加の費用 | 比 |
|---|---:|---:|---:|
| 置換表の記録手なし、残り深さ1 | 197,962ノード = 107.7ミリ秒 | SEE 355,324回 35.5ミリ秒 + 生成 31,975回 41.1ミリ秒 = 76.6ミリ秒 | 1.41 |
| 同、残り深さ2 | 34,779ノード = 18.9ミリ秒 | SEE 44,542回 + 生成 2,821回 = 8.1ミリ秒 | 2.34 |
| 同、残り深さ3 | 6,201ノード = 3.4ミリ秒 | SEE 5,026回 + 生成 155回 = 0.7ミリ秒 | 4.81 |
| 置換表の記録手あり、残り深さ1〜3 | 1,683ノード = 0.9ミリ秒 | 2.5ミリ秒 | 0.06〜0.67 |

SEEの回数は、その区分の捕獲段の先頭の件数（零窓でないノードを含む上界）である。
回避できる見込みの費用は、前置したkiller手が必ず先にカットすると仮定した上界であり、killer手がカットしなければその部分木が新たな費用になる。
この診断では、対象の母集団でkiller手がどれだけカットするかは測っていない。

### 項目4　候補3（静止探索の群内の順序への捕獲履歴の適用）

| 指標 | 深さ6 | 深さ8 |
|---|---:|---:|
| 発動率（捕獲履歴で先頭が変わる群／置換表の記録手を除いた捕獲手が2手以上ある群） | 58,116／283,703 = **20.48%** | 221,397／1,100,803 = **20.11%** |
| αを固定して`QsearchMoveLimit`の枠に入る捕獲手の集合が変わるノード／静止探索の手のループに入ったノード | 4,599／203,086 = 2.26% | 22,494／859,992 = 2.62% |

群の先頭は5回に1回変わるが、読む捕獲手の集合が変わるノードは2〜3%にとどまる。
群内の順序は、集合が同じでもβカットの早さを変えるので、集合の変化率だけで効果の上限を定めることはできない。

段階5の非ゼロ参照率（根ごとに初期化する表で0.73%と0.62%）に対し、持ち越す表ではSTC相当で5.75%と8.94%、LTC相当で17.06%と22.12%になった。

## 結論

候補1、候補2、候補3、候補4、候補5は発動率の基準5%を満たし、候補6の再診断も持ち越し状態で発動率44.6〜71.3%（counter move history）と61.3〜71.8%（continuation history）を示した。
候補2は、置換表の記録手がある零窓ノードではSEE負の先頭捕獲手が現行のSEE pruningで既に枝刈りされているので、対象を「置換表の記録手がない残り深さ1〜3の零窓ノード」に絞る。この変種では、回避できる見込みの費用が追加の費用を残り深さ1で1.4倍、残り深さ2で2.3倍、残り深さ3で4.8倍上回る。
候補1は発動率の基準を満たすが、実際にβカットした捕獲手を影の順序が後ろへ動かす件数が前へ動かす件数の約2倍であり、採否の測定では不利な兆候として扱う。候補4でも持ち越す表は成功した捕獲手を後退させる件数の方がやや多い（STC相当で1.06%対1.18%、LTC相当で0.93%対1.24%）。
候補3は群の先頭が20%で変わる一方、読む集合が変わるノードは2〜3%であり、設計書どおり参照探索との比較を経て自己対局で判定する。
候補6は設計書どおり本書では実装せず、表の寸法と初期化の費用を含む設計を別の設計書に委ねる。

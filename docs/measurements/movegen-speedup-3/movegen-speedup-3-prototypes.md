# 利きの逆引きと駒コードの復号の試作

## 目的

[第3期の設計書](../../plans/movegen-speedup-3.md)を改める前に、[再診断](movegen-speedup-3-rediagnosis.md)が候補に挙げた走りの逆引きの事前選別と、その代案を試作し、masterのコミット`b0ad2268`と比べて、探索結果が変わらないことと、命令数、サイクル数、および毎秒ノード数の変化を確かめる。
試作は設計書の段階を選ぶための予備の測定であり、段階の採否は設計書が定める規則で測り直す。

## コマンドライン

試作は4つあり、リポジトリの外に作ったworktreeに差分を当ててビルドした。
以下では、升にある駒を表す1バイトの値を駒コードと呼ぶ。駒コードは、対局者、成り、および駒種の番号を1バイトに詰めた値であり、空升と盤外にも専用の値がある。

- **試作A（走り駒集合）**：対局者と絶対方向ごとに、その方向へ走る駒がある升の集合（16個のビットボード）を`Position`に持たせ、駒を置く処理と除く処理で更新する。利きの逆引き`sliding_attackers_to`は、各方向について、対象升の利き線、逆方向の走り駒集合、および占有の3つの積が空ならその方向を飛ばし、空でなければ最初の遮蔽駒がその集合に属する場合に攻撃駒とする。[差分](movegen-speedup-3-prototypes/a-slider-sets.patch)。
- **試作B（走りの方向の駒コード表）**：局面には何も足さない。最初の遮蔽駒の駒コードから、照会した対局者の駒としての走りの方向マスクを、256要素の表で1回で引く。現行は、自駒の集合への所属の検査、駒コードから駒種への復号、駒種から動きの定義への変換、および動きの定義から方向マスクへの表引きを順に行う。[差分](movegen-speedup-3-prototypes/b-slide-mask-by-code.patch)。
- **試作C（Bに加えて、近傍走査の駒コード表）**：5×5近傍の自駒について固定利きが届くかを調べる走査で、駒コードから駒種のビットを256要素の表で1回で引く。[差分](movegen-speedup-3-prototypes/c-kind-bit-by-code.patch)。
- **試作D（Cに加えて、駒種の復号の表引き）**：駒コードから駒種を返す`PieceCode::kind`を、256要素の定数の表の1回の表引きにする。現行は、空升と番兵の検査、番号の取り出し、範囲の検査、および駒種の表引きを順に行う。この関数は探索と評価の全体から呼ばれる。[差分](movegen-speedup-3-prototypes/d-kind-by-code.patch)。

```console
git worktree add --detach /tmp/minase-ms3-proto b0ad2268
cd /tmp/minase-ms3-proto && git apply <差分>
CARGO_TARGET_DIR=<リポジトリ>/target/ms3-rediag/<試作名> cargo build --release --locked -p minase --bin minase
```

負荷は再診断と同じ2つであり、`bench`の深さ16と、各局面を2万ノードで探索する教師生成の2局である。
命令数、サイクル数、および分岐予測ミスの回数は、基準と試作を順に1回ずつ実行する組を、`bench`は5回、教師生成は3回繰り返して、次の形で測った。

```console
taskset -c 3 perf stat -x, -e cpu_core/cycles/u,cpu_core/instructions/u,cpu_core/branch-misses/u -- \
  <バイナリ> --protocol usi < bench16r1.usi
taskset -c 3 perf stat -x, -e cpu_core/cycles/u,cpu_core/instructions/u,cpu_core/branch-misses/u -- \
  <バイナリ> data selfplay generate --eval-file net.bin --output-dir <出力> --chunk-games 2 --games 2 \
  --seed 9010200000 --nodes 20000 --random-moves 0 --concurrency 1 --hash-mb 16 --allow-dirty
```

`bench16r1.usi`は、`RuleSet JCSA`、`EvalFile`、`isready`、`bench depth 16 threads 1 repetitions 1`、`quit`の5行である。
比較は3回に分けて行い、1回目は基準、試作A、試作Bを、2回目は基準、試作B、試作Cを、3回目は基準、試作C、試作Dを同じ組の中で測った。
試作Aの毎秒ノード数は、`repetitions 3`にした`bench`の中央値の行を、基準と交互に5回ずつ読んだ。

## エンジン

基準はmasterのコミット`b0ad2268`であり、試作はそれに各差分を当てたものである。
ネットは探索の測定の標準のP型のネット（SHA-256は`37054c9e49c9218bb18efdd1814fe1b298de5cbfc9c14352f6ad6eaecbb70dea`）をすべてに使った。
`bench`の規則セットは`JCSA`、教師生成の規則セットは`lishogi`である。
ビルドはリポジトリのrelease設定である。

## 環境

測定機はIntel Core Ultra 7 265KF（性能コア8、高効率コア12、スレッドは計20）で、Linux `6.18.63-3-lts`、Rust `1.100.0`である。
探索ワーカーは1であり、すべての実行を性能コアの論理CPU 3に固定した。
2026年11月24日の2時57分から3時36分に測定した。
同じ機械で、対局の測定、SPSA、および教師生成は動いていなかった。lishogiのBotのコンテナは起動したままだった。
3回目の比較は、基準のサイクル数が1回目と2回目より約1.3%（教師生成は約2.5%）多く、測定機の状態が違っていた。原因は確かめていない。このため、試作の値は同じ回の基準とだけ比べる。

## 結果

探索結果はすべての試作で一致した。
`bench`の深さ16の局面別の行（ノード数、最善手、評価値）は15局面とも基準と同じであり、教師生成のファイルのSHA-256も同じだった（`63c0bbe4a8c1775e…`）。

サイクル数と分岐予測ミスは中央値で比べた。命令数は実行ごとの差が100万分の1以下で再現する。

|---|---|---:|---:|---:|---:|---:|

| B（走りの方向の駒コード表） | 1回目 | −1.85% | −2.16% | −1.565% | −1.770% | −5.4% |

各回の基準のサイクル数の中央値は、`bench`が18,251,158,192、18,204,674,987、18,454,261,555であり、教師生成が105,828,842,667、105,942,746,744、108,567,923,381である。

5回のうち1回は基準を下回り、増分は基準の5回の幅（最大と最小の差を中央値で割った値）の1.14%より小さかった。

### 設計書の範囲の外の試作

再診断で探索時間の19%を占めたNNUEの後段の計算についても、積和の関数`affine`を1つだけ書き換える試作を同じ手順で測った。
現行の`affine`は、8ビットの重みと入力を1個ずつ32ビットへ広げて積を足す形で書かれている。
試作は、入力が0から127、重みが符号つき8ビットで、積が16ビットに収まることを使い、積を16ビットで求めて2個ずつ足してから32ビットの和へ加える形にした。
探索結果は一致したが、命令数は`bench`で7.3%、教師生成で6.9%増え、サイクル数は`bench`で4.9%（3回の中央値）、教師生成で5.4%（2回の平均）増えた。
コンパイラが出した機械語は、書き換えの前と同じく、8ビットを32ビットへ広げる命令（`vpmovsxbd`と`vpmovzxbd`）を使っていた。
この試作の差分は保存していない。書き換えた関数は次のとおりである。

```rust
fn affine(bias: i32, weights: &[i8], input: &[u8]) -> i32 {
    let pairs = weights.len() / 2 * 2;
    let mut sum = bias;
    for (w, x) in weights[..pairs].chunks_exact(2).zip(input[..pairs].chunks_exact(2)) {
        let a = i16::from(w[0]) * i16::from(x[0]);
        let b = i16::from(w[1]) * i16::from(x[1]);
        sum += i32::from(a) + i32::from(b);
    }
    for (&w, &x) in weights[pairs..].iter().zip(&input[pairs..]) {
        sum += i32::from(w) * i32::from(x);
    }
    sum
}
```

## 結論

走り駒集合（試作A）のサイクル数の減少は約1%にとどまり、局面に状態を足さない駒コード表（試作B）の約2%に及ばない。駒コードの復号を表引きにまとめる変更は、利きの逆引きの2箇所と`PieceCode::kind`を合わせた試作Dで、探索結果を変えずにサイクル数を`bench`で4.4%、教師生成で5.1%減らした。
1%前後の差は毎秒ノード数の交互測定5回の幅に収まるので、段階の採否はサイクル数の対比較で判定する必要がある。

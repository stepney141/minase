# 第3期高速化の再診断（bench深さ16と教師生成）

## 目的

[第3期の設計書](../../plans/archived/movegen-speedup-3.md)は2026年9月17日に起案され、その後に評価関数がNNUE（着手ごとに差分で更新できる小さなニューラルネット）へ替わり、静止探索（駒を取る手だけを読み進める探索の末端）と利きの逆引きも作り直された。
本測定は、2026年11月24日のmasterと探索の測定に使う標準のネットで、探索時間の内訳と、利きの逆引き、静的交換評価（SEE、到達升での駒の取り合いを見積もる評価）、および静止探索の候補の生成で省ける処理の件数を取り直し、設計書を改める根拠にする。

## コマンドライン

負荷は2種類を使った。
1つ目は、固定の15局面を固定の深さで探索するUSIの独自コマンド`bench`の深さ16であり、対局中の探索の代わりとする。
2つ目は、自己対局の各局面を2万ノードで探索する教師生成の2局であり、NNUEの教師を作るときの探索に当たる。

```console
printf 'setoption name RuleSet value JCSA\nsetoption name EvalFile value net.bin\nisready\nbench depth 16 threads 1 repetitions 3\nquit\n' \
  | taskset -c 3 <バイナリ> --protocol usi
taskset -c 3 <バイナリ> data selfplay generate --eval-file net.bin --output-dir <出力> --chunk-games 2 --games 2 \
  --seed 9010200000 --nodes 20000 --random-moves 0 --concurrency 1 --hash-mb 16
```

基準の速さは、上の2つを`perf stat -x, -e cpu_core/cycles/u,cpu_core/instructions/u`の下で3回ずつ実行して測った。`bench`のサイクル数と命令数は`repetitions 1`の実行で測り、毎秒ノード数は`repetitions 3`の中央値の行を3回読んだ。

関数別の内訳は、フレームポインタを残したビルドを次の形で採取し、[教師生成の高速化の付属資料](../teacher-generation-speedup/teacher-generation-speedup-engine/)の`inline_prof.py`でインライン展開まで解決して集計した。
採取の周期は、`bench`が500,009サイクル、教師生成が2,000,003サイクルである。

```console
CARGO_PROFILE_RELEASE_DEBUG=1 CARGO_TARGET_DIR=target/ms3-rediag/prof \
  RUSTFLAGS="-C target-cpu=native -C llvm-args=-inline-threshold=1000 -C force-frame-pointers=yes" \
  cargo build --release --locked -p minase --bin minase
taskset -c 3 perf record -o <記録> --user-callchains --call-graph fp -e 'cpu_core/cycles,period=<周期>/u' -- <上の2つのコマンド>
python3 inline_prof.py <記録> <バイナリ> --top 110
python3 inline_prof.py <記録> <バイナリ> --callers '<関数の正規表現>'
python3 inline_prof.py <記録> <バイナリ> --tree '<関数の正規表現>' --tree-depth 4
```

件数は、[診断差分](movegen-speedup-3-rediagnosis/diagnostic.patch)を当てた別のworktreeのビルドで数えた。
診断差分は件数のカウンタだけを加え、プロセスの終了時に標準エラーへ出力する。
`bench`の件数は`repetitions 1`の1回分である。

```console
git worktree add --detach /tmp/minase-ms3-rediag b0ad2268
cd /tmp/minase-ms3-rediag && git apply <診断差分>
CARGO_TARGET_DIR=<リポジトリ>/target/ms3-rediag/diag cargo build --release --locked -p minase --bin minase
```

カウンタの全値は[benchの件数](movegen-speedup-3-rediagnosis/counts-bench16.txt)と[教師生成の件数](movegen-speedup-3-rediagnosis/counts-teacher.txt)に、関数別の集計は[benchの内訳](movegen-speedup-3-rediagnosis/profile-bench16.txt)、[benchの呼び出し元と呼び出し先](movegen-speedup-3-rediagnosis/profile-bench16-breakdown.txt)、[教師生成の内訳](movegen-speedup-3-rediagnosis/profile-teacher.txt)、および[教師生成の呼び出し元と呼び出し先](movegen-speedup-3-rediagnosis/profile-teacher-breakdown.txt)にある。
件数のファイルで値が0の`see_from_picker`と`pk_tt_ret`は、数える箇所を入れていないカウンタである。

## エンジン

対象はmasterのコミット`b0ad2268`である。
ネットは[NNUEの評価関数の手引き](../../guides/evaluation-nnue.md)が探索の測定の標準とするA型のネット（SHA-256は`37054c9e49c9218bb18efdd1814fe1b298de5cbfc9c14352f6ad6eaecbb70dea`）であり、構成は`Features=P(Friend)[13680->256x2]`、後段は`AffineTransform[16<-512]`、`AffineTransform[32<-30]`、`AffineTransform[1<-32]`の3層である。
`bench`の規則セットは`JCSA`に固定されており、教師生成の規則セットは`lishogi`（`L1,L2,P0,P3,R1,E1,E3`）に固定されている。
ビルドはリポジトリのrelease設定（`target-cpu=native`、インライン閾値1000、LTO有効、`codegen-units=1`）である。
基準の速さを測ったバイナリのSHA-256は`fb8c569e4410fa91…`である。

## 環境

測定機はIntel Core Ultra 7 265KF（性能コア8、高効率コア12、スレッドは計20、メモリ30 GiB）で、Linux `6.18.63-3-lts`、Rust `1.100.0`、perf `7.3.4`である。
探索ワーカーは1、教師生成の置換表は16 MiBであり、すべての実行を性能コアの論理CPU 3に固定した。
2026年11月24日の2時20分から2時50分に測定した。
測定の前に、対局の測定、SPSA、および教師生成が同じ機械で動いていないことを確かめた。開始時の1分の負荷平均は0.45であり、lishogiのBotのコンテナは起動したままだった。

利きの逆引きの呼び出し元は、SEEが6.2%（教師生成は7.5%）、王手判定が1.0%（0.8%）、王駒への攻撃判定が0.5%（0.5%）、獅子の足の判定が0.2%（0.2%）である。
SEEの呼び出し元は、静止探索が4.2%（5.7%）、主探索の本体が2.5%（3.0%）、手選択器が0.8%（0.8%）、静かな王手の採点が0.4%（0.3%）である。
主探索の捕獲手の生成は、静止探索の初期化と同じ関数`capture_targets_without_special`で通常駒の捕獲可能升を求めており、この関数とその呼び出し先は3.6%（教師生成は5.0%）を使う。

設計書が対象とする処理の割合は、主な呼び出しの重なりを除いて足すと約28%（教師生成は約32%）になる。獅子の足の判定のように、足した処理の内側から呼ばれる利きの逆引きが一部に残るので、この値は概算である。
足したのは、SEEの8.0%（9.7%）、SEE以外から呼ぶ利きの逆引きの1.7%（1.6%）、静止探索の初期化の6.4%（7.7%）、静止探索の群の生成と取り出しの2.2%（2.2%）、主探索の捕獲手の生成の4.0%（3.9%）、非捕獲手の生成の2.4%（3.3%）、王手判定から利きの逆引きを除いた2.4%（1.9%）、および合法性の判定の1.2%（1.4%）である。

自己時間が最も大きい関数は、後段の層の積和`affine`（9.0%、教師生成は9.1%）と置換表の読み出し`unpack_critical`（9.0%、7.3%）である。
`affine`は`dense`へインライン展開されており、その機械語は8ビットの重みと入力を`vpmovsxbd`と`vpmovzxbd`で32ビットへ広げてから積和を取っている。
1回の評価で第1層は16×512個の積を計算する。

升の駒を表す1バイトの値（駒コード）から駒種などを求める関数の、呼び出し先を含む割合は次のとおりである。
駒コードから駒種を返す`PieceCode::kind`が1.3%（教師生成は1.5%）、升の駒コードを返す`Position::piece_at`が1.1%（1.3%）、駒コードから駒状態を返す`piece_state`が1.3%（1.6%）、駒価値を返す`piece_value`が1.1%（1.1%）である。
教師生成での`PieceCode::kind`の呼び出し元は、`piece_state`が0.60%、駒を置く処理が0.15%、履歴表の添字の計算が0.10%、SEEが0.08%であり、残りは補正表の鍵の計算や利きの逆引きなどへ0.07%以下ずつ分かれる。

## 結論

NNUEの後段の計算が探索時間の約19%を、置換表の照会が7〜9%を占めており、設計書の対象である利きの逆引き、SEE、捕獲手と非捕獲手の生成、および王手判定は、主な重なりを除いた概算で、合わせて探索時間の約3割である。
件数の上で省ける余地が確認できたのは、走りの逆引きの方向の9割で利き線上に該当する走り駒がいないことと、特殊駒の候補の3分の1が生成の後に除かれることの2つである。

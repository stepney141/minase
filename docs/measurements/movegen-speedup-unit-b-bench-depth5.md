# 単位B（静止探索の探索専用捕獲生成）のbench比較（深さ5）

## 目的

静止探索の捕獲生成を、捕獲升と整列キーの受け渡し、規則判定の早期終了、バッファ再利用、入口の閾値による対象除外、および価値グループ順の段階生成へ改めた単位Bが、照合参照コミットと局面別のノード数、最善手、探索値で一致するかを確かめ、基準コミットと参照コミットに対する速度比を測って採否を決める。あわせて、検証点ごとの速度と、通常駒の生成方式（駒別生成と対象升からの逆引き）の比較を記録する。

## コマンドライン

```console
scripts/bench_compare.py --reference 5c1db50 --baseline 0e3dfa6 --depth 5 --repetitions 3 --threads 1
```

検証点の比較は、各状態のソースを別ディレクトリへ展開して通常のrelease設定でビルドし、`bench --depth 5 --threads 1 --repetitions 3`の中央値を同じ時間帯に測った。

## エンジン

基準はコミット`0e3dfa6b59c489049c15e2cd00455e190a3fbf52`（master）、参照は照合参照コミット`5c1db5000baea831ce53d994cbf664ee12a0e5e6`である。
候補は単位A採用版（`283a0a6`）に対して、`src/core/movegen/search_captures.rs`（探索専用の候補型と、特殊駒の全捕獲生成、通常駒の利きを1回だけ求める登録と対象升への出力、置換表の手の捕獲検査）、`src/core/attacks/tables.rs`（遮蔽なしの到達範囲の表）、`src/search/mod.rs`（plyごとの再利用バッファ、駒価値の順位の前計算、順位ビット集合と特殊駒候補のマージによる段階生成）、および`src/eval/pst.rs`（駒状態と駒価値の公開）を加えたものである。
`bench`は規則セット`engine-default`を固定で使う。

## 環境

測定機はIntel Core Ultra 7 265KF（物理20コア、論理20コア）であり、2026年9月15日に他の負荷を走らせずに1スレッドで測った。
置換表は既定容量を1個使い回し、局面ごとの`clear()`は計測区間外である。

## 結果

局面別の深さ、ノード数、最善手、探索値は15局面すべてで参照と一致した。

| 版 | 総ノード数 | 経過（中央値） | NPS（中央値） |
|---|---:|---:|---:|
| 基準 0e3dfa6 | 1,268,805 | 0.830秒 | 1,528,164 |
| 参照 5c1db50 | 1,268,607 | 0.853秒 | 1,487,154 |
| 候補（単位B） | 1,268,607 | 0.568秒 | 2,232,661 |

候補の基準比はNPS 1.461倍、ノード数 0.9998倍、経過時間 0.684倍である。
候補の参照比はNPS 1.501倍、ノード数 1.0000倍、経過時間 0.666倍である。
単位Aの採用版は参照比1.344倍だったので、単位Bの上乗せは参照比で約11.7%である。

検証点ごとの経過（中央値）と参照比は次のとおりである。いずれも局面別の出力は参照と一致した。

| 検証点 | 経過（中央値） | 参照比 |
|---|---:|---:|
| 単位A採用版（比較の起点） | 0.635秒 | 1.344倍 |
| 段階生成の初版（グループごとに通常駒を全走査し、置換表の手を全合法手生成で検査） | 0.736秒 | 1.159倍 |
| 通常駒の利きをノードごとに1回だけ計算し、置換表の手を1駒の捕獲生成で検査 | 0.630秒 | 1.328倍 |
| 同じ状態で通常駒を対象升からの逆引きで生成 | 0.703秒 | 1.190倍 |
| 駒価値の順位を前計算してグループ構築の整列と線形探索を除いた採用版 | 0.568秒 | 1.501倍 |

段階生成の初版はperfの包含時間で`generate_ordinary_captures`が30.7%を占め、グループごとの通常駒の全走査が利き計算を繰り返していた。
利きを1回だけ計算した版でも、`QsearchBuffers::initialize`の包含時間33.7%のうち相手駒の走査、グループの線形探索、およびグループの整列が約14%を占め、生成件数の削減（[打ち切り位置の診断](movegen-speedup-stage-cutoff-counts.md)では63.6%）を相殺していた。
逆引き方式は、打ち切りが起きないノードで全グループの対象升に逆引きを行うため、駒別生成より遅かった。

確保回数は、`bench`に確保を数えるグローバルアロケータを入れ、生成と整列を行う`QsearchBuffers::reset`と`next`の内側だけを数える診断ビルドで測った。
1回の`bench`あたりの確保は深さ3で1,193回、深さ5で1,670回、深さ6で2,015回であり、同じ深さでは実行間で一定だった。
ノード数は深さ3から6で188,716から2,865,635へ増えるので、確保はノード数に比例せず、探索ごとに新しく作る探索ワーカーのplyごとのバッファが各plyで最初に使われるときの容量拡張だけである。
参照コミットの同じ診断（全確保）は1回の`bench`あたり2,619,780回だった。

## 結論

単位Bは参照と局面別に一致し、NPSを基準比1.461倍（単位Aから参照比で約11.7%の上乗せ）にしたので採用し、通常駒の生成方式は駒別生成を採る。

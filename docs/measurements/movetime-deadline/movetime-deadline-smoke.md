# 固定時間の探索の締切と途中結果の煙試験（フェーズ3）

## 目的

[固定時間（movetime）の探索の締切と途中結果](../../plans/movetime-deadline.md)の候補と変更前のコミットを、本測定と同じ選別条件（`movetime=300,timemargin=100`）と判定条件（`movetime=1000,timemargin=100`）で24ペアずつ対局させ、フェーズ3の煙試験の判定基準（時間切れ・異常・拒否着手が0件、候補の思考時間と`movetime`の比の中央値が0.95以上、`movetime`を超えた量の最大値が50 ms以下、手数帯ごとの完了深さが基準を下回らない）を確かめ、本測定の所要時間を見積もる。

## コマンドライン

```console
minase match run --run-dir data/matches/movetime-deadline-smoke-300 --seed 6100000000 \
  --candidate commit:de7b151af8c0b3193c3f51aae5e81f466dafc5a1 --baseline commit:b62e83d434c932a4775eaab296680b7dd0697ce2 \
  --each movetime=300,timemargin=100 --concurrency 12 elo --pairs 24
minase match run --run-dir data/matches/movetime-deadline-smoke-1000 --seed 6110000000 \
  --candidate commit:de7b151af8c0b3193c3f51aae5e81f466dafc5a1 --baseline commit:b62e83d434c932a4775eaab296680b7dd0697ce2 \
  --each movetime=1000,timemargin=100 --concurrency 12 elo --pairs 24
python3 scripts/movetime_deadline/smoke_profile.py data/matches/movetime-deadline-smoke-300
python3 scripts/movetime_deadline/smoke_profile.py data/matches/movetime-deadline-smoke-1000
```

途中結果が着手を変えた割合は対局記録から分からないので、[発動の確認](movetime-deadline-activation.md)と同じ200局面（`byoyomi-a-smoke-long`の対局記録からシード1で抽出したもの）を、基準と候補のバイナリに同じ`go`引数で探索させて比べた。

```console
python3 scripts/lishogi_byoyomi_usage/paired_depth_probe.py data/matches/byoyomi-a-smoke-long <基準> <候補> "movetime 300" 200
python3 scripts/lishogi_byoyomi_usage/paired_depth_probe.py data/matches/byoyomi-a-smoke-long <基準> <候補> "movetime 1000" 200
```

集計の出力は[movetime-deadline-smoke/](movetime-deadline-smoke/)にある。

## エンジン

候補は`de7b151a`（フェーズ2の後半、バイナリのSHA-256は`2349660f…`）、基準は`b62e83d4`（フェーズ2の直前、エンジンのコードはmasterの`e600faa5`と同一、SHA-256は`16cac49a…`）である。
規則セットは`engine-default`、両者とも`Threads=1`、`USI_Hash`は256 MBである。
runnerは`de7b151a`のminase 2.5.0（SHA-256は`62b8f181…`）である。

## 環境

測定機とは別の機械ryzen0で実行した。
測定機（Intel Core Ultra 7 265KF、物理20コア）は、別のプロジェクトの計算が約16コアを使い続け、lishogiのBotも4スレッドで対局していたので、同時12対局の時間制御の測定には使えなかった。
ryzen0のCPUはAMD Ryzen Threadripper 2990WX（物理32コア、論理64コア）、メモリは125 GB、コンパイラはRust 1.99.0である。
runnerは物理コア数を8と誤って検出する（`invocations.json`の`physical_cores`）が、同時対局数は`--concurrency 12`で明示した。
測定中、ryzen0にはほかの計算がなかった。
ただし、300 msの煙試験の前半には、同じ機械で上記の局面比較（1プロセスずつ交互に探索）を並行して走らせた。

|---|---|---|---:|---:|---:|---:|
| 300 ms | [1, 2, 10, 2, 9] | ＋120.4（＋34.0〜＋224.5） | 0 | 0 | 0 | 601秒 |

## 判定基準の確認

300 msの条件は、4つの判定基準をすべて満たした。

1,000 msの条件は、時間切れ・異常・拒否着手が0件で、候補の思考時間と`movetime`の比の中央値も1.011だったが、残る2つの基準を満たさなかった。
次の調査により、どちらも候補の変更とは関係しないと判断した。

1つ目は、`movetime`を超えた量の最大値が候補70.2 ms、基準69.2 msで、50 msを超えたことである。
40 msを超えた手は全24,767手のうち4手（候補3手、基準1手）で、いずれも測定の開始時に同時に始まった12局のうちの2局（ペア5とペア6の1局目）にあり、局内の2〜29手目だった。
エンジンの起動直後の影響を除くために各局の最初の6手を除くと、残る24,479手では、超過の99.9パーセンタイルが30.1 msで、40 msを超えた手は上記の1手だけだった。
このため、測定の開始時に多数のエンジンが一斉に起動したことによる一過性の遅れと判断した。
候補と基準の双方に同じ程度に出ており、`timemargin`の100 msには30 msの余裕が残る。
設計書の「原因を調べてから本測定へ進む」に従い、`timemargin`は変えずに本測定へ進む。

2つ目は、手数200以上の帯で候補の完了深さの平均（21.92）が基準（22.28）を下回ったことである。
この帯の15,926手のうち3,896手は、手数上限に達して破棄されたペア6の1局目（開始局面までの11手を除いて4,085手）のものだった。
この1局では、両者が深さ30前後まで読む局面が続き、基準の平均が32.64、候補の平均が29.97だった。
対局の各手番は候補と基準で別の局面を探索するので、1局に偏った帯の平均は局面の違いを反映しやすい。
対局ハーネスがGSPRTやEloの統計から破棄ペアを除くのと同じく破棄ペアを除くと、すべての帯で候補の完了深さが基準より0.39〜0.64大きい。
同じ局面で比べた局面比較でも、候補の完了深さは300 msで0.520、1,000 msで0.675大きく、差は標準誤差の7倍以上だった。

## 所要時間の見積り

同時12対局では、300 msで1時間に約173ペア、1,000 msで1時間に約45〜52ペアを指す。
選別条件は150ペアで約1時間、1,000ペアで約6時間、上限の3,000ペアで約17時間である。
判定条件は150ペアで約3時間、1,000ペアで約20時間である。
[秒読みつき時計の計画](../../plans/archived/byoyomi-time-usage.md)の同種の測定と同じく、両条件とも150ペア前後で`H1`（候補が有意に強いという判定）となれば、合計で約4時間である。

## 結論

300 msの条件は判定基準をすべて満たし、1,000 msの条件で満たさなかった2つの基準は、測定の開始時の一斉起動と破棄された1局による偏りと判断したので、選別条件（300 ms）の本測定へ進み、その結果に応じて判定条件（1,000 ms）の本測定へ進む。

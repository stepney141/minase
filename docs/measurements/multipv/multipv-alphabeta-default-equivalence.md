# αβ探索がN本の読み筋を読むようにした変更の、既定値1での出力、時間管理の判断、および速さの一致

## 目的

[MultiPVの設計書](../../plans/multipv.md)のフェーズ2として、αβ探索が根の上位N手の読み筋を読むようにした変更が、既定値1でエンジンの出力、探索の判断、および速さを変えないかを判定する。
MultiPV（multiple principal variations）は、根の上位N手の読み筋を同時に示す機能であり、αβ探索はNが2以上のとき、反復深化の各深さで根の探索をN回繰り返す。
Nが1のときは2回目以降に関わる処理をすべて飛ばすので、探索の手順は変更の前と同じになるはずである。
判定には、設計書の「検証」の節の1.、2.、3.、および5.を使う。
1.はαβ探索の`bench`、2.はUSIの`go depth`と`go nodes`、3.は持ち時間つきの探索の時間管理、5.は`bench`の速さの一致である。

## コマンドライン

測定日は2026年11月17日である。
`<wt>`は変更の後の作業ツリーであり、比べる相手は変更の前のmasterのコミット7a0b2676である。

検証1は、[読み筋の列へ改めたイベントの記録](multipv-events-default-equivalence.md)と同じく、`scripts/bench_compare.py`の参照、基準、および親のすべてに7a0b2676を与え、交互測定1回、各回の`bench`の繰り返し2回で実行した。
検証2と検証3の手順も、同じ記録の「コマンドライン」の節と同じである。
検証3の一時的な診断は、変更で関数の引数と戻り値の形が変わったので、診断が探索を呼ぶ箇所と、出力の行を入れる箇所だけを新しい形に合わせ、出す欄は変更の前と同じにした。

検証5は、ほかの負荷のない状態で、性能コアの論理CPU 3に固定して実行した。

```console
cd <wt>
taskset -c 3 python3 scripts/bench_compare.py --reference 7a0b2676 --baseline 7a0b2676 --parent 7a0b2676 \
  --depth 9 --threads 1 --rounds 3 --repetitions 3
```

`bench_compare.py`は、基準、参照、親、および候補の4つのバイナリを交互に3回ずつ測り、各回では`bench`を3回実行して毎秒ノード数の中央値をとる。
親比は候補と親の毎秒ノード数の比であり、分解能は、親の各回の中央値の最大と最小の差を、それらの中央値で割った割合である。
採否の条件は、親比と1との差が親の分解能以内に収まることである。

## エンジン

変更の前のバイナリは、`scripts/bench_compare.py`がコミット`7a0b267612ea063093bf6622f59069687648456a`を展開して`cargo build --release`でビルドしたものであり、SHA-256は`deb9ae5f4fb2850e0174ba7a7e0c39eb494c0c36e4895693890a86b5408349a4`である。
変更の後のバイナリは、ブランチ`multipv`のコミット`5cdc335b`の作業ツリーを同じ設定でビルドしたものであり、SHA-256は`af370d13dcc18b8e9623388984b81e9c2ebf734607a75753e37c199cd2415677`である。
検証1〜3はコミットの前の作業ツリーで行い、コミットの後に作業ツリーからビルドし直したバイナリのSHA-256は、検証2に使ったバイナリと同じであった。

## 環境

作業機（Intel Core Ultra 7 265KF、物理20コア、論理20コア）で測った。
検証5を始める前に、lishogiのBotの対局、ほかの棋力測定、およびビルドが動いていないことを確かめた。
検証1〜3は出力の一致だけを判定するので、負荷の影響を受けない。

## 結果

4つの検証のすべてで、変更の前後の出力が一致し、速さの差は分解能の内側に収まった。

検証1では、`bench_compare.py`が「15 positions agree」と報告し、15局面の局面ごとの深さ、ノード数、最善手、および評価値が全行一致した。
ノード数の合計は、どちらも136,697である。

検証2では、握手列の`MultiPV`の宣言の1行を除き、`readyok`以後の出力が30回の`go`のすべてで、変更の前のバイナリと一致した。
`go nodes`の停止の理由と最後の`info`の行の深さは、[読み筋の列へ改めたイベントの記録](multipv-events-default-equivalence.md)の表と同じである。

検証3では、診断の出力5,084行が、変更の前の診断の出力と全行一致した。
診断の実行時間は932秒であった。
48回の持ち時間つきの探索の停止の理由、完了した深さ、時間管理の伸縮の入力、および補助ワーカーの24回の単独の実行の結果も、変更の前と同じである。

検証5の結果は次のとおりである。
毎秒ノード数は、各回の中央値の中央値である。

| バイナリ | 毎秒ノード数 | 各回の中央値 | 分解能 |
|---|---|---|---|
| 基準（7a0b2676） | 1,062,519 | 1,062,519、1,067,247、1,062,358 | 0.46% |
| 参照（7a0b2676） | 1,064,986 | 1,065,446、1,064,986、1,064,946 | 0.05% |
| 親（7a0b2676） | 1,063,726 | 1,063,726、1,054,062、1,063,927 | 0.93% |
| 候補 | 1,061,673 | 1,063,199、1,061,673、1,057,368 | 0.55% |

候補の親比は0.9981であり、1との差の0.19%は親の分解能0.93%の内側に収まった。
ノード数の比は1.0000である。

## 結論

αβ探索がN本の読み筋を読むようにした変更は、既定値1で、`bench`の結果、USIの`go depth`と`go nodes`の出力、持ち時間つきの探索の時間管理の判断、および`bench`の速さを変えない。

# 読み筋の列へ改めたイベントの、既定値1での出力と時間管理の判断の一致

## 目的

[MultiPVの設計書](../../plans/multipv.md)のフェーズ1として、探索から通信層へ渡すイベントの読み筋を1本から順位つきの列へ改め、USIのオプション`MultiPV`を宣言した変更が、既定値1でエンジンの出力と探索の判断を変えないかを判定する。
MultiPV（multiple principal variations）は、根の上位N手の読み筋を同時に示す機能であり、このフェーズでは探索はどちらの方式もまだ1本だけを返す。
判定には、設計書の「検証」の節の1.〜4.を使う。
1.はαβ探索の`bench`、2.はαβ探索のUSIの`go depth`と`go nodes`、3.は持ち時間つきの探索の時間管理、4.はAlphaZero型探索のPV-MCTS（方策と価値を出すネットで木を広げるモンテカルロ木探索）の`go nodes`の一致である。

## コマンドライン

測定日は2026年11月17日である。
`<wt>`は変更の後の作業ツリー、`<base>`は変更の前のmasterのコミット7a0b2676を`git archive`で展開してビルドしたバイナリ、`<cand>`は`<wt>`でビルドしたバイナリである。

検証1は、`scripts/bench_compare.py`の参照、基準、および親のすべてに変更の前のコミットを与えて実行した。
このフェーズでは速さを判定しないので、交互測定は1回、各回の`bench`の繰り返しは2回とした。

```console
cd <wt>
python3 scripts/bench_compare.py --reference 7a0b2676 --baseline 7a0b2676 --parent 7a0b2676 \
  --depth 9 --threads 1 --rounds 1 --repetitions 2
```

検証2では、2つのバイナリを`--protocol usi`で起動し、`RuleSet`を`JCSA`、`Threads`を1として、`bench`の15局面（`crates/minase/src/diagnostics/bench.rs`の`BENCH_POSITIONS`）のそれぞれに`usinewgame`、`position sfen <局面> - 1`、および`go`を送り、`bestmove`までの出力を集めた。
`go`は局面ごとに`go depth 9`と`go nodes <n>`の2つであり、nは変更の前のバイナリの`bench depth 9 threads 1`でその局面に要したノード数の半分である。
出力の`time`と`nps`の値は、実行のたびに変わるので伏せてから比べた。

検証3では、2つの作業ツリーのαβ探索の単体試験の場所に、同じ内容の一時的な診断を置いて、`cargo test --release`で実行した。診断はコミットしていない。
診断の時計は、呼ばれるたびに1 msずつ進む試験用の時計である。
`Threads`が1の探索では、時計を読む位置が探索の手順で決まるので、持ち時間つきの探索でも結果が実行ごとに変わらない。
診断は、初期局面から固定の着手列で進めた同じ対局の16の連続した局面を、置換表とhistory表を引き継いで探索し、反復ごとの時間管理の入力、送られたイベント、探索の結果、停止の理由、および次の探索へ引き継ぐ値を1行ずつ出す。
反復ごとの時間管理の入力は、最善手、評価値、反復の中で最善手が変わった回数、最善手に費やしたノード数、全体のノード数、4つの伸縮の因子、伸縮した時間、最善手の安定の判定、深さを増やさずに始めた反復の回数、および詰みによる早期停止の判定である。
次の探索へ引き継ぐ値は、評価値とその平均、時間の短縮率、および先読みの探索を始めたかである。
時計は次の3種類で、局面ごとの手数に合わせて与えた。

| 事例 | 持ち時間 | 1手ごとの加算 | 秒読み |
|---|---|---|---|
| 切れ負け | 120,000 ms | 0 | 0 |
| 加算 | 30,000 ms | 2,000 ms | 0 |
| 秒読み | 0 | 0 | 3,000 ms |

あわせて、補助ワーカーの関数を、同じ対局の8局面で、ワーカー番号1〜3のそれぞれについて単独で深さ7まで動かし、結果を出した。

検証4では、2つのバイナリを`--protocol usi --search mcts`で起動し、`RuleSet`を`JCSA`、`NnBackend`を`cpu`として、検証2と同じ15局面に`go nodes 800`を送った。
ONNX Runtimeの環境は、bashで`tools/train/zero/env.sh`を読み込んで用意した。

## エンジン

変更の前のバイナリ`<base>`は、`scripts/bench_compare.py`がmasterのコミット`7a0b267612ea063093bf6622f59069687648456a`を展開して`cargo build --release`でビルドしたものであり、SHA-256は`deb9ae5f4fb2850e0174ba7a7e0c39eb494c0c36e4895693890a86b5408349a4`である。
変更の後のバイナリ`<cand>`は、ブランチ`multipv`の作業ツリーを同じ設定でビルドしたものであり、SHA-256は`37d49f33926e79b6876b4de525b7b9a4545cba4075949e12d0a8989c825211ca`である。
この作業ツリーは、後にコミットした内容と、`crates/minase/src/search/mod.rs`の空行1行だけが異なる。

検証4のネットは、AlphaZero型探索の強化学習の1回目のサイクル32で得た、10ブロック128チャネルのネットである。
チェックポイント`/mnt/synology_nas/minase/alphazero/cycles/cycle-0032/train/checkpoint.pt`（SHA-256は`8ece92ab0891937148cea95defe750416d2a09a6361afd4b17effa576ff40205`）を、コミットc1c84466の学習器の`minase_zero export-onnx`でONNX形式のファイルへ書き出し直した。
いまのmasterの学習器は2回目の学習のネットの形に改めてあり、1回目のチェックポイントを読めないからである。
c1c84466の後に、推論器が受け付けるONNXの入出力の形は変わっていない。
書き出したファイルのSHA-256は`cdc64e02fbd3ff54a935775c1bfe7610e33b02e498d41270a55bc705792d76a6`であり、[固定の相手の測定](../mcts-fixed-opponents/mcts-fixed-opponents-alphabeta-baseline.md)で同じチェックポイントから書き出したファイルと一致する。
両方のバイナリは、`isready`への応答で同じ値をネットのSHA-256として返した。

## 環境

作業機（Intel Core Ultra 7 265KF、物理20コア、論理20コア）で測った。
測定のあいだ、lishogiのBotの対局で、4スレッドの探索を使うminaseのプロセスが2つ動いていた。
この記録は出力の一致だけを判定し、速さを判定しないので、負荷の影響を受けない。

## 結果

4つの検証のすべてで、変更の前後の出力が一致した。

検証1では、`bench_compare.py`が「15 positions agree」と報告し、15局面の局面ごとの深さ、ノード数、最善手、および評価値が全行一致した。
ノード数の合計は、どちらも136,697である。

検証2では、`usi`への応答の握手列に新しく`option name MultiPV type spin default 1 min 1 max 35856`の1行が加わったことを除き、`readyok`以後の出力が30回の`go`のすべてで一致した。
15回の`go nodes`はどれも`info string stop nodes`で止まり、最後の`info`の行の深さは5〜7で、9より浅かった。
最後の`info`の行のノード数はどれも上限より小さいので、どの探索も次の反復の途中で上限に達し、その未完了の反復を捨てた。

|---|---|---|---|
| initial | 1,313 | 7 | 1,184 |
| game-2-ply-40 | 4,199 | 7 | 3,239 |
| game-2-ply-60 | 4,458 | 7 | 4,409 |
| game-3-ply-310 | 5,519 | 6 | 5,327 |
| game-3-ply-465 | 6,108 | 6 | 4,716 |
| game-4-ply-164 | 3,955 | 6 | 2,130 |

| game-6-ply-77 | 5,426 | 5 | 1,993 |

検証3では、診断の出力5,084行が全行一致した。
変更の前の診断の実行時間は963秒、変更の後は922秒であった。
48回の持ち時間つきの探索は、目安時間（soft limit）で45回、上限時間（hard limit）で3回止まり、完了した深さは23〜50であった。
時間管理の伸縮の入力の行は1,206行あり、そのうち135行は深さを増やさずに始めた反復の回数が1以上、104行は反復の中で最善手が変わった回数が1以上であった。
途中結果を採った探索と、詰みによる早期停止は、この診断では起きなかった。
この2つの経路は、変更なしで通る既存の単体試験（`crates/minase/src/search/alphabeta/tests/partial.rs`と`tests/time.rs`）が固定している。
補助ワーカーの24回の単独の実行も、結果、読み筋、およびノード数が一致した。

検証4では、`readyok`以後の出力が15局面の`go nodes 800`のすべてで一致した。
最初の3局面の読み筋の深さは7、11、および6であった。

## 結論

イベントの読み筋を列へ改め、`MultiPV`を宣言した変更は、既定値1で、αβ探索の`bench`の結果、USIの`go depth`と`go nodes`の出力、持ち時間つきの探索の時間管理の判断、およびPV-MCTSの`go nodes`の出力を変えない。
変わったのは、握手列に`MultiPV`の宣言が1行加わったことだけである。

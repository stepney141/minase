# 構成の見直しの評価値を変えない高速化と幅の費用

## 目的

NNUEの差分更新を1回の走査へまとめる変更、および累算値の16ビット化の採否を探索速度で判定し、第1層を幅256へ広げる費用を、評価値を変えずに測る。
棋力測定ではなく、[設計書](../../plans/nnue-architecture-revision.md)のフェーズ1の測定である。

## コマンドライン

各段階を次の形で測った。`<親>`は段階ごとに記す。

```console
taskset -c 3 python3 scripts/bench_compare.py --reference master --baseline master \
  --parent <親> --depth 15 --repetitions 3 --rounds 5
taskset -c 3 perf stat -x, -e cycles:u,instructions:u <バイナリ> dev bench --depth 15 --repetitions 1
```

候補は作業ツリーのビルドである。
深さ15の15局面は合計1,401,505ノードで、1回あたり約1.9秒かかる。
深さ9は合計143,873ノード（0.18秒）で短すぎるので、設計書の例より深くした。

## エンジン

- 親と照合参照はmasterの`48fa73da`である。
- 差分更新のまとめは、`48fa73da`に未コミットの差分を当てた作業ツリーで測り、不採用としたのでコミットしていない。
- 累算値の16ビット化は`65f0697c`である。
- 幅の費用は、`65f0697c`の`crates/minase/nets/nnue.bin`だけを、後述の変換で幅256にしたネットへ差し替えたビルドで測り、差し替えはコミットしていない。

幅256のネットは、第1層の各行とバイアスを[旧0..64, 旧0..64, 旧64..128, 旧64..128]の順に並べ、出力重み$`w`$を同じ順で1回目を$`\lfloor w/2\rfloor`$、2回目を$`w-\lfloor w/2\rfloor`$へ分けて作った。
成分$`j`$と$`j+128`$が鏡映の対になるので復号の検査を通り、活性化後の2成分が同じ値なので整数の評価が元と一致する。

## 環境

Intel Core Ultra 7 265KF（性能コア8、高効率コア12、スレッド数20）で、1スレッドの`minase dev bench`を性能コアのCPU 3へ固定した。
ビルドは`-C target-cpu=native`、`lto = true`、`codegen-units = 1`である。
測定の間、同じ機械でlishogiのBot（2プロセスで最大約4コア）と、別の作業の探索（最大約12コア）が動いていた。
負荷の平均は5から25の間で変動した。
対局を行わないので、棋力測定の記録項目のうちワーカー数、`USI_Hash`、同時対局数、ペンタノミアル度数、および時間切れは該当しない。

## 結果

どの段階でも、局面別のノード数、最善手、および評価値は`48fa73da`と全15局面で一致した。

| 段階 | 親 | NPSの増分 | 親の幅 | cycleの増分 | 命令数の増分 |
|---|---|---:|---:|---:|---:|
| 差分更新のまとめ | `48fa73da` | −0.78% | 7.22% | +0.5% | +0.29% |
| 累算値の16ビット化 | `48fa73da` | +1.10% | 5.62% | | −1.32% |
| 幅256（16ビット化の後） | `65f0697c` | −1.94% | 43.81% | +1.4% | +1.70% |

cycleと命令数は、各バイナリを交互に3回ずつ実行した`cpu_core`の値である。
命令数は3回の差が0.0001%未満で、機械の負荷の影響を受けない。
cycleは負荷の影響を受ける。16ビット化の測定は負荷の高い時間帯に当たり、差が一定しなかったので表に書いていない。

差分更新のまとめは、別の条件でも深さ9で−1.08%、深さ17で−1.15%であり、速くならなかった。
命令数も増えており、幅128では親の複写がすでに十分に速い。

累算値の16ビット化は、同じ条件の測定を3回行い、増分は+1.14%、+1.09%、および+1.10%だった。
交互測定の15回の組のすべてで候補が親を上回った。
親の幅はそれぞれ6.41%、2.92%、および5.62%で、増分を上回る。
幅が大きいのは機械の負荷の変動によるもので、2回目は親と同じコードの他の2つのラベルの幅が0.51%と1.05%だったが、親のラベルの1回だけが695,575 NPSへ外れた。

幅256は、幅128との比で命令数が1.70%増えただけだった。
16ビット化で累算値の大きさが幅128のi32と同じ1,024バイトに収まり、出力の内積が増えても費用は小さい。
NPSの測定は、親の幅が43.81%と大きく、値としては目安にとどまる。

## 結論

差分更新のまとめはNPSが上がらないので採用しない。
累算値の16ビット化は、設計書の「増分が親の幅を超える」という基準を機械の負荷のために満たしていないが、3回の増分の一致、全15組の優位、および負荷によらない命令数の1.32%の減少から採用した。
第1層の幅を256へ広げる費用は、出力部の隠れ層を除くと約2%である。

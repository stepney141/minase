# Finny tablesの最終測定（探索結果の一致とCPUサイクル数の対比較）

## 目的

[Finny tablesの設計書](../../plans/archived/nnue-finny-tables.md)のフェーズ4（最終測定）として、探索ごとに作るFinny tables（以下、表）を入れた候補と、入れる前の基準とを比べ、表をmasterへ入れるかを判定する。
比べるのは、探索結果の一致と、3つの負荷のCPUサイクル数である。3つの負荷は、採否を決める主の負荷であるHalfKP_vmのネットでの教師生成と、遅くなっていないことを確かめる従の負荷であるHalfKP_vmとA型のネットでの`bench`である。HalfKP_vmとA型はNNUEの入力特徴集合の種類であり、ネットはその重みのファイルである。

## コマンドライン

測定には、[準備の測定記録](nnue-finny-tables-setup.md)に付属する[`finny_bench.py`](nnue-finny-tables-setup/finny_bench.py)を使った。
このスクリプトは、基準と候補のバイナリを1組として、それぞれを`taskset -c 3 perf stat -x, -e cpu_core/cycles/u,cpu_core/instructions/u,cpu_core/LLC-load-misses/u,cpu_core/dTLB-load-misses/u`の下で実行する。組iでは、iが偶数なら基準を、奇数なら候補を先に実行するので、20組の半数ずつで実行順が入れ替わる。
組の2つの実行で探索結果が一致しなければ、スクリプトは終了コード1で止まる。一致を確かめる項目は、`bench`では15局面それぞれの深さ、ノード数、最善手、および評価値であり、教師生成では対局数、探索ノード数の合計、および教師のファイルのSHA-256である。
教師生成は、実行時の作業ディレクトリのgitのコミットハッシュを教師のファイルに書く。そこで、両方のバイナリを、基準のコミット`f2eb2fbf`に固定した変更のないworktree（`data/nnue-finny-tables/cwd`）から起動し、実行のたびに空の出力先を使った。

最終測定で測る組の数は、設計書のフェーズ4の手順に従い、基準と候補の組を測る前に、基準のバイナリどうしを20組測って決めた。
主の負荷では、`--early-stop`を付けて、最初の8組の時点で差dの平均の片側95%信頼区間の下限が0以上なら（候補が減らしていないことが明らかなら）測定を打ち切る。

```console
B=data/nnue-finny-tables/bin/minase-f2eb2fbf
C=data/nnue-finny-tables/bin/minase-1576a9a8
H=<HalfKP_vmのネット>; A=<A型のネット>; W=data/nnue-finny-tables/cwd
# 組の数の算定（基準どうし）
python3 finny_bench.py pairs --workload generate --baseline $B --candidate $B --net $H --pairs 20 --games 2 \
  --seed-base 9030000000 --out calib-gen.jsonl --cwd $W
python3 finny_bench.py pairs --workload bench --baseline $B --candidate $B --net $H --depth 19 --pairs 20 \
  --out calib-bench-halfkp.jsonl --cwd $W
python3 finny_bench.py pairs --workload bench --baseline $B --candidate $B --net $A --depth 21 --pairs 20 \
  --out calib-bench-a.jsonl --cwd $W
python3 finny_bench.py npairs calib-<負荷>.jsonl
# 最終測定
python3 finny_bench.py pairs --workload generate --baseline $B --candidate $C --net $H --pairs 20 --games 2 \
  --seed-base 9040000000 --early-stop --out final-gen.jsonl --cwd $W
python3 finny_bench.py pairs --workload bench --baseline $B --candidate $C --net $H --depth 19 --pairs 20 \
  --out final-bench-halfkp.jsonl --cwd $W
python3 finny_bench.py pairs --workload bench --baseline $B --candidate $C --net $A --depth 21 --pairs 20 \
  --out final-bench-a.jsonl --cwd $W
python3 finny_bench.py summary final-<負荷>.jsonl
```

教師生成の1回の実行は、`data selfplay generate --eval-file <HalfKP_vmのネット> --output-dir <空の出力先> --chunk-games 2 --games 2 --seed <その組の基本シード> --nodes 20000 --random-moves 0 --concurrency 1 --hash-mb 16`である。組iの基本シードは、算定では`9030000000 + 2i`、最終測定では`9040000000 + 2i`である。
`bench`の1回の実行は、標準入力に`setoption name RuleSet value JCSA`、`setoption name EvalFile value <ネット>`、`isready`、`bench depth <深さ> threads 1 repetitions 1`、`quit`を送る`minase --protocol usi`である。
全組の値は、付属資料のJSON Lines（[算定の教師生成](nnue-finny-tables-final/calib-gen.jsonl)、[算定のHalfKP_vmの`bench`](nnue-finny-tables-final/calib-bench-halfkp.jsonl)、[算定のA型の`bench`](nnue-finny-tables-final/calib-bench-a.jsonl)、[最終の教師生成](nnue-finny-tables-final/final-gen.jsonl)、[最終のHalfKP_vmの`bench`](nnue-finny-tables-final/final-bench-halfkp.jsonl)、[最終のA型の`bench`](nnue-finny-tables-final/final-bench-a.jsonl)）にある。

## エンジン

基準は、設計書のブランチ`nnue-finny-tables`の分岐元であるmasterのコミット`f2eb2fbfd8a6f2ca32ef7bd497e3dd615d3b69cf`で、バイナリのSHA-256は`416da18a94440ea490740bfd74396066131f54c0deb6d4a52e86407d2c62e4f8`である。
候補は、フェーズ1の実装のコミット`1576a9a8026a89d4d0a30d1b7b2882a1cab4c88a`で、バイナリのSHA-256は`874f14afc5d2f21470c769b2e95ad41b9aba90facf519335a0e859ade66e72b4`である。フェーズ3（表を対局の間保持する実装）は行わず、測定のためだけに入れた処理もないので、このコミットをそのまま凍結した候補とした。
この候補では、`cargo fmt --check`、`cargo clippy --release --all-targets`、`cargo test --release`、`cargo test --release --features invariants`、および`--features invariants`でビルドした深さ9の`bench`（HalfKP_vmのネット）が通った。
基準と候補のバイナリはいずれも、リポジトリのrelease設定（`target-cpu=native`、インライン閾値1000、LTO有効、`codegen-units=1`）で、`invariants`機能なしにビルドした。
HalfKP_vmのネットのSHA-256は`d0d1bf33fa7aef3faa40fb0696872eb632a959313d9b03a6df216d99b4f5441d`、A型のネットのSHA-256は`415020879b9086772acb168397dfa406a1432350c151f87b635b3f271153d1a9`である。
`bench`の規則セットは`JCSA`、教師生成の規則セットは`lishogi`（`L1,L2,P0,P3,R1,E1,E3`）である。

## 環境

測定機はIntel Core Ultra 7 265KF（性能コア8、高効率コア12、論理CPUは計20、メモリ30 GiB）で、Linux `6.18.63-3-lts`、Rust `1.100.0`、perf `7.3.6`である。
探索ワーカーは1、教師生成の同時対局数は1である。置換表は、教師生成が16 MiB、`bench`が`USI_Hash`の既定値である。すべての実行を性能コアの論理CPU 3に固定した。
`/sys/kernel/mm/transparent_hugepage/enabled`は`[always] madvise never`だった。
組の数の算定は2026年11月27日の0時29分から1時48分に、最終測定は同日の1時48分から3時8分に行った。
どちらも開始の前に、自己対局による棋力測定、探索の係数の自動調整（SPSA）、学習、教師生成、およびビルドが同じ機械で動いていないことを確かめた。

## 結果

### 探索結果の一致

3つの負荷の最終測定の60組すべてで、基準と候補の探索結果は一致した。
教師生成では、20組すべてで対局数（2局）、探索ノード数の合計、および教師のファイルのSHA-256が一致した。
`bench`では、HalfKP_vmとA型のネットの両方で、15局面それぞれの深さ、ノード数、最善手、および評価値が20組すべてで一致した。
HalfKP_vmの`bench`における累算器の計数（`accumulator_updates=41118010 accumulator_refreshes=1494759 refresh_fraction=0.036353`）も基準と候補で同じだった。表を使った更新も全再計算として数える設計どおりである。
組の数の算定の60組でも、同じバイナリの2回の実行の探索結果はすべて一致した。

### 組の数

基準どうしの20組から求めた組の数nは、3つの負荷とも下限の20だった。
組ごとの値は、教師生成では組のサイクル数の差d = 候補 − 基準、`bench`では比の自然対数r = ln(候補 ÷ 基準)である。sは基準どうしの組の値の標準偏差、Kは教師生成の1回の局数である。

## 結論

探索ごとのFinny tablesは、探索結果を変えず、深さ19の`bench`ではHalfKP_vmの探索のサイクル数を1.15%減らした。しかし、目的である教師生成のサイクル数の変化（平均−0.14%）は95%信頼区間で0と区別できなかったので、設計書の完了条件に従い、表のコードをmasterへ入れずに完了（不採用）とする。

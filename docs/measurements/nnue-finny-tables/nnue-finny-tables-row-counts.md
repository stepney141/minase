# Finny tablesの行数の診断（探索ごとの表と対局内で保持する表）

## 目的

[Finny tablesの設計書](../../plans/nnue-finny-tables.md)のフェーズ2として、HalfKP_vmのネットでの探索について、第1層の値を作るために足し引きする重みの行の数を数える。
数えるのは、全再計算で足す行数Aと、表を使った場合に足し引きする行数Dであり、そこから、探索ごとに作る表で減る行数Sと、表を対局の間保持することでさらに減る行数Tを求める。
SとTを設計書の判定基準に当てて、フェーズ3（対局内の保持）へ進むかを決める。

## コマンドライン

計数は、フェーズ1の実装（コミット`1576a9a8`）に計数用の[差分](nnue-finny-tables-row-counts/diagnostic.patch)を当てた測定専用のビルドで行った。この差分はmasterへ入れない。
計数用の差分は探索結果を変えない。
HalfKP_vmでは、先手と後手の視点ごとに、その側の王将（なければ太子）の位置から文脈が決まり、王駒をすべて失った視点には文脈がない（設計書の「HalfKP_vmの文脈」の節）。
差分は、次の2種類の事象ごとに、文脈がある視点それぞれで行数を数える。

- 根の事象は、探索の開始時に、探索木の根の局面の累算値を作ることである。
- 文脈変更の事象は、着手の後に、ある視点の文脈が親の局面と異なる値になることである。着手の後に文脈がなくなった視点は数えない。

null moveは文脈を変えないので数えない。
各事象で、次の3つの行数を求める。

- Aは、現在の局面で`Indexer::row`が行を返す特徴の数であり、全再計算で足す行数に当たる。
- D（探索ごと）は、フェーズ1の実装と同じく探索の開始時に空にする表を使った場合に足し引きする行数である。根の事象ではAになる。
- D（保持）は、`HistoryTables`を作るときと消去するときにだけ空にする表を使った場合の行数である。`HistoryTables`は探索の履歴の表をまとめた構造体であり、教師生成では対局ごとに作り直し、開始局面の候補を探索するたびに消去する。この表は根の事象でも参照する。

どちらの方式でも、有効印が偽の項目ではD=Aとし、有効な項目では保存した駒配置と先獅子の対象升を現在のものと比べて、引く行と足す行の数の和をDとする。差分の計算はフェーズ1の表と同じ関数で行う。
行数を数えるだけなので、保持の方式の表は第1層の値を持たず、駒配置、先獅子の対象升、および有効印だけを持つ。
この表はプロセスに1つだけ置くので、診断のビルドは、2つ以上の探索ワーカーでHalfKP_vmの探索が走るとパニックで止まる。

```console
git worktree add -b nnue-finny-tables-diag data/worktrees/nnue-finny-tables-diag 1576a9a8
cd data/worktrees/nnue-finny-tables-diag && git apply diagnostic.patch && cargo build --release --bin minase
cd data/nnue-finny-tables/cwd
printf 'setoption name RuleSet value JCSA\nsetoption name EvalFile value <HalfKP_vmのネット>\nisready\nbench depth 19 threads 1 repetitions 1\nquit\n' \
  | taskset -c 3 <診断のバイナリ> --protocol usi
taskset -c 3 <診断のバイナリ> data selfplay generate --eval-file <HalfKP_vmのネット> --output-dir <空の出力先> \
  --chunk-games 20 --games 20 --seed 9020000000 --nodes 20000 --random-moves 0 --concurrency 1 --hash-mb 16
taskset -c 3 <診断のバイナリ> data selfplay generate --eval-file <HalfKP_vmのネット> --output-dir <空の出力先> \
  --chunk-games 20 --games 20 --seed 9020000000 --nodes 2000 --random-moves 0 --concurrency 1 --hash-mb 16
```

`bench`は`info string finny_diag:`の行に、自己対局による教師生成（`data selfplay generate`）は`summary:`のブロックの最後の`finny_diag:`の行に、計数を出力する。
全出力は付属資料の[`bench19.txt`](nnue-finny-tables-row-counts/bench19.txt)、[`teacher-20000.txt`](nnue-finny-tables-row-counts/teacher-20000.txt)、および[`teacher-2000.txt`](nnue-finny-tables-row-counts/teacher-2000.txt)にある。

## エンジン

診断のビルドは、コミット`1576a9a8026a89d4d0a30d1b7b2882a1cab4c88a`に計数用の差分を当てたもので、SHA-256は`9404e7209b58c593793c4b7d28e1af98b5cd23929d3e754e233b38bf11f6da4b`である。ビルド設定はリポジトリのrelease設定である。
ネットは、[準備の測定記録](nnue-finny-tables-setup.md)と同じHalfKP_vmのネット（SHA-256は`d0d1bf33fa7aef3faa40fb0696872eb632a959313d9b03a6df216d99b4f5441d`）である。
`bench`の規則セットは`JCSA`、教師生成の規則セットは`lishogi`（`L1,L2,P0,P3,R1,E1,E3`）である。

## 環境

測定機は[準備の測定記録](nnue-finny-tables-setup.md)と同じIntel Core Ultra 7 265KFである。
探索ワーカーは1、教師生成の同時対局数は1で、すべての実行を論理CPU 3に固定した。
2026年11月27日の0時21分から0時27分に測定した。本測定は行数だけを数えるので、時間とサイクル数は判定に使わない。

## 結果

深さ19の`bench`における全15局面の合計ノード数は42,904,203で、基準のコミットの同じ`bench`と一致した。
教師生成は、1手2万ノードと2,000ノードのどちらも20局を終え、探索ノード数の合計は188,580,000と16,080,000だった。

事象ごとの行数は次のとおりである。D/Aは、ΣDをΣAで割った値である。

| 負荷 | 事象 | 事象の数 | ΣA | ΣD（探索ごと） | D/A（探索ごと） | ΣD（保持） | D/A（保持） |
|---|---|---|---|---|---|---|---|
| `bench`（深さ19） | 根 | 30 | 1,702 | 1,702 | 1.000 | 1,702 | 1.000 |
| `bench`（深さ19） | 文脈変更 | 1,494,744 | 65,765,730 | 8,414,075 | 0.128 | 8,414,075 | 0.128 |
| 教師生成（2万ノード） | 根 | 18,858 | 1,050,256 | 1,050,256 | 1.000 | 117,063 | 0.111 |
| 教師生成（2万ノード） | 文脈変更 | 4,452,235 | 181,372,148 | 27,744,305 | 0.153 | 23,670,505 | 0.131 |
| 教師生成（2,000ノード） | 根 | 16,080 | 882,390 | 882,390 | 1.000 | 43,816 | 0.050 |
| 教師生成（2,000ノード） | 文脈変更 | 480,696 | 15,536,703 | 3,814,554 | 0.246 | 2,012,702 | 0.130 |

根と文脈変更を合わせた件数は次のとおりである。
「初めて使う回数」は、有効印が偽の項目を引いて全再計算した回数であり、探索ごとの方式では根の事象をすべて含む。
「D≥A（初回を除く）」は、有効な項目を使ったのにDがA以上だった回数である。
「Σmax(D − A, 0)」は、表を使ったために全再計算より余分に足し引きした行数の合計である。

| 負荷 | 方式 | 初めて使う回数 | D=0の回数 | D≥A（初回を除く） | Σmax(D − A, 0) |
|---|---|---|---|---|---|
| `bench`（深さ19） | 探索ごと | 462 | 63,946 | 976 | 1,583 |
| `bench`（深さ19） | 保持 | 462 | 63,946 | 976 | 1,583 |
| 教師生成（2万ノード） | 探索ごと | 143,663 | 277,188 | 12,588 | 12,293 |
| 教師生成（2万ノード） | 保持 | 1,884 | 282,016 | 15,620 | 37,075 |
| 教師生成（2,000ノード） | 探索ごと | 75,421 | 42,867 | 2,895 | 1,856 |
| 教師生成（2,000ノード） | 保持 | 1,338 | 48,018 | 4,978 | 17,198 |

探索ごとの表で減る行数S = Σ(A − D（探索ごと）)と、保持によってさらに減る行数T = Σ(D（探索ごと） − D（保持）)は次のとおりである。

| 負荷 | ΣA | S | T | T/S |
|---|---|---|---|---|
| `bench`（深さ19） | 65,767,432 | 57,351,655 | 0 | 0 |
| 教師生成（2万ノード） | 182,422,404 | 153,627,843 | 5,006,993 | 0.033 |
| 教師生成（2,000ノード） | 16,419,093 | 11,722,149 | 2,640,426 | 0.225 |

`bench`は局面ごとに`HistoryTables`を消去し、1局面を1回の探索で読むので、保持の方式は探索ごとの方式と同じになり、Tは0である。
1手2万ノードの教師生成では、全再計算で足す行数ΣAのうち、探索ごとの表が84.2%を減らし、保持の表はさらに2.7%を減らす。
Tの内訳は、根の事象が933,193行、文脈変更の事象が4,073,800行である。
設計書は、DがA以上になるときに表を使わず作り直す判定を適用範囲から外し、該当する回数が多ければ別の設計書で扱うとしている。探索ごとの方式で、有効な項目を使ったのにDがA以上だった回数は、2万ノードの教師生成の事象4,471,093回のうち12,588回（0.28%）なので、別の設計書は起案しない。

## 結論

設計書のフェーズ2は、1手2万ノードの教師生成について次のように定めている。S+T≤0なら、フェーズ3とフェーズ4を行わずに完了（不採用）とする。S≤0<S+Tなら、フェーズ3へ進む。S>0で10T≥Sなら、フェーズ3へ進む。それ以外は、フェーズ3を行わずにフェーズ4へ進む。
S = 153,627,843 > 0であり、10T = 50,069,930 < Sなので、フェーズ3（対局内の保持）を行わずにフェーズ4（最終測定）へ進む。

# 載せ替えの前と後のA型のbenchの速さ

## 目的

[tatara化とHalfKP_vmの設計書](../../plans/archived/nnue-tatara-framework-and-halfkp-vm.md)の「検証」の節に従い、載せ替える前のA型と、tataraのLayerStackへ載せ替えた後のA型で、深さ5の`bench`の毎秒ノード数（nps）を性能コアに固定して5回ずつ交互に測る。
2つの版はネットも探索木も異なるので、局面ごとの探索結果は比べず、速さだけを読む。
この比較は、探索の評価器を列挙型で分岐させた費用だけでなく、要素積、後段の層、および量子化の変更と、線形の経路をPSQT（駒と升ごとの点数の表）に替えた変更を合わせた、載せ替え全体の費用を測るものである。
判定の基準は設計書のとおり、後の5回の平均が、前の5回の値の幅（最大値と最小値の差）を超えて前の平均より遅いかどうかであり、超えて遅ければ`perf`で時間の内訳を調べ、列挙型による分岐が目立つ場合にだけ、探索を評価器の具体型ごとに単相化する（型引数で別々にコンパイルする）案を検討する。

|---|---|---|
| 前のA型 | `a48f03aa`（本書のブランチを切ったmaster） | `fc86cce6b2f60c357061222fd54afdd62a5a88330b0a9207c93ec0119622ee71.bin`（MNUEの形式） |
| 後のA型 | `8389b160` | `37054c9e49c9218bb18efdd1814fe1b298de5cbfc9c14352f6ad6eaecbb70dea.bin`（tataraのLayerStackの形式） |

2本のネットは、[載せ替えの確認の学習](nnue-tatara-framework-and-halfkp-vm-training.md)で同じ教師から学んだものである。

## コマンドライン

`scripts/bench_compare.py`は全ての版に同じ`--eval-file`を渡すので、MNUEのネットを読む前の版とtataraの形式のネットを読む後の版を比べられない。
そこで、各版にそれぞれのネットを渡す点だけを変えた単発のスクリプトをリポジトリの外に置き、`bench_compare.py`と同じ手順で測った。
各回は、版ごとに`RuleSet JCSA`、`EvalFile`、`isready`、`bench depth 5 threads 1 repetitions 3`、`quit`をエンジンへ送り、3回の反復の中央値の行（`median:`）の毎秒ノード数を読む。
1回の中で前、後の順に測り、これを5回繰り返した。

```console
taskset -c 3 python3 bench_two_nets.py <前のminase> <前のネット> <後のminase> <後のネット> 5
```

## 環境

2026年11月18日21時28分から、測定機（Intel Core Ultra 7 265KF、性能コア8、効率コア12、計20スレッド、メモリ30 GiB）で行った。
`bench`は性能コアの論理CPU 3に固定し、1スレッドで実行した。
lishogiのBotのコンテナのCPU使用量が2分続けて0.1コア未満になってから始め、開始時の1分の負荷平均は1.02、終了時は1.09だった。
ほかの学習と対局は動かしていない。

## 結果

| 版 | 5回の値（nps） | 平均（nps） | 幅（nps、平均に対する割合） |
|---|---|---:|---:|
| 前のA型 | 1,105,005、1,102,804、1,098,834、1,104,223、1,108,791 | 1,103,931 | 9,957（0.90%） |
| 後のA型 | 1,068,054、1,073,577、1,072,294、1,073,516、1,069,431 | 1,071,374 | 5,523（0.52%） |

後の平均は前の平均より32,557 nps小さく（−2.95%）、前の幅9,957 npsを超えた。
1回の`bench`の探索のノード数は前が59,785、後が57,815であり、経過時間は前が約0.0541秒、後が約0.0539秒でほぼ同じだった。

## 時間の内訳

基準を超えて遅かったので、両方の版で`repetitions`を40にした`bench`を`perf record -F 4999 -g --user-callchains`で記録し、関数ごとの時間を比べた。

| 関数 | 前のA型 | 後のA型 |
|---|---:|---:|
| `minase::diagnostics::bench::run_bench`（自身、呼び出し先を除く） | 61.88% | 61.87% |
| 後段の評価（前は`PairwiseL16L32::output`と`hidden2_sum`、後は`LayerStackNetwork::dense`） | 1.78% | 2.60% |
| `Searcher::ensure_accumulator` | 0.77% | 0.83% |
| `Searcher::quiesce`（自身） | 4.81% | 4.00% |
| `Searcher::negamax`（自身） | 2.38% | 2.57% |

`run_bench`の自身の時間のほとんどは、局面ごとに作り直す継続履歴の表を初期値−586（`CONTINUATION_HISTORY_INITIAL`）で埋める処理で、両方の版で同じ割合である。
経過時間の約6割をノード数によらないこの固定の費用が占めるので、探索のノード数が3.3%少ない後の版は、経過時間がほとんど変わらないままノード数だけが減り、毎秒ノード数が小さく出る。
後の版で増えた時間は後段の評価の`dense`に現れ、探索の評価器の列挙による分岐は別の関数として目立たなかった。
したがって設計書の基準により、探索を具体型ごとに単相化する案は検討しない。

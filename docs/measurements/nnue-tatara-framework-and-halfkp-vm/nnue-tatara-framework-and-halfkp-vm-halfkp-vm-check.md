# HalfKP_vmの動作の確認

## 目的

[tatara化とHalfKP_vmの設計書](../../plans/nnue-tatara-framework-and-halfkp-vm.md)の「HalfKP_vmの動作の確認」の節に従い、自玉の位置で条件付ける入力特徴集合HalfKP_vmのネット（将棋のNNUE学習器tataraのSimpleの構造、256x2-32-32）を、王の位置を使わない入力特徴集合P型と同じ教師37本から64 superbatch学び、学習、書き出し、エンジン、教師生成、および連続生成スクリプトで使えることを確かめる。
このネットの棋力は採否に使わない。

## 本番の学習の前に見つかった問題

### チェックポイントの保存でメモリの上限を超えた

最初に、コミット`bce593df`の学習器で、メモリ上限18 GiB、スワップなしの`systemd-run`のサービスとして学び始めたところ、最初の検証の直後に行うチェックポイントの保存の間に、cgroupのメモリが上限の18 GiBに達し、メモリ不足（OOM）で止められた。
同じ教師でP型のLayerStackを学んだときの最大は12.4 GiBで、その大部分はメモリに置いた教師（教師の常駐）だった。

教師を1本、1 superbatchあたりの更新を4回、検証と保存を毎superbatchにした学習で、cgroupの`memory.stat`の`anon`（ページキャッシュを除いた確保済みのメモリ）を0.3秒ごとに読むと、教師の常駐は約0.3 GiBで、再開用のチェックポイントの保存と、推論用のネットの書き出しのたびに`anon`が約9.4 GiB増え、最大9.69 GiBになった。
Simpleの重みと最適化器の2つのモーメントは合わせて約2.76 GiBであり、チェックポイントの形式NPZ（NumPyの配列の形式NPYのファイルをZIPで束ねた形式）の保存の経路が、配列をバイト列、NPYの符号化、ZIPのバッファの順に複製していたことが原因だった。
コミット`8b853b66`で、配列を借用したままファイルへ直接書き、再開ではファイルから直接読む形に改めると、同じ条件の`anon`の最大は保存で3.20 GiB、チェックポイントからの再開で4.01 GiBになった。
ファイルの中身は変わらない。

### 1回の更新が遅かった

メモリの問題を直した学習器（コミット`8b853b66`）で教師37本から学び直すと、1 superbatch（6,104更新）が約55分たっても終わらなかったので止めた。
GPUをほかの処理と分け合わない状態で、`nnue bench-step simple --batch 16384 --steps 10 --profile`を教師1本で測ると、1回の更新の内訳は次のとおりだった。

| 区間 | 修正の前（`8b853b66`） | 修正の後（`264b7fc4`） |
|---|---:|---:|
| 逆伝播 | 453.38 ms | 24.33 ms |
| 最適化器 | 145.57 ms | 16.84 ms |
| 順伝播 | 4.99 ms | 4.97 ms |

修正の前の約604 msでは、64 superbatch（390,656更新）に約2.7日かかる。
原因は2つあった。
1つ目は、最適化器が約2.5億個の要素の更新を倍精度で計算していたことである（GeForceの倍精度は単精度の1/64の速さである）。
2つ目は、逆伝播が、バッチに現れない行も含めて第1層の964,224行すべてに計算のブロックを割り当て、同じwarpのレーンが別々の局面の行を読んでいたことである。
コミット`264b7fc4`で、最適化器の要素ごとの計算を単精度にし、試験で照合するCPUの参照実装も同じ演算の順の単精度に揃えた。
逆伝播は、バッチに現れる行だけを対象にし、同じ局面の行の隣り合う成分をまとめて読む形に改めた。
損失と勾配の式、全ての行を毎回更新する密な更新、学習中の切り詰め、および仮想行の扱いは変えておらず、CPUとGPUの一致の試験は今の許容差のまま通る。
`264b7fc4`のコミットのメッセージは修正の前を「学習で約1.3秒、64 superbatchに約6日」と書いているが、約1.3秒はP型の学習とGPUを分け合っていた間の短い学習で測った値であり、GPUを分け合わない状態の値は上の約604 ms（約2.7日）である。

2つの問題から得た規則は、[教師1本で保存と再開のメモリと1回の更新の時間を測る教訓](../../lessons/measure-memory-and-update-time-with-one-teacher-file-before-a-large-network-run.md)に書いた。

## 学習

### コマンドライン

本体のリポジトリのルートで、コミット`264b7fc4`に固定したworktreeの学習器を、メモリ上限12 GiB、スワップなしの`systemd-run`のサービスとして実行した。
`$DATA`はP型と同じ教師37本（`data/nnue-tatara-framework-and-halfkp-vm/teacher-jcsa-v3/book-0.mnsd`〜`book-36.mnsd`）を番号順に並べたものである。

```console
minase-trainer nnue train simple --data $DATA \
  --output-dir data/nnue-tatara-framework-and-halfkp-vm/train-hkvm --rules JCSA \
  --teacher-cp-per-logit 679.029296875 --lambda 1.0 --batch 16384 --superbatches 64 \
  --lr-schedule cosine:64:0.027 --validation-superbatches 8 --seed 1 --device cuda --threads 4 \
  --buckets 16 --bucket-positions 6100000 --scratch-dir data/nnue-tatara-framework-and-halfkp-vm/scratch
```

P型の学習の命令との違いは、構造の指定（`simple`）と、教師を16個のbucketに分けて一時ファイルへ置く設定（`--buckets 16`、`--bucket-positions 6100000`、`--scratch-dir`）だけである。
bucketに分け、1つずつメモリへ読む形にしたのは、並行して動かした短時間条件（STC）の対局とlishogiのBotのエンジンの分のメモリを空けるためであり、全ての局面をエポックごとに一様に並べ替える点は全局面をメモリに置く場合と同じである。
書き出しの除数m＝12と、ネットの出力を評価値（cp、センチポーン）へ換算する尺度K_o＝677.33 cpは、P型と同じである。

### 環境

2026年11月18日22時49分から、測定機（Intel Core Ultra 7 265KF、20コア、メモリ30 GiB、NVIDIA GeForce RTX 3060 Ti）で行った。
訓練は96,462,343局面、検証は5,162,867局面で、前処理は228秒だった。

### 学習の速さとGPUのメモリ

学習は2026年11月19日5時56分に64 superbatch（390,656更新、約66.3エポック）を終え、前処理を含めて25,479秒（約7.1時間）だった。
訓練の速さは、64 superbatchの中央値で毎秒307,306局面（最小151,001、最大320,601）、1回の更新は中央値で46.8 msであり、P型をtataraのLayerStackへ載せ替えた後の学習器の毎秒271,154局面より速い。
11月19日の1時から5時ごろにかけて、別の作業の学習と対局が同じ機械で動き、その間は1 superbatchの所要時間が約6分から約10分に延びた。
GPUのメモリの使用量は、この学習のプロセスだけでなくGPU全体の値であり、64 superbatchの最大は5,571,739,648バイト（約5.19 GiB）である。

### 検証損失

| superbatch | 訓練損失 | 検証損失 |
|---:|---:|---:|
| 0 | | 0.0728161 |
| 8 | 0.0005443 | 0.0015331 |
| 16 | 0.0004484 | 0.0015452 |
| 32 | 0.0003651 | 0.0015956 |
| 64 | 0.0003048 | 0.0016448 |

検証損失は8 superbatchごとの観測でsuperbatch 8が最も小さく、その後は増えた。
同じ教師から学んだP型（[学習の記録](nnue-tatara-framework-and-halfkp-vm-training.md)）と比べると、superbatch 64の訓練損失はP型の0.0006192より小さく、検証損失はP型の0.0014470より大きい。
HalfKP_vmはP型よりパラメータがはるかに多いので、同じ教師ではP型より強く過学習したと読める（推論）。
検証損失は教師への当てはまりを表す値であり、棋力は本書では測らない。

## 書き出し

書き出したネットは493,701,123バイトで、NASの`/mnt/synology_nas/minase/nnue/nets/d0d1bf33fa7aef3faa40fb0696872eb632a959313d9b03a6df216d99b4f5441d.bin`に置いた。
学習器が検証の10,000局面で測った量子化誤差（整数の評価から実数の評価を引いた差）と、活性化の前の値が0以下か1以上の成分の割合（飽和の割合）は次のとおりである。

| 項目 | HalfKP_vm | 参考：載せ替えた後のP型 |
|---|---:|---:|
| 量子化誤差の絶対値の平均 | 38.32 cp | 14.33 cp |
| 量子化誤差の符号つきの平均 | −32.42 cp | +10.18 cp |
| 量子化誤差の絶対値の最大 | 242.13 cp | 122.28 cp |
| 第1層の出力の飽和の割合 | 74.4% | 70.5% |
| 幅32の1つ目の隠れ層の飽和の割合 | 88.2% | |
| 幅32の2つ目の隠れ層の飽和の割合 | 37.3% | |

P型の後段は幅16と幅32の層からなり、Simpleの2つの隠れ層と対応しないので、その2行はP型の欄を空けた。

HalfKP_vmの量子化誤差は、P型より大きく、一方向にも偏っている。
載せ替え後のP型では、後段の重みを8ビット整数（尺度64）から16ビット整数に変えると、実数評価との誤差が減った。対局で測った棋力への影響は対戦相手によって異なった。[P型の棋力低下の調査報告](../../audits/tatara-p-regression-2026-11-19.md)
学習器は同じ検証の10,000局面で、王駒以外の盤上の駒を1枚ずつ除き、除く前後のネットの評価の差の符号が、手書きの評価関数v0の駒価値の差と逆になった割合も測る。
その割合は514,739件中9,363件の1.82%だった（評価を定義できない除去は106件）。

## エンジン

エンジンにはコミット`264b7fc4`のworktreeの`minase`を使い、NASのネットをUSIのオプション`EvalFile`で渡し、実行するCPUを性能コアの論理CPU 3に限った。
測定の直前の`top`では、ほかの学習、対局、およびlishogiのBotのエンジンは見当たらなかったが、1分の負荷平均は4.19〜5.30だった。

| 項目 | 結果 |
|---|---|
| `isready`の完了までのネットの読み込みを含むプロセスの時間 | 0.29〜0.31秒（3回） |
| 読み込み後の常駐メモリの最大 | 1,181,908 kB（約1.13 GiB） |
| `bench depth 5 threads 1 repetitions 3`の実行後の常駐メモリの最大 | 1,483,748 kB（約1.42 GiB） |
| `bench`の1回の探索のノード数 | 75,447 |
| `bench`の毎秒ノード数（3回の中央値） | 835,366 |
| 自玉の移動などで第1層を全再計算した割合 | 1.17%（1回の`bench`で累算器の更新66,624回のうち781回） |

読み込みの時間は、直前にネットをNASへ複製したので、ファイルがページキャッシュにある状態の値である。
`bench`の毎秒ノード数は1回の実行（反復3回）で測った値であり、P型の5回の交互の測定（[速さの記録](nnue-tatara-framework-and-halfkp-vm-bench-speed.md)）とは条件が違うので比べない。

## 学習器の診断

駒除去差分の診断`diag nnue-removal`は、学習の`latest.npz`（実数の重み）と書き出したネット（整数の重み）を渡し、教師37本のうち`book-0.mnsd`の検証の局面から1,000局面を抽出して実行し、最後まで動いた。
実数の2つの計算経路の差は最大0 cpで検査を通り、実数と整数の評価の差は平均21.04 cp、最大279.33 cp、評価の差の符号がv0の駒価値の差と逆になった除去は52,718件中1,013件の1.92%だった。
教師37本すべてを渡すと、診断が全ての局面をメモリに読み込むので、メモリ上限8 GiBのサービスではOOMで止められた。
1本では最大4.5 GiBだった。

合法手の評価差の診断`diag nnue-moves`は、次の節の教師生成で新しく作った`book-0.mnsd`の40局面について、HalfKP_vmのネットと、以前の評価関数PST＋FM（駒と升ごとの点数の表PSTに、駒の組の関係を表すFactorization Machine（FM）を足したもの）の重み`crates/minase/nets/pst.bin`で全ての合法手を比べ、片方にしかない合法手は0件で、エラーなく最後まで動いた。

## 教師生成と連続生成スクリプト

HalfKP_vmのネットを`data selfplay generate --eval-file`に渡し、コミット`264b7fc4`に固定したworktreeで、1冊40局、1手2,000ノード、同時4局の条件で教師ファイル（以下、本）を2冊作った（シードは1,001と1,002）。
記録した局面はそれぞれ12,492局面と12,258局面で、生成の時間は10.8秒と15.8秒だった。
本のヘッダに記録された生成のコミットは`264b7fc4`、ネットのSHA-256は`d0d1bf33…`、規則セットは`lishogi`である。

この2冊を第1世代の本として、連続生成スクリプト`scripts/vast/generation_chain.py`を、教師の生成のために借りる計算機（生成機）を使わずに、測定機だけで動かした。
本がそろった世代では、スクリプトは生成機に接続せずに、本の検査、勝率尺度の較正、学習、診断、ネットの保管、および`bench`を順に行う。
主な引数は、`--structure simple`、`--train-place local`、`--first-generation 1`、`--last-generation 1`、`--books-per-generation 2`、`--batch 1024`、`--superbatches 2`、`--lr-schedule cosine:2:0.027`、`--removal-sample 100`である。
スクリプトは終了コード0で終わり、第1世代の教師の勝率尺度は781.99 cpと較正された。
学習は訓練24,532局面、検証218局面で2 superbatchを終えて、学習器の判定が候補（`candidate`）となり、量子化誤差の絶対値の平均は25.35 cpだった。
学んだネット（SHA-256は`83ed40cd…`）はネットの保管場所に置かれ、`bench`が深さ5まで完走した。

最初の2回の試行は、引数が教師の量と合わず、学習器と診断がそれぞれ明示的なエラーを出して止まった。
1回目の1冊4局、計8局では、対局単位で分ける検証の集合が空になり、学習器は「訓練と検証の集合がどちらも空でないこと」を求めて止まった。
2回目に1冊40局へ増やしたときは、`--removal-sample 1000`が検証の218局面を超えたので、診断が範囲外のエラーで止まった。
どちらも引数の誤りを黙って補わずに止める意図どおりの動作であり、引数を改めて最後まで動いた。

## 結論

HalfKP_vmのネットは、学習器の`nnue train simple`で、学習の間だけ王の位置によらない仮想行を足す特徴分解つきで学べ、tataraの形式で書き出せた。
さらに、書き出したネットをエンジンが読んで深さ5の`bench`を完走し、教師生成、連続生成スクリプト、および学習器の2つの診断でも使えた。
設計書の「HalfKP_vmをいつでも使える状態」の項目を満たすことを、この記録で確かめた。
書き出しの量子化誤差の大きさは、P型の弱さの切り分けの結果とあわせて、HalfKP_vmの世代反復を起案するときに扱う。

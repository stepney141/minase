# 静止探索の補正と枝刈りの形の変更による探索ノード数、探索速度、および発動回数

## 目的

[静止探索の補正と枝刈りの形の見直しの設計書](../../plans/archived/qsearch-forms.md)のフェーズ1で入れたコミットを対象とする。
探索を変えない4つの移行のコミットについては、探索ノード数、評価値、および最善手が直前のコミットと同じになることを確かめる。
探索を変えるコミット（Q1からQ7）については、`minase dev bench`の探索ノード数の変化を記録する。
あわせて、探索速度、最大常駐メモリ、各枝刈りと免除が働いた回数、および係数の既定値を動かしたときのテストの結果を記録する。
棋力測定ではない。新しい係数はStockfishの値を換算した開始値のままであり、SPSAで調整した後に、事前対局と短時間条件（10秒＋1手0.1秒）の逐次検定STCで強さの変化を記録する。

## コマンドライン

ノード数は、各コミットの`cargo build --release --bin minase`によるminaseで、次のコマンドを深さ3、5、7について1回ずつ実行して数えた。
`dev bench`は固定の15局面を固定の深さで探索し、局面ごとに置換表と履歴の表を初期化するので、同じバイナリなら出力は毎回同じになる。

```console
minase dev bench --depth <深さ>
```

探索速度と最大常駐メモリは、比べる2つのコミットのminaseを交互に3回ずつ、性能コアのCPU 3に固定して測った（[速度比較のbenchは性能コアへ固定して測る](../../lessons/pin-bench-to-performance-core.md)）。
各回の値は、計測外のウォームアップ1回の後に3回探索した中央値である。最大常駐メモリは`/usr/bin/time -f %M`で取得した。

```console
/usr/bin/time -f %M taskset -c 3 minase dev bench --depth 9 --repetitions 3
```

各枝刈りと免除が働いた回数は、起点と最後のコミットを`--features search-stats`つきでビルドしたminaseで、`minase dev bench --depth 9`の全15局面の合計として数えた。

1局あたりの最大常駐メモリは、最後のコミットの調整用ビルド同士の1ペア（2局）をSTCの持ち時間で指して測った。

```console
<最後のコミットのminase> match run \
  --run-dir data/matches/qsearch-forms-rss --seed 4470000000 \
  --candidate "<調整用ビルド> --protocol usi --rules engine-default" \
  --baseline "<調整用ビルド> --protocol usi --rules engine-default" \
  --each time=10000+100 --concurrency 2 elo --pairs 1
```

## エンジン

起点はコミット`662c1ab6`（[探索の関数形の見直しの統括計画](../../plans/archived/search-forms.md)のサブタスク4の完了後のmaster）、最後のコミットは`e9abbc86`である。各コミットは結果の表に挙げる。
`e9abbc86`はQ6の`394d7ed3`の後のコミットであり、係数の既定値に依存していたテストを直しただけで、探索の挙動は変えていないので、benchの出力はQ6と同じである。
規則セットは`engine-default`、探索のワーカーは1、置換表は既定の256 MBである。

## 環境

測定機はIntel Core Ultra 7 265KF（性能コア8個と高効率コア12個、20スレッド）である。
ほかの対局測定、SPSA、教師生成、および学習は動いていなかった。lishogiのBotは止めておらず、探索速度はBotのエンジンが動いていない間にだけ測った。

### 探索速度

起点と最後のコミット、およびQ1の直前（移行3）と直後のコミットを、それぞれ交互に3回ずつ測った。測定の間、Botは通信対局を指していたが、各回の前にBotのエンジンが3秒間CPUを使っていないことを確かめ、各回の間にBotのエンジンが使ったCPU時間がすべて0秒だったことを確かめた。
NPSは1秒あたりの探索ノード数、所要時間は深さ9で全15局面を読み終える時間である。

| 回 | 起点のNPS | 起点の所要時間 | 最後のNPS | 最後の所要時間 |
|---:|---:|---:|---:|---:|
| 1 | 792,290 | 0.350411秒 | 728,882 | 0.372327秒 |
| 2 | 792,756 | 0.350205秒 | 733,841 | 0.369810秒 |
| 3 | 793,627 | 0.349820秒 | 734,963 | 0.369246秒 |

深さ9の探索ノード数は、起点が277,627、最後のコミットが271,382であり、2.2%少ない。
最後のコミットは、起点に比べてNPSが約7.4%下がり、深さ9を読み終える時間が約5.6%延びた。

| 回 | 移行3のNPS | 移行3の所要時間 | Q1のNPS | Q1の所要時間 |
|---:|---:|---:|---:|---:|
| 1 | 789,469 | 0.351663秒 | 780,575 | 0.529623秒 |
| 2 | 791,842 | 0.350609秒 | 780,843 | 0.529440秒 |
| 3 | 791,649 | 0.350694秒 | 778,833 | 0.530807秒 |

静止探索で補正値を読むQ1は、NPSを約1.4%下げた。深さ9の探索ノード数は277,627から413,410へ約49%増えたので、深さ9の所要時間は約51%延びた。この増加は、深さ3、5、7の合計の減少（11.3%）と向きが逆であり、後のコミットで深さ9の探索ノード数は起点より少なくなった。

### 負荷時の速度

調整機の持ち時間の換算に使う測定機の負荷時の速度（[統括計画](../../plans/archived/search-forms.md#持ち時間の換算)）を、起点と最後のコミットの調整用ビルドで測った。
`scripts/vast-spsa/bench.py`で16本の`minase dev bench --depth 9 --repetitions 3`を同時に走らせた1本あたりのNPSの平均を1回とし、Botのエンジンが動いていない間に、最後のコミットで5回、起点で3回測った中央値である。

| コミット | 各回のNPS | 中央値 |
|---|---|---:|
| 起点`662c1ab6` | 449,106、458,408、439,286 | 449,106 |
| 最後`e9abbc86` | 359,196、381,699、377,413、372,435、385,841 | 377,413 |

負荷時の速度は約16%下がり、1つのコアで測った約7.4%の低下より大きかった。
最後のコミットは静止探索の全ノードで置換表を照会するので、16本が同時にメモリへアクセスする負荷の下で1本あたりの速度が大きく下がったと考えているが、確かめてはいない。

### 最大常駐メモリ

探索速度と同じ実行で取得した最大常駐メモリは、起点が約509.4 MB、最後のコミットが約509.4 MBであり、変わらなかった。置換表のエントリは16バイトのままである。
調整用ビルド同士の1ペアをSTCの持ち時間で指したときの1局あたりの最大常駐メモリ（2局のそれぞれで2つのエンジンの最大常駐メモリを足し、その大きい方）は1,003,966,464バイトであり、[サブタスク4の記録](../correction-history-tables/correction-history-tables-bench.md)の1,002,328,064バイトとほぼ同じだった。

### 係数の既定値に依存するテスト

各調整係数の既定値を、その係数の調整範囲の1/3と2/3の位置に置いた一時的な`params.rs`で、`cargo test --workspace --no-fail-fast`と`cargo test -p minase --lib --features search-stats,tuning --no-fail-fast`を実行した。
1/3の表では7件、2/3の表では8件のテストが失敗した。
そのうち7件の原因は、静止探索のstand-patが補正後の値になったことにある。補正表が学習する前でも、continuation correctionの番兵の要素の初期値と重みの係数によって補正値が0にならないので、補正前の静的評価から導いた期待値と1か2ずれた。
残りの1件の原因は、aspiration windowsの中断のテストが、現在の係数で測ったノード数から中断の上限を決めていたことにある。
テストは、補正を検査しないものでは補正表を0にしてから確かめ、中断のテストでは係数によらずノード数が決まる局面を使うように直した（コミット`e9abbc86`）。
最後のコミットでは、1/3と2/3のどちらの表でもすべてのテストが通った。

## 結論

4つの移行のコミットは探索を変えず、Q1からQ6のコミットは3つの深さの合計で探索ノード数を9.8%減らした。
最後のコミットは起点に比べて、深さ9の探索ノード数が2.2%少なく、NPSが約7.4%低く、深さ9を読み終える時間が約5.6%長い。
NPSの低下のうちQ1の補正値の読み出しによる分は約1.4%であり、残りの内訳は測っていない。考えられる要因は、静止探索の全ノードでの置換表の照会、王手の判定（深さ9で151,615回）、および低価値の群の生成の増加である。

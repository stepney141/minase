# vast.aiの調整機でSPSAを実行するスクリプトの検証

## 目的

[探索の関数形の見直しの統括計画](../../plans/archived/search-forms.md)のフェーズ1として、`scripts/vast-spsa/`の`launch.sh`、`remote.sh`、および`fetch.sh`と、教師生成と共通の処理を置く`scripts/vast/common.sh`を実際のvast.aiの機械で動かし、統括計画の「検証」の表の条件で、正常の流れと異常時の止まり方を確かめる。
棋力測定ではない。

## コマンドライン

各検査は、測定機で次の形で実行した。セッション名は検査ごとに`verify-a`から`verify-f`とした。

```console
bash scripts/vast-spsa/launch.sh <セッション名> <出品のID> <期限までの分数>
nohup bash scripts/vast-spsa/fetch.sh <セッション名> > data/vast-spsa/<セッション名>/fetch.log 2>&1 &
```

各セッションの`session.env`は、調整対象を2026年10月17日のmasterの先頭`99ccc6bb`、runnerを統括計画のブランチのコミット`1ed11881`（再開時のビルドし直しを受け入れる`minase spsa`の変更を含む）、規則を`engine-default`、1反復のペア数を8とし、測定機の負荷時の速度`LOCAL_NPS`を[試走](vast-spsa-trial.md)の1,264,584、1局あたりの最大常駐メモリ`GAME_RSS_BYTES`を630,000,000バイトとした。
パラメーターファイルは、`minase spsa params`が出力したmasterの既定のファイルから`FmScale`の行を除いた38係数である。
検査ごとに変えた値は、結果の表に書く。

## エンジン

調整用ビルドは、各調整機で`99ccc6bb`を`--features tuning`つきでビルドしたminaseである。
runnerは、各調整機で`1ed11881`をビルドした通常のminaseである。
`fetch.sh`の`minase spsa apply`による検査は、測定機のworktreeでビルドしたrunnerで行った。

## 環境

測定機は、Intel Core Ultra 7 265KF（20スレッド）である。
調整機は、統括計画の選定条件で照会した出品から、その時点で安いものを選んだ。

| セッション | インスタンス | CPU | 物理コア | 同時対局数 | 負荷時の速度 | `f` |
|---|---|---|---:|---:|---:|---:|
| verify-a | 56422592 | AMD EPYC 7W83の2基構成（台湾） | 128 | 127 | 588,672 NPS | 2.15 |
| verify-b（1台目） | 56425523 | AMD EPYC 7W83の2基構成（台湾） | 128 | 127 | 記録なし（2台目の記録で上書きされた） | 2.15 |
| verify-b（2台目） | 56427939 | AMD EPYC 9K84の2基構成（ベトナム） | 192 | 191 | 828,920 NPS | 1.53 |
| verify-c | 56428284 | AMD EPYC 7W83の2基構成（台湾） | 128 | 51 | 658,190 NPS | 1.92 |
| verify-d | 56429613 | AMD EPYC 7742の2基構成（台湾） | 128 | 127 | 記録なし | 記録なし |
| verify-e | 56434385 | AMD EPYC 9654の2基構成（カナダ） | 192 | 164 | 503,953 NPS | 0.60 |
| verify-f | 56429868 | AMD EPYC 9654の2基構成（スペイン） | 192 | — | — | — |

表の`f`は、測定機の負荷時の速度`LOCAL_NPS`を調整機の負荷時の速度で割った換算係数である。
verify-cの同時対局数51は、`GAME_RSS_BYTES`を大きくしてメモリから決まるようにした値である。
verify-dとverify-eの`f`は、`LOCAL_NPS`を小さくして持ち時間を短くしたので、測定機との比較には使えない。
時間単価は1時間0.72〜2.00米ドルであり、検証全体の費用は、残高の減り方から本番のセッションの分を除いて約4米ドルと見積もった。

## 結果

| 条件 | 変えた値 | 結果 |
|---|---|---|
| 選定条件を満たさない出品（48スレッド）を`launch.sh`に与える。 | — | 「選定条件を満たす出品の中に、指定した出品が見つかりません」と表示し、機械を作らずに止まった。 |
| 同じラベルの調整機があるときに`launch.sh`を実行する。 | verify-aの稼働中 | 「同じラベルのインスタンスがあります」と表示し、機械を作らず、`deadline`も書き換えずに止まった。 |
| 10分以内に稼働しない機械（カリフォルニアのEPYC 7K62）で起動する。 | verify-a | 10分の上限で「起動を確認できないため削除します」と表示し、削除を確かめて止まった。 |
| 小さいセッションを中断せずに実行し、`fetch.sh`で取得する。 | verify-a、2反復 | 全2反復が`run/`にそろい、`apply`の検査が通り、調整機の削除を確かめて終了コード0で終わった。 |
| 実行中に`vastai reboot instance`でコンテナを再起動する。 | verify-b、40反復、6反復の適用後 | 起動時スクリプトが`remote.sh`を起動し直し、`remote.sh`は既存の実行ディレクトリを`--resume`で再開した。適用済みの6反復は再計算しなかった。 |
| 実行中に調整機を削除し、別のCPU型の調整機を`launch.sh`で作る。 | verify-b、35反復の時点で削除（手元の`run/`は6反復） | 2台目は`run/`を受け取り、その機械で調整用ビルドを作り直して`--resume`で再開した。runnerは実行ファイルのSHA-256の違いを通知して続行し、全40反復がそろって`apply`の検査が通り、削除を確かめて終了コード0で終わった。1台目が削除までに進めた29反復は失われた。 |
| 所要時間の見込みが上限を超えるセッションを始める。メモリから同時対局数が決まるようにする。 | verify-c、3,750反復、`GAME_RSS_BYTES` 4,000,000,000 | 同時対局数は物理コア数から求める127ではなく、メモリから求める51になった。所要時間の見込みは45.4時間であり、`remote.sh`は事前確認の前に終了コード3で止まった。`fetch.sh`は記録を表示し、調整機を削除して終了コード3で終わった。 |
| `incoming/`に適用番号の欠けた記録を作り、再開用の写しを更新させる（測定機だけで実施）。 | verify-bの40反復から適用番号20を除く | `sync_run.py`は「適用番号が1から連続していません」と表示して終了コード2を返し、`run/`は前の40反復のまま残った。 |
| 時間切れが起きる短い持ち時間で時間切れの事前確認を行う。 | verify-d、`LOCAL_NPS` 20,000 | 事前確認が異常件数0の条件を満たさず、`remote.sh`は本番を始めずに終了コード4で止まった。`fetch.sh`は調整機を停止して0以外の終了コードで終わった。 |
| 事前確認の途中で、エンジンのプロセスを`kill -9`で1つ終了させる。 | verify-e、`LOCAL_NPS` 300,000（持ち時間`time=6000+60`） | 最終要約にクラッシュが1件数えられ（`summary: applied=134`、`crashes=1`）、`remote.sh`は本番を始めずに終了コード4で止まった。`fetch.sh`は調整機を停止して0以外の終了コードで終わった。 |
| 期限を短くして調整機を作る。 | verify-f、期限20分、40反復 | 期限（3時20分46秒）の約3分後には、`actual_status`が`exited`、`intended_status`が`stopped`になっていた。停止した調整機からの`vastai copy`は、貸し手の機械で`bwrap: command not found`となって失敗し、`fetch.sh`は取得できなかった。 |
| `commit:`の形式の調整対象で、記録と異なるコミットの調整用ビルドで再開する。 | — | 実機では行わず、`minase spsa`の単体テスト（`resume_rejects_different_commit_even_with_matching_engine_digest`）で、エンジンの不一致として止まることを確かめた。 |

`vastai copy`は、コンテナのSSHではなく貸し手の機械のrsyncのデーモンを通る。
検証では、ベトナムの貸し手で動いているインスタンスからの取得が`kex_exchange_identification: read: Connection reset by peer`で3回続けて失敗し、台湾の貸し手で起動直後の1回目が`rsync error: error starting client-server protocol (code 5)`で失敗した。
このため、動いているインスタンスからは、コンテナのSSHを通したrsyncで取得するように`fetch.sh`を改め、改めた後のverify-bの2台目では取得が通った。
停止したインスタンスからの取得は`vastai copy`でしかできないので、上のverify-fのように貸し手によっては失敗する。

`fetch.sh`を`kill`で止めると、その子の`sleep`がロックのファイル記述子を引き継いだまま残り、最大10分のあいだ次の`fetch.sh`と`launch.sh`が「実行中」として止まった。
`flock`の`-o`でロックのファイル記述子を子へ渡さない形に改めた。

## 結論

統括計画の「検証」の表の条件は、停止した調整機からの取得を除いて、すべて期待どおりの結果になった。
停止した調整機からの取得は貸し手の環境に依存して失敗することがあるので、`fetch.sh`は調整機が動いている間に10分ごとに取得し、調整機が止まった場合に失われる反復を、最後の取得以後の分に抑える。
EPYC 9K84の2基構成は、191本の平均で828,920 NPSであり、30,000ペアのセッションを約9.6時間（測定機での見込み75時間 × 16 × 1.53 ÷ 191）で終えられる見込みである。

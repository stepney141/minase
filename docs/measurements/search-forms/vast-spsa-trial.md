# vast.aiの調整機でのSPSAの試走

## 目的

[探索の関数形の見直しの統括計画](../../plans/search-forms.md)のフェーズ0として、vast.aiで借りる調整機の負荷時の速度と測定機の負荷時の速度から持ち時間の換算係数`f`を求め、換算した持ち時間で両機の手数帯ごとの到達深さを比べる。
あわせて、1局あたりの最大常駐メモリを測り、時間切れの事前確認と同じ反復数のSPSAで異常件数を数え、所要時間と費用の見積もりを実測で確かめる。
棋力測定ではない。

## コマンドライン

対象は、2026年10月17日時点のmasterの先頭`99ccc6bb`の調整用ビルドである。
測定機と調整機は、それぞれ次のコマンドで調整用ビルドを作った。このコマンドは既定のパラメーターファイルを出力するが、その前に、指定したコミットの調整用ビルドを作って`target/match-cache/`に置く。調整機では、GitHubからcloneしたリポジトリで`cargo build --release --locked --bin minase`を実行してrunnerを作ってから、このコマンドを実行した。

```console
minase spsa params --engine commit:99ccc6bb --rules engine-default
```

負荷時の速度は、同時対局数と同じ数の`minase dev bench --depth 9 --repetitions 3`のプロセスを同時に起動し、各プロセスが出力する中央値NPSの平均として、各機で3回測った。

調整機は次のコマンドで作った。起動時スクリプトは、`/root/.ssh`の所有者と権限の修正、tmuxを開かせない`/root/.no_auto_tmux`の作成、および期限での自己停止の予約を行う（[vast.aiでの教師生成の試走](../vast-selfplay/vast-selfplay-trial.md)と同じ方式）。

```console
vastai create instance <出品のID> --image rust:1.98.0-bookworm --disk 50 --ssh --direct --cancel-unavail \
  --label minase-spsa-trial-<番号> --onstart <起動時スクリプト>
```

到達深さの比較の対局は、両機とも基本シード5,600,000,000で、調整用ビルドを起動コマンドの形式で候補と基準の両方に指定した。

```console
# 測定機（STC、同時対局数16、95ペア）
minase match run --run-dir data/vast-spsa-trial/local-stc --seed 5600000000 \
  --candidate "<調整用ビルド> --protocol usi --rules engine-default" \
  --baseline "<調整用ビルド> --protocol usi --rules engine-default" \
  --each time=10000+100 --concurrency 16 elo --pairs 95
# 調整機（換算した持ち時間、同時対局数95、190ペア）
minase match run --run-dir /workspace/job/remote-stc --seed 5600000000 \
  --candidate "<調整用ビルド> --protocol usi --rules engine-default" \
  --baseline "<調整用ビルド> --protocol usi --rules engine-default" \
  --each time=14600+146 --concurrency 95 elo --pairs 190
```

手数帯ごとの平均到達深さは、測定機の全95ペアと、調整機のペア番号1〜95を、`scripts/clock_profile.py --budget quadruple-soft`で集計した。

SPSAは、`minase spsa params`が出力した既定のパラメーターファイルから`FmScale`の行を除いた38係数で、調整機で次のとおり実行した。反復数78は、統括計画の`⌈13 × 同時対局数 ÷ 16⌉`である。

```console
minase spsa --run-dir /workspace/job/spsa-trial --seed 5700000000 \
  --engine commit:99ccc6bb --params /workspace/job/trial.params \
  --rules engine-default --each time=14600+146 --concurrency 95 \
  --iterations 78 --pairs-per-iteration 8
```

## エンジン

調整用ビルドは、両機ともコミット`99ccc6bbeff0360fe48598de54d96b1d4e64621a`を`--features tuning`つきでビルドしたminaseである。
実行ファイルのSHA-256は、測定機で`2d8ca3f8…`、調整機（Threadripper PRO 9995WX）で`a2968d1f…`であり、`target-cpu=native`のため機械ごとに異なる。
規則は`engine-default`（`L0,P0,R1,E0`）、置換表は既定の256 MB、探索のワーカーは1である。

## 環境

測定機は、Intel Core Ultra 7 265KF（性能コア8個と高効率コア12個、20スレッド）である。
測定の間、同じ機械でlishogiのBotが動いていたが、ほかの対局測定、SPSA、教師生成、および学習は動いていなかった。

調整機の候補は、2026年10月17日に統括計画の選定条件で照会し、見込みの1回の費用の安い順に試した。統括計画のSPSAのセッションで負荷時の速度を測った記録のあるCPU型はなかったので、見込みの費用は時間単価に24時間を掛けた値である。

|---|---|---|---:|---:|---:|---|---:|---:|---|
| 1 | 56402420 | AMD EPYC 7642の2基構成（Zen 2、最大2.3 GHz） | 96 | 0.60米ドル | 95 | 532,418、533,902、533,535 | 2.37 | 約30時間 | 24時間の上限を超えるので削除 |
| — | 38001277 | Intel Xeon Phi 7250 | 68 | 0.87米ドル | — | — | — | — | 試さず |
| 2 | 43920286 | AMD EPYC 7B12の2基構成（Zen 2、最大2.25 GHz） | 128 | 1.05米ドル | 127 | 440,963、433,448、444,681 | 2.87 | 約27時間 | 24時間の上限を超えるので削除 |
| 3 | 55530776 | AMD Ryzen Threadripper PRO 9995WX（Zen 5、最大5.46 GHz） | 96 | 1.29米ドル | 95 | 871,756、867,528、866,859 | 1.46 | 約18.4時間 | 採用 |

時間単価はディスク50 GBを含む。
Xeon Phi 7250は、物理68コアでは同時対局数が67になる。所要時間を24時間以内に収めるには`f`が約1.34以下、つまり1コアの負荷時の速度が測定機の約75%以上でなければならない。動作周波数1.4 GHzのこのCPUでは届かないので、試さずに外した。

採用した調整機は、インスタンス56409205（マシンID 7584、ノルウェー、信頼度0.998、送信速度827 Mbps）である。
CPUはThreadripper PRO 9995WXの1基（物理96コア、192スレッド）であり、搭載するRTX 3090は使っていない。
コンテナのメモリの上限（cgroup v1）は258,729,836,544バイト（約241 GiB）、CPU時間の上限は論理CPU約184.3個分だった。
作成から`running`までは約44秒、cloneとrunnerのビルドは約33秒だった。

## 結果

### 負荷時の速度と換算係数

測定機の16本の平均は、3回で1,262,967、1,266,100、および1,264,686 NPSであり、平均は1,264,584 NPSだった。
3回の幅（最大と最小の差）は平均の0.25%である。
調整機の95本の平均は、3回で871,756、867,528、および866,859 NPSであり、平均は868,714 NPS、幅は平均の0.56%だった。
換算係数は`f` = 1,264,584 ÷ 868,714 ≈ 1.4557であり、小数第2位に丸めて1.46とした。換算した持ち時間は`time=14600+146`である。

### 到達深さ

| 手数帯 | 測定機の平均到達深さ | 調整機の平均到達深さ | 差 | 測定機の思考時間の中央値 | 調整機の思考時間の中央値 | 比 |
|---|---:|---:|---:|---:|---:|---:|
| 0〜49 | 9.10 | 9.45 | +0.35 | 91 ms | 131 ms | 1.44 |
| 50〜99 | 8.66 | 8.94 | +0.28 | 113 ms | 161 ms | 1.42 |
| 100〜149 | 8.34 | 8.62 | +0.28 | 131 ms | 191 ms | 1.46 |
| 150〜199 | 8.12 | 8.34 | +0.22 | 142 ms | 202 ms | 1.42 |
| 200〜299 | 8.03 | 8.31 | +0.28 | 147 ms | 212 ms | 1.44 |
| 300〜399 | 8.73 | 9.06 | +0.33 | 123 ms | 181 ms | 1.47 |
| 400〜 | 12.87 | 13.30 | +0.43 | 91 ms | 121 ms | 1.33 |

調整機は、どの手数帯でも測定機より0.22〜0.43手深く読んだ。
思考時間の比はほぼ`f`のとおりなので、換算した持ち時間の下で、調整機の1手あたりの探索量は測定機よりやや多い。
benchの負荷時の速度の比が、対局中の両機の速度の比よりやや大きいことを示すが、原因は調べていない。
2026年10月18日、利用者は、SPSAは係数の最適化なのでこの程度の差に厳密にこだわる必要はないとして、`f` = 1.46のままSPSAを始めると決めた。

対局はどちらも時間切れとエンジン異常が0件であり、手数上限による破棄は測定機で1ペア、調整機で1ペアだった。
所要時間は、測定機の95ペアが834秒、調整機の190ペアが803秒だった。

### メモリ

1局あたりの最大常駐メモリ（記録の`candidate_peak_rss_bytes`と`baseline_peak_rss_bytes`の和）は、測定機で最大628 MB、中央値604 MB、調整機で最大626 MB、中央値606 MBだった。
採用した調整機では、メモリから求める同時対局数は241 GiB ÷ (0.63 GB × 1.25)で約300となり、物理コア数から求める95の方が小さい。

### SPSA

78反復をすべて適用し、有効ペアは621、手数上限で破棄したペアは3、異常件数（不正着手、クラッシュ、応答期限超過、時間切れ、拒否着手）はすべて0だった。
所要時間は1,467秒だった。

### 所要時間と費用の見積もり

SPSAの624ペアに1,467秒かかったので、同じ機械で30,000ペアのセッションは約70,500秒（約19.6時間）かかる見込みである。
測定機での所要時間の見込み75時間と負荷時の速度から求めた見込み（75 × 16 × 1.46 ÷ 95 ≈ 18.4時間）より約7%長い。
1時間1.29米ドルでは、1セッションは約25米ドルになる。
試走の費用は、3台の利用時間と時間単価から約1.3米ドルである。

## 結論

Threadripper PRO 9995WXの調整機では`f` = 1.46となり、30,000ペアのSPSAを約20時間、約25米ドルで実行できる見込みである。
換算した持ち時間の下で、調整機は測定機より約0.3手深く読む。
異常件数はすべて0であり、同時対局数95での対局の進行に問題は見つからなかった。

# 探索の枝刈りとLMRの関数形の変更による探索ノード数と探索速度

## 目的

[探索の枝刈りとLMRの関数形の見直し](../plans/search-pruning-forms.md)のフェーズ1で入れた9コミットを対象とする。
探索を変えない移行の3コミットについては、探索ノード数、評価値、および最善手が起点と同じになることを確かめる。
探索を変える6コミットについては`minase dev bench`の探索ノード数の変化を記録し、あわせて起点と最後のコミットの探索速度を比べる。
棋力測定ではない。新しい係数はStockfishの値の換算値のままであり、採否はSPSAで係数を調整した後の段階ゲートで判定する。

## 方法

ノード数は、各コミットのworktreeで`cargo build --release --bin minase`によりビルドしたminaseを使い、次のコマンドを深さ3、5、7について1回ずつ実行して数えた。
`dev bench`は固定の15局面を固定の深さで探索するので、同じバイナリなら出力は毎回同じになる。

```console
minase dev bench --depth <深さ>
```

探索を変えない移行の3コミット（F0、F1の準備、F4の準備）については、全15局面の3つの深さのすべてで、探索ノード数、評価値、および最善手が直前のコミットと一致することを確かめた。
探索を変える6コミットについては、直前のコミットからの変化を記録した。6コミットは設計書の順にF2、F1、F3、F4、F5、F6と並ぶ。F1がF2の定める静的評価と判定用の評価値を使うので、F2を先に置いている。

探索速度は、起点と最後のコミットのminaseを交互に3回ずつ、性能コアのCPU 3に固定して測った（[速度比較のbenchは性能コアへ固定して測る](../lessons/pin-bench-to-performance-core.md)）。
各回の値は、計測外のウォームアップ1回の後に3回探索した中央値である。

```console
taskset -c 3 minase dev bench --depth 9 --repetitions 3
```

## 環境

測定機はIntel Core Ultra 7 265KF（性能コア8個と高効率コア12個、20スレッド）である。
測定の間、同じ機械でlishogiのBotが動いていたが、ほかの対局測定、SPSA、教師生成、および学習は動いていなかった。
探索のワーカーは1、置換表は既定の256 MBである。

F1（reverse futility pruning）でノード数が大きく減った理由は2つある。
1つは、新しい余裕値の開始値がStockfishの換算値であり、深さ1で歩兵価値の約24%と、起点の余裕値（歩兵価値の428%）よりはるかに小さいことである。
もう1つは、適用する残り深さの上限が3から18へ広がったことである。
F4（LMR）で増えたのは、PVノードで減深後の深さに1手を足し、根からの手数が反復の深さの2倍未満なら負の減深量で最大2手まで延長するためである。
F6（前の反復の根の評価値が大きい反復で、reverse futility pruning、razoring、およびnull move pruningを控える調整）の変化は、深さ7で評価値の絶対値が約3,000以上の8局面にだけ現れ、ほかの7局面のノード数はF5と同じだった。
深さ7の最善手は、15局面のうち10局面で起点と同じだった。

### 探索速度

| 回 | 起点（`99ccc6bb`）のNPS | 最後のコミット（`388c5244`）のNPS |
|---:|---:|---:|
| 1 | 1,549,547 | 1,955,843 |
| 2 | 1,564,091 | 1,953,930 |
| 3 | 1,535,498 | 1,949,852 |

3回の中央値は、起点が1,549,547 NPS、最後のコミットが1,953,930 NPSであり、最後のコミットは起点の1.26倍である。
3回のばらつきの幅（最大と最小の差）は、中央値に対して起点が1.8%、最後のコミットが0.3%であり、両者の速度の差（26%）より十分に小さい。
探索速度を測った深さ9では、15局面の探索ノード数は、起点が4,284,286、最後のコミットが4,292,601であり、所要時間は起点が2.74〜2.79秒、最後のコミットが2.19〜2.20秒だった。

## 結論

探索を変えない移行の3コミットは起点と同じ探索になり、探索を変える6コミットのノード数の変化は、結果の節に書いたとおり各項目の式と開始値から説明できる。
最後のコミットでは、F2で全ノードの静的評価の計算が、F1とF4で置換表の手の合法性の確認が加わったが、探索速度は起点より26%速かった。
reverse futility pruningなどで手を生成せずに返るノードの割合が増え、1ノードあたりの処理時間が短くなったためと考えられる。ただし、ノードの種類ごとに数えて確かめてはいない。

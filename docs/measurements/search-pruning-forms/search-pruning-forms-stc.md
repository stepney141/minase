# 枝刈りとLMRの関数形を変えた候補のSTC

## 目的

[探索の枝刈りとLMRの関数形の見直し](../../plans/search-pruning-forms.md)のフェーズ5として、[SPSA](search-pruning-forms.md)の最終値を反映した候補が起点より短時間条件で強いかを、GSPRTで測る。
2026年10月18日、この測定の実行中に利用者は、後続のサブタスクで強さが改善される可能性があるので、本書の変更をSTCの結果によらず採用すると決めた。続けて、各サブタスクのSTCは採否に使わない記録とし、LTCは行わないと決めた（[統括計画](../../plans/search-forms.md)の設計判断「各サブタスクの採否」）。
したがって、この測定の判定は採否に使わない。

## コマンドライン

[統括計画](../../plans/search-forms.md)の決定により、SPSAを終えた調整機で、持ち時間を換算せずに実行した。

```console
target/release/minase match run \
  --run-dir /workspace/job/matches/search-pruning-forms-stc --seed 3350000000 \
  --candidate commit:d52aefb3a50732a638d860df903593045d8f37c0 \
  --baseline commit:99ccc6bbeff0360fe48598de54d96b1d4e64621a \
  --each time=10000+100 --concurrency 95 gsprt --max-pairs 3000
```

実行ディレクトリは、実行中は10分ごとに、終了後にもう一度、測定機の`data/matches/search-pruning-forms-stc`へ取得した。

## エンジン

候補と起点、およびrunnerは、[事前対局](search-pruning-forms-smoke.md)と同じ実行ファイルである。
候補は`d52aefb3a50732a638d860df903593045d8f37c0`（SHA-256 `40e2cfb7d923776b345a88f5e33e3fca1c37a6ff22e187b46f3bbe3a61571b2a`）、起点は`99ccc6bbeff0360fe48598de54d96b1d4e64621a`（SHA-256 `fd14865d6dbd14e06850cab0171887b6600355d4db74a4741073fe383ca0820d`）である。
runnerは、調整機で`388c5244`をビルドした通常のminase（2.4.0、SHA-256 `029a87159c8955a11910e6019cc99b0625aaa630e2afc6d62c9b566f71353483`）であり、起動の記録は1件である。
規則セットは`engine-default`（`L0,P0,R1,E0`）である。

## 環境

調整機は、SPSAと同じvast.aiのAMD Ryzen Threadripper PRO 9995WX（インスタンス56409205、物理96コア、論理192スレッド、runnerが記録した論理CPUは184）である。
この機械の1コアは測定機（Intel Core Ultra 7 265KF）より遅く、負荷時の速度の比`f`は1.46である（[試走の記録](../search-forms/vast-spsa-trial.md)）。持ち時間は換算していないので、1手の探索量は測定機の同じ条件より少ない。
候補と起点はいずれも`Threads=1`、`USI_Hash`は各256 MB、同時対局数は95である。
手数上限は4,096手、応答タイムアウトは120秒、仮説はH0がelo=0、H1がelo=10、α = β = 0.05である。
2026年10月18日17時52分から18時19分に実施した。

| 量 | 値 |

| 判定 | `H0` |
| 判定までのペア | 776（有効766、手数上限到達による破棄10） |
| ペンタノミアル度数 | [188, 23, 384, 16, 155] |
| LLR | −2.962 |
| エンジン異常 | 不正着手0、クラッシュ0、応答タイムアウト0、時間切れ0、拒否着手0 |

有効766ペアの度数から求めた候補の平均得点は0.476であり、Eloに直すと約−17である。
この値は固定局数の推定ではなく、採否にも使わない。
保存されたペアは番号1〜1,117のうち1,077個であり、判定の時点で並行して進んでいた番号777以降のペアは統計に含まれていない。

## 弱くなった原因の手がかり

原因は特定していない。設計書は全項目を1つの候補として束ね、項目ごとの寄与を測らない形にしているからである。
原因の調査は、統括計画を終えてから行うかどうかを決める（2026年10月18日の利用者の決定）。
その時に使えるよう、測定記録から読み取れる手がかりを残す。

- [事前対局](search-pruning-forms-smoke.md)では、候補は同じ時間で起点より平均約2.8手深い反復まで読み終えていた。深く届いても弱いので、減深と枝刈りで読まなかった手の中に必要な手が含まれていたと考えられる。
- [SPSA](search-pruning-forms.md)は、多くの係数をStockfishの換算値より枝刈りと減深を弱める側へ動かした。`ReverseFutilityMultBase`は22から235、`LmpBase`は300から1,799、`LmrCutNode`は393から164になり、`LmrTtCapture`と`LmrMoveCount`は0、`RazoringMargin2`と`DeltaMargin`は範囲の上限になった。
- 68係数のうち14個は、SPSAの最後の1,250反復でも`c_end`の0.5倍以上動いており、調整は収束していなかった。
- 候補はLMRの減深をStockfishの形に寄せたが、それを打ち消すhistoryの項は起点の±1の形のままである。historyの形は統括計画のサブタスク3が扱う。
- このSTCは換算しない持ち時間で行ったので、1手の探索量は、SPSAで係数を選んだ条件より少ない。
- 実装がStockfishと同じ振る舞いになっているかは、F1〜F6の項目ごとには確かめていない。

## 結論

候補は、調整機で持ち時間を換算しないSTCで、起点より10 Elo強いとは言えない（`H0`）。
時間切れとエンジン異常は0件だった。
利用者の決定により、本書の変更はこの判定によらず採用し、LTCは行わない。
7本を通して元のmasterより強くなったかは、統括計画のフェーズ10で確かめる。

# 浅い前向き枝刈りの拡張による探索ノード数、探索速度、および検証探索の矛盾率

## 目的

[浅い前向き枝刈りの深さと対象の拡張](../../plans/archived/shallow-pruning-extensions.md)のフェーズ1で入れた11コミットを対象とする。
探索を変えない移行の2コミット（M1とM2）については、探索ノード数、評価値、および最善手が起点と同じになることを確かめる。
探索を変える9コミット（S1〜S9）については`minase dev bench`の探索ノード数の変化を記録し、あわせて起点と最後のコミットの探索速度、王手の判定の費用、およびnull moveの検証探索の矛盾率を測る。
棋力測定ではない。新しい係数はStockfishの値の換算値のままであり、SPSAで調整した後に事前対局とSTCで強さの変化を記録する。

## コマンドライン

ノード数は、各コミットのworktreeで`cargo build --release --bin minase`によりビルドしたminaseを使い、次のコマンドを深さ3、5、7について1回ずつ実行して数えた。
`dev bench`は固定の15局面を固定の深さで探索するので、同じバイナリなら出力は毎回同じになる。

```console
minase dev bench --depth <深さ>
```

探索速度は、起点と最後のコミットのminaseを交互に3回ずつ、性能コアのCPU 3に固定して測った（[速度比較のbenchは性能コアへ固定して測る](../../lessons/pin-bench-to-performance-core.md)）。
各回の値は、計測外のウォームアップ1回の後に3回探索した中央値である。

```console
taskset -c 3 minase dev bench --depth 9 --repetitions 3
```

王手の判定の費用は、最後のコミットの`Position::gives_check`が同じ判定を2回計算するように書き換えた使い捨ての写しと、元の最後のコミットを、同じ方法で交互に3回ずつ測り、所要時間の差から求めた。
2回目の計算の結果は捨てるので、探索ノード数は変わらない。

検証探索の矛盾率は、`search-stats`機能を有効にしてビルドしたminaseで、全15局面を深さ18と20で探索して数えた。

```console
taskset -c 5 minase dev bench --depth 18
taskset -c 5 minase dev bench --depth 20
```

最後のコミットでは、S7で加えた`search-stats`の計数（完了した検証探索の数と、その値がβを下回った数）を読んだ。
起点は検証探索を持たないので、[段階4の診断](../strength-stage4/strength-stage4-nmp-verify-bench.md)と同じく、起点のコミットを展開した使い捨ての写しに、null moveの打ち切りが決まった後で同じ条件（残り深さ16以上、検証探索中でない）の検証探索を追加で行って数える計測を入れた。
この計測は打ち切りの判断と返す値を変えないが、追加の探索で置換表などが更新されるので、計測のない起点とは探索が少し異なる。計測のコードは残していない。

## エンジン

起点はコミット`a892a5e6`、最後のコミットは`364c10aa`である。各コミットは結果の表に挙げる。
規則セットは`engine-default`、探索のワーカーは1、置換表は既定の256 MBである。

## 環境

測定機はIntel Core Ultra 7 265KF（性能コア8個と高効率コア12個、20スレッド）である。
測定の間、同じ機械でlishogiのBotが動いていたが、ほかの対局測定、SPSA、教師生成、および学習は動いていなかった。

### 探索速度

| 回 | 起点（`a892a5e6`）のNPS | 最後のコミット（`364c10aa`）のNPS |
|---:|---:|---:|
| 1 | 1,895,537 | 1,101,039 |
| 2 | 1,904,118 | 1,097,713 |
| 3 | 1,897,599 | 1,098,095 |

深さ9の探索ノード数は、起点の1,059,634から最後のコミットの370,388へ65%減り、全15局面を読み終える時間は約0.558秒から約0.337秒へ40%減った。
1秒あたりの探索ノード数（NPS）は約190万から約110万へ42%下がった。
1ノードあたりの時間は約1.7倍になったが、読む局面が減った分だけ、同じ深さを早く読み終える。
探索ノード数は着手を適用した回数なので、飛ばした手の判定にかかる時間は、残った手の1ノードあたりの時間に加わる。

### 王手の判定の費用

| 回 | 最後のコミットの所要時間 | 王手の判定を2回計算した写しの所要時間 |
|---:|---:|---:|
| 1 | 0.348738秒 | 0.360805秒 |
| 2 | 0.351755秒 | 0.369574秒 |
| 3 | 0.352390秒 | 0.368140秒 |

王手の判定を2回計算すると、所要時間は0.012〜0.018秒、約4%増えた。
したがって、王手の判定の費用は探索時間の約4%である。
`perf`による自己時間の割合では、利きの逆引きと計算に関わる関数（`attackers_to_by`、`sliding_control`、`piece_control_without_special`、`piece_control_with_occupancy`、`gives_check`）の合計が、深さ12の探索で起点の約13%から最後のコミットの約27%へ増えた。
王手の判定はこのうち約4%に当たり、残りは、静かな手のSEEと、枝刈りを判定するノードと手が増えたことによる王駒への利きの判定とSEEだと考えられるが、呼び出し元ごとには分けていない。

## 結論

M1とM2は探索を変えず、S1からS9は3つの深さの合計で探索ノード数を58%減らし、深さ9を読み終える時間を40%縮めた。NPSは42%下がった。
王手の判定は探索時間の約4%なので、設計書の取り決めに従い、Stockfishの形の前計算は加えない。
検証探索の矛盾率は起点と最後のコミットのどちらも0%であり、[前の設計書の事前対局](../search-pruning-forms/search-pruning-forms-smoke.md)の読み終えた深さの平均（約12手）から見て、STCでは残り深さ16以上のノードがほとんど現れないので、検証探索は実質的に働かない。

# 調整係数の表の導入によるbench速度比較

## 目的

探索と時間管理の係数を `src/search/params.rs` の表へ移す変更について、通常ビルドの探索が1ノードも変わらず、NPSが変更前の99%以上であることを判定し、調整用ビルドの速度比を記録する。

## コマンドライン

変更前、変更後の通常ビルド、変更後の調整用ビルドの順に、次のコマンドを交互に5巡実行した。

```sh
taskset -c 3 <bench> --depth 8
```

探索結果の一致は、同じ3つのバイナリの `--depth 6` の出力から `elapsed=` と `nps=` を除いて比較した。
調整用ビルドは `cargo build --release --bin bench --features tuning --target-dir target/tuning` で作った。

## エンジン

変更前はコミット`a65edd4a15b20d3c72bfce39d5ce35007a59f3b2`、変更後は係数の表を導入したコミット`546477937cd0005659ed7e6c97bbd715922d8199`である。
調整用ビルドの係数はすべて既定値のままである。
対局ではないため、規則セットは該当しない。

## 環境

CPUはIntel Core Ultra 7 265KFであり、物理コア数と論理CPU数はいずれも20である。
benchは単一スレッドで、性能コアのCPU 3へ固定して実行した。
測定中は、lishogiのBotの対局と別の作業のビルドが同じ測定機のほかのコアで動いており、負荷平均は約6から7であった。
rustcは1.98.0である。
`USI_Hash`と同時対局数は該当しない。

## 結果

深さ6では、15局面すべての `nodes`、`best`、`score` と総ノード数1,813,911が、3つのバイナリで完全に一致した。
深さ8の総ノード数も、3つのバイナリで10,128,396に一致した。
深さ8のNPSの5回の中央値は、変更前が2,122,145、変更後の通常ビルドが2,123,205、調整用ビルドが2,119,639であった。
変更後の通常ビルドは変更前の100.05%であり、調整用ビルドは通常ビルドの99.83%であった。
各バイナリの5回の最小値と最大値の幅は0.8%以内であった。
破棄ペア数、異常件数、`time_forfeits`、対局の総経過時間は該当しない。

## 結論

通常ビルドの探索は変わらず、NPSは完了条件の99%を上回ったので、係数の表の導入は速度の条件を満たす。

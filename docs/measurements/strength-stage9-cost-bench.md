# 棋力向上段階9の追加特徴の計算費用（bench深さ5）

## 目的

[棋力向上段階9](../plans/strength-stage9.md)のフェーズ1として、追加特徴の重みをすべて0にした構成と段階開始版の毎秒の探索ノード数を比べ、評価のたびに特徴を再計算する費用を項目の組ごとに測る。

## コマンドライン

```console
taskset -c 3 target/release/bench --depth 5 --repetitions 3
```

各構成を3回ずつ実行し、各回が出力する3反復の中央値を記録した。
段階開始版と項目1だけの構成は、交互に実行した。

## エンジン

段階開始版はmasterの `1633f53` である。
追加特徴の構成はブランチ `strength-stage9-diag` であり、3項目すべての構成はコミット `e6574bf` である。
項目1だけの構成と、項目1に項目3の計算だけを加えた構成は、同コミットの `king_features::extract` の近傍升の走査を一時的に変更して測り、変更はコミットしていない。
前者は近傍升の走査を省き、後者は走査を距離1の升に限って守る側の逆引きだけを行う。
どの構成も68列の重みを持ち、重みはすべて0である。

## 環境

測定機はIntel Core Ultra 7 265KF（物理20コア、論理20コア、実メモリ32 GB）である。
測定の間、lishogiのBotの対局（4スレッド）と別の探索プロセス（1スレッド）が動いており、負荷平均は約6だった。
固定しない実行では同じバイナリの値が1.56Mから1.95Mまで揺れたので、性能コア（論理CPU 3）へ固定して測った。
固定後の3回の値の幅は、どの構成でも1%以内だった。
2026年9月21日に実施した。

## 結果

総ノード数は全構成で598,014であり、15局面の最善手と評価値も段階開始版と一致した。

| 構成 | 1評価あたりの逆引きの回数 | 毎秒の探索ノード数（3回） | 段階開始版との差 |
|---|---:|---|---:|
| 段階開始版 | 0 | 2,154,976、2,141,802、2,141,688 | ― |
| 項目1だけ | 0 | 1,958,516、1,944,987、1,946,192 | −9.3% |
| 項目1と項目3の計算 | 最大16 | 959,942、973,196、959,908 | −55.1% |
| 3項目すべて | 最大96 | 381,332、380,205、382,500 | −82.2% |
| 項目1の候補（24列、`001b551`） | 0 | 1,968,223、1,966,215、1,918,161 | −8.5% |

項目1の候補は、ブランチ `strength-stage9-shelter` の項目1の24列だけを持つ構成であり、同じ時間帯に測り直した段階開始版の2,143,956、2,150,297、2,147,582と比べた。
項目1は、王駒の段ごとの前方の升の集合と、縦の走り駒の駒種を初回に表へ前計算している。
前計算の前は、固定しない実行で項目1だけの構成が982,619だった。

1ノードあたりの時間の差から求めると、疑似利きの逆引き `attackers_to_by` は1回あたり約22 nsから33 nsである。
段階開始版の1ノードあたりの時間は約0.47 μsなので、低下を10%以内に収めるには、逆引きは1評価あたり2回程度までしか使えない。

自己対局の持ち時間の感度は、持ち時間2倍で+216 Eloである（[sensitivity-time2x](sensitivity-time2x.md)）。
3項目すべての構成の速度は段階開始版の0.18倍であり、この感度を目安にすると、評価の改善が補うべき速度の損失は約500 Eloに相当する。

## 結論

項目1の再計算の費用は目安の10%を下回るので、項目1はそのまま学習と採否測定へ進める。
項目2と項目3は、王駒の近傍の升ごとに疑似利きを逆引きする現在の定式化では、再計算の費用が採否を左右する。
利用者の決定により、項目2と項目3は学習と採否測定を行わずに見送った。

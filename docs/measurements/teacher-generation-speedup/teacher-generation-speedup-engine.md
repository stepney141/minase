# 探索結果を変えない高速化の測定

## 目的

[教師生成の高速化](../../plans/teacher-generation-speedup.md)の変更について、探索結果が基準版と同じであることを確かめたうえで、探索速度を基準版と比べる。

## コマンドライン

探索結果の一致は、基準版で記録した結果と候補の結果を次の検査で比べて確かめた。
照合の対象は、`dev bench --depth 9`の15局面の全行、2通りのシードの教師ファイルのSHA-256、および6通りの規則セットの14局面を6万ノードで探索した最終の`info`行と`bestmove`である。
教師ファイルのヘッダは`git rev-parse HEAD`を含むので、実行ディレクトリをコミット`9380aa7f`の固定のworktreeにした。

```console
python3 verify_identical.py record --binary <基準版> --out baseline.json
python3 verify_identical.py check --binary <候補> --baseline baseline.json
```

性能コアの比較は次の形で、基準版と候補を回ごとに順序を入れ替えて交互に実行した。

```console
python3 pcore_cmp.py --cpu 3 --rounds 5 base=<基準版> int4=<候補>
python3 pcore_cmp.py --cpu 3 --rounds 3 --max-ply 4000 base=<基準版> int4=<候補>
```

各試行が実行する生成は次のとおりである。

```console
taskset -c 3 perf stat ... -- <バイナリ> data selfplay generate --output <出力> --seed 9010200000 \
  --games 2 --concurrency 1 --nodes 20000 --random-moves 0 --max-ply <200または4000> --hash-mb 16 --allow-dirty
```

生成機の代理環境の比較は次の形で、12個のE-coreで12局を同時に動かした。

```console
python3 ecore_cmp.py --cwd <固定のworktree> --cpus 8-19 --concurrency 12 --rounds 5 --max-ply 300 base=<基準版> int4=<候補>
```

負荷の内訳は、`-C force-frame-pointers=yes`を足したビルドを`perf record --user-callchains --call-graph fp`で採取し、`inline_prof.py`でインライン展開まで解決して集計した。
使ったスクリプトと基準の結果は[付属資料](teacher-generation-speedup-engine/)にある。
呼び出し回数は、`stats_patch*.py`で計数用のカウンタを入れた使い捨てのビルドで数えた。

## エンジン

基準版はmasterのコミット`9380aa7f`であり、候補はブランチ`teacher-speedup`のコミット`6988af2b`である。
両版とも同じネット（`features=P;ft=256;linear=tapered2;head=pairwise-l16-l32`、SHA-256は`987f060d…`）を埋め込み、規則セットは`L0,P0,R1,E0`である。
候補のバイナリのSHA-256は`1b76b030dae838a8…`である。
ビルドは`CARGO_PROFILE_RELEASE_DEBUG=1`を付けたrelease設定、`target-cpu=native`、LTO有効、`codegen-units=1`である。

## 環境

測定機はIntel Core Ultra 7 265KF（性能コア8、高効率コア12、スレッドは計20）で、Linux `6.18.57-2-lts`、Rust `1.98.0`である。
探索ワーカーは1局あたり1、置換表は16 MiBである。
単独スレッドの比較は論理CPU 3、代理環境は論理CPU 8〜19に固定した。
代理環境の1スレッドあたりのキャッシュ量（L2が1 MiB相当、L3が2.5 MiB相当）は生成機（L2が0.5 MiB、L3が2 MiB）に近い。
旧版（`9f393ecc`）と生成0（`6f874692`）の速度比も、代理環境が0.36、生成機が0.33である。
最終の比較を始めた時点では、同じ機械のlishogi Botはほぼ待機していた。

## 結果

### 速度

3つの条件のいずれでも、候補は基準版の約1.55倍の速さになった。

| 条件 | 指標 | 基準版 | 候補 | 比 |
|---|---|---:|---:|---:|
| 性能コア、2局、完局（3回） | 探索速度 | 748,250ノード/秒 | 1,163,869ノード/秒 | 1.555倍 |
| | 命令数/ノード | 27,342.9 | 14,783.0 | −45.9% |
| | サイクル数/ノード | 7,318.1 | 4,786.6 | −34.6% |
| | L1ロードミス/ノード | 30.38 | 23.91 | −21.3% |
| 性能コア、2局、200手（5回） | 探索速度 | 635,914ノード/秒 | 988,006ノード/秒 | 1.554倍 |
| | 命令数/ノード | 31,783.8 | 18,375.9 | −42.2% |
| | サイクル数/ノード | 8,599.6 | 5,791.5 | −32.7% |
| E-core 12個、同時12局、300手（5回） | 探索速度 | 4,608,674ノード/秒 | 7,283,937ノード/秒 | 1.580倍 |
| | 命令数/ノード | 31,429.4 | 17,669.7 | −43.8% |
| | サイクル数/ノード | 9,963.9 | 6,742.3 | −32.3% |
| | ロードのストール/ノード | 1,767.9 | 1,585.7 | −10.3% |
| | うち最終キャッシュミス/ノード | 884.6 | 863.7 | −2.4% |

代理環境の探索速度の範囲は、基準版が3,703,215〜4,611,243、候補が6,050,010〜7,296,437ノード/秒である。
低い値はそれぞれ5回のうち1回だけで、同じ機械のBotの対局と重なった可能性があるが、原因は確かめていない。
参考として、同じ条件の別の実行で旧版は10,700,804ノード/秒、命令数16,607/ノード、サイクル数4,518/ノード、ロードのストール664/ノードだった。
命令数は旧版に近づいたが、メモリ待ちと分岐予測ミスの差は残っている。
生成機での同じ比較はまだ行っていない。

### 探索結果の一致

候補は`verify_identical.py`の全項目で基準版と一致した。
教師ファイルのSHA-256は、シード`9010200000`（2局、2,300万ノード）が`0474f011c52257cf…`、シード`424242`（4局、2,664万ノード）が`382b1e98a61b9269…`である。

別の条件として、候補のコードへ第0世代のネット（コミット`6f874692`）を入れたビルドと、生成機で使っている`6f874692`のビルドを、シード`9000000000`で3局、上限1,200手の生成で比べた。
教師ファイルのSHA-256はどちらも`841f4a17998cada8…`、探索ノード数は1,636万で一致し、経過時間は24.83秒から17.93秒へ縮んだ。

全変更の差分について、旧実装と結果が変わる反例を探すレビューを別途行った。
9規則セット、24局面、各5,000ノードの216通りの探索を比べ、評価値、読み筋、ノード数、最善手がすべて一致し、反例は見つからなかった。
`cargo test -p minase -p minase-core`、`--features search-stats,tuning`の試験、`cargo clippy --workspace --all-targets -- -D warnings`、および`cargo fmt --check`が通った。

### 変更ごとの効果

下表は採用した変更ごとの増分であり、直前の版に対する、性能コアで200手の3回比較の中央値である。
同じ機械でビルドなどの別の作業が同時に動いていた回があるので、サイクル数には揺れがあり、採否は主に命令数で判断した。
作業ごとに別の親から測ったので、値を掛け合わせても最終の比にはならない。

## 結論

探索結果を保ったまま、単独スレッドで1.555倍、生成機の代理環境で1.580倍に速くなった。

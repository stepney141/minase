# 持ち時間の伸縮の形の変更の候補の秒読みつきの短い条件

## 目的

[探索の不安定さに応じた持ち時間の伸縮の設計書](../../plans/time-instability-scaling.md)のフェーズ6として、SPSAの最終値を反映した候補と起点を、秒読みつきの短い条件（持ち時間6秒、秒読み0.3秒）の逐次検定で対局させる。
設計書の案1（2026年10月22日の利用者の決定）により、この条件と長い条件の両方が`H1`なら候補をそのまま統合し、どちらかが`H1`でなければ、探索の不安定さによる持ち時間の伸縮のうち相手との残り時間の差による補正を除く項目の適用を、秒読みが0の時計に限るコミットを加える。

## コマンドライン

統括計画の決定により、SPSAを終えた調整機で実行した。同時対局数は、設計書のとおりSPSAの同時対局数95の半分の47とした。

```console
target/release/minase match run \
  --run-dir /workspace/job/matches/time-instability-scaling-byoyomi-short --seed 5250000000 \
  --candidate commit:1930dcb29cec7d2fc3ebe5bdb65a8f47c9e24eb5 \
  --baseline commit:370f707780548b0fa65d3e1303881a9fd609c05b \
  --each time=6000+0,byoyomi=300 --concurrency 47 gsprt --max-pairs 3000
```

有効1,471ペアの時点で時間切れが1件出たので、測定を止めて原因を調べた。
runnerはシグナルの処理を持たず、バックグラウンドで起動したのでSIGINTも無視された。そこで、runnerとエンジンのプロセスグループをSIGTERMで終了させた。
調べた後、同じ実行ディレクトリを次のコマンドで再開した。

```console
target/release/minase match run \
  --resume /workspace/job/matches/time-instability-scaling-byoyomi-short
```

実行ディレクトリは、終了後に調整機から測定機の`data/matches/time-instability-scaling-byoyomi-short`へ複製した。

## エンジン

候補は、形の変更に[SPSAの最終値](time-instability-scaling.md)を反映したコミット`1930dcb29cec7d2fc3ebe5bdb65a8f47c9e24eb5`である。
起点は、設計書を始めた時点のmaster`370f707780548b0fa65d3e1303881a9fd609c05b`である。
runnerは、調整機で形の変更の最後のコミット`68d3a4d4`をビルドした通常のminase（版2.4.0、SHA-256`462b83de…`）である。`invocations.json`の起動の記録は2件で、どちらも同じrunnerと調整機である。
規則は`engine-default`（`L0,P0,R1,E0`）である。
秒読みの締切の余裕`ByoyomiMargin`は、両エンジンとも既定の30 msである。秒読み期（持ち時間を使い切った後）の1手の締切は、秒読み300 msから余裕を引いた270 msになる。

## 環境

調整機は、vast.aiのインスタンス57236964（AMD Ryzen Threadripper PRO 9995WX、物理96コア、論理192スレッド、ギリシャ）である（[時間切れの事前確認](time-instability-scaling-safety.md)）。
両エンジンの`Threads`は1、`USI_Hash`は既定の256 MB、同時対局数は47である。
GSPRTの仮説は既定のelo0 = 0、elo1 = 10、α = β = 0.05である。

有効1,634ペアの度数から求めた候補の平均得点は0.494（Eloに直すと約−4）であり、正規化したペア得点の分散による95%信頼区間はおよそ−15〜+7である。
終局の内訳は、詰みによる勝ち3,038局、反復による引き分け221局、駒枯れによる勝ち26局と引き分け4局、王駒の捕獲による勝ち3局、時間切れ1局、および手数上限の打ち切り25局だった。
王駒の捕獲による勝ちのうち2局はペア1121の2局であり、ランダムに進めた開始局面で後手の王駒がすでに取られる形になっていた。どちらの局も先手が13手目で王駒を取り、候補と起点が先後を入れ替えて同じ結果になった。

### 時間切れ

時間切れは、ペア1481の第2局で、後手の候補が343手目に起こした。持ち時間を使い切った後の秒読み期の手である。
候補はこの手で深さ16の反復を探索開始から293 msで完了し、反復の境界で止まった。着手が審判層に届いたのは302.2 msであり、秒読み300 msを超えた。直前の数手は、両エンジンとも探索途中のhardによる中断で、思考時間は約272〜282 msだった。
エンジンが報告した反復の完了時刻と思考時間の乖離は9 msであり、反復の境界で止まった秒読み期の手の乖離（中央値7.0 ms、最大は候補11.9 ms、起点12.6 ms）の範囲にある。この手が遅れたのは、反復の完了が締切の270 msより23 ms遅れたためである。

秒読み期の手の思考時間の分布は、両エンジンでほぼ同じだった。

| 量 | 候補 | 起点 |
|---|---:|---:|
| 秒読み期の手数 | 656,367 | 686,329 |
| hardで中断した手の思考時間の中央値 | 282.1 ms | 282.1 ms |
| 同じく上位0.1%の値 | 283.7 ms | 283.8 ms |
| 同じく最大 | 293.6 ms | 292.7 ms |
| 思考時間が285 msを超えた手 | 425 | 446 |
| 反復の境界で止まった手の完了時刻の最大 | 293 ms | 285 ms |

ペア1366では、両エンジンの複数の手がそろって292 ms前後まで遅れており、調整機の側の一時的な遅れも起きていた。
時間切れの手は、両エンジンに共通する締切からの遅れの分布の裾（まれに起きる大きな遅れ）で起きた1件であり、候補の変更によるものとは判断しなかった。調整機はコンテナであり、カーネルのログは調べられなかった。
秒読みの余裕30 msは、この遅れの裾に対して小さい。lishogiのBotは余裕を3,000 msにして運用している。

時間切れのペアを除いた度数[310, 115, 814, 89, 305]のLLRは、`minase::stats::gsprt_llr`で−2.922であり、`H0`の境界−2.944に届かない。
つまり、`H0`の判定はこの1ペアに左右されている。
ただし、案1の規則では、短い条件が`H1`でなければ（上限での判定保留を含む）適用を限定する。時間切れのペアを除いてもLLRは`H1`の境界+2.944から大きく離れているので、この後の対応は変わらない。

## 結論

候補は、秒読みつきの短い条件で起点に対して`H1`とならなかった（`H0`、LLR −2.991、約−4 Elo）。
時間切れが1件出たが、両エンジンに共通する締切からの遅れの裾によるものであり、この1ペアを除いても`H1`には遠い。
設計書の案1により、長い条件は行わず、探索の不安定さによる持ち時間の伸縮のうち相手との残り時間の差による補正を除く項目の適用を、秒読みが0の時計に限るコミット`7dbcb085`を加えた。
このコミットは、4因子、根の候補が1手の局面の上限、increaseDepth、詰みでの早期停止、および先読みの後の25%増しを、秒読みが0で`movetime`のない時計に限る。最善手が続けて同じときの二値の短縮の反復数と、SPSAで調整し直した既存の係数は、これまでどおりすべての時計で使う。
限定するコミットを加えた版は、設計書の規則により測り直さない。

# 持ち時間の伸縮の形の変更の時間切れの事前確認

## 目的

[探索の不安定さに応じた持ち時間の伸縮の設計書](../../plans/archived/time-instability-scaling.md)のフェーズ2として、SPSAの本番の前に、時間管理の係数を思考時間が長くなる側の値に置いても、調整機の持ち時間で時間切れとエンジン異常が起きないことを確かめる。
棋力測定ではない。

## コマンドライン

パラメーターファイル`time-instability-scaling-safety.params`は、本番の103係数のファイルの写しである。設計書のフェーズ2のとおり、次の16係数の開始値を書き換えた。

| 係数 | 本番の開始値 | 事前確認の値 |
|---|---:|---:|
| `HardSoftRatio` | 571 | 800 |
| `HardRemainingShare` | 47 | 50 |
| `MinMoves` | 40 | 40 |
| `IterationRatio` | 203 | 150 |
| `StableIterations` | 4 | 8 |
| `TimeFallingBase` | 115 | 1500 |
| `TimeFallingPrevious` | 4784 | 8000 |
| `TimeFallingIteration` | 2288 | 5000 |
| `TimeReductionIntercept` | 254 | 0 |
| `TimeReductionSlope` | 78 | 0 |
| `TimeReductionScale` | 2284 | 1000 |
| `TimeInstabilityBase` | 1077 | 1500 |
| `TimeInstabilitySlope` | 2229 | 4000 |
| `TimeEffortIntercept` | 1642 | 2500 |
| `TimeEffortSlope` | −888 | 500 |
| `TimeAdvantage` | 900 | 0 |

`MinMoves`は、本番の開始値がすでに範囲の下端の40である。
この組は時間を長く使う傾向を狙った確認用の値であり、全局面で持ち時間の伸縮の積が最大になる組ではない。

反復数78は、[統括計画](../../plans/search-forms.md)が定める`⌈13 × 同時対局数 ÷ 16⌉`（同時対局数95）である。
持ち時間は、測定機のSTCの`time=10000+100`に換算係数1.00を掛けた値であり、STCと同じになった。
換算係数は、測定機の負荷時の速度448,693 NPSを、調整機で95本の`dev bench`を同時に走らせた負荷時の速度450,346 NPSで割った比（0.996）を、小数第2位に丸めた値である。
測定機の値は、調整用ビルドを16本同時に`minase dev bench --depth 9 --repetitions 3`で走らせた平均NPSを5回測った中央値であり、5回の値は448,661、448,693、465,953、443,459、および452,349 NPSだった。
測定の間、lishogiのBotは通信対局を指し続けていたので、各回の前にBotのエンジンが3秒間CPUを使っていないことを確かめ、各回の間にBotのエンジンが使ったCPU時間が0.5秒未満の回だけを採用する条件とした。5回とも0秒であり、除外した回はない。
コマンドは、調整機の`scripts/vast-spsa/remote.py`が起動した。

```console
minase spsa \
  --run-dir /workspace/job/time-instability-scaling-safety --seed 5000000000 \
  --engine commit:68d3a4d4 --params /workspace/job/safety.params \
  --rules engine-default --each time=10000+100 --concurrency 95 \
  --iterations 78 --pairs-per-iteration 8
```

## エンジン

調整対象は、形の変更の最後のコミット`68d3a4d491c94dee29f979b8de70025fca902565`の調整用ビルドであり、調整機でビルドした実行ファイルのSHA-256は`f4e99032…`である。
runnerは同じコミットの通常ビルド（版2.4.0、SHA-256`462b83de…`）である。
調整機では、測定機で作った`git bundle`からブランチを取り込み、`cargo build --release --locked --bin minase`でrunnerを、`minase spsa params --engine commit:68d3a4d4 --rules engine-default`で調整用ビルドを作った。
このコマンドが出力した既定のパラメーターファイルから`FmScale`の行を除いたものは、測定機で作った103係数のファイルと一致した。
規則は`engine-default`（`L0,P0,R1,E0`）、置換表は既定の256 MB、探索のワーカーは1である。

## 環境

調整機は、vast.aiのインスタンス57236964（出品57221898、機械のID 154306、ギリシャ、検証なし、1時間約2.00米ドル）である。
CPUはAMD Ryzen Threadripper PRO 9995WX（物理96コア、論理192スレッド）、`cpu_ram`は192,513 MBである。コンテナのCPU割り当ては184 CPUぶんで、runnerが記録した論理CPUも184だった。
同時対局数は、物理コア数から1を引いた95である。メモリから決まる同時対局数の上限（調整機の実メモリを1局あたりの最大常駐メモリの1.25倍で割った数）は154であり、この上限には掛からなかった。
1局あたりの最大常駐メモリは、測定機で調整用ビルド同士の1ペア（シード5080000000）をSTCの持ち時間で対局させ、2局それぞれについて2つのエンジンの最大常駐メモリを足した値のうち、大きい方の1,003,606,016バイトとした。

この調整機は、統括計画の候補とした型の出品が出なかったために、利用者の決定で借りたものである。
2026年10月22日16時40分（日本時間）から、`launch.py`で、EPYC 9K84、9654、9B14、9J14、または9655を載せ、論理384スレッド以上、`cpu_ram`が260,000 MB以上、1時間2.5米ドル以下の出品を待った。
同日18時10分に、利用者の判断で、vast.aiの検証を受けていない出品も候補に加えた。
その後、検証を受けていないEPYC 9B45の出品を2回借りたが、どちらもSPSAを始めずに削除した。

1回目は、18時19分に作成したインスタンス57188626（出品57070691、機械のID 154394、ネバダ、1時間約1.36米ドル）である。
出品の表示は論理384スレッドだったが、コンテナには46 CPUぶんの割り当てしかなかった。
`remote.py`はコンテナのCPU割り当てを読まず、`lscpu`が返す物理192コアから同時対局数を191として負荷時の速度を測った。
その結果は34,089 NPS、換算係数13.16、所要時間の見込み約83.1時間であり、見込みが24時間を超えたので`remote.py`は事前確認の前に止まり、取得側のスクリプトがインスタンスを削除した。

2回目は、出品57070744（機械のID 150493、ネバダ、1時間約1.46米ドル）で作成したインスタンス57214081である。
SSHで接続できる状態にならなかったので、`launch.py`が作成から約5分で削除した。
2回の費用は合わせて1米ドル未満だった。

2回目の後、EPYC 9B45を候補から外して22時11分から待機を続けたが、10月23日1時までに条件を満たす出品は出なかった。
この時点で借りられた出品のうち、物理96コアのThreadripper PRO 9995WXは、所要時間の見込みが物理192コアの調整機より長いが、1時間あたりの価格は、統括計画のサブタスク4〜6で借りたEPYC 9K84または9654の2基構成（1時間約1.87〜2.01米ドル）と同程度だった。
見込みの時間と費用を利用者に示し、利用者が借りることを決めたので、出品のIDを`launch.py`に渡して1時5分にインスタンスを作成した。
`remote.py`の見積りでは、SPSAの本番の所要時間は約12.7時間である。

## 結果

78反復をすべて適用し、624ペアのうち有効ペアは618、手数上限で破棄したペアは6だった。
異常件数は、不正着手、クラッシュ、応答タイムアウト、時間切れ（`time_forfeits`）、および拒否着手のいずれも0だった。
所要時間は1,232秒だった。

## 結論

時間管理の係数を思考時間が長くなる側の値に置いても、調整機の持ち時間で時間切れとエンジン異常は起きなかったので、本番のSPSAへ進む。

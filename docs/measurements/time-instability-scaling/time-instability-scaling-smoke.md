# 持ち時間の伸縮の形の変更の候補の事前対局

## 目的

[探索の不安定さに応じた持ち時間の伸縮の設計書](../../plans/archived/time-instability-scaling.md)のフェーズ4として、SPSAの最終値を反映した候補がSTCの条件で時間切れやエンジン異常を起こさないことを確かめ、時間の使い方の変化を見るために、候補と起点を32ペア（64局）対局させる。
棋力の判定には使わない。

## コマンドライン

[統括計画](../../plans/search-forms.md)の決定により、SPSAを終えた調整機で、持ち時間を換算せずに対局を実行した。
候補のコミットは、測定機で作った`git bundle`で調整機のcloneへ取り込んだ。

```console
target/release/minase match run \
  --run-dir /workspace/job/matches/time-instability-scaling-smoke --seed 5100000000 \
  --candidate commit:1930dcb29cec7d2fc3ebe5bdb65a8f47c9e24eb5 \
  --baseline commit:370f707780548b0fa65d3e1303881a9fd609c05b \
  --each time=10000+100 --concurrency 95 elo --pairs 32
```

実行ディレクトリは、終了後に測定機の`data/matches/time-instability-scaling-smoke`へ取得し、集計は測定機で次のコマンドで行った。
`clock_profile.py`の予算に対する比の欄は古い係数が固定値として残っているので参照せず、手数帯ごとの実測値の集計だけを用いた（[起点の時計の記録](time-instability-scaling-baseline.md)と同じ扱い）。

```console
data/spsa/time-instability-scaling-runner/minase match report \
  --run-dir data/matches/time-instability-scaling-smoke
scripts/clock_profile.py data/matches/time-instability-scaling-smoke \
  --budget quadruple-soft --role candidate
scripts/clock_profile.py data/matches/time-instability-scaling-smoke \
  --budget quadruple-soft --role baseline
```

## エンジン

候補は、形の変更に[SPSAの最終値](time-instability-scaling.md)を反映したコミット`1930dcb29cec7d2fc3ebe5bdb65a8f47c9e24eb5`である。
起点は、設計書を始めた時点のmaster`370f707780548b0fa65d3e1303881a9fd609c05b`である。
runnerは、調整機で形の変更の最後のコミット`68d3a4d4`をビルドした通常のminase（版2.4.0、SHA-256`462b83de…`）である。
規則は`engine-default`（`L0,P0,R1,E0`）である。

既定値を反映した候補の`cargo test`（通常ビルドと調整用ビルド）では、`correction_can_prevent_reverse_futility_and_razoring`の1件が両方のビルドで失敗した。
このテストは補正の表のうちmaterialの表だけを更新し、局面の補正値が0でないことを前提にしていた。`CorrectionMaterialWeight`の既定値がSPSAで5から1に下がったので、補正値が丸めで0になり、前提が崩れた。
調整係数の既定値に結びついたテストの問題であり、エンジンの挙動の問題ではないので、テストだけを直すコミット`903ab780`を別に加えた。このコミットでは、失敗したテストを補正の重みに依存しない形に書き直した。あわせて、補正の重みが範囲の下端の0に近いと前提が崩れるほかの11件を、重みを0でない値に固定した子プロセスの中で走らせるようにした。
このコミットはエンジンの実行ファイルを変えないので、事前対局とSTCの候補は`1930dcb2`のままとした。
事前対局は、測定機でのテストの修正と並行して行った。

## 環境

調整機は、vast.aiのインスタンス57236964（AMD Ryzen Threadripper PRO 9995WX、物理96コア、論理192スレッド、ギリシャ）である。測定機との1コアの速さの比`f`は1.00である（[時間切れの事前確認](time-instability-scaling-safety.md)）。
両エンジンの`Threads`は1、`USI_Hash`は既定の256 MB、同時対局数は95である。

## 結果

| 量 | 値 |
|---|---:|
| 有効ペア | 32（破棄0） |
| ペンタノミアル度数 | [3, 3, 15, 2, 9] |
| 正規化した平均得点 | 0.586 |
| Elo | +60.3 |
| 95%信頼区間 | [−14.9, +141.7] |
| エンジン異常 | 不正着手0、クラッシュ0、応答タイムアウト0、時間切れ0、拒否着手0 |
| 経過時間 | 177.5秒（`summary.json`の累計） |
| 1局の最大常駐メモリ | 1,009,225,728バイト |

32ペアの固定局数Eloは信頼区間の幅が約157 Eloあり、強さの判定には使わない。

時間の使い方は次のとおりである。
64局の手数は平均472手、中央値472手だった。

| 量 | 候補 | 起点 |
|---|---:|---:|
| 64局の総思考時間 | 1,945.1秒 | 2,015.5秒 |
| 着手数 | 14,786 | 14,780 |
| 1手の平均思考時間 | 131.6 ms | 136.4 ms |
| 終局時の残り時間の中央値 | 1,873 ms | 1,012 ms |
| 反復の境界での停止（soft） | 14,722 | 14,727 |
| 探索途中のhardによる中断 | 64 | 53 |

候補の総思考時間は起点の0.965倍であり、[教訓](../../lessons/compare-total-time-usage-before-sprt.md)が定める基準（起点の90%以上110%以下）に収まった。

手数帯ごとの平均完了深さと思考時間の中央値は次のとおりである。

| 手数帯 | 手数（候補） | 完了深さ（候補） | 完了深さ（起点） | 思考時間の中央値（候補、ms） | 思考時間の中央値（起点、ms） |
|---|---:|---:|---:|---:|---:|
| 0〜49 | 1,283 | 17.97 | 16.61 | 81 | 111 |
| 50〜99 | 1,576 | 17.35 | 16.24 | 81 | 111 |
| 100〜149 | 1,565 | 17.43 | 16.21 | 81 | 111 |
| 150〜199 | 1,536 | 17.05 | 15.65 | 91 | 111 |
| 200〜299 | 2,990 | 16.58 | 15.03 | 111 | 121 |
| 300〜399 | 2,707 | 16.83 | 15.56 | 111 | 131 |
| 400〜 | 3,129 | 16.40 | 15.55 | 81 | 101 |

候補の完了深さは、7つの帯のすべてで起点を0.85〜1.55上回った。
設計書の設計判断「事前対局での時間の使い方の確認」の条件（総思考時間が起点の90%以上110%以下、完了深さがどの帯でも起点を下回らない）を、両方とも満たした。
ただし、候補はSPSAで探索の係数も調整し直しているので、完了深さの差は時間の配分だけによるものではない。また、窓を浅く読んだ反復も反復の番号で数えるので、候補の完了深さは実際に読んだ深さより深く数えられている。
候補の思考時間の中央値はどの帯でも起点より短く、総思考時間も起点よりやや短い。終局時の残り時間の中央値は起点より約0.9秒多い。

## 結論

SPSAの最終値を反映した候補は、時間切れとエンジン異常を起こさず、時間の使い方の条件も満たしたので、STCへ進む。

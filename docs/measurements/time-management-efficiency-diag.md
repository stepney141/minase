# time-management-efficiency-diag

## 目的

現行の時間管理（hardが秒読み分まで4倍する式、[持ち時間の効率的な使用](../plans/time-management-efficiency.md)の「フェーズ1」）について、「診断の指標」の6項目を秒読みつきの時間制御で数え、第1段階以降の比較基準にする。
あわせて、削除済みブランチの診断（[初形の実測](time-management-efficiency-probe.md)の「参考」）と同じ基本シードで現行の値が再現することを確かめ、復元した集計スクリプトの正しさを確認する。

## コマンドライン

短い時間制御の10ペア自己対局は次のとおりである。

```console
target/release/match_runner --run-dir data/matches/time-management-efficiency-diag --seed 20260916 \
  --candidate commit:ee3fd60 --baseline commit:ee3fd60 \
  --each time=9000+0,byoyomi=300 --concurrency 4 elo --pairs 10
```

5分＋10秒の先手60手自己対局は、初形から`go btime … wtime … byoyomi 10000`を送るスクリプトで時計を再現した。

```console
python3 scripts/byoyomi_game_profile.py --engine target/release/minase --rules L0,P0,R1,E0 --hash 256 \
  --time 300000+0 --byoyomi 10000 --black-moves 60 --budget quadruple-soft \
  --record data/experiments/time-management-efficiency/diag-5m10s.record.json \
  --json data/experiments/time-management-efficiency/diag-5m10s.summary.json
```

集計は、10ペア対局が`scripts/clock_profile.py data/matches/time-management-efficiency-diag --budget quadruple-soft`、60手自己対局が上記スクリプトの出力であり、いずれも`scripts/clock_budget_stats.py`の共通関数で予算を再計算した。
`quadruple-soft`は現行の式`hard = max(1, min(4·soft_raw, remaining/4 + ⌊0.8·byoyomi⌋, safe_hard))`を指す。

## エンジン

候補と基準はともにコミットee3fd60（本設計書の着手前のコミット。時間管理は削除済みブランチの診断が使ったa180739と同じ式）、規則セットは`L0,P0,R1,E0`である。
60手自己対局のバイナリは同じコミットの作業ツリーから`cargo build --release`で作った`target/release/minase`であり、両側を別プロセスで起動した。

## 環境

CPUはIntel Core Ultra 7 265KF（物理20コア、論理20コア）、候補と基準の`Threads`は1、`USI_Hash`は256 MB、同時対局数は明示した4である。
同じ機で別の測定（合法手生成高速化第2期の段階7〜9のLTC、同時対局数16）が並行しており、負荷平均は16〜22であった。
到達深さはこの負荷の影響を受けるが、判定に使う指標は壁時計で判定される予算の帰結である。
hardの超過の最大値は負荷の影響を直接受けるので、本記録の値は上限の参考値として扱う。

## 結論

持ち時間局面では思考時間の中央値がsoftを下回る一方、90パーセンタイルはsoftの1.5〜2.0倍、最大は2.7倍に達し、hardによる打ち切りは0〜6%にとどまるので、softを超える長考はhardではなくsoft停止の反復完了で終わっている。
秒読み局面では利用率の中央値が0.49〜0.56であり、hard停止した手だけが秒読みの8割を使う。
持ち時間は10ペア対局で25〜39手目（中央値31手目）、5分＋10秒で36〜37手目に尽きた。
初手の実測思考時間はissueの条件で11,891 msであり、再構成の第1段階の許容値1,033 ms（hard 933 msに100 msを加えた値。[設計書](../plans/time-management-efficiency.md)の「棄却した再構成の各段階」）の比較基準になる。
集計は削除済みブランチの診断と同じ範囲に再現し、復元したスクリプトの正しさを確認した。
hardの超過の最大値は10ペア対局の秒読み局面で36.5 ms（負荷平均16〜22の下）であり、30 ms未満の判定を採否測定後の診断（フェーズ7）で満たすには、他の測定と重ならない負荷で実行する必要がある。

# 合法手生成の高速化計画への追加候補

2026年9月13日時点の[高速化計画書](plans/movegen-speedup.md)と作業ツリーを調べた結果、追加案の優先候補は、静止探索で不要になる捕獲を生成前に除くことと、必要になった捕獲だけを段階的に生成することである。
本書で追加案と比較している計画は、追加案を統合する前の2026年9月13日時点の内容を指す。
現行の着手順と採用条件は、リンク先の計画書を参照する。
15局面の診断では、生成した捕獲手の39.3%を入口の評価値だけで除外でき、48.5%は探索ループ内の検査まで到達していなかった。
この2群には重複があるため、削減率は加算できない。
以下の提案は処理件数とソースに基づく仮説であり、速度向上の実測値ではない。

## 2倍に必要な削減量

100%以上の高速化を、同じ探索を半分以下の時間で終えることと解釈する。
[既存測定](measurements/bench-movegen-profile-depth5.md)では、基準コミット`0e3dfa6`の0.845秒に対して試作が0.639秒なので、基準比2倍の目標は0.422秒である。
試作からさらに0.216秒、すなわち33.8%の時間削減が必要であり、速度では約51.2%の上積みに相当する。
既存試作の約1.32倍に追加案を重ねて基準比2倍を狙う余地はあるが、追加案だけで試作をさらに2倍にできる根拠はまだない。

既存プロファイルの割合は、置換表のクリアなど探索の計測区間外も含む。
その割合を探索時間に直接掛けて、各案の速度倍率を算出してはならない。
探索区間内で対象処理が占める割合を `f`、その処理の速度倍率を `s` と測り直した場合、全体倍率は `1 / (1 - f + f / s)` で見積もれる。
例えば残りの探索時間の65%を占める処理群を2倍にできれば、試作全体は約1.48倍、基準比では約2.03倍となるが、65%と2倍は達成条件の例であり測定値ではない。

## 処理件数の診断

作業ツリーのソースを一時ディレクトリへ複製し、既存の探索を最後まで実行したまま件数を数えた。
`bench --depth 5 --threads 1 --repetitions 1` の15局面を使い、総ノード数は1,438,048であった。
診断の入力は当時のmaster（`d0d3c52`）であり、評価の重みが異なる現在の基準コミット`0e3dfa6`とは総ノード数が一致しない。件数の割合は処理の構造に依存するため、そのまま案の選別根拠に使う。
計数を加えない比較版と、各局面のノード数、最善手、探索値が15局面すべてで一致した。
同時に16並列の自己対局生成が動いていたため、今回の実行時間を速度の根拠には使っていない。

生成後のループでは、評価値による棄却、静的交換評価、子局面の探索の順に処理する。
したがって「ループ内で検査した手」も、すべて子局面を探索したわけではない。
上表の割合は削減候補の件数であり、各手の費用が等しいとも、同じ割合の時間を削れるとも仮定していない。
生データと再現用差分は[診断資料](measurements/movegen-speedup-ideas-counts/totals.json)に付属する。

## 評価値で捕獲対象を生成前に絞る

現在の[静止探索](../src/search/mod.rs#L1412)は、すべての捕獲を生成して合法性を調べ、成りを展開し、整列した後で、獲得価値が足りない手を捨てる。
入口のα、局面の静的評価値 `stand_pat`、既存の余裕値 `delta_margin` から、捕獲価値の閾値 `α - stand_pat - delta_margin` を先に求められる。
αはそのノード内で低下しないため、入口で棄却条件を満たす手は後でも棄却される。

探索専用の生成入口へ捕獲対象升の集合を渡し、閾値以下の駒を取る通常手を生成対象から外す。
これは調査時点の計画にある「幾何的に捕獲先がない自駒の早期棄却」と異なり、既存の探索判定を生成前へ移す変更である。
今回の39.3%は、この方法の最初の適用範囲となる。
2枚取りを含めて捕獲価値の合計を扱えれば対象を広げられるが、45.5%全部を通常捕獲の升マスクだけで除けるわけではない。

正しさには、経由升の捕獲、2枚取り、最後の王駒を取る手の例外を保つ必要がある。
公開の捕獲生成関数は全捕獲手を返す契約を保ち、探索専用の部分生成と区別する。
置換表の手を先頭と交換する現在の `swap(0, index)` は、直後に捨てる手にも作用するため、単に候補を削除してから交換してはならない。
元の全体順で交換した場合と同じ残存手順を再現して初めて、探索結果の不変性を主張できる。

## 静止探索の捕獲を段階的に生成する

現在の静止探索は、最初の捕獲で探索が打ち切られる場合にも全捕獲の生成と整列を済ませている。
捕獲価値の高いグループから必要分だけ生成すれば、打ち切り後のグループを生成する費用を省ける。
今回の48.5%はこの候補を支持するが、価値が同じグループの途中で打ち切られる場合もあるため、48.5%すべての生成を省けるとは限らない。
次の診断では価値グループごとの打ち切り位置を数える。

[HaChuの一次実装](https://github.com/ddugovic/hachu/blob/649ef114dd5fa39d3e1be4112e63ebe2ab3d5d8b/hachu.c#L223)は、捕獲対象升から取り手を求め、探索側で価値の等しい捕獲対象のグループを順に扱う。
minaseでも前項の閾値で相手駒を絞り、その対象から取り手を求める方式が候補になる。
ただし相手駒すべてに高価な逆引きを行うだけでは速くなる保証がないため、対象を絞る効果と逆引きの費用を測る。

調査時点の計画の段階生成は主探索が対象なので、静止探索の段階生成は追加案である。
同じ捕獲価値では取り手の価値と元の生成順を保ち、置換表の手との交換も再現する。
獅子の2枚取りは2枚分の価値で分類し、居喰いを含む特殊手の正準表現を保つ。
この順序を維持できれば探索アルゴリズムの変更は要らないが、維持しない試作は調査時点の計画の結果不変条件を満たさない。

## 静的交換評価を判定に必要な範囲で打ち切る

現在の呼び出し側が静的交換評価（SEE）から使う情報は、[値が負で、かつ判定不能でないこと](../src/search/mod.rs#L1938)だけである。
一方、[SEE本体](../src/search/see.rs#L25)は交換列を最後まで作ってから値を逆算している。
[Stockfishの `see_ge`](https://github.com/official-stockfish/Stockfish/blob/master/src/position.cpp#L1268)にも、値全体を返す代わりに閾値との比較で早期終了する実装がある。
minaseでは成りと獅子規則の扱いを含めて独自に同値条件を導く必要がある。

初手で取る駒の価値をC、動く駒の成り前後の価値をMとP、相手の最初の取り返しで得る成り益をdとする。
現行の利得列の最初の2項は `g0 = C + P - M` と `g1 = P - g0 + d = M - C + d` である。
逆算結果は、後続値をXとして `min(g0, max(-g1, X))` となるので、`g0 >= 0 && g1 <= 0` なら後続にかかわらず非負である。
相手が取り返せない場合は、現行どおりg0で終わる。

この条件が成立すれば、その場で「枝刈りしない」と判定できる。
後続の獅子規則により元のSEEが `None` を返す場合でも、元から枝刈りしないため判断は一致する。
反対に「負だから枝刈りする」という早期終了には、後続で `None` にならないことの証明が別途必要である。

診断ではこの条件が114,479回成立し、その後の利き逆引き214,958回を省略可能と数えた。
数値を返した事例では非負であることも実行時に確認した。
これはSEE内の逆引き回数の12.3%であり、探索全体の時間を12.3%短縮するという意味ではない。

この案は調査時点の計画にある差分更新と異なり、交換の反復そのものを省く。
ただし、早期終了した判定から元の正確なSEE値や `None` は復元できないので、調査時点の計画の「SEEの値と `None` の一致」をそのまま適用できない。
実装へ進むなら判定関数の契約を `new_prune == old_see.is_some_and(|v| v < 0)` として明記し、元の値計算を検証用の参照に用いる。
枝刈りの真偽値、生成順、局面別の探索結果を一致させることが採用前の条件となる。

## 同じ捕獲先に関する準備を共有する

調査時点の計画は特殊利きを「SEEの1回につき1回」計算する。
これを同じ探索ノードの同じ到達升につき1回に広げれば、固定利き、特殊利き、走りの遮蔽駒の並びを複数の捕獲評価で共有できる。
今回、経由升を持たないSEEの19.7%は、そのノードで既に調べた到達升への再照会だった。
ただし移動元を取り除くと開く利き線が変わるので、到達升だけをキーにSEE値そのものを共有してはならない。

同じ移動元と到達升について成りと不成りを両方評価する場合には、交換列自体を共有できる範囲もある。
前節のg1では初手の成り後価値Pが消えるため、麒麟が獅子に成る場合を除けば、以後の占有状態、取り返し駒、成り判定が一致する。
診断の9.9%は同じ移動元と到達升への再照会率であり、除外すべき麒麟も含む上限候補である。
共有のために初期化する費用を含め、ノード内で必要な対象だけ準備する方式を比較する。

## 固定利きを移動量ごとにまとめる

[現在の生成器](../src/core/movegen/mod.rs#L297)は、駒種、移動元の順に各駒の固定利きを引く。
同じ移動量dを持つ駒の集合をSdとし、`shift(Sd, d) & 捕獲対象` をまとめて計算すれば、捕獲元を逆シフトで復元できる。
歩兵のように同じ移動をする駒が複数ある場合、駒ごとの表参照を集合演算へ置き換えられる。

これは調査時点の計画の固定利き逆引きの近傍走査とも、色を反映したプロファイルの巻き上げとも異なる。
Sdを毎ノード構築する費用、または駒の移動と成りで維持する費用が増えるため、現時点では副候補とする。
まず一括処理できる駒数と固定利き計算の費用を数え、効果が見込める場合だけ、元の生成順へ戻す費用と着手適用費用を含めて比較する。

## 走りを1本の線へ圧縮する

調査時点の計画は192ビットの利き線を方向ごとに処理し、借りの伝播や回転で分岐を減らす。
追加の代替案は、段、筋、斜線の占有を最大12ビットへ圧縮し、両方向の最初の遮蔽位置または利きを小表で求める方法である。
長さ12の線で、12起点、4,096占有、2バイトの相対結果を持つ素朴な表は96 KiBになる。
これは共通の相対表の容量であり、盤全体への展開や添字情報は別に要る。

[Stockfishの現行ソース](https://github.com/official-stockfish/Stockfish/blob/master/src/attacks.h#L81)には、複数方向の走りをまとめて計算し、横方向を圧縮占有の小表で引く実装がある。
minaseでは現在の16ビット幅の段表現から横方向を安く取り出せるため、横方向だけを安全な整数演算と表参照で比較するところから始められる。
縦と斜めでは圧縮と展開の費用が加わるため、192ビット全体の方式より速いとはまだ言えない。

さらに小さい変更として、通常捕獲用には利き線全体を構成せず、最初の遮蔽駒の升だけを返す照会も比較できる。
通常捕獲と走りの逆引きは、その駒が相手または該当する走り駒かを調べれば足りる。
いずれも調査時点の計画にある走りの分岐除去の代替となる部分があるため、同じ費用の削減を重ねて数えない。

## 実行プロファイルをビルドへ反映する

プロファイル誘導最適化（PGO）は代表入力の実行頻度をコンパイラへ戻し、インライン化や機械語の配置へ使う。
Rustには[公式の生成、集約、再ビルド手順](https://doc.rust-lang.org/rustc/profile-guided-optimization.html)がある。
このプロジェクトは既にCPUに合わせた最適化とリンク時最適化を有効にしているため、追加候補はPGOである。

生成器の変更と独立に比較できるが、minaseでの改善率は未測定である。
学習用と測定用の局面を分け、同じコミットと同じCPU向け設定で比較し、対局用バイナリにも同じ最適化を適用する。
PGOを指定する `RUSTFLAGS` に `-C target-cpu=native` も明示して、現在のビルド設定が比較の途中で変わらないようにする。

## 比較の順序と再現方法

最初に生成前の閾値除外を試し、次に静止探索の段階生成を比較する。
この2案は捕獲生成の入口で仕事を減らせるため、調査時点で計画済みの利き計算改善と合わせて2倍を狙う中心候補になる。
SEEの早期終了とPGOをそれぞれ比較し、共有、固定利きの一括処理、線占有の圧縮は残った負荷を見て選ぶ。
各案の削減対象は重なるため、直前の採用版に対する増分を測る。

今回の診断の入力は、当時のmaster（`d0d3c52`）に作業ツリーの差分を適用したものとして保存した。
[環境情報](measurements/movegen-speedup-ideas-counts/environment.json)、[入力差分](measurements/movegen-speedup-ideas-counts/input.patch)、[診断差分](measurements/movegen-speedup-ideas-counts/diagnostic.patch)、[元ファイルのSHA-256](measurements/movegen-speedup-ideas-counts/source-sha256.json)、[局面別件数](measurements/movegen-speedup-ideas-counts/counts.log)、[比較結果](measurements/movegen-speedup-ideas-counts/comparison.json)を保存している。
再現するときは新規の一時ディレクトリへ当時のmasterを展開し、入力差分と診断差分を順に適用する。

```console
git archive d0d3c52024c5ab4d74cc82588640a55953426aad | tar -x -C <新規の一時ディレクトリ>
cd <新規の一時ディレクトリ>
git apply <診断資料の絶対パス>/input.patch
git apply <診断資料の絶対パス>/diagnostic.patch
cargo build --release --bin bench -j 2
target/release/bench --depth 5 --threads 1 --repetitions 1
```

このバイナリは処理件数を数えるためのもので、速度測定には使用しない。
速度比較では診断コードを外し、他のCPU負荷がない状態で通常ビルドの `bench --depth 5 --repetitions 3 --threads 1` を実行する。
生成順、合法性、成り、特殊手、判定不能の扱いを各案の契約に従って検証し、局面別のノード数、最善手、探索値を照合する。
棋力に影響し得る候補の採否は、[プロジェクトの測定方針](sprt.md)に従うコミット間の自己対局の逐次確率比検定で決める。

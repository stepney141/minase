# 設計書の書き方

本書は、docs/plans/ に置くマイルストーン設計書の型と、設計書から切り出す測定記録および教訓の置き場を定める。
進捗の正は docs/ROADMAP.md のマイルストーン状態表であり、設計書はそのマイルストーンの設計判断を定め、完了後はそのサブシステムの現行設計の正として保守する。
過去の経緯は git 履歴に任せ、設計書には現在の設計と現在の状態だけを書く。

## 設計書の役割

設計書は、着手前に設計判断と完了条件を確定させ、完了後は後続のマイルストーンが前提として参照する文書である。
たとえば評価関数の世代反復は、評価関数の設計書にある教師値と採否測定の判断を前提に起案された。
したがって、完了後も設計判断、契約、検証の各節は現行の実装と一致するよう保守する。
一方、いつ何を実装したか、どのレビューで何を直したかという経緯は、設計書の読者が必要とする情報ではないので書かない。

## 節の順序

設計書の節は次の順序で並べる。
該当する内容がない節は省いてよいが、順序は変えない。

1. 先に読む要約
2. 状態
3. 目的
4. 適用範囲
5. 依存関係
6. 設計判断
7. 各論（設計書ごとに必要な節を自由に置く）
8. 実装フェーズ
9. 検証
10. 完了条件
11. 参考資料

「先に読む要約」は、目的、方式、完了条件を初心者向けに5〜10文で述べる。
読者は最初の要約だけで大枠を理解しようとするので、専門用語はここで定義するか、定義済みの文書へリンクする。

「状態」は1段落だけを書く。
内容は、状態表と同じ状態語（起案、進行中、待機中、完了のいずれか）、起案日と着手日、完了済みのフェーズ、いま詰まっている点、および次の一手である。
待機中なら待機の理由と再開条件を書く。
完了時には、完了日、採否の結論1文、および根拠となる測定記録へのリンクに書き換える。

「設計判断」は、採った方式と棄却した代案を理由つきで並べる。
「実装フェーズ」は着手順と各フェーズの完了条件を書き、「検証」は完了前に実行する確認手順を、「完了条件」は状態を完了へ変える判定基準を書く。

## 上書きの規則

「先に読む要約」と「状態」の2節は追記せず、常に現在形で書き直す。
設計書が肥大化する機構は追記そのものであり、上限を設けても上限まで埋まってから捨てる作業が発生するため、上書きだけを認める。
状態を書き直して「いま詰まっている点」を消すときは、その詰まりから汎用的な教訓が得られたかを後述の試金石で判定し、該当すれば docs/lessons/ へ出し、該当しなければ捨てる。
docs/ROADMAP.md の「現在地」節にも同じ規則を適用し、直近に完了したマイルストーンの結論、進行中と待機中の各マイルストーンの状態、および次期候補だけを保持する。

## 設計書に書かないこと

実施記録、レビューの記録、フェーズごとの着手ログ、コミットハッシュ、およびテスト件数は設計書に書かない。
どのコミットで何が入ったかは git log が、テストの通過は CI と `cargo test` が持っているからである。
レビューで設計判断が変わった場合は、変わった結果だけを「設計判断」節へ反映し、指摘と修正の経緯は書かない。
測定の結果は測定記録へ、詰まりから得た教訓は教訓ファイルへ置き、設計書からはリンクで参照する。

## 測定記録

棋力測定は、測定が終わった時点で直ちに `docs/measurements/<測定名>.md` へ1測定1ファイルで記録する。
測定名は `match_runner` の `--run-dir` に指定した名前と一致させ、設計書、記録ファイル、および実行ディレクトリの3者を同じ名前で突き合わせられるようにする。
索引ファイルは作らず、ディレクトリの一覧を索引とする。

記録は次の見出しを順に持ち、docs/sprt.md の記録項目をすべて含める。

1. 目的（何と何を比べ、何を判定するかを1文で）
2. コマンドライン（シードを含む全体）
3. エンジン（候補と基準のコミットハッシュ、外部エンジンなら版とビルド手順、規則セット）
4. 環境（CPU型、物理コア数と論理コア数、候補と基準のワーカー数、`USI_Hash`、同時対局数）
5. 結果（ペンタノミアル度数、LLRと判定またはEloと95%信頼区間、破棄ペア数、異常件数、`time_forfeits`、経過時間）
6. 結論（採否または解釈を1文で）

実行ディレクトリが残っていない過去の測定を起こす場合、判明しない項目は「記録なし」と明記し、推定で埋めない。

## 教訓

作業で詰まった箇所から得た汎用的な教訓は、`docs/lessons/<slug>.md` へ1教訓1ファイルで置く。
ファイルは「症状」「原因」「以後の規則」「出典」の4見出しを順に持ち、10〜30行に収める。
「出典」には、起点となった設計書、コミット、または測定記録へのリンクを書く。
`docs/lessons/README.md` は索引であり、1教訓につき `- [題名](ファイル名) — 以後の規則の要約` の1行だけを置く。
作業を始めるエージェントは、まずこの索引に目を通す。

教訓として切り出すのは、起点のマイルストーン以外の将来の作業にも適用できる規則を持つものに限る。
試金石は、「以後の規則」の見出しに将来の具体的な行動を1文で書けるかどうかである。
たとえば「隣接シードは対局数以上離す」は教訓だが、「置換表を16バイト2語に配置した理由」は Lazy SMP の設計判断であり、設計書に残す。
規則解釈の確定は RULES.md へ、コードの落とし穴はテストか rustdoc へ置き、教訓ファイルにはしない。
書く時点は詰まりが解消した瞬間とし、マイルストーン完了時にまとめて書かない。

## レビュー

設計書を作成または大きく改訂したら、Haiku のサブエージェントにレビューさせる。
まず「先に読む要約」だけを読ませて大枠を説明させ、正しく説明できなければ要約を書き直す。
次に全文を読ませ、理解できなかった箇所を論理のギャップとして書き直す。
Haiku が理解できない箇所は、書き手にしか分からない前提が省かれている箇所である。
Haiku を起動できない環境では、レビューを省略せず、書き手とは別の独立したサブエージェントに同じ2段階の確認をさせる。
計画書に対する codex のレビューは、AGENTS.md の共通ポリシーに従って別に求める。

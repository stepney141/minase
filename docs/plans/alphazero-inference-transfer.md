# AlphaZero型探索の推論のホストとGPUの間の転送の削減の設計書

## 先に読む要約

本書は、[AlphaZero型探索と深層強化学習の統括計画](alphazero.md)のもとで、ネットの推論がホスト（CPU側のメモリ）とGPUの間でやり取りするデータを減らし、自己対局の生成を速くするマイルストーンの設計書である。
今の推論は、1局面あたり、入力の91,584バイトをホストからGPUへ送り、方策の出力の143,424バイトをGPUからホストへ戻す。
どちらも、ONNX Runtimeの`session.run`が扱うページング可能なメモリ（OSが退避できる普通のメモリ）を通る。
vast.aiで借りた4枚のRTX 4090の仮想マシンでは、このGPU→ホストの転送が4枚の合計で毎秒約7 GBで頭打ちになり、生成が別の機械の約3分の1の速さになったと考えられる（[複数GPU化のvast.aiの測定](../measurements/alphazero-multi-gpu/alphazero-multi-gpu-vast.md)の「機械Hの生成が遅い理由」）。
本書は4つの候補を1つずつ入れて、生成の速さを親のコミットと交互に測り、速くなった候補だけを採る。
候補は、出力をピン留めメモリ（pinned memory、OSが退避しないメモリ）で受け取ること（IoBinding）、入力をuint8で送ること、方策をFP16で返すこと、および方策を盤面によらず取り得る16,108ラベルへ固定の表で詰めること（Lc0のpolicy mapと同じ考え方）である。
後の3つは、ネットの入出力の形（ONNXの署名）を変える。
完了条件は、採った候補を入れた生成器が照合の許容誤差を守り、[2回目の実行](alphazero-rl-2.md)のサイクル1より前にmasterへ入ることである。

## 目的

本書の目的は、自己対局の生成で、推論の入出力の転送に費やす時間を減らすことである。

2回目の実行は、1サイクルの料金が最も安い機械で回す（[2回目の実行の設計書](alphazero-rl-2.md)の「費用」の節）。
4枚の4090の機械Bは1サイクルを約36分で回したが、出品の料金がほぼ同じ機械Hでは生成だけで約51分かかり、1サイクルの料金は約2倍になった（複数GPU化のvast.aiの測定）。
機械Hの探索のスレッドは、CPUを時間の49〜62%しか使わず、残りは推論の呼び出しの中で待っていた。GPUの使用率も40〜55%であった。
そこで、推論の転送を減らせば、遅い機械の生成の速さを機械Bに近づけ、借りる機械の選び方の幅も広げられると考える。
ColabのG4と速い機械でも転送が生成を律速しているかは、まだ測っていない。

## 適用範囲

対象は、推論器`OnnxEvaluator`（`crates/minase/src/nn/onnx.rs`）、その入力を作る符号化、学習器のONNXの書き出し（`tools/train/zero/minase_zero/net.py`の`export_onnx`）、および書き出したネットの照合である。
推論器は、自己対局の生成器、対局用のMCTS、および照合の`minase dev nn-eval`が共有しているので、変更はこの3つすべてに効く。

対象外は次のとおりである。

- 合法手だけをGPU上で取り出す案。先行実装に例がなく、合法手の数の上限も分かっていないので、2026年11月11日の利用者の決定で候補から外した。
- 独自のCUDAカーネル、CUDAのストリームの指定、および外部のメモリを包むテンソル。どれも`unsafe`を要し、ワークスペースは`unsafe_code = "forbid"`だからである。ビットで詰めた入力をGPUで展開する方式（dlshogiとLc0）も、独自のカーネルを要するので外す。
- CUDAグラフ。転送の量を減らさず、IoBindingでアドレスを固定する必要があるので、本書の後に別に考える。
- 学習の計算。学習器は書き出しの包みだけを変え、学習の順伝播と損失は変えない。

本書は、[複数GPU化](archived/alphazero-multi-gpu.md)とONNX Runtime 1.31.1への更新（[ADR](../adr/load-onnx-runtime-1-31-1-through-ort-rc13-for-zero-inference.md)）の後の状態から始める。

1回目の実行のネット（サイクル0〜32）は、対局に使うときに書き出し直す。

## 設計判断

### 費用の式

1回の推論（バッチb）の時間を、次の和で考える。

```math
t_{\mathrm{call}}(b) = t_{\mathrm{enc}}(b) + \frac{b\,s_{\mathrm{in}}}{B_{\mathrm{in}}} + t_{\mathrm{gpu}}(b) + \frac{b\,s_{\mathrm{out}}}{B_{\mathrm{out}}} + t_{\mathrm{collect}}(b)
```

$`s_{\mathrm{in}}`$と$`s_{\mathrm{out}}`$は1局面あたりの入力と出力のバイト数、$`B_{\mathrm{in}}`$と$`B_{\mathrm{out}}`$は、ほかのスレッドとGPUが同時に転送しているときの実効の帯域である。
$`t_{\mathrm{enc}}`$は入力の符号化、$`t_{\mathrm{collect}}`$は合法手のlogitの取り出しにかかるCPUの時間である。
候補は、$`s_{\mathrm{in}}`$、$`s_{\mathrm{out}}`$、または$`B_{\mathrm{out}}`$を変える。

機械Hで4枚が同時に転送したときの実効の帯域（GPU 1枚あたり）を使うと、バッチ128の転送時間は次のように見込まれる（推論）。

| 構成 | 入力の転送 | 出力の転送 |
|---|---|---|
| 今（float32の入力、float32の35,856要素、ページング可能） | 11.7 MB、2.5〜4.3ミリ秒 | 18.4 MB、8.8〜11.5ミリ秒 |
| A. 出力をピン留めメモリで受け取る | 変わらない | 18.4 MB、1.5〜2.6ミリ秒 |
| B. 入力をuint8で送る | 2.9 MB、0.6〜1.1ミリ秒 | 変わらない |
| C. 方策をFP16で返す | 変わらない | 9.2 MB、4.4〜5.8ミリ秒 |
| D. 方策を16,108ラベルへ詰める | 変わらない | 8.2 MB、3.9〜5.2ミリ秒 |
| CとDを合わせる | 変わらない | 4.1 MB、2.0〜2.6ミリ秒 |

帯域は、ページング可能なメモリでホスト→GPUが毎秒2.7〜4.7 GB、GPU→ホストが毎秒1.6〜2.1 GB、ピン留めメモリのGPU→ホストが毎秒7.2〜12.5 GBである（複数GPU化のvast.aiの測定）。
$`t_{\mathrm{gpu}}`$は測っていないが、GPUの使用率が40〜55%なので、転送と同じ桁であると考えられる。
この表は転送の時間の見込みであり、生成の速さの見込みではない。生成の速さは、候補ごとに親のコミットと比べて測る。

### 候補

| 候補 | 一般名 | 先例 | 変えるもの |
|---|---|---|---|
| A. 出力をピン留めメモリで受け取る | pinned host buffer、IoBinding | dlshogi（ふかうら王）、Lc0、KataGoのCUDAの実装はすべて、入出力をピン留めメモリに置く | 推論器だけ |
| B. 入力をuint8で送り、グラフの中でfloat32へ変換する | uint8 input | なし。TensorRTはuint8の入出力と`Cast`に対応する | 署名、符号化、書き出し |
| C. 方策をFP16で返す | FP16 output | Lc0のFP16のネット | 署名、書き出し |
| D. 方策を盤面によらず取り得るラベルへ固定の表で詰める | policy map | Lc0は生の出力を1,858要素へ固定の表で詰める | 署名、書き出し、ラベルの添字 |

Aは、ONNX Runtimeの`IoBinding`で、方策と価値の出力をピン留めメモリの領域へ結び付ける。
ortの`bind_output_to_device`にCUDAのピン留めメモリの`MemoryInfo`を与える方式を先に試す。この方式では、TensorRTはGPUの上に出力を書き、ONNX Runtimeがピン留めメモリへ非同期に転送する。
ONNX Runtime 1.28.3では、出力をピン留めメモリへ結び付けると、同じ領域への転送として拒まれた（[実現性の実測](../measurements/alphazero-environment/alphazero-feasibility.md)）。
1.31.1では試していないので、フェーズ1で最初に確かめ、動かなければAは採らない。
入力は、今と同じくページング可能なメモリから送る。入力をピン留めメモリに置くと、1.31.1ではTensorRTがホストのメモリを直接読む形になり（`utils.cc`の`CanSourceSatisfyTarget`）、Lc0はその形が遅いと記しているからである。

Bは、入力の159面がすべて0か1であること（`crates/minase/src/nn/encoding.rs`）を使い、入力をuint8の`[バッチ, 159, 12, 12]`で受け取る。
書き出しの包みは、受け取った入力を`Cast`でfloat32へ変換してから、今のネットへ渡す。
0と1の変換は誤差を生まないので、ネットが見る値は変わらない。

Cは、書き出しの包みの最後で、方策のlogitを`Cast`でFP16へ変換する。
価値は1局面あたり4バイトしかないので、float32のまま返す。
FP16の丸めでlogitには相対で約5×10⁻⁴の誤差が加わるので、照合の許容誤差に収まるかをフェーズ3で確かめる。

Dは、書き出しの包みの最後で、方策を固定の添字の表で`Gather`し、35,856要素から16,108要素へ詰める。
表は、盤面によらず可能なラベルの定数マスク（`tools/train/zero/minase_zero/encoding.py`の`policy_mask`、[ADR](../adr/mask-impossible-policy-labels-and-diagnose-the-zero-trainer-on-final-weights.md)）の真の位置を昇順に並べたものとする。
書き出しは、この表を、ONNXのメタデータに昇順の整数の並びとして書き込む。
推論器は、セッションを作るときにメタデータの表を読み、昇順であること、要素の数が出力の幅と等しいこと、および値が35,856未満であることを確かめてから、ラベルから詰めた添字への逆引きの表を作る。
合法手のラベルが表にない場合は、明示的なエラーにする。
表をネットのファイルに持たせるので、RustにPythonと同じマスクの規則を書き写さずに済み、書き出しと推論で表が食い違うこともない。

候補の順序は、署名を変えないAを先にし、続けてB、C、Dの順とする。
各候補は1つのコミットにまとめ、親のコミットとの比較で採否を決める。
採らなかった候補のコミットは取り除き、後の候補をその親の上に載せ直す。

### 検討した代案

ビットで詰めた入力（1局面2,862バイト）をGPUで展開する案は採らなかった。
dlshogiとLc0の先例はあるが、展開に独自のCUDAカーネルが要り、minaseでは`unsafe`を使えないからである。
uint8の入力は、詰め方では劣るが、TensorRTの`Cast`だけで済む。

合法手だけをGPUで取り出す案は採らなかった（「適用範囲」の節）。

出力の領域をあらかじめ確保してピン留めメモリに置き、`bind_output`で結び付ける案は、Aの第1の方式が動かない場合にも採らない。
1.31.1ではTensorRTがホストのメモリへ直接書く形になり、Lc0のソースは、GPUのメモリに書いてから転送するほうが速いと記しているからである。
また、ONNX Runtimeが後で同じ領域への転送を試みてエラーになるかどうかが、ソースからは決まらないからである。

## 測定

### 測り方

各候補は、親のコミットと交互に同じ生成を行って測る（[教訓](../lessons/alternate-speed-rounds-against-parent.md)）。
生成は、複数GPU化の測定の`gen`段と同じ条件とする。具体的には、組み替えた初期配置から4,096局を、探索32回、GPUあたり4スレッド、スレッドごとに同時128局で生成し、毎秒の訓練局面を比べる。
ネットは2回目の実行の初期ネット（20ブロック256チャネル）とし、署名を変えるコミットでは、そのコミットの学習器でチェックポイントから書き出し直したネットを使う。
基準のコミットと4つの候補のコミットを1回の借用でビルドし、5つのコミットを1周ずつ順に回すことを5周繰り返す。
候補を採るのは、親に対する速さの比が、親どうしの周回の幅を超えて1を上回る場合である。

測る機械は次の3種類とする。

| 機械 | 目的 |
|---|---|
| vast.aiの4枚の4090で、出品の`pcie_bw`が12 GB/s以下のもの | 転送で律速される機械での効果 |
| vast.aiの4枚の4090で、`pcie_bw`が20 GB/s以上のもの | 速い機械で遅くならないこと |
| ColabのG4 | 2回目の実行の候補の機械での効果 |

G4が借りられない日は、vast.aiの2種類だけで判定し、G4は採った候補を入れたコミットでだけ測る。
作業機（RTX 3060 Ti）は、試験と出力の一致の確認に使う。

### 出力の確認

各候補で、照合の`minase dev nn-eval`のCPUとTensorRTのバッチ1、7、256の出力を、学習器の参照の出力と比べ、実行器の照合と同じ許容誤差に収まることを確かめる。
Aは推論の計算を変えないので、作業機で1スレッド、GPU 1枚の生成が、親のコミットとバイト単位で同じ塊を書くことも確かめる。
署名を変える候補は、TensorRTのエンジンが変わるので、生成の塊の一致は求めない。

## 実装フェーズ

本書のブランチをmasterから切り、worktreeで実装する。
実装はcodexに委任し、GPUを使う確認はClaudeが作業機と借りた機械で行う（[教訓](../lessons/run-gpu-training-outside-codex-sandbox.md)）。

### フェーズ1　A（出力のピン留めメモリ）

- 作業機で、ONNX Runtime 1.31.1とTensorRTの実行プロバイダが、ピン留めメモリへの`bind_output_to_device`を受け付けるかを、最小の試験で確かめる。受け付けなければAを採らず、フェーズ2へ進む。
- 推論器を`IoBinding`で書き直し、出力の領域を呼び出しの間で使い回せるかを確かめる。
- 作業機で、1スレッド、GPU 1枚の生成の塊が、親のコミットとバイト単位で一致することを確かめる。

### フェーズ2　B（uint8の入力）

- 符号化をuint8で書く形に改め、今のfloat32の符号化と同じ0と1を書くことを試験で確かめる。
- 書き出しの包みに`Cast`を入れ、推論器の署名の検査をuint8の入力に改め、TensorRTの最適化プロファイルの指定を合わせる。
- 学習器に、チェックポイントからONNXだけを書き出し直すサブコマンドを加える。

### フェーズ3　CとD（方策の型と詰め方）

- 書き出しの包みにFP16への`Cast`を入れ、推論器がFP16の方策を読む形に改める。
- 書き出しの包みに固定の表の`Gather`を入れ、表をONNXのメタデータに書き、推論器がそれを読んで逆引きの表を作る形に改める。
- CとDは別々のコミットにする。

### フェーズ4　測定と採否

- 作業機で、各候補の照合の出力が許容誤差に収まることを確かめる。
- vast.aiの2種類の機械（とG4）で「測り方」の節の測定を行い、採否を決める。
- 採った候補だけを残したコミットで、2回目の実行の初期ネットを書き出し直し、照合を行う。

### フェーズ5　移し替えとマージ

- 採った方式のADRを書き、推論の方式のADRとネットの入出力のADRのうち置き換わる部分を改める。
- 2回目の実行の設計書の初期ネットの記述と、深層強化学習を回す手引きを直す。
- 試験とcodexのレビューを通し、利用者の許可を得てmasterへマージする。

## 費用

vast.aiの4枚の4090は1時間約1.7〜2.1米ドルで、導入に約5〜12分、5つのコミットのビルドに約20分かかる。
4,096局の生成は、速い機械で約3.5分（機械Aの211秒）、遅い機械で約7分（機械Hの毎秒約390局面）かかる。
5つのコミットを5周回すと、速い機械で約2時間、遅い機械で約3.5時間になり、合わせて約10〜12米ドルと見込む（推論）。
遅い機械の周回を3周に減らすと、遅い機械は約2.3時間、約4〜5米ドルになる。
G4は1時間8.90 CUで、1回の生成を約10分と見て、5つのコミットを3周回すと約3時間、約27 CUになる（推論）。
借りる前に、そのときの出品の料金と周回の数を示して利用者の承認を得る。

## 検証

フェーズ1から3の試験が通り、作業機で、各候補の照合の出力が許容誤差に収まることを確かめる。
Aを採る場合は、1スレッド、GPU 1枚の生成が親のコミットと同じ塊を書くことを確かめる。
採った候補をすべて入れたコミットで、vast.aiの4枚の機械で照合まで含む1サイクルが最後まで回ることを確かめる。

## 完了条件

本書は、フェーズ4の測定を記録して採否を決め、採った候補を入れたコミットを試験とレビューを通してmasterへマージした時点で完了する。
候補をすべて採った場合は完了（採用）、一部を採った場合は完了（一部不採用）、1つも採らなかった場合は完了（不採用）とする。
完了は、2回目の実行のサイクル1を始める前とする。

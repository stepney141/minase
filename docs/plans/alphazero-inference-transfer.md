# AlphaZero型探索の推論で、ホストとGPUの間の転送を減らす設計書

## 先に読む要約

本書は、[AlphaZero型探索と深層強化学習の統括計画](alphazero.md)のもとで、自己対局の生成を速くするマイルストーンの設計書である。
ニューラルネットワーク（以下、ネット）の推論で、CPU側のメモリであるホストとGPUの間でやり取りするデータを減らす。
今の推論は、1局面あたり、float32の入力（159面×12×12、91,584バイト）をホストからGPUへ送り、float32の方策の出力（35,856要素、143,424バイト）をGPUからホストへ戻す。
どちらも、ONNX Runtimeの`session.run`が扱うページング可能なメモリ（OSが退避できる普通のメモリ）を通る。
vast.aiで借りた4枚のRTX 4090の仮想マシンである機械Hでは、毎秒の訓練局面で表す生成の速さが、同じGPUの構成で料金もほぼ同じ機械Bの約0.37倍にとどまった。
これは、GPU→ホストの転送が4枚の合計で毎秒約7 GBで頭打ちになったためと考えられる（[複数GPU化のvast.aiの測定](../measurements/alphazero-multi-gpu/alphazero-multi-gpu-vast.md)の「機械Hの生成が遅い理由」）。
この原因は仮説であり、本書の測定で確かめる。
候補は、出力をピン留めメモリ（pinned memory、OSが退避しないメモリ）で受け取るA、入力をuint8で送るB、方策をFP16で返すC、および方策を盤面によらず取り得る16,108ラベルへ固定の表で詰めるDの4つである。
このうちDは、Lc0のpolicy mapと同じ考え方に基づく。
候補を1つずつ積み重ねたコミットを作り、遅い機械で直前のコミットと交互に生成の速さを測って、速さの増分が測定の揺れを超えた候補だけを採る。
採った候補は、書き出したネットの推論の出力を学習器の参照と比べる照合（確率の差1×10⁻²、価値の差5×10⁻²などの許容誤差）を守らなければならない。
完了条件は、採った候補を入れたコミットが、[2回目の実行](alphazero-rl-2.md)（20ブロック256チャネルのネットでやり直す2回目の強化学習）のサイクル1より前にmasterへ入ることである。

利用者は同じ日に、候補を上の4つに限り、2回目の実行のサイクル1より前に本書を終えると決めた。

## 目的

本書の目的は、自己対局の生成で、推論の入出力の転送に費やす時間を減らすことである。

2回目の実行は、1サイクルの料金が最も安い機械で回す（[2回目の実行の設計書](alphazero-rl-2.md)の「費用」の節）。
これまでに借りた4枚の4090の機械は次のとおりで、生成の速さは出品によって約2.7倍違った（複数GPU化のvast.aiの測定）。

| 機械 | CPU | 1時間の料金 | 出品の`pcie_bw` | 生成の速さ | 1サイクル |
|---|---|---|---|---|---|
| A | EPYC 7K62、cgroupの割当て92 CPU | 1.894米ドル | 22.6 GB/s | 4,096局を211秒、毎秒716局面 | 回していない |
| B | 2ソケットのEPYC 7663の半分 | 2.034米ドル | 22.5 GB/s | 毎秒948局面 | 約36分、約1.23米ドル |
| H | EPYC 7543の仮想マシン、36個の仮想CPU | 2.054米ドル | 10.9 GB/s | 毎秒355局面 | 約67分、約2.30米ドル |

`pcie_bw`は、vast.aiが出品ごとに測ってCPUとGPUの間の帯域として載せる値である。
機械Aの生成の速さは、4,096局の短い生成のもので、対局の終わりの待ちを含むので、1サイクルの生成の速さとは直接比べられない。
機械Hの探索のスレッドは、稼働時間の49〜62%しかCPUを使わず、残りの時間は推論の呼び出しの完了を待っていた。GPUの使用率も40〜55%であった。
推論の呼び出しの中の待ちには、GPUの計算の時間も含まれるので、待ちの大半が転送であるかは測っていない。
転送を減らして遅い機械の生成が速くなれば、借りる機械の選び方の幅が広がり、1サイクルの料金も下がる。
ColabのG4と速い機械でも転送が生成を律速しているかは、まだ測っていない。

2回目の実行のサイクル1より前に終えるのは、2回目の実行の途中で生成器とネットの入出力の形を変えずに済むようにするためである（2026年11月11日の利用者の決定）。

## 適用範囲

本書で使う部品の名前は次のとおりである。

| 名前 | 中身 |
|---|---|
| 推論器 | ONNX Runtimeでネットを推論するRustの`OnnxEvaluator`（`crates/minase/src/nn/onnx.rs`） |
| 生成器 | 自己対局で教師を作る`minase data zero-selfplay` |
| 学習器 | PyTorchでネットを学び、ONNXに書き出す`minase_zero`（`tools/train/zero/`） |
| 実行器 | 借りた機械でサイクルの生成、学習、照合を順に起動する`minase_zero run-cycles` |
| 照合 | 書き出したネットを推論器で動かし、学習器の参照の出力と288局面で比べる処理（`minase dev nn-eval`と`nn_compare.py`） |

対象は、推論器、その入力を作る符号化、学習器のONNXの書き出し、照合、および学習器のRustの拡張`mnsd_reader`である。
推論器は、生成器、対局用のMCTSのUSIエンジン、および照合の`minase dev nn-eval`が共有しているので、変更はこの3つすべてに効く。
`mnsd_reader`は、推論器と同じ符号化の関数で学習の入力を作るので、符号化を変えると影響を受ける。

ONNXの署名とは、ONNXのネットの入力と出力の名前、型、および形のことである。
推論器は、セッションを作るときに署名を検査し、決めたものと違えば起動を拒む（`validate_signature`）。
学習器は、学習に使うネットの順伝播とは別に、書き出しのときだけ使う薄い包み（以下、書き出しの包み）を通してONNXを書き出す。候補B〜Dは、この包みだけを変え、学習の順伝播と損失は変えない。

対象外は次のとおりである。

- 合法手のラベルの並びを局面ごとにGPUへ送り、GPUの上で合法手のlogitだけを取り出してホストへ戻す案。先行実装に例がなく、合法手の数の上限も分かっていないので、2026年11月11日の利用者の決定で候補から外した。
- 独自のCUDAカーネル、CUDAのストリームの指定、および外部のメモリを包むテンソル。どれも`unsafe`を要し、ワークスペースは`unsafe_code = "forbid"`だからである。入力をビットで詰めてGPUで展開する方式（dlshogiとLc0）も、独自のカーネルを要するので外す。
- CUDAグラフ。転送の量を減らさず、IoBindingでアドレスを固定する必要があるので、本書の後に別に考える。
- 学習の計算。

## 依存関係

本書は、[複数GPU化](archived/alphazero-multi-gpu.md)とONNX Runtime 1.31.1への更新（[ADR](../adr/load-onnx-runtime-1-31-1-through-ort-rc13-for-zero-inference.md)）の後の状態から始める。
2回目の実行のサイクル1は、本書の完了を待つ。

候補B〜Dのどれかを採ると、署名が変わり、既存のネットのONNXは新しい推論器で読めなくなる。
データ形式の版は1つに保ち、古い形式を読み続けないので、必要なネットはチェックポイントから書き出し直す。
チェックポイントは、各サイクルの`train/checkpoint.pt`としてNASにある。
書き出し直すとONNXのファイルのSHA-256（以下、検査和）が変わる。検査和は、TensorRTのエンジンのキャッシュの鍵、生成器の設定、生成のファイルのヘッダ、および実行器のサイクルの記録に入っている。
既存の生成のファイルと記録は、書いた時点の検査和のまま残す。
2回目の実行の初期ネット`cycles-rl2/cycle-0000/`は、まだどのサイクルも回していない。
そのため、元の内容を別の場所へ保存したうえで、同じチェックポイントから書き出し直したONNXと集計で置き換え、元の検査和、新しい検査和、およびチェックポイントの検査和の対応を記録する。
1回目の実行のネットは、対局などで使うことになった時点で、別の場所へ書き出し直す。

## 設計判断

### 費用の式

1回の推論（バッチb）の時間を、次の和で考える。

```math
t_{\mathrm{call}}(b) = t_{\mathrm{enc}}(b) + \frac{b\,s_{\mathrm{in}}}{B_{\mathrm{in}}} + t_{\mathrm{gpu}}(b) + \frac{b\,s_{\mathrm{out}}}{B_{\mathrm{out}}} + t_{\mathrm{collect}}(b)
```

$`t_{\mathrm{enc}}`$は入力の符号化、$`t_{\mathrm{gpu}}`$はGPUの計算、$`t_{\mathrm{collect}}`$は合法手のlogitの取り出しにかかる時間である。
$`s_{\mathrm{in}}`$と$`s_{\mathrm{out}}`$は1局面あたりの入力と出力のバイト数であり、$`B_{\mathrm{in}}`$と$`B_{\mathrm{out}}`$は、ほかのスレッドやGPUも同時に転送しているときの入力と出力の実効の帯域である。
1本の探索のスレッドの中では`session.run`が同期して返るので、5つの項は重ならずに足される。
生成器はGPU 1枚あたり4本のスレッドを動かすので、スレッドの間では、ある呼び出しの転送と別の呼び出しの計算が重なり得る。

バッチbは、1本のスレッドが同時に進める対局の数（`--games-per-thread`、2回目の実行では128）以下で、各対局が1回の推論に1局面ずつ出す。
入力の159面は、手番側と相手側の駒の状態47面ずつ、先獅子の升1面、および手番側と相手側の擬似的な利き32面ずつで、すべて0か1である（[入力のADR](../adr/encode-zero-network-inputs-as-159-planes-with-pseudo-control-from-the-side-to-move.md)）。
方策の35,856要素は、移動元の升144個ごとに移動の種類249面を割り当てたラベルである（[方策のADR](../adr/encode-the-zero-policy-as-249-planes-per-from-square.md)）。
そのうち、盤面によらず合法手になり得るラベルは16,108個で、学習器の定数マスク`policy_mask`（`tools/train/zero/minase_zero/encoding.py`）が定める。

帯域には、複数GPU化のvast.aiの測定で、機械Hの4枚のGPUが同時に18.4 MBずつ転送したときの、GPU 1枚あたりの実効の値を使う。
ページング可能なメモリではホスト→GPUを毎秒2.7〜4.7 GB、GPU→ホストを毎秒1.6〜2.1 GBとし、ピン留めメモリではGPU→ホストを毎秒7.2〜12.5 GBとする。
この帯域が転送の大きさによらないと仮定すると、バッチ128の転送時間は次のように見込まれる。

| 構成 | 入力の転送 | 出力の転送 |
|---|---|---|
| 今（float32の入力、float32の35,856要素、ページング可能） | 11.7 MB、2.5〜4.3ミリ秒 | 18.4 MB、8.8〜11.5ミリ秒 |
| Aだけ（出力をピン留めメモリで受け取る） | 変わらない | 18.4 MB、1.5〜2.6ミリ秒 |
| Bだけ（入力をuint8で送る） | 2.9 MB、0.6〜1.1ミリ秒 | 変わらない |
| Cだけ（方策をFP16で返す） | 変わらない | 9.2 MB、4.4〜5.8ミリ秒 |
| Dだけ（方策を16,108ラベルへ詰める） | 変わらない | 8.2 MB、3.9〜5.2ミリ秒 |
| CとD（ページング可能） | 変わらない | 4.1 MB、2.0〜2.6ミリ秒 |

この表は、1つの候補だけを入れたときの転送の時間であり、Aと組み合わせたときの変化の量でも、生成の速さの見込みでもない。
小さい転送ほど、確保、同期、および待ちの固定の時間の割合が増えるので、表の値より長くなり得る。
BのCastとDのGatherはGPUの計算を足し、Bはホストの符号化の書き方も変えるので、$`t_{\mathrm{enc}}`$と$`t_{\mathrm{gpu}}`$も変わる。
$`t_{\mathrm{gpu}}`$は測っていないので、転送を減らしても生成が速くならないことがありうる。
この場合は候補を採らない。4つとも採らなければ、転送が律速しているという仮説を捨てる。

### 候補

| 候補 | 一般名 | 先例 | 変えるもの |
|---|---|---|---|
| A. 出力をピン留めメモリで受け取る | pinned host buffer、IoBinding | dlshogi（ふかうら王）、Lc0、KataGoのCUDAの実装はすべて、入出力をピン留めメモリに置く | 推論器だけ |
| B. 入力をuint8で送り、グラフの中でfloat32へ変換する | uint8 input | なし。TensorRTはuint8の入出力と`Cast`に対応する | 署名、符号化、書き出し、`mnsd_reader` |
| C. 方策をFP16で返す | FP16 output | Lc0のFP16のネット | 署名、書き出し、照合 |
| D. 方策を盤面によらず取り得るラベルへ固定の表で詰める | policy map | Lc0は生の出力を1,858要素へ固定の表で詰める | 署名、書き出し、推論器のラベルの添字 |

**A.** IoBindingは、ONNX Runtimeで、推論を始める前に入力と出力のメモリの置き場所を指定する機能である。
Aは、方策と価値の出力をCUDAのピン留めメモリに置くよう指定する（ortの`bind_output_to_device`）。
この方式では、TensorRTはGPUのメモリに出力を書き、ONNX Runtimeがそれをピン留めメモリへ転送する。
ONNX Runtime 1.28.3では、出力をピン留めメモリへ結び付けると、同じ領域どうしの転送として`gpu_data_transfer.cc`で拒まれた（[実現性の実測](../measurements/alphazero-environment/alphazero-feasibility.md)）。
1.31.1の`utils.cc`の170行を読むと、ピン留めの出力の領域を呼び出しの間で保持し、次の呼び出しで実行プロバイダの出力の置き場所として使い回す実装になっている。
そのため、2回目以降の呼び出しで、1.31.1でも`gpu_data_transfer.cc`の94〜104行で同じ領域どうしの転送として拒まれるおそれがある。
そこでフェーズ2では、最初に、呼び出しごとに出力を結び付け直す方式と、結び付けを保つ方式の両方で、1,000回の連続の推論と、バッチの大きさを1から128まで変える推論が通るかを確かめる。
どちらも通らなければAを採らない。
入力は今と同じくページング可能なメモリから送る。入力をピン留めメモリに置くと、1.31.1ではTensorRTがホストのメモリを直接読む動作になり（`utils.cc`の`CanSourceSatisfyTarget`）、Lc0はその方式が遅いと記しているからである。
CPUの実行プロバイダでは、今と同じく`session.run`で出力を受け取る。

**B.** 入力の159面がすべて0か1であることを使い、推論器は入力をuint8の`[バッチ, 159, 12, 12]`で送る。
書き出しの包みは、受け取った入力を`Cast`でfloat32へ変換してから、今のネットへ渡す。
0と1の変換は誤差を生まないので、ネットが見る値は変わらない。
符号化の関数は`mnsd_reader`と共有しているので、符号化をuint8で書く形に改め、`mnsd_reader`はそれをfloat32へ変換して今と同じ配列を学習器へ返す。

**C.** 書き出しの包みの最後で、方策のlogitを`Cast`でFP16へ変換する。
価値は1局面あたり4バイトしかないので、float32のまま返す。
FP16の単位の丸め誤差は2⁻¹¹（約4.9×10⁻⁴）なので、logitの丸めの誤差は相対で最大約4.9×10⁻⁴であり、logitが1付近なら絶対誤差も約4.9×10⁻⁴になる。
照合におけるCPUの実行プロバイダでの比較は、logitの絶対誤差1×10⁻⁴を求めているため（`runner.py`の`check_script`）、Cを入れると今の基準では通らない。
そこでCのコミットでは、CPUでの比較に使う参照のlogitをFP16へ丸めてから比べ、許容誤差を1×10⁻⁴にFP16の1目盛りを足した値とする。
float32の出力から変わる大きさは、これとは別に、学習したネットの確率の差で評価する（[教訓](../lessons/judge-low-precision-inference-on-trained-outputs.md)）。
TensorRTとCUDAの比較は、今と同じく確率の差1×10⁻²、価値の差5×10⁻²とする。

**D.** 書き出しの包みの最後で、方策を固定の添字の表で`Gather`し、35,856要素から16,108要素へ詰める。
表は、`policy_mask`が真である添字を昇順に並べたものとする。
書き出しは、この表をONNXのメタデータに昇順の整数の並びとして書き込む。
推論器は、セッションを作るときにメタデータの表を読み、昇順であること、要素の数が出力の幅と等しいこと、および値が35,856未満であることを確かめる。
そのうえで、元のラベルから詰めた後の添字を引く逆引きの表を作る。
`policy_mask`はどの盤面の合法手のラベルも含むように作られており、学習器の試験がそれを確かめている（[マスクのADR](../adr/mask-impossible-policy-labels-and-diagnose-the-zero-trainer-on-final-weights.md)）。
それでも、推論器の`policy_label`と書き出しのマスクの定義が将来食い違えば、合法手のラベルが表にないことが起こりうるので、その場合は推論を明示的なエラーにする。
表をネットのファイルに持たせるので、RustにPythonと同じマスクの規則を書き写さずに済み、書き出しと推論で表が食い違うこともない。

### 採否の決め方

採否は、対局でのSPRTではなく、生成の速さと照合の許容誤差で決める。
4つの候補は、ネットも探索の規則も変えず、推論の値を照合の許容誤差の中で変えるだけだからである。
TensorRTのFP16の推論も、同じく照合の許容誤差で採った（[ネットの入出力と推論の設計書](archived/alphazero-network.md)の「先に読む要約」）。
この扱いはCONTRIBUTING.mdの棋力測定の規則の例外であり、2026年11月11日の本書の承認で決まった。

候補は、共通の準備のコミットSの上に、A、B、C、Dの順で1つずつ積み重ねる。
Sには、書き出し直しのサブコマンドと測定のスクリプトなど、どの候補を採っても要るものを入れる。
署名を変えないAを先にし、Bの後に、照合の基準を変えるCと、推論器の添字を変えるDを置く。
各候補の比較の相手は、積み重ねた列の直前のコミットである。

| 候補 | 比較の相手 |
|---|---|
| A | S |
| B | A |
| C | B |
| D | C |

ある候補を採らなかった場合は、その後の候補を、採った直前のコミットの上に載せ直し、載せ直したコミットを改めて照合し、測り直す。
載せ直す前の測定は、親の転送量と速さが違うので、判定に使わない。

## 測定

### 測り方

生成は、組み替えた初期配置（1〜3段目の駒を段の中で並べ替えた初期局面）から4,096局を、完全な探索32回、速い探索8回、GPUあたり4スレッド、スレッドごとに同時128局の条件で行う。
生成の速さは、訓練局面の数を生成の経過時間で割った値とする。
ネットは2回目の実行の初期ネットとし、署名を変えるコミットでは、そのコミットの学習器でチェックポイントから書き出し直したネットを使う。
測る前に、各コミットのネットで最大バッチ128のTensorRTのエンジンを作っておき、エンジンの作成の時間は別に記録する。
1周では、S、A、B、C、Dの5つを順に1回ずつ生成し、次の周は逆の順に生成する。これを5周繰り返す。
各回の訓練局面の数、総手数、完全な探索と速い探索の回数、および経過時間を残す。

同じコミットでも、生成の対局番号は全スレッドで共有するカウンタから取るので、どのスレッドがどの対局を進めるかは回ごとに変わり、推論のバッチの組み方と処理の時間が揺れる。
そのため、コミットごとに5回の生成の速さの中央値を取り、最大と最小の差を中央値で割った値をそのコミットの幅とする。
遅い機械での測定で、候補の中央値を相手の中央値で割った値から1を引いたものを増分とする。
候補を採るのは、この増分が候補と相手の幅の大きいほうを超える場合である（[教訓](../lessons/alternate-speed-rounds-against-parent.md)）。
増分が0より大きく幅以下の場合は、その2つのコミットだけを3周追加で測り、8回で同じ判定をする。それでも幅以下なら採らない。

| 機械 | 選び方 | 測るコミット | 判定 |
|---|---|---|---|
| 遅い機械 | vast.aiの4枚の4090で、出品の`pcie_bw`が12 GB/s以下のもの | S、A、B、C、D | 採否を決める |
| 速い機械 | vast.aiの4枚の4090で、`pcie_bw`が20 GB/s以上のもの | S、A、B、C、D | 採った候補の増分が、相手の幅を超えて負にならないこと |
| G4 | ColabのG4 | Sと、採った候補をすべて入れた最終のコミット | 最終のコミットの中央値が、Sの中央値から幅を超えて下がらないこと |

速い機械とG4で幅を超えて遅くなった候補は採らない。
`pcie_bw`は出品を選ぶ目安にだけ使い、借りた後に4枚で同時の転送の帯域（[copy-bandwidth.py](../measurements/alphazero-multi-gpu/copy-bandwidth.py)）とSの生成の速さを測る。
遅い機械は、ページング可能なメモリにおけるGPU→ホストの4枚の合計の帯域が速い機械を下回り、かつSの生成が速い機械より遅いことを確かめてから使う。
G4が借りられない日は、G4の比較を後の日に回し、完了の前に必ず行う。

### 出力の確認

照合の参照は、ネットを書き出した機械と同じ機械で、学習器の`fixture-eval`を使って作る。
`fixture-eval`は、チェックポイントから書き出し直したONNXと与えたONNXのバイト列が一致することを求めるが、CPUが異なるとその一致が崩れる（[教訓](../lessons/compare-reexported-onnx-bytes-only-on-the-exporting-machine.md)）からである。
署名を変える候補では、作業機で、そのコミットの学習器でネットを書き出し、同じ作業機で参照を作り、そのネットと参照の組を借りた機械へ配る。
`nn_compare.py`は参照とネットの検査和の一致を確かめるので、署名の違うコミットの間で参照を使い回さない。

各候補で、照合の`minase dev nn-eval`のCPU、CUDA、TensorRTのバッチ1、7、256の出力を参照と比べ、上の許容誤差に収まることを確かめる。
確かめるネットは、2回目の実行の初期ネットと、複数GPU化で1サイクル学んだネット（`multi-gpu-vast/cycle-0001`と`multi-gpu-vast-2/cycle-0001`）とする。
USIエンジンについては、各候補の署名のネットで、準備、3回の連続の探索、推論器の設定を変えた後の推論器の作り直し、およびCUDAの実行プロバイダでの探索を確かめる。USIエンジンは最大バッチ1,024まで受け付けるので、その大きさでも確かめる。
Aは推論の計算を変えないので、作業機で1スレッド、GPU 1枚の生成が、親のコミットと同じ対局を書くことも確かめる。
生成のファイルのヘッダには生成器のコミットが入るので、比較ではその欄を除き、ほかのヘッダの欄と対局のデータのバイト列の一致を求める。
署名を変える候補は、TensorRTのエンジンが変わるので、生成の対局の一致は求めない。

## 実装フェーズ

本書のブランチをmasterから切り、worktreeで実装する。
実装はcodexに委任し、GPUを使う確認はClaudeが作業機と借りた機械で行う（[教訓](../lessons/run-gpu-training-outside-codex-sandbox.md)）。

### フェーズ1　共通の準備（コミットS）

- 学習器に、チェックポイントからONNXだけを書き出し直すサブコマンドを加える。
- 「測り方」の節の生成を、5つのコミットについて周回の順を反転させながら行い、各回の記録を残す測定のスクリプトを、本書の測定記録のディレクトリに置く。

### フェーズ2　A（出力のピン留めメモリ）

- 作業機で、ONNX Runtime 1.31.1とTensorRTの実行プロバイダについて、「候補」の節のAの2つの方式で、1,000回の連続の推論と、バッチを1から128まで変える推論が通るかを確かめる。どちらも通らなければAを採らず、フェーズ3へ進む。
- 通った方式で、TensorRTとCUDAの推論器を`IoBinding`で書き直す。
- 作業機で、1スレッド、GPU 1枚の生成が、ヘッダの生成器のコミットの欄を除いて、親のコミットと同じ対局のデータを書くことを確かめる。

### フェーズ3　B（uint8の入力）

- 符号化をuint8で書く形に改め、今のfloat32の符号化と同じ0と1を書くことを試験で確かめる。
- `mnsd_reader`は、uint8の符号化をfloat32へ変換して今と同じ配列を返す形に改め、拡張を作り直して学習器の試験を通す。
- 書き出しの包みに`Cast`を入れ、推論器の署名の検査をuint8の入力に改め、TensorRTの最適化プロファイル（入力の形の最小、最適、最大の指定）を合わせる。

### フェーズ4　CとD（方策の型と詰め方）

- Cでは、書き出しの包みにFP16への`Cast`を入れ、推論器がFP16の方策を読む形に改め、照合のCPUの比較を「候補」の節のとおりに改める。ortでFP16を読むには、ortの`half`機能と`half`クレートを依存に加える。
- Dでは、書き出しの包みに固定の表の`Gather`を入れ、表をONNXのメタデータに書き、推論器がそれを読んで逆引きの表を作る形に改める。
- CとDは別々のコミットにする。

### フェーズ5　測定と採否

- 作業機で、「出力の確認」の節の確認を各候補で行う。
- vast.aiの遅い機械と速い機械で、「測り方」の節の測定を行い、採否を決める。採らなかった候補があれば、後の候補を載せ直し、照合と測定をやり直す。
- G4で、Sと最終のコミットを比べる。

### フェーズ6　移し替えとマージ

- 採った方式のADRを書き、推論の方式のADRとネットの入出力のADRのうち置き換わる部分を改める。
- 2回目の実行の初期ネットを「依存関係」の節のとおりに書き出し直し、2回目の実行の設計書と、深層強化学習を回す手引きを直す。
- 採った候補をすべて入れたコミットで、vast.aiの4枚の機械で照合まで含む1サイクルを回す。
- 試験とcodexのレビューを通し、利用者の許可を得てmasterへマージする。

## 費用

次の値は、機械Aの4,096局の生成の時間211秒と、機械Hの生成の速さ（毎秒355局面、4,096局の約15万局面で約7分）から求めた見込みである。
vast.aiの4枚の4090は1時間約1.7〜2.1米ドルで、導入に約5〜12分、5つのコミットのビルドに約20分、エンジンの作成と帯域の測定に約12分かかる。

| 機械 | 生成 | 合計の時間 | 費用 |
|---|---|---|---|
| 遅い機械 | 5つのコミット×5周×約7分＝約175分 | 約3.6時間 | 約7〜8米ドル |
| 速い機械 | 5つのコミット×5周×約3.5分＝約88分 | 約2.2時間 | 約4〜5米ドル |
| G4（1時間8.90 CU） | 2つのコミット×5周×約5分＝約50分 | 約1.5時間 | 約13 CU |

G4の4,096局の生成の時間は、2回目の実行の設計書の見積もり（1サイクルの生成約34分で約100万局面）から約5分とした。
これに、未決の比較の追加の周回、候補を載せ直した後の測り直し（遅い機械で最大約4時間、約8米ドル）、およびフェーズ6の1サイクル（約2.5米ドル）が加わりうる。
合わせて約14〜26米ドルと約13 CUと見込む。
借りる前に、そのときの出品の料金と周回の数を示して利用者の承認を得る。

## 検証

フェーズ1から4の試験が通り、作業機で、各候補の照合の出力が許容誤差に収まることを確かめる。
Aを採る場合は、1スレッド、GPU 1枚の生成が、ヘッダの生成器のコミットの欄を除いて、親のコミットと同じ対局のデータを書くことを確かめる。
採った候補をすべて入れたコミットで、USIエンジンの確認と、vast.aiの4枚の機械で照合まで含む1サイクルが最後まで回ることを確かめる。

## 完了条件

本書は、フェーズ5の測定を記録して採否を決め、採った候補を入れたコミットを試験とレビューを通してmasterへマージした時点で完了する。
候補をすべて採った場合は完了（採用）、一部を採った場合は完了（一部不採用）、1つも採らなかった場合は完了（不採用）とする。

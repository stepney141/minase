# AlphaZero型探索の学習器と自己対局生成のGPU実行の高速化の設計書

## 先に読む要約

minaseのAlphaZero型の強化学習は、方策と価値を出すニューラルネットワーク（以下ネット）を、自己対局と学習の繰り返しで強くする。
1サイクルでは、作業機（開発者の手元の計算機）で動く実行器`runner.py`が、vast.aiで時間貸しされるGPU 4枚の機械（以下、借りた機械）で、自己対局の生成器`zero-selfplay`、PyTorchの学習器、および照合（学習したネットを推論用の形式で動かした出力が学習器の出力と一致するかの確認）の3つのプロセスを順に動かし、出力のファイルを検査和（SHA-256）で確かめながら作業機へ受け取る。
この設計書は、学習の式と教師データの作り方を変えずに、この1サイクルを短くする変更を定める。
[GPU計算ボトルネック調査報告](../audits/gpu-computation-bottlenecks-2026-11-28.md)の集計では、2回目の強化学習のサイクル90〜100で、1サイクルの中央値約1,009秒のうち約396秒は、3つのプロセスが計時している区間の外にあった。
報告は、その多くを、実行器がファイルを1つずつ受け取って照合する時間と、状態を照会した後に60秒待機する監視のために工程の終了に気づくのが遅れる時間だと推定しているが、内訳は測っていない。
また、作業機の測定では生成器がGPUの推論で律速されており、その生成器は、手ごとに作り直す探索木と、全局を同じ初期局面から始める設定での共通の序盤で、同じ局面をネットに評価させ直している。
学習器は、ネットの入力のうち駒の利きを表す面をCPUで計算するためにデータをGPUとCPUの間で往復させているが、作業機の簡易な測定では、この往復を含む入力の組み立ての時間は1回の学習の計算の約1.4%だった。
そこで、第1に実行器の受信を一括にし、終了の検知を借りた機械の側の待ち合わせに替え、借りた機械へ送ったファイルのうち照合済みで書き換わらないものは検査和を使い回し、第2に生成器にネットの出力のキャッシュを足し、第3に学習器の入力の組み立てを除いた場合に短縮できる時間の上限を測って、学習の時間の5%を超える場合に限り改める。
完了条件は、プロセスとプロセスの間の時間（工程の切れ目の時間）の中央値が、同じ条件で測った変更前の半分以下になり、キャッシュと学習器の改善を採るかどうかが、本書の定める基準で決まっていることである。

## 目的

3回目の強化学習で、1サイクルの時間と借りた機械の費用を減らす。
学習の式、照合の基準、および教師データの作り方は変えない。
自己対局のキャッシュを採る場合は、推論の数値の誤差の範囲で生成される対局が変わるので、教師データの統計が変わらないことを「自己対局にネットの出力のキャッシュを足す」の節の基準で確かめる。

## 適用範囲

対象は次のとおりである。

- 実行器：`tools/train/zero/minase_zero/runner.py`と、その試験`tools/train/zero/tests/test_runner.py`
- 自己対局の生成器：`crates/minase/src/bin/minase/zero_selfplay/`と、推論器`crates/minase/src/nn/onnx.rs`
- 学習器：`tools/train/zero/minase_zero/train.py`、`encoding.py`、およびRust拡張`tools/train/zero/mnsd_reader/`

キャッシュは自己対局の生成器からだけ有効にし、対局用PV-MCTS（`crates/minase/src/search/mcts/`）と照合の推論の動作は変えない。
キャッシュを有効にすると、TensorRTではバッチの組み方で同じ入力の出力が誤差の範囲で変わるので、別のバッチで推論した値を使い回す分だけ生成される対局が現在と変わる。
対局用PV-MCTSの探索は[対局用PV-MCTSの高速化の設計書](mcts-search-gpu-speedup.md)が扱う。
学習器のリプレイバッファ（直近のサイクルの自己対局の教師データを学習に使う範囲）の読み込み（中央値68秒、上の396秒には含まれない）は、プロセスの中の処理であり、3回目の強化学習ではリプレイバッファを直近4万局に限って大きさを抑えるので、対象外とする。
照合を次のサイクルの生成と並行させることは、照合に通る前のネットで生成を始めることになり、照合に落ちたときに生成が無駄になるので採らない。

## 設計判断

| 項目 | 採る方式 | 採らない代案 |
|---|---|---|
| 受信 | 工程ごとのファイルの列について、検査和と大きさの照会、rsync、および手元の照合をそれぞれ1回で行い、工程の完了の印を最後に置く | ファイルごとに3回の遠隔呼び出しを行う現在の方式 |
| 監視 | 借りた機械の側で1秒ごとに状態を調べ、変化か上限の時間まで待ってから返る | 照会の後に60秒待機する現在の方式、待機時間を短くする方式 |
| 送信の照合 | 同じ借りた機械に送った、書き換わらないファイルに限り、照合済みの検査和を実行器のプロセスの中で使い回す | 毎回すべてのファイルの検査和を求め直す現在の方式 |
| 自己対局のキャッシュ | スレッドごとに容量の上限を設けたキャッシュを推論器の中の符号化の後に置き、入力の全バイトと方策のラベルの列で照合する | 探索木を手の間で持ち越す方式 |
| 学習器の前処理 | 前処理を除いた場合の学習の時間を測って上限を求め、5%を超える場合に限り改める | Profilerの同期時間の合計で判断する方式、測らずにGPUへ移す方式 |

### 工程の切れ目の時間を測る

本計画が縮める対象は、借りた機械で3つのプロセスのどれも動いていない時間である。
これを測るため、実行器が借りた機械でプロセスを起動するスクリプトに、プロセスの開始と終了の時刻を借りた機械の時計で書く処理を足す。
1サイクルの**工程の切れ目の時間**は、生成器の終了から学習器の開始まで、学習器の終了から照合の開始まで、および照合の終了から次のサイクルの生成器の開始までの3つの時間の和と定め、借りた機械の時計だけで求める。
N個のサイクルの工程の切れ目の時間を得るには、N+1個目のサイクルの生成器の開始までを観測する。
調査報告の残り約396秒には、生成器の最後の塊（生成器が一定の数の対局ごとに書き出すファイルの組）の後の終了処理や、学習器の起動、チェックポイントの保存、およびネットの書き出しのように、プロセスの中で行われる処理も含まれるので、396秒をそのまま基準にはしない。

あわせて、実行器が行う遠隔呼び出し、rsync、手元の検査和の計算、およびサイクルの記録のための手元の処理（教師データの統計の集計など）の開始と終了の時刻を作業機の時計で記録し、工程の切れ目の時間を、受信と照合、送信と照合、終了の検知の遅れ、およびその他の手元の処理に、重ならないように分ける。
2つの時計のずれは、サイクルごとに借りた機械の時刻を照会して求め、作業機の時刻を借りた機械の時刻へ直してから分ける。
終了の検知の遅れは、プロセスの終了から、実行器がその終了を知った時刻までとし、その間に監視の処理の中で進んでいた塊やチェックポイントの受信は受信の側に数える。
生成器が動いている間に進む塊の受信は、プロセスと重なっているので、工程の切れ目の時間には数えない。

### 実行器の受信を一括にする

現在の`receive()`は、まだ受け取っていない書き換わらないファイルについて、借りた機械での検査和の計算、大きさの照会、およびrsyncの3回の遠隔呼び出しと、手元での検査和の計算を行う。
調査報告では、サイクル100の生成器が終わってから30ファイルを受け取り終えるまでに約110秒かかった。
照合の工程でも、出力の32ファイルを同じ方法で受け取っている。

本計画では、確定させる順序つきのファイルの列を受け取る関数を設ける。
この関数は、1回の遠隔呼び出しで列のすべてのファイルの検査和と大きさを求め、手元にすでにあるファイルと比べ、異なれば現在と同じく、書き換わらないはずのファイルが異なるとしてエラーにする。
残りのファイルを1回のrsyncで、作業ディレクトリと同じファイルシステムの一時の場所へ受け取り、手元で検査和を照合してから、列の順に名前を変えて確定する。
名前を変えるたびに、現在と同じくファイルと親ディレクトリの内容を`fsync`で記憶装置へ書き込んで確定させる。
時間の上限は、受け取るバイト数の合計を毎秒1 MBで割った秒数に120秒を足す現在の規則を、列の合計に当てはめる。

名前を変える途中で止まると、列の一部だけが確定する。
そのため、工程全体を一度に確定させることは求めず、工程の完了の印を確定させた時点で、その工程の成果物がすべて確定していることを契約とし、工程ごとに次のとおり定める。

- 生成：生成器は対局を一定の数ずつまとめて、教師データの形式MNSDのファイルと集計のJSONの組（塊）として書く。塊はMNSDをJSONより先に確定し、JSONを塊の確定の印とする。すべての塊と標準出力と標準エラーのログを確定した後に、工程の集計`selfplay/summary.json`を最後に確定し、これを工程の完了の印とする。生成が失敗しても、確定した塊は再開のために残す。
- 学習：`summary.json`は一時の場所で読み、サイクルの番号と、受け取った`model.onnx`の検査和が`summary.json`に記録された値と一致した後にだけ確定し、これを工程の完了の印とする。`checkpoint.pt`は、現在と同じく借りた機械で一時の名前へ複写したファイルについて検査和と大きさを求めてから受け取り、手元の古い版と異なっても置き換え、失敗したときは古い版を残す。
- 照合：出力とログを受け取った後に、照合の終了コード`check.exit`を最後に確定し、これを工程の完了の印とする。照合が0以外で終わった場合も、診断の出力とログを受け取ってから止まる。

### 監視を借りた機械の側の待ち合わせに替える

現在の`_monitor()`は、状態の照会、成果物の受信、および`--poll-seconds`（2回目の強化学習では60秒）の待機を繰り返す。
工程の終了に気づくまでには、最大で60秒の待機に、その回の受信の時間を足した時間がかかる。
待機時間を短くすると、借りた機械への遠隔呼び出しが増える。

本計画では、借りた機械の側で動く短いスクリプトが、1秒ごとにプロセスの状態と新しく確定した塊のJSONの有無を調べ、どちらかが変わるか`--poll-seconds`が過ぎたときに状態を返すようにする。
借りた機械の側で待っている間の検知の粒度は1秒になる。
ただし、塊が1つ確定するたびにスクリプトが戻るので、60秒の間に塊が別々の時刻に確定すると、現在は1回の照会でまとめて扱っていた塊ごとに遠隔呼び出しが起きる。
呼び出しの回数と作業機での検知の遅れはフェーズ1とフェーズ5で測る。
呼び出しから戻るたびに、まだ受け取っていない塊を先に調べ、学習の工程では塊がなくても`--poll-seconds`ごとにチェックポイントを受け取る。
PIDが残っていて終了コードがなく、プロセスもいなければ異常終了として止める現在の判定は、同じスクリプトで行う。

### 送信の照合を使い回す

現在の`send()`は、送るファイルの検査和を、送信済みのものも含めて毎回、手元と借りた機械の両方で求め直す。
2回目の強化学習では、リプレイバッファがサイクル100で1,867ファイル、3.6 GBに育ち、生成の受信完了から学習の起動までの時間が、サイクル5の7秒からサイクル90〜100の中央値26秒（最大約150秒）へ延びた。

本計画では、実行器が1つのプロセスの中で、同じ借りた機械の同じ作業場所へ送って照合した、確定後に書き換わらないファイル（リプレイバッファの塊、初期ネット、およびサイクルごとに別の名前で一度だけ書く学習データの一覧）に限り、照合した検査和を覚えておき、次の送信では照合を省く。
借りた機械にないことの確認は毎回行い、なくなっていて送り直したファイルは、送った後に照合し直す。
学習中に置き換わる`checkpoint.pt`は対象外とし、現在と同じく毎回照合する。
この方式は、借りた機械の上で照合済みのファイルが書き換わらないことを前提とする。
実行器を起動し直したときは、覚えた検査和がないので、最初の送信で全ファイルを照合する。
3回目の強化学習はリプレイバッファを直近4万局に限るので、照合の時間の延びは2回目より小さくなる見込みである（推論）。

### 自己対局にネットの出力のキャッシュを足す

生成器は1手ごとに探索木を作り直すので、前の手の探索で評価した局面を次の手の探索でも評価する。
開始局面`initial`（標準の初期局面から全局を始める設定）では、序盤の局面は多くの対局で重なる。
作業機では生成がGPUの推論で律速されているので、評価を省いた割合だけ生成が速くなると見込まれる（推論）。

キャッシュは、生成のスレッドごとに、ONNX Runtime（ネットの推論のライブラリで、生成器はその上でNVIDIAの推論エンジンTensorRTを使う）を呼ぶ推論器`OnnxEvaluator`の中で、局面をネットの入力へ符号化した直後に置き、ロックを使わない。
符号化の後に置くのは、推論器の外に置くと、キャッシュに当たらなかった局面を二度符号化することになるからである。
推論器を作る関数に容量の引数を足し、自己対局の生成器だけが0より大きい容量を渡す。

ネットの入力は、12×12升の盤の各升について0か1を持つ159枚の面（1局面22,896バイト）であり、手番側から見た駒の配置、先獅子（直前に獅子が取られたときに課される、獅子を取り返す手の制限）の升、および駒の利きだけから作られ、対局の履歴を含まない。
一方、自己対局の根では、同一局面の繰り返し（千日手）の規則による勝ち負けを履歴から判定して指す手の候補を選別するので、同じ入力でも、ネットに方策を求める手の列は違いうる。
キャッシュには、ネットの方策の出力全体（16,108ラベルで1局面約32 KB）ではなく、依頼された手のlogitだけを保存して容量を節約する。
そのため、キャッシュの鍵は、入力の全バイトと、依頼された手の方策のラベル（`policy_label(mv, side_to_move)`の値）の列とし、両方が一致したときだけキャッシュの値を使う。
索引には短いハッシュを使い、引き当てた項目は鍵の全体で照合して、ハッシュの衝突による取り違えを防ぐ。
値は、ラベルの列の順のlogitと、手番側の勝率（0〜1）とする。
探索の後の値、教師の価値、および投了の判定は使い回さない。
容量はバイト数で上限を決め、上限に達したら古い項目から捨てる。

同じバッチの中で同じ入力の依頼が重なったときは、推論を1回にまとめ、同じ出力の行から、各依頼のラベルの列の順にlogitを取り出して、元の依頼の順に返す。
スレッドをまたいだ重複の割合がスレッドの中の重複より大きいと測られた場合に限り、GPUごとに共有するキャッシュを検討する。

キャッシュから返す値は、別のバッチで推論した値であり、TensorRTでは同じ入力でもバッチの組み方で出力が誤差の範囲で変わるので、生成される対局は現在と一致しない。
そのため、採否は、借りた機械で、3回目の強化学習の条件の生成を、シードs1、s2、s3のそれぞれでキャッシュの有無の両方について行う6回の生成で決める。
1つ目の基準は速さであり、1秒あたりの訓練局面数について、キャッシュありの中央値とキャッシュなしの中央値の差が、両条件それぞれの最大値と最小値の差のうち大きいほうを超えることとする。
2つ目の基準は教師データの統計であり、次の各量について、キャッシュありの3回の平均とキャッシュなしの3回の平均の差の絶対値が、キャッシュなしの3回の最大と最小の差以下であることとする。

- 終局の理由ごとの対局の割合と、投了で終わった対局の割合
- 1局の手数の平均と、10%、50%、90%の分位点
- 記録した価値の平均と、10%、50%、90%の分位点
- 記録した方策のエントロピーの平均
- 投了を禁じた対局で記録した手番側の最小の勝率（実行器が投了の閾値を決める材料）の平均

### 学習器の前処理を測ってから改める

学習器の`encode_planes`は、駒の配置などの面をGPUで作る一方、64枚の利きの面はRust拡張の`control_planes`がCPUで計算するので、盤面をCPUへ戻し、計算した結果をGPUへ送り直している。
調査報告の作業機の測定では、1ミクロバッチ（256局面）の入力の組み立て全体が2.95ミリ秒、`torch.compile`を使わないbf16の簡易な学習の1ミクロバッチが約216ミリ秒だった。
ただし、この比は本番の学習の内訳ではない。
3回目の強化学習は、全体のバッチを1,024から256に減らし、新しい局面1つあたりの学習の標本を4倍にするので、更新の回数は2回目の約16倍になり、ミクロバッチも256から64に減るので、組み立てが学習の時間に占める割合も変わりうる。

本計画では、組み立てを除いた場合に学習がどれだけ速くなるかの上限を、借りた機械の3回目の条件（全体のバッチ256、ミクロバッチ64、GPU 4枚、コンパイルあり）で測る。
組み立てを含む全期間の入力を前もってGPUに置くと、学習時の入力は1局面91,584バイト（float32）なので、3回目の1サイクルの標本ではGPUのメモリに収まらない。
そこで測定用のスクリプトで、同じ抽出の順序で並べた、GPUに収まる長さ（例えば200更新）の更新列について、入力を前もって組み立ててGPUに置いた学習と、通常の学習を、それぞれ2回以上交互に走らせる。
比べる時間は、その更新列の経過時間（以下、学習の時間）であり、測定用のスクリプトが分散学習の各GPUのプロセスで測った値のうち最も遅いものを使う。
PyTorch Profilerの同期の時間は、先に投入したGPUの計算や通信の完了待ちも含むので、内訳の手がかりにだけ使い、採否には使わない。
組み立てを除いた学習の時間の短縮が、通常の学習の時間の5%を超える場合に限り、ピン留めメモリへの先読みでCPUの組み立てをGPUの計算と並行させる方式と、利きの面をGPUで計算する方式を比べて改める。
利きの面をGPUで計算する方式は、獅子と走り駒（何升でも進める駒）の利きの規則を2つの実装で持つことになるので、保守の費用も比べる。
前処理を改める場合も、抽出の順序、各GPUへのミクロバッチの割り当て、およびバッチ正規化の統計の更新の順序は変えず、コンパイルとbf16の設定も保つ。

## 実装フェーズ

### フェーズ1：変更前の測定

実行器に「工程の切れ目の時間を測る」の節の記録を足し、変更前の実行器を使い、RTX 4090を4枚積んだ借りた機械で、2回目の強化学習のネットとリプレイバッファから分岐した試験用の系列を、中断せずに5サイクルを終えて6サイクル目の生成器が始まるまで回す。
同じ借用の中で、学習器の前処理の上限を「学習器の前処理を測ってから改める」の節の方法で測る。
作業機で、生成器の4スレッドの生成について、スレッドの中とスレッドをまたいだ評価の重複の割合を、開始局面`initial`と`shuffled-setup`（自陣の手前3段の駒をそれぞれの段の中で並べ替えた配置から始める設定）の両方で測る。
完了条件は、工程の切れ目の時間とその内訳、学習器の前処理の上限、および評価の重複の割合が測定記録に残ることである。

### フェーズ2：実行器の受信、監視、および送信

「実行器の受信を一括にする」、「監視を借りた機械の側の待ち合わせに替える」、および「送信の照合を使い回す」の3つを実装する。
完了条件は、実行器の試験が通り、受信の途中の失敗、検査和の不一致、既存のファイルの相違、名前を変える途中での停止と再開、工程の異常終了、および照合の0以外の終了の各経路で、不完全な成果物のまま工程の完了の印が確定することがなく、再開に必要な塊とチェックポイントと失敗の診断が残ることが試験で確かめられていることである。

### フェーズ3：自己対局のキャッシュ

キャッシュとバッチの中の重複の除去を実装する。
完了条件は、「自己対局にネットの出力のキャッシュを足す」の節の6回の生成で、2つの基準による採否が決まっていることである。
採らない場合は、キャッシュを外す。

### フェーズ4：学習器の前処理

フェーズ1で測った上限が5%を超える場合に限り、2つの方式を試作し、フェーズ1と同じ更新列で通常の学習と交互に測る。
学習の時間の短縮が通常の学習の時間の5%を超えた方式のうち、短縮の大きいほうを採る。
どちらも5%を超えない場合と、上限が5%以下の場合は、前処理を改めず、測定記録に理由を残してこのフェーズを閉じる。

### フェーズ5：変更後の測定

採った変更をすべて入れた版で、フェーズ1と同じ種類の借りた機械と同じ分岐元から、中断せずに5サイクルを終えて6サイクル目の生成器が始まるまで回し、フェーズ1と同じ方法で5サイクル分の工程の切れ目の時間を測る。
リプレイバッファのファイルの数と大きさもフェーズ1と並べて記録する。

## 検証

1. 実行器の変更は、`tools/train/zero`で`uv run --frozen python -m unittest discover -s tests -t .`を実行して試験し、借りた機械で1サイクルを回して、確定したファイルの検査和が借りた機械のファイルと一致することを確かめる。
2. 自己対局のキャッシュは、ハッシュの衝突を人工的に起こす試験、同じ入力で手の列が異なる試験、および同じバッチの中で同じ入力の依頼が重なる試験で、取り違えがないことを確かめる。容量0の推論器（対局用PV-MCTSと照合が使う設定）では、キャッシュもバッチの中の重複の除去も行われないことを、重複する入力を含むバッチを、容量0の推論器と変更前の推論器の両方でCPUの実行プロバイダを使って推論し、出力が一致することで確かめる。
3. 学習器の前処理を改めた場合は、固定の局面集について、変更後の前処理が作る159面が変更前のRust拡張の出力とすべて一致することを確かめ、GPUのbf16で、PyTorchのコンパイラであるInductorのキャッシュを空にした状態から、同じGPUの枚数で止めて再開した学習が、止めずに通した学習とバイト単位で一致することを確かめる。

## 完了条件

- フェーズ5の工程の切れ目の時間の中央値が、フェーズ1の中央値の半分以下になっている。
- 自己対局のキャッシュと学習器の前処理の改善について、本書の基準による採否が決まり、採った変更の正しさが検証の手順で確かめられている。
- 測定記録、採った方式ごとのADR、および[強化学習の手引き](../guides/alphazero-training.md)の所要時間の見込みの改訂がそろっている。

# AlphaZero型探索の学習と自己対局生成の複数GPU化の設計書

## 先に読む要約

本書は、[AlphaZero型探索と深層強化学習の統括計画](../alphazero.md)のもとで、強化学習（RL）の1サイクルを、GPUを複数持つ1台の機械のすべてのGPUで回せるようにするマイルストーンの設計書である。
1サイクルは、前のサイクルのネットによる自己対局の生成と、直近のサイクルの局面をためたリプレイバッファからの学習からなり、今の生成器と学習器はどちらもGPUを1枚しか使わない。
[2回目の実行の設計書](../alphazero-rl-2.md)は、20ブロック256チャネルのネットを学習し、使う機械を1サイクルの料金で選ぶ。
vast.aiで借りる複数GPUの機械もその候補にできるように、本書の実装と測定を、その学習のサイクル1より前に終える。
学習器は、PyTorch Lightningの部品のうち、今の学習の手順をそのまま残せるLightning Fabric（以下Fabric）を使って、分散データ並列（DDP、GPUごとに同じネットを持ち、勾配を平均して全GPUで同じ更新をする方式）にする。
1回の更新に使う局面の数（全体のバッチ）は、GPUの枚数によらず1,024に固定し、GPUが少ない機械では、1回の更新の前に順伝播と逆伝播を複数回行って勾配を足し合わせる勾配累積（gradient accumulation）で、複数GPUのときと同じ更新を行う。
したがって同じ学習器が、GPU 1枚の機械（ColabのG4や作業機）でも、4枚のvast.aiの機械でも同じ設定で動き、借りた機械によって学習の規則が変わらない。
自己対局の生成器は、1つのプロセスの中で探索のスレッドをGPUに割り振り、GPUごとに推論器を持たせる。
サイクルの生成と学習を借りた機械で起動する実行器は、vast.aiの機械にも対応させ、生成器と学習器にGPUの枚数を渡せるようにする。
学習の順伝播には、PyTorchの実行時のコンパイル機能`torch.compile`を使い、その採否は速さ、再開の一致、および勾配の一致で決める。
完了条件は3つである。
作業機とvast.aiの4枚の機械で生成と学習が規則どおりに動き、GPUの枚数を1枚と4枚に変えて学んだネットの出力の差が定めた基準に収まること。
1サイクルを丸ごと回した時間と料金を、ColabのG4と並べて利用者へ示すこと。
そのうえで、試験とレビューを通してmasterへマージすることである。

## 目的

本書の目的は、複数GPUの機械を借りたときに、1サイクルの時間をGPUの枚数に応じて縮め、1サイクルの料金をColabのG4と比べられるようにすることである。

2回目の学習の20ブロック256チャネルのネットでは、ColabのG4の1サイクルは、生成約34分、学習約19分、固定分約8分で、合わせて約1時間、Colabの計算単位（CU）で約9 CUと見込まれている（2回目の設計書の「費用」の節）。
固定分は、リプレイバッファの読み込み、最終の重みの診断（学習を終えた重みで、訓練と検証の局面の損失と方策の一致率を求める処理）、およびネットの出力の照合（書き出したネットを生成器と同じ推論の経路で読み、PyTorchの出力と比べる処理）からなる。
CUの追加購入の価格は100 CUあたり9.99米ドルなので、1サイクルは約0.9ドルにあたる。
vast.aiでは、2026年11月9日の時点で、GPU 4枚の機械が、RTX 3090で1時間0.80ドル、RTX 4090で1.71ドル、RTX 5090で1.87ドルから出品されていた（貸し手の検証済み、信頼性98%超の出品）。
4枚のRTX 4090の機械がG4と同じ1サイクル約0.9ドルになるには、1サイクルを約31分（0.9÷1.71時間）で回す必要がある。

GPUを効率よく使うには、生成と学習の両方が全部のGPUを使う必要がある。
GPU 1枚あたりの料金が同じ機械で、生成と学習が枚数に比例して速くなり、固定分は縮まないと仮定して、上のG4の内訳で比べる。
1枚では1サイクルが約61分である。
生成と学習を4枚に分けると、1サイクルは約21分（34÷4＋19÷4＋8）になり、料金は4枚分の約21分なので1枚の約1.4倍になる（推論）。
学習だけを4枚に分けると、1サイクルは約47分（34＋19÷4＋8）で、料金は1枚の約3.1倍になる（推論）。
生成も複数GPUにする理由はこの差にある。

学習器をPyTorch Lightningへ移すこと、2回目の学習のサイクル1より前に入れること、および生成も複数GPUにすることは、2026年11月9日の利用者の決定である。
本書はLightningのうちFabricを使い、学習の手順を任せる部品のTrainerは使わない（「学習器の枠組み」の節）。
全体のバッチをGPUの枚数によらず固定し、GPUが少ない機械では勾配累積で補う方針は、2026年11月10日の利用者の決定である。

## 適用範囲

本書では、次の作業を行う。

- 自己対局の生成器に、使うGPUの枚数を受け取る必須の引数を加え、探索のスレッドをGPUに割り振る。
- GPUの照会（`nvidia-smi`でGPUの機種と容量を調べる処理）を、同じ機種のGPUを複数持つ機械でも動くように改める。
- 学習器を、FabricによるDDPと勾配累積で、GPUの枚数によらず同じ更新をする形に改め、各GPUのプロセスに局面を分けて読み込ませる。
- 学習の順伝播を`torch.compile`でコンパイルし、その採否を測定で決める。
- 実行器を改め、vast.aiで借りた複数GPUの機械で、生成、学習、および出力の照合をすべて回せるようにする。
- 作業機、vast.aiの機械、およびColabのG4で、規則どおりに動くこと、GPUの枚数を変えたときの一致、速さ、および1サイクルの時間と料金を測り、記録する。
- 標準レシピ、手引き、統括計画、および設計判断の記録（ADR、`docs/adr/`）を、新しい学習器と実行器に合わせて書き直す。

次の項目は対象外とする。

- 2回目の学習で使う機械の選択。本書の測定の結果を受けて、2回目の設計書の「費用」の節の規則で利用者が決める。
- 複数の機械にまたがる学習（multi-node）。1台の機械のGPUだけを使う。
- 進捗測定と到達の判定の対局。作業機の1枚のGPUで行う今の方式のままとする。
- 全体のバッチ、学習率、およびBatchNormの移動統計の更新の規則のほかの、学習の設定の変更。

### 学習器の枠組み（Lightning Fabric）

今の学習器は、学習ループを自前で持ち、強制終了から再開した学習が途中で止めない学習と出力のバイト列まで一致することを確かめている（[再開の方式のADR](../../adr/archive/resume-zero-training-from-the-update-count-over-a-seeded-permutation.md)）。
再開は、シードで固定した抽出の列と完了した更新の回数だけで読取位置を決め、読んだ順序をSHA-256の連鎖（`data_order_sha256`）で照合する。

LightningのTrainerは、学習ループ、チェックポイント、および再開をTrainerの側で持ち、2.6.6では次の3点がminaseの保証と食い違う（Lightningのタグ2.6.6、コミット771017e4）。
第1に、状態を保存できないデータローダでエポックの途中から再開すると、ローダーを作り直してエポックの先頭から読み直し、規定の回数で打ち切るので、先頭の局面を2回学び、末尾の局面を読まない（`src/lightning/pytorch/loops/fit_loop.py` 272〜276行、`training_epoch_loop.py` 212〜249行）。
第2に、既定の`use_distributed_sampler=True`では、独自の標本の並びを`DistributedSamplerWrapper`で包み、`PL_GLOBAL_SEED`と回数から作る順列で並べ替えてから各GPUへ配るので、minaseの抽出の列の順序が変わる（`src/lightning/pytorch/trainer/connectors/data_connector.py` 230〜244行）。
第3に、`bf16-mixed`の精度は`training_step`の全体をautocastで包むので、autocastを順伝播だけに掛ける今の範囲を保てない（`src/lightning/pytorch/strategies/strategy.py` 380〜391行、`src/lightning/pytorch/plugins/precision/amp.py` 114〜122行）。
これらを避けるには、ローダーの状態の保存、並びの分配、および精度の扱いをTrainerの拡張の仕組み（コールバックなど）の上で作り直すことになる。

Fabricは、学習ループを利用者のコードに残したまま、機器への配置、DDP、勾配の同期の制御（`no_backward_sync`）、集団通信、および複数プロセスの調整だけを受け持つ、Lightningの軽い層であり、単体のパッケージ`lightning-fabric`として配布されている。
本書はFabricを使い、抽出の列、各GPUへの分配、更新ごとの学習率、勾配のクリップ、損失の検査、チェックポイントの形式、および再開の照合を今の学習器の形のまま保つ。
精度は`32-true`とし、順伝播だけを今と同じく`torch.autocast`で包むので、損失の数値は今と変わらない。
KataGoはLightningを使わず、PyTorchのDDPを直接使う（KataGoのコミットd91ea855、`python/katago/train/trainloop_helpers.py` 150〜224行）。
直接使っても行数は大きく変わらないが、Lightningの導入は利用者の決定であり、Fabricはその範囲で今の保証を最も多く残す。

各GPUのプロセスは、`Fabric`を作り、引数なしの`fabric.launch()`を呼んでから`fabric.setup`でネットと最適化器を包む。
Fabric 2.6.6は、DDPで`setup`を呼ぶ前に`launch`が済んでいることを確かめ、済んでいなければ例外を出す（`src/lightning/fabric/fabric.py` 1193〜1201行）。
`torchrun`が起動したプロセスでは、`launch()`は子プロセスを作らず、分散の環境を初期化するだけである。
GPUが1枚でも`torchrun --nproc-per-node 1`とDDPを通すので、1枚と複数枚で学習器の経路は変わらない。

Fabricの既定値には頼らず、機器、GPUの枚数、分散の方式、精度、DDPの引数、および集団通信の待ち時間の上限を、`Fabric`と`DDPStrategy`の引数にすべて明示する。
minaseの学習器はPyTorch 2.11.0を使う（`tools/train/zero/uv.lock`）。
`lightning-fabric` 2.6.6の配布元の試験はPyTorch 2.10までしか試していない（`.github/workflows/ci-tests-pytorch.yml` 48〜62行）ので、2.11.0との組合せはフェーズ2の試験と作業機の確認で確かめる。

### 全体のバッチと勾配累積

全体のバッチを1,024、ミクロバッチを256とする。
学習器は、サイクルの初めに、リプレイバッファから学ぶ局面を一様に選び、その通し番号をシードで固定した順に並べた列（以下、抽出の列）を作る。
k番目の更新は、今と同じく抽出の列sの区間s[1024k : 1024(k+1)]を使い、これを先頭から4つのミクロバッチj = 0, 1, 2, 3に分ける。
GPUがN枚のとき、GPU rはj mod N = rのミクロバッチを番号の順に処理する。
各GPUの勾配累積の回数は4/Nであり、最後のミクロバッチを除く順伝播と逆伝播は、逆伝播のたびに行われるGPUの間の勾配の平均を一時的に止めるFabricのコンテキストマネージャ`fabric.no_backward_sync`の中で行い、勾配の平均を最後のミクロバッチの逆伝播だけで行う。
各ミクロバッチの損失は、そのミクロバッチの平均に勾配累積の回数の逆数N/4を掛けて逆伝播する。
ミクロバッチjの平均損失の勾配をg_jとすると、DDPはGPUの枚数で勾配を平均するので、平均した後の勾配は(1/N)×Σ_r Σ_{j mod N = r}(N/4)g_j = (1/4)Σ_j g_jとなり、どのNでも1,024局面の損失の平均の勾配に等しい。
ミクロバッチの中身はNによらないので、BatchNormの訓練時の統計も同じ256局面で計算され、更新の式はNによらない。
Nによる違いは、浮動小数点の加算の順序だけになる（BatchNormの移動統計は「BatchNormの移動統計」の節の規則でそろえる）。

1回の更新の処理は、各GPUのプロセスで行うものと、全体で1回だけ行うものに分かれる。

| 処理 | 扱い |
|---|---|
| 損失の非有限の検査 | 各GPUのプロセスが、自分のすべてのミクロバッチの各損失を検査し、1つでも非有限（NaNか無限大）なら学習全体を異常終了させる |
| 勾配のクリップと更新 | 勾配の平均が済んでから、全GPUのプロセスで、`clip_grad_norm_`（`error_if_nonfinite=True`）、学習率の設定、および`optimizer.step()`を1回ずつ行う。勾配も最適化器の状態も全GPUで同じになる |
| 累計標本数と学習率 | 全GPUのプロセスで同じ更新番号と累計標本数を使い、1回の更新の増分は1,024とする |
| 読んだ順序のハッシュ | 抽出の列の区間s[1024k : 1024(k+1)]を元の順に連鎖させる。各GPUの取り分をGPUの順に並べ直さない |
| 損失と学習曲線 | N/4を掛ける前の各ミクロバッチの平均の損失に256を掛けると、そのミクロバッチの局面ごとの損失の和になる。その更新の分を全GPUで和をとる（`all_reduce`の`sum`）と1,024局面の損失の和になり、これを全GPUのプロセスの累計に加える。累計を学んだ局面の数で割れば、今と同じ局面あたりの平均になる。Fabricの`all_reduce`の既定は平均なので、和を明示する |
| 保存と診断 | 更新の後、GPU 0のプロセスだけがチェックポイント、ONNX、および集計を書く。最終の重みの診断は、DDPを通さないラッパーの中のネットで、GPU 0のプロセスだけが行う |

再開したプロセスは、チェックポイントの累計の損失を全GPUで復元し、その後の更新の分だけを全GPUで和をとって加えるので、過去の累計をGPUの枚数倍に数えない。

全体のバッチを256のまま各GPUに64ずつ分ける案は採らない。
20ブロック256チャネルのネットでは、1回の更新ごとに約2,800万個の勾配（float32で約112 MB）を全GPUで平均する。
GPUごとに64局面では、その通信の時間が1回の更新の計算の時間と同程度になり、4枚にしても速さが4倍に届かない見込みである（推論）。
また、BatchNormの訓練時の統計を64局面で取ることになり、今の256局面より小さくなる。
dlshogiの開発者は、40ブロック512フィルタのネットで、1枚のGPUに載る小さいバッチでは時間がかかるうえBatchNormの影響で精度も落ちることを、8枚で学習した理由に挙げている（[40ブロック512フィルタの学習](https://tadaoyamaoka.hatenablog.com/entry/2024/06/07/224348)、2024年6月7日）。

GPUごとに256局面で全体の大きさを枚数とともに変える案は、借りた機械によって学習の規則が変わるので採らない。
KataGoの`-batch-size`とdlshogiのLightning版の`batch_size`はどちらもGPUごとの値であり、全体のバッチはGPUの枚数に比例する（KataGoの`python/train.py` 85行、dlshogiの`dlshogi/ptl.py` 237〜244行）。
dlshogiの開発者は、20ブロック256フィルタで、GPUごとのバッチを4096に固定して2枚と3枚にすると損失が上がり正解率が下がった一方、全体のバッチを4096に固定した2枚は1枚の0.53倍の時間で同じ損失になったと報告している（[DDPの記事](https://tadaoyamaoka.hatenablog.com/entry/2024/03/02/194650)、2024年3月2日）。
30ブロック384フィルタの8枚では、全体のバッチ4096で1枚の0.15倍の時間であった（[8GPUの記事](https://tadaoyamaoka.hatenablog.com/entry/2024/03/04/230906)、2024年3月4日）。
これは、全体のバッチを機械によらず固定する本書の方針と合う結果である。

Nを1、2、4に限るのは、4つのミクロバッチを等しく分けられる枚数だからである。
8枚の機械は、ミクロバッチの大きさか全体のバッチを変えない限り使えないので、本書では扱わない。

### 学習率

最適化器は、今と同じくネステロフのモーメンタム（0.9）つきの確率的勾配降下法（SGD）である。
全体のバッチを4倍にするので、基準の学習率を0.01から0.04へ4倍にする。
1サイクルの約400万標本に対する更新の回数は、約15,600回から約3,900回へ4分の1になる。
バッチをk倍にしたら学習率もk倍にし、学習の初めにウォームアップを置く線形スケーリング則は、GoyalらがモーメンタムつきのSGDで、バッチ8,192までのImageNetの学習を、バッチ256とほぼ同じ精度で再現した方式である（arXiv:1706.02677）。
この規則は更新の列が厳密に等しくなることを保証せず、バッチの大きさを変えた学習の近似である。
AlphaZeroは全体のバッチ4,096で学習率0.2から始めており、バッチ256あたりに直すと0.0125で、minaseの0.01と同じ程度の大きさである（Silverら、2018年）。
KataGoのSGDの学習は、学習率を1局面あたりの値で持ち、損失をバッチの和にしてGPUの枚数を掛けるので、1回の更新の大きさは全体のバッチに比例し、線形スケーリング則と同じ向きになる（KataGoの`python/train.py` 1238〜1249行、1733〜1734行）。
dlshogiの上の比較は、GPUの枚数を変えても学習率を変えていないので、全体のバッチを増やしたときに損失が上がったことは、学習率を比例させた場合の結果を示さない。
ウォームアップの長さは標本の累計で200万（約1,950回の更新）のまま、サイクル内のcosine annealingも今の式のままとする（[学習率のADR](../../adr/archive/warm-up-the-zero-learning-rate-and-anneal-it-within-each-cycle-without-comparing-a-constant-rate.md)）。

全体のバッチと学習率を変えて初期の学習が悪くならないかは、フェーズ4で確かめる。
同じ初期ネット、同じ教師データ（1回目のサイクル32の生成データ）、同じ抽出のシード、GPU 1枚、同じコンパイルの設定で、全体のバッチ256・学習率0.01と、1,024・0.04の学習を1サイクル分ずつ行う。
どちらも初期ネットから始め、最適化器の状態と累計標本数を同じ0から始める。
どちらも本書の学習器で行うので、使う局面の数はバッチの大きさの倍数への切り捨てにより最大768個違うが、1サイクルの約400万標本の0.02%未満なので、そのまま比べる。
学習に使っていない対局の価値の損失と方策の損失のそれぞれについて、1,024から256を引いた差の95%区間を、対局単位の対応のあるブートストラップで求める（[教訓](../../lessons/compare-nets-with-paired-game-bootstrap.md)）。
劣ることを許す幅は0とし、2つの区間の上限がどちらも0以下なら、1,024は256に劣らないと判定する。
どちらかの区間の下限が0より大きければ1,024は劣ると判定し、どちらでもなければ判定できないとする。
1,024が劣る場合と判定できない場合は、結果を添えて利用者に諮る。
この比較は1サイクルの初期の学習の確認であり、長い学習の強さを保証するものではない。

### サイクルの端数

今の学習器は、1サイクルの更新回数をceil(抽出数/256)とし、最後の更新を端数のバッチで行う。
本書では、抽出数をS、使う局面の数をM = 1,024×floor(S/1,024)とし、抽出の列の先頭M個だけを使う。
端数の局面（多くとも1,023個、1サイクルの抽出数約400万の0.03%未満）は、そのサイクルでは使わない。
KataGoも、各GPUの取り分を「更新回数×GPUの枚数×バッチ」の整数倍に切りそろえ、端数の行を捨てる（`python/katago/train/data_processing_pytorch.py` 50〜72行）。
端数を捨てるので、すべての更新がちょうど1,024局面になり、すべてのミクロバッチがちょうど256局面になる。
そのため、どのGPUにも各更新で同じ数のミクロバッチが行き渡り、`torch.compile`が受け取る入力のテンソルの形状が最後まで変わらないので、形状の変化による再コンパイルを避けられる。

チェックポイントと学習の集計`summary.json`の記録の欄は、次のように定める。
`sample_count`と`sample_sha256`は、今と同じく抽出の列の全体（S個）を表す。
`total_steps`はM/1,024、学んだ局面の数の記録`positions_seen`は1,024×`completed_steps`、累計標本数`samples_seen`は`samples_seen_start`＋`positions_seen`とする。
今の学習器の再開の照合は`total_steps`がceil(`sample_count`/バッチ)に等しいことを求める（`tools/train/zero/minase_zero/train.py` 613〜616行）ので、この照合を新しい定義に合わせて改める。
Sが1,024未満なら、更新が1回もできないので、学習の開始時にエラーにする。

### BatchNormの移動統計

BatchNorm（バッチ正規化）は、各層の出力を、訓練時にはそのバッチの平均と分散で正規化し、推論時には訓練中の値の指数移動平均（移動統計）で正規化する。
移動統計は、推論と、推論用に書き出すONNXの形式のネットに使う値であり、訓練時の正規化には使わない。
今のネットの移動統計は、PyTorchの既定のmomentum 0.1で、順伝播のたびに更新される（`tools/train/zero/minase_zero/net.py` 20〜23行）。

勾配累積とDDPをそのまま使うと、移動統計がGPUの枚数によって変わる。
1回の更新の前の移動平均をm、4つのミクロバッチの平均をμ_0〜μ_3とすると、1枚では4回の順伝播で更新されて0.9⁴m＋0.1(0.9³μ_0＋0.9²μ_1＋0.9μ_2＋μ_3)になり、4枚のGPU 0では1回だけ更新されて0.9m＋0.1μ_0になる。
これでは、追随の速さも初期値の残り方も、GPUの枚数によって違う。

そこで、各更新の移動統計は、最初のミクロバッチj = 0だけで更新する。
各GPUのプロセスは、j ≠ 0のミクロバッチの順伝播の前に、各BatchNormの移動平均、移動分散、および`num_batches_tracked`を複製して退避し、そのミクロバッチの逆伝播が終わってから次の順伝播までに、`torch.no_grad()`の中で元の値を書き戻す。
順伝播の直後、逆伝播の前に書き戻すと、逆伝播が使う保存済みのテンソルの版が変わって逆伝播が失敗することを、2026年11月10日にPyTorch 2.11.0のCPUで再現した。
j = 0はいつもGPU 0の担当の中で番号が最初のミクロバッチなので、保存するGPU 0の移動統計は、どのNでも1回の更新ごとに0.9m＋0.1μ_0で更新される。
4枚のときにGPU 0が自分のミクロバッチだけで移動統計を更新するのは、KataGoが保存するランク0の統計と同じ形であり（`trainloop_helpers.py` 175〜183行）、本書はそれを1枚と2枚にも当てはめる。
移動統計の退避と復元は、コンパイルした順伝播の外で、バッファの型、形状、および置き場所を変えずに値だけを書き戻す。

PyTorchのDDPは、既定（`broadcast_buffers=True`）では各順伝播の前にGPU 0の移動統計を他のGPUへ配る（PyTorch 2.11.0の`torch/nn/parallel/distributed.py` 558〜560行）。
GPU 0の移動統計は配る元なので、配る通信の有無で値は変わらない。
保存するのもGPU 0の値なので、KataGoと同じく`broadcast_buffers=False`として、この通信を省く。
SyncBatchNormは、全GPUの統計を順伝播のたびに同期するので、1枚の勾配累積の256局面ごとの統計と同じ値にはならず、Nによらない学習という目的に合わない。

この規則で、1回の更新の式は、重みの更新も保存するGPU 0の移動統計の更新もNによらなくなり、N=1とN=4の違いは浮動小数点の加算の順序による丸めだけになる。
ただし、その丸めの差は次の更新の重みに入って積み重なるので、学習を続けた後の重みと移動統計が完全に一致するわけではない。
その影響の大きさは、フェーズ4で、同じ初期値と同じ教師データから1サイクル分学んだN=1とN=4のネットについて、照合用の固定局面集の推論の出力をfloat32で比べて確かめる。
受け入れの基準は、TensorRTのFP16の推論の照合で許している差（合法手の確率の差1×10⁻²、価値の差5×10⁻²、[照合の許容誤差のADR](../../adr/compare-fp16-zero-network-values-within-five-hundredths.md)）とする。
対局に使う推論では、TensorRTのFP16の出力がPyTorchのfloat32からこの大きさまでずれることを許しているので、Nによる差がそれより小さければ、対局で使うネットの出力のぶれの範囲に収まる。
この基準は、同じネットの推論の経路の違いに許している大きさを借りた暫定の目安であり、2つのネットが対局の上で同じ強さであることを示すものではない。
収まらない場合は、結果を添えて利用者に諮る。

### 局面の保持

今の学習器は、リプレイバッファの全ファイルの対局の手順をたどって局面を復元し（以下、再生）、抽出した局面と診断の局面だけを保持する（`tools/train/zero/minase_zero/data.py` 277〜300行）。
抽出の列から重複を除いた通し番号の昇順の配列で保持し、更新のたびに抽出の列の各位置をその配列の行番号へ引き直す（`train.py` 638〜640行）。
1回目のサイクル32では、リプレイバッファの2,838万局面のうち385万局面を保持し、読み込みの最大常駐メモリは5.15 GBであった（NASの`cycles/cycle-0032/train/summary.json`）。

本書では、各GPUのプロセスが同じ規則で抽出の列を作り、使う先頭M個の位置のうち自分のミクロバッチに入る位置を先に決め、その位置の通し番号から重複を除いて保持する。
同じ局面が複数回抽出されて別のGPUに割り当たることもあるので、割り当ては局面ではなく抽出の列の位置で決める。
各プロセスは、元の通し番号と自分の配列の行番号の対応を持つ。
KataGoも、各GPUのプロセスが同じファイルを読み、展開の前に自分の取り分の行だけを選ぶ（`data_processing_pytorch.py` 50〜72行）。

GPU 0のプロセスは、最終の重みの診断に使う局面も保持する。
訓練の局面の診断は、抽出した局面のうち対局のハッシュで選んだ対局に属するもの（今の`training_sample`）を使う。
これらの局面は抽出の列のどの位置にもあり得るので、GPU 0の取り分だけでは足りず、ほかのGPUの取り分にもまたがる。
そのため、Rustの拡張モジュールの読み込みの関数（`tools/train/zero/mnsd_reader/src/lib.rs` 367〜389行の`read_selected`）に、診断の対局の訓練局面も保持する指定を加える。
検証の局面はGPU 0のプロセスだけが保持し、ほかのプロセスに検証の局面を要求する今の検査（`train.py` 525〜533行の`_counts`）は改め、記録する件数は各プロセスの件数ではなく全体の件数とする。
診断のバッチは全体のバッチと分け、今と同じ256局面とする。

メモリの合計は、プロセス数倍にはならないが、1枚のときと同じにもならない。
リプレイバッファの訓練局面の数Tが抽出数Sより少ないサイクルでは、局面の順列を複数回つないで抽出の列を作るので、同じ局面が複数のGPUに保持される。
1サイクルの抽出数Sは、そのサイクルで生成した訓練局面の数の4倍であり（[リプレイバッファのADR](../../adr/sample-four-times-from-a-zero-replay-buffer-of-ten-times-the-parameter-count-from-cycle-3-after-cycle-13.md)）、リプレイバッファがそのサイクルだけの最初のサイクルではS = 4Tになる。
端数を除いて概算すると、各局面を4回抽出するこのサイクルでは、4枚で保持する訓練局面の合計は、重複を除いた全体の約2.73倍（4×(1−(3/4)⁴)）になり、S = 2Tでは約1.75倍（4×(1−(3/4)²)）になる（推論）。
T ≥ Sのサイクルでは、抽出による重複はない。
これとは別に、GPU 0のプロセスは、ほかのGPUの取り分と重なる診断の局面を保持する。

今の読み込みは、各プロセスで使えるCPUの数だけ再生のスレッドを作る（`data.py` 277〜281行）ので、そのまま4つのプロセスにすると、CPUの数の約4倍のスレッドが動く。
各GPUのプロセスの再生のスレッドは、使えるCPUの数をNで割った数とする。
読み込みの時間はリプレイバッファの大きさに比例し、サイクル32の約2,800万局面で262秒であったので、上限の約2.8億局面では、CPUの数による並列化を除いて約10倍になり得る（推論）。
この時間は機械のCPUの割当てで変わり、料金に効くので、フェーズ4で機械ごとに測る。

### 再開

チェックポイントは、全GPUの勾配を平均して更新した後の重み、最適化器の状態、および更新回数を、GPU 0のプロセスだけが今と同じ形式で書く。
再開では、全GPUのプロセスが同じチェックポイントから重み、最適化器の状態、および記録を復元し、今と同じく完了した更新の回数から読取位置を決める。
同じ機械で同じNのまま止めて再開した学習は、途中で止めない学習と出力のバイト列まで一致することを確かめる。
`torch.compile`の採否の2つ目の条件で、利用者が許容誤差による一致を認めた場合は、その決定、比べる値、および許容誤差を測定記録に書き、以後の再開の確認もその基準で行う。
別の枚数の機械で再開した学習は、更新の式は同じだが加算の順序が変わるので、バイト列は一致しない。
これは今でもGPUの機種を替えて再開すると起きることであり、許容する。
今の学習器が書いた途中のチェックポイントは、全体のバッチと記録の欄の定義が違うので、新しい学習器では再開せず、明示的なエラーにする。
2回目の学習は新しく作る初期ネットから始めるので、この制限は2回目の学習の妨げにならない。

### 自己対局の生成器

今の生成器は、1つのプロセスの中で複数の探索のスレッドを動かし、スレッドごとに推論器を1つ持ち、対局番号を全スレッドで共有する原子的なカウンタから取る（[葉をまとめて推論するADR](../../adr/batch-zero-self-play-leaves-across-many-games.md)）。
対局は、決まった数の対局ずつの塊にまとめて確定する。
塊の確定、生成を止める規則、および再開は、このカウンタと出力先の塊のファイルだけで決まる（[塊の確定のADR](../../adr/commit-zero-self-play-in-fixed-game-chunks-up-to-the-first-prefix-reaching-the-target-positions.md)）。
本書は、スレッドtの推論器をGPU t mod Nに置くだけにとどめ、塊、停止、再開、およびシードの規則を変えない。
対局のシードは基本シードと対局番号から導く（`crates/minase/src/bin/minase/zero_selfplay/game.rs` 109〜110行）ので、同じ基本シードと対局番号の対局は、Nによらず同じシードを使う。
着手まで同じになるとは限らない。推論のバッチの組み方がNで変わり、FP16の推論の丸めが変わり得るからである（推論）。
ONNX RuntimeのTensorRTとCUDAの実行プロバイダは機器の番号を受け取るので（ortクレート2.0.0-rc.13の`with_device_id`、引数は`i32`）、推論器を作るときに番号を渡す。

GPUごとに生成器のプロセスを起動して塊を分け合う案は採らない。
今の生成器は1つの出力先を1つのプロセスだけが使うようにロックし、生成を止める規則は、塊0から連続して確定した塊を見渡す必要がある。
プロセスの間で塊を分け合うには、塊の取り合いと停止の判定をファイルの上で作り直すことになり、変更が大きい。

起動引数には、使うGPUの枚数`--devices <N>`を必須の引数として加え、`--threads`はNの倍数でなければ起動を拒む。
CPUの探索の量はスレッド数に比例するので、GPUあたりのスレッド数は今の4を出発点とし、フェーズ4の測定で決める。

### GPUの照会とTensorRTのキャッシュ

TensorRTの実行プロバイダは、GPUの機種名とメモリの容量を、ネットの検査和と最大バッチと合わせて鍵にし、作ったエンジンをキャッシュする（`crates/minase/src/nn/tensorrt_cache.rs`）。
今の照会は`nvidia-smi`の出力がちょうど1行であることを求め、2枚以上の機械では起動を拒む。
`nvidia-smi`は`CUDA_VISIBLE_DEVICES`を無視し、作業機で変数を空や存在しない番号にしても1枚のGPUを表示した（2026年11月9日に確かめた）。
一方、PyTorchとONNX Runtimeは`CUDA_VISIBLE_DEVICES`に従う。

本書では、GPUの照会と、推論に使う機器の番号の決め方を分ける。
照会は、`nvidia-smi`の全GPUが同じ機種名と容量であることを確かめて、GPUの枚数と、その機種名と容量を返し、機種が混ざっていればエラーにする。
推論に使うCUDAの機器の番号は、生成器ではスレッドtにt mod Nとし、出力の照合に使う`minase dev nn-eval`などほかのサブコマンドでは0とする。
生成器は、照会したGPUの枚数がNと等しいことも確かめる。
すべて同じ機種なので、`nvidia-smi`の番号とCUDAの番号の並びが違っても鍵は変わらない。
`CUDA_VISIBLE_DEVICES`が設定されていれば（空の文字列を含む）、`nvidia-smi`の見るGPUとONNX Runtimeの見るGPUが食い違い得るので、GPUを使うサブコマンドは起動を拒む。
同じ鍵のエンジンは、プロセスの中で推論器を1つずつ作る今の手順により、最初の推論器が作り、残りはキャッシュから読む。
TensorRTのエンジンはGPUの機種ごとに作るものなので、同じ機種の別の番号のGPUでも同じエンジンを読めるという前提に立つ。
作業機はGPUが1枚なのでこの前提を確かめられず、フェーズ4の4枚の機械で確かめる。

### torch.compile

[ふかうら王の学習](https://github.com/yaneurao/YaneuraOu/wiki/%E3%81%B5%E3%81%8B%E3%81%86%E3%82%89%E7%8E%8B%E3%81%AE%E5%AD%A6%E7%BF%92)（YaneuraOuのwikiのコミット87d9c8c2、2026年11月3日版）の「学習の基本その14」は、dlshogiの学習器で`torch.compile`を使うと学習が約1.6倍速くなると書く。
dlshogiの測定は、20ブロック256フィルタのResNetにTransformerを加えたモデルを、バッチ4096、bf16で学習したものである（[記事](https://tadaoyamaoka.hatenablog.com/entry/2026/05/09/210912)、2026年5月9日）。
[1回目の実行の設計書](alphazero-rl.md)は、2026年10月29日の利用者の決定でこれを導入し、採否をGPUの実機で決めるとしていたが、測らないまま1回目の学習を中断した。

コンパイルするのは、dlshogiの学習器（DeepLearningShogiのコミット26bbc67b、`dlshogi/train.py`と`dlshogi/network/policy_value_network.py`の`compile_model`）と同じく、ネットの順伝播だけとする。
損失の計算、最終の重みの診断、およびONNXの書き出しはコンパイルしないまま実行する。
診断は評価モードで動き、BatchNormの計算が学習時と違うので、同じ関数を通すと別のコンパイルが起きるからである。
DDPは`forward`の呼び出しで勾配の同期を準備するので、学習用の全出力を返す順伝播を`forward`に持つ薄いラッパーの`nn.Module`でネットを包み、そのラッパーに`torch.compile(..., fullgraph=True)`を掛ける。
これを`fabric.setup(..., _reapply_compile=False)`に渡し、コンパイルしたラッパーをDDPの内側に置く。
Fabric 2.6.6の`setup`は、既定ではコンパイルを外してDDPで包み、DDPの外側にコンパイルを掛け直す（`src/lightning/fabric/fabric.py` 229〜289行）。
PyTorch 2.11.0のDDPの`forward`には、コンパイルの対象から明示的に外した前処理があるので（`torch/nn/parallel/distributed.py` 1507〜1512行の`_inside_ddp_forward`）、外側をそのまま1つのグラフにできる前提には立たない。
`_reapply_compile`は名前が下線で始まる引数なので、Fabricの版を上げるときに動作を確かめ直す。
この配置には代償がある。
コンパイルした逆伝播は1つのグラフとして最後にまとめて勾配を返すので、DDPが勾配のまとまりごとに逆伝播の計算と重ねて行う全GPUの平均の通信（20ブロック256チャネルでは1回の更新あたり約112 MB）が、逆伝播の後にまとめて行われ、計算と重ならなくなる（推論）。
DDPの外側でコンパイルしたときにPyTorchがグラフを勾配のまとまりの境目で分けるのは、この重なりを保つためである（`torch/_dynamo/backends/distributed.py`）。
この代償の大きさは、フェーズ4で、4枚の機械のコンパイルの有無の学習の時間として測り、採否の1つ目の条件で判断する。
チェックポイントとONNXには、ラッパーの中のネットの重みを今と同じ名前で書く。
コンパイルの回数と時間は、フェーズ4で測る。

KataGoは、コンパイルのキャッシュの有無でGPUごとのプロセスが最初の集団通信に数分ずれて着くので、集団通信の待ち時間の上限を既定の約10分から1時間に延ばしている（`python/train.py` 264〜274行）。
本書でも、`DDPStrategy`の`timeout`を1時間と明示する。
`fullgraph=True`は、グラフが途中で切れたときに遅い経路へ移らず、エラーで止まるようにするために付ける。
モードは既定とし、dlshogiの記事が手元でエラーになったと書く`max-autotune`は使わない。

学習器は順伝播だけをbf16のautocastの中で呼び、逆伝播はその外で呼ぶ。
一方、PyTorch 2.11.0の既定（`torch._functorch.config.backward_pass_autocast="same_as_forward"`）は、コンパイルした区間の逆伝播も順伝播と同じautocastの下で走るとみなしてトレースする（`torch/_functorch/config.py`、`_aot_autograd/graph_capture_wrappers.py`）。
そこで、コンパイルした順伝播は`backward_pass_autocast="off"`を有効にした状態で呼び、逆伝播の計算をコンパイルしない実行と同じにする。

1局面の順伝播の計算は、20ブロック256チャネルでは、残差ブロックの3×3の畳み込み40層が256×256×9×144回の積和をそれぞれ行うので約34億回の積和、約6.8 GFLOPであり、10ブロック128チャネル（約0.94 GFLOP）の約7倍である。
[実現性の測定](../../measurements/alphazero-environment/alphazero-feasibility.md)では、補助ヘッドを持たない旧構成の20ブロック256チャネルのbf16の学習は、G4で毎秒6,720局面、L4で毎秒1,371局面であった。
`torch.compile`は、BatchNorm、ReLU、および残差の加算のような要素ごとの計算を1つのカーネルにまとめ（カーネルの融合）、GPUのメモリの読み書きとカーネルの起動の回数を減らし、順伝播と逆伝播のPythonの処理も減らす。
CPUでのバッチの準備や損失の検査の同期の時間は、コンパイルしない部分にあるので縮まない。
1回目の10ブロック128チャネルの学習では、L4の実測は毎秒3,695標本で、実現性の測定の旧構成の10ブロック128チャネル（L4で毎秒7,426局面）の半分ほどであった。
2つの測定は補助ヘッドの有無とバッチの準備の有無が違うので、この差の原因は切り分けられていないが、CPUでのバッチの準備などコンパイルの効かない時間が大きかった可能性がある（推論）。
20ブロック256チャネルでは、GPUの計算が約7倍に増える一方、CPUでのバッチの準備の時間は1局面あたりでネットの大きさによらずほぼ同じなので、コンパイルの効く部分の割合が大きくなり、`torch.compile`の効果は10ブロック128チャネルより大きいと見込む。
これは測定の前の仮説であり、効果の大きさはフェーズ4で測る。

採否の条件は3つとする。
1つ目は、初回のコンパイルを含めた1サイクルの学習の時間が、コンパイルしないコミットより短いことである。
2つ目は、同じ機械で同じNのまま途中で強制終了して再開した学習が、途中で止めない学習と、`model.onnx`のバイト列と、チェックポイントに保存した重み、最適化器の状態、更新回数、累計標本数、読んだ順序のハッシュ、学習曲線、および診断の値まで一致することである。
ONNXは推論用の出力だけを含み、補助ヘッドと最適化器の状態を含まないので、チェックポイントの値も比べる。
以前、GPUの`scatter_add_`が実行ごとに加算の順序を変えて、この一致を一度崩した（[再開の確認](../../measurements/alphazero-restart-techniques/alphazero-restart-techniques-resume-check.md)）。
torch.compileの既定のモードは、BatchNormの統計や大域プーリングの総和をTritonのカーネルにし、その設定を実行時に測って選ぶことがあるので、プロセスごとに選択が変わると丸めも変わり得る（推論）。
そこで再開の確認では、途中で止めない学習、強制終了した学習、および再開した学習の3つのプロセスに、それぞれ空のコンパイルのキャッシュを与える。
3つ目は、同じ重みと同じミクロバッチの勾配を、コンパイルしない実行のbf16、コンパイルした実行のbf16、およびコンパイルしない実行のfp32で求め、コンパイルの有無による勾配の相対誤差が、同じ確認で測るbf16とfp32の間の相対誤差より小さいことである。
学習器はbf16の学習をすでに使っているので、bf16とfp32の間の差は、今の学習がすでに受け入れている大きさである。
相対誤差は、全パラメータのクリップする前の勾配を並べたベクトルの差のノルムを、コンパイルしない勾配のノルムで割った値とする。
再開の一致だけでは、途中で止めない学習と再開した学習が同じ誤った計算をしている場合を見つけられないので、3つ目の条件を加える。

3つの条件をすべて満たせば採用する。
1つ目を満たさなければ、コンパイルのコミットを戻す。
2つ目か3つ目を満たさなければ、許容誤差で一致とみなすかを含めて利用者に諮り、その決定に従って採用するか戻す。

### 実行器とvast.aiの機械

今の実行器`minase_zero run-cycles`は、作業機で動き、借りた機械の上で生成、学習、および出力の照合を順に起動して、確定したファイルをNASへ受け取る（`tools/train/zero/minase_zero/runner.py`）。
接続はColabの`colab ssh`を中継に使うSSHに固定され、借りた機械の作業場所は`/content/az`と`/content/src`であり、次のサイクルを始めるかは終了期限と`colab usage`のCUの残高で決める。
機械を借りることと止めることは実行器の役目ではなく、起動スクリプト（1回目では`docs/measurements/alphazero-rl/alphazero-rl-sessions/launch-session.sh`）が、Colab機を借りて実行器を走らせ、終了コードによらず止める。
[借りる機械の操作の手引き](../../guides/alphazero-machines.md)の7節は、レンタル機について、事業者が公開するUbuntuとCUDAのイメージに`tools/train/zero/setup.sh`で環境を導入すること、vast.aiの公式CLI`vastai`で操作し、中継を通らないSSHのrsyncで転送すること、貸出期限の前に処理と転送を終えること、および作業を終えたら機械を削除することを定めている。
本書の実行器と起動スクリプトは、これらの規則に従う。

実行器には、機械の種類を選ぶ必須の引数`--machine colab|vast`を加える。
`vast`では、vast.aiのインスタンスの番号を必須の引数で受け取り、起動の時点で`scripts/vast/common.py`の`ssh_address`で公開IPとSSHのポートを1回だけ照会し、vast.ai専用の鍵`~/.ssh/id_vastai`と1本の共有の接続（ControlMaster）で操作する。
今の実行器は、作業場所`/content/az`、ソース`/content/src`、およびキャッシュ`/content/cache`を固定し、学習器、エンジン、および照合の局面集の場所（`SOURCE`、`ENGINE`、`FIXTURE`）をソースの場所から書いている（`runner.py` 85〜87行、471行、738行）。
vast.aiでは、作業場所を`/workspace/az`、ソースを`/workspace/src`、キャッシュを`/workspace/cache`とし、学習器、エンジン、および局面集の場所は機械の種類ごとのソースの場所から導く。
転送は、今と同じ一括のrsyncと検査和の照合を、この接続の上で行う。
生成と学習の起動、終了コードの確認、確定したファイルの受け取り、およびNASに記録した工程を機械を替えても繰り返さない規則は、機械の種類によらず今のままとする。

GPUの枚数は、実行器が最初のサイクルの前に借りた機械の`nvidia-smi`で数え、全GPUが同じ機種であることを確かめて、機械の記録に機種、枚数、CPU、および使えるCPUの数を残す。
生成器のスレッド数は、GPUあたりのスレッド数を実行器の必須の引数で受け取り、GPUの枚数を掛けて`--threads`に渡し、`--devices`にはGPUの枚数を渡す。
学習器は`torchrun --nproc-per-node N`で起動し、出力の照合はGPU 0で行う。
使えるCPUの数Cは、cgroupのCPUの割当てから、`cpuset`のCPUの数と、`cpu.max`の割当て（上限がある場合は割当て÷周期の切り捨て）の小さいほうとして求める。
生成器のスレッドの総数（GPUあたりのスレッド数×GPUの枚数）がCを超えれば、実行器は生成を起動せずにエラーで止める。
学習器の各GPUのプロセスの再生のスレッド数はfloor(C/N)とし、CがNより小さければ学習を起動せずにエラーで止める。
cgroupの割当てを使うのは、手引きの7節が定めるとおり、vast.aiのコンテナでは表示されるCPUの数が割当てより多いことがあるからである。
SPSAでは、表示されたCPUの数から同時対局数を決めたので、割当てを超えて対局を並べ、所要時間の見込みが延びた（[SPSAの手引き](../../guides/spsa.md)の8節）。

次のサイクルを始めるかの判定は、機械の種類で分ける。
終了期限`--deadline`と1サイクルの見込みの分数`--cycle-minutes`は、どちらの機械でも必須とする。
見込みの分数は、2回目の設計書の起動の規則と同じく、1サイクルの見積もりにそのセッションで送るリプレイバッファの転送の時間を足し、約1.3倍の余裕を持たせた値とする。
Colabでは、今と同じく、現在の時刻に見込みの分数を足した時刻が終了期限以前で、CUの残高が1サイクルの見込みのCU（`--cycle-cu`）以上のときに始める（`runner.py` 272〜273行の`can_start`）。
vast.aiでは、現在の時刻に見込みの分数を足した時刻が終了期限以前のときに始め、`--cycle-cu`は指定できず、残高は照会しない。
vast.aiの口座の照会は、2要素認証のログインがほぼ毎日切れてHTTP 401を返し得るので（SPSAの手引きの8節）、長い学習の途中でこれに頼ると、学習と関係のない理由で止まるからである。
vast.aiの終了期限は、起動スクリプトが機械を作るときに決める自己停止の時刻と、出品の貸出期限の早いほうとする。
料金は、起動スクリプトがインスタンスごとに記録する。
記録するのは、作成時の出品の1時間あたりの料金、ディスクの保管料、1 TBあたりの転送料、作成、自己停止、停止、および削除の時刻、送受信したバイト数、最後の状態、およびそのインスタンスで回したサイクルの番号である。
vast.aiの料金は、稼働中の1時間あたりの料金のほかに、停止した後から削除までのディスクの保管料と、貸し手ごとの転送料（1 TBあたり4〜40米ドル、[vast.aiでの教師生成の設計書](../vast-selfplay.md)の「費用」の節）がかかる。
新しい機械へリプレイバッファの上限の約29 GBを送ると、転送料は約0.1〜1.2米ドルになる（推論）。
サイクルの記録は完了したサイクルにしか書かれず（`runner.py` 875〜898行）、途中で失われた機械の費用は残らないので、インスタンスごとの記録を別に持ち、サイクルの記録にはインスタンスの番号を残して対応づける。
導入、失敗、および再開に使った時間の費用も、インスタンスごとの記録から求める。
費用の上限は、SPSAと同じく、セッションの見積もりに余裕を加えた額だけを入金して自動補充を設定しないこと、機械が期限に自己停止すること、および作業を終えた機械を削除することで抑える（[SPSAの費用のADR](../../adr/limit-rented-spsa-costs-by-self-stop-deadlines-and-deletion-after-the-last-game.md)）。
回すサイクルの範囲は、利用者が承認した範囲を起動スクリプトの引数で与える。
本書のフェーズ4の測定では借りる前に料金を示して承認を得て、2回目の学習では機械を決めた後に、2回目の設計書の費用の規則で承認を得る。

vast.aiの起動スクリプトは、標準ライブラリだけのPythonで書き、`scripts/vast/common.py`の関数で、出品からの作成、起動とSSHの準備の確認、環境の導入とビルド、実行器の起動、および削除を順に行う。
作成するときは、`scripts/vast/onstart.sh`で自己停止の時刻を予約し、ディスクはリプレイバッファの上限の約29 GB、環境の約20 GB、およびサイクルの出力を置けるように100 GBとする（環境の大きさは推論であり、フェーズ4で確かめる）。
起動スクリプトは、作業機の側でも終了期限を見張り、期限を過ぎても機械が止まっていなければ停止を要求する。
SPSAの費用のADRも、機械の自己停止に加えて作業機の側で期限の超過を検知して停止を要求すると定めており、自己停止の要求自体が失敗して終わることもあるからである（`scripts/vast/onstart.sh` 11〜33行）。
実行器が終わったら、正常に終わったか異常で終わったかによらず、必要なファイルを受け取って検査和を確かめてから機械を削除する（[教訓](../../lessons/stop-rented-machines-before-waiting-for-a-decision.md)）。
最後の受け取りに失敗した場合は、機械を削除せず、受け取れていないファイルとインスタンスの番号を記録して異常で終わり、利用者に報告する。
SPSAの`scripts/vast-spsa/fetch.py`も、最後の取得に失敗したときは機械を操作しない（160〜163行）。
機械は自己停止の時刻まで動き続けるので、その間に受け取り直して検査和を確かめてから削除する。
削除が2要素認証の切れで失敗したときは、機械にSSHで入り、vast.aiがコンテナに渡す、そのコンテナだけを操作できる番号と鍵（PID 1の環境変数の`CONTAINER_ID`と`CONTAINER_API_KEY`）で停止を要求してから、利用者に認証し直してもらって削除する（SPSAの手引きの8節と同じ手順）。
停止した機械もディスクの課金が続くので、削除までを起動スクリプトの終わりとする。

接続が途中で切れた場合は、実行器は接続の再試行の後に異常で終わる。
接続が切れただけでは機械とその上のファイルが失われたとは限らないので、起動スクリプトは機械を削除せず、上の最後の受け取りに失敗した場合と同じく記録して報告する。
機械が失われたことを確かめてから、残った機械を削除する。
次の機械で同じ系列を起動し直すと、NASに確定した工程は繰り返さず、生成は確定済みの塊を送り直して欠けた塊だけを作り、学習はNASのチェックポイントから再開する。
次の機械のGPUの枚数が違っても、学習は「再開」の節の規則で続けられる。

vast.aiの機械を選ぶ条件は、GPUの枚数が1、2、または4で同じ機種であること、NVIDIAのドライバがCUDA 13に対応すること（版580以上）、中継を通らないSSHが使えること、貸出期限が承認したサイクルの範囲を回せる長さであること、および上のディスクを確保できることとする。
ドライバの条件は、学習器のPyTorch（2.11.0のCUDA 13.0版）と、生成器が使うONNX RuntimeとTensorRTが、どちらもCUDA 13の版だからである（[実現性の測定](../../measurements/alphazero-environment/alphazero-feasibility.md)の「道具と環境定義」の節）。
リプレイバッファの上限の約2.81億局面は、1局面約104バイトで約29 GBあり、新しい機械へ送るたびに転送の時間がかかる（2回目の設計書の「系列の置き場所と起動」の節）。
作業機からvast.aiの機械への転送の速さは測っていないので、フェーズ4で測る。

### 1サイクルの時間と料金の比較

2回目の設計書は、1サイクルの料金が最も安い機械を選ぶ。
生成と更新の速さだけを短く測っても、その選択には足りない。
1サイクルには、読み込み、初回のコンパイル、診断、チェックポイントとONNXの書き出し、新しいネットのTensorRTのエンジンの作成、および出力の照合も含まれ、今の学習器の`training`の時間は保存とONNXの書き出しを含まないからである（`train.py` 93〜99行）。
また、2回目の設計書のG4の見積もりは、補助ヘッドを持たない旧構成の速さの比から求めた推論である（2回目の設計書の「費用」の節）。

そこで本書では、vast.aiの4枚の機械とColabのG4で、同じコミットのコードと同じ条件の1サイクルを丸ごと回して比べる。
条件は、準備の設計書で作る補助ヘッドつきの20ブロック256チャネルの初期ネット、2回目の学習の事前学習の期間の開始局面（組み替えた初期配置）、同じ探索の設定、訓練局面の目標100万、および全体のバッチ1,024とする。
生成、読み込み、初回のコンパイル、更新、診断、保存と書き出し、エンジンの作成、照合、および転送の時間を、それぞれ記録する。
サイクル1のリプレイバッファは1サイクルだけで小さいので、読み込みの時間は、1回目のサイクル3〜31の生成データ（約2,984万局面、約3.1 GB）を読み込ませて別に測り、リプレイバッファの大きさに比例させて見積もる。
環境の導入と最初のリプレイバッファの転送の時間は、1回のセッションで回すサイクルの数で割って1サイクルに配る。
G4は1回のセッションが最長8時間で約7サイクルである。vast.aiの機械にはセッションの上限がなく、出品の貸出期限だけがあるので、仮定したセッションの長さを明記する。
4枚の機械を1台だけ測る場合、結論は測った出品とG4の比較に限る。
どちらを使うかは、その結果を見て利用者が決める。

### 着手時に補った決定

次の事項は本書の起案時に定めておらず、2026年11月10日の着手時にClaudeが決めた（利用者の決定ではない）。

生成器について、次のとおり決めた。

- `--nn-backend cpu`では`--devices`を1に限り、GPUを照会しない。CPUの推論には分ける機器がないからである。
- `CUDA_VISIBLE_DEVICES`の拒否は、TensorRTとCUDAの推論器を作る処理（`OnnxEvaluator::new`）で行う。これで生成器、`minase dev nn-eval`、およびMCTSのUSIエンジンのすべてに同じ規則が効く。生成器は、推論器を作る前の照会でも同じ検査を行う。
- `--devices`は、`--threads`と同じく実行の条件として扱い、保存する生成条件（`config.json`）には入れない。

学習器について、次のとおり決めた。

- ミクロバッチの大きさは、学習器の必須の引数`--micro-batch-size`で受け取り、実行器が定数の256を渡す。試験用の教師ファイルは訓練局面が643しかなく、ミクロバッチを256に固定すると試験で数十回の更新を学ばせられないからである。全体のバッチも、今と同じく実行器が引数で渡す。
- `train`は`torchrun`が起動したプロセスでだけ動き、`WORLD_SIZE`などの環境変数がなければ起動を拒む。
- 再生のスレッド数は必須の引数`--replay-threads`で受け取り、保存する設定にも再開の照合にも入れない。
- 診断の訓練標本は、抽出の列の先頭M個（端数で捨てた位置を除く）に現れる局面のうち、訓練標本の対局に属するものとする。学んでいない局面を訓練側の診断に混ぜないためである。
- 記録する`training_count`は先頭M個の通し番号から重複を除いた数、読み込みの秒数は全プロセスの最大、最大常駐メモリは全プロセスの和とし、来歴にサイクル開始時のプロセス数`world_size`を加える。メモリを和にするのは、機械のメモリの見積もりに使うからである。
- 教師ファイルのSHA-256を含む来歴は、GPU 0のプロセスだけが計算する。リプレイバッファの上限の約29 GBを、プロセスの数だけ読み直さないためである。
- GPU 0以外のプロセスは、最後の更新の後に分散のプロセス群を解放して終わり、GPU 0のプロセスが単独で診断と書き出しを行う。ほかのプロセスが診断の間に集団通信で待たないようにするためである。
- `torch.compile`には、本書の設計に加えて、Inductorの設定を2つプロセス全体で有効にする。1つ目の`emulate_precision_casts`は、融合した演算の間でもeagerと同じbf16の丸めを残す設定である。作業機のRTX 3060 Tiでは、これがないとコンパイルしたbf16の逆伝播で28,052,008個のパラメータのうち25,885,184個の勾配がNaNになった。コンパイルしないbf16、コンパイルしたfp32、およびInductorを通さない`aot_eager`のbf16は有限であった。大域プーリングの`amax`の逆伝播は最大値と等しい位置へ勾配を分けるので、丸めを省いて計算し直した値が保存したbf16の最大値と一致しなくなったと考えられる（推論）。2つ目の`deterministic`は、縮約のカーネルの構成を実行時の計測で選ばない設定である。これがないと、同じNのまま強制終了して再開した学習が、途中で止めない学習と重みまで食い違った。どちらの設定でも、作業機の学習の速さは変わらなかった（[作業機の測定](../../measurements/alphazero-multi-gpu/alphazero-multi-gpu-workstation.md)）。
- DDPの`find_unused_parameters`を`True`にして、最初の更新の後の勾配のバケットの組み替えを止める。vast.aiの4枚の機械で、再開した学習が再開した直後の区間から途中で止めない学習と食い違い、`True`にすると一致したからである。
- 記録にだけ使う方策の損失の値と、診断の合法手の確率の和は、GPUの原子的な加算（`scatter_add_`）をやめ、足す順序が決まった計算で求める。コンパイルしない学習器でも、再開した学習の学習曲線の1つの値が、float32の最後の1桁で食い違ったからである。勾配と重みはこの変更で変わらない。

実行器について、次のとおり決めた。

- `--session`はColabだけの必須の引数とし、vast.aiでは指定できない。vast.aiでは接続にも記録にも使わないからである。
- 生成器のスレッド数は、`--threads`を廃止して`--threads-per-gpu`で受け取る。
- vast.aiのセッションの区間の記録は残高の欄を持たず、`machine_kind`と`vast_instance`を持つ。Colabの区間の記録にも`machine_kind`を加える。

## 実装フェーズ

本書のブランチをmasterから切り、worktreeで実装する。
実装はcodexに委任し、GPUを使う確認はClaudeが作業機と借りた機械で行う（[教訓](../../lessons/run-gpu-training-outside-codex-sandbox.md)）。

### フェーズ1　生成器の複数GPU

- 生成器`minase data zero-selfplay`に必須の引数`--devices <N>`を加え、スレッドtの推論器をGPU t mod Nに置く。
- GPUの照会を「GPUの照会とTensorRTのキャッシュ」の節のとおりに改め、`minase dev nn-eval`などほかのサブコマンドは、同じ機種の複数GPUの機械でもGPU 0で動くようにする。
- 試験では、照会の出力の解析（1行、同じ機種のN行、機種の混在、行数とNの不一致、`CUDA_VISIBLE_DEVICES`の設定）と、`--threads`がNの倍数でない場合の拒否を確かめ、N=1の生成が今と同じ塊を書くことを作業機のGPUで確かめる。

### フェーズ2　学習器のFabric化とtorch.compile

[準備の設計書](alphazero-rl-2-prep.md)の完了の後に、masterを取り込んでから始める。

- 学習器をFabricで書き直し、「全体のバッチと勾配累積」「サイクルの端数」「BatchNormの移動統計」「局面の保持」「再開」の各節のとおりにする。
- 依存に`lightning-fabric==2.6.6`を加え、`tools/train/zero/uv.lock`を更新する。
- 基準の学習率を0.04、全体のバッチを1,024とし、ミクロバッチの256は固定の値とする。
- 試験では、CPUの2プロセス（`torchrun --nproc-per-node 2`、CPUの集団通信の方式gloo）とCPUの1プロセスで、同じ初期値と同じ教師データから数回の更新を学ぶ。読んだ順序のハッシュと記録の欄が一致し、学習するパラメータ、クリップする前の勾配、および最適化器の状態が、PyTorchの`torch.testing.assert_close`のfloat32の既定の許容誤差で一致することを確かめる。BatchNormの移動統計は、保存するGPU 0のプロセスの値を同じ許容誤差で別に確かめ、整数の`num_batches_tracked`は完全な一致で確かめる。
- 今のSIGKILLの再開の試験は、1プロセスと2プロセスの両方で保つ。
- 抽出数が1,024未満の場合と、今の学習器の途中のチェックポイントからの再開が、どちらも明示的なエラーになることを試験する。
- コンパイルは別のコミットで入れ、コンパイルしないコミットと比べられるようにする。

### フェーズ3　実行器のvast.ai対応

- 実行器に必須の引数`--machine colab|vast`とvast.aiのインスタンスの番号を加え、「実行器とvast.aiの機械」の節のとおりに、接続、作業場所、GPUの枚数の数え方、スレッド数とCPUの割当て、次のサイクルを始める判定、および料金の記録を機械の種類で分ける。
- 生成器の`--threads`の代わりに、GPUあたりのスレッド数を実行器の必須の引数とし、学習器を`torchrun --nproc-per-node N`で起動する。
- vast.aiの起動スクリプトを、標準ライブラリだけのPythonで書き、作成、導入、実行器の起動、受け取り、および削除を一続きに行う。1回目の`launch-session.sh`と同じく、起動スクリプトはそれを使う測定記録のディレクトリ（本書のフェーズ4では`docs/measurements/alphazero-multi-gpu/`、2回目の学習では2回目の設計書の測定記録のディレクトリ）に置き、vast.aiの操作は`scripts/vast/common.py`の関数を呼ぶ。
- 試験では、機械の種類ごとの引数の検査（vast.aiでの`--cycle-cu`の拒否を含む）、vast.aiの接続のコマンドの組み立て、作業場所とキャッシュの切り替え、`nvidia-smi`の出力からのGPUの枚数と機種の判定、cgroupの割当てからのCPUの数とスレッド数の上限による拒否、次のサイクルを始める判定、およびインスタンスごとの料金の記録を、外部のコマンドを置き換えて確かめる。
- 起動スクリプトの試験では、導入の失敗、最後の受け取りの失敗、接続の切断、自己停止の失敗と作業機の側の期限の超過、および削除のときの2要素認証の切れの各場合に、機械を削除するか残すかが本書の規則どおりになり、記録が残ることを、外部のコマンドを置き換えて確かめる。
- 借りる機械の操作の手引きの7節に、vast.aiの機械で学習のセッションを起動し、止め、削除する手順を加える。

### フェーズ4　測定と料金の比較

測定は`docs/measurements/alphazero-multi-gpu/`に記録する。

- 作業機（RTX 3060 Ti、1枚、`alphazero-multi-gpu-workstation`）：コンパイルの有無の勾配の比較、空のキャッシュでの再開の一致、および勾配累積を4回行う学習が最後まで動くこと。
- vast.aiのGPU 4枚の機械（`alphazero-multi-gpu-vast`）：生成、学習、および出力の照合を含む1サイクルを丸ごと回した各工程の時間、生成のGPUあたりのスレッド数、コンパイルの有無の学習の時間、同じN=4の再開の一致、N=1とN=4の推論の出力の差、全体のバッチ256と1,024の比較、約3,000万局面の読み込みの時間と最大メモリ、および作業機からの転送の速さ。
- ColabのG4（`alphazero-multi-gpu-g4`）：同じ1サイクルを丸ごと回した各工程の時間と、約3,000万局面の読み込みの時間。
- 測定の結果から、vast.aiの機械とG4の1サイクルの時間と料金を並べて利用者へ示す。

フェーズ4の費用は、各測定の回数と所要時間を積み上げて見込む。
vast.aiのRTX 4090の4枚の機械（1時間1.71ドル）では、導入約10分、約3.2 GBの転送約10分、1サイクル約30分、読み込みの測定約10分、コンパイルの有無の学習2回で約12分、N=1の学習約15分、全体のバッチの比較2回で約30分、および再開の確認約10分で、約2.5〜3時間、約5ドルと見込む（推論）。
G4（1時間8.90 CU）では、導入約5分、転送約10分、1サイクル約60分、および読み込みの測定約10分で、約1.5時間、約13 CUと見込む（推論）。
借りる前に、そのときの出品の料金を示して利用者の承認を得る。

### フェーズ5　移し替えとマージ

- 採った方式のADRを書き、置き換える旧ADR（再開の方式、学習率）を`docs/adr/archive/`へ移す。
- 深層強化学習を回す手引きの標準レシピとオプション一覧を書き直す。
- 試験とcodexのレビューを通し、利用者の許可を得てmasterへマージする。

## 検証

フェーズ1から3の試験が通り、作業機のGPUで、N=1の生成と、勾配累積を4回行う学習が最後まで動くことを確かめる。
フェーズ4で、vast.aiの4枚の機械で、生成と学習が全GPUを使い、出力の照合まで含む1サイクルが最後まで回り、同じNの再開が「再開」の節の基準で一致し、N=1とN=4の推論の出力の差が「BatchNormの移動統計」の節の基準に収まることを確かめる。

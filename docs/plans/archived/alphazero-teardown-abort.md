# AlphaZero型探索の推論で、終了処理での異常終了をなくす設計書

## 先に読む要約

本書は、[AlphaZero型探索と深層強化学習の統括計画](../alphazero.md)のもとで、ニューラルネットワーク（以下、ネット）の推論を使うプロセスが終了処理で異常終了する不具合を直すマイルストーンの設計書である。
`minase dev nn-eval`と自己対局の生成器は、出力を書き終えた後の終了処理で、glibcがヒープの破壊（`corrupted double-linked list`）を検出して異常終了することがある。
強化学習の1サイクルは、自己対局の生成、学習、および照合（書き出したネットの推論の出力を、`minase dev nn-eval`で学習器の参照と比べる工程）からなる。これらを順に起動する実行器（`minase_zero run-cycles`）は、0以外の終了コードを失敗として止まるので、この異常終了が起きる機械ではサイクルを回せない。
原因は、ONNX RuntimeのRustバインディングであるortクレートのrc.13が、ONNX Runtimeの環境（プロセスに1つの共有の設定。以下、環境）の解放を、実行中に読み込んだONNX Runtimeの共有ライブラリの静的デストラクタより後に走る`.fini_array`から呼ぶことである（[原因の調査の記録](../../measurements/adhoc/zero-teardown-abort-root-cause.md)）。
その結果、ONNX RuntimeのCUDAの実行プロバイダが静的変数に持つ登録表が、解放された後にもう一度手放され、解放済みのメモリが書き換わる。
方式は、ortをこの仕組みを持たないrc.15へ上げ、環境をプロセスの終了まで保持して解放しないことである。
rc.15はRust 1.92を要求するので、minaseの`rust-version`（ビルドできる最小のRustの版）を1.88から1.92へ上げる。
完了条件は、作業機で、gdbの検査が「`exit`に入った後に登録表を手放す関数が呼ばれない」ことを示し、同じプロセスで推論器を作り直せ、推論と生成の出力が変更の前と一致し、マージ前の検査が通ることである。

## 目的

本書の目的は、推論を使うプロセスが、機械やヒープの配置によらず、終了処理で異常終了しないようにすることである。
[2回目の強化学習の実行](../alphazero-rl-2.md)は借りた機械でサイクルを繰り返すので、生成器か照合が終了処理で異常終了すると、実行器がそこで止まる。
2026年11月11日の測定では、RTX 4090を4枚積んだ機械の1台で、4,096局の生成の25回中9回が異常終了した（[生成の速さの測定](../../measurements/alphazero-inference-transfer/alphazero-inference-transfer-generation-speed.md)の「終了処理での異常終了」）。

異常終了が観測されない機械でも、解放済みのメモリへの書き込みは実行のたびに起きている（原因の調査の記録の「現行の構成で起きていること」）。
そこで本書は、異常終了の回数を減らすことではなく、この書き込みをなくすことを目標にする。

## 適用範囲

対象は次のとおりである。

- `crates/minase/Cargo.toml`のortの版と`rust-version`、および`Cargo.lock`。
- 推論器の初期化（`crates/minase/src/nn/onnx.rs`）と、そのエラー型（`crates/minase/src/nn/error.rs`）。
- 版と終了処理に触れる文書（ADR、手引き、`README.md`）。

対象としないものは次のとおりである。

- ONNX Runtimeの実行時ライブラリの版。1.31.1のままとする（[ONNX Runtimeの版のADR](../../adr/load-onnx-runtime-1-31-1-through-ort-rc13-for-zero-inference.md)）。
- 推論の入出力の形と、実行プロバイダの選び方。
- `minase-core`の`rust-version`。ortに依存しないので1.88のままとする。
- 借りた機械での確認。次節の理由により、作業機だけで確かめる。
- ortクレートとONNX Runtimeの開発元への報告。

## 設計判断

| 項目 | 採った方式 | 棄却した代案と理由 |
|---|---|---|
| ortの版 | `=2.0.0-rc.15`に固定する。機能の指定は今の`std`、`load-dynamic`、`tensorrt`、`cuda`、`api-28`、および`half`のままとする | rc.13のまま、環境への参照を`std::mem::forget`で捨てて解放させない（ortが公開していない内部の持ち方に頼る回避策であり、開発元が同じ仕組みを取り除いた版がすでにある）。rc.14にとどめる（rc.15と同じ要求であり、新しい版を避ける理由がない） |
| `rust-version` | `crates/minase`を1.92へ上げる | 上げずに済ませる方法はない（rc.14以降は`rust-version = "1.92"`を宣言している） |
| 環境の寿命 | 推論器の初期化が作った環境を、プロセスに1つの静的変数に保持し、プロセスの終了まで解放しない | 推論器ごとに環境を持ち、最後の推論器の破棄で解放する（USIエンジンは実行プロバイダなどの設定が変わると推論器を破棄して作り直すので、同じプロセスで環境を2回作ることになる。rc.15の`build()`は、環境を1回作ったプロセスでは、その環境が解放された後でも2回目をエラーにする）。実行ファイルの入口が環境を持ち、推論器へ渡す（`process::exit`で終わる経路では解放されないので、経路によって終了処理が変わる。推論器を作るすべての呼び出しに引数が増える） |
| 修正の確かめ方 | gdbで、`exit`に入った後に登録表を手放す関数が呼ばれないことを確かめる | 異常終了の回数を数える（異常終了はヒープの配置に依存し、現行のコードは作業機で1回も異常終了しないので、修正の前後を区別できない） |

環境を解放しない方式では、プロセスの終了時に`ReleaseEnv`が呼ばれない。
原因の調査で観測した終了時の`Shutdown()`は、環境の破棄から呼ばれていたので、`ReleaseEnv`が呼ばれなければ、静的デストラクタより後のこの呼び出しはなくなり、登録表は静的デストラクタで1回だけ解放される。
ONNX Runtimeは、実行プロバイダの初期化が例外で失敗したときにも`Shutdown()`を呼ぶ（`provider_bridge_ort.cc`の`ProviderLibrary::Get()`）。これは終了処理の前に起きる正しい順序の解放なので、妨げない。
環境が生きたままプロセスが終わっても、ONNX Runtimeの側に環境を解放する静的デストラクタはない。`OrtEnv`は生のポインタで管理され、実行プロバイダのライブラリを表す`ProviderLibrary`のデストラクタは空である（`ort_env.cc` 30行、`provider_bridge_ort.cc` 1996〜1998行）。
環境が持つメモリは、プロセスの終了とともにOSが回収する。

ortのrc.15は、環境を`ort::init_from(path)?.build()?`が返す値として利用者に持たせ、セッションの作成に`Session::builder(&environment)`の形で渡させる。
セッションは環境への参照を持つので、環境は、利用者の値とすべてのセッションが破棄された時点で解放される。
rc.15のソースには、`.fini_array`にも`atexit`にも登録する処理がない。

rc.13では、環境の設定を`commit()`で確定していた。エラー型の`NnError::RuntimeAlreadyInitialized`は、環境がすでに設定済みのときに`commit()`が偽を返すことに対応していた。
rc.15の`build()`は、環境がすでにあるときに`ort::Error`を返すので、このエラーは既存の`NnError::Runtime`として伝わる。作る経路のなくなった列挙子は取り除く。
推論のモジュールはまだどのリリースにも含まれていないので、公開APIの互換性は問題にならない。

## 実装フェーズ

### フェーズ1　ortの版の引き上げと環境の保持

`crates/minase/Cargo.toml`のortを`=2.0.0-rc.15`に、`rust-version`を1.92にする。
推論器の初期化を、環境を静的変数に保持する形に書き換え、セッションの作成に環境を渡す。
初期化は排他ロックで直列化し、`build()`が成功した直後、セッションの作成のように失敗し得る処理より前に、環境を静的変数へ入れる。rc.15は2回目の`build()`を拒むので、作った環境を失敗の経路で手放すと、そのプロセスでは推論器を作れなくなるからである。
完了条件は、[マージ前の検査](../../guides/testing-minase-rules.md)の4つのコマンドが通り、Rust 1.92のツールチェーンで`cargo check --workspace --all-targets`が通ることである。

完了条件は、次節の4つの確認がすべて通ることである。

## 検証

確認は作業機で行う。
原因の書き込みは実行のたびに起き、gdbの下では決定的に観測できるので、異常終了が起きやすい機械を借りる必要はない。

1. **登録表の2回目の解放がないこと。** 原因の調査の記録の`probe.py`を、変更後の実行ファイルに当てる。CUDAとTensorRTの`minase dev nn-eval`、推論なしで終わる経路（入出力の形が合わないネットを渡す）、および自己対局の生成器の短い実行のそれぞれで確かめる。合格の条件は、gdbが`exit`の入口で止まること、その時点でCUDAの実行プロバイダのライブラリが読み込まれていて登録表の管理ブロックが生きていること、その後に登録表を手放す関数に届かないこと、およびプロセスが期待する終了コード（推論は0、入出力の形が合わない経路は1）で終わることである。シグナルによる終了とgdbのエラーは不合格とする。対照として、変更前の実行ファイルでは同じ関数に届くことを同じ手順で確かめる。
2. **同じプロセスで推論器を作り直せること。** USIエンジン（`--search mcts`）で、TensorRTで探索し、実行プロバイダをCUDAへ切り替えて探索し、TensorRTへ戻して探索し、バッチの大きさを変えて探索する。USIエンジンは設定が変わるたびに推論器を破棄して作り直すので、4回の推論器の作成がすべて成功し、エンジンが終了コード0で終わることを確かめる。環境を`exit`より前に解放する誤った実装は、1の確認を通ってしまうが、rc.15が2回目の`build()`を拒むので、この確認で見つかる。推論器の作成が失敗した後に同じプロセスで作り直す呼び出し元はないので（USIエンジン、`minase dev nn-eval`、および生成器は、失敗するとプロセスを終える）、失敗の経路は1の「入出力の形が合わないネット」の確認と、環境を静的変数へ入れる位置のコードの確認で確かめる。
3. **推論の出力が変わらないこと。** 変更の前後の実行ファイルで、CPU、CUDA、およびTensorRT（同じ保存済みのエンジンを読む）の`minase dev nn-eval`の出力のJSONを比べる。288局面をバッチ7で評価するので、推論は1回の実行で42回呼ばれる。バイト列が一致しない組は、`nn_compare.py`で実行器の照合と同じ許容誤差に収まることを確かめる。
4. **生成器の出力と速さが変わらないこと。** 自己対局の生成器を、変更の前後の実行ファイルで同じシードと引数で64局動かし、終了コードが0であること、生成した訓練データの検査和が一致すること、および生成の速さが同程度であることを確かめる。rc.15は、環境の扱いのほかに、`IoBinding`の入力の結び付けで条件によって入力を複製する処理と、セッションの作成時に入出力のメモリの情報を得る処理を加えているので、出力と速さの両方を見る。

## 完了条件

検証の4つの確認が通り、マージ前の検査が通り、決定がADRに移り、変更がmasterに入ったときに、状態を完了へ変える。

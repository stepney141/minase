# ファイル形式の整理と形式の仕様の整備の設計書

## 先に読む要約

minaseのコードがディスクに読み書きするファイル形式は36種類あり、そのうち`MN`で始まる独自のマジック（ファイル先頭の識別バイト列）を持つバイナリ形式が7種類ある。
形式が多い理由は3つある。下流に読み手のない形式が残っていること、同じ情報を複数のファイルへ重ねて書いていること、そして過去のファイルを読み続けるために、1つの形式に複数の版を併存させていることである。
教師データ（自己対局などの局面に教師の探索値と対局結果を付けた学習用のデータ）には、全体のSHA-256を記した付随ファイル（来歴JSON）を置き、読み込みのたびに照合している。
一方、独自形式の仕様は、読み書きするモジュールのdocコメント、凍結した設計書の本文、および2026年10月13日に廃止した`docs/reference/`に分かれて書かれてきており、その一部は現行の実装と食い違っていた。
本書は次の3つの原則で形式を整理する。各形式の版は1つだけにする。過去のファイルは読み続けない。`MN`の独自形式は3つに絞る。残すのは、教師データのMNSD、評価関数のニューラルネットであるNNUEの重みのMNUE、駒と升の点数表であるPSTと2駒の補正であるFMの重みのMNPTである。
そのために、来歴JSONと付け直し（保存済みの教師データを探索し直して別ファイルへ書く機能）を撤去し、学習器のチェックポイントは標準形式のNPZに置き換える。
残った形式は、その形式を読み書きするモジュールのdocコメントにバイト配置と欄の一覧として書き、以後は実装を変えるコミットで同時に直す。形式の一覧（名前、マジックと版、書き手、読み手、仕様を書いたモジュール）だけを手引き`docs/guides/file-formats.md`に置く。
完了条件は、`MN`の形式が7から3へ減り、どの形式も現行の版だけを受け付け、残った全形式の仕様がdocコメントにそろうことである。
エンジンの評価関数と探索は変えないので、棋力の測定は行わない。

## 状態

完了（採用）。2026年10月13日に起案と着手をし、同日に完了した。
教師データの来歴JSON、付け直し（MNRS）、3種のチェックポイントのマジック、およびMNPTの版2を廃止して、`MN`の独自形式をMNSD、MNUE、MNPTの3つにし、残った全形式の仕様を書き手のdocコメントに、形式の一覧を[ファイル形式の一覧](../../guides/file-formats.md)に置いた。
変更の前後で学習の局面数、教師用K、および損失がビット単位で一致し、チェックポイントの中断と再開も中断しない学習と一致することを[照合の記録](../../measurements/file-format-consolidation-equivalence.md)で確かめ、使えなくなった`data/`のファイル594件（約30 GB）を削除した。
設計判断は[由来の欄](../../adr/archive/record-the-origin-in-mnsd-records.md)、[版を1つにする原則](../../adr/archive/keep-one-version-per-file-format.md)、および[NPZのチェックポイント](../../adr/store-trainer-checkpoints-as-npz.md)のADRへ移した。

## 目的

利用者は2026年10月13日に、次の5点を指摘した。

- 教師データのSHA-256による照合は、将棋の教師形式（hcpeやPackedSfenValue）に比べて過剰である。
- ファイル形式が多すぎる。
- 独自形式の説明がdocs/に見当たらない。
- 同じ`MN`の形式に複数の版があり、`MN`の形式自体も多く分かれている。
- 過去のファイルを読み続けられるように保つのは、過剰な互換性の維持である。

そのうえで、付け直しの撤去、教師データの照合の廃止、PSTとFMの重みの1つの配置への統一、および使えなくなった古いデータの削除を決めた。
中将棋も指せるオンライン対局サイトlishogiの実戦棋譜の取り込み（`data lishogi games`と`data lishogi openings`）は残す。[AlphaZero型探索の設計書](../alphazero.md)が、自己対局の開始局面の半数をlishogiの実戦棋譜から取ると定めているからである。

形式や版が多いと、変更のたびに書き手、読み手、検査、文書をそろえる手間が増え、そろわなかった箇所が不具合や古い記述として残る。
現に[評価関数の設計書](evaluation.md)には、実装と合わない記述が3か所ある。MNUEのヘッダを版2の96バイトとして説明している箇所（現行のコードは版5の192バイト）、MNSDの`network_checksum`を`pst.bin`の検査和と説明している箇所（現行はNNUEの重みの検査和）、学習器が付け直しの値を使うと書いている箇所（現行の学習器は読まない）である。

本書で使う語を次のように定める。
MNSDは教師データの形式、MNUEはNNUE（評価関数のニューラルネット）の重みの形式、MNPTはPST（駒と升の組ごとの点数表）と、FM（2駒の位置関係を表す補正）の重みの形式である。
NPZは、NumPyの配列を名前つきで収めたZIP形式のファイルであり、学習器はすでに浮動小数点の重みの受け渡しに使っている。
チェックポイントは、学習を中断して再開するために学習器が保存するモデルと最適化器の状態である。
検査和は、ファイルの内容から計算するSHA-256の値である。
教師用Kは、探索値を勝率へ換算する尺度であり、教師データの分類ごとに訓練集合から推定する。
混合比λは、教師値を作るときに、探索値から換算した勝率と対局結果を混ぜる比である（`λ·勝率 + (1−λ)·結果`）。
検証分割は、約5%の対局を検証集合へ固定する割り当てであり、同じ対局の局面が訓練集合と検証集合にまたがらないよう、対局単位で割り当てる。
先読み教師値は、同じ対局の将来の探索値を幾何加重平均した教師値であり、その条件は割引率と窓幅である（[先読み教師値の設計書](lookahead-teacher.md)）。
SPSAは、対局の勝敗から探索の係数を自動で調整する手法（同時摂動確率近似）であり、`minase spsa`が実装する。
由来は、教師データの局面がどの経路で作られたかの区分であり、「MNSD」の節で定める。
診断は、学習器`minase-trainer`の`diag`サブコマンドであり、学習の入力や重みを調べて報告を書き出す。

## 原則

各形式の版は1つだけにする。
読み手は現行の配置だけを受け付け、複数の版を読み分けるコードを書かない。
版番号の欄を持つ形式では、その欄は古いファイルを誤読せずにエラーで止めるためだけに使う。

過去のファイルは読み続けない。
形式を変えるときは変換コマンドを作らず、読めなくなったファイルは必要になったときに生成し直す。
`crates/minase/nets/`に埋め込む重みのように、その時点でコードが必要とするファイルだけは、コードに残さない使い捨ての手順で書き直し、同じコミットに含める。

`MN`の独自形式は、エンジンが読む重みと、学習器が読む教師データに限る。
学習器の内部だけで使うファイルには、独自形式を作らず、NPZとJSONを使う。

## 適用範囲

形式の数は、ディスク上のスキーマ（バイト配置または欄の構成）ごとに1つと数える。
現在の36形式の一覧は、フェーズ0で手引き`docs/guides/file-formats.md`に書く。

本書が変えるのは次のものである。

- 教師データの形式、その書き手（`crates/minase/src/training/`、`crates/minase/src/datagen/`、`crates/minase/src/bin/minase/selfplay_gen/`、`crates/minase/src/bin/minase/lishogi_import/`）、および読み手（`crates/minase-trainer/src/data/`と診断）。
- MNPTの配置と、その書き手と読み手。
- 学習器のチェックポイント、学習の記録（`config.json`）、診断の記録が入力を識別する方法。
- `minase match report`が受け付ける実行ディレクトリの版。
- 形式を読み書きするモジュールのdocコメントと、形式の一覧の手引き。
- `data/`の、使えなくなったファイル。

次のものは変えない。

- MNUEの形式。読み手はすでに版5だけを受け付けている。重み本体の検査和は、教師データのヘッダに写して、教師データを生成した重みを区別する識別子として使っている。
- 対局ハーネスとSPSAの実行ディレクトリの形式と、`target/match-cache/`のバイナリの検査和。再開時に、対局するエンジンが記録と同じであることを確かめる仕組み（[測定の再開条件の簡素化](match-resume-simplification.md)）の一部であり、過去のファイルとの互換のためのものではない。
- 学習器と診断が出力するだけで読み返さない報告のJSON（`summary.json`、診断の`--output`など）。

## 依存関係

前提となる完了済みの設計書は、[評価関数](evaluation.md)（MNSDとMNPTの定義）、[棋力向上段階9](strength-stage9.md)（来歴JSONと付け直し）、[Python学習器の撤去](python-trainer-retirement.md)（現行の学習器の構成）である。

AlphaZero型探索の実装は、masterへ統合する前のブランチ`alphazero-phase1`にある。
このブランチは、自己対局の生成処理から開始局面一覧の読み込み（`selfplay_gen/opening.rs`の`read_openings`）を呼び出しており、MNSDの符号化関数の可視性も変えている。
本書は開始局面一覧の形式と`read_openings`を変えないので、統合時の衝突は可視性の変更とMNSDの読み書きの箇所に限られる。
同ブランチが加える独自形式（MNZTなど）には、統合する時点で本書の原則を当てはめる。

## 設計判断

| 判断 | 採った方式 | 棄却した代案と理由 |
|---|---|---|
| 来歴JSON | 廃止する。教師の情報（生成コミット、重みの検査和、ノード上限、規則セット、シード）はMNSDヘッダだけに置き、由来はレコードの未使用のバイトへ移す。 | 来歴JSONから全体の検査和だけを外す案では、ヘッダの写しを来歴と突き合わせる重複と、1つのデータを2ファイルで表す構造が残る。 |
| 教師データの全体の検査和 | 計算も照合もしない。切り詰めはファイル長の検査で、同じファイルの重複指定は正規化したパスの比較で検出する。 | ビット化けの検出として残す案は、利用者が不要と決めた。hcpeとPackedSfenValueも検出しない。 |
| 検証分割 | 由来によらず、現行の乱数開始の自己対局と同じ`hash64(ヘッダのシード, 対局番号) % 20 == 0`で検証に入れる。 | 実戦に由来するデータで棋譜IDから所属を決める現行方式は、同じ棋譜に由来するデータがファイルをまたいで同じ集合に入る性質を持つ。しかし棋譜IDの対応表を要し、それが来歴JSONの存在理由になっている。この性質が効くのは、実戦対局のデータと実戦開始の自己対局のデータを同時に学習する場合だけである。 |
| 診断で対局を数える単位 | ファイルと対局番号の組を1対局とする。対局番号はファイル内で一意なので、組が衝突することはない。 | 現行の`diag pst-compare`は、同じ棋譜IDを持つ実戦由来の対局をファイルをまたいで1対局にまとめ、対局数と対局ごとの平均損失を出している（`crates/minase-trainer/src/data/mnsd.rs`の`game_key`）。棋譜IDを持たなくなるので、この集計は保てない。ヘッダのシードと対局番号の組で数える案は、シードの一意性を乱数開始の自己対局にしか課していないので、別のファイルの対局を取り違えるおそれがある。 |
| 混合比λ | 学習器と`diag pst-compare`の必須の引数`--lambda`に一本化し、自己対局に由来するデータへ適用する。実戦対局のデータは常にλ=0とする。 | 来歴から読む現行方式は、学習器の`--lambda-override`と値の出どころが2つになる。NNUEの学習器が持つ既定値1.0も廃止する。既定値で値を補う方式は、プロジェクトの方針が禁じるフォールバックに当たる。 |
| 探索条件（対局中か局面単独か） | 欄を持たず、由来から決める。実戦対局の局面は1局面ずつ置換表を消して探索する（局面単独）ので、実戦対局は局面単独、自己対局は対局中とする。 | 自己対局のデータを局面単独と記す経路は、付け直しと`data selfplay provenance --search-condition`だけであり、どちらも本書で撤去する。 |
| 付け直し | `data selfplay rescore`、その出力形式MNRS、および付け直す記録の通し番号を列挙したテキストファイルを撤去する。 | 付け直しの出力を読むのは付け直し自身の再開処理だけで、学習器は読まない。利用者が撤去を決めた。 |
| 実戦棋譜の詳細 | 棋譜ごとの詳細（レーティング、持ち時間、終局の理由など）を書いていた`.games.json`を、取り込みの除外の報告（`--report`）へ統合する。 | `.games.json`を消すだけの案は、棋譜の詳細が失われる。 |
| MNPT | 版3だけにする。FM節の次元の欄は0または32とし、0はFMを持たないPSTだけの重みを表す（32は現行のFMの次元であり、配置は「MNPT」の節で定める）。PSTだけの重みを書くコマンド（PSTの学習器と`fm scale --fm-scale 0`）は、次元0の版3を書く。 | 版2（PSTだけ）と版3（PSTとFM）を併存させる現行方式は、原則に反する。PSTだけの重みを廃止してNNUEの重みへ統合する案は、エンジンのPSTとPST＋FMの評価をソースとして残すという2026年10月9日の決定に反するので、利用者が採らなかった。 |
| チェックポイント | 4種の学習器（NNUE、PST、FM、PSTとFMの同時学習）とも、NPZの`latest.npz`と`best.npz`に保存する。現行のチェックポイントが持つ状態をすべて配列として収め、進捗と、学習の設定を記した`config.json`の比較対象の欄をJSON文字列の配列として収め、再開時に現在の`config.json`と欄ごとに比べる。`nnue-float.bin`は書かず、`best.npz`を使う。 | 現行の3種のマジック（`MNTRCKPT`、`MNFMCKPT`、`MNJTCKPT`）による独自形式は、学習器の内部でしか読まれない。末尾の検査和と、設定を結びつける検査和は、設定そのものを収めて比べれば要らない。`nnue-float.bin`は`best.bin`を読み直して同じ内容で書いた複製である。 |
| 学習器の入力の識別 | `config.json`には、MNSDを正規化したパス、バイト長、ヘッダの各欄で、MNPTをパスとヘッダの検査和で、NPZをパスとバイト長で記す。診断の`file_identity`と、FMの補正を縮める`fm quarter`と`fm scale`の報告も同じ方法で識別する。 | 入力ファイルの全体の検査和は、教師データの照合と同じ理由でやめる。 |
| 実行ディレクトリの版 | `minase match report`は、`minase match run`と同じく現行の版5だけを受け付ける。 | 版4も読む現行方式は、原則に反する。 |
| 古いデータ | 使えなくなったファイルを、対象の一覧を示して利用者の確認を得てから削除する。 | 残す案は、読めないファイルが`data/`に混ざり、どのファイルが使えるか分からなくなる。 |

## MNSD

ヘッダ（136バイト）とレコード（160バイト）の配置と版番号（1）は変えない。
レコードの先頭から0始まりで数えたオフセット156のバイトは、現行の読み手が0に固定し、0以外を拒否している。このバイトを由来の欄とし、オフセット157から159のバイトは引き続き0とする。

| 値 | 由来 | λ | 探索条件 |
|---|---|---|---|
| 0 | 乱数開始の自己対局（初期局面から乱数で選んだ数手を指した局面から始める） | `--lambda` | 対局中 |
| 1 | 実戦開始の自己対局（lishogiの実戦棋譜の途中局面から始める） | `--lambda` | 対局中 |
| 2 | 実戦対局（lishogiの実戦棋譜の局面そのもの） | 0 | 局面単独 |
| 3 | 合成（診断が書き出す標本、初期局面、駒を1枚除いた局面など、どの対局にも由来しないレコード） | 学習に使わない | なし |

学習器は、教師用Kの分類を、ヘッダの生成コミット、重みの検査和、ノード上限、規則セット、レコードの由来、先読み教師値の条件、適用したλの組で決める。
1ファイル内で由来が混在する入力と、由来が合成のレコードを含む入力は、明示的なエラーで拒否する。
既存の乱数開始の自己対局のデータはバイト156が0なので、そのまま新しい定義に合う。これは乱数開始に値0を割り当てた結果として整合するだけであり、互換のための処理は設けない。

## MNPT

ヘッダ（80バイト）と、PSTの重みと駒価値からなる本体の前半は、現行の版3と同じである。
本体の後半のFM節は、次元が32ならば現行の版3と同じく、次元（u32）、指数（u32）、32個の符号、埋め込みからなる。
次元が0ならば、FM節は次元（0）と指数（0）の8バイトだけからなり、読み手はFMを持たない重みとして復号する。
ヘッダの検査和は、どちらの場合もFM節を含む本体全体に対して計算する。
読み手は、ヘッダの後に次元の欄を読んでから、期待するファイル長を導いて検査する。

## チェックポイント

NPZのファイルは、現行のチェックポイントが持つ各状態の配列と、付随する情報を収めた`meta`配列からなる。
現行の状態とは、学習器ごとのモデルの重み、最適化器のモーメントとステップ数、NNUEの観測マスクと固定した初期値、FMと同時学習のマスクと勾配の履歴である（`nnue/model/checkpoint.rs`、`fm/checkpoint.rs`、`joint/checkpoint.rs`）。
NNUEのGPU上の状態は、現行と同じくスナップショットの経路（`nnue/train/backend.rs`）でホストへ集めてから書く。
乱数の状態はシードとエポックから導かれるので、保存しない。
`meta`はUTF-8のJSON文字列を収めたu8の配列であり、学習器の種別、エポック、最良の記録、経過時間、シード、および`config.json`の比較対象の欄（`settings`、`inputs`、`preprocessing`）を持つ。
読み手は、種別が期待と一致すること、配列の名前と形が学習器の構成と一致すること、`meta`の設定が現在の`config.json`と一致することを確かめる。
NPZの読み書きは学習器の既存の`nn/npz.rs`を使う。

## 形式の仕様の置き場所

各形式の仕様は、次の場所のdocコメントに書く。書き手と読み手が別のモジュールにある形式は、符号化関数を持つ書き手の側に書き、読み手からはrustdocのリンクで指す。

| 形式 | 仕様を書くdocコメントの内容 |
|---|---|
| MNSD | ヘッダとレコードのバイト配置と、由来の規則。 |
| MNUE、MNPT、NPZの重み | 重みのバイト配置と、NPZの重みの配列の一覧。 |
| チェックポイント | 4種の学習器のチェックポイントの配列と`meta`の欄。 |
| 対局ハーネスとSPSAの実行ディレクトリ | 各ファイルの欄。 |
| テキストの入力 | 開始局面一覧、lishogiのNDJSONの入力、SPSAの係数ファイル、SPSAの結果を書き戻すソースコード中のマクロ`parameters!`の構文、`--io-log`の行の形式。 |

手引き`docs/guides/file-formats.md`には、全形式の一覧（名前、マジックと版、書き手、読み手、仕様を書いたモジュール）と、同じファイル名で中身が違うJSON（対局ハーネスとSPSAの`manifest.json`と`invocations.json`、対局ハーネスと学習器の`summary.json`）の区別だけを書く。
学習器の記録（`config.json`、`training.jsonl`など）の欄も、書き出すモジュールのdocコメントに書く。
凍結した設計書（[評価関数](evaluation.md)、[段階9](strength-stage9.md)、[Factorization Machine](factorization-machine.md)、[NNUEの完全代替](nnue-replacement.md)、[Rust製NNUE学習器](nnue-trainer-rust.md)など）のバイト配置の記述は、凍結の規則に従って書き換えない。

## 実装フェーズ

フェーズ0では、本書が変えない形式（MNUE、NPZの重み、対局ハーネスとSPSAの実行ディレクトリ、テキストの入力）の仕様をdocコメントに書き、現在の36形式の一覧を手引きに書く。
完了条件は、docコメントの各欄とバイト位置がコードの符号化関数と一致することである。

フェーズ1では、変更前の基準を記録する。
着手時点のmasterの学習器で、`data/nnue-replacement-gen`の`generated-2000000.bin`と`generated-2100000.bin`を入力に、NNUE（`--device cpu`、`--lambda-override 1.0`）とPST（`--lambda-override 0.75`）を同じシードとスレッド数で2エポック学習する。
コマンドライン全体、初期の重み、入力の順序、`config.json`の局面数と教師用K、各エポックの訓練損失と検証損失を、`docs/measurements/file-format-consolidation-equivalence.md`に記録する。

フェーズ2では、教師データとMNPTを置き換える。
付け直し、来歴JSON、学習器の入力の識別は型と関数を共有しているので、1つのフェーズで変える。

- 付け直しを撤去する（`data selfplay rescore`、`training/rescore.rs`、`selfplay_gen/rescore.rs`、学習器の`rescore_exclusions`）。
- 来歴JSONを撤去する（`training/provenance.rs`、`datagen/provenance.rs`、`data selfplay provenance`、学習器の`InputProvenance`）。開始局面一覧が使う`GameOrigin`は`selfplay_gen/opening.rs`へ移し、`.games.json`は除外の報告へ統合する。
- 生成器（`data selfplay generate`、`data lishogi games`）はレコードに由来を書き、`diag pst-compare`は標本を`records::Writer`で合成として書く。バイト列を独自に組み立てていた書き出し処理は削除する。
- 学習器は由来とヘッダから分類と分割を決め、学習器と`diag pst-compare`の`--lambda-override`を必須の`--lambda`に改め、`config.json`と診断の入力の識別を改める。
- 来歴JSON、棋譜IDによる分割、実戦対局の0以外のλ、ファイルごとのλ、MNPTの版2を前提とするテスト（`crates/minase-trainer/tests/data.rs`、`tests/fm.rs`など）は、新しい定義を確かめるテストに置き換える。
- MNPTを版3だけにし、PSTだけの重みを書くコマンドは次元0の版3を書く。`fm scale`の報告が書く版番号、FMを要する診断の検査（版3ならFMを持つという前提を、次元32の検査に改める）、および版2への変換を勧める診断のエラー文も直す。`crates/minase/nets/`のPSTだけの2ファイル（`pst-init.bin`と`nnue-epoch0-pst.bin`）は、使い捨ての手順で次元0の版3へ書き直す。
- `minase match report`の版4の受け付けを削除する。
- NNUEの学習器が再開時に`config.json`の`resumes`の欄がなければ空の配列で補う処理（`nnue/train/record.rs`）と、それを求めるテストを削除し、欄を必須にする。
- MNSDと重みの仕様のdocコメント、[NNUEの学習手順](../../guides/nnue-training.md)、[PSTとFMの学習手順](../../guides/pst-training.md)、および[棋力測定の手引き](../../guides/sprt.md)を同じコミットで直す。

完了条件は、`cargo test --workspace`が通り、`git grep -iE "rescore|provenance" -- crates`が何も返さず、検証の1から3が通ることである。

フェーズ3では、チェックポイントをNPZに置き換え、`nnue-float.bin`の書き出しをやめ、`diag nnue-removal --float`は`best.npz`を読む。`checkpoints.md`を同じコミットで書く。
完了条件は、4種の学習器がそれぞれ短い学習を中断して再開でき、中断しない学習と同じ損失の列を出すこと、および`meta`の設定が異なるチェックポイントからの再開を拒否することである。

フェーズ4では、使えなくなった`data/`のファイルの一覧を作り、利用者の確認を得てから削除する。
対象の候補は、来歴JSON（56ファイル）、来歴が失われて由来を表せない段階9の実戦由来のMNSD（5ファイル）、旧形式のチェックポイントと`nnue-float.bin`、MNPTの版2のファイル、`.games.json`、および撤去済みのPython学習器の手順が生成した`generated-N.json`、`commands.jsonl`、`config.toml`である。
対局ハーネスの実行ディレクトリは、測定記録の根拠なので、版4のものも削除しない。
最後に、形式の一覧の手引きを最終の形式の集合と照らし合わせる。

## 検証

1. フェーズ1と同じ条件で学習し、局面数、教師用K、各エポックの訓練損失と検証損失が、フェーズ1の記録とビット単位で一致する。
2. 学習器は、由来が混在するMNSD、合成のレコードを含むMNSD、オフセット157から159が0でないMNSDを、明示的なエラーで拒否する。MNPTの読み手は、版3以外のファイルと、FMの次元が0と32以外のファイルを拒否する。
3. `data selfplay inspect`と`diag nnue-moves --positions`が、合成のMNSDを読める。エンジンが`nets/`の書き直したPSTだけの重みで、書き直す前と同じ評価値を返す。
4. 各形式について、docコメントのバイト位置と欄の名前を符号化関数と突き合わせる。

## 完了条件

`MN`の独自形式が、MNSD、MNUE、MNPTの3つだけになっていること（MNRSと3種のチェックポイントのマジックを廃止する）。
どの形式の読み手も現行の版だけを受け付け、変換コマンドと旧版の読み分けがコードにないこと。
来歴JSON、付け直しの対象番号ファイル、`.games.json`が廃止され、教師データの全体の検査和をどのコマンドも計算していないこと。
残った全形式の仕様が、読み書きするモジュールのdocコメントにあり、形式の一覧が手引きにあること。
フェーズ4の削除を終えていること。

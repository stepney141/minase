# 中断可能な計算機での教師生成

## 先に読む要約

本計画では、NNUEの教師データをvast.aiの中断可能インスタンスで生成する仕組みを作り、どのくらいの費用対効果で生成できるかを測る。
NNUEは着手ごとに差分で更新できる小さなニューラルネットの評価関数であり、その教師データは、自己対局の局面に探索で求めた評価値（探索値）を付けた学習データである。
vast.aiは個人や事業者が貸し出す計算機を時間単位で借りられる市場であり、中断可能インスタンス（interruptible instance、一般にはspot instanceと呼ぶ）は、入札で安く借りる代わりに、より高い入札が入るといつでも止められる借り方である。
生成器`minase data selfplay generate`は、7,500局の教師ファイル1つを250局ずつの塊に分けて確定させ、止まった後は同じコマンドで続きから生成できる。
以下では、手元の開発用の計算機を作業機、vast.aiで借りた計算機を生成機と呼ぶ。
本計画では、作業機で動く生成専用の制御スクリプトを新しく作り、生成機から確定した塊を60秒おきに作業機へ回収する。
生成機が止まったら、制御スクリプトは止まった機械を削除し、別の機械を借りて回収済みの塊を送り、同じ教師ファイルの続きから生成を再開する。この一連の手順を移行と呼ぶ。
作業機は、届いた教師ファイルの全対局を復号して生成条件と照合する受け入れの検査を行う。
教師ファイルに学習用として記録された局面を、記録局面と呼ぶ。
費用対効果の主な指標は、この検査に通った記録局面1億あたりの総費用であり、移行で失った計算と準備の時間も費用に含める。
最初に候補の機械の速さを現行のコードで測って借りる機種を決め、次に制御スクリプトを実装し、最後に中断可能インスタンスと止められない通常の借り方（オンデマンド）で同じ10本を生成して費用を比べる。
完了条件は、生成機を途中で止めても制御スクリプトが回収済みの塊を使って別の機械で生成を続け、検査に通る教師ファイルを作ることと、2つの借り方の総費用と中断の記録から標準の借り方を決めることである。

## 目的

利用者の目的は、教師生成をできるだけ安く速く行い、借りた機械が止まっても別の機械ですぐに続きを生成できるようにすることである。
NNUEの世代反復（[標準レシピv1と世代反復のやり直し](../nnue-standard-recipe.md)）は、1世代につき教師ファイルを37本生成する。
これまでの生成は、vast.aiでオンデマンドの機械を1台借り、[連続生成スクリプト](../../../scripts/vast/generation_chain.py)で生成から学習まで行ってきた。
[第2世代の生成](../../measurements/nnue-generation-reset/nnue-generation-reset-gen2-training.md)では、EPYC 9B14を2個載せた384論理スレッドの機械を1時間3.203米ドルで借り、37本を約6.5時間で生成した。

2026年11月14日のvast.aiでは、同じ規模のEPYC 9654を2個載せた機械が、オンデマンドで1時間1.011米ドル、中断可能で最低入札額1時間0.400米ドルで出ていた。
この機械が第2世代と同じ1ファイル約632秒で生成するなら、1ファイルあたりの計算料金はオンデマンドで約0.18米ドル、中断可能で約0.07米ドルになる。
ただし、この見込みは、第2世代の生成に使ったコミット`7c2cfe4e`が別の機種（EPYC 9B14）で出した速さを当てはめた試算である。
フェーズ0の測定時点では、この1時間1.011米ドルの9654機は出品になく、最も安く生成できるEPYC 7B13の256スレッド機で換算した1ファイルあたりの計算料金は、オンデマンドで約0.50米ドル、最低入札額で約0.38米ドルであった。
中断可能インスタンスがどのくらいの頻度で止められ、止まるたびにどのくらいの計算を失うかは、まだ測っていない。
本計画では、実機での生成の速さと中断による損失を測るとともに、機械が止まっても生成を続ける仕組みを作る。

## 適用範囲

対象は、教師ファイルの生成、生成機からの回収、受け入れの検査、および生成機が止まったときの移行である。
制御スクリプトは、検査に通った教師ファイルと生成ログを、連続生成スクリプトが読むのと同じ配置（`gen-<N>/teacher/book-<i>.mnsd`と`gen-<N>/logs/book-<i>.log`）に置く。
連続生成スクリプトは、学習を作業機で行う設定（`--train-place local`）では、教師ファイルがそろった世代について生成機を借りずに学習へ進む。
この動作は`generation_chain.py`の`execute`と`prepare_machine`にあり、本計画の出力をそのまま世代反復の学習に使える。

次の事項は対象外とする。

- 学習、補正、および世代のコミットは、連続生成スクリプトが行い、本計画では変えない。
- 生成機は1台とし、複数台への教師ファイルの配布は行わない。理由は設計判断の8にある。
- GCP（Google Cloud Platform）のSpot VMは使わない。理由は設計判断の9にある。
- 生成器、探索、および教師データの形式は変えない。生成器の進捗の出力も変えないので、移行で失う計算の一部は推定で求める。

## 依存関係

生成器の塊の確定と再開の仕組みは、[教師生成の中断と再開の設計書](resumable-nnue-teacher-generation.md)で導入されたものであり、仕様は`crates/minase/src/bin/minase/selfplay_gen/output.rs`のdocコメントにある。
教師ファイルはminaseの教師データのバイナリ形式MNSDで書かれ、ヘッダには生成コミット（生成器をビルドしたgitのコミット）、重みのチェックサム、規則、シード、および探索ノード数が入る。
シードは対局を決める乱数の種、探索ノード数は1手の探索で調べる局面の数の上限である。
手数の上限（4,000手）に達した対局は、教師ファイルに入れずに破棄する。
生成器は出力先に、生成条件を記録する`config.json`と、塊ごとのMNSDファイル`chunk-NNNNN.mnsd`および集計JSON`chunk-NNNNN.json`を置く。
集計JSONは塊のMNSDを確定させた後に書かれ、その存在が塊の確定を表す。以下では、同じ番号のMNSDと集計JSONを塊の組と呼ぶ。
確定済みの塊の組と`config.json`を別の機械の出力先へ写せば、同じコマンドで続きを生成できる。
再開のときに集計JSONがあるのにMNSDが欠けた塊があると、生成器は探索を始める前に止まる。
異なる機械の間で同じ対局になることは再開の条件ではなく、異なる機械で生成した塊が1つの教師ファイルに混ざってよい。この判断は[設計判断の記録（ADR）](../../adr/commit-nnue-teacher-files-in-fixed-game-chunks-and-reassemble-them-into-one-file.md)にある。
2026年11月14日の[GCPでの予備測定](../../measurements/adhoc/gcp-spot-teacher-generation-speed.md)では、GCPの2台がそれぞれビルドしたバイナリで、最初の塊を同じバイト列で作り、作業機の塊とはMNSDヘッダの生成コミットの欄だけが異なった。

生成機の側では、既存の[生成機の作業プロセス](../../../scripts/vast/generation_worker.py)を変えずに使う。
作業プロセスは、生成機の起動時のスクリプトが目印のファイル`/workspace/job/started`を見つけた後に起動され、設定ファイル`worker.json`の`idle_limit_seconds`（仕事がないまま待つ上限の秒数）を読む。
その後、gitのbundle（コミットを1ファイルにまとめたもの）から指定のコミットをビルドし、ジョブのファイル`job.json`に従って教師ファイルを生成する。
生成する教師ファイルの番号`i`は、0以上`target_books`未満の番号のうち、`job.json`の`skip_books`に含まれず、まだ生成機の`teacher/gen-<N>/`にない番号であり、小さい番号から順に、`work/gen-<N>/book-<i>/`を出力先とする。
作業プロセスは、完成した教師ファイルを`teacher/gen-<N>/`へ置き（以下、公開と呼ぶ）、その後に作業用の出力先を消す。
制御スクリプトは、機械の作成、SSH、rsync、および削除に既存の[共通部品](../../../scripts/vast/common.py)を使う。
本計画では、入札で借りる機能と、ファイルの大きさから転送の時間の上限を求める機能を、この共通部品へ加える。

## 回収、受け入れ、および移行

### 回収と受け入れ

制御スクリプトは、作業機の実行ディレクトリ`<run-dir>`に、回収先の`<run-dir>/remote/`と、受け入れた成果物の`gen-<N>/teacher/`および`gen-<N>/logs/`を置く。
回収は60秒おきに行い、生成機の`/workspace/job/`の下の`work/gen-<N>/`、`teacher/gen-<N>/`、および`logs/gen-<N>/`をrsyncで`<run-dir>/remote/`へ引き取る。
rsyncの終了コード24は転送中に元のファイルが消えたことを表し、作業プロセスが教師ファイルを公開して作業用の出力先を消すと起きるので、失敗としては扱わない。
この場合は受け取れたファイルだけを残し、次の回収で公開済みの教師ファイルを取り直す。
それ以外の終了コードは回収の失敗とする。

公開済みの教師ファイルと生成ログが届いたら、連続生成スクリプトの`accept_books`と同じ検査を行い、通ったものだけを`gen-<N>/teacher/`へ置く。
検査は、`minase data selfplay inspect`による全対局の復号と、ヘッダの生成コミット、重みのチェックサム、規則、シード、および探索ノード数の照合である。
あわせて、保存した局数と手数上限で破棄した局数の和が7,500であること、および生成ログの記録局面数`recorded_positions`が`inspect`の数えた記録局面数`eligible_positions`と一致することを確かめる。
受け入れた教師ファイルの塊は、回収先から消す。
検査の処理は、2つのスクリプトで同じ関数を使うように`common.py`へ移す。

### 停止の判定

制御スクリプトは、回収のたびに次の表を上から順に当てはめ、最初に当てはまった行の扱いをとる。

| 観測 | 扱い |
|---|---|
| 状態の照会が、認証の失効や通信の失敗で答えない。 | 状態不明として、新しい機械を借りずに止まる。 |
| 状態の照会が成功し、2回続けて稼働中でない状態を返し、SSHも接続できない。 | 止まったとして移行する。入札負け（より高い入札による停止）かどうかは断定せず、観測した状態の欄をそのまま記録する。 |
| 回収（SSHかrsync）の失敗が、最後の回収の成功から30分続いている。 | 通信の障害として、移行せずに止まる。 |
| 作業プロセスが終了コードを残している。 | 生成の失敗として、機械を替えずに止まる。 |
| 作業プロセスがなく、終了コードも残っていない。 | 作業プロセスが強制終了したとみなし、生成の失敗として止まる。 |
| 作業プロセスとその子プロセスの合計のCPU時間が、10分間増えていない。 | 生成の失敗として止まる。 |
| 上のどれにも当てはまらない。 | 確定した塊の数が増えていなくても、ビルドか生成の最中として扱う。 |

制御スクリプトが止まるときは、終了時の手順（設計判断の10）に従って、最後の回収と削除を行う。
口座の操作がAPIの照会頻度の上限（HTTPの状態コード429）で断られた場合は、答えないとはみなさず、60秒待って同じ操作を再試行し、5回続けて断られたときに状態不明とする。
フェーズ0では、3台の状態を5秒おきに並行して照会したときにこの応答が返り、vast.aiのCLIは標準出力に何も出さずに終了した。

表の回数と時間は、誤った判定で失う計算と、待つ間の費用から決めた。
「止まった」の判定に2回続けて稼働中でない状態を求めるのは、1回の照会の誤りで移行して、動いている機械を削除しないためである。
通信の障害と判定するまでの30分は、既存の連続生成スクリプトの試験で使った5分より長くとる。
通信の障害と判定して止まると、終了時の削除で生成機の未回収の塊と準備の時間を失うので、一時的な通信の障害では止まらないようにする。
1時間0.400米ドルの機械で30分待つ費用は約0.2米ドルにとどまる。
CPU時間が増えない時間の上限を10分としたのは、生成中は全スレッドが探索を続けてCPU時間が秒単位で増え、ビルドも数分でCPUを使い続けるので、10分間増えない状態は異常に限られるからである。

### 移行

移行は次の順に行う。

1. 旧機を削除し、インスタンスの一覧から消えたことを確かめる。確かめられなければ、新しい機械を借りずに止まる。
2. 回収先に片側だけ残った塊のファイルを消す。
3. 出品を選んで新しい機械を借り、起動時のスクリプトで実行全体の絶対期限に自己停止を予約する。
4. 作業プロセスと`worker.json`を送り、作業プロセスの`cpu-info`でスレッド数とCPUの上限を確かめてから、bundleを送る。
5. 回収先の各教師ファイルの`config.json`と、組のそろった塊を、新しい機械の`work/gen-<N>/book-<i>/`へ送る。
6. `job.json`を送る。`target_books`は担当する番号の範囲の最後の番号に1を足した値とし、`skip_books`には、範囲の始まりより前の番号と、受け入れ済みの番号を入れる。
7. 送り終えてから`started`の目印を置き、作業プロセスを起動させる。

最初の機械を借りるときは、1、2、および5を除いて同じ手順をとる。

転送の時間の上限は、[教訓](../../lessons/derive-transfer-time-limits-from-size.md)に従い、転送するバイト数を、見込む最低の速さで割った時間に固定の余裕を足して求め、送る処理と受け取る処理の両方に付ける。
見込む最低の速さは毎秒1 MB、余裕は120秒とする。
最も大きい転送は約53 MBのbundleであり、上限は約3分になる。
ただし、絶対期限までの残り時間から削除の手順に充てる10分を引いた時間が、この上限より短い場合は、その時間を上限とする。

新しく借りた機械が作成から10分以内に稼働しない場合と、稼働の確認から5分たってもSSHでつながらない場合は、その機械を削除して削除の完了を確かめ、別の出品を借りる。
10分は、連続生成スクリプトが稼働を待つ上限と同じである。
フェーズ0では、4台のうち3台が作成から39秒以内に稼働し、イメージの取得に時間のかかった1台は約16分かかった。
5分は、これまでvast.aiで、SSHを使えない機械を見切って借り直すときの目安にしてきた時間である。
5分で見切る扱いは、一度SSHでつながった後の失敗には使わない。
SSHでつながったら、作業プロセスの`cpu-info`でcpusetのスレッド数とcgroup（コンテナのCPU時間の上限を決めるLinuxの仕組み）のCPUの上限を読み、cpusetのスレッド数が出品の`cpu_cores`と等しく、CPUの上限が`cpu_cores`の0.9倍以上（上限がない場合を含む）であることを確かめる。
満たさない機械も削除して削除の完了を確かめ、その実行の間はその機械（出品の`machine_id`）を選ばずに、別の出品を借りる。
フェーズ0では、出品の表示が384スレッドの機械が、cpusetで48スレッド、cgroupで46.08 CPU分しか使えなかった。
CPUの上限の0.9倍は、連続生成スクリプトの検査と同じ値であり、フェーズ0で表示どおりに使えた3台はいずれも0.96倍であった。
これらの借り直しも借りる回数に数える。
機械の作成の応答を受け取れなかった場合は、作成時に付ける識別用のラベルが同じ機械がないことを確かめてから再試行し、二重に借りることを防ぐ。

### 出品の選択

出品は、次の条件をすべて満たすもののうち、見込みの探索速度あたりの時間単価が最も安いものを選ぶ。
条件は、CPUがx86-64であること、GPUを全部借りる出品であること（`gpu_frac=1`）、出品の表示どおりのスレッド数を使えること、SSHとrsyncで直接つなぐための公開のポートがあること、および機種の条件とメモリの下限を満たすことである。
vast.aiの出品はすべてGPU付きの機械であり、CPUは借りたGPUの割合に応じて割り当てられるので、GPUを全部借りれば機械全体のCPUを使える。
出品の表示どおりのスレッド数を使えるとは、使えるスレッド数`cpu_cores_effective`と機械のスレッド数`cpu_cores`が等しいことをいう。
この条件を満たしても実際には使えない機械があるので、借りた後にも「移行」の節の検査を行う。

機種の条件は、CPU名`cpu_name`がEPYC 7B13またはEPYC 9654であり、`cpu_cores`が256以上であることとする。
この2機種は、フェーズ0で表示どおりのスレッド数を使え、探索速度あたりの費用が安い順に1位と2位であった。
フェーズ0で測った192スレッドのEPYC 7643機は、1世代37本の生成時間の換算が約24.2時間で、設計判断の8の24時間を超えたので、256以上の条件で除く。
見込みの探索速度は、`cpu_cores`にフェーズ0で測った1スレッドあたりの探索速度（7B13が186,200 NPS、9654が214,300 NPS）を掛けた値とする。
NPSは1秒あたりの探索ノード数である。
時間単価は、オンデマンドではストレージの料金を含む合計の時間単価`dph_total`、中断可能インスタンスでは入札額とする。
時間単価が上限を超える出品は選ばない。

同時対局数は、借りた機械のcpusetの論理スレッド数とする。
フェーズ0の4台では、論理スレッド数で指す方が物理コア数で指すより1.13〜1.35倍速かった。
SMT（1つの物理コアで2つの論理スレッドを動かす機能）を持つCPUでは、論理スレッド数は物理コア数の2倍である。
メモリの下限は、同時対局数×220 MiB×1.25とし、出品の`cpu_ram`（MiB単位）と比べる。
出品を選ぶ時点ではまだcpusetを読めないので、出品の`cpu_cores`を同時対局数として下限を求める。
220 MiBは、フェーズ0で測った1局あたりの常駐メモリの最大値である。
1.25は、OSと作業プロセスのための余裕であり、SPSAの調整機の[ADR](../../adr/run-one-game-per-physical-core-with-the-default-hash-and-filter-rented-offers-by-architecture-threads-and-duration.md)と同じ値である。

### 損失の見積もり

1回の移行で失う計算は、止まった時点で終えたのに確定していなかった対局、確定したのに回収していなかった対局、および指している最中の対局の3つである。
塊の局数を$`M`$、回収の間隔を$`\Delta`$、生成の速さを$`r`$局/秒、同時対局数を$`C`$とする。
止まる時刻の分布は分かっていないので、最も単純な一様分布を仮定する。
さらに、各局の計算量が等しく、塊の確定の遅れと転送の時間を無視すると、確定を待つ対局は0から$`M`$まで、未回収の対局は0から$`r\Delta`$まで、指している最中の各局の進み具合は0から1局分までを一様に動き、それぞれの平均はその半分になる。
したがって、失う計算の期待値は、平均的な1局の計算量を単位として次のように近似できる。

```math
\mathbb{E}[L] \approx \frac{M}{2} + \frac{r\Delta}{2} + \frac{C}{2}
```

例として第2世代の条件（同時384局、1ファイル632秒）をとると、$`M = 250`$、$`\Delta = 60`$秒、$`C = 384`$、$`r = 7{,}500 / 632 \approx 11.9`$局/秒であり、失う計算の期待値は125＋約356＋192＝約673局分、同じ速さで約57秒の生成に当たる。
これに、新しい機械の準備（イメージの取得とビルド）の時間が加わる。

この式は実際の損失を小さく見積もる。
第1項の$`M/2`$は塊の確定の遅れを無視した下限であり、作業機での[中断と再開の照合](../../measurements/resumable-nnue-teacher-generation/resumable-nnue-teacher-generation-equivalence.md)では、同時16局でも、終えたのに確定していなかった対局が平均141.8局、最大315局あった。
第2項も、回収の失敗が続いた場合や、長い対局を待って複数の塊がまとめて確定した場合は、式の値を超える。

### 移行と費用の記録

制御スクリプトは、回収のたびに、回収した生成ログの最後の進捗の行が示す終えた対局数と確定させた対局数、および作業機に回収した塊の局数を時刻つきで記録する。
これらは観測値である。
進捗の行の2つの数は、再利用した塊を含まず、その機械での起動の中で終えた対局と確定させた対局だけを数える。
止まった機械については、最後の回収の後の進捗は観測できないので、移行で失った計算を推定値として記録し、観測値と区別する。
推定値は、最後の回収の時点における、その起動で終えた対局数から、その起動で確定させた塊のうち回収済みの塊の局数を引き、指している最中の対局の推定$`C/2`$を足した値とする。
あわせて、止まったことの検知、旧機の削除、新しい機械の作成、ビルドの完了、および生成の再開の各時刻を記録する。
借りた機械ごとに、出品、借り方、時間単価、ストレージと転送の単価、作成と削除の時刻、および移行の理由も記録する。

制御スクリプトは、借りた機械の単価と時間から累計費用の見込みを求め、累計費用の上限を超えないように借用と終了を決める。
累計費用の見込みは、借りていた時間に時間単価とストレージの時間単価の和を掛けた額と、転送したバイト数に転送の単価を掛けた額の合計とする。
新しい機械を借りる前に、累計費用の見込みにその機械の1時間分を足した額が上限を超えるなら借りない。
借りている間は、累計費用の見込みにその機械の30分分を足した額が上限に達した時点で、最後の回収と削除を行って止まる。
30分分は、最後の回収と削除にかかる時間の費用を上限の内側に残すための余裕である。
削除を確かめられない機械は課金が続くので、その場合は上限を守れないことを示して止まる。
起動時のスクリプトによる自己停止は機械を停止するだけで削除はしないので、停止後もストレージの料金がかかる。
測定の総費用には、実行の前と後の口座の残高の差を使い、実行中にほかの用途でvast.aiを使わない。

## 実装フェーズ

### フェーズ0: 候補の機械の速さを測る

現行のmasterのコミットを固定し、制御スクリプトは作らずに、作業機から手作業で候補の機械を借りて測る。
2026年11月14日の出品は主に384、256、および192スレッドの3つの規模に分かれていたので、候補として、各規模からスレッドあたりのオンデマンドの価格が最も安い出品を1台ずつ選ぶ。
各機械には、起動時のスクリプトで借りてから2時間の絶対期限に自己停止を予約し、測定が終わったら削除する。
1台の測定は、イメージの取得とビルドを含めて40分前後で終わる見込みなので、2時間はその約3倍の余裕である。

各機械でコミットをビルドし、同時対局数`C`を論理スレッド数と物理コア数の2通りにして、次のコマンドを1回ずつ実行する。
引数のうち探索ノード数、ランダム着手、および置換表の容量は、[標準レシピの生成の引数](../nnue-standard-recipe.md)と同じである。

```sh
minase data selfplay generate --output-dir <一時の出力先> --chunk-games <C> --games <C> --concurrency <C> \
  --seed 9699000000 --nodes 20000 --random-moves 0 --max-ply 200 --hash-mb 16
```

1局を200手で打ち切るので、全スレッドがほぼ最後まで探索し、各局の探索量は1手2万ノード×200手でほぼ等しい。
要約の探索ノードの合計`searched_nodes_total`を経過時間`elapsed_seconds`で割った全体の探索速度と、開始から12秒後の常駐メモリを記録する。
12秒は、[生成機での教師生成の速さ](../../measurements/nnue-generation-reset/nnue-generation-reset-generator-speed.md)の測定と同じ時点であり、値を比べられるようにするためである。
全体の探索速度あたりのオンデマンドの価格と最低入札額を比べ、機種の条件、同時対局数の決め方、およびメモリの下限を決める。
2026年11月14日の各規模の最安のオンデマンドの価格は、384スレッド級が1時間1.011米ドル、256スレッド級が1.055米ドル、192スレッド級が0.508米ドルであった。
各40分前後借りると合計約1.7米ドルになるので、費用は約2米ドルの見込みである。
借りる前に、出品と見込みの費用を示す。
結果は`docs/measurements/interruptible-teacher-generation/interruptible-teacher-generation-candidates.md`に記録する。

完了の基準は、3台の測定を記録し、機種の条件、同時対局数の決め方、およびメモリの下限を決めたことである。

2026年11月14日に、384スレッド級の2台（EPYC 9B45とEPYC 9654）、256スレッド級のEPYC 7B13、および192スレッド級のEPYC 7643を測り、費用は残高の差で0.899米ドルであった。
384スレッド級の最安の出品（EPYC 9B45）は48スレッドしか使えず、次に安いEPYC 9654の出品はコンテナが起動しなかったので、その次に安いEPYC 9654の出品を加えた。
同時対局数を論理スレッド数としたときの探索速度は、7B13機が4,767万NPS、7643機が3,467万NPS、9654機が8,229万NPSであった。
この結果から、「出品の選択」の節の機種の条件、同時対局数、およびメモリの下限を決め、借りた後のスレッド数の検査を「移行」の節に加えた。

### フェーズ1: 制御スクリプトを実装する

masterからブランチ`interruptible-teacher-generation`とworktreeを作り、実装をcodex（OpenAIのコーディングエージェント）へ委任する。
実装するのは、制御スクリプト`scripts/vast/teacher_generation.py`と、`common.py`へ加えるか移す3つの機能と、それらの試験である。
3つの機能は、入札で借りる機能、ファイルの大きさから転送の時間の上限を求める機能、および教師ファイルの検査である。
制御スクリプトの引数は、生成コミット、世代の番号N、教師ファイルの番号の範囲、シードの式（基本シードと番号ごとの刻み）、生成器の引数、借り方、時間単価の上限、絶対期限、累計費用の上限、借りる回数の上限、および実行ディレクトリとし、すべて必須とする。

作業機の試験では、vast.aiのCLIと生成機を偽物に置き換え、次を確かめる。

- 回収の途中でrsyncが終了コード24を返しても、公開済みの教師ファイルを次の回収で受け入れる。
- 移行のとき、片側だけ残った塊のファイルを消し、組のそろった塊だけを新しい機械へ送り、`config.json`、塊、および`job.json`を送り終えてから`started`の目印を置く。
- 番号の範囲の始まりが0でないとき、`skip_books`に範囲の始まりより前の番号が入り、範囲外の教師ファイルを生成しない。
- 旧機の削除を確かめられなければ、新しい機械を借りずに止まる。
- 新しく借りた機械に5分たってもSSHでつながらなければ、その機械を削除して別の出品を借り、その回数を借りる回数に数える。
- 累計費用の見込みにその機械の30分分を足した額が上限に達したら、最後の回収と削除を行って止まる。
- 状態の照会が認証の失効で失敗したら、借りずに止まり、残っている機械のIDを示す。
- 停止の判定の表の各行が、表の順に当てはめられる。
- 累計費用、絶対期限、および借りる回数の上限は、制御スクリプトを起動し直しても初期化されない。
- 受け入れた教師ファイルを、連続生成スクリプトの`books`がそのまま読める。
- 正常終了、異常終了、および中断の信号のどの経路でも、最後の回収と削除を行う。

vast.aiでの復旧試験では、オンデマンドの機械で教師ファイルを2本生成させる。
シードは基本シード9,700,000,000、番号ごとの刻み100,000、番号の範囲1〜2とする。
1本目の途中で、塊の組を1つ以上回収した後に、生成機を管理画面から停止する。
制御スクリプトが旧機を削除し、別の機械を借りて回収済みの塊から続きを生成することを確かめる。
合格の条件は3つある。
2本とも受け入れの検査に通ること、1本目の生成ログの`chunks_reused`が新しい機械へ送った塊の数と一致すること、および送った塊のMNSDのヘッダより後のバイト列が、受け入れた教師ファイルの対応する範囲と一致することである。
結果は`docs/measurements/interruptible-teacher-generation/interruptible-teacher-generation-recovery.md`に記録する。

完了の基準は、作業機の試験が通り、復旧試験が合格の条件を満たしたことである。

### フェーズ2: 2つの借り方で同じ10本を生成する

フェーズ0で決めた機種の条件で、同じ10本を、中断可能インスタンスとオンデマンドで別々の実行ディレクトリに生成する。
シードは基本シード9,701,000,000、番号ごとの刻み100,000、番号の範囲0〜9とし、2つの借り方で同じ生成条件と番号の10本を生成させて、生成の量をそろえる。
10本は1世代37本の約4分の1であり、フェーズ0の7B13機の換算では約4.8時間、準備を含めて約5時間かかる。
中断がまれなら、この時間の中で1回も起きないこともある。
口座の残高の差で総費用を測るので、2つの実行は並行させずに順に行い、絶対期限はそれぞれの実行の開始から10時間後とする。
2026年11月14日の7B13機の価格では、見込みの費用は、中断可能で約5時間×最低入札額1時間0.56〜0.80米ドル＝約2.8〜4.0米ドルにストレージの料金を足した額、オンデマンドでストレージの料金を含めて約5時間×1時間1.055米ドル＝約5.3米ドルである。
累計費用の上限は、どちらの見込みの2倍以上である12米ドルとし、移行を繰り返しても費用が際限なく増えないようにする。
中断可能インスタンスは最低入札額で借り、借りる回数の上限を11回とする。
11回は、最初の1回に加えて、1本につき1回止められても移行して生成を続けられる回数である。
オンデマンドは、借りる回数の上限を3回とする。
3回は、新しく借りた機械が稼働しない、SSHでつながらない、またはスレッド数の検査に通らずに借り直す場合の余裕である。

借りた機械ごとに、入札額、作成から生成開始までの時間、止まった時刻と観測した状態、移行にかかった時間、および失った計算（観測値と推定値を区別したもの）を記録する。
手動の停止は行わず、自然に起きた中断だけを記録する。
10本の生成中に中断が起きなかった場合は、観測した時間の中で0回だったという結果として記録し、中断が少ないとは結論しない。

2つの借り方の記録局面1億あたりの総費用と実効の生成速度を比べ、標準の借り方（中断可能かオンデマンドか、および入札額の決め方）を決める。
総費用の小さい方を標準とする。
ただし、その借り方の実効の生成速度から換算した1世代37本の生成時間が24時間を超える場合は、もう一方の借り方が24時間以内に収まるならそちらを標準とする。
この決定は、観測した条件での比較に基づく暫定のものとして、ADRに条件とともに記録する。
1世代37本の換算の生成時間は、設計判断の8の再検討の条件にも使う。
結果は`docs/measurements/interruptible-teacher-generation/interruptible-teacher-generation-trial.md`に記録する。

完了の基準は、2つの借り方で10本ずつを受け入れ、総費用と中断の記録から標準の借り方を決めたことである。

## 検証

フェーズ1の完了前に、worktreeで`python3 -m unittest discover -s scripts/vast -p 'test_*.py'`を実行し、既存の試験と新しい試験がすべて通ることを確かめる。
連続生成スクリプトの試験は、教師ファイルの検査を`common.py`へ移した後も、試験の変更なしで通ることを確かめる。
フェーズ1とフェーズ2で受け入れたすべての教師ファイルについて、`minase data selfplay inspect`が全対局を復号して終了コード0で終わることを確かめる。
移行を挟んだ教師ファイルについては、保存した局数と手数上限で破棄した局数の和が7,500であることと、生成ログの`recorded_positions`が`inspect`の`eligible_positions`と一致することを確かめる。

## 完了条件

完了条件は2つある。
1つ目は、フェーズ1の復旧試験で、生成機を止めても制御スクリプトが回収済みの塊を使って別の機械で生成を続け、検査に通る教師ファイルを作ることである。
2つ目は、フェーズ2で2つの借り方による10本ずつの生成を終え、総費用と中断の記録から標準の借り方を決めることである。
この2つを満たしたら、制御スクリプトの仕様をdocコメントへ、設計判断と標準の借り方をADRへ、手順を`docs/guides/nnue-training.md`へ移し、状態を完了（採用）に書き換える。
フェーズ2の結果、中断可能インスタンスがオンデマンドより高くつくと判断した場合も、制御スクリプトはオンデマンドでの移行に使えるので、標準の借り方をオンデマンドとして完了（採用）とする。

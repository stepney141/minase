# 第1層の全再計算を差分で置き換える表（Finny tables）の設計書

## 先に読む要約

minaseの評価関数NNUE（[評価関数の手引き](../../guides/evaluation-nnue.md)）は、盤上の駒と升の組を入力特徴とする。第1層の値（累算値）は、先手と後手の視点ごとに、バイアスに発火した入力特徴の重みの行を足したものであり、着手で増減した特徴の行だけを足し引きして更新する。これを差分更新と呼ぶ。
入力特徴集合HalfKP_vmは、視点の側の王将（王将がなければ太子）の位置で入力特徴を条件付ける。以下、この基準になる駒を基準の王駒と呼ぶ。
基準の王駒が別の升へ動くと、その視点のすべての特徴の番号が変わるので、差分更新が使えず、第1層をバイアスから計算し直す。これを全再計算と呼ぶ。
Finny tables（accumulator cache、refresh tableとも呼ぶ）は、基準の王駒の位置ごとに、最後に計算した第1層の値とそのときの駒配置を保存する表である。全再計算の代わりに、保存した駒配置と現在の駒配置の差の分だけを足し引きする。
本書はHalfKP_vmのネットにこの表を入れる。HalfKP_vmの世代反復（自己対局で教師データを作り、次のネットを学ぶことの繰り返し）が教師データを作り始める前に、教師生成を速くしておくことが目的である。
採用するには、次の3つをすべて満たす必要がある。

- 探索結果が、表を入れる前とビット単位で一致すること。
- HalfKP_vmの教師生成のCPUサイクル数の合計が減ったと、95%信頼区間で言えること。
- 固定した15局面を探索するコマンド`bench`が、HalfKP_vmと、現在の標準である入力特徴集合A型のどちらのネットでも、0.5%を超えて遅くならないこと。

サイクル数は、基準の版と表を入れた版を1組ずつ交互に測って比べる。
表は探索結果を変えないので、自己対局で棋力を検定する段階ゲートは行わない。

## 状態

本書は完了時点で凍結した記録であり、以後の変更を反映しない。現行の仕様はコードのdocコメントに、設計判断は[docs/adr/](../../adr/README.md)にある。
状態は完了（不採用）であり、2026年11月27日に完了した。
探索ごとの表は探索結果を変えず、HalfKP_vmの`bench`のサイクル数を1.15%減らしたが、教師生成のサイクル数の減少（平均0.14%）は95%信頼区間で0と区別できなかったので、表のコードをmasterへ入れなかった（[最終測定](../../measurements/nnue-finny-tables/nnue-finny-tables-final.md)、[ADR](../../adr/do-not-replace-half-kp-vm-refreshes-with-per-search-finny-tables.md)）。
フェーズ2の[行数の診断](../../measurements/nnue-finny-tables/nnue-finny-tables-row-counts.md)で対局内の保持の効果が小さかったので、フェーズ3は行わなかった。負荷とシードの条件は[準備の測定記録](../../measurements/nnue-finny-tables/nnue-finny-tables-setup.md)にある。

## 目的

- HalfKP_vmのネットを使う探索で、基準の王駒の移動による第1層の全再計算を、表からの差分の更新に置き換える。
- 置き換えが探索結果を変えないことと、HalfKP_vmの教師生成のCPUサイクル数を減らすことを、測定で確かめてからmasterへ統合する。

## 適用範囲

本書が扱うのは次の作業である。

- `FeatureTransformer::update_after_move`（`crates/minase/src/eval/nnue/transformer.rs`）のうち、文脈（基準の王駒の位置で決まる区分と鏡映の有無）が変わった視点の第1層をバイアスから全再計算する分岐を、表からの差分の更新に置き換える。探索の根の累算値を全再計算したときも、その結果を表に保存する。
- フェーズ2の診断の結果に応じて、表を対局の間保持するように変える（フェーズ3）。
- 置き換えの前後で、探索結果の一致とCPUサイクル数を比べる。

次の事項は扱わない。

- A型のネットには表を入れない。A型は文脈が1種類なので、全再計算は探索の根でしか起きない。ただし、探索の準備はA型と共通の経路を通るので、A型の探索結果の一致と速度は最終測定で確かめる。
- 行を加減算する`add_row`を、SIMD命令（1命令で複数のデータを処理する命令）で明示的に書き直すことはしない。これは親からの差分更新にも効く別の変更であり、先に機械語で自動ベクトル化の有無を確かめる（[教訓](../../lessons/check-autovectorization-before-explicit-simd.md)）。
- Stockfishのhybrid更新（「先行実装」の節）は入れない。これは表に入らない特徴の全加算を避けるための処理であり、minaseのHalfKP_vmのネットには表に入らない特徴がない。
- 足し引きする行の数が全再計算で足す行の数以上のときに、表を使わず作り直す判定（やねうら王の`USE_FINNY_RESET`の一部）は入れない。フェーズ2で該当する回数を記録し、多ければ別の設計書で扱う。
- 学習器は変えない。表は推論の計算順序だけを変え、重みと評価値は変えない。

## 依存関係

### HalfKP_vmの文脈

中将棋の盤は12筋×12段の144升である。minaseは筋と段を0〜11の番号で表す（`crates/minase-core/src/board/square.rs`）。
入力特徴集合は列挙型`FeatureSet`が定め、番号付けはトレイト`Indexer`が持つ（`crates/minase/src/eval/nnue/input/mod.rs`）。
`Indexer::context`は視点ごとの文脈を返し、`Indexer::row`は文脈と基底特徴の番号から第1層の行の番号を返す。基底特徴は、盤上の駒の状態と升の組、および先獅子の対象升である（「Finny tablesの仕組み」の節）。
HalfKP_vmの文脈`HalfKpVmContext`は、区分（0〜71）と左右鏡映の有無の組であり、基準の王駒の升から次のように決まる（`input/half_kp_vm.rs`）。

- 筋の番号が6未満なら鏡映ありとし、筋を`11 − 筋`へ写す。鏡映後の筋は6〜11になる。
- 段は、先手の視点ではそのまま、後手の視点では`11 − 段`とする。これを相対段と呼ぶ。
- 区分は`6×相対段 + (11 − 鏡映後の筋)`である。

区分を6で割った商が相対段、余りが鏡映後の筋を決め、鏡映の有無から元の筋が決まる。したがって、視点を固定すると文脈と基準の王駒の升は1対1に対応し、1視点の文脈は144通りある。
基準の王駒が別の升へ動くたびに文脈が変わり、その視点は全再計算になる。
`Indexer::context`は、王将が2枚ある視点、王将がなく太子が2枚ある視点、および王将も太子もない視点でエラー値を返す。このとき、その視点は文脈なしになり、累算値の全成分を0にする。
探索の根では、この3つの状態をいずれも`check_search_root`が拒否する。探索中の着手で生じ得るのは、王駒をすべて失った視点だけである。

### 第1層の値

第1層の値は`i16`で持ち、加減算は`wrapping_add`と`wrapping_sub`による2^16を法とする剰余演算で行う（`transformer.rs`の`add_row`）。
ネットの読み込み時に、`validate_ft`（`crates/minase/src/eval/nnue/network/mod.rs`）が区分と成分ごとに、バイアスの絶対値、升ごとの重みの絶対値の最大値144個、および先獅子の重みの絶対値の最大値の和を求め、32,767を超えるネットを拒否する。
1升には駒が1枚しかなく先獅子の対象升も1つなので、この和はどの局面の累算値の絶対値以上になる。
HalfKP_vmのネットは`network/simple.rs`の`SimpleNetwork`で、第1層の幅は2〜1,024の偶数であり、線形の経路も駒と升ごとの点数の表（PSQT）も持たない。
現在のHalfKP_vmのネットは幅256で、第1層の重みは964,224行×256成分×2バイトの約494 MBになる。1区分あたりでは13,392行の約6.9 MBである。

### 探索での累算値の扱い

探索は累算値を局面ごとにすぐには計算しない。子へ降りる前か、静的評価を読む時点で確定する（`crates/minase/src/search/alphabeta/searcher.rs`の`ensure_accumulator`）。
子へ降りる前に親の累算値は必ず確定するので、差分の連鎖は途切れない。全再計算が起きるのは、探索の根と、新しい文脈がある視点で文脈が変わったときだけである。
累算器は列挙型`SearchEvaluator`（`network/evaluator.rs`）が深さごとに持ち、探索ごとに作られる。HalfKP_vmのネットで探索するときは、その値`SearchEvaluator::Simple`が使われる。
ワーカーは探索のたびに`thread::scope`で作り直される（`search/alphabeta/team.rs`の`run_worker_team`）。探索をまたいでワーカーごとに残る状態は、`HistoryTables`（`search/alphabeta/history.rs`）だけが持つ。
`HistoryTables`は、[対局内で履歴を持ち越す設計判断の記録（ADR）](../../adr/carry-histories-and-correction-histories-within-a-game.md)に従って対局の間は保持され、次の契機で消去または作り直される。

- 将棋の思考エンジンの通信規約USIで動くエンジン（`search/alphabeta/engine.rs`と`protocol/usi.rs`）では、新規対局、規則セットの設定、引き分けの評価値の変更、`EvalFile`、および`USI_Hash`の設定で消去し、`Threads`の値が変わると作り直す。
- 教師生成（`crates/minase/src/bin/minase/selfplay_gen/play.rs`）は、対局ごとに作り直し、さらに開始局面の候補を探索するたびに消去する。採用した候補の探索結果は、対局の最初の手に使う。
- `bench`（`crates/minase/src/diagnostics/bench.rs`）は、局面ごとに消去する。

公開の`search`関数（`search/handle.rs`）は、ネットと`HistoryTables`を別々の引数で受け取る。そのため、呼び出し側は同じ`HistoryTables`に別のネットを渡せる。

### 計数、照合、および測定の道具

`bench`は、固定した15局面を固定の深さで探索するUSIの独自コマンドである（[USIの拡張の手引き](../../guides/usi-extensions.md)）。
`bench`の前には、オプション`RuleSet`と`EvalFile`を設定して`isready`を送る。規則セットを設定しないと`isready`はエラーで終わる。
累算器の更新の回数は`AccumulatorStats`（`eval/nnue/stats.rs`）が数え、`bench`の`accumulators:`行が`refresh_fraction`として出力する。
この計数では、1回の更新（両視点を含む）を1回と数え、探索の根か、少なくとも1視点で全再計算が起きた更新を全再計算の回数に入れる。新しい文脈がなく全成分を0にしただけの更新は、全再計算には数えない。
`invariants`機能を有効にしたビルドでは、静的評価を読む局面ごとに、差分更新の累算値を全再計算の結果と照合する（`SearchEvaluator::assert_accumulator`）。

本書の測定には、[HalfKP_vmの動作の確認](../../measurements/nnue-tatara-framework-and-halfkp-vm/nnue-tatara-framework-and-halfkp-vm-halfkp-vm-check.md)で教師37本から学んだHalfKP_vmのネットを使う。SHA-256は`d0d1bf33fa7aef3faa40fb0696872eb632a959313d9b03a6df216d99b4f5441d`である。
このネットは過学習しており、棋力の判定には使わない。しかし、このネットを使う探索の速度と探索結果の一致は、本書の判定に使える。

## Finny tablesの仕組み

着手の前後で番号付けが変わらなければ、動いた駒の特徴の行を引いて足すだけで次の局面の第1層の値が得られる。
中将棋の通常の着手では、動いた駒の移動元と移動先、取られた駒（獅子などの2回動きでは最大2枚）、および先獅子の消滅と発生の、2〜6個の特徴を更新する。
先獅子は、獅子以外の駒が相手の獅子を取った直後に、条件によって相手がこちらの獅子を取れなくなる一時的な禁止であり（[規則](../../rules/chu-shogi.md)の第15条）、入力特徴としては獅子が取られた升（先獅子の対象升）で表す。
HalfKP_vmでは、基準の王駒が動くと視点の文脈が変わり、盤上のすべての駒の特徴が別の行へ移るので、差分更新が使えない。
HalfKP_vmの基底特徴には両陣営の王将が含まれないので、全再計算では、王将を除く盤上のすべての駒と先獅子の特徴を足す。初期配置は両陣営46枚ずつで、王将を除くと90枚である。幅256では1行が512バイトなので、1視点で約45 KiBの重みを読む。

Finny tablesは、視点と文脈の組ごとに、その文脈で最後に計算した第1層の値と、そのときの駒配置を保存する。
全再計算が必要になったら、新しい文脈の項目を取り出し、保存した駒配置と現在の駒配置の差を求める。差とは、保存した後に盤上から消えた駒の特徴と、新たに現れた駒の特徴である。その差だけを項目の値に足し引きすれば、現在の局面の累算値が求まる。
計算した値と現在の駒配置は項目へ書き戻し、次に同じ文脈へ戻ったときの起点にする。
表で計算が減るのは、足し引きする行の数（消えた特徴と現れた特徴の和）が、全再計算で足す行の数より少ない場合である。この差の大きさは探索が読む局面の並びで決まるので、minaseでの効果は測って確かめる。

表を使っても、第1層の値は全再計算の結果とビット単位で一致する。
同じ文脈では、項目の値は保存した駒配置での行の和を2^16で割った剰余であり、消えた行を引いて現れた行を足すと、各成分は現在の駒配置での行の和を2^16で割った剰余になる。剰余の加減算は順序によらないので、途中の値がどれだけ`i16`の範囲を外れても、同じバイアスと同じ行の集まりからは同じ`i16`の値が得られる。
これは`validate_ft`の上限によらずに成り立つ。上限は、その値が真の和そのものであることを保証する。
加減算を飽和演算に置き換えると、途中で飽和した値が順序に依存するので、この一致が崩れる。

## 先行実装

### Stockfish

Stockfishは、コミット`49ef4c93`（2024年4月、PR #5183、"Implement accumulator refresh table"）で表を導入した。
コミットの本文は、この考え方を最初に述べたのはチェスエンジンKoivistoの作者Luecxであり、一般に"Finny Tables"と呼ばれていると記している。
Stockfishの検定基盤fishtestでは、短い持ち時間、長い持ち時間、および8スレッドの短い持ち時間の検定のいずれにも合格した。速度の比は記載されていない。
`be142337`（2024年4月、PR #5203）は、表を探索の開始ごとではなく履歴の表と同じ時機に消すべきだと述べ、そのように変えた。
`67645619`（2025年10月、PR #6366）は、項目の駒配置をビットボードから升ごとの駒の配列へ変えた。

2026年11月22日のコミット`3e8fde75`では、表は`AccumulatorCaches`であり、探索スレッドの`Search::Worker`が持つ（`src/search.h`の395〜396行）。
項目は、駒の構成で決まる3通りのブロック、王の升64、および視点2で引く（`src/nnue/nnue_accumulator.h`の85〜86行）。3通りのブロックは`ff7cee42`（2026年10月、PR #7265）で入った。各項目は、16ビットの第1層の値1,024個、64升の駒の配列、および占有升のビットボードを保存する。
表を消すのは`Worker::clear`だけで、新規対局、置換表の消去、ネットの読み込み、およびスレッド数の変更のときに呼ばれる。根の局面の累算値も表から作る。
表が保存するのは、王の位置で条件付けた駒の配置の特徴の和だけである。駒の利きの特徴と駒の対の特徴は、項目を更新した後に現在の局面から列挙して足す。
`db98633b`（2026年7月、PR #6990）のhybrid更新は、王が盤の同じ半分の中で動き、盤上の駒が15枚以上ある場合に、親の累算値から移動前の升の項目を引いて移動後の升の項目を足す。これは、表に入らない利きと対の特徴の全加算を避けるための処理であり、作者の測定では約0.6%速くなった。

### やねうら王

将棋エンジンやねうら王は、コミット`72c91d81`（2026年8月5日、「NNUE、finny tables導入。」）で表を導入した。
作者の解説記事は、推論部が30〜50%程度、NPSが15%程度速くなったと述べるが、測定の条件は書かれていない。
2026年11月24日のコミット`4482ea17`でも、表はコンパイル時に`USE_FINNY_TABLES`を定義したときだけ有効になり、既定のビルドでは使われない。
有効にする条件は第1層の幅の半分が4,096以下であることだけであり、HalfKP_vmを含め、入力特徴集合による除外はない。
表はスレッド局所の領域にあり、所有するネットと、ネットの読み込みごとに増える世代番号を照合して無効にする（`source/eval/nnue/nnue_feature_transformer.h`の986〜993行）。
項目は、全再計算の契機の種類、視点、および鏡映前の玉の升81個で引き、第1層の値と、計算に使った特徴番号の列を保存する。
`USE_FINNY_TABLES`だけでは、表を使うのは現在の局面も直前の局面も累算値が未計算の場合に限られ、玉が動いた視点は従来どおりバイアスから全再計算する。
`6a58a169`（2026年10月25日）で加わった`USE_FINNY_RESET`（既定は無効）を併せて定義すると、玉が動いた視点でも表を使い、差分の数が全特徴の数以上なら表を作り直す。
作者の測定メモ（`tools/memo/finny-reset-measurement-audit-20261030.txt`）では、`USE_FINNY_RESET`の有無で32スレッドのNPSが平均19.3%違った。これは将棋のSFNN halfka2 2304のネットでの値であり、HalfKP系の測定はない。

### 先行実装から言えること

王駒の移動の頻度や区分の数と効果の関係を定量的に示した資料は見つからなかった。表が2次キャッシュに収まらない場合の効果の低下を測った資料も見つからなかった。
項目の差分と親からの差分を比べて安い方を選ぶ処理は、調べたどのエンジンにもなかった。
minaseに最も近い構成の先例はrshogiのHalfKP 256x2-32-32の+11.1%である。ただし、全再計算で足す行は、将棋の38〜40に対して中将棋では最大90と多い一方、探索中に基準の王駒が動く頻度はまだ測っていない。どちらの影響が大きいかは、minaseで測るまで分からない。

## minaseで全再計算が起きる頻度

文脈を変え得る着手は、王将の移動、王将がない側の太子の移動、および、王将と太子の両方を持つ側が王将を取られる着手である。最後の場合は、基準の王駒が王将から太子に替わる。
醉象が成って太子が現れても、王将がある側では基準は王将のままなので、文脈は変わらない。
[HalfKP_vmの動作の確認](../../measurements/nnue-tatara-framework-and-halfkp-vm/nnue-tatara-framework-and-halfkp-vm-halfkp-vm-check.md)では、深さ5の`bench`1回で、累算器の更新66,624回のうち781回（1.17%）が全再計算だった。数え方は「計数、照合、および測定の道具」の節のとおりで、根を含む。
[入力特徴の調査](../../proposals/archived/nnue-input-features.md)が教師データの隣接局面26,225,953組を集計したところ、着手した側の王将が動いた着手は全体の7.54%で、150手目より前では0.15%以下、150手目以降では10.63%だった。
これは対局で指された手の割合であり、探索が読む局面での割合ではない。

## 方式

表は、視点と文脈の組ごとに1項目を持つ。1視点あたり144項目、両視点で288項目である。
各項目は、第1層の値`i16`×幅、144升の駒コード、先獅子の対象升（なしを含む）、および有効印を保存する。駒コードは1升1バイトの値で、駒種、成りの有無、および先後を表す（`crates/minase-core/src/piece/code.rs`）。
幅256で64バイト境界に揃えると、1項目は704バイト、1ワーカーあたり約198 KiBになる。上限の幅1,024では約630 KiBである。

探索の根で累算値を全再計算したときは、文脈がある視点ごとに、結果、現在の駒配置、および先獅子の対象升を項目へ保存し、有効印を真にする。
`update_after_move`で、新しい文脈がある視点の文脈が変わったときは、バイアスからの全再計算の代わりに次の手順で処理する。

1. 新しい文脈の項目を取り出す。有効印が偽なら、全再計算し、結果、現在の駒配置、および先獅子の対象升を項目へ保存して有効印を真にし、ここで終える。
2. 144升のそれぞれで、保存した駒コードと現在の駒コードを比べる。異なる升では、項目の第1層の値から保存した駒の特徴の行を引き、現在の駒の特徴の行を足す。空の升は足し引きしない。
3. 先獅子の対象升が異なる場合も、同じように項目の値から引いて足す。
4. 行の番号は新しい文脈で`Indexer::row`を通して求めるので、鏡映もこの写像が扱う。王将の特徴には行がなく、`row`が`None`を返すので読み飛ばす。
5. 更新した項目の第1層の値を累算器へ写す。項目には、更新した第1層の値、現在の駒配置、および現在の先獅子の対象升が残る。

新しい文脈がない視点では表を使わず、全成分を0にする。
null moveでは文脈が変わらないので、全再計算も表の参照も起きない。

表を対局の間保持する場合（フェーズ3）は、次のようにネットと照合する。
`SimpleNetwork`は構築のたびに、ほかのネットと区別するための印として、中身のない`Arc`を1つ作って持つ。表はその複製を保持し、探索の開始時に`Arc::ptr_eq`で照合して、違えば全項目の有効印を落とす。幅が違えば領域も作り直す。
表が古い印の複製を保持している限り、その印の領域は解放されないので、別のネットの印が同じアドレスに作られて取り違えることはない。

累算値は全再計算の結果とビット単位で一致しなければならない。
`invariants`機能つきのビルドの照合（`SearchEvaluator::assert_accumulator`）は、表を通らない`refresh`の結果を基準として、両視点の文脈と全成分を比べる。根の累算値を表から作る場合も、照合の基準には表を使わない。

## 実装フェーズ

実装はコーディングエージェントへ委任し、Claudeが設計の確定とレビューを担う（[委任の手引き](../../guides/codex-delegation.md)）。
masterから本書のブランチ`nnue-finny-tables`を切り、worktreeで作業する。
各フェーズの完了条件にある「検証」は、「検証」の節のコマンドがすべて通ることを指す。

### フェーズ0　準備

探索結果の一致を確かめるスクリプトと、サイクル数の対比較を行うスクリプトを用意し、測定記録のディレクトリ`docs/measurements/nnue-finny-tables/`の付属資料に置く。[着手生成の高速化第3期](../movegen-speedup-3.md)が同じ目的のスクリプトをすでに作っていれば、それを使う。
次に、基準のコミットで測って、最終測定の負荷の条件を固定する。

- `bench`の深さは、HalfKP_vmとA型のネットのそれぞれについて、深さ16から始め、1局面あたりの探索時間が数秒以上になる深さを選ぶ。
- 教師生成の1回の局数Kは、2局から始める。

あわせて、ネットの読み込みだけを行う起動のサイクル数を測る。標準入力に`setoption name RuleSet value JCSA`、`setoption name EvalFile value <ネット>`、`isready`、`quit`を送り、`info string network_sha256`の行が期待するSHA-256と一致すること、`readyok`が出ること、および終了コードが0であることを確かめる。
このサイクル数が、ある負荷の1回の実行の5%を超える場合は、その負荷の深さまたは局数を増やしてから固定する。

最後に、最終測定のシードの列を固定する。教師生成は、対局番号を1から数え、対局のシードを`derive_seed(基本シード, 対局番号)`で導く。そのため、組の間で対局が重ならないように、組ごとの基本シードをK以上離す。
組の数の算定（基準どうし）では、組iの基本シードを`9030000000 + i×K`とする。最終測定では`9040000000 + i×K`とする。

完了条件は、スクリプトがそろい、負荷とシードの条件と、基準のコミットでの`refresh_fraction`が測定記録`nnue-finny-tables-setup.md`に書かれていることである。

### フェーズ1　探索ごとの表の実装

表を`SearchEvaluator::Simple`に持たせ、探索ごとに作る。根の累算値は全再計算で作り、その結果を表へ保存する。
テストは、表を必ず通る手順を組み立て、各段階の後で両視点の文脈と全成分を表を通らない`refresh`と比べる。
左右と先後で値が異なる重みを持つテスト用のネットを使い、鏡映や視点の取り違えを検出できるようにする。
各手順では、同じ項目を3回使う。1回目は初めての使用、2回目は保存時と異なる駒配置での使用である。3回目は、2回目と同じ駒配置で再び使って足し引きする行が0であることと、2回目と異なる駒配置で使って足し引きする行が2回目の駒配置との差だけであることを確かめる。これにより、項目の値と駒配置の両方が2回目の結果へ書き戻されたことを確かめる。テストでは、足し引きした行の数をテスト用の計数で読む。
手順では、次の場面を確かめる。

- 王将の移動で区分が変わる着手と、同じ区分のまま鏡映の有無が変わる着手を確かめる。
- 同じ着手を後手の視点でも確かめる。
- 占有升を変えずに駒が入れ替わる差として、成りと駒の取り替わりを確かめる。
- 先獅子の発生と消滅だけが差になる手順を確かめる。
- 2枚の駒を取る着手を確かめる。
- 両視点の文脈が同時に変わる着手として、王将で相手の王将を取り、相手に太子が残る着手を確かめる。
- 王将が取られて太子が基準になる手順と、王将がある側で醉象が成って太子が現れても文脈が変わらない手順を確かめる。
- 新しい文脈がない視点が生じる着手と、null moveを確かめる。

完了条件は、テストを含む検証が通ることである。

### フェーズ2　行数の診断

測定専用のコミットで、探索の根と、新しい文脈がある視点で文脈が変わるたびに、全再計算で足す行数Aと、表を使った場合に足し引きする行数Dを数える。
Aは`Indexer::row`が行を返す特徴の数であり、Dは保存した駒配置との差で実際に引く行と足す行の数の和である。有効印が偽の項目ではD=Aとする。新しい文脈がない視点は数えない。
同じ探索の並びについて、次の2つの方式を同時に模して集計する。

- 探索ごとの方式では、フェーズ1の製品と同じく、探索の開始時に表を空にし、根では全再計算して保存する。
- 保持の方式では、`HistoryTables`と同じ時機（「依存関係」の節の契機）にだけ表を空にし、根でも表を使う。

診断用の表は第1層の値を持たず、駒配置、先獅子の対象升、および有効印だけを持てばよい。差分の計算には製品の実装を使う。このコミットはmasterへ入れない。
負荷は、フェーズ0で固定した深さのHalfKP_vmのネットでの`bench`と、HalfKP_vmのネットでの教師生成である。教師生成は基本シード`9020000000`の20局を同時1局で生成し、1手2万ノードで集計する。参考として、同じ20局を1手2,000ノードでも集計する。
数える量は、項目を初めて使う回数、D=0の回数、D≥Aの回数、Σmax(D探索ごと − A, 0)、および次の2つの行数である。

- 探索ごとの表で減る行数S = Σ(A − D探索ごと)
- 保持によってさらに減る行数T = Σ(D探索ごと − D保持)

保持の方式で減る行数はS+Tになる。1手2万ノードの教師生成について、次のように判定する。

- S+T≤0なら、どちらの方式でも表は全再計算より行を減らさないので、フェーズ3とフェーズ4を行わずに完了（不採用）とする。
- S≤0<S+Tなら、行を減らすのは保持の方式だけなので、フェーズ3へ進む。
- S>0で10T≥Sなら、フェーズ3へ進む。10%は、保持のために増えるコード（ネットとの照合と消去の契機）に見合う効果の目安として置いた値である。
- それ以外は、フェーズ3を行わずにフェーズ4へ進む。

完了条件は、測定記録`nnue-finny-tables-row-counts.md`が書かれ、次に進むフェーズか、完了（不採用）かが決まっていることである。

### フェーズ3　対局内の保持（条件つき）

フェーズ2の判定でフェーズ3へ進む場合だけ行う。
表を`HistoryTables`へ移してワーカーごとに持ち、履歴の表と違って値を減衰させずに対局の間保持する。`SearchEvaluator::Simple`は探索の間だけ表を借りる。A型のネットで探索する場合は、表の本体を確保しない。
表の扱いは次のとおりである。

| 契機 | 扱い |
|---|---|
| 同じ対局の次の探索 | 保持し、根の両視点の累算値も表から作る |
| `HistoryTables::clear`を呼ぶ既存の契機と、`HistoryTables::new`による作り直し | 全項目の有効印を落とすか、作り直す |
| 探索の開始時に、ネットの印が表の保持する印と違う | 全項目の有効印を落とす。幅が違えば領域も作り直す |

テストには、フェーズ1の項目に加えて次を含める。

- 探索をまたいで根の累算値を表から作る手順を確かめる。
- 同じ`HistoryTables`で、同じ幅の別のネットと、異なる幅のネットへ交換した後の探索を確かめる。
- 複数のワーカーでの探索と、ワーカー数を変えた後の探索を確かめる。最善手は探索ごとに変わり得るので比べず、各ワーカーの累算値を表を通らない`refresh`と比べる。

完了条件は、テストを含む検証が通ることである。

### フェーズ4　最終測定

最初に、測定のためだけに入れた処理を取り除き、候補のコミットを凍結する。凍結したコミットで検証を通す。
基準は、本書のブランチの分岐元のmasterのコミットとする。
基準と候補の両方について、`invariants`機能なしの通常のreleaseビルドのバイナリを作り、SHA-256を記録して最終測定に使う。`invariants`機能つきのビルドは静的評価のたびに全再計算を追加するので、速度の測定には使わない。
凍結した後に実行コードを変えた場合は、変えた後の版で検証と最終測定をやり直す。

探索結果の一致は、次の2つで確かめる。

- 1ワーカーの`bench`の15局面それぞれで、深さ、ノード数、最善手、および評価値が基準と一致することを確かめる。HalfKP_vmのネットと、[評価関数の手引き](../../guides/evaluation-nnue.md)の「探索の測定に使う標準のネット」にあるA型のネットの両方で確かめる。
- 教師生成で、対局数、探索ノード数の合計、および教師のファイルのSHA-256が基準と一致することを、最終測定の各組で確かめる。教師生成は、バイナリのコミットではなく、実行時の作業ディレクトリのコミットをファイルに書く。そのため、基準と候補のバイナリを同じコミットの変更のない作業ディレクトリから起動し、実行のたびに空の出力先を使えば、探索結果が同じとき2つのファイルは一致する。

サイクル数は次の3つの負荷で測る。

| 負荷 | 役割 | 組ごとの値 | 条件 |
|---|---|---|---|
| HalfKP_vmのネットでの教師生成（1手2万ノード、K局、同時1局） | 主 | サイクル数の差 d = 候補 − 基準 | dの平均の両側95%信頼区間の上限が0未満 |
| HalfKP_vmのネットでの`bench`（フェーズ0で固定した深さ） | 従 | サイクル数の比の自然対数 r = ln(候補 ÷ 基準) | rの平均の片側95%信頼区間の上限がln(1.005)以下 |
| A型のネットでの`bench`（フェーズ0で固定した深さ） | 従 | 同上 | 探索結果が一致し、rの平均の片側95%信頼区間の上限がln(1.005)以下 |

組の数は、負荷ごとに、最初の候補の組を測る前に次の手順で固定する。

1. 基準のバイナリどうしで20組を測り、組ごとの値の標準偏差sを求める。教師生成では組の数の算定用のシードの列を使う。
2. 自由度n−1のt分布の分位点t(q, n−1)を使い、主の負荷ではt(0.975, n−1)×s÷√n ≤ 0.003×（基準のサイクル数の平均）、従の負荷ではt(0.95, n−1)×s÷√n ≤ ln(1.003)を満たす、20以上60以下の最小の偶数nを求める。満たすnがなければ60とする。
3. 結果を見て組を足すことはしない。

最終測定の信頼区間は、組の数の算定に使ったsではなく、候補と基準の組の値の標本標準偏差から求める。
組ごとに基準と候補の実行順を入れ替え、組の半数は基準を先に、残りの半数は候補を先に実行する。
主の負荷では、最初の8組を測った時点で、その8組から求めたdの平均の片側95%信頼区間の下限（自由度7）が0以上なら、候補はサイクル数を減らしていないと判断して測定を打ち切り、不採用とする。それ以外の場合は、打ち切らずにn組を測り終えてから一度だけ判定する。採用の側での途中の打ち切りはしない。

サイクル数の対比較は、性能コアの論理CPU（測定機では3番）に固定して次のように実行する。

```console
taskset -c 3 perf stat -x, -e cpu_core/cycles/u,cpu_core/instructions/u -- \
  <バイナリ> data selfplay generate --eval-file <HalfKP_vmのネット> --output-dir <空の出力先> --chunk-games <K> --games <K> \
  --seed <その組の基本シード> --nodes 20000 --random-moves 0 --concurrency 1 --hash-mb 16
taskset -c 3 perf stat -x, -e cpu_core/cycles/u,cpu_core/instructions/u -- \
  <バイナリ> --protocol usi < bench.usi
```

`bench.usi`は、`setoption name RuleSet value JCSA`、`setoption name EvalFile value <ネット>`、`isready`、`bench depth <深さ> threads 1 repetitions 1`、`quit`の5行である。
同じ区間で`cpu_core/LLC-load-misses/u`と`cpu_core/dTLB-load-misses/u`も採れる場合は記録し、行数の減少とサイクル数の減少が食い違ったときに原因を調べる手がかりにする。これらの値は判定に使わない。
測定の前に、`/sys/kernel/mm/transparent_hugepage/enabled`の値を記録し、対局の測定、探索の係数の自動調整（SPSA）、学習、および教師生成が同じ機械で動いていないことを確かめる（[教訓](../../lessons/check-running-measurements-before-cpu-load.md)）。
測定記録は`nnue-finny-tables-final.md`とし、組ごとの値、平均、信頼区間、および探索結果の一致を書く。
完了条件は、測定記録が書かれ、採否が決まっていることである。

## 検証

フェーズ1、フェーズ3、およびフェーズ4の凍結したコミットでは、次のコマンドがすべて通ることを確かめる。

```console
cargo fmt --check
cargo clippy --release --all-targets
cargo test --release
cargo test --release --features invariants
printf 'setoption name RuleSet value JCSA\nsetoption name EvalFile value <HalfKP_vmのネット>\nisready\nbench depth 9 threads 1\nquit\n' \
  | cargo run --release --features invariants --bin minase -- --protocol usi
```

`bench`の出力は`info string end`で終わり、終了コードが0でなければならない。
フェーズ4の探索結果の一致とサイクル数の対比較は、フェーズ0で用意したスクリプトで行う。

## 完了条件

本書は次のいずれかで完了する。

- フェーズ4で、探索結果の一致と、サイクル数の3つの条件をすべて満たした場合は、完了（採用）とする。フェーズ3を行わず探索ごとの表を採用した場合も、表の寿命は1つの候補の中の選択なので、完了（採用）とする。
- フェーズ2でS+T≤0だった場合、フェーズ4で主の負荷が打ち切りの条件に当たった場合、フェーズ4でサイクル数の条件を1つでも満たさなかった場合、または探索結果が一致しない原因を本書の範囲で直せない場合は、表のコードをmasterへ入れず、測定記録を残して完了（不採用）とする。

どちらの場合も、[設計書の書き方](../README.md)の「完了時の移し替えと凍結」に従う。採用した場合は、表の仕様をコードのdocコメントへ、採否の判断をADRへ移してからmasterへ統合する。

# AWSのEC2での教師生成

## 先に読む要約

本計画では、中将棋の教師データの生成をAWSのEC2へ移し、開発に使っている作業機より短い時間で、作業機を占有せずに生成を終えられるようにする。
教師データは、自己対局の各局面に探索値や対局結果を付けた学習用のデータであり、既存の生成コマンド`minase data selfplay generate`がシード範囲1つにつきファイル1本を書く。
生成機では、このコマンドをシード範囲ごとに順に実行し、検査に通ったファイルをAmazon S3へ送る。
S3にファイルがあることをそのまま完了の記録とし、生成機が途中で止まった場合は、同じ計画で再起動してS3にないシード範囲だけを生成し直す。
機種はAMD EPYC Turinの物理192コアを持つc8a.48xlarge、リージョンはオンデマンド価格が最も安い米国東部を第一候補とし、30ファイルの生成を約3時間、約30米ドルと見積もる。
購入方式は、中断のないオンデマンドとし、AWSの都合で中断され得る代わりに安価なスポットは、節約額が小さいので採らない。
見積もりは公開ベンチマークから導いた推定なので、本生成の前に候補機種で20分程度の試走を行い、作業機より速いことを実測で確かめる。
完了条件は、作業機より速い生成を実サービスで確認し、生成機を途中で止めても確定済みのファイルの欠落と重複が起きないことである。

## 状態

状態は起案であり、起案日は2026年10月16日である。
実装には未着手である。
次の一手は、利用者の許可を得てAWSのvCPU上限を確認し、必要なら引き上げを申請したうえで、フェーズ0の試走で機種を確定することである。

## 目的

作業機（Intel Core Ultra 7 265KF、Pコア8＋Eコア12の20スレッド）では、教師生成と棋力測定が計算資源を取り合い、30ファイルの生成に約35時間かかる。
教師生成をEC2へ移し、作業機より短い時間で生成を終えることが第一の目的である。
費用は、生成1回あたりの金額が作業機の占有時間と見合う範囲に収める。
速度で作業機に劣る機種は、費用が安くても採用しない。

## 適用範囲

対象は、`minase data selfplay generate`による、乱数で開始局面を作る自己対局の教師生成である。
生成機は1実行につき1台とし、1つのファイルの中で`--concurrency`によって複数の対局を並列に進める。
S3への保存、作業機への回収、および同じ計画での再開までを実装対象とする。

探索、教師データ形式MNSD版2、および学習器は変更しない。
対局の途中状態の保存、実戦棋譜からの生成、複数台への作業配布、および学習中の重みの再開は対象外とする。
作業機で追加生成した結果をS3へ送る操作も設けない。作業機で続ける場合は、新しいシード範囲の別の実行として手引きどおりに生成する。

## 依存関係

教師データの構造と検査は、[MNSD版2の実装](../../crates/minase/src/training/records.rs)と[生成・検査コマンド](../../crates/minase/src/bin/minase/selfplay_gen/)を使う。
学習器は複数の完成ファイルを入力できるため、ファイルを1つへ連結する必要はない。
生成条件と過去のシード範囲の確認は、[教師生成の手引き](../guides/pst-training.md)に従う。
生成コマンドはヘッダの生成コミットを`git rev-parse HEAD`で取り、作業ツリーが汚れていれば停止するので、生成機にも固定コミットのGit作業コピーが要る（[生成コミットを固定する教訓](../lessons/pin-generation-binary-to-worktree.md)）。

[メモリより大きい教師データの一様シャッフル](out-of-core-shuffle.md)は、生成後のデータを学習する側の計画であり、本計画は同計画の完了を前提にしない。

## 設計判断

| 論点 | 採る方式と理由 | 採らない方式と理由 |
|---|---|---|
| 計算機の調達先 | AWSのEC2。物理192コアのx86-64機を1台で借りられ、S3と同じ口座で費用を管理できる。 | RunpodのCPU Podは1台あたり最大32 vCPU（2026年10月16日にAPIで確認。プラン`cpu3c`が0.03米ドル、`cpu5c`が0.035米ドル/vCPU時）であり、1台では作業機の数倍に届かない。 |
| 機種 | c8a.48xlarge（AMD EPYC 9R45、物理192コア、SMTなし）。公開ベンチマークの1スレッド性能が候補の中で最も高く、1ファイルあたりの費用は他の候補と同程度である。 | c7a（EPYC 9R14）は1スレッド性能が約2割低い。c8i（Xeon 6）はvCPUがハイパースレッドで、1コアに2対局を載せる分だけ遅い。c8g（Graviton4）は費用が同程度で速度が劣り、aarch64のビルドが要る。 |
| リージョン | 米国東部（us-east-1またはus-east-2）。オンデマンド価格が最も安く、転送量は無料枠に収まるので、対局データの往復に距離は関係ない。 | 東京（ap-northeast-1）はオンデマンドが約26%高く、速度の利点がない。大阪にはc8aがない。 |
| 購入方式 | オンデマンド。生成1回の費用が約30米ドルなので、スポットの節約額は約15米ドルにとどまり、再開の待ち時間と在庫の不確実さに見合わない。 | スポットは採らない。大型の機種はスポットの在庫がなく起動できないことがあり、中断の頻度帯が20%を超えるプールもある。必要になれば、インスタンスの購入方式の属性1つを変えるだけで切り替えられる。 |
| 再開の単位 | シード範囲1つにつきファイル1本という既存の生成単位をそのままバッチとし、S3にファイルがないシード範囲だけを生成し直す。1回の中断で失う計算は最大1ファイル分（c8a.48xlargeで約6分）である。 | 対局や探索の途中状態の保存は、保存対象と復元条件を増やすので入れない。試行ごとのディレクトリと完了記録ファイルも、検査に通らなかった試行は何も送らないので要らない。 |
| 完了の記録 | 検査に通った教師ファイルをS3へ最後に送り、そのオブジェクトの存在を完了とする。送信は既存キーを上書きしない条件付きで行う。 | 別の完了記録ファイル、バケットポリシーによる条件付き書き込みの強制、およびローカルとS3の間の競合検出は、本計画が禁じる2台同時実行を防ぐためだけの仕組みなので設けない。 |
| 実行環境 | 生成機の起動時に、固定した版のRustツールチェーンを入れ、固定コミットをcloneして`target-cpu=native`でビルドする。依存はCargo.lockとツールチェーンの版で固定され、ヘッダの生成コミットは作業コピーから記録される。 | Dockerイメージの作成、S3への保管、イメージの検査和の照合、およびCPU適合の検査は、ビルドを1回に減らすための仕組みであり、ビルドが数分で終わる192コア機には要らない。 |
| AWS資源の管理 | S3バケットは計算機の寿命の外で1回だけ作る。計算機側はTerraformの構成1つ（IAMロール、インスタンス、起動スクリプト）とし、既定VPCと既定のセキュリティグループを使う。 | 専用VPC、S3のgateway endpoint、EventBridgeによる終了予定、Systems Managerの接続、および状態ファイルの喪失に備えるタグ運用は、受信接続の要らない使い捨ての1台には過剰である。 |
| 費用の上限 | 起動スクリプトの先頭で`shutdown -h +<分>`を予約し、OS停止時の動作を終了にする。 | 外部のスケジューラによる終了は、起動スクリプトが動かない場合にも効くが、その場合はインスタンスが課金されるだけで生成もされず、作業機から1回の確認で片付く。 |

## 機種、リージョン、費用

### 見積もりの土台

作業機の実測は、[初代NNUEの教師生成](../measurements/nnue-replacement-generation.md)の20ファイル（7,500局、1局面20,000ノード、同時12局）に22.87時間かかった記録を使う。
1ファイルあたり1.14時間、30ファイルで約35時間である。
記録は57.9M局面であり、1局面160バイトなので1ファイル約460 MB、30ファイルで約14 GBになる。

候補機種の1スレッド性能は、PassMarkの単一スレッド評価（2026年9月8日時点）で、作業機のPコア（Core Ultra 7 265K、4,928）に対する比として次のとおりである。
EPYC 9R45（c8a）が0.77、EPYC 9R14（c7a）が0.59、Xeon Platinum 8488C（c7i）が0.63である。
Graviton4（c8g）はPassMarkに記載がなく、Geekbench 6の単一コアがc7aの約0.92倍なので0.54とした。
Xeon 6（c8i）の該当品番も記載がないので、見積もりから外す。
作業機の同時12局にはEコアも含まれるが、すべてPコアで動くとみなして作業機の性能を過大に見積もる。一方、PassMarkの値は1スレッドだけを動かしたときの値であり、AWSはc8aの全コア稼働時の周波数を公表していないので、192コアを同時に使うと1コアあたりの速度は下がり得る。同時12局から192局への外挿も、メモリとキャッシュの競合を含まない。以下の倍率はこの両方向の不確かさを持つ推定であり、採否はフェーズ0の実測で決める。

### 候補の比較

価格はAWSの価格表（2026年10月版）のus-east-1のLinuxオンデマンドであり、同じインスタンスファミリーの中ではvCPU数に比例する。
スポットはinstances.vantage.shの平均値（2026年10月16日参照）であり、プールと時刻で変わる。

| 機種 | vCPU | vCPUの実体 | 作業機比 | 1ファイル | 30ファイル | オンデマンド/時 | 30ファイルの費用 | スポット平均/時 |
|---|---|---|---|---|---|---|---|---|
| c8a.48xlarge | 192 | 物理コア | 約12倍 | 約6分 | 約2.8時間 | 10.35米ドル | 約29米ドル | 5.07米ドル |
| c8a.24xlarge | 96 | 物理コア | 約6倍 | 約11分 | 約5.6時間 | 5.17米ドル | 約29米ドル | 記載なし |
| c7a.48xlarge | 192 | 物理コア | 約9倍 | 約7分 | 約3.6時間 | 9.85米ドル | 約36米ドル | 3.58米ドル |
| c8g.48xlarge | 192 | 物理コア（aarch64） | 約9倍 | 約8分 | 約4.0時間 | 7.66米ドル | 約30米ドル | 2.64米ドル |

同じインスタンスファミリーでは1ファイルあたりの費用が機種の大きさに依らないので、速度を優先して最大のc8a.48xlargeを採る。
東京でc8a.48xlargeを使うと、オンデマンドは13.02米ドル/時で30ファイルが約36米ドルになり、速度の利点なしに約7米ドル高い。
S3の保存は0.023米ドル/GB月なので14 GBで月0.3米ドル、インターネットへの転送は月100 GBの無料枠に収まる。
20分の試走は、c8a.48xlargeのオンデマンドで約3.5米ドルである。

### 実行前の確認

AWSは、1リージョンで同時に動かせるオンデマンドの標準インスタンスの合計vCPU数にアカウントごとの上限を設けており、新規アカウントの既定値は5である。
c8a.48xlargeは1台で192 vCPUを消費するので、試走の前に`aws service-quotas get-service-quota --service-code ec2 --quota-code L-1216C47A`で現在値を確認し、192未満なら引き上げを申請する。
AWSは審査の所要時間を公表していない。

## 生成と保存

### 生成計画

実行ごとに`run_id`を決め、S3の`<バケット>/<run_id>/`の下に次の配置で保存する。

| キー | 内容 |
|---|---|
| `plan.tsv` | 1行に1ファイル分の`名前`、`シード`、`局数`をタブ区切りで並べる。 |
| `conditions.env` | 生成コミット、Rustツールチェーンの版、ノード上限、手数上限、置換表容量、ランダム着手、期待する規則コード列、および期待する重みの検査和を、シェル変数として1行ずつ書く。規則は生成コマンドが`engine-default`に固定しており変更できないので、`inspect`の`rule_set`と比べる期待値である。重みの検査和は`inspect`の`network_checksum`（重みファイルのヘッダを除いた本体のSHA-256、16進表記）と比べる期待値であり、作業機で同じコミットのビルドによる短い生成の`inspect`出力から写す。 |
| `teacher/<名前>.mnsd` | 検査に通った教師ファイル。存在が完了の記録である。 |
| `logs/<名前>.log` | 生成の標準出力・標準エラーと`inspect`の出力を連結したもの。 |
| `logs/boot.log` | 起動スクリプトのログ。 |

計画をTOMLではなくタブ区切りと環境変数ファイルにするのは、起動スクリプトと`run.sh`がシェルだけで読めるようにするためである。
シードは互いに局数以上離し、過去の生成と重ならないことを手引きの手順で確認する。
`plan.tsv`と`conditions.env`は既存キーを上書きしない条件で送り、同じ`run_id`の計画は変更しない。条件を変える場合は新しい`run_id`で別の実行にする。
`--concurrency`は生成機のスレッド数に合わせる実行時の値であり、Terraformの変数から起動スクリプトを経て`run.sh`の引数として渡す。省略時の既定値は置かず、省略はエラーにする。
`run.sh`は生成を始める前に計画全体を読み、名前の一意性、列数、シードと局数の値の範囲、および`conditions.env`の必須項目の有無を検査し、不正なら停止する。名前が重複すると、先の行の送信後に後の行が完了として飛ばされるからである。

### 生成機での手順

生成機のOSにはAmazon Linux 2023を使い、起動スクリプト（EC2のuser-data）は次を順に行う。
user-dataは初回起動時にしか実行されないので、再開はインスタンスの再起動ではなく`terraform apply`による再作成で行う。

1. `shutdown -h +<分>`で費用上限の停止を予約する。分数は、ビルドを含む総時間としてフェーズ0の実測から決める。起動スクリプトのログは、60秒ごとにバックグラウンドで`logs/boot.log`へ送り、期限切れで終了しても直前までの記録が残るようにする。
2. Amazon Linux 2023に同梱のAWS CLIで`plan.tsv`と`conditions.env`を取り、生成コミットとツールチェーンの版を読む。
3. `dnf`でgitとgccを入れ、`rustup-init`でその版のツールチェーンを最小構成で入れる。GitHubの公開リポジトリから生成コミットをcloneし、リポジトリの`.cargo/config.toml`にある`target-cpu=native`のまま`cargo build --release --locked --bin minase`を実行する。評価関数の重みは実行ファイルに埋め込まれるので、別に配布しない。
4. `run.sh`を呼ぶ。`run.sh`は計画を検査した後、行ごとに`teacher/<名前>.mnsd`の有無を`head-object`で調べ、404なら生成し、200なら飛ばし、それ以外の応答は停止する。
5. 生成コマンドは、カレントディレクトリを生成コミットの作業コピーにしたまま実行する。生成コマンドはカレントディレクトリで`git rev-parse HEAD`と`git status`を実行するからである。`--allow-dirty`は付けない。出力とログは行ごとに新しく作る作業コピー外の一時ディレクトリへ絶対パスで書く。生成コマンドは出力を新規作成でしか開けず、失敗時に出力を削除するので、強制終了で残った途中のファイルが次の試行に影響しない。
6. 生成プロセスの終了コード0と、要約の`games_completed`、`nodes`、`max_ply`、`hash_mb`、`random_moves_max`が計画と一致することを確かめる。続いて`inspect`を実行し、その終了コード0を確認してから、ヘッダの`generation_commit`、`rule_set`、`seed`、`teacher_search_budget`、および`network_checksum`が`conditions.env`と`plan.tsv`に一致すること、ならびにヘッダの`game_count`と生成要約の`games_discarded_max_ply`の和が要求局数と一致することを検査する。生成と`inspect`の失敗は、ログを`tee`で取る場合もそれぞれ保持する。
7. ログを`logs/<名前>.log`へ送り、最後に教師ファイルを`put-object`で、`--if-none-match '*'`と、ファイル全体のSHA-256をBase64表記にした`--checksum-sha256`を付けて送る。教師ファイルは5 GBを超えないので、分割送信は使わない。既存キーの違反（412）を受けた場合は、応答の喪失後の再試行で既に確定している可能性があるので、`head-object --checksum-mode ENABLED`が返す`ChecksumSHA256`と比べ、一致すれば完了として扱い、異なるか欠けていれば停止する。
8. `run.sh`は一覧を終えるか、いずれかの確認に失敗した時点で終了コードを返して止まる。失敗時は次のファイルへ進まない。起動スクリプトは`run.sh`の終了後に`logs/boot.log`を送ってOSを停止する。OSの停止を`run.sh`に含めないのは、作業機から実行して検証するためである。

要求した全局が手数上限で破棄された場合も、正常終了と件数の照合ができれば、保存局数0の完了ファイルとして扱う。
手数上限で破棄した対局も予約したシード範囲を消費するので、保存局数の不足を理由に同じ実行の局数やシードを増やさない。

### 回収

作業機では`aws s3 sync`でS3上の`<run_id>/`を取得し、`head-object --checksum-mode ENABLED`が返すBase64表記の`ChecksumSHA256`とローカルの計算値を照合し、`inspect`で検査してから学習の入力に使う。
`fetch.sh`は`plan.tsv`の全行を基準にし、S3に教師ファイルがない名前は、ログの有無にかかわらず未完了として報告する。学習に渡す一覧には、S3上の存在と作業機での検査を確認したファイルだけを`plan.tsv`の順に載せ、未完了の名前が1つでもあれば0以外の終了コードを返す。
S3のデータは回収後も残し、削除は手作業とする。

## 操作の入口

スクリプトは`scripts/aws-selfplay/`に置く。

| 操作 | 内容 |
|---|---|
| `run.sh` | 生成機の起動スクリプトから呼ばれ、「生成機での手順」の4から8のうち`run.sh`の担当分を行う。引数はバケット、`run_id`、作業コピーのパス、および並列度である。OSを停止せず終了コードを返すので、作業機から実行して検証にも使う。 |
| `fetch.sh` | S3上の`<run_id>/`を作業機へ取得し、SHA-256と`inspect`で検査する。 |
| Terraform（`infra/aws-selfplay/`） | `terraform apply`で生成機を起動し、`terraform destroy`で片付ける。変数はバケット、`run_id`、機種、リージョン、停止までの分数、および並列度である。生成コミットとツールチェーンの版は`conditions.env`から読むので変数にしない。 |

バケットは1回だけ作る。作成はAWS CLIの1コマンドで済み、Terraformの管理対象にしない。
バケットにはパブリックアクセスの遮断を設定し、インスタンスのIAMロールには当該バケットの一覧、読み取り、および書き込みだけを許す。一覧の権限がないと、存在しないキーへの`head-object`が404ではなく403を返し、手順4の判定が崩れる。削除の権限は与えない。
インスタンスは既定VPCのパブリックサブネットに置き、GitHubとS3へ到達するためにパブリックIPv4を付ける。受信規則は設けず、SSH鍵も作らない。
ルートボリュームは、ツールチェーンとリリースビルドの成果物に加えて送信前の教師ファイルを置けるよう、gp3の50 GBとし、終了時に削除する。
OS停止時の動作は終了にする。Amazon Linux 2023の`shutdown -h`は電源断に対応するので、予約した期限が来るとインスタンスは終了する。

## 実装フェーズ

フェーズ0では、c8a.48xlargeをオンデマンドで20分ほど借り、`minase dev bench`の1スレッドの探索速度（NPS、1秒あたりのノード数）と、同時対局数をスレッド数に合わせた1ファイル（7,500局）の生成の所要時間と記録局面/秒を測る。
作業機では、他の処理を止めた状態で同じ測定を行う。
ファイルの終わりで長い対局だけが残ってスレッドが空く時間も測り、無視できない場合は1ファイルの局数を増やす。
同じシード範囲を作業機と生成機で生成して教師ファイルの内容を比べ、差があれば測定記録に残す。この比較は完了条件に含めない。
完了条件は、機種、リージョン、並列度、1ファイルの局数、停止までの分数、および生成1回の費用見積もりが実測に基づいて確定していることである。

フェーズ1では、`run.sh`と`fetch.sh`を実装し、作業機から本番と同じバケットの試験用の`run_id`に対して、小さい局数の計画で「検証」の最初の6条件を通す。
保存先をローカルのディレクトリに切り替える経路は設けず、検証も実際のS3の経路で行う。
完了条件は、「検証」の最初の6条件を通すことである。

フェーズ2では、Terraformの構成と起動スクリプトを実装し、AWS上で本生成と同じ条件の小規模な実行を行う。
完了条件は、生成機をコンソールから終了させた後に`apply`で再作成し、確定済みのファイルを再生成せずに完走して`fetch.sh`で回収できること、および停止までの分数を短くした起動で期限どおりに終了することである。

フェーズ3では、`docs/guides/aws-selfplay.md`に準備、起動、停止、回収、費用の確認、および片付けの手順をまとめ、試走の測定を`docs/measurements/aws-selfplay-trial.md`へ記録する。
永続的な仕様をスクリプトの冒頭の説明へ、設計判断をADRへ移してから本書を凍結する。

## 検証

| 条件 | 期待する結果 |
|---|---|
| 複数ファイルの計画を中断せず実行する。 | 計画した全ファイルが1回ずつ保存され、要求局数と保存・破棄局数が整合する。 |
| 名前が重複する計画、列数の足りない計画、および必須項目の欠けた`conditions.env`を与える。 | 生成を始める前に停止する。 |
| 生成中と送信中に`kill -9`し、同じ計画で再開する。 | 保存済みのファイルは再生成されず、未保存の名前だけが同じシードで再実行される。途中のファイルはS3に現れない。 |
| 生成が異常終了した0局のファイルと、全局を正規に破棄した0局のファイルを用意する。 | 前者は送られず、後者は要求・破棄局数が一致する完了ファイルとして送られる。 |
| 既にS3にある教師ファイルと同じキーへ、同じ内容と異なる内容を送る。 | 同じ内容は検査和の一致により完了として扱われ、異なる内容は停止する。既存のファイルは変わらない。 |
| 存在しないキーの`head-object`を、一覧の権限がないロールで呼ぶ。 | 403で停止し、再生成に進まない。 |
| 生成機をAWSのコンソールから終了し、`apply`で再作成する。 | 残りの名前だけを生成して完走する。 |
| 停止までの分数を短く設定して起動する。 | 期限でインスタンスが終了し、確定済みのファイルと`logs/boot.log`は残る。 |

## 完了条件

フェーズ0の実測で、採用した機種の記録局面/秒が作業機を上回っていること。
生成、S3への保存、作業機への回収、および再開をスクリプトから行え、「検証」の各条件を満たしていること。
試走の時間、費用、および転送量の記録と、同じ操作を再現できる手引きがあること。
仕様と設計判断の移し替えを終え、`docs/ROADMAP.md`の状態を更新して本書を凍結していること。

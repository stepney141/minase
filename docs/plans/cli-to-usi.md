# 起動引数と診断ツールをUSIへ移す設計書

## 先に読む要約

本マイルストーンは、minaseへの情報の渡し方と診断機能の呼び出し方を、プロセスの起動時のコマンドライン（以下CLI）から、起動後の通信プロトコルへ移す。
minaseは、GUIや対局用のプログラムと、USI（Universal Shogi Interface、将棋エンジンの標準の通信プロトコル）またはCECP（Chess Engine Communication Protocol、チェス系のGUIであるXBoardが使う通信プロトコル）で対話するエンジンである。
現在は、対局の規則と、AlphaZero型探索が局面の評価に使うニューラルネット（以下ネット）のファイルを起動引数でしか渡せず、合法手の経路数を数えるperftや固定局面で探索の速度を測るbenchは、エンジンとは別のサブコマンドとしてしか呼べない。
本書の方針は、USIで渡せる情報と呼べる機能はすべてUSIへ移し、CLIにはUSIへ移せないものだけを残すことである。
移す対象は、起動引数`--rules`と`--nn-model`、およびサブコマンド`dev perft`、`dev bench`、`dev nn-eval`、`dev nn-fixture`、`dev random-play`の7つである。
CLIに残すのは、起動引数`--protocol`、`--search`、`--io-log`と、対局測定、係数調整、学習データの生成と集計、および校正用のランダム着手エンジンのサブコマンドである。

規則セットとは、対局に採用する規則コードの組であり、規則コードは、規則書`docs/rules/chu-shogi.md`の第33条が定める、獅子の規則（L）、成りの規則（P）、反復の規則（R）、および駒枯れの規則（E）の4群の記号である。
規則セットは既定値をなくして、USIのオプション`RuleSet`、またはCECPの`option RuleSet=`による指定を必須にし、あわせて、規則コード列`L0,P0,R1,E0`を表す規則セット名`engine-default`を、`JCSA`（Japan Chu Shogi Association、日本中将棋連盟の略）へ改名する。

探索の内容は変えないので、棋力の測定は行わず、移す前後でbenchの局面ごとのノード数と各診断の出力が一致することを確かめる。
完了条件は、移した機能がUSIから移す前と同じ結果を返すこと、移した起動引数とサブコマンドが削除されていること、呼び出し側のスクリプトと文書が新しい呼び出し方に揃っていること、および設計判断がADR（設計判断の記録）へ移されていることである。

## 目的

minaseのエンジンは、サブコマンドなしの`minase --protocol <usi|cecp> --rules <規則>`で起動する。
現在は、次の情報と機能がCLIに置かれている。

- 対局の規則セットは起動引数`--rules`が必須であり、USIのオプション`RuleSet`と二重に指定できる。
- minaseは、ニューラルネットの評価関数であるNNUEを使うαβ探索と、AlphaZero型探索のMCTS（モンテカルロ木探索）の2つの探索方式を持つ。MCTSが使うネットは、起動引数`--nn-model`でしか指定できない。
- perft、bench、ネットの出力の照合、照合用の固定局面集の生成、およびランダム対局による不変条件の検査は、`minase dev <名前>`のサブコマンドとしてしか呼べない。

この配置には3つの不都合がある。
1つ目は、同じ情報の入口が2つあることである。
規則は`--rules`と`RuleSet`の両方で渡せる。
`dev nn-eval`の3つの引数（推論を実行する基盤である実行プロバイダ、1回の推論にまとめる局面数であるバッチの大きさ、およびキャッシュの場所）と、`dev random-play`の`--rules`は、エンジンがすでに持つUSIのオプションと同じ内容である。
`dev nn-eval`のネットの引数も、本書が加えるオプション`NnModel`と同じ内容になる。
2つ目は、エンジンを起動する側が引数の組み立てを知る必要があることである。
引数を渡せないLishogi-Bot（オンライン対局サイトlishogiとエンジンを仲介するプログラム）のために、配備用のリポジトリは引数を固定した起動用のスクリプトを置いている。
3つ目は、診断がエンジンのセッションの設定を使えないことである。
`dev perft`は、USIの`position`コマンドで復元した局面をそのまま数えられず、局面をSFEN（局面の文字列表記）に書き出して別のプロセスへ渡す必要がある。
`dev nn-eval`は、対局に使う推論器（ネットを読み込んで局面を評価する部品）とは別に、引数から推論器を組み立て直している。

本マイルストーンは、エンジンの設定と、エンジンの実装を検証する診断を、起動後のプロトコルへ集める。
CLIには、プロトコルが始まる前に決まっていなければならない情報と、エンジンを外から制御する道具だけが残る。

## 適用範囲

本マイルストーンでは、次の作業を行う。

- 規則セット名`engine-default`を`JCSA`へ改名する。`minase-core`の定数`Rules::ENGINE_DEFAULT`を`Rules::JCSA`へ改名し、規則を明示せずに対局を作る`Game::with_default_rules()`を削除する。規則書`docs/rules/chu-shogi.md`を第17版へ改める。
- 起動引数`--rules`を削除し、USIの`RuleSet`とCECPの`option RuleSet=`による指定を必須にする。エンジンは規則の既定値を持たない。
- 起動引数`--nn-model`を削除し、MCTSで起動したときだけ宣言するUSIのオプション`NnModel`を加える。
- MCTSで起動したときのUSIの独自コマンド`eval`を、NNUEの内訳ではなくネットの出力を表示するよう定義し直す。
- USIの独自コマンド`perft`、`bench`、`nn-eval`、`nn-fixture`、`random-play`を加え、対応するサブコマンドを削除する。
- エンジンどうしを対局させて棋力を測る対局ハーネス`minase match run`と、係数調整`minase spsa`がエンジンを起動するときの固定の引数から`--rules`を外す。`match run --rules`は既定値をなくし、新規の実行で必須にする。校正用のランダム着手エンジン`minase dev usi-random`の`RuleSet`の既定値も削除する。
- 対局ハーネスが、エンジンの返すネットのチェックサムを実行条件に記録し、対局の開始時と再開時に一致を確かめる。
- エンジンを起動する`scripts/`のスクリプト、benchを呼ぶスクリプト、および学習の実行器`tools/train/zero/minase_zero/runner.py`を、新しい呼び出し方へ改める。
- 利用者向けの文書（`README.md`、`CONTRIBUTING.md`、`docs/guides/`）を改め、完了時に設計判断をADRへ移す。

次の項目は対象外とする。

- 起動引数`--protocol`、`--search`、`--io-log`は残す。理由は「設計判断」節にある。
- 環境変数`ORT_DYLIB_PATH`（ONNX Runtimeの共有ライブラリの場所）は残す。理由は「設計判断」節にある。
- サブコマンド`match run`、`match report`、`spsa`（`apply`と`params`を含む）、`data`の6本（`selfplay generate`、`selfplay inspect`、`zero-selfplay`、`teacher-stats`、`lishogi games`、`lishogi openings`）、および`dev usi-random`は残す。理由は「設計判断」節にある。
- CECPには診断のコマンドを加えない。開発用GUIと対局ハーネスはminaseとUSIで接続し、既存の診断用の独自コマンドである`d`（局面の表示）、`eval`（評価の内訳の表示）、`tt`（置換表の項目の表示）もUSIだけに置いている（[ADR](../adr/show-position-evaluation-and-tt-as-usi-commands.md)）。
- ビルドのフィーチャや現在の設定値を照会するコマンドは加えない。CLIにも存在しない新しい機能であり、本書の目的である移行に当たらない。
- NNUEの重みを外部のファイルから読むオプションは加えない。重みは実行ファイルへの埋め込みだけで運用しており、差し替える用途がない。
- MCTSの速度を測るbenchは加えない。`bench`は移す前と同じαβ探索の測定である。
- 開発用GUI（`minase-gui`）とlishogi Botの配備一式（`minase-lishogi-bot`）は別のリポジトリであり、本書では必要な変更を「関連リポジトリへの影響」節に挙げるにとどめる。

## 依存関係

USIの状態機械、`position`の扱い、および規則を次局から確定する仕組みは[プロトコル層](archived/protocol-layer.md)と[ADR](../adr/commit-pending-rules-on-first-position.md)が定める。
探索方式を起動時に選ぶ構造と、探索器の境界`Searcher`は[ADR](../adr/select-the-search-method-at-startup-through-a-closed-enum.md)が定める。
ネットの読み込みと推論器は`crates/minase/src/nn/onnx.rs`にあり、対局ハーネスが、比べる2つのエンジン（候補と基準）へUSIのオプションを送る仕組みは[ADR](../adr/pass-usi-options-to-match-engines-and-record-them-in-the-manifest.md)が定める。
本書は完了済みのマイルストーンだけを前提とする。

進行中または起案中のマイルストーンとは、次の点で順序を調整する。

- [AlphaZero型探索の強化学習の2回目の実行](alphazero-rl-2.md)は、学習の実行器が`minase dev nn-eval`を各サイクルで呼ぶ。実行器とエンジンの実行ファイルは同じコミットから取るので、2回目の実行が進行中の間は、その実行が使うworktreeへ本書の変更を取り込まない。
- [詰み探索](mate-search.md)は`go mate`をUSIに実装する。本書は`go`の引数の検査を変えないので、どちらを先に進めてもよい。
- 対局ハーネスの記録形式の版を上げるので、本書のフェーズ2をマージする時点で、再開を予定している実行が残っていないことを確かめる。

## 設計判断

採った方式と、棄却した代案を次の表に示す。
各項目の詳細は後の節にある。

| 項目 | 採った方式 | 棄却した代案と理由 |
|---|---|---|
| 配置の基準 | 実行中のエンジンのセッションについて、構成の設定、状態の観測、または計算の実装の検証を行う操作をUSIへ移す。プロセスの起動条件、別のエンジンの起動、実験全体の管理、およびデータ一式の生産と集計はCLIに残す。 | 「標準入力からコマンドとして呼べるものはすべて移す」基準は採らない。どの処理にも当てはまるので、配置を決める基準にならない。 |
| 規則の既定値 | 既定値を持たず、`RuleSet`の指定を必須にする。 | `RuleSet`の既定値を`JCSA`にする案は採らない。指定漏れのまま、意図しない規則で対局が始まる。起動時に規則を明示させる現在の契約を、プロトコルの側で保つ。 |
| 規則の未設定の検出 | `isready`で検査し、未設定ならエラーの行を出して終了コード1で終える。 | 最初の`position`で検査する案は採らない。Lishogi-Botと対局ハーネスはどちらも`usi`、`setoption`、`isready`の順に送るので、`isready`のほうが早く、1か所で検出できる。エラーの行だけを返して待つ案は、`readyok`を待つ相手が止まるので採らない。 |
| 規則セット名 | `engine-default`を`JCSA`へ改名し、旧名の別名は置かない。 | 旧名も受理する案は、同じ規則セットに2つの名前を残すので採らない。 |
| ネットの指定 | MCTSで起動したときだけ宣言するオプション`NnModel`で指定し、`isready`で読み込む。 | 起動引数のまま残す案は採らない。[元のADR](../adr/archive/select-zero-networks-by-startup-argument-and-embed-only-the-judged-one.md)が起動引数を選んだ理由は、対局ハーネスが任意のオプションを送れないことだったが、`--candidate-option`の追加で解消している。 |
| 探索方式の選択 | 起動引数`--search`のまま残す。 | USIのオプションにする案は採らない。理由は「CLIに残すもの」節にある。 |
| 入出力の記録 | 起動引数`--io-log`のまま残す。 | USIのオプションにする案は採らない。理由は「CLIに残すもの」節にある。 |
| 診断の実行方法 | 探索していないときに同期で実行し、各行に`info string`を付けて`info string end`で終える。 | 探索と同じ別スレッドで実行して`stop`を受け付ける案は採らない。診断は対局中に送るものではなく、停止の経路を持つ費用に見合う用途がない。 |
| 診断の失敗の通知 | 引数の誤りはエラーの行を出してセッションを続け、実行時の失敗はエラーの行を出して終了コード1で終える。 | すべての失敗でセッションを続ける案は採らない。スクリプトが終了コードで失敗を検出できなくなる。 |
| 引数の渡し方 | 診断はUSIの独自コマンドとして受ける。 | Stockfishのように起動引数の列を1つのコマンドとして実行する方式は採らない。引数の解析に失敗した入力をプロトコルのコマンドとして解釈する経路ができ、打ち間違いを検出できなくなる。 |
| ネットの同一性 | 対局ハーネスは、エンジンが`isready`で返すネットのチェックサムを実行条件に記録し、対局の開始時と再開時に一致を確かめる。不一致なら測定を止める。 | パスだけを記録して、ファイルを上書きしない運用に頼る現在の方式は続けない。書き換えを検出できない。ハーネスがオプションの値をパスとして読んでチェックサムを計算する案は採らない。どのオプションがネットを指すかをハーネスが知ることになる。不一致をその側の反則負けにする案は採らない。測定の条件が崩れたことを、勝敗の統計に混ぜてしまう。 |
| 過去の記録 | 対局ハーネスの記録形式の版を7から8へ上げ、版7の読み込みや変換は作らない。 | 版を据え置く案は採らない。コミットから作るエンジンの起動引数の欄の意味が変わるので、版7の実行を新しいハーネスで再開すると、記録と異なる引数でエンジンを起動する。 |

配置の基準に照らすと、各項目は次のように分かれる。

| 配置 | 項目 | 理由 |
|---|---|---|
| USIへ移す | `--rules` | セッションの規則の設定である。 |
| USIへ移す | `--nn-model` | セッションの推論の設定である。 |
| USIへ移す | `dev perft` | セッションの局面と規則で合法手生成を検証する。 |
| USIへ移す | `dev bench` | エンジンの探索の実装を固定の条件で測る。 |
| USIへ移す | `dev nn-eval` | セッションの推論器の出力を固定局面で検証する。引数のうち3つが既存のオプションと重複し、残るネットの引数は`NnModel`と重複する。 |
| USIへ移す | `dev nn-fixture` | エンジンの入力の符号化と着手のラベルの参照出力を取り出す。 |
| USIへ移す | `dev random-play` | セッションの規則で合法手の適用の不変条件を検証する。`--rules`が`RuleSet`と重複している。 |
| CLIに残す | `--protocol` | どのプロトコルで入力を解釈するかは、プロトコルが始まる前に決まっている必要がある。 |
| CLIに残す | `--search` | 握手（接続の直後に、エンジンが名前とオプションを宣言するやり取り。USIでは`usi`への応答）で宣言するオプションの集合が探索方式で決まる。 |
| CLIに残す | `--io-log` | 最初の入力から記録するには、入力を読み始める前に保存先が要る。 |
| CLIに残す | `dev usi-random` | 校正用の別のエンジンを起動する入口である。 |
| CLIに残す | `match`、`spsa` | エンジンを子プロセスとして起動し、実験全体を管理する側である。 |
| CLIに残す | `data`の6本 | 多数の対局や外部の棋譜から、来歴を持つデータ一式を生産し、集計する。 |

`match`、`spsa`、および`data`をUSIのコマンドにすると、引数の検査と`--help`、スクリプトが成否の判定に使う終了コード、および長時間の処理の間にUSIの入力を処理する能力を失う。
これらはエンジンの機能ではなく、エンジンを使う道具であり、移しても渡す情報は減らない。

## 先行実装

診断をプロトコルのコマンドとして持つ方式には先例がある。
Stockfishは、`bench`、局面を表示する`d`、評価を表示する`eval`、およびネットをファイルへ書き出す`export_net`をUCI（チェスエンジンの標準の通信プロトコル）のコマンドとして受け、perftは`go perft <深さ>`として受ける（`src/uci.cpp`の155〜175行と224〜241行）。
やねうら王も、`bench`、`d`、`eval`をUSIのコマンドとして受け、`go`の引数として`perft`を受ける（`source/usi.cpp`の361〜372行と651行）。

ネットをオプションで指定する方式にも先例がある。
Stockfishのオプション`EvalFile`は、評価関数のネットのファイルを指定し、設定された時点で読み込む（`src/engine.cpp`の136〜140行）。
将棋のエンジンdlshogiのオプション`DNN_Model`と、チェスのエンジンlc0のオプション`WeightsFile`も、ネットのファイルを指定する。この2つは、[元のADR](../adr/archive/select-zero-networks-by-startup-argument-and-embed-only-the-judged-one.md)が該当箇所を挙げている。

コマンドの失敗でプロセスを終了する方式にも先例がある。
Stockfishは、`go`の引数が不正な場合や局面の反転に失敗した場合に、`info string CRITICAL ERROR`で始まる行を出して終了コード1で終わる（`src/uci.cpp`の232行と695〜700行）。
minase自身も、`isready`での準備の失敗をエラーの行と終了コード1で知らせている（`crates/minase/src/protocol/usi.rs`の`handle_idle_line`）。

一方、本書はStockfishの2つの方式を採らない。
1つは、起動引数の列を1つのコマンドとして実行して終了する方式である（`src/uci.cpp`の98〜103行と188行）。
もう1つは、入出力の記録をオプション`Debug Log File`で有効にする方式である（`src/engine.cpp`の69〜72行）。
理由は「設計判断」節と「CLIに残すもの」節にある。

## 規則セットの指定

### 未設定の状態

プロトコル層は、規則が未設定の間は対局の状態機械`Engine`（`crates/minase/src/protocol/engine.rs`）を持たず、最初の有効な`RuleSet`を受けた時点で`Engine`を生成する。
`Engine`は生成時から検証済みの規則と対局を持つ型であり、この性質は変えない。
未設定の状態を`Engine`の内部に持たせると、現局用の規則、次局用の規則、および対局そのものに未設定の場合分けが広がるので、`Engine`の外に置く。

現在は、実行ファイルの側が起動引数の規則から`Engine`を生成し、プロトコルの構造体の生成時と、セッションを実行する関数（`Protocol::run`と`run_channel`）の呼び出し時に渡している。
これを、プロトコルの構造体（`UsiProtocol`、`CecpProtocol`）が`Engine`を0個または1個所有する形に改め、生成と実行の関数の引数から`Engine`を外す。
`dev usi-random`の内部の状態も同じ形に改める。

探索器`Searcher`と、対局に依存しない設定は、これまでどおり起動時から存在する。
`USI_Hash`、`Threads`、`NnBackend`などのオプションは、規則が未設定の間に届いても、届いた時点で検査して適用する。
lishogi Botの設定は`Threads`と`USI_Hash`を先に並べており、Lishogi-Botは設定の順に送るので、規則より先にほかのオプションが届く順序は実際に起こる。

最初の`RuleSet`は、現局用と次局用の両方の規則になる。
2回目以降の`RuleSet`は、これまでと同じく次局用の規則だけを変え、`usinewgame`、または対局の開始を待つ状態で最初に受けた`position`で確定する。
したがって、起動引数で規則を渡していたときと、対局への規則の適用の時点は変わらない。

### USIでの宣言と拒否

`usi`への応答では、`option name RuleSet type string default <empty>`と宣言する。
`<empty>`は、USIが空の文字列を表すために使う表記であり、minaseはすでに`NnCacheDir`の空の既定値をこの表記で宣言している。
値のない`setoption name RuleSet`と、値が`<empty>`の指定は、`info string error: RuleSet requires a value`で拒否する。

`isready`は、規則が未設定なら`info string error: required option RuleSet is not set`を出し、`readyok`を返さずに終了コード1で終える。
この扱いは、推論器の準備に失敗したときの既存の扱いと同じである。
MCTSでは、実行プロバイダがTensorRT（NVIDIAのGPU向けの推論の基盤）でキャッシュの場所が空のときに、`isready`がすでに同じ形で失敗する（`crates/minase/src/search/mcts/engine.rs`の`execution_provider`）。

`isready`を送らない入力に備えて、`Engine`を必要とするコマンドは、規則が未設定なら同じ文言のエラーの行で拒否し、セッションは続ける。
該当するコマンドは、`usinewgame`、`position`、`go`、`gameover`、独自コマンドの`moves`（全合法手の照会）と`state`（規則、盤面、および対局の状態の照会）、ならびに`d`、`eval`、`tt`、`perft`、`random-play`である。
この検査は、各コマンドの固有の検査より先に行う。
たとえば`eval`は、どちらの探索方式でも現局面を必要とするので、規則が未設定なら、推論器の準備の有無を調べる前にこの文言で拒否する。

### CECPでの宣言と拒否

CECPでは、`feature option="RuleSet -string "`と宣言し、既定値の欄を空にする。
最初の`new`までに`option RuleSet=<規則>`を受けていなければ、`Error (required option RuleSet is not set): new`を出し、終了コード1で終える。
CECPには`isready`に当たるコマンドがないので、規則を必要とする最初のコマンドである`new`で検出する。
XBoardは、握手の直後に`new`を送る。
XBoard 4.9.1は、起動設定`-firstOptions`に書いたオプションを、握手の`feature option`を受理した直後に送り、`new`はその後に送る。
この順序は、実物のXBoardとminaseの入出力の記録で確かめた。
規則が未設定のまま届いた`go`、`setboard`、`usermove`は、`Error (required option RuleSet is not set): <コマンド名>`で拒否し、セッションは続ける。
`new`を送らずにこれらを送る入力に備えるためであり、USIで`isready`を送らない入力に備えるのと同じ扱いである。

### 規則セット名の改名

規則セット名`engine-default`を`JCSA`へ改名する。
中身は`L0,P0,R1,E0`のままである。
名前の照合は従来どおり大文字と小文字を区別せず、正準の表記は`JCSA`とする。
`state rules`と対局ハーネスの記録が返す値は、正準のコード列（`L0,P0,R1,E0`）なので、改名の影響を受けない。

`JCSA`は日本中将棋連盟の規則そのものではない。
規則書の標準規則は連盟の競技規則に基づくが、連盟式の千日手（規則コードR0）は、条文にない解釈を補わなければ裁定できないので実装していない（[ADR](../adr/do-not-implement-r0-repetition.md)）。
そこで、規則書の第33条第5項を次の文に改め、題名の版数を第17版とする。

> Minaseは、標準規則の千日手（R0）をR1に置き換えた構成「L0＋P0＋R1＋E0」（第3項の表記では「標準規則－R0＋R1」）を、規則セット名JCSAとしても受理する。JCSAは日本中将棋連盟（Japan Chu Shogi Association）の略である。MinaseはR0を選択可能な規則コードとして提供しない（第31条）ため、この規則セットは、千日手の扱いに限り連盟の規則と異なる。規則セット名の照合は大文字小文字を区別せず、規則コードまたは他の規則セット名との併記は認めない。この名前は第12版でengine-defaultとして追記し、第14版で構成を全群明示の形に改め、第17版でJCSAへ改名した。

`minase-core`では、定数`Rules::ENGINE_DEFAULT`を`Rules::JCSA`へ改名し、`Game::with_default_rules()`を削除する。
削除した関数の呼び出し元は`Game::new(Rules::JCSA)`と書く。
自己対局生成器が名前の文字列を解析して規則を得ている箇所（`selfplay_gen/mod.rs`と`zero_selfplay/mod.rs`の`engine_default_rules`）は、定数を直接使う形に改める。

AlphaZero型探索の学習器が、教師データの形式（MNSD）のファイルを読むためのRustの拡張`tools/train/zero/mnsd_reader`は、リポジトリのワークスペースに属さない独立したプロジェクトであり、`cargo test --workspace`の対象にならない。
この拡張は`Rules::ENGINE_DEFAULT`を参照し、規則がこの規則セットと一致するかどうかを`engine_default`という名前の欄でPythonの側へ渡している（`tools/train/zero/minase_zero/data.py`）。
定数の改名に合わせて、この欄の名前も`jcsa`に改める。

改名で書き換える文書は、現在の操作と仕様を案内するものに限る。
対象は、`README.md`、`docs/guides/`、規則書、未完了の設計書、およびコードのコメントとテストである。
測定記録、完了済みの設計書、監査報告、および変更履歴は、過去の事実の記録なので書き換えない。
`engine-default`を含むファイルは、`docs/measurements/`に353、それ以外に134ある。

### 保存済みの記録への影響

名前`engine-default`を保存している形式は、対局ハーネスとSPSA（同時摂動確率近似による係数調整）が実行ディレクトリに書く、実行条件の記録`manifest.json`である。
どちらも、利用者が入力した規則の原文と、正準のコード列の両方を保存し、再開のときは原文を解析し直す。
したがって、原文が`engine-default`である実行は、改名の後のハーネスでは再開できない。
対局ハーネスでは、後の「対局ハーネスとSPSA」節で述べるとおり、記録形式の版も上げる。

MNSDのヘッダは、規則セットを32バイトの文字列として保存し、読み込みのときに解析する。
現行の生成器はコード列を書くので、生成器が書いたファイルは改名の影響を受けない。
2026年11月12日の時点で、作業機の`data/`にあるMNSDのファイルは145個であり、140個がコード列`L0,P0,R1,E0`を保存している。
残る5個は、ヘッダの欄を現行の形式として読めない旧い形式のファイルであり、現行のコードでも読み込めない。
名前`engine-default`を保存したファイルは見つからなかった。
名前を保存したファイルがほかの機械にあれば、改名の後は読み込みで拒否される。
学習器のテスト（`tools/train/zero/`）は、合成したMNSDのヘッダに`engine-default`を書いているので、フェーズ1で改める。
自己対局生成器の生成条件もコード列を保存しているので、改名の影響を受けない。

`scripts/resign_diagnosis.py`は、規則の原文が`engine-default`である記録だけを集計の対象に選んでいる。
この条件は、正準のコード列の欄が`L0,P0,R1,E0`であることに改める。
こうすれば、改名の前後どちらの記録も同じ条件で選べる。

## 推論のネットの指定

MCTSで起動したminaseは、`option name NnModel type string default <empty>`を宣言する。
値は、ONNX（ニューラルネットの交換用のファイル形式）のファイルのパスである。
相対パスは、これまでの`--nn-model`と同じく、エンジンの作業ディレクトリから解決する。

ネットは`isready`で読み込む。
`NnModel`が未設定なら、`isready`は`info string error: required option NnModel is not set`を出して終了コード1で終える。
読み込みに成功した`isready`は、`readyok`の直前に`info string network_sha256 <64桁の16進数>`を出す。
この値は、推論に渡すバイト列のチェックサム（SHA-256）であり、TensorRTのキャッシュの鍵に使っている値と同じである。

`NnModel`の変更を受理した時点で、読み込み済みのネット、推論器、およびMCTSが対局の間に持ち越す探索木を捨てる。
次の`isready`でネットを読み直して推論器を作るまで、`go`、`eval`、および`nn-eval`は拒否する。
したがって、設定した値と異なるネットで探索や診断が動くことはない。
既存の`NnBackend`、`NnCacheDir`、`NnBatchSize`の変更は推論器だけを捨てるが、ネットが変わると探索木が持つ評価も無効になるので、探索木も捨てる。
推論器がないまま届いた`go`を拒否する処理はすでにある（`crates/minase/src/search/mcts/engine.rs`の`prepare_driver`）。

現在のMCTSの探索器は、生成時に読み込み済みのネットを必ず受け取る（`Searcher::mcts`と`mcts::Engine::new`）。
これを、ネットを持たずに生成でき、`isready`で読み込む形に改める。
起動引数の組合せを検査している`crates/minase/src/bin/minase/engine.rs`の`create_searcher`からは、`--nn-model`に関する2つのエラーがなくなる。

対局ハーネスでは、MCTSを`--candidate-args '--search mcts'`と`--candidate-option 'NnModel=<パス>'`の組で指定する。
オプションの値であるパスは、`manifest.json`に残る。
ネットの内容は、エンジンが返すチェックサムを記録して照合する（「ネットのチェックサムの記録」の項）。

USIの`setoption name <名前> value <値>`で渡す文字列のオプションは、`value`の後の語を1つの空白でつないで値にする。
したがって、連続する空白やタブを含むパスは指定できない。
この制約は既存の`NnCacheDir`と同じであり、本書では変えない。

## 診断のコマンド

### 共通の契約

5つの診断のコマンドと、定義し直す`eval`は、次の契約に従う。

- 探索していないときに同期で実行する。探索中に届いた場合は、ほかのコマンドと同じく待ち行列に入り、探索が終わってから実行する。実行中に届いた`stop`と`quit`は、診断が終わってから処理する。
- 出力の各行に`info string`を付け、正常に終わったときだけ最後に`info string end`を出す。この形は既存の`eval`と`tt`と同じである。
- 引数の誤り（未知の語、値の欠落、範囲外の値、重複）は、`info string error: <内容>`の1行で拒否し、セッションを続ける。終端の行は出さない。
- 実行時の失敗（不変条件の違反、推論の失敗、ファイルの書き込みの失敗）は、`info string error: <内容>`を出して終了コード1で終える。
- 対局の局面、置換表（αβ探索が局面の結果を覚える表）、history表（探索が手の成績を覚える表）、および設定を変えない。

利用する側のスクリプトは、終了コードが0であることと、終端の行があることの両方で成功を判定する。
終了コードだけでは、引数の誤りを検出できない。

### perft

```text
perft <深さ> [divide]
```

現局面から、指定した深さまでの合法手の経路数を、深さごとに数える。
局面は`position`で設定したものを使い、規則は現局に適用中の着手の規則を使う。
したがって、`dev perft`の`--sfen`と`--rules`に当たる引数はない。
`divide`を付けると、根の合法手ごとの内訳を出す。
深さ0は受け付け、`divide`との併用だけを引数の誤りとして拒否する。
この2点は`dev perft`と同じである。

計数は、対局の裁定（千日手や終局の判定）を使わず、合法手生成器と局面の複製で行う。
この数え方も`dev perft`と同じであり、終局した対局の局面でも数えられる。
`dev perft`が受け付けていた、盤面と手番だけの2欄のSFENは、USIの4欄の形式で`position sfen <盤面> <手番> - 1`と書けば同じ局面になる。

`go perft <深さ>`の形にはしない。
`go`の引数の検査は深さ1以上を要求し、調整用のビルドでは最初の`go`で係数を固定するので、perftを`go`の経路に載せると、探索のための検査がperftにも掛かる。

### bench

```text
bench [depth <N>] [threads <N>] [repetitions <N>]
```

固定の局面集をαβ探索で探索し、局面ごとの深さ、ノード数、最善手、評価値と、全体の毎秒ノード数を出す。
省略時の値は`dev bench`と同じく、`depth`が3、`threads`が1、`repetitions`が1である。
測定の内容は`dev bench`から変えない。
規則は`Rules::JCSA`に固定し、既定の容量の置換表を1つ確保して局面ごとに計測の外で消し、反復が2回以上ならウォームアップを1回行って中央値を出す。
置換表を使い回して計測の外で消すのは、確保と消去の時間を速度の指標に含めないためである（[教訓](../lessons/bench-allocation-outside-timing.md)）。

`bench`は、規則の設定も`isready`も要求しない。
局面、規則、置換表、およびhistory表はbench専用のものを使い、セッションの対局、`USI_Hash`、および`Threads`には触れない。
MCTSで起動したプロセスでも、同じαβ探索の測定として実行できる。

調整用のビルド（Cargoのフィーチャ`tuning`を有効にしたビルド）では、枝刈りの閾値などの探索の係数をUSIのオプション`Tune_<名前>`で変えられ、その値はプロセス全体で共有される。
このビルドは、最初の`go`を受けた後は係数の変更を拒否する。
`bench`も探索を実行するので、`go`と同じく、実行した時点から係数の変更を拒否する。
係数を変えてから`bench`を実行した場合は、変えた後の係数で測ることになる。

### nn-eval

```text
nn-eval out <パス>
```

固定の288局面をセッションの推論器で推論し、各局面の価値（手番側の勝率）と合法手ごとのlogit（着手の確率である方策の、正規化する前の値）をJSONのファイルへ書き出す。
288局面は、初期局面、固定のシードのランダム対局から採った283局面、および手で組んだ4局面である。
出力の形式は`dev nn-eval`と同じであり、ネットを学習した側（機械学習のライブラリPyTorch）の出力と`tools/train/zero/nn_compare.py`で突き合わせる。

`nn-eval`はMCTSで起動したプロセスでだけ使え、`isready`で推論器を準備した後に受け付ける。
ネット、実行プロバイダ、バッチの大きさ、およびキャッシュの場所は、`NnModel`、`NnBackend`、`NnBatchSize`、`NnCacheDir`の値を使う。
推論は`NnBatchSize`の局面数ごとにまとめて行うので、バッチ推論の出力の並びを検査する役目は保たれる。
αβ探索で起動したプロセスでは、`info string error: nn-eval requires --search mcts`で拒否する。

`dev nn-eval`が標準エラーへ出していた推論の所要時間は、`info string`の行として出す。
推論器の作成の所要時間は`isready`の処理時間になるので、`nn-eval`の出力からは除く。

### nn-fixture

```text
nn-fixture out <パス>
```

`nn-eval`が使う288局面について、局面、入力の符号化、および合法手のラベルをJSON Linesのファイルへ書き出す。
出力は、リポジトリにコミットしている`crates/minase/tests/fixtures/nn-positions.jsonl`の再生成に使う。
規則の設定も`isready`も要求せず、どちらの探索方式で起動したプロセスでも実行できる。

### random-play

```text
random-play [games <N>] [seed <S>] [game <K>] [max-ply <N>] [verify-all] [verbose]
```

ランダムな合法手で対局を進め、毎手、局面の不変条件と合法手の適用を検査する。
引数の意味と既定値は`dev random-play`と同じである。
規則は、最後に受理した`RuleSet`を使う。
したがって、`dev random-play`の`--rules`に当たる引数はなく、規則が未設定なら拒否する。

違反を見つけたときは、`info string error: random-play invariant failure: <内容>`に続けて、規則、基本シード、局番号、手数、問題の着手、直前の局面のSFEN、および全手順を`info string`の行で出し、終了コード1で終える。
`dev random-play`は違反を見つけた関数の中でプロセスを終了しているので、違反を呼び出し元へ返す形に改める。

### MCTSでのeval

MCTSで起動したプロセスの`eval`は、現局面をセッションの推論器で推論し、手番側の勝率と、全合法手のlogitおよび事前確率（探索が各手を読み始めるときに使う確率）を表示する。
現在は、MCTSで起動してもNNUEの内訳を表示しており、対局に使うネットの出力をUSIで照会する手段がない。
αβ探索で起動したプロセスの`eval`は変えない。

推論器が準備されていなければ、`info string error: eval requires isready`で拒否する。
`eval`から暗黙にネットを読み込むことはしない。
既存の`tt`も探索方式で振る舞いが変わり、MCTSではエラーを返すので、`eval`を探索方式に応じた表示にしても、独自コマンドの体系は崩れない。

### 推論器の利用

`eval`と`nn-eval`は、MCTSの探索器が持つ推論器を使う。
推論器は探索器の内部にあり、推論の呼び出しは推論器を書き換える参照を必要とする。
探索中は探索器の全体が探索スレッドへ移り、探索が終わるとプロトコル層へ戻るので、診断は探索器が戻っている間にだけ実行できる。
この条件は「共通の契約」の、探索していないときに実行する定めと一致する。

探索が葉の局面を評価する既存の処理は、方策の温度（事前確率を作るときに方策のlogitを割る係数）の適用と探索木の更新までを一度に行うので、診断にはそのまま使えない。
そこで探索器の境界`Searcher`に、局面の列を準備済みの推論器で推論して、生のlogitと価値を返す操作を加える。
事前確率は、探索と共通の温度の計算で生のlogitから求め、同じ計算式を2か所に書かない。

### 実装の置き場所

診断の処理は、現在は実行ファイルの側（`crates/minase/src/bin/minase/`）にある。
USIの処理はライブラリの側（`crates/minase/src/protocol/usi.rs`）にあり、ライブラリから実行ファイルの側のモジュールは呼べないので、診断の処理をライブラリへ移す。
各診断は、解析済みの引数と行の出力先を受け取り、失敗を型つきのエラーで返す関数にする。
ライブラリの中ではプロセスを終了しない。
実行時の失敗は、`isready`の失敗と同じ経路で扱う。
プロトコル層がエラーの行を出力してフラッシュし、セッションを実行する関数がエラーを返して、実行ファイルの側（`crates/minase/src/bin/minase/engine.rs`）がそれを終了コード1に変える。

## CLIに残すもの

### --search

探索方式は、起動引数`--search alphabeta|mcts`のまま残す。
`usi`への応答で宣言するオプションの集合は、探索方式で決まる。
現在の宣言では、`Threads`の範囲はαβ探索で1〜256、MCTSで1だけであり、`NnBackend`などはMCTSだけが宣言する。
握手より前に方式が決まっている必要があるので、プロトコルの種類を決める`--protocol`と同じ性質の情報である。

オプションにする場合の実現方法は2つあり、どちらも採らない。
1つは、方式が決まる前に届いた設定を溜めておき、`isready`で適用する方法である。
現在の`setoption`は、起動時に決まった探索器へ値を即時に適用し、その探索器の宣言に照らして検査している。
設定を溜める方法では、方式に固有の誤りの通知が`setoption`の直後から`isready`へ遅れる。
もう1つは、`Search`を受けた時点で探索器を作り直す方法である。
この方法では、`Search`より前に送った設定が黙って失われる。
対局ハーネスは`USI_Hash`を追加のオプションより先に送るので、実際にこの順序になる。

どちらの方法でも、握手では両方式のオプションをまとめて宣言することになる。
対局ハーネスは、エンジンを事前に起動して握手で宣言を取得し、対局を始める前に、宣言された範囲に照らして指定値を検査している（`crates/minase/src/harness/engine/probe.rs`）。
両方式のオプションをまとめて宣言すると、この検査で方式に合わない値を検出できなくなる。

### --io-log

入出力の記録は、起動引数`--io-log <パス>`のまま残す。
記録は、入力スレッドが1行を読み終えた直後に、起動からの経過時間を付けて書き、毎行フラッシュする（`crates/minase/src/bin/minase/io_log.rs`）。
オプションで途中から有効にすると、有効にする前の行は記録できない。
欠けるのは握手だけではない。
入力スレッドは処理より先に行を読むので、記録を有効にする`setoption`と同時に送られた`go`も、受信の時刻を記録できないことがある。
時間切れの調査では`go`の受信の時刻を記録から読むので、欠けることがある記録は調査の資料にならない。

### 環境変数ORT_DYLIB_PATH

ONNX Runtimeの共有ライブラリの場所は、環境変数`ORT_DYLIB_PATH`のまま残す。
読み込みは最初の推論器を作るときなので、技術的にはオプションへ移せる。
しかし、環境を設定する`tools/train/zero/env.sh`は、同時に`LD_LIBRARY_PATH`で、GPUでの推論に要る共有ライブラリ（TensorRT、CUDA、およびcuDNN）の場所も渡しており、こちらは起動時にしか渡せない。
片方だけを移しても、起動の前の環境の設定は減らない。
また、CLIに残す`data zero-selfplay`も同じ初期化を使うので、渡し方が2通りになる。

## 対局ハーネスとSPSA

対局ハーネスは、`commit:<コミット>`の形で指定されたコミットをビルドして、そのminaseを`--protocol usi --rules <規則>`の固定の引数で起動し、その後に`--candidate-args`と`--baseline-args`の引数を足している（`crates/minase/src/harness/player.rs`）。
固定の引数を`--protocol usi`だけにする。
規則は、これまでどおり握手の後に`setoption name RuleSet`で送る。

`match run --rules`は既定値をなくし、新規の実行で必須にする。
`--resume`は`--rules`と排他であり、再開では`manifest.json`の値を使う。
この形は、新規の実行でだけ`--rules`を要求する`spsa`と同じである。

本書の変更より前のコミットのエンジンは、起動引数`--rules`を必須とし、規則セット名`JCSA`を知らない。
変更の前後をまたぐ対局では、変更より前の側に`--baseline-args '--rules L0,P0,R1,E0'`を付け、`match run --rules`にも同じコード列を渡す。
ハーネスに、コミットの新旧を判定して引数を切り替える分岐は加えない。

`manifest.json`のエンジンの欄`args`は、固定の引数の後に足す引数だけを保存している。
固定の引数が変わると、この欄の意味が変わるので、記録形式の版を7から8へ上げ、版7の読み込みや変換は作らない。
版7の実行ディレクトリの再開と集計は、その測定を開始したハーネスで行う。
この扱いは、版を5から6、6から7へ上げたときと同じである。
`data/matches/`にある版7の実行ディレクトリは、2026年11月12日の時点で41件である。

`spsa`も、`commit:`のエンジンを同じ固定の引数で起動している（`crates/minase/src/bin/minase/spsa_runner/engine.rs`）。
こちらも`--protocol usi`だけにする。
`spsa`には起動引数を足す引数がないので、変更より前のコミットを調整の対象にするときは、その時点のハーネスを使う。
係数のファイルを生成する`spsa params`の引数`--rules`は、握手で宣言を読むためのエンジンの起動引数にしか使っていないので、削除する。
調整機で`spsa params`を呼ぶ`scripts/vast-spsa/remote.py`も合わせて改める。
`spsa`の`manifest.json`には形式の版の欄がないので、フェーズ2をマージする前に、再開を予定しているSPSAの実行が残っていないことを確かめる。

### ネットのチェックサムの記録

現在の`manifest.json`は、ネットをパスだけで記録している。
同じパスのファイルを測定の途中や再開の前に書き換えると、記録と実際に対局したネットの対応が失われる。
これまでは、ネットをサイクル番号つきのファイル名で保持して上書きしない運用で防いできた。
`commit:`で指定したエンジンの実行ファイルについては、ハーネスはすでにチェックサムを記録し、再開のときに照合している。
ネットにも同じ扱いをする。

チェックサムは、エンジンが`isready`で出す`info string network_sha256 <64桁の16進数>`の行から得る。
ハーネス自身はファイルを読まない。
どのオプションがネットを指すかを知っているのはエンジンであり、エンジンが返す値は、推論に実際に使うバイト列から計算した値だからである。

値は、`manifest.json`のエンジンごとの記録（`candidate`と`baseline`）に、欄`network_sha256`として保存する。
欄は省略できず、行を出さないエンジンでは明示的に`null`を書く。
`null`にするのは、`readyok`を正常に受け取り、その間にチェックサムの行がなかった場合だけである。
初期化の失敗を`null`に読み替えることはしない。
`readyok`までにチェックサムの行が2回以上届いた場合と、値が64桁の16進数でない場合は、エラーにする。

記録と照合は、次の3つの時点で行う。

- 測定の開始時。ハーネスは対局の前に、候補と基準のエンジンを順に1回ずつ起動し、握手で宣言を読んでオプションを検査している（`crates/minase/src/harness/engine/probe.rs`の`probe_engine_defaults`）。この事前の起動を`isready`まで進め、`readyok`までに読んだ値を記録する。
- 再開時。同じ事前の起動で得た値を、記録した値と比べる。異なれば、探索スレッドの数の既定値が記録と異なる場合と同じく、再開をエラーで拒否する。
- 各対局の開始時。ハーネスは局ごとにエンジンを起動し直し、`isready`を送って`readyok`を待つ（`crates/minase/src/harness/engine/process.rs`の`start`）。この間に読んだ値を、記録した値と比べる。

記録が`null`であるのにエンジンが行を出した場合と、その逆の場合は、どの時点でも不一致として扱う。

事前の起動は、対局の開始時と同じ初期化の列を送る。
送るのは、`RuleSet`、指定がある場合の`USI_Hash`、`ResignValue`、および追加のオプションであり、その後に`isready`を送る。
`USI_Hash`を省くと、αβ探索のminaseは`isready`で既定の256 MiBの置換表を確保するので、小さい容量を指定した測定でも、事前の起動だけが大きいメモリを要求することになる。
初期化の列を事前の起動と対局の開始で2か所に書かないよう、1つの処理にまとめる。

再開時の復元は、順序を改める。
現在は、追加のオプションを空にした設定で事前の起動を行い、その後で保存したオプションを設定に戻している（`crates/minase/src/bin/minase/match_runner/resume.rs`の`restore_player`）。
事前の起動を`isready`まで進めると、この順序では`NnModel`が未設定のまま`isready`を送ることになり、ネットを変えていない再開も失敗する。
保存したオプションを、事前の起動より前に設定へ戻す。

事前の起動を行わないエンジンは、これまでと変わらない。
校正用のランダム着手エンジンと、CECPで起動するエンジンは、現在も事前の起動を行わずに既定の値を返しており、チェックサムの欄は`null`になる。
`spsa`と`spsa params`が使う宣言の読み取り（`probe_usi_options`）は、握手だけを行う別の処理であり、`isready`を加えない。
`spsa`は`tuning`のビルドのαβ探索だけを対局させるので、`spsa`の記録には欄を足さない。

各対局の開始時に値が異なった場合は、その局を反則負けにせず、測定の全体をエラーで止める。
現在の対局の進行は、エンジンの起動と初期化の失敗をすべてその側の反則負けとして記録する（`crates/minase/src/harness/game.rs`の`play_game`）。
チェックサムの不一致は、エンジンの異常ではなく測定の条件が崩れたことを表すので、反則負けの5分類（不正着手、クラッシュ、応答の期限切れ、時間切れ、着手の拒否）とは別の誤りにする。
具体的には、エンジンの初期化（`start`）が不一致を反則負けの分類とは別の誤りとして返し、1局の進行（`play_game`）と1ペアの進行（`run_pair`）が、その誤りを呼び出し元へそのまま返す。
ペアを実行するワーカーは、すでに誤りを受け取る形になっており、誤りを受けたハーネスは停止の旗を立て、ペアの割り当てを終え、全ワーカーの終了を待って終了コード1で終わる（`crates/minase/src/bin/minase/match_runner/`の`scheduler.rs`と`mod.rs`）。
ただし、現在は、終了を待つ間に残っていた誤りを、原因によらず「ワーカーがパニックした」という文言に置き換えている。
不一致の原因が利用者に届くよう、この置き換えをやめて元の誤りの内容を出す。

止まった測定は、それまでに終わったペアの記録を保つ。
ハーネスは、終わったペアを結果の取り込みより前に保存し、再開では保存済みの番号を除いて実行するので、既存の仕組みがそのまま使える。
ネットのファイルを元に戻せば再開でき、戻さなければ再開時の照合が拒否する。
エラーで終わった測定には、ほかの異常終了と同じく、正常に終わらなかった起動があることを示す印（`summary.json`の`interrupted`）が付く。
この印は再開しても消えず、印の付いた測定は、`minase match report`の校正用の集計に使えない。

事前の起動を`isready`まで進めると、MCTSのエンジンでは、測定の開始時と再開時に推論器の作成が1回ずつ増える。
推論器の作成にかかる時間は、既存の応答の期限（`--response-timeout`、既定は120秒）の中に含まれ、途中の出力があっても期限は延びない。
TensorRTの初回のエンジンの作成が期限を超える場合は、事前の起動がエラーで終わるので、期限を延ばして実行し直す。
事前の起動は候補と基準を順に処理し、それぞれのプロセスの終了を待ってから対局を始めるので、事前の起動と対局のエンジンがGPUのメモリを同時に占めることはない。

記録の欄を足すのは、版を8へ上げるのと同じ変更の中である。
版8は本書のブランチをmasterへマージするまで外に出ないので、フェーズ2で版を上げ、フェーズ3でこの欄を足しても、版は8のままにする。
フェーズ2とフェーズ3の間にブランチで作った実行ディレクトリは、確認のための使い捨てとし、フェーズ3の後は読めなくてよい。

### ランダム着手エンジン

校正用のランダム着手エンジン`dev usi-random`は、`RuleSet`の既定値`L0,P0,R1,E0`を持つ。
この既定値を削除し、エンジン本体と同じ宣言と拒否にする。
対局ハーネスはランダム着手エンジンにも`RuleSet`を送っているので、ハーネス経由の動作は変わらない。

### CECPで起動するエンジン

対局ハーネスは、`cecp:<起動コマンド>`の形で指定されたエンジンをCECPで初期化するとき、規則を送らずに`new`を送っている（`crates/minase/src/harness/engine/process.rs`）。
この経路はHaChuなどの外部エンジンのほか、minase自身をCECPで動かす場合にも使う。
同じminaseをCECPとUSIで対局させて、着手列と結果が一致することを確かめる統合テストがある（`crates/minase/tests/match_runner.rs`の`minase_cecp_match_is_failure_free_and_matches_usi`）。
起動引数`--rules`がなくなると、この経路のminaseは規則が未設定のまま`new`を受けて終了する。
そこで、ハーネスは握手で受けた`feature`の行を調べ、エンジンが`option="RuleSet ..."`を宣言している場合に限り、`new`の前に`option RuleSet=<規則>`を送る。
宣言していない外部エンジンへは、これまでどおり送らない。
CECPでは、エンジンが`feature`で宣言したオプションだけをGUIが送る決まりなので、この判定はプロトコルの通常の使い方である。

## 関連リポジトリへの影響

開発用GUI（`minase-gui`）は、次の点を変える必要がある。

- エンジンの起動引数から`--rules`を外す（`src/main.rs`の`spawn_engine`）。握手の後に`RuleSet`、`isready`の順で送る処理はすでにある。
- ランチャーは必須の引数`--rules`を持ち、その値を子プロセスのエンジンへ渡すためだけに保持している（`src/main.rs`の`Cli`）。エンジンへ渡さなくなるので、この引数を画面の規則の初期値として使うか、削除するかを決める。どちらの場合も、起動スクリプト（`init-engine.sh`、`init-gui.sh`）、`compose.yaml`、および起動引数を検査しているテストを合わせて改める。
- 握手の`RuleSet`の既定値から画面の規則の初期値を作っている（`web/src/shared/state.ts`の`declaredSettingsDefaults`）。既定値が`<empty>`になるので、未選択の状態を表示できるようにする。
- 規則セット名の解析（`web/src/shared/rules.ts`）を`JCSA`に合わせる。

lishogi Botの配備一式（`minase-lishogi-bot`）は、次の点を変える必要がある。

- 起動用のスクリプト`minase-lishogi`から`--rules lishogi`を外す。`--protocol usi`を渡すために、スクリプトは残る。
- `config.yml`の`usi_options`に`RuleSet: lishogi`を加える。Lishogi-Botは、`usi`、オプションの設定、`isready`の順で送る。

Botのイメージは、crates.ioで公開されたminaseを、版を固定してビルドする（`Dockerfile`）。
したがって、本書の変更がBotに届くのは、変更を含む版をリリースし、Botが固定する版を上げたときである。
配備の順序を誤ると、Botが動かなくなる。
新しいminaseを古い設定で起動すると、規則が未設定のまま`isready`を受けて終了する。
古いminaseを新しい起動用のスクリプトで起動すると、`--rules`がないので起動の直後に終了する。
Botのイメージでは、minaseの版、起動用のスクリプト、および`config.yml`を同じコミットで切り替え、配備と同じ環境でエンジンを実際に起動して`readyok`まで確かめる（[教訓](../lessons/verify-bridge-launch-path.md)）。

## 実装フェーズ

実装は、masterから切った1つのブランチのworktreeで進める。
各フェーズの終わりには、[テストの手引き](../guides/testing-minase-rules.md)の「マージ前の検査」の4つを通し、変更したPythonのスクリプトのテストを実行する。
独立したプロジェクト`tools/train/zero/mnsd_reader`を変えたフェーズでは、そのディレクトリでの`cargo test`と、学習器のPythonのテストも実行する。
各フェーズは、呼び出し側のスクリプトと手引きの変更までを含めて1つのまとまりとし、フェーズの境界で作業ツリーが一貫した状態になるようにする。

| フェーズ | 内容 | 完了条件 |
|---|---|---|
| 1 | 規則セット名を`JCSA`へ改名する。`Rules::JCSA`への改名、`Game::with_default_rules()`の削除、規則書の第17版、および現行の文書とスクリプトの名前の書き換えを行う。独立したプロジェクト`tools/train/zero/mnsd_reader`と学習器のPythonのコードも改める。 | `engine-default`が、書き換えない記録の文書を除いて残っていない。`dev bench`の局面ごとの出力が、変更の前と一致する。`mnsd_reader`のテストと、学習器のPythonのテスト（`tools/train/zero/tests/`）が通る。 |
| 2 | `--rules`を削除し、`RuleSet`を必須にする。USI、CECP、`dev usi-random`、対局ハーネス、`spsa`、およびエンジンを起動するスクリプトを改める。記録形式の版を8へ上げる。 | 「検証」節の規則の指定の項目を満たす。変更の前のコミットとの対局が、追加の起動引数を付けて完走する。minaseをCECPとUSIで対局させる統合テストが通る。 |
| 3 | `--nn-model`を削除し、`NnModel`を加える。チェックサムの行と、MCTSでの`eval`を実装する。対局ハーネスに、ネットのチェックサムの記録と照合を加える。 | 「検証」節のネットの指定の項目を満たす。 |
| 4 | `perft`と`bench`をUSIへ移し、`dev perft`と`dev bench`を削除する。benchを呼ぶ3本のスクリプトを改める。 | 「検証」節のperftとbenchの項目を満たす。 |
| 5 | `nn-eval`、`nn-fixture`、`random-play`をUSIへ移し、対応するサブコマンドを削除する。学習の実行器を改める。 | 「検証」節の3つの診断の項目を満たす。 |
| 6 | 利用者向けの文書を仕上げ、設計判断をADRへ移す。 | 「完了条件」節を満たす。 |

フェーズ1を先に置くのは、機械的な改名を挙動の変更と分けるためである。
フェーズ2より後のコードと文書は、最初から`JCSA`と書ける。

## 検証

探索の内容を変えないので、対局による棋力の測定は行わない。
代わりに、移す前後で出力が一致することを、次の項目で確かめる。
比較の基準は、本書のブランチを切った時点のmasterのコミットとする。
基準のコミットの実行ファイルは、リポジトリの外のworktreeでビルドして確保する。
`scripts/bench_compare.py`は、比べる実行ファイルをすべて同じ呼び出し方で実行するので、基準と変更の後を比べるこの確認には使えない。
基準の側は移す前のサブコマンドで、変更の後の側は標準入力のコマンドで実行し、変更の後の出力から`info string`の接頭辞と終端の行を除いて突き合わせる。
この突き合わせは本書の確認に1回だけ使うので、そのためのスクリプトはリポジトリに置かない。

規則の指定については、次を確かめる。

- 規則を設定せずに`isready`を送ると、エラーの行が出て、終了コード1で終わる。
- 規則を設定する前の`position`、`go`、`moves`、`state`、`d`、`eval`、`tt`が、エラーの行で拒否され、セッションが続く。
- 規則を設定する前に送った`USI_Hash`と`Threads`が、届いた時点で検査され、規則を設定した後の探索に反映される。
- 最初の`RuleSet`が現局の規則になり、2回目以降の`RuleSet`が次局から反映される。
- CECPで、`option RuleSet=`の前の`new`が拒否される。XBoardの起動設定で`new`の前に規則を渡せることを、実物で確かめる。
- `engine-default`の指定が、未知の名前として拒否される。
- 対局ハーネスで、変更の後のコミットどうしの対局と、変更の前のコミットに`--baseline-args`を付けた対局が、それぞれ完走する。

ネットの指定については、次を確かめる。

- `NnModel`を設定せずに`isready`を送ると、エラーの行が出て、終了コード1で終わる。
- 同じネットで、`go nodes <N>`の最善手と評価値が、変更の前の`--nn-model`での結果と一致する。
- `NnModel`を別のネットへ変えて`isready`を送ると、チェックサムの行が変わり、探索木が持ち越されない。
- `NnModel`を変えた後、`isready`を送る前の`go`、`eval`、`nn-eval`が拒否される。
- 対局ハーネスでMCTSのエンジンを測ると、`manifest.json`にネットのチェックサムが記録され、αβ探索のエンジンの欄は`null`になる。
- 測定を中断し、ネットのファイルを変えずに再開すると、再開が成功する。
- 測定を中断し、同じパスのネットのファイルを別の内容に差し替えてから再開すると、再開がエラーで拒否される。
- 測定の途中で同じパスのネットのファイルを差し替えると、次の対局の開始時に測定がエラーで止まり、不一致の原因がエラーの文言に出て、その局が反則負けとして記録されない。ペアの2局目の開始で不一致になった場合も同じである。
- 同時に複数のペアを実行している測定が不一致で止まったとき、それまでに保存されたペアの記録が残る。ファイルを元に戻して再開すると、保存されていない番号のペアだけが実行される。
- 記録が`null`のエンジンがチェックサムの行を出した場合と、記録に値があるエンジンが行を出さなかった場合が、どちらも不一致になる。
- チェックサムの行の値が64桁の16進数でない場合と、行が2回届いた場合が、エラーになる。
- `USI_Hash`に小さい容量を指定した測定で、事前の起動も同じ容量を送る。

perftとbenchについては、次を確かめる。

- 初期局面と、先獅子または成りの保留を含む局面で、`perft`の深さごとの件数と`divide`の内訳が、変更の前の`dev perft`と一致する。
- 探索スレッドの数が1のとき、`bench`の局面ごとの深さ、ノード数、最善手、および評価値が、変更の前の`dev bench`と一致する。毎秒ノード数は、同じ性能コアへ固定して交互に測り、変更の前の値の幅に収まることを確かめる（[教訓](../lessons/verify-move-only-reorganization.md)、[教訓](../lessons/pin-bench-to-performance-core.md)）。
- 引数の誤りでセッションが続き、終端の行が出ない。
- 実行ファイルに対して、探索中に診断のコマンドを送ると、探索が終わるまで保留され、`stop`で探索を止めた後に実行される。

3つの診断については、次を確かめる。

- `nn-fixture`の出力が、コミット済みの固定局面集とバイト単位で一致する。
- 同じネットと同じ機械を使い、実行プロバイダをCPU、バッチの大きさを[照合の手引き](../guides/alphazero-network-check.md)が定める1、7、256としたときの`nn-eval`の出力が、それぞれ変更の前の`dev nn-eval`の出力と一致する。
- 同じ規則、シード、および局数で、`random-play`の集計が、変更の前の`dev random-play`と一致する。
- 不変条件の違反を人為的に起こしたとき、違反の報告の行が出て、終了コード1で終わる。この確認は、検査の対象の処理に一時的な誤りを入れて行い、確認の後に戻す。

テストは、USIの手引きとコードのdocコメントに書いた契約から期待値を導いて書く（[テストの手引き](../guides/testing-minase-rules.md)）。
テストの入力は、ほかのクライアントと同じく、先頭で`setoption name RuleSet`を送る。
規則を設定済みのセッションをテストのためだけに作る入口は設けない。

## 完了条件

次のすべてを満たしたときに、状態を完了（採用）へ変える。

- 「検証」節の項目がすべて確かめられている。
- 起動引数`--rules`と`--nn-model`、およびサブコマンド`dev perft`、`dev bench`、`dev nn-eval`、`dev nn-fixture`、`dev random-play`が削除されている。
- `README.md`、公開するcrateの2つの`README.md`、`CONTRIBUTING.md`の互換性の対象の記述、および「書き換える箇所の洗い出し」節に挙げた手引きが、新しい呼び出し方を案内している。
- 設計判断がADRへ移されている。新しく書くADRは、規則の指定を必須にして既定値を持たない決定、規則セット名の改名、ネットをオプションで指定する決定、対局ハーネスがネットのチェックサムを記録して照合する決定、診断をUSIのコマンドにする決定と配置の基準、および起動引数に残すものの理由である。置き換えられるADRは、[ネットを起動引数で指定する決定](../adr/archive/select-zero-networks-by-startup-argument-and-embed-only-the-judged-one.md)であり、`docs/adr/archive/`へ移す。[補助ツールをサブコマンドにする決定](../adr/run-developer-tools-as-engine-subcommands.md)、[起動引数を足す決定](../adr/append-startup-arguments-to-commit-engine-specs.md)、および[規則を最初の局面設定で確定する決定](../adr/commit-pending-rules-on-first-position.md)は、本書が変える部分について新しいADRから参照する。
- 関連リポジトリに必要な変更が、それぞれのリポジトリの計画として起案されている。

本書の変更は、エンジンの起動引数、USIのオプション、およびライブラリの公開APIの互換性を壊す。
該当するコミットには、`CONTRIBUTING.md`の規約に従って`!`と`BREAKING CHANGE:`のフッターを付ける。
リリースの版数は、リリースの時点で決める。

# correction historyの表の追加と持ち越しの設計書

## 先に読む要約

本書は、静的評価の補正（correction history）の仕組みを、チェスのStockfishと将棋のやねうら王（YaneuraOu）が共通に持つ形へ寄せ、現行のmasterより強くなるかを確かめる。
correction historyは、探索値と静的評価のずれを局面の特徴ごとに表へ学習し、枝刈りの判断に使う静的評価を補正する手法である。
minaseの補正表は駒種別の枚数を鍵にした1つの表だけで、探索ごとに0から学び直す。
両エンジンは、駒の配置を鍵にした複数の表と、手番側自身の少し前の手を文脈として直前の相手の手で引く表（continuation correction history）の補正を重み付きで足し合わせ、表を対局の間持ち越し、補正量の大きさを枝刈りと減深の式にも使う。
本書が変えるのは6つである。
1つ目に、補正表を探索をまたいで持ち越し、新しい探索の開始時に、係数で定める割合だけ値を残す。
2つ目に、歩兵と仲人の配置、先手の歩兵と仲人以外の駒の配置、および後手の歩兵と仲人以外の駒の配置を鍵にした3つの表（pawn correction historyとnon-pawn correction historyに相当）を加え、現行の表とともに重み付きで足し合わせる。
3つ目に、2手前と4手前の手を文脈として直前の手で引く表（continuation correction history）を加える。
4つ目に、表の更新で、探索値がα以下に終わったノード（置換表へ上界として保存するノード）の重みと、重みを決める残り深さの上限8を係数にする。
5つ目に、補正量の絶対値を、reverse futility pruning（静的評価がβを十分に上回るノードを読まずに返す枝刈り）の余裕値に使う。
6つ目に、同じ値をlate move reductions（LMR、後方の手を浅く読む減深）の減深量に使う。
本書は、探索の関数形を両エンジンの形へ寄せる設計書の連鎖の4本目であり、1つ前の設計書が完了した後のmasterを起点とする。
新しい係数はすべて現行と同じ探索になる値を開始値とし、既存の係数とまとめてSPSA（simultaneous perturbation stochastic approximation、全係数を同時に少しずらした2つの設定を対局させて係数を動かす調整法）で調整する。
調整した版を起点のmasterと短時間条件STCおよび長時間条件LTCの2段階の逐次検定（段階ゲート）で対局させ、1つの候補として採否を決める。
完了条件は、候補の採否が測定記録とともに確定することである。

## 目的

本書が確かめるのは、「補正表の鍵、寿命、および補正量の使い道を両エンジンの形へ寄せ、新しい形の係数を調整すれば、現行の形で調整した探索より強くなる」という仮説である。
[係数の関数形の比較](../research/search-coefficient-forms-prior-art.md)は、correction historyの鍵、寿命、および適用先を、係数の値の調整では埋まらない差に分類した。
このうち適用先の拡大は[探索の枝刈りとLMRの関数形の見直し](search-pruning-forms.md)のF2が扱い、本書は残りの鍵と寿命、および補正量の大きさの利用を扱う。

現行の形は、[ADR](../adr/key-correction-history-by-material.md)が診断に基づいて選んだものである。
その診断は、駒配置の表を加えると予測誤差が悪化したとして見送ったが、比べた予測は現行の表と追加の表の等分の平均であり、現行の補正を半分に薄める形だった（[診断の記録](../measurements/strength-stage12-activation-diag.md#項目6の補正表の鍵)）。
同じ記録で、歩兵と仲人の配置を鍵にした表は、平均しても誤差を0.20%しか悪化させず、0でない値を返す参照が89.50%あった。
この表は現行の表と同程度の予測力を持つとみられ、両エンジンと同じく重み付きの和にすれば、和の重みをSPSAに選ばせることができる。
表の持ち越しを見送った根拠の発動率（STC相当で0.69%）も、補正をfutility pruningにだけ使う前提の値である。
加えて、これらの診断は既定の評価関数がPSTだった時期のものであり、評価関数をNNUEに替えた後には測られていない。

## 適用範囲

本書の用語を次のように定める。

- **起点**は、連鎖の1つ前の設計書が完了した後、フェーズ1を始める時点のmasterの先頭のコミットである。
- **形の変更**は、本書の6項目を実装したコミット列であり、新しい係数を開始値に置く。
- **候補**は、形の変更の上に、SPSAの最終値を`minase spsa apply`で表（`crates/minase/src/search/alphabeta/params.rs`）の既定値へ書き込んだコミットである。
- **STC**と**LTC**は、それぞれ10秒＋1手0.1秒と60秒＋1手0.2秒の持ち時間で行う自己対局の採否測定である（[SPRTの手引き](../guides/sprt.md)）。
- **補正表**は、`crates/minase/src/search/alphabeta/correction.rs`の`CorrectionTable`と同じ形の表である。手番側ごとに、要素を1024倍の固定小数点値で持ち、更新のたびに探索値と補正前の静的評価の差へ指数移動平均で近づける。
- **材料表**は、現行の補正表（双方の駒種別の枚数の組を鍵にした表）をいう。
- **補正量**は、全表の値を重み付きで足し合わせ、上限で切り詰めた値であり、静的評価と同じ単位を持つ。補正後の静的評価は、補正前の静的評価に補正量を足した値である。
- **k手前の手**は、現局面へ至る着手を1手前として、探索経路を遡って数えた着手である。2手前と4手前の手は手番側自身の手、1手前の手は相手の手である。
- **改良の判定（improving）**は、`negamax.rs`の`improving`が定める判定であり、同じ手番の2手前の局面より静的評価が上がったことをいう。
- 減深量と深さの単位は、探索の深さ1を1手と数える。

対象は次の6項目である。

- 補正表の持ち越し（C1）。
- 駒配置を鍵にした3つの表と、表の重み付きの和（C2）。
- continuation correction historyの表（C3）。
- 更新の重みの細部（C4）。
- reverse futility pruningの余裕値の補正量の項（C5）。
- LMRの減深量の補正量の項（C6）。

次の事項は対象外とする。

- 静止探索のstand-patへの補正の適用。連鎖の次の`qsearch-forms.md`で扱い、本書の補正量をそのまま使う。
- Stockfishのminor piece correction history（騎士と角の配置を鍵にした表）に相当する表。YaneuraOuは将棋向けに、香、桂、銀、金、およびその成駒を鍵の対象として定義し直している（`source/position.cpp:27-36`）。中将棋には、規則書のRULES.mdにも既存の診断にもこれに当たる駒の区分がなく、区分を新たに決める根拠がないので加えない。
- 王駒の升の組を鍵にした表。[ADR](../adr/key-correction-history-by-material.md)はこの鍵を材料表の鍵の代わりとして比べただけであり、両エンジンにも対応する表がない。王駒の升は、C2の先手と後手の配置の鍵に含まれる。
- 表ごとの更新の速さの係数。両エンジンは表ごとに更新量の倍率を変えているが（Stockfish `src/search.cpp:130-141`）、本書は全表に共通の`CorrectionWeight`を使う。設計判断の表を参照。
- 補助ワーカーの間での表の共有。設計判断の表を参照。
- 置換表の値で補正後の評価を置き換えること（Stockfish `src/search.cpp:862-865`）。補正表ではなく置換表の使い方の変更だからである。
- null move pruningを試す条件に補正後の評価を使う変更を、本書で新たに加えること。この条件は[浅い枝刈りの深さと対象の拡張](shallow-pruning-extensions.md)のS6が扱う。S6とF2がともに採用されていれば、条件には既に補正後の評価が使われており、本書の補正量もその条件に入る（依存関係の節を参照）。
- 根より前の対局の着手を、continuation correction historyの文脈に使うこと。探索のワーカーは対局の着手列を持たず、両エンジンも根より前を番兵の値で扱う（Stockfish `src/search.cpp:303-309`）。

## 依存関係

本書は、[探索の枝刈りとLMRの関数形の見直し](search-pruning-forms.md)から始まる設計書の連鎖の4本目である。
起点は、連鎖の1つ前の[historyの更新量の形とcontinuation historyの設計書](history-forms.md)が完了した後のmasterの先頭であり、前の設計書の候補が採用されたかどうかは問わない。
この順序は提案であり、最終的な順序は利用者が決める。
前の設計書の候補がmasterへ統合されると`params.rs`の既定値と探索の式が変わり、本書の検証（起点との探索ノード数の一致）の基準も変わるので、実装を含めて前の設計書の完了後に始める。
起点の表の既定値を、SPSAの開始値とする。

本書の項目は、起点に連鎖の前の設計書の変更が入っているかどうかで、次のように扱う。
以下のF1、F2、F4は、[探索の枝刈りとLMRの関数形の見直し](search-pruning-forms.md)の項目であり、それぞれreverse futility pruningの余裕値の形、補正後の評価の適用先の拡大、およびLMRの減深量の形の変更である。
フェーズ1の最初に起点のコードを読み、どちらに当たるかを確かめる。

- [探索の枝刈りとLMRの関数形の見直し](search-pruning-forms.md)が採用されていれば、補正後の静的評価はreverse futility pruning、razoring、null move pruningの減深量、改良の判定、およびfutility pruningに使われている。本書の補正量は、それらすべての判定に入る。
- さらに[浅い枝刈りの深さと対象の拡張](shallow-pruning-extensions.md)のS6（null move pruningを試す条件に、減深量の計算と同じ静的評価を使う変更）も採用されていれば、本書の補正量はnull move pruningを試すかどうかの判定にも入る。
- 同じ設計書が採用されていなければ、補正後の静的評価はfutility pruningにだけ使われている。本書は適用先を広げない。不採用の束から一部の項目だけを選び直して再測定することになるからである。この場合、新しい表と持ち越しが探索に及ぶ範囲はfutility pruning、C5、およびC6だけになり、効果は小さいと見込まれる。着手するかは、この場合に限り利用者が改めて決める。
- C6が補正項を引く位置と単位は、先行案の採否ではなく起点の実装で決める。起点のLMRが手の端数を持つ単位（F4またはhistory-formsの1/100手）で減深量を計算していれば、その単位を使う。手単位の整数で計算していれば、F4の設計判断「LMRの減深量の単位」と同じ方法で表を1/100手単位に改める。この変更は、整数`h`について`floor((floor(100x) + 100h)/100) = floor(x) + h`が成り立つので、探索を変えない。起点の単位が1/100手以外なら、`LmrCorrection`はその単位で定め、新しい係数の表の範囲と換算値もその単位へ直す。
- [historyの更新量の形とcontinuation historyの設計書](history-forms.md)は、ply `q`のノードで指した手について、その`Move`と着手前の駒種をplyごとに記録する（null moveと根より前は記録を持たない）。この記録が起点にあれば、C3はそれを再利用する。なければ、C3で同じ定義の記録を加える。

SPSAの手順と既定の設定は[SPSAによる係数調整の手引き](../guides/spsa.md)に、採否の手順は[SPRTの手引き](../guides/sprt.md)に従う。
測定機はlishogiのBotと共用するので、同時対局数は16を上限とする。
実装はcodexへ委任する（[委任の手引き](../guides/codex-delegation.md)）。

本書は次のADRの決定の一部を変える。
採用した場合は、完了時に、起点の時点で有効なADR（先行の設計書が置き換えていればその後継）を確かめ、新しいADRで置き換える。
一部だけを変えるADRでは、残る決定も新しいADRへ引き継ぐ。

- [correction historyの鍵と適用先のADR](../adr/key-correction-history-by-material.md)は、2026年9月21日に、材料表だけを鍵とし、探索ごとに初期化し、補正をfutility pruningにだけ使うと決めた。本書は、鍵の表を加え、持ち越しを係数にし、補正量の大きさを余裕値と減深量に使う。更新の条件（最善手が捕獲手でないこと、王駒に相手の利きが届かないこと、および境界の種類による向き）は変えない。決定と根拠の診断は既定の評価関数がPSTだった時期のものであり、ADR自身が、各表の補正を平均せずに足し合わせる形を未測定の候補として残している。先行の設計書がこのADRを既に置き換えていれば、その後継のADRが置き換えの対象になる。
- [butterfly historyと捕獲履歴の持ち越しのADR](../adr/carry-history-tables-within-a-game.md)は、2026年10月10日に、補正表を持ち越さないと決めた。本書のC1は、持ち越す割合を係数にする。この決定は既定の評価関数がPSTだった時期のもので、根拠はfutility pruningにだけ補正を使う前提の発動率0.69%である。ADRは補正表の持ち越しの再測定を留保していない。
- 起点でLMRの式を定めているADRは、C6で補正量への依存が加わる。現行の[late move reductionsの式のADR](../adr/reduce-lmr-by-log-table-with-stepped-history-adjustment.md)は2026年9月7日のPST時期の決定であり、上限と段差のhistory補正をSTCの到達深さが5〜6だった時期の判断として見直しの余地を留保している。同じADRが棄却した連続量の項はhistoryの項であり、補正量の項ではない。連鎖の前の設計書がこのADRを置き換えていれば、その後継のADRが置き換えの対象になる。
- reverse futility pruningの余裕値の形を定めたADRは現在なく、[適用条件のADR](../adr/skip-static-eval-pruning-when-a-royal-is-attacked.md)は適用条件と返り値だけを定めている。先の設計書のF1が採用されていればF1の決定を記録したADRを新しいADRで置き換え、採用されていなければ、C5の決定と「静的評価 ≥ β」の独立条件を新しいADRに書く。

## 設計判断

| 項目 | 決定 |
|---|---|
| 候補の束ね方 | 6項目を1つの候補とし、既存の係数とまとめて1回のSPSAで調整してから、1回の段階ゲートで採否を決める。[不採用だった探索部の改良の再調整](archived/search-revival-spsa.md)が8項目をこの方式で採用した先例に従う（[ADR](../adr/adopt-revived-search-items-as-a-bundle.md)）。項目ごとにSPSAと段階ゲートを繰り返す案は、1項目あたりSPSAの約75時間（約3日）にSTCとLTCを加えた約8〜45時間を要するので採らない。代償として、項目ごとの寄与は測らない。不採用のときに一部の項目だけを選び直して再測定しない。 |
| 新しい係数の開始値 | 全項目を、開始値で現行と同じ探索になる値から始める。持ち越す割合0%、材料表の重み100%、追加の表の重み0%、上界の更新の倍率100%、深さの頭打ち8、補正量の項の係数0である。追加の表は重み0でも更新するが、読む値に0を掛けるので探索は変わらない。これにより、全項目のコミットを探索ノード数の一致で検証でき、最終値はSPSAが決める。 |
| 新しい係数の範囲 | 両エンジンの対応する値を範囲に含め、開始値を範囲の内側に置く。重みと補正量の項の係数は、開始値0を内側に置くために負の値を含める。負の重みは表の予測を逆向きに使う形であり、意味のある値ではないが、範囲の内側から始めるために含める。持ち越す割合`CorrectionDecay`だけは、負の割合に意味がないので範囲を0〜100とし、開始値0が下限に一致する。下限では摂動の一方が0へ切り詰められるが、もう一方の摂動との差から上へ動く向きの更新は得られる。[利得のADR](../adr/decay-spsa-gains-over-30000-pair-sessions.md)は範囲の端での切り詰めを許容している。負の値を0とみなして範囲を負へ広げる案は、係数の意味に例外を加えるだけで探索は変わらないので採らない。 |
| SPSAの対象 | 起点の表の調整対象の全係数（`FmScale`を除く）に、新しい9係数を加える。係数の数は起点の時点で数え直す。新しい係数だけを調整する案は、既存の係数との相互作用を検証の外に置くので採らない（先例のADRと同じ理由）。時間管理の係数を含めるので、本番の前に時間切れの事前確認を行う。 |

## 変更の内容

以下の式で、`P`は評価関数の重みファイルが持つ探索用の歩兵価値、`d`はIIR（内部反復減深）を適用した後の残り深さ、`trunc`は0方向への切り捨て、`[条件]`は条件が成り立てば1、成り立たなければ0を表す。
`cap`は`P × CorrectionCap/100`である。

### C1　補正表の持ち越し

補正表を`Searcher`の生成時に作る現行の形をやめ、`HistoryTables`にワーカーごとに置いて探索をまたいで受け渡す。
新しい根の探索の開始時に、`HistoryDecay`を掛けるのと同じ箇所（`team.rs`の`run_search_team`）で、全表の全要素`F`を`trunc(F × CorrectionDecay/100)`に置き換え、その探索の`cap`の1024倍で切り詰める。
`CorrectionDecay`が0のとき、全要素が0になり、現行と同じになる。
`minase dev bench`は局面ごとに`HistoryTables`を初期化するので、持ち越しの挙動は単体テストで確かめる。

### C2　駒配置を鍵にした表と重み付きの和

材料表に加えて、歩兵と仲人の配置の表`F_P`、先手と後手の歩兵と仲人以外の配置の表`F_N先`と`F_N後`を持つ。
配置の鍵は、駒と升の組ごとの64ビットの乱数を排他的論理和で重ねたものとし、着手の移動元、到達升、および捕獲した駒の升から差分で更新し、null moveでは前の局面の鍵をそのまま引き継ぐ。
居喰いのように移動元と到達升が同じ着手でも、同じ式で正しく更新される。
補正量`c`を次の式で求める。

```math
c = \mathrm{clamp}\left(\mathrm{trunc}\left(\frac{w_M F_M + w_P F_P + w_N (F_{N先} + F_{N後}) + w_C (F_{C2} + F_{C4})}{100 \times 1024}\right), -\mathrm{cap}, \mathrm{cap}\right)
```

ここで`F_M`は材料表、`F_C2`と`F_C4`はC3の表の要素であり（記録のない文脈の項は和に含めない）、いずれも手番側の行から引いた1024倍の固定小数点値である。
`w_M`、`w_P`、`w_N`、`w_C`は、それぞれ`CorrectionMaterialWeight`、`CorrectionPawnWeight`、`CorrectionNonPawnWeight`、`CorrectionContinuationWeight`である。
更新は、現行の`update_correction`が材料表を更新する条件を満たしたときに、同じ差と深さで全表を更新する。
`w_M`が100で他の重みが0のとき、`c`は`trunc(F_M/1024)`に等しく、各要素は既に`cap`の1024倍で切り詰められているので、現行の`CorrectionTable::read`と同じ値になる。

### C3　continuation correction history

ply `p`のノードの`k`手前の手は、history-formsの記録のうちply `p − k`のノードで指した手である。
1手前の手はply `p − 1`、2手前はply `p − 2`、4手前はply `p − 4`の記録にあたる。
各記録の`Move`と着手前の駒種から、着手後の駒種（成る手なら成った駒種）と到達升`Move::to`の組を求める。
居喰いとじっとの到達升は移動元と同じ升である。
1手前の記録と`k`手前の記録（`k`は2と4）がともにあるとき、2つの組から順序を区別する64ビットの鍵を作り、continuation correction historyの表を引いて`F_Ck`とする。
どちらかの記録がない文脈では、`F_Ck`の項を補正量の和に含めず、その文脈では更新もしない。
2つの文脈は同じ表を引き、更新ではそれぞれの鍵の要素を同じ差と深さで更新する。

### C4　更新の重みの細部

材料表の現行の更新式の重みを、次の式に改め、全表に使う。

```math
F \leftarrow F + \mathrm{trunc}\left(\frac{(1024 D - F) \times \min(\min(d, \mathrm{CorrectionDepthCap}) \times \mathrm{CorrectionWeight} \times u,\ 102400)}{102400}\right)
```

ここで`D`は探索値と補正前の静的評価の差、`u`は置換表へ保存する境界が上界なら`CorrectionUpperWeight`、それ以外なら100である。
現行の式は、`u`の因子と102400での切り詰めを除き、`min(d, 8)`と`CorrectionWeight`（現行の既定値37）を使う同じ形である。
`min`の第1引数を102400で割った値が、1回の更新で値が目標の差へ近づく割合であり、`min`はこの割合を1以下に切り詰める。
更新後の`F`は現行どおり`cap`の1024倍で切り詰める。
`CorrectionDepthCap`が8、`CorrectionUpperWeight`が100のとき、分子と分母に100を掛けただけの式になり、0方向への切り捨ても含めて現行と同じ値になる。

### C5　reverse futility pruningの余裕値の補正量の項

起点のreverse futility pruningの余裕値に、`trunc(|c| × ReverseFutilityCorrection/100)`を加える。
`c`はnull move pruningより前に読んだ補正量である。
`ReverseFutilityCorrection`は負の値を取り得るので、余裕値が負になり得る。
このため、F1の採否にかかわらず、reverse futility pruningは「静的評価 − 余裕値 ≥ β」に加えて「静的評価 ≥ β」を独立した条件として要求する。
F1が採用されていれば起点に既にこの条件があり、採用されていなければC5で加える。
この条件がないと、β未満の値を返して探索を打ち切り得る。
起点の余裕値が0以上であれば、条件を加えても開始値では探索は変わらない。
`ReverseFutilityCorrection`が0のとき、現行と同じになる。

### C6　LMRの減深量の補正量の項

起点のLMRの1/100手単位の減深量`r`から、`trunc(LmrCorrection × |c| / P)`を引く。
history-formsが採用されていれば、補正項は同書が定める1本の式の補正項の位置、つまり手の種類（静かな手、killer手、捕獲手）の倍率を掛ける前に置く。
倍率の後に引くと、倍率0で減深しない手の種類でも、負の`LmrCorrection`によって減深が生じるからである。
その後、手単位への切り捨てと、0以上`min(上限, d − 2)`以下への切り詰めを起点の式どおりに行う。
上限側の`d − 2`は現行と同じく0で飽和させるので、残り深さ2以下では減深しない。
`c`はfutility pruningと同じく、null move pruningより後に読んだ補正量である。
減深の対象の手、手番号の扱い、および根で行わないことは変えない。
`LmrCorrection`が0のとき、現行と同じになる。
`CorrectionCap`が現行の220のとき補正量の絶対値は歩兵価値の2.2倍以下なので、範囲の上限200でも減らす量は4.4手以下である。

| `LmrCorrection`（歩兵価値1枚分の補正量あたりに減らす減深量、1/100手） | 0 | −50〜200 | Stockfishは約101（131072×208/(26310×1024)、歩兵価値208、`src/search.cpp:1353`）、YaneuraOuは約45（131072×90/(25600×1024)、歩兵価値90、`yaneuraou-search.cpp:3890`）。負の値は補正量が大きいほど減深を増やす形であり、開始値を内側に置くために含める |

## 所要時間の見積り

時間は、同時対局数16の測定機での見積りである。
SPSAは、3,000ペア（同時対局数16）の[セッション](../measurements/spsa-stage9-20260925-c5.md)が27,138秒（1ペア約9秒）を要したことから、30,000ペアを約75時間（約3日）と見込む。
段階ゲートの時間は、判定までのペア数が強さの差で変わるので幅を持たせた。

| 段階 | 内容 | 見積り |
|---|---|---|
| 1 | 形の変更の実装と検証（codexへ委任） | 1日程度 |
| 2 | 時間切れの事前確認（13反復、104ペア） | 約15分 |
| 3 | SPSA（30,000ペア） | 約75時間 |
| 4 | 反映、テスト、および事前対局（32ペア） | 約1時間 |
| 5 | 候補のSTC | 約1〜8時間 |
| 6 | 通過した場合のLTC | 約5〜30時間 |

実装を除く測定機の占有は、STCで棄却される場合は段階2から5までの和の約77〜84時間（約3.2〜3.5日）、LTCまで進む場合は段階2から6までの和の約82〜114時間（約3.4〜4.8日）となる。

## 実装フェーズ

基本シードは、時間切れの事前確認を4100000000、セッションを4150000000、事前対局を4200000000、STCを4250000000、LTCを4300000000と仮に定める。
これらは起案時点で、保存済みの測定とSPSAの基本シード（`data/matches/`と`data/spsa/`の`manifest.json`）、および他の設計書が予約した値から、各測定のペア数以上離れた未使用の値である（[教訓](../lessons/derive-seed-adjacent-collision.md)）。
着手時に同じ方法で未使用であることを確かめ直し、使われていれば設計書を書き換える。
各測定の開始前に、測定機でほかの対局測定、SPSA、教師生成、および学習が動いていないことを実行ファイル名で確かめる。

### フェーズ1　形の変更の実装

起点からブランチ`correction-history-tables`を切り、worktree `data/worktrees/correction-history-tables`で作業する。
最初に起点のコードを読み、依存関係の節のどの場合に当たるかを確かめて、C6で減深量の単位を改める必要があるか、C3で手の配列を加える必要があるかを決める。
C1、C2、C3、C4、C5、C6の順に、1項目を1コミットにする。
C6で減深量の単位を改める場合は、その変更をC6の前の独立したコミットにする。
いずれのコミットも開始値で探索を変えないので、各コミットで`minase dev bench`の全15局面を深さ3、5、7のそれぞれで探索し、探索ノード数、評価値、および最善手が起点と一致することを確かめる。
追加の表は重み0でも鍵の差分更新と表の更新を行うので、`taskset -c 3`で1つのコアに固定した`minase dev bench --depth 9 --repetitions 3`の中央値を、起点と形の変更の最後のコミットで交互に3回ずつ測り、探索速度（NPS、1秒あたりの探索ノード数）の変化を記録する（[教訓](../lessons/pin-bench-to-performance-core.md)）。
新しい係数は`params.rs`の表へ追加し、調整用ビルド（`--features tuning`つきのビルド）が`Tune_<係数名>`のUSIオプションとして宣言することを確かめる。
単体テストは、式の写しではなく数値の例で書く（[テストの手引き](../guides/testing.md)）。
少なくとも、重み付きの和と上限の数値例、`CorrectionDecay`が0と0以外のときの持ち越し、C4の重みの切り詰め、continuation correction historyの鍵が2つの手の順序を区別すること、および固定シードの着手列とその全候補手について差分更新した配置の鍵と文脈の鍵が局面からの再計算と一致することを確かめる。
最後の照合は、現行の`correction_incremental_keys_match_seeded_playouts_and_undo`と同じく、捕獲、成り、獅子の2枚取り、居喰い、およびnull moveを含める。
完了条件は、`cargo test`（通常ビルドと調整用ビルド）、`cargo clippy -- -D warnings`、および`cargo fmt --check`の通過、ノード数の一致、および探索速度の記録である。

### フェーズ2　パラメーターファイルと時間切れの事前確認

形の変更の最後のコミットでビルドした`minase`を`data/spsa/correction-history-tables-runner/`へ複製してrunner（測定を実行するプログラム）として固定し、以後のフェーズはこのrunnerで実行する。
`minase spsa params --engine commit:<形の変更> --rules engine-default`で既定のパラメーターファイルを生成し、`FmScale`の行を削除したファイルを`data/spsa/correction-history-tables.params`とする。
開始値と範囲が形の変更の`params.rs`の表と一致すること、および`c_end`と`r_end`が既定値であることを、使い捨てのスクリプトで機械的に突き合わせる。

続いて、手引きの第3節に従い、時間管理の4係数を思考時間が最も長くなる側の範囲の端に置いても時間切れが起きないことを確かめる。
写しの開始値を`HardRemainingShare`＝50、`HardSoftRatio`＝800、`MinMoves`＝40、`IterationRatio`＝150へ書き換えた`data/spsa/correction-history-tables-safety.params`で、13反復（104ペア）を実行する。
起点で時間管理の係数の名前や範囲が変わっていれば、手引きの第3節の値を起点の表に合わせて読み替える。

```console
<固定したminase> spsa \
  --run-dir data/spsa/correction-history-tables-safety --seed 4100000000 \
  --engine commit:<形の変更> --params data/spsa/correction-history-tables-safety.params \
  --rules engine-default --each time=10000+100 --concurrency 16 \
  --iterations 13 --pairs-per-iteration 8
```

`time_forfeits`（時間切れの件数）が1件でもあれば、[デバッグの手引き](../guides/debugging.md#時間切れと時間管理)の手順で原因を調べ、該当する係数の範囲を狭める案を利用者に示してから本番へ進む。
結果は測定記録`correction-history-tables-safety`に残す。
完了条件は、時間切れとエンジン異常が0件であることと、測定記録の保存である。

### フェーズ3　SPSAによる調整

```console
<固定したminase> spsa \
  --run-dir data/spsa/correction-history-tables --seed 4150000000 \
  --engine commit:<形の変更> --params data/spsa/correction-history-tables.params \
  --rules engine-default --each time=10000+100 --concurrency 16 \
  --iterations 3750 --pairs-per-iteration 8
```

最終のθ（調整中の係数の中心値の組）を整数に丸めた値を調整の結果とし、途中の値を対局の成績で選び直さない。
結果は測定記録`correction-history-tables`に、手引きの第6節の項目とともに残す。
最終値を丸めた整数が範囲の上限または下限になった係数を示す。
新しい9係数については、最終値が開始値（現行と同じ挙動）からどれだけ離れたかを、`c_end`に対する比で示す。
この比は、どの形の変更が使われたかを読むための目安であり、採否には使わない。
完了条件は、セッションの完了と測定記録の保存である。

### フェーズ4　反映と事前対局

手引きの第7節の手順1に従い、`minase spsa apply`で最終値を表の既定値へ書き込み、`git diff`で既定値だけが変わったことを確かめてコミットする。
続いて`cargo test`（通常ビルドと調整用ビルド）を測定より先に実行し、表の既定値に依存するテストが失敗した場合は、テストの前提が新しい既定値でも成り立つようにテストを直して別のコミットにする。
テストの失敗を、末尾に`; true`を付けるようなコマンドの組み方で握りつぶさない。
候補の調整用ビルドの宣言を`minase spsa params`で出力し、既定値の欄が`apply`の出力と一致することを確かめる。

採否測定の前に、候補が時間切れやエンジン異常を起こさないことと、時間の使い方の変化を確かめるため、STCの条件で候補と起点の32ペアの事前対局を行う。

```console
<固定したminase> match run \
  --run-dir data/matches/correction-history-tables-smoke --seed 4200000000 \
  --candidate commit:<候補> --baseline commit:<起点> \
  --each time=10000+100 --concurrency 16 elo --pairs 32
```

手引きの第7節の手順2に従い、候補と起点の総思考時間の比、終局時の残り時間、手数帯ごとの完了深さ（反復深化で読み終えた深さ）、および探索を止めた理由の分布を集計して、測定記録`correction-history-tables-smoke`に残す。
完了条件は、テストの通過、事前対局での時間切れとエンジン異常が0件であること、および測定記録の保存である。

### フェーズ5　採否測定

```console
<固定したminase> match run \
  --run-dir data/matches/correction-history-tables-stc --seed 4250000000 \
  --candidate commit:<候補> --baseline commit:<起点> \
  --each time=10000+100 --concurrency 16 gsprt --max-pairs 3000
```

STCの判定は[SPRTの手引き](../guides/sprt.md)の振分け規則に従う。
候補が有意に強い`H1`ならLTCへ進み、改善を示せない`H0`なら不採用とし、3,000ペアで判定保留ならその時点の対数尤度比の符号でLTCへ進むかを決める。
LTCは測定名の接尾辞を`-ltc`、基本シードを4300000000、持ち時間を`time=60000+200`とし、`--max-pairs`を付けない。
LTCで`H1`となり、エンジン異常、時間切れ、および拒否着手が0件なら採用し、`H0`なら不採用とする。
LTCの判定保留は、手引きのとおり`--resume`と`--target-pairs`で延長する。
結果は測定名ごとの測定記録に残す。
完了条件は、採否の確定と測定記録の保存である。

## 検証

- C1からC6までの各コミットで、`minase dev bench`の全15局面の深さ3、5、7の探索ノード数、評価値、および最善手が起点と一致すること。
- 差分更新した配置の鍵と文脈の鍵が、捕獲、成り、獅子の2枚取り、居喰い、およびnull moveを含む着手列で、局面からの再計算と一致すること。
- 新しい9係数が調整用ビルドの`Tune_`オプションとして宣言され、パラメーターファイルの開始値と範囲が表と一致すること。
- 候補の`params.rs`の差分が既定値の書き換えだけであり、調整用ビルドの宣言の既定値が`apply`の出力と一致すること。
- `cargo test`（通常ビルドと調整用ビルド）、`cargo clippy -- -D warnings`、および`cargo fmt --check`が通過すること。
- 時間切れの事前確認、SPSA、事前対局、および採否の測定で、エンジン異常、時間切れ、および拒否着手が0件であること。最初の測定で1件でも出た場合は、測定を止めて原因を調べる。

## 完了条件

- 形の変更の検証結果と探索速度、時間切れの事前確認、SPSAの結果、事前対局、および採否が、測定記録に残っている。
- 採用した場合は、候補のブランチがmasterへ統合され、依存関係の節に挙げたADRが新しいADRに置き換えられている。統合は利用者の許可を得てから行う。
- 不採用の場合は、結論と測定記録だけをmasterへ残し、候補のブランチはmasterへ統合しない。
- ROADMAPの状態表が本書の結論と一致している。

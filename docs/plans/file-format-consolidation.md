# ファイル形式の整理と形式の仕様の整備の設計書

## 先に読む要約

minaseのコードがディスクに読み書きするファイル形式は36ある（バイナリ11、JSON 19、テキスト6）。独自のマジック（ファイル先頭の識別バイト列）を持つバイナリ形式は7つある。
数が増えた主な原因は3つある。1つ目は、下流に読み手のない形式が残っていることである。下流とは、その形式を入力として読むほかのコマンドを指す。2つ目は、同じ情報を複数の形式へ重ねて書いていることである。3つ目は、教師データのSHA-256による照合を何重にも行っていることである。
照合は、来歴JSON、撤去済みのPython学習器の手順が残した生成記録、学習器の読み込み、付け直しのファイル、学習器の記録の5か所で行われている。来歴JSONは教師データごとに置く付随ファイルであり、付け直しは保存済みの教師データの局面を探索し直して新しい探索値を別ファイル（MNRS形式）へ書く機能である。
一方、形式の仕様は、読み書きするモジュールのdocコメント、凍結した設計書の本文、および2026年10月13日に廃止した`docs/reference/`に分かれて書かれてきており、その一部は現行の実装と食い違っていた。
本書は、教師データを将棋の教師形式hcpeやPackedSfenValue（どちらもヘッダも検査和も持たない固定長レコードの列）に近づけ、1ファイルで完結させる。来歴JSON、付け直し、教師データのビット化け検出をやめ、チェックポイントの包み（先頭の識別部と末尾の検査和）を1種類にまとめる。
来歴JSONが担っていた教師データの分類と検証分割（約5%の対局を検証用に固定する割り当て）は、MNSDの各レコードにある未使用の4バイトへ移すので、ファイルの長さは変わらない。
実戦棋譜の取り込みは、AlphaZero型探索の計画が自己対局の開始局面に使うので残す。
残った形式は、その形式を読み書きするモジュールのdocコメントにバイト配置と欄の一覧として書き、以後は実装を変えるコミットで同時に直す。形式の一覧（名前、マジックと版、書き手、読み手、仕様を書いたモジュール）だけを手引き`docs/guides/file-formats.md`に置く。
完了条件は次の3つである。形式が36から32へ、マジックが7から4へ減ること。`data/`の教師データを変換した後の学習が、変換前と同じ局面数、探索値を勝率へ換算する尺度（教師用K）、損失を出すこと。残った全形式の仕様がdocコメントにそろうこと。
エンジンの評価関数と探索は変えないので、棋力の測定は行わない。

着手は利用者の指示を待つ。
本書の実装は学習器のコードに手を入れるので、[NNUE学習器の学習率スケジュール](nnue-lr-schedule.md)と[NNUEの隠れ層](nnue-hidden-layer.md)とは同時に進めず、着手の順序は利用者が決める。

## 目的

利用者は2026年10月13日に、次の3点を指摘した。教師データのSHA-256による照合が、hcpeなどの先行例に比べて過剰であること。minaseのファイル形式が多すぎること。独自形式の説明がdocs/に見当たらないこと。
そのうえで、付け直しの撤去、教師データのビット化け検出の廃止、および形式の削減と形式の仕様の整備を1枚の設計書で行うことを決めた。
実戦棋譜の取り込みは残すことにした。[AlphaZero型探索の設計書](alphazero.md)が、自己対局の開始局面の半数をlishogiの実戦棋譜から取ると定めており、その実装が取り込みの開始局面一覧を読むからである。

形式が多いと、変更のたびに書き手、読み手、検査、文書の4か所をそろえる必要がある。そろっていない箇所は、不具合や古い記述として残る。
現に[評価関数の設計書](archived/evaluation.md)には、実装と合わない記述が3か所ある。MNUEのヘッダを版2の96バイトとして説明している箇所（現行のコード`crates/minase/src/eval/nnue/format.rs`は版5の192バイト）、MNSDの`network_checksum`を`pst.bin`の検査和と説明している箇所（現行はNNUEの重みの検査和）、学習器がMNRSの値を使うと書いている箇所（現行の学習器は読まない）である。

本書で使う語を次のように定める。
教師データは、自己対局または実戦棋譜の局面に、教師の探索値と対局結果を付けた学習用のデータであり、MNSDはその形式である。
MNUEはNNUE（評価関数のニューラルネット）の重みの形式、MNPTはPST（駒と升の組ごとの点数表）だけの重み（版2）またはPSTとFM（2駒の位置関係の補正）の重み（版3）の形式である。
検査和はファイルの内容から計算するSHA-256の値であり、本書では内容の照合に使う場合も、重みの識別子として使う場合も、この語で呼ぶ。
教師用Kは、探索値を勝率へ換算する尺度であり、教師データの分類ごとに訓練集合から推定する。
混合比λは、教師値を作るときに探索値から換算した勝率と対局結果を混ぜる比である（`λ·勝率 + (1−λ)·結果`）。
検証分割は、約5%の対局を検証集合へ固定する割り当てであり、同じ対局の局面を訓練と検証に分けない。訓練に使った局面と同じ対局の局面で検証すると、汎化誤差を過小に見積もるからである。
棋譜IDはlishogiが各対局に付ける英数字の識別子である。
由来は、レコードがどの経路で作られたか（乱数開始の自己対局、実戦開始の自己対局、実戦対局、合成）を示す区分であり、「MNSD版2」の節で定める。
診断は、学習器`minase-trainer`の`diag`サブコマンドであり、学習の入力や重みを調べて報告を書き出す。
NPZは、NumPyの配列を収めたZIP形式のファイルであり、学習器が浮動小数点の重みの受け渡しに使う。
同時学習は、PSTとFMを1つの目的関数で同時に学ぶ学習器である。

## 適用範囲

形式の数は、ディスク上のスキーマ（バイト配置または欄の構成）ごとに1つと数える。同じスキーマの複数のファイルは1つ、同じファイル名でもスキーマが違えば別の形式とする。
現在の36形式の一覧は、フェーズ0で手引き`docs/guides/file-formats.md`に書く。

本書が変えるのは次のものである。

- 教師データの形式と、その書き手（`crates/minase/src/training/`、`crates/minase/src/datagen/`、`crates/minase/src/bin/minase/selfplay_gen/`、`crates/minase/src/bin/minase/lishogi_import/`）、および読み手（`crates/minase-trainer/src/data/`と診断）。
- 学習器の記録（`config.json`）と診断の記録が、入力ファイルを識別する方法。
- 学習器のチェックポイントの包み。
- 形式を読み書きするモジュールのdocコメントと、形式の一覧の手引き。

次のものは変えない。

- MNUEとMNPTの形式。重み本体の検査和は、教師データのヘッダに写して、教師データを生成した重みを区別する識別子として使っており、照合のためのものではない。
- 対局ハーネスとSPSAの実行ディレクトリ、および`target/match-cache/`のバイナリの検査和。再開時に対局するエンジンの同一性を照合する契約（[測定の再開条件の簡素化](archived/match-resume-simplification.md)）の一部であり、教師データとは別の問題である。SPSAの`manifest.json`が版番号を持たないことは、その仕様のdocコメントに書くにとどめる。
- 学習器と診断が出力するだけで読み返さない報告のJSON（`summary.json`、診断の`--output`など）。
- 同じファイル名で中身が違うJSON（対局ハーネスとSPSAの`manifest.json`と`invocations.json`、対局ハーネスと学習器の`summary.json`）。名前を変えると既存の実行ディレクトリが読めなくなるので、形式の一覧の手引きで区別して書く。
- 撤去済みのPythonの手順が`data/`に残した`generated-N.json`、`commands.jsonl`、`config.toml`。現行コードに読み手も書き手もない。

## 依存関係

前提となる完了済みの設計書は、[評価関数](archived/evaluation.md)（MNSDの定義）、[棋力向上段階9](archived/strength-stage9.md)（来歴JSONと付け直し）、[Python学習器の撤去](archived/python-trainer-retirement.md)（現行の学習器の構成）である。

AlphaZero型探索の実装は、masterへ統合する前のブランチ`alphazero-phase1`にある。このブランチは、自己対局の生成処理から開始局面一覧の読み込み（`selfplay_gen/opening.rs`の`read_openings`）を呼び出しており、MNSDの符号化関数の可視性も変えている。
本書は開始局面一覧の形式と`read_openings`を変えないので、統合時の衝突は、可視性の変更とMNSDの読み書きの箇所に限られる。
同ブランチが加える独自形式（MNZTなど）は本書の対象外とし、統合する時点で、そのdocコメントと形式の一覧へ加える。

## 設計判断

| 判断 | 採った方式 | 棄却した代案と理由 |
|---|---|---|
| 来歴JSON | 廃止する。教師の情報はMNSDヘッダだけを正とし、分類と検証の所属は各レコードの未使用の4バイトへ移す。 | 来歴JSONから全体の検査和だけを外す案は、ヘッダの写しを来歴と突き合わせる重複と、1つのデータを2ファイルで表す構造が残るので採らない。 |
| 教師データの全体の検査和 | 計算も照合もしない。切り詰めはファイル長の検査で、同じファイルの重複指定は正規化したパスの比較で、乱数開始の自己対局の内容の重複は生成シードの一意性で検出する。ビット反転は検出しなくなり、壊れた局面は復号の検査に掛かった場合だけ拒否される。 | ビット化けの検出として残す案は、利用者が不要と決めた。hcpeとPackedSfenValueも検出しない。 |
| 由来と検証の所属の置き場 | レコードごとに置く。学習器は、1ファイル内の由来がすべて同じであること、および同じ対局の検証の所属が揃っていることを読み込み時に検査する。 | ヘッダに由来を置く案は、ヘッダが136バイトから伸びて全ファイルの書き直しが必要になり、由来が混在する診断の標本ファイルを表せない。 |
| 検証の所属を決める時点 | 生成時に生成器が決めて書く。計算式は現行の学習器と同じにし、変換したファイルの分割が変わらないようにする。 | 学習器が読み込み時に計算する現行方式は、実戦に由来するデータで棋譜IDの対応表を必要とする。その対応表が来歴JSONの存在理由の1つになっている。 |
| 診断で対局を数える単位 | 「ファイルと対局番号の組」を1対局とする。 | 現行の`diag pst-compare`は、同じ棋譜IDを持つ対局をファイルをまたいで1対局にまとめ、対局数と対局ごとの平均損失を出している（`crates/minase-trainer/src/data/mnsd.rs`の`game_key`）。この挙動を保つには棋譜IDをレコードへ持たせる必要があるが、空きは4バイトしかない。違いが出るのは、同じ棋譜に由来するデータを複数のファイルで同時に入力した場合だけである。 |
| 混合比λ | 学習器の必須の引数`--lambda`に一本化し、自己対局に由来するデータへ適用する。実戦対局のデータは常にλ=0とする。 | 来歴から読む現行方式は、学習器の`--lambda-override`と値の出どころが2つになる。来歴でファイルごとに任意のλを指定する機能は失われるが、実戦棋譜の取り込みが書く値は常に0.0であり（`lishogi_import/mod.rs`）、ほかの値は手で書き換えた来歴でしか現れない。NNUEの学習器が持つ既定値1.0も廃止し、PSTやFMと同じく必須にする。既定値で値を補う方式は、プロジェクトの方針が禁じるフォールバックに当たる。 |
| 探索条件（対局中か局面単独か） | 欄を持たず、由来から決める。実戦対局の局面は1局面ずつ置換表を消して探索する（局面単独）ので、実戦対局の由来は局面単独、自己対局の由来は対局中とする。 | 自己対局のデータに局面単独と書く経路は、付け直しと`data selfplay provenance --search-condition`だけであり、どちらも本書で撤去する。`data/`にある既存の56個の来歴JSONにも、この対応の例外はない。 |
| 付け直し（MNRS） | `data selfplay rescore`、MNRS、および付け直す記録の通し番号を列挙したテキストファイル（対象番号ファイル）を撤去する。 | 付け直しのファイルを読むのは付け直し自身の中断からの再開処理だけで、学習器は読まない。利用者が撤去を決めた。 |
| 実戦棋譜の取り込み | `data lishogi games`、`data lishogi openings`、`--openings`、lishogiのNDJSONの入力、除外の報告（`--report`）は残す。棋譜ごとの詳細（レーティング、持ち時間、終局の理由など）を書いていた`.games.json`は、除外の報告へ統合して廃止する。 | `.games.json`を消すだけの案は、棋譜の詳細が失われる。 |
| 学習器の入力の識別 | `config.json`には、MNSDを正規化したパス、バイト長、ヘッダの各欄で、MNPTをパスとヘッダの重みの検査和で、NPZをパスとバイト長で記す。チェックポイントを学習の設定に結びつける`config_hash`と`input_hash`は残し、`input_hash`はこの識別の列から計算する。 | 入力ファイルの全体の検査和は、教師データの全体の検査和と同じ理由でやめる。結びつけまで外す案は、別の学習のチェックポイントを、次元、シード、進捗が一致するだけで受け入れてしまう。 |
| チェックポイントの包み | FMと同時学習を、NNUEとPSTが使う包み（マジック`MNTRCKPT`、版2、96バイトの構造の文字列、末尾の検査和）へ合わせる。種別は構造の文字列で区別する。書き出しと検査は学習器の`nn/`に1つだけ置く。`nnue-float.bin`は書かず、`best.bin`を使う。 | 末尾の検査和も外して版3にする案は、`data/`にある12個の`MNTRCKPT`のチェックポイントの変換を要する。外して得るのは十数行のコードだけである。`nnue-float.bin`は`best.bin`を読み直して同じ内容で書いた複製である（`nnue/export.rs`）。 |
| 既存データの移行 | 1度限りの変換コマンドで`data/`のMNSDを版2へ書き換え、全件の変換と検証を終えたら、同じブランチの最後のフェーズでコマンドを削除する。読み手は版1を明示的なエラーで拒否する。 | 新旧両方を読む読み手は旧形式の経路を残し続けることになり、プロジェクトの方針に反する。全データを生成し直す案は、1ファイル（約290万局面）に約70分かかり（`data/nnue-replacement-gen`の生成ログ）、実験の出力は生成し直せないので採らない。 |
| 形式の仕様の置き場所 | 残った形式の仕様を、その形式を読み書きするモジュールのdocコメントに書き、実装を変えるコミットで同時に直す。形式の一覧だけを手引きに置き、凍結した設計書のバイト配置の記述は書き換えない。 | 設計書に仕様を置く方式では、完了後に設計書が保守されずに古くなり、現に3か所が実装と食い違っていた。仕様の写しをコードの外の文書に置く方式も、同じ理由で実装とずれる。 |

## MNSD版2

ヘッダは版1と同じ136バイトで、版の欄（0始まりでバイト4から7）だけを2にする。
レコードは版1と同じ160バイトである。版1が0に固定し、復号で0以外を拒否していたバイト156から159（0始まり）を、次のように使う。

| バイト | 欄 | 値 |
|---|---|---|
| 156 | 由来 | 0は乱数開始の自己対局、1は実戦開始の自己対局、2は実戦対局、3は合成（下記） |
| 157 | 検証の所属 | 0は訓練、1は検証 |
| 158から159 | 予約 | 0 |

乱数開始の自己対局は、初期局面から乱数で選んだ数手を指した局面から始める自己対局である。実戦開始の自己対局は、lishogiの実戦棋譜の途中局面から始める自己対局であり、実戦対局はlishogiの実戦棋譜の局面そのものである。
合成は、どの対局にも由来しないレコードである。診断が書き出す標本、初期局面、駒を1枚除いた局面、実験の出力がこれに当たる。学習器は合成のレコードを含むファイルを拒否する。

版1の来歴JSONの3つの欄は、`data/`にある56個の来歴JSONでは次の3通りの組み合わせしか現れない。
実戦対局の`start_origin`が`random`なのは、実戦対局のデータには自己対局の開始局面がなく、版1の書き手がこの欄に既定値を入れていたためである。

| 由来 | 件数 | 版1の`result_origin` | 版1の`start_origin` | 版1の`search_condition` | λ |
|---|---|---|---|---|---|
| 乱数開始の自己対局 | 51 | `selfplay` | `random` | `in-game` | `--lambda` |
| 実戦開始の自己対局 | 3 | `selfplay` | `human-game` | `in-game` | `--lambda` |
| 実戦対局 | 2 | `human` | `random` | `standalone` | 0 |

検証の所属は、現行の学習器（`crates/minase-trainer/src/data/shuffle.rs`と`data/mnsd.rs`）と同じ式で決める。
乱数開始の自己対局では、`hash64(ヘッダのシード, 対局番号) % 20 == 0`なら検証とする。
実戦に由来する2つでは、棋譜IDのUTF-8表現のSHA-256の先頭8バイトをリトルエンディアンの整数として読み、20で割った余りが0なら検証とする。
ここでのSHA-256は内容の照合ではなく、棋譜IDから所属を決定的に選ぶための関数である。これにより、同じ棋譜とその棋譜から始めた自己対局は、ファイルが異なっても同じ集合に属し、訓練と検証の間で同じ棋譜の局面が漏れない。
`hash64`は学習器から本体の`minase::training`へ移し、生成器と変換コマンドが使う。

学習器は、教師用Kの分類を、ヘッダの生成コミット、重みの検査和、ノード上限、規則セット、レコードの由来、先読み教師値の条件、適用したλの組で決める（由来を除けば現行と同じ）。

## 変換コマンド

`minase data selfplay upgrade`は、版1のMNSDを版2へ書き換える。
来歴JSONを持つファイルでは、来歴から由来と検証の所属を決める。来歴JSONを持たないファイルは、`--synthetic`を付けた場合にだけ受け付け、由来を合成、検証の所属を0とする。この区別により、来歴JSONを失ったファイルを誤って合成として変換することを防ぐ。
各ファイルは、版2を一時ファイルへ書き、全レコードを読み直してバイト156と157以外が元のファイルと一致することを確かめてから、一時ファイルの名前を元のファイル名に変えて置き換える。来歴JSONは置き換えの後に削除する。
来歴の教師の情報がヘッダと一致しない場合、由来が上の3通りに当てはまらない場合、実戦に由来するデータで全対局の棋譜IDがそろわない場合は、何も書き換えずにエラーで終了する。
置き換えと来歴JSONの削除の間で中断した場合は、版2のファイルと古い来歴JSONが残る。その状態で再実行するとエラーで終了してファイル名を示すので、来歴JSONを手で削除する。

対象は`data/`の配下にあるMNSDのすべてであり、2026年10月13日の時点で次の284ファイルある。

- 来歴JSONを持つ56ファイル。`data/nnue-replacement-gen`（20）、`data/gen3`（5）、`data/strength-stage7/gen2`（5）、`data/`直下（6）、`data/strength-stage9`の配下（6）、および実験と作業ツリーの出力（14）である。
- 来歴JSONを持たない228ファイル（合計21 GB）。完了した実験の出力（`leaves.bin`など）と診断の標本（`diagnostic-samples.bin`、`representatives.bin`、`removals.bin`など）であり、`--synthetic`で変換する。

## 形式の仕様の置き場所

各形式の仕様は、次の場所のdocコメントに書く。書き手と読み手が別のモジュールにある形式は、符号化関数を持つ書き手の側に書き、読み手からはrustdocのリンクで指す。

| 形式 | 仕様を書くdocコメントの内容 |
|---|---|
| MNSD | ヘッダとレコードのバイト配置、由来と検証の所属の規則。 |
| MNUE版5、MNPT版2と版3、NPZ | 重みのバイト配置と、NPZの配列の一覧。 |
| チェックポイント | 包みと、NNUE、PST、FM、同時学習の4種の本体。 |
| 対局ハーネスとSPSAの実行ディレクトリ | 各ファイルの欄。 |
| テキストの入力 | 開始局面一覧、lishogiのNDJSONの入力、SPSAの係数ファイル、SPSAの結果を書き戻すソースの表`parameters!`の文法、`--io-log`の行の形式。 |

手引き`docs/guides/file-formats.md`には、全形式の一覧（名前、マジックと版、書き手、読み手、仕様を書いたモジュール）と、同じファイル名で中身が違うJSONの区別だけを書く。
学習器の記録（`config.json`、`training.jsonl`など）の欄も、書き出すモジュールのdocコメントに書く。
凍結した設計書（[評価関数](archived/evaluation.md)、[段階9](archived/strength-stage9.md)、[NNUEの完全代替](archived/nnue-replacement.md)、[Rust製NNUE学習器](archived/nnue-trainer-rust.md)など）のバイト配置の記述は、凍結の規則に従って書き換えない。

## 実装フェーズ

フェーズ0では、本書が変えない形式（MNUE、MNPT、NPZ、対局ハーネスとSPSAの実行ディレクトリ、テキストの入力）の仕様をdocコメントに書き、現在の36形式の一覧を手引きに書く。
完了条件は、docコメントの各欄とバイト位置がコードの符号化関数と一致することである。

フェーズ1では、変換前の基準を記録する。
着手時点のmasterの学習器で、後述の検証の1に挙げる2組の入力について、NNUE（`--device cpu`、`--lambda-override 1.0`）とPST（`--lambda-override 0.75`）を同じシードとスレッド数で2エポック学習し、`config.json`の局面数と教師用K、各エポックの訓練損失と検証損失を記録する。
記録は`docs/measurements/file-format-consolidation-equivalence.md`に置く。

フェーズ2では、教師データの形式を置き換える。付け直し、来歴JSON、学習器の入力の識別は互いに型と関数を共有しているので、1つのフェーズで変える。

- 付け直しを撤去する（`data selfplay rescore`、`training/rescore.rs`、`selfplay_gen/rescore.rs`、学習器の`rescore_exclusions`）。
- MNSD版2を実装する。生成器（`data selfplay generate`、`data lishogi games`）は由来と検証の所属を書き、`diag pst-compare`は標本を`records::Writer`で合成として書き、バイト列を独自に組み立てていた書き出し処理を削除する。
- 来歴JSONを撤去する（`training/provenance.rs`、`datagen/provenance.rs`、`data selfplay provenance`、学習器の`InputProvenance`）。開始局面一覧が使う`GameOrigin`は`selfplay_gen/opening.rs`へ移す。`.games.json`は除外の報告へ統合する。
- 学習器は版2を読み、`--lambda-override`を必須の`--lambda`に改め、`config.json`の入力の識別を改める。診断の`file_identity`と、FMの補正を縮める`fm quarter`と`fm scale`の報告も、同じ方法で入力を識別する。
- 変換コマンドを実装し、`data/`の284ファイルを変換する。
- MNSDの仕様のdocコメント、[NNUEの学習手順](../guides/nnue-training.md)、および[PSTとFMの学習手順](../guides/pst-training.md)を同じコミットで直す。

完了条件は、`cargo test --workspace`が通り、`git grep -iE "rescore|provenance" -- crates`が何も返さず、検証の1から4が通ることである。

フェーズ3では、チェックポイントの包みを1種類にする。
FMと同時学習を`MNTRCKPT`の包みへ移し、`nnue-float.bin`の書き出しをやめて、`diag nnue-removal --float`は`best.bin`を読む。
完了条件は、4種の学習器がそれぞれ短い学習を中断して再開でき、中断しない学習と同じ損失の列を出すこと、および`data/`の12個の既存のチェックポイントが読めることである。

フェーズ4では、変換コマンドを削除し、形式の一覧の手引きを最終の形式の集合と照らし合わせる。

## 検証

1. 変換の前後で同じ結果が出る。入力は、乱数開始の自己対局の2ファイル（`data/nnue-replacement-gen`の`generated-2000000.bin`と`generated-2100000.bin`）、および`data/strength-stage9`の実戦対局と実戦開始の自己対局のファイル（`human/human.bin`と`diag-c/human-start.bin`）の2組である。フェーズ1と同じ条件で学習し、局面数、教師用K、各エポックの訓練損失と検証損失が、フェーズ1の記録とビット単位で一致する。
2. 変換コマンドは、元のファイルとバイト156と157以外が一致することを全レコードで確かめてから置き換える。また、来歴の教師の情報とヘッダが一致しないファイル、由来が3通りに当てはまらないファイル、実戦に由来するデータで棋譜IDが欠けたファイル、および`--synthetic`を指定せずに渡した来歴JSONのないファイルを、何も書き換えずに拒否する。
3. 学習器は、版1のMNSD、合成のレコードを含むMNSD、1ファイル内で由来が混在するMNSD、同じ対局で検証の所属が混在するMNSDを、明示的なエラーで拒否する。
4. `data selfplay inspect`と`diag nnue-moves --positions`が、変換後の合成のファイルを読める。
5. 各形式について、docコメントのバイト位置と欄の名前を符号化関数と突き合わせる。

## 完了条件

形式が36から32へ減っていること（MNRS、対象番号ファイル、来歴JSON、`.games.json`の4つを廃止する）。
独自のマジックが7から4へ減っていること（MNRSを廃止し、FMと同時学習のチェックポイントのマジックを`MNTRCKPT`へまとめる）。
`data/`のMNSDが版2へ変換され、検証の1から4が通っていること。
残った全形式の仕様が、読み書きするモジュールのdocコメントにあり、形式の一覧が手引きにあること。
教師データの全体の検査和が、どのコマンドでも計算されていないこと。

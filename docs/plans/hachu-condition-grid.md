# HaChu対minaseの条件格子測定の設計書

## 先に読む要約

本マイルストーンでは、外部エンジンHaChuとminaseの強さの差が、思考時間の比と置換表容量の比によってどう変わるかを測る。
これまで段階ごとの進捗記録では、両者に同じ持ち時間（60秒＋1手1秒加算）と同じ置換表容量（256 MB）を与えた対等条件でHaChu戦を記録してきた。
今回はHaChuの条件を対等条件のまま固定し、minaseの持ち時間を1、1/2、1/4、1/8倍に縮めた4条件と、minaseまたはHaChuの置換表を16 MBまたは1,024 MBへ変えた4条件、計8条件（以下、セルと呼ぶ）で対局させる。
各セルでは同じ200個の開始局面を使い、同じ開始局面で先手と後手を入れ替えて2局ずつ戦う（この2局を1ペアと呼ぶ）。
結果はセルごとにEloと95%信頼区間で記録する。
Eloは勝率をロジスティック関数で写した強さの差であり、100 Eloの差は約64%の勝率に相当する。
採否を判定する測定ではなく条件ごとの効果量を並べる測定なので、採否用の逐次確率比検定（GSPRT）は使わず、ペア数を固定して測る。
対局ハーネス`match_runner`には置換表容量を指定する手段がなかったので、候補と基準ごとに容量を指定するオプションを先に追加する。
8セルの完了後、利用者の「1手固定時間ではminase 1秒対HaChu 2秒でHaChuが明確に強い」という仮説を確かめるため、1手固定時間の2セル（fixed1-2とfixed1-1）を追加した。
完了条件は、全セルの測定記録が揃い、本書の状態の節にEloの一覧表が載ることである。

## 目的

HaChuに対するminaseの強さは、段階ごとの進捗指標として対等条件の固定200ペアEloで記録してきた。
直近の[段階5の記録](../measurements/strength-stage5-hachu-elo200.md)では+188.5 Elo（95%信頼区間+153.1〜+228.0）である。
一方、[非対称時間の要因分析](../measurements/hachu-vs-search-tc-handicap-4x.md)では、minaseに120秒＋2秒加算、HaChuに30秒＋1秒加算を与えると、当時の等時間の−252 Eloが+14 Eloまで回復しており、持ち時間の比が強さの差に大きく影響することが分かっている。
ただしこの測定は基本時間4倍、加算2倍の非対称条件であり、今回の比例縮小と同じ倍率効果ではない。
本測定は、持ち時間の比と置換表容量の比を系統的に変え、どの条件でどちらがどれだけ強いかをEloで示す。
持ち時間の比については、minaseの持ち時間をどこまで縮めるとEloが0付近まで下がるかを見る。
たとえば1/4で0付近になれば、対等条件の強さの差はminaseにとって持ち時間4倍分に相当すると解釈できる。
置換表容量の比については、この時間制御で置換表の大小がどれだけ強さに影響するかを、両エンジンについて確かめる。

## 適用範囲

対象は、HaChuの既定規則（RULES.md第33条第7項、`L1,L3,P0,P5,P6,R2,E1,E2`）による、現行HEADのminaseとHaChuの対局である。
minaseは`Threads=1`とし、規則、開始局面の作り方、およびハーネスの異常時の裁定は既存のHaChu戦と同じにする。
ハーネスの変更は、候補と基準ごとに置換表容量を指定して記録する機能に限る。

自己対局での置換表感度、`Threads>1`での測定、HaChuの規則オプションの変更、および両エンジンの条件を同時に変える格子は対象外とする。
測定結果は解釈にとどめ、探索や時間管理の変更には直接つなげない。

## 依存関係

対局の実行、保存、および再開は[対局ハーネスのバイナリ対戦化](match-harness.md)と[棋力測定ハーネス基盤の効率化](match-harness-efficiency.md)を前提とする。
HaChuとのCECP接続は[外部対局接続](engine-connectivity.md)が確立した手順に従い、HaChuの版とビルド手順は既存のHaChu戦の記録と同じである。
固定局数Eloの統計契約は[SPRTによる棋力測定の手引き](../sprt.md)の「進捗記録の固定局数Elo」の節が定める。

## 設計判断

HaChuの条件を固定し、minaseの条件だけを変える。
既存の段階記録はすべてHaChuを60秒＋1秒加算、256 MBで測っているので、同じHaChu条件に対するEloとして横並びに比較できる。
両者の条件を同時に変える案は、時間比と絶対時間の効果が混ざるため棄却した。
ただし置換表容量については、HaChu側の感度も知りたいので、minase側を256 MBに固定してHaChu側だけを変えるセルも置く。

測定は固定200ペアEloとし、GSPRTを使わない。
本測定は機能の採否ではなく効果量を条件ごとに並べる測定であり、docs/sprt.mdの「進捗記録の固定局数Elo」の枠に当たる。
200ペアは既存のHaChu戦の記録と同じ精度であり、1セルの95%信頼区間の幅は約±35 Eloである。
2セルの差の95%信頼区間は独立なら約±50 Eloになるので、本測定は条件ごとの概況を把握する標本数と位置付け、差が約50 Elo未満の2セルを「異なる」とは主張しない。
セル間の差の解釈は、時間比の隣り合うセル同士と、置換表比の各セルと対等条件のtime1との比較に限る。

持ち時間は基本時間と加算を同じ比で縮める。
時間制御の表記`60000+1000`はミリ秒単位の「基本時間+1手ごとの加算」であり、対等条件は60秒＋1秒加算である。
たとえば1/4のセルは`15000+250`、すなわち15秒＋0.25秒加算であり、1手あたりの時間配分の形を保ったまま総思考時間だけを変える。
加算だけを変える案は時間管理の挙動を変えてしまうため棄却した。
CECP側の時間制御は整数秒に限られるが、変えるのはUSI側のminaseなので制約に触れない。

置換表容量は2の冪に限る。
HaChuは`memory`で受けた容量を2の冪へ丸めて確保するため（hachu.cの`SetMemorySize`）、記録した値と実際の容量を一致させるには2の冪を指定する必要がある。
測定者がCECPエンジンに2の冪以外の容量を指定した場合、ハーネスは対局を始めずにエラーで停止する。

置換表容量はハーネスの対局条件として指定し、機能比較のスイッチにはしない。
docs/sprt.mdが禁じるのは差分の内容を知るスイッチであり、時間制御と同じく両エンジンへ与える資源条件は`manifest.json`に記録される条件である。
指定がなければ従来どおりエンジンの既定値（minaseは`USI_Hash`の既定256 MB、CECPは`memory 256`）で走るので、既存の測定手順は変わらない。

結果の正は実行ディレクトリの`pairs/`、累計実行時間の正は`summary.json`の`active_wall_time_ns`である。
時間制御が等しいtime1と置換表比の4セルは、docs/sprt.mdの定めどおり`match_report`で保存記録から再集計したJSONを記録の値とする。
`match_report`は候補と基準の時間制御が等しい測定だけを受け付けるため、minaseの持ち時間を縮めた3セルは、[自己対局の持ち時間感度](../measurements/sensitivity-time2x.md)と同じく`match_runner`の標準出力の要約（ペンタノミアル度数、Elo、信頼区間、異常件数）を記録の値とする。

全セルで同じ基本シードを使い、同じ200個の開始局面で戦わせる。
開始局面はペア番号ごとにシードから決定的に派生するので、シードを揃えればセル間の差に開始局面の違いが混ざらない。
時間制御の対局は着手時間の実測に依存するため、同じシードでも対局そのものは再現されない。
隣接シードの衝突（[教訓](../lessons/derive-seed-adjacent-collision.md)）は意図しない重複を避ける規則であり、比較のために意図して局面を揃えることは妨げない。
シードは既存の記録が10,000刻みで使ってきた系列（直近は20550903）の次の値20560903とする。

同時対局数は全セルで12に統一する。
時間制御の対局ではCPUやメモリ帯域の競合が探索量に影響し得るため、セルごとに同時対局数を変えると、置換表容量の効果と並列度の効果が混ざる。
置換表1,024 MBのセルは18並列だと置換表だけで約22.5 GiBになり実メモリ約30 GiBに対して余裕がないので、この制約で決まる12を全セルの共通値とする。

## 測定格子

HaChu側の時間制御は全セルで`time=60000+1000`に固定し、置換表容量は表の指定に従う。minaseは`Threads=1`である。
測定名は`hachu-grid-<セル名>`であり、実行ディレクトリと測定記録のファイル名に使う。

| セル名 | minase持ち時間 | minase置換表 | HaChu置換表 |
|---|---|---|---|
| time1 | 60000+1000 | 256 MB | 256 MB |
| time1of2 | 30000+500 | 256 MB | 256 MB |
| time1of4 | 15000+250 | 256 MB | 256 MB |
| time1of8 | 7500+125 | 256 MB | 256 MB |
| hash16-256 | 60000+1000 | 16 MB | 256 MB |
| hash1024-256 | 60000+1000 | 1,024 MB | 256 MB |
| hash256-16 | 60000+1000 | 256 MB | 16 MB |
| hash256-1024 | 60000+1000 | 256 MB | 1,024 MB |

1手固定時間のセルは次の2つである。

| セル名 | minase | HaChu |
|---|---|---|
| fixed1-2 | 1手1秒（`time=0+0,byoyomi=1000`） | 1手2秒（`time=0+0,byoyomi=2000`、`st 2`） |
| fixed1-1 | 1手1秒 | 1手1秒（`st 1`） |

fixed1-2が利用者の仮説の条件であり、fixed1-1は固定時間という方式そのものがminaseに不利かどうかを比率と切り離して見る参照である。
minaseは秒読み1秒を時間管理の安全余裕（30 ms）の内側で使い切る。
HaChuは`st`のとき毎手の`time`の値（ハーネスは秒読みを送る）の0.4倍を目標とし、0.16倍を超えたら新しい反復深化を始めず、0.98倍で探索を中断するので、実際の思考時間は指定値より短くなる。
この挙動はHaChu自身の固定時間の定義であり、記録には実際の思考時間の分布を併記する。

シードは全セルで20560903、同時対局数は全セルで12である。
CECPエンジンは`Threads`を報告しないため同時対局数の自動計算は使えず、毎回明示する。
置換表1,024 MBのセルの置換表合計は（1,024＋256）MiB×12で約15 GiBである。

時間比のセルは、既存の`--candidate-limit`と`--baseline-limit`で両者に別の時間制御を与える。
コマンドは次の型である。

```console
match_runner --run-dir data/matches/hachu-grid-time1of4 --seed 20560903 \
  --candidate commit:<minaseのコミット> --candidate-limit time=15000+250 \
  --baseline "cecp:../hachu-debian/hachu" --baseline-limit time=60000+1000 \
  --rules L1,L3,P0,P5,P6,R2,E1,E2 --concurrency 12 elo --pairs 200
```

置換表比のセルは時間制御を`--each`で揃え、本マイルストーンで追加する`--candidate-hash`と`--baseline-hash`で容量を与える。
1手固定時間のセルは、両側に基本時間と加算が0で秒読みだけの時間制御を与える（例: `--candidate-limit time=0+0,byoyomi=1000 --baseline-limit time=0+0,byoyomi=2000`）。
コマンドは次の型である。

```console
match_runner --run-dir data/matches/hachu-grid-hash16-256 --seed 20560903 \
  --candidate commit:<minaseのコミット> --candidate-hash 16 \
  --baseline "cecp:../hachu-debian/hachu" --baseline-hash 256 \
  --rules L1,L3,P0,P5,P6,R2,E1,E2 --each time=60000+1000 --concurrency 12 elo --pairs 200
```

`match_runner`は、ハーネス変更のコミットを取り出したgit worktree（本体の作業ツリーとは別の場所に同じリポジトリを展開したもの）でビルドし、全セルでそのバイナリを使う（[教訓](../lessons/pin-generation-binary-to-worktree.md)）。
本体の作業ツリーで開発を続けてもバイナリが変わらないようにするためである。
セルは1つずつ直列に走らせ、同時に2セルを走らせて同時対局数の前提を崩さない。
順序は、対等条件のtime1を基準として最初に測り、次に互角に近いと予想されるtime1of4、続いてtime1of2、time1of8とする。
置換表比はhash16-256、hash256-16、hash1024-256、hash256-1024の順とし、メモリを多く使う2セルを最後に置く。
所要時間は、等時間のセルで約4.5時間、minaseの持ち時間を縮めたセルでは対局が短くなる分だけ減り、合計約32時間を見込む。

## 実装フェーズ

1. ハーネスに`--candidate-hash`と`--baseline-hash`（MB）を追加し、CECPエンジンに秒読みだけの時間制御を`st`として伝える対応を加える。USIエンジンには`setoption name USI_Hash`、CECPエンジンには`memory`で伝え、`manifest.json`の`hash_mb`に明示値を記録する。完了条件は、単体テストとclippyが通ることである。あわせてdocs/sprt.mdへ指定方法を追記する。
2. 煙試験を行う。固定深さの1ペアで16 MBと1,024 MBの指定がHaChuとminaseの双方で起動と対局を通り、`manifest.json`の`hash_mb`が指定値になることを確認する。加えて、最短のtime1of8の時間制御で1ペアを対局させ、時間切れが出ないことと、保存された着手時間から長手数の局面でも残り時間が安全余裕の内側に収まることを確認する。煙試験の実行ディレクトリは記録に残さない。完了条件は、両容量と最短時間制御で異常件数が0であることである。
3. 8セルを測定し、セルごとに`docs/measurements/hachu-grid-<セル名>.md`へ記録する。完了条件は、8件の記録がdocs/plans/README.mdの6見出しを持ち、異常件数と拒否着手を記載していることである。
4. 本書へ8セルのEloと95%信頼区間の一覧表を載せ、状態を完了に書き換え、docs/ROADMAP.mdの状態表と現在地を更新する。

## 検証

各セルの終了時に、標準出力の要約から`engine_failures`の理由別件数、`time_forfeits`、および`rejected_moves`を確認する。
`time_forfeits`は規約どおり当該局の負けとして算入するが、0でなければ原因を調べ、そのセルのElo低下を探索量の減少だけの効果とは解釈しない。
`rejected_moves`は、審判層が合法とした着手を相手エンジンが拒否した件数であり、0でなければ規則の不一致が疑われる。
HaChuには、敵陣入域時に不成を選んだ歩兵が最奥段へ非捕獲で到達する成りを拒否する既知の規則差（RULES.md第30条P5の典拠欄、[等時間GSPRTの記録](../measurements/hachu-vs-search-tc60.md)）があるので、当該局の着手列を再現してこの既知差かどうかを判定してから記録する。
HaChuは2,000手を超える対局で棋譜配列の上限により異常終了することが分かっており、これは当該局のHaChuの負けとして算入される既知の挙動なので、件数を記録して結論の感度を確認する。
置換表1,024 MBのセルでは、測定中の実メモリ使用量を確認し、スワップが発生していないことを記録する。

## 完了条件

8セルの測定記録が`docs/measurements/`に揃い、いずれも異常の内訳を記載していること。
本書の状態の節に、8件の記録へのリンクとEloおよび95%信頼区間の一覧表が載り、持ち時間2倍あたりのEloが参考値として書かれていること。
この値は時間比が隣り合うセルのElo差として定義する参考値であり、Eloが時間比の対数に比例するとは仮定せず、採否の根拠にも使わない。

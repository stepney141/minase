# Lazy SMPの設計書

## 実施状況

2026年8月13日に本設計書を起案した。
実装は未着手である。

起案時点では、探索部マイルストーンのフェーズ1、2、3、5と、外部対局接続マイルストーンのフェーズ1が完了している。
本マイルストーンは、探索部の静止探索と第2層の探索改良の採否が完了し、外部対局接続のCECP対局進行が完成した後に着手する。
この順序により、単一ワーカー探索の基準を固定してから並列化し、探索改良と並列化の効果を別々に測定する。

起案にあたり、2026年8月13日時点のStockfishとやねうら王の実装を一次資料として確認した。
両実装とも、複数の探索ワーカーが独立に反復深化を実行し、置換表を共有した後に探索チームの結果を集約する構造を採っている。
ただし、両実装が許容する競合をRustの通常メモリアクセスで再現すると未定義動作になるため、Minaseではデータ競合のない原子型の置換表を使う。

## 目的

本マイルストーンは、対称型マルチプロセッシング（symmetric multiprocessing、SMP）環境で複数の探索ワーカーを同時に動かし、同じ壁時計時間で到達できる探索深さと棋力を向上させる。
方式は、各ワーカーが独立した反復深化アルファベータ探索を行い、置換表だけを共有するLazy SMPとする。

Lazy SMPは着手を乱数で変える機能ではない。
ワーカー数が2以上の場合は共有置換表へのアクセス順が実行時スケジューリングに依存するため、同じ局面と制限でも結果が変わり得るが、この非決定性を着手多様化の手段として扱わない。

完了基準は次の4点とする。

- `Threads=1`で、着手、評価値、深さ、ノード数、主変化、および固定深さbenchの総ノード数が実装前と一致する。
- `Threads=2`以上で、全ワーカーが同じ停止要求と探索予算に従い、合法な最善手を1回だけ返して終了する。
- 時間制御のコミット対コミット一般化逐次確率比検定（GSPRT）で、`Threads=2`が`Threads=1`に対してH1へ到達する。
- Universal Shogi Interface（USI）の`Threads`とChess Engine Communication Protocol（CECP）の`cores`から、次の探索に使うワーカー数を設定できる。

## 適用範囲

本マイルストーンでは、次の作業を行う。

- 置換表を、複数ワーカーが共有できる原子型の16バイトエントリへ変更する。
- 現行の探索スレッドを探索チームの調整役兼主ワーカーへ変更し、探索ごとに補助ワーカーを生成して終了時に全員を待機する。
- 停止要求、hard limit、soft limit、およびノード上限を探索チーム全体へ適用する。
- USIの`Threads`オプションとCECPの`smp=1`および`cores`コマンドを実装する。
- 固定局面benchへワーカー数と反復回数を追加し、単一ワーカーの回帰と並列時の速度向上を分けて測定する。
- 並列探索時の再現性と測定条件を`docs/sprt.md`へ追記する。

次の項目は対象外とする。

- 先読み（ponder）、分散メモリ探索、非均一メモリアクセス（non-uniform memory access、NUMA）配置、中央処理装置（CPU）の固定割り当て、および永続ワーカープールは実装しない。
- 補助ワーカーの結果による投票、最深ワーカーの採用、および複数主変化出力は実装しない。
- 乱数によるルート手選択、低棋力化、および定跡手の乱択は実装しない。
- 置換表のクラスタ化、ノード数の一括予約、および停止確認周期の短縮は、実測で必要性が示されるまで実装しない。
- `match_runner`へ候補側と基準側の機能を切り替えるオプションは追加しない。
- `src/core/`と評価関数は変更しない。

## 依存関係

探索部の静止探索と第2層の探索改良を先に完了させる。
探索順序、枝刈り、および延長を並列化と同時に変更すると、棋力差と性能差の原因を分離できないためである。

外部対局接続のCECP対局進行も、本マイルストーンのプロトコル接続フェーズより先に完了させる。
CECPの状態機械と探索中コマンドの所有権は`engine-connectivity.md`にあり、本マイルストーンは完成した境界へ`smp`と`cores`だけを追加する。

評価関数の本格化は本マイルストーンの着手条件ではない。
Lazy SMPの採否は、着手時点で完成している単一ワーカー探索を基準として独立に測定する。

## 設計判断

| 項目 | 決定 |
|---|---|
| ワーカー数 | `Threads`は主ワーカーを含む探索ワーカーの総数とし、既定値1、最小値1、最大値256とする。入力値をCPU数に合わせて暗黙に変更しない。 |
| 探索制限との境界 | ワーカー数は停止条件ではないため`SearchLimits`へ追加せず、`NonZeroUsize`として探索開始関数へ明示的に渡す。 |
| ワーカーの寿命 | 現行どおり探索ごとにスレッドを生成する。永続ワーカープールは導入しない。 |
| 共有状態 | 置換表、停止状態、停止理由、総ノード数、開始時刻、および時間予算だけを共有する。局面、合法手生成器、探索経路、主変化、および将来の探索履歴はワーカーごとに所有する。 |
| 最善手 | 主ワーカーの最後に完了した反復深化だけを最終結果とする。補助ワーカーは置換表を温めるが、進捗と最善手を直接返さない。 |
| 多様化 | 補助ワーカーは、通常の指し手順序付け前のルート合法手列をワーカー番号だけ左回転する。時刻と乱数は使わない。 |
| 置換表容量 | `USI_Hash`とCECPの`memory`は全ワーカーで共有する置換表の総容量を表し、ワーカー数倍に増やさない。 |
| ノード上限 | `go nodes N`は探索チーム全体で最大Nノードとし、ワーカーごとにNノードを与えない。 |
| 進捗 | `Progress`は主ワーカーのイテレーション完了時だけ送る。`nodes`は送信時点のチーム総数とし、`Finished`は全ワーカーの終了後に1回だけ送る。 |
| 再現性 | `Threads=1`は現行の決定性を維持する。`Threads>1`は固定深さと固定ノード数でも完全再現を保証しない。 |
| 対応環境 | 原子型の64ビット整数を利用できる共有メモリ環境を対象とする。該当しないコンパイル対象はコンパイル時に明示的に拒否する。 |

## 探索チーム

`start_search`が生成する現行の探索スレッドを、探索チームの調整役兼主ワーカーとする。
このスレッドは共通状態を構築し、`std::thread::scope`内で`Threads-1`本の補助ワーカーを生成した後、自身で主ワーカーの探索を実行する。
`scope`を抜ける前に全補助ワーカーを待つため、正常終了、停止、および`panic`のいずれでも孤児スレッドを残さない。

`SearchHandle`の公開契約は探索スレッド1本から探索チーム全体へ読み替える。
`request_stop`はチーム共通の停止状態を更新し、`join`は全ワーカーの終了後に共有置換表を返す。
ワーカー生成に失敗した場合は少ないワーカー数へ縮退せず、探索チームを失敗させて既存のチャネル切断とjoinエラーの経路へ接続する。

`SearchSnapshot`は調整役が所有し、scope内の全ワーカーが不変参照する。
各ワーカーは根局面を複製し、`Searcher`、合法手生成器、探索経路、主変化、および局所ノード数を個別に持つ。
置換表の世代は調整役がワーカー生成前に1回だけ進め、ワーカーごとには更新しない。

主ワーカーは深さ1から通常どおり反復深化する。
補助ワーカーも同じ深さ列を探索するが、ルート合法手列をワーカー番号だけ左回転してから既存の安定な指し手順序付けを適用する。
これにより、置換表手と捕獲価値の優先順位を保ちながら、同順位のルート手の開始順を決定的に分散する。

補助ワーカーが深さ上限へ到達しても、主ワーカーと他の補助ワーカーを停止しない。
主ワーカーが深さ上限またはsoft limitへ到達した場合と、いずれかのワーカーがhard limitまたはノード上限へ到達した場合は、共通停止状態を更新して全員を巻き戻す。

## 共有置換表

現行の`Vec<Entry>`と`&mut TranspositionTable`は複数ワーカーから共有できないため、置換表の操作を`&self`で行う原子型へ変更する。
1エントリは次の16バイトとし、現行と同じ容量計算とスロット数を維持する。

| 原子値 | 内容 |
|---|---|
| `AtomicU64 critical` | 検証キー32ビット、評価値16ビット、深さ8ビット、バウンド2ビット、および予約6ビット。 |
| `AtomicU64 advisory` | 指し手25ビット、世代8ビット、および予約31ビット。 |

指し手は`from`、`mid`、`to`の各8ビットと成り1ビットで25ビットに収まる。
評価値によるカットオフへ必要な検証キー、評価値、深さ、およびバウンドを1回の原子的読み取りで得るため、競合中も異なる書き込みの値を組み合わせない。

書き込み側は`advisory`をRelaxedで書いた後に`critical`をReleaseで公開し、読み取り側は`critical`をAcquireで読んでから`advisory`をRelaxedで読む。
競合する別の書き込みにより、記録手または世代だけが`critical`と異なる書き込みに由来する可能性は許容する。
記録手は指し手順序付けにしか使わず、復号と現局面の合法手列への所属を検証してから採用するため、取り違えても評価値による誤ったカットオフは起こらない。
世代は置換優先度にしか使わないため、取り違えは書き込みの採否だけに影響し、探索値の正しさを変えない。

書き込み側は読み取った既存値から現行と同じ置換可否を判定し、競合を待たずに2個の原子値を更新する。
最後に公開された`critical`が有効な探索値となり、競合で失われた記録手と世代は置換表の助言的情報として扱う。
検証キー、予約ビット、バウンド、および指し手の復号に失敗した場合は置換表の未命中として扱い、不正な`Move`を構築しない。

`clear`と`resize`は探索チームが存在しないときだけ実行する。
`USI_Hash`とCECPの`memory`の変更、新規対局、および規則変更は、既存どおり実行中探索を停止してjoinした後に置換表へ適用する。

## 停止と探索予算

探索チームは、外部停止フラグ、チーム停止フラグ、停止理由、総ノード数、開始時刻、および時間予算を共有する。
外部停止と内部停止を別の原子値にすることで、他ワーカーが立てた停止を`ExternalStop`と誤認しないようにする。

停止理由の優先順位は、`ExternalStop`、`HardLimit`、`NodeLimit`、`SoftLimit`、`DepthCompleted`の順とする。
複数条件が近接した場合は原子値に優先度の高い理由を残し、実行順による表示上の揺れを抑える。

総ノード数は`AtomicU64`で数える。
ノード上限がある場合は各ノードの進入時に`compare_exchange`で1ノードを予約し、Nノードを超える予約を拒否して`NodeLimit`を設定する。
初版では一括予約を行わず、`Finished.nodes`がNを超えない契約を優先する。

hard limitは全ワーカーが同じ開始時刻から計算した期限と比較する。
スレッド生成時間は利用者が観測する思考時間に含まれるため、開始時刻は補助ワーカー生成前に記録する。
soft limitは主ワーカーのイテレーション境界だけで評価し、補助ワーカーの完了時点では評価しない。

現在の4096局所ノードごとの時計確認は初版で維持する。
ワーカー数に伴う停止遅延は時間制御試験で測定し、時間切れまたは過大なjoin遅延が観測された場合に限り、確認周期を別コミットで変更してGSPRTにかける。

## プロトコル設定

USIの握手では、次のオプションを宣言する。

```text
option name Threads type spin default 1 min 1 max 256
```

`setoption name Threads value N`は1以上256以下の10進整数だけを受理する。
値の欠落、非整数、0、および上限超過には固定した`info string error`を返し、直前の設定を保持する。
探索中に届いた設定変更は既存の入力待機列に載せ、実行中探索を変更せず次の探索から適用する。

CECPでは`feature smp=1`を宣言し、`cores N`を同じ範囲で受理する。
不正値は固定したCECPエラーを返し、少ない値やCPU数へ丸めない。
USIの`Threads`とCECPの`cores`は同じ探索開始引数へ写し、プロトコルごとの並列探索実装を作らない。

`Threads`の既定値は、検証後も1を維持する。
利用可能CPU数を既定値に使うと、同じバイナリの資源消費と再現性が環境に依存するためである。

## 再現性

`Threads=1`では共有置換表への競合がないため、現行の固定深さと固定ノード数の完全再現契約を維持する。
原子型への置換後も、置換規則、容量、スロット番号、および世代幅を変えず、既存benchの総ノード数を一致させる。

`Threads>1`では、固定深さと固定ノード数でも共有置換表の公開順がオペレーティングシステム（OS）のスケジューリングに依存する。
このため、`docs/sprt.md`の完全再現契約を`Threads=1`に限定し、並列時には合法手、予算上限、イベント順序、および停止後の全joinだけを決定的な契約とする。

固定深さbenchは`--threads N`と`--repetitions R`を受け取る。
`Threads=1`かつ反復1回の既定出力は現行の決定性検査に使い、`Threads>1`はウォームアップ1回を除く5回以上の中央値で、到達深さ、総ノード数、経過時間、ノード毎秒、および単一ワーカーに対する速度比を記録する。

## 採否測定

並列化の棋力採否は、`docs/sprt.md`に従って時間制御のコミット対コミットGSPRTで行う。
固定ノード数では計算資源の増加による時間短縮を棋力へ反映できず、固定深さでは両者の探索深さが同じになるため、いずれも主たる採否条件には使わない。

測定用の基準コミットは、並列探索の全コードを含み、`DEFAULT_THREADS=1`としたコミットとする。
候補コミットはこの定数だけを2へ変更し、`match_runner`にはワーカー数を設定する機能比較スイッチを追加しない。
測定後は結果にかかわらず製品の既定値を1へ戻し、利用者がプロトコル設定で明示した場合だけ並列探索を有効にする。

最初に`Threads=2`対`Threads=1`を測定する。
対立仮説H1へ到達した場合だけ`Threads=4`対`Threads=2`を追加測定し、帰無仮説H0へ到達した場合は原因を分析して設計へ戻る。
判定保留の場合は、同じ仮説と時間制御を保ったまま上限ペア数を延長し、都合のよい水準へ変更しない。

時間制御は両者に同じ壁時計条件を与える。
候補側がより多くのCPU時間を使うことは並列規模拡大の測定対象であり、同一CPU時間の比較とは呼ばない。
同時対局数Cは、`C × max(候補Threads, 基準Threads)`が利用可能な物理コア数を超えない値とし、OSとハーネス用に1コア以上を残す。

測定記録には、通常のGSPRT記録に加えて、CPU型、物理コア数、論理コア数、両エンジンのワーカー数、`USI_Hash`、同時対局数、時間制御、および`time_forfeits`を含める。
時間制御対局は完全再現の対象外であるが、着手の非決定性を理由に測定結果を選別しない。

## 実装フェーズ

### フェーズ1　原子型置換表

置換表エントリを16バイトの原子型へ置き換え、`probe`と`store`を`&self`へ変更する。
エントリの詰め込み、公開順序、競合書き込み、世代更新、無効データの未命中化、およびサイズ上限を単体テストで固定する。

このフェーズは`Threads=1`だけで実行し、既存の探索結果とbench総ノード数が完全一致しなければ次へ進まない。
一致しない場合は棋力測定で正当化せず、置換表の意味論を修正する。

### フェーズ2　探索チーム

調整役兼主ワーカー、補助ワーカー、`scope`による全join、ワーカー固有状態、決定的なルート順序分散、および主ワーカーだけの結果採用を実装する。
`Threads=1`の経路も同じ調整役を通し、単一ワーカー専用の旧経路は残さない。

### フェーズ3　共通停止と予算

停止理由、総ノード数、開始時刻、hard limit、およびsoft limitを探索チームの契約へ移す。
外部停止、ノード上限、時間上限、深さ上限、およびワーカーの`panic`について、全joinと1回だけの完了通知を検証する。

### フェーズ4　プロトコルとbench

USIの`Threads`、CECPの`smp=1`と`cores`、およびbenchのワーカー数と反復回数を実装する。
`docs/sprt.md`の再現性契約と並列測定の記録項目を更新する。

### フェーズ5　性能と棋力の採否

固定局面benchで`Threads=1`、2、4の経過時間とノード毎秒を測定し、オーバーサブスクリプションがない条件を確定する。
次に、既定ワーカー数だけが異なる測定コミットを作り、時間制御GSPRTで`Threads=2`対1を判定する。
H1の場合だけ`Threads=4`対2へ進み、各結果を本設計書の実施状況へ記録する。

## 検証

各フェーズで次のコマンドを実行する。

```console
cargo test
cargo clippy --all-targets
cargo fmt --all -- --check
git diff --check
```

単体試験と台本試験では、次の契約を検証する。

- 原子型置換表は、同一スロットへの並行`probe`と`store`を反復しても`panic`せず、不正な指し手を返さない。
- `Threads=1`は既存の探索結果、主変化、進捗深さ、ノード数、およびbench署名を維持する。
- `Threads=2`と4は、深さ、ノード、時間、無期限探索からの`stop`、`gameover`、`quit`、および入力終了で全ワーカーをjoinする。
- `Progress.depth`と`Progress.nodes`は単調増加し、`Finished`と`bestmove`は各探索で1回だけ出力される。
- `go nodes N`の`Finished.nodes`はNを超えず、`USI_Hash`の実メモリ量はワーカー数で増えない。
- 探索中の`Threads`、`cores`、`USI_Hash`、および`memory`変更は、実行中探索を変えず次の探索へ反映される。
- 1、2、4ワーカーで短時間制御の反復試験を行い、スレッドリーク、`panic`、反則手、および時間切れがないことを確認する。

並行性の検査は通常テストだけに依存しない。
ThreadSanitizerを利用できるRust nightly環境では置換表の競合試験を実行し、利用できない場合はその事実を検証記録へ明記する。

## 完了条件

- 原子型置換表が16バイト以内であり、`Threads=1`のbench署名と探索結果が実装前に一致している。
- 探索チームの共有状態とワーカー固有状態が設計どおり分離され、停止後に全ワーカーがjoinされている。
- `Threads=2`以上でも、探索予算、イベント順序、合法手、および置換表容量の契約を満たしている。
- USIの`Threads`とCECPの`cores`が、暗黙の丸めや縮退なしに同じワーカー数設定へ接続されている。
- 固定局面benchの並列測定と、`Threads=2`対1の時間制御GSPRTが記録され、GSPRTがH1へ到達している。
- `docs/sprt.md`が、完全再現を`Threads=1`へ限定し、並列測定の資源記録を要求している。
- 全検証コマンドが成功し、時間制御の反復試験で`time_forfeits=0`である。

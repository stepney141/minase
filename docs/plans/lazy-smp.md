# Lazy SMPの設計書

## 先に読む要約

本マイルストーンは、複数のCPUコアで探索を並列に実行し、同じ思考時間でより深く読めるようにする。
方式のLazy SMPとは、複数の探索ワーカー（スレッド）がそれぞれ独立に反復深化探索（深さ1から1段ずつ深くして探索を繰り返す方式）を行い、探索済み局面の結果を保存する置換表だけを共有する並列化方式であり、ワーカー間の作業分担を明示的には調整しない。
Minaseでは、置換表をデータ競合のない原子型の16バイトエントリへ改め、主ワーカーが補助ワーカーを生成して停止と探索予算をチーム全体で共有し、USIの`Threads`とCECPの`cores`でワーカー数を設定できるようにした。
初版では、固定局面bench（固定した局面集合を一定の深さまで探索して所要時間とノード数を測る性能試験）で経過時間が短縮せず、時間制御の自己対局でも棋力差が出なかった。
原因は2つあり、第1に補助ワーカーが主ワーカーと同じ深さを遅れてなぞる複製になって新しい情報を置換表へ供給しなかったこと、第2に全ノードの約98%を占める静止探索（駒の取り合いの途中で評価すると駒得を誤るため、捕獲手だけを読み続けて局面が静まるまで評価を延ばす探索）が置換表を使っておらず、共有の利益が及ばなかったことである。
第2版では、静止探索でも置換表を照会・記録し、補助ワーカーが一部の深さを飛ばして主ワーカーより先の反復へ進むことで、主ワーカーが同じ深さへ到達したときに先に書かれた置換表の記録で探索を短縮できるようにし、停止時に最も深い反復を完了したワーカーの結果を採用する方式へ改めた。
採否は、[docs/sprt.md](../sprt.md) に定める時間制御のGSPRT（一般化逐次確率比検定。対局を重ねながら候補が基準より有意に強いかを統計的に判定する手法）で、`Threads=2`対`Threads=1`を比べて判定する。
結果は上限500ペアで判定保留であったが、同じ対局結果から固定局数のElo（勝率から換算した強さの差の尺度）を求めると+62（95%信頼区間 +41から+83）であった。
本書の採否測定の節は500ペアで判定保留なら不採用と定めているが、信頼区間が0を大きく上回ることを根拠に、この規定からの逸脱を明記したうえで採用し、2026年8月23日に完了した。
製品の既定ワーカー数は1のままであり、利用者が明示した場合だけ並列探索が有効になる。

## 目的

本マイルストーンは、対称型マルチプロセッシング（symmetric multiprocessing、SMP）環境で複数の探索ワーカーを同時に動かし、同じ壁時計時間で到達できる探索深さと棋力を向上させる。
方式は、各ワーカーが独立した反復深化アルファベータ探索を行い、置換表だけを共有するLazy SMPとする。

Lazy SMPは着手を乱数で変える機能ではない。
ワーカー数が2以上の場合は共有置換表へのアクセス順が実行時スケジューリングに依存するため、同じ局面と制限でも結果が変わり得るが、この非決定性を着手多様化の手段として扱わない。

完了基準は次の4点とする。

- `Threads=1`で、着手、評価値、深さ、ノード数、主変化、および固定深さbenchの総ノード数が基準コミットと一致する。基準コミットは初版では実装前のコミット、第2版のフェーズ7以降ではフェーズ6の採用コミットとする。
- `Threads=2`以上で、全ワーカーが同じ停止要求と探索予算に従い、合法な最善手を1回だけ返して終了する。
- 時間制御のコミット対コミット一般化逐次確率比検定（GSPRT）で、`Threads=2`が`Threads=1`に対してH1へ到達する。
- Universal Shogi Interface（USI）の`Threads`とChess Engine Communication Protocol（CECP）の`cores`から、次の探索に使うワーカー数を設定できる。

## 適用範囲

本マイルストーンでは、次の作業を行う。

- 置換表を、複数ワーカーが共有できる原子型の16バイトエントリへ変更する。
- 現行の探索スレッドを探索チームの調整役兼主ワーカーへ変更し、探索ごとに補助ワーカーを生成して終了時に全員を待機する。
- 停止要求、hard limit、soft limit、およびノード上限を探索チーム全体へ適用する。
- USIの`Threads`オプションとCECPの`smp=1`および`cores`コマンドを実装する。
- 固定局面benchへワーカー数と反復回数を追加し、単一ワーカーの回帰と並列時の速度向上を分けて測定する。
- 並列探索時の再現性と測定条件を`docs/sprt.md`へ追記する。

次の項目は対象外とする。

- 先読み（ponder）、分散メモリ探索、非均一メモリアクセス（non-uniform memory access、NUMA）配置、中央処理装置（CPU）の固定割り当て、および永続ワーカープールは実装しない。
- 補助ワーカーの結果による投票と複数主変化出力は実装しない（最深ワーカーの採用は第2版で採用した）。
- 乱数によるルート手選択、低棋力化、および定跡手の乱択は実装しない。
- 置換表のクラスタ化と停止確認周期の短縮は、実測で必要性が示されるまで実装しない（ノード数の一括予約は第2版のフェーズ7で試みたが不採用とした）。
- `match_runner`へ候補側と基準側の機能を切り替えるオプションは追加しない。
- `src/core/`と評価関数は変更しない。静止探索の置換表利用は探索部の変更だが、本マイルストーンの原因修正として第2版の適用範囲に含める。

## 依存関係

探索部の静止探索と第2層の探索改良を先に完了させる。
探索順序、枝刈り、および延長を並列化と同時に変更すると、棋力差と性能差の原因を分離できないためである。

外部対局接続のCECP対局進行も、本マイルストーンのプロトコル接続フェーズより先に完了させる。
CECPの状態機械と探索中コマンドの所有権は`engine-connectivity.md`にあり、本マイルストーンは完成した境界へ`smp`と`cores`だけを追加する。

評価関数の本格化は本マイルストーンの着手条件ではない。
Lazy SMPの採否は、着手時点で完成している単一ワーカー探索を基準として独立に測定する。

## 設計判断

| 項目 | 決定 |
|---|---|
| ワーカー数 | `Threads`は主ワーカーを含む探索ワーカーの総数とし、既定値1、最小値1、最大値256とする。入力値をCPU数に合わせて暗黙に変更しない。 |
| 探索制限との境界 | ワーカー数は停止条件ではないため`SearchLimits`へ追加せず、`NonZeroUsize`として探索開始関数へ明示的に渡す。 |
| ワーカーの寿命 | 現行どおり探索ごとにスレッドを生成する。永続ワーカープールは導入しない。 |
| 共有状態 | 置換表、停止状態、停止理由、総ノード数、開始時刻、および時間予算だけを共有する。局面、合法手生成器、探索経路、主変化、および将来の探索履歴はワーカーごとに所有する（総ノード数のキャッシュライン分離は第2版フェーズ7で試したがNPSゲートに達せず不採用）。 |
| 最善手 | 停止時に最も深い反復深化を完了したワーカーの結果（最善手、評価値、深さ、主変化を同一ワーカーの同一反復から一括採用）を採用し、同じ深さならワーカー番号が最小のもの（主ワーカーは0）を優先する。補助ワーカーは完了した反復の結果を保持して調整役へ返すが、進捗は送らない（第2版）。 |
| 多様化 | 補助ワーカーは一部の深さを飛ばして主ワーカーより先の反復へ進む。補助ワーカーk（k=1、…、Threads−1）の周期を`p = 2 + ((k - 1) % 4)`とし、深さdのうち`d == 1`または`(d - 1) % p == 0`を満たす反復と、深さ上限の反復を探索する（k=1、上限6なら1、3、5、6）。ルート合法手列の回転、時刻、および乱数は使わない（第2版。初版のルート回転は置換表手の先頭入れ替えで打ち消されることが判明した）。 |
| 置換表容量 | `USI_Hash`とCECPの`memory`は全ワーカーで共有する置換表の総容量を表し、ワーカー数倍に増やさない。 |
| ノード上限 | `go nodes N`は探索チーム全体で最大Nノードとし、ワーカーごとにNノードを与えない。各ノードの進入時に共有カウンタへ反映し、上限があるときは`compare_exchange`で1ノードずつ予約する（第2版のフェーズ7で試した1024ノード単位の局所反映は、NPSゲートに達せず不採用とした）。 |
| 進捗 | `Progress`は主ワーカーのイテレーション完了時だけ送る。`nodes`は送信時点のチーム総数とし、`Finished`は全ワーカーの終了後に1回だけ送る。最深ワーカーの採用により、`Finished.depth`は最後の`Progress.depth`以上になり、最善手と評価値も最後の`Progress`と異なり得る。USIは、採用した深さと評価値をGUIへ伝えるため、`Finished.depth`が最後に出力した深さを超える場合だけ`bestmove`の前に最終`info`を出す（第2版）。 |
| 再現性 | `Threads=1`は現行の決定性を維持する。`Threads>1`は固定深さと固定ノード数でも完全再現を保証しない。 |
| 対応環境 | 原子型の64ビット整数を利用できる共有メモリ環境を対象とする。該当しないコンパイル対象はコンパイル時に明示的に拒否する。 |

起案にあたり、2026年8月13日時点のStockfishとやねうら王の実装を一次資料として確認した。
両実装とも、複数の探索ワーカーが独立に反復深化を実行し、置換表を共有した後に探索チームの結果を集約する構造を採っている。
ただし、両実装が許容する競合をRustの通常メモリアクセスで再現すると未定義動作になるため、Minaseではデータ競合のない原子型の置換表を使う。

## 探索チーム

`start_search`が生成する現行の探索スレッドを、探索チームの調整役兼主ワーカーとする。
このスレッドは共通状態を構築し、`std::thread::scope`内で`Threads-1`本の補助ワーカーを生成した後、自身で主ワーカーの探索を実行する。
`scope`を抜ける前に全補助ワーカーを待つため、正常終了、停止、および`panic`のいずれでも孤児スレッドを残さない。
同期版の`search`も同じ調整役の経路を通り、単一ワーカー専用の経路は持たない。

`SearchHandle`の公開契約は探索スレッド1本から探索チーム全体へ読み替える。
`request_stop`はチーム共通の停止状態を更新し、`join`は全ワーカーの終了後に共有置換表を返す。
ワーカー生成に失敗した場合は少ないワーカー数へ縮退せず、探索チームを失敗させて既存のチャネル切断とjoinエラーの経路へ接続する。

`SearchSnapshot`は調整役が所有し、scope内の全ワーカーが不変参照する。
各ワーカーは根局面を複製し、`Searcher`、合法手生成器、探索経路、主変化、および局所ノード数を個別に持つ。
置換表の世代は調整役がワーカー生成前に1回だけ進め、ワーカーごとには更新しない。

主ワーカーは深さ1から通常どおり反復深化する。
補助ワーカーk（k=1、…、Threads−1）は周期`p = 2 + ((k - 1) % 4)`を持ち、深さdのうち`d == 1`または`(d - 1) % p == 0`を満たす反復と、深さ上限の反復を昇順に探索する（k=1は周期2で深さ1、3、5、…、k=2は周期3で深さ1、4、7、…を探索し、k=1で上限6なら1、3、5、6となる）。
周期を4種類で循環させるのは、ワーカー番号をそのまま周期にすると多数ワーカーで深さ1しか探索しない補助ワーカーが生じるためであり、5本目以降の補助ワーカーは既存の周期を重複して受け持つ。
飛ばした反復の分だけ補助ワーカーは主ワーカーより先の深さへ進み、主ワーカーが同じ深さへ到達したときに共有置換表の記録がカットオフと指し手順序付けに使われる。

この方式は、初版の多様化（補助ワーカーが主ワーカーと同じ深さ列を探索し、ルート合法手列をワーカー番号だけ回転する）が棋力に転化しなかった原因の診断から導いた（[measurements/lazy-smp-v1-diversification-bench.md](../measurements/lazy-smp-v1-diversification-bench.md)）。
初版では、各ワーカーの指し手順序付けが共有置換表に記録された最善手（置換表手）を先頭へ入れ替えるため、主ワーカーが根の置換表エントリを書いた後は補助ワーカーも回転した並びを捨てて主ワーカーと同じ手から同じ深さを探索し、補助ワーカーは主ワーカーを遅れてなぞる複製になって新しい情報をほとんど供給しなかった。
さらに、単一ワーカーの深さ5探索では、置換表を照会する残り深さ1以上のノードが全ノードの約2%であり、残りは置換表を使わない静止探索と深さ0ノードであったため、置換表共有が減らせる部分木はごく一部であった（教訓は [lessons/qsearch-dag-without-tt.md](../lessons/qsearch-dag-without-tt.md)）。
2026年8月22日の診断では、補助ワーカーが同じ深さを時間的に先行して探索している間だけ主ワーカーのノードが減り（深さ5で22%減）、補助ワーカーが1つ深い反復にいる間は逆に補助ワーカー側が主ワーカーの記録から利益を得ることが分かった。
後者の利益を捨てないため、各ワーカーは完了した反復ごとに最善手、評価値、深さ、および主変化を同一反復の組として保持し、調整役は全ワーカーのjoin後に最も深い反復を完了したワーカーの結果を採用する。
同じ深さならワーカー番号が最小のものを優先し、`Threads=1`では主ワーカーしかいないため結果は初版と変わらない。
ルート合法手列の回転は使わない。

いずれかのワーカーが深さ上限の反復を完了した場合、主ワーカーがsoft limitへ到達した場合、およびいずれかのワーカーがhard limitまたはノード上限へ到達した場合は、共通停止状態を更新して全員を巻き戻す。
深さ上限の完了で停止するのは、採用される結果が既に要求深さに達しているためであり、これにより固定深さbenchは探索チームが要求深さへ到達するまでの時間を測る。

## 共有置換表

現行の`Vec<Entry>`と`&mut TranspositionTable`は複数ワーカーから共有できないため、置換表の操作を`&self`で行う原子型へ変更する。
1エントリは次の16バイトとし、現行と同じ容量計算とスロット数を維持する。

| 原子値 | 内容 |
|---|---|
| `AtomicU64 critical` | 検証キー32ビット、評価値16ビット、深さ8ビット、バウンド2ビット、および予約6ビット。 |
| `AtomicU64 advisory` | 指し手25ビット、世代8ビット、および予約31ビット。 |

指し手は`from`、`mid`、`to`の各8ビットと成り1ビットで25ビットに収まる。
評価値によるカットオフへ必要な検証キー、評価値、深さ、およびバウンドを1回の原子的読み取りで得るため、競合中も異なる書き込みの値を組み合わせない。

書き込み側は`advisory`をRelaxedで書いた後に`critical`をReleaseで公開し、読み取り側は`critical`をAcquireで読んでから`advisory`をRelaxedで読む。
競合する別の書き込みにより、記録手または世代だけが`critical`と異なる書き込みに由来する可能性は許容する。
記録手は指し手順序付けにしか使わず、復号と現局面の合法手列への所属を検証してから採用するため、取り違えても評価値による誤ったカットオフは起こらない。
世代は置換優先度にしか使わないため、取り違えは書き込みの採否だけに影響し、探索値の正しさを変えない。

書き込み側は読み取った既存値から置換可否（スロットにある既存エントリを新しい結果で上書きするかどうか）を判定し、競合を待たずに2個の原子値を更新する。
置換可否は次の式で一意に定める（第2版。初版は同一キーへ無条件に書き込んでいたが、静止探索が深さ0の記録を書くようになると通常探索の深い記録を消すため改めた）。
空きスロットへは常に書き込む。同一キーへは世代を問わず`depth >= existing.depth`のときだけ書き込み、浅い結果は保持する（保持する場合は世代も更新しない）。異なるキーへは`age > 0 || depth > existing.depth`のときだけ書き込む。
同一キー・同深さは最終書き込み優先であり、Exactが後発のLowerまたはUpperで置き換わることを許容する。
この判定は読み取り後書き込みのロックレス方式であり、2ワーカーが同じ既存値を読んで双方が書き込み可と判断した場合は浅い結果が後から公開され得る。これは最善努力として許容し、比較交換による再判定は行わない。
静止探索の記録は深さ0で格納する。静止探索の値は捕獲手しか読んでいない浅い結果であり、通常探索の照会条件`hit.depth >= depth`（深さ1以上）を満たさないため、静止探索の評価値が通常探索のカットオフに使われることはないが、記録手は通常探索の指し手順序付けに使われ得る。
指し手25ビットには全ビットが1の「手なし」符号を設け、`Hit.best_move`を`Option<Move>`とする。手なし符号は未命中ではなく有効なエントリとして扱い、それ以外の復号失敗だけを未命中とする。
最後に公開された`critical`が有効な探索値となり、競合で失われた記録手と世代は置換表の助言的情報（探索値の正しさに影響せず、指し手順序付けと置換優先度にだけ使う情報）として扱う。
検証キー、予約ビット、バウンド、および指し手の復号に失敗した場合は置換表の未命中として扱い、不正な`Move`を構築しない。

`clear`と`resize`は探索チームが存在しないときだけ実行する。
`USI_Hash`とCECPの`memory`の変更、新規対局、および規則変更は、既存どおり実行中探索を停止してjoinした後に置換表へ適用する。

## 停止と探索予算

探索チームは、外部停止フラグ、チーム停止フラグ、停止理由、総ノード数、開始時刻、および時間予算を共有する。
外部停止と内部停止を別の原子値にすることで、他ワーカーが立てた停止を`ExternalStop`と誤認しないようにする。
scopeの終了後に外部停止を再確認して停止理由を上書きすることはせず、自然完了した探索の理由を保つ。

停止理由の優先順位は、`ExternalStop`、`HardLimit`、`NodeLimit`、`SoftLimit`、`DepthCompleted`の順とする。
複数条件が近接した場合は原子値に優先度の高い理由を残し、実行順による表示上の揺れを抑える。

総ノード数は`AtomicU64`で数え、各ノードの進入時に共有カウンタへ反映する。
ノード上限がある場合は`compare_exchange`で1ノードずつ予約し、Nノードを超える予約を拒否して`NodeLimit`を設定する。
ノード上限があるときの1024ノード単位の一括予約は、単一の共有カウンタでは`Finished.nodes`と決定性を両立できないため採らない。
第2版のフェーズ7では、停止フラグとの偽共有を避けるキャッシュライン分離と、上限なし時の1024ノード単位の局所反映を試したが、ワーカーあたりNPSの改善がゲート（3%）に達しなかったため不採用とし、初版の毎ノード反映を維持する（[measurements/lazy-smp-counter-nps-gate.md](../measurements/lazy-smp-counter-nps-gate.md)）。
静止探索の置換表を導入した後は、2ワーカーと4ワーカーのワーカーあたりNPSが単一ワーカーとほぼ同じであり、初版で観測した競合による低下は解消している。
`Progress.nodes`と`Finished.nodes`は送信時点のチーム総数であり、`Finished.nodes`は最後の`Progress.nodes`以上かつ（上限があれば）N以下である。

hard limitは全ワーカーが同じ開始時刻から計算した期限と比較する。
スレッド生成時間は利用者が観測する思考時間に含まれるため、開始時刻は補助ワーカー生成前に記録する。
soft limitは主ワーカーのイテレーション境界だけで評価し、補助ワーカーの完了時点では評価しない。

外部停止とチーム停止は毎ノードの原子読み取りで確認し、hard limitの時計確認は4096局所ノードごとに行う。
ワーカー数に伴う停止遅延は時間制御試験で測定し、時間切れまたは過大なjoin遅延が観測された場合に限り、確認周期を別コミットで変更してGSPRTにかける。

## プロトコル設定

USIの握手では、次のオプションを宣言する。

```text
option name Threads type spin default 1 min 1 max 256
```

`setoption name Threads value N`は1以上256以下の10進整数だけを受理する。
値の欠落、非整数、0、および上限超過には固定した`info string error: Threads must be an integer from 1 to 256`を返し、直前の設定を保持する。
探索中に届いた設定変更は既存の入力待機列に載せ、実行中探索を変更せず次の探索から適用する。

CECPでは`feature smp=1`を宣言し、`cores N`を同じ範囲で受理する。
不正値は固定した`Error (invalid command): cores`を返し、少ない値やCPU数へ丸めない。
USIの`Threads`とCECPの`cores`は同じ探索開始引数へ写し、プロトコルごとの並列探索実装を作らない。

`Threads`の既定値は、検証後も1を維持する。
利用可能CPU数を既定値に使うと、同じバイナリの資源消費と再現性が環境に依存するためである。

## 再現性

`Threads=1`では共有置換表への競合がないため、現行の固定深さと固定ノード数の完全再現契約を維持する。
原子型への置換後も、置換規則、容量、スロット番号、および世代幅を変えず、既存benchの総ノード数を一致させる。
第2版のフェーズ6は置換規則と静止探索を意図的に変えるため、その採用コミットのbench総ノード数（[measurements/qsearch-tt-nodes100k.md](../measurements/qsearch-tt-nodes100k.md)）を以後の基準とし、フェーズ7と8は`Threads=1`でこの基準と一致しなければならない。

`Threads>1`では、固定深さと固定ノード数でも共有置換表の公開順がオペレーティングシステム（OS）のスケジューリングに依存する。
このため、`docs/sprt.md`の完全再現契約を`Threads=1`に限定し、並列時には合法手、予算上限、イベント順序、および停止後の全joinだけを決定的な契約とする。

固定深さbenchは`--threads N`と`--repetitions R`を受け取り、反復時はウォームアップ1回の後に各回の到達深さ、総ノード数、経過時間、ノード毎秒と、それらの中央値を出力する。
`Threads=1`かつ反復1回の既定出力は現行の決定性検査に使い、`Threads>1`はウォームアップ1回を除く5回以上の中央値で、到達深さ、総ノード数、経過時間、ノード毎秒、および単一ワーカーに対する速度比を記録する。

## 採否測定

並列化の棋力採否は、`docs/sprt.md`に従って時間制御のコミット対コミットGSPRTで行う。
固定ノード数では計算資源の増加による時間短縮を棋力へ反映できず、固定深さでは両者の探索深さが同じになるため、いずれも主たる採否条件には使わない。

時間制御の水準は測定前に固定する。
初版の測定に使った`time=10000+100,byoyomi=200`は1手あたり約0.4秒、到達深さ4〜5であり、補助ワーカーが先行する余地がほとんどない（[measurements/lazy-smp-threads2-tc.md](../measurements/lazy-smp-threads2-tc.md)）。
第2版の採否測定は`time=30000+300,byoyomi=500`（初手のsoft limitは約1.2秒、到達深さ5〜6）、同時対局数8、`--max-pairs 500`で行い、結果を見てから水準を変えない。
500ペアで判定保留の場合は不採用（判定保留）として固定局数のEloと信頼区間を記録し、設計へ戻る。
時間制御GSPRTの前に固定深さbenchのゲートを置く。
ゲートは、深さ5と6のそれぞれで、ウォームアップ1回を除く5回の中央値が`Threads=2`で`Threads=1`より10%以上短く、かつ両構成の5回の最大値と最小値の範囲が重ならないこととする。
これは統計的有意性ではなく外れ値に保守的な工学ゲートであり、同時負荷のない状態で`bench --depth D --threads T --repetitions 5`を深さと構成ごとに順に実行して判定する。
第2版では深さ上限の完了がチーム停止になるため、このゲートは最深ワーカー採用を含むチームの到達時間を測る。
ゲートに達しない場合は時間制御GSPRTへ進まず、設計へ戻る。

測定用の基準コミットは、並列探索の全コードを含み、`DEFAULT_THREADS=1`としたコミットとする。
候補コミットはこの定数だけを2へ変更した測定用ブランチに置き、`match_runner`にはワーカー数を設定する機能比較スイッチを追加しない。
測定後は結果にかかわらず製品の既定値を1へ戻し、利用者がプロトコル設定で明示した場合だけ並列探索を有効にする。
測定用ブランチは記録の参照用に残す。

最初に`Threads=2`対`Threads=1`を測定する。
対立仮説H1へ到達した場合だけ`Threads=4`対`Threads=2`を追加測定し、帰無仮説H0へ到達した場合は原因を分析して設計へ戻る。
判定保留の場合は、同じ仮説と時間制御を保ったまま上限ペア数を延長し、都合のよい水準へ変更しない。
`Threads=4`対2の測定は1回が半日規模になるため、必要になった時点で同じ手順で実施する。

時間制御は両者に同じ壁時計条件を与える。
候補側がより多くのCPU時間を使うことは並列規模拡大の測定対象であり、同一CPU時間の比較とは呼ばない。
同時対局数Cは、`C × max(候補Threads, 基準Threads)`が利用可能な物理コア数を超えない値とし、OSとハーネス用に1コア以上を残す。

測定記録には、通常のGSPRT記録に加えて、CPU型、物理コア数、論理コア数、両エンジンのワーカー数、`USI_Hash`、同時対局数、時間制御、および`time_forfeits`を含める。
時間制御対局は完全再現の対象外であるが、着手の非決定性を理由に測定結果を選別しない。

## 実装フェーズ

### フェーズ1　原子型置換表

置換表エントリを16バイトの原子型へ置き換え、`probe`と`store`を`&self`へ変更する。
エントリの詰め込み、公開順序、競合書き込み、世代更新、無効データの未命中化、およびサイズ上限を単体テストで固定する。

このフェーズは`Threads=1`だけで実行し、既存の探索結果とbench総ノード数が完全一致しなければ次へ進まない。
一致しない場合は棋力測定で正当化せず、置換表の意味論を修正する。

### フェーズ2　探索チーム

調整役兼主ワーカー、補助ワーカー、`scope`による全join、ワーカー固有状態、決定的なルート順序分散、および主ワーカーだけの結果採用を実装する。
`Threads=1`の経路も同じ調整役を通し、単一ワーカー専用の旧経路は残さない。

### フェーズ3　共通停止と予算

停止理由、総ノード数、開始時刻、hard limit、およびsoft limitを探索チームの契約へ移す。
外部停止、ノード上限、時間上限、深さ上限、およびワーカーの`panic`について、全joinと1回だけの完了通知を検証する。

### フェーズ4　プロトコルとbench

USIの`Threads`、CECPの`smp=1`と`cores`、およびbenchのワーカー数と反復回数を実装する。
`docs/sprt.md`の再現性契約と並列測定の記録項目を更新する。

### フェーズ5　性能と棋力の採否

固定局面benchで`Threads=1`、2、4の経過時間とノード毎秒を測定し、オーバーサブスクリプションがない条件を確定する。
次に、既定ワーカー数だけが異なる測定コミットを作り、時間制御GSPRTで`Threads=2`対1を判定する。
H1の場合だけ`Threads=4`対2へ進み、各結果を docs/measurements/ の測定記録へ残す。
初版の結果は [measurements/lazy-smp-v1-bench-depth4.md](../measurements/lazy-smp-v1-bench-depth4.md) と [measurements/lazy-smp-threads2-tc.md](../measurements/lazy-smp-threads2-tc.md) にあり、固定深さの経過時間が短縮せず時間制御でも判定保留であったため、第2版のフェーズ6〜8へ進んだ。

### フェーズ6　静止探索の置換表と置換規則（第2版）

静止探索で置換表を照会・記録し、同一キーの置換規則を深さで判定し、置換表の指し手に「手なし」符号を導入する。
静止探索の順序は`enter_node`、最大ply判定、入力時alphaの保存、置換表照会、stand-patとし、照会ヒットのバウンドがExactか、Lowerで`score >= beta`、Upperで`score <= alpha`ならその値を返す。
記録は経路別に、stand-patによるβ超過はLowerかつ手なし、通常出口は最善値が`beta`以上ならLower、入力時alpha以下ならUpper、それ以外はExactとし、最善値がstand-patなら手なし、捕獲手なら記録手とする。最大ply葉と置換表ヒットは記録しない。
照会と記録には現在の`ply`を渡し、最後の王駒捕獲の`MATE - ply`は既存の変換で往復させる。
このフェーズは単一ワーカーの探索結果を変えるため、bench署名を新しい値として記録し、採否は`--each nodes=100000`のコミット対コミットGSPRT（`--max-pairs 3000`）で判定する。
受入試験は、同一キーの浅い値の保持、同深さの置換、過去世代の置換、異なるキーの規則、静止探索の3バウンド、手なしの往復、詰み値、最大ply葉の非記録を列挙する。
GSPRTはH1に到達し、採用した（[measurements/qsearch-tt-nodes100k.md](../measurements/qsearch-tt-nodes100k.md)）。

### フェーズ7　共有カウンタの配置と一括予約（第2版）

総ノード数を停止フラグと別のキャッシュラインへ分離し、ノード上限がないときは各ワーカーの局所カウンタから1024ノードごとに加算する。
フェーズ6採用コミットの`Threads=1`固定深さbench署名は不変でなければならない。
採否は、フェーズ6採用コミットと本フェーズのコミットで`bench --depth 5 --threads T --repetitions 5`をT=1、2、4について同時負荷なしで順に実行し、ワーカーあたりNPS（中央値NPSをTで割った値）がT=2と4で3%以上改善し、T=1の中央値NPSの低下が2%以内であることとする。棋力測定は行わない。
実測の結果このゲートに達せず不採用となり、計数方式を毎ノード反映へ巻き戻した（[measurements/lazy-smp-counter-nps-gate.md](../measurements/lazy-smp-counter-nps-gate.md)）。

### フェーズ8　最深ワーカーの採用と深さスキップ（第2版）

各ワーカーが完了した反復の結果を保持して調整役へ返し、調整役が最も深い反復を完了したワーカーの結果を採用する。
補助ワーカーの反復列を周期付きの深さスキップへ変更し、ルート回転を撤去し、いずれかのワーカーの深さ上限完了をチーム停止条件に加える。
USIは`Finished.depth`が最後に出力した深さを超える場合に最終`info`を出す。
採否測定の節に定めた固定深さbenchのゲートを通過した場合だけ、`DEFAULT_THREADS`だけを2へ変えた候補コミットで`time=30000+300,byoyomi=500`の時間制御GSPRT（`--max-pairs 500`）を行う。
benchゲートは深さ5で26.5%、深さ6で17.9%の短縮で通過し（[measurements/lazy-smp-v2-bench-gate.md](../measurements/lazy-smp-v2-bench-gate.md)）、時間制御GSPRTは上限500ペアで判定保留ながらElo +62.1（95%信頼区間［+41.5, +83.0］）であったため採用した（[measurements/lazy-smp-v2-threads2-tc.md](../measurements/lazy-smp-v2-threads2-tc.md)）。

## 検証

各フェーズで次のコマンドを実行する。

```console
cargo test
cargo clippy --all-targets
cargo fmt --all -- --check
git diff --check
```

単体試験と台本試験では、次の契約を検証する。

- 原子型置換表は、同一スロットへの並行`probe`と`store`を反復しても`panic`せず、不正な指し手を返さない。
- `Threads=1`は基準コミット（初版では実装前、第2版のフェーズ7以降ではフェーズ6の採用コミット）の探索結果、主変化、進捗深さ、ノード数、およびbench署名を維持する。
- `Threads=2`と4は、深さ、ノード、時間、無期限探索からの`stop`、`gameover`、`quit`、および入力終了で全ワーカーをjoinする。補助ワーカーの`panic`はチャネル切断とjoinエラーの経路へ接続され、完了通知の契約の対象外とする。
- `Progress.depth`と`Progress.nodes`は単調増加し、`Finished.depth`は最後の`Progress.depth`以上、`Finished.nodes`は最後の`Progress.nodes`以上であり、`Finished`と`bestmove`は各探索で1回だけ出力される。
- `go nodes N`の`Finished.nodes`はNを超えず、`USI_Hash`の実メモリ量はワーカー数で増えない。
- 探索中の`Threads`、`cores`、`USI_Hash`、および`memory`変更は、実行中探索を変えず次の探索へ反映される。
- 1、2、4ワーカーで短時間制御の反復試験を行い、スレッドリーク、`panic`、反則手、および時間切れがないことを確認する。

並行性の検査は通常テストだけに依存しない。
ThreadSanitizerを利用できるRust nightly環境では置換表の競合試験を実行し、利用できない場合はその事実を検証記録へ明記する。
本マイルストーンの完了時点では、Rust nightlyが導入されていないためThreadSanitizerの競合試験を実施していない。

## 完了条件

- 原子型置換表が16バイト以内であり、`Threads=1`のbench署名と探索結果が基準コミット（初版では実装前、第2版ではフェーズ6の採用コミット）に一致している。
- 探索チームの共有状態とワーカー固有状態が設計どおり分離され、停止後に全ワーカーがjoinされている。
- `Threads=2`以上でも、探索予算、イベント順序、合法手、および置換表容量の契約を満たしている。
- USIの`Threads`とCECPの`cores`が、暗黙の丸めや縮退なしに同じワーカー数設定へ接続されている。
- 固定局面benchの並列測定と、`Threads=2`対1の時間制御GSPRTが記録され、GSPRTがH1へ到達している。
- `docs/sprt.md`が、完全再現を`Threads=1`へ限定し、並列測定の資源記録を要求している。
- 全検証コマンドが成功し、時間制御の反復試験で`time_forfeits=0`である。

# lishogi Bot接続の設計書

## 先に読む要約

本マイルストーンは、minaseをオンライン対局サイトlishogiへBotアカウントとして接続し、人間および他のBotと中将棋を公開対局できるようにする。
接続には、lishogiのBot API（lichess由来の、Botアカウントが対局イベントを受け取り着手を送るためのHTTPインターフェース）とUSIエンジンを仲介するPython製ブリッジLishogi-Botをそのまま使い、minase側にはブリッジ専用のコードを書かない。
minaseは[外部対局接続](engine-connectivity.md)でLishogi-Botの送信系列に対応済みなので、本マイルストーンの主な作業は、実接続で初めて問題になる3点の解消である。
第1に、lishogiの反復裁定（同一局面の繰り返しによる終局の判定、RULES.md第24条と第31条）は「対局開始または直前の不可逆手の直後から、可逆手が12手以上続いている」ことを前提条件にする。不可逆手とは、元の局面へ戻れなくなる着手であり、中将棋では捕獲、成り、歩兵または香車の着手を指す。それ以外の着手を可逆手という。同じ局面が4回現れた時点で裁定する現行のminaseは、この前提条件を持たないためlishogiより先に対局を終局と判断し、次に届く`position`を拒否して着手不能になり得る。この差を規則R1の定義と実装の訂正で解消する。
第2に、Lishogi-Botは自分の残り時間から固定の余裕、受信からの経過時間、加算、および秒読みを引いた値を`btime`または`wtime`として送り、秒読みの回数は送らない。この換算の下でminaseの時間管理が安全側に働くことと、着手がサーバへ届くまでの遅延を含めて時間切れが起きないことを確かめる。
第3に、Botアカウントの作成、認証トークンの管理、公開の範囲（非レート対局から始めてレート対局へ広げる順序）を運用手順として定める。
完了条件は、非レートの公開対局10局とレート対局10局で、受諾した全対局を母数として着手拒否、時間切れ、エンジン異常、および裁定の不一致が0件であることである。

## 目的

minaseを、lishogiのBotアカウントとして人間および他のBotと対局できる状態に置く。
対象は、Lishogi-Botを介したUSI接続だけであり、CECPおよび自作GUIは扱わない。
接続の成立に加えて、公開対局で規則の不一致や時間切れによる不本意な負けを出さないことを、対局記録の事後照合で保証する。

## 適用範囲

本マイルストーンでは、次の作業を行う。

- 規則R1の反復裁定へ、lishogiの規則ライブラリscalashogiが実装する前提条件を取り込み、RULES.md、`src/core/repetition.rs`、`src/core/adjudication.rs`、および`src/core/game.rs`を更新する。
- lishogiの実対局のうち、この前提条件で裁定が分かれる対局をリプレイ照合のフィクスチャへ追加し、取得スクリプト`scripts/fetch_lishogi_replays.py`の初期局面の扱いを直す。
- Lishogi-Botを固定した版で導入し、minase用の設定ファイルをリポジトリに置く。
- Botアカウントの作成と昇格、認証トークンの管理、およびエンジンバイナリの固定手順を定める。
- 非レート対局とレート対局の2段階で公開運用し、対局記録の事後照合で異常0件を確認する。

次の項目は対象外とする。

- ponder。Lishogi-Botの設定で無効にする。導入は[棋力向上の段階計画](strength-stages.md)の段階10が扱う。
- 通信対局（correspondence）。Lishogi-Botの設定で受け付けない。
- 自前のブリッジの実装、Lishogi-Botの改変、およびminaseへのBot API対応の組み込み。
- 探索、評価、時間管理の予算式の変更。時間管理に欠陥が見つかった場合は、本マイルストーンを待機中にして段階計画側で修正する。
- 定跡、評価値による任意投了、および引き分け提案。
- チャットへの応答機能の拡張。Lishogi-Botの既定の挨拶文を設定するにとどめる。

## 設計判断

| 項目 | 決定 |
|---|---|
| ブリッジ | TheYoBots/Lishogi-Botを固定した版でそのまま使う。Rustで自前のブリッジを書く案は、Bot APIのイベントストリーム、対局の受諾、時計の換算、切断からの再接続を再実装する費用に対して、minase側に得られる利点がないため棄却した。Lishogi-Botの改変も、上流の更新へ追従する費用が増えるため行わない。 |
| エンジンの指定 | `--protocol usi --rules lishogi`を必須とする。他の規則セットでの公開対局は、lishogiの裁定との互換性を保証しないため行わない。 |
| エンジンバイナリ | 公開運用に使うコミットを固定し、そのコミットを検出したgit worktree（同じリポジトリの別コミットを別ディレクトリへ展開したもの）でビルドしたバイナリを使う（[長時間の生成は生成コミットを固定したworktreeで実行する](../lessons/pin-generation-binary-to-worktree.md)）。作業ツリーのバイナリを直接使うと、開発中の変更が公開対局へ混入するためである。 |
| 反復裁定の差 | R1の定義と実装をscalashogiに合わせて訂正する仕様変更を行う。差をUSI層で吸収する案（終局後の`position`を許容する）は、規則の曖昧さをコード側で補わないRULES.mdの方針と、暗黙のフォールバックを置かない方針に反するため棄却した。差を放置する案は、minaseが先に終局と判断した対局で`bestmove`を返せず時間切れ負けになるため棄却した。詳細は「反復裁定の整合」の節に記す。 |
| R1訂正の採否判定 | SPRTの対象外とし、利用者の裁定で採用する。理由は「反復裁定の整合」の節に記す。 |
| 公開の順序 | 非レート対局だけを受け付ける段階を先に置き、異常0件を確認してからレート対局を有効にする。Lishogi-Botには挑戦者を限定する設定がないため、非レート段階でも不特定の相手と対局する。 |
| 認証トークン | 環境変数`LISHOGI_BOT_TOKEN`で渡し、設定ファイルにもリポジトリにも書かない。 |
| 同時対局数 | 1とする。複数対局は探索スレッドと置換表を対局間で奪い合い、時間切れの原因になるためである。 |
| ponder | 無効にする。minaseはponder（相手の手番中に先読みする機能）を実装しておらず、`USI_Ponder`を宣言せず、`bestmove`にponder手を付けず、`go ponder`にはエラーを返す。Lishogi-Botはponder手が返らなければ`go ponder`を送らないので、既定値（有効）のままでも対局は進むが、設定を実装と一致させて挙動を明示する。 |
| 秒読みの回数 | 秒読みつきの対局を受け付け、minaseは秒読みを1回として扱う。Lishogi-Botは秒読みの回数を挑戦の受諾判定にもUSIにも使わないため、minaseは回数を知り得ない。回数が実際には複数あっても、1回と仮定した予算は実際の上限を超えないので、安全側に働く。 |
| 時間制御の受付範囲 | 超早指し（ultraBullet、bullet）と通信対局は受け付けない。持ち時間が短い対局では、Lishogi-Botが引く固定の余裕と通信遅延が1手あたりの思考時間を上回り、実力と無関係な時間切れが増えるためである。受け付ける下限と秒読みの上限は運用パラメータであり、設定ファイルで変える。 |

## 反復裁定の整合

### 差の内容

scalashogiは、反復の裁定に2つの条件を課す（`History.scala`の`isRepetition`）。
第1に、同じ手番の局面が4回現れていること。
第2に、局面ハッシュの履歴が12個を超えていること。
履歴は対局開始時に空であり、最初の可逆手で、その着手の前の局面と後の局面の2つが入り、以後は可逆手のたびに着手後の局面が1つ増える。
不可逆手が指されると、履歴はその直後の局面1つだけを残して空になる（`Situation.scala`）。
したがって第2の条件は、対局開始または直前の不可逆手の直後から、可逆手が先後合計で12手以上続いていることと同じである。
中将棋の不可逆手は、捕獲、成り、および歩兵または香車の着手である（`variant/Chushogi.scala`の`isIrreversible`）。

一方、RULES.md第31条のR1と現行の`src/core/repetition.rs`は、第1の条件だけで裁定する。
このため、不可逆手の直後から双方がじっと（RULES.md第3条、駒を動かさずに手番を渡す着手）を繰り返す2手周期の反復では、不可逆手の直後の局面を1回目として2手ごとに同じ局面が現れるので、minaseは6手後の4回目で裁定するのに対し、lishogiは12手後まで裁定しない。
lishogiの全棋譜との照合（2026年8月26日、GitHub issue #5）で現存する差異はこの1種類だけであり、その実例が対局uy7y6mP6、EHUTJJu4、およびA4EO2swaの3局である。

差が問題になるのは片方向だけである。
不可逆手の後には、それ以前の局面が再現し得ないため、履歴を空にする処理は裁定の対象となる局面を変えない。
したがってlishogiの裁定条件を満たす局面は必ずminaseの裁定条件も満たし、lishogiが裁定する局面ではminaseも同じ手か、それ以前の手で必ず裁定している。
逆に、lishogiが裁定しないままminaseだけが先に裁定する場合があり、この場合だけが問題になる。
minaseが先に終局と判断すると、`Engine`は`Finished`になり、lishogiが対局を続けて次に送る`position`は終局後の着手を含むため拒否される。
拒否後の`go`は[外部対局接続](engine-connectivity.md)の契約どおり`bestmove`を返さず、Lishogi-Botは`bestmove`を待ち続けて時間切れになる。

### 取り込み方

RULES.md第31条のR1の規則文へ、裁定の前提条件として「対局開始または直前の不可逆手の直後から、可逆手が先後合計で12手以上続いていること」を加え、不可逆手の定義を典拠のscalashogiの実装に合わせて書く。
現行の条文は4回目の出現で無条件に裁定するので、これは裁定される局面の集合を狭める仕様変更である。
R1はLishogiの規則として定義されたコードであり、変更の目的は典拠への適合である。
R2とR3は変えない。

実装は次の境界で行う。
`src/core/game.rs`の`play`は着手の巻き戻し情報`Undo`（移動前の駒種と捕獲した駒）を持つので、ここで着手が不可逆かどうかを1か所で判定し、`src/core/adjudication.rs`の`record_move`を通じて`src/core/repetition.rs`のR1の履歴へ渡す。
R1の履歴は、直前の不可逆手からの可逆手の数を持ち、対局開始時は0、不可逆手のたびに0へ戻し、裁定の判定に前提条件を加える。
仮想着手に対するR1の判定経路（`src/core/adjudication.rs`）も同じ判定を使う。

探索部は、読み筋の中で対局履歴と同じ局面が再び現れると、その枝を引き分けの評価値で打ち切る。
これは手を選ぶための評価であって規則の裁定ではなく、4回目の出現や前提条件を待たずに2回目の出現で働くので、前提条件の追加によって変えない。
この評価は対局の同期には影響しない。
探索が引き分けと評価した手を指してもlishogiが裁定しなければ対局は続き、minaseは次の`position`を受理して探索を続けるだけである。

### 採否判定をSPRTの対象外とする理由

この変更は探索、評価、時間管理を変えず、対局が終局する時点だけを変える。
コミット対コミットの自己対局では、審判層と両エンジンが同じ規則コードを解釈するため、旧コミットのエンジンは新しい審判層が続行する対局を終局済みと判断して`go`に応答できず、反則負けになる。
この測定が捉えるのは規則の不一致であって棋力ではないので、SPRTは採否の根拠にならない。
したがって採否は利用者の裁定によるものとし、正しさの根拠は次の検証に置く。

### 検証

上記3局のうち、lishogi APIから4欄以上の完全なSFENまたは`startpos`として取得できる対局をリプレイ照合のフィクスチャへ追加し、終局裁定がlishogiと一致することを確認する。
追加は`scripts/fetch_lishogi_replays.py`の対象棋譜へ加えて再生成する。
このスクリプトは途中局面開始の対局を旧欄名`initialFen`の有無で検出して拒否し、常に標準初期局面を保存するので、lishogi APIの現行の欄名`initialSfen`を読んで初期局面をフィクスチャへ格納するよう修正する。
SFEN（盤面、手番、獅子捕獲升、手数などを空白区切りの欄で表す局面表記、[プロトコル層](protocol-layer.md)）の欄が欠けた古い書き出し形式の対局は、欄を推測して補わず、フィクスチャに入れない。
3局のうち完全な初期局面を持つ対局が1局以上フィクスチャへ入ることを要し、3局とも欄が欠けている場合は、同じ差異を示す別の対局を全棋譜照合の方式で探す。

## 接続の構成

### 構成要素

構成要素は、lishogiサーバ、Lishogi-Bot、およびminaseの3つである。
Lishogi-Botはリポジトリの外（`../Lishogi-Bot`）へ固定した版で取得し、Pythonの仮想環境で動かす。
Lishogi-Botは対局を1局受諾するたびにエンジンプロセスを起動し、終局時に`quit`で終了させるので、置換表や`Engine`の状態は対局間に持ち越されない。
`usinewgame`と`gameover`は送られない。
変種は、対局ごとの最初の探索の前に`setoption name USI_Variant value chushogi`で1回だけ通知され、以後は`position`と`go`の反復になる。
これらはいずれも外部対局接続の台本テストが固定している系列である。

### 設定ファイル

minase用の設定は`tools/lishogi-bot/config.yml`としてリポジトリに置く。
認証トークンだけは書かず、環境変数で渡す。
設定は少なくとも次の階層を持つ。

```yaml
engine:
  dir: "<固定コミットのworktreeのtarget/release>"
  name: "minase"
  protocol: "usi"
  ponder: false
  engine_options:
    protocol: usi
    rules: lishogi
  usi_options:
    Threads: <運用機の物理コア数から決める>
    USI_Hash: <運用機の実メモリ容量から決める>
move_overhead: 1900
challenge:
  concurrency: 1
  variants:
    - chushogi
  time_controls:
    - blitz
    - rapid
    - classical
  modes:
    - casual
greeting:
  hello: "<開発中のエンジンであることとリポジトリの所在>"
  goodbye: "<短い挨拶>"
```

`engine.protocol`はLishogi-Bot自身がエンジンの種別を選ぶ項目であり、`engine_options`はminaseの起動引数である。
Lishogi-Botは`engine_options`の各項目を`--protocol=usi --rules=lishogi`の形で渡し、minaseの引数解析（clap）はこの形を受理する。
`go_commands`は与えない。深さやノード数の上書きは時間管理を無効にするためである。
`move_overhead`は、雛形`config.yml.default`の値が1,900ミリ秒、項目を省略したときのコード上の既定値が1,000ミリ秒と異なるので、明示する。
`Threads`と`USI_Hash`の値、時間制御の下限、および秒読みの上限は運用パラメータであり、契約ではない。

### 時計の換算

Lishogi-Botは、自分の手番で`go`を送る前に、lishogiから受け取った残り時間から`move_overhead`と受信からの経過時間を引き、さらに秒読みと加算を引いた値を`btime`または`wtime`に入れる。
秒読みと加算は、それとは別に`byoyomi`、`binc`、`winc`として送る。
各対局の最初の1手だけは、時計の引数ではなく固定の`movetime`で探索する。
したがってminaseが受け取る残り時間は、実際の残り時間より常に少なく、秒読みと加算を予算式が足し戻しても実際の上限を超えない。
lishogiの秒読みは複数回（periods）を持ち得るが、Lishogi-Botは回数を送らないので、minaseは1回として扱う（「設計判断」の節）。

この換算は安全側だが、サーバの時間切れ判定は、minaseが`bestmove`を出してからLishogi-Botが着手をHTTPで送り、サーバが受け取るまでの遅延を含む。
そのため、エンジン内部の予算が受信した残り時間の内側に収まることだけでは不十分であり、対局イベントの受信からサーバの着手受理までを端到端で測り、最小の余裕を記録する。
測定は、Lishogi-Botの詳細ログから`go`の引数、`bestmove`の時刻、および着手送信の時刻を取り出し、lishogi側の時計と突き合わせて行う（[時間管理を変える前に保存記録から時計を再構成する](../lessons/reconstruct-clock-from-match-records.md)）。
余裕が不足して時間切れが起こる場合は、`move_overhead`を増やして対処せず、本マイルストーンを待機中にして時間管理側を修正する。

### 開始局面

Lishogi-Botは、途中局面から始まる対局では`initialSfen`をそのままminaseへ渡す一方、自分の手番判定には着手数だけを使う。
後手番から始まる局面では両者の手番判定が食い違うが、lishogiがBotへの挑戦で途中局面の開始を許すかどうかは未確認である。
フェーズ2の接続試験として、利用者が自分の通常アカウントからBotアカウントへ途中局面からの挑戦を送って可否を確かめ、許される場合は先手番開始と後手番開始の両方を試す。
後手番開始でLishogi-Botが正しく動かない場合は、上流を改変しない方針に従い、この開始形の対局を受け付けない設定または運用（挑戦の手動拒否）を定めて記録する。

### アカウントと認証

Botアカウントは、対局履歴のない新規アカウントを作り、`bot:play`スコープの認証トークンを発行したうえで、Lishogi-Botの`-u`オプションで昇格する。
昇格は取り消せず、一度でも対局したアカウントは昇格できない。
これらの操作は利用者だけが行い、トークンは環境変数`LISHOGI_BOT_TOKEN`として運用機に置く。
Botのプロフィールには、エンジン名、リポジトリの所在、および運用中のコミットを記す。

### 運用手順

運用は次の順序で行う。

1. 公開に使うコミットを決め、そのコミットのworktreeで`cargo build --release --bin minase`を実行する。
2. 設定ファイルの`engine`がそのバイナリを指すことを確認する。
3. 環境変数にトークンを置き、`python3 lishogi-bot.py -v --logfile <ログファイル>`で起動する。
4. 運用の開始と終了、使用コミット、および受け付けた対局条件を運用記録に残す。運用記録は`tools/lishogi-bot/`に置かず、Botアカウントのプロフィールとgit履歴で足りる範囲にとどめる。

運用中のコミットを差し替えるときは、1から3をやり直す。
差し替えは棋力向上の段階が完了するたびに行い、段階の途中のコミットは使わない。

## 実装フェーズ

### フェーズ1　反復裁定の整合

RULES.md第31条のR1へ前提条件を追記し、`src/core/game.rs`、`src/core/adjudication.rs`、および`src/core/repetition.rs`を更新し、単体テストとリプレイ照合の対局を追加する。
単体テストは、対局開始直後、不可逆手の直後、および仮想着手の判定経路の3つの境界を含める。
完了条件は、`cargo test`が通り、追加した対局の終局裁定がlishogiと一致し、既存の全フィクスチャの結果が変わらないことである。
着手前に、R1の条文変更とSPRT対象外の扱いについて利用者の裁定を得る。

### フェーズ2　環境の構築

Lishogi-Botを固定した版で取得し、Pythonの仮想環境を作り、設定ファイルを書き、固定コミットのバイナリを用意する。
Lishogi-Botが固定する依存パッケージのPython 3.14での動作は確認されていないので、導入できない場合はuvで3.11系の仮想環境を用意し、原因となったパッケージとエラーを記録する。
利用者がBotアカウントを作成し昇格する。
途中局面からの挑戦の可否を確かめる（「開始局面」の節）。
完了条件は、Lishogi-Botがサーバへ接続して挑戦の待受に入り、ログに認証エラーがないことである。

### フェーズ3　非レート対局の公開運用

非レート対局だけを受け付けて運用し、受諾した対局が10局に達した時点で事後照合を行う。
10局には、Bot相手の対局と秒読みつきの対局をそれぞれ1局以上含める。
完了条件は、「検証」節の事後照合で、この10局の異常が0件であることである。
異常があれば運用を止め、原因を特定して修正してから局数を数え直す。

### フェーズ4　レート対局の有効化

設定の`modes`へ`rated`を加えて運用し、受諾したレート対局が10局に達した時点で、端到端の時計の確認を含むフェーズ3と同じ事後照合を行う。
完了条件は、この10局の異常が0件であることであり、異常時の扱いもフェーズ3と同じである。

## 検証

- `cargo test`、`cargo clippy --all-targets`、`cargo fmt --all -- --check`、`git diff --check`をフェーズ1の完了条件とする。
- リプレイ照合`tests/lishogi_replay.rs`が、追加した対局を含む全局で各手の合法性と終局裁定の一致を報告する。
- 公開運用の事後照合は、受諾した全対局を母数とする。完走した対局は、lishogi APIから取得してminaseの`--rules lishogi`で再生し、各手の受理と終局裁定の一致を確かめる。取得と照合は、lishogi全棋譜照合で使った方式（`/api/games/user/<Bot名>?perfType=chushogi&moves=true`で取得し、USIの`state`で照合する）を踏襲する。
- 完走しなかった対局は、無活動による中断（abort）、相手の切断、Lishogi-Botの通信例外、および対局ストリームの終了に理由を分け、minase側に起因するものが0件であることを確かめる。相手の切断と相手による中断は異常に数えない。
- 同じ対局群について、Lishogi-Botのログから次の件数を数える。`position`の拒否、`bestmove`の欠落、エンジンプロセスの異常終了と残存、および時間切れ負け。いずれも0件であることを要する。

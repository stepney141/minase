# 棋力測定ハーネス基盤の効率化

## 先に読む要約

Minaseは、変更前後のエンジンを同じ条件で対局させて棋力差を測り、その結果だけで変更の採否を決める。
測定の単位は、同一開始局面で先後を入れ替えた2局からなるペアであり、候補側のペア得点は0、0.5、1、1.5、2の5分類（ペンタノミアル）に分かれる。
この5分類の度数から逐次的に採否を判定する一般化逐次確率比検定（GSPRT）と、固定ペア数からEloを推定する方式の2つを使い、GSPRTはペア番号順に結果を取り込んで判定するので、並列実行でも取り込み順序を変えてはならない（手順と統計契約は[SPRTによる棋力測定の手引き](../sprt.md)）。
従来の対局ハーネスには、番号の若いペアが遅れると並列枠が空くこと、中断後に確定済み対局を再利用できないこと、および測定条件と全着手を監査できる保存記録がないことの3つの問題があった。

本マイルストーンは、ペア番号順の取り込みを保ったまま空いた並列枠を補充し、完了した各ペアを直ちに保存して、欠番だけを再実行できる対局ハーネスへ改修した。
保存記録には、実行条件、エンジンバイナリの検査和（SHA-256）、全着手、思考情報、終局理由、異常分類、CPU時間、局時間、および最大常駐メモリを含め、過去のコミットのエンジンはGitオブジェクトからビルドして検査和で検証できるキャッシュへ保存する。
棋力の採否方法は変更しておらず、探索、評価、時間管理など棋力に影響し得る変更は、引き続き機能スイッチではなくコミット対コミットの時間制御GSPRTで判定する。

本マイルストーンは2026年8月28日に完了し、実データの煙試験と校正カード200ペアの完走によって、保存、再開、および再集計が機能することを確認した。
時間制御と同時対局数の校正、および短時間選別から長時間最終測定へ進む段階ゲートは[棋力測定条件の校正](match-measurement-calibration.md)へ、評価値による早期投了は[早期投了の導入判定](match-early-resignation.md)へ分離し、両マイルストーンの未完了は本マイルストーンの完了条件に含めない。

## 目的

本マイルストーンは、次の4点を達成する。

- GSPRTの判定と停止ペア番号を変えずに、遅い先頭ペアによる並列枠の空きを解消する。
- GSPRTと固定ペア数Eloを、確定済みペアを再利用して同じ実験として再開できるようにする。
- 実行条件、全着手、思考情報、終局理由、異常分類、および実効資源を保存記録から監査できるようにする。
- 履歴バイナリと集計器の入力を検査し、破損または条件不一致を推測で補わず拒否する。

## 文書の所有権

本書は、並列枠の維持、実行記録、再開、履歴バイナリのキャッシュ、および保存記録の集計基盤を所有する。
現行ハーネスの成立過程は[対局ハーネスのバイナリ対戦化](match-harness.md)が、GSPRTの計算方式は[探索部](search.md)と`src/stats.rs`が所有する。
利用者向けの標準コマンド、再開手順、および記録方法は[SPRTによる棋力測定の手引き](../sprt.md)が所有する。

## 対象外

次の項目はハーネス基盤と独立に採否できるため、本マイルストーンへ含めない。

- 時間制御、比較カード、および同時対局数の校正は、[棋力測定条件の校正](match-measurement-calibration.md)で扱う。
- 短時間選別と長時間最終測定の段階ゲートは、[棋力測定条件の校正](match-measurement-calibration.md)で扱う。
- 評価値による早期投了は、[早期投了の導入判定](match-early-resignation.md)で扱う。
- 固定した互角局面集、早期引き分け、複数マシンへの分散実行、およびエンジンプロセスの局間再利用は導入しない。
- 実lishogiサーバーへの接続は、探索と評価が成熟した後の別マイルストーンで扱う。

## 設計判断

| 論点 | 決定 |
|---|---|
| 棋力の採否 | 時間制御のコミット対コミットGSPRTで決め、ハーネスへ機能比較スイッチを追加しない。 |
| 並列実行 | 対局の投入と統計への取り込みを分離し、空いた枠へ次のペアを補充する。 |
| 統計順序 | 完了順にかかわらず、ペア番号順にLLRと停止判定へ取り込む。 |
| 永続化 | 新規実行と再開のどちらでも実行ディレクトリを明示し、記録なしの実行経路を設けない。 |
| 再開 | 保存記録を厳密に検証し、欠番だけを再実行する。 |
| 実験同一性 | エンジン、規則、探索制限、シード、資源設定、測定機、およびrunnerのSHA-256を照合する。 |
| 資源記録 | 思考応答の壁時計時間だけでは校正に必要なCPU時間を得られないため、各局の両エンジンのCPU時間、局全体の壁時計時間、各プロセスの最大常駐メモリ、実効ワーカー数、物理コア数、および実メモリ容量を保存する。 |
| 履歴ビルド | Gitオブジェクトだけを入力にし、未コミットの作業ツリーを混入させない。 |
| 破損時の扱い | 互換読込み、既定値による補完、および不完全な記録からの推測再開を行わない。 |
| 文書の分割 | 校正と早期投了の未完了が基盤の完了条件へ混入しないよう、完成済みの基盤だけを本書に残し、両者を別マイルストーンへ分離する。 |

## 並列枠の維持

対局の投入数は、統計へ取り込めた件数ではなく、ワーカーから結果を1件受信した事実によって補充する。
結果をペア番号をキーとする待機表へ入れ、次に取り込む番号から連続する結果だけをGSPRTへ渡す。
判定が`pending`で上限へ達していなければ、受信で空いた1枠へ次のペア番号を投入する。
若い番号のペアが遅れても後続ペアを実行でき、GSPRTの対数尤度比（LLR）、判定、および停止ペア番号は完了順に依存しない。

境界へ到達した後は新しいペアを投入せず、進行中のワーカーへ停止を通知する。
停止ペア番号より後に完了した結果は監査用に保存しても、統計へ取り込まない。

## 実行記録と再開

実行ディレクトリは、条件を固定する`manifest.json`、累計実行時間と中断状態を持つ`summary.json`、および確定済みペアを持つ`pairs/`からなる。
新規実行の`--run-dir`と再開の`--resume`はどちらか一方を必須とし、新規実行は存在するパスを拒否し、再開は存在しないパスを拒否する。
同じ実行ディレクトリを使うrunnerは排他的にロックする。

`manifest.json`には、エンジンの識別子と検査和、規則、探索制限、シード、手数上限、応答タイムアウト、実効`Threads`、`USI_Hash`、同時対局数、CPU型、物理コア数、実メモリ容量、およびrunnerの検査和を保存する。
ペア記録には、開始手順、派生シード（基本シードからペア番号ごとに決定的に導いた、開始局面と両エンジンの乱数の種）、候補の先後、両局の全着手、各着手の思考時間、最後のUSI評価値、評価の視点（どちらの色から見た値か）、探索深さ、上下界、詰み表示、終局理由、異常分類、両エンジンのCPU時間、局時間、最大常駐メモリ、およびペア得点分類を保存する。
評価情報を返さないエンジンでは、評価の記録を`null`として保存し、欠測を明示する。

ワーカーは2局と分類を確定した後、一時ファイルの同期、rename、およびディレクトリ同期を終えてから完了結果を送る。
再開時は各記録のファイル名、JSON形式、ペア番号、派生値、全着手の合法性、時計、終局理由、およびペア分類を検証し、条件不一致、記録破損、および保存済み番号より小さい上限を拒否する。
保存済みの連続範囲をペア番号順に読み直してLLRと判定を再計算し、欠番があれば保存済みの後続記録を保持したまま最小の欠番から再実行する。

固定深さまたは固定ノード数では、中断なしの実行と再開した実行の度数、LLR、判定、および停止ペア番号が一致する。
時間制御では対局結果の完全再現を主張せず、確定済みペアを変更せずに同じ逐次検定を継続する。

## 履歴バイナリのキャッシュ

履歴コミットは`git archive`で一時ソースツリーへ展開し、releaseバイナリとSHA-256を原子的にキャッシュする。
キャッシュの欠損または検査和不一致は再ビルドし、同じコミットの並行ビルドはロックで直列化する。

## 保存記録の集計

`match_report`は、同一時間制御の固定ペア数Eloで正常終了した実行ディレクトリを厳密に読み込み、Elo、95%信頼区間、異常件数、CPU時間、局時間、最大常駐メモリ、および校正指標をJSONで再計算する。
GSPRT、異なる時間制御の対戦、実行中または強制終了を含む記録、欠番、条件不一致、および算出不能な主指標（ペア得点の分散または総CPU時間が0で校正指標を計算できない記録）は拒否する。
比較時は時間制御以外の実行条件とペア番号列の完全一致を要求する。

## 実装フェーズ

### フェーズ1　並列枠の維持

対局結果の受信ごとに次ペアを補充し、番号順の統計取り込みと停止判定を維持した。

### フェーズ2　実行記録と再開

実行条件記録、原子的なペア記録、排他ロック、および明示的な再開操作を実装した。

### フェーズ3　監査可能な資源記録

CPU時間、局時間、最大常駐メモリ、実効ワーカー数、実メモリ容量、履歴バイナリのSHA-256検証、および`match_report`を実装した。

## 検証

Rust 1.98.0で、次の標準コマンドがすべて成功した。

```console
cargo fmt --all -- --check
cargo check --all-targets --all-features
cargo clippy --all-targets --all-features
cargo test --all-targets --all-features
RUSTDOCFLAGS='-D warnings' cargo doc --no-deps --all-features
```

ハーネス固有の回帰テストは、次の動作を固定した。

| 状態 | 期待結果 |
|---|---|
| 先頭ペアだけが遅い並列実行 | 後続結果を待機表へ置きながら、指定並列数まで新しいペアを補充する。 |
| 並列度1と複数の固定ノード対局 | ペンタノミアル度数、LLR、判定、および停止ペア番号が一致する。 |
| GSPRT境界への到達 | 停止ペア番号より後の結果を監査用に保存しても統計へ含めない。 |
| 新規実行の既存ディレクトリ | 上書きせず起動を拒否する。 |
| 再開時の条件不一致 | 新しい実験へ切り替えず起動を拒否する。 |
| ペア記録の破損または重複 | 推測で補完せず起動を拒否する。 |
| 保存済み番号の途中にある欠番 | 後続結果を保持し、最小の欠番から再実行する。 |
| 固定ノード対局の中断と再開 | 中断なし実行と統計結果および停止ペア番号が一致する。 |
| 時間制御対局の中断と再開 | 確定済みペアを変更せず、次の欠番から同じGSPRTを継続する。 |
| 再計算だけで判定境界へ到達 | 同じ判定を報告し、新しいペアを投入しない。 |

実データの確認は、煙試験2件と校正カード2件で行った。
ランダムエンジン同士の4ペア煙試験は15.41秒で完走し、保存記録だけから総CPU時間14.80秒、物理コア数20、実メモリ容量33,218,965,504バイト、および異常0件を再集計できた。
Lazy SMPの深さ1の1ペア煙試験は、コミット93bccd9を2ワーカー、コミット4ec0b1dを1ワーカーとして実効ワーカー数を記録し、各局のCPU時間と最大常駐メモリが保存記録に残ることを確認した。
校正カードの正例[measurements/calibration-positive-current.md](../measurements/calibration-positive-current.md)は、現行時間制御200ペアの保存、再集計、および異常検査が実データで機能することを確認した。
校正カードの負例[measurements/calibration-negative-current.md](../measurements/calibration-negative-current.md)は、分散0に対する算出不能の拒否が機能する一方でカード自体が校正に不適切であることを示したため、校正の判断は[棋力測定条件の校正](match-measurement-calibration.md)へ移した。

## 完了条件

次の条件をすべて満たしたため、本マイルストーンを完了とする。

- 遅い先頭ペアがあっても指定並列数を維持し、番号順の統計結果と停止ペア番号が変わらない。
- GSPRTと固定ペア数Eloを、原子的に保存したペア記録から同じ実験として再開できる。
- 全着手、思考情報、終局理由、異常分類、および実効資源を監査できる。
- 履歴バイナリ、runner、および保存記録をSHA-256と厳密な形式検査で識別できる。
- 利用者向けの新規実行、再開、および集計手順が`docs/sprt.md`に反映されている。
- 全標準検証と実データによる煙試験が成功している。

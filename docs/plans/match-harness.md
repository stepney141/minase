# 対局ハーネスのバイナリ対戦化の設計書

## 実施状況

2026年8月11日に本設計書を起案した。
起案時に、作り直しの範囲、通信方式、エンジン指定、思考制限、旧経路の処分、異常時裁定、並列実行、マイルストーンの位置づけの8論点を確定した。
また、fishtestとfastchessの一次資料調査を実施し、本書の「fishtestとの構造対応」の節に反映した。
同2026年8月11日に実装に着手した。
フェーズ1（同期版goとランダムUSIエンジン）は同日完了した（コミット0045833）。
benchの総ノード数241,231がフェーズ2完了時点（93b4bd4）と一致することを確認したため、**凍結ベースラインはコミット0045833のバイナリに`depth=1`を指定したもの**として確定する。
テストは311件全緑であり、`go depth|nodes`と`usi_random`は実プロセスのパイプ経由でも`bestmove`応答を確認した。

フェーズ2（プロセス供給層への差し替え）も同2026年8月11日に完了した。
`src/bin/selfplay.rs`を`src/bin/match_runner.rs`へ改名し、in-processのエンジン対局経路と旧`depth=N` specを削除して、USIプロセス方式（局ごとの起動、`position startpos moves ...`による同期、審判層による合法性照合）へ一本化した。
異常時裁定（IllegalMove・Crash・Timeout）は反則負けとして算入し、理由別件数をサマリに出す。
実装レビューの過程で、エンジンspecに起動引数を書けない欠落（minase本体は`--protocol`と`--rules`を要求する）を発見し、specを空白区切りの起動コマンドとして解釈する形へ拡張した。
移行検証は2件とも再現した。凍結ベースライン（0045833、depth=1）対randomは100ペア全勝（ペンタノミアル[0, 0, 0, 0, 100]、異常0、2.6秒）、depth=2対depth=1のGSPRTは207ペア・LLR 2.9576でH1採用となり、in-process時代の同一シード実行と同じペンタノミアル度数・LLR値を得た。
テストは316件全緑である。

フェーズ3（コミット指定と並列実行）も同2026年8月11日に完了し、本マイルストーンの全フェーズが終了した。
`commit:<hash>`はrev-parseによる正規化、git worktreeでの展開、`cargo build --release`、完全ハッシュをキーとするキャッシュ（`target/match-cache/`）で解決し、minase本体の起動引数`--protocol usi --rules`を自動付与する。
`--concurrency N`はペア単位のワーカープールで並列対局し、出力とLLR取り込みをペア番号順に整列するため、判定は並列度に依存しない（並列度1と4の出力一致を統合テストで固定）。
完了条件の実演として、`--candidate commit:f7a228d --candidate-limit depth=2 --baseline commit:0045833 --baseline-limit depth=1 --concurrency 8 gsprt`が、2コミットのビルドから207ペア・LLR 2.9576のH1採用まで9.0秒で完走し、逐次実行・in-process時代と同一のペンタノミアル度数とLLR値を得た。
テストは319件全緑である。

2026年8月24日、外部エンジンとの比較のためにCECPエンジン指定`cecp:<起動コマンド>`を追加した。
動機はHaChu（Debianパッケージ収録のオリジナル版、コミットdf26f4a）との強さ比較である。
事前検証として、HaChuの自己対局3局（計1,146手）を規則セット`L1,L3,P5,P6,R2,E1,E2`の審判層で照合して全手合法を確認し、2プロセス間で80手を`usermove`で転送しても拒否が起こらず両プロセスの内部盤面が一致することを確認した。
docs/protocols/hachu.md第11章がddugovic派生版（コミット649ef114）で確認した`usermove`照合の欠陥は、オリジナル版には存在しない。
この検証に用いたscripts/hachu_replay.pyは、CECP対局進行の実装（engine-connectivity.mdフェーズ2）以降`new`の直後に`force`を送らないと`usermove`が自動応手を誘発する状態になっていたため、`force`の送信を追加した。
実装後の煙試験（`--seed 1 --each depth=2 elo --pairs 2`、規則`L1,L3,P5,P6,R2,E1,E2`）は4局を完走し、うち1局でHaChuがminaseの着手`c2c1+`を拒否した。
着手列を復元して照合したところ、この着手は敵陣入域時に不成を選んだ後手の歩兵が非捕獲で最奥段へ到達する成りであり、RULES.md第30条P5の本文では強制成りだが、HaChuの標準設定（"Promote on entry"有効）は同条典拠欄の注記どおり最奥段での成りを捕獲着手に限り、不成の`c2c1`だけを受理する。
この差はP5の規則本文が意図的に置いた注記どおりの既知の不一致であり、本ハーネスでは拒否した側（HaChu）の反則負けとして算入される。
HaChuとの測定では`rejected_moves`と`illegal_moves`の件数を結果とともに記録し、判定への影響を評価する。

同2026年8月24日、この機能の初回運用としてminase対HaChuの時間制御GSPRTを実施した。
コマンドは`match_runner --seed 20260824 --candidate commit:a49bd46 --baseline "cecp:../hachu-debian/hachu" --rules L1,L3,P5,P6,R2,E1,E2 --each time=60000+1000 --concurrency 8 gsprt --max-pairs 200`である。
環境はIntel Core Ultra 7 265KF（物理20コア、論理20、SMTなし）、候補Threads=1、基準は単一スレッドのHaChu、`USI_Hash`と`memory`はともに256 MB、同時対局数8、時間制御60秒＋1秒加算である。
HaChuはDebianパッケージ収録のオリジナル版（コミットdf26f4a、`gcc -O2`でビルド、規則オプションは既定のまま）を用いた。
結果は200ペア消化（破棄0）でペンタノミアル[125, 0, 74, 0, 1]、LLR −2.8536584430、判定は上限到達によるpendingであり、経過時間は26,852秒だった。
minaseの得点は400局中76勝（勝率19%）で、固定局数Elo換算は−252［−294, −216］である。
LLRはH0境界−2.944に僅かに届かなかったが、これはelo0=0とelo1=5の狭い仮説帯に対して真の差が桁違いに大きく、1ペアあたりの尤度差が飽和するためであり、順序を入れ替えた仮想LLR（+2.81）も同様に境界手前にとどまる。
95%信頼区間が0から大きく離れているため、この対局条件ではHaChuが明確に強いと結論する。
異常は`crashes=2`と`rejected_moves=1`、`time_forfeits=0`だった。
クラッシュ2件はいずれもHaChuが2,001〜2,002手目で落ちたもので、hachu.cの`MAXMOVES 2000`の棋譜配列上限が原因である。
拒否1件（ペア85第2局304手目）は本節で先述した規則不一致の系統であり、3件とも当該局のHaChuの負けとして算入されている。
3件の該当局をすべてHaChuの勝ちへ振り替えた感度計算でもペンタノミアルは[128, 0, 71, 0, 1]、Elo −260［−303, −223］であり、結論は変わらない。

## 動機

探索部フェーズ2で導入したselfplayのエンジン指定（`--candidate depth=N`と機能フラグ）は、比較対象の機能構成をハーネスが知る設計であり、新機能を追加するたびにspec語彙を広げる必要があった。
測定基盤に求められるのは逆であり、「エンジンにどの機能が追加されたか」を知らずに、旧エンジンと新エンジンの勝敗だけから効果を計算する、ソースコードから一歩離れたメタ的な視点である。
fishtestはまさにこの構造を持ち、テストは2つのgitリビジョンで定義され、ワーカーが両方をビルドし、対局ランナーは差分の内容を一切知らない。
本マイルストーンは、プレイヤー供給層をこの方式へ置き換える。

## fishtestとの構造対応

2026年8月11日の一次資料調査（fishtest wiki、worker/games.py、server/fishtest/rundb.py、fastchessソース）で確認した事実を、本設計との対応で整理する。

| fishtest | 確認した事実 | 本設計での対応 |
|---|---|---|
| テスト定義 | test branch/base branchと各bench署名で定義。baseは通常master | 候補・基準の2エンジンをバイナリパスまたは`commit:<hash>`で指定 |
| ワーカーのビルド | コミットSHAからソースを取得してビルドし、SHAとコンパイラをキーにバイナリをキャッシュ | `commit:`指定をgit worktree＋cargo buildで解決し、ハッシュをキーにキャッシュ |
| 対局ランナー | fastchessが`-repeat -games 2`のペア対局・ペンタノミアル集計・異常時の負け帰属を担う | ハーネスの対局進行層（ペア・開始局面・審判裁定）を保持し、プロセス起動と異常裁定を追加 |
| 異常時裁定 | 不正着手・切断・時間切れ・応答停止は当該エンジンの負け（fastchess match.cpp） | 同方式。反則負けとして算入し、終局理由を記録 |
| 停止判定 | ワーカーは固定バッチを回し、GSPRTのLLR再計算と停止判定はサーバーがバッチ取り込みごとに行う | 対局実行とLLR判定を分離し、取り込みはペア番号順に整列して決定的に行う |
| エンジン別設定 | fastchessは`-engine`ごとに`tc=`・`nodes=`・`depth=`・`option.X=`を指定できる | マッチ共通既定＋エンジン個別上書き |
| SPRT境界 | Stockfish運用はnElo境界（例 {0.0, 2.0}）、α=β=0.05 | 既存statsのロジスティックElo {0, 5}・α=β=0.05を維持（後述） |

fishtestのbench署名検証（ビルド結果が意図したコードと探索的に同一であることの保証）に相当する仕組みは、既存benchコマンドの総ノード数照合が担える。

## 適用範囲

- エンジンバイナリに同期版USI `go depth N`／`go nodes N`と`bestmove`応答を実装する（外部対局接続マイルストーンからの前倒し。時間制御・`stop`・`info`・非同期化は前倒ししない）。
- シードをUSIオプションで注入できるランダム着手のUSIエンジンバイナリを追加する。
- selfplayのプレイヤー供給層を、外部USIエンジンプロセス方式へ全面的に置き換える。in-processのエンジン対局経路（`Player`トレイトのエンジン実装と`depth=N`指定）は削除する。
- エンジン指定にバイナリパスと`commit:<hash>`の両形式を実装する。
- 異常時裁定（不正着手・クラッシュ・応答タイムアウトの反則負け）を実装する。
- ペア単位の並列実行と、ペア番号順の決定的なLLR取り込みを実装する。
- 凍結ベースラインを再定義する（後述）。

次の項目は対象外とする。

- 統計層（`src/stats.rs`）と対局進行層（ペア対局、ランダム開始局面、審判裁定、手数上限のペア破棄）は変更しない。fishtest参照値で検証済みのLLR計算を含め、これらは保持する。
- 時間制御つき対局（movetime・持ち時間）は探索部フェーズ5の時間管理完成後に制限語彙へ追加する。
- 分散実行（複数マシン）、サーバー・ワーカー分離、開始局面bookは実装しない。開始局面は現行のランダム8〜12手方式を維持する。
- USIの`go`一式（時間引数・`stop`・`info`・ponder）の完全実装は外部対局接続マイルストーンに残す。
- Eloモデルの変更（fishtest流のnormalized Eloへの移行）は行わない。探索部設計書で確定したロジスティックElo {0, 5} を維持し、必要が生じた場合に別途判断する。

## 設計判断

2026年8月11日の起案時に確定した決定を示す。

| 論点 | 決定 |
|---|---|
| 作り直しの範囲 | プレイヤー供給層のみ差し替える。統計層と対局進行層は保持する。 |
| 通信方式 | USIサブセット（`position sfen … moves …`・`go depth\|nodes`・`bestmove`）。既存USI実装は`go`以外を処理済みであり、追加は同期版`go`だけである。 |
| エンジン指定 | バイナリパスを原始形とし、`commit:<hash>`をworktree＋ビルド＋キャッシュで解決する。 |
| 思考制限 | マッチ共通既定（例 `--each depth=4`）＋エンジン個別上書き。機能採否SPRTは対等条件、完了基準ゲートは非対称条件を同じCLIで表現する。 |
| 旧経路の処分 | in-processエンジン対局は削除し、ランダムもUSIエンジンバイナリ化して全プレイヤーをプロセスに統一する。 |
| 異常時裁定 | 不正着手・クラッシュ・タイムアウトは当該局の反則負けとして算入し、終局理由を報告する。手数上限打ち切りは従来どおりペア破棄。 |
| 並列実行 | `--concurrency N`のペア単位並列。LLR取り込みはペア番号順に整列し、判定を並列度に依存させない。 |
| 位置づけ | 独立マイルストーンとし、探索部フェーズ3（置換表）の前に実施する。 |

## エンジン側の追加

### 同期版go

USIプロトコルへ`go depth <N>`と`go nodes <N>`を実装する。
受理条件は対局中（`position`適用済み）であり、探索は呼び出しスレッド上で同期実行し、完了後に`bestmove <着手>`を1行返す。
探索エントリは既存の`search::search`をそのまま使い、ルート合法手は審判層の`legal_moves()`、履歴キーは`Game::search_key_history()`から渡す。
`go`に両引数がない場合と、`movetime`等の未対応引数が付く場合は、既存の契約に合わせて`info string error: ...`を返し`bestmove`を送出しない。
外部対局接続マイルストーンが後日この同期版を非同期の探索呼び出し境界（`SearchSnapshot`・停止フラグ・チャネル）へ置き換えても、wire上の`go depth|nodes`と`bestmove`の契約は変わらない。

### ランダムUSIエンジン

新バイナリ（`src/bin/usi_random.rs`を提案）として、`position`と`go`を受けて合法手から一様ランダムに1手を`bestmove`で返す最小のUSIエンジンを追加する。
乱数は`setoption name Seed value <u64>`で注入し、ハーネスが局ごとに決定的に派生したシードを設定する。
規則セットは既存の`setoption name RuleSet value ...`を使う。
これにより、フェーズ1以来のelo=0既知の校正カード（ランダム対ランダム）と、ランダムを相手にした煙試験を、プロセス経路のまま維持できる。

## ハーネス側の変更

### エンジン指定と解決

`--candidate <spec>`と`--baseline <spec>`のspecは次の2形式とする。

- パス形式: 実行ファイルの起動コマンド。空白区切りの2語目以降は起動引数として渡す（fastchessの`cmd=`＋`args=`に相当。minase本体は起動時に`--protocol usi --rules <規則>`を要求するため、この形式が必要である。フェーズ2の実装時に追加した）。
- コミット形式: `commit:<hash>`。ハーネスが`git worktree add`で当該コミットを一時展開し、`cargo build --release --bin minase`でビルドし、成果物を正規化した完全ハッシュをキーに`target/match-cache/`（提案）へキャッシュする。キャッシュ命中時はビルドを省略する。worktreeはビルド後に破棄する。

ランダムエンジンは`random`という予約specで指定し、現行ビルドの`usi_random`バイナリを起動する。

CECP形式は`cecp:<起動コマンド>`とし、パス形式と同じく空白区切りの2語目以降を起動引数として渡す（2026年8月24日追加）。
この形式のエンジンは規則をハーネスから受け取らないため、`--rules`にはそのエンジンが実装する規則を指定する。

### USIセッション管理

各対局でハーネスは、両エンジンプロセスを起動し、`usi`→`setoption name RuleSet value <マッチ規則>`→（ランダムエンジンのみ`setoption name Seed value <局シード>`）→`isready`→`usinewgame`で初期化する。
毎手、手番側エンジンへ`position sfen <開始SFEN> moves <着手列>`と`go depth|nodes <制限>`を送り、`bestmove`を受けて審判層の`Game`へ適用する。
対局進行・合法性判定・終局裁定は従来どおりハーネスの審判層が正であり、エンジンの返答は着手の提案としてのみ扱う。
プロセスはペアごとに起動し直し、ペア内2局の間でエンジンの内部状態（将来の置換表を含む）を持ち越さない。

### CECPセッション管理

CECP形式のエンジンには、起動後に`xboard`と`protover 2`を送り、`feature done=1`を待つ。
続けて`memory 256`（HaChuは`memory`を受けるまで置換表を確保せず、確保前の`go`で異常終了する。256MBはminaseの`USI_Hash`既定値に合わせた値である）、`new`、`variant chu`、`easy`、`nopost`、`force`を送り、時間制御なら`level 0 <分>[:<秒>] <加算秒>`、深さ固定なら`sd <深さ>`を送る。
CECPは対局状態をエンジン側に持つため、毎手の同期は`position`の再送ではなく、前回送信以降の着手だけを`usermove`で転送する形で行う。
エンジン自身の着手はエンジン側で適用済みとして送信済みに数える。
転送後、時間制御なら`time`と`otim`（センチ秒）を送り、深さ固定ではHaChuが時計残量0で反復深化を即座に打ち切るため、十分大きい固定値（3,000,000センチ秒。HaChuは`5×残量`を32ビット整数で計算するため、この上限に収める）を送る。
次に`go`と`ping <手数>`を続けて送り、`pong`までの行を読む。
HaChuは非ポンダー時に探索中の入力を読まないため、`pong`は着手と結果行の後に返り、応答の終端を確定できる。
着手は`move`行で受け、2段階移動はコンマで終わる中間レグの`move`行と最終レグの`move`行を連結する。
じっとの`@@@@`は、審判層の合法手のうち移動元の升番号が最小の正準じっとへ割り当てる。
着手を受けたら`force`を送り、次の`usermove`で自動応手しない状態へ戻す。
`move`行の前に`Illegal move`行が来た場合は、審判層が合法とした着手の拒否として当該エンジンの反則負けとする。
着手がなく結果行（`1-0`・`0-1`・`1/2-1/2`）だけが来た場合は投了として当該エンジンの負けとし、反則には数えない。
思考制限のうち`nodes`と秒読み、および秒未満の持ち時間・加算は、CECPに対応する指定がないため解決時に拒否する。

### 思考制限

`--each depth=N|nodes=M`をマッチ共通既定とし、`--candidate-limit`・`--baseline-limit`（提案）で個別に上書きできる。
機能採否のSPRTは`--each`だけの対等条件で走らせ、完了基準ゲートはベースライン側だけ`depth=1`へ上書きする非対称条件で走らせる。
時間制御語彙（movetime等）は探索部フェーズ5の完成後に追加する。

### 異常時裁定

次の事象は、fastchessと同じく、起こしたエンジンの当該局の反則負けとしてペンタノミアルへ算入し、終局理由（IllegalMove・Crash・Timeout相当）を局結果の行と最終サマリに記録する。

- `bestmove`の着手が審判層の合法手リストにない場合。
- エンジンプロセスの異常終了・パイプ切断。
- 応答タイムアウト（既定値を設け、`--response-timeout`で変更可能とする。深さ・ノード固定対局では探索時間が有界であるため、余裕を持った既定でよい）。
- CECPエンジンが、審判層の合法手として転送された相手の着手を`Illegal move`で拒否した場合（RejectedMove相当。2026年8月24日追加）。

CECPエンジンが着手を返さずに結果行だけを出した場合は投了であり、当該局の負けとして算入するが反則には数えない。

手数上限への到達は実力と無関係な打ち切りであるため、従来どおりペアごと破棄し件数を報告する。

### 並列実行と決定性

`--concurrency N`でペア単位に並列対局する。
ペアシードは従来どおりペア番号から独立に派生するため、各ペアの結果は並列度に依存しない。
GSPRTのLLR取り込みは完了順ではなくペア番号順に整列して行い、同一シード・同一引数なら並列度によらず同一の判定と停止ペア番号を得る。
これはfishtestの「対局実行（ワーカー）とLLR判定（サーバー）の分離」をローカル単機で再現する構造である。

### CLIの形

バイナリは`selfplay`を置き換える形で改名する（`src/bin/match_runner.rs`、名称は起案時提案でありレビューで確定する）。
サブコマンド`gsprt`と`elo`、`--rules`、`--max-ply`、`--seed`、ペア再現情報の出力形式は現行selfplayから引き継ぐ。

使用例（提案）:

```console
match_runner --candidate commit:abc1234 --baseline commit:93b4bd4 \
  --each depth=4 --concurrency 8 gsprt

match_runner --candidate target/release/minase --baseline random \
  --each depth=1 elo --pairs 100
```

## 凍結ベースラインの再定義

探索部フェーズ2で凍結したベースライン「深さ1固定・評価関数v0・静止探索なし・置換表なし」を、バイナリ対戦方式では次のとおり再定義する。

凍結ベースラインは、同期版USI `go`を実装した最初のコミットのバイナリに`depth=1`を指定したものとする。
当該コミットの探索挙動がフェーズ2完了時点（93b4bd4）と同一であることは、benchの総ノード数一致で確認して凍結する（fishtestのbench署名検証に相当）。
以後、完了基準ゲートは常にこのコミットハッシュを`--baseline commit:<hash>`へ指定して実行し、機能追加によるベースラインの変質は構造的に起こらない。

## 実装フェーズ

### フェーズ1　同期版goとランダムUSIエンジン

USIの`go depth|nodes`同期実装と`usi_random`バイナリを実装する。
benchの総ノード数が93b4bd4と一致することを確認し、このコミットを凍結ベースラインのコミットとして本設計書へ記録する。

### フェーズ2　プロセス供給層への差し替え

USIセッション管理、異常時裁定、`--each`と個別上書き、パス形式のエンジン指定を実装し、in-processエンジン経路と旧`depth=N` specを削除する。
移行検証として、フェーズ2完了時の測定を新方式で再現する（凍結ベースライン対randomの全勝、depth=2対depth=1のH1採用）。

### フェーズ3　コミット指定と並列実行

`commit:<hash>`の解決（worktree＋ビルド＋キャッシュ）と`--concurrency`のペア並列・ペア番号順取り込みを実装する。
同一シードで並列度1と並列度Nの出力（経過時間を除く）が一致することをテストで確認する。

## 検証

- `cargo test`全緑、`cargo clippy --all-targets`警告なし、`cargo fmt --check`を各フェーズの完了条件とする。
- USI往復（`position`→`go`→`bestmove`）の単体テストと、不正着手・クラッシュ・タイムアウトそれぞれの反則負け裁定のテストを備える。
- ランダムUSIエンジンのシード再現性（同一シードで同一着手列）をテストする。
- 統計層と対局進行層に変更がないことは、既存テスト（fishtest参照値・モンテカルロ・ペア進行）の無修正通過で保証する。
- 並列決定性は、並列度1と並列度Nの結果一致テストで確認する。

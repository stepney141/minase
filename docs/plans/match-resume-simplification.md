# 測定の再開条件の簡素化の設計書

## 先に読む要約

対局測定`minase match run`と係数調整`minase spsa`は、中断した実行を`--resume`で再開できる。
現在の再開は、利用者に全実行条件を指定し直させたうえで、保存済みの`manifest.json`と完全一致で照合する。
照合の対象には、対局を進める実行ファイル（runner）自身のSHA-256と、測定機のCPU情報も含まれる。
runnerは2026年10月5日の[補助ツールのサブコマンド化](cli-subcommands.md)でエンジンと同じ実行ファイル`minase`になったので、探索や評価だけを変えたコミットでもSHA-256が変わり、作業ツリーを再ビルドすると測定を再開できなくなった。
fishtest、fastchess、cutechess-cli、およびやねうら王系のAyaneは、いずれも再開時にrunner自身のハッシュを照合しない（「参考資料」）。
本書は、runnerのSHA-256と測定機を照合から外して起動ごとの記録に改め、`--resume`は実行条件を`manifest.json`から読む形にする。
エンジンの同一性と実験条件の不変性は、引き続き保証する。
完了条件は、runnerを再ビルドした後でも測定とSPSAの調整セッションを再開でき、起動ごとのrunnerと測定機が記録に残ることである。

## 状態

完了（採用）。
2026年10月5日に起案し、同日に3つのフェーズを終えてmasterへ統合した。
対局測定とSPSAの再開は実行条件を`manifest.json`から読み、runnerと測定機は起動ごとに`invocations.json`へ記録する。
runnerを再ビルドした後の再開、変更前の形式の測定に対する`minase match report`の出力の一致、および変更前の形式のSPSAセッションに対する`minase spsa apply`の結果の一致を確かめた。
本書は棋力に影響しないので、SPRTによる採否の測定は行っていない。

## 目的

測定とSPSAの再開を、作業ツリーの再ビルドや測定機の違いで止まらないようにする。
あわせて、再開の操作を`--resume <実行ディレクトリ>`の1つにし、条件の指定し直しと照合の手間をなくす。
再開の前後で対局の条件が変わらないという保証は、条件の出どころを`manifest.json`の1か所にすることで保つ。

## 適用範囲

対象は、`minase match run`の再開、`minase match report`の測定機の扱い、`minase spsa`の再開、対局ハーネスの`random`指定の同一性、およびこれらを説明する文書である。
エンジンの起動引数、対局の進行、審判層、統計、および保存するペアと反復の記録の中身は変えない。

学習の実行（`tools/train`の`workflow.py`）が記録する生成器と診断の実行ファイルのSHA-256は対象外とする。
こちらは再開の照合ではなく、学習データがどのコミットの生成器で作られたかという来歴であり、生成器を[worktreeに固定する運用](../lessons/pin-generation-binary-to-worktree.md)の前提だからである。
`minase data selfplay rescore`が出力に書く自身のSHA-256も、同じ理由で対象外とする。

## 依存関係

実装のビルドと試験はCPUを使うので、進行中の対局測定が終わってから着手する。
進行中の測定の確認は[進行中の測定を確認する教訓](../lessons/check-running-measurements-before-cpu-load.md)の手順による。

変更後の`minase`は、現在の形式の実行ディレクトリを集計できるが、再開はできない（「旧形式の実行ディレクトリは読み取りだけ受け付ける」の節）。
変更より前に開始した測定は、その測定を開始したrunnerで完了させる。
2026年10月5日時点で進行中の対照CcのLTCは、固定したrunner（`data/eval-coadaptation-runner/match_runner`）で動いているので、この変更の影響を受けない。

## 設計判断

### runnerのSHA-256は照合せず、起動ごとに記録する

runnerのSHA-256の照合が防いでいるのは、1つの測定の途中で審判層、開始局面の生成、または時計の裁定の意味が変わることである。
しかし、ハッシュはこれらと無関係な変更（探索、評価、文書の文字列など）でも変わる。
意味の変化そのものは、審判層の試験、perft、および固定シードの出力の一致で検証しているので、ハッシュの照合が加える保護は小さい。
先行するツールにも、再開時にrunnerのハッシュを照合するものはない。
fishtestはworker自身のファイルのハッシュを起動時に1回照合するが、結果を自己申告するだけで、サーバーは改変されたworkerを拒否しない。

そこで、runnerの版とSHA-256は照合をやめ、起動のたびに記録する（「起動の記録」の節）。
前回の起動とSHA-256が異なる場合は、標準エラーへ1行の通知を出して実行を続ける。
測定の記録者は、起動の記録に複数のrunnerが現れた場合、そのことを測定記録に書く。

棄却した代案は2つある。
1つ目は、runnerが開始時に自分の実行ファイルをハッシュ値をキーにした置き場へ保存し、ハッシュが一致しない再開ではそのパスを示して止める方式である。
再開は確実になるが、先行例のない照合を保つために保存と手順を増やすことになる。
2つ目は、指揮役のrunnerをPythonのスクリプトへ移す方式である。
審判層は`minase`の側に残るので、スクリプトが呼ぶ`minase`の同一性を照合する必要は変わらず、問題は解消しない。

### `--resume`は実行条件を`manifest.json`から読む

現在の`--resume`は、利用者が指定し直した条件から`manifest.json`を組み立て直し、保存済みのものと完全一致で比べる。
条件の出どころが利用者の入力と保存済みの記録の2つあるので、照合が必要になっている。
fastchessと同じく、再開は保存済みの記録だけから条件を読む形にすれば、出どころが1つになり、照合は不要になる。

`minase match run --resume <実行ディレクトリ>`は、エンジン、思考制限、規則、統計モードとGSPRTの仮説、シード、手数上限、応答タイムアウト、先読みの有無、置換表容量、および同時対局数を`manifest.json`から読む。
GSPRTのH0、H1、α、およびβは、再開したrunnerの既定値ではなく、`manifest.json`に記録した値でLLRと判定境界を計算する。
再開時に指定できる引数は、目標のペア数を引き上げる`--target-pairs <N>`だけとする。
`--target-pairs`は、GSPRTではペア数上限（新規実行の`--max-pairs`）、固定局数Eloではペア数（新規実行の`--pairs`）を置き換える。
GSPRTはLLRが判定境界を越えた時点で止まり、上限は境界に達しない場合の打ち切りにだけ働く。固定局数Eloは指定したペア数をすべて実行する。
どちらも「どのペア番号まで実行してよいか」を表すので、再開時は1つの引数で扱う。
`--target-pairs`の値は直前の起動の目標より大きくなければならず、同じ値以下ならエラーで終了する。
`--resume`とそれ以外の条件の引数を同時に指定した場合は、引数のエラーで終了する。
`--target-pairs`は`--run-dir`と同時に指定できない。

`minase spsa --resume <実行ディレクトリ>`は、`manifest.json`の全条件で再開し、ほかの引数を受け付けない。
SPSAの総反復数は開始時に固定する設計なので（[SPSAの設計書](spsa.md)）、延長の引数は設けない。

保存済みの記録からエンジンを組み立て直す規則は次のとおりである。
`commit:`のエンジンは、記録した完全ハッシュのコミットを現在と同じ手順で解決する。
SPSAは調整用のfeatureでビルドするので、同じfeatureで解決する。
起動コマンドで指定したエンジン（`cecp:`を含む）は、記録したプログラム、引数、およびプロトコルで起動する。
起動コマンドの相対パスと引数は作業ディレクトリによって意味が変わるので、再開時の作業ディレクトリが記録した作業ディレクトリと異なる場合はエラーで終了する。
`random`は、再開したrunner自身を`dev usi-random`で起動する。
記録にSHA-256を持つエンジン（対局測定の`commit:`と、SPSAの調整対象のエンジン）は、組み立て直した実行ファイルのSHA-256が記録と一致しなければエラーで終了する。

探索ワーカー数と置換表容量は、新規実行と同じく、両エンジンを1回起動して`Threads`と`USI_Hash`の既定値を読み取ってから決める。
ハーネスは`Threads`をエンジンへ送らないので、エンジンが実際に使うワーカー数はその既定値である。
読み取った既定値が記録した探索ワーカー数と異なる場合は、対局の条件が変わったのでエラーで終了する。
置換表容量は、記録した値が読み取った既定値と等しければ新規実行で省略した場合と同じく送らず、異なれば新規実行で明示した場合と同じく送る。
`manifest.json`は明示値と既定値の区別を持たないが、この規則で新規実行時と同じ送り方を再現できる。
同時対局数は記録した値を使う。
SPSAの`manifest.json`は探索ワーカー数と置換表容量を持たず、SPSAはどちらもエンジンの既定値で対局するので、SPSAの再開ではこの読み取りを行わない。

エンジンの同一性の照合は残す。
ここでいうエンジンの同一性は、対局するエンジンの実行ファイルのSHA-256であり、runnerのSHA-256とは別のものである。
runnerのハッシュの変化は対局の中身と無関係なことが多いが、エンジンのハッシュが変われば、対局する相手そのものが変わる。
この照合は安価で実害のある取り違えを防ぎ、fishtestもbenchのノード数による署名で同じ取り違えを検出している。
`commit:`のキャッシュは、破損を検出すると同じコミットを再ビルドするので、ビルドが再現する限り照合は通る。
ツールチェーンの更新などでビルド結果が変われば照合は失敗し、その測定は元のエンジンでなければ再開できない。

### 測定機は照合せず、起動ごとに記録する

候補と基準は同じ測定機で対局するので、再開の前後で測定機が変わっても、比較は対称なまま保たれる。
そこで、CPUの機種、物理コア数、論理コア数、および実メモリ容量を`manifest.json`から外し、runnerと同じく起動ごとに記録する。
前回の起動と異なる場合は、標準エラーへ1行の通知を出して実行を続ける。
同時対局数は`manifest.json`の値を使い続けるので、物理コア数の少ない測定機で再開すると、同時対局数が物理コア数を超えることがある。
これは意図した動作であり、再開時に同時対局数を測定機に合わせて変えることはしない。
同時対局数を変えると、時間制御の対局で各エンジンが受けるCPUの競合が変わり、再開の前後で条件がそろわなくなるからである。
過剰な同時対局による時間切れは、通常どおり`time_forfeits`に現れる。

一方、`minase match report`の校正用の指標（CPU時間あたりの指標と、物理コアを1つ残しているかの判定）は、測定機ごとに意味が変わる。
そこで、`minase match report`は、実行ディレクトリの全起動の測定機の記録が一致することを要求し、一致しなければエラーで終了する。
`--compare-to`は、比較する2つの実行ディレクトリの全起動の測定機が互いに一致することも要求する。

### `random`指定の同一性からSHA-256を外す

`random`指定のエンジンはrunner自身を`dev usi-random`で起動するので、記録されるSHA-256はrunnerのSHA-256と同じ値である。
runnerの照合だけを外しても、この値が残るとエンジンの同一性の照合で再開が止まる。
そこで、`random`の同一性は種類だけとする。
`random`が起動する実行ファイルはrunnerそのものなので、そのSHA-256は起動の記録のrunnerの欄に起動ごとに残る。

### 旧形式の実行ディレクトリは読み取りだけ受け付ける

対局測定の記録形式の版（`FORMAT_VERSION`）を4から5へ上げる。
`data/matches/`には版4の完了済みの測定が多数あり、`minase match report`による再集計や、新しい測定との`--compare-to`の比較に使うことがある。
そこで、読み取るだけの処理は版4も入力として受け付け、版4にしかない欄は読み飛ばす。
一方、実行ディレクトリへ書き込む再開は、版5だけを受け付ける。
版4の`manifest.json`へ版5の起動の記録を書き足すと、1つの実行ディレクトリに2つの形式が混ざり、以後の読み取りがそれを区別しなければならなくなるからである。
版4の実行ディレクトリの再開は、その測定を開始したrunnerで行う。
版3以前の実行ディレクトリは、現在の`minase match report`も拒否しており、本書でも扱いを変えない。

`minase match report`は、版4の実行ディレクトリを次のとおり読む。
`runner`の欄と、`random`の同一性のSHA-256は読み飛ばす。
`cpu`の欄は、全起動に共通する測定機の記録として扱う。
版4の再開は測定機の完全一致を要求していたので、この欄は全起動の測定機を正しく表している。
したがって、版4の測定でも校正用の指標は従来どおり計算できる。
`--compare-to`は、版4と版5の実行ディレクトリの組合せも受け付け、両者の`manifest.json`から思考制限、`runner`、`cpu`、および`random`の同一性のSHA-256を除いた条件と、測定機の記録の一致を比べる。

SPSAの`manifest.json`は版を持たず、未知の欄を拒否して読み込むので、変更後の再開は変更前の形式を読み込み時のエラーで拒否する。
係数をソースへ反映する`minase spsa apply`は、`manifest.json`のうち調整の設定（係数と更新規則の定数）だけを使う読み取りの処理である。
そこで、`apply`は調整の設定の欄だけを読み、ほかの欄は読み飛ばす。
これにより、変更前に完了した調整セッションも、変更後の`minase`で反映できる。

## 起動の記録

対局測定とSPSAの実行ディレクトリに、起動ごとの記録`invocations.json`を置く。
内容は起動の配列であり、各要素はrunnerの版とSHA-256、および測定機のCPUの機種、物理コア数、論理コア数、実メモリ容量を持つ。
対局測定では、その起動の目標のペア数も持つ。
記録するのは、対局を1つ以上実行する起動だけである。
目標までのペアがすべて保存済みで、結果を表示し直すだけの再開は、要素を追加しない。
こうしないと、別の測定機で結果を表示し直しただけで測定機の記録が混ざり、`minase match report`がその測定を集計できなくなる。

再開の処理は、実行ディレクトリのロックを取得した後、次の順序で進める。
まず`manifest.json`、`invocations.json`、および保存済みのペアを読んで検査し、未実行のペアがあるかを決める。
未実行のペアがあれば、新しい要素を加えた`invocations.json`を原子的に書き、続いて`summary.json`に実行中の状態を書き、その後に対局を始める。
この順序なら、途中で中断しても、保存済みのペアが記録より後の目標で実行されたものになることはない。
再開時の目標のペア数は、`--target-pairs`を指定しなければ最後の要素の値を引き継ぐ。
目標より大きい番号のペアがすでに保存されている場合は、エラーで終了する（現在の再開も同じ検査をしている）。

`summary.json`の累計実行時間と中断状態は変えない。
`manifest.json`は新規実行時に書いた後は変更しない。

## 実装フェーズ

### 第1フェーズ　対局測定の再開

`manifest.json`から`runner`と`cpu`を外し、`invocations.json`を追加し、`FORMAT_VERSION`を5へ上げる。
`--resume`を条件の再指定なしの形に改め、`--target-pairs`を追加し、保存済みの記録からエンジンを組み立て直す。
`random`の同一性からSHA-256を外す。
`minase match report`と`--compare-to`の測定機の検査を`invocations.json`へ移し、版4の実行ディレクトリを読み取りだけ受け付ける。
完了条件は、「検証」の節の対局測定の項目がすべて成り立つことである。

### 第2フェーズ　SPSAの再開

`manifest.json`から`runner`と`cpu`を外し、`invocations.json`を追加し、`--resume`を条件の再指定なしの形に改める。
`minase spsa apply`は、`manifest.json`の調整の設定の欄だけを読むように改める。
完了条件は、「検証」の節のSPSAの項目がすべて成り立つことである。

### 第3フェーズ　文書の書き換え

[SPRTの手引き](../guides/sprt.md)の「実行ディレクトリと再開」の節、LTCの判定保留の延長、`--compare-to`の一致条件、置換表容量と同時対局数の再開時の扱い、および記録項目を、新しい再開手順に合わせる。
[SPSAの手引き](../guides/spsa.md)のrunnerのSHA-256の検査、「中断したセッションを再開する」の節を書き換える。
完了済みの設計書のうち、再開の照合を現行の契約として述べる箇所（[match-harness-efficiency.md](match-harness-efficiency.md)の実験同一性、[cli-subcommands.md](cli-subcommands.md)の実行ファイルのSHA-256の意味の変化、[spsa.md](spsa.md)と[spsa-apply.md](spsa-apply.md)の再開の照合、[match-cost-reduction.md](match-cost-reduction.md)、[ponder.md](ponder.md)、および[bin-harness-layout.md](bin-harness-layout.md)の該当箇所）は、本書へのリンクを付けて現在の契約に合わせる。
測定記録、監査報告、および調査記録は当時の記録なので書き換えない。

## 検証

対局測定は次の項目を確かめる。

- 既存の試験が、再開の照合に関わる試験の改訂を除いて全件通る。
- `random`対`random`の固定局数Eloの小さな測定を完了させた後、runnerのソースに挙動と無関係な変更（ヘルプ文の1文字など）を加えて再ビルドし、SHA-256が変わったことを確かめてから、`--resume`と`--target-pairs`でペア数を引き上げて完走できる。このとき`invocations.json`は2要素で、runnerのSHA-256が異なり、標準エラーに通知が1行出る。
- `manifest.json`に記録したエンジンのSHA-256が、解決した実行ファイルと異なる場合の再開は、エンジンの同一性の不一致でエラーになる（単体試験で、記録を変えた実行ディレクトリを用いる）。
- 記録したGSPRTの仮説がrunnerの既定値と異なる実行ディレクトリを再開すると、記録した仮説でLLRを計算する（単体試験）。
- `--target-pairs`に直前の目標以下の値を指定した再開、および作業ディレクトリが記録と異なる起動コマンドのエンジンの再開は、エラーになる。
- 目標までのペアがすべて保存済みの再開は、`invocations.json`に要素を追加しない。
- `--resume`に条件の引数を加えた呼び出し、および`--run-dir`に`--target-pairs`を加えた呼び出しは、引数のエラーで終了する。
- 版4の実行ディレクトリは、`--resume`ではエラーになる。
- `data/matches/`にある版4の完了済みの測定のうち、変更前の`minase match report`で集計できたものは、変更後も集計でき、出力のJSONが変更前と一致する。
- 版4と版5の実行ディレクトリの組合せを、`--compare-to`で比較できる（単体試験）。
- 測定機の記録が異なる起動を含む実行ディレクトリを、`minase match report`と`--compare-to`がエラーで拒否する。
- 固定シード、深さ制限の同じ測定について、中断せずに完走した場合と、途中で中断して再開した場合のペンタノミアル度数とLLRが一致する。

SPSAは次の項目を確かめる。

- 既存の試験が、再開の照合に関わる試験の改訂を除いて全件通る。
- 小さな調整セッションを中断し、runnerを再ビルドした後に`minase spsa --resume <実行ディレクトリ>`だけで再開して完走できる。このとき`invocations.json`は2要素になる。
- `--resume`にほかの引数を加えた呼び出しは、引数のエラーで終了する。
- 変更前の形式の`manifest.json`を持つ実行ディレクトリの再開は、読み込み時のエラーで拒否される。
- 変更前に完了した調整セッションの実行ディレクトリ（`data/spsa/`の既存のセッション）を、変更後の`minase spsa apply`で反映でき、書き換え後のソースが変更前の`apply`の結果と一致する。

## 完了条件

「検証」の節の全項目が成り立ち、第3フェーズの文書の書き換えを終えてmasterへ統合した時点で、完了（採用）とする。
本書は棋力に影響しないので、SPRTによる採否の測定は行わない。

## 参考資料

先行ツールの再開と同一性の扱いは、各リポジトリの次のコミットのソースで確認した。

- fishtest（コミット4136e07）：ローカルでの再開はなく、無応答のタスクはサーバーが回収して残りを新しいタスクとして配り直す（`rundb.py`の`scavenge_dead_tasks`）。worker自身のファイルのSHA-384は起動時にGitHub masterの`sri.txt`と1回照合し（`worker.py`の`verify_remote_sri`）、結果を自己申告するだけで、サーバーは拒否しない。エンジンは固定したコミットからビルドし、benchのノード数を署名と照合する（`games.py`の`verify_signature`）。
- fastchess（コミットa281caf）：中断時に保存した`config.json`を`-config file=…`で読み込んで再開し、設定と統計をまとめて置き換える（`cli.cpp`の`loadJson`）。自身の版数は保存せず、エンジンはファイルの存在だけを確かめる。
- cutechess-cli（コミット5e84232）：再開機能を持たず、実行ファイルの同一性を照合しない。
- Ayane（コミット5fc6afd）とやねうら王の`engine_invoker5.py`：再開機能を持たず、エンジンはファイルの存在だけを確かめる。

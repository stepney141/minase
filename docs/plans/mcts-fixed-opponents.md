# AlphaZero型探索の強さを測る固定の相手の設計書

## 先に読む要約

本書は、中将棋エンジンminaseのAlphaZero型探索の強さを、強化学習の途中で測るための固定の相手と対局の条件を決める設計書である。
AlphaZero型探索は、ニューラルネットワーク（以下、ネット）で局面を評価しながらモンテカルロ木探索を行う探索であり、以下ではMCTSと書く。
ネットは、自己対局の生成と学習からなるサイクルを繰り返す強化学習で育てる（[統括計画](alphazero.md)）。
強化学習の1回目では、10サイクル前の自分のネットとの対局で強さを測っていた。この測り方では強さが伸び続けて見えたが、別の相手であるminaseのαβ探索には大敗していた。
そこで2回目は、学習の間ずっと変えない2つの相手との対局で測る。
主な相手は、minaseと探索も評価関数も独立している中将棋の外部エンジンHaChuであり、思考の深さを固定して使う。
副次の相手は、コミットを固定したminaseのαβ探索であり、1手の探索を500ノードに固定して使う。
本書では、HaChuの深さを予備の対局で選び、1回目の学習のネットを2つの相手と対局させて、2回目の測定値と比べる基準を作る。
minase本体のコードの変更は行わず、測定のスクリプトと測定記録を成果とする。
完了条件は、2つの相手との対局の条件が固定され、1回目のネットの基準の値が記録されていることである。

## 目的

本書の目的は、強化学習の途中のネットが強くなっているかどうかを、自己対局と独立した相手で確かめられるようにすることである。

強化学習の1回目では、10サイクル前の自分のネットとの対局で強さを測った。
対局の結果から求める強さの尺度であるEloの差の点推定は、サイクル10に対するサイクル20が+199、サイクル20に対するサイクル30が+237であった。
ところが、サイクル32のネットは、minaseのαβ探索に、各10秒+0.1秒の持ち時間の対局で2勝192敗であった（[記録](../measurements/alphazero-rl/alphazero-rl-restart-stc-c0032.md)）。
10サイクル前の自分のネットとの対局で見えた伸びが、ほかの相手に対しても同じだけ得られていたかは、測っていない。
αβ探索と固定のノード数で対局させた記録はサイクル32の1点だけであり、サイクル10と20のネットの値がない（[記録](../measurements/adhoc/alphazero-rl-c0032-ab-ladder.md)）。

本書では、2回目の学習を始める前に、次の2つを行う。
1つは、学習の間ずっと変えない相手と条件を決めることである。
もう1つは、1回目の学習のネットを同じ条件で測り、1回目の伸びが固定の相手に対しても現れていたかを確かめて、2回目の測定値と比べる基準にすることである。

## 適用範囲

本書では、次の作業を行う。

- HaChuとの対局の条件を定め、深さを予備の対局で選ぶ。
- 固定したαβ探索との対局の条件を、規則セット`lishogi`で定める。
- 2つの相手との対局を行うスクリプトを用意する。
- 1回目の学習のサイクル10、20、および32のネットを、2つの相手と対局させて記録する。
- [棋力測定の手引き](../guides/sprt.md)に、深さを固定した外部エンジンの使い方を書き足す。

次の項目は対象外とする。

- MCTSがHaChuの規則で探索できるようにする変更は、完了した[対局用MCTSの規則コードへの対応の設計書](archived/mcts-rule-codes.md)で扱った。
- 10サイクルごとの測定の実行、続行の判断、および伸びが止まったときの手順は、強化学習の2回目の実行の設計書で扱う。
- MCTSとαβ探索のどちらが強いかの判定は、統括計画の「到達の判定」の節で扱う。本書の対局は、同じ相手に対する成績の変化を追うものであり、エンジンの間の強さの比較ではない。
- HaChuの側の修正は行わない。

### 先行実装

固定した相手との対局を主な指標にするのは、先行実装の実践に倣うものである。

- 出村と金子の論文は、将棋のAlphaZero型の学習で、自己対局の100万局ごとに、ノード数を2万に固定した将棋エンジン水匠5との2,000局で強さを測った（[doi:10.3233/ICG-240255](https://doi.org/10.3233/ICG-240255)の4.2節）。
- AlphaZero型の将棋エンジンAobaZeroは、学習の初期には、新しいネットを1つ前のネットと対局させて強さを見積もっていた。この方法は、外部のエンジンとの対局に比べてEloの差が2倍程度大きく出るうえに、自己対局の150万局以降は強さの伸びを捉えられなくなったので、ノード数を固定した外部エンジンKristallweizenとの800局に改めた（[コンピュータ将棋協会誌 Vol.31](http://www2.computer-shogi.org/journal/CSA_vol31.pdf)の40ページ）。
- AlphaZero型の将棋エンジンdlshogiの開発者は、過去の版との対局ではレーティングの差が実際より大きくなる傾向があるとして、測定に水匠5を加えた（[将棋AIの進捗 その60](https://tadaoyamaoka.hatenablog.com/entry/2022/12/11/153857)）。
- AlphaZero型のチェスエンジンlc0のFAQは、自己対局のEloを、ネットの強さの真の指標ではなく、学習の健全さを示す目安と述べている（[FAQ](https://github.com/LeelaChessZero/lc0/wiki/FAQ)）。

### HaChuとの対局の条件

HaChuは中将棋の外部エンジンであり、探索も評価関数もminaseと独立している。
対局の条件は次のとおりである。

| 項目 | 値 |
|---|---|
| MCTS | 対局用のPUCT（方策を探索項に使う上側信頼限界による手の選択）の1手800シミュレーション。USI（将棋エンジンの通信規約）のオプション`NnBatchSize`は16 |
| HaChu | CECPの深さを指定するコマンド`sd`による深さの制限。値は「深さの選定」の節で選ぶ。探索済みの局面を覚える置換表は256 MB |
| 規則 | `L1,L3,P0,P5,P6,R2,E1,E2`を、審判層とMCTSの双方に与える |
| 開始局面 | ハーネスが標準の初期局面から8〜12手を乱択で指した局面。1ペアは、同じ開始局面で先後を入れ替えた2局 |
| 手数の上限 | `--max-ply`を1,900手にする |
| 得点 | 引き分けは0.5点とする。決まった数のペアを対局させ、その得点からEloの差と95%信頼区間をハーネスが推定する |

HaChuの思考の制限には深さを使う。
HaChuはノード数の制限を持たず（`hachu.c`）、時間の制限は機械の速さと負荷に左右されるので、機械によらない固定の強さにできるのは深さだけである。
HaChuは着手に乱数を使わないので、深さを固定すれば、同じ局面と履歴に対して同じ手を指す（推論）。
棋力測定の手引きは、深さを固定した対局を、探索1段の意味がエンジンごとに異なるという理由で、エンジンの間の強さの比較に使わないと定めている。
本書の対局は、HaChuとminaseの強さを比べるものではなく、同じ相手に対するネットの成績の変化を追うものである。
成績の変化を追うには、相手の強さが測定のたびに変わらないことが要るので、深さの固定を使う。
この使い分けを、棋力測定の手引きの「外部エンジンとの強さ比較」の節に書き足す。

規則は、HaChuの既定の設定に対応する規則コードの組を使う（[競技規則](../rules/chu-shogi.md)第33条第7項）。
2回目の学習の自己対局は、オンライン対局サイトlishogiの実装に近い規則セット`lishogi`で行う。その反復の規則R1は、同一局面の4回目の出現で引き分けか攻撃側の負けを裁定する。
HaChuは、既出の局面を再現する着手を禁じる規則R2で指し、反復を許すオプションに切り替えても、R1にはならない。
したがって、この対局は、自己対局と強さの測定を`lishogi`で行うという統括計画の決定の例外であり、ネットが自己対局で学んだ規則とは、反復、成り、および終局の扱いが異なる規則での強さを測る。

HaChuとの対局には、対局の条件と記録の扱いで対処する問題が4つある。
第1に、棋譜の配列の上限が2,000手であり、それを超えると異常終了する（`hachu.c`の`MAXMOVES`）。そこで手数の上限を1,900手にする。
第2に、上限に達した対局があると、ハーネスは、もう一方の対局が終局していても、そのペアごと破棄して件数を報告する。対局の長さはネットによって変わるので、破棄の件数の違いが成績の変化に見えるおそれがある。そこで、破棄したペアがあるときは、破棄したペアをMCTSの2敗とした場合と2勝とした場合のEloを併記する。その回の測定で破棄したペアが、試行したペアの5%を超えた場合は、その回のEloを伸びの判定に使わない。
第3に、HaChuは局面の同一を駒の配置だけで判定し、審判層は、直前の着手で獅子以外の駒が獅子を取ったかどうかという先獅子の状態も含めて判定するので、審判層が認めた着手をHaChuが既出の局面の再現として拒否することがまれにある（[記録](../measurements/hachu-condition-grid/hachu-grid-time1of4.md)）。拒否した件数`rejected_moves`は毎回記録し、0でない場合は、当該局の着手列を再現して、この既知の食い違いかどうかを確かめる。
第4に、HaChuは反復の判定に直近の200局面しか使わないので、既出の局面を再現する着手を禁じる規則R2の下でも、200手より前の局面を再現する着手を指すことがある。審判層はこの着手を合法手から除いているので、ハーネスはHaChuの不正着手として数える（[記録](../measurements/mcts-rule-codes/mcts-rule-codes-hachu-smoke.md)）。不正着手の件数`illegal_moves`も毎回記録し、0でない場合は、当該局の着手列を再現して、この既知の食い違いかどうかを確かめる。

ハーネスは、着手を拒否した側と不正着手を指した側の反則負けとして対局を数えるので、HaChuの拒否と不正着手は、棋力と関係なくMCTSの得点を上げる。
そこで、深さの選定、基準の測定、および定例の測定のどれでも、拒否または不正着手のあった対局を含むペアを除いたEloを併記する。
拒否または不正着手のあった対局を含むペアと、手数の上限で破棄したペアの合計が、試行したペアの5%を超えた条件の値は、深さの選定、基準、および伸びの判定に使わず、原因を調べて利用者に諮る。

### 深さの選定

HaChuの深さは、1回目の学習のサイクル32のネットを、HaChuの深さ1、2、および3と30ペアずつ対局させ、得点率が5割に最も近い深さを選ぶ。
選んだ深さでの得点率が2割から8割の範囲にない場合は、その深さを採らず、深さの範囲を広げるか別の制限を使うかを、結果を添えて利用者に諮る。
サイクル32のネットを使うのは、2回目の学習の最初の数十サイクルのネットが、これに近い強さになると見込むからである（推論）。
選んだ深さは、2回目の学習の間、次に述べる場合を除いて変えない。
学習が進んで、定例の測定の得点率が9割を超えるか1割を下回った場合は、相手の強さを改める。
このときは、同じネットを新旧2つの条件で対局させ、2つの条件のEloの差を、以後の測定値に足して、条件を変える前の値と比べられるようにする（以下、系列をつなぐ）。
HaChuでは、1つ深い、または1つ浅い深さを新しい条件にする。
ハーネスは深さ0を受け付けないので、深さ1で得点率が1割を下回った場合は浅くできない。その場合は、結果を添えて利用者に諮る。
この手順を使う時点は、強化学習の2回目の実行の設計書が定める。

### 固定したαβ探索との対局の条件

副次の相手は、コミット`45d5db54`のminaseのαβ探索であり、1手の探索を500ノードに固定する。
このコミットは、評価関数のNNUE（差分計算する小型のニューラルネットワーク）を埋め込んでいる。
統括計画の目標は、MCTSがminaseのαβ探索とNNUEの組合せと同等以上に強くなることなので、この対局は目標までの距離の目安になる。
コミットを固定し、対局の棋譜を学習に使わないので、後でNNUEを更新しても、この物差しは変わらない。

対局は規則セット`lishogi`で行い、MCTSの条件と開始局面はHaChuとの対局と同じにする。
このコミットは、規則を起動引数`--rules`で受けていた版なので、棋力測定の手引きの「エンジンの指定方法」の節のとおり、αβ側には起動引数`--rules lishogi`を足す。
このコミットのNNUEは`JCSA`の自己対局で学んだものであり、`lishogi`での対局は、学んだ規則と少し異なる規則での対局になる。

1回目のサイクル32のネットは、日本中将棋連盟の規則に基づく規則セット`JCSA`では、MCTSの1手800回とこのαβ探索の500ノードの対局で、Eloの点推定+56であった（[記録](../measurements/mcts-royal-capture-temperature/mcts-royal-capture-temperature-t140-ladder.md)）。
得点率が9割を超えるか1割を下回って差を測れなくなった場合は、HaChuと同じく、250ノードまたは1,000ノードを新しい条件にして、系列をつなぐ。

### MCTSのバイナリ

HaChuとの対局のMCTSは、対局用MCTSの規則コードへの対応をマージした後のmasterのコミットに固定する。
固定したαβ探索との基準の測定は、その前のmasterのコミットで先に行ってよい。
規則コードへの対応の設計書は、規則セット`lishogi`での探索の結果が変更の前後で一致することを確かめるので、その確認が通れば、先に測った値はそのまま使える。
確認が通らなかった場合は、マージした後のコミットで測り直す。
強化学習の2回目の実行は、定例の測定のMCTSを、サイクル1を始めたときのmasterのコミットに固定する。
そのコミットまでの間にMCTSの探索の結果を変える変更が入った場合は、基準の3つのネットを、新しいコミットで2つの相手と測り直す。

## 実装フェーズ

測定のスクリプトは、実装を担うAIエージェントのCodexに委任し、試験とCodexのレビューを通す。
対局はGPUを使うので、Claudeが作業機で実行する。
スクリプトと測定記録は`docs/measurements/mcts-fixed-opponents/`に置き、masterへのマージは利用者の許可を得てから行う。

### フェーズ1　固定したαβ探索との基準

1回目の学習のサイクル10、20、および32のチェックポイントを、今の入出力の形のONNXに書き出し直す。
固定したαβ探索と対局させるスクリプトを用意し、3つのネットをそれぞれ100ペア対局させて、`mcts-fixed-opponents-alphabeta-baseline`として記録する。
このフェーズは、前提の設計書の完了を待たずに行える（「MCTSのバイナリ」の節）。
1回目の学習のネットは10ブロック128チャネルであり、対局は、1つのネットの100ペアあたり約25分と見込む（推論）。

### フェーズ2　HaChuの深さの選定

対局用MCTSの規則コードへの対応の完了の後に始める。
HaChuと対局させるスクリプトを用意し、[外部エンジンは接続前に棋譜照合と着手転送で検証する](../lessons/verify-external-engine-before-cecp-match.md)に従って接続を確かめる。
「深さの選定」の節のとおり、サイクル32のネットを深さ1、2、および3と30ペアずつ対局させ、`mcts-fixed-opponents-hachu-depth`として記録する。
測定の前に、少数のペアで1局あたりの時間を測り、全体の所要時間の見積もりを利用者へ示す。

### フェーズ3　HaChuとの基準

サイクル10、20、および32のネットを、選んだ深さのHaChuとそれぞれ100ペア対局させて、`mcts-fixed-opponents-hachu-baseline`として記録する。
記録には、2つの相手に対する3つのネットのEloを並べ、10サイクル前の自分との対局の伸び（+199と+237）と比べる。
棋力測定の手引きに、深さを固定した外部エンジンの使い方を書き足す。

## 検証

全部の対局で、エンジンの異常終了と時間切れが0件であることを確かめる。
HaChuとの対局では、`rejected_moves`、`illegal_moves`、および手数の上限で破棄したペアの数を記録し、破棄したペアがあるときは、それをMCTSの2敗とした場合と2勝とした場合のEloを併記する。
スクリプトは、少数のペアで最後まで動くことを確かめてから、本番の対局に使う。

## 完了条件

本書の完了条件は、HaChuの深さが選ばれて2つの相手との対局の条件が固定され、1回目の学習のサイクル10、20、および32のネットの、2つの相手に対するEloが記録されていることである。
本書は、変更の採否を決めるものではなく、基準の値を測ること自体を目的とするので、記録がそろった時点で、状態を完了（採用）に改める。
完了の時点で、2つの相手、対局の条件、拒否と破棄の扱い、および系列のつなぎ方を、設計判断の記録（ADR）に書く。
HaChuの深さ1から3のどれも得点率が2割から8割に入らず、利用者と決め直した条件でも固定の相手にできない場合は、その結果を記録し、利用者の決定で扱いを決める。

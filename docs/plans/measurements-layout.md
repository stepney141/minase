# 測定記録の再配置の設計書

## 先に読む要約

docs/measurements/ には、棋力測定、速度測定、学習、および診断の記録が1測定1ファイルで411件ある。
これらは、記録に付随する生データや再現用スクリプトを入れたディレクトリ（以下、付随ディレクトリ）42個と同じ階層に並んでいる。
記録は2026年9月に249件、10月は18日までに119件増えた。
現行の規則（[設計書の書き方](README.md)の「測定記録」節）はディレクトリの一覧を索引とするが、この件数では、ある設計書のもとで行った測定を一覧から拾い出すことが難しくなった。
本書は、各記録を、その測定を計画した設計書ごとのディレクトリ`docs/measurements/<設計書名>/`へ移す。
設計書名は、docs/plans/ または docs/plans/archived/ にある設計書のファイル名から`.md`を除いたものである。
どの設計書も計画していない測定（ビルド設定の速度測定や、設計書の完了後に追加で行った測定など）だけを`docs/measurements/adhoc/`に置く。
測定名は変えないので、記録のファイル名が`minase match run`の`--run-dir`に指定した名前と一致する規則は保たれる。
移動に伴い、記録を指すリンクを、ADR（設計判断の記録）や完了時に凍結した設計書を含むすべての Markdown で書き換える。凍結した文書は本来書き換えないが、リンクのパスに限って書き換えることを2026年10月18日に利用者が認めた。
書き換えたリンクが移動前と同じファイルを指し続けることを検証し、規則を定める文書を新しい配置に合わせて書き直した時点で完了とする。

## 状態

起案。
2026年10月18日に起案した。
置き場所の決め方と例外表は起案の時点で確定しており、着手は利用者の指示を待っている。
次の一手は、着手時点のmasterでのフェーズ1（帰属表の作成）である。

## 目的

ある設計書のもとで行った測定を、ディレクトリの一覧だけで拾い出せるようにする。
あわせて、新しい記録の置き場所を、書き手が判断に迷わずに決められる規則にする。

## 適用範囲

対象は、docs/measurements/ の記録411件、付随ディレクトリ42個、直下に置かれた JSON ファイル1個（fm-phase3-speed.json）、およびリポジトリで追跡している Markdown ファイルにある、これらへのリンクとパスである。

書き換えの範囲は、文書が凍結されているかどうかで分ける。
本書で「凍結した文書」とは、作成後に本文を書き換えない規則を持つ文書をいい、docs/measurements/ の記録と付随ディレクトリの中の Markdown、docs/adr/ のADR、docs/plans/archived/ の設計書、および docs/audits/ の監査報告がこれに当たる。
それ以外の Markdown（docs/plans/ 直下の設計書、手引き、調査メモ、教訓、ROADMAP.md、README.md、CONTRIBUTING.md など）を、本書では「保守する文書」と呼ぶ。

すべての Markdown で、リンクの参照先と、リンクの表示文字列に書かれたパスを書き換える。
記録の外から記録または付随ディレクトリを指すリンクは252ファイルに1,371本あり、移動する Markdown の中の相対リンクは306ファイルに859本ある。
移動する Markdown には、記録のほか、付随ディレクトリの中の`.md`ファイル10個を含む。
表示文字列にパスを書いたリンクは113本ある。
本文に書かれたパス（`docs/measurements/<測定名>.md`の形の記述や、付随ディレクトリの中のファイルを指す記述）は、保守する文書でだけ書き換える。
凍結した文書の本文中のパスは、記録した時点の場所を示す記述として残す。

規則を定める文書のうち、docs/README.md、docs/plans/README.md、CONTRIBUTING.md、および docs/guides/ の sprt.md、spsa.md、nnue-training.md、pst-training.md、debugging.md の8つは、新しい配置に合わせて書き直す。

### 対象外

対象外とするものは次のとおりである。

- 凍結した文書の本文中のパスは書き換えない。記録に書かれた実行コマンドや、`a05478a:docs/measurements/magic-bitboard-prototype/diagonal.patch`のようにコミットを添えた参照は、当時のコミットの中での場所を示す履歴の証拠だからである。付随ディレクトリのスクリプトを再実行するときは、移動前のコミットを取り出して実行する。例えば magic-bitboard-prototype/reproduce.py は自分の位置から2段上をリポジトリの根とみなすので、移動後の位置からは正しく動かない。
- Markdown 以外のファイルは、内容を変えずに移す。付随ディレクトリのスクリプト、パッチ、JSON、TSV は、記録した時点の作業ツリーを前提に書かれており（例えば relational-correction-prep/phase0.py は当時の worktree の絶対パスを読む）、現在の配置に合わせて書き換えても再現できるようにはならないからである。docs/audits/ の監査報告に付く TSV も、当時の機械的な解析の出力なので書き換えない。
- 記録を削除する棚卸しは行わない。記録はADRと凍結した設計書の根拠であり、ADRが参照する記録だけで195件ある。ほかの記録を含むどの文書からもリンクされない記録は17件で、その大半は煙試験（採否の測定の前に、対局が異常なく完走するかを数ペアで確かめる試験）の記録なので、削っても一覧はほとんど短くならない。
- リポジトリの容量の削減は目的に含めない。付随ディレクトリと JSON が約8.0 MB、記録が約1.8 MBを占めるが、移動しても git の履歴の容量は変わらない。
- 対局の実行ディレクトリ`data/matches/<測定名>/`は、階層を持たない現行の配置のまま変えない。測定名は全体で一意なので（「設計判断」節）、実行ディレクトリを設計書ごとに分ける必要はない。
- .claude/worktrees/ と data/worktrees/ にある作業ツリーは書き換えない。これらの作業ツリーの文書はmasterとリンクの形が食い違うが、ブランチを統合する時点で本書の規則に合わせる（「依存関係」節）。
- 別リポジトリ minase-gui の docs/plans/hachu-cecp.md は、本文で`docs/measurements/strength-stage1-hachu-elo200.md`に触れている。別リポジトリなので本書の完了条件には含めず、minase-gui 側の別のコミットで直す。

## 依存関係

masterに統合していないブランチのうち12本が、docs/measurements/ に記録を追加または変更している。
該当するブランチは、eval-search-coadaptation、fm-eval、heuristic-learning-diagnosis、pst-fm-joint-training、qsearch-output-training、rank-loss-training、relational-correction、search-aware-evaluation、search-forms、search-pruning-forms、strength-stage9-diag-b、および strength-stage9-pre-squash である。
このうち作業が続いているのは search-forms と search-pruning-forms の2本であり、残りの10本を統合するかどうかは本書では決めない。

git は統合の際に、名前の変更を検出したファイル（既定では内容の50%以上が一致するもの）への変更を移動先へ追従させる。
しかし、ブランチで新しく作った記録は直下に置かれたまま統合され、ブランチで追加または変更した文書の中の旧形式のリンクとパスもそのまま残る。
例えば fm-eval ブランチの docs/research/evaluation-improvement-strategy.md は、本文で`docs/measurements/fm-quarter-vs-pst-stc.md`に触れている。
そこで、これらのブランチを本書の完了後にmasterへ統合するときは、統合のコミットの中で、直下に置かれた記録を本書の規則に従って移し、ブランチ由来の文書のリンクと、保守する文書の本文中のパスを書き換える。
そのうえで、統合後の木で次の3点を確かめる。
1点目は、統合で追加または変更された Markdown の相対リンクがすべて解決できることである。
2点目は、`git ls-files docs/measurements | awk -F/ 'NF==3'`の出力が空で、直下にファイルがないことである。
3点目は、統合後の木に存在しないパスを指すリンクと、保守する文書の本文中のそうしたパスが、統合で変わったファイルに残っていないことである。
ブランチ qsearch-output-training と rank-loss-training は、設計書と同じ名前の付随ディレクトリにファイルを加えている。
この2つの付随ディレクトリは本書で`docs/measurements/<設計書名>/<設計書名>/`へ移る（「実装フェーズ」節）ので、統合後に加わったファイルの位置を特に確かめる。

本書のブランチも、masterへ統合する直前にmasterを取り込み、ブランチの作成後にmasterへ加わった記録を移す（フェーズ4）。

## 設計判断

記録をどの設計書のディレクトリに置くかの判定規則は、次節「帰属の決め方」で定める。

| 論点 | 採用 | 棄却した代案 |
|---|---|---|
| 分け方の軸 | 測定を計画した設計書ごとに分ける | 測定の種類（stc、ltc、bench、diag）ごとに分ける案は、ファイル名の接尾辞と重複し、1つの設計書の記録が散らばる。月ごとに分ける案は、記録を日付で探す読み手がいない。対象領域（探索、NNUE、合法手生成など）ごとに分ける案は、新しい記録のたびに境界の判断が要る。索引ファイルを加える案は、「索引ファイルは作らない」規則に反し、更新漏れが起こる |
| ディレクトリ名 | 設計書のファイル名から`.md`を除いたもの | 短い別名は、設計書との対応表が別に要る |
| 測定名 | 変えない | ディレクトリ名と重なる接頭辞（`strength-stage6-`など）を外す案は、data/matches/ が階層を持たないので測定名が全体で一意でなくなり、記録と実行ディレクトリの突き合わせもできなくなる |
| 複数の設計書が参照する記録 | 計画した設計書の下に1つだけ置き、ほかの設計書はリンクで参照する | 参照する設計書ごとの複製やシンボリックリンクは、同じ記録が複数の場所にでき、どれが正か分からなくなる |
| 同じ候補を段階的に測る一連の測定の後段（短時間条件のSTCに続く長時間条件のLTCなど） | 前段と同じディレクトリ | 後段を行った時点で進行中だった設計書に置く案は、前段と後段が別々の場所に分かれることがある |
| 設計書を起案する前に行った予備測定 | 既存の記録は、起案時の本文がその測定を起案の根拠として引用した設計書に置く。本書の完了後は、設計書を起案してから測定し、起案前に行った測定は adhoc/ に置く | 既存の記録を adhoc/ に置く案は、その設計書の測定を一覧で拾えなくなる。記録を追加したコミットの時刻で分ける案は、同じ性格の予備測定が、設計書と同じコミットか数分前のコミットかで別の場所に分かれる。今後の予備測定を、これから起案する設計書の名前のディレクトリに置く案は、設計書が起案されないと、ディレクトリがどの設計書にも対応しなくなる |
| どの設計書も計画していない測定 | adhoc/ に置く（起案時点で11件） | 測定を依頼した調査メモの名前のディレクトリに置く案は、調査メモもない測定（ビルド設定の速度測定、リリース時のHaChu比較）の置き場が別に要る。関係の深い設計書へ寄せる案は、設計書が計画した測定と計画していない測定の区別がなくなる |
| 完了した設計書の記録 | 動かさない | plans/archived/ に合わせて archived/ の層を設ける案は、設計書が完了するたびに記録のパスとリンクが変わる |
| 付随ディレクトリ | 同名の記録と同じディレクトリへ移す | 付随ディレクトリだけを別の階層にまとめる案は、記録から付随ファイルへの相対リンク（`<測定名>/summary.json`など）まで書き換えの対象に加わる |
| 凍結した文書の中のリンク | リンクの参照先と表示文字列のパスだけを書き換え、本文中のパスは残す（2026年10月18日に利用者が決定）。この例外は完了時にADRへ記録し、凍結の規則そのものは変えない | 書き換えない案は、ADRと凍結した設計書から記録へのリンクが切れる。本文中のパスも書き換える案は、コミットを添えた参照や当時の実行コマンドを、当時の木に存在しないパスに変えてしまう。旧パスに転送用のファイルを残す案は、411個のファイルが直下に残り、再配置の目的に反する |
| Markdown 以外のファイル | 内容を変えずに移す | パスを書き換える案は、記録した時点の作業ツリーを前提にしたファイルなので、書き換えても再現できない |

## 帰属の決め方

記録の置き場所は、その測定を計画した設計書で決める。
「計画した」とは、測定を始めた時点で設計書が存在し、測定がその設計書の段階や判定の一部として行われたことをいう。
ただし、既存の記録のうち、設計書を起案するために行った予備測定は、起案時の設計書の本文が起案の根拠として引用していれば、その設計書に置く。
設計書の完了後に追加で行った測定と、どの設計書の段階や判定にも属さない測定は、adhoc/ に置く。
ほかの設計書やADRが後から引用しても、置き場所は変わらない。
設計書が完了して plans/archived/ へ移ってもファイル名は変わらないので、ディレクトリ名は引き続き同じ設計書に対応する。

計画した設計書は、次の3つの手がかりから判定する。

1. 記録の本文がリンクしている設計書がちょうど1つなら、その設計書。記録の「目的」節（この節を持たない記録では冒頭の段落）は、多くの場合、測定を計画した設計書とその段階を明記している。
2. 記録を追加したコミットで追加または変更された設計書がちょうど1つなら、その設計書。
3. 測定名の先頭が設計書名とハイフンで区切られて一致するなら、一致する設計書名のうち最も長いもの。

3つの手がかりに優先順位はつけず、得られた手がかりがすべて同じ設計書を指す記録を、その設計書の候補とする。
起案の時点では411件のうち365件がこれに当たった。
ほかの文書から記録へのリンクは、引用であって計画を示さないので、手がかりに使わない。
例えば magic-bitboard-prototype は crate-split の設計書だけから参照されるが、その参照は第三者のコードの来歴に触れたものであり、測定は docs/research/ の調査メモ[magic bitboardの適用可能性](../research/magic-bitboard-feasibility.md)のために行った。

手がかりが食い違うか1つも得られない記録は46件あった。
候補が決まった365件のうち、手がかりが1つしかない148件は、目的節の冒頭または追加したコミットの件名を読んで確かめ、手がかりが誤っていた5件を改めた（次の表で※を付けた記録）。
手がかりが食い違うか得られなかった46件と、手がかりを改めた5件を合わせた51件は、記録の「目的」節と追加したコミットを読んで置き場所を決めた。

この結果、直下には、設計書名のディレクトリ59個と adhoc を合わせた60個のディレクトリが残る。

本書の完了後に記録を書く人は、記録を書く時点で、その測定を計画した設計書のディレクトリへ置き、ディレクトリがなければ作る。
どの設計書も計画していない測定は adhoc/ に置き、ある設計書のための測定にしたい場合は、先に設計書を起案する。
一度置いた記録は動かさない。

## 実装フェーズ

フェーズ1は、帰属表の作成である。
帰属表は、記録、付随ディレクトリ、および直下の JSON の各項目と、その移動先のディレクトリとの対応を並べた表である。
付随ディレクトリについては、その中のすべてのファイル（付随ディレクトリの中の Markdown 10個を含む）を移動前と移動後のパスの対として展開して持つ。
着手時点のmasterで、前節の手がかりと例外表からすべての項目の移動先を求める。
本書の起案後に加わった記録は、同じ手順で決め、手がかりが割れたものと手がかりが1つしかないものを読んで決める。
帰属表は作業用の一時ファイルとし、リポジトリにはコミットしない。移動後のファイルの配置そのものが帰属表の内容を表すからである。
すべての項目が移動先をちょうど1つ持ち、移動先が既存の設計書名か adhoc であることを、このフェーズの完了条件とする。

フェーズ2は、移動とリンクおよびパスの書き換えである。
`git mv`による移動、すべての Markdown のリンクの書き換え、および保守する文書の本文中のパスの書き換えを、1つのコミットで行う。
分けると途中のコミットでリンクが切れるからである。
付随ディレクトリ qsearch-output-training と rank-loss-training は、移動先として新設する同名のディレクトリとパスが衝突するので、いったん一時的な名前に変えてから移動先の下へ移す。

リンクの書き換えは、文字列の置換ではなく、次の手順で行う。
まず、各リンクの参照先を、リンクを含むファイルの移動前の位置から解決して、リポジトリの中のパスにする。
次に、そのパスを帰属表に従って移動後のパスに置き換え、リンクを含むファイルの移動後の位置からの相対パスに直す。
`#`以降の見出しの指定はそのまま残す。
文字列の置換では、別のディレクトリへ移る記録どうしの相対リンク（起案時点で88本）と、1段深くなった記録からほかの文書へのリンクを正しく直せないからである。
リンクの表示文字列に書かれたパスは、そのパスが指す項目を帰属表で移動後のパスに置き換え、表示の書き方（`docs/`から書くか`measurements/`から書くかなど）は保つ。

保守する文書の本文中のパスは、移動した項目を指す`measurements/<名前>`の部分を`measurements/<設計書名>/<名前>`に置き換え、後ろに続くファイル名や行番号（`:565`など）はそのまま残す。
コミットを添えた参照（`<コミット>:docs/measurements/...`）は、保守する文書でも書き換えない。
`<測定名>`のような雛形の記述はフェーズ3で手作業で直す。
`docs/measurements/**/test_*.py`のように`**`を含むパターンは、配置が深くなっても同じファイルに一致するので書き換えない。

移動と書き換えの使い捨てのスクリプトは、[codexへの実装委任の手引き](../guides/codex-delegation.md)に従ってcodexに書かせ、リポジトリにはコミットしない。
検証のスクリプトは、移動のスクリプトとは独立に Claude が書く。
「検証」節のV1からV5までを満たすことを、このフェーズの完了条件とする。

フェーズ3は、規則を定める文書の書き直しである。
「適用範囲」節に挙げた8つの文書で、記録の置き場所を`docs/measurements/<設計書名>/<測定名>.md`に改める。
あわせて、前節の帰属の規則、adhoc/ の定義、および新しい記録の置き方を書く。
索引についての記述は、直下の一覧が設計書ごとの目次になり、各ディレクトリの一覧がその設計書の測定の目次になる、という2段の構成に改める。
付随ファイルの置き場所（debugging.md の`diagnostic.patch`など）も`docs/measurements/<設計書名>/<測定名>/`に改める。
このフェーズでは規則の文章そのものを改めるので、フェーズ2とは別のコミットにし、差分を読んで確かめる。
書き直した文書の中に旧形式の置き場所の記述が残っていないことと、V1、V4、およびV5を再び満たすことを、このフェーズの完了条件とする。

フェーズ4は、完了処理とmasterへの統合である。
統合の直前にmasterを取り込み、ブランチの作成後にmasterへ加わった記録をフェーズ1の手順で移す。
この移動は1つのコミットにまとめ、そのコミットとその親についてV2とV3を、取り込み後の木についてV1、V4、およびV5を確かめる。
置き場所の規則、adhoc/ の定義、および凍結した文書のリンクを書き換えた例外をADRに記録する。
本書の「状態」節を完了の段落に書き換えて凍結し、docs/plans/archived/ へ移して本書へのリンクを直し、ROADMAP.md の状態表と「現在地」を更新する。
そのうえで、利用者の許可を得てmasterへ統合し、作業ツリーとブランチを削除する。

## 検証

検証は、フェーズ2の直前のコミット（以下、移動前の木）とフェーズ2のコミット（以下、移動後の木）を比べて行う。
V1、V4、およびV5は、フェーズ3の後とフェーズ4でmasterを取り込んだ後にも、その時点の木で再び確かめる。

V1は、リンクが解決できることの確認である。
ここで「解決できる」とは、リンクの参照先を、リンクを含むファイルの位置からリポジトリの中のパスへ直したとき、そのパスにファイルかディレクトリがあることをいう。
移動前と移動後の木のそれぞれで、追跡しているすべての Markdown の相対リンク（脚注の定義を含む）を解決する。
URLとページ内の見出しだけを指すリンクは除き、`#`以降は解決の前に取り除く。
移動後に解決できないリンクの集合が、移動前に解決できなかったリンクの集合を帰属表で移動後のパスに置き換えたものと一致することを確かめる。
起案時点で、移動と関係なく解決できないリンクがリポジトリ全体に約1,100本ある。大半は、旧配置のソースコードの行を指す監査報告のリンクと、手引きの中の雛形である。docs/measurements/ に関わるものとしては、docs/lessons/simulate-acceptance-criteria-on-the-candidate.md から存在しない`time-management-byoyomi-k1.md`へのリンクがある。

V2は、各リンクとパスが移動前と同じファイルを指すことの確認である。
書き換えた各 Markdown ファイルで、移動前の各リンクの参照先を帰属表で移動後のパスに置き換えたものが、移動後の対応するリンクの参照先と一致することを確かめる。
比べるのは文字列ではなく、解決したリポジトリの中のパスと`#`以降の指定である。
リンクの表示文字列に書かれたパスと、保守する文書の本文中のパスは、後ろに続くファイル名や行番号を含む記述全体を単位として、移動前の記述を帰属表で移動後のパスに置き換えたものと、移動後の記述が一致することを確かめる。
そのうえで、凍結した文書ではリンクの参照先と表示文字列を除いた本文が、保守する文書ではさらに本文中のパスを除いた本文が、移動の前後で同じであることを確かめる。

V3は、Markdown 以外のファイルが変わっていないことの確認である。
帰属表で対応づけた移動前と移動後のパスについて、git のオブジェクトのハッシュが一致することを確かめる。
git の名前変更の検出（`git diff -M`）は、内容が同じ別のファイルを移動元と移動先の対にすることがあるので、対応づけには使わない。

V4は、配置の確認である。
docs/measurements/ の直下がディレクトリだけであり、各ディレクトリ名が docs/plans/ または docs/plans/archived/ の設計書名か adhoc であることを確かめる。
あわせて、帰属表に展開したすべてのファイルが、帰属表どおりの位置にちょうど1回ずつ現れ、移動先に帰属表にないファイルが現れないことを確かめる。
件数は、その時点の帰属表から数える。

V5は、旧配置のパスが残っていないことの確認である。
ここで「旧配置のパス」とは、移動前の木に存在し、移動後の木に存在しない、docs/measurements/ の下のパスをいう。
すべての Markdown のリンクの参照先と表示文字列、および保守する文書の本文中のパスのうち、旧配置のパスを指すものがないことを確かめる。
判定は、後ろに続くファイル名を含めたパス全体で行い、先頭の文字列の一致では行わない。
`docs/measurements/qsearch-output-training/`のように、移動前と移動後で別の項目を指す同じ文字列があるからである。

## 完了条件

masterを取り込んだ後のブランチでV1からV5までを満たし、フェーズ3の規則の書き直し、ADRへの記録、本書の凍結、およびROADMAP.mdの更新を終え、利用者の許可を得てmasterへ統合した時点で、完了（採用）とする。

# Minase GUI初版の計画書

## 文書の位置付け

2026年8月11日に、非公開の`minase-gui`リポジトリを作成するための計画として起案した。
リポジトリの作成時に本書を移し、それ以後の進捗と実施記録は移動先だけで管理する。
本書はminaseのマイルストーン状態に含めない。

## 目的

中将棋のAI対AIをブラウザで1局ずつ観戦できる開発用GUIを作る。
人間対AIはAI対AIの完成後に追加し、初版の完了条件には含めない。

GUIとエンジンの意味的な通信にはUSIだけを使う。
GUIは規則、合法手生成、終局判定を実装しない。
CECPと人間対人間は対象にしない。

## 先行例

[ShogiHome](https://github.com/sunfish-shogi/shogihome/blob/b9c492c1d820191e72e1187ef30bd1be5f1141b0/src/renderer/game/game.ts#L180-L209)は先手と後手を独立したUSIプレイヤーとして構築しているため、座席ごとに1つのエンジンプロセスを割り当てる構成の参考にする。
[Lishogiの中将棋盤](https://lishogi.org/analysis/chushogi)と[Shogiground](https://github.com/WandererXII/shogiground)は、12×12盤の表示と将来の2段移動入力の参考にする。
[XBoardの中将棋操作](https://www.gnu.org/software/xboard/whats_new/rules/Chu.html)は、2段移動の中間升を保持する操作モデルの比較対象とする。

先行例から利用するのは盤面部品と確認済みの操作・プロセス構成であり、対局規則はminaseから取得する。

## 構成

GUIはVite、TypeScript、Shogigroundで構成し、React、Vue、状態管理ライブラリを追加しない。
Rust製のローカルランチャーが静的ファイルとWebSocketを`127.0.0.1`だけで提供し、USIプロセスの標準入出力を中継する。

```text
ブラウザGUI
    ⇅ WebSocket上の座席付きUSI行
ローカルランチャー
    ⇅ 標準入出力
先手USIプロセス / 後手USIプロセス
```

ランチャーは指し手、規則、盤面、終局理由を解釈しない。
WebSocketの通常メッセージは座席とUSIの1行だけを持つ。

```json
{"seat":"black","line":"go movetime 1000"}
```

子プロセスの終了はUSI行で表せないため、ランチャーからGUIへの制御メッセージを1種類だけ設ける。
要求ID、応答ID、再接続復旧、盤面APIは追加しない。

## プロセスの扱い

ランチャーは絶対パスの`--black-engine`と`--white-engine`を受け取る。
初版は両方の指定を必須とし、先後に独立したUSIプロセスを1つずつ起動する。
シェル文字列とエンジン固有の追加引数は受理しない。

1つのランチャーは1つのブラウザ接続だけを受理する。
2つ目の接続は拒否し、接続が切れた場合は子プロセスを終了する。
再接続時は新しいプロセスで最初から開始する。

通常の次局ではプロセスを再起動せず、`setoption`、`isready`、`usinewgame`、`position startpos`を送る。
異常時の自動再試行、自動再起動、途中局面からの復旧は実装しない。

## 対局開始

GUIは両プロセスへ`usi`を送り、エンジン名と宣言されたオプションを表示する。
`USI_Variant`が宣言された場合は`chushogi`を設定する。
`RuleSet`は両プロセスへ同じ値を送り、`isready`、`usinewgame`、`position startpos`の後に両者の`state rules`が一致することだけを確認する。
規則が一致しない場合は対局を開始せず、接続ログに理由を表示する。

開始局面は`startpos`だけとする。
SFEN入力と局面編集は設けない。

## 各手の処理

GUIは対局開始からのUSI着手列を棋譜として保持する。
各手では、次の処理だけを行う。

1. GUIは両プロセスへ同じ`position startpos moves ...`を送る。
2. GUIは手番側プロセスへ`state`を送り、表示用盤面と終局状態を得る。
3. 終局していなければ、GUIは同じプロセスへ`moves`を送る。
4. GUIは同じプロセスへ`go movetime N`を送る。
5. 通常の`bestmove`が直前の`moves`に含まれる場合だけ棋譜へ追加する。

`state`の手番は棋譜長から求めた手番と照合する。
一致しない場合は、直前の`position`が反映されていないものとして対局を停止する。

`bestmove resign`は候補との照合を行わず、返した側の投了として扱う。
`bestmove win`はminaseが対応する勝ち宣言規則を持たないため、対局を停止する。

`state`が終局を返した場合、GUIは各エンジンから見た`win`、`lose`、`draw`を`gameover`で通知する。
利用者の中止では、探索中なら`stop`を送り、返された`bestmove`を適用せず、結果なしの`gameover`を送る。

エンジン終了、`info string error:`の受信、不正なUSI行、`moves`にない`bestmove`では対局を停止し、現在の盤面、棋譜、接続ログを残す。
異常を分類して復旧する機構は設けない。
初版は応答タイムアウトを設けず、応答待ちの対局は利用者の中止操作で終了する。

## 画面

画面はデスクトップ用の1画面とする。
左に12×12盤、右に対局状態、先後の探索情報、棋譜を置き、上部に設定、下部に折り畳み式の接続ログを置く。
スマートフォン、タブレット、専用のタッチ配置は対象外とする。

盤面はShogigroundとLishogiの`ryoko_1kanji`駒素材を使い、先手を手前に表示する。
盤反転ボタンは設けるが、盤と駒のテーマ選択は設けない。
当面は非公開とし、公開時のライセンス判断は初版の対象外とする。

各エンジンについて、最新の`depth`、`score`、`nodes`、`nps`、`pv`を表示する。
接続ログは各エンジンの直近200行をメモリ上に保持する。

棋譜はUSI着手列として表示する。
規則セット、先後のエンジン名、結果、終局理由、`position startpos moves ...`をクリップボードへコピーできるようにする。
ファイルのダウンロードと棋譜読込みは設けない。

各手後の`state board`を保存し、棋譜の手を選ぶと過去局面を読み取り専用で表示する。
この表示用SFENから対局を再開しない。

## 設定

初版の設定は、共通の`RuleSet`、先後別の`movetime`、宣言された場合だけ先後別の`USI_Hash`に限る。
`movetime`の初期値は`1000 ms`とし、正の整数だけを受理する。
`USI_Hash`はエンジンの宣言値を初期値とする。
設定はブラウザへ永続化しない。

AI対AIは1局ずつ手動で開始する。
連続対局、先後交替、勝敗集計、対局時計、ponderは実装しない。

## テスト用USIプロセス

探索実装前にランチャーとAI対AIを確認するため、固定した短い対局だけを返すテスト用USIプロセスを1本置く。
このプロセスはTypeScriptで書き、Nodeで実行する。
規則、探索、任意シナリオの設定、故障注入は実装しない。

このプロセスは`usi`、`isready`、`usinewgame`、`position`、`state`、`moves`、`go`、`gameover`、`quit`の固定台本だけに応答する。
各手の`state`と`moves`は静的な文字列の表から返し、通常手を数手返した後の`go`に`bestmove resign`を返して終局させる。
任意の局面やエラーを作る設定機能は持たせない。

自動試験はGUI側のテストランナーから駆動する。
テストがビルド済みランチャーを子プロセスとして起動し、自らWebSocketクライアントとなって2つのテスト用プロセスによる固定対局を投了まで進め、投了以外の各`bestmove`が直前の`moves`に含まれることだけを確認する。
実GUIと同じWebSocket経路を通すことで、中継の契約を端到端で検証する。
GUIの内部構造へ依存するブラウザ操作試験は追加しない。

## 実装段階

### 第1段階　ランチャー

子プロセス管理、静的ファイル配信、1接続のWebSocket中継を実装する。
Webフレームワークと静的ファイルの埋込み方式は、着手時に必要な依存関係だけから決める。

### 第2段階　盤面と表示

Shogigroundによる盤面、対局設定、探索情報、棋譜、過去局面、コピー、接続ログを実装する。

### 第3段階　AI対AI

2つのUSIプロセスを使う対局進行を実装し、固定対局を終局まで実行する。

### 第4段階　実探索との接続

探索部マイルストーンのフェーズ5が完了した後、標準USIの`info`、`USI_Hash`、`go movetime`を実minaseへ接続する。
GUI専用の探索APIは追加しない。

## 人間対AI

人間対AIはAI対AIの完成後に別の段階として起案する。
その段階では、ランチャーを1プロセス構成へ広げ、`moves`の候補だけからクリック入力、2段移動、成り選択、投了を実装する。

2段移動は候補文字列を移動元、第1到達升、第2到達升、成り接尾辞へ分解して扱う。
`from == to`だけを根拠にじっとと判定せず、3升表記の中間升を保持する。

人間対AIの完了条件と試験方法は、その段階の起案時に決める。
初版の完了条件へ先に追加しない。

## 完了条件

- 絶対パスで指定した2つのUSIプロセスを独立して起動できる。
- 両プロセスへ同じ棋譜を送り、手番側だけへ`state`、`moves`、`go movetime`を送って対局を進められる。
- 通常の`bestmove`を直前の`moves`で検証する。
- 固定応答の短いAI対AI対局が終局まで進む。
- 盤面、探索情報、棋譜、接続ログを1画面で確認できる。
- 初版の対象外機能を実装していない。

# 合法手生成と利き計算の高速化（第2期）の設計書

## 先に読む要約

本マイルストーンは、[第1期](movegen-speedup.md)の採用版を新しい基準とし、同じ時間でより深く読めるようにして棋力を上げることを目的とする。
変更は、探索木（探索が訪れる局面の集合）を変えないものと変えるものの2種類に分ける。
探索木を変えない変更（段階1から段階6）は、固定局面を固定深さで探索する測定プログラム`bench`のNPS（1秒あたりに処理する局面数）で採否を決め、まとめて1回の自己対局の逐次確率比検定（SPRT）にかけ、NPSを基準比1.3倍以上にすることを目標とし、1.15倍以上を最低受入条件とする。
探索木を変える変更（段階7から段階9）は、`bench`の固定深さの経過時間で事前に選別したうえで、SPRTで採否を決める。
[起案時の診断](../measurements/movegen-speedup-2-diagnostics-depth5.md)では、探索時間の約7割が静止探索（駒を取る手だけを読み進める探索の末端）にあり、静止探索ノードの初期化で自駒の利きを求める走り計算、置換表（探索済み局面の結果を保存する表）の照合で生じるメモリ待ち、および静的交換評価（SEE、到達升での駒の取り合いを見積もる評価）の利き逆引きが3大負荷である。
走り計算の78%は捕獲対象へ届かない駒に属し、対象升が4升以下のノードが3分の1あるので、利き線を対象升で事前に選別する変更と、対象升が少ないノードだけ対象升から取り手を逆引きする変更を先に行い、続いて走り計算の書き換え、SEE逆引きの近傍走査、静止探索と主探索の固定費の削減を1段階1測定単位で判定する。
静止探索の置換表は照合の的中率が11%しかないので、探索木を変える変更として静的評価の打ち切りを照合より先に行う変更と捕獲対象がないノードで置換表へ触れない変更を、静止探索の獅子の候補を絞る変更とともにSPRTへ出す。
置換表のメモリ待ちそのものを隠すプリフェッチ命令は`unsafe`を要し、利用者が`unsafe`を許可しないと決めたため使わず、ビットボード（144升の集合を3個の64ビット整数で表す型）の微最適化も試作で効果がなかったので扱わない。

進行中。2026年9月15日に起案し、2026年9月16日に着手した。

段階10の前半では、段階6までの採用版と第1期の採用版の[STC](../measurements/movegen-speedup-2-stage6-stc.md)と[LTC](../measurements/movegen-speedup-2-stage6-ltc.md)がいずれも`H1`かつ異常0件で、段階6までの採用版を採用した。

次の一手はそのSTCの判定であり、通過すればLTCへ進む。

## 目的

第1期は基準比1.500倍で完了したが、目標の2倍には届かなかった。
本マイルストーンは第1期の採用版を新しい基準にして残存負荷を削り、加えて探索木を変えてでも同じ深さへ速く到達できる変更を棋力で判定して採用する。
新しい基準の`bench`（深さ5、1スレッド、3回の中央値）は経過0.562秒、NPS 2,256,193、総ノード数1,268,607であり、目標の1.3倍は経過0.432秒以下、最低受入条件の1.15倍は経過0.489秒以下に相当する。
第1期の基準コミット（master、`0e3dfa6`）に対しては、それぞれ約1.95倍と約1.73倍になる。
削減する処理の件数と実行時間を分けて測り、効果が重なる段階の改善率を加算しない。

## 適用範囲

対象は次のコードとビルド設定である。

- `src/core/movegen/`は合法手の生成、探索専用の捕獲生成、および利きの逆引きを実装する。
- `src/core/attacks/`は駒種ごとの動きの定義、固定利きの表、および走り計算を実装する。
- `src/core/bitboard.rs`は144升の集合を3個の64ビット整数で表し、段階4の走り計算の書き換えでだけ対象になる。
- `src/core/position.rs`は着手の適用と復元、駒種別のビットボード、およびzobristハッシュを保持する。
- `src/core/rules.rs`は獅子捕獲後の足と成りを判定する。
- `src/search/mod.rs`の静止探索、主探索の手選択器、およびノード計数を対象とする。
- `src/search/see.rs`は交換列を評価する。
- `src/eval/pst.rs`は駒位置評価の累算値を差分更新する。
- `Cargo.toml`のreleaseプロファイルを対象とする。

本書の用語は第1期の設計書の定義に従う。
加えて、**入口の閾値**は静止探索の入口で決まる値`alpha − stand_pat − delta_margin`（αは最善値の下限、`stand_pat`は静的評価値、`delta_margin`は既存の枝刈りの余裕値）であり、取る駒の価値がこれ以下の捕獲は探索しても最善値を更新できない。
**対象升**は入口の閾値を超える価値の相手駒がある升の集合、**取り手**はある升の駒を取れる手番側の駒、**利き線**は遮蔽を考慮せずに走りが通り得る升の集合、**在席マスク**は各対局者について盤上に存在する駒種の集合を表すビット集合であり、段階4の測定条件を満たす場合だけ導入する候補である。

評価関数、時間管理、規則の解釈、着手の正準表現、および主探索の着手順は変えない。
静止探索の候補集合と置換表の使い方は、段階7から段階9に限り、SPRTで採否を決める前提で変えてよく、段階8を採用した場合は探索専用生成の残存手順の契約を除外条件を適用した参照列へ改める。
主探索の枝刈りと着手順の改良は棋力向上の段階計画（[棋力向上の段階計画](strength-stages.md)）の範囲であり、本書では扱わない。
公開の全手生成と捕獲生成では、着手集合、順序、合法性、および`perft`の経路数を維持する。
プロファイル誘導最適化（PGO）は第1期で利用者が不採用と決めたので、本マイルストーンでは再提案しない。

## 設計判断

### 残存負荷の測り直しから段階を選ぶ

第1期の採用版に対して、フレームポインタを有効にし、探索部と生成の主要関数のインライン化を`#[inline(never)]`で止めた通常最適化のビルドで`perf record -F 6000 --call-graph fp`を取り、計測区間外の置換表クリアを除いた探索中の標本（10,642標本、統計誤差は各値で約±1ポイント）に対する自己時間を集計した。
インライン化を止めた分だけ経過は約5%長いが、関数間の割合は通常ビルドの分布と整合する。

| 関数 | 自己時間 | 主な呼出元 |
|---|---:|---|
| `TranspositionTable::probe` | 13.9% | 静止探索12.7% |
| `piece_control_without_special`と`sliding_control` | 17.9% | 静止探索の初期化11.3%、主探索の全手生成3.6%、SEEと獅子の足判定1.9% |
| `Position::attackers_to_by`（SEEの逆引き） | 9.1% | `see_prunes` |
| `MoveGenerator::collect_ordinary_capturers` | 8.1% | 静止探索の初期化 |
| `QsearchBuffers::initialize`（相手駒の走査、特殊候補の構築） | 7.0% | 静止探索 |
| 着手の適用と復元（`make_move_unchecked`、`unmake_move`、`put_piece`、`remove_piece`） | 4.6% | 主探索と静止探索 |
| `MovePicker::next`（全手生成と非捕獲の選別を含む） | 3.8% | 主探索 |
| `Pst::update_accumulator_after_move` | 3.7% | 主探索と静止探索 |
| `promotion_choice`と`promotion_choice_for` | 3.7% | 生成と着手の適用 |
| `QsearchBuffers::generate_group`（価値グループの合流と整列） | 3.4% | 静止探索 |
| `Position::captured_squares` | 3.1% | 成り判定、手選択器、獅子規則 |
| 手の整列（`move_order_key`、`sort_by_key`、`quicksort`） | 2.6% | 主探索と静止探索 |
| `see_prunes`と`least_valuable_attacker`（逆引きを除くSEE本体） | 2.1% | 静止探索 |
| `special_move_is_legal`と`lion_has_foot_after_capture` | 1.7% | 生成 |
| ノードごとの固定費（`quiesce`、`negamax`、`enter_node`、`search_move`、`QsearchBuffers::next`、`store`） | 4.7% | 探索 |

探索部に属する自己時間（置換表、静止探索の初期化とグループ構築、手選択器、評価の差分更新、SEE本体、整列、ノードごとの固定費）は合計で約41%であり、その3分の1が置換表の照合である。
通常ビルドの包含時間では、主探索の全手生成（`generate_moves::<false>`）が7.6%、手選択器の整列を含めると10.5%を占め、静止探索の外側が探索時間の29.8%である。
置換表の照合は自己時間13.9%を1回の読み込みが占め、1ノードあたり約58ナノ秒でDRAMの遅延に相当する。
本機の透過的な大ページ設定は`always`であり、TLBミスは主因ではない。
ハードウェアカウンタでは探索全体のIPC（1サイクルあたりの命令数）が約3.4であり、置換表の照合を除けば演算律速である。

静止探索の初期化に診断出力を加えて数えた件数は次のとおりである。

| 項目 | 値 |
|---|---:|
| 初期化に到達したノード数（総ノード数に対する割合） | 468,981（37.0%） |
| 1ノードあたりの対象升数の平均 | 15.05 |
| 対象升が2升以下、4升以下、8升以下のノードの割合 | 22.5%、33.4%、46.7% |
| 対象升が相手の全駒に一致するノードの割合 | 30.7% |
| 1ノードあたりの自駒の利き計算（`piece_control_without_special`）の回数 | 5.12 |
| 1ノードあたりの走り計算（`sliding_control`）の回数 | 17.05 |
| 1ノードあたりの対象升へ届く自駒の数 | 1.39 |
| 対象升へ届く自駒に属する走り計算の割合 | 22.3% |

対象升へ届く自駒は1ノードあたり1.39枚に過ぎず、走り計算の77.7%は捕獲を1つも生まない。
現行の到達範囲による事前選別は駒単位なので、方向ごとの利き線と対象升の交差を調べれば、対象升へ届き得ない方向の走り計算を省ける。
ただし77.7%は「対象升へ届かない駒」に属する走り計算の割合であって方向単位の値ではなく、届く駒にも対象升と交わらない方向があり、逆に利き線が交わっていても遮蔽で届かない方向は省けない。
省略できる方向の割合は段階1で直接数え、選別の費用を含めて見込みを定める。
また対象升が4升以下のノードが3分の1あり、そこでは対象升から取り手を逆引きする方が、自駒約31枚を走査するより少ない演算で済む。
第1期の単位Bで逆引き方式が負けたのは、対象升の数にかかわらず全グループで逆引きしたためであり、対象升数で切り替える混成方式は試していない。

置換表の照合は、第1期のE1（着手適用の直後に行を`black_box`で読む方式）で差がなかった。
通常の読み込みは値が届くまでリタイアできず、後続の命令がリオーダバッファを埋めた時点で停止するので、非同期のプリフェッチ命令でなければ待ちを隠せない。
本機で`_mm_prefetch`を着手適用の直後に置く試作はNPS比約1.03倍で局面別の出力も一致した（[起案時の診断](../measurements/movegen-speedup-2-diagnostics-depth5.md)）。
この命令は`#[target_feature]`つきの関数であり、`-C target-cpu=native`で機能が有効でも呼出側に`unsafe`を要する（rustc 1.98.0で確認、`unsafe`なしの包み関数でも同じエラーになる）。
現行の`Cargo.toml`は`unsafe_code = "forbid"`であり、利用者は`unsafe`を許可しないと決めたので、置換表の先読みは実施せず、試作の測定値だけをここに残す。
`unsafe`を使わない早期の読み込みは、読み込み命令がリオーダバッファの先頭に達した時点で後続の実行が止まり、隠せる待ちがバッファの容量（本機では約170サイクル分の命令）に限られるため、SEEの前に置いてもE1と同じく効果がない。
したがって置換表の照合の自己時間13.9%は、探索木を変えない段階では残る負荷として扱い、照合の回数を減らす変更を探索木を変える段階7と段階9で判定する。
置換表の既定容量を3次キャッシュに収まる値へ下げる案は、対局条件そのものを変えるので本書では扱わない。

ビットボードの型そのものについては、走査で見つけた升を再検証せずに作る変更と、3語の走査を条件分岐のない語選択に置き換えて語添字の境界検査を飽和で消す変更を試作した（[起案時の診断](../measurements/movegen-speedup-2-diagnostics-depth5.md)）。
前者は増分がなく、後者は約17%遅くなった。
3語の走査は分岐予測がよく当たる短いループであり、分岐を消すと3語をすべて読んで添字で選び直す分だけ命令が増える。
また探索全体のIPCが約3.4と高く、集合演算そのものは3命令で終わるので、4語化してAVX2の1命令にまとめる変更や、番兵の列を除いた密な配置への変更は、表の容量を増やすか升の変換を増やすだけで見込みがない。
したがってビットボードの表現と基本演算は変えず、ビットボード演算の回数を減らす段階（段階2、3、5、6）と、走り計算で2回の依存する表引きと走査を減らす段階4に絞る。
段階4は、分岐を消すこと自体ではなく表引きと走査の回数を減らすことを目的とし、試作で速くならなければ採用しない。

ビルド設定では、`codegen-units = 1`がNPS比1.014倍から1.025倍の効果を示し（[起案時の診断](../measurements/movegen-speedup-2-diagnostics-depth5.md)）、`panic = "abort"`は追加の差がなく、探索ワーカーのパニックを閉じ込める`catch_unwind`の契約にも反するので採らない。

### 探索木を変えない段階の採否

段階1から段階6までは探索木を変えない。
各段階は1コミットにまとめ、直前の採用版である親コミットと比較し、照合参照コミット（第1期の設計書が定める照合参照コミットであり、探索木は現行と同一）との局面別のノード数、最善手、探索値の一致と、NPS中央値の増加を採用条件とする。
候補と親は交互に3回以上測り、候補のNPS中央値の増分が交互測定における親の中央値の幅（本日の測定では約±0.6%）を超えない段階は採用せず、その理由と測定値を記録する。
数%の高速化は1件ずつSPRTで検出できないので、段階6までの採用版をまとめて1回のSPRT（STC、続いてLTC）にかける。
各段階の見込みは自己時間の割合に削減できる処理の割合を掛けた概算であり、実測で置き換える。
複数の段階が同じ処理を削る場合（段階2、3、4、5）、後の段階の見込みは直前の採用版で測り直し、本書の初期値を加算しない。

### 探索木を変える段階の採否

段階7から段階9は探索木を変えるので、局面別一致では判定できず、[SPRTの手引き](../guides/sprt.md)の段階ゲートに従って親コミットとのSTC、続いてLTCで採否を決める。
SPRTへ出す前に、`bench`の固定深さの経過時間（15局面の合計、3回の中央値）が親より短いことを事前選別の条件とし、ノード数の増減も併記する。
NPSは探索木が変わる変更の指標にならないので使わない。
同じ着想のパラメータ違いは事前選別で1つに絞り、SPRTの結果を見てから追加しない。

試作した5変種の固定深さの経過時間と局面別のノード数は[起案時の診断](../measurements/movegen-speedup-2-diagnostics-depth5.md)にある。
静的評価の先行打ち切りはノードが1.8%増えて経過が約2%縮み、静止探索の獅子候補の絞り込みはノードが1.2%減って経過が約4%縮んだので、それぞれ段階7と段階8の候補にする。
静止探索の置換表を全く使わない変種も基準より速いが、ノードが9.2%増えて先行打ち切りより短縮量が小さいので、候補を先行打ち切りに絞る。
先行打ち切りに最善手のない結果の保存省略を加えた変種は増分がなく、取る駒の価値が動かす駒の価値以上ならSEEを省く変種は経過が約6%延びたので、いずれも採らない。

静止探索ノードの終わり方を数えると、静止探索ノード757,927件のうち28.1%が静的評価で打ち切られ、9.9%が置換表で打ち切られ、62.0%が候補生成へ進む。
置換表の照合が的中するのは11.0%で、静的評価で打ち切れるノードの照合は99.6%が外れており、置換表で打ち切ったノードの42%は静的評価でも打ち切れる。
候補生成へ進むノードで置換表の手が得られるのは0.7%に過ぎない。
したがって静止探索の置換表は、照合1回あたりのDRAM待ちに対して得るものが少なく、照合の回数を減らす変更が段階7と段階9の対象になる。

SPRTの所要時間は次のとおり見積もる。
STC（10秒＋0.1秒）は1ペアが約136秒、同時16対局で1ペアあたり約8.5秒、LTC（60秒＋0.2秒）は1ペアが約432秒、同時16対局で1ペアあたり約27秒である。
[SPRTの手引き](../guides/sprt.md)の期待ペア数から、真の効果が10 Eloなら約2,600ペアでSTC約6時間とLTC約20時間、20 Eloなら約950ペアでSTC約2時間とLTC約7時間、40 Eloなら約410ペアでSTC約1時間とLTC約3時間になる。
持ち時間2倍が約216 Eloに相当する[感度測定](../measurements/sensitivity-time2x.md)の目安では、固定深さの経過時間の4%の短縮は約12 Elo、2%は約6 Eloであり、段階ごとのSPRTは判定保留になりやすく1件あたり1日規模の測定を要する。
[SPRTの手引き](../guides/sprt.md)は同じコミット対についてSTCを通過してからLTCへ進むことを求めるので、STCを通過した段階だけを寄せ集めて1回のLTCにかける方式は採れない。
採れる方式は、段階ごとに直前の採用版とのSTCと同じコミット対のLTCで判定する方式と、事前選別を通過した3段階を1コミットに固定してその構成全体について1回のSTCとLTCで判定する方式の2つである。
利用者は後者を選んだ。
段階ごとの効果（各2%から4%、約6 Eloから12 Elo）はH1の10 Eloの谷に落ちて判定保留になりやすいのに対し、3段階を合わせた効果は10%前後（約30 Elo）が見込め、600ペア程度で決着する見込みだからである。
段階ごとの効果の切り分けは失うが、有害な段階が混ざる危険は段階ごとの固定深さの経過時間による事前選別で抑える。
結果は合算せず、ハーネスに機能比較スイッチを加えない。

## 各段階

### 段階1　計測基盤の更新とビルド設定

`scripts/bench_compare.py`に、段階の親コミットを指定して候補と親を交互に測る`--parent`を加え、速度の基準（`--baseline`）は第1期の採用版、参照（`--reference`）は照合参照コミットのまま使う。
局面別一致は参照に対して、累積の速度比は基準に対して、段階の採否は親に対して報告する。
第1期の[処理件数診断の差分](../measurements/movegen-speedup-ideas-counts/diagnostic.patch)（`src/search/mod.rs`と`src/core/movegen/`へ件数の出力を加える差分で、診断用のターゲットディレクトリにだけ当てる）へ、静止探索の初期化における対象升数、自駒の利き計算回数、走り計算回数、対象升と交わらない利き線の方向数、対象升へ届く自駒数、置換表の照合の的中率、SEEで逆引きなしに早期終了できる呼出し数（段階6）、および静止探索ノードの終わり方（静的評価の打ち切り、置換表の打ち切り、候補が空、候補あり）の分布（段階7と段階9）の集計を加える。
各件数には独立した参照を定める。
対象升数は、相手駒を独立に走査して価値の閾値と王駒の条件から再構成した集合の大きさと一致しなければならない。
対象升へ届く自駒数は、特殊駒を除く自駒について合法性判定前の利きを独立に求め、対象升と交わる駒を数えた値と一致しなければならない。
利き計算回数は到達範囲と対象升の交差を別の走査で数え直した値と、走り計算回数は利き計算ごとの動きの定義の走り方向数の和と、方向数は利き線の表を直接引いた値と一致しなければならない。
SEEの早期終了の件数は、条件を満たす呼出しで参照実装の値が`Some(v)`かつ`v < 0`なら診断を停止し、`None`（規則依存）と非負の値は認めて件数を別記する。
不一致なら診断を停止して原因を調べる。
差分と入力は測定記録の付属ディレクトリへ保存する。
`Cargo.toml`のreleaseプロファイルへ`codegen-units = 1`を加える。
完了条件は、参照、基準、親との比較が1コマンドで実行でき、診断ビルドと速度ビルドが分離され、診断の各件数が参照と一致し、`codegen-units = 1`の採否が局面別一致とNPSで確定していることである。
診断の結果は[段階1の件数診断](../measurements/movegen-speedup-2-stage1-counts.md)、`codegen-units = 1`の採否は[段階1のbench比較](../measurements/movegen-speedup-2-stage1-bench-depth5.md)にある。

### 段階2　通常駒の捕獲生成における利き線の事前選別

`MoveGenerator::ordinary_capturer`は、遮蔽なしの到達範囲と対象升の交差を確かめた後、走りの全方向を計算している。
これを、方向ごとの利き線と対象升が交わる方向だけ走り計算を行い、交わらない方向を省く変種へ改める。
利き線は遮蔽を考慮しない超集合なので、交わらない方向の到達升が対象升と交わることはなく、結果は`piece_control_without_special(...) & allowed`と一致する。
固定利きだけの駒では走りの検査自体を省き、走りを持つ駒でも固定利きと対象升の積を先に取る。
見込みは、走り計算の自己時間のうち静止探索の初期化に属する約11ポイントに、段階1で数える「対象升と交わらない方向」の割合を掛け、選別の費用を差し引いた値とする。
参考として、届かない駒に属する走り計算の割合77.7%をそのまま当てはめると約8.6ポイントになるが、これは方向単位の値ではないので見込みには使わない。
検証は、`src/search/search_captures_tests.rs`の残存手順一致、`src/core/movegen/tests/properties.rs`の捕獲生成一致、および局面別一致とNPSによる。
結果は[段階2のbench比較](../measurements/movegen-speedup-2-stage2-bench-depth5.md)にある。

### 段階3　対象升が少ないノードの逆引き生成

対象升の数が閾値以下のノードでは、自駒を走査せず、各対象升への取り手を`attackers_to_by`と同じ方式で逆引きし、取り手の集合を駒種順と升順に並べ直して`OrdinaryCapturer`の列を復元する。
復元した列は現行の走査順（`PieceKind::ALL`の順に各駒種のビットボードを昇順に走査した順）と同一でなければならない。
閾値は、段階1の診断で対象升数ごとに現行の走査の演算数（利き計算と走り計算の回数）と逆引きの演算数（対象升数×8方向の走りと近傍の固定利き）を数え、逆引きの演算数が現行を下回る最大の対象升数とし、着手前に1つへ固定する。
見込みは、対象升が4升以下のノードが33.4%あることから、初期化の走査費用のうち該当ノード分の大半、探索時間の3%から6%である。
段階2と削減対象が重なるので、段階2の採用後に対象升数ごとの演算数を測り直してから着手し、閾値が1未満になるか、NPSの増分が親の中央値の幅を超えなければ採用しない。
検証は段階2と同じ契約テストと局面別一致に加え、閾値の両側で同じ残存手順になることを固定シードの局面で検査する。
段階2の採用後の[測り直し](../measurements/movegen-speedup-2-stage3-counts.md)では、逆引きの走り計算だけで対象升1升あたり8回を要するのに対し、現行の走査は1升のノードで利き計算と走り計算の合計が0.82回であり、閾値が1未満になるので着手しない。

### 段階4　走り計算の書き換えとSEE逆引きの近傍走査

`AttackTables::sliding_control`は、利き線と占有の積から最初の遮蔽駒を求める際に、3語のビットボードを分岐つきで走査し、`Square::from_raw`の再検証を経て`Option`を返し、遮蔽駒の利き線を再度引く。
これを、添字が増える4方向では、`b = ray & occupied`として3語を1つの192ビット整数とみなす借り伝播つきの`2^192`を法とする減算で`b − 1`を求め、`ray & (b ^ (b − 1))`を遮蔽駒までの升（遮蔽駒を含む）とする分岐なしの計算へ改める。
`b`が0のときは`b ^ (b − 1)`が全ビット1になり、`ray`との積で利き線全体が得られる。
添字が減る4方向では、3語の`leading_zeros`と条件付き移動で最上位ビットの添字を求め、遮蔽駒がない場合を表す番兵の添字で空集合を引く利き線表（193要素）を使う。
全28種類の動きの定義で走りは距離無制限なので、`max_steps`の分岐と`range_masks`表（432 KB）は本番経路で使われておらず削除する。
方向ごとに「この駒種はこの方向へ走るか」を16分岐の照合で求めている箇所は、対局者と動きの定義ごとの方向マスクの表引きに置き換える。
`Bitboard::contains`などは升番号を64で割った語添字で3語の配列を引くが、升番号は`u8`なので商が3になり得ると見なされ境界検査が残る。
商を2で飽和させれば添字が常に配列の範囲内であることをコンパイラが証明でき、検査が消える。
見込みは、走り計算の自己時間（合計17.9ポイント）のうち走査と2回目の表引きに当たる部分であり、探索時間の1%から3%とする。
語選択の分岐除去が試作で遅くなった結果を踏まえ、まず添字が増える4方向の減算方式だけを1変種として測り、速くならなければ本段階は表の削除と方向マスクの表引きだけを残す。
検証は`src/core/attacks/tables.rs`の逐次歩行との一致テスト（両方向、語境界、遮蔽なし、複数遮蔽、仮想占有）と、`src/core/movegen/tests/`の駒の動きのテストによる。

SEEの逆引きの固定利きも本段階に含める。
`attackers_to_by`は、固定利きについて29駒種の逆引き表を順に引き、駒種ごとに空集合の検査を挟んでいる。
固定利きの移動量はすべて5×5の近傍に収まるので、固定利きの逆引きは対象升の近傍にある指定側の駒だけを列挙し、移動量から動きの定義を引く小さな表で判定する方式へ先に改める。
在席マスク（各対局者について盤上に存在する駒種の集合）は、近傍走査の採用後に駒種の走査が残る箇所（特殊駒3種の検査など）を測り、維持費（`put_piece`と`remove_piece`での更新）を含めて増分がある場合にだけ加える。
`lion_has_foot_after_capture`が使う`square_is_controlled`は、獅子を取った駒の升に対して、取られた側（獅子の所有者）の全駒の利きを仮想盤面で順方向に計算しているので、仮想盤面の占有と取られた側を与えた`attackers_to_by`へ置き換える。
見込みは、逆引きの自己時間9.1ポイントのうち固定利きの逆引きに当たる部分の半分、探索時間の1%から3%である。
検証は`src/core/movegen/tests/attackers.rs`の逆引きと駒別利きの一致、`src/search/see.rs`の参照実装との枝刈り判断の一致、および獅子規則のテストによる。
変種ごとの測定と採否は[段階4のbench比較](../measurements/movegen-speedup-2-stage4-bench-depth5.md)にあり、減算方式は親比1.0904倍、近傍走査と足判定の逆引き化は1.0507倍で採用し、減少方向の`leading_zeros`と番兵表への書き換え（1.0039倍）と在席マスク（0.9952倍）は親の幅内で採用しなかった。

### 段階5　静止探索の候補処理の簡素化

`QsearchBuffers::initialize`は、相手の全駒を1升ずつ取り出し、盤面から駒コードを読んで駒状態（駒種と成否の組、47種類）を求め、既存の駒状態別の価値表と順位表を引いている。
これを駒種別のビットボードで走査し、成駒と不成駒で価値が異なる駒種だけ盤面を読む方式へ改め、升ごとの盤面参照を減らす。
特殊駒の候補は、閾値と最後の王駒の判定を終える前に`QsearchCapture`を構築しているので、判定を先に行い、残る候補だけを構築する。
最後の王駒の判定に使う王駒の集合と枚数は、候補ごとではなくノードごとに1回求める。
獅子が隣接する相手駒を取ってから進む手のうち、同じ移動元と経由升で経由升の駒だけを取る手（居喰いを含む）は、捕獲価値と攻撃駒価値が等しく、同じ価値グループ内で連続するので、経由升ごとに1件の圧縮した候補として保持し、取り出すときに展開する。
到達升でも駒を取る手は捕獲価値が異なるので別候補のままにする。
展開は価値グループ内の順序と置換表の手の重複除外を保ち、展開後の列は現行の候補列と同一でなければならない。
`reset`が置換表の手を検証するために行う1駒分の生成は、後の初期化で同じ駒の利きを再計算するので、検証結果の利きを初期化へ引き継ぐ。
価値グループの構築（`generate_group`、自己時間3.4%）は、候補が1ノード平均2.5件しかないのに、10バイトの候補を48バイトの`QsearchCapture`へ複写し、特殊候補との合流と整列を毎グループ行っている。
`QsearchCapture`の順序キーと連番は各フィールドの最大値を確認したうえで小さい整数へ縮め、通常候補は中間バッファを経ずにグループへ直接出力して生成順の連番を付け、特殊候補がないグループでは合流だけを省く。
通常候補は駒種順に出力され攻撃駒価値順ではないので、攻撃駒価値と連番による整列は残す。
見込みは、初期化の自己時間7.0ポイントとグループ構築の3.4ポイントの合計の3分の1程度、探索時間の3%から4%である。
検証は残存手順一致と局面別一致による。

候補ごとの重複計算も本段階に含める。
1つの捕獲候補について、捕獲升は生成時、成り判定（`promotion_choice`）、整列キー（`move_order_key`）、および着手の適用で`captured_squares`により繰り返し求められ、その自己時間は3.1%、成り判定は3.7%である。
成れない駒と成駒での成り判定の早期終了と、静止探索の最後の王駒判定への捕獲升の受け渡しは既に実装されているので、それ以外の重複、すなわち`promotion_choice`内の`captured_squares`と`piece_at(mv.from)`の再計算、着手の適用での再計算、および整列の比較ごとの整列キーの再計算を削減対象とする。
`captured_squares`自体も、`Option`配列の`map`と`filter`による経由升と到達升の判定を、駒の有無を直接読む分岐の少ない実装に改める。
主探索の整列キーは、捕獲生成が返した順に捕獲升を1回だけ求めて保持し、整列の比較ごとに再計算しない。
候補ごとの重複計算の見込みは探索時間の2%から3%であり、初期化とグループ構築の見込みと合わせて段階全体を一括で測る。
検証は、`captured_squares`の新旧実装の一致を全規則セットの固定シード局面の全合法手で検査し、残存手順一致と局面別一致で確かめる。
結果は[段階5のbench比較](../measurements/movegen-speedup-2-stage5-bench-depth5.md)にある。

### 段階6　主探索の手生成と探索ノードの固定費

`generate_quiets`は全手を生成してから捕獲を捨てているため、主探索の各ノードで捕獲が2回生成され、`captured_squares`で1手ずつ判別している。
非捕獲手だけを生成する経路を加え、`MovePicker`が捕獲と非捕獲を各1回だけ生成するようにする。
非捕獲手は、到達升が空升である1段階の手と直接の跳び（跳び越す升の駒は取らないので非捕獲）、および元の升へ戻るじっとであり、経由升で駒を取って空升へ進む手と居喰いは捕獲として除く。
生成順は全手生成の順序から捕獲を除いた順序と同一でなければならない。
`generate_moves`が呼出しごとに確保する`base_moves`、`MovePicker::new`がノードごとに確保する2つの`Vec`、置換表の手の合法性検証（`is_legal_move`）で使う2つの作業用`Vec`、および非捕獲手を履歴で整列する`sort_by_cached_key`が確保するキー配列は、探索ワーカーが深さごとに所有するバッファへ移す。
履歴の値は殺し手の検索の後で変わり得るので、現行と同じくQuiets段階への移行時に計算し、`(Reverse(履歴値), 生成順の添字)`の組を整列して現行の安定な整列と同じ順序を得る。
殺し手は各Killer段階で直ちに返し、返した手には印を付けて以後の殺し手検索と非捕獲手の列挙から除き、`position`と`remove`による線形の詰め直しをなくす。
主探索の着手順は変えず、同点と重複を含む手選択器の全出力列を参照と照合する。
見込みは、主探索の全手生成の包含時間7.6ポイントのうち捕獲の再生成と判別に当たる部分、探索時間の2%から4%である。
検証は、非捕獲生成の結果が全手生成から捕獲を除いた列と順序まで一致する契約テストを`src/core/movegen/tests/properties.rs`へ加え、経由升で取って空升へ進む手、相手駒を跳び越す直接の跳び、じっと、および角鷹と飛鷲の2段階移動を含む局面で確かめ、局面別一致で確かめる。

探索ノードの固定費も本段階に含める。
次の変更を1単位にまとめる。

- `make_move_unchecked`は規則P0かつP5なしでは成り権保留を追跡しないので、その場合は成り権保留のためだけに行う`promotion_choice`の呼出しを省く。
- `unmake_move`は`remove_piece`と`put_piece`でzobristを更新した後に`undo.previous_zobrist`で上書きしているので、復元用にハッシュを更新しない変種を使う。
- `zobrist_keys()`の`OnceLock`照会は関数ごとに1回へ巻き上げる。
- `see_prunes`は呼出しごとに372バイトの利得配列を宣言している。コンパイラがゼロ埋めを省いているかを生成コードで確認し、実際に埋めている場合だけ探索ワーカーが所有する作業領域を渡す。
- `see_prunes`の早期終了は、最初の取り返しを求める逆引きを行ってから`g0 ≥ 0 && g1 ≤ 0`を判定している。`g1 = M − C + d`のdは取り返す駒の成り益であり、任意成りでは`max(0, 成り益)`、強制成りでは符号つきの成り益が加わるので、使用中の駒価値表から`d_max = max(0, max(V成 − V不成))`を求めればdの上限になる。到達升が敵陣外でも敵陣内からの捕獲では成れる規則があるため、到達升だけでd = 0とはしない。既存の経由升つきの手と麒麟が獅子を取って成る手の除外を先に行い、その後で`g0 ≥ 0`かつ`M − C + d_max ≤ 0`なら逆引きを行わずに「枝刈りしない」を返す。取り返しがなければ参照値は`g0 ≥ 0`、獅子規則に依存すれば参照は判定不能、取り返しがあれば`min(g0, max(−g1, X)) ≥ 0`なので、いずれも参照実装の判定と一致する。該当する呼出しの割合は段階1の診断で数え、SEEの逆引き（自己時間9.1%）に対する見込みは1%前後である。
- `enter_node`はノード上限がない場合にも`fetch_add`で総ノード数を更新しているので、上限がない場合に限りワーカー内で数えて停止検査の間隔ごとと探索の終了時に反映する。ノード上限がある場合の予約と停止の判定、外部停止とチーム停止の毎ノードの検査は変えない。ノード数を読む側は反映後の値を使い、固定ノード数の探索結果が参照と一致することを検査する。
- 駒位置評価の重みを序中盤と終盤で交互に並べ、1特徴につき1回の読み込みで両方の値を得る。整数和なので評価値は変わらない。
- `search_move`は主探索の着手ごとに対局の履歴キー全体を線形に走査して反復を調べる。`bench`の履歴は1件なので現れないが、対局では手数に比例して増える（[手数に比例する固定費の教訓](../lessons/per-move-overhead-grows-with-game-length.md)）。対局の履歴は探索開始時に単一の`HashSet<u64>`へ変換して所属判定だけに使い、探索経路の`path_keys`は現行の`Vec`と追加位置を保つ（null moveは経路にキーを追加しないので、手番の偶奇で分ける方式は経路には適用できない）。300手の履歴とnull moveを含む探索で、反復判定と固定深さのノード数、最善手、探索値を参照と照合し、経過で効果を測る。

各項目の見込みは1%前後で交互測定の幅に近いため、単独では採否を判定できず、1単位にまとめて合計で探索時間の3%から5%を見込む。
作業領域や集合など状態を追加する項目は、対象処理の実行頻度と費用を確認してから着手し、一括測定で採用候補になった後にその項目だけを外した比較を行い、効果を確認できない状態は残さない。
検証は、着手の復元が観測可能な全成分を戻すテスト、累算値と全再計算の一致テスト、SEEの参照実装との一致、ノード上限のテスト、固定ノード数の探索結果の一致、および局面別一致による。
結果は[段階6のbench比較](../measurements/movegen-speedup-2-stage6-bench-depth5.md)にあり、SEEの作業領域、ノード数の一括反映、および対局履歴の`HashSet`は、その項目だけを外した比較（履歴は300手の履歴を与えた探索の経過を含む）で効果を確認できず外した。

### 段階7　静止探索における静的評価の先行打ち切り（探索木を変える）

静止探索は現在、置換表を照合してから静的評価を求め、静的評価が探索上限β以上なら下限として保存して返す。
これを、静的評価を先に求め、β以上なら置換表を照合も保存もせずに返す順序へ改める。
静的評価は盤面走査を伴わない定数時間の補間で求まるので、この順序は静止探索ノードの28.1%でDRAM待ちを伴う照合と保存を省く。
探索木への影響は3つある。
置換表で打ち切っていたノードの42%は静的評価でも打ち切れるので、そこでは返す値が置換表の値から静的評価へ変わる。
静止探索の照合は深さを問わず既存の項目を受け入れるので、主探索が保存した項目の値と最善手をそのノードで参照しなくなる。
保存を省いた分だけ置換表の置換と既存の最善手の保持が変わり、主探索が浅い項目の最善手を着手順と深さ短縮の判断に使う経路にも影響する。
`enter_node`、主変化の消去、`MAX_PLY`の判定は現行の順序を保ち、打ち切らないノードでは照合した置換表の手を候補生成へ渡す。
試作では総ノード数が1.8%増え、固定深さの経過時間は約2%縮んだ（[起案時の診断](../measurements/movegen-speedup-2-diagnostics-depth5.md)）。
着手時には試作差分、比較条件、局面別出力、および終わり方別の件数を測定記録に残す。
事前選別の条件は固定深さの経過時間が親より短いことであり、採否はSTC、続いてLTCで決める。
段階7から段階9の事前選別の結果は[事前選別の記録](../measurements/movegen-speedup-2-stage7-9-prescreen-depth5.md)にある。

### 段階8　静止探索の獅子候補の絞り込み（探索木を変える）

静止探索の特殊駒の候補は、獅子が隣接する相手駒を取ってから空升へ進む手を、経由升ごとに最大7通り（元の升へ戻る居喰いを除く）生成している。
これらは同じ駒を取る手の到達升違いであり、獅子のある局面で候補数を数倍にする。
静止探索に限り、獅子の手のうち経由升に相手駒があり、着手前の到達升が空升で、到達升が移動元と異なる手だけを候補から外す。
居喰い、2枚取り、1升で停止する捕獲、および経由升を持たない直接の跳びによる捕獲は残す。
角鷹と飛鷲の2段階移動にも同じ形の手があるが、本段階の対象外とする。
候補生成と置換表の手の受入判定（`is_legal_capture`）で同じ除外条件を使う。
公開の生成と主探索の候補は変えない。
この除外には戦術上の見落としの危険がある。
移動元と経由升が攻撃されていて、駒を取ってから安全な到達升へ移る手だけが損失を避けられる局面では、静止探索がその手を見ないため評価が悪化し得る。
試作では総ノード数が1.2%減り、固定深さの経過時間は約4%縮んだが、局面によってはノードが増える（1局面で+54%）ので（[起案時の診断](../measurements/movegen-speedup-2-diagnostics-depth5.md)）、棋力への影響はSTCとLTCで判定する。
本段階を採用した場合、段階5で導入した獅子候補の圧縮は対象が減るので、有効性を測り直して効果がなければ取り除く。

### 段階9　捕獲対象が空のノードでの置換表アクセスの省略（探索木を変える）

第1期の[処理件数診断](../research/movegen-speedup-ideas.md)では、静止探索で候補生成へ進むノードの30.0%で全捕獲が入口の閾値で捨てられていた。
この値は段階生成の前の版で測った旧診断であり、仮説の根拠に限る。
これらのノードでも現在は置換表の照合と保存を行っている。
現行の対象升の集合は相手の王駒の升を常に含むので、対象升が空かどうかでは判定できない。
入口の枝刈りの後に残る合法な捕獲がないことを、2枚取りの合計価値と最後の王駒を取る例外を含めて判定する処理を置換表の照合より前へ切り出し、該当するノードでは照合と保存を省いて静的評価を返す。
保存の省略は返す値を変えないが、通常の出口では入口のα以下なら上限、それ以外なら正確な値として保存していた結果の再利用を失う。
照合の省略による返す値の変化は、判定処理の追加費用とともに固定深さの経過時間で測る。
段階5と段階7の採否が確定した後、直前の採用版で省略条件の成立率を段階1の診断で測り直し、固定深さの経過時間で事前選別してからSTCとLTCで判定する。
対象の判定は段階5の初期化と同じ相手駒の走査を使うので、段階5の後に着手する。

### 段階10　最終測定

段階6までの採用版と新しい基準（第1期の採用版）のSPRTをSTC、続いてLTCで行い、`decision: H1`かつエンジン異常、時間切れ、拒否着手が0件なら採用する。
第1期の採用版を基準にするのは、第1期の最終SPRTがPGOを含む構成で行われ、PGOを外した採用版の自己対局が未実施だからでもある。
段階7から段階9の採否が確定した後、最終の採用版と第1期の採用版の固定200ペアのEloを進捗記録として測る。
併せて、段階1と同じ方法で残存負荷のプロファイルと件数を測り直し、記録する。

## 実装フェーズ

1. 段階1を完了し、基準の更新、診断の集計、および`codegen-units = 1`の採否を確定する。
2. 段階2と段階3を順に判定する。段階3は段階2の採用後に測り直してから着手する。
3. 段階4、段階5、段階6を順に判定する。
4. 段階6までの採用版をまとめてSTC、続いてLTCにかける（段階10の前半）。
5. 段階7、段階8、段階9の順に固定深さの経過時間で事前選別し、通過した段階を1コミットに固定して、段階6までの採用版とのSTC、続いてLTCにかける。採用後は段階5で導入した獅子候補の圧縮の有効性を再評価する。
6. 最終の採用版の固定200ペアのEloと残存負荷を測定記録へ残す（段階10の後半）。

各フェーズの完了条件は、該当段階の採否が測定記録とともに確定していることである。
`bench`の速度測定はSPRTと同時に行えないので、測定機を占有する順序で計画する。

## 検証

実装した段階では次を実行する。

```console
cargo fmt --check
cargo clippy --release --all-targets
cargo test --release
scripts/bench_compare.py --reference <照合参照コミット> --baseline <第1期の採用版> --parent <直前の採用版> --depth 5 --repetitions 3 --threads 1
target/release/perft 3
```

速度測定中は他のCPU負荷を止め、候補と親を交互に3回以上測って中央値を比べ、親の中央値の幅を増分の分解能として記録する。
診断ビルドとフレームポインタつきの性能測定は別のターゲットディレクトリで行い、その経過時間をNPS比較へ混ぜない。
段階6までの局面別の一致は、照合参照コミットの`bench`の局面別出力（ノード数、最善手、探索値）と候補の出力を全行で比較する。
段階7から段階9では局面別一致を求めず、`bench_compare.py`に固定深さの経過時間とノード数の親比を報告する出力を加えて事前選別に使い、採否はSPRTの記録で示す。
段階2と段階3では、対象升が空、対象升が1升、対象升が相手の全駒、特殊手だけが残る局面、および閾値の両側の局面で残存手順の一致を検査する。
段階4では、長さ12の全起点と両方向、語境界をまたぐ利き線、遮蔽なし、複数遮蔽、仮想占有を逐次歩行と照合する。
段階5では、`captured_squares`の新旧実装の一致を全規則セットの固定シード局面の全合法手で検査する。
段階6では、非捕獲生成と全手生成の差集合の一致を全規則セットで検査する。
段階8では、静止探索の候補から外す手の条件（経由升に相手駒があり、着手前の到達升が空升で、到達升が移動元と異なる）を単体テストで固定し、探索専用生成の残存手順の参照列にも同じ除外を適用して一致を検証し、公開生成が変わらないことを`perft`と生成契約で確かめる。
SPRTは測定名`movegen-speedup-2-<段階名>-stc`および`-ltc`で`docs/measurements/`へ記録する。

## 完了条件

段階6までの採用版が照合参照コミットと局面別のノード数、最善手、探索値で一致し、NPS中央値が新しい基準の1.15倍以上である。
1.3倍以上を目標とし、未達なら基準比、残りの時間削減量、残存負荷を同じ測定条件で記録する。
段階6までの採用版と新しい基準のSPRTがSTCの振分けを通過し、LTCで`H1`かつエンジン異常、時間切れ、拒否着手が0件である。
段階7から段階9について、事前選別の結果と、通過した段階を1コミットに固定した構成のSTCとLTCの判定、または着手しない理由が記録されており、採用した構成はLTCで`H1`かつ異常0件である。
段階1から段階9までの採否が、採用しない段階の理由と測定値を含めて記録されている。
`perft`、全規則セットの公開生成契約、探索専用生成の残存手順（段階8を採用した場合は除外条件を適用した参照列）、利き逆引き、およびSEEの枝刈り判断の検証が通過している。
採用しなかった方式、互換のために残す経路、使われない表と状態、および計測のためだけに本番の経路へ入れた処理が残っていない。

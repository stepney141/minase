# 合法手生成、利き計算、およびNNUEの後段の高速化（第3期）の設計書

## 先に読む要約

本マイルストーンは、探索の結果を変えずに探索を速くして、持ち時間の対局では同じ時間でより深く読めるようにし、NNUE（着手ごとに差分で更新できる小さなニューラルネットの評価関数）の学習データである教師を、1局面あたり固定のノード数（探索が着手を適用した回数）の自己対局で作る費用を下げる。
速さは、固定の15局面を深さ16まで探索する負荷（独自コマンド`bench`）と、教師を作る自己対局2局の負荷のCPUサイクル数で比べ、変更前のサイクル数を変更後のサイクル数で割った値を速度比と呼ぶ。採用の条件として、局面別のノード数、最善手、評価値、および教師のファイルが変更の前後で変わらないことを求める。
段階1は、NNUEの後段（第1層の出力から評価値を計算する小さな全結合層）の計算を、Rustの`unsafe`（コンパイラの安全性の検査を外す記法）を使わずに、コンパイラが自動でSIMD命令（1命令で複数の値を同時に計算する命令）を出せる形へ書き直す変更であり、試しに実装した版（[試作](../measurements/adhoc/nnue-dense-safe-vectorization-20261127.md)）の`bench`の速度比は1.104倍だった。
段階2は、ある升へ利きが届く駒を求める利きの逆引きで、升の駒を表す1バイトの値（駒コード）から走りの方向や駒種を求める処理を256要素の表の表引きにする変更であり、段階3は、駒コードから駒種、駒状態、および駒価値を求める処理を同じく表引きにする変更である。段階2と、段階3のうち駒種の表引きを1つの版に入れた[試作](../measurements/movegen-speedup-3/movegen-speedup-3-prototypes.md)の速度比は、`bench`で1.046倍、教師生成で1.053倍であり、段階2だけの試作の速度比は約1.026倍だった。
段階4は、静止探索（駒を取る手だけを読み進める探索の末端）がもともと候補から除いている獅子の手を生成の時点で省く変更であり、段階5は、それらの後に残る時間の内訳を調べ、省ける処理が見つかった場合だけ変更を追加する診断である。
各変更は1コミットずつ、変更前と変更後のバイナリを1組ずつ順序を入れ替えて繰り返し実行し、`bench`で速くなったことと、教師生成で0.5%を超えて遅くならないことが、95%信頼区間で確かめられた場合だけ採用する。
採用した変更をまとめた版は、両方の負荷で速度比の95%信頼区間の下端が1.02倍以上であれば、持ち時間を設けた自己対局で強さを比べる採否の測定（[SPRTの手引き](../guides/sprt.md)が定める逐次確率比検定による段階ゲート）にかけ、採用と判定されればmasterへ統合する。
目標の速度比1.15倍は、段階1の試作と、段階2と段階3の一部の試作の速度比の積から置いた値であり、2つを組み合わせて測ってはいない。下限の1.02倍は、段階2だけの試作の約1.026倍より低く置いた値であり、目標に届かなくても下限と段階ゲートを満たせば統合する。
探索木（探索が訪れる局面の集合）を変える静止探索の調整と、置換表（探索済み局面の結果を保存する表）の変更は、本書の対象にしない。

## 目的

現行のminaseは、NNUEを評価関数とし、[第2期](archived/movegen-speedup-2.md)と[教師生成の高速化](archived/teacher-generation-speedup.md)の変更を含んでいる。
本マイルストーンは、その現行の探索を対象に、探索の結果を変えない変更だけで探索の時間を減らす。
探索が速くなると、持ち時間の対局では読みが深くなり、1局面を固定のノード数で探索する教師生成では、同じ教師を作る費用が下がる。

速さは、次の2つの負荷のサイクル数で測る。
1つ目は、固定の15局面を固定の深さで探索する独自コマンド`bench`の深さ16であり、対局中の探索の代わりとする。以下では**bench深さ16**と呼ぶ。`bench`は、将棋エンジンの通信プロトコルUSIでエンジンへ送る、minase独自のコマンドである。
2つ目は、自己対局の各局面を2万ノードで探索する教師生成の2局であり、以下では**教師生成2局**と呼ぶ。
2026年11月27日のmasterで測った値は、bench深さ16が3,371,474ノードで約224億〜241億サイクル、教師生成2局が16,400,000ノードで約1,027億〜1,438億サイクルである（[記録](../measurements/adhoc/nnue-dense-safe-vectorization-20261127.md)）。
この測定の間は、同じ機械でlishogiのBotのエンジンが探索しており、値の揺れが大きい（「探索木を変えない段階の採否」の節）。
サイクル数はプロセスの全体を数えるので、bench深さ16の値には、ネット（NNUEの重みのファイル）の読み込みや、局面ごとの履歴表（探索中に着手の成績を記録する表）の消去のように、探索の外で行う処理も含まれる。[再診断](../measurements/movegen-speedup-3/movegen-speedup-3-rediagnosis.md)のプロファイルでは、履歴表の消去がbench深さ16の標本の6.0%を占めた。探索の外の処理の費用が変更の前後で同じであれば、その分だけ、bench深さ16の変化率は探索だけの変化率より小さく出る。
基準の値は、ブランチを切った時点のmasterで、測定機に他の負荷がない状態で測り直す。

目標は、どちらの負荷でも**速度比**（基準のサイクル数を採用版のサイクル数で割った値）が1.15倍以上になることである。最低受入条件は、どちらの負荷でも速度比の両側95%信頼区間の下端が1.02倍以上になることである。速度比とその信頼区間は、組ごとのサイクル数の比の対数の平均から求める（「探索木を変えない段階の採否」の節）。
サイクル数の減少率をxとすると、速度比は1÷(1−x)である。
1.15倍は、bench深さ16での段階1の試作の速度比1.104倍と、段階2と段階3の一部に当たる試作の速度比1.046倍の積（約1.155倍）から置いた。
2つの試作は別の関数を書き換え、それぞれ別の時点のmasterで測ったものであり、組み合わせては測っていない。同じ基準から省いたサイクル数が足し合わさるとすれば、速度比の積は近似になる。
教師生成2局での段階1の試作は信頼区間が広い（1.065〜1.256倍）ので目標の算出に使わず、両方の負荷に同じ目標を置いた。
1.02倍は、段階2だけに当たる試作の速度比（約1.026倍）より低く置いた値であり、段階2だけが採用された場合にも統合する価値があると判断する下限である。段階4だけの見込み（0.4%から0.5%の減少）ではこの下限に届かないので、段階4だけが採用された場合は統合しない。
どちらも予備の測定に基づく方針の値であり、確かめられた下限ではない。

## 適用範囲

変更するコードは次のとおりである。

- `crates/minase/src/eval/nnue/network/layer_stack.rs`のNNUEの後段の計算（`LayerStackNetwork::dense`）と、その重みを保持する`LayerStackNetwork`を書き換え、`crates/minase/src/eval/nnue/network/mod.rs`の要素積の関数`pair`を16ビットの値を返す形に変える。
- `crates/minase-core/src/movegen/control.rs`の利きの逆引き（`ordinary_attackers_to`と`sliding_attackers_to`）を書き換える。
- `crates/minase-core/src/attacks/tables.rs`の前計算表に、駒コードから引く表を加える。
- `crates/minase-core/src/piece/code.rs`の駒コードの復号（`PieceCode::kind`）を書き換え、駒コードを表の添字として読むアクセサを加える。
- `crates/minase-core/src/position/mod.rs`に、升の駒コードを空升も含めて返すクレート内のアクセサを加える。
- `crates/minase/src/eval/features.rs`の駒状態（`piece_state`）と、`crates/minase/src/eval/piece_values.rs`の駒価値（`piece_value`）を表引きにする。
- `crates/minase-core/src/movegen/lion.rs`と`crates/minase-core/src/movegen/search_captures.rs`の探索専用の獅子の捕獲の生成、および`crates/minase/src/search/alphabeta/quiesce.rs`の静止探索の初期化を書き換える。

本書で使う語を次のとおり定める。
中将棋の駒の動きと、`L0`や`P1`のような規則コードの意味は、[規則の文書](../rules/chu-shogi.md)にある。
NNUEの構造と量子化の式は、[NNUEの評価関数の手引き](../guides/evaluation-nnue.md)にある。

- **後段**：A型のNNUE（王の位置を使わない入力特徴集合のネット）で、第1層の累算値（16ビット整数）から評価値を計算する部分。NNUEは手番側と相手側の2つの視点で累算値を持つ。第1層の幅（1つの視点の累算値の成分の数）をHとすると、各視点の累算値の前半H/2個と後半H/2個を0から127へ切り詰めて成分ごとに掛け、7ビット右シフトした要素積を視点ごとにH/2個、両視点で合わせてH個作る。後段は、それを入力とする16出力の層L1、L1の15個の出力をそれぞれ2つの活性化関数に通した30個を入力とする32出力の層L2、および1出力の層からなり、L1の残りの1個の出力（以下、skip）は最後の出力へそのまま足す。L1とL2の重みは8ビット整数である。探索の測定で標準として使うネットでは、Hは256である。
- **自動ベクトル化**：ソースに個別の命令を書かずに、コンパイラ（rustcが使うLLVM）がループや配列の計算をSIMD命令へ変換すること。`unsafe`を使わずにSIMD命令を得る、現行の方針で唯一の手段である。
- **駒コード**：升にある駒を表す1バイトの値（`PieceCode`）。対局者、成り、および駒種の番号を詰めた値であり、空升と盤外（番兵）にも専用の値がある。公開の構築子から作れるのは、両対局者の成っていない駒と成駒、空升、および番兵の値だけである。以下では、これらを**構築できる駒コード**と呼ぶ。
- **利きの逆引き**：ある升へ利きが届く駒を、その升の側から求める処理（`Position::attackers_to_by`）。静的交換評価（SEE、到達升での駒の取り合いを見積もる評価）、王手判定、王駒への攻撃判定、対局の終局を裁定する審判層、および詰みの探索が使う。
- **測定単位**：1コミットにまとめて採否を判定する変更の単位。
- **親**と**基準**：基準は、ブランチを切った時点のmasterのコミットである。親は、ある測定単位を判定するときの直前のコミットであり、最初の測定単位では基準、以降は直前までに採用した測定単位を含むコミット（採用版）である。
- **採用版**：採用した測定単位をすべて含む、ブランチの先頭のコミット。
- **対比較**：候補と親を1回ずつ実行した組を、組ごとに実行の順序を入れ替えながら繰り返し、組ごとの差を集める測り方。測定機の状態の変化が、同じ組の両方に同じように掛かるので、差の揺れが小さくなる。
- **段階ゲート**：[SPRTの手引き](../guides/sprt.md)が定める、自己対局による採否の測定。短い持ち時間の測定（STC）で候補を選別し、長い持ち時間の測定（LTC）で採否を判定する。

次の事項は対象外とする。

- 探索木を変える変更。枝刈りの条件、着手の順序、評価値の計算式、および置換表の使い方は変えない。[静止探索の時間の内訳の記録](../measurements/adhoc/qsearch-cost-breakdown-20261124.md)が挙げた、静止探索で枝刈りを免除する対象から成る手と王手になる手を外す候補もここに含まれ、扱うなら段階ゲートで判定する別の設計書として起案する。
- 公開の全手生成と捕獲生成の着手集合、順序、および合法性。
- 置換表。照会の時間のほぼすべては記録の読み出しの待ちである。対象にしない理由は「設計判断」の節に書く。
- HalfKP_vm（王の位置ごとに第1層の別の行を引く入力特徴集合）のネットが使う後段`SimpleNetwork::out`。理由と、扱う時期は「設計判断」の節に書く。
- NNUEの第1層の累算値の差分更新。機械語では既に256ビットのSIMD命令へベクトル化されている。対象にしない理由は「設計判断」の節に書く。
- 測定機以外のCPUと命令の集合での効果。`cargo install`で利用者がビルドするバイナリは、`.cargo/config.toml`がcrates.ioのパッケージに含まれないので、`RUSTFLAGS`を与えなければ既定のx86-64の命令の集合でビルドされ、CIも`-C target-cpu=x86-64`でビルドする。本書は`-C target-cpu=native`の測定機だけで速さを測る。
- Rustの`unsafe`、PGO（実行頻度をコンパイラへ渡す最適化）、および置換表の先読み。いずれも既存の設計判断の記録（ADR）が使わないと決めている（[unsafe](../adr/allow-unsafe-only-in-the-trainer-gpu-code.md)、[PGO](../adr/do-not-build-with-pgo.md)、[先読み](../adr/do-not-prefetch-transposition-table-entries.md)）。unsafeのADRが禁じるのはエンジンとライブラリのクレート自身の`unsafe`だが、本書は、内部やマクロの展開で`unsafe`を使うSIMDのクレートに依存する方式も採らない。

## 依存関係

着手を妨げる未完了の計画はない。
完了済みの[ネットの外部ファイル化](archived/nnue-external-network-file.md)により、`bench`の前には、USIのオプション`RuleSet`（規則セット）と`EvalFile`（ネットのファイル）を設定して`isready`を送る。
ネットは、[NNUEの評価関数の手引き](../guides/evaluation-nnue.md)が探索の測定の標準とする、第3世代のA型のネット（SHA-256は`415020879b9086772acb168397dfa406a1432350c151f87b635b3f271153d1a9`）を使う。
`bench`の規則セットは日本中将棋連盟の規則に基づく`JCSA`に、教師生成の規則セットはオンライン対局サイトlishogiの実装に近い`lishogi`に固定されている。
探索の係数は、第3世代のネットに合わせて[調整し直した値](../measurements/adhoc/nnue-gen3-search-retune.md)が現行のmasterに入っており、本書はこれを変えない。

利きの逆引きの契約は[棋力向上段階3](archived/strength-stage3.md)が、探索専用の捕獲生成の契約は[捕獲生成のADR](../adr/generate-qsearch-captures-by-value-group-per-piece.md)が、静止探索の候補から除く獅子の手の定義は[静止探索の入口のADR](../adr/probe-the-tt-before-the-qsearch-stand-pat-and-blend-fail-highs-toward-beta.md)が定める。
NNUEの後段の整数の計算式は、[A型をLayerStackとPSQT（駒と升の組ごとの点数の表）で組むADR](../adr/compose-p-as-a-tatara-layerstack-with-a-psqt-and-halfkp-vm-as-a-simple-network.md)と`layer_stack.rs`のdocコメント（コードに付ける仕様の説明）が定める。
本マイルストーンはこれらの契約と計算式を変えない。

教師を生成する計画は、生成に使うコミットを計画ごとに固定する。
起案中の[判定と除外の処理を外した教師の比較](nnue-teacher-without-adjudication.md)も生成用のコミットを固定するので、本書の変更がmasterへ入っても、その計画の速さと結果は変わらない。
本書の高速化が教師生成に効くのは、統合の後に生成のコミットを決める計画からである。

速度の測定は、[測定機の確認の教訓](../lessons/check-running-measurements-before-cpu-load.md)と[性能コアへの固定の教訓](../lessons/pin-bench-to-performance-core.md)に従う。
ビルド設定は変えないので、[ビルド設定の教訓](../lessons/do-not-mix-builds-across-cargo-config-changes.md)が扱う混在は起きない。
自動ベクトル化を狙う変更は、[自動ベクトル化の教訓](../lessons/check-autovectorization-before-explicit-simd.md)に従い、機械語の命令名ごとの出現数を変更の前後で比べて記録する。

## 設計判断

### 対象と方式の選択

再診断では、bench深さ16と教師生成2局について、関数別の時間の内訳と、省ける処理の件数を取り直した。
試作では、その中の候補を実際に実装して、探索の結果の一致とサイクル数を測った。
試作は6つあり、以下では次の名前で呼ぶ。
**試作A**は、対局者と方向ごとの走り駒の集合を局面に持たせる。
**試作B**は、利きの逆引きの走りの判定を駒コードの表引きにする。
**試作C**は、試作Bに加えて、利きの逆引きの固定利きの判定も駒コードの表引きにする。段階2に当たる。
**試作D**は、試作Cに加えて、駒コードから駒種を返す`PieceCode::kind`を表引きにする。段階3の1つ目の測定単位に当たる。
**試作E**は、NNUEの後段を`unsafe`なしで自動ベクトル化が効く形へ書き直す。段階1に当たる。
**試作F**は、比較の上限の目安として、後段を`unsafe`の組み込み関数でAVX-VNNI命令（`vpdpbusd`、8ビット整数4組の積を32ビットの和へ足す命令）を使って書いた版であり、方針に反するので採否の候補にしない。
試作AからDは[movegen-speedup-3の試作の記録](../measurements/movegen-speedup-3/movegen-speedup-3-prototypes.md)に、試作EとFは[後段の試作の記録](../measurements/adhoc/nnue-dense-safe-vectorization-20261127.md)にある。

下表は、これらの測定から決めた方式と、棄却した代案である。
数値を2つ並べた箇所は、bench深さ16、教師生成2局の順である。割合は、断りがなければ、その負荷を`perf`で採取したプロセス全体のサイクルの標本に対する割合であり、本書ではこれを探索時間に対する割合と呼ぶ。

### 探索木を変えない段階の採否

測定単位の採否は、探索の結果の一致とサイクル数の対比較で決める。
毎秒ノード数の交互測定は使わない。
試作Aの毎秒ノード数の増分は0.95%で、基準を5回測った値の幅（最大と最小の差を中央値で割った値）の1.14%に収まり、[交互測定の教訓](../lessons/alternate-speed-rounds-against-parent.md)の「増分が親の幅を超える段階だけを残す」という規則では判定できなかった。
命令数も採否の条件にしない。
命令数は実行ごとの差が100万分の1以下で再現するが、試作Aでは命令数の減少が0.25%と0.48%だったのに対してサイクル数の減少は0.95%と1.12%であり、時間の変化を表していなかった。
命令数、分岐予測ミスの回数、および自動ベクトル化を狙う段階での命令名ごとの出現数は、原因を調べる材料として測定記録に残す。

対比較の1組からは、候補のサイクル数を親のサイクル数で割った値の自然対数（以下、対数比）を取る。
対数を使うのは、比の向きを逆にしても平均の絶対値が変わらず、段階ごとの判定と最終の速度比を同じ量で扱えるからである。
組ごとの対数比の平均と、t分布による信頼区間を求め、速度比は、対数比の平均の符号を変えて指数を取った値とする。

測定単位を採用する条件は、次の3つをすべて満たすことである。
1つでも満たさない測定単位は採用せず、同じ測定単位を測り直して判定を変えることはしない。

1. 探索の結果が親と一致する。確かめ方は「検証」の節に書く。
2. bench深さ16の対比較で、対数比の平均の両側95%信頼区間が、上端まで0より小さい。
3. 教師生成2局の対比較で、対数比の平均の片側95%信頼区間の上端が、0.5%の退行に当たる値（1.005の自然対数）以下である。

bench深さ16を改善の判定に、教師生成2局を退行の見張りに使うのは、教師生成2局の1回の揺れがbench深さ16より大きく、小さな改善を教師生成2局の区間で確かめるには組数が多く要るからである。
教師生成2局の条件は測定単位ごとに0.5%までの退行を見逃し得るので、退行の積み重ねは、最終測定で採用版を基準と直接比べて確かめる。
測定単位の採用は最終測定までの仮の採用であり、統合するかどうかは最終測定と段階ゲートで決まる。

組数は、準備のフェーズで定める。
まず、同じバイナリを候補と親の両方に使う対比較を、両方の負荷で20組ずつ行い、組ごとの対数比の標準偏差sを求める。この対比較は、変更がないときの揺れを測るものである。
次に、組数をn、自由度n−1のt分布の臨界値をtとして、区間の端から平均までの距離`t × s ÷ √n`が、bench深さ16の両側の区間で0.1%の変化に当たる値（1.001の自然対数）以下、教師生成2局の片側の区間で0.3%の変化に当たる値（1.003の自然対数）以下になる、最小の偶数のnを求める。偶数にするのは、候補を先に実行する組と親を先に実行する組を同数にするためである。
上限は、bench深さ16が40組、教師生成2局が60組とする。上限でも届かない場合は、上限の組数で測る。その場合は区間が広くなって採用されにくくなるが、組の間の独立を仮定した1回の判定の名目の水準は変わらない。
最終測定にも同じ組数を使う。
2026年11月27日の試作Eの対比較では、組ごとの対数比の標準偏差がbench深さ16で0.0103、教師生成2局で0.1154だった。この測定は、lishogiのBotのエンジンが同じ機械で探索している間に行ったものであり、教師生成2局の値には、基準のサイクル数が他の組より約25%から30%多く計測された2組が含まれる。
この揺れのまま上限の組数で測ると、区間の端から平均までの距離は、bench深さ16の両側の区間で約0.33%、教師生成2局の片側の区間で約2.5%になる。そうなると、bench深さ16で0.4%から0.5%しか減らない段階4は採用の境界の近くにあり、教師生成2局で速くならない測定単位は0.5%の退行の条件を満たせない。
そのため、測定の間はBotのコンテナを止める（「検証」の節）。Botの負荷のない状態の揺れは測っていないので、組数の見込みは立てない。
組数と判定の規則は測定単位を測る前に固定し、結果を見てから組数を増やさない。
試作の値は段階を選ぶための予備の測定であり、採否には使わない。

### 持ち時間の対局による確認

採用版は、最終測定で最低受入条件を満たした場合に限り、基準との段階ゲートにかける。
段階ゲートは、[SPRTの手引き](../guides/sprt.md)の標準のSTCとLTCであり、改善が0 Eloという仮説と10 Eloという仮説を比べる検定である。STCで手引きの規則によりLTCへ進むと判定された場合に限りLTCを行う。
最終測定で最低受入条件を満たさなかった場合と、STCでLTCへ進まないと判定された場合は、次の測定を行わず、その理由を測定記録に残す。

段階ゲートの結果による統合の判断は、手引きの採用の規則（LTCの`decision: H1`）ではなく、明確な退行がないことだけを条件とする（2026年11月27日の利用者の決定）。
明確な退行とは、行った段階ゲートの測定のいずれかで、Eloの両側95%信頼区間の上端が0より小さいこと、または時間切れ、エンジン異常、もしくは拒否着手が1件でも出たことをいう。
利用者は、合法手生成と探索が速くなることを、棋力の向上が検定で確かめられない場合でも採る価値があると判断した。本書の変更は固定の仕事量での探索の結果を変えないので、持ち時間の対局での強さを下げる経路は、時間の使い方を通じたものに限られる。
[開発の規約](../../CONTRIBUTING.md)は、棋力に影響し得る変更の採否を自己対局で判定すると定めており、探索の結果を変えない変更でも、同じ時間で探索できる量が増えることを通じて強さに影響するので、規約どおり段階ゲートを行う。

段階ゲートの代わりに、固定の200ペアの対局で異常がないことだけを確かめる案は採らない。
この案の利点は対局の費用が小さいことだが、それは改善が十数Elo以下と見込まれる場合の利点である。
速さとEloの関係は確かめていないが、[持ち時間2倍の感度測定](../measurements/evaluation-gen1/sensitivity-time2x.md)の「持ち時間2倍あたり約216 Elo」を、時間の比の2を底とする対数に比例すると仮定して当てはめると、目標の1.15倍は約44 Elo、最低受入条件の1.02倍は約6 Eloに当たる。
同記録は評価関数がNNUEへ替わる前の値であり、線形性も確かめていないので、この換算は採否に使わない。
手引きの近似では、1回の検定の判定までの期待ペア数は、真の差が40 Eloなら約410ペア、5 Eloなら約4,200ペアである。真の差が目標に近ければSTCとLTCはそれぞれ数百ペアで済み得るが、下限に近ければそれぞれ数千ペアを要する。

探索の結果の一致の検査で確かめられないことも明記する。
固定の仕事量での探索の結果の一致は、持ち時間のもとで完了する反復深化の回数、指す手、および勝敗の一致を意味しない。
複数ワーカーの探索は、置換表の共有とノード数の割り当ての順序で結果が変わり得るので、結果の一致を確かめる対象にしていない。
段階ゲートの測定で、時間切れ、エンジン異常、または拒否着手（審判層が合法とした相手の着手を、エンジンが受け付けなかった反則）が1件でも出た場合は、手引きに従って測定を停止して原因を調べる。

探索の結果が親と一致しない変更は、本マイルストーンから外す。

## 各段階

段階1から段階4は、1つ以上の測定単位からなる。
見込みには、試作の実測がある場合はその値を書き、ない場合は未測定と書く。
試作AからDと試作Eは、それぞれ別の時点のmasterで測ったものであり、ブランチを切った時点のmasterで測り直すと変わり得る。

### 段階1　NNUEの後段の自動ベクトル化

`LayerStackNetwork::dense`を、LLVMの自動ベクトル化が効く形に書き直す。
試作Eに当たり、現行のmasterとの対比較で、速度比はbench深さ16で1.104倍（95%信頼区間1.099〜1.110）、教師生成2局で1.156倍（同1.065〜1.256）だった。
命令数は12%から13%減り、15局面の局面別の出力と教師のファイルは一致した。
試作Eは要素積、L1、およびL2と出力層の3か所をまとめて書き換えたものであり、本段階はこれを2つの測定単位に分けて、順に判定する。
速度比1.104倍は試作E全体の値であり、2つの単位それぞれの効果は測っていない。

現行の`dense`は、要素積の一部を添字の範囲検査つきのスカラーのループで計算し（範囲検査の分岐がループのベクトル化を妨げる）、L1では8ビットの重みと入力を32ビットへ広げてから8個ずつ掛けており、L2も出力ごとに30個の積を足している。

1つ目の測定単位は、要素積とL1の書き換えである。
要素積は、各視点の累算値を前半と後半に分けて反復子で対にし、0から127へ切り詰めた2つの値の積を16ビット整数のまま求めて7ビット右シフトし、16ビットの配列に書く。積の上限は127×127＝16,129なので、16ビットに収まる。添字の計算をなくすことで範囲検査が消え、標準のネットを測ったビルドでは全成分が256ビット幅の16ビットの積の命令`vpmullw`へベクトル化された。
要素積の式は関数`pair`の1か所に保ち、`pair`を16ビットの値を返す形に変えて反復子の中から呼ぶ。
L1は、ネットを読み込むときに8ビットの重みを16ビットへ広げた行優先の複製を作り、16ビットの入力との積を32ビットで足す。16ビットどうしの積和の命令`vpmaddwd`へベクトル化される。

2つ目の測定単位は、L2と出力層の書き換えである。
ネットを読み込むときに、L2の重みを入力ごとに出力を並べた配列（入力30×出力32）へ組み替えた16ビットの複製を作り、入力2つ分の積の和を16ビットのまま求めてから、32出力の32ビットの和へ加える。
続けて、L2の出力に活性化関数を通した値と出力層の重みの積和を、同じ反復で計算する。
L2の入力は、L1の出力に活性化関数`activation`と`square_activation`を通した0から127の値であり、重みは−128から127なので、2つの積の和は−32,512から32,258の範囲にあり、16ビットに収まる。
1つ目の単位が採用されなかった場合は、元のL1のままの親に対して判定する。
2つの単位がどちらも単独では採用されなかった場合に限り、試作Eと同じ組み合わせを、同じ親に対する1つの測定単位として1回だけ判定する。

どちらの単位でも、計算する値は現行と同じであり、整数の結果はすべての入力で一致する。
値域は型と定数が保証する。累算値は16ビット整数で、切り詰めた後は0から127であり、重みは読み込みの時点で8ビット整数である。したがって、読み込み時の検査は加えない。また、要素積とL2の積の和が16ビットに収まることは、活性化の上限127、8ビット整数の最小値−128、および16ビットの中で足す積の数2から、コンパイル時の表明（`const`の`assert!`）で固定する。
重みの複製の大きさは、第1層の幅をHとすると、L1が32Hバイト（標準のネットのH＝256で8,192バイト、上限のH＝1,024で32,768バイト）、L2が1,920バイトである。ネットは探索スレッドの間で共有されるので、探索の深さやスレッドの数では増えない。
元の8ビットの配列は、ネットのファイルの表現の正本として残す。ネットの書き出し（`encode`）が使い、重みの検査と読み書きの処理はHalfKP_vmの`SimpleNetwork`と共有しているからである。
複製は非公開の派生の配列とし、`LayerStackNetwork::new`の1か所で、既存の検査（重みの値域と、左右に鏡映した特徴の対で重みが共有されていることの検査）を通った後の値から作る。
`affine`はHalfKP_vmの後段が、`activation`は両方の構造の後段が、`square_activation`はA型の後段が使うので残す。

後段の計算は、両視点の累算値の行2本を受け取る関数として切り出し、`dense`はその関数を呼ぶだけにする。
試験用の固定ネットは第1層の幅が32なので、この切り出しによって、ネット全体を作らずに、いろいろな幅で後段だけを試験できる。
検証では、現行の`dense`の書き方を、変更する`pair`を共有しない独立の参照実装として単体テストの中に残し、書き換えた後段と結果を比べる。
比べるのは、評価値ではなく、後段の出力（`LayerStackBreakdown::dense`に当たる値）である。評価値は除数で割って切り詰めるので、後段の出力の違いを隠すことがある。
比べる入力は次のとおりである。

- 第1層の幅が2、30、34、62、66、254、256、258、および1,024の場合の、乱数の累算値。
- 同じ幅で、各視点の前半の最後の成分と後半の最後の成分の両方を127にし、他を0にした累算値。この入力では最後の要素積だけが126（127×127を7ビット右シフトした値）になるので、L1のskipの行の最後の重みを0でない値にし、両視点で値か重みを変えておけば、末尾の成分の読み落としと視点の取り違えを後段の出力の違いとして検出できる。
- 累算値が16ビットの最小値と最大値、0、127、および128の境界にある値を含む固定の入力と、`pair`の境界の値。
- L2の入力の対が(127, 127)で、重みの対が(−128, −128)と(127, 127)の場合。バイアスは、出力の切り詰めで違いが隠れない値にする。

既存の、第1層から評価値までを独立に計算する参照実装との照合（`network/tests.rs`の`reference_layer`）も残す。
単体テストは、CIの`cargo test --workspace`（開発用の設定のビルドで、整数の桁あふれを検査する）と、本書の検証の`cargo test --release`の両方で通す。
あわせて、教訓に従い、採用したリリースビルドの`dense`を逆アセンブルし、ループごとに何個の積を何命令で処理したか、レジスタの幅、水平加算の有無、および入力の配列を0で埋める長さを、測定記録に残す。

自動ベクトル化は、コンパイラの版の更新で外れることがある。
rustcでは、1.87で`chunks_exact`と`zip`で書いたループのベクトル化が外れて60%遅くなった例（rust-lang/rust#142519）と、LLVM 23へ更新した1.99から、`chunks_exact`で書いた16ビット整数の比較のループが、それまでの約20倍の命令数の列にコンパイルされるようになった例（rust-lang/rust#166207）がある。
一方、命令名の出現数を単体テストやCIの合否にする方式は採らない。CIは`-C target-cpu=x86-64`でビルドするので測定機と命令の集合が違い、単体テストのビルドはリリースのビルドとも違う。また、より良い命令が出るようになれば出現数が減るので、固定の出現数は改善も退行と誤って判定する。
代わりに、完了時に、後段の書き方が自動ベクトル化に依存していることと、測り直す契機を、`dense`のdocコメントと設計判断のADRに書く。
測り直す契機は、ビルドに使うrustcとLLVMの版が変わったときと、後段の型、ループ、またはビルド設定を変えたときであり、前者では同じコミットを新旧のコンパイラでビルドして、後者では親と候補を同じコンパイラでビルドして、本書の対比較の手順で比べる。
bench深さ16の命令数は100万分の1以下の差で再現するので、変化の検知には使えるが、速さに比例しないので合否の閾値にはしない。

### 段階2　利きの逆引きの駒コード表

利きの逆引きのうち、駒コードから駒種を復号している2箇所を、駒コードを添字にして引く表に置き換える。
試作Cに当たり、試作のサイクル数の減少は、bench深さ16で2.5%、教師生成2局で2.5%から2.8%（2回の比較の値）である。

1つ目は走りの逆引きである。
`sliding_attackers_to`は、対象升から8方向へ最初の遮蔽駒（その方向で最初に当たる駒）を求めた後、その駒が照会した対局者の駒であり、逆方向へ走る動きを持つかを調べる。
現行はこの判定に、照会した対局者の駒の集合への所属の検査、駒コードから駒種への復号、駒種から動きの定義への変換、および動きの定義から方向マスクへの表引きを使う。
これを、照会した対局者と駒コードから方向マスクを返す256要素の表の1回の表引きにする。
表は、照会した対局者の駒でない駒コード、空升、および番兵に0を返すので、所属の検査を兼ねる。

利きの逆引きは、駒がある升の集合（占有）を引数で受け取り、呼び出し元は実際の盤面と違う占有を渡すことがある。各升の駒コードは、占有によらず実際の盤面から読む。
SEEは交換列で取られた駒を占有から除き、王手判定は、動かす駒の移動元を除いて到達升を加える。
最初の遮蔽駒は渡された占有から選ぶので、除かれた駒が遮蔽駒になることはない。遮蔽駒の升について、現行の所属の検査は、実際の盤面でその升に照会した対局者の駒があるかを調べており、表の検査と同じ結果になる。
王手判定が加えた到達升が遮蔽駒になった場合、その升は実際の盤面では空升か、照会した対局者から見た相手駒か、移動元と同じ升である。空升と相手駒では表が0を返し、現行が自駒でないとして飛ばすのと同じ結果になる。移動元と同じ升である場合は、その升に動かす駒が残っているので、現行も表も同じ駒を調べる。

2つ目は固定利きの逆引きである。
`ordinary_attackers_to`は、対象升を中心とする5×5升の範囲にある自駒について、相対位置から、走りでない動き（固定利き）が届く駒種の集合を表で引き、その駒の駒種が集合に含まれるかを調べる。
現行は駒種を駒コードから復号している。
これを、駒コードから駒種のビットを返す256要素の表の表引きにする。

2つの表は`AttackTables`に加え、駒コードを0から255の添字として返すアクセサを`PieceCode`に、升の駒コードを空升も含めて返すクレート内のアクセサを`Position`に加える。
`PieceCode`のアクセサは、段階3で評価のクレートからも使うので公開する。読み取りだけを許し、添字から駒コードを作る手段は加えない。
表の値は、構築できる駒コードのすべてについて、現行の復号の連鎖の結果と一致することを単体テストで固定する。
構築できない値の欄は0とする。現行の復号は、構築できない値の一部にも駒種を返すが、そのような値は盤面に現れないので、一致の対象にしない。
逆引きの結果は、`crates/minase-core/src/movegen/tests/attackers.rs`の逆引きと駒別の利きの一致で確かめる。

### 段階3　駒種、駒状態、および駒価値の復号の表引き

段階3は2つの測定単位に分ける。

1つ目は、駒コードから駒種を返す`PieceCode::kind`を、256要素の定数の表の表引きにする変更である。
現行は、空升と番兵の検査、駒種の番号の取り出し、範囲の検査、および駒種の表引きを順に行う。
試作Dに当たり、試作Cからのサイクル数の減少は1.9%と2.6%である。
表の各欄は次のように定める。空升、番兵、および駒種の番号の欄が1から29の範囲にない値は`None`とし、それ以外は、番号から1を引いた添字の駒種とする。
構築できる駒コードのすべてについて、戻り値は現行と一致する。
構築できない値のうち、空升以外で駒種の番号の欄が0である7つの値は、現行では番号から1を引く計算が桁あふれを起こすので、リリースビルドで`None`を返し、桁あふれを検査するビルドでパニックする。表ではどちらのビルドでも`None`を返すので、この7つの値については、256通りの全部で現行の動作を保つことにはならない。これらの値は構築子から作れず、盤面に現れないので、この違いは外から観測できない。
試作Dはこの扱いをテストで固定していないので、実装では256欄の期待値を、表の定め方とは独立に書いたテストで固定する。

2つ目は、駒コードから駒状態（成りの有無を含めた47通りの駒の区分）を返す`piece_state`と、駒価値を返す`piece_value`を、それぞれ256要素の定数の表の表引きにする変更である。
再診断では、`piece_state`が探索時間の1.3%と1.6%、`piece_value`が1.1%を使っており、教師生成2局では`piece_state`の時間の約4割が`PieceCode::kind`の呼び出しである。
1つ目の単位の後に残る時間は測っていないので、見込みは未測定とする。
空升と番兵の駒コードでパニックするという現行の契約は変えない。そのため、表には無効を表す値を入れ、引いた後に検査する。
構築できる駒コードのすべてについて、戻り値とパニックの有無が現行と一致することを単体テストで固定する。

### 段階4　生成の内側での獅子の手の除外

静止探索は、獅子が経由升で相手駒を取り、移動元と異なる空升へ進む手を候補から除く。
現行は、特殊駒の全捕獲を生成してから、候補へ入れるときにこの手を捨てている。
再診断では、特殊駒の候補の生成数の35.6%と33.0%がこうして捨てられ、特殊駒の候補の生成は探索時間の1.5%と1.3%を使っている。

変更は、静止探索の候補を作る経路に限り、獅子の2段階移動の第2段階の到達升を、相手駒のある升と移動元に限ることである。
獅子の2段階移動の生成`generate_lion_double_and_jumps`は、公開の捕獲生成と主探索の捕獲生成も使うので、共通の経路は変えず、到達升を絞る指定を引数で受ける。
特殊駒の全捕獲を出力する公開のメソッド`generate_special_captures`は、公開の捕獲生成から特殊駒の手を抜き出した列と一致するという契約を持ち、その契約のテストがある。このメソッドの契約は変えず、静止探索の候補にする特殊駒の捕獲の列を出力する入口を別に加えて、静止探索の初期化はその入口を呼ぶ。
静止探索の初期化にある、生成の後の除外は削除する。
置換表の手を検査する`is_legal_capture`は変えない。この関数は、先に除外の条件を調べてから、駒1枚分の全捕獲への所属で判定している。

見込みは未測定である。
捨てている割合を特殊駒の候補の生成の時間に掛けると、探索時間の0.5%と0.4%になる（35.6%×1.5%と33.0%×1.3%）。ただし、候補1件の費用は手の種類で違うので、この値は等しい費用を仮定した概算である。

検証は、次の3つを別々の単体テストで照合する。
1つ目は、公開のメソッド`generate_special_captures`の列であり、既存の契約のテストが変わらず通ることを確かめる。
2つ目は、新しい入口の列であり、公開の捕獲生成の列を「特殊駒の手であり、除外の条件に当たらない手」に絞った順序つきの部分列と一致することを確かめる。獅子がその場の相手駒だけを取って元の升へ戻る手、2枚を取る手、経由升のない直接の跳び、および角鷹と飛鷲の手が残ることを、固定の局面でも確かめる。
3つ目は、静止探索が実際に取り出す候補の列と`is_legal_capture`の真偽である。候補の列は、置換表の手の先頭化と群の中の並べ替えを含む既存の参照実装（`crates/minase/src/search/alphabeta/tests/captures.rs`）との一致が、`is_legal_capture`の真偽は、公開の捕獲生成の集合と比べる既存のテスト（`crates/minase-core/src/movegen/tests/search_captures.rs`）が、変わらず通ることを確かめる。

### 段階5　残る負荷の診断

段階1から段階4の採否が決まった後に、採用版で関数別の内訳を取り直し、次の3点を1回だけ調べる。
本段階は診断であり、測定単位を1つも起こさずに終わってよい。

1点目は、NNUEの後段に残る時間である。
L1の積和が128ビット幅にとどまる時間と水平加算の時間、入力の配列を0で埋める長さ（試作Eでは、使うのは512バイトなのに2,048バイトを埋めていた）、およびL2を32ビットの積和`vpmaddwd`の形で書いた場合の命令数を、機械語と標本で調べる。
L1を256ビット幅の積和にする書き方を試すのは、隣接する2つの積の和を固定の個数ずつ作る変種1つに限り、主ループが32個の積を256ビット幅の積和2命令で処理するようになり、命令数が減ることを機械語で確かめてから、測定単位として起こす。
2点目は、駒コードの復号の連鎖が残っている箇所である。
`Position::piece_at`、`PieceCode::color`、`PieceCode::is_promoted`、および駒種から動きの定義への変換について、呼び出し元ごとの時間を集計する。
3点目は、通常駒の捕獲可能升の走査（`capture_targets_without_special`と、その呼び出し元の`collect_ordinary_capturers`および`generate_piece_moves`）である。
分岐予測ミスの標本の帰属と機械語を調べる。

調べた結果、探索の結果を変えずに省ける処理が具体的に見つかり、その処理の時間がどちらかの負荷で探索時間（その負荷のプロセス全体の標本）の0.5%以上である項目だけを、測定単位として起こす。
0.5%は測定単位を起こす目安であり、採用の条件は他の段階と同じである。
該当する項目がなければ、診断の記録だけを残して本段階を終える。
本段階で起こす測定単位は、NNUEの評価、利きの逆引き、手の生成、および駒コードの復号の範囲に限り、`unsafe`を使わない。

## 実装フェーズ

1. **準備**：masterから本マイルストーンのブランチを切り、worktreeを作る。探索の結果の一致を確かめるスクリプトと、サイクル数の対比較を行うスクリプトを、[教師生成の高速化の付属資料](../measurements/teacher-generation-speedup/teacher-generation-speedup-engine/)と[後段の試作の付属資料](../measurements/adhoc/nnue-dense-safe-vectorization-20261127/)から現行のコマンドに合わせて作り直し、測定記録の付属資料に置く。基準の出力と基準の速さを記録し、同じバイナリどうしの対比較から組数を定める。完了条件は、スクリプト、基準の出力、および組数が測定記録`movegen-speedup-3-baseline`にあることである。
2. **段階1**：NNUEの後段を2つの測定単位に分けて書き直し、それぞれ採否を判定する（測定記録`movegen-speedup-3-stage1-pair-l1`と`movegen-speedup-3-stage1-l2`）。
3. **段階2**：駒コード表を実装し、採否を判定する（`movegen-speedup-3-stage2`）。
4. **段階3**：2つの測定単位を順に実装し、それぞれ採否を判定する（`movegen-speedup-3-stage3-kind`と`movegen-speedup-3-stage3-state-value`）。
5. **段階4**：獅子の手の除外を移し、採否を判定する（`movegen-speedup-3-stage4`）。
6. **段階5**：診断を行い（`movegen-speedup-3-stage5-diagnosis`）、測定単位を起こした場合はそれぞれ採否を判定する。
7. **最終測定**：採用版と基準の対比較を、段階の判定とは別の測定として行い、速度比を求めて、残る負荷の内訳を記録する（`movegen-speedup-3-final`）。採用した測定単位が1つもない場合は、最終測定と段階ゲートを行わない。
8. **段階ゲート**：最終測定が最低受入条件を満たした場合に限り、採用版と基準のSTCを行い（`movegen-speedup-3-stc`）、手引きの規則でLTCへ進む場合に限りLTCを行う（`movegen-speedup-3-ltc`）。
9. **統合または不統合の確定**：「完了条件」の節の統合の条件を満たせば、設計判断をADRへ、表と後段の仕様をdocコメント（コードに付ける仕様の説明）へ移し、masterへ統合する。満たさなければ統合せず、統合しない理由と測定値を記録し、採用されなかった方式の仕様はdocコメントへ移さない。どちらの場合も、設計書を凍結してdocs/ROADMAP.mdを更新する。完了条件は、統合するかどうかが測定記録とともに確定していることである。

段階1から段階5のフェーズの完了条件は、該当する段階の採否が測定記録とともに確定していることである。
プログラムの実装は、[委任の手引き](../guides/codex-delegation.md)に従って測定単位ごとに別のエージェントへ委任し、採否の測定は、委任した側が測定機に負荷のない状態で行う。
採用しなかった測定単位のコミットは、ブランチから外す。

## 検証

実装した測定単位ごとに、次を実行する。

```console
cargo fmt --all --check
cargo clippy --release --all-targets
cargo test --release
```

`cargo test`は、探索のほかに利きの逆引きと公開の手生成を使う処理の検査を含む。公開の手生成の集合と順序の契約テスト、審判層の裁定を全手生成による参照と比べるテスト、詰みの探索のテスト、複数ワーカーの探索のテスト、およびNNUEの評価値と累算値の検査である。
先獅子（獅子を取った直後の取り返しを制限する規則）、成り権の保留、履歴を使う反復の判定、および終局の裁定は、その状態を与える既存の境界のテストで確かめる。
段階1では、これに加えて、段階1の節に書いた参照実装との一致の単体テストを、開発用の設定のビルドの`cargo test --workspace`でも実行する。
統合の前には、[検証の手引き](../guides/testing-minase-rules.md)の「マージ前の検査」の4つ（`cargo fmt --all --check`、`cargo clippy --workspace --all-targets -- -D warnings`、`cargo test --workspace`、および`scripts/ci/run_feature_only_tests.sh`）を通す。

探索の結果の一致は、探索ワーカーを1にした固定の仕事量について、基準のバイナリで記録した次の4種類の出力と、候補の出力を比べて確かめる。

- `bench`の深さ16の15局面の行のうち、ノード数、最善手、および評価値を比べる。
- 教師生成のファイルのSHA-256と探索ノード数の合計を比べる。シード`9010200000`の2局と、シード`424242`の4局の2通りを使う。
- 7つの規則セット（`JCSA`、`lishogi`、および規則コードを並べた`L1,L3,P0,P5,P6,R2,E1,E2`、`L0,P0,R3,E0`、`L0,P1,R1,E0`、`L1,L2,P2,P3,P4,R2,E0`、`L0,L4,P0,R1,E0`）のそれぞれで、`bench`の15局面を6万ノードで探索し、`bestmove`までにエンジンが出力した最後の`info depth`の行の深さ、ノード数、評価値、および読み筋と、`bestmove`の手を比べる。
- 同じ7つの規則セットのそれぞれで、`bench`の15局面から`perft 2 divide`（深さ2までの合法手の経路数を、最初の手ごとに出力するコマンド）を実行し、最初の手ごとの行を出力の順序も含めて比べ、深さごとの経路数と総数の行も比べる。

`info`行の経過時間と毎秒ノード数は実行ごとに変わるので比べない。
`perft`の経過時間と毎秒ノード数の行も比べない。
どの検査も、基準と候補の両方が所定の数の行（`bench`は15行、規則セットを使う検査は7×15局面分）を出力したことを確かめ、行や比べる欄が欠けた場合は不一致とする。
`bench`の規則セットは`JCSA`に、教師生成は`lishogi`に固定されているので、成り権の保留や先獅子の扱いが違うほかの規則コードの経路は、3つ目の検査で確かめる。
4つ目の検査は、公開の手生成の最初の手の順序と経路数を見る補助の診断である。経路数は手の順序の入れ替えを検出できないので、公開の手生成の契約は`cargo test`の契約テストで確かめる。

教師生成は、実行時の作業ディレクトリのコミットを教師のファイルに書く。また、対局をまとめて保存する単位（塊）が出力先にすでにあると、探索せずに、その塊から教師のファイルを作り直す。
そのため、教師生成の比較では、基準と候補のバイナリを同じコミットの変更のない作業ディレクトリから起動し、実行のたびに空の出力先を使う。
生成が完了したこと、対局数、および探索ノード数の合計が基準と同じであることを、ファイルのSHA-256と合わせて確かめる。

サイクル数の対比較は、性能コアの論理CPU（測定機では3番）に固定して次の2つを測り、1組ごとに候補と親の順序を入れ替える。

```console
taskset -c 3 perf stat -x, -e cpu_core/cycles/u,cpu_core/instructions/u,cpu_core/branch-misses/u -- \
  <バイナリ> --protocol usi < bench16.usi
taskset -c 3 perf stat -x, -e cpu_core/cycles/u,cpu_core/instructions/u,cpu_core/branch-misses/u -- \
  <バイナリ> data selfplay generate --eval-file <ネット> --output-dir <空の出力先> --chunk-games 2 --games 2 \
  --seed 9010200000 --nodes 20000 --random-moves 0 --concurrency 1 --hash-mb 16
```

`bench16.usi`は、`setoption name RuleSet value JCSA`、`setoption name EvalFile value <ネット>`、`isready`、`bench depth 16 threads 1 repetitions 1`、`quit`の5行である。
測定の前に、対局の測定、探索の係数の自動調整（SPSA）、および教師生成が同じ機械で動いていないことを確かめる。
lishogiのBotのエンジンは、対局のたびに複数の探索スレッドで同じ機械のCPUを使うので、測定の間はBotのコンテナを止め、測定が終わってから起動し直す。
測定記録は`docs/measurements/movegen-speedup-3/`に置き、組ごとの値、平均、信頼区間、および探索の結果の一致を書く。

## 完了条件

次の記録は、結果によらずそろえる。

- 段階1から段階4の測定単位と、段階5で起こした測定単位の採否。採用しない測定単位の理由と測定値を含む。
- 段階5の診断の記録。
- 採用した測定単位がある場合は、採用版と基準の対比較による最終測定の記録と、段階ゲートの記録。

採用版をmasterへ統合するのは、測定の結果が次のすべてを満たす場合である。

- 採用版の探索の結果が、「検証」の節の4種類の出力のすべてで基準と一致している。
- 最終測定で、bench深さ16と教師生成2局のどちらでも、速度比の両側95%信頼区間の下端が1.02倍以上である。速度比の平均が1.15倍に届かない場合は、速度比と残る負荷の内訳を記録する。
- 採用版と基準の段階ゲートで、「持ち時間の対局による確認」の節が定める明確な退行がない。

最終測定の前に、次の仕上げを済ませる。最終測定と段階ゲートの後に実行コードを変えた場合は、変えた後の版で検証、最終測定、および段階ゲートをやり直す。

- 「検証」の節の測定単位ごとの検査と、統合の前の4つの検査を通す。
- 採用しなかった方式、使われない表、および測定のためだけに入れた処理を取り除く。

設計判断のADRへの移し替えと、表と後段の仕様のdocコメントへの移し替えは、実行コードを変えないので、段階ゲートの後、統合の前に行う。

本書が起案の時点で扱うと予定していた、探索の結果を変えずに省ける処理の候補のうち、攻撃駒が1枚見つかった時点で利きの逆引きを終える案（[教師生成の高速化候補](../proposals/nnue-teacher-generation-speedup.md)）は、測定単位を起こす前に再診断の件数で見送っている。
そのため、統合したときの状態は、起こした測定単位をすべて採用した場合も含めて、完了（一部不採用）とする。
測定単位を1つも採用しなかった場合と、測定の結果が統合の条件を満たさない場合は、本書の変更は1つもmasterへ入らないので、理由と測定値を記録して、状態を完了（不採用）とする。
利用者の決定で、これらの判定に至る前に計画を閉じる場合は、[設計書の書き方](README.md)に従って状態を中断とする。

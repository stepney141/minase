# 合法手生成と利き計算の高速化（第3期）の設計書

## 先に読む要約

本マイルストーンは、探索の結果を変えずに探索を速くする。
探索が速くなると、持ち時間の対局では同じ時間でより深く読めるようになり、NNUE（着手ごとに差分で更新できる小さなニューラルネットの評価関数）の学習データである教師を、1局面あたり固定のノード数（探索が着手を適用した回数）の探索で作る自己対局では、作る費用が下がる。
速さは、固定の15局面を深さ16まで探索する負荷（独自コマンド`bench`）と、教師を作る自己対局2局の負荷について、同じ探索に費やすCPUのサイクル数で比べ、局面別のノード数、最善手、評価値、および教師のファイルが変更の前後で変わらないことを条件とする。
2026年11月24日の[再診断](../measurements/movegen-speedup-3/movegen-speedup-3-rediagnosis.md)では、NNUEの後段の層の計算が探索時間の19%を、探索済み局面の結果を保存する置換表の照会が7〜9%を占めたが、前者は別の診断から始める主題であり、後者は探索が訪れる局面の集合（探索木）を変えずに減らす具体的な方式を持たないので、どちらも本書の対象にしない。
本書が対象とするのは、ある升へ利きが届く駒を求める利きの逆引きと手の生成であり、その中で効果を確かめられたのは、升の駒を表す1バイトの値（駒コード）から駒種や走りの方向を求める処理を、何段もの検査と表引きから256要素の表の1回の表引きへ置き換える変更である。
この変更の[試作](../measurements/movegen-speedup-3/movegen-speedup-3-prototypes.md)は、段階1と段階2の一部に当たり、サイクル数を2つの負荷で4.4%と5.1%減らした（基準のサイクル数を試作のサイクル数で割った速度比で1.046倍と1.053倍）のに対し、起案時の主な候補だった、方向ごとの走り駒の集合を局面に持たせる方式は約1%の減少にとどまったので、後者は採らない。
段階1は利きの逆引きに駒コードの表を使う変更、段階2は駒種、駒状態、および駒価値を求める処理を表引きにする変更、段階3は静止探索（駒を取る手だけを読み進める探索の末端）がもともと候補から除いている獅子（2回続けて動ける中将棋の駒）の手を生成の時点で省く変更であり、段階4は、これらの後に残る探索時間の内訳を調べて追加の変更の候補を探す診断である。
段階1から段階3の変更は、変更の前と後のバイナリを交互に実行してサイクル数の差を集め、`bench`の負荷で減少が95%信頼区間で確かめられ、教師を作る負荷で0.5%を超える退行がない場合だけ採用する。
採用した変更をまとめた版を変更前の版と比べ、どちらの負荷でも速度比の95%信頼区間の下端が1.02倍（最低受入条件）以上であればmasterへ統合して完了とし、目標は1.05倍である。
探索の結果が変わらないので、持ち時間の自己対局で強さの差を判定する測定は行わず、対局中の異常（エンジンの停止、時間切れ、反則）がないことだけを、変更前の版との持ち時間の対局200ペア（同じ開始局面を先手と後手を入れ替えて指す2局が1ペア）で確かめる方式を提案しており、この点は着手の前に利用者の判断を得る。

## 状態

状態は起案である。2026年9月17日に起案し、着手していない。
次の一手は、持ち時間の自己対局による採否測定に代えて固定200ペアの対局で異常がないことだけを確かめる方式（「設計判断」の節）について利用者の判断を得たうえで、masterから本マイルストーンのブランチを切り、準備のフェーズに着手することである。
利用者が採否測定を求めた場合は、固定200ペアの対局に代えてその測定を最終測定で行うことにして、同じように着手する。

## 目的

現行のminaseは、NNUEを評価関数とし、[第2期](archived/movegen-speedup-2.md)と[教師生成の高速化](archived/teacher-generation-speedup.md)の変更を含んでいる。
本マイルストーンは、その現行の探索を対象に、探索の結果を変えない変更だけで探索の時間を減らす。
探索が速くなると、持ち時間の対局では読みが深くなり、1局面を固定のノード数で探索する教師生成では、同じ教師を作る費用が下がる。

速さは、次の2つの負荷のサイクル数で測る。
1つ目は、固定の15局面を固定の深さで探索する独自コマンド`bench`の深さ16であり、対局中の探索の代わりとする。以下では**bench深さ16**と呼ぶ。`bench`は、将棋エンジンの通信プロトコルUSIでエンジンへ送る、minase独自のコマンドである。
2つ目は、自己対局の各局面を2万ノードで探索する教師生成の2局であり、以下では**教師生成2局**と呼ぶ。
再診断の時点の値は、bench深さ16が2,819,426ノードで約181億サイクル（1ノードあたり約6,420サイクル）、教師生成2局が17,600,000ノードで約1,048億サイクル（1ノードあたり約5,950サイクル）である。
サイクル数はプロセスの全体を数えるので、bench深さ16の値には、ネット（NNUEの重みのファイル）の読み込みや、局面ごとの履歴表（探索中に着手の成績を記録する表）の消去のように、探索の外で行う処理も含まれる。再診断のプロファイルでは、履歴表の消去がbench深さ16の標本の6.0%を占めた。探索の外の処理の費用が変更の前後で同じであれば、その分だけ、bench深さ16の変化率は探索だけの変化率より小さく出る。
基準の値は、ブランチを切った時点のmasterで測り直す。

目標は、どちらの負荷でも**速度比**（基準のサイクル数を採用版のサイクル数で割った値）が1.05倍以上になることであり、最低受入条件は1.02倍以上である。
サイクル数の減少率をxとすると、速度比は1÷(1−x)である。
1.05倍は、段階1と段階2の一部に当たる試作の実測（基準からの減少が4.4%と5.1%、速度比で1.046倍と1.053倍）に近い値として置いた。
1.02倍は、段階1だけに当たる試作の実測（約1.026倍）より低く置いた値であり、段階1だけが採用された場合にも統合する価値があると判断する下限である。
どちらも予備の測定に基づく方針の値であり、確かめられた下限ではない。

## 適用範囲

変更するコードは次のとおりである。

- `crates/minase-core/src/movegen/control.rs`の利きの逆引き（`ordinary_attackers_to`と`sliding_attackers_to`）を書き換える。
- `crates/minase-core/src/attacks/tables.rs`の前計算表に、駒コードから引く表を加える。
- `crates/minase-core/src/piece/code.rs`の駒コードの復号（`PieceCode::kind`）を書き換え、駒コードを表の添字として読むアクセサを加える。
- `crates/minase-core/src/position/mod.rs`に、升の駒コードを空升も含めて返すクレート内のアクセサを加える。
- `crates/minase/src/eval/features.rs`の駒状態（`piece_state`）と、`crates/minase/src/eval/piece_values.rs`の駒価値（`piece_value`）を表引きにする。
- `crates/minase-core/src/movegen/lion.rs`と`crates/minase-core/src/movegen/search_captures.rs`の探索専用の獅子の捕獲の生成、および`crates/minase/src/search/alphabeta/quiesce.rs`の静止探索の初期化を書き換える。

本書で使う語を次のとおり定める。
中将棋の駒の動きと、`L0`や`P1`のような規則コードの意味は、[規則の文書](../rules/chu-shogi.md)にある。

- **駒コード**：升にある駒を表す1バイトの値（`PieceCode`）。対局者、成り、および駒種の番号を詰めた値であり、空升と盤外（番兵）にも専用の値がある。公開の構築子から作れるのは、両対局者の成っていない駒と成駒、空升、および番兵の値だけである。以下では、これらを**構築できる駒コード**と呼ぶ。
- **利きの逆引き**：ある升へ利きが届く駒を、その升の側から求める処理（`Position::attackers_to_by`）。静的交換評価（SEE、到達升での駒の取り合いを見積もる評価）、王手判定、王駒への攻撃判定、対局の終局を裁定する審判層、および詰みの探索が使う。
- **測定単位**：1コミットにまとめて採否を判定する変更の単位。
- **親**と**基準**：親は、ある測定単位を判定するときの、直前の採用版のコミットである。基準は、ブランチを切った時点のmasterのコミットである。
- **採用版**：採用した測定単位をすべて含む、ブランチの先頭のコミット。
- **対比較**：候補と親を1回ずつ実行した組を、組ごとに実行の順序を入れ替えながら繰り返し、組ごとの差を集める測り方。測定機の状態の変化が、同じ組の両方に同じように掛かるので、差の揺れが小さくなる。
- **段階ゲート**：[SPRTの手引き](../guides/sprt.md)が定める、自己対局による採否測定。短い持ち時間の測定で候補を選別し、長い持ち時間の測定で採否を判定する。

次の事項は対象外とする。

- 探索木を変える変更。枝刈りの条件、着手の順序、および置換表の使い方は変えない。
- 公開の全手生成と捕獲生成の着手集合、順序、および合法性。
- NNUEの推論と置換表。再診断で最大の負荷だが、対象にしない理由を「設計判断」の節に書く。
- Rustの`unsafe`（コンパイラの安全性の検査を外す記法）、PGO（実行頻度をコンパイラへ渡す最適化）、および置換表の先読み。いずれも既存の設計判断の記録（ADR）が使わないと決めている（[unsafe](../adr/allow-unsafe-only-in-the-trainer-gpu-code.md)、[PGO](../adr/do-not-build-with-pgo.md)、[先読み](../adr/do-not-prefetch-transposition-table-entries.md)）。

## 依存関係

着手を妨げる未完了の計画はない。
完了済みの[ネットの外部ファイル化](archived/nnue-external-network-file.md)により、`bench`の前には、USIのオプション`RuleSet`（規則セット）と`EvalFile`（ネットのファイル）を設定して`isready`を送る。
ネットは、[NNUEの評価関数の手引き](../guides/evaluation-nnue.md)が探索の測定の標準とする、王の位置を使わない入力（P型）のネットを使う。
`bench`の規則セットは日本中将棋連盟の規則に基づく`JCSA`に、教師生成の規則セットはオンライン対局サイトlishogiの実装に近い`lishogi`に固定されている。

利きの逆引きの契約は[棋力向上段階3](archived/strength-stage3.md)が、探索専用の捕獲生成の契約は[捕獲生成のADR](../adr/generate-qsearch-captures-by-value-group-per-piece.md)が、静止探索の候補から除く獅子の手の定義は[静止探索の入口のADR](../adr/probe-the-tt-before-the-qsearch-stand-pat-and-blend-fail-highs-toward-beta.md)が定める。
本マイルストーンはこれらの契約を変えない。

[P型の世代反復](archived/nnue-generation-iteration.md)は、ネットの自己対局で教師を作り、その教師で次のネットを学ぶことを繰り返す計画であり、全世代の教師の生成、学習、および判定に同じコミットを使う。
そのため、本書の変更がmasterへ入っても、進行中の世代反復の速さと結果は変わらない。
本書の高速化が教師生成に効くのは、次に生成のコミットを決める計画からである。

速度の測定は、[測定機の確認の教訓](../lessons/check-running-measurements-before-cpu-load.md)と[性能コアへの固定の教訓](../lessons/pin-bench-to-performance-core.md)に従う。
ビルド設定は変えないので、[ビルド設定の教訓](../lessons/do-not-mix-builds-across-cargo-config-changes.md)が扱う混在は起きない。

## 設計判断

### 対象と方式の選択

再診断では、bench深さ16と教師生成2局について、関数別の時間の内訳と、省ける処理の件数を取り直した。
試作では、その中の候補を実際に実装して、探索の結果の一致とサイクル数を測った。
試作は4つあり、以下では次の名前で呼ぶ。
**試作A**は、対局者と方向ごとの走り駒の集合を局面に持たせる。
**試作B**は、利きの逆引きの走りの判定を駒コードの表引きにする。
**試作C**は、試作Bに加えて、利きの逆引きの固定利きの判定も駒コードの表引きにする。段階1に当たる。
**試作D**は、試作Cに加えて、駒コードから駒種を返す`PieceCode::kind`を表引きにする。段階2の1つ目の測定単位に当たる。

下表は、この2つの測定から決めた方式と、棄却した代案である。
数値を2つ並べた箇所は、bench深さ16、教師生成2局の順である。割合は、断りがなければ探索時間に対する割合である。

| 判断 | 採る方式 | 棄却した代案と理由 |
|---|---|---|
| 範囲 | 利きの逆引き、手の生成、および駒コードの復号に限る | NNUEの後段の計算（19.2%、19.5%）は最大の負荷だが、積和の関数を素朴に書き換える試作はサイクル数を4.9%と5.4%増やした。[自動ベクトル化の教訓](../lessons/check-autovectorization-before-explicit-simd.md)が定める機械語の診断から始める別の主題なので、本書に入れない。置換表の照会（9.1%、7.5%）は、時間のほぼすべてが記録を読み出す関数に付く（9.0%、7.3%）。読み出しの待ちを隠す先読みは行わない決定があり、照会の回数を減らす変更は探索木を変えるので、本書では具体的な方式を採らない。 |
| 利きの逆引きの走りの判定 | 最初の遮蔽駒の駒コードから、照会した対局者の駒としての走りの方向マスクを、256要素の表で引く（試作B） | 試作Aは、利き線と走り駒の集合の共通部分が空の方向を飛ばす。サイクル数の減少は0.95%と1.12%で、試作Bの1.85%と2.16%の半分だった。試作Aも駒コードの復号を通らないので、差は集合の維持と共通部分の検査の費用によると考えられるが、切り分けてはいない。方向を問わない1つの集合で8方向をまとめて飛ばす案は、飛ばせる呼び出しがSEEからの逆引きの20.6%と14.2%にとどまる。駒種別の集合から呼び出しのたびに合成する案は、走りを持つ十数種類の駒種について、毎回ビットボードの和集合を求めることになる。 |
| 駒種の復号 | `PieceCode::kind`そのものを256要素の定数の表の表引きにする（試作D） | `PieceCode::kind`を呼ぶ箇所ごとに駒種の表を足す案は採らない。再診断では、`PieceCode::kind`の時間は駒状態の計算、着手の適用、履歴表の添字、評価の補正表の鍵、およびSEEへ分かれており、関数を1つ直す方が変更が小さい。 |
| SEEの構造 | 変えない | SEEは、取り合いの手順（交換列）の各段で利きの逆引きをやり直す。これを差分の更新に替える案は、[教師生成の高速化の測定](../measurements/teacher-generation-speedup/teacher-generation-speedup-engine.md)で2つの変種を試し、命令数が1.0%と0.9%増え、サイクル数は+0.4%と−0.8%で、改善を確かめられなかった。再診断でも、交換列へ入った呼び出しの逆引きは平均1.80回と1.76回で、84%と87%が2回以内に終わる。段階1の後は逆引き1回の費用も下がるので、やり直しを省いて得られる時間はさらに小さくなる。静止探索は1つの候補に、枝刈りの閾値と下限の2つの値でSEEを呼ぶことがあるが、閾値のSEEを通過した候補に下限のSEEも呼ぶ場合は、静止探索からのSEEの呼び出し約151万回と約1,228万回のうち、237件と2,608件しかない。 |
| 静止探索の候補の生成 | 獅子が経由升で取って空升へ進む手を、生成の後ではなく生成の内側で省く | 静止探索は、取る駒の価値が高い群から順に候補を生成する。特殊駒（獅子、角鷹、飛鷲）の候補を必要になるまで生成しない案は、最初の群を決めるときから特殊駒の候補の最大の価値が要るので、順序を保つ実装が複雑になる。候補の初期化を置換表の手の後まで遅らせる案は、置換表の手で探索窓の上限（β）を超えるノードが、初期化したノードの0.9%と1.2%しかない。取る駒の価値の閾値で生成の前に対象を絞る案は、現行の静止探索が閾値以下の候補も数え、取り返しと成りと王手になる手を枝刈りから免除し、最善値の引き上げにも使うので、探索木を変える。対象升から取り手を逆引きする案は、初期化1回あたり相手駒26.4枚と30.7枚のうち、通常駒の利きが届くのが2.4枚と2.3枚であり、捕獲生成のADRが退けた理由が現行でも成り立つ。 |
| 王手判定と攻撃駒の存在判定 | 変えない | [教師生成の高速化候補](../proposals/nnue-teacher-generation-speedup.md)の、攻撃駒が1枚見つかった時点で逆引きを終える案は、SEE以外の逆引きで結果が空でないのが4.6%と2.9%しかない。結果が空の呼び出しは最後まで調べないと空だと分からないので、この案で省ける処理はほとんどない。王駒へ利く升を前計算する案は、[王手判定のADR](../adr/judge-gives-check-on-the-post-move-occupancy-without-precomputation.md)が退けている。 |
| 静止探索の置換表 | 変えない | 静止探索で置換表を使わない案は探索木を変える。現行の静止探索は、最大の深さに達した場合を除く全ノードで置換表を照会し、静止探索の全ノードに対して、的中が19.7%と25.6%、置換表の値による打ち切りが7.8%と12.5%であり、的中した記録は静的評価の再利用にも使われる。 |
| 通常駒の捕獲可能升の走査 | 段階4で1回だけ診断する | 静止探索の初期化と主探索の捕獲生成は、同じ関数`capture_targets_without_special`で通常駒の捕獲可能升を求めており、この関数は探索時間の3.6%と5.0%を使う。静止探索の初期化では、走りを持つ駒のうち76%と85%が遮蔽なしの到達範囲の検査を通るのに、実際に取れる駒があるのは24%と14%である。ただし、探索の結果と候補の順序を保ったまま走査を減らす具体的な方式が見つかっていないので、診断なしには段階にしない。 |

駒コードの復号が、関数別の内訳に現れる時間より大きく効く理由は確かめていない。
試作Dは、基準に対して命令数を2.8%と3.1%減らしたのに対し、サイクル数を4.4%と5.1%、bench深さ16の分岐予測ミスを8.1%減らした。
関数別の内訳では、`PieceCode::kind`とその呼び出し先の時間は1.3%と1.5%であり、試作Dが試作Cから減らした1.9%と2.6%より小さい。
したがって、各段階の見込みは内訳の割合ではなく試作の実測に基づいて書き、試作のない項目は未測定と書く。

先行エンジンも、利きの逆引きを速くするために駒の集合の合成や向きの絞り込みを前計算している。
Stockfishの`attackers_to`は、走り駒を`pieces(ROOK, QUEEN)`のように2駒種の集合の和で引く。
やねうら王は、`attackers_to`でよく使う合成の集合を着手のたびに作り直す。
Fairy-Stockfishは、香車のように向きのある走り駒を、対象升から見た到達範囲の表との共通部分で絞る。
中将棋は走りの方向の組合せが駒種ごとに違い、盤も144升でビットボードが3語になるので、これらの形はそのまま移せず、本書は駒コードから方向マスクを引く形を採る。
HaChuは、升ごとの攻撃の表を着手のたびに全駒から作り直し、捕獲の生成もその表を前提にする。minaseは升ごとの攻撃の表を持たず、この方式には新しい表を着手のたびに作る費用が要るので、採らない。

### 探索木を変えない段階の採否

測定単位の採否は、探索の結果の一致とサイクル数の対比較で決める。
毎秒ノード数の交互測定は使わない。
試作Aの毎秒ノード数の増分は0.95%で、基準を5回測った値の幅（最大と最小の差を中央値で割った値）の1.14%に収まり、[交互測定の教訓](../lessons/alternate-speed-rounds-against-parent.md)の「増分が親の幅を超える段階だけを残す」という規則では判定できなかった。
命令数も採否の条件にしない。
命令数は実行ごとの差が100万分の1以下で再現するが、試作Aでは命令数の減少が0.25%と0.48%だったのに対してサイクル数の減少は0.95%と1.12%であり、時間の変化を表していなかった。
命令数と分岐予測ミスの回数は、原因を調べる材料として測定記録に残す。

対比較の1組からは、候補のサイクル数を親のサイクル数で割った値の自然対数（以下、対数比）を取る。
対数を使うのは、比の向きを逆にしても平均の絶対値が変わらず、段階ごとの判定と最終の速度比を同じ量で扱えるからである。
組ごとの対数比の平均と、t分布による信頼区間を求め、速度比は、対数比の平均の符号を変えて指数を取った値とする。

測定単位を採用する条件は、次の3つをすべて満たすことである。
1つでも満たさない測定単位は採用せず、同じ測定単位を測り直して判定を変えることはしない。

1. 探索の結果が親と一致する。確かめ方は「検証」の節に書く。
2. bench深さ16の対比較で、対数比の平均の両側95%信頼区間が、上端まで0より小さい。
3. 教師生成2局の対比較で、対数比の平均の片側95%信頼区間の上端が、0.5%の退行に当たる値（1.005の自然対数）以下である。

bench深さ16を改善の判定に、教師生成2局を退行の見張りに使うのは、教師生成2局の1回の揺れがbench深さ16より大きく、小さな改善を教師生成2局の区間で確かめるには組数が多く要るからである。
教師生成2局の条件は測定単位ごとに0.5%までの退行を見逃し得るので、退行の積み重ねは、最終測定で採用版を基準と直接比べて確かめる。
測定単位の採用は最終測定までの仮の採用であり、統合するかどうかは最終測定で決まる。

組数は、準備のフェーズで定める。
まず、同じバイナリを候補と親の両方に使う対比較を、両方の負荷で20組ずつ行い、組ごとの対数比の標準偏差sを求める。この対比較は、変更がないときの揺れを測るものである。
次に、組数をn、t分布の臨界値をtとして、区間の端から平均までの距離`t × s ÷ √n`が、bench深さ16の両側の区間で0.1%の変化に当たる値（1.001の自然対数）以下、教師生成2局の片側の区間で0.3%の変化に当たる値（1.003の自然対数）以下になる、最小の偶数のnを求める。偶数にするのは、候補を先に実行する組と親を先に実行する組を同数にするためである。
上限は、bench深さ16が40組、教師生成2局が60組とする。上限でも届かない場合は、上限の組数で測る。その場合は区間が広くなって採用されにくくなるが、組の間の独立を仮定した1回の判定の名目の水準は変わらない。
最終測定にも同じ組数を使う。
試作の3回から5回の実行の値の幅から仮定すると、組数はbench深さ16が20組、教師生成2局が40組になる見込みであるが、試作は組ごとの分散を記録していないので、この見込みは確かめていない。
組数と判定の規則は測定単位を測る前に固定し、結果を見てから組数を増やさない。
試作の値は段階を選ぶための予備の測定であり、採否には使わない。

### 持ち時間の対局による確認

本書は、採用版について段階ゲートを行わず、固定200ペアの対局を1回行って、対局中の異常がないことだけを確かめる方式を提案する。
1ペアは、同じ開始局面を先手と後手を入れ替えて指す2局である。
対局は、持ち時間10秒と1手ごとの加算0.1秒の条件で、採用版と基準の間で行い、エンジン異常、時間切れ、および拒否着手（審判層が合法とした相手の着手を、エンジンが受け付けなかった反則）が0件であることを確かめる。
この対局から求める強さの差の推定値（Elo）は進捗の記録として残し、採否には使わない。
[開発の規約](../../CONTRIBUTING.md)は棋力に影響し得る変更の採否を自己対局で判定すると定め、[交互測定の教訓](../lessons/alternate-speed-rounds-against-parent.md)は速度で選んだ段階をまとめた版を段階ゲートにかけるとしている。
本書の方式はその例外なので、着手の前に利用者の判断を得る。
利用者が段階ゲートを求めた場合は、固定200ペアの対局に代えて、採用版と基準の段階ゲートを最終測定で行い、その結果を統合の条件にする。

例外を提案する理由は次のとおりである。
探索の結果が親と一致する変更は、同じ局面を同じノード数まで探索したときの手と評価値を変えない。強さに影響するのは、同じ時間で探索できる量が増えることを通じてであり、その量の変化はサイクル数の対比較で見積もれる。
段階ゲートは、改善が0 Eloであるという仮説と10 Eloであるという仮説を比べる検定であり、手引きの近似では、判定までの期待ペア数は、真の差が10 Eloのとき約2,600ペア、5 Eloのとき約4,200ペアである。
目標の1.05倍が何Eloに当たるかは測っていない。[持ち時間2倍の感度測定](../measurements/evaluation-gen1/sensitivity-time2x.md)の「持ち時間2倍あたり約216 Elo」を、時間の比の2を底とする対数に比例すると仮定して当てはめると約15 Eloになるが、同記録は評価関数がNNUEへ替わる前の値であり、線形性を仮定せず採否に用いないとしている。
改善が数Eloから十数Eloの範囲にあれば、段階ゲートは数千ペアを要する。探索木も変えた第2期の段階7から段階9は、短い持ち時間の測定と長い持ち時間の測定に、合わせて約15時間を要した。
[教師生成の高速化](archived/teacher-generation-speedup.md)も、探索の結果を変えない変更を持ち時間の対局にかけずに統合しているが、これは世代反復のブランチへの統合に限った利用者の決定であり、本書にそのまま当てはまる先例ではない。

この方式で確かめられないことも明記する。
サイクル数はプロセスの全体を数えた代わりの指標であり、持ち時間のもとで探索できる量を直接測るものではない。
固定の仕事量での探索の結果の一致は、持ち時間のもとで完了する反復深化の回数、指す手、および勝敗の一致を意味しない。
速くなった分が持ち時間の対局で何Eloになるかは、固定200ペアの対局では区別できない。
複数ワーカーの探索は、置換表の共有とノード数の割り当ての順序で結果が変わり得るので、結果の一致を確かめる対象にしていない。

探索の結果が親と一致しない変更は、本マイルストーンから外す。

## 各段階

段階1から段階3は、1つ以上の測定単位からなる。
見込みには、試作の実測がある場合はその値を書き、ない場合は未測定と書く。

### 段階1　利きの逆引きの駒コード表

利きの逆引きのうち、駒コードから駒種を復号している2箇所を、駒コードを添字にして引く表に置き換える。
試作Cに当たり、試作のサイクル数の減少は、bench深さ16で2.5%、教師生成2局で2.5%から2.8%（2回の比較の値）である。

1つ目は走りの逆引きである。
`sliding_attackers_to`は、対象升から8方向へ最初の遮蔽駒（その方向で最初に当たる駒）を求めた後、その駒が照会した対局者の駒であり、逆方向へ走る動きを持つかを調べる。
現行はこの判定に、照会した対局者の駒の集合への所属の検査、駒コードから駒種への復号、駒種から動きの定義への変換、および動きの定義から方向マスクへの表引きを使う。
これを、照会した対局者と駒コードから方向マスクを返す256要素の表の1回の表引きにする。
表は、照会した対局者の駒でない駒コード、空升、および番兵に0を返すので、所属の検査を兼ねる。

利きの逆引きは、駒がある升の集合（占有）を引数で受け取り、呼び出し元は実際の盤面と違う占有を渡すことがある。各升の駒コードは、占有によらず実際の盤面から読む。
SEEは交換列で取られた駒を占有から除き、王手判定は、動かす駒の移動元を除いて到達升を加える。
最初の遮蔽駒は渡された占有から選ぶので、除かれた駒が遮蔽駒になることはない。遮蔽駒の升について、現行の所属の検査は、実際の盤面でその升に照会した対局者の駒があるかを調べており、表の検査と同じ結果になる。
王手判定が加えた到達升が遮蔽駒になった場合、その升は実際の盤面では空升か、照会した対局者から見た相手駒か、移動元と同じ升である。空升と相手駒では表が0を返し、現行が自駒でないとして飛ばすのと同じ結果になる。移動元と同じ升である場合は、その升に動かす駒が残っているので、現行も表も同じ駒を調べる。

2つ目は固定利きの逆引きである。
`ordinary_attackers_to`は、対象升を中心とする5×5升の範囲にある自駒について、相対位置から、走りでない動き（固定利き）が届く駒種の集合を表で引き、その駒の駒種が集合に含まれるかを調べる。
現行は駒種を駒コードから復号している。
これを、駒コードから駒種のビットを返す256要素の表の表引きにする。

2つの表は`AttackTables`に加え、駒コードを0から255の添字として返すアクセサを`PieceCode`に、升の駒コードを空升も含めて返すクレート内のアクセサを`Position`に加える。
`PieceCode`のアクセサは、段階2で評価のクレートからも使うので公開する。読み取りだけを許し、添字から駒コードを作る手段は加えない。
表の値は、構築できる駒コードのすべてについて、現行の復号の連鎖の結果と一致することを単体テストで固定する。
構築できない値の欄は0とする。現行の復号は、構築できない値の一部にも駒種を返すが、そのような値は盤面に現れないので、一致の対象にしない。
逆引きの結果は、`crates/minase-core/src/movegen/tests/attackers.rs`の逆引きと駒別の利きの一致で確かめる。

### 段階2　駒種、駒状態、および駒価値の復号の表引き

段階2は2つの測定単位に分ける。

1つ目は、駒コードから駒種を返す`PieceCode::kind`を、256要素の定数の表の表引きにする変更である。
現行は、空升と番兵の検査、駒種の番号の取り出し、範囲の検査、および駒種の表引きを順に行う。
試作Dに当たり、試作Cからのサイクル数の減少は1.9%と2.6%である。
表の各欄は次のように定める。空升、番兵、および駒種の番号の欄が1から29の範囲にない値は`None`とし、それ以外は、番号から1を引いた添字の駒種とする。
構築できる駒コードのすべてについて、戻り値は現行と一致する。
構築できない値のうち、空升以外で駒種の番号の欄が0である7つの値は、現行では番号から1を引く計算が桁あふれを起こすので、リリースビルドで`None`を返し、桁あふれを検査するビルドでパニックする。表ではどちらのビルドでも`None`を返すので、この7つの値については、256通りの全部で現行の動作を保つことにはならない。これらの値は構築子から作れず、盤面に現れないので、この違いは外から観測できない。
試作Dはこの扱いをテストで固定していないので、実装では256欄の期待値を、表の定め方とは独立に書いたテストで固定する。

2つ目は、駒コードから駒状態（成りの有無を含めた47通りの駒の区分）を返す`piece_state`と、駒価値を返す`piece_value`を、それぞれ256要素の定数の表の表引きにする変更である。
再診断では、`piece_state`が探索時間の1.3%と1.6%、`piece_value`が1.1%を使っており、教師生成2局では`piece_state`の時間の約4割が`PieceCode::kind`の呼び出しである。
1つ目の単位の後に残る時間は測っていないので、見込みは未測定とする。
空升と番兵の駒コードでパニックするという現行の契約は変えない。そのため、表には無効を表す値を入れ、引いた後に検査する。
構築できる駒コードのすべてについて、戻り値とパニックの有無が現行と一致することを単体テストで固定する。

### 段階3　生成の内側での獅子の手の除外

静止探索は、獅子が経由升で相手駒を取り、移動元と異なる空升へ進む手を候補から除く。
現行は、特殊駒の全捕獲を生成してから、候補へ入れるときにこの手を捨てている。
再診断では、特殊駒の候補の生成数の35.6%と33.0%がこうして捨てられ、特殊駒の候補の生成は探索時間の1.5%と1.3%を使っている。

変更は、静止探索の候補を作る経路に限り、獅子の2段階移動の第2段階の到達升を、相手駒のある升と移動元に限ることである。
獅子の2段階移動の生成`generate_lion_double_and_jumps`は、公開の捕獲生成と主探索の捕獲生成も使うので、共通の経路は変えず、到達升を絞る指定を引数で受ける。
特殊駒の全捕獲を出力する公開のメソッド`generate_special_captures`は、公開の捕獲生成から特殊駒の手を抜き出した列と一致するという契約を持ち、その契約のテストがある。このメソッドの契約は変えず、静止探索の候補にする特殊駒の捕獲の列を出力する入口を別に加えて、静止探索の初期化はその入口を呼ぶ。
静止探索の初期化にある、生成の後の除外は削除する。
置換表の手を検査する`is_legal_capture`は変えない。この関数は、先に除外の条件を調べてから、駒1枚分の全捕獲への所属で判定している。

見込みは未測定である。
捨てている割合を特殊駒の候補の生成の時間に掛けると、探索時間の0.5%と0.4%になる（35.6%×1.5%と33.0%×1.3%）。ただし、候補1件の費用は手の種類で違うので、この値は等しい費用を仮定した概算である。

検証は、次の3つを別々の単体テストで照合する。
1つ目は、公開のメソッド`generate_special_captures`の列であり、既存の契約のテストが変わらず通ることを確かめる。
2つ目は、新しい入口の列であり、公開の捕獲生成の列を「特殊駒の手であり、除外の条件に当たらない手」に絞った順序つきの部分列と一致することを確かめる。獅子がその場の相手駒だけを取って元の升へ戻る手、2枚を取る手、経由升のない直接の跳び、および角鷹と飛鷲の手が残ることを、固定の局面でも確かめる。
3つ目は、静止探索が実際に取り出す候補の列と`is_legal_capture`の真偽である。候補の列は、置換表の手の先頭化と群の中の並べ替えを含む既存の参照実装（`crates/minase/src/search/alphabeta/tests/captures.rs`）との一致が、`is_legal_capture`の真偽は、公開の捕獲生成の集合と比べる既存のテスト（`crates/minase-core/src/movegen/tests/search_captures.rs`）が、変わらず通ることを確かめる。

### 段階4　残る負荷の診断

段階1から段階3の採否が決まった後に、採用版で関数別の内訳を取り直し、次の2点を1回だけ調べる。
本段階は診断であり、測定単位を1つも起こさずに終わってよい。

1点目は、駒コードの復号の連鎖が残っている箇所である。
`Position::piece_at`、`PieceCode::color`、`PieceCode::is_promoted`、および駒種から動きの定義への変換について、呼び出し元ごとの時間を集計する。
2点目は、通常駒の捕獲可能升の走査（`capture_targets_without_special`と、その呼び出し元の`collect_ordinary_capturers`および`generate_piece_moves`）である。
分岐予測ミスの標本の帰属と機械語を調べる。

調べた結果、探索の結果を変えずに省ける処理が具体的に見つかり、その処理の時間がどちらかの負荷で探索時間の0.5%以上である項目だけを、測定単位として起こす。
0.5%は測定単位を起こす目安であり、採用の条件は他の段階と同じである。
該当する項目がなければ、診断の記録だけを残して本段階を終える。
本段階で起こす測定単位は、利きの逆引き、手の生成、および駒コードの復号の範囲に限る。

## 実装フェーズ

1. **準備**：masterから本マイルストーンのブランチを切り、worktreeを作る。探索の結果の一致を確かめるスクリプトと、サイクル数の対比較を行うスクリプトを、[教師生成の高速化の付属資料](../measurements/teacher-generation-speedup/teacher-generation-speedup-engine/)から現行のコマンドに合わせて作り直し、測定記録の付属資料に置く。基準の出力と基準の速さを記録し、同じバイナリどうしの対比較から組数を定める。完了条件は、スクリプト、基準の出力、および組数が測定記録`movegen-speedup-3-baseline`にあることである。
2. **段階1**：駒コード表を実装し、採否を判定する（測定記録`movegen-speedup-3-stage1`）。
3. **段階2**：2つの測定単位を順に実装し、それぞれ採否を判定する（`movegen-speedup-3-stage2-kind`と`movegen-speedup-3-stage2-state-value`）。
4. **段階3**：獅子の手の除外を移し、採否を判定する（`movegen-speedup-3-stage3`）。
5. **段階4**：診断を行い（`movegen-speedup-3-stage4-diagnosis`）、測定単位を起こした場合はそれぞれ採否を判定する。
6. **最終測定と統合**：採用版と基準の対比較を、段階の判定とは別の測定として行い、速度比を求める（`movegen-speedup-3-final`）。固定200ペアの対局、または利用者が求めた場合は段階ゲートを行い、残る負荷の内訳を記録する。「完了条件」の節の統合の条件を満たせば、設計判断をADRへ、表の仕様をdocコメント（コードに付ける仕様の説明）へ移し、masterへ統合する。完了条件は、統合するかどうかが測定記録とともに確定していることである。採用した測定単位が1つもない場合は、最終測定を行わない。

段階1から段階4のフェーズの完了条件は、該当する段階の採否が測定記録とともに確定していることである。
プログラムの実装は、[委任の手引き](../guides/codex-delegation.md)に従って測定単位ごとに別のエージェントへ委任し、採否の測定は、委任した側が測定機に負荷のない状態で行う。
採用しなかった測定単位のコミットは、ブランチから外す。

## 検証

実装した測定単位ごとに、次を実行する。

```console
cargo fmt --check
cargo clippy --release --all-targets
cargo test --release
```

`cargo test`は、探索のほかに利きの逆引きと公開の手生成を使う処理の検査を含む。公開の手生成の集合と順序の契約テスト、審判層の裁定を全手生成による参照と比べるテスト、詰みの探索のテスト、および複数ワーカーの探索のテストである。
先獅子（獅子を取った直後の取り返しを制限する規則）、成り権の保留、履歴を使う反復の判定、および終局の裁定は、その状態を与える既存の境界のテストで確かめる。

探索の結果の一致は、探索ワーカーを1にした固定の仕事量について、基準のバイナリで記録した次の4種類の出力と、候補の出力を比べて確かめる。

- `bench`の深さ16の15局面の行のうち、ノード数、最善手、および評価値を比べる。
- 教師生成のファイルのSHA-256と探索ノード数の合計を比べる。シード`9010200000`の2局と、シード`424242`の4局の2通りを使う。
- 7つの規則セット（`JCSA`、`lishogi`、および規則コードを並べた`L1,L3,P0,P5,P6,R2,E1,E2`、`L0,P0,R3,E0`、`L0,P1,R1,E0`、`L1,L2,P2,P3,P4,R2,E0`、`L0,L4,P0,R1,E0`）のそれぞれで、`bench`の15局面を6万ノードで探索し、`bestmove`までにエンジンが出力した最後の`info depth`の行の深さ、ノード数、評価値、および読み筋と、`bestmove`の手を比べる。
- 同じ7つの規則セットのそれぞれで、`bench`の15局面から`perft 2 divide`（深さ2までの合法手の経路数を、最初の手ごとに出力するコマンド）を実行し、最初の手ごとの行を出力の順序も含めて比べ、深さごとの経路数と総数の行も比べる。

`info`行の経過時間と毎秒ノード数は実行ごとに変わるので比べない。
`perft`の経過時間と毎秒ノード数の行も比べない。
どの検査も、基準と候補の両方が所定の数の行（`bench`は15行、規則セットを使う検査は7×15局面分）を出力したことを確かめ、行や比べる欄が欠けた場合は不一致とする。
`bench`の規則セットは`JCSA`に、教師生成は`lishogi`に固定されているので、成り権の保留や先獅子の扱いが違うほかの規則コードの経路は、3つ目の検査で確かめる。
4つ目の検査は、公開の手生成の最初の手の順序と経路数を見る補助の診断である。経路数は手の順序の入れ替えを検出できないので、公開の手生成の契約は`cargo test`の契約テストで確かめる。

教師生成は、実行時の作業ディレクトリのコミットを教師のファイルに書く。また、対局をまとめて保存する単位（塊）が出力先にすでにあると、探索せずに、その塊から教師のファイルを作り直す。
そのため、教師生成の比較では、基準と候補のバイナリを同じコミットの変更のない作業ディレクトリから起動し、実行のたびに空の出力先を使う。
生成が完了したこと、対局数、および探索ノード数の合計が基準と同じであることを、ファイルのSHA-256と合わせて確かめる。

サイクル数の対比較は、性能コアの論理CPU（測定機では3番）に固定して次の2つを測り、1組ごとに候補と親の順序を入れ替える。

```console
taskset -c 3 perf stat -x, -e cpu_core/cycles/u,cpu_core/instructions/u,cpu_core/branch-misses/u -- \
  <バイナリ> --protocol usi < bench16.usi
taskset -c 3 perf stat -x, -e cpu_core/cycles/u,cpu_core/instructions/u,cpu_core/branch-misses/u -- \
  <バイナリ> data selfplay generate --eval-file <ネット> --output-dir <空の出力先> --chunk-games 2 --games 2 \
  --seed 9010200000 --nodes 20000 --random-moves 0 --concurrency 1 --hash-mb 16
```

`bench16.usi`は、`setoption name RuleSet value JCSA`、`setoption name EvalFile value <ネット>`、`isready`、`bench depth 16 threads 1 repetitions 1`、`quit`の5行である。
測定の前に、対局の測定、探索の係数の自動調整（SPSA）、および教師生成が同じ機械で動いていないことを確かめる。
測定記録は`docs/measurements/movegen-speedup-3/`に置き、組ごとの値、平均、信頼区間、および探索の結果の一致を書く。

## 完了条件

次の記録は、結果によらずそろえる。

- 段階1から段階3の測定単位と、段階4で起こした測定単位の採否。採用しない測定単位の理由と測定値を含む。
- 段階4の診断の記録。
- 採用した測定単位がある場合は、採用版と基準の対比較による最終測定の記録。

採用版をmasterへ統合するのは、測定の結果が次のすべてを満たす場合である。

- 採用版の探索の結果が、「検証」の節の4種類の出力のすべてで基準と一致している。
- 最終測定で、bench深さ16と教師生成2局のどちらでも、速度比の両側95%信頼区間の下端が1.02倍以上である。速度比の平均が1.05倍に届かない場合は、速度比と残る負荷の内訳を記録する。
- 固定200ペアの対局で、エンジン異常、時間切れ、および拒否着手が0件である。利用者が段階ゲートを求めた場合は、この条件に代えて、採用版と基準の段階ゲートが[SPRTの手引き](../guides/sprt.md)の規則で採用の判定になることを条件とする。

固定200ペアの対局で異常が1件でもあれば、原因を調べる。原因が測定機の外部要因であると確かめられた場合は、その原因を記録して測定を無効とし、原因を除いた後に固定200ペアの全体を取り直して、取り直した測定で0件を求める。原因が本書の変更にあれば、探索の結果の一致の検査が見逃した不具合として直し、直した版で検証と最終測定をやり直す。

最終測定の前に、次の仕上げを済ませる。最終測定と対局の後に実行コードを変えた場合は、変えた後の版で検証と最終測定をやり直す。

- `cargo test --release`、`cargo clippy --release --all-targets`、および`cargo fmt --check`を通す。
- 採用しなかった方式、使われない表、および測定のためだけに入れた処理を取り除く。

設計判断のADRへの移し替えと、表の仕様のdocコメントへの移し替えは、実行コードを変えないので、最終測定の後、統合の前に行う。

統合したときの状態は、採用しなかった測定単位がなければ完了（採用）、あれば完了（一部不採用）とする。
採用した測定単位が1つもない場合と、測定の結果が統合の条件を満たさない場合は、採用版をmasterへ統合せず、理由と測定値を記録して、状態を完了（不採用）とする。
利用者の決定で、これらの判定に至る前に計画を閉じる場合は、[設計書の書き方](README.md)に従って状態を中断とする。

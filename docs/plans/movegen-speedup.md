# 合法手生成と利き計算の高速化の設計書

## 先に読む要約

本マイルストーンでは、探索結果を保ったまま、探索が1秒間に処理する局面数（NPS、ノード数を経過時間で割った値）を基準コミットの2倍以上にすることを目標とし、1.5倍以上を最低受入条件とする。
基準コミットは、[局面別の比較の測定記録](../measurements/bench-movegen-oneside-depth5.md)が記録するmasterのコミットである。
負荷の大半は静止探索（駒を取る手だけを読み進める探索の末端）にあるので、静止探索が結局捨てる捕獲を生成前に除き、必要な捕獲だけを価値の高い順に段階的に生成する。
静的交換評価（SEE、到達升での駒の取り合いを見積もる評価）は、枝刈りしないと確定した時点で残りの計算を省く。
指定升へ届く駒を求める利き逆引きの片側化（単位A）は採用済みであり、固定局面を固定深さで探索する測定プログラム`bench`の15局面で照合参照コミットとノード数、最善手、探索値が一致し、NPSは基準比1.319倍である。
プロファイル誘導最適化（PGO、代表的な実行頻度をビルドへ反映する方法）は、基盤を作る前に効果だけを先に測る。
探索木を変えない変更は、局面別のノード数、最善手、探索値の一致とNPSの増加で採否を決め、自己対局の逐次確率比検定（SPRT）は最終的な採用版に対して1回だけ行う。
探索木の一致は、基準コミットに静止探索の手順の小さな変更を加えた照合参照コミットに対して確かめ、速度の基準は基準コミットのままとする。
この採否の方式は本マイルストーンに限る利用者の決定であり、理由は設計判断の節に記す。
最低受入条件を満たし、必須候補の採否が確定し、最終のSPRTが長時間条件で採用判定（`H1`）を得たら完了とし、2倍に達しなければ差と残存負荷を測定記録に残す。

## 目的

合法手生成と利き計算の費用を減らし、同じ時間でより深く探索できるようにする。
速度比の基準は基準コミットであり、以後の測定はこのコミットを`git archive`で展開したビルドと比較する。
[プロファイルの測定記録](../measurements/bench-movegen-profile-depth5.md)では、基準の`bench`（深さ5、1スレッド、3回の中央値）は0.845秒、片側化を含む試作は0.639秒であり、その比が約1.32倍である。
同じ探索木で基準比2倍を達成するには0.4225秒以下、すなわち試作からさらに33.9%の時間削減が必要であり、1.5倍には0.5633秒以下、試作から11.8%の削減で足りる。
この時間目標は後述の回転の前の参考値であり、回転で探索木が変わった後は、基準のノード数を`N_B`、照合参照コミットのノード数を`N_R`、基準の経過時間を`T_B`として、NPSを`k`倍にする時間条件を`T ≤ T_B × (N_R / N_B) / k`で再計算する。
削減する処理の件数と実行時間を分けて測り、効果が重なる案の改善率を加算しない。

## 適用範囲

対象は次のコードとビルド手順である。

- `src/core/movegen/`は合法手の生成と利きの逆引きを実装する。
- `src/core/attacks/`は駒種ごとの動きの定義と利きの前計算表を実装する。
- `src/core/bitboard.rs`は144升の集合を3個の64ビット整数で表し、走り計算の代替方式に着手する場合だけ対象になる。
- `src/core/rules.rs`は獅子捕獲後の足と成りを判定する。
- `src/search/see.rs`は交換列を評価し、探索で捕獲手を捨てるかを判定する。
- `src/search/mod.rs`の静止探索が生成器を呼び、置換表の手を先頭へ移す。
- PGOの比較は`Cargo.toml`、`.cargo/`、およびプロファイルの生成手順を対象とする。

本書では次の用語を使う。
**升**は盤の目、**ノード**は探索が訪れた局面である。
**走り**は任意の升数を進む動き、**利き**は駒が次の1手で到達できる升の集合である。
**疑似利き**は獅子の捕獲規則などの合法性を考慮せず、駒の動きと盤上の遮蔽だけから求めた利きである。
**経由升**は獅子、角鷹、飛鷲の2段階移動で第1段階に止まる升であり、**居喰い**は隣接する相手駒を第1段階で取って元の升へ戻る手、**2枚取り**は第1段階と第2段階で1枚ずつ取る手である。
**取り手**はある升の駒を取れる手番側の駒、**成り益**は成ることで増える駒価値である。
**置換表**は探索済み局面の結果を保存する表であり、置換表の手はそこに保存された前回の最善手である。
**特殊利き**は獅子の跳びと、獅子、角鷹、飛鷲の2段階移動による到達範囲であり、**仮想占有集合**は交換列の途中で取り除いた駒を除いた盤上の占有状態を表す集合である。
**公開生成**はライブラリの利用者へ全合法手または全捕獲手を返す生成であり、**探索専用生成**は探索の内部でだけ使い、探索が検査しない手を省いてよい生成である。

探索の枝刈り条件、評価関数、時間管理、規則の解釈、着手の正準表現は変えない。
主探索の着手選択も変えず、静止探索で置換表の手を先頭へ移す方法だけを設計判断の節のとおり回転へ改める。
公開の全手生成と捕獲生成では、着手集合、順序、合法性、および`perft`の経路数を維持する。
探索専用の部分生成は、入口条件で必ず捨てる手と、先行手による探索打ち切り後に検査されない後続グループの生成を省く。
除外後に残る手の順序を以下では**残存手順**と呼び、探索打ち切りまでに実際に検査する手の列を参照と一致させる。

局面別の一致の参照は、基準コミットに回転の変更と`bench`の出力拡張だけを加えた**照合参照コミット**とする。
探索の実装で参照が基準と異なる点は回転だけであり、`bench`の出力拡張は参照と全候補に共通して含める。
回転は探索木を変えるので、基準そのものとの一致は回転の前までしか成り立たない。
速度比は基準コミットとのNPS中央値の比で報告し、ノード数の比と経過時間の比も併記する。
同じ探索に対する高速化は、照合参照コミットとの比較で報告する。

SEEを正確な値として計算する経路には、値と判定不能を表す`None`の一致を求める。
早期終了を導入した後の本番経路は`new_prune == reference_see.is_some_and(|value| value < 0)`を契約とし、正確な値計算は検証専用の参照実装に置く。
数値を返す関数の結果を真偽値で代用したり、`None`を負の評価値へ読み替えたりしない。
参照実装は互換用の実行経路にはしない。

## 設計判断

### 処理を省く順に着手する

基準コミットのプロファイル（[測定記録](../measurements/bench-movegen-profile-depth5.md)）では、静止探索配下が性能コアの標本の76.2%、SEEの利き逆引きの自己時間が合計29.8%、捕獲生成配下が31.2%であった。
主探索の全手生成配下は5.1%なので、静止探索を先に改修する。
片側化の試作後は捕獲生成配下が40.5%へ増え、走りの利きを求める計算（`piece_control_without_special`と`sliding_control`）が逆引きと捕獲生成の両方に残る。
これらの割合は計測区間外の置換表クリアと起動を含み、包含時間にも重複があるため、そのまま探索全体の速度倍率へ換算しない。

[処理件数診断](../movegen-speedup-ideas.md)では、生成した捕獲の39.3%が入口の評価値で除外できる経由升なしの手であり、48.5%は途中の打ち切りでループ内の検査まで到達しなかった（いずれも診断の件数比）。
捕獲生成を呼んだノードの30.0%では全捕獲が入口で捨てられるのに、現行の静止探索はそのノードでも全生成、整列キーの計算、整列、およびバッファの確保を行っている。
この2群は重複し、件数と処理時間も比例するとは限らない。
それでも、生成してから処理を省く現状には削減対象が存在するため、捕獲対象の事前除外と静止探索の段階生成を、走り利きの演算方式の変更より先に比較する。

### 利き逆引きを片側へ絞る

利き逆引きは対局者を引数に取り、SEEと王駒への利き判定が必要とする側だけを返す。
走りは、駒種ごとに利きを引く代わりに、対象升から8方向へ利き線を伸ばして最初の遮蔽駒を調べ、その駒が逆方向へ走れるかで判定する（以下、方向主導化）。
現行の全28種類の動きの定義で走りが距離無制限である前提を明記し、仮想占有集合での契約テストを保つ。
特殊移動を持つ駒種は獅子、角鷹、飛鷲だけなので、特殊利きの走査もこの3種に限定する。
この3変更は一体で試作し、`bench`の15局面で基準とノード数が一致し、NPSは約1.32倍だった。
個別の速度寄与は測っていないので、3変更をまとめて1つの測定単位とする。

### 静止探索の置換表の手を回転で先頭へ移す

現行の静止探索は、整列済みの捕獲列で置換表の手を見つけると`swap(0, index)`で先頭と交換する。
この交換は、整列で先頭にあった最高評価の捕獲を置換表の手の位置まで降格させる。
例えば整列済みの列が`[a, b, c, t, d]`で置換表の手がtなら、検査順は`[t, b, c, a, d]`になる。
この癖を段階生成で再現するには、整列済みの全捕獲列の中での置換表の手の位置と、それより前で入口除外される手の数を知る必要があり、置換表の手自体が入口除外される場合は交換の有無で残存手順が変わる。
順位を知るには上位グループをすべて生成しなければならず、後続グループを生成しないという段階生成の利点が消える。

したがって、段階生成の前に、置換表の手を先頭へ移し他の手の相対順序を保つ回転へ改める。
回転後の参照列は「置換表の手が合法な捕獲として残るならそれを先頭に、続いて整列済みの列から置換表の手を除いたもの」であり、段階生成はこの列を追加の情報なしに再現できる。
回転は他の手の相対順序を保つが、静止探索は手ごとにαを更新して打ち切るため、順序差が未訪問の部分木の規模を変え得る。
探索木への影響量は未測定なので、回転単独でノード数、最善手、探索値の差を記録する。
回転は探索木を変える唯一の変更なので、照合参照コミットとして基準の直後に置き、以後の局面別一致はこのコミットに対して確認する。
回転単独の棋力への効果は最終のSPRTに含めて判定し、単独のSPRTは行わない。

### 捕獲対象を生成前に除外する

静止探索の入口で、局面の静的評価値を`stand_pat`、それまでに見つかった最善値の下限αを`stand_pat`で引き上げた値を`alpha_entry`、既存の枝刈りが見積り誤差のために足す余裕値を`delta_margin`とする。
通常捕獲では`captured_value <= alpha_entry - stand_pat - delta_margin`を満たす対象を生成前に除ける。
この条件を満たす手は、取る駒の価値を丸ごと得たとしても評価値が`alpha_entry`を超えないので、探索しても最善値を更新できない。
αはそのノードで見つかった最善値の下限であり、より良い手が見つかったときに引き上げるだけなので、ノード内で低下しない。
したがって、入口でこの条件を満たす手は後でも捨てられる。
探索中に引き上がったαでの既存の判定も維持する。

静止探索は、この閾値を超える価値の相手駒がある升の集合（以下、対象升）を作り、生成器の探索専用の入口へ渡す。
生成器は対象升へ到達する捕獲だけを作る。
最初の適用は経由升を持たない手に限り、最後の王駒を取る手は必ず残す。
経由升を持つ手は2枚の駒価値の合計で判定するので、1升の駒価値では除外を決められない。
そのため経由升を持つ手は専用経路で生成し、2枚取りを含む捕獲価値の合計と王駒捕獲の例外を判定する。
相手駒の価値だけを見て、居喰いや2枚取りの候補を除いてはならない。

自駒ごとに全方向の利き線と固定利きが対象升と交わるかを検査し、交わらなければ通常捕獲の走り計算を省く。
走りの到達升は遮蔽を考慮しない利き線の部分集合なので、利き線が対象升と交わらなければ到達升も交わらない。
特殊手は経由升の捕獲もあるため、この検査だけでは除かない。
残る候補は中間バッファを経由せず整列キー付きで出力し、生成時に得た捕獲升を規則判定と整列に渡す。
成れない駒と成駒では成り判定を打ち切り、獅子規則は実際に取る升の集合が相手獅子と交わる場合だけ調べる。
角鷹が前方の獅子を居喰いする例では到達升が移動元に戻るため、経由升の検査を省かない。

バッファは探索ワーカーが深さごとに所有して再利用し、ノードごとの新規確保をなくす。
深さごとに持つのは、再帰の各深さで同時にバッファが使用中になるからである。
診断ビルドで容量拡張と整列内部の確保も数え、同じ診断標本の一巡後には生成と整列の確保が0回になることを検査する。
最大合法手数を証明していない固定長配列や、未測定の全局面に対する再確保0の保証は採らない。

### 静止探索の捕獲を段階的に生成する

捕獲価値が高いグループから生成し、同じグループでは攻撃駒価値の昇順と元の生成順を保つ。
価値の高い捕獲は評価値を最も大きく引き上げ、探索上限βを超えて打ち切りを起こしやすいので、この順序なら後続グループを生成せずに済むノードが増える。
枝刈りでノードの探索が終わったら、後続グループは生成しない。
価値グループごとの打ち切り位置も数え、同じグループ内で既に生成済みとなる分を削減見込みから除く。

生成は、対象升から取り手を逆引きする方式と、対象升を使う駒別生成を比較し、駒別生成を採った（[単位Bの記録](../measurements/movegen-speedup-unit-b-bench-depth5.md)）。
駒別生成では、通常駒の利きをノードの初期化で1回だけ求めて対象升との積を保持し、各グループでは保持した集合とグループの対象升の積だけを出力する。
駒価値の降順の順位は探索中に変わらないので探索ワーカーの生成時に前計算し、ノードごとのグループ構築は順位のビット集合で行い、整列と線形探索を置かない（[段階生成の固定費](../lessons/staged-generation-fixed-cost.md)）。
逆引きの結果は疑似利きなので、それだけで合法手として出力しない。
特殊移動の経由升、居喰い、2枚取りの正準表現と成り展開は専用の生成処理を通す。
2枚取りは2枚分の捕獲価値で分類し、同じ手を経由升と到達升から重複出力しない。
比較の正は回転後の参照列であり、同値性を保てない段階生成は採用しない。

### SEEの不要な反復を省く

初手で取る駒の価値をC、動く駒の成り前後の価値をMとP、相手の最初の取り返しに伴う成り益をdとする。
現行SEEの利得列の最初の2項は`g0 = C + P - M`と`g1 = P - g0 + d = M - C + d`である。
`g0`は相手が取り返さない場合に手番側が得る値、`g1`は相手が最初に取り返した場合に相手が得る値である。
取り返しが存在する場合、逆算結果は後続値Xを用いて`min(g0, max(-g1, X))`となるため、`g0 >= 0 && g1 <= 0`なら非負である。
初手が損でなく、かつ最初の取り返しが相手の得にならなければ、手番側はその後どこで交換を止めても損をしないからである。
この条件が成立したら「枝刈りしない」と返し、残る逆引きと利得の逆算を省く。

後続で獅子規則により`None`になる場合も、参照実装は枝刈りしないため判断が一致する。
負と判定して早期に枝刈りする方式は、後続で`None`にならないことを証明していないので採らない。
相手の成り益と、初手の強制成りで価値が下がる場合も扱い、単にCとMだけを比べる条件へ簡略化しない。
相手が取り返せない場合と初手から規則依存になる場合は、参照実装と同じ枝刈り判断を返す。

[診断](../movegen-speedup-ideas.md)で省略可能だった逆引きはSEE内の呼び出しの12.3%であり、最初の取り返しを求める逆引きは早期終了後も残る。
呼び出しごとの費用が等しいと仮定すると、試作後の逆引きの自己時間（標本全体の約10%）との単純積は約1.3%であり、探索時間の削減率はこの仮定なしには決まらないので、同じ構成での件数と探索区間内の包含時間を測って見積もる。
いずれにせよ数%の規模なので、この単位は局面別一致とNPSで採否を決める方式でなければ判定の費用に見合わない。
早期終了を単独で比較した後、残る反復の費用を測り、占有集合から除いた駒によって開く走りだけを計算し直す差分更新と、占有に依存しない利きの事前計算を単位Cの後続比較として加えるか決める。
測定では3回目以降の逆引きが全体の約21%で、後続比較で省ける時間は全体の1〜2%にとどまるため、どちらも実施しない（[単位Cの記録](../measurements/movegen-speedup-unit-c-bench-depth5.md)）。

### 探索木を変えない変更は局面別一致と速度で採否を決める

本マイルストーンの変更は、回転を除き、固定深さの探索で局面別のノード数、最善手、探索値を変えない。
このような変更の棋力への効果は、実時間で到達する深さの増加を通じてだけ現れる。
深く読めば棋力が上がることは期待できるが、単調性の保証ではない。
Stockfishの開発でも、`bench`の結果が変わらない高速化は原則としてfishtestへ出すが、検定で検出できない微小な高速化は速度測定などの別の証拠で扱う例外がある。

単位ごとにSPRTを行う方式は、微小な高速化の判定に費用がかかりすぎる。
自己対局では持ち時間2倍が約216 Eloに相当する（[感度測定](../measurements/sensitivity-time2x.md)、別コミットで得た値であり線形性は仮定しない目安）。
持ち時間の倍率を対数で換算すると、2%の高速化は`log2(1.02) × 216`で約6 Eloであり、SPRTの仮説H0（0 Elo）とH1（10 Elo）の谷に落ちる。
[SPRTの手引き](../sprt.md)の期待ペア数では、谷の中央の5 Eloで約4,200ペアを要し、長時間条件（LTC、1局あたり約216秒）では同時16対局でも30時間規模になるうえ、正しい変更がH0で棄却され得る。
SEEの早期終了のような数%の単位は、この方式では現実的な費用で採否を判定できない。

そこで、探索木を変えない各単位は、照合参照コミットとの局面別一致とNPS中央値の増加で採否を決める（利用者の決定、本マイルストーンに限る例外）。
SPRTは最終的な採用版と基準コミットの間で1回だけ行い、短時間条件（STC）の振分け、長時間条件の再開による延長、および異常時の停止は[SPRTの手引き](../sprt.md)の標準どおり適用する。
1.5倍の速度は同じ換算で`log2(1.5) × 216`、約126 Eloに相当するので、この検定は数百ペアで決着する見込みである（参考見積り）。
長時間条件の判定保留は同じ測定を`--resume`で延長し、`H0`なら採用版を採用せず、マイルストーンは完了しない。
`H0`の場合は原因調査として、回転だけを加えたコミットを基準と比べる測定を別に行い、探索木を変えた回転の影響と速度の効果を切り分ける。

### PGOは効果を測ってから基盤を作る

PGOは、代表入力で実行頻度を集めるビルド、その実行、プロファイルの集約、およびプロファイルを適用するビルドの順に行う。
既に有効なCPU向け最適化とリンク時最適化は両版で同じにし、`RUSTFLAGS`を使う診断では`-C target-cpu=native`も明示する。
学習用と測定用の局面を分け、序盤、中盤、終盤、獅子戦を含む入力、規則、および実行コマンドを測定前に固定する。

最初の比較は、捕獲生成とSEEの改修が終わった時点の同じソースで、通常版とPGO版を手動ビルドして行う。
この時点で測るのは、手動の最適化がPGOの効果（分岐配置やインライン化）と重なるためであり、改修前に測った値は改修後に流用できない。
測定用の標本でNPS中央値が10%以上増えなければ、基盤を作らずにPGOを不採用として記録する。
10%は、プロファイルの再生成と保存という継続的な負担に見合う下限として置く判断値である。

10%以上増えた場合だけ、採否測定へ進むための再現条件を整える。
`match_runner`はコミットを`git archive`で展開して標準の`cargo build --release --bin minase`でビルドし、完全なコミットハッシュでバイナリをキャッシュするが、外部フラグやツールチェーンの一致は検査しない。
したがって、プロファイルと適用設定は候補コミットに含め、パスは展開先から解決し、同じコミットに異なる外部フラグを与えた成果物を採否測定に混在させない。
学習対象ソースと入力の識別子、RustとLLVMの版、プロファイルのSHA-256、およびビルド手順を記録し、標準ビルドが実行する検証処理で、最適化対象のソース、評価データ、依存関係、ツールチェーン、適用設定の識別子をプロファイル作成時の記録と照合する。
対象ファイルの追加と削除も検出し、不足、不一致、非対応のプロファイルは明示的にビルドを失敗させ、通常ビルドへ黙って切り替えない。
新規のキャッシュで候補と親をそれぞれビルドし、診断に使った対局バイナリと同じ構成であることを確認する。
照合するソースは対局バイナリのコンパイル対象に限定して文書とテスト専用ファイルを除き、プロファイルと検証記録自身はハッシュ対象から外して循環参照を避ける。
PGOの採用後に上記の照合対象（ソース、評価データ、依存関係、ツールチェーン、適用設定）のいずれかが変わる場合は、固定済みの学習入力と手順でプロファイルを再生成して候補コミットへ含め、親は親コミットに固定したプロファイルでビルドし、学習入力や最適化設定の調整は同じ比較へ混ぜず、通常ビルド同士の補助診断も記録する。
再生成時間、プロファイル容量、複数回更新した場合のgitオブジェクトの増分を測り、速度の利益と併記したうえで採否測定へ進むか決める。
ハーネスへPGOの有無を切り替える機能比較スイッチは追加しない。

### 残存負荷に応じて代替方式を比べる

以下は必須の実装ではなく、単位AからDまでの後のプロファイルと件数から着手の理由を記録できる場合の候補である。
候補ごとに1方式へ絞ってから1単位として測り、使わない表、フィールド、実行経路は残さない。
実装の詳細は、着手する候補についてだけ、着手時に本節へ書き加える。

| 候補 | 着手の条件 | 検証条件 |
|---|---|---|
| 同じ捕獲先の準備（固定利き、特殊利き、遮蔽駒の並び）をノード内で共有する。 | SEEの逆引きが主要な自己時間として残り、同じ到達升への再照会率（診断では19.7%）が残っている。 | SEE値は動かした駒の後ろに開く利きに依存し、同じ到達升でも動かす駒ごとに異なるので、移動元の除去による開通を手ごとに反映し、到達升だけでSEE値を共有しない。共有情報はノードをまたいで再利用せず、成り、2枚取り、居喰い、手番変更、復元で古い状態を参照しないことを検査し、構築費と容量の増加も計測する。 |
| 成りと不成りの交換列を共有する。 | 同じ移動元と到達升への再照会率（診断では9.9%、共有できない麒麟を含む上限）が残っている。 | g1から初手の成り後価値が消えることを使い、麒麟が獅子に成る場合を除き、元の手順と規則依存の判定を保つ。 |
| 固定利きの逆引きを近傍走査に変える。 | 単位Aの後も固定利きの逆引きが主要な自己時間として残っている。 | 契約テストで駒別の利きとの同値を保つ。 |
| 固定利きを移動量ごとの集合演算で求める。 | 捕獲生成の固定利き計算が主要な自己時間として残っている。 | 集合の構築または維持、元の生成順への復元、着手適用と復元の費用を含めて比較する。集合を差分維持する場合は、成り、2枚取り、居喰い、手番変更、復元のそれぞれで、再計算した集合との一致を検査する。 |
| 走り計算を別方式（最初の遮蔽駒だけの照会、線占有の圧縮表、分岐のない192ビット演算）に置き換える。 | 走り計算の自己時間が主要な負荷として残っている。 | 逐次歩行を参照に、ワード境界、両方向、遮蔽なし、複数遮蔽、仮想占有、着手適用と復元を検査する。圧縮表は長さ12の全起点と4,096通りの占有を網羅し、短い斜線と盤端も照合する。3方式のうち勝者だけを残す。 |
| 獅子系の生成と列挙を整理する。 | 獅子、角鷹、飛鷲の生成が主要な自己時間として残っている。 | 仮想盤面、ビットボードの列挙、色を反映した動きの定義の巻き上げを比較し、NPSが増えた変更だけを残す。 |
| 置換表行をプリフェッチする。 | 置換表の照合にメモリ待ちが残ることをプロファイルで示せる。 | 探索結果が一致し、命令数と取得データの使用率も測る。 |

主探索の着手選択の変更は、探索順を変える棋力向上の課題であり、本設計書の範囲外とする。

### 採否を機能単位で決める

次の単位ごとに、候補を1コミットへまとめて、直前の採用版である親コミットと比較する。
単位内のフェーズは検証点であり、個別に事前選別してから、残った変更を一体として判定する。
棄却した単位は次の親に含めず、条件付き候補を実装しない場合もその理由と根拠のプロファイルを記録する。

| 測定単位 | 対象 | 採用の条件 |
|---|---|---|
| A | 片側化、方向主導化、特殊利きの走査限定。 | 照合参照コミットとの局面別一致と、NPSの増加。 |
| B | 捕獲対象の除外、規則判定の早期終了、バッファ再利用、静止探索の段階生成。 | 各検証点での残存手順と局面別の一致と、統合版のNPSの増加。 |
| C | SEEの早期終了と、その後続比較の差分更新。 | 全捕獲の枝刈りの真偽値と局面別の一致と、NPSの増加。 |
| D | PGO。 | 分離した入力でNPSが10%以上増え、再現条件と継続負担を評価して進むと決めている。 |
| E | 残存負荷に応じて選んだ代替方式。 | 着手の条件を満たし、必要な生成契約とSEE判定と局面別の一致と、維持費を含むNPSの増加。 |

Eで互いに独立した候補を複数試す場合は、E1、E2のように分け、各候補の採否を確定してから次へ進む。
速度が増えない検証点や候補は外し、事前選別で棄却した場合は自己対局を行ったと記録しない。
全単位の採否が確定したら、最終の採用版と基準コミットのSPRTを1回行う。

## 実装フェーズ

1. 計測基盤を整える。
   `bench`の局面別出力に最善手と探索値を計測区間外で加え、照合参照コミット（探索の差分は回転だけ、出力拡張を含む）を作る。
   処理件数は既存の[診断差分](../measurements/movegen-speedup-ideas-counts/diagnostic.patch)を再利用して数え、価値グループごとの打ち切り位置を追加する。
   生成数、入口で棄却できる手数、価値グループ別の未訪問数、およびSEEの逆引きと早期終了の件数は独立した参照と突き合わせ、不一致なら診断を停止して原因を調べる。
   完了条件は、照合参照コミットとの局面別比較が1コマンドで実行でき、診断用と速度用のビルドが分離されていることである。
2. 単位Aを確定する。
   両対局者と仮想占有の契約テストを通し、照合参照コミットとの局面別一致と速度を確認する。
   完了条件は単位Aの採否が確定していることである。
3. 単位Bを確定する。
   まず捕獲升と整列キーの受け渡し、規則判定の早期終了、バッファ再利用を検証し、次に入口の閾値による対象除外を加え、最後に段階生成を接続して逆引き方式と駒別生成を比較する。
   公開生成の順序一致、探索専用の残存手順一致、局面別の一致、標本一巡後の確保0回、およびNPSの増加を検証点ごとの条件とする。
   完了条件は通過した変更で単位Bの採否を確定するか、不採用の理由を記録していることである。
4. 単位Cを確定する。
   早期終了を単独で比較し、残る費用を測って差分更新と特殊利きの事前計算を加えるか決める。
   全捕獲の真偽値と参照SEEの一致、局面別の一致、およびNPSの増加を条件とする。
   完了条件は単位Cの採否、または不採用の理由が記録されていることである。
5. 単位Dを判定する。
   分離した入力で通常版とPGO版を手動ビルドで比較し、10%以上なら再現条件と継続負担を評価して進むか決める。
   完了条件は単位Dの採否、または速度診断までにとどめる理由が記録されていることである。
6. 単位Eを判定する。
   残存負荷から着手の条件を満たす候補だけを実装し、選んだ候補ごとに正しさと総費用を確認する。
   完了条件は単位Eの採否を確定し、着手しない候補の理由も記録していることである。
7. 最終のSPRTを行う。
   採用版と基準コミットをSTC、続いてLTCで比べ、結果を測定記録に残す。
   完了条件はLTCの`H1`と、エンジン異常、時間切れ、拒否着手が0件であることである。

## 検証

実装したフェーズでは次を実行する。

```console
cargo fmt --check
cargo clippy --release --all-targets
cargo test --release
target/release/bench --depth 5 --repetitions 3 --threads 1
target/release/perft 3
```

実行前に対象バイナリを通常のrelease設定でビルドし、速度測定中は他のCPU負荷を止める。
呼出履歴を採るためフレームポインタを有効にしたビルドの性能測定、確保回数の診断、および処理件数の診断は別ビルドで行い、その経過時間をNPS比較へ混ぜない。
`perft`の検査つき着手適用の費用を合法手生成単体の速度と読まない。

局面別の一致は、照合参照コミットの`bench`（1回実行）の局面別のノード数、最善手、探索値を保存し、候補の出力と全行で比較する。
生成の正は全規則セットの既存契約とし、探索専用生成は入口の評価値と置換表候補を固定した参照列と比較する。
同じ価値の手、成りと不成り、捕獲対象が空、特殊手だけが残る局面、置換表候補が入口除外となる局面を含める。
捕獲価値と閾値が等しい境界、2枚取りの合計だけが閾値を超える例、最後の王駒の捕獲、角鷹の居喰いによる先獅子の禁止も検証する。
段階生成では、任意のグループ境界で停止したときに未生成の後続があることと、列を最後まで要求した場合の参照列一致を検査する。

SEEは`bench`の15局面とシードを固定した乱数対局の標本で、全捕獲手の枝刈りの真偽値を参照値計算と比較する。
値0、強制成りで価値が下がる場合、相手の成り益、初手から判定不能の場合、交換列の後方で判定不能になる場合を含める。
差分更新を統合する前には、交換列を完走する診断で値と`None`の一致も確認する。

単位Eに着手した場合は、候補表の検証条件に従い、着手時に本節へ検査項目を加える。
PGOは入力分割、プロファイル、および候補コミットからの対局バイナリの再現を確認する。
最終のSPRTは測定名ごとに`docs/measurements/`へ記録する。

## 完了条件

採用版が照合参照コミットと局面別のノード数、最善手、探索値で一致し、通常ビルドまたは採用済みのPGOビルドのNPS中央値が基準コミットの1.5倍以上である。
2倍以上を目標とし、未達なら基準比、残りの時間削減量、残存負荷を同じ測定条件で記録する。

必須候補AからDについて採否が確定し、条件付き候補Eについても採否または実施しない根拠が記録されている。
採用版と基準のSPRTがSTCの振分けを通過し、LTCで`H1`かつエンジン異常（`engine_failures`）、時間切れ（`time_forfeits`）、拒否着手（`rejected_moves`）が0件である。
`perft`、全規則セットの公開生成契約、探索専用生成の残存手順、利き逆引き、およびSEEの枝刈り判断の検証が通過している。
採用しなかった方式、旧方式との互換のために残す経路、使われない状態、および計測のためだけに本番の経路へ入れた処理が残っていない。

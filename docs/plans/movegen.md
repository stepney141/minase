# 中将棋の合法手生成の設計書（第3版）

## 1. 目的と適用範囲

本書は、中将棋エンジン minase のマイルストーン「合法手生成、make move、unmake move の成立」の設計と、その完了後に実施した修正作業の結果を記録する。
規則の正は RULES.md（中将棋統合競技規則案 第6版）であり、本書と RULES.md が矛盾する場合は RULES.md を優先する。
探索部、評価関数、時間管理、棋譜入出力は対象外とする。

第2版は RULES.md 第5版を基準として書かれ、マイルストーンは2026年7月30日にその仕様で完了した。
その後、RULES.md は第6版へ改訂され、実装規定（旧第3条から第5条までのゲーム状態・着手データ・状態遷移、および旧第11章の適合要件）を削除してドメインルールのみとなり、全条項が改番された。
第3版は、この改訂への追随、2026年7月31日の実装診断と削減、および付け喰いの典拠調査の結果を反映する。
条文の参照はすべて第6版の番号による。

第1版から引き継いだ基盤は次のとおりである。

- `Square`、`Bitboard`（3×64ビット、段あたり16ビット）、`Direction` と方向シフトは変更しない。
- `Color`、`PieceKind`、`PieceCode`、および `Position` の冗長表現（マス配列と駒種別ビットボード）は変更しない。
- `core/attacks/` のレイ表、固定移動表、移動プロファイルは変更しない。ただし2026年7月31日の削減で、モジュールと内部表現型の可視性は `pub(crate)` 以下へ縮小した（12節）。

これらの仕様は実装とテストを正とし、本書では再述しない。

## 2. 設計判断の一覧

本版は次の9点を決定として採用する。
各判断の根拠と詳細は括弧内の節で述べる。

| 判断 | 決定 |
|---|---|
| 合法手の定義 | 王駒の安全を合法性条件に含めない（3節） |
| 指し手表現 | 経路構造の enum とし、捕獲は盤面から導出する（4節） |
| 状態スコープ | 盤面、手番、先獅子トリガーまでを実装する（5節） |
| 先獅子の計算 | トリガーは make 時に記録し、足判定は生成時に遅延する（6節） |
| 付け喰いの幾何 | 隣接していない相手獅子への着手に限る（6節、10節） |
| ローカルルール機構 | 設定構造体とし、標準規則のみ実装する（7節） |
| 検証 | 条文対応テスト、参照実装、ランダムプロパティ、perft 照合と自己回帰で定義する（9節） |
| 規則解釈の境界 | 採用解釈を明文化して実装し、文献調査で裏を取る（10節） |
| 温存と削減の基準 | 呼び出し数ではなく、次マイルストーンでの必要性と再導入コストで個別に判定する（12節） |

## 3. 合法手の定義

**合法手**は、RULES.md 第3条8項に従い、駒の移動能力、捕獲規則、成り規則、獅子の捕獲制限（第13条から第16条まで）、および採用ローカルルールをすべて満たす着手と定義する。
王駒の安全は合法性条件に含めない。
第8条3項から5項までが王手放置と自殺手を合法と定めているためである。

この定義により、旧設計の「疑似合法手を1手ずつ適用して王駒の安全を検査する」ループは不要になった。
生成器は規則検査を生成中に完結させ、`generate_moves` の一本で合法手を直接返す。

詰みと王駒の捕獲による終局（第21条）、駒枯れ（第22条）、合法手がない場合の敗北（第23条）は終局判定であり、次マイルストーンの対局管理層で扱う。

## 4. 指し手表現

指し手は経路構造の enum で表す。

```rust
#[derive(Clone, Copy, PartialEq, Eq, Hash, Debug)]
pub enum Move {
    /// 1段階移動。走り、固定移動、麒麟や鳳凰の固定跳び、
    /// 獅子や角鷹の1歩停止を含む。
    Step   { from: Square, to: Square, promote: bool },
    /// 2段階移動。獅子、角鷹の前方、飛鷲の前斜めが行う。
    /// to == from が帰還であり、mid に敵駒があれば居喰い、
    /// mid が空升なら「じっと」になる。
    Double { from: Square, mid: Square, to: Square, promote: bool },
    /// 獅子力の直接跳び。中間升を検査せず2升目へ進む。
    Jump   { from: Square, to: Square, promote: bool },
}
```

捕獲升はフィールドに持たない。
適用時に、`mid` と `to` の上にある敵駒を取ると定める（`to == from` の場合は `mid` のみ）。
これにより、同じ物理的行動に対する表現が1つになり、居喰いを2通りに重複生成する余地が型ごと消える。

各バリアントの使い分けは次のとおりである。

- **Step**：単一の移動先だけで定まる着手すべてに使う。麒麟の縦横2升跳びのように、2段階の代替経路を持たない固定跳びも Step で表す。
- **Double**：第1段階と第2段階を持つ着手に使う。第11条と第12条の帰還、居喰い、じっと、2回捕獲をこの形で表す。
- **Jump**：獅子（第12条5項から7項まで）、角鷹、飛鷲（第11条1項d）の直接跳びに使う。同じ最終升へ到達する Double とは中間捕獲の有無が異なるため（第11条4項、第12条7項）、別の着手として区別する。

Double と Jump の区別、および居喰いとじっとの区別は、第6版では実装規定ではなく用語定義（第3条13項と14項）と捕獲規則（第7条6項から8項まで）から導かれる。
着手の適用に必要な「捕獲される駒」は、適用前局面と `Move` の組から一意に導出でき、独立のフィールドを要しない。

型は経路の幾何（隣接性や方向の整合）を強制しない。
幾何の正しさは生成器が保証し、`make_move` は debug ビルドで検査する。
指し手のサイズ制約（旧設計の8バイト固定）は設けず、pack は探索実装時に計測へ基づいて再検討する。

成りフラグは着手全体の終了後に適用する（第18条6項）。
第1段階と第2段階の間で成らないこと（第18条7項）は、移動能力を現在の駒種で計算する生成器の構造が保証する。

## 5. ゲーム状態と make/unmake

`Position` は次の状態を保持する。

```rust
pub struct Position {
    board: [PieceCode; RAW_SQUARE_COUNT],
    occupied: Bitboard,
    by_color: [Bitboard; COLOR_COUNT],
    by_kind: [[Bitboard; PIECE_KIND_COUNT]; COLOR_COUNT],
    side_to_move: Color,
    /// 直前手で獅子以外の駒が獅子を取った升。先獅子（第15条）の
    /// トリガーであり、該当しない手の後は None に戻る。
    lion_taken_by_non_lion: Option<Square>,
}
```

着手履歴は保持しない。
履歴を持つと、合法手集合に影響しない情報が同一局面の比較（第24条）へ混入するためである。
`lion_taken_by_non_lion` は合法手集合に影響する唯一の一時状態である。
ただし `PartialEq` の全フィールド比較は「状態の完全一致」であり、第24条の同一局面判定そのものではない。
標準規則の先獅子判定は Some か None かの区別しか使わないため、トリガーの捕獲升だけが異なる2局面は、合法手集合が同一でも `PartialEq` では区別される。
反復判定と局面ハッシュでは、採用ルールに応じてトリガーを射影した局面キー（標準規則では Some か None の1ビット、L1 と L2 では升の値）を使う（第24条1項c）。
反復履歴、対局結果、駒枯れの取り返し猶予（第22条5項から7項まで）、P1 と P2 の成る権利は、次マイルストーンで `Position` の外側の対局管理層に置く。

make/unmake は次の形にする。

```rust
pub struct Undo {
    mv: Move,
    moved_piece_before: PieceCode,
    captured: [Option<CapturedPiece>; 2],
    previous_lion_taken: Option<Square>,
}

impl Position {
    pub(crate) fn make_move_unchecked(&mut self, mv: Move) -> Undo;
    pub(crate) fn unmake_move(&mut self, undo: Undo);
    pub fn try_make_move(&mut self, mv: Move, ...) -> Result<Undo, IllegalMove>;
}
```

`Undo` は適用した `Move` を内包し、`unmake_move` は `Undo` だけを受け取る。
make が失った差分情報と、その差分を生んだ指し手が1つの値として運ばれるため、異なる手との誤った組合せは構成できない。
`Undo` は値で消費されるので、同じ `Undo` による二重の取り消しはコンパイルエラーになる。

適用手順は実装の選択として次の順とする。
第1段階の捕獲を反映し、第2段階を適用し（第7条8項）、最後に成りを適用して（第18条6項）手番を反転する。
`lion_taken_by_non_lion` の更新は駒種の比較だけで決まる機械的事実であり、利き計算を必要としない。
したがって make/unmake は規則層に依存しない。

`make_move_unchecked` と `unmake_move` の往復後、局面は全フィールドで元と一致しなければならない。
不正な着手が `try_make_move` に入力された場合、局面を変更しない（第27条1項）。
`make_move_unchecked` と `unmake_move` は `pub(crate)` にとどめる。
対局管理層は同一クレート内に置く想定であり、外部公開の範囲は探索部の設計時に決める。

### 5.1 増分更新の原則

盤面更新は増分更新を原則とする。
探索は1つの `Position` に make と unmake を数百万回適用し続ける前提であり、盤面更新の効率はエンジン全体の性能を直接決めるためである。

- `board`、`occupied`、`by_color`、`by_kind` は、着手で影響を受ける升だけを `put_piece` と `remove_piece` 経由で更新する。全升の走査や再集計は行わない。
- `unmake_move` は `Undo` に保存した差分から復元する。局面のクローンや情報の再計算はしない。
- 局面のコピーは、対局管理や検証など低頻度の場面に限る。
- 将来の派生情報にも同じ原則を適用する。局面ハッシュは XOR による増分更新とし、旧値を `Undo` に積む。評価関数の差分計算を導入する場合も同じ形で拡張する。

第2版では make と unmake の末尾で不変条件検査（`validate`）を `debug_assert!` により実行していたが、2026年7月31日に削除した。
全升走査が毎ノード走ると、デバッグビルドの深い perft が実用にならないためである。
不変条件検査は、プロパティテストが適用手ごとに `validate` を明示的に呼ぶ形で維持している（9節）。

規則判定が使う仮想盤面にも増分更新の原則を適用する。
足判定（6.2節）で必要になる捕獲後の盤面は、`Position` 全体のクローンではなく、ビットボードの局所コピー（`LocalOccupancy`）で構成する。

## 6. 獅子規則の判定

### 6.1 先獅子のトリガーと足判定の分担

先獅子（第15条）の判定は、記録と評価に分ける。

**記録**は `make_move` が行う。
獅子以外の駒（麒麟が同じ着手で獅子に成る場合を含む。第15条7項）が相手の獅子を取ったとき、その捕獲升を `lion_taken_by_non_lion` に記録する。
獅子が獅子を取った場合は記録しない（第15条6項）。
該当しない着手の後は None に戻す（第15条4項と5項）。
標準規則の判定には Some か None かの区別だけで足りるが、将来の L1 と L2 が捕獲升を必要とするため升も保存する。

**評価**は合法手生成時に行う。
`lion_taken_by_non_lion` が Some のとき、手番側は「足のある相手獅子」を取る手を生成しない。
足がない獅子は取れる（第15条2項）。
付け喰いに該当する手は禁止の対象外とする（第16条7項）。

### 6.2 足の判定

**足**（第13条）は、対象の獅子が取られた直後に、取った駒を取り返せる味方の利きと定義される。
実装は、当該の捕獲手を適用した後の仮想盤面で、取られた側が捕獲駒の升に利きを持つかで判定する（第13条4項）。
獅子が盤上から除かれた後の盤面を使うため、裏足（第3条10項)は走り駒の利きとして自然に通る。
足となる駒自身が取られる状態でも足として扱い、王駒であることを理由に除外しない。
第2版ではこの2点を利きベース判定からの帰結として採用していたが、第6版は第13条5項と6項で明文化した。
条文テストで固定してある。

第13条3項の「取り返す駒が本来の動きで移動できること」については、次の解釈を採用する。
取り返しは疑似的な捕獲手の存在で判定し、その捕獲手自体への獅子捕獲制限の再帰は適用しない（深さ1で打ち切る）。

### 6.3 獅子による獅子の捕獲

獅子で相手の獅子を取る手（第14条）は、着手前の両獅子のチェビシェフ距離で分岐する。

- 距離1（隣接）の捕獲は、足の有無にかかわらず合法とする（第14条1項）。
- 距離2の捕獲は、取られる獅子に足がなければ合法とし、足があれば原則として不可とする（第14条2項と3項）。
- 足がある場合でも、付け喰いに該当すれば合法とする（第16条4項）。

**付け喰い**（第16条）は、隣接していない相手獅子を取る `Double` の第1段階で mid 上の価値ある駒（歩兵と仲人以外）を取り、第2段階でその獅子を取る手と解釈する。
構成要件は、動かす駒が獅子であること（第16条2項）、着手前の自獅子と取られる獅子のチェビシェフ距離が2であること（第16条1項の「隣接していない相手獅子」）、および第1捕獲が経由升の上で行われること（第16条11項）である。
「間」にある駒は2段階移動の経由升で取られる駒を指し、両獅子と直線上に並ぶ位置に限らない（第16条11項。典拠は補足編のケース2）。
隣接する相手獅子を別の升経由の2段階で取る手は付け喰いではなく、第14条1項の無条件捕獲として扱う（第16条12項）。
この解釈の典拠は10節で確定した。

付け喰いの例外は着手全体に適用する。
1手で相手の獅子を2枚取る付け喰いでは、中間で取る獅子に足があっても、着手全体を先獅子の禁止対象外とする（第15条8項、第16条7項）。

第16条8項から10項までには特に注意する。
相手獅子の唯一の足が歩兵または仲人である場合、第1段階でその駒を取っても足は消滅したと扱わず、第2段階の獅子捕獲は不可とする。
実装は、捕獲後の仮想盤面での利き判定に、「第1段階で取られた歩兵または仲人が、取られる前の升から最終到達升へ利いていたか」の論理和を加える形で行う。
取られた駒の占有ビットを仮想盤面へ戻す方式は採らない。
占有まで復元すると、その駒の除去によって開通するはずの走り駒の足（第13条4項）を遮蔽し、第14条2項が禁じる距離2の捕獲を過剰に許すためである。

## 7. ローカルルール機構

採用コードは設定構造体で保持する。

```rust
pub struct Rules {
    lion: LionRule,            // L0（標準）、L1、L2、L3
    promotion: PromotionRule,  // 標準、P1、P2
    lance_rescue: bool,        // P3
    go_between_rescue: bool,   // P4
    repetition: RepetitionRule,// 標準、R1、R2
    capture_ending: bool,      // E1
    no_bare_rule: bool,        // E2
}
```

`Rules` の構築は対局開始時に一度だけ行い（第28条2項）、矛盾する組合せ（L0とL1、P1とP2、R1とR2）を拒否する（第33条7項）。
実装済みなのは標準規則（L0相当）のみであり、未実装コードの指定は構築時に明示的なエラーで拒否する。
黙って標準規則へフォールバックすることはしない。

2026年7月31日の診断で、この機構は「生成結果に影響しない配線」であることを確認した上で、現状維持と決定した。
R1 と R2（反復）および E1 と E2（終局）は次マイルストーンの対局管理層で使われるため、削って戻す往復コストの方が高いと判断したためである。

## 8. 着手生成の構成

- 合法手生成に関わるモジュール（square、bitboard、direction、piece、mv、position、rules、attacks、movegen）は `src/core/` 配下に置く。対局管理（game、adjudication）、SFEN入出力（sfen）、検証ツール（perft）はクレート直下に残す。
- `core/movegen/mod.rs` は実装の単一ファイルであり、`MoveGenerator`、1段階移動の生成、獅子・角鷹・飛鷲の2段階移動と直接跳びの生成（第2段階は `LocalOccupancy` による局所占有）、`IllegalMove` と `try_make_move` をこの順で収める。normal.rs、lion.rs、legal.rs の3ファイル分割は2026年7月31日の再編で廃止した（11節）。
- テストは `core/movegen/tests/` に置き、条文対応（articles.rs）と不変量・乱数（invariants.rs）の内容種別で分ける。局面構築ヘルパはクレート共通の `test_util` モジュールに置く。
- 獅子規則の検査（6節）は生成中に適用する。足判定に使う `square_is_controlled` は規則層に置く。

生成の手順は次のとおりである。

1. 手番側の各駒について、移動プロファイルから1段階移動を生成する。
2. 獅子力を持つ駒（獅子、角鷹、飛鷲）について、2段階移動と直接跳びを生成する。直接跳びは中間升の占有にかかわらず常に候補とする（第11条1項d、第12条5項から7項まで）。
3. 獅子を取る手に第13条から第16条までの検査を適用し、先獅子の禁止（第15条）を適用する。
4. 各着手に成りの選択肢（第17条と第18条）を展開する。

成りの選択は、敵陣への進入、敵陣内または敵陣から出る際の捕獲、歩兵の最奥段到達で与える（第18条1項と2項、第19条1項）。
敵陣への進入は着手の始点と終点で判定し、2段階移動の経由升だけが敵陣に入る場合は成れない（10節）。
成れない着手への成り指定は `try_make_move` が拒否する（第26条8項）。

`MoveGenerator` は `&'static AttackTables` を保持する非ジェネリック型である。
外部から利き表を注入する構成は、呼び出し元が存在しないまま型全体へライフタイムを伝播させていたため、2026年7月31日に廃止した（12節）。

## 9. 検証

検証は条文対応テストとランダムプロパティテストの2本柱で行う。
2026年7月31日の movegen 再編完了時点でテストは118件である。

**ランダムプロパティテスト**：決定的な軽量乱数（手書きの xorshift）でランダム局面と手順を作り、次を検査する。

## 10. 規則解釈の境界と調査結果

採用解釈を条文テストに固定した上で実装し、文献調査で裏を取る方針とした。
2026年7月29日の調査で次の3点を確定した。

1. 第13条3項の「取り返す駒が本来の動きで移動できること」は、疑似的な捕獲手の存在で判定し、獅子捕獲制限の再帰は適用しない（深さ1打ち切り。6.2節）。英語版 Wikipedia が再帰非適用を明文で述べ、shogiops も利きベースの判定で一致する。連盟資料はこの境界に記述がない。
2. 付け喰いの第1捕獲は、2段階移動の第1段階で取る mid 上の駒と解釈する（6.3節）。英語文献は「第1段階での捕獲」として定義し、shogiops も第1捕獲の駒種だけを検査する。
3. 敵陣への進入の成り（第18条1項）は、着手の始点と終点で判定する。経由升だけが敵陣に入る2段階移動では成れない。Muller の成りルール比較と shogiops の実装がいずれも始点と終点だけを参照する。標準規則の駒立てでは、2段階移動を行える駒（獅子、角鷹、飛鷲）はいずれも成れないため、この境界が実戦の合法手に現れることはない。

2026年7月31日には、付け喰いの幾何条件を対象とする追加調査を実施した。
背景は、RULES.md 第6版の初稿が第16条から「1升を隔てた獅子同士の間」という幾何条件を落とし、実装（距離2要件）との間に文理上の差が生じたことである。
調査の結論は次のとおりである。

1. 日本語の典拠3点（連盟総則編、岡崎「中将棋の指し方」、『中将棋指南抄』翻刻）は、いずれも付け喰いを「獅子と獅子の間に敵の駒がある場合」という条件節つきで定義しており、幾何条件は典型例の描写ではなく規則文の要件である。
2. 足による捕獲制限（第14条）が距離2でしか発動しないため、幾何条件の有無は先獅子が絡まない限り合法手集合を変えない。差が出るのは先獅子の禁止下で、隣接獅子への「価値ある駒を取ってからの2段階捕獲」を付け喰いとして許すか否かの1点である。この場合を扱った資料はなく、全資料が沈黙している。
3. shogiops（WandererXII/shogiops の chushogi.ts）は、着手開始升から標的獅子への距離と第1捕獲の駒種で判定しており、外延として本実装と一致する。
4. 以上から、幾何条件を RULES.md 第16条1項へ復活させ、11項と12項で「間」の意味（経由升であり直線位置に限らない）と隣接獅子の扱い（付け喰いの成立を要しない）を補った。実装は変更しない。

未解決のまま残る論点は次のとおりである。

1. 1手で獅子を2枚取る着手（角鷹または飛鷲の2回捕獲）における先獅子トリガーの表現。標準規則では Some か None の区別で足りるが、L1 と L2 の実装時に捕獲升の一意性が問題になる。
2. 先獅子の禁止対象が「取った側に残る獅子」複数枚に及ぶ場合の扱い。トリガーと盤面から遅延評価するため表現上の制約はないが、規則上の意図は未確認である。
3. 先獅子の禁止下で、制限側の獅子が隣接する相手獅子を取り返す着手の扱い。第15条1項の文理どおり禁止として実装し、テストで固定してあるが、獅子の直接交換を例外とする歴史的な読みがあるため文献調査の対象として残す。2026年7月31日の調査でもこの論点を扱う資料は見つからなかった。
4. 居喰いとじっとの棋譜表記。棋譜実装のマイルストーンで扱う。

## 12. 温存と削減の記録

削減の判定基準は「文書由来の不要な忠実さ」であり、現在の呼び出し数ではなく、次マイルストーン（対局管理層）での必要性と再導入コストで個別に判定した。

2026年7月31日に削減したものは次のとおりである。

- `Bitboard` の方向シフト8種と fill 方式の演算子群。利き計算は事前計算テーブルとブロッカー方式で完結しており、シフト伝播は一度も使われていなかった。
- `SpecialMovement::JumpingGeneral` と `JumpingGeneralProfile`。中将棋に跳越し将は存在せず、大将棋への拡張を見越した先回りだった。
- `PromotionChoice::PromotionRequired`。中将棋に強制成りは存在しない（歩兵と香車は最奥段で移動不能の駒として盤上に残る。第19条2項と3項）。
- `MoveGenerator<'a>` のライフタイムと `with_tables`。呼び出しゼロの注入口のために型全体へライフタイムが伝播していた。
- `attacks` の未使用公開メソッドと内部表現型の公開。モジュールを非公開とし、生きている型は `pub(crate)` 以下へ縮小した。

温存したものと理由は次のとおりである。

- `Rules` と `RuleCode` の機構。R1、R2、E1、E2 が対局管理層で使われる（7節）。
- `Position::royal_pieces` と `PieceKind::is_royal`。現在は呼び出しゼロだが、対局管理層の詰みと駒枯れの判定が必要とする。呼び出し数だけを基準にすると次マイルストーンの土台を削ることになる、という個別判定の代表例である。
- `try_make_move` と `IllegalMove`。第6版は不合法着手の処理方法を実装の外に置いたため（第27条2項と3項）、規則上の根拠条文は失ったが、境界 API という実装の選択として維持する。
- 参照実装（9節）。ただしこの温存判定は同日中に覆り、movegen 再編で削除した（9節と11節）。

第1版から第2版への移行で削除した項目（`MoveKind`、`SquareOrNone`、`MoveHistory`、`RuleSet` トレイト、疑似合法手の2段階生成、8バイト固定制約）は第2版の記録どおりであり、本版で変更はない。

# 固定時間（movetime）の探索の締切と途中結果

## 先に読む要約

本書は、USIの`go movetime <ms>`で1手の思考時間を固定した探索（以下、固定時間の探索）で、minaseが指定された時間を使い切らず、探索に使った時間の一部も着手に反映されていない問題を解決するマイルストーンの設計書である。
固定時間の探索を使うのは、lishogiのBotの通信対局（1手300秒、4スレッド）、Botの通常対局の初手（1,000 ms）、および開発用GUIでUSIのエンジンと指す固定時間の対局である。
minaseは反復深化（iterative deepening）で探索の深さを1段ずつ増やすが、現行の固定時間の探索では、次の反復を始めるのは予測した完了時刻が指定時間に収まるときだけであり、指定時間で打ち切った反復の結果は捨てる。
Botの通信対局では、minase 2.5.0の探索の47%が300秒で打ち切られ、主な探索スレッド（主ワーカー）が最後に反復を完了した時刻は平均192秒だった（[調査メモ](../research/movetime-prior-art-and-correspondence-usage.md)）。
StockfishとYaneuraOuは、固定時間の探索では指定時間まで反復を続け、打ち切った反復で読み終えた手が直前の最善手を上回れば、その手を指す。
本書は、minaseが秒読み期（持ち時間を使い切った後の手）にだけ使っている「締切まで反復を始め、打ち切った反復の途中結果（partial result）で指す」規則を、時計と併用しない`movetime`の探索にも適用する。
途中結果とは、打ち切った反復で直前の最善手を読み終えていた場合に、その反復で読み終えた手から選ぶ最善の手であり、直前の最善手と同じこともある。
採否は、対局ハーネスに固定時間の思考制限`movetime=`を加え、1手300 msで選別し1手1,000 msで判定する自己対局の逐次検定（GSPRT）で決める。
持ち時間の時計による探索は、標準の採否測定の短時間条件STCと長時間条件LTCを含めて、予算、反復の開始判定、および打ち切り時の結果を現行と同一に保つ。

## 状態

進行中。2026年10月25日に着手した。
フェーズ0の[発動の確認](../measurements/movetime-deadline/movetime-deadline-activation.md)では、秒読み期の`go`の完了深さが`movetime`の`go`より深くなった局面が300 msで51.5%、1,000 msで41.5%あり、途中結果が着手を変えた局面は2.0%と3.0%だったので、停止条件に当たらなかった。
フェーズ1（対局ハーネスの思考制限）とフェーズ2（対象の探索の締切と途中結果）を進めている。

## 目的

固定時間の探索で、予測による早期の停止をやめて原則として指定時間まで探索し、その計算を着手に反映して棋力を上げる。
lishogiのBotでは、通信対局の思考時間の上限（現行300秒）を延ばさずに、着手に反映される思考時間を増やす。

## 適用範囲

対象は次のとおりである。

- `crates/minase/src/search/alphabeta/`の時間予算（`time.rs`）、反復の開始判定（`deepening.rs`）、先読みの的中後の判定（`searcher.rs`）、および途中結果を有効にする条件（`team.rs`）のうち、時計と併用しない`movetime`の探索に関わる部分。
- 対局ハーネスの固定時間の思考制限`movetime=`（`crates/minase/src/harness/limit.rs`、`clock.rs`、USIエンジンの`go`の組み立て、および実行条件の記録）と、[棋力測定の手引き](../guides/sprt.md)への記載。
- 予算と停止の契約テスト（`crates/minase/src/search/alphabeta/tests/`）とハーネスのテスト。
- 診断のスクリプト（`scripts/movetime_deadline/`）と、[調査メモ](../research/movetime-prior-art-and-correspondence-usage.md)の集計スクリプト。

対象外は次のとおりである。

- 持ち時間の時計による探索。秒読みが0の時計（STCとLTCを含む）と秒読みが正の時計の予算、反復の開始判定、根の手の順序、および打ち切り時の結果は、現行と同一に保つ。
- `movetime`を時計、深さ、またはノード数と併用した探索。現行どおり、予算は`movetime`と併用した制限から決まる値の小さい方を採り、途中結果を採らない。開発用GUIがCECPのエンジンと指す固定時間の対局は、`st`と各手の`time`を送るので、この併用に当たる。minaseのCECPは`level`と`time`で受けた時計を`st`で消さないので、CECPの`st`が本書の対象になるのは、時計の情報も`sd`による深さもない場合だけである。
- 複数ワーカーの結果の選び方（「設計判断」の「ワーカー間の選択」）。
- Lishogi-Botの設定。通信対局の思考時間の上限を延ばすかどうかは、本書の結果とは別に利用者が決める。
- `ByoyomiMargin`。固定時間の探索では参照しない。
- `minase match report`。集計の対象は時間制御の測定のままとし、`movetime=`の実行ディレクトリは`depth=`と同じく集計の対象外としてエラーで終了する。

## 設計判断

用語を次のとおり定める。
反復とは、反復深化で1つの深さを読み切る1回の探索である。
softは反復を完了するたびに次の反復を始めるかを判断する目安の時間、hardは探索の途中でも打ち切る上限の時間であり、両者をまとめて予算と呼ぶ。
締切とは、本書の対象の探索でsoftとhardを兼ねる時間、つまり`movetime`である。
minaseは複数のスレッドで探索するLazy SMPを使い、着手と`info`の出力を担うスレッドを主ワーカー、それ以外を補助ワーカーと呼ぶ。
根とは探索を始める局面であり、窓とは、aspiration windowsが根の探索に与える評価値の下限と上限である。
先読み（ponder）は相手の手番中に予想手を指したと仮定して探索することであり、相手が予想どおりに指したことを的中という。
GSPRT、LLR、`H0`、`H1`、STC、LTC、煙試験、および破棄ペアは、[棋力測定の手引き](../guides/sprt.md)の定義に従う。

本書の変更を適用する探索を「対象の探索」と呼ぶ。
対象の探索とは、有限の探索のうち、時間の制限が`movetime`だけであり、時計、深さ、およびノード数の制限を併用しないものをいう。
先読み（`go ponder movetime`）を含み、先読みでは締切を的中の時刻から数える。
予算、反復の開始判定、先読みの的中後の判定、根の手の順序、および途中結果の採用は、すべてこの1つの条件で切り替える。

| 固定倍の予測を外してよい理由 | [固定倍の予測のADR](../adr/predict-next-iteration-by-fixed-ratio.md)は、予測が過大なら時間が時計に残って後の手へ回ることを前提に、完了の見込みがない反復を始めない規則を採った。固定時間の探索では、使い残した時間は後の手へ回らない。この構造は、使わなかった秒読みを持ち越せない秒読み期と同じである。秒読み期の手も、1手に使える時間が外から決まり、反復の開始判定と途中結果の採用はその1手の中で完結するので、同じ規則をそのまま当てはめられる。秒読み期の規則は、持ち時間と秒読みの比が20と150の2条件のGSPRTでともに`H1`だった（[byoyomi-a-short-c10](../measurements/byoyomi-time-usage/byoyomi-a-short-c10.md)、[byoyomi-a-long-c10](../measurements/byoyomi-time-usage/byoyomi-a-long-c10.md)）。また、Botの2.5.0で300秒に打ち切られた探索では、主ワーカーの最後の完了反復は平均約130秒の時点にあり、次の反復は残り約170秒で完了しなかった。300秒のような長い探索では、`IterationRatio`による1.52倍の予測は、次の反復の実際の所要時間より大幅に短い。 |
| 時計と併用した`movetime`を対象外にする理由 | 併用時の予算は、現行では時計と`movetime`のsoftとhardのそれぞれで小さい方を採る。Stockfishは両方の条件で止め、YaneuraOuは`movetime`だけを使うので、先行実装の扱いが分かれている。併用を送る呼び出し側は、開発用GUIのCECPの経路だけであり、本書の目的（Botの通信対局とUSIの固定時間の対局）に含まれないので、現行のまま残す。 |
| 人間との対局で棋力を落とさないという決定との関係 | 2026年9月18日の利用者の決定により、人間との対局で棋力を落とす変更は認めない。対局ハーネスは`movetime`を送らないので、STCとLTCの探索は計算式も実行経路も変わらず、その条件で測り直す必要はない。秒読みが0の時計では`byoyomi_clock`の判定が成り立たないので、後述の条件の拡張もこの時計に及ばない。人間との対局のうち、開発用GUIでUSIのエンジンと指す固定時間の対局とBotの初手は`movetime`を使うので、`movetime`の2条件のGSPRTで強くなったことを確かめてから採用する。 |
| ワーカー間の選択 | 現行の選択（`team.rs`の`select_worker_outcome`）は完了深さを最優先し、途中結果は同じ深さのときだけ優先する。途中結果を持つのは主ワーカーだけなので、補助ワーカーが主ワーカーより1段深い反復を完了していると、主ワーカーがその深さの途中で見つけた最善手より補助ワーカーの結果が選ばれる。StockfishとYaneuraOuは、途中結果を含む各スレッドの先頭の手を評価値で投票して選ぶ。Botの2.5.0の通信対局では、300秒で打ち切られた97件のうち36件で補助ワーカーの結果が指されており、4スレッドではこの選択の影響が大きい。選択の規則は秒読み期の探索と共有しており、変えると秒読み期の挙動も変わるので、本書では変えない。採否測定は`Threads=1`で行うので、4スレッドでの効果は測定に現れない。投票による選択は、必要なら別の設計書で扱う。 |
| 判定の印と有効化条件 | 時間予算の`TimeBudget::byoyomi_period`は、予測を使わず締切まで反復を始める予算を表しており、対象の探索でも同じ扱いが要る。対象の探索ではこの印を立て、意味に合わせて名前を改める（例：`deadline`）。途中結果と根の順序を有効にする条件（`team.rs`で`byoyomi_clock(limits).is_some()`を渡している箇所）も、秒読みつきの時計の探索または対象の探索へ広げる。`byoyomi_clock`は秒読みが正の時計だけを返すので、秒読みが0の時計はどちらの条件にも当たらない。 |
| 採否の判定方法 | STCとLTCは対象の探索を通らないので、この変更を測れない。対局ハーネスに固定時間の思考制限を加え、その条件のGSPRTで判定する。思考制限は`time=`や`--ponder`と同じ対局条件であり、候補と基準に同じ条件を与えるので、[棋力測定の手引き](../guides/sprt.md)が禁じる機能比較のスイッチには当たらない。 |
| 総思考時間の比較との関係 | [予算の機構を変えたら総思考時間と使い残しを現行と比べる](../lessons/compare-total-time-usage-before-sprt.md)は、持ち時間を各手へ配分する時計で、候補の総思考時間が現行の90〜110%に収まることを求める。固定時間の探索では1手の時間を呼び出し側が与えるので、候補が与えられた時間を使い切るのは目的そのものである。このため90〜110%の条件は適用せず、煙試験では、思考時間と`movetime`の比、手数帯ごとの完了深さ、および途中結果が着手を変えた割合を記録する。 |
| 発動の確認 | [採否測定の条件で改良が発動することを実装前に確認する](../lessons/measure-feature-activation-before-sprt.md)に従い、実装の前に現行のminaseで発動を確かめる。秒読み期の探索は、締切が「秒読み − `ByoyomiMargin`」である点を除けば対象の探索と同じ規則なので、`go btime 0 wtime 0 byoyomi 330`（既定の`ByoyomiMargin`30 msで締切300 ms）と`go movetime 300`を同じ局面に与えて比べれば、実装後の候補と基準の差を前もって見積もれる。変更の働きは、追加の反復を始めて完了することと、途中結果で着手を変えることの2つに分けて記録する。 |

## 対象の探索の規則

対象の探索では、次の規則を適用する。

1. softとhardはともに`movetime`である。先読みでは的中の時刻から数える。
2. 主ワーカーは反復を完了するたびに、経過時間（先読みでは的中からの経過時間）がhard未満なら次の反復を始める。
3. 最善手安定時の早期終了、詰みを見つけたときの早期終了、および合法手が1つのときの上限は適用しない。探索は、hardに達するか、深さの上限に達するか、外部から停止されるまで続く。
4. 先読みの的中時に、進行中の反復が予算に収まるかを予測して打ち切る処理（`searcher.rs`の当て直し）は行わない。
5. 根では直前に完了した反復の最善手を先頭に置き、hardで打ち切ったときは「設計判断」の「途中結果の採用」の規則で途中結果を選ぶ。条件を満たす手がなければ、最後に完了した反復の結果を使う。
6. 投了の判定、根の置換表への記録、およびワーカー間の選択は、秒読み期の探索と同じ規則に従う。

対象でない探索は、併用の場合も含めて、現行の経路をそのまま通る。

## 対局ハーネスの固定時間の思考制限`movetime=`

思考制限の文法に`movetime=<ms>,timemargin=<ms>`を加える。
2つの値はどちらも省略できず、`movetime`は1以上、`timemargin`は0以上の整数ミリ秒とする。
USIエンジンには毎手`go movetime <movetime>`を送り、時計の引数は送らない。
思考時間（`go`の送信から`bestmove`の受信まで）が`movetime + timemargin`を超えた手は時間切れとし、`time_forfeits`に数える。
これはcutechess（`projects/lib/src/timecontrol.cpp:362`）とfastchess（`app/src/game/timecontrol/timecontrol.cpp:46-49`）の1手固定時間と同じ判定である。
両ツールでは`timemargin`の既定値が0だが、`movetime`に達した時点で打ち切るエンジンは、停止の検査の間隔と入出力の分だけ必ず`movetime`を超えるので、本書のハーネスでは値の明示を求める。
`timemargin`はハーネスの判定だけに使い、エンジンへは送らない。
候補と基準には同じ時間切れの判定を適用する。

この思考制限は、[棋力測定の手引き](../guides/sprt.md)がCECPのエンジンに使う「1手固定時間」（基本時間と加算が0で秒読みが整数秒の時間制御を`st`で送る形）とは別のものである。
手引きには、USIのエンジンに`go movetime`を送る思考制限として書き、両者を区別する。

`movetime=`は、`--ponder`、およびCECPのエンジン（`cecp:`）と併用できず、指定するとエラーで終了する。
`--ponder`は現行でも`time=`の条件にだけ指定でき、先読みを有効にした固定時間の対局の測定は本書の目的に含まれないからである。
対象の探索の先読み（`go ponder movetime`）は、開発用GUIが先読みを有効にした固定時間の対局で使う経路であり、正しさはフェーズ2の単体テストで確かめる。
実行条件の記録（`manifest.json`の思考制限）に`movetime`の種類を加え、再開ではこの値を使う。
既存の実行ディレクトリに現れない種類を加えるだけなので、記録形式の版は上げない。
この種類を持つ実行ディレクトリを旧版の`minase`で読むと、未知の種類としてエラーで終了する。

## 測定条件

選別条件は`movetime=300,timemargin=100`、判定条件は`movetime=1000,timemargin=100`とする。
300 msは、秒読み期の採否測定の秒読みと同じ値である。
1,000 msは、Botの通常対局の初手が使う値であり、選別条件の約3.3倍の時間でも効果が残るかを確かめる。
`timemargin`の100 msは暫定値であり、秒読みつきの採否測定で実質の余裕だった30 ms（エンジンが締切の30 ms前に打ち切る）の3倍強とした。
[外部エンジンの固定時間の教訓](../lessons/fixed-time-forfeit-margin.md)に従い、本測定と同じ同時対局数の煙試験で`movetime`を超えた量の分布を測り、最大値が50 msを超えた場合は原因を調べてから本測定へ進む。
50 msは`timemargin`の半分であり、本測定の数十万手で超過量の分布の裾が伸びても、時間切れの判定（100 ms）に届かない余裕を残す。

測定の順序と判定は、標準の段階ゲート（[棋力測定の手引き](../guides/sprt.md)の「機能採否の段階ゲート」）に従い、STCを選別条件、LTCを判定条件に置き換える。

1. 選別条件で、候補と着手前のコミットを上限3,000ペアのGSPRTで比べる。`H0`、または上限到達で停止時のLLRが負なら不採用とする。`H1`、または上限到達で停止時のLLRが0以上なら判定条件へ進む。
2. 判定条件で比べ、`H1`で、エンジン異常、時間切れ、および拒否着手が0件なら採用する。判定保留は`--resume`と`--target-pairs`で延長する。`H0`なら不採用とする。

同時対局数は12とする。
lishogiのBotが同じ測定機で1局あたり4スレッド、最大2局を指すので、12局と合わせて物理20コアに収まるからである。
シードは測定ごとに、既存の測定のシードからペア数以上離れた未使用の値とする（[隣接する基本シードの教訓](../lessons/derive-seed-adjacent-collision.md)）。
測定機で重い計算を始める前に、進行中の測定を確かめる（[進行中の測定を確認する教訓](../lessons/check-running-measurements-before-cpu-load.md)）。

所要時間は、秒読み期の採否測定の短い条件の実績（同時対局数10で138ペアに3,893秒、1ペアあたり同時対局1枠で約282秒）から見積もる。
選別条件の1手の時間はその条件の秒読み期とほぼ同じなので、同時対局数12では150ペアが約1時間、1,000ペアが約6.5時間、3,000ペアが約20時間である。
判定条件は1手の時間が約3.3倍なので、150ペアが約3時間、1,000ペアが約22時間である。
秒読み期の採否測定は両条件とも130〜160ペアで`H1`となったので、効果が同程度なら合計で約4〜5時間と見込む。
効果が小さければ、判定までの期待ペア数が増え、所要時間は数倍になる。
見積りは煙試験の実時間と破棄ペア数で更新し、本測定の前に利用者へ示す。

測定は`Threads=1`、先読みなしで行い、Botは`Threads=4`、置換表2,048 MB、1手300秒で動く。
測定の1手の時間はBotの通信対局（1手300秒）の300分の1以下であり、ワーカー間の選択の効果は測定に現れない。
これらの差は本書の限界として記録し、配備後にBotのログで、指定時間を使い切った探索の割合と途中結果の採用を確かめる（フェーズ4）。

## 実装フェーズ

### フェーズ0　実装前の発動の確認

`scripts/movetime_deadline/deadline_probe.py`を作る。
このスクリプトは、[秒読みつき時計の診断](../../scripts/lishogi_byoyomi_usage/paired_depth_probe.py)と同じ方法で、既存の実行ディレクトリの対局記録から局面を選ぶ。
そのうえで、1つのエンジンに2つの`go`引数を同じ局面で与え、局面ごとに完了深さ、途中結果の有無、および途中結果が最後の完了反復の最善手と異なる手を返したかを記録する。
途中結果の`info`行は完了深さ＋1を報告するので、完了深さには`lowerbound`の付かない最後の`info`行を使う。
現行のmasterのminaseに、`go movetime 300`と`go btime 0 wtime 0 byoyomi 330`を、手数0〜200の200局面で与える。
同じことを`go movetime 1000`と`go btime 0 wtime 0 byoyomi 1030`でも行う。

記録する値は、`byoyomi`の`go`での完了深さが`movetime`の`go`より増えた局面数と減った局面数、完了深さの差（`byoyomi`の`go`の深さ−`movetime`の`go`の深さ）の平均と標準誤差、途中結果を採った局面の割合、および途中結果が着手を変えた局面の割合である。
次のどちらかに当たれば、実装へ進まずに利用者へ報告する。

- 両条件とも、完了深さが増えた局面が全体の5%未満で、かつ途中結果が着手を変えた局面が1%未満である。この場合、測定条件で変更がほとんど働かない。
- どちらかの条件で、完了深さの差の平均が負であり、その絶対値が標準誤差の2倍以上である。この場合、変更で深さが浅くなっている。

完了条件は、値の記録と、実装へ進むかの判断である。

### フェーズ1　対局ハーネスの思考制限

「対局ハーネスの固定時間の思考制限`movetime=`」の節を実装し、[棋力測定の手引き](../guides/sprt.md)の「エンジンの指定方法」と思考制限の説明に`movetime=`を書き加える。
次の検査を加える。

- 文法の受理と拒否（値の省略、0の`movetime`、負の値、`--ponder`との併用、CECPのエンジンとの併用）。
- USIエンジンへ送る`go`の文字列。
- 思考時間が`movetime + timemargin`と等しい手を受理し、超えた手を時間切れとすること。
- 実行条件の記録と再開での復元。

完了条件は、`cargo test`の通過と、`random`同士の`movetime=`の煙試験が完走することである。

### フェーズ2　対象の探索の締切と途中結果

「対象の探索の規則」を実装する。
判定の印の改名と対象の探索の判定を1コミット、途中結果と根の順序の有効化を1コミットに分ける。
次の検査を加える。

- 対象でない探索（秒読みが0の時計、秒読みが正の時計、`movetime`と時計、深さ、またはノード数の併用、深さだけ、ノード数だけ）で、予算値、開始判定、停止理由、根の手の順序、および打ち切り時の結果が現行と一致すること。
- 対象の探索で、経過時間がhard未満なら次の反復を始め、予測による開始の制限と早期終了が働かないこと。
- 対象の探索で、hardで打ち切った反復の途中結果が秒読み期と同じ規則で採られること、途中結果を根の置換表へ記録しないこと、および投了の判定が最後に完了した反復の値を使うこと。
- 対象の探索の先読みで、締切を的中の時刻から数え、的中時の当て直しを行わないこと。
- `Threads=4`の対象の探索で、返す着手が合法で、思考時間が`movetime`を大きく超えないこと。

完了条件は、`cargo test`の通過と、固定深さのbench総ノード数が着手前と一致することである。
benchは深さ固定の探索なので、対象の探索の変更はノード数を変えない。

### フェーズ3　煙試験と採否測定

選別条件と判定条件のそれぞれで、同時対局数12の24ペアの煙試験を行う。
ハーネスは1ペアを1つの単位として割り当て、ペアの2局を順に指す。このため、12局を同時に指し続けるには12ペア以上が必要であり、24ペアあれば負荷の続く区間を確保できる。

煙試験の対局記録から、各手の思考時間、停止理由、および評価値の境界を集計するスクリプト`scripts/movetime_deadline/smoke_profile.py`を作る。
評価値の境界が下界の手は途中結果を採った手であり、その手の報告された深さは完了深さ＋1なので、完了深さは1を引いて数える。
`Threads=1`では補助ワーカーの結果がないので、この補正で足りる。
途中結果が着手を変えた割合は対局記録から分からないので、[秒読みつき時計の診断](../../scripts/lishogi_byoyomi_usage/paired_depth_probe.py)に基準と候補のバイナリと`go`引数`movetime 300`（判定条件では`movetime 1000`）を与え、同じ200局面で測る。

煙試験の判定条件は次のとおりである。

- 時間切れ、エンジン異常、および拒否着手が0件であること。
- 候補の思考時間と`movetime`の比の中央値が0.95以上であること。候補は早期終了をしないので、中央値は1に近くなるはずであり、下回れば予測による停止が残っている。
- `movetime`を超えた量の最大値が50 ms以下であること。
- 手数帯ごとの完了深さの平均が、基準を下回らないこと。

あわせて、停止理由の内訳、候補が途中結果を採った手の割合、途中結果が着手を変えた割合、基準の思考時間と`movetime`の比、1ペアの実時間、および破棄ペア数を記録し、所要時間の見積りを更新して利用者へ示す。
途中結果の割合は診断として記録するだけであり、測定へ進むかの条件にはしない。
変更全体が働いていることは、フェーズ0の値と、思考時間と完了深さの判定条件で確かめる。
煙試験を通過したら、「測定条件」の手順に従って測定する。
完了条件は、採否の判定と測定記録である。

### フェーズ4　配備の確認と文書

採用した場合は、masterへ統合し、次のリリースを利用者が配備した後、Botの通信対局のログを[調査メモ](../research/movetime-prior-art-and-correspondence-usage.md)のスクリプトで、配備の時刻以降に範囲を限って集計する。
配備後の通信対局の探索100件以上について、300秒で打ち切られた探索の割合、途中結果を採った割合、途中結果が着手を変えた割合、および補助ワーカーの結果を指した割合を記録する。
採否の決定をADRに書き、[秒読み期の締切と途中結果のADR](../adr/search-to-the-byoyomi-deadline-and-play-partial-results.md)からリンクする。
規則の詳細は`time.rs`の`time_budget`と`root.rs`の`RootResults`のdocコメントへ移す。
`minase-lishogi-bot`の`README.md`の「通信対局」節に、minaseが予測による早期の停止をせず、原則として300秒まで探索することを書き加える。
完了条件は、配備後の記録、ADR、および文書の更新である。

## 検証

- 対象でない探索の代表入力で、予算値、開始判定、停止理由、根の手の順序、および打ち切り時の結果が現行と一致すること。
- 固定深さのbench総ノード数が着手前と一致すること。
- 煙試験と測定の時間切れ、エンジン異常、および拒否着手が0件であること。

## 完了条件

完了（採用）の条件は、「測定条件」の判定で採用され、フェーズ4の記録と文書の更新が済んでいることである。
完了（不採用）の条件は、選別条件で`H0`または上限到達時のLLRが負となるか、判定条件で`H0`となり、測定記録と原因の記録が残っていることである。
フェーズ0またはフェーズ3の診断で利用者へ報告した場合は、待機中とし、利用者が測定条件を改めるか見送るかを決めるまで待つ。
見送りと決まった場合は、診断の記録を残して完了（一部不採用）とする。[設計書の書き方](README.md)は、事前の診断で見送った候補がある場合をこの状態と定めている。
不採用の場合も、フェーズ1で加えた思考制限`movetime=`は、測定記録を同じ版のハーネスで再現できるように残す。

# 複数の読み筋を同時に示すMultiPVの設計書

## 先に読む要約

本書は、中将棋エンジンminaseに、上位N手の読み筋と評価値を同時に示す機能MultiPV（multiple principal variations）を加える手順を定める。
読み筋（主変化、PV）は、探索を始める局面である根から、探索が最善と見た手とそれに続く双方の応手を並べた列であり、いまのminaseは最善手の読み筋を1本だけ示す。
MultiPVは、対局の検討や評価関数の診断で、最善手に次ぐ手がどれだけ劣るかを見るための機能であり、将棋エンジンのやねうら王とdlshogi、およびチェスエンジンのStockfishが備えている。
USI（エンジンとGUIの通信規約）のオプション`MultiPV`で本数Nを指定し、既定値1では、探索の結果も出力もいまと同じに保つ。
αβ探索は深さ1から1ずつ深くして探索を繰り返す反復深化で読み、Stockfishとやねうら王と同じく、各深さで根の探索をN回繰り返して、k回目はk−1回目までに選んだ手を除いた残りの手から最善の手を探す。
AlphaZero型探索のPV-MCTS（方策と価値を出すニューラルネットワークで木を広げるモンテカルロ木探索）では、dlshogiと、やねうら王に同梱されたdlshogi系のエンジンであるふかうら王と同じく、探索は変えずに、終了時に根から指せる手を並べて上位N本を出し、並べる規則にはminaseが最善手を選ぶ比較規則をそのまま使う。
Nが2以上では、全N本を読み終えた反復だけを結果とし、途中で止まった反復は丸ごと捨てる。
完了の第1の条件は、既定値1で、固定の局面集を探索するコマンド`bench`の出力、固定の深さとノード数の探索の出力、および試験用の時計で進めた持ち時間つきの探索の判断がいまと一致し、速さも変わらないことである。
残りの条件は、Nが2以上の出力が「検証」の節の性質を満たすことと、仕様をソースのdocコメントと手引きへ、設計判断を決定記録（ADR）へ移したことである。
既定値では探索の手順を変えないので、自己対局の勝敗から逐次検定で採否を決める棋力測定（SPRT）は行わない。

## 目的

本書の目的は、minaseの探索の結果を、最善手1本だけでなく上位N手の比較として読めるようにすることである。
次の2つの用途で、2番手以下の手の評価値と読み筋が要る。

第1は、対局や棋譜の検討である。
検討では、利用者が指した手やほかの候補手が最善手に比べてどれだけ悪いかを知りたい。
読み筋が1本だけでは、2番手の手がわずかに劣るのか大きく劣るのかが分からない。
第2は、探索と評価関数の診断である。
αβ探索の評価関数NNUE（着手ごとに差分で更新できる小さなニューラルネットワーク）やPV-MCTSのネットが、特定の局面で候補手をどう順位づけるかは、上位N手の評価値の並びを見ると分かる。
いまは、候補手ごとの評価を見る手段が、PV-MCTSの方策の確率を出す診断のコマンドだけである。

MultiPVは、対局の強さを上げる機能ではない。
既定値1では探索も時間管理も出力もいまと変えず、対局と棋力測定には既定値を使う。

## 適用範囲

本書が扱うのは、USIオプション`MultiPV`の宣言、αβ探索でN本の読み筋を求める処理、PV-MCTSでN本の読み筋を出す処理、探索から通信層へ読み筋を渡すイベントの形、USIの`info`行の出力、対局ハーネスの評価値の記録、およびその仕様と設計判断の文書化である。

次の項目は扱わない。

- 開発用GUI（別リポジトリ`minase-gui`）で複数の読み筋を表示する変更は扱わない。GUIの側の変更は、本書の完了後に`minase-gui`で別に計画する。
- PV-MCTSの探索中の定期的な`info`の出力は扱わない。いまのPV-MCTSは探索の終了時にだけ`info`を出し（[MCTSの対局の探索のADR](../adr/search-mcts-games-by-puct-with-virtual-loss-batches.md)）、本書もその規則を保つ。
- αβ探索で、窓外れの読み直しの途中や、1本ずつの読み筋の完了ごとに途中経過を出す処理は扱わない。理由は「αβ探索の出力の時期」の節にある。
- USIの`go searchmoves`（根の候補を利用者が絞る指定）は扱わない。minaseは`go`の未知の引数を拒否しており、本書もその扱いを変えない。
- xboard系の通信規約CECP（`--protocol cecp`）での複数の読み筋は扱わない。CECPの層は探索のオプションを宣言せず（`crates/minase/src/protocol/cecp.rs`）、探索は既定値1で動き続ける。
- AlphaZero型探索の自己対局生成器と、NNUEの教師の生成器は扱わない。どちらも同期版の探索を直接呼ぶので、Nは常に1である。

## 設計判断

本書では、Nを`MultiPV`の値と根の候補手の数の小さい方とし、Nが1のときの処理はいまと同じにする。
次の表は、Nが2以上のときの処理を中心に、採った方式と棄却した代案をまとめる。

| 判断 | 採る方式 | 棄却した代案 |
|---|---|---|
| オプションの名前 | `MultiPV`（spin、既定値1、最小1、最大35,856） | USI原典の予約名`USI_MultiPV`、両方の名前の宣言、最大256 |
| オプションの持ち主 | USIの層が持ち、探索の開始時に探索へ渡す | 2つの探索方式がそれぞれ宣言する |
| αβ探索の方式 | 各深さで根の探索をN回繰り返し、選んだ手を除いていく（Stockfishの`pvIdx`のループ） | 根の窓を下げて上位N手の正確な値を1回の探索で求める方式 |
| 2本目以降の各読み筋の窓 | 前の反復のN本のうち、まだ選んでいない最上位の手の、その時点の平均を中心に置く | 値の範囲を絞らない全窓で読む、その時点の根の手の並びの先頭の手を使う（Stockfish） |
| 2本目以降の根の記録 | 置換表とcorrection historyは更新せず、historyは更新する | Stockfishと同じくcorrection historyも更新する |
| 反復の完了 | 全N本を読み終えた反復だけを完了とし、途中で止まった反復は丸ごと捨てる | 読み終えた読み筋だけを残す（Stockfish） |
| 途中結果 | Nが2以上では秒読みと固定時間の途中結果を使わない | 1本目にだけ途中結果を適用する |
| 時間管理 | いまの規則を保ち、1本目の最善手の変化だけを数え、詰みの早期停止はN本目の値で判定する（Stockfish） | Nが2以上で持ち時間の伸縮を止める |
| Lazy SMP | 補助ワーカーもN本を読み、結果の選び方は変えない（現行のStockfish） | Nが2以上なら主ワーカーの結果だけを採る（やねうら王） |
| αβ探索の出力の時期 | 全N本を読み終えた反復ごとに、N行をまとめて出す | 1本ずつ、または一定のノード数の後に毎回出す |
| PV-MCTSの方式 | 探索は変えず、終了時に根の辺（根から指せる手）を`best_edge`と同じ比較規則で並べて上位N本を出す（dlshogi、ふかうら王） | 上位N手へ訪問を配る選択式 |
| PV-MCTSの未訪問の辺 | 2本目以降は評価値を付けずに出す（dlshogi） | 出さない、勝率0.5として出す（ふかうら王） |
| `info`行の形 | `MultiPV`が1なら現行のまま、2以上なら`depth`の直後に`multipv k`を入れる | Nによらず`multipv 1`を付ける（Stockfish、やねうら王） |
| `bestmove`と`ponder` | 1本目の読み筋の1手目と2手目 | 別に保持した最善手 |
| 対局ハーネスの評価値 | `multipv`のない行と`multipv 1`の行だけを記録する | 最後の評価値つきの行を記録するいまの規則 |
| 採否の判定 | 既定値1での出力と時間管理の判断の一致と、benchの速さの確認 | SPRTによる対局の測定 |

### オプションの名前と範囲

オプションの名前は`MultiPV`とする。
USI原典は予約名として`USI_MultiPV`を定める（[USI原典の調査](../research/protocols/usi-lishogi.md)）が、本書が読んだやねうら王、ふかうら王、およびdlshogiは、どれも`MultiPV`で宣言する。
GUIが送るオプション名はエンジンが宣言した名前に従うので、実績のあるエンジンと同じ名前にしておけば、それらのエンジン向けの検討の設定をそのまま使える。
両方の名前を宣言すると同じ設定に2つの入口ができ、どちらを後に送ったかで値が決まる。

既定値は1、最小値は1とする。
最大値は、方策の要素数`POLICY_SIZE`の35,856とする（`crates/minase/src/nn/policy.rs`）。
合法手はどれも異なる方策の要素へ写り、その写像が単射であることは試験で確かめてあるので（[方策の符号化のADR](../adr/encode-the-zero-policy-as-249-planes-per-from-square.md)）、1局面の合法手の数は35,856を超えない。
先行実装も、最大値を合法手の数の上界から決めている。
Stockfishは、チェスの合法手の上界`MAX_MOVES`の256を最大値にする（`src/types.h`の115行）。
やねうら王は、将棋の合法手の最大数593に余裕を加えた600を最大値にする（`source/types.h`の704行）。
dlshogiは、593を最大値にする（`cppshogi/usi.cpp`の92行）。
minaseは中将棋の合法手の最大数をまだ証明していないので、証明済みの上界である方策の要素数を使う。
最大値を256のような表示の都合の値にする案は、中将棋の合法手の数が256以下であることを示す根拠がなく、根拠のない上限を設けることになるので採らない。

### オプションの持ち主

`MultiPV`は、USIの層が宣言して保持し、探索を始めるときに探索器へ渡す。
引き分けの評価値`DrawValueBlack`と`DrawValueWhite`も、USIの層が保持して`SearchSnapshot::with_draw_value`で探索へ渡しており、同じ形にする。
USIの層が値を知っていれば、`MultiPV`が2以上のときに根の候補手が1つしかなくても`multipv 1`を付けられる。
2つの探索方式にそれぞれ宣言させると、USIの層が出力の形を決めるために探索器へ値を問い合わせることになる。
同期版の`search()`と、CECP、自己対局、および教師の生成器は、`MultiPV`を1として探索する。

Nは、`MultiPV`の値と根の候補手の数の小さい方である。
根の候補手は全合法手ではなく、`SearchSnapshot::from_game`が選んだ手である（`crates/minase/src/search/snapshot.rs`）。
同一局面の反復に関する規則R1では、反復勝ちの手があればその手だけを、なければ反復負けに直結する手を除いた手を候補にし、全合法手が反復負けに直結するなら全手を残す。
MultiPVの読み筋はその候補の中から選び、候補の選別は引き続き`SearchSnapshot`に任せる。
MultiPVのために候補を広げることも、MultiPVの側で候補を選び直すこともしない。
探索の処理と途中結果の扱いはNで分け、USIの出力の行に`multipv`を付けるかだけを`MultiPV`の値で分ける。
したがって、根の候補手が1つの局面では、`MultiPV`が2以上でも探索と途中結果はNが1のときと同じであり、出力の行にだけ`multipv 1`が付く。

### αβ探索の方式

αβ探索では、反復深化の各深さで、根の探索をN回繰り返す。
k回目（k＝1、…、N）は、同じ深さのk−1回目までに選んだ手を根の候補から除き、残りの手の中で最善の手とその値と読み筋を求める。
k回目の探索が終わるたびに、その深さで選んだk本を、同じ値なら元の順を保つ安定な整列で、値の降順に並べ直す。
この方式は、Stockfishの`pvIdx`のループ（`src/search.cpp`の373〜524行）と同じである。
やねうら王も、このループを移している（`yaneuraou-search.cpp`の1542行以降）。

棄却した代案は、根の窓の下端を下げて、1回の探索で上位N手の正確な値を同時に得る方式である。
この方式は、上位N手のすべてで窓の内側の値を得るために、根の窓をN番手の値の下まで広げる必要がある。
αβ探索は窓が広いほど枝を刈れなくなるので、この方式は1本目の探索そのものを遅くする。
本書が読んだ3つの実装は、どれもこの方式を採っていない。

Nが1のときは、1回目の探索だけを行い、いまの反復深化と同じ処理になる。
反復を始めるときの処理、すなわち`begin_iteration`と、深さを増やさずに始めた反復の回数`search_again_counter`の更新は、N本の全体で1回だけ行う。
どちらも、読み筋の本数ではなく反復の回数を数える量だからである。

k回目の探索では、まず、その回の窓と手の並べ方の基準にする手を1つ決める。
この手は、前の反復のN本を順位の順に見て、この反復でまだ選ばれていない最初の手とする。
前の反復のN本がすべて選ばれているか、前の反復がない場合は、残りの手をいまの並べ方で並べた先頭の手とする。
Stockfishは、この手として、その時点の根の手の並びで`pvIdx`番目にある手を使う（`src/search.cpp`の383〜395行）。
Stockfishの根の手の並びは、各回の探索の後に、その回で得た値で並べ直されるので（同420行）、`pvIdx`番目の手は前の反復のk番目の手とは限らない。
本書がStockfishの方式を写さずに前の反復の順位を使うのは、前の反復で完了したN本を次の反復の各回の出発点にすると、どの回がどの手から始まるかを反復の結果だけから説明できるからである。

2回目以降だけに働く処理は、次の7つである。
行番号は「依存関係」の節の表のコミットのものである。

1. 根の候補は、その深さでまだ選んでいない手に限る（Stockfish `src/search.cpp`の1164行）。
2. 窓の中心は基準の手の評価値の平均とし、窓の幅の半分（半幅）は、いまと同じ式で、その手の評価値の符号つき2乗の平均から求める。この2つの平均は、いまの実装が窓の計算のために根の手ごとに保持し、根の手を読むたびに更新している量であり（`root.rs`の`RootMoveStats`）、同じ反復の前の回で読んだ分も含むその時点の値を使う。基準の手に平均の記録がなければ、値の範囲を絞らない全窓で読む。Stockfishも、各回の手の平均を中心にする（同389〜392行）。
3. 根で最初に読む手は基準の手とし、残りの手は、いまと同じく前の反復の部分木のノード数の降順に並べる。Stockfishも、根の置換表の手を各回の手に置き換えて最初に読む（同840行）。
4. 前の反復の読み筋を追う指し手の順序付けには、基準の手の前の反復の読み筋を使う。基準の手が前の反復のN本になければ、追う読み筋を持たない。Stockfishも、各回の手の前の反復の読み筋を追う（同383行と793〜794行）。
5. 根の局面の評価値と最善手を、置換表へ保存しない（同1656行）。根のcorrection history（静的評価と探索値の差を局面の特徴ごとに学ぶ表）も更新しない。除いた手がある探索の値は、根の局面の値ではないからである。Stockfishは置換表の保存だけを止めてcorrection historyは更新するが（同1663〜1672行）、correction historyは駒の配置の一部をキーにして多くの局面で共有されるので、更新を続けるとNが大きいときにk回目の低い値が根以外の局面の補正まで引き下げる。止めるのは根の探索値による更新だけであり、根より下の節点の更新と、除いた手によらない根の局面の補正前の静的評価を置換表へ保存する処理は、いまのとおり行う。この保存は`root.rs`の`search_root`の冒頭にある。history（指し手の成績の表）の根での更新は、残りの手の中でどの手がよかったかを記録する量であり、除いた手があっても意味を保つので、Stockfishと同じく行う。
6. 根で最善手が変わった回数は数えない（同1531行）。この回数は、1本の根の探索の中で、後に読んだ手の値が先に読んだ手の値を上回った回数であり、時間管理で1本目の探索の揺れを測るのに使う。2本目以降は1本目の手を除いた別の探索なので、その中での入れ替わりは1本目の揺れではない。
7. fail high（窓の上端を超えた結果）の後に次の反復の探索の深さを減らす持ち越しの量は、1本目の探索でだけ減らして更新し、2本目以降の探索では減らしも更新もしない。Stockfishの同404〜405行と461〜462行に当たる。

1.、3.、4.、6.、および7.は、Stockfishが`pvIdx`が0でないときだけ変える処理と同じである。
2.は基準の手の選び方だけが、5.はcorrection historyの扱いだけが、Stockfishと異なる。
この7つのほかに、次に述べる詰みを探す印の決め方もStockfishと異なる。

根の部分木のノード数は、根の手の並べ方に使う（[根の手の順序のADR](../adr/order-root-moves-by-previous-subtree-nodes.md)）。
いまは、窓外れの読み直しの分も含めて手ごとに足し、窓の中で探索を終えたときに前の反復の記録を置き換える（`root.rs`の`search_iteration`）。
Nが2以上では、読み直しの分を含むN本の全体で手ごとに足し合わせ、反復が完了したときに1回だけ置き換える。
1本ごとに置き換えると、最後の読み筋で読んだ手の記録だけが残るからである。

根の置換表の記録は、いまも根では探索の打ち切りに使わない。
LMRは、後に読む手の深さを減らす手法である。
根では、記録の手を最初に読む手の候補に使い、記録の値と深さを、LMRの量の計算と、枝刈りの判断に使う評価の補正（`pruning.rs`の`pruning_eval`）に使う。
また、記録にある補正前の静的評価は、根の局面の静的評価としてそのまま使う（`root.rs`の`order_root_moves`と`search_root`）。
2本目以降は、最初に読む手を3.の基準の手に置き換え、記録の値と深さと静的評価はいまのとおりに使う。
Stockfishも、2本目以降の根では置換表の手だけを置き換え（同840行）、記録の値は同じように使う。

詰みを探す印（seek mate）は、前の反復の値の絶対値が深さに応じた閾値を超えたときに立てる印である。
この印は、null move pruningで減らす深さと、王手の手のLMRを控えめにする（`pruning.rs`の`is_seek_mate`）。
null move pruningは、手番を1回飛ばして浅く読み、それでも十分に良ければ枝を刈る手法である。
本書は、k回目の印を基準の手の前の反復の値で決め、基準の手が前の反復のN本になければ印を立てない。
印は前の反復の値が勝ちか負けに近いことを表すので、その回で読む手の前の反復の値で決めるのが印の定義に沿う。
Stockfishでは、この印はその時点の`rootMoves[pvIdx]`の値から決まる（同395行）。
Stockfishは、各回の根の探索で最初に読んだ手でも最善の値を更新した手でもない根の手の値を負の無限大にするので（同1538行）、2本目以降の`rootMoves[pvIdx]`がそのような手なら、値の絶対値が閾値を超えて印が立つ。
Stockfishはこの印の閾値を棋力のための調整の対象にしないと明記しており（同394行）、本書はこの挙動を写す理由がないと推論する。

### 反復の完了と途中で止まった反復

Nが2以上では、全N本を窓の中で読み終えた反復だけを完了とする。
反復の途中で探索が止まったら、その反復で読み終えた読み筋も含めて丸ごと捨て、最後に完了した反復のN本を結果とする。
Nが1なら、これはいまの規則と同じである。
深さ1のN本を読み終える前に止まった場合は、いまと同じく、深さ0の結果として根の候補の先頭の手と静的評価を返す。
このとき完了のイベントの読み筋の列は、その1手だけの1要素とし、Nにかかわらず`info`行を出さない。
いまも深さ0の結果は`info`行として出さないので（`usi.rs`の`write_final_info_if_deeper`）、この扱いはNが1のときと同じである。

minaseは、上限時間で止めた反復の値を捨て、秒読みと固定時間の途中結果だけを例外とする規則を採っている（[中断した反復を捨てるADR](../adr/keep-discarding-hard-interrupted-iterations-and-reject-fair-share-budgets.md)）。
本書はこの規則をN本の全体へ広げる。
Stockfishは、止まった反復で読み終えた読み筋を残し、未完了の順位には前の反復の値と1つ浅い深さを出す（`src/search.cpp`の2318〜2323行）。
さらに、止まった探索の値が先に完了した読み筋の確定した負けを追い越さないよう補正する（同464〜510行）。
この方式を採ると、出力の1行ごとに深さが異なり、前の反復の読み筋を手ごとに保持して出力に使う仕組みと、止まった探索の値の補正が要る。
本書の方式では、出力はいつも同じ深さのN本であり、そのどちらも要らない。
代わりに、短い思考時間で大きなNを指定すると、最初のN本がそろうまで結果が深さ0のままになる。

各ワーカーは、前の節の2.〜4.の処理と詰みを探す印に使うために、最後に完了した反復のN本の手、値、および読み筋を、次の反復まで保持する。
これは、Stockfishの`RootMove`が持つ`previousScore`と`previousPV`のうち、上位N手の分に当たる。

### 途中結果

秒読みは、持ち時間が尽きた後に1手ごとに与える一定の時間である。
秒読みつきの時計と、1手の思考時間を固定する`go movetime`の探索では、上限時間で止めた反復でも、前の反復の最善手を読み終えていれば、その反復で読み終えた手の中の最善手を途中結果として採ることがある（`root.rs`の`RootResults`）。
これらの探索では、根で置換表の手に代えて前の反復の最善手を最初に読むように並べ替える。

Nが2以上では、途中結果も、この並べ替えも使わない。
途中結果は1本の読み筋の下界であり、前の節の「同じ深さのN本」という結果の形に収まらない。
また、前の反復の最善手を最初に読む並べ替えは、その手が根の候補にあることを前提とするので、その手を除いた2本目以降の探索では使えない。
1本目にだけ途中結果を使う代案は、止まった反復の1本目だけを新しい深さにすることになり、前の節の方式と矛盾する。
Nを2以上にするのは対局のためではないので、秒読みの着手の選び方がNで変わっても、対局と棋力測定には影響しない。

### 時間管理

時間管理は、反復が完了した時点で、いまと同じ規則で判断する。
判断に使う最善手は、並べ直した後の1本目の手である。
反復をまたぐ最善手の安定の判定もこの手で行うので、並べ直しで最善手が入れ替わればその変化も数える。
1本の探索の中での最善手の変化の回数は、1本目だけで数える（「αβ探索の方式」の節の6.）。
最善手に費やしたノード数の割合は、Stockfishと同じく、1本目の手の累計ノード数を全体のノード数で割って求める。
Nが2以上では2本目以降のノード数も全体に入るので、割合は小さくなるが、Stockfishはこれを補正しない（同592〜610行）。

詰みによる早期停止では、Stockfishと同じく、N本目の値が3手以内の勝ちであるか、1本目の値がちょうど2手の負けであるときに探索を止める（同624行）。
3手と2手は、いまの`mate_early_stop`（`time.rs`）がStockfishから写した値であり、本書は変えない。
1本目だけで勝ちを判定すると、2番手以下の手の値が分からないまま探索を止めてしまう。
Nが1ならN本目は1本目であり、いまの`mate_early_stop`と同じ判定になる。

棄却した代案は、Nが2以上で、評価値の低下、最善手の安定、最善手の変化の回数、および最善手への探索量の集中による持ち時間の伸縮を止める案である。
この案の根拠は、伸縮が1本目の手の安定だけを見ており、2番手以下の手の安定を表さないことである。
しかし、Stockfishもやねうら王も、Nが2以上でこの伸縮を使い続ける（やねうら王`yaneuraou-search.cpp`の1924行以降）。
また、伸縮を使うかどうかの判定は、相手の手番に読む先読み（ponder）の後の手で持ち時間の目安を25%増やす処理などと共有されている。
この判定は`team.rs`の`uses_instability_scaling`であり、25%の増分は[先読みの予算のADR](../adr/measure-budget-from-ponderhit-and-add-a-quarter-after-pondering.md)が定めたものである。
Nが2以上のときだけ伸縮を止めると、この共有の判定を2つに割ることになる。
Nを2以上にするのは対局のためではないので、分岐を増やしてまで2番手以下の安定を時間配分に反映する理由がない。

### Lazy SMP

補助ワーカーも、主ワーカーと同じ反復深化の関数でN本を読む。
Stockfishとやねうら王のLazy SMPも、補助スレッドが同じループでN本を読む。

結果の選び方は変えない。
いまのminaseは、完了した深さが最も大きいワーカーの結果を採る（`team.rs`の`select_worker_outcome`）。
採ったワーカーの最後に完了した反復のN本を、そのまま結果とする。
ワーカーの間で読み筋を混ぜることはない。
Stockfishは2026年4月のコミット50e8ff1eで、Nが2以上でもスレッドを選ぶようにした。
やねうら王は、Nが1のときだけスレッドを選び、2以上では主スレッドの結果を採る（`yaneuraou-search.cpp`の1167行）。

本書は現行のStockfishに合わせ、Nによって選び方を分けない。
主ワーカーの結果に限る代案の利点は、探索中に出した`info`と最後の結果が同じワーカーから来ることである。
しかし、いまもNが1で補助ワーカーの結果がより深ければ、最後にその結果を出しており（`usi.rs`の`write_final_info_if_deeper`）、この関係はNが2以上でも変わらない。
採ったワーカーのN本はその深さでそろっているので、主ワーカーに限る理由がなく、限ればNが1の経路と2以上の経路を別々に確かめることになる。

### αβ探索の出力の時期

探索中の`info`は、反復の全N本を読み終えたときに、N行をまとめて出す。
USI原典は、複数の読み筋を出すときは「k本をk行でまとめて送る」と定める。
探索の終了時には、いまと同じく、採った結果が最後に出した深さより深い場合にだけもう1回出す。
「反復の完了と途中で止まった反復」の節の方式では、最後に出したN本と同じ深さの結果は同じ反復のN本なので、出し直す必要がない。

Stockfishは、ノード数が1,000万を超えた後は、反復の完了を待たずに読み筋を1本読み終えるたびにも途中の出力を出す（同516行）。
やねうら王は、これに出力の間隔の下限`PvInterval`を加え、その既定値は300ミリ秒である（同1789〜1792行）。
本書がこれを採らないのは、いまのminaseが1本の読み筋でも窓外れの途中経過を出さず、反復の完了ごとにだけ出しており、その規則を保つ方が単純だからである。
深い検討で更新が遅いという要望が出たら、そのときに別に計画する。

### PV-MCTSの方式

PV-MCTSでは、探索は変えない。
探索の木では、局面を節点、指し手を節点から子へ向かう辺で表す。
確定した手とは、その先を読み切って勝ちか負けかが決まった手である。
探索の終了時に、根の辺をいまの最善手と同じ比較規則（`tree.rs`の`compare_edges`）で降順に安定に並べ、上位N本を読み筋とする。
比較規則では、まず、確定した勝ちの手、未確定の手、確定した負けの手の順に並べる。
確定した手どうしは、確定した値で比べる。
未確定の手どうしは、その辺を通って読んだ回数である訪問回数で比べる。
訪問回数が同じなら、訪問済みの手は平均の勝率Qで比べる。
未訪問の手は、ネットが各手に与える確率である方策を、確率に正規化する前の値logitで比べる。
最後まで同じなら、元の辺の順序を保つ。
`best_edge`も同じ比較規則で、同じときは先の辺を採るので、1本目の手は常に最善手と一致する。
並べるのは辺の添字の列であり、木の辺そのものは並べ替えない。
木の経路は辺の添字で表され、次の手で木を再利用するときにもその添字を使うからである。

dlshogiは、Nが2以上のとき、確定した勝ちの手を先に、確定した負けの手を後にし、残りを訪問回数、次に方策の確率の順に並べる比較関数で根の子を部分的に整列して上位N本を出し、探索の選択式は変えない（`usi/UctSearch.cpp`の812〜856行と973〜1029行）。
ただし、Nが1のときは別の関数`select_max_child_node`（`usi/UctSearch.h`の127行）で最善手を選び、この関数は訪問回数が同じ手を方策で比べないので、Nが1の最善手とNが2以上の1本目が一致しないことがある。
ふかうら王は、最善手を選ぶ関数と同じ比較関数で上位N本を整列し、1本目を`bestmove`にする（`PrintInfo.cpp`の24〜46行、102〜131行、および280行）。
minaseはふかうら王と同じく、最善手と読み筋の順位に1つの比較規則を使う。
上位N手へ訪問を配る選択式を新しく作る代案は、どの先行実装にもなく、対局の探索の配り方を変えてしまうので採らない。
その代わり、2番手以下の手は最善手より少なく読まれるので、その評価値は最善手の評価値より粗い推定になる。

各読み筋は、根の辺の手に、その子の節点から`best_edge`をたどった手を続けたものとする。
これは`principal_variation`と同じたどり方であり、未訪問の辺に達したら止める。
深さは読み筋の手数とし、いまと同じである。

評価値は辺ごとに求める。
確定した辺は、子の確定した勝敗を根の手番側から見た勝敗に反転し、手数を1増やした値を使う。
これはいまの`Proof::score`と同じ値であり、同一局面の反復による勝敗の帯の区別もそのまま保つ。
未確定で訪問済みの辺は、その辺のQを勝率pとし、いまの`Driver::score`と同じく0.001〜0.999に丸めてから、勝率尺度（ロジット1あたりの評価値の大きさで、単位はcp）を掛けた対数オッズで評価値に換算する。
換算の式と丸めの範囲は、[MCTSの対局の探索のADR](../adr/search-mcts-games-by-puct-with-virtual-loss-batches.md)が定めたものである。
1本目は、いまの`Driver::score`の値をそのまま使う。
`go nodes 1`のように最善手が未訪問のときも、1本目はいまと同じく根の価値から評価値を求める。

2本目以降の未訪問の辺は、評価値を付けず、その手だけの読み筋として出す。
未訪問の辺には、その手を指した後の局面の価値の推定がないからである。
これはdlshogiと同じ扱いである（`usi/UctSearch.cpp`の1017行）。
ふかうら王は未訪問の辺を勝率0.5、すなわち評価値0として出すが（`PrintInfo.cpp`の133行）、0は推定ではなく根拠のない値なので採らない。
未訪問の辺を出さない代案は採らない。
比較規則では、未訪問の未確定の辺は確定した負けの辺より上位にあるので、未訪問の辺を省くと、その下にある確定した負けの手の行まで省くか、比較規則の順を飛ばして出すことになる。
USI原典は`info`行の`score`を必須としておらず、dlshogiも評価値のない行を出す。
1本目の評価値は、いまと同じく常に出す。

`nodes`は、いまと同じく全体のシミュレーション回数を各行に出す。
ふかうら王は2本目以降の行の`nodes`にその辺の訪問回数を出すが（`PrintInfo.cpp`の250〜251行）、USIの`nodes`は探索全体の量であり、ふかうら王の該当箇所のコメントにも、GUIの側に特別な扱いが要ると記されている。

### `info`行の形

`MultiPV`が1のときの`info`行は、いまの形を変えない。

```text
info depth <d> score <評価> nodes <n> nps <nps> time <ms> pv <着手>...
```

`MultiPV`が2以上のときは、`depth`の直後に`multipv <k>`を入れたk＝1、…、Nの行を、順位の順に続けて出す。

```text
info depth <d> multipv <k> score <評価> nodes <n> nps <nps> time <ms> pv <着手>...
```

PV-MCTSの2本目以降の未訪問の辺の行は、`score <評価>`の部分を持たない。
各行の`depth`は、その読み筋の深さであり、αβ探索では全行が同じ深さ、PV-MCTSでは行ごとに読み筋の手数になる。
`nodes`、`nps`、および`time`は、全行で同じ値を出す。
途中結果の下界を示す`lowerbound`と、その前の`info string partial`は、途中結果を使うNが1のときだけ、いまと同じく出る。

USI原典は、複数の読み筋を出す場合に最善の読み筋へ`multipv 1`を付けると定め、1本だけの場合は求めていない。
dlshogiも、Nが1のときは`multipv`を付けない（`usi/UctSearch.cpp`の988行）。
Stockfishとやねうら王はNによらず`multipv 1`を付けるが、それに合わせると、既定値でも出力がいまと変わる。
いまの`info`行は、`protocol/usi.rs`の試験が行の文字列で照合しており、既定値の出力を変えるとそれらの期待も書き換えることになる。
一方、根の候補手が1つでも`MultiPV`が2以上なら、途中結果の`lowerbound`つきの行を含めて、`info`行に`multipv 1`を付ける。

`bestmove`は1本目の読み筋の1手目、ponderの予想手は1本目の読み筋の2手目とし、いまと同じく合法性を確かめてから付ける。
評価値による投了の判定（`should_resign`）も、いまと同じく採った結果の値、すなわち1本目の値で行う。
2本目以降の悪い値では投了しない。

### 対局ハーネスの評価値

対局ハーネス`minase match run`と、係数を対局の勝敗から調整するSPSAの道具`minase spsa`は、`bestmove`の前の最後の評価値つき`info`行の値を、その手の評価値として記録する（`crates/minase/src/harness/engine/usi.rs`の`observe_usi_evaluation`）。
いまのままでは、エンジンに`MultiPV`を2以上で指定すると、N番手の値を最善手の評価値として記録してしまう。
そこで、`multipv`を含まない行と`multipv 1`の行だけを記録の対象にする。
USI原典は、複数の読み筋を出すときに最善の読み筋へ`multipv 1`を付けると定めるので、この規則はminaseに限らず外部のエンジンにも当てはまる。
棋力測定は既定値1で行うので、この変更は測定の記録を変えない。

### 採否の判定

既定値1では探索の手順を変えないので、採否は対局ではなく、出力の一致と速さで確かめる。
CONTRIBUTING.mdは、棋力に影響し得る変更の採否をSPRTで決めると定める。
本書の変更が既定値で棋力に影響しないと言える根拠は、次の2つである。

第1に、Nが1のときの処理は、2回目以降の読み筋に関わる分岐をすべて飛ばし、いまと同じ手順になるように書く。
この手順の一致は、まず、時計を使わずに結果が決まる`Threads=1`の固定の深さと固定のノード数の探索で、各局面の最善手、評価値、およびノード数がいまと一致することで確かめる。
ただし、持ち時間つきの探索の時間管理は、反復ごとの最善手と評価値に加えて、反復の中で最善手が変わった回数、最善手に費やしたノード数、全体のノード数、および前の探索から引き継ぐ評価値の平均と時間の短縮率を入力にして判断する（`deepening.rs`の`run_main_worker_with_iteration_hook`、`team.rs`の`record_previous_search`）。
固定の深さの探索の結果が一致しても、これらの入力の一致までは確かめられない。
そこで、試験用の制御できる時計`ManualClock`（`crates/minase/src/search/alphabeta/tests/mod.rs`）で持ち時間つきの探索を進める一時的な診断を、基準と候補の作業ツリーに同じ内容で置いて実行し、反復ごとの時間管理の入力、停止の理由、および結果が一致することを確かめる。
診断では、前の探索の状態を引き継ぐように同じ対局の局面を続けて探索し、補助ワーカーの関数（`deepening.rs`の`run_auxiliary_worker`）も単独で動かす。
手順は「検証」の節の3.にある。
`Threads`が2以上の探索は、置換表への書き込みの順序が実行ごとに変わり、いまも結果の再現を保証していないので（`team.rs`のモジュールのdocコメント）、主ワーカーと補助ワーカーの関数をそれぞれ単独で動かして確かめる。
診断はいまの出力を正解として残す試験ではないので、コミットしない。
時間管理の各判断を固定したいまの試験（`crates/minase/src/search/alphabeta/tests/time.rs`など）が変更なしで通ることも確かめる。

第2に、変更は根の探索と反復深化の関数に閉じ、各節点の探索（`negamax.rs`、`quiesce.rs`）は変えないので、1ノードあたりの処理は変わらない見込みである。
この見込みは、「検証」の節のbenchの速さの比較で確かめる。
速さが変わらず手順が同じなら、同じ持ち時間で読む量も選ぶ手も変わらない。

SPRTを行う代案は採らない。
Eloは、対局の勝率から換算した強さの差である。
minaseのSPRTの採否基準は、帰無仮説を0 Elo、対立仮説を10 Eloの改善とする検定であり（[SPRTの手引き](../guides/sprt.md)）、変わらないことを示す検定ではないので、本書の採否の判定には使えない。
処理を変えない変更をbenchの出力の一致で確かめる方法は、探索部のモジュール再編などで採ってきた（[移動だけの再編の教訓](../lessons/verify-move-only-reorganization.md)）。

## 探索から通信層へ渡すイベント

探索から通信層へ送る進捗のイベント`SearchEvent::Progress`と完了のイベント`SearchEvent::Finished`は、いま1本の読み筋`pv`と、その値`score`と深さ`depth`を持つ。
これを、順位の順に並べた読み筋の列に改める。
列の各要素は、読み筋の手の列、深さ、および値を持ち、値はPV-MCTSの未訪問の辺では持たない。
ノード数、経過時間、および探索の識別子は、いまと同じくイベント全体で1つずつ持つ。
`Finished`は、いまと同じく、`bestmove`に使う最善手、投了の判定に使う完了した反復の値と深さ、途中結果の下界、および停止の理由も持つ。
`MultiPV`が1のとき、列は1要素であり、その要素はいまの`pv`、値、および深さと同じである。
途中結果を採ったときは、いまと同じく、列の要素の読み筋を途中結果の読み筋とし、値の下界は`Finished`の途中結果の欄で示す。

CECPの層は、`Finished`の最善手だけを使っており、変更の影響を受けない。
`SearchEvent`は`minase`クレートの公開の型であり（`crates/minase/src/search/mod.rs`）、そのフィールドを変えるのは、CONTRIBUTING.mdの公開APIの互換性を壊す変更に当たる。
エンジンの公開APIから型を消した過去の変更も、互換性を壊す変更として扱った（[旧パスを残さないADR](../adr/do-not-re-export-moved-items-at-old-paths.md)）。
そのため、この変更のコミットメッセージでは、Conventional Commitsのtypeの直後に`!`を付け、本文に`BREAKING CHANGE:`フッターを書く。
旧い形のフィールドは残さない。

## 検証

各フェーズで、`cargo fmt --check`、`cargo clippy`、および[テストの手引き](../guides/testing-minase-rules.md)のマージ前の検査を行う。
既定値1の一致は、変更前のmasterのコミットを基準、変更後のコミットを候補として、同じ機械で同じrelease設定でビルドした2つのバイナリで確かめる。
αβ探索の局面には、`bench`の15局面（`crates/minase/src/diagnostics/bench.rs`の`BENCH_POSITIONS`）を使う。

1. `scripts/bench_compare.py`の参照、基準、および親の3つの指定のすべてに基準のコミットを与え、`--depth 9 --threads 1`で候補と比べたとき、局面ごとのノード数、最善手、および評価値が全行一致する（[移動だけの再編の教訓](../lessons/verify-move-only-reorganization.md)）。深さ9は、係数を対局の勝敗から調整するSPSAの道具が、借りる機械の速さを測るのに使う深さと同じである。
2. αβ探索を`Threads=1`で起動し、15局面のそれぞれに`go depth 9`と`go nodes <n>`を送ったUSIの出力が、`time`と`nps`の値を除いて一致する。nは、1.のbenchでその局面の深さ9の探索に要したノード数の半分とし、深さ9までのどこかの反復の途中で止まるようにする。`go nodes`では、`info string stop nodes`が出て、最後の`info`行の深さが停止の前に完了した反復の深さであること、すなわち反復の途中で止めて未完了の反復を捨てたことも確かめる。
3. 「採否の判定」の節の一時的な診断で、制御できる時計を使った持ち時間つきの探索を、基準と候補で同じ局面の列について実行し、反復ごとの時間管理の入力（最善手、評価値、反復の中で最善手が変わった回数、最善手に費やしたノード数、全体のノード数）、前の探索から引き継ぐ値、停止の理由、および結果が一致する。局面の列は、初期局面から固定の着手列で進めた同じ対局の連続した局面とし、表を引き継いで続けて探索する。補助ワーカーの関数も、同じ局面で単独で動かして結果を比べる。
4. PV-MCTSを、推論にCPUを使う設定（`NnBackend=cpu`）で起動し、同じ15局面に`go nodes 800`を送ったUSIの出力が、`time`と`nps`の値を除いて一致する。800回は、これまでのMCTSの固定ノードの対局と同じ1手の回数である。ネットは、AlphaZero型探索の強化学習の1回目の実行で32周目（サイクル32）に得た学習の状態を、学習器の`export-onnx`でONNX形式のファイルとしてリポジトリの外の作業用ディレクトリへ書き出し直したものとする。ネットワーク接続の記憶装置（NAS）にある`nets/cycle-0032.onnx`は入力と方策の出力が32ビットの浮動小数点数であり、いまの推論器が受け付ける形式と異なるからである。いまの推論器は、入力を8ビットの整数、方策を16ビットの浮動小数点数で受け渡す。2つのバイナリは同じ書き出し済みのファイルを使い、ONNX Runtimeの環境は`tools/train/zero/env.sh`で読み込み、ファイルのSHA-256を記録する。
5. 1.の`scripts/bench_compare.py`で、`--rounds 3 --repetitions 3`の速度の比較を、ほかの負荷を止めた同じ機械で行う。親に対する候補の速度比（親比）と1との差が、同じ出力に併記される親の分解能以内に収まる。親比は候補と親の毎秒ノード数の比であり、分解能は、親を候補と交互に測った各回の中央値について、最大と最小の差を、それらの中央値で割った割合である。3回ずつの交互測定は、`scripts/bench_compare.py`の既定の回数である。収まらなければ、生成コードの関数の集合と機械語の大きさを`nm --size-sort`で基準と比べて原因を調べる。`nm`による比較は原因を探すためのものであり、速度の条件を満たしたことの代わりにはならない。

Nが2以上の性質は、実装の出力を写すのではなく、MultiPVの定義、USI原典、および本書の契約から導いた期待で試験する（[テストの一般原則](../guides/testing-general-principles.md)）。

6. αβ探索で`Threads=1`の固定の深さの探索をすると、各`Progress`の読み筋の数はNであり、各読み筋の1手目はすべて異なって根の候補に含まれ、全行の深さは同じで、値は降順に並ぶ。最後の`Progress`の1本目の手は、`Finished`の最善手と一致する。`MultiPV`が根の候補手の数より大きい局面、根の候補手が1つの局面、R1で反復勝ちの手だけが候補になる局面、およびR1で全合法手が反復負けに直結して全手が候補に残る局面も試す。
7. 王駒を取る手がちょうど2つあり、ほかの手には固定の深さで詰みがないことを確かめた固定の局面で、その深さで`MultiPV`を3にすると、1本目と2本目がその2手で詰みの値を持ち、3本目は詰みの値を持たない。
8. 深さ1の探索では、根の子は静止探索で読まれ、静止探索はcorrection historyを更新しない。そこで、新しい表から始めた`MultiPV`が1の深さ1の探索と2の深さ1の探索とで、根の局面の置換表の記録と、根の局面のキーに当たるcorrection historyの値が一致することを確かめる。これは、2本目の根の探索が根の局面の値として保存も学習もしないことを示す。
9. αβ探索を反復の途中で止める試験を、最初の反復の途中で止める場合と、前の反復が完了した後の2本目以降の途中で止める場合に分けて行う。前者では深さ0の1手だけの結果になり、後者では直前に完了した反復のN本と一致する。
10. Lazy SMPの結果の選び方を、主ワーカーと補助ワーカーの結果を組み立てた入力で試す。採ったワーカーの同じ反復からN本すべてを返し、同じ深さでは主ワーカーを採り、補助ワーカーの結果がより深いときだけ最後のN行を出す。
11. PV-MCTSの読み筋の順位を、確定した勝ちの辺、未確定の辺、確定した負けの辺、訪問回数、Q、未訪問の辺の方策のlogit、およびすべてが同じ辺の組を具体的に並べた木で試す。期待する順位は、`compare_edges`で求めるのではなく、本書の比較規則から手で書く。1本目は最善手と一致し、2本目以降の未訪問の辺は値を持たない。最善手が未訪問の`go nodes 1`に当たる木も試す。
12. PV-MCTSの確定した辺の値を、通常の勝敗と同一局面の反復による勝敗とに分けて試す。どちらも、子の勝敗を親から見た勝敗に反転して手数を1増やした値になり、反復による勝敗の値は`score mate`へ変換されずにcpとして出る。読み筋を取り出しても、木の辺の順序、訪問回数、Q、および次の手での木の再利用の結果は変わらない。
13. USIの層で、`MultiPV`が2以上のとき、`info`行は`multipv 1`から順に連続して出て、各行の読み筋は根から合法に指し進められる。`bestmove`は、投了する場合を除き、`multipv 1`の行の1手目と一致する。`MultiPV`が1のときは`multipv`を含まない。根の候補手が1つで`MultiPV`が2以上なら、途中結果の`info string partial`の後に続く`lowerbound`つきの`info`行にも`multipv 1`が付く。探索が自然に終わる経路の`handle_search_event`、`stop`で止める経路の`finish_search`、および`ponderhit`を通る経路のそれぞれで確かめる。`MultiPV`の1、2、および35,856を受け付け、0、35,857、および整数でない値の`setoption`は拒否する。
14. 対局ハーネスは、`multipv 2`以降の行の評価値を記録せず、`multipv`のない行と`multipv 1`の行の評価値を記録する。`multipv 1`の行の後に、評価値つきの`multipv 2`以降の行と評価値のない行が続いても、`multipv 1`の行の記録を保つ。

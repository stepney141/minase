# NNUEに合わせた探索係数と時間管理係数のSPSAによる再調整の設計書

## 先に読む要約

本書は、探索が使う既定の評価関数がNNUEに置き換わったことを受けて、探索と時間管理の係数をNNUEのもとで調整し直し、現行のmasterより強くなるかを確かめる。
係数とは、futility pruningやrazoringの余裕値、aspiration windowsの窓幅、historyの更新量、持ち時間の配分の比率など、`crates/minase/src/search/alphabeta/params.rs`の表にある整数である。
現行の値は、評価関数がPST（駒の種類と升ごとの点数の表）とFM（2駒の関係の補正）だった時期に、SPSA（simultaneous perturbation stochastic approximation、同時摂動確率近似）で決めた。SPSAは、全係数を同時に少しずらした2つの設定を対局させ、勝った側へ係数を動かす調整法である。
[NNUEの採用](archived/nnue-replacement.md)では、評価関数の効果を切り分けるために探索係数を固定していたため、係数はNNUEに合わせて一度も調整されていない。
NNUE（efficiently updatable neural network、差分更新できる小型のニューラルネットの評価関数）は、評価値の並び方も探索の速さもPST＋FMと異なるので、枝刈りの余裕値や時間配分の最適値が動いている見込みがある。
そこで、表の39係数のうち、NNUEでは評価に作用しない`FmScale`を除く38係数を、標準の規模で一度に調整する。標準の規模は3,000ペアであり、ペアは同じ開始局面から先後を入れ替えて指す2局の組である。
調整した値を表の既定値へ書き込んだ候補を、調整を始めた時点のmaster（起点）と対局させ、段階ゲートで採否を決める。段階ゲートは、短時間条件STCと長時間条件LTCの2段階で、勝敗が有意な差に達した時点で止める逐次検定を行う手順である。
完了条件は、調整の結果と候補の採否が測定記録とともに確定することである。

## 状態

起案。2026年10月13日に起案した。
係数の集合に時間管理の6係数を含めること、およびNNUE学習器の2計画（[学習率スケジュール](nnue-lr-schedule.md)と[隠れ層](nnue-hidden-layer.md)）の結論を待たずに現行のネットで調整することは、同日の利用者の決定である。
次の一手は、利用者の着手の指示を受けてフェーズ1（時間切れの事前確認）を始めることである。

## 目的

本書が確かめるのは、「探索係数と時間管理係数をNNUEに合わせて調整し直せば、調整前より強くなる」という仮説である。
係数の最適値が評価関数に依存する理由は2つある。
1つ目は、余裕値の意味が評価値の分布に依存することである。αβ探索は、最善手の評価値が入ると見込む区間（窓）を持ち、余裕値は、静的評価値が窓からどれだけ離れていれば手を読まずに捨てるかを決める閾値である。このため、評価値の散らばり方や局面ごとの誤差の出方が変わると、同じ余裕値でも捨てる手の割合が変わる。
2つ目は、探索の速さと木の形が変わったことである。[NNUEの学習記録](../measurements/nnue-replacement-training.md)のbench（15局面、深さ9）では、同じ係数のままで、NNUEの1秒あたり探索ノード数はPST＋FMより約9%少なく、深さ9までの総ノード数は6,326,125から4,202,024へ約34%減った。
同じ持ち時間で到達する深さと枝刈りの効き方が変われば、深さを得るために持ち時間をどれだけ使うかの釣り合いも変わり得るので、時間配分の係数の最適値も動く見込みがある。
先例は2つある。
[C5のセッション](../measurements/spsa-stage9-20260925-c5.md)は、一度SPSAで調整した値を同じ構成のまま調整し直し、STCとLTCでともに`H1`となって採用された。
一方、[共適応の検証](archived/eval-search-coadaptation.md)では、評価値の尺度を変えなかったPSTの候補の負けを、探索係数の再調整で取り戻せなかった。
どちらもPSTの時期のもので、評価関数の種類を替えた後の再調整ではないので、NNUEでの効果の大きさを予測する根拠にはならない。
そこで本書は、効果量を見込まずに対局で判定する。

## 適用範囲

本書の用語を次のように定める。

- **起点**は、フェーズ1を始める時点のmasterの先頭のコミットである。各フェーズのコマンドの`<起点>`には、このコミットのハッシュを入れる。起案時点の先頭はf99b6b6であり、評価関数は[NNUEの採用](archived/nnue-replacement.md)で入った幅128のNNUE（P型、現行のPSTを線形の経路として内包する型）である。
- **候補**は、起点からブランチを切り、調整の最終値を`minase spsa apply`で表の既定値へ書き込んだコミットである。
- **STC**と**LTC**は、それぞれ10秒＋1手0.1秒と60秒＋1手0.2秒の持ち時間で行う自己対局の採否測定である（[SPRTの手引き](../guides/sprt.md)）。
- **調整用ビルド**、**θ**（調整中の係数の中心値の組）、**反復**、**セッション**、`c_end`、`r_end`などSPSAの用語は、[SPSAによる係数調整の手引き](../guides/spsa.md)に従う。

対象は次のとおりである。

- 探索の32係数と時間管理の6係数（`ExpectedPlies`、`MinMoves`、`IncrementShare`、`HardSoftRatio`、`HardRemainingShare`、`IterationRatio`）を、起点の既定値から1つのセッションで調整する。探索の32係数には、[手の順序付けの改善](archived/move-ordering.md)で加わり、まだ一度も調整していない`HistoryBonusScale`、`HistoryMalusScale`、および`CaptureHistoryDecay`を含む。
- 候補を起点に対して段階ゲートで判定する。

次の事項は対象外とする。

- `FmScale`の調整。この係数を読むのはPST＋FMの評価（`crates/minase/src/eval/pst/fm.rs`）だけであり、NNUEを既定とするエンジンでは勝敗に影響しない。勝敗に影響しない係数を含めると、その係数の更新は雑音だけになるので、パラメーターファイルから削除する。表から係数自体を取り除くことは本書では行わない。
- 秒読みに関わる係数と`ByoyomiMargin`。調整は秒読みのない時間制御で行うので、勝敗に影響しない（[秒読みの項の係数のADR](../adr/exclude-byoyomi-terms-and-safety-margin-from-spsa.md)）。
- 係数の範囲の変更と、係数の追加や削除。
- NNUEの重みと評価式の変更。

## 依存関係

調整の対象は、起点の探索、時間管理、およびNNUEの重みの組である。
本書の着手前に、起点の探索、時間管理、または評価関数を変える変更がmasterへ入った場合は、新しい先頭を起点とし直す。
SPSAの手順と既定の設定は[SPSAによる係数調整の手引き](../guides/spsa.md)に、採否の手順は[SPRTの手引き](../guides/sprt.md)に従う。
調整用ビルドがNNUEの採用後もコンパイルできることは、起案時に`cargo check -p minase --features tuning --bin minase`で確かめた。

NNUE学習器の2計画のどちらかが採用されるとネットが変わり、係数の最適値もまた動く。
その時点で再調整するかどうかは、その計画の完了時に決める。

測定機はlishogiのBotと共用するので、同時対局数は16を上限とする。
[AlphaZero型探索の計画](alphazero.md)はフェーズ2の教師生成をSPSAの調整セッションの完了後に始めると定めているので、本書のセッションと同時には走らない。
[ファイル形式の整理](file-format-consolidation.md)は、SPSAと対局ハーネスの実行ディレクトリの形式を変えない。
ただし、セッションの途中で作業ツリーの`minase`が変わっても対局条件が揺れないように、runnerとして、起点でビルドした`minase`を専用の場所へ複製して固定する。

## 設計判断

| 項目 | 決定 |
|---|---|
| 係数の集合 | `FmScale`を除く38係数とする。時間管理の6係数を含めるのは2026年10月13日の利用者の決定である。NNUEは同じ持ち時間で到達する深さを変えるので、探索の係数だけを動かして時間配分を固定すると、時間配分の最適値の変化に追従できない。代償として、候補が強くなった場合に、その向上が探索と時間管理のどちらによるかは切り分けない。時間管理を含めたので、本番の前に時間切れの事前確認を行う（フェーズ1）。 |
| 開始値 | 起点の表の既定値とする。現行の値はPST＋FMで調整した値であり、NNUEの最適値から遠いとしても、範囲の中点などの人が選んだ値より近いと見込む。 |
| 範囲 | 起点の表の範囲をそのまま使い、本書の調整を既存の範囲の中に限る。余裕値は、探索用駒価値の歩兵の価値に係数を百分率として掛けて求める（`crates/minase/src/search/alphabeta/pruning.rs`の`futility_margin`など）。NNUEは探索用駒価値と、出力をセンチポーンへ換算する尺度（出力用K）を、採用PSTの重みファイルと同じ値で持つので（[NNUEの設計書](archived/nnue-replacement.md)の用語の節）、係数と余裕値の対応は変わっていない。ただし、これは評価の誤差や、静的評価値と探索値の差の分布が同じであることまでは意味しない。futility pruning、razoring、`DeltaMargin`、`CorrectionCap`、`AspirationDelta`などは、分布の変化によって最適値が範囲の外へ出る可能性がある。`SeeMargin1`（既定10、下限0）のように範囲の端に近い係数では、摂動した設定が範囲の端で切り詰められるが、これは過去のセッションと同じ扱いである。最終値を丸めた整数が範囲の上限または下限になった係数は、本書の範囲の制約に達した係数として測定記録に残し、範囲の見直しは本書では行わない。 |
| 同時対局数 | 16とする。測定機（20コア）はlishogiのBot（4スレッドで最大2局）と共用であり、Botが2局を指している間は、測定の16スレッドと合わせて20コアを超え得る。それでも16を保つのは、過去のSPSAと採否の測定がすべて同じ共用条件の16で行われていて、本書の結果をそれらと同じ条件で解釈できるからである。また、SPSAのθ+とθ−、および採否の測定の候補と起点は、同じ時間帯に同じ負荷を受ける。共用の負荷が係数の最適値を偏らせる可能性は残るが、同時対局数を下げると所要時間が延びるので、本書では下げない。 |
| SPSAの設定 | 既定の設定を流用する。`c_end`は範囲の1/6、`r_end`は0.002であり、摂動幅と学習率はfishtestの既定の指数で減衰する（[利得のADR](../adr/decay-spsa-gains-from-one-sixth-of-the-range.md)）。375反復、1反復8ペア（計3,000ペア）、持ち時間はSTCと同じ10秒＋0.1秒、同時対局数16とする。3,000ペアは最適値を精密に求める量ではなく、候補を1つ作るための予算であり、最終値を最適値とは呼ばない。 |
| NNUE学習器の計画との順序 | 現行のネットで先に調整する（2026年10月13日の利用者の決定）。採用中の構成をすぐに強くできることを優先し、ネットが変わった場合の再調整はその時点で決める。 |
| 採否 | 候補を新、起点を旧として、標準のSTCとLTCのGSPRTで判定する。LTCで`H1`となり、エンジン異常、時間切れ、および拒否着手が0件なら採用する。SPSA中の対局結果は採用の根拠にしない。候補は38係数の値を1組として扱い、不採用のときに一部の係数だけを選び直して再測定しない。 |
| 結果の解釈の記録 | 調整前に対する総思考時間の比、終局時の残り時間、手数帯ごとの完了深さ、および停止理由の分布を、採否の前の事前対局で記録する。時間の使い方が変わることは調整の目的に含まれるので、これらは合否の条件にしない（[SPSAの手引き](../guides/spsa.md)の第7節）。 |

## 所要時間の見積り

時間は、同時対局数16の測定機での見積りである。
SPSAの所要時間は、同じ規模の過去のセッション（3,000ペア、[C5](../measurements/spsa-stage9-20260925-c5.md)の27,138秒と[不採用改良の再調整](../measurements/search-revival-t.md)の29,463秒）に基づく。
1局の壁時計の時間は、手数、持ち時間の使い残し、および調整する時間配分で変わるので、表の値はPST＋FMの時期の記録に基づく概算である。フェーズ1の実測で、SPSA本体の見込みを更新する。

| 段階 | 内容 | 見積り |
|---|---|---|
| 1 | 時間切れの事前確認（13反復、104ペア） | 約20分 |
| 2 | SPSA（3,000ペア） | 約8時間 |
| 3 | 反映、テスト、および事前対局（32ペア） | 約1時間 |
| 4 | 候補のSTC | 約1〜8時間（判定までのペア数は強さの差で変わる） |
| 5 | 通過した場合のLTC | 約5〜30時間 |

全体では、STCで棄却される場合の約半日から、LTCまで進む場合の約2日までとなる。

## 実装フェーズ

エンジンのコードは変えない。
変更は、フェーズ3で`params.rs`の表の既定値を書き換えるコミットと、表の既定値に依存するテストの修正だけである。

基本シードは、時間切れの事前確認を2450000000、セッションを2500000000、事前対局を2550000000、STCを2600000000、LTCを2700000000とする。
いずれも起案時点で、保存済みの測定とSPSAの基本シード（`data/matches/`と`data/spsa/`の`manifest.json`）から各測定のペア数以上離れた未使用の値である（[教訓](../lessons/derive-seed-adjacent-collision.md)）。
着手時に同じ方法で未使用であることを確かめ直す。

各フェーズの開始前に、測定機でほかの対局測定、SPSA、教師生成、および学習が動いていないことを実行ファイル名で確かめる。

### フェーズ1　パラメーターファイルと時間切れの事前確認

起点でビルドした`minase`を`data/spsa/nnue-search-spsa-runner/`へ複製してrunnerとして固定し、以後のフェーズはすべてこのrunnerで実行する。
次のコマンドで既定のパラメーターファイルを生成し、`FmScale`の行を削除した38行のファイルを`data/spsa/nnue-search-spsa.params`とする。

```console
<固定したminase> spsa params \
  --engine commit:<起点> --rules engine-default > <既定のファイル>
```

生成したファイルの開始値と範囲が起点の`params.rs`の表と一致すること、および`c_end`と`r_end`が既定値であることを確かめる。

続いて、手引きの第3節に従い、時間管理の係数を思考時間が最も長くなる側の範囲の端に置いても時間切れが起きないことを確かめる。パラメーターファイルの写しの開始値を`HardRemainingShare`＝50、`HardSoftRatio`＝800、`MinMoves`＝40、`IterationRatio`＝150へ書き換えた`data/spsa/nnue-search-spsa-safety.params`で、13反復（104ペア）を実行する。

```console
<固定したminase> spsa \
  --run-dir data/spsa/nnue-search-spsa-safety --seed 2450000000 \
  --engine commit:<起点> --params data/spsa/nnue-search-spsa-safety.params \
  --rules engine-default --each time=10000+100 --concurrency 16 \
  --iterations 13 --pairs-per-iteration 8
```

`time_forfeits`が1件でもあれば、保存された異常局の記録から[デバッグの手引き](../guides/debugging.md#時間切れと時間管理)の手順で原因を調べ、該当する係数の範囲を狭める案を利用者に示してから本番へ進む。
結果は測定記録`nnue-search-spsa-safety`に残す。
完了条件は、時間切れとエンジン異常が0件であることと、測定記録の保存である。

### フェーズ2　SPSAによる調整

```console
<固定したminase> spsa \
  --run-dir data/spsa/nnue-search-spsa --seed 2500000000 \
  --engine commit:<起点> --params data/spsa/nnue-search-spsa.params \
  --rules engine-default --each time=10000+100 --concurrency 16 \
  --iterations 375 --pairs-per-iteration 8
```

最終のθを整数に丸めた値を、調整の結果とする。
途中の値を対局の成績で選び直さない。
結果は測定記録`nnue-search-spsa`に、手引きの第6節の項目（コマンドライン全体、起点とrunnerのコミット、パラメーターファイルの内容、θの開始値と最終値、有効ペア数と破棄ペア数、異常件数、および所要時間）とともに残す。
最終値を丸めた整数が範囲の上限または下限になった係数を測定記録で示す。
あわせて、開始値からの移動量が最後の反復の摂動幅`c_end`以上の係数を、移動の大きい係数として区別する。この閾値は解釈のための目安であり、採否には使わない。
完了条件は、セッションの完了と測定記録の保存である。

### フェーズ3　反映と事前対局

起点からブランチ`nnue-search-spsa`を切り、worktree `data/worktrees/nnue-search-spsa`で作業する。
手引きの第7節の手順1に従い、`minase spsa apply`で最終値を表の既定値へ書き込み、`git diff`で既定値だけが変わったことを確かめてコミットする。
続いて`cargo test`（通常ビルドと調整用ビルド）を測定より先に実行する。
表の既定値に依存するテスト（たとえば余裕値から窓を作る固定局面に依存する`razoring_accepts_quiescence_equal_to_alpha`）が失敗した場合は、テストの前提が新しい既定値でも成り立つ局面または窓へテストを直し、別のコミットにする。
テストの失敗を、末尾に`; true`を付けるようなコマンドの組み方で握りつぶさない。

候補の調整用ビルドの宣言を`minase spsa params`で出力し、既定値の欄が`apply`の出力と一致することを確かめる。
そのうえで、STCの条件で候補と起点の32ペアの事前対局を行う。

```console
<固定したminase> match run \
  --run-dir data/matches/nnue-search-spsa-smoke --seed 2550000000 \
  --candidate commit:<候補> --baseline commit:<起点> \
  --each time=10000+100 --concurrency 16 elo --pairs 32
```

候補と起点の総思考時間の比と終局時の残り時間は、`pairs/`に保存された各手の思考時間から計算する。終局時の残り時間は、持ち時間10秒に1手0.1秒の加算を着手数だけ足し、思考時間の合計を引いて求める。
手数帯ごとの完了深さと停止理由の分布は、`scripts/clock_profile.py`を`--role candidate`と`--role baseline`で別々に実行して集計する。このスクリプトが出す時間予算の比は、旧係数の予算式に基づくので解釈に使わない。
結果は測定記録`nnue-search-spsa-smoke`に残す。
完了条件は、テストの通過、事前対局での時間切れとエンジン異常が0件であること、および測定記録の保存である。

### フェーズ4　採否測定

```console
<固定したminase> match run \
  --run-dir data/matches/nnue-search-spsa-stc --seed 2600000000 \
  --candidate commit:<候補> --baseline commit:<起点> \
  --each time=10000+100 --concurrency 16 gsprt --max-pairs 3000
```

STCの判定は[SPRTの手引き](../guides/sprt.md)の振分け規則に従う。候補が有意に強い`H1`ならLTCへ進み、`H0`なら不採用とし、3,000ペアで判定保留ならその時点の対数尤度比の符号でLTCへ進むかを決める。
LTCは測定名の接尾辞を`-ltc`、基本シードを2700000000、持ち時間を`time=60000+200`とし、`--max-pairs`を付けない。
結果は測定名ごとの測定記録に残す。
完了条件は、採否の確定と測定記録の保存である。

## 検証

- パラメーターファイルが38行であり、`FmScale`を含まず、開始値と範囲が起点の表と一致すること。
- 候補の`params.rs`の差分が既定値の書き換えだけであり、調整用ビルドの宣言の既定値が`apply`の出力と一致すること。
- `cargo test`（通常ビルドと調整用ビルド）、`cargo clippy -- -D warnings`、および`cargo fmt --check`が通過すること。
- 時間切れの事前確認、SPSA、事前対局、および採否の測定で、エンジン異常、時間切れ、および拒否着手が0件であること。最初の測定で1件でも出た場合は、測定を止めて原因を調べる。測定機の外部要因による時間切れは、SPRTの手引きの「異常時の裁定」に従って扱う。

## 完了条件

- 時間切れの事前確認、SPSAの結果（θの推移と最終値）、事前対局、および採否が、測定記録に残っている。
- 採用した場合は、候補のブランチがmasterへ統合されている。統合は利用者の許可を得てから行う。
- 不採用の場合は、結論と測定記録だけをmasterへ残し、候補のブランチはmasterへ統合しない。
- ROADMAPの状態表が本書の結論と一致している。

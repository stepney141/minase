# 直前局面生成器の設計書

## 先に読む要約

本マイルストーンは、規則集合と対象局面を受け取り、その局面へ1手で到達できる直前局面をすべて列挙する`PredecessorGenerator`をライブラリの公開APIとして実装する。
直前局面とは、その局面で1つの合法手を指すと対象局面になる局面のことであり、逆方向探索（目標局面から手を逆にたどる探索）の基本操作になる。
生成器は思考エンジンの探索からは呼ばれず、minaseを依存ライブラリとして使う外部のRustプログラムだけが使う。
方式は、着手を逆向きに構成した候補局面を上位集合として作り、既存の順方向合法手生成器で候補着手を適用し直して対象局面と一致するものだけを残す。
合法性の判定は既存の生成器だけを正とし、逆生成側に規則の判定を複製しない。
候補の構成には、駒の動きの幾何を反転した移動元の集合、初期配置から求めた復元できる捕獲駒の在庫、および盤面だけから決まらない一時状態の列挙を使う。
一時状態とは、先獅子状態（非獅子が獅子を取った直後の1手だけ取り返しを制限する状態、RULES.md第15条）と成り権保留状態（敵陣で成らなかった駒が後で成れる権利を追跡する状態で、成り規則P1、P2、P5が使う、RULES.md第30条）の2つである。
準備として、`Position`に一時状態を読む公開アクセサと`Hash`を追加し、`validate()`にZobrist値の一致検査を加えるが、`Position`の内部表現、構築経路およびエンジンの探索経路は変えない。
完了条件は、全移動形式の固定テスト、全順方向辺の逆包含テスト、有限状態オラクルとの集合一致、公開APIによる深さ2の逆方向探索、および固定コーパスの計測記録がそろい、順方向の合法手生成、対局裁定、拡張SFEN、Zobrist値、perft値に挙動変更がないことである。

## 状態

待機中。2026年8月10日に起案し、実装は未着手である。依存するプロトコル層、探索部、評価関数はいずれも完了済みで、着手を妨げる未完了の依存はなく、着手前に確定を要する判断もない。再開条件は利用者による着手時期の決定であり、次の一手は、着手時点のmasterからブランチを切ってフェーズ1（`Position`の公開面の追加）を始めることである。

## 目的

本マイルストーンは、規則集合と対象局面`Position`を受け取り、その対象局面へ1手の局面合法手で到達できる直前局面を漏れなく列挙する`PredecessorGenerator`を実装する。
出力は盤面、手番、一時状態を含む完全な`Position`の集合とし、同じ直前局面へ至る着手が複数あっても、その局面を1回だけ返す。

主な利用者は、minaseを依存ライブラリとして呼び出す独立したRustプログラムである。
これにより、IshiiとTanakaが将棋の到達可能性判定に用いた逆方向探索と同型の探索を、中将棋の`Position`グラフ上へ構築できるようにする。
生成器は思考エンジンの探索からは呼ばれないため、`Position`の内部表現、評価関数、探索、プロトコル層、および学習データ形式に影響する変更を本マイルストーンで持ち込まない。

## 適用範囲

本マイルストーンでは、次の作業を行う。

- `Position`に、先獅子の記録升と成り権保留集合を読む公開アクセサを追加する。
- `Position`に、既存の`Eq`と整合する衝突安全な`Hash`を実装する。
- `Position::validate()`に2種類のZobrist値の一致検査を加える。
- 全直前局面を列挙する公開型`PredecessorGenerator`を追加する。
- 初期配置の駒在庫を基準に、復元できる捕獲駒を所有者別かつ由来別に制限する。
- 通常移動、走り、固定跳び、獅子、角鷹および飛鷲の全移動形式を逆向きに構成する。
- 非捕獲、1枚捕獲、2枚捕獲、既成駒の移動および直前手での成りを扱う。
- 対象局面から決定できない直前局面の一時状態をすべて列挙する。
- 全候補を既存の順方向合法手生成器で検証し、対象局面との完全一致を確認する。
- 健全性、相対的完全性、一意性および性能を再現可能な方法で検証する。

次の項目は対象外とする。

- `Position`の内部表現（`LionTrigger`、`promotion_deferred`、`Undo`、`NullUndo`）、Zobristキー、および既存の構築経路`PositionBuilder::mark_promotion_deferred`と`Position::set_lion_capture`は変更しない。
- 評価関数、探索、学習データ形式、拡張SFENの契約、プロトコル層、および`src/bin`配下のエンジンと補助バイナリは変更しない。
- `Game`全体、反復履歴、手数、駒枯れ猶予および終局結果の逆生成は行わない。
- 初期局面から各直前局面までの大域的な到達可能性は判定しない。
- 集計、状態の縮約、状態数の計算および永続化は行わない。
- 多手の逆方向探索、探索順序、目標集合および到達不能判定は実装しない。
- ファイル入出力、CLI、USI、CECPおよびGUIとの接続は行わない。
- 計測前に専用逆利き表、並列化、キャッシュまたは逆向き差分更新を導入しない。

## 依存関係

本マイルストーンは、完了済みの[プロトコル層](protocol-layer.md)と[規則集合の代数的データ型化](rules-type.md)を前提とする。
プロトコル層は、成り権保留集合を`PositionBuilder::mark_promotion_deferred`で、先獅子状態を`Position::set_lion_capture`で設定する公開の構築経路と、局面を文字列で受け渡す拡張SFEN（[protocol-layer.md](protocol-layer.md)が定める5欄の局面表記）を提供しており、生成器と外部プログラムはこれらをそのまま使う。
規則集合は`Rules`と、その部分である着手規則`MoveRules`に分かれており、生成器は後者だけを受け取る。

順方向の探索部と評価関数は本マイルストーンの完了を前提とせず、本マイルストーンはそれらの挙動を変えない。
作業は共通ポリシーに従い、着手時点のmasterから本設計書専用のブランチを切って行う。

## 設計判断

| 項目 | 決定 |
|---|---|
| 生成対象 | `Game`ではなく、次の局面合法手を決める`Position`を対象とする。反復履歴と裁定状態は`Game`が別に持つためである。 |
| 出力単位 | 一時状態を含む完全な直前`Position`とする。着手は内部検証にだけ使う。 |
| 一意性 | 同じ`Position`を1回だけ返し、返却順序は公開契約に含めない。 |
| 合法性の正 | 既存の`MoveGenerator`を唯一の正とし、逆生成側に合法手判定を複製しない。 |
| 規則の受け取り | 生成器は`MoveRules`を受け取る。反復規則と終局規則は`Position`単位の合法手を変えないため、`Rules`全体は保持しない。 |
| `Position`の内部表現 | 変更しない。生成器が必要とするのは一時状態の読み出し、既存の構築経路、および`Hash`だけであり、エンジンの探索経路に触れる理由がない。 |
| 一時状態の構築 | 既存の公開経路`mark_promotion_deferred`と`set_lion_capture`を使い、新しい構築APIを追加しない。麒麟成り例外の盤面からの導出は`set_lion_capture`が既に実装している。 |
| 構築経路の受理範囲 | 既存の構築経路と拡張SFENの受理範囲は変えず、逆生成専用の必要条件は生成器だけが課す。 |
| 候補生成 | 逆向きの幾何、在庫および一時状態から上位集合を構成し、順方向再適用で絞る。 |
| 移動元 | 既存の移動プロファイルと利き表から`Bitboard`として構成し、専用逆利き表は設けない。 |
| 捕獲駒 | 初期配置から対象局面の盤上駒を差し引いた由来別在庫だけを復元候補にする。 |
| 一時状態の列挙 | 不明値や既定値へ置換せず、局所的に整合する具象値を列挙する。P2の待機満了で消える保留状態も列挙する。 |
| 候補局面 | 初回実装では`PositionBuilder`で盤面全体を再構築する。 |
| 不正入力 | 対象局面にも集合`A`の全条件を課し、違反は空集合へ変換せず、条件の群ごとの型付きエラーにする。 |
| 候補の検査 | 候補局面は順方向再適用の前に集合`A`への所属を検査する。再適用と対象局面との一致だけでは、着手で消えるビットの違反を検出できないためである。 |
| ハッシュ | `Position::Hash`は`HashSet`のバケット選択に使い、局面一致は常に`Eq`で確定する。反復判定のキーには使わない。 |
| 実行状態 | 生成器は呼び出し間の可変状態を持たず、`Send + Sync`である。 |
| 最適化 | 全機能版の計測後に、支配的と確認された処理だけを変更する。 |
| 互換性 | 別名API、暗黙の規則変更および失敗時の代替経路を追加しない。 |

棄却した代案は次のとおりである。
先獅子状態と成り権保留状態を1つの公開値`TransientState`へ統合し、`Position`、`Undo`、`NullUndo`、規則判定、評価関数、探索、学習データ、拡張SFEN、プロトコル層を新表現へ移行する案は、生成器が使わないエンジンの経路を広く変更し、麒麟成りフラグの廃止に伴うZobristキーと学習データ形式の扱いまで決めなければならないため棄却した。
`Rules`全体を受け取る案は、生成器が使わない反復規則と終局規則を保持することになり、`MoveGenerator::new`が`MoveRules`を取る現行の型とも合わないため棄却した。
記録升の不成獅子を既存の構築経路で拒否する案は、拡張SFENが非手番側の不成獅子を明示的に受理する現行契約と衝突するため棄却し、条件を生成器側の必要条件に限定した。

## 直前局面の定義

規則集合を`R`、対象局面を`q`、`R`の下で`p`から生成される局面合法手集合を`Moves_R(p)`、着手適用後の局面を`Next_R(p, m)`とする。
本機能が返す集合を次のように定義する。

\[
\operatorname{Pred}_R(q)
=
\{p\in A\mid
\exists m\in\operatorname{Moves}_R(p),\
\operatorname{Next}_R(p,m)=q
\}.
\]

集合`A`は、`Position::validate()`を満たし、2種類のZobrist値（盤面、手番、先獅子状態から計算する通常Zobrist値と、成り権保留集合から計算する成り権保留Zobrist値。「Positionのハッシュ」節を参照）が再計算値と一致し、各所有者の由来別駒数が初期在庫を超えず、採用規則と一時状態が次の局所条件を満たす`Position`の集合とする。
条件は3群に分かれ、それぞれ役割が異なる。
`validate()`とZobrist値の一致は、公開の構築経路で作れる整合した`Position`だけを対象にするための条件である。
由来別駒数の在庫は、直前手で取られた駒として復元できる駒を有限に絞るための条件であり、これがないと任意の駒を捕獲駒として復元できてしまう（「駒在庫」節）。
一時状態の局所条件は、対象局面から決まらない一時状態の列挙を有限かつ小さく保つための条件であり、以下の条件はすべて、`p`に至る着手（`p → q`の着手ではなく、その1手前の着手）が現行の着手適用で生み出し得る一時状態を、局面単体で見分けるための必要条件である。

成り権保留集合の局所条件は次のとおりである。

- 各ビットの升には、所有者から見た敵陣内に、その所有者の成れる不成駒がある。
- P0を採用しP5を採用しない規則では、成り権保留集合が空である。
- P0とP5を採用する規則では、ビットは歩兵の升にだけある。
- P2を採用する規則では、各対局者について、P5の歩兵を除くビットが高々1個である。

先獅子の記録升の局所条件は次のとおりである。

- 記録升があるなら、その升は空であるか、`p.side_to_move().opposite()`の非獅子駒または麒麟由来の成獅子で占められている。
- 記録升があるなら、`p.side_to_move()`の獅子由来または麒麟由来の駒が、由来別在庫から1枚以上欠けている。
- 記録升が空升なら、`p.side_to_move().opposite()`の角鷹または飛鷲が盤上にある。

成り権保留集合の第1条件は現行の`validate()`が検査する条件と同じであり、第2条件と第3条件は着手適用がその規則の下で立てるビットの範囲から従う。
P2の高々1個の条件は、待機の成立過程から従う。
P2の待機は、敵陣へ入る着手で不成を選んだ駒にだけ付き、その側の次の着手の完了時に、着手前から存在した待機ビットは動かなかった駒の分も含めてすべて満了し、その着手による待機ビットだけが新設され得る（`Position::make_move_with_captures_unchecked`）。
P5の歩兵の保留ビットは恒久状態であり、この満了の対象外である。
したがって、ある対局者の待機ビットは直前の自手番で動かした1駒にしか付かない。
この条件がないと、P2の逆生成は着手側の適格な駒の部分集合を列挙して候補数が指数的に膨張する。

記録升の第1条件は、記録升に残る駒が獅子を取った直前着手側の駒であることから従う。
後2条件は、先獅子状態の成立過程から従う必要条件である。
先獅子状態は、`p`に至る着手で`p.side_to_move()`の獅子が非獅子に取られた場合にしか生じないため、手番側の獅子になり得る駒が在庫どおり盤上に揃っている局面では記録升を許さない。
また、記録升が空になるのは経由升での捕獲に限られ、非獅子で経由升の捕獲を行える駒は角鷹と飛鷲だけである。
この2条件がないと、空升を指す記録升の変種が候補ごとに数十通り生成され、順方向再適用では除外できないまま、歴史的に到達不能な局面として出力を膨張させる。

これらは局面単体で判定できる必要条件だけであり、その一時状態を生じさせた直前着手の存在までは要求しない。
候補着手の順方向再適用は、候補`p`から対象局面`q`への遷移と矛盾する組合せだけを除外する。
`p`より前の履歴における一時状態の到達可能性は、本機能では判定しない。
局面の一致は盤面、手番および一時状態について判定し、Zobrist値は一致を高速化する派生データとして扱う。

同じ`p`から異なる着手で`q`へ到達できても、`p`は1回だけ返す。
中将棋では、異なる獅子力の駒による「じっと」が同じ結果局面へ至る場合があるため、着手ではなく局面を一意性の単位とする。

初期在庫制約と一時状態の局所条件は到達可能性の必要条件にすぎない。
本機能が主張する完全性は、集合`A`の要素のうち`q`へ1手で遷移できるものを漏らさないという、集合`A`に対する相対的な完全性である。
「相対的」と呼ぶのは、`A`の外にある局面（初期局面から到達できないが構築はできる局面）については何も主張しないからである。
返された`p`が初期局面から実際に到達可能かどうかは本機能では分からず、初期局面まで逆にたどれるかを調べる後続の逆方向探索が判定する。

## Positionの公開面

盤面と手番だけから導出できず、過去の着手に由来して、後続の合法手または局面同一性の判定に影響する局面付随状態を**一時状態**と定義する。
現行の`Position`は、先獅子状態を内部型`LionTrigger`（記録升と麒麟成りフラグ）で、成り権保留状態を`Bitboard`で保持し、いずれもクレート内にだけ公開している。
本マイルストーンは内部表現を変えず、次の2つの公開アクセサを追加する。

```rust
impl Position {
    /// 直前の着手で獅子以外の駒が相手獅子を取った升を返す。
    pub fn lion_capture_square(&self) -> Option<Square>;
    /// 成り権を保留中(P1・P2・P5)の駒がある升の集合を返す。
    pub fn promotion_deferred(&self) -> Bitboard;
}
```

`lion_capture_square`は`LionTrigger`の記録升だけを返し、麒麟成りフラグは公開しない。
フラグは記録升に直前着手側の麒麟由来の成獅子がいるかどうかと同値であり、外部プログラムは盤面から導出できるからである。
この同値性は、着手適用で生じた局面では次の論証により成り立ち、構築経路で作った局面では`set_lion_capture`自身が同じ盤面条件からフラグを設定することにより成り立つ。
着手適用時の判定（動かした駒が麒麟であり、その着手で成った）と盤面からの導出が同値である理由は次のとおりである。
先獅子状態は非獅子が獅子を取った着手でだけ立ち、記録升に残る駒はその非獅子駒である。
不成の獅子は成りで生じないため記録升に現れず、成獅子は麒麟の成りでしか生じない。
成りは着手の終了時に起こるので、記録升に成獅子が残るのは、麒麟が獅子を取り同じ着手で成った場合に限られる。
角鷹または飛鷲が経由升で獅子を取った場合は記録升が空になり、成獅子ではない。
`promotion_deferred`は現行の`pub(crate)`アクセサを公開に改めるだけである。

一時状態を持つ局面の構築には、既存の公開経路をそのまま使う。
呼び出し順は、`PositionBuilder::new`で手番を決め、`put`で駒を置き、`mark_promotion_deferred`で成り権保留集合を設定し、`finish()`で`Position`を得てから、`set_lion_capture`で先獅子状態を設定する。
`set_lion_capture`は記録升に手番側の駒がある入力を拒否し、記録升の駒から麒麟成りフラグを導出し、Zobrist値を増分更新する。
各関数の契約は`src/core/position.rs`のrustdocと[protocol-layer.md](protocol-layer.md)「局面設定」が定めており、本書では変更しない。
記録升に不成の獅子がいる状態は、現行の拡張SFENが受理し、テストでも受理を固定しているため、既存の構築経路では拒否しない。
その状態を除外するのは「直前局面の定義」節の集合`A`の条件であり、生成器だけが課す。
規則に依存する条件のうち、P0かつP5なしでの空集合は現行の拡張SFENの解析が既に検査しており、そのまま維持する。
P0とP5での歩兵限定とP2での高々1個は現行の解析が検査しておらず、拡張SFENの受理範囲を変えないため、生成器だけが課す。

`Position::validate()`は、現行の盤面とビットボードの整合検査に加えて、通常Zobrist値と成り権保留Zobrist値が再計算値に一致することを検査し、不一致には専用の`PositionError`を返す。
`PositionBuilder`の`put`と`mark_promotion_deferred`は既に2種類のZobrist値を増分更新しているため、`finish()`が検証してから再計算する現行の順序は変えない。
検証が一致を保証した後の再計算は不要になるので削除し、増分更新の不具合を再計算で覆い隠さず検証で検出する。
公開の構築経路と`try_make_move`はいずれもZobrist値を整合した状態で更新するため、既存の利用箇所でこの検査が失敗することはない。

反復判定は現行どおり、R1が通常Zobrist値と成り権保留Zobrist値の組、R2とR3が通常Zobrist値だけをキーに使い、完全な`Position`では照合しない。
`Game`の探索キー履歴と探索も、両値の排他的論理和を使う現行の合成を維持する。
本マイルストーンで導入する`Position::Hash`と`HashSet<Position>`は生成器と外部プログラム向けの契約であり、反復判定と探索キーの契約へは波及させない。

## Positionのハッシュ

外部のRustプログラムと生成器内部で`HashSet<Position>`を使えるよう、`Position`へ`Hash`を実装する。
実装は通常Zobrist値と成り権保留Zobrist値を`Hasher`へ渡し、衝突時の同一性判定を既存の`Eq`へ委ねる。

既存の`Eq`は導出実装であり、盤面、占有集合、手番、一時状態に加えて、派生キャッシュである2種類のZobrist値も比較へ含む。
この比較が盤面、手番および一時状態による一致判定と同値であることは、`Position::validate()`のZobrist一致検査と、Zobrist値を整合して更新する構築経路だけが公開されていることによって保証する。

通常Zobrist値は盤面、手番、先獅子状態から、成り権保留Zobrist値は成り権保留集合から計算する派生値であり、反復規則R1が両者の組を、R2とR3が通常値だけを同一局面のキーに使うため2つに分かれている。
ハッシュ値は永続識別子、交換形式または局面一致の代用として使用しない。

## 公開API

実装は`src/core/predecessor/`に置き、`src/core/mod.rs`と`src/lib.rs`から公開する。
公開面は次の形とする。

```rust
#[derive(Clone)]
pub struct PredecessorGenerator {
    forward: MoveGenerator,
}

impl PredecessorGenerator {
    pub fn standard() -> Self;
    pub fn new(rules: MoveRules) -> Self;

    pub fn generate_predecessors(
        &self,
        target: &Position,
    ) -> Result<Vec<Position>, PredecessorError>;
}
```

`standard()`は`MoveRules::standard()`（L0とP0）を明示的に選ぶ便宜コンストラクタとする。
`new`へ渡された`MoveRules`はそのまま`MoveGenerator::new`へ渡して保持し、規則の欠落や矛盾を別の規則へ置換しない。
規則コード列から規則集合を作る際の重複、矛盾、各群の欠落の検査は`Rules::from_codes`の責務であり、生成器は型付きの`MoveRules`だけを受け取る。
外部プログラムは`Rules::from_codes`または`Rules::ENGINE_DEFAULT`などの定数から`Rules`を作り、その`moves`を渡す。

`generate_predecessors`は重複のない局面を返すが、順序は保証しない。
生成器は規則と既存の`MoveGenerator`だけを保持し、作業領域やキャッシュを呼び出し間で共有しない。
`MoveGenerator`は`'static`な利き表への参照と`Copy`型の`MoveRules`だけを持つため、生成器は自動的に`Send + Sync`になり、外部プログラムは1つの生成器を複数スレッドで共有できる。
この性質は公開契約とし、コンパイル時の静的表明で固定する。

外部プログラムが対象局面を文字列で与え、直前局面を文字列で受け取る経路には、公開済みの拡張SFENを使う。
`notation::sfen::parse_extended_sfen`は5欄の文字列と`MoveRules`から`SetupPosition`を作り、`into_parts`で`Position`、先獅子の記録升、および次の手数を取り出せる。
記録升の`Position`への反映は、プロトコル層と同じく`set_lion_capture`で行う。
書き出しは`SetupPosition::new`で`Position`、記録升、および1以上9999以下の手数を包み、`to_extended_sfen`で5欄の文字列にする。
手数は生成器の対象外であり、外部プログラムが表記のために指定する。
解析と書き出しには生成器へ渡したものと同じ`MoveRules`を使う。
本マイルストーンはこれらの関数を変更しない。

エラー型は少なくとも次の原因を区別する。

```rust
#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum PredecessorError {
    InvalidPosition(PositionError),
    MaterialExceedsInitial {
        color: Color,
        origin: PieceKind,
        found: u8,
        maximum: u8,
    },
    RuleStateMismatch,
    InvalidLionState,
}
```

対象局面`q`にも集合`A`の全条件を課し、違反は条件の群ごとに次のエラーへ写す。
`Position::validate()`が拒否する盤面とZobrist値の不一致は`InvalidPosition`とする。
由来別在庫の超過は`MaterialExceedsInitial`とする。
局面単体は構築できても採用規則から生じない成り権保留集合には`RuleStateMismatch`を返す。
該当するのは、P0を採用しP5を採用しない規則で成り権保留集合が非空である場合、P0とP5を採用する規則で歩兵以外の升にビットがある場合、およびP2を採用する規則でいずれかの対局者にP5の歩兵以外のビットが2個以上ある場合である。
先獅子の記録升の3条件（記録升の駒、手番側の獅子在庫、空升に対する角鷹または飛鷲の存在）に反する局面には`InvalidLionState`を返す。
既存の構築経路と拡張SFENはこれらの局面を受理するため、生成器の入力検査だけがこの区別を行う。
正常な局面に直前局面がない場合だけ`Ok(Vec::new())`を返す。

## 駒在庫

中将棋では各対局者が46枚の駒を持って開始し、取られた駒は盤上から除かれて再使用されない。
したがって、直前手で取られた駒は、対象局面で初期在庫から欠けている駒に限られる。

在庫は現在の`PieceKind`ではなく、**由来**、すなわちその駒が初期配置にあったときの駒種ごとに数える。
不成駒の由来はその駒種自身であり、成駒の由来は`PieceKind::unpromoted()`が返す成る前の駒種である。
たとえば不成の金将の由来は金将、成った金将（歩兵の成駒）の由来は歩兵、不成の獅子の由来は獅子、成獅子の由来は麒麟である。
これにより、初期配置の金将と歩兵が成った金将、初期配置の獅子と麒麟が成った獅子を別在庫として扱う。
由来別在庫の上限は、初期配置にその由来の駒が各対局者に何枚あるかで決まる。

製品コードの初期在庫は`Position::initial()`から導出し、同じ配置表を別の定数として複製しない。
テストではRULES.md第4条と第5条から独立に書いた期待数と照合し、初期配置と在庫計算が同じ誤りを共有しても検出できるようにする。

対象局面が初期在庫を超える場合は`MaterialExceedsInitial`を返す。
捕獲駒を復元するたびに残数を減らし、2枚捕獲で同じ由来を2回使う場合も上限を超えないようにする。

## 逆向き候補の構成

生成の流れは次の順である。
まず対象局面`q`が集合`A`の全条件を満たすことを検査し、違反は「公開API」節のエラーで返す。
次に、動いた駒、移動元、捕獲駒、成り、一時状態の順に候補`p`を構成する。
一時状態まで構成した候補が`A`の条件に反する場合は、エラーにせず黙って捨てる。
残った候補に候補着手を順方向に再適用し、`q`と一致したものを重複排除して返す。
エラーになるのは入力`q`の違反だけであり、候補`p`の違反は除外の理由にしかならない。

対象局面の手番と反対側を直前の着手者とする。
対象局面にある直前着手者の各駒を、直前手で動いた駒として順に仮定する。

到達駒が不成駒なら、移動前も同じ不成駒であり、`promote`は`false`である。
到達駒が成駒なら、既に成っていた駒が`promote: false`で動いた場合と、対応する不成駒が`promote: true`で動いた場合を列挙する。

移動元候補は既存の移動プロファイルと利き表から`Bitboard`として構成する。
使う関数は`step_square`が公開、それ以外が`pub(crate)`であり、生成器は`core`配下に置くためいずれも参照できる。

- 固定移動と固定跳びは、`movement_profile(kind)`で得た識別子から`movement_profile_data`の`fixed_deltas`を引き、`RelativeDelta::for_color`で色に応じた変位に直してから反転し、到達升から移動元を求める。
- 走りは、`slides`の各方向を`for_color`で絶対方向にして反転し、`AttackTables::sliding_control(to, direction.opposite(), Bitboard::EMPTY)`で空の占有集合に対する利き線を求める。
- 獅子の1升移動と直接跳びは対称なので、到達升に対する`king_steps`と`lion_jumps`を使う。
- 角鷹と飛鷲は、`SpecialMovement::LionLike`の許可方向を反転し、`step_square`で1升前と2升前を求める。

既存の`Position::attackers_to_by`は盤上に実在する駒と占有集合で結果を絞るため、空の移動元を含む逆生成の代替にはならない。

走りでは、対象局面の占有状態を使って経路を打ち切らない。
対象局面の占有状態は直前局面の占有状態と異なり、動いた駒は移動元になく、取られた駒は盤上にないため、対象局面で打ち切ると遮蔽の判定を誤るからである。
対象局面から消えている捕獲駒を復元した後の遮蔽物判定は、候補盤面に対する順方向検証へ委ねる。

獅子力のある駒では、1段階移動、直接跳び、じっと、居喰いおよび2段階移動を区別する。
`mid: Some(square)`は経由升で必ず捕獲する正準表現とし、空の経由升を持つ別表現は生成しない。
現行の生成器も、経由升に相手駒がある場合にだけ`mid: Some`を生成する。

各候補は`PositionBuilder`で盤面全体を再構築し、`mark_promotion_deferred`で成り権保留集合を、`finish()`後に`set_lion_capture`で先獅子状態を設定する。
局所的な生変更APIや逆向き差分適用は、性能測定節の第3候補が計測で正当化されるまで追加しない。

## 捕獲駒の復元

通常移動、走り、固定跳びおよび直接跳びでは、到達升が空だった場合と、相手駒を捕獲した場合を列挙する。
2段階移動と居喰いでは、経由升へ相手駒を必ず復元する。
2段階移動の到達升では、非捕獲と捕獲を列挙するため、最大2枚を復元する。
じっとでは捕獲駒を復元せず、居喰いと移動元へ戻る2段階移動では経由升だけへ復元する。
到達升への復元は`to != from`の場合に限る。

復元候補は相手側の不足在庫から選ぶ。
成れる由来駒については、捕獲時に不成だった場合と成っていた場合を双方列挙する。
本将棋の持駒のような所有者変更や駒打ちは導入しない。

## 一時状態の逆生成

直前局面の先獅子状態は、`p → q`の着手適用で`q`の値に書き換わるため、対象局面から一意に決まらない。
記録升なしと全144升を上限とする合計145状態から、集合`A`で定義した局所条件に反する値だけを除き、残りを列挙する。
候補`p`の手番側の獅子由来と麒麟由来の駒が両方とも盤上にある場合は、獅子在庫の局所条件により記録升ありの全状態が除かれ、記録升なしだけが残る。
記録升が空の場合は経由升で獅子を取った場合として扱い、候補`p`の`side_to_move().opposite()`の非獅子駒がある場合は到達升で取った場合として扱う。
同じ所有者の麒麟由来の成獅子がある場合だけ、L2の麒麟成り例外を適用できる状態として扱う。
この所有者は`p → q`の着手者ではなく、`p`の一時状態を生じさせたさらに1手前の着手者である。
記録された捕獲の実在は推測せず、局所条件を通った各値を候補着手の順方向再適用へ渡す。
再適用は`p → q`との整合だけを検査し、記録された捕獲の存在を証明しない。
不明値を表す列挙子や記録升なしへの正規化は導入しない。

成り権保留集合は、対象局面の集合から、移動元、到達升および実際の捕獲升（その候補着手で捕獲駒を復元した升）のビットを最初にすべて除外して構成する。
着手に影響されない升だけを対象局面から引き継ぎ、移動元の駒と実際の捕獲升に復元した適格駒について、直前の保留ありと保留なしを独立に列挙する。
この独立列挙はP1とP5に対するものであり、P2の着手側については後述の全体列挙がこれを置き換える。
対象局面の到達升にあるビットは直前手で新設された可能性があるため、そのまま直前局面へコピーしない。
到達升が移動元または捕獲升でもある場合は、その升に直前局面で置く駒について列挙した値だけを使う。
したがって、じっとと居喰いの`from == to`でも対象局面の値を引き継がず、影響升を1個の`Bitboard`へまとめて重複処理を避ける。

P2を採用する規則では、着手側（`q.side_to_move().opposite()`）の着手前から存在した待機ビットが着手完了時にすべて満了するため、着手に関係しない着手側の駒にも直前局面で待機ビットがあり得る。
その待機ビットは`p`に至る着手（`p → q`の1手前の着手側の着手）で敵陣へ入った駒に付いたものであり、どの駒がそれかは`q`から分からず、順方向再適用もすべて満了させるため区別できない。
そこで、候補`p`における着手側の駒のうち適格なもの、すなわち移動元に置く駒を含めて敵陣内にある成れる不成駒からP5の歩兵を除いた`k`駒を求め、待機ビットなしの1通りと、`k`駒のうちちょうど1駒に待機ビットを付けた`k`通りの、合計`k + 1`通りを列挙する。
2駒以上に付ける組合せは集合`A`の高々1個の条件に反するため列挙しない。
復元した捕獲駒は相手側（`q.side_to_move()`）の駒であり、その待機ビットは前段の独立列挙で扱うが、相手側についても高々1個の条件が候補の検査で働く。
P5の歩兵の保留ビットは恒久状態であり、P2の満了で消えないため、P1と同じく移動元と捕獲升以外は対象局面から引き継ぐ。

一時状態まで構築した各候補は、順方向再適用の前に集合`A`の全条件を検査し、違反する候補を捨てる。
順方向再適用は候補着手で消えるビットを検査できないため、たとえばP2で復元した2枚の捕獲駒の両方に待機ビットを付けた候補は、再適用と対象局面との一致だけでは除外できない。

## 順方向検証

逆向きに構成した候補は、その時点では合法手とみなさない。
集合`A`への所属を検査して通った候補局面の複製へ、同じ規則の`MoveGenerator`を渡した`try_make_move`で候補着手を適用する。

```rust
let mut replayed = candidate.clone();
if replayed.try_make_move(mv, &self.forward).is_ok() && replayed == *target {
    // candidateを採用する
}
```

この1回の順方向検証により、移動、遮蔽物、捕獲、成り、先獅子および成り権保留状態を既存実装だけで判定する。
逆生成側には同じ合法性判定を複製しない。

採用局面は`HashSet<Position>`で既出判定し、初出時だけ返却用`Vec`へ追加する。
ハッシュ衝突時には`Eq`が完全な局面を比較するため、異なる局面を失わない。

## ローカルルール

L0からL4までとP0からP6までは、候補局面または候補着手の順方向合法性を変え得るため、最初の完成時点からすべて対応する。
L4は先獅子の禁止対象を非獅子の駒による捕獲に限定し、P5は歩兵の恒久保留と最奥段での強制成りを、P6は前進専用駒の最奥段での強制成りを変える。
標準規則専用の部分実装を完成扱いにしない。

R1からR3までとE0からE3までは、`Position`単位の順方向合法手を変えないため、生成器は受け取らず、対局履歴や終局裁定へ展開しない。
利用側がE3を含む`Rules`で対局を管理していても、生成器へ渡すのは`rules.moves`だけである。

## 完全性の根拠

順方向再適用は、生成した候補が正しいことを示す健全性検査であり、候補の漏れがないことまでは示さない。
相対的完全性は、次の3層で検証する。

第1層では、全順方向移動形式と逆構成の対応表を本書の「移動形式と逆構成の対応」節に置き、実装時に完成させる。
全144升の完全性をテスト件数だけから主張せず、各移動形式、捕獲数、成りおよび一時状態に対応する逆構成が存在することを場合分けして説明する。

第2層では、固定局面とシード固定局面の全合法手を順方向に適用する。
各辺`p → q`について、`generate_predecessors(q)`が`p`を含むことを確認する。

第3層では、テスト専用の有限状態オラクルを作る。
オラクルは、盤の一部の升集合（たとえば片隅の4×4升）、少数の駒集合（王駒2枚と検証したい駒種を数枚）、両手番、およびその規則で取り得る一時状態の値を固定し、それらの配置をすべて列挙して有限の局面集合`S`を作る。
`S`の各局面に既存の順方向生成器で全合法手を適用し、後続局面ごとに「その局面へ至った`S`の局面の集合」を表として記録する。
これがオラクルの直前局面表であり、`S`内で完全である。
`S`の各局面`q`について製品の`generate_predecessors(q)`を呼び、返された局面のうち`S`に属するものの集合が、表の`q`の行と集合として等しいことを検査する。
オラクルは製品コードの逆経路、在庫枝刈りおよび捕獲復元関数を呼ばず、順方向生成器だけに依存する。
`S`は列挙した局面のうち集合`A`の条件を満たすものに限り、その判定はRULES.mdと本書の条件文からテスト側で独立に書き、製品の入力検査関数を呼ばない。

### 移動形式と逆構成の対応

実装時に、次の行を持つ表を本節へ書く。
各行は、順方向の移動形式、捕獲数、成りの有無、一時状態の扱い、対応する逆構成の関数、および根拠となる固定テストの分類を示す。

- 固定移動と固定跳び（非捕獲、到達升捕獲）。
- 走り（距離1、距離2以上、遮蔽あり、捕獲）。
- 獅子の1段階移動、直接跳び、じっと、居喰い、2段階移動（経由升捕獲、2枚捕獲）。
- 角鷹と飛鷲の向き付き1段階移動、直接跳び、じっと、居喰い、2段階捕獲。
- 不成、直前手での成り、既成駒の移動。
- 先獅子状態の新設、消滅、L2例外。
- 成り権保留状態のP1、P2（待機の新設と満了）、P5。

## 逆方向探索への接続条件

本機能だけでは、論文と同じ意味で到達不能を証明できない。
後続の逆方向探索マイルストーンでは、目標集合、探索終了条件、経路保存および`Game`履歴の扱いを別途確定する。

探索を途中で打ち切る場合は、不明と到達不能を別の結果型にする。
open集合が空になるまで探索した場合だけ、生成器の相対的完全性を前提として到達不能を返せる。

本将棋の論文が用いる玉2枚だけの目標集合は、中将棋ではそのまま使わない。
中将棋には持駒と駒打ちがなく、捕獲で減った駒を再び盤上へ増やせないためである。

## 実装フェーズ

フェーズ2からフェーズ4までは、各フェーズで扱う移動形式について健全性（返した局面がすべて`A`に属し、再適用で`q`に一致する）と「検証」節の固定テストを確保し、完全性は各フェーズの範囲内で第2層（逆包含）の固定局面テストにより確認する。
第3層の有限状態オラクルと全順方向辺の逆包含テストは、全移動形式がそろうフェーズ5でまとめて行う。
「性能測定」節の「全機能版」とは、フェーズ4を完了した時点の実装をいう。

### フェーズ1　`Position`の公開面の追加

`lion_capture_square()`、公開の`promotion_deferred()`、`Position::Hash`、およびZobrist一致を検査する`Position::validate()`を実装し、`PositionBuilder::finish()`の検証後の再計算を削除する。
内部表現、既存の構築経路、Zobristキー、評価関数、探索、プロトコル層、および学習データには触れない。

完了条件は、全既存テストとperftに挙動変更がなく、全局面のZobrist値が変更前と一致し、`Hash`の契約（`Eq`で等しい局面は同じハッシュ値を持ち、衝突しても`HashSet`が異なる局面を保持する）がテストで固定されていることである。
探索、評価およびZobrist値のいずれも変えないため、棋力測定は行わない。

### フェーズ2　公開API、入力検査および在庫

`PredecessorGenerator`、`PredecessorError`、由来別在庫計算および衝突安全な重複排除を実装する。
不正局面、規則状態の矛盾、在庫超過、正常な空集合および`Send + Sync`の静的表明をテストする。

### フェーズ3　通常移動、捕獲および成り

固定移動、走り、固定跳びの移動元候補を`Bitboard`として構成する。
0枚または1枚の捕獲駒、既成駒の移動および直前手での成りを復元し、全候補を順方向に検証する。

### フェーズ4　獅子力と一時状態

獅子、角鷹および飛鷲の1段階移動、直接跳び、じっと、居喰いおよび2段階移動を実装する。
最大2枚の捕獲復元、先獅子状態の最大145状態、成り権保留状態のP1、P2、P5、および結果に影響する全ローカルルールを扱う。

### フェーズ5　完全性検証と計測

全順方向辺の逆包含テスト、有限状態オラクル、移動形式との対応表および公開APIによる深さ2の結合テストを追加する。
固定コーパスをreleaseビルドで測定し、結果を測定記録`docs/measurements/predecessor-generator-profile.md`へ置いて本書からリンクする。

## 検証

### 固定テスト

固定テストは、次の分類をすべて含める。

| 分類 | 必須事例 |
|---|---|
| 通常移動 | 非捕獲、到達升捕獲、盤端および両所有者を扱う。 |
| 走り | 距離1、距離2以上、味方遮蔽、相手遮蔽および捕獲を扱う。 |
| 固定跳び | 中間升が空、味方駒、相手駒の場合と到達升捕獲を扱う。 |
| 獅子の1段階移動 | 非捕獲と捕獲を扱う。 |
| 獅子の直接跳び | 非捕獲と到達升捕獲を扱う。 |
| じっと | 異なる駒のじっとが同じ結果局面へ至る場合も1局面だけ返す。 |
| 居喰い | `from == to`、`mid == Some`および1枚捕獲を扱う。 |
| 2段階移動 | 経由升だけの捕獲と、経由升および到達升の2枚捕獲を扱う。 |
| 角鷹と飛鷲 | 両所有者について、向き付き1段階移動、直接跳び、じっと、居喰いおよび2段階捕獲を扱う。 |
| 成り | 不成のみ、成りと不成の両候補、直前手での成り、既成駒の移動、二重成りの拒否、P6の最奥段での不成拒否を扱う。 |
| 先獅子 | 標準規則、L1、L2、L3およびL4で、以前の捕獲升と新しい捕獲升を扱う。手番側の獅子在庫が揃っていて記録升ありの状態が全滅する局面と、記録升が空の状態に必要な角鷹または飛鷲の有無も扱う。 |
| 成り権保留 | P1の移動駒、復元捕獲駒、到達升および無関係な駒の保留状態、P2の待機の新設と非移動駒の満了、P5の歩兵の恒久保留と強制成り、P2とP5、P2とP6の併用を扱う。 |
| 在庫 | 不成と成駒の由来、同一由来2枚の復元、在庫充足および在庫超過を扱う。 |

各出力について、直前局面が集合`A`の全条件を満たし、手番が対象局面と反対であり、順方向再適用結果が対象局面と完全一致することを検査する。
入力した対象局面は変更されず、返却局面に重複がなく、4種類のエラーと正常な空集合が区別されることも確認する。

`tests/`には公開APIだけを使う深さ2の逆方向探索を置く。
初期局面から2手進めた対象局面を逆方向へ2手たどり、`HashSet<Position>`を使って初期局面を発見する。
対象局面の入力と直前局面の出力には拡張SFENを使い、外部プログラムと同じ経路で往復できることを確認する。
先獅子状態ありと成り権保留ありの局面についても、公開APIだけで拡張SFENへ書き出して解析し直し、`Position`が完全一致することを確認する。
製品用の探索器は追加しない。

### 性能測定

全機能版の正しさを確立した後、releaseビルドで固定コーパスを測定する。
コーパスには、初期局面付近、1枚捕獲後、2枚捕獲後、成り直後、先獅子状態あり、P1状態あり、P2の待機あり、P5の保留歩兵あり、および駒が少ない局面を含める。

各局面について、候補構成数、`try_make_move`回数、採用局面数、候補対採用比、経過時間の中央値および95パーセンタイルを測定記録に残す。
初回マイルストーンには根拠のない速度閾値を置かない。

性能改善を行う場合は、同じ環境と固定コーパスで変更前後を比較する。
プロファイルで支配的、すなわち自己時間の割合が最大であると確認されていない処理は最適化しない。

現時点で判明している変更候補を3つ記録する。
いずれもフェーズ5の計測で支配的と確認された場合に限り、本マイルストーン内で導入する。
第1に、現行の`try_make_move`は内部で全合法手を生成してから照合するため、検証コストは候補数と全手生成の積になる。
クレート内には移動元の駒の合法手だけを生成して照合する`MoveGenerator::is_legal_move`が既にあり、置き換え候補になる。
第2に、対象局面に先獅子の記録升がある場合、直前手はその記録升で非獅子が獅子を取る着手に限られるため、候補構成段階の枝刈りに使える。
第3に、返却局面の構築と保持が支配的である場合は、`for_each_predecessor(&self, q, f: impl FnMut(&Position))`の形のビジターAPIへ置き換える。
呼び出しごとのローカル変数として作業用`Position`を1つ持ち、候補ごとに逆差分の適用、順方向検証および巻き戻しを行い、採用局面だけを参照として閉包へ貸し出す。
作業局面を生成器のフィールドにはせず、呼び出し間で状態を共有しない契約と`Send + Sync`を維持する。
`PositionBuilder`による盤面全体の再構築と所有権付き`Vec<Position>`の返却を廃止し、利用側は貸し出された参照から必要な形式だけを自分で複製する。
標準の`Iterator`は自身のバッファへの参照を要素にできないため、外部イテレータではなく内部イテレーションを採用する。
導入する場合は`generate_predecessors`をこのAPIで置き換えて両方式を併存させず、本書の「公開API」節、エラーの返却形式、結合テストおよび完了条件を改訂する。
一意性保証のための既出判定集合は生成器内部に残るため、この変更で削れるのは返却用と利用側の保持分に限られる。
いずれも計測で支配的と確認されるまで導入しない。

### 検証コマンド

各フェーズで対象モジュールのテストを実行し、最終確認では次のコマンドを実行する。

```console
cargo fmt --all -- --check
cargo clippy --all-targets
cargo test
git diff --check
cargo run --release --quiet --bin perft -- 4
cargo test --release predecessor_profile -- --ignored --nocapture
```

perftの深さ1から4までが`36`、`1,296`、`48,315`、`1,801,639`のままであることを確認する。
最後のコマンドはフェーズ5で追加する計測テストであり、性能の合否判定ではなく、固定コーパスの基準値を測定記録へ残すために使う。

## 完了条件

次の条件をすべて満たした時点で、本マイルストーンを完了とする。

- `Position`が先獅子の記録升と成り権保留集合を公開アクセサで返し、内部表現、既存の構築経路、Zobristキー、評価関数、探索、プロトコル層および学習データ形式が変わっていない。
- `Position::Hash`が`Eq`と整合し、衝突時にも異なる局面を保持する。反復判定と探索キーの契約は変わっていない。
- `Position::validate()`が2種類のZobrist値の一致を検査する。
- 公開APIが本書の定義どおり`Pred_R(q)`を重複なく列挙し、生成器が`Send + Sync`である。
- 不正局面、在庫超過、規則状態の矛盾および先獅子状態の矛盾が型付きエラーになり、正常な空集合と区別される。
- 通常移動、走り、固定跳び、獅子、角鷹、飛鷲、非捕獲、1枚捕獲、2枚捕獲および成りの固定テストが成功する。
- L0からL4まで、P0からP6までの`Position`遷移に関係する全分岐が検証されている。
- 全順方向辺の逆包含テストと有限状態オラクルとの集合一致が成立する。
- 公開APIによる深さ2の逆方向探索が、拡張SFENで与えた対象局面から初期局面を発見する。
- 固定コーパスの測定条件、候補数、採用数、中央値および95パーセンタイルが測定記録にあり、本書からリンクされている。
- 順方向の合法手生成、対局裁定、拡張SFENの受理範囲、静的評価値、全局面のZobrist値、`bench`のノード数と最善手、および既存perft値に挙動変更がない。
- 検証コマンドがすべて成功する。

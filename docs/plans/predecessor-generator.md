# 直前局面生成器の設計書

## 先に読む要約

本マイルストーンでは、規則集合と対象局面を受け取り、その局面へ1手で到達できる直前局面をすべて列挙する`PredecessorGenerator`を、ライブラリの公開APIとして実装する。
直前局面とは、1つの合法手を指すことで対象局面へと遷移する局面を指す。これは、目標局面から手を逆にたどる逆方向探索において基本となる操作である。
本生成器は思考エンジンの探索からは呼び出されず、minaseを依存ライブラリとして利用する外部のRustプログラムのみが使用する。
処理方式としては、着手を逆向きに構成した候補局面を上位集合としてまず生成する。その上で、既存の順方向合法手生成器を用いて候補着手を再適用し、対象局面と一致するものだけを抽出して残す。
合法性の判定については既存の生成器のみを正とし、逆生成側に規則の判定処理を重複して持たせない。
候補の構成にあたっては、駒の動きの幾何を反転させた移動元の集合、初期配置に基づいて算出した復元可能な捕獲駒の在庫、および盤面情報だけからは定まらない一時状態の列挙を用いる。
一時状態とは、先獅子状態（非獅子が獅子を取った直後の1手のみ取り返しを制限する状態、RULES.md第15条）と、成り権保留状態（敵陣で成らなかった駒が後で成る権利を追跡する状態で、成り規則P1、P2、P5で使用する、RULES.md第30条）の2点である。
事前準備として、`Position`に一時状態を取得する公開アクセサと`Hash`を実装し、`validate()`にZobrist値の一致検査を追加する。ただし、`Position`の内部表現、構築経路、およびエンジンの探索経路は変更しない。
本マイルストーンの完了条件は、全移動形式の固定テスト、全順方向辺の逆包含テスト、有限状態オラクルとの集合一致、公開APIを用いた深さ2の逆方向探索、ならびに固定コーパスの計測記録が整い、かつ順方向の合法手生成、対局裁定、拡張SFEN、Zobrist値、perft値に挙動変更がないことである。

## 状態

完了である。2026年8月10日に起案し、2026年9月18日にブランチpredecessor-generatorで着手して同日に完了した。全フェーズの成果はブランチに残り、masterへの統合は利用者の判断を待つ。固定コーパスの計測は [measurements/predecessor-generator-profile.md](../measurements/predecessor-generator-profile.md) に記録した。計測の結論は、自己時間が最大の処理は存在せず、「性能測定」節の3つの改善案はいずれも採用しないというものである。直前局面の集合は、不足在庫が多い局面や着手側の獅子在庫が欠けた局面で数百万局面に達し、これは集合`A`に対する相対的完全性の定義どおりの結果である。

## 目的

本マイルストーンの目的は、規則集合と対象局面`Position`を受け取り、その対象局面へ1手の局面合法手で到達できる直前局面を漏れなく列挙する`PredecessorGenerator`を実装することである。
出力は、盤面、手番、一時状態を含む完全な`Position`の集合とする。同じ直前局面へと至る着手が複数存在する場合であっても、その局面は1回のみ返却する。

主な想定利用者は、minaseを依存ライブラリとして呼び出す独立したRustプログラムである。
本機能により、IshiiとTanakaが将棋の到達可能性判定で用いた逆方向探索と同型の探索を、中将棋の`Position`グラフ上でも構築できるようにする。
なお、本生成器は思考エンジンの探索からは呼び出されない。そのため、`Position`の内部表現、評価関数、探索、プロトコル層、および学習データ形式に影響を及ぼす変更は、本マイルストーンでは一切行わない。

## 適用範囲

本マイルストーンで実施する作業は次のとおりである。

- `Position`に、先獅子の記録升と成り権保留集合を取得する公開アクセサを追加する。
- `Position`に、既存の`Eq`と整合する衝突安全な`Hash`を実装する。
- `Position::validate()`に2種類のZobrist値の一致検査を追加する。
- すべての直前局面を列挙する公開型`PredecessorGenerator`を追加する。
- 初期配置の駒在庫を基準として、復元可能な捕獲駒を所有者別かつ由来別に制限する。
- 通常移動、走り、固定跳び、獅子、角鷹、飛鷲のすべての移動形式を逆向きに構成する。
- 非捕獲、1枚捕獲、2枚捕獲、既成駒の移動、および直前手での成りを処理対象とする。
- 対象局面から一意に決定できない直前局面の一時状態をすべて列挙する。
- すべての候補を既存の順方向合法手生成器で検証し、対象局面と完全に一致することを確認する。
- 健全性、相対的完全性、一意性、および性能を、再現可能な手順で検証する。

以下の項目は作業の対象外とする。

- `Position`の内部表現（`LionTrigger`、`promotion_deferred`、`Undo`、`NullUndo`）、Zobristキー、ならびに既存の構築経路である`PositionBuilder::mark_promotion_deferred`と`Position::set_lion_capture`は変更しない。
- 評価関数、探索、学習データ形式、拡張SFENの契約、プロトコル層、および`src/bin`配下のエンジンと補助バイナリは変更しない。
- `Game`全体、反復履歴、手数、駒枯れ猶予、および終局結果の逆生成は実施しない。
- 初期局面から各直前局面への大域的な到達可能性については判定しない。
- 集計、状態の縮約、状態数の算出、およびデータの永続化は行わない。
- 複数手にわたる逆方向探索、探索順序の制御、目標集合の管理、および到達不能の判定は実装しない。
- ファイル入出力、CLI、USI、CECP、ならびにGUIとの接続処理は行わない。
- 計測を実施する前に、専用の逆利き表、並列化、キャッシュ、または逆向き差分更新の仕組みを導入しない。

## 依存関係

本マイルストーンは、完了済みである[プロトコル層](protocol-layer.md)と[規則集合の代数的データ型化](rules-type.md)の成果を前提とする。
プロトコル層は、成り権保留集合を`PositionBuilder::mark_promotion_deferred`で、先獅子状態を`Position::set_lion_capture`で設定できる公開の構築経路を提供している。また、局面を文字列として受け渡す拡張SFEN（[protocol-layer.md](protocol-layer.md)が定める5欄の局面表記）も提供しており、生成器や外部プログラムはこれらをそのまま活用する。
規則集合は`Rules`と、その一部である着手規則`MoveRules`に分離されており、本生成器は後者のみを受け取る設計とする。

なお、順方向の探索部と評価関数は本マイルストーンの完了に依存しておらず、本マイルストーンがそれらの挙動を変更することもない。
作業にあたっては共通ポリシーに従い、着手時点のmasterから本設計書専用の作業ブランチを作成して進める。

## 設計判断

| 項目 | 決定 |
|---|---|
| 生成対象 | `Game`ではなく、次の局面合法手を決定する`Position`を対象とする。反復履歴や裁定状態は`Game`が個別に管理するためである。 |
| 出力単位 | 一時状態を含む完全な直前`Position`とする。着手情報は内部検証のみに利用する。 |
| 一意性 | 同一の`Position`は1回のみ返却し、返却順序は公開契約に含めない。 |
| 合法性の正 | 既存の`MoveGenerator`を唯一の正とし、逆生成側には合法手判定処理を重複して実装しない。 |
| 規則の受け取り | 生成器は`MoveRules`を受け取る。反復規則や終局規則は`Position`単位の合法手を左右しないため、`Rules`全体は保持しない。 |
| `Position`の内部表現 | 変更しない。生成器が必要とする処理は一時状態の読み出し、既存の構築経路、および`Hash`の実装のみであり、思考エンジンの探索経路に手を加える理由がないためである。 |
| 一時状態の構築 | 既存の公開経路である`mark_promotion_deferred`と`set_lion_capture`を利用し、新たな構築APIは追加しない。麒麟成り例外の盤面からの導出処理は、すでに`set_lion_capture`内に実装されている。 |
| 構築経路の受理範囲 | 既存の構築経路や拡張SFENの受理範囲は変更せず、逆生成に特有の必要条件は生成器側でのみ課す。 |
| 候補生成 | 逆向きの幾何、在庫、および一時状態から上位集合を構成し、順方向への再適用によって絞り込む。 |
| 移動元 | 既存の移動プロファイルと利き表から`Bitboard`として構成し、専用の逆利き表は新設しない。 |
| 捕獲駒 | 初期配置から対象局面の盤上駒を差し引いて算出した、由来別の在庫のみを復元候補とする。 |
| 一時状態の列挙 | 不明値や既定値へ置き換えるのではなく、局所的に整合する具体的な値を列挙する。P2の待機満了によって消失する保留状態も列挙の対象とする。 |
| 候補局面 | 初回実装においては、`PositionBuilder`を用いて盤面全体を再構築する。 |
| 不正入力 | 対象局面に対しても集合`A`の全条件を課し、違反時は空集合へ丸め込まず、条件の分類ごとに型付きエラーを返却する。 |
| 候補の検査 | 候補局面については、順方向の再適用を行う前に集合`A`を満たしているかを検査する。再適用と対象局面との一致確認だけでは、着手によって消失するビットの違反を検出できないためである。 |
| ハッシュ | `Position::Hash`は`HashSet`のバケット選択に利用し、局面の一致確認は常に`Eq`で確定する。反復判定のキーとしては用いない。 |
| 実行状態 | 生成器は呼び出しをまたぐ可変状態を保持せず、スレッドセーフ（`Send + Sync`）とする。 |
| 最適化 | 全機能版の実装後に計測を行い、性能面で支配的であると確認された処理に限定して改善を加える。 |
| 互換性 | 別名のAPI、暗黙的な規則変更、および失敗時の代替経路は新設しない。 |

棄却した代案は次のとおりである。

第1に、先獅子状態と成り権保留状態を1つの公開値`TransientState`へと統合し、`Position`、`Undo`、`NullUndo`、規則判定、評価関数、探索、学習データ、拡張SFEN、およびプロトコル層を新表現へ移行する案である。この案は、生成器では利用しない思考エンジンの処理経路を広範囲に変更することになる。また、麒麟成りフラグの廃止に伴ってZobristキーや学習データ形式をどう扱うかまで決定しなければならなくなるため、採用を見送った。

第2に、`Rules`全体を受け取る案である。この案では、生成器が使用しない反復規則や終局規則まで保持することになる。また、`MoveGenerator::new`が`MoveRules`を受け取る現行の型設計とも整合しないため、採用を見送った。

第3に、記録升に不成の獅子が存在する状態を既存の構築経路で拒否する案である。この案は、非手番側の不成獅子を明示的に受理するという拡張SFENの現行契約と矛盾する。そのため採用を見送り、該当の条件は生成器側で課す必要条件に限定することとした。

## 直前局面の定義

規則集合を`R`、対象局面を`q`、`R`の下で`p`から生成される局面合法手集合を`Moves_R(p)`、着手適用後の局面を`Next_R(p, m)`とする。
本機能が返却する集合を、次のように定義する。

\[
\operatorname{Pred}_R(q)
=
\{p\in A\mid
\exists m\in\operatorname{Moves}_R(p),\
\operatorname{Next}_R(p,m)=q
\}.
\]

集合`A`は、`Position::validate()`を満たし、2種類のZobrist値（盤面、手番、先獅子状態から計算する通常Zobrist値と、成り権保留集合から計算する成り権保留Zobrist値。「Positionのハッシュ」節を参照）が再計算値と一致し、各所有者の由来別駒数が初期在庫を超えず、採用規則と一時状態が次の局所条件を満たす`Position`の集合とする。
これらの条件は3群に分かれており、それぞれ異なる役割を持つ。
第1に、`validate()`とZobrist値の一致は、公開の構築経路で生成できる整合性のとれた`Position`のみを対象とするための条件である。
第2に、由来別駒数の在庫制約は、直前手で取られた駒として復元できる駒を有限の範囲に絞り込むための条件である。この制約がない場合、任意の駒を捕獲駒として復元できてしまう（詳細は「駒在庫」節を参照）。
第3に、一時状態の局所条件は、対象局面からは一意に定まらない一時状態の列挙を、有限かつ小さな範囲に抑えるための条件である。以降に示す条件はいずれも、`p`に至る着手（`p → q`の着手ではなく、その1手前の着手）が現行の着手適用処理によって生み出し得る一時状態を、局面単体から見分けるための必要条件である。

成り権保留集合に関する局所条件は次のとおりである。

- 各ビットが立つ升には、その所有者から見た敵陣内に、所有者の成れる不成駒が存在していること。
- P0を採用しP5を採用しない規則においては、成り権保留集合が空であること。
- P0とP5を採用する規則においては、ビットが歩兵の升にのみ存在すること。
- P2を採用する規則においては、各対局者について、P5の歩兵を除くビットが高々1個であること。

先獅子の記録升に関する局所条件は次のとおりである。

- 記録升が存在する場合、その升は空升であるか、または`p.side_to_move().opposite()`の非獅子駒もしくは麒麟由来の成獅子によって占められていること。
- 記録升が存在する場合、`p.side_to_move()`の獅子由来または麒麟由来の駒が、由来別在庫から1枚以上欠けていること。
- 記録升が空升である場合、盤上に`p.side_to_move().opposite()`の角鷹または飛鷲が存在すること。

成り権保留集合における第1の条件は、現行の`validate()`が検査している条件と同一である。また、第2および第3の条件は、着手適用処理が該当規則の下でビットを立てる範囲から自然に導かれる。
P2における「高々1個」という条件は、待機状態の成立過程に基づいている。
P2の待機状態は、敵陣へ入る着手で不成を選択した駒にのみ付与される。そして、その対局者の次の着手が完了した時点で、着手前から存在していた待機ビットは動かなかった駒の分も含めてすべて満了し、その着手によって生じる待機ビットのみが新たに設定され得る（`Position::make_move_with_captures_unchecked`）。
なお、P5による歩兵の保留ビットは恒久的な状態であるため、この満了処理の対象にはならない。
したがって、ある対局者の待機ビットは、直前の自手番で動かした1駒にしか付与されないことになる。
この条件を設けない場合、P2の逆生成処理において着手側の適格な駒の部分集合をすべて列挙することになり、候補数が指数関数的に膨張してしまう。

記録升に関する第1の条件は、記録升に残る駒が、獅子を取った直前の着手側の駒であることから導かれる。
続く2つの条件は、先獅子状態の成立過程から導かれる必要条件である。
先獅子状態は、`p`へと至る着手において`p.side_to_move()`の獅子が非獅子に取られた場合にのみ発生する。そのため、手番側の獅子になり得る駒が在庫どおり盤上に揃っている局面では、記録升の存在を許容しない。
また、記録升が空升になるケースは経由升での捕獲に限られ、非獅子で経由升の捕獲を行える駒は角鷹と飛鷲のみである。
これら2つの条件を設けない場合、空升を指す記録升の変種が候補ごとに数十通り生成されてしまう。それらは順方向の再適用では除外できず、過去の対局履歴上あり得ない局面として出力が膨張する原因となる。

以上の条件は、いずれも局面単体で判定できる必要条件にとどまり、その一時状態を生じさせた直前着手の存在までは要求しない。
候補着手の順方向再適用は、候補`p`から対象局面`q`への遷移と矛盾する組み合わせのみを除外する。
したがって、`p`よりも前の履歴における一時状態の到達可能性については、本機能では判定しない。
局面の一致判定は盤面、手番、および一時状態を対象として行い、Zobrist値は一致判定を高速化するための派生データとして取り扱う。

なお、同一の`p`から異なる着手によって`q`へと到達できる場合であっても、`p`は1回のみ返却する。
中将棋では、異なる獅子力の駒による「じっと」が同一の結果局面をもたらすケースがあるため、着手ではなく局面を一意性の単位として管理する。

初期在庫の制約や一時状態の局所条件は、到達可能性に関する必要条件にすぎない。
本機能が保証する完全性は、集合`A`に属する要素のうち、`q`へ1手で遷移できるものを漏れなく列挙するという、集合`A`に対する相対的な完全性である。
「相対的」と表現するのは、集合`A`の範囲外にある局面（初期局面からは到達できないが、データ構造としては構築できる局面）については、何ら保証しないためである。
返却された`p`が初期局面から実際に到達可能であるかどうかは本機能単体では判断できず、初期局面まで手を逆にたどれるかを検証する後続の逆方向探索処理によって判定する。

## Positionの公開面

盤面と手番の情報だけからは導出できず、過去の着手に由来して後続の合法手や局面の同一性判定に影響を与える局面の付随状態を、**一時状態**と定義する。
現行の`Position`では、先獅子状態を内部型`LionTrigger`（記録升と麒麟成りフラグ）で、成り権保留状態を`Bitboard`でそれぞれ管理しており、いずれもクレート内限定で公開されている。
本マイルストーンでは内部表現を変更せず、次の2つの公開アクセサを追加する。

```rust
impl Position {
    /// 直前の着手で獅子以外の駒が相手獅子を取った升を返す。
    pub fn lion_capture_square(&self) -> Option<Square>;
    /// 成り権を保留中(P1・P2・P5)の駒がある升の集合を返す。
    pub fn promotion_deferred(&self) -> Bitboard;
}
```

`lion_capture_square`は`LionTrigger`の記録升のみを返却し、麒麟成りフラグは公開しない。フラグの値は記録升に直前着手側の麒麟由来の成獅子が存在するかどうかと同値であり、外部プログラム側でも盤面情報から導出可能だからである。
この同値性は、着手適用によって生じた局面においては後述の論証によって成立し、構築経路で作成した局面においては`set_lion_capture`自体が同一の盤面条件に基づいてフラグを設定することで成立する。
着手適用時の判定（動かした駒が麒麟であり、その着手によって成った）と、盤面情報からの導出が同値である理由は次のとおりである。
先獅子状態は、非獅子が獅子を取った着手においてのみ発生し、記録升に残る駒はその非獅子駒となる。
不成の獅子は成ることによって生じることはないため記録升には現れず、成獅子は麒麟が成ることでしか発生しない。
成りは着手の完了時に発生するため、記録升に成獅子が残るのは、麒麟が獅子を取り、同一の着手で成った場合に限定される。
角鷹または飛鷲が経由升で獅子を取ったケースでは記録升は空升となり、成獅子にはならない。
`promotion_deferred`については、現行の`pub(crate)`アクセサを`pub`に変更するだけである。

一時状態を持つ局面の構築には、既存の公開経路をそのまま利用する。
メソッドの呼び出し順序は、まず`PositionBuilder::new`で手番を決定し、`put`で駒を配置し、`mark_promotion_deferred`で成り権保留集合を設定する。続いて`finish()`で`Position`のインスタンスを取得した後に、`set_lion_capture`で先獅子状態を設定する。
`set_lion_capture`は記録升に手番側の駒が配置されている入力を拒否し、記録升の駒情報から麒麟成りフラグを導出した上で、Zobrist値を増分更新する。
各関数の契約は`src/core/position.rs`のrustdocおよび[protocol-layer.md](protocol-layer.md)「局面設定」に定められており、本書では変更しない。
記録升に不成の獅子が存在する状態は、現行の拡張SFENにおいて受理されており、テストコードでも受理されることが固定されている。そのため、既存の構築経路ではこれを拒否しない。
その状態を除外する役割は、「直前局面の定義」節で定義した集合`A`の条件が担い、生成器側でのみ制限を課す。
規則に依存する条件のうち、P0を採用しP5を採用しない場合の空集合判定は、現行の拡張SFENの解析処理で既に検査されており、これをそのまま維持する。
一方で、P0とP5における歩兵限定の制約や、P2における高々1個という制約は現行の解析処理では検査していない。拡張SFENの受理範囲を変更しないよう、これらの制約は生成器側でのみ課すこととする。

`Position::validate()`は、現行の盤面とビットボードの整合性検査に加え、通常Zobrist値と成り権保留Zobrist値が再計算値と一致するかどうかも検査し、不一致の場合には専用の`PositionError`を返却する。
`PositionBuilder`の`put`および`mark_promotion_deferred`はすでに2種類のZobrist値を増分更新しているため、`finish()`において検証を行ってから再計算するという現行の処理順序は変更しない。
ただし、検証によって一致が保証された後の再計算処理は不要となるため削除する。これにより、増分更新の不具合が再計算によって覆い隠されることを防ぎ、検証処理によって確実に検出できるようにする。
公開の構築経路および`try_make_move`はいずれもZobrist値を整合した状態で更新するため、既存の実装箇所においてこの検査が失敗することはない。

反復判定の処理は現行どおりとし、R1では通常Zobrist値と成り権保留Zobrist値の組み合わせを、R2とR3では通常Zobrist値のみをキーとして使用し、完全な`Position`による照合は行わない。
`Game`における探索キー履歴や探索処理についても、両値の排他的論理和を用いる現行の合成方式を維持する。
本マイルストーンで導入する`Position::Hash`および`HashSet<Position>`は生成器と外部プログラムに向けた契約であり、反復判定や探索キーの契約へ影響を波及させることはない。

## Positionのハッシュ

外部のRustプログラムや生成器の内部処理において`HashSet<Position>`を利用できるよう、`Position`に`Hash`を実装する。
実装としては、通常Zobrist値と成り権保留Zobrist値を`Hasher`へと渡し、ハッシュ衝突時の同一性判定は既存の`Eq`に委ねる。

既存の`Eq`は導出（derive）実装であり、盤面、占有集合、手番、一時状態に加えて、派生キャッシュである2種類のZobrist値も比較対象に含んでいる。
この比較が盤面、手番、一時状態に基づく一致判定と同値であることは、`Position::validate()`におけるZobrist値の一致検査と、Zobrist値を整合した状態で更新する構築経路のみが公開されていることによって保証される。

通常Zobrist値は盤面、手番、先獅子状態から計算され、成り権保留Zobrist値は成り権保留集合から計算される派生値である。反復規則R1が両者の組み合わせをキーとし、R2とR3が通常値のみを同一局面判定のキーとして使用するため、2つに分かれている。
なお、これらのハッシュ値を永続的な識別子、データ交換形式、あるいは局面一致判定の代替手段として使用してはならない。

## 公開API

実装は`src/core/predecessor/`に配置し、`src/core/mod.rs`および`src/lib.rs`から公開する。
公開インターフェースは次の形状とする。

```rust
#[derive(Clone)]
pub struct PredecessorGenerator {
    forward: MoveGenerator,
}

impl PredecessorGenerator {
    pub fn standard() -> Self;
    pub fn new(rules: MoveRules) -> Self;

    pub fn generate_predecessors(
        &self,
        target: &Position,
    ) -> Result<Vec<Position>, PredecessorError>;
}
```

`standard()`は、`MoveRules::standard()`（L0およびP0）を明示的に選択する簡易コンストラクタとする。
`new`に渡された`MoveRules`は、そのまま`MoveGenerator::new`へと渡して保持する。規則の欠落や矛盾を別の規則へ置き換えない。
規則コード列から規則集合を構築する際の重複、矛盾、または各群の欠落に関する検査は`Rules::from_codes`の責務である。生成器側では型付けされた`MoveRules`のみを受け取る。
外部プログラムは、`Rules::from_codes`または`Rules::ENGINE_DEFAULT`などの定数から`Rules`を構築し、その`moves`フィールドを渡す。

`generate_predecessors`は重複のない局面のリストを返却するが、返却順序は保証しない。
生成器は規則と既存の`MoveGenerator`のみを保持し、作業領域やキャッシュを複数の呼び出し間で共有しない。
`MoveGenerator`は`'static`な利き表への参照と`Copy`型である`MoveRules`のみを持つため、生成器は自動的にスレッドセーフ（`Send + Sync`）となる。したがって、外部プログラムは単一の生成器インスタンスを複数スレッド間で安全に共有できる。
この特性は公開契約とし、コンパイル時の静的表明によって固定する。

外部プログラムが対象局面を文字列で指定し、直前局面を文字列で受け取る経路には、すでに公開されている拡張SFENを用いる。
`notation::sfen::parse_extended_sfen`は、5欄で構成される文字列と`MoveRules`から`SetupPosition`を生成する。そして`into_parts`を呼び出すことで、`Position`、先獅子の記録升、および次の手数を取得できる。
記録升の情報を`Position`へ反映する処理は、プロトコル層と同様に`set_lion_capture`を用いて実施する。
局面の書き出しにあたっては、`SetupPosition::new`を用いて`Position`、記録升、および1以上9999以下の手数をラップし、`to_extended_sfen`を呼び出して5欄の文字列へと変換する。
手数の管理は生成器の対象外であるため、表記の都合上、外部プログラム側で指定する。
文字列の解析と書き出しには、生成器に渡したものと同一の`MoveRules`を使用する。
なお、本マイルストーンにおいてこれらの関数を変更することはない。

エラー型は、少なくとも次の原因を区別して返却できるものとする。

```rust
#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum PredecessorError {
    InvalidPosition(PositionError),
    MaterialExceedsInitial {
        color: Color,
        origin: PieceKind,
        found: u8,
        maximum: u8,
    },
    RuleStateMismatch,
    InvalidLionState,
}
```

対象局面`q`に対しても集合`A`の全条件を課し、違反が検出された場合は条件の分類に応じて次のエラーへと対応付ける。
`Position::validate()`によって拒否される盤面およびZobrist値の不一致は、`InvalidPosition`とする。
由来別在庫の超過は、`MaterialExceedsInitial`とする。
局面単体としては構築可能であっても、採用規則からは発生し得ない成り権保留集合については、`RuleStateMismatch`を返却する。
該当するのは、P0を採用しP5を採用しない規則で成り権保留集合が空でない場合、P0とP5を採用する規則で歩兵以外の升にビットが存在する場合、ならびにP2を採用する規則でいずれかの対局者にP5の歩兵以外のビットが2個以上存在する場合である。
先獅子の記録升に関する3つの条件（記録升の駒種、手番側の獅子在庫、空升に対する角鷹または飛鷲の存在）に違反する局面に対しては、`InvalidLionState`を返却する。
既存の構築経路や拡張SFENはこれらの局面を受理するため、生成器の入力検査においてのみこの区別を実施する。
正常な入力局面に対して直前局面が存在しない場合に限り、`Ok(Vec::new())`を返却する。

## 駒在庫

中将棋では、各対局者が46枚の駒を持って対局を開始し、取られた駒は盤上から取り除かれて再利用されることはない。
したがって、直前手で取られた駒は、対象局面において初期在庫から欠損している駒のみに限定される。

在庫は、現在の`PieceKind`ではなく**由来**、すなわちその駒が初期配置にあったときの駒種ごとに数える。
不成駒の由来はその駒種自身であり、成駒の由来は`PieceKind::unpromoted()`が返却する成る前の駒種となる。
たとえば、不成の金将の由来は金将であり、成った金将（歩兵の成駒）の由来は歩兵となる。同様に、不成の獅子の由来は獅子であり、成獅子の由来は麒麟である。
この仕組みにより、初期配置にあった金将と歩兵が成った金将、あるいは初期配置にあった獅子と麒麟が成った獅子を、別の在庫として区別して取り扱う。
由来別在庫の上限数は、初期配置においてその由来の駒が各対局者に何枚存在するかによって決定される。

製品コードの初期在庫は`Position::initial()`から導出し、同一の配置データを別の定数として重複して定義しない。
テストコードにおいては、RULES.md第4条および第5条に基づいて独立して記述した期待値と照合を行い、初期配置と在庫計算処理が同一の誤りを共有していた場合であっても確実に検出できるようにする。

対象局面が初期在庫を超過している場合は、`MaterialExceedsInitial`を返却する。
捕獲駒を復元する処理を行うたびに残数を減算し、2枚捕獲において同一の由来を2回使用する場合であっても上限を超過しないように制御する。

## 逆向き候補の構成

生成処理全体の流れは次の順序で進める。
まず、対象局面`q`が集合`A`の全条件を満たしているかを検査し、違反がある場合は「公開API」節で定めたエラーを返却する。
続いて、動いた駒、移動元、捕獲駒、成り、一時状態の順に候補`p`を構成する。
一時状態まで構成した候補が集合`A`の条件に違反している場合は、エラーとはせず単に破棄する。
残った候補に対して候補着手を順方向に再適用し、対象局面`q`と一致したものを重複排除した上で返却する。
エラーを返却するのは入力である`q`に違反がある場合のみであり、生成過程の候補`p`における違反は除外の理由としてのみ扱う。

対象局面の手番の相手側を、直前の着手者とみなす。
対象局面における直前着手者の各駒について、直前手で動いた駒であると順次仮定して処理を行う。

移動後の到達駒が不成駒である場合、移動前も同一の不成駒であり、`promote`は`false`となる。
到達駒が成駒である場合は、すでに成っていた駒が`promote: false`で動いたケースと、対応する不成駒が`promote: true`で動いて成ったケースの双方を列挙する。

移動元の候補は、既存の移動プロファイルと利き表から`Bitboard`として構成する。
使用する関数のうち`step_square`は公開関数であり、それ以外は`pub(crate)`関数である。生成器の実装は`core`配下に配置するため、いずれも問題なく参照できる。

- 固定移動と固定跳びについては、`movement_profile(kind)`から得られる識別子を用いて`movement_profile_data`の`fixed_deltas`を取得する。そして`RelativeDelta::for_color`で駒の所有者の色に応じた変位に変換した後に反転させ、到達升から逆算して移動元を求める。
- 走りについては、`slides`の各方向を`for_color`で絶対方向に変換して反転させる。その上で、`AttackTables::sliding_control(to, direction.opposite(), Bitboard::EMPTY)`を呼び出し、障害物のない空の占有集合に対する利き線を求める。
- 獅子の1升移動および直接跳びは方向に対称であるため、到達升に対する`king_steps`と`lion_jumps`をそのまま使用する。
- 角鷹と飛鷲については、`SpecialMovement::LionLike`の許可方向を反転させ、`step_square`を用いて1升前および2升前の升を求める。

なお、既存の`Position::attackers_to_by`は、盤上に実際に存在する駒と現在の占有集合に基づいて結果を絞り込む仕様である。そのため、空升である移動元を含む逆生成の用途には代替として利用できない。

走りの移動元の探索においては、対象局面の占有状態に基づいて経路の探索を打ち切らない。
対象局面の占有状態は直前局面の占有状態とは異なっている。動いた駒は移動元の升に存在せず、取られた駒も盤上に残っていないため、対象局面の盤面で探索を打ち切ると遮蔽物の判定を誤ることになるからである。
対象局面から消失している捕獲駒を復元した後の遮蔽物判定については、候補盤面に対する順方向の検証処理に委ねる。

獅子力を持つ駒については、1段階移動、直接跳び、じっと、居喰い、および2段階移動を明確に区別して取り扱う。
`mid: Some(square)`は経由升で必ず駒を捕獲する正準表現とし、経由升が空であるような別表現は生成しない。
現行の順方向合法手生成器においても、経由升に相手駒が存在する場合にのみ`mid: Some`を生成する仕様となっている。

各候補局面は`PositionBuilder`を用いて盤面全体を再構築し、`mark_promotion_deferred`で成り権保留集合を設定し、`finish()`の呼び出し後に`set_lion_capture`で先獅子状態を設定する。
局所的なインプレース変更APIや逆向きの差分適用処理は、「性能測定」節で述べる第3の改善案が実測によって正当化されるまでは導入しない。

## 捕獲駒の復元

通常移動、走り、固定跳び、および直接跳びでは、到達升が空升であったケースと、相手駒を捕獲したケースの双方を列挙する。
2段階移動および居喰いでは、経由升において相手駒を必ず復元する。
2段階移動の到達升においては非捕獲と捕獲の双方を列挙するため、経由升と合わせて最大2枚の駒を復元する。
じっとでは捕獲駒を復元しない。また、居喰いおよび移動元へ戻る2段階移動では経由升に対してのみ駒を復元する。
到達升に対する捕獲駒の復元は、`to != from`が成り立つ場合に限る。

復元する駒の候補は、相手側の不足在庫の中から選択する。
成ることが可能な由来駒については、捕獲された時点で不成であったケースと成駒であったケースの双方を列挙する。
なお、本将棋の持駒のように駒の所有者が変更されたり、盤上へ駒を打ったりするルールは導入しない。

## 一時状態の逆生成

直前局面における先獅子状態は、`p → q`の着手適用処理によって局面`q`の値へと上書きされるため、対象局面の情報からは一意に定まらない。
記録升が存在しない状態と、全144升を上限とする記録升が存在する状態を合わせた合計145状態のうち、集合`A`で定義した局所条件を満たすものだけを列挙する。実装では、局所条件を満たす升の集合を先に`Bitboard`として求め、その升についてだけ基底の候補局面のクローンに`set_lion_capture`で記録升を設定する。全144升へ設定してから検査する方式は、構成した候補の大半を記録升の条件で棄却することになり、そのクローンの費用が無駄になるためである。
候補`p`において、手番側の獅子由来および麒麟由来の駒が盤上に揃っている場合は、獅子在庫に関する局所条件に基づき記録升が存在するすべての状態が除外され、記録升なしの状態のみが残る。
記録升が空升である場合は経由升で獅子を捕獲したケースとして扱い、候補`p`の`side_to_move().opposite()`の非獅子駒が存在する場合は到達升で獅子を捕獲したケースとして取り扱う。
同一所有者の麒麟由来の成獅子が存在する場合に限り、L2の麒麟成り例外を適用可能な状態として扱う。
この所有者は`p → q`の着手者ではなく、局面`p`の一時状態を生み出したさらに1手前の着手者である。
記録升に記録された捕獲が過去に実在したかどうかを推測することはせず、局所条件を通過した各値をそのまま候補着手の順方向再適用処理へと渡す。
順方向の再適用処理は`p → q`の遷移との整合性のみを検査し、記録された捕獲の存在自体を証明するわけではない。
なお、不明値を表す列挙子の追加や、記録升なしへの正規化は導入しない。

成り権保留集合の構成にあたっては、対象局面の保留集合から、移動元、到達升、および実際の捕獲升（その候補着手において捕獲駒を復元した升）のビットをあらかじめすべて除外する。
着手による影響を受けない升のビットのみを対象局面から引き継ぎ、移動元の駒および実際の捕獲升に復元した適格な駒について、直前の手番における保留ありと保留なしの状態をそれぞれ独立に列挙する。
この独立列挙はP1およびP5を対象とした処理であり、P2の着手側については後述する全体列挙の処理で置き換える。
対象局面の到達升に立っているビットは直前の着手で新設された可能性があるため、そのまま直前局面にコピーしてはならない。
到達升が移動元または捕獲升でもあるケースでは、直前局面においてその升に配置される駒に関して列挙した値のみを使用する。
したがって、じっとや居喰いのように`from == to`となる場合であっても対象局面の値は引き継がず、影響を受ける升を1つの`Bitboard`にまとめて重複処理を防止する。

P2を採用する規則においては、着手側（`q.side_to_move().opposite()`）が着手する前から存在していた待機ビットが着手完了時にすべて満了するため、着手に関与していない着手側の駒であっても、直前局面において待機ビットを保持していた可能性がある。
その待機ビットは、局面`p`に至る着手（`p → q`の1手前における着手側の着手）で敵陣へと進入した駒に付与されたものである。どの駒がそれに該当するかは対象局面`q`の情報からは判別できず、順方向の再適用処理においてもすべて満了するため区別がつかない。
そこで、候補`p`における着手側の駒のうち適格な駒、すなわち移動元に配置される駒を含め、敵陣内に存在する成れる不成駒からP5の歩兵を除いた`k`個の駒を特定する。そして、待機ビットが存在しない1通りと、`k`個の駒のうちいずれか1駒のみに待機ビットを付与した`k`通りを合わせた、合計`k + 1`通りを列挙する。
2駒以上に待機ビットを付与する組み合わせは、集合`A`の「高々1個」という条件に反するため列挙しない。
復元された捕獲駒は相手側（`q.side_to_move()`）の駒であり、その待機ビットは前述した独立列挙の処理で扱うが、相手側についても候補局面の検査において高々1個の条件が適用される。
P5における歩兵の保留ビットは恒久的な状態であり、P2の満了処理によって消失することはないため、P1と同様に移動元と捕獲升以外のビットは対象局面からそのまま引き継ぐ。

一時状態まで構築を完了した各候補局面は、順方向の再適用を行う前に集合`A`の全条件を満たしているかを検査し、違反する候補を破棄する。
順方向の再適用処理では候補着手によって消失するビットの妥当性を検査できないためである。たとえば、P2において復元した2枚の捕獲駒の双方に待機ビットを付与した候補などは、再適用と対象局面との一致確認だけでは除外できない。

## 順方向検証

逆向きに構成した候補着手は、その時点では合法手とみなさない。
集合`A`への適合検査を通過した候補局面のクローンを作成し、同一規則を設定した`MoveGenerator`を渡して`try_make_move`を実行し、候補着手を適用する。

```rust
let mut replayed = candidate.clone();
if replayed.try_make_move(mv, &self.forward).is_ok() && replayed == *target {
    // candidateを採用する
}
```

この1回限りの順方向検証によって、移動経路、遮蔽物の有無、捕獲、成り、先獅子、および成り権保留状態の正当性を、既存の実装のみを用いて判定する。
逆生成処理の側には、これらと同一の合法性判定ロジックを重複して持たせない。

検証に合格して採用された局面は、`HashSet<Position>`を用いて既出であるかを判定し、初めて出現した局面のみを返却用の`Vec`へと追加する。
ハッシュ値が衝突した場合であっても`Eq`によって完全な局面の比較が行われるため、異なる局面が誤って失われることはない。

## ローカルルール

L0からL4まで、およびP0からP6までの各規則は、候補局面または候補着手の順方向における合法性を左右し得るため、初期の完成時点からすべて網羅して対応する。
具体的には、L4は先獅子の禁止対象を非獅子駒による捕獲のみに限定し、P5は歩兵の恒久保留と最奥段での強制成りの仕様を変更し、P6は前進専用駒の最奥段での強制成りの仕様を変更する。
したがって、標準規則のみに限定した部分的な実装を完成とみなすことはしない。

一方、R1からR3まで、およびE0からE3までの各規則は、`Position`単位における順方向合法手を変化させない。そのため、生成器側ではこれらを受け取らず、対局履歴の管理や終局裁定の処理へも展開しない。
利用側のプログラムがE3を含む`Rules`を用いて対局を管理している場合であっても、生成器に渡す引数は`rules.moves`のみとなる。

## 完全性の根拠

順方向の再適用処理は、生成した候補が正しいことを示す健全性の検査であり、候補に漏れがないことまでは証明できない。
本機能における相対的完全性は、次の3層のアプローチで検証する。

第1層では、順方向のすべての移動形式と逆構成の対応表を本書の「移動形式と逆構成の対応」節に記載し、実装完了時に内容を確定させる。
全144升に対する完全性を単なるテスト件数のみから主張するのではなく、各移動形式、捕獲数、成り、および一時状態に対応する逆構成処理が存在することを、場合分けを用いて論理的に説明する。

第2層では、固定局面およびシード固定局面から得られるすべての合法手を順方向に適用する。
そして生成される各辺`p → q`について、`generate_predecessors(q)`の返却結果に局面`p`が漏れなく含まれていることを確認する。

第3層では、テスト専用の有限状態オラクルを構築する。
オラクルは、盤上の一部の升集合（たとえば片隅の4×4升）、少数の駒集合（王駒2枚と検証対象の駒種を数枚）、両手番、および該当規則で取り得る一時状態の値を固定し、それらの配置をすべて列挙して有限の局面集合`S`を生成する。
続いて`S`の各局面に対して既存の順方向生成器から全合法手を適用し、後続局面ごとに「その局面へ到達した`S`の局面の集合」を表として記録する。
これがオラクルによる直前局面表となり、集合`S`の範囲内において完全性が保証される。
その上で、`S`の各局面`q`について製品コードの`generate_predecessors(q)`を呼び出し、返却された局面のうち`S`に属するものの集合が、表に記録された`q`の行と集合として完全に一致することを検査する。
なお、オラクルは製品コードの逆経路、在庫枝刈り、および捕獲復元関数を呼び出さず、順方向生成器のみに依存する構成とする。
また、`S`は列挙した局面のうち集合`A`の条件を満たすものに限定する。その判定ロジックはRULES.mdおよび本書の条件記述に基づいてテスト側で独立して実装し、製品コードの入力検査関数は利用しない。

### 移動形式と逆構成の対応

順方向のすべての移動形式と逆構成の対応を次の表に示す。
逆構成の関数はいずれも`src/core/predecessor/`にあり、`reverse::moves`が到達升から候補着手を、`reverse::restorations`が捕獲駒を、`transient::candidates`が成り権保留集合を、`transient::lion_records`が先獅子の記録升をそれぞれ列挙する。
成りの3通り（不成、直前手での成り、既成駒の移動）は`reverse::enumerate_candidates`が到達駒から移動前の駒を決める段階で扱い、すべての移動形式に共通する。
一時状態の列は、直前局面`p`の一時状態をどう列挙するかを示し、対象局面`q`の一時状態は順方向の再適用が着手から再現する。

| 順方向の移動形式 | 捕獲数 | 逆構成 | 固定テストの分類 |
|---|---|---|---|
| 固定移動（1升移動） | 0〜1（到達升） | `reverse::moves`の固定移動枝。`fixed_deltas`を所有者の色で絶対変位に変換して反転し、到達升から移動元を求める。 | 通常移動、成り、在庫 |
| 固定跳び（麒麟・鳳凰の2升跳び） | 0〜1 | 同じ固定移動枝。中間升の駒の有無は問わない（第7条第6項）。 | 固定跳び |
| 走り | 0〜1 | `reverse::moves`の走り枝。空の占有集合に対する逆方向の利き線を移動元とし、遮蔽の判定は順方向検証に委ねる。 | 走り |
| 獅子の1段階移動 | 0〜1 | `reverse::moves`の獅子枝。`king_steps(to)`を移動元とする。 | 獅子の1段階移動 |
| 獅子の直接跳び | 0〜1 | 獅子枝。`lion_jumps(to)`を移動元とする。 | 獅子の直接跳び |
| 獅子のじっと | 0 | 獅子枝。`from = to`、`mid = None`。第1段階に使える空升の有無は順方向検証が判定する。 | じっと |
| 獅子の居喰い | 1（経由升） | 獅子枝。`from = to`、`mid ∈ king_steps(to)`で、経由升には必ず相手駒を復元する。 | 居喰い |
| 獅子の2段階移動 | 1〜2 | 獅子枝。`mid ∈ king_steps(to)`、`from ∈ king_steps(mid)`で、経由升に必ず、到達升に任意で相手駒を復元する。 | 2段階移動 |
| 角鷹・飛鷲の向き付き1段階移動 | 0〜1 | `reverse::moves`の獅子力枝。許可方向を所有者の色で絶対方向に変換し、その逆方向へ1升戻った升を移動元とする。 | 角鷹と飛鷲 |
| 角鷹・飛鷲の直接跳び | 0〜1 | 獅子力枝。逆方向へ2升戻った升を移動元とし、`mid = None`。 | 角鷹と飛鷲 |
| 角鷹・飛鷲の2段階捕獲 | 1〜2 | 獅子力枝。逆方向へ2升戻った升を移動元とし、`mid`は1升戻った升。 | 角鷹と飛鷲 |
| 角鷹・飛鷲の居喰い | 1 | 獅子力枝。`from = to`、`mid`は許可方向へ1升進んだ升。 | 角鷹と飛鷲 |
| 角鷹・飛鷲のじっと | 0 | 獅子力枝。`from = to`、`mid = None`。 | 角鷹と飛鷲 |

一時状態の列挙と固定テストの対応は次のとおりである。

| 一時状態 | 直前局面`p`での列挙 | 固定テストの分類 |
|---|---|---|
| 先獅子状態の新設（`q`の記録升） | 列挙しない。順方向の再適用が着手から`q`の記録升と麒麟成りフラグを再現する。 | 先獅子 |
| 先獅子状態の消滅とL2例外（`p`の記録升） | `transient::lion_records`が、記録升なしと局所条件を満たす升の各値を列挙する。L1からL4までの合法性は順方向検証が判定する。 | 先獅子 |
| 成り権保留のP1およびP5 | `transient::candidates`が、移動元の駒と復元した捕獲駒について保留の有無を独立に列挙し、他の升のビットは`q`から引き継ぐ。 | 成り権保留 |
| 成り権保留のP2（待機の新設と満了） | `transient::candidates`が、着手側の適格な`k`駒について待機なしと1駒だけの`k + 1`通りを列挙し、相手側は独立列挙と高々1個の検査で扱う。 | 成り権保留 |

## 逆方向探索への接続条件

本機能単体では、先行研究の論文と同義での到達不能を証明することはできない。
後続となる逆方向探索のマイルストーンにおいて、目標集合の定義、探索終了条件、探索経路の保存方法、および`Game`履歴の取り扱いを個別に確定させる必要がある。

探索を途中で打ち切る場合においては、到達可能性が不明である結果と到達不能である結果を、別の結果型として明確に区別する。
open集合が空になるまで網羅的に探索した場合に限り、生成器の相対的完全性を前提として到達不能と判定できる。

なお、本将棋の論文が用いる玉2枚だけの目標集合は、中将棋ではそのまま使わない。
中将棋には持駒や駒打ちの概念がなく、一度捕獲されて減少した駒を再び盤上へ増やすことができないためである。

## 実装フェーズ

フェーズ2からフェーズ4までは、各フェーズで対象とする移動形式について健全性（返却された局面がすべて集合`A`に属し、再適用によって`q`と一致すること）と「検証」節の固定テストを担保する。完全性については、各フェーズの範囲内において第2層（逆包含）の固定局面テストを用いて確認する。
第3層の有限状態オラクルおよび全順方向辺の逆包含テストは、すべての移動形式が出揃うフェーズ5においてまとめて実施する。
なお、「性能測定」節で言及する「全機能版」とは、フェーズ4を完了した時点の実装を指す。

### フェーズ1　`Position`の公開面の追加

`lion_capture_square()`、公開の`promotion_deferred()`、`Position::Hash`、ならびにZobrist値の一致を検査する`Position::validate()`を実装し、`PositionBuilder::finish()`における検証後の再計算処理を削除する。
内部表現、既存の構築経路、Zobristキー、評価関数、探索処理、プロトコル層、および学習データ形式には一切手を加えない。

完了条件は、すべての既存テストとperftの実行結果に挙動の変更がなく、全局面のZobrist値が変更前と一致し、`Hash`の契約（`Eq`で等しい局面は同一のハッシュ値を持ち、衝突時にも`HashSet`が異なる局面を正しく保持すること）がテストによって固定されていることである。
探索、評価、Zobrist値のいずれも変更しないため、棋力測定は実施しない。

### フェーズ2　公開API、入力検査および在庫

`PredecessorGenerator`、`PredecessorError`、由来別在庫の計算ロジック、および衝突安全な重複排除処理を実装する。
不正局面、規則状態の矛盾、在庫超過、正常な空集合の返却、ならびに`Send + Sync`の静的表明をテストによって検証する。

### フェーズ3　通常移動、捕獲および成り

固定移動、走り、固定跳びの移動元候補を`Bitboard`として構成する処理を実装する。
0枚または1枚の捕獲駒、既成駒の移動、および直前手での成りを復元し、すべての候補局面を順方向に検証する。

### フェーズ4　獅子力と一時状態

獅子、角鷹、飛鷲における1段階移動、直接跳び、じっと、居喰い、および2段階移動を実装する。
最大2枚の捕獲復元、先獅子状態における最大145状態の列挙、成り権保留状態のP1、P2、P5、ならびに結果に影響を与えるすべてのローカルルールに対応する。

### フェーズ5　完全性検証と計測

全順方向辺の逆包含テスト、有限状態オラクル、移動形式との対応表、および公開APIを用いた深さ2の結合テストを追加する。
固定コーパスをreleaseビルドで測定し、その結果を測定記録ファイル`docs/measurements/predecessor-generator-profile.md`に保存した上で、本書からリンクを設定する。

## 検証

### 固定テスト

固定テストには、次の分類をすべて含める。

| 分類 | 必須事例 |
|---|---|
| 通常移動 | 非捕獲、到達升捕獲、盤端での挙動、および先後両方の所有者を検証する。 |
| 走り | 距離1、距離2以上、味方駒による遮蔽、相手駒による遮蔽、および捕獲を検証する。 |
| 固定跳び | 中間升が空升、味方駒、相手駒の各ケースと、到達升での捕獲を検証する。 |
| 獅子の1段階移動 | 非捕獲と捕獲の双方を検証する。 |
| 獅子の直接跳び | 非捕獲と到達升での捕獲を検証する。 |
| じっと | 異なる駒による「じっと」が同一の結果局面へと至る場合であっても、1局面のみを返却することを検証する。 |
| 居喰い | `from == to`、`mid == Some`、および1枚捕獲のケースを検証する。 |
| 2段階移動 | 経由升のみでの捕獲と、経由升および到達升での2枚捕獲の双方を検証する。 |
| 角鷹と飛鷲 | 先後両方の所有者について、向き付き1段階移動、直接跳び、じっと、居喰い、および2段階捕獲を検証する。 |
| 成り | 不成のみ、成りと不成の両候補、直前手での成り、既成駒の移動、二重成りの拒否、ならびにP6における最奥段での不成拒否を検証する。 |
| 先獅子 | 標準規則、L1、L2、L3、L4において、以前の捕獲升と新しい捕獲升の双方を検証する。また、手番側の獅子在庫が揃っていて記録升ありの状態がすべて除外される局面や、記録升が空升の状態に必要な角鷹または飛鷲が存在するかどうかのケースも検証する。 |
| 成り権保留 | P1における移動駒、復元捕獲駒、到達升、および無関係な駒の保留状態を検証する。さらに、P2における待機の新設と非移動駒の満了、P5における歩兵の恒久保留と強制成り、ならびにP2とP5、P2とP6を併用した場合の挙動を検証する。 |
| 在庫 | 不成駒と成駒の由来の区別、同一由来の駒2枚の復元、在庫充足時および在庫超過時の挙動を検証する。 |

返却される各出力について、直前局面が集合`A`の全条件を満たしていること、手番が対象局面と反対であること、ならびに順方向の再適用結果が対象局面と完全に一致することを検査する。
あわせて、入力として渡した対象局面が変更されないこと、返却された局面に重複が存在しないこと、そして4種類のエラーと正常な空集合が正しく区別して返却されることも確認する。

`tests/`ディレクトリには、公開APIのみを利用した深さ2の逆方向探索テストを配置する。
初期局面から2手進めた対象局面から手を逆に2手たどり、`HashSet<Position>`を活用して初期局面を正しく発見できることを確認する。
対象局面の入力および直前局面の出力には拡張SFENを用い、外部プログラムが利用する経路と同一の処理で問題なく往復変換できることを確認する。
先獅子状態が存在する局面や成り権保留が存在する局面についても、公開APIのみを用いて拡張SFENへの書き出しと再解析を行い、`Position`が完全に一致することを確認する。
なお、本テストのために製品コード側へ探索器を追加することはない。

### 性能測定

全機能版の実装において正しさを確立した後に、releaseビルドを用いて固定コーパスの測定を実施する。
対象とするコーパスには、初期局面付近、1枚捕獲後、2枚捕獲後、成り直後、先獅子状態あり、P1状態あり、P2の待機あり、P5の保留歩兵あり、および盤上の駒が少ない局面を含める。

各局面について、候補構成数、`try_make_move`の呼び出し回数、採用局面数、候補対採用比、ならびに経過時間の中央値と95パーセンタイルを測定記録に残す。
なお、初回マイルストーンの段階では、客観的根拠のない速度の閾値（基準値）は設定しない。

性能改善を実施する場合は、同一の実行環境と固定コーパスを用いて変更前後の性能を比較する。
プロファイル計測によって支配的であること、すなわち自己時間の割合が最大であると確認されていない処理に対しては、最適化を行わない。

現時点で判明している改善候補を次の3点として記録しておく。
いずれもフェーズ5の計測において支配的であると確認された場合に限り、本マイルストーン内で導入する。
第1に、現行の`try_make_move`は内部ですべての合法手を生成してから照合を行うため、検証コストが候補数と全手生成コストの積となってしまう点である。クレート内には移動元の駒の合法手のみを生成して照合する`MoveGenerator::is_legal_move`が既に存在し、置き換え候補となる。
第2に、対象局面に先獅子の記録升が存在する場合、直前の手はその記録升において非獅子が獅子を取る着手に限定されるため、候補構成の段階で枝刈りとして利用できる点である。
第3に、返却局面の構築および保持処理が性能上支配的である場合は、`for_each_predecessor(&self, q, f: impl FnMut(&Position))`という形状のビジターAPIへ置き換える。
呼び出しごとのローカル変数として作業用の`Position`を1つ保持し、候補ごとに逆差分の適用、順方向検証、および巻き戻しを行う。そして、採用された局面のみを参照としてクロージャへと貸し出す設計とする。
この作業局面は生成器のフィールドには保持せず、呼び出し間で状態を共有しないという契約とスレッドセーフ性（`Send + Sync`）を厳格に維持する。
これにより、`PositionBuilder`による盤面全体の再構築と所有権付きの`Vec<Position>`の返却を廃止でき、利用側のプログラムは貸し出された参照から必要なデータのみを各自で複製できるようになる。
なお、標準ライブラリの`Iterator`は自身が持つバッファへの参照を要素として返却できないため、外部イテレータではなく内部イテレーション方式を採用する。
もしこの方式を導入する場合は、`generate_predecessors`を本APIで置き換えて両方式を混在させないこととし、本書の「公開API」節、エラーの返却形式、結合テスト、および完了条件を改訂する。
ただし、一意性を保証するための既出判定用集合は生成器の内部に依然として残るため、本変更によって削減できるのは、返却用および利用側の保持分のみに限定される。
いずれの案も、実際の計測によって支配的な処理であると確認されるまでは導入しない。

計測の結果は [measurements/predecessor-generator-profile.md](../measurements/predecessor-generator-profile.md) のとおりであり、自己時間の割合が最大の処理は存在しなかった。
順方向の再適用、候補局面の構築と複製、集合`A`の検査、および重複排除の集合への挿入がいずれも1割から2割の範囲に分散するため、上記3案はいずれも採用しない。
処理時間と返却集合の大きさは、不足在庫の由来数と、着手側の獅子在庫が欠けた局面での記録升の変種の数に比例する。

### 検証コマンド

各フェーズにおいて対象モジュールのテストを実行し、最終確認の段階では次のコマンドを実行する。

```console
cargo fmt --all -- --check
cargo clippy --all-targets
cargo test
cargo test predecessor_completeness -- --ignored --test-threads=1
cargo test predecessor_oracle -- --ignored --test-threads=1
git diff --check
cargo run --release --quiet --bin perft -- 4
cargo test --release predecessor_profile -- --ignored --nocapture
```

perftの深さ1から4までの値が、それぞれ`36`、`1,296`、`48,315`、`1,801,639`のままであり、変更がないことを確認する。
全順方向辺の逆包含テストと有限状態オラクルは、直前局面の集合が大きい局面で1テストあたり数十秒から数分と数GBのメモリを要するため、`#[ignore]`を付けて通常の`cargo test`から外し、上記のコマンドで1スレッドずつ実行する。
最後のコマンドは計測テストであり、性能の合否判定ではなく、固定コーパスの基準値を測定記録に残すために実行する。

## 完了条件

次の条件をすべて満たした時点で、本マイルストーンを完了とする。

- `Position`が先獅子の記録升と成り権保留集合を公開アクセサで返却し、内部表現、既存の構築経路、Zobristキー、評価関数、探索処理、プロトコル層、および学習データ形式に変更がないこと。
- `Position::Hash`が`Eq`と整合しており、ハッシュ衝突時であっても異なる局面を正しく区別して保持できること。また、反復判定や探索キーの契約に変更がないこと。
- `Position::validate()`が2種類のZobrist値の一致を検査していること。
- 公開APIが本書の定義どおりに`Pred_R(q)`を重複なく列挙し、生成器がスレッドセーフ（`Send + Sync`）であること。
- 不正局面、在庫超過、規則状態の矛盾、および先獅子状態の矛盾が型付きエラーとして返却され、正常な空集合と明確に区別されること。
- 通常移動、走り、固定跳び、獅子、角鷹、飛鷲、非捕獲、1枚捕獲、2枚捕獲、および成りの固定テストがすべて成功すること。
- L0からL4まで、ならびにP0からP6までの`Position`遷移に関係するすべての条件分岐が検証されていること。
- 全順方向辺の逆包含テスト、および有限状態オラクルとの集合一致が成立すること。
- 公開APIを用いた深さ2の逆方向探索により、拡張SFENで指定した対象局面から初期局面を正しく発見できること。
- 固定コーパスの測定条件、候補数、採用数、中央値、および95パーセンタイルが測定記録に記載され、本書から正しくリンクされていること。
- 順方向の合法手生成、対局裁定、拡張SFENの受理範囲、静的評価値、全局面のZobrist値、`bench`の探索ノード数と最善手、および既存のperft値の挙動に一切変更がないこと。
- 定められた検証コマンドがすべて正常に終了すること。

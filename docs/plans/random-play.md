# ランダム対局検証ハーネスの設計書

## 実施状況

2026年8月9日に本設計書を起案した。2026年8月10日に、プロトコル層設計書（plans/protocol-layer.md）の起案に伴い本書を改版し、`to_sfen`の表記規範の参照先とフェーズ順序を改め、`--rules`を必須指定へ変更した。2026年8月11日に、`--rules`の値文法をエンジンバイナリと統一し、検証済みプリセット名`engine-default`と`lishogi`の単独指定にも対応した。

同2026年8月10日に、フェーズ1（乱数モジュールの分離）、フェーズ3（`Game`の複製）、フェーズ2（`to_sfen`）を実装しコミットした。フェーズ1では、設計書に記載のなかった`src/game.rs`テスト内の3つ目のXorShift64コピーも統合対象へ含めた。フェーズ2では`to_sfen`を盤面部と手番部の2欄基本形とし、`parse_sfen`も2欄受理のまま維持すると決定した（決定の記録はdocs/protocols/usi-lishogi.mdの「to_sfenへの要求事項」節）。同日のcodexによる設計レビューを受け、シード派生の式と再現契約、成り権保留局面のテスト要件、検証用の代表規則セットを本書へ確定反映した。

フェーズ4（`random_play`バイナリ）も同2026年8月10日に完了し、本マイルストーンの完了条件をすべて満たした。代表9規則セット×各300局の計2,700局が異常なし・打ち切り0局で完走し、終局理由の内訳は王駒捕獲と詰みが大半、駒枯れが少数で、反復裁定・ステイルメイト・引き分けは0局だった。反復裁定パスがランダム対局では踏まれないというこの観測は、ハーネスの目的どおり裁定パスのカバレッジの穴として記録する（反復裁定自体は単体テストが担保している）。`--seed 1 --game 5`固定の2回実行は全手順一致し、`--verify-all`付き20局も完走、テスト200件・clippy・fmt・perft自己回帰値も全緑だった。

`--max-ply`の既定値は4096で確定した。実測（代表2,700局とR1追加1,000局、いずれも打ち切り0局）の手数分布は最小19手、中央値242手、99パーセンタイル928手、最大1,363手であり、4096は実測最大の約3倍の余裕を持つ。

## 目的

本マイルストーンは、終局まで指し続けるランダムプレイヤーを検証ハーネスとして整備し、合法手生成器と審判層を通した全経路の異常を自動検出できるようにする。
やねうら王miniの開発記録が示すとおり、合法手からランダムに1手を選んで指すループは、単体テストでは到達しにくいレアケースを自動で踏み、assertと組み合わせることで効率よくバグを検出する。
探索部の実装前にこの装置を持つことで、規則組合せごとの裁定パスが実際に踏まれているかどうかも観測できる。

ハーネスは1局を眺める観察ツールではなく、多数局を回して不変条件を検査するテスト装置として設計する。
異常を検出した局は、シードと局番号だけから単独で再実行できることを再現性の要件とする。

本マイルストーンは探索部に依存しない。
プロトコル層へ先送りしていた`to_sfen`の基本形（盤面と手番の往復変換）は、異常局面のダンプに必要となるため本マイルストーンへ前倒しする。
ただし`to_sfen`の表記規範は、プロトコル層フェーズ1のusi-lishogi調査で一次資料により検証したshogiops仕様（docs/protocols/usi-lishogi.md）とするため、フェーズ2は同調査の完了後に実施する。
先獅子状態や成り権状態を含む拡張SFENの設計は、引き続きプロトコル層で扱う。

## 適用範囲

本マイルストーンでは、次の作業を行う。

- `position.rs`と`movegen/tests/invariants.rs`に重複しているXorShift64乱数生成器を`src/rng.rs`へ分離し、3箇所目の利用者として新バイナリを加える。
- `sfen.rs`へ`to_sfen`（`Position`からSFEN文字列への出力）を追加し、`parse_sfen`とのラウンドトリップテストを付ける。
- `Game`へ`Clone`を追加し、全数検証で複製した対局に着手を適用できるようにする。
- 検証ハーネス`src/bin/random_play.rs`を新設する。

探索部、評価関数、USIおよびCECPのプロトコル本体、拡張SFEN、性能最適化は対象外とする。

## 設計判断

| 項目 | 決定 |
|---|---|
| 役割 | N局を回して不変条件を検査する検証ハーネスとし、単局観察は`--verbose`で兼ねる。 |
| 実行形態 | perftと同格の`src/bin/`独立バイナリとし、cargo testの実行時間を増やさない。 |
| 乱数 | 既存のXorShift64を分離して再利用し、外部クレートを追加しない。 |
| 乱数モジュールの公開範囲 | `src/rng.rs`をクレート直下の`pub mod`とし、`#[doc(hidden)]`でrustdocから隠す。 |
| 規則指定 | `--rules`でコード列または検証済みプリセット名を受け取り、共通の`parse_rule_set`で解決してから`Rules::from_codes`で検証する。プリセット名は単独で指定する。明示指定を必須とし、省略時の既定は設けない。値文法と必須方針はエンジンバイナリ（plans/protocol-layer.md）と統一する。 |
| 再現性 | 各局の乱数状態を基本シードと局番号から派生させ、任意の1局を単独再実行できるようにする。 |
| 検証深度 | 既定は軽量検証とし、`--verify-all`指定時だけ全合法手の受理を全数検証する。 |
| 手数上限 | `--max-ply`到達は異常ではなく打ち切りとして別集計する。 |
| 局面ダンプ | SFEN形式とし、`to_sfen`を本マイルストーンで実装する。 |
| バイナリ名 | 将来の探索部入り自己対局と区別するため`random_play`とする。 |

## 乱数モジュールの分離

XorShift64は現在、`src/core/position.rs`のZobristキー生成用（非公開、`next`のみ）と、`src/core/movegen/tests/invariants.rs`のテスト用コピー（`index`付き）の2箇所に重複している。
これを`src/rng.rs`の単一実装へ統合し、`next`と`index`の両方を備える。
乱数生成器は中将棋のドメイン概念ではないため、`core/`配下ではなくクレート直下へ置く。

モジュールは`pub mod rng`として公開するが、ライブラリ利用者向けAPIではないため`#[doc(hidden)]`を付け、crate rootからの再公開は行わない。
シード0の禁止は現行どおりassertで保つ。

この分離は純粋な移動であり、生成される乱数列を変更してはならない。
`ZOBRIST_SEED`から得られるZobristテーブルが分離前後で一致することは、既存のZobrist整合テストとperft自己回帰値の不変で確認する。

## SFEN書き出し

`sfen.rs`へ、`Position`から盤面と手番を持つSFEN文字列を生成する公開関数`to_sfen`を追加する。
座標系と駒表記は、プロトコル層フェーズ1調査で検証したshogiops仕様（docs/protocols/usi-lishogi.md）を規範とする。
現行`parse_sfen`は「shogiops互換」を謳うが一次資料での検証を経ていないため、調査で規約との乖離が見つかった場合は、本フェーズで`to_sfen`と`parse_sfen`の両方を修正する。
`parse_sfen(to_sfen(p))`が元の局面の盤面と手番を復元することをラウンドトリップテストで固定する。
テストには初期局面、成駒を含む局面、および成り権保留（`mark_promotion_deferred`相当の状態）を含む局面を用いる。
`to_sfen`は盤面部と手番部の2欄基本形であり、成り権保留状態はSFENが運ばないため、保留を含む局面のテストは盤面と手番の保存（および`to_sfen`再適用の同一性）の検証とし、保留状態自体の復元は要求しない。保留状態を含む完全な復元は、プロトコル層の拡張SFENの検証項目である。

ダンプされたSFENは`perft --sfen`へそのまま入力できるため、異常局面の分岐数調査に直結する。
先獅子状態と成り権状態を含む拡張形式は本関数の対象外であり、プロトコル層の設計で扱う。
このため、反復や先獅子に依存する異常の完全な再現はSFEN単体では保証されず、後述する全手順ダンプが再現の正となる。

## Gameの複製

`Game`へ`#[derive(Clone)]`相当の複製を追加する。
`Position`、`MoveGenerator`、`AdjudicationState`はいずれも所有データだけを持つため、構造的な複製で十分である。
用途は全数検証で候補手ごとに対局を複製することであり、探索部のための最適化された複製やundo APIは追加しない。

## random_playバイナリ

### コマンドライン引数

`clap`のderiveでperftと同じ形式のCLIを構成する。

| 引数 | 意味 |
|---|---|
| `--games N` | 対局数。既定は1とする。 |
| `--seed X` | 基本シード。省略時は時刻から生成し、いずれの場合も必ず表示する。 |
| `--game N` | 指定した局番号だけを実行する。異常局の単独再現に使う。 |
| `--rules R1,L1,P3` | 採用する規則コード列または検証済みプリセット名。`engine-default`はR1を表す。`parse_rule_set`で解決し、`Rules::from_codes`で検証する。必須とし、省略はエラーとする。 |
| `--max-ply N` | 1局の手数上限。到達した局は打ち切りとして別集計する。 |
| `--verify-all` | 毎手、全合法手を複製した対局へ適用して受理を全数検証する。 |
| `--verbose` | 各局の全手順を表示する。 |

`--max-ply`の既定値は4096とする。2026年8月10日の実測（実施状況の節参照）で、実測最大手数1,363の約3倍の余裕を持つことを確認して確定した。

### シード派生

各局の乱数状態は、基本シードと局番号をsplitmix64で混合して得る。
再現性を実装の細部でなく仕様として固定するため、派生式を次のとおり定める。
局番号`n`は1起算とし、表示・`--game`の指定とも同じ値を用いる。
派生値は`splitmix64(base_seed.wrapping_add(n))`とし、splitmix64は標準定数による有限混合（`z = x + 0x9E37_79B9_7F4A_7C15`、`z = (z ^ (z >> 30)) * 0xBF58_476D_1CE4_E5B9`、`z = (z ^ (z >> 27)) * 0x94D0_49BB_1331_11EB`、`z ^ (z >> 31)`。加算・乗算はすべてラッピング演算）とする。
派生値が0になる場合は固定の非ゼロ定数`0x9E37_79B9_7F4A_7C15`へ置き換え、XorShift64のシード0禁止と両立させる。
`--game`は`--games`と同時に指定できず、同時指定はエラーとする。
この設計により、同一の`--rules`（および既定値以外を使った場合は同一の`--max-ply`）の下で、`--seed X --game N`により当該局の着手列が完全に再現され、やねうら王記事の「同条件で再実行してブレークポイントを仕掛ける」手順がそのまま使える。規則セットは合法手集合と終局を変えるため、シードと局番号だけでは再現は完結しない。異常時ダンプには採用規則を含める（後述）。

### 対局ループと検証

1局は`Game::new`で構築し、`legal_moves()`から乱数で1手を選んで`play()`へ渡すループで進める。
終局（`GameStatus::Finished`）または手数上限で抜ける。

毎手、次の不変条件を検査する。

- `legal_moves()`が返した着手を`play()`が拒否しない。拒否は即座に異常とする。
- 着手後の局面が`Position::validate()`を通過する。
- `--verify-all`指定時は、全合法手をそれぞれ複製した`Game`へ適用し、すべて受理されることを確認する。

終局後は、`legal_moves()`が空を返すこと、および追加の`play()`が`GameError::GameAlreadyOver`を返すことを確認する。

### 異常時の出力

異常を検出した場合は、採用規則、基本シード、局番号、手数、問題の着手、直前局面のSFEN、および開始からの全手順を標準エラー出力へダンプし、非ゼロの終了コードで終了する。
着手の表記はperftの`move_text`と同じ形式とし、両ツールの出力を突き合わせられるようにする。

### 正常時の出力

正常時は1局ごとに局番号、手数、結果と終局理由を1行で出力する。
全局終了後に、勝敗と終局理由（`WinReason`および`DrawReason`の変種）別の局数、手数の最小・最大・平均、打ち切り局数、所要時間を集計として出力する。
終局理由の内訳から、駒枯れや反復裁定など特定の裁定パスが一度も踏まれていないことを観測でき、テストカバレッジの穴の発見に使う。
`--verbose`指定時は各局の全手順も表示する。

## 実装フェーズ

実装は、既存挙動を変えない分離と新規追加を混在させないように4フェーズへ分ける。
各フェーズはcodexへ委任し、レビューとコミットを分担する。
フェーズ1と3は依存がなく即時着手できる。
フェーズ2はプロトコル層フェーズ1のusi-lishogi調査の完了を前提とし、フェーズ4はダンプに`to_sfen`を使うためフェーズ2の後に実施する。

### フェーズ1　乱数モジュールの分離

XorShift64を`src/rng.rs`へ移し、`position.rs`と`invariants.rs`の重複を解消する。
Zobrist値と全テストの不変を確認する。

### フェーズ2　SFEN書き出し

`to_sfen`を実装し、ラウンドトリップテストを追加する。

### フェーズ3　Gameの複製

`Game`へ`Clone`を追加する。

### フェーズ4　バイナリ新設と文書更新

`random_play`バイナリを実装し、数百局の実測で`--max-ply`既定値を確定し、`docs/ROADMAP.md`を更新する。

## 検証

単体テストでは、次の性質を検査する。

- `parse_sfen(to_sfen(p))`が初期局面、成駒を含む局面、成り権保留を含む局面を復元する。
- 分離後のXorShift64が分離前と同じ乱数列を生成する（既存のZobrist整合テストの不変で兼ねる）。

ハーネス自体の検証は実行によって行う。

- `--seed`と`--game`（および同一の`--rules`）を固定した2回の実行が同一の手順と結果を出力する。
- 次の代表規則セットのそれぞれで数百局が異常なしで完走する。反復規則の3系統（R1、R2、R3の各単独指定）に加え、L、P、E系列の裁定パスを踏むため、`lishogi`、`L3,R1`、`P1,R1`、`P2,R1`、`P4,R1`、`E2,R1`を用いる。
- `--verify-all`を付けた少数局が完走する。

最終確認では、次のコマンドを実行する。

```console
cargo test
cargo clippy --all-targets
cargo fmt --all -- --check
git diff --check
cargo run --quiet --bin perft -- 4
cargo run --release --bin random_play -- --games 500 --seed 1 --rules engine-default
```

初期局面perftの深さ1から4までの自己回帰値`36`、`1,296`、`48,315`、`1,801,639`が変化しないことを確認する。

## 完了条件

次の条件をすべて満たした時点で、本マイルストーンを完了とする。

- XorShift64が`src/rng.rs`の単一実装になり、Zobrist値が変化していない。
- `to_sfen`がラウンドトリップテストとともに実装されている。
- `random_play`が本設計書のCLIと検証項目を備え、検証の節に定める代表規則セットのそれぞれで数百局を異常なしで完走する。
- 異常検出時のダンプから`--seed`と`--game`だけで当該局を再現できる。
- `--max-ply`の既定値が実測に基づいて確定している。
- 本節の検証コマンドがすべて成功する。
- `Cargo.toml`、`Cargo.lock`および`src/bin/perft.rs`にある既存のmimalloc実験差分を変更していない。

# 探索部の不具合修正の設計書

## 先に読む要約

本マイルストーンは、[探索部の不具合監査](../audits/search-bugs-2026-09-28.md)（以下「監査」）が挙げた指摘のうち、null moveをまたぐ反復の検出を修正し、修正後の探索がmasterより10 Elo規模で弱くなっていないことを自己対局で確かめてから取り込む。
null move pruningは、手番を仮に相手へ渡して浅く読む枝刈りである。その直後に相手がじっと（獅子が隣の升へ出て同じ手で元の升へ戻る手）を指すと、盤面が元に戻ったことを同一局面の反復として引き分けと判定していた。null moveは実際の対局に現れないので、この引き分けは実在しない。
修正は、反復の検出をnull moveより前の局面へ遡らせないことであり、Stockfishなどと同じ扱いである。
監査は、ほかに2件を修正の候補に挙げた。
1件は、読みの末端で捕獲手だけを読む静止探索の枝刈り（delta pruning）が、捕獲と同時に成る手の成り益を無視することである。修正を試したが、修正前の版がわずかに強い方向の結果（約+7 Elo、判定なし）となったので、利用者の決定により取り込まず、不具合として記録に残す。
もう1件は、王駒がすべて狙われている静止探索の局面で、何も指さずに現局面の評価値を確保できるとみなす下限（stand-pat）を使うことである。これは静止探索の近似の一例であり不具合ではないと分類し直し、対象から外した。全合法手を読む修正は約120 Elo弱かった。
null moveの件は探索の正しさの修正なので、利用者の決定により、採否は棋力の向上ではなく非劣性で判定する。
非劣性の判定は、masterを候補、修正のコミットを基準にした標準のGSPRT（勝敗から強さの差を逐次判定する統計検定、[棋力測定の手引き](../guides/sprt.md)）を、短時間と長時間の2条件で1回ずつ行う。どちらも「masterが10 Elo強い」という仮説が棄却されれば（判定`H0`）修正を採用する。
2026年9月29日に、null moveの件の修正が短時間と長時間の両条件で非劣性を通過し、採用してmasterへ統合した。

## 状態

完了（一部不採用）。2026年9月28日に起案して着手し、2026年9月29日に完了した。
null moveをまたぐ反復の修正は、非劣性のSTC（[search-bug-fixes-null-move-noninferiority-stc](../measurements/search-bug-fixes-null-move-noninferiority-stc.md)、masterの得点率45.7%）とLTC（[search-bug-fixes-null-move-noninferiority-ltc](../measurements/search-bug-fixes-null-move-noninferiority-ltc.md)、masterの得点率48.0%）でともに`H0`となり、採用してmasterへ統合した。
delta pruningの件の修正は、診断のSTCで修正前の版がわずかに強い方向の結果（[search-bug-fixes-delta-promotion-diag-stc](../measurements/search-bug-fixes-delta-promotion-diag-stc.md)、判定なし）となり、利用者の決定により取り込まなかった。
stand-patの件の修正は、3件を積んだ組の非劣性のSTC（[search-bug-fixes-noninferiority-stc](../measurements/search-bug-fixes-noninferiority-stc.md)）の不合格の主因であり（[search-bug-fixes-qsearch-evasion-diag-stc](../measurements/search-bug-fixes-qsearch-evasion-diag-stc.md)）、不具合ではなく静止探索の近似と分類し直して対象から外した。

## 目的

監査は、null moveの件について、`bench`（15局面を固定深さで探索し、総ノード数を出力する実行ファイル）の深さ9でnull moveをまたぐ反復が1,986件あり、これを反復と扱わないだけで総ノード数が8.0%減ることを示した。
本マイルストーンは、これを直して反復の検出が返す値の正しさを回復する。
棋力の向上は目的に含めないが、修正が棋力を10 Elo規模で下げていないことは測定で確かめる。

## 適用範囲

対象は`src/search/alphabeta/`の`negamax.rs`と`searcher.rs`、および関係するテストである。
合法手生成、評価関数、および対局管理層は変更しない。

監査の指摘のうち、本計画で扱わないものと理由は次のとおりである。

- delta pruningの件は、修正を測定したうえで取り込まない（設計判断の「delta pruningの件の扱い」）。不具合は残る。
- stand-patの件は、不具合ではなく静止探索の近似として扱う（設計判断の「不具合の判定基準」）。
- 静止探索が合法手のない局面の負け（RULES.md第23条）を検出しない件は、中将棋でこの局面がほとんど現れず、全静止探索ノードで合法手を生成する費用に見合わないので扱わない。
- 置換表の詰みの値が深い位置で詰みの帯から外れ得る件は、実際の探索深さで起こらないので扱わない。
- 置換表を通じた反復の値の漏れと、反復規則を探索の木の中で引き分けとして扱う近似は、[探索内の反復負け回避](search-repetition.md)の範囲なので扱わない。

## 依存関係

基準は監査の基準コミット（masterの先頭）である。
[探索内の反復負け回避](search-repetition.md)は起案の状態であり、同書は「null moveを含む手順で局面が再現した場合は引き分けとする」ことを前提にしている。
本書の修正はこの前提を「null moveより前の局面の再現は反復として検出しない」に変えるので、採用した場合は同書の記述を書き直す（検証の節）。

## 設計判断

| 判断事項 | 採った方式と理由 |
|---|---|
| 不具合の判定基準 | 不具合とは、実装がその手法自身の契約に反し、契約上起こらないはずの値を返すことをいう。反復検出の契約は「対局上の同一局面の再現を引き分けとする」ことであり、実際の対局に現れないnull moveを挟んだ再現を引き分けとするのは、これに反する。delta pruningの契約は「最善の場合でもαに届かない捕獲だけを省く」ことであり、成り益を無視するとαに届く捕獲まで省くので、これも不具合である。一方、stand-patは「現局面の評価値を下回らない手がある」とみなす楽観的な近似であり、王駒が詰んでいる局面での誤りは、両取りのように避けられない脅威すべてに共通する誤りの一例である。監査の再現例で深さ1が詰みを見落とし深さ2で見つけたのも、固定深さの探索に伴う地平線効果である。したがって、stand-patの件は不具合ではなく近似の限界であり、変えるなら通常の段階ゲート（+10 Eloの向上を要求するSTCとLTC）で判定すべき探索の改良である。王駒がすべて狙われた静止探索の局面で全合法手を読む方式は、親コミットに対する診断のSTCで約120 Elo弱かった（[search-bug-fixes-qsearch-evasion-diag-stc](../measurements/search-bug-fixes-qsearch-evasion-diag-stc.md)）。 |
| delta pruningの件の扱い | 取る駒の価値と成り益の和で捕獲を判定する修正（成り益はSEE、すなわち到達升での駒の取り合いの見積りと同じ計算）を実装し、親コミットと比べる診断のSTCを行った。3,000ペアの上限で判定に達せず、親の得点率は51.0%（約+7 Elo）、LLRは0.93で、修正前の版がわずかに強い方向の証拠が残った。利用者の決定により、この修正は取り込まない。修正により静止探索の候補が増える費用が、成りの読み落としを減らす利益を上回った可能性がある。この件を再び扱う場合は、棋力を下げない判定方式を別の計画で探す。 |
| 採否の判定 | 利用者の決定により非劣性で判定する。null moveの件は探索が返す値の誤りの修正であり、棋力に中立でも取り込む価値がある。通常の段階ゲートは+10 Eloの向上（`H1`）を要求するので、中立の修正は不採用となり不具合が残る。非劣性は、ハーネスへ比較のスイッチを足さずに、候補と基準を入れ替えた標準のGSPRTで判定する。masterを候補、修正のコミットを基準にすると、修正から見た比較点は0 Eloと−10 Eloになる。判定が`H0`なら「masterが10 Elo強い」が棄却され、10 Eloを非劣性の限界とする測定を通過したとして採用する。`H1`なら不採用とする。`H0`は10 Elo未満の小さな低下までは否定しない。この入れ替えは[持ち時間の効率的な使用](time-management-efficiency.md)の非劣性の測定と同じ手続きである。 |
| 測定の単位と回数 | 採否を決める検定は、修正のコミットとmasterの1組を、短時間（STC）と長時間（LTC）で1回ずつとする。当初は3件の修正を積んだ1組を測り、不合格となった後に各コミットをその親と比べる診断のSTCで原因を調べた。診断は採否を決めず、修正を外す判断はいずれも本書の改訂として利用者が決めた。null moveの件の修正の親はmasterなので、その診断は本書の非劣性のSTCと同じ比較になり、別には行わない。同じ候補を別のシードで再試行することはしない。 |
| null moveの件の検出範囲 | 探索ワーカーは、直近のnull moveを適用した時点の探索経路の長さを境界として保持する。null moveを適用したら、null move直後の局面の局面キーを探索経路へ積む。この局面キー自体では反復を判定しない。null moveの部分木の中では、境界以降に積んだ局面キー（null move直後の局面を含む）との一致だけを反復とし、境界より前の探索経路と対局履歴は参照しない。null moveの外では現行どおり、対局履歴と探索経路の全体を参照する。null move直後の局面を積むのは、部分木の中で双方がじっとを指してnull move直後の局面へ戻る手順が、null moveを含まない本物の反復だからである。Stockfishは反復の検出を直前のnull moveまでに限り、ElephantEyeも遡りをnull moveで止める（[反復の先行実装の調査](../research/search-repetition-prior-art.md)）。null moveが入れ子になる場合は内側のnull moveの境界を使い、部分木から戻るとき（中断による戻りを含む）に探索経路と外側の境界を元に戻す。 |

## 測定の所要時間

これまでの実績（同時対局数16）では、STC（`time=10000+100`）が1ペアあたり約9.5秒、LTC（`time=60000+200`）が約27秒であった。
真の差が0に近い場合、非劣性の判定までの期待ペア数は[棋力測定の手引き](../guides/sprt.md)の近似式で約2,600ペアである。
したがって、STCは約7時間、LTCは約20時間を見込む。
LLR（対数尤度比。GSPRTが判定に使う統計量）は、差が大きいほど速く境界に達するので、大きな差があれば測定は短く終わる。
LTCへ進む前に、STCの結果とこの見積りを利用者へ示して進め方を確認する。

## 実装フェーズ

### フェーズ1　null moveをまたぐ反復の修正（完了）

設計判断の「null moveの件の検出範囲」を実装した。
null moveの直後に相手がじっとを指してnull moveの前の局面へ戻る場合は引き分けとしないこと、部分木の中で双方がじっとを指してnull move直後の局面へ戻る場合は引き分けとすること、null moveの外の反復検出が変わらないこと、および入れ子のnull moveから戻る場合と中断した場合に探索経路と境界が元に戻ることを、テストで固定した。
`bench`の深さ9の総ノード数は16,519,597から15,195,794へ8.0%減った（[search-bug-fixes-bench](../measurements/search-bug-fixes-bench.md)）。

### フェーズ2　非劣性の測定（完了）

null moveの件の修正を加えたコミットを修正のコミットとし、監査の基準コミットと比べる。
3件を積んだ最初の組の測定と診断は、状態の節に挙げた測定記録に残してある。
STCの標準コマンドに対して候補と基準を入れ替え、次のとおり実行する。

```console
data/worktrees/search-bug-fixes-runner/target/release/match_runner \
  --run-dir data/matches/search-bug-fixes-null-move-noninferiority-stc --seed 83200000 \
  --candidate commit:<基準コミット> --baseline commit:<修正のコミット> \
  --concurrency 16 --each time=10000+100 gsprt --max-pairs 3000
```

STCが`H0`ならLTCへ進み、`H1`なら不合格とする。
上限3,000ペアに達した`pending`は、停止時点のLLRが負ならLTCへ進み、0以上なら不合格とする。
LTCは次のとおり実行し、`H0`なら採用、`H1`なら不合格とし、`pending`なら同じ実行ディレクトリを`--resume`で再開して`--max-pairs`だけを増やす。

```console
data/worktrees/search-bug-fixes-runner/target/release/match_runner \
  --run-dir data/matches/search-bug-fixes-null-move-noninferiority-ltc --seed 83300000 \
  --candidate commit:<基準コミット> --baseline commit:<修正のコミット> \
  --concurrency 16 --each time=60000+200 gsprt
```

`match_runner`は、測定中にmasterが進んでも再開できるよう、監査の基準コミットに固定したworktreeでビルドしたものを使う。
いずれの測定も、エンジン異常、時間切れ、および拒否着手が0件であることを採用の条件に含める。
シードは既存の測定で使われていない値であり、STCとLTCは上限ペア数以上離してある。
不合格となった場合は、採否の判定を終えて利用者へ報告する。

## 検証

- フェーズ1に挙げたテストが通る。
- `cargo test`、`cargo clippy --all-targets`、`cargo fmt --check`が通る。
- 修正は探索の挙動を変えるので、`bench`の総ノード数の不変は採否の条件にしない。
- [探索部の設計書](search.md)の「静止探索」節には、王手中のstand-patが他の脅威を無視するのと同じ種類の近似であることと、全合法手を読む方式が測定で約120 Elo弱かったことを記した。
- [探索部の設計書](search.md)の「探索内の終局と規則処理」節の反復の記述と、[探索内の反復負け回避](search-repetition.md)の「周回の区間と攻撃側の判定」の行および検証の節を、null moveより前の局面の再現は反復として検出しないという記述へ改めた。

## 完了条件

- 修正がテストで固定されている。
- 非劣性の測定記録（STCとLTC、および3件の組の測定と診断）が残り、採否が本書の状態の節に記録されている。
- 採用した場合は修正がmasterへ統合され、関係する設計書が修正後の挙動と一致している。不採用の場合は修正がmasterへ入っていない。

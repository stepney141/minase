# 探索の関数形の見直しの統括計画

## 先に読む要約

本計画は、minaseの探索と時間管理の式をチェスのStockfishと将棋のYaneuraOu（やねうら王）の形へ寄せる7本の設計書（依存関係の節の表に挙げる）をサブタスクとして束ね、実行の順序、7本に共通する調整の実行環境、および全体の完了条件を定める。
7本はそれぞれ、式の形を変える実装をしたうえで、その時点の全係数をSPSA（simultaneous perturbation stochastic approximation、全係数を同時に少しずらした2つの設定を対局させて係数を動かす調整法）で30,000ペア調整する。
2026年10月18日の利用者の決定により、各サブタスクは対局の結果によらず採用し、短時間条件STCの逐次検定を強さの変化の記録として残す。7本を通して強くなったかは、最後に長時間条件LTCの逐次検定で、本計画を始める前のmasterと比べて確かめる。
SPSAはこれまで、開発と棋力測定に使う手元の機械（以下、測定機）で、STCと同じ持ち時間10秒＋0.1秒の対局により行ってきた。
30,000ペアのSPSAは測定機で1本あたり約75時間かかり、7本のSPSAだけで約22日、段階ゲートを含めると約1か月、測定機を占有する。
本計画では、SPSAを、計算機を時間単位で借りられる市場vast.aiで借りる物理コアの多い計算機（以下、調整機）で実行し、1本あたりの所要時間を、物理192コアの機械で約13〜18時間に縮める。
調整機は、CPUの世代ではなく、実測した機械全体の速さと時間単価から見込む1回の費用で選ぶ。
調整機のサーバー向けCPUは多数のコアを低いクロックで動かすので、1コアは測定機より遅く、同じ持ち時間では1手に読む局面の数が減り、浅い探索に合う係数を選ぶおそれがある。
そこで、Stockfishの分散テスト基盤fishtestと同じく、同時対局数と同じ本数の速度計測を両機で走らせ、その速度の比を持ち時間に掛けて、1手あたりの探索量を測定機のSTCとそろえる。
SPSAの結果の反映は測定機で行い、事前対局とSTC、および最後の通しのLTCは調整機で、それぞれ持ち時間を換算せずに行う。
この分担は2026年10月18日に利用者が決めた。これらの対局で知りたいのは候補が起点より強いかどうかなので、測定機との速さと持ち時間の違いは考慮しない。
完了条件は、試走で持ち時間の換算を確かめ、中断と再開を含む検証を通した手順が手引きにまとまり、7本のサブタスクがそれぞれの設計書の完了条件に従って完了することである。

## 目的

第一の目的は、7本のサブタスクのSPSAを、測定機を占有せずに、測定機の数分の1の時間で終えることである。
第二の目的は、調整機で選んだ係数が測定機のSTCで選んだ係数と同じ条件の結果とみなせるように、1手あたりの探索量をそろえることである。
SPSAの対局はこれまで測定機のSTCの持ち時間で行ってきたので、1手あたりの探索量をそろえれば、調整機で選んだ係数を、これまでのSPSAと同じ条件で選んだ係数として扱える。
第三の目的は、7本を同じ手順で順に進め、全体の進み具合を1か所で追えるようにすることである。

## 適用範囲

本計画の用語を次のように定める。

- **測定機**は、Intel Core Ultra 7 265KFを積んだ手元の機械であり、高性能のPコア8個と省電力のEコア12個の物理20コアを持つ。lishogiのBotと共用するので、SPSAと段階ゲートの同時対局数は16を上限とし、Botは止めない。[vast.aiでの教師生成](vast-selfplay.md)では同じ機械を作業機と呼ぶ。
- **調整機**は、SPSAの1セッション、それに続く事前対局とSTC、およびフェーズ10のLTCのためにvast.aiで借りる計算機である。
- **負荷時の速度**は、同時対局数と同じ本数の`minase dev bench`を同時に走らせたときの、1本あたりの探索速度（1秒あたりのノード数、NPS）の平均である。
- **換算係数**`f`は、測定機の同時対局数16での負荷時の速度を、調整機の同時対局数での負荷時の速度で割った値である。
- **調整用ビルド**は、`--features tuning`を付けてビルドしたminaseであり、SPSAの対局はこのビルドで行う（[SPSAの手引き](../guides/spsa.md)の用語）。両機は、同じコミットをそれぞれの機械でビルドする。
- **時間切れの事前確認**は、SPSAの本番の前に、時間管理の係数を思考時間が最も長くなる側の範囲の端に置いた短いSPSAを、本番と同じ持ち時間と同時対局数で回し、時間切れが0件であることを確かめる手順である（[SPSAの手引き](../guides/spsa.md)の第3節）。7本はいずれも時間管理の係数を調整の対象に含むので、この手順を持つ。
- **事前対局**は、SPSAの結果を反映した候補と起点を、STCの前にSTCと同じ持ち時間で短く対局させ、時間切れと時間の使い方を確かめる手順である。

本計画が扱うのは、依存関係の節に挙げる7本のサブタスクの実行順序と、各サブタスクのうちSPSAに関わる2つの手順（時間切れの事前確認とSPSAのセッション）および採否のための対局測定の実行環境である。
調整機の調達、持ち時間の換算、セッションの起動、調整機から測定機への実行ディレクトリとログの取得、中断後の再開、および費用の上限を実装の対象とする。

各サブタスクの式の形、係数、開始値と範囲、シード、および事前対局は、各設計書が定める。
採否の決め方は、2026年10月18日の利用者の決定により本計画が定め、各設計書の段階ゲートの規則に優先する（設計判断の「各サブタスクの採否」）。
各サブタスクの対局（事前対局、STC、および秒読みつきの確認）は、SPSAを終えた同じ調整機で、各設計書の時間制御を換算せずに、SPSAと同じ同時対局数`c`で行う。
SPSAの更新則、30,000ペアの規模、および`minase spsa`のコードは変えない。
教師生成をvast.aiへ移すことは[vast.aiでの教師生成](vast-selfplay.md)が扱い、本計画の対象外とする。

### サブタスク間の依存

サブタスクの間には2種類の依存がある。
1つ目は、すべてのサブタスクの間にある順序の依存である。

この依存は連鎖を組んだことから生じるものであり、コードの依存ではない。

前のサブタスクが不採用で、使う仕組みが起点にない場合の扱いは、各設計書が定めている。
多くの場合は、後のサブタスクが同じ仕組みを探索を変えない移行として自分で入れる。
たとえば、2はF0が起点になければフェーズ1の最初に同じ移行を行い、3は2の王手の判定がなければ自分で導入し、7は6のM2がなければ同じ定義で導入してT7の式からA5の項を除く。
例外は4である。1が不採用だと補正量を入れる先が広がらず、4の効果が小さくなるので、4の設計書はこの場合に着手するかを利用者が決めると定めている。

順序は、1から5の間では後ろが前の仕組みを使うので、表の順に進めるのが自然である。
6と7の組は1から5に依存しないので、7を6の後に置くことを守れば、組ごと1の前や1から5の間へ移せる。
移す場合は、各設計書の「状態」と依存関係の節が名指しする1つ前の設計書を、着手の前に書き換える。基本シードの予約は設計書ごとに重ならない範囲なので、順序を変えても書き換えなくてよい。

## 調整機でのSPSA

### 持ち時間の換算

換算係数は、セッションの開始時に次の手順で決める。

1. 測定機で、調整対象のコミットの調整用ビルドを16本同時に`minase dev bench --depth 9 --repetitions 3`で走らせ、16本のNPSの平均を測定機の負荷時の速度とする。`dev bench`は固定の15局面を固定の深さで探索する速度計測であり、深さ9は1本が数秒で終わる深さである。測定の間は、ほかの対局測定、SPSA、教師生成、および学習を止める。Botは止めない。測定機でのSPSAも、Botと共用した状態で行ってきたからである。
2. 調整機で、同じコミットの調整用ビルドを同時対局数と同じ本数だけ同時に走らせ、同じく平均を調整機の負荷時の速度とする。
3. `f`は測定機の値を調整機の値で割った比とし、小数第2位に丸める。持ち時間は`time=<10000×f>+<100×f>`（ミリ秒、整数に丸める）とする。たとえば`f`が2.31なら`time=23100+231`である。

教師生成の試走の値から見積もると、EPYC 9654の2基構成で同時に192局を探索したときの全体の速度は約1億NPS、1スレッドあたりでは約52万NPSである。
測定機の同時16局での値は測っていない。Pコア1本だけのbenchは約145万〜148万NPSであり（[記録](../measurements/nnue-hidden-layer/nnue-hidden-layer-bench.md)）、16局のうち8局はEコアで動き、全コアの負荷でクロックも下がるので、平均は下がる。下限は仮にPコア単独の約7割の約105万NPSと置き、約105万〜145万NPSと見込む。
したがって`f`は約2.0〜2.8である。
SPSAでは1局の時間が持ち時間で決まるので、同時対局数を`c`とすると、調整機の処理量は測定機の`c ÷ (16 × f)`倍、セッションの所要時間は約`75 × 16 × f ÷ c`時間になる。
EPYC 9654の2基構成で`c`が191なら、処理量は約4.3〜6.0倍、所要時間は約13〜18時間である。

起案時のminaseが各手に割り当てる思考時間の予算は、残り時間と加算に係数の比を掛けて決まり、固定の値は安全余裕の30 msだけである（`crates/minase/src/search/alphabeta/time.rs`の`clock_budget_with_margin`）。
このため、持ち時間を一様に伸ばしても、時間管理の係数の働きはほぼ変わらない。
例外は、[持ち時間の伸縮](time-instability-scaling.md)が加える、合法手が1つの局面で目安の思考時間（soft）を500 msに抑える上限であり、この上限は換算されない。同書はこの上限が働くことはまれと見込んでいるので、そのセッションの記録で発動の件数を確かめる。
一方、安全余裕と、対局を進める審判のプロセスとエンジンの間で1手ごとに生じる通信の遅れは伸びないので、持ち時間に対する割合は測定機の1/`f`になり、調整機の対局がわずかに有利になる。
fishtestも同じ近似で持ち時間を伸ばしている。

### 同時対局数とメモリ

同時対局数`c`は、調整機の物理コア数とメモリの両方から決める。
`minase spsa`は、先後を入れ替えた1ペアの2局を順に指すので、同時に動く局の数は同時対局数に等しく、1局につき2つのエンジンのプロセスが置換表を確保する。
測定機の記録では1局あたりの最大常駐メモリは約613 MBであり（[記録](../measurements/strength-stage8/strength-stage8-elo200.md)）、同時191局で約117 GBになる。
サブタスクが進むと、1局あたりのメモリは増える。たとえば[historyの形](archived/history-forms.md)はエンジン1つあたり約157 MB、[correction historyの表](archived/correction-history-tables.md)は約37 MBを加えるので、両方を採用した後の1局は約1.0 GB、同時191局で約191 GBになる。
このため、メモリの条件は固定の値にせず、セッションごとに決める。
セッションの準備で、測定機で調整対象のコミットの調整用ビルド同士の1ペアをSTCで指し、各局の記録の`candidate_peak_rss_bytes`と`baseline_peak_rss_bytes`の和を求め、2局のうち大きい方の値を1局あたりの最大常駐メモリとする。
同時対局数`c`は、物理コア数から1を引いた数と、調整機の実メモリをこの値の1.25倍で割って切り捨てた数の小さい方とする。1.25倍は、OSとrunnerのための余裕である。
`remote.py`は、物理コア数を`lscpu`で、実メモリをコンテナのメモリの上限（cgroup）と`/proc/meminfo`の小さい方で求める。
起案時のmasterでは、物理192コアの機械でメモリの制限を受けずに`c`を191にするには約146 GBが要る。

### 選定条件

調整機の候補は、`vastai search offers`で次の条件をすべて満たすオンデマンドの出品とする。
条件のうち、`gpu_frac`が1で`cpu_cores_effective`が`cpu_cores`と等しいこと、検証済みで信頼度`reliability`が0.95以上であること、直接接続のポートを持つこと、送信速度`inet_up`が100 Mbps以上であること、およびディスクが50 GB以上であることは、[vast.aiでの教師生成](vast-selfplay.md)の選定条件と同じである。

- CPUのアーキテクチャ`cpu_arch`がx86-64である。テストと測定を行ってきた環境と同じにするためであり、CPUの世代と命令セットは問わない。エンジンはSIMDの組込み命令を直接使わず、`target-cpu=native`でビルドした機械の命令に合わせるからである。
- スレッド数`cpu_cores`が192以上である。SMTを持つCPUでは物理96コア以上に当たり、物理コアの少ない機械を試す手間を省くための足切りである。物理コア数は出品の情報にないので、借りた後に`lscpu`で確かめる。
- 貸出期限までの日数`duration`が2日以上である。`duration`は貸し手が決めた、その機械を借りていられる最長の期間であり、課金は実際に借りている時間の分だけである。1セッションは長ければ24時間かかるので、再開に備えて余裕を持たせる。

候補は、見込みの1回の費用の安い順に試す。
セッションの記録に速さのあるCPU型は、記録の負荷時の速度と前節の`c`から見込む所要時間に、時間単価を掛けた値を見込みの費用とする。
記録のないCPU型は、所要時間を上限の24時間と仮に置いた値を見込みの費用とする。速さを知らない機械は、最も遅い場合でも上限で止まるからである。
借りた機械の開始時の実測で所要時間の見込みが24時間を超えた場合は、本番を始めずに削除し、そのCPU型の速さを記録してから次の候補を試す。
1台を試して削除するまでの費用は、ビルドと速度の測定の約15分の分である。

2026年10月17日に照会した、96スレッド以上の検証済みの出品74件では、候補の状況は次のとおりだった。
EPYC 9654の2基構成（物理192コア、メモリ126 GB、1時間1.01米ドル）は、メモリの制限で`c`が起案時のmasterで約164、historyの表とcorrection historyの表を採用した後は約100になる。
EPYC 9K84の2基構成（物理192コア、メモリ755 GB、1時間1.87米ドル）は、メモリの制限を受けない。
EPYC 7K62の2基構成（Zen 2、物理96コア、1時間0.86米ドル）は安いが、物理コアの数と1コアの速さから見て、所要時間が上限を超える見込みが高い。
EPYC 7763などの1基構成やThreadripper PRO 5995WX（Zen 3、物理64コア、1時間0.62〜1.00米ドル）は128スレッドなので、スレッド数の足切りで候補から外れる。
物理256コアのEPYC 9754の2基構成（1時間8.54米ドル）やZen 5の技術評価用サンプル（512スレッド、1時間13.1米ドル）は速いと見込まれるが、GPU 8枚と一緒に貸されるので、1回の費用は物理192コアの機械の3倍以上になる。
出品は貸し手の都合で入れ替わり、価格も変わるので、選定はセッションごとに照会し直して行う。

### 実行の構成

セッションごとに、測定機の`data/vast-spsa/<セッション名>/`に次の配置で置く。
セッション名は、各設計書のSPSAの実行ディレクトリ名と同じにする（たとえば`search-pruning-forms`）。

| パス | 内容 |
|---|---|
| `session.toml` | 調整対象のコミット、`minase spsa`を実行するrunnerのコミット、基本シード、反復数、1反復のペア数、規則、時間切れの事前確認の要否と基本シード、測定機の負荷時の速度、および1局あたりの最大常駐メモリを、TOMLのキーと値の組として1行ずつ書く。 |
| `params`と`safety.params` | 各設計書が定めるパラメーターファイルと、その写しの時間管理の係数を範囲の端に置いた時間切れの事前確認用のファイル。 |
| `incoming/` | 調整機の実行ディレクトリを取得する場所。転送の途中のファイルを含み得る。 |
| `run/` | 適用番号の連続を確かめた再開用の写し。`incoming/`の各ファイルへのハードリンクであり、内容を複製しない。セッションの終了後は、各設計書の`data/spsa/<セッション名>`へ移して`apply`に使う。 |
| `safety/` | 時間切れの事前確認の実行ディレクトリの写し。 |
| `logs/` | ビルド、負荷時の速度、換算した持ち時間、`minase spsa`の標準出力、および終了コードの記録の写し。 |
| `deadline` | 現在の調整機の停止の期限（UNIX時刻）。`launch.py`が書き、`fetch.py`が自己停止の失敗を見つけるために読む。 |

時間切れの事前確認の反復数は、`13 × 同時対局数 ÷ 16`を切り上げた数（同時対局数191なら156反復、1,248ペア、約35分）とする。
同時対局数と同じ数のペアが一通り入れ替わるまでを1巡と呼ぶと、SPSAの手引きの13反復（104ペア）は、同時対局数16で6.5巡に当たり、対局の枠が埋まった状態を長く続ける。
調整機で13反復を回すと同時対局数の半分しか埋まらず、セッションより軽い負荷で時間切れを確かめることになるので、巡の数を手引きにそろえる。

### 操作の入口

スクリプトは`scripts/vast-spsa/`に置く。

| 操作 | 内容 |
|---|---|
| `launch.py` | 測定機で実行する。引数はセッション名、出品のID、および期限までの分数である。期限までの分数は、SPSAの所要時間の見積もりの上限に1.3を掛け、ビルド、速度の測定、および事前確認の45分を足した値とする（18時間なら1,449分）。1.3倍は、教師生成の設計書の期限と同じ余裕である。`session.toml`と、出品が選定条件を満たすことを検査し、同じセッション名のラベルを持つ調整機があれば止まる。`git bundle`、パラメーターファイル、`remote.py`、および再開の場合は`run/`を送ってから、開始の印となる空ファイル`started`を作る。 |
| `remote.py` | 調整機で、起動時スクリプトから呼ばれる。bundleからcloneして、`minase spsa`を実行する通常のビルド（以下、runner）と調整用ビルドを作る。runnerは`session.toml`で指定したrunnerのコミットからビルドする。調整対象のコミットが、再開時にビルドし直しを受け入れる`minase spsa`の変更より前のことがあるからである。再開の場合も、その機械で調整用ビルドを作り直す。続いて、物理コア数と実メモリから同時対局数`c`を決め、負荷時の速度を測って`f`と持ち時間と所要時間の見込みを求め、`logs/`に記録する。所要時間の見込みが24時間を超えれば、ここで0以外の終了コードで止まる。超えなければ、時間切れの事前確認とSPSAのセッションを順に実行する。事前確認の全反復が完了しなかった場合と、最終要約の`engine_failures:`行の件数（不正着手、クラッシュ、応答期限超過、時間切れ、および拒否着手）が1件でもあった場合は、セッションを始めずに0以外の終了コードで止まる。`minase spsa`は異常があっても終了コード0で終わるので、終了コードでは判定しない。実行ディレクトリがすでにあれば、`f`を決め直さずに`--resume`で再開する。持ち時間は実行ディレクトリの記録から読まれる。再開した調整機の負荷時の速度は記録に残すが、最初の記録とは照合しない。 |
| `fetch.py` | 測定機で実行する。10分ごとに実行ディレクトリを`incoming/`へ、ログを`logs/`へ取得し（動いている調整機からはSSHを通したrsync、停止した調整機からは`vastai copy`）、適用番号が1から連続していれば`run/`を更新する。終了コードが0で全反復がそろったら、調整対象のコミットの`params.rs`の一時的な写しに`minase spsa apply`（最終値を係数の表の既定値へ書き込むコマンド）を実行して記録の連鎖を検査し、通れば調整機を削除する。所要時間の見込みが上限を超えて`remote.py`が止まった場合は、ログを取得してから調整機を削除する。 |

再開時に負荷時の速度を照合しないのは、2026年10月18日の利用者の判断による。SPSAは係数の最適化であり、調整機の速さの違いで1手あたりの探索量が少しずれても、強さは対局で確かめるので、そのずれには厳密にこだわらない。

## 所要時間と費用

SPSAのセッションは、測定機の同時対局数16で3,000ペアに27,138秒かかった記録（[セッションの記録](../measurements/spsa-gain-calibration/spsa-stage9-20260925-c5.md)）から、測定機では30,000ペアで約75時間かかる。
調整機では、EPYC 9654またはEPYC 9K84の2基構成で`c`を191とすると約13〜18時間と見込み、ビルド、負荷時の速度の測定、および時間切れの事前確認に約45分を加える。
1時間1.87米ドルのEPYC 9K84の2基構成では、1セッションの費用は約25〜35米ドル、7本で約175〜245米ドルになる。
1時間1.01米ドルのEPYC 9654の2基構成は、メモリの制限で`c`が下がる分だけ所要時間が延びるが、`c`が約164なら1セッションは約15〜21時間、約16〜22米ドルと見込まれる。
フェーズ0の試走は約3時間（約6米ドル）、フェーズ1の検証は少ないコアの安い機械で約2米ドルと見込む。

1つのサブタスクは、実装に半日〜2日、調整機での事前確認とSPSAに約13〜18時間、測定機での反映とテストに約1時間、調整機での事前対局に数分、STCに約0.2〜1.3時間を要する。
STCとフェーズ10のLTCの時間は、測定機の段階ゲートの記録（[STC](../measurements/strength-stage8/strength-stage8-see-capture-stc.md)は同時対局数16で1ペアあたり約151秒、[LTC](../measurements/strength-stage8/strength-stage8-see-capture-ltc.md)は約431秒）を同時対局数95へ割り戻し、STCは400〜3,000ペア、LTCは950〜4,200ペアで判定すると見込んだ値である。持ち時間は換算しないので、1局の時間は測定機とほぼ同じになる。
測定機の占有は反映とテストの約1時間だけであり、調整機はその間も止めずに待たせる。事前対局、STC、および待ち時間の費用は、1時間1.29米ドルの機械で1本あたり約2〜3米ドルである。フェーズ10のLTCは1回だけで、約1〜5時間、約2〜7米ドルである。
持ち時間の伸縮のサブタスクは、秒読みつきの時計での確認に、測定機の見積りの約3〜58時間を同時対局数95へ割り戻した約0.5〜10時間を加える。

## 記録

各セッションの記録は、[SPSAの手引き](../guides/spsa.md)の第6節の項目に加えて、次を含める。

- 出品のIDと機械のID、CPU型、物理コア数とスレッド数、`cpu_ram`、時間単価、および費用の合計。
- 所要時間の見込みが上限を超えて削除した機械があれば、その出品とCPU型、`c`、負荷時の速度、および見込みの所要時間。次の選定で、そのCPU型の見込みの費用に使う。
- 測定機と調整機の負荷時の速度、`f`、換算した持ち時間、および同時対局数。
- 時間切れの事前確認の`time_forfeits`。
- 調整機を作り直して再開した場合は、その回数、各調整機の記録、および失った反復の数。

調整機で行った事前対局、STC、およびLTCの記録には、[SPRTの手引き](../guides/sprt.md)の並列測定の項目に加えて、vast.aiの調整機であること、出品とCPU型、およびその機械の`f`（測定機との1コアの速さの比）を書く。測定機で行った過去の段階ゲートと条件を比べられるようにするためである。

## 実装フェーズ

### フェーズ0　試走と持ち時間の換算の確定

選定の規則に従って候補を試し、所要時間の見込みが上限に収まった最初の調整機を約3時間借りて、現行のmasterで次を測る。以下では、その調整機の同時対局数を`c`と書く。
スクリプトはまだないので、[試走の記録](../measurements/vast-selfplay/vast-selfplay-trial.md)と同じく、SSHで接続して手作業で実行する。

1. 測定機と調整機の負荷時の速度を、それぞれ3回ずつ測り、`f`と繰り返しのばらつきを求める。
2. 同じ基本シード5,600,000,000で、現行のmasterの調整用ビルド同士を`minase match run`で対局させる。測定機ではSTCと同時対局数16で`c`ペア、調整機では換算した持ち時間と同時対局数`c`で`2c`ペアを指す。調整用ビルドは、各機で負荷時の速度の測定に使った実行ファイルを、起動コマンドの形式（`"<パス> --protocol usi --rules engine-default"`）で両側に指定する。`commit:`の形式は通常のビルドを作るので使わない。同じシードを使い、同じ開始局面で両機の探索の深さを比べる。調整機で2巡分を指せば、ペア番号1〜`c`の対局は対局の枠が埋まった負荷の下で指される。
3. 両機のペア番号1〜`c`の記録から、`scripts/clock_profile.py`で手数帯ごとの平均到達深さを、記録の`candidate_peak_rss_bytes`と`baseline_peak_rss_bytes`から1局あたりの最大常駐メモリを集計する。
4. 調整機で、`minase spsa params`が現行のmasterから生成した既定のパラメーターファイルを使い、換算した持ち時間と同時対局数`c`による時間切れの事前確認と同じ反復数（`c`が191なら156反復）のSPSA（基本シード5,700,000,000）を回して、時間切れとエンジン異常が0件であることを確かめる。

完了条件は、`f`の測り方、メモリの条件、および所要時間と費用の見積もりが実測に基づいて確定し、両機の手数帯ごとの平均到達深さの差が記録されていることである。
深さの差の合否の基準は、事前に根拠を持って決められないので置かない。差を利用者に示し、`f`の測り方を見直すかを利用者が決めてから次のフェーズへ進む。
結果は測定記録`vast-spsa-trial`に残す。

### フェーズ1　スクリプトの実装と検証

`scripts/vast-spsa/`の3つのスクリプトと、[vast.aiでの教師生成](vast-selfplay.md)のスクリプトと共通する処理を置く`scripts/vast/common.py`を実装する。
あわせて、`minase spsa --resume`が、`commit:`の形式の調整対象についてはコミットのハッシュの一致で再開を認め、ビルドし直した実行ファイルを受け入れるように改める。
そのうえで、選定条件を満たす出品のうち最も安い機械で、2反復程度の小さいセッションを使って「検証」の全条件を通す。
完了条件は、「検証」の全条件を通すことである。

### フェーズ2　手引きとADR

[SPSAの手引き](../guides/spsa.md)に、調整機で実行する手順（準備、起動、取得、再開、費用の確認、および片付け）を加え、第4節の同時対局数16の記述を測定機の場合に限る。
持ち時間を負荷時の速度の比で換算して借りた計算機でSPSAを行う方式を、ADRに記録する。
完了条件は、手引きとADRがmasterへ入ることである。

### フェーズ3〜9　サブタスク1〜7

依存関係の表の順に、各設計書の実装フェーズを進める。
時間切れの事前確認とSPSAのセッションは、手引きの調整機の手順で実行し、事前対局とSTCは同じ調整機で行う。採否は設計判断の「各サブタスクの採否」により、各設計書の段階ゲートの規則によらない。それ以外のフェーズは各設計書のとおり測定機で行う。
各サブタスクの完了は、その設計書の完了条件による。
サブタスクを始める前に、利用者が順序と取捨を確かめ、そのセッションの費用を入金する。

### フェーズ10　通しの確認

7本のサブタスクを終えた後のmasterの先頭を候補、統括計画を始める前のmasterの先頭`99ccc6bb`を起点として、[SPRTの手引き](../guides/sprt.md)の標準のLTC`time=60000+200`のGSPRTを、調整機で持ち時間を換算せずに行う。
基本シードは、その時点で保存済みの測定と、各設計書が予約した値から、ペア数以上離れた未使用の値とする。
結果は測定記録に残す。`H1`でなければ、どのサブタスクから見直すかを利用者が決める。
完了条件は、判定と測定記録の保存である。

## 検証

| 条件 | 期待する結果 |
|---|---|
| 同じセッション名のラベルを持つ調整機があるときに`launch.py`を実行する。 | 新しい調整機を作らずに止まる。 |
| `cpu_arch`、`cpu_cores`、または`duration`が条件を満たさない出品を`launch.py`に与える。 | 調整機を作らずに止まる。 |
| 物理コアの少ない機械で、所要時間の見込みが上限を超えるセッションを始める。 | `remote.py`が事前確認の前に止まり、`fetch.py`がログを取得して調整機を削除する。ログに`c`、負荷時の速度、および見込みの所要時間が残る。 |
| メモリの上限を小さくしたコンテナで`remote.py`を動かす。 | `c`が、物理コア数から1を引いた数ではなく、メモリから求めた数になる。 |
| 小さいセッションを中断せずに実行し、`fetch.py`で取得する。 | 全反復が測定機の`run/`にそろい、一時的な写しへの`apply`が通り、調整機の削除が確かめられて終了コード0で終わる。 |
| 実行中に`vastai reboot instance`でコンテナを再起動する。 | `remote.py`が負荷時の速度を確かめてから`--resume`で再開し、完了した反復を再計算しない。 |
| 実行中に調整機を削除し、別のCPU型の調整機を`launch.py`で作る。 | 取得済みの`run/`と、その機械でビルドし直した調整用ビルドで再開し、最後には全反復がそろい、`apply`が通る。 |
| `incoming/`へ一部の反復の記録だけが届いた状態を作り、適用番号に欠番がある状態で`fetch.py`を1回動かす。 | `run/`は前回の連続した状態のまま更新されない。この`run/`で別の調整機を再開させると、再開できる。 |
| `commit:`の形式の調整対象で、記録と異なるコミットの調整用ビルドを置いて`--resume`を実行する。 | エンジンの不一致で再開せずに止まる。 |
| 時間切れが起きる短い持ち時間で時間切れの事前確認を行う。 | セッションを始めずに0以外の終了コードで止まり、`fetch.py`が調整機を停止する。 |
| 事前確認の途中で、エンジンのプロセスを`kill -9`で1つ終了させる。 | 最終要約にクラッシュが数えられ、セッションを始めずに0以外の終了コードで止まる。 |
| 期限を短くして調整機を作る。 | 期限に調整機が停止する。停止した調整機からの取得は貸し手の環境に依存し、失敗することがある。 |

## 完了条件

フェーズ0から2を終え、調整機でのSPSAの手順が試走と検証を経て手引きとADRにまとまっていること。
7本のサブタスクが、それぞれの設計書の完了条件に従って完了していること。利用者が取捨の判断で外したサブタスクは、その判断を本書の「状態」節に記す。
完了の種別は、採用したサブタスクと採用しなかったサブタスクの組合せで、[設計書の書き方](README.md)の規則に従って決める。
フェーズ10の通しの確認の判定が、測定記録に残っていること。
仕様と設計判断の移し替えを終え、`docs/ROADMAP.md`の状態を更新して本書を凍結していること。

# 探索の関数形の見直しの統括計画

## 先に読む要約

本計画は、minaseの探索と時間管理の式をチェスのStockfishと将棋のYaneuraOu（やねうら王）の形へ寄せる7本の設計書（依存関係の節の表に挙げる）をサブタスクとして束ね、実行の順序、7本に共通する調整の実行環境、および全体の完了条件を定める。
7本はそれぞれ、式の形を変える実装をしたうえで、その時点の全係数をSPSA（simultaneous perturbation stochastic approximation、全係数を同時に少しずらした2つの設定を対局させて係数を動かす調整法）で30,000ペア調整し、短時間条件STCと長時間条件LTCの2段階の逐次検定（段階ゲート）で採否を決める。
SPSAはこれまで、開発と棋力測定に使う手元の機械（以下、測定機）で、STCと同じ持ち時間10秒＋0.1秒の対局により行ってきた。
30,000ペアのSPSAは測定機で1本あたり約75時間かかり、7本のSPSAだけで約22日、段階ゲートを含めると約1か月、測定機を占有する。
本計画では、SPSAだけを、計算機を時間単位で借りられる市場vast.aiで借りる物理192コア程度の計算機（以下、調整機）で実行し、1本あたりの所要時間を約13〜18時間に縮める。
調整機のサーバー向けCPUは多数のコアを低いクロックで動かすので、1コアは測定機より遅く、同じ持ち時間では1手に読む局面の数が減り、浅い探索に合う係数を選ぶおそれがある。
そこで、Stockfishの分散テスト基盤fishtestと同じく、同時対局数と同じ本数の速度計測を両機で走らせ、その速度の比を持ち時間に掛けて、1手あたりの探索量を測定機のSTCとそろえる。
SPSAの結果の反映と段階ゲートは、これまでどおり測定機で行う。
完了条件は、試走で持ち時間の換算を確かめ、中断と再開を含む検証を通した手順が手引きにまとまり、7本のサブタスクがそれぞれの設計書の完了条件に従って完了することである。

## 状態

起案。2026年10月17日に起案した。
7本のサブタスクはいずれも起案であり、着手していない。
SPSAは、2026年10月17日の利用者の決定により、サブタスクごとに行う（設計判断の「SPSAの単位」）。
利用者の判断を待つ点は、サブタスクの順序と取捨、および調整機の費用の上限の2つである。
vast.aiのアカウントの残高は約9.45米ドルであり、フェーズ0の試走には足りるが、SPSAの1セッション（約25〜35米ドル）には足りない。
次の一手は、利用者の指示を受けてフェーズ0（試走と持ち時間の換算の確定）を始めることである。

## 目的

第一の目的は、7本のサブタスクのSPSAを、測定機を占有せずに、測定機の数分の1の時間で終えることである。
第二の目的は、調整機で選んだ係数が測定機のSTCで選んだ係数と同じ条件の結果とみなせるように、1手あたりの探索量をそろえることである。
SPSAの対局はSTCの持ち時間で行い、採否はその後の段階ゲートで測定機が判定するので、調整の条件が測定機とずれると、段階ゲートに出す候補の質が下がる。
第三の目的は、7本を同じ手順で順に進め、全体の進み具合を1か所で追えるようにすることである。

## 適用範囲

本計画の用語を次のように定める。

- **測定機**は、Intel Core Ultra 7 265KFを積んだ手元の機械であり、高性能のPコア8個と省電力のEコア12個の物理20コアを持つ。lishogiのBotと共用するので、SPSAと段階ゲートの同時対局数は16を上限とし、Botは止めない。[vast.aiでの教師生成](vast-selfplay.md)では同じ機械を作業機と呼ぶ。
- **調整機**は、SPSAの1セッションのためにvast.aiで借りる計算機である。
- **負荷時の速度**は、同時対局数と同じ本数の`minase dev bench`を同時に走らせたときの、1本あたりの探索速度（1秒あたりのノード数、NPS）の平均である。
- **換算係数**`f`は、測定機の同時対局数16での負荷時の速度を、調整機の同時対局数での負荷時の速度で割った値である。
- **調整用ビルド**は、`--features tuning`を付けてビルドしたminaseであり、SPSAの対局はこのビルドで行う（[SPSAの手引き](../guides/spsa.md)の用語）。両機は、同じコミットをそれぞれの機械でビルドする。
- **時間切れの事前確認**は、SPSAの本番の前に、時間管理の係数を思考時間が最も長くなる側の範囲の端に置いた短いSPSAを、本番と同じ持ち時間と同時対局数で回し、時間切れが0件であることを確かめる手順である（[SPSAの手引き](../guides/spsa.md)の第3節）。7本はいずれも時間管理の係数を調整の対象に含むので、この手順を持つ。
- **事前対局**は、SPSAの結果を反映した候補と起点を、段階ゲートの前に測定機のSTCで短く対局させ、時間切れと時間の使い方を確かめる手順である。

本計画が扱うのは、依存関係の節に挙げる7本のサブタスクの実行順序と、各サブタスクのうちSPSAに関わる2つの手順（時間切れの事前確認とSPSAのセッション）の実行環境である。
調整機の調達、持ち時間の換算、セッションの起動、調整機から測定機への実行ディレクトリとログの取得、中断後の再開、および費用の上限を実装の対象とする。

各サブタスクの式の形、係数、開始値と範囲、シード、事前対局、段階ゲート、および採否の判定は、各設計書が定め、本計画は変えない。
採否のための対局測定（事前対局、段階ゲート、および秒読みつきの確認）は測定機で行い、調整機へは移さない。調整機で行う対局は、SPSAと、フェーズ0で換算を確かめる対局だけである。
SPSAの更新則、30,000ペアの規模、および`minase spsa`のコードは変えない。
教師生成をvast.aiへ移すことは[vast.aiでの教師生成](vast-selfplay.md)が扱い、本計画の対象外とする。

| SPSAの規模と更新の遅れ | 3,750反復×8ペアの標準のまま実行する。`minase spsa`は、空いた対局の枠に未配布のペアを配り、なければ次の反復をその時点のθで発行し、反復の8ペアがすべて終わった時点で、その結果を現在のθへ適用する（`spsa_runner`の`runner`モジュール）。同時対局数191では開始時に約24反復が発行され、ある反復の発行から適用までの間に、ほかの反復のペアがおよそ同時対局数の1〜2倍、すなわち約190〜380ペア終わる。したがって、各反復の結果は総ペア数の約0.6〜1.3%だけ古いθの周りで得たものになる。反復の8ペアのうち長い対局が1つ残ると、並走する反復の数はさらに増え得るが、同時に進むペアの数は同時対局数を超えない。fishtestも、各ワーカーが要求時のθで1回あたり同時対局数の6倍のペア（持ち時間10秒＋0.1秒のSPSAの場合、12倍の局）を指し、その結果を更新時点の現在のθへ加え（`server/fishtest/spsa_handler.py`の`__update_spsa_data`）、多数のワーカーが並行して動く。この程度の遅れはfishtestの運用の範囲に収まるとみて、更新則と規模を変えない。これは利用者の決定ではなく起案時の判断であり、利用者が変更できる。 | 1反復のペア数を増やして反復数を減らし、並走する反復を減らす案は、利得の減衰の式に入る総反復数を変えるので、[利得と規模のADR](../adr/decay-spsa-gains-over-30000-pair-sessions.md)の改訂を要する。同時対局数16と191の遅れを対局時間のばらつきを含めて模擬して比べる案は、模擬の道具に非同期の発行を加える実装を要し、fishtestの先例で足りると判断して採らない。 |

| 費用の上限 | セッションごとに、見積もりに余裕を加えた額だけを入金し、自動補充は設定しない。調整機は作成時に決めた期限に自分を停止し、測定機の取得スクリプトも期限の超過を見て停止を要求する。セッションを終えた調整機は、次のサブタスクまで残さずに削除する。 | 残高を上限の代わりにする案は、残高が0でもディスクの課金が負の残高として続くので採らない（[vast.aiでの教師生成](vast-selfplay.md)の設計判断）。 |
| サブタスクの並行 | 行わない。各サブタスクは1つ前の完了後のmasterを起点とし、その表の既定値をSPSAの開始値とするからである。本計画のフェーズ0から2は、サブタスク1の実装と並行してよい。 | 2つのサブタスクのSPSAを同時に回す案は、後のサブタスクの開始値が前の採否で変わるので成り立たない。 |

## 調整機でのSPSA

### 持ち時間の換算

換算係数は、セッションの開始時に次の手順で決める。

1. 測定機で、調整対象のコミットの調整用ビルドを16本同時に`minase dev bench --depth 9 --repetitions 3`で走らせ、16本のNPSの平均を測定機の負荷時の速度とする。`dev bench`は固定の15局面を固定の深さで探索する速度計測であり、深さ9は1本が数秒で終わる深さである。測定の間は、ほかの対局測定、SPSA、教師生成、および学習を止める。Botは止めない。測定機でのSPSAも、Botと共用した状態で行ってきたからである。
2. 調整機で、同じコミットの調整用ビルドを同時対局数と同じ本数だけ同時に走らせ、同じく平均を調整機の負荷時の速度とする。
3. `f`は測定機の値を調整機の値で割った比とし、小数第2位に丸める。持ち時間は`time=<10000×f>+<100×f>`（ミリ秒、整数に丸める）とする。たとえば`f`が2.31なら`time=23100+231`である。

教師生成の試走の値から見積もると、EPYC 9654の2基構成で同時に192局を探索したときの全体の速度は約1億NPS、1スレッドあたりでは約52万NPSである。
測定機の同時16局での値は測っていない。Pコア1本だけのbenchは約145万〜148万NPSであり（[記録](../measurements/nnue-hidden-layer-bench.md)）、16局のうち8局はEコアで動き、全コアの負荷でクロックも下がるので、平均は下がる。下限は仮にPコア単独の約7割の約105万NPSと置き、約105万〜145万NPSと見込む。
したがって`f`は約2.0〜2.8である。
SPSAでは1局の時間が持ち時間で決まるので、調整機の処理量は測定機の`191 ÷ (16 × f)`倍、つまり約4.3〜6.0倍になる。

起案時のminaseが各手に割り当てる思考時間の予算は、残り時間と加算に係数の比を掛けて決まり、固定の値は安全余裕の30 msだけである（`crates/minase/src/search/alphabeta/time.rs`の`clock_budget_with_margin`）。
このため、持ち時間を一様に伸ばしても、時間管理の係数の働きはほぼ変わらない。
例外は、[持ち時間の伸縮](time-instability-scaling.md)が加える、合法手が1つの局面で目安の思考時間（soft）を500 msに抑える上限であり、この上限は換算されない。同書はこの上限が働くことはまれと見込んでいるので、そのセッションの記録で発動の件数を確かめる。
一方、安全余裕と、対局を進める審判のプロセスとエンジンの間で1手ごとに生じる通信の遅れは伸びないので、持ち時間に対する割合は測定機の1/`f`になり、調整機の対局がわずかに有利になる。
fishtestも同じ近似で持ち時間を伸ばしている。

### 同時対局数とメモリ

同時対局数は調整機の物理コア数から1を引いた数とする。
`minase spsa`は、先後を入れ替えた1ペアの2局を順に指すので、同時に動く局の数は同時対局数に等しく、1局につき2つのエンジンのプロセスが置換表を確保する。
測定機の記録では1局あたりの最大常駐メモリは約613 MBであり（[記録](../measurements/strength-stage8-elo200.md)）、同時191局で約117 GBになる。
サブタスクが進むと、1局あたりのメモリは増える。たとえば[historyの形](history-forms.md)はエンジン1つあたり約157 MB、[correction historyの表](correction-history-tables.md)は約37 MBを加えるので、両方を採用した後の1局は約1.0 GB、同時191局で約191 GBになる。
このため、メモリの条件は固定の値にせず、セッションごとに決める。
セッションの準備で、測定機で調整対象のコミットの調整用ビルド同士の1ペアをSTCで指し、各局の記録の`candidate_peak_rss_bytes`と`baseline_peak_rss_bytes`の和を求め、2局のうち大きい方の値を1局あたりの最大常駐メモリとする。
調整機の実メモリ（vast.aiの`cpu_ram`）は、この値に同時対局数を掛け、25%の余裕を加えた値以上を条件とする。
起案時のmasterでは約146 GBである。

### 選定条件

調整機は、`vastai search offers`で次の条件をすべて満たすオンデマンドの出品のうち、1時間あたりの価格が最も安いものとする。
条件は、[vast.aiでの教師生成](vast-selfplay.md)の選定条件（`gpu_frac`が1、Zen 4以降のEPYC、384スレッド以上、検証済み、信頼度0.95以上、直接接続のポート、送信速度、ディスク50 GB）に、次の2つを加えたものである。

- `cpu_ram`が、前節の式でそのセッションについて求めた値以上である。
- 貸出期限までの日数`duration`が2日以上である。`duration`は貸し手が決めた、その機械を借りていられる最長の期間であり、課金は実際に借りている時間の分だけである。1セッションは約13〜18時間かかるので、再開に備えて余裕を持たせる。

2026年10月17日に公開APIで照会した出品では、384スレッド以上の10件のうち最も安いEPYC 9654の2基構成（1時間1.01米ドル）はメモリが126 GBで起案時のmasterの条件も満たさず、条件を満たす最も安い出品はEPYC 9K84の2基構成（メモリ755 GB、1時間1.87米ドル）だった。

### 実行の構成

セッションごとに、測定機の`data/vast-spsa/<セッション名>/`に次の配置で置く。
セッション名は、各設計書のSPSAの実行ディレクトリ名と同じにする（たとえば`search-pruning-forms`）。

| パス | 内容 |
|---|---|
| `session.env` | 調整対象のコミット、基本シード、反復数、1反復のペア数、規則、時間切れの事前確認の要否と基本シード、測定機の負荷時の速度、および1局あたりの最大常駐メモリを、シェル変数として1行ずつ書く。 |
| `params`と`safety.params` | 各設計書が定めるパラメーターファイルと、その写しの時間管理の係数を範囲の端に置いた時間切れの事前確認用のファイル。 |
| `incoming/` | 調整機の実行ディレクトリを取得する場所。転送の途中のファイルを含み得る。 |
| `run/` | 適用番号の連続を確かめた再開用の写し。`incoming/`の各ファイルへのハードリンクであり、内容を複製しない。セッションの終了後は、各設計書の`data/spsa/<セッション名>`へ移して`apply`に使う。 |
| `safety/` | 時間切れの事前確認の実行ディレクトリの写し。 |
| `engine/` | 調整用ビルドの実行ファイルと検査和（`target/match-cache/<コミット>-tuning/`の中身）の写し。再開にだけ使う。 |
| `logs/` | ビルド、負荷時の速度、換算した持ち時間、`minase spsa`の標準出力、および終了コードの記録の写し。 |
| `deadline` | 現在の調整機の停止の期限（UNIX時刻）。`launch.sh`が書き、`fetch.sh`が自己停止の失敗を見つけるために読む。 |

時間切れの事前確認の反復数は、`13 × 同時対局数 ÷ 16`を切り上げた数（同時対局数191なら156反復、1,248ペア、約35分）とする。
同時対局数と同じ数のペアが一通り入れ替わるまでを1巡と呼ぶと、SPSAの手引きの13反復（104ペア）は、同時対局数16で6.5巡に当たり、対局の枠が埋まった状態を長く続ける。
調整機で13反復を回すと同時対局数の半分しか埋まらず、セッションより軽い負荷で時間切れを確かめることになるので、巡の数を手引きにそろえる。

### 操作の入口

スクリプトは`scripts/vast-spsa/`に置く。

| 操作 | 内容 |
|---|---|
| `launch.sh` | 測定機で実行する。引数はセッション名、出品のID、および期限までの分数である。期限までの分数は、SPSAの所要時間の見積もりの上限に1.3を掛け、ビルド、速度の測定、および事前確認の45分を足した値とする（18時間なら1,449分）。1.3倍は、教師生成の設計書の期限と同じ余裕である。`session.env`と出品のCPU型、`cpu_ram`、`duration`を検査し、同じセッション名のラベルを持つ調整機があれば止まる。`git bundle`、パラメーターファイル、`remote.sh`、および再開の場合は`run/`と`engine/`を送ってから、開始の印となる空ファイル`started`を作る。 |
| `remote.sh` | 調整機で、起動時スクリプトから呼ばれる。bundleからcloneして、`minase spsa`を実行する通常のビルド（以下、runner）と調整用ビルドを作る。`engine/`が送られていれば、それを`target/match-cache/`へ置き、調整用ビルドを作り直さない。続いて、負荷時の速度を測って`f`と持ち時間を決め、`logs/`に記録してから、時間切れの事前確認とSPSAのセッションを順に実行する。事前確認の全反復が完了しなかった場合と、最終要約の`engine_failures:`行の件数（不正着手、クラッシュ、応答期限超過、時間切れ、および拒否着手）が1件でもあった場合は、セッションを始めずに0以外の終了コードで止まる。`minase spsa`は異常があっても終了コード0で終わるので、終了コードでは判定しない。実行ディレクトリがすでにあれば、`f`を決め直さず、負荷時の速度が最初の記録から許容幅に収まることを確かめてから`--resume`で再開する。 |
| `fetch.sh` | 測定機で実行する。10分ごとに実行ディレクトリを`incoming/`へ、ログを`logs/`へ取得し、適用番号が1から連続していれば`run/`を更新する。終了コードが0で全反復がそろったら、調整対象のコミットの`params.rs`の一時的な写しに`minase spsa apply`（最終値を係数の表の既定値へ書き込むコマンド）を実行して記録の連鎖を検査し、通れば調整機を削除する。 |

負荷時の速度の許容幅は、フェーズ0で同じ調整機を3回測ったときの最大と最小の差を、3回の平均で割った比とする。
再開時に測った値と最初の記録の値の差が、最初の記録の値に対してこの比を超えた場合を、幅を外れたとみなす。
再開した調整機の速度がこの幅を外れた場合は、同じ持ち時間で1手の探索量がそろわないので、再開せずに止まり、利用者が新しいセッションとしてやり直すかを決める。

## 所要時間と費用

SPSAのセッションは、測定機の同時対局数16で3,000ペアに27,138秒かかった記録（[セッションの記録](../measurements/spsa-stage9-20260925-c5.md)）から、測定機では30,000ペアで約75時間かかる。
調整機では、前節の4.3〜6.0倍の処理量から約13〜18時間と見込み、ビルド、負荷時の速度の測定、および時間切れの事前確認に約45分を加える。
1時間1.87米ドルの調整機では、1セッションの費用は約25〜35米ドル、7本で約175〜245米ドルになる。
フェーズ0の試走は約3時間（約6米ドル）、フェーズ1の検証は少ないコアの安い機械で約2米ドルと見込む。

1つのサブタスクは、実装に半日〜2日、調整機での事前確認とSPSAに約13〜18時間、測定機での反映と事前対局に約1時間、STCに約1〜8時間、LTCに約5〜30時間を要する。
測定機の占有は、反映と事前対局、STC、およびLTCの和であり、STCで棄却される場合に約2〜9時間、LTCまで進む場合に約7〜39時間になる。
持ち時間の伸縮のサブタスクは、秒読みつきの時計での確認に約3〜58時間を加える。

## 記録

各セッションの記録は、[SPSAの手引き](../guides/spsa.md)の第6節の項目に加えて、次を含める。

- 出品のIDと機械のID、CPU型、物理コア数とスレッド数、`cpu_ram`、時間単価、および費用の合計。
- 測定機と調整機の負荷時の速度、`f`、換算した持ち時間、および同時対局数。
- 時間切れの事前確認の`time_forfeits`。
- 調整機を作り直して再開した場合は、その回数、各調整機の記録、および失った反復の数。

## 実装フェーズ

### フェーズ0　試走と持ち時間の換算の確定

選定条件に合う調整機を約3時間借り、現行のmasterで次を測る。
スクリプトはまだないので、[試走の記録](../measurements/vast-selfplay-trial.md)と同じく、SSHで接続して手作業で実行する。

1. 測定機と調整機の負荷時の速度を、それぞれ3回ずつ測り、`f`と繰り返しのばらつきを求める。
2. 同じ基本シード5,600,000,000で、現行のmasterの調整用ビルド同士を`minase match run`で対局させる。測定機ではSTCと同時対局数16で191ペア、調整機では換算した持ち時間と同時対局数191で382ペアを指す。調整用ビルドは、各機で負荷時の速度の測定に使った実行ファイルを、起動コマンドの形式（`"<パス> --protocol usi --rules engine-default"`）で両側に指定する。`commit:`の形式は通常のビルドを作るので使わない。同じシードを使い、同じ開始局面で両機の探索の深さを比べる。調整機で2巡分を指せば、ペア番号1〜191の対局は対局の枠が埋まった負荷の下で指される。
3. 両機のペア番号1〜191の記録から、`scripts/clock_profile.py`で手数帯ごとの平均到達深さを、記録の`candidate_peak_rss_bytes`と`baseline_peak_rss_bytes`から1局あたりの最大常駐メモリを集計する。
4. 調整機で、`minase spsa params`が現行のmasterから生成した既定のパラメーターファイルを使い、換算した持ち時間と同時対局数191による156反復のSPSA（基本シード5,700,000,000）を回して、時間切れとエンジン異常が0件であることを確かめる。

完了条件は、`f`の測り方と許容幅、メモリの条件、および所要時間と費用の見積もりが実測に基づいて確定し、両機の手数帯ごとの平均到達深さの差が記録されていることである。
深さの差の合否の基準は、事前に根拠を持って決められないので置かない。差を利用者に示し、`f`の測り方を見直すかを利用者が決めてから次のフェーズへ進む。
結果は測定記録`vast-spsa-trial`に残す。

### フェーズ1　スクリプトの実装と検証

`scripts/vast-spsa/`の3つのスクリプトを実装し、少ないコアの安い機械で、2反復程度の小さいセッションを使って「検証」の全条件を通す。
完了条件は、「検証」の全条件を通すことである。

### フェーズ2　手引きとADR

[SPSAの手引き](../guides/spsa.md)に、調整機で実行する手順（準備、起動、取得、再開、費用の確認、および片付け）を加え、第4節の同時対局数16の記述を測定機の場合に限る。
持ち時間を負荷時の速度の比で換算して借りた計算機でSPSAを行う方式を、ADRに記録する。
完了条件は、手引きとADRがmasterへ入ることである。

### フェーズ3〜9　サブタスク1〜7

依存関係の表の順に、各設計書の実装フェーズを進める。
時間切れの事前確認とSPSAのセッションは、手引きの調整機の手順で実行し、それ以外のフェーズは各設計書のとおり測定機で行う。
各サブタスクの完了は、その設計書の完了条件による。
サブタスクを始める前に、利用者が順序と取捨を確かめ、そのセッションの費用を入金する。

## 検証

| 条件 | 期待する結果 |
|---|---|
| 同じセッション名のラベルを持つ調整機があるときに`launch.sh`を実行する。 | 新しい調整機を作らずに止まる。 |
| CPU型、`cpu_ram`、または`duration`が条件を満たさない出品を`launch.sh`に与える。 | 調整機を作らずに止まる。 |
| 小さいセッションを中断せずに実行し、`fetch.sh`で取得する。 | 全反復が測定機の`run/`にそろい、一時的な写しへの`apply`が通り、調整機の削除が確かめられて終了コード0で終わる。 |
| 実行中に`vastai reboot instance`でコンテナを再起動する。 | `remote.sh`が負荷時の速度を確かめてから`--resume`で再開し、完了した反復を再計算しない。 |
| 実行中に調整機を削除し、同じCPU型の別の調整機を`launch.sh`で作る。 | 取得済みの`run/`と`engine/`で再開し、最後には全反復がそろい、`apply`が通る。 |
| `incoming/`へ一部の反復の記録だけが届いた状態を作り、適用番号に欠番がある状態で`fetch.sh`を1回動かす。 | `run/`は前回の連続した状態のまま更新されない。この`run/`で別の調整機を再開させると、再開できる。 |
| 再開する調整機へ`engine/`を送らない。 | 再ビルドした実行ファイルのSHA-256が記録と違えば、`--resume`がエンジンの不一致で止まり、一致すれば再開する。この検証は再開の手段を確かめるものではなく、ビルドの再現性を記録するためのものなので、どちらの結果も合格とし、結果を記録する。 |
| 再開した調整機の負荷時の速度が許容幅を外れるように、別のCPU型の機械で再開させる。 | 再開せずに0以外の終了コードで止まる。 |
| 時間切れが起きる短い持ち時間で時間切れの事前確認を行う。 | セッションを始めずに0以外の終了コードで止まり、`fetch.sh`が調整機を停止する。 |
| 事前確認の途中で、エンジンのプロセスを`kill -9`で1つ終了させる。 | 最終要約にクラッシュが数えられ、セッションを始めずに0以外の終了コードで止まる。 |
| 期限を短くして調整機を作る。 | 期限に調整機が停止し、停止した調整機から`fetch.sh`が実行ディレクトリを取得できる。 |

## 完了条件

フェーズ0から2を終え、調整機でのSPSAの手順が試走と検証を経て手引きとADRにまとまっていること。

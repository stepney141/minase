# 探索部の反復負け回避の設計書

## 先に読む要約

本マイルストーンは、エンジンが千日手による負けを自分で避けられるようにすることを目的とする。
Minaseの既定の反復規則R1（RULES.md第31条）は、同一局面の4回目の出現を原則として引き分けとするが、その間の自分の着手がすべて攻撃的着手（王手、または動かした駒が相手の駒に当たる着手）であった対局者が一方だけなら、その攻撃側の負けとする（将棋の連続王手の千日手、perpetual checkに相当する）。
現行の探索は、探索木の中で同一局面が再現した時点で評価値0の引き分けとして読みを打ち切り、どちらが攻撃側かを調べない。
[保存済みの自己対局記録の診断](../measurements/search-repetition-outcome-diag.md)では、94,466局の4.2%が攻撃側の反復負けで終わり、負けた側は3,938局のすべてで直前の評価値に0を報告していた。
これらの負けはすべて、自分の着手が4回目の出現を生じさせたか、自分の着手の直後に相手が4回目の出現を完成させたかのどちらかであり、根（探索を開始する現局面）から2手以内で確定している。裁定は4回目の出現を完成させた着手の完了時に対局を終わらせるので、負けた側から見ると、敗着は必ず最後の自分の着手であり、裁定はその着手か直後の相手の応手で成立するためである。
本書は、探索を始める前に、根の合法手と相手の応手を対局の写しへ実際に適用して審判層（対局の終局を裁定する層）の裁定を確かめ、反復負けに直結する手を根の候補手から除く方式（根の反復負け回避）を項目1として定める。
項目2は、探索木の中で同一局面が1回再現した時点で、その周回の攻撃的着手が一方だけなら攻撃側の負けを専用の評価値で返す方式（木の中の反復の勝敗）である。
これは将棋エンジンが連続王手の千日手を、シャンチー（中国象棋）のエンジンが長将と長捉を扱う標準的な方式であり（[既存実装の調査](../research/search-repetition-prior-art.md)）、攻撃側が負けになる周回へ向かうこと自体を早い段階で避けられる。
項目1は裁定の瀬戸際を審判層の正確な判定で守り、項目2は探索の読みの中で周回の損得を近似する。
採否は、実装コミットと直前コミットの自己対局GSPRT（勝敗から強さの差を逐次判定する統計検定、[docs/guides/sprt.md](../guides/sprt.md)）を短時間条件と長時間条件の2段階で行って判定する。
完了条件は、各項目の採否または見送りが記録されていることである。

## 目的

現行の探索は、着手を適用した局面の探索局面キー（RULES.md第24条第1項が同一局面の条件とする盤面、手番、および一時的な権利と制限を1つにまとめたハッシュ値）が対局履歴または探索経路のどれかと一致すると、`DRAW_SCORE`（0）を返す（`src/search/alphabeta/negamax.rs`の`search_move`）。
この近似は、[探索部](search.md)が「4回目の出現の裁定は木の中では追わない」と明記して、主要エンジンと同種の妥協として許容したものである。
一方、[棋力向上の段階計画](strength-stages.md)の段階11は、この歪みが敗着になった局を数えてから厳密化の要否を決めると定めている。
診断の結果は次のとおりである。
全87実行、94,466局のうち、攻撃側の反復負けは3,938局（4.17%）、反復による引き分けは2,276局（2.41%）であり、直近の測定では反復負けが約6%に達する。
負けた側が最後に報告した評価値は3,938局のすべてで0であり、探索は負けになる反復を引き分けと見込んで選んでいた。
負けた側が4回目の出現を生じさせる着手を自分で指した局は60.3%、負けた側の着手の直後に相手が4回目の出現を完成させた局は39.7%である。
負けた側の直前の形勢（最後の20手のうち最後の非0の評価値）は中央値−34であり、−300以下だった局は18.3%である。
この値は反復を外れた場合の形勢を直接測ったものではないので、「外れていれば勝負が続いた局が多い」という見立ては仮説にとどまり、採否測定で確かめる。
本マイルストーンは、この負けをエンジンが避けられるようにする。
lishogiの対局条件も反復規則R1を使うので（RULES.md第33条第6項）、同じ改善がlishogi上の対局にも及ぶ。

## 適用範囲

対象は、`SearchSnapshot::from_game`（対局の状態から探索の入力を作る関数）が根の候補手を確定する処理、対局管理層が根の合法手を反復の裁定で分類する関数、および[探索部](search.md)の「探索内の終局と規則処理」の記述である。
項目2では、`src/search/alphabeta/negamax.rs`の`search_move`にある反復の判定、探索ワーカーが持つ探索経路の記録、置換表の照会、詰みの帯を参照する枝刈りの保護条件、および補正履歴の更新条件が加わる。
本書の用語は次のとおりである。
**根**は探索を開始する局面、すなわち実際の対局の現局面である。
**再現**は、着手後の局面の探索局面キーが、対局履歴または探索経路のいずれかの局面と一致することをいう。
**出現回数**は、対局履歴と探索経路を通じてその局面が現れた回数であり、再現した局面自身を含めて数える。
**審判層の状態**は、審判層が対局の進行に沿って更新する`AdjudicationState`であり、R1では局面ごとの出現回数と最初の出現の手数、対局者ごとの攻撃連続数、連続可逆手数、および対局開始からの手数を持つ。
**反復負けに直結する手**は、根の合法手のうち、その着手の完了時にR1の裁定で自分の負けとなる手、またはその着手の後に相手がR1の裁定で自分を負けにできる応手を持つ手をいう。
**反復勝ちの手**は、その着手の完了時にR1の裁定で自分の勝ちとなる手をいう。

次の事項は範囲に含めない。

- R2とR3の探索内の扱いは変えない。R2とR3は反復を生じさせる着手を不合法とする規則であり、根では審判層が禁止手を除いているので、対局が反復で終わることはない（HaChuとの対局17実行で反復による終局は0局）。探索木の中で禁止手を引き分けとして扱う近似は[探索部](search.md)の既知の歪みとして残る。
- 引き分けの評価値を形勢や相手に応じて変える仕組み（contempt）は導入しない。診断では、+300以上の形勢から反復による引き分けを受け入れた対局者は引き分けの当事者の4.4%であり、全局の0.2%程度にとどまる。
- 静止探索には反復の判定を加えない。静止探索は捕獲手だけを再帰し、各手で盤上の駒が減るので同一局面へ戻らない。
- 駒枯れとE3裸玉の終局値の厳密化（段階11の同じ項目の残り）は扱わない。
- 候補手が1手に絞られた場合の思考時間の短縮は扱わない。

## 設計判断

| 項目 | 決定 |
|---|---|
| 根の選別を先に入れる | 反復負けの確実な回避は、探索木の中の評価値ではなく、根の候補手の選別で実現する。診断が示した負けは、すべて根から2手以内（自分の着手、または相手の直後の応手）で裁定が成立する。この範囲は`Game::play`の終局の裁定で漏れなく正確に判定でき、探索の深さ、置換表、および枝刈りの影響を受けない。木の中の評価値だけで避ける方式には、後述の3つの穴があり、根の選別なしでは負けを確実には防げない。調査した既存エンジンは根の選別を自分では計算せず、1回の再現での先取り（項目2）によって瀬戸際まで進むこと自体を減らしている。根で禁じ手を除くという考え方の先例は、GUIが禁じ手をエンジンへ渡すUCCIプロトコルの`banmoves`と、根でだけ規則どおりの回数で判定するElephantEyeにある。R1の裁定は、対局履歴の正確な出現回数、可逆手12手の前提条件、および最初の出現からの区間に依存するので、Minaseでは瀬戸際の判定を審判層に任せる。 |
| 木の中だけで避ける方式の穴 | 第1に、置換表の打ち切りが裁定を隠す。周回中の局面は直前の周回で深く探索済みであり、そのとき保存された値（多くは引き分けの0）が、裁定を完成させる応手を調べる前に返る。第2に、futility pruningのように手を展開せずに飛ばす枝刈りが、裁定を完成させる静かな応手を飛ばす。第3に、R1は局面の出現回数を到達経路によらず数える。たとえば局面AからB、C、Dを経てAへ戻る周回を3回繰り返す途中で、2周目だけDの代わりに別の局面D′を通ると、Aが3回出現した時点でDはまだ1回しか出現していない。ここで攻撃側がCからDへ進むと、Dは2回目の出現にすぎないが、相手の次の1手でAの4回目の出現が完成する。現行の探索はDを再現として引き分けで打ち切るので、その先の相手の1手を読まない。いずれも根から2手以内で起こるので、根の選別が必要になる。 |
| 選別の内容 | 規則がR1の対局で、根の合法手を、反復勝ちの手、反復負けに直結する手、およびそれ以外の3種に分ける。反復勝ちの手があれば、根の候補手を反復勝ちの手だけにする。なければ、反復負けに直結する手を根の候補手から除く。全部の合法手が反復負けに直結する場合は除かず、全部を候補手にする。中将棋では着手せずに手番を渡せないので（RULES.md第6条第5項）、探索は必ず1手を返す必要があり、この場合はどの手を選んでも結果が変わらないためである。R1以外の規則では何もしない。 |
| 判定の実装 | 判定は対局管理層（`src/core/game.rs`）に置き、`Game`の写しへ着手を実際に適用する`Game::play`の終局結果だけを判定の根拠にする。根の着手を写しへ適用し、終局理由が反復の勝敗ならその結果で分類する。反復以外の理由で終局した着手は分類せず、応手も調べない。終局しなかった場合だけ、相手の応手を写しへ適用し、相手の反復勝ちで終局する応手があれば、根の着手を反復負けに直結する手とする。終局の裁定は、王駒の捕獲、R1の反復、駒枯れと裸玉、合法手なし、詰みの順に確定するので、この順序、可逆手が12手以上続くという前提条件、および最初の出現からの区間の数え方は、すべて`Game::play`がそのまま担う。R1の規則や終局の順序を選別の側に書き直す案は採らない。裁定と選別が食い違う余地を作るためである。 |
| 判定の費用 | `Game`の写しと`Game::play`は、反復履歴の複製と詰みの判定を含むので、根の合法手と応手の全部の組（100手×100手程度）に適用するには重い。そこで、適用する対象を探索局面キーで先に絞る。R1の反復の裁定は4回目以降の出現でだけ成立するので、着手後の局面が対局履歴に既に3回以上出現していなければ、その着手で裁定が成立することはない。手番も同一局面の条件に含まれるので、根から2手の間に同じ局面の出現回数が増えるのは最大1回であり、裁定が5回目以降の出現へ遅れる場合もこの条件は変わらない。したがって、対局履歴に出現回数が3以上の局面がなければ選別全体を省き、ある場合も、着手後の探索局面キーがその局面のどれかと一致する根の着手と応手だけを`Game::play`で判定する。キーの計算は局面への着手の適用と取り消しだけで済む。絞り込みは判定の対象を減らすだけであり、判定そのものは`Game::play`が行う。所要時間はフェーズ2で実測する。 |
| 選別が保証する範囲 | 選別が保証するのは、根に反復負けに直結しない合法手が1つでもあれば、根から2手以内の反復負けを避けることである。全部の合法手が反復負けに直結する根に至ることまでは防がない。 |
| 項目2の位置づけ | 木の中の反復の勝敗は、項目1の採否が確定した後に、その時点の採用構成を基準として測る。項目1が採用されていれば項目1の採用版が、不採用なら段階開始版が基準になる。項目2の役割は、攻撃側が負けになる周回を探索が引き分けと見込んで目指すことを防ぎ、受ける側には周回が自分に有利であることを教えることである。 |
| 勝敗を返す時点 | 探索木の中の1回の再現で返す。上流のやねうら王、Apery、技巧、dlshogi、およびElephantEyeがこの方式であり、規定回数の成立を待つのはFairy-Stockfishだけである。攻撃側には、途中の周回で攻撃的でない着手を1手挟んで裁定を引き分けへ変える逃げ道がある。着手を切り替える地点が探索木の中にあれば、その手順は別の兄弟手として読まれるので、1回の再現で負けを返しても逃げ道は失われない。切り替える地点が根より前の対局履歴にしかない場合は、探索は対局履歴の局面へ戻った時点で読みを打ち切って負けの値を返すので、戻った後に攻撃的でない着手へ切り替える手順を読まない。このため、対局履歴の局面へ戻る手を実際より悪く評価する。これは1回の再現で判定する方式に共通の近似であり、周回のたびに同じ局面が現れるので、戻る手の代わりに選ぶ手は、後の周回で反復を外れるときに選ぶ手と盤上では同じである。この近似が棋力を損なうかどうかは採否測定で判定する。4回目の出現でだけ審判層の裁定を再生する案は採らない。発動するのが対局履歴に3回以上出現した局面がある場合に限られ、その範囲は項目1が正確に守っているので、加わる情報がほとんどないためである。 |
| 対局履歴との一致 | 対局履歴との1回の一致を再現として扱う現行の方式を保つ。この方式はやねうら王の大会用ビルドと同じであり、作者は、根より前へ遡らない方式がレーティングで5程度弱いという実測を残している。Stockfishが根の局面の再現を引き分けとしないのは、複数の候補手の値を同時に正しく表示するためであり、棋力のためではない。 |
| 周回の区間と攻撃側の判定 | 再現した局面から、対局履歴と探索経路を新しい方から遡って最初に一致した出現までを周回の区間とする。区間の中の自分の着手がすべて攻撃的着手である対局者が一方だけなら、その対局者を攻撃側とする。双方が該当する場合と、どちらも該当しない場合は引き分けとする。可逆手12手の前提条件と4回目の出現という回数は調べない。これは将棋エンジンが連続王手を4回の成立を待たずに判定するのと同じ近似である。区間は、再現を完成させる現在の着手を含む。現在の着手は、探索経路へ局面キーを積む前に判定されるので、区間へ明示的に加える。区間にnull moveが含まれる場合は、実際の対局に現れない手順なので引き分けとする（ElephantEyeも遡りをnull moveで止める）。 |
| 攻撃的着手の判定の計算 | 探索経路上の着手は、再現を検出したときにだけ判定する。探索ワーカーは、経路の着手を根からの探索手数と対応づけて積むスタックを持つ。null moveは局面キーの経路には積まれないが、手番と先獅子の状態を変えるので、このスタックにはnull moveも記録する。再現を検出したノードで、根の局面の写しにスタックの着手とnull moveを順に適用して局面を再生し、区間の中の着手にだけ審判層の`move_was_attacking`を呼ぶ。区間より前にあるnull moveは、局面の再生のためにだけ適用する。双方に攻撃的でない着手が見つかった時点で打ち切る。判定の結果はスタックの各要素に記録し、同じ経路の下で再現が繰り返し検出されても再計算しない。記録は、その着手を探索経路から取り消すときに要素とともに捨てる。対局履歴の側の着手は、根の時点の審判層の状態が持つ対局者ごとの攻撃連続数で判定する。区間に含まれるその対局者の履歴上の着手数が攻撃連続数以下なら、履歴の側はすべて攻撃的である。再現を検出したときにだけ計算する方式はPikafishと同じであり、再現のないノードに費用をかけない。ElephantEyeのように着手のたびに旗を計算して積む方式は、大多数のノードで使われない計算を払うので採らない。攻撃の定義は審判層の関数をそのまま使い、探索の側に書き直さない。 |
| 勝敗の評価値と置換表 | 反復による勝敗は、詰みの帯のすぐ内側に設ける専用の帯の値で返す。詰みの帯の下端`MATE_THRESHOLD`は29,744であり、評価関数の値は±28,999に制限されているので、勝ちの値を`29,743 − ply`（`ply`は最大256なので29,487以上）とし、絶対値が29,487以上29,744未満の範囲を専用の帯とする。通常の評価値がこの帯に届かないことをテストで固定する。この帯の値は置換表へ手数の補正をせずに記録し、通常探索と静止探索のどちらの照会でも打ち切りに使わず、記録手だけを着手の順序づけに使う。補正をしないので、どの深さで読み出しても値は帯の中にとどまり、通常の値として誤って打ち切りに使われることがない。詰みの帯の値の補正と打ち切りは変えない。これはElephantEyeの専用の帯による保護を参考にした方式である。反復による勝敗は対局履歴と経路に依存するので、置換表からの打ち切りに使うと、別の経路、後の手番の探索、または置換表を共有する別のワーカーへ誤った勝敗が漏れる（graph history interaction）。R1の攻撃側の判定は区間の全着手に依存するので、連続王手の回数だけを見る将棋より経路依存が強い。詰みの帯をそのまま使う案（やねうら王、Apery、Pikafish）は、この漏れを防げないので採らない。Pikafishのように置換表の鍵へ既出の印を混ぜる案は、既出の状態が異なる経路の間の命中を失ううえ、区間の攻撃側という経路依存までは区別できないので採らない。反復から返る引き分け値の`DRAW_SCORE`は通常の評価値の0と区別できないので、置換表の保護の対象にしない。したがって、ある対局履歴で引き分けだった周回の値が祖先に残り、別の対局履歴では一方の負けになる同じ周回を調べる前に再利用されることがある。これは現行の引き分けの近似が既に持つ漏れと同じ性質のものであり、既知の近似として残す。ElephantEyeのように引き分け値も打ち切りから除くには、引き分け値を評価関数が返さない値にする必要があり、本書の範囲を超える。null move pruning、futility pruning、SEE（静的交換評価）による捕獲手の枝刈り、およびaspiration windowsが詰みの帯に対して持つ保護は、判定の閾値を専用の帯の下端へ下げて両方の帯に適用する。[棋力向上段階8](strength-stage8.md)で採用した補正履歴（correction history）も、反復による勝敗を静的評価の誤差として学習しないよう、更新から除く評価値の範囲を専用の帯まで広げる。この変更は規則によらず適用するので、専用の帯の値が現れない探索でも、探索窓の端が29,487以上29,744未満に入る場合に限って探索の手順が変わり得る。USIの`info`出力は、この帯の値を詰みとしてではなく通常の評価値として表示する。 |
| Pikafishの中間方式 | Pikafishは、2回目の出現での勝敗を、同じ周回がもう1回起こり得ないと確認できた場合にだけ確定し、それ以外では探索窓を引き分け値の側へ狭めるだけにする。この方式は採らない。確認の条件がシャンチーの規則の回数に依存しており、R1へ移すには別の設計が要るためである。 |
| 引き分け値の改良 | 引き分け値の揺らぎ（Stockfish、やねうら王）と、根の手番に応じた引き分け値の符号づけ（やねうら王、技巧）は、反復負けの回避とは独立の改良なので扱わない。 |
| 未採用コードの扱い | 不採用または見送りとなった項目はコードに残さず、設計だけを本書に保持する。 |

## 項目1　根の反復負け回避

対局管理層に、根の合法手をR1の裁定で分類する関数を追加する。
関数は`Game`への共有参照だけを入力とし、反復勝ちの手の一覧と、反復負けに直結する手の一覧を返す。
判定には`Game`の写しを使うので、元の対局の状態は変わらない。
`SearchSnapshot::from_game`は、この結果で根の候補手を「設計判断」の「選別の内容」のとおりに確定する。
探索ワーカー、置換表、および時間管理は変更しない。
選別は探索の入力だけを変えるので、`Threads`の値に依存しない。
対局履歴に出現回数が3以上の局面がない場合、根の候補手は現行と同一であり、探索の結果も現行と一致する。

既知の限界は次のとおりである。
項目1だけでは、根から3手以上先で成立する裁定は現行どおり引き分けとして近似される。項目2はこの近似を改める。
このため、攻撃側は反復を引き分けと見込んだまま周回に入り、最後の周回で候補手から除かれた時点で別の手へ切り替える。
周回のたびに盤上には同じ局面が現れるので、最後の周回で外れる場合の盤上の選択肢は、早い周回で外れる場合と同じである。
ただし、反復履歴が進むと、外れた先での反復の裁定や詰みの成否が変わることがあるので、両者が同じ価値であるとは限らない。
この差と周回に使う持ち時間が棋力へ与える影響は、採否測定に含めて測る。

## 項目2　木の中の反復の勝敗

対象は`src/search/alphabeta/negamax.rs`の`search_move`にある反復の判定、探索ワーカーの探索経路の記録、置換表の照会、詰みの帯を参照する枝刈りの保護条件、および補正履歴の更新条件である。
`SearchSnapshot`は、根の時点の対局者ごとの攻撃連続数を審判層の状態から受け取る。

`search_move`は、着手を適用した局面が再現であり、規則がR1である場合に、「設計判断」の「周回の区間と攻撃側の判定」に従って攻撃側を求める。
攻撃側が着手した側なら負けの値を、相手側なら勝ちの値を返し、それ以外は現行どおり`DRAW_SCORE`を返す。
R1以外の規則では現行の処理を変えない。
反復で値を返すノードは、現行どおり置換表の照会より前に戻るので、置換表へ保存されない。

既知の近似は次のとおりである。
1回の再現で判定するので、可逆手12手の前提条件と出現回数は見ない。
区間は最も近い出現までとするので、R1が定める「最初の出現から」の区間より短いことがある。
専用の帯の値は置換表から打ち切りに使わないが、その値に基づいて選ばれた記録手は順序づけに使われ、祖先の値が通常の評価値の範囲へ戻った場合（たとえば攻撃側が周回を避けて別の手を選んだ結果の値）は、通常の値として置換表に残る。
後者は、周回を避けた結果の値であって周回の勝敗そのものではないが、周回が負けであるという経路依存の判断を前提にしている点で、経路依存の誤りを完全には除けない。
項目1を採用している場合は、裁定の瀬戸際の正確さを項目1が受け持つ。項目1が不採用の場合は、瀬戸際の保護がないので、根から2手先の裁定が置換表の打ち切りや枝刈りに隠れ得ることを既知の限界として[探索部](search.md)に記す。
項目1が反復勝ちの手だけに候補を絞った場合でも、項目2は最も近い出現までの区間で近似するので、その手の評価値が勝ちの値になるとは限らない。着手の選択は項目1の候補手で決まるので、対局の結果には影響しない。

## 実装フェーズ

### フェーズ1　根の合法手の分類関数

対局管理層に根の合法手の分類関数を追加し、「検証」の節の分類関数のテストを通す。
探索の入力はまだ変えない。
完了条件は、テストがすべて通ることである。

### フェーズ2　根の候補手の選別

`SearchSnapshot::from_game`へ選別を組み込み、「検証」の節の探索のテストを通す。
対局履歴に出現回数が3以上の局面がある対局の状態を用意し、選別1回あたりの所要時間を計測する。
完了条件は、テストがすべて通り、`bench`の総ノード数が段階開始版と一致し、選別1回あたりの所要時間がSTCの1手あたりの思考時間の1%（約1ミリ秒）以下であることである。
計測は、`bench`の計時がスナップショットの構築後から始まるので、`bench`とは別に行う。

### フェーズ3　記録局面での確認

`data/matches/movegen-speedup-2-stage7-9-ltc`（第2期高速化の最終LTC測定の保存記録。全着手と終局理由を持つ）にある反復負け184局について、負けた側の最後の着手の直前の対局の状態を、記録の着手列を`Game`へ適用して再構成する。
各局について、分類関数とは別に診断用に書く参照実装で、選別前の全部の合法手を分類する。
参照実装は、分類関数の結果と突き合わせる正解を作るための総当たりの手続きであり、探索局面キーによる絞り込みを使わない。
具体的には、根の合法手のそれぞれを`Game`の写しへ`Game::play`で適用し、終局しなければ相手の合法手のそれぞれをさらに適用して、反復勝ちの手の集合と反復負けに直結する手の集合を作る。
診断は一時的なコードで行い、差分と結果を測定記録`search-repetition-replay-diag`へ保存する。
完了条件は、184局のすべてで、分類関数が返す2つの集合が参照実装の集合と一致し、記録の着手（負けた側が実際に指した手）が反復負けに直結する手の集合に含まれることである。
集合の一致を求めるのは、安全な手を誤って除く不具合も検出するためである。
全部の合法手が反復負けに直結する局かどうかも参照実装の集合で判定し、その局数を記録する。

### フェーズ4　項目1の採否測定

フェーズ1から3までを通過した最終のコミットを候補、段階開始版を基準として、STC（`time=10000+100`、上限3,000ペア）とLTC（`time=60000+200`）の段階ゲートを標準コマンドで実行する。
測定名は`search-repetition-root-stc`と`search-repetition-root-ltc`とし、LTCのシードはSTCの基本シードから3,000以上離す。
過去の測定の所要時間から見積もると、STCは上限の3,000ペアまで走った場合に約8時間、LTCは1,000ペアあたり約7.5時間である。
真の差がH1と同じ10 Eloなら、LTCの期待ペア数は約2,600ペア（約19時間）である。
診断の件数から見ると、候補が攻撃側として負けていた局は全局の2%から3%であり、これが互角に近い勝負へ戻るとしても得点率の改善は1ポイント前後なので、真の差はH1と同程度かそれを下回る可能性がある。
その場合、STCは上限まで走り、LTCは4,000ペア（約30時間）を超え得る。
測定の終了後、[集計スクリプト](../measurements/search-repetition-outcome-diag/count.py)で候補と基準の反復負けの件数を数え、測定記録へ併記する。
候補の反復負けは、全部の合法手が反復負けに直結した局を除いて0件のはずであり、0件でなければ採否の前に原因を調べる。

### フェーズ5　項目2の発動の確認

採否測定の条件で項目2が着手の選択を変えるかを、測定の前に確かめる。
項目1の採否が確定した構成を基準とし、項目2を実装したビルドを候補とする。
標本は`data/matches/movegen-speedup-2-stage7-9-ltc`のペア番号の小さい順に20ペア40局とし、各局を初手から終局まで記録の着手で進めながら、手番が先手の局面をすべて探索させる。各ペアは同じ開始局面で先後を入れ替えた2局なので、先手の局面だけを取っても候補と基準の両方の立場が同数含まれ、探索の回数を半分にできる。
置換表は局の開始時に初期化し、局の中では保持するので、実際の対局と同じく前の手番の探索の内容が残った状態で数えることになる。
思考制限は固定ノード数とし、`Threads=1`で実行して結果を決定的にする。
ノード数は、保存記録の1手あたりの思考時間の中央値に`bench`のNPSを掛けた値を、STCの記録とLTCの記録のそれぞれから求め、2つの条件で別々に実行する。
固定ノード数は診断のためだけに使い、採否の根拠にはしない（[docs/guides/sprt.md](../guides/sprt.md)）。
数えるのは、再現を検出した回数、そのうち攻撃側が一方に定まった回数、攻撃的着手の判定を実際に計算した回数、および基準と最善手が変わった局面の数である。
評価値だけが変わった局面は、根の選択に影響していないので発動に数えない。
結果は測定記録`search-repetition-tree-activation-diag`へ保存する。
完了条件は、STC相当とLTC相当のどちらかの条件で、最善手が変わった局面が探索した局面の1%以上あることである。
1局は片側約240手なので、1%は1局あたり2手から3手に相当する。診断では反復による終局が全局の約7%であり、1局に1手未満しか着手が変わらない改良がこの頻度の事象の勝敗を測定可能な大きさで動かすとは見込めないので、1局あたり2手を下限の目安とした。
どちらの条件でも1%に満たない場合は、採否測定の条件で発動しないと判断して項目2を見送る。
STC相当で満たさずLTC相当でだけ満たす場合は、STCを省略してLTCへ直行し、その理由を測定の開始前に本書の状態へ記録する。

### フェーズ6　項目2の実装の仕上げ

フェーズ5のビルドを、「検証」の節の項目2のテストがすべて通る状態に仕上げる。
完了条件は、テストがすべて通り、`bench`のNPSの低下が基準の1%以内であることである。
項目2は探索木を変えるので、`bench`の総ノード数は基準と一致しなくてよい。
NPSの低下が1%を超えた場合は、攻撃的着手の判定の計算回数をフェーズ5の計数で確かめ、判定を動かした駒だけの捕獲手の生成へ絞る修正を1回だけ行って測り直す。
それでも1%を超える場合は、項目2を見送る。

## 検証

テストは仕様から期待値を導き、各テストの名前または説明にRULES.md第31条R1を引く。
対局履歴つきの局面は、少数の駒だけを置いた局面から双方が駒を往復させて同一局面を繰り返す着手列を`Game`へ適用して作る。
審判層の既存テスト（王駒だけの周回`kings_cycle`と、飛車が歩兵を照準し続ける周回）が同じ作り方をしている。

分類関数のテストは次のとおりである。

- 攻撃側が根の手番であり、周回を続ける着手が4回目の出現を生じさせる状態で、その着手が反復負けに直結する手に分類される。
- 攻撃側の着手の直後に相手が4回目の出現を完成させられる状態で、その着手が反復負けに直結する手に分類される。
- 前項と同じ構造で、周回の途中に別の手順を挟み、根の着手後の局面がまだ2回目の出現である状態でも、その着手が反復負けに直結する手に分類される。
- 相手が攻撃側であり、自分の着手が4回目の出現を完成させる状態で、その着手が反復勝ちの手に分類される。
- 双方が攻撃的着手を続けた周回と、どちらも続けていない周回では、4回目の出現を生じさせる着手がどちらにも分類されない。
- 可逆手が12手に満たない4回目の出現（じっとの往復による2手周期）ではどちらにも分類されず、可逆手が12手に達した後の出現では分類される。
- 根の着手が反復以外の理由（王駒の捕獲、駒枯れ、詰みなど）で対局を終わらせる場合、その着手はどちらにも分類されず、応手も調べられない。
- 反復勝ちの手と、相手の最後の王駒を取る手が同時にある状態で、反復勝ちの手だけが反復勝ちの手に分類される。
- 王手を受けた側が反復勝ちの手によって詰みを免れる状態（第21条第3項c）で、その手が反復勝ちの手に分類される。
- 分類の結果が、探索局面キーによる絞り込みを使わずに全部の合法手と応手を`Game::play`で適用した結果と、上記の全状態で一致する。
- 分類関数の呼び出しの前後で、元の`Game`の状態が変わらない。
- R2とR3の規則セットでは、どの手も分類されない。

探索のテストは次のとおりである。

- 反復負けに直結する手が、静的な形勢では最善に見える状態で、探索が別の手を返す。
- 反復勝ちの手がある状態で、探索がその手を返す。
- 全部の合法手が反復負けに直結する状態で、探索が合法手を返し、パニックしない。
- 対局履歴に出現回数が3以上の局面がない状態で、探索の結果とノード数が段階開始版と一致する。

項目2のテストは次のとおりである。

- 探索経路の中だけで完結する周回で、一方の着手だけがすべて攻撃的である場合、再現を生じさせる着手に、攻撃側から見て負け、相手側から見て勝ちの専用の帯の値が返る。
- 双方の着手がすべて攻撃的である周回と、どちらにも攻撃的でない着手がある周回では、`DRAW_SCORE`が返る。
- 周回が対局履歴へまたがる場合、履歴の側の判定が根の時点の攻撃連続数と一致し、履歴の側に攻撃的でない着手が1手あれば攻撃側と判定されない。
- 攻撃側に、攻撃的でない着手を挟んで同じ局面へ戻る手順があり、着手を切り替える地点が探索木の中にある局面で、探索がその手順の値（引き分け）を攻撃側の値として返す。
- 区間にnull moveが含まれる場合は`DRAW_SCORE`が返る。
- 区間より前にnull moveがある経路で周回が完結する場合、null moveを含めて再生した局面で攻撃側が正しく判定される。
- 再現を完成させる現在の着手が攻撃的でない場合、その対局者は攻撃側と判定されない。
- 専用の帯の値が置換表に記録されていても、照会はその値で打ち切らず、記録手だけを返す。詰みの帯の値による打ち切りは変わらない。
- 置換表に専用の帯の値が残った状態で対局履歴だけを変えて同じ局面を探索したとき、前の探索の反復の勝敗が打ち切りとして再利用されない。前の探索の値が引き分けの0であった場合は再利用され得ることを、既知の近似としてテストの説明に記す。
- 専用の帯の値は、記録したときと異なる探索手数で読み出しても帯の中にとどまる。
- 通常の評価値の最大の絶対値が、専用の帯の下端に届かない。
- 専用の帯の値に対して、null move pruning、futility pruning、SEEによる捕獲手の枝刈り、およびaspiration windowsの保護が詰みの帯と同じように働く。
- 探索値が専用の帯にある場合、詰みの帯と同じく補正履歴を更新しない。
- `Threads=2`で上記の最初のテストを10回連続して通す（[教訓](../lessons/repeat-concurrency-regression-tests.md)）。
- R2とR3の規則セットでは、`bench`の総ノード数と結果が基準と一致する。`bench`の局面では探索窓の端が専用の帯に入らないので、保護の閾値の変更は結果を変えない。

追加した回帰テストは、修正を一時的に外すと失敗することを確認する（[教訓](../lessons/confirm-regression-test-fails-without-fix.md)）。
完了前に`cargo test`、`cargo clippy`、および`bench`の総ノード数の照合を実行する。

## 完了条件

STCは候補をLTCへ進めるかどうかの振分けだけを行い、採用はLTCの判定だけが決める。
項目1の採用の条件は、LTCの判定が`H1`であり、エンジン異常、時間切れ、および拒否着手が0件であることである。
STCが`H0`の場合、STCが上限到達時に負のLLRで判定保留となった場合、またはLTCが`H0`の場合は不採用とする。
各項目の結論は、採用、不採用、見送りの3つのいずれかである。採用と不採用は測定の判定で決まり、見送りは測定を行わずに実装しないと決めた場合をいう。
項目2は、フェーズ5の発動の確認とフェーズ6の速度の基準を通過した場合は項目1と同じ条件で採用か不採用かを決め、どちらかを通過しなかった場合は見送りとして記録する。
2項目の結論が記録され、測定記録が保存され、フェーズ8の文書の更新が済んだ時点で状態を完了へ変える。

# テストスイートのspec-first再構築

本書は、既存ユニットテストを全廃し、仕様文書だけを期待値の根拠とするテストスイートへ再構築するマイルストーンの設計書である。
動機は、カバレッジは高いものの、仕様ではなく現在の実装や通るべき条件を写しているテストが多いという問題であり、2026年8月14日の全数棚卸しでこの問題の範囲と作業範囲を確定した。

## 原則

テストの目的は、意図された挙動からの逸脱を検出することであり、現在の実装を記述することではない。
この原則から、期待値の根拠は次の優先順位の証拠に限る。

1. RULES.mdおよび各領域の規範文書（docs/protocols/、docs/sprt.md、docs/plans/search.md ほか設計書の確定事項）
2. 外部プロトコル・外部実装との互換性契約（fishtest参照値、lishogi実棋譜、XBoard/HaChu駒文字表）
3. 確認済みの過去のバグと境界事例（棚卸しで特定した引き継ぎ資産）
4. 意図的な挙動を符号化していると確認できた既存テスト

現在の実装は「正しい挙動の証拠」として使わない。
規範文書から期待挙動を確定できない場合はSPEC_UNCLEARとして登録し、根拠を捏造したassertを書かない。
各テストは「挙動マトリクス（典拠、前提条件、期待される観測結果、境界・不正事例、性質）」を先に作成し、実装コードはマトリクス確定後に到達手段・フィクスチャ構築のためだけに読む。

## 棚卸しの要約（2026年8月14日、全357件）

内訳はlib 329件（core層208件、notation 36件、protocol 60件、search 17件、eval 2件、stats 6件）、binユニット25件、統合テスト3件である。

core層は約149件が条番号を名前に持つSPECテストであり、条文座標から期待升集合を導く参照実装（`ray_destinations`）など優れた構造を既に持つ。
一方で次の欠陥を確認した。

- 最大の穴は第9条（初期駒21種の動き）で、実装のPROFILESテーブル自身から期待値を再導出する自己参照テスト（`every_piece_control_matches_coordinate_reference`）しかない。成駒側（第10条）は7種すべて条文座標接地があるのと対照的である。
- zobrist分離・鍵構造体・privateフィールド直叩き・エラー文字列リテラル一致など、実装写し（IMPL）が全域で約60件ある。
- eval層の駒価値29定数はテスト内への丸写しであり、search.mdが出自とする HaChu `chuPieces[]` の元表がリポジトリ内に存在しないため、現状は追跡不能な数値の変更検知にしかなっていない。
- 未カバーの仕様も多い（第4条、第11条・第12条の細目、第26条の不合法手類型の大半、`estimate_elo`の全体、GSPRT境界値±2.944の照合など）。

## 再構築の範囲と方針

ユニットテスト全数（lib 329件＋bin 25件）を削除し、挙動マトリクスから書き直す。
統合テスト3件（tests/lishogi_replay.rs、tests/match_runner.rs）は既に外部オラクル接地（lishogi実裁定10局、sprt.mdの再現契約）であるため削除対象とせず、実装カップリング監査だけを行う。
`scripts/fetch_lishogi_replays.py`と`tests/fixtures/`も保全する。

テストの配置と命名は現行の規約を維持する。
すなわち、ファイル内`#[cfg(test)] mod tests`（movegenのみ分離ディレクトリ）、条番号・規範文書名を名前へ埋め込む命名（`article_14_1_...`）、`test_util`のプログラム的局面構築である。

### SPEC_UNCLEARの扱い

棚卸しで、実装挙動は意図的だが規範文書に明文がない事項を多数特定した。
これらは次の2通りに振り分ける。

- 規範文書の欠落・矛盾が原因のものは、所有文書へ最小限の規範文を追記してから、その文言に接地したテストを書く（文書補修）。フェーズ1で実施した補修は、feature `time`の値の食い違い決着（protocol-layer.mdへengine-connectivity.mdを正とする注記）、置換表の同世代同深さ保持の明文化、`movetime`と時計の併用則、深さ制約1〜256、停止理由5値の語彙（以上search.md）、駒価値29定数の凍結値表（HaChu variant.cの`chuPieces[]`原文と全駒照合のうえsearch.mdへ規範化）、sprt.mdの`--max-pairs`既定値の不一致修正である。棚卸しが欠落と報告した拡張SFEN第5欄文法とじっと代表升規約は、protocol-layer.mdに規範記述が既に存在することを確認した（補修不要）。
- それ以外は設計書末尾のSPEC_UNCLEAR登録簿に記録し、テストを書く場合は「実装契約」であることをテスト名またはコメントで明示する。

RULES.md本文の改訂は本マイルストーンの範囲外とする。
条文が沈黙する規則解釈（例: 第14条1項の隣接無条件と第15条1項の先獅子禁止の優先関係）は、採用中の解釈を登録簿へ記録して解釈固定テストとし、RULES.md第13版での明文化は今後の裁定事項として残す。

### 移行手順の統制と追跡台帳

削除と再実装は領域単位の1ステップで行い、領域の完了時点で`cargo test`全緑を確認してから次の領域へ進む。
これにより「旧テストが消え新テストが未実装」の窓が領域境界をまたいで残ることを防ぐ。
各領域の実装者は完了報告に追跡台帳（旧テスト名→対応するマトリクスID、または引き継がない理由）を含め、354件の全数がマトリクスの挙動か明示的な不採用判断のどちらかへ対応することを監査で確認する。

### 変異検証

各領域のテスト完成後、代表的なセマンティック変異（条件反転、`<`と`<=`の入替、境界定数の変更、必須副作用の除去、もっともらしい誤値の返却、検証分岐のスキップ）を実装へ一時適用し、新テストが検出することを確認する。
合格条件は、領域ごとに最低8件（上記6類型のうち3類型以上を含む）の変異を適用し、全件が検出されることとする。
生存した変異は挙動マトリクスへ差し戻し、オラクルの弱さか未カバー挙動かを判定して補強したうえで再適用する。
意味を変えない変異（等価変異）と判定した場合はその根拠を記録する。
cargo-mutantsが利用可能なら補助に使うが、判定の主体は手選の代表変異とする。

## SPEC_UNCLEAR登録簿

領域ごとの全登録（計63件）は [spec-first-tests/matrices/](spec-first-tests/matrices/) の各マトリクス末尾のSPEC_UNCLEAR節が正である。
ここには、実装・テストへ影響する裁定を行った項目だけを記す。

1. **隣接獅子の取り返しと先獅子の優先関係（D2）**: 第14条1項と第15条1項の衝突は条文に明文がない。着手ごとの足判定（第13条3項の「獅子捕獲後の升」への移動可能性）を採用解釈として固定した。帰結として、先獅子中の隣接獅子への取り返しは、停止形（足の利きが到達升に届く）は不合法、居喰い形（起点へ戻り足が届かない）は合法である。`articles_15_1_and_14_1_senjishi_blocks_even_an_adjacent_lion_recapture` がこの挙動のテストである。2026年8月24日のRULES.md第13版は第15条の解説段落で、先獅子の禁止が隣接獅子を獅子で取る着手にも及ぶことを明文化した（停止形の不合法は条文ベースとなり、着手ごとの足判定だけが補充規定として残る。D2の第13版追補）。
2. **拡張SFEN手数欄の`+1`受理（D5）**: u32のFromStrが先頭`+`を受理するため、protocol-layer.mdの整数文法から逸脱していた。スペック側を正として実装を数字列限定へ修正し、テストで固定した（本マイルストーン唯一のプロダクション修正。ほかに未使用となったテスト専用ヘルパ7件の削除がある）。
3. **movetime=0の受理（D7）**: 現実装は拒否せず、1ms下限へ丸めた即時打ち切り探索として合法手を返す。挙動が無害なため変更せず、断定もしない。search.mdへの拒否規定の追加は将来の裁定事項とする。
4. **先獅子が複数獅子に及ぶ範囲（D2、独立保護を解釈固定）**、**第21条3項cに駒枯れ勝利が算入されるか（D3）**、**内部密番号の順序の文書定義（D5）**、**estimate_eloの信頼区間構成（D8）** などは未裁定のまま登録簿に残り、該当テストは両解釈が一致する範囲だけを断定している。**P2の待機「1手」の単位と再不成後の再待機（D1）**は、2026年8月24日のRULES.md第13版がP2の本文を改訂したことで解消し、D1の第13版追補のとおりテストで断定している。

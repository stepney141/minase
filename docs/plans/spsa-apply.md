# SPSAの調整結果をソースへ反映するコマンドの設計書

## 先に読む要約

本マイルストーンは、SPSA（同時摂動確率近似法、[docs/plans/spsa.md](spsa.md)）で調整した係数の最終値を、通常ビルドのソースへ自動で書き込むコマンド `spsa_runner apply` を追加する。
minaseの探索と時間管理の係数は、`src/search/alphabeta/params.rs` にある1つの表に「名前、既定値、最小値、最大値」の形で並び、通常ビルドはこの既定値を定数として使う（以下、この表を単に**表**、その既定値を**表の既定値**と呼ぶ）。
SPSAのセッション（1つの実行ディレクトリに対応する調整の実行全体）は、終了時に各係数の最終値を画面へ表示するだけで、表は更新しない。
現行の手引き [docs/guides/spsa.md](../guides/spsa.md) は、人手で最終値を四捨五入して表の既定値へ書き写し、コミットしてから採否をGSPRT（勝敗から強さの差を逐次判定する統計検定、[docs/guides/sprt.md](../guides/sprt.md)）で判定する手順を定めている。
22個の値を手で書き写す作業は、転記の誤り、丸め規則の揺れ、および途中で止まったセッションや別の表に対する誤った適用を防げない。
`apply` は、実行ディレクトリの保存記録を再開時と同じ検査にかけて最終値を復元し、係数はすべて整数型なので四捨五入した整数で表の既定値だけを書き換える。
式と範囲を変えないのは、書き換えたソースをコミットした**候補のコミット**が、調整したときのソースである**調整対象のコミット**と係数の値だけで異なる状態を保ち、両者の対局による採否の測定が係数の効果だけを測るようにするためである。
表の名前、範囲、および開始値が保存記録と食い違う場合や、表に本書の書き換え規則で認識できない行がある場合は、何も書かずにエラーで終了する。
書き換えた後の確認は `git diff` で行い、候補のコミットを作って既存の採否の手順にかける工程は変えない。
完了条件は、`apply` が検査と書き換えのテストを通してmasterへ入り、手引きの採否の手順が `apply` を使う形へ改訂され、短い実セッションの実行ディレクトリから `apply` で候補のコミットを作れることである。

## 目的

SPSAの成果を通常ビルドへ取り込む工程を、保存記録から機械的に再現できる操作にする。
現行の手引きは、最終値の転記を人手の作業として残している。
この作業には次の4つの誤りの余地がある。
第1に、22個の数値を書き写すときの転記の誤りである。
第2に、丸め規則の揺れである。runnerは終了時に `f64::round` で丸めた整数も表示するが、手で書き写すときに別の規則を使っても検出できない。
第3に、候補にしてはならない実行ディレクトリの値を誤って適用することである。途中で止まったセッションの値は、設計したスケジュールの結果ではない。事前確認のセッション（本調整の前に、時間管理の係数を長く考える側の端へ置いて時間切れの有無を確かめる短いセッション。手引きの第3節）の値も、候補にしてはならない。
第4に、セッションを開始した時点と異なる表へ適用することである。表の既定値がセッションの開始値と違えば、調整した係数と書き込む先の係数の整合が失われている。そこへ最終値を書けば、候補と基準の差に係数の値以外の差が混ざり、採否の測定が係数の効果だけを測らなくなる。
`apply` は、第1から第3までを保存記録の検査によって、第4を表との照合によって機械的に排除する。
ただし表との照合が確かめるのはセッションに含まれる係数の整合だけであり、係数以外の変更の有無は判定しない。候補のコミットが調整対象のコミットから係数の値だけで異なることは、調整対象のコミットからブランチを切って `git diff` を確認する運用が保証する。
同種の自動転記は、やねうら王の `tune.py apply`、fishutils、およびRust製エンジンapeironの `spsa apply` が提供しており、[調査メモ](../research/spsa-parameter-application.md)で一次資料を確認した。

## 適用範囲

本マイルストーンでは、次の作業を行う。

- `spsa_runner` に `apply` サブコマンドを追加し、完了したセッションの実行ディレクトリから最終値を復元して表の既定値へ書き込む。
- 実行ディレクトリを開いて保存記録を検査する処理を、再開の処理から分けて `apply` と共有する。
- 検査、書き換え、および実際の表に対する解析のテストを追加する。
- docs/guides/spsa.md の「値の採否を判定する」の手順を、`apply` を使う形へ改訂する。

次の項目は対象外とする。

- gitの操作。ブランチの作成、コミット、および設計書の値の改訂は、`apply` の後に人またはエージェントが行う。
- 表の既定値以外の書き換え。式、範囲、文書コメント、および表への係数の追加や削除は扱わない。
- 途中のセッションからの適用。総反復数はセッションの開始時に固定されるので、全反復が完了した実行ディレクトリだけを受け付ける。
- 差分だけを表示する `--dry-run`。書き換えの確認は `git diff` で行う。
- 測定記録の生成。セッションの記録は手引きの第6節に従って別に書く。

本書の用語は spsa.md の定義に従い、次を加える。
**表**は `src/search/alphabeta/params.rs` の `parameters!` マクロの呼び出しに並ぶ係数の宣言をいい、各宣言は `名前(アクセサ名): 既定値, 最小値, 最大値;` の形の1行である。
**調整対象のコミット**はセッションが調整用ビルドをビルドしたコミットであり、採否の測定で旧エンジンとなる。
**候補のコミット**は、調整対象のコミットから表の既定値だけを変えたコミットであり、採否の測定で新エンジンとなる。
**開始値**はセッションでθが出発する値であり、本調整のセッションでは表の既定値と同じ値である。
**パラメーターファイル**は、セッションで調整する係数と開始値、範囲、および摂動幅を1係数1行で書いた入力ファイルであり、表の係数の一部だけを書くこともできる（手引きの第2節）。
spsa.md は、θの現在値を別のファイルへ持たず、`iterations/` の反復のファイルだけを保存記録の正としている。
**連鎖の検査**は、`spsa_runner` が再開時に保存記録へ既に行っている検査であり、反復のファイルの適用番号が1から連続すること、各反復の摂動の符号がシードから再現できること、および各ファイルに保存されたθが前の反復から更新則で再計算した値と一致することを確かめる。

## 依存関係

- spsa.md のフェーズ1からフェーズ3まで（係数の表、`harness` モジュール、および `spsa_runner`）がmasterへ入っていることを前提とする。
- 実行ディレクトリの形式は spsa.md の「保存と再開」の設計判断が所有し、本書は変更しない。
- 実行ディレクトリの排他ロックは `harness::lock_run_directory` を使う。`match_report` が保存記録の集計で同じロックを取る。
- セッションはrunnerのコミットを固定したworktreeから実行されるので、セッションを走らせたバイナリは本コマンドの追加より古いことがあり、その場合 `apply` を持たない。`apply` は本ブランチまたは統合後のmasterからビルドしたバイナリで実行し、再開と違ってrunnerのSHA-256の一致は求めない（理由は「設計判断」）。

## 設計判断

| 項目 | 決定 |
|---|---|
| コマンドの置き場 | `spsa_runner` のサブコマンド `apply` とする。既存の `params` サブコマンドと同じ置き方であり、実行条件の型、係数の型、および連鎖の検査を同じbinの中で再利用できる。やねうら王とapeironも、調整と反映を同じ道具の別コマンドとして提供する。`match_runner` へ足す案は、採否を判定する計器に係数の書き換えを持ち込むので採らない。別のbinにする案は、`spsa_runner` の内部型を公開する必要が生じるので採らない。 |
| 入力は実行ディレクトリ | 最終値は、runnerの標準出力ではなく、実行ディレクトリの `manifest.json` と `iterations/` から復元する。θの現在値を別のファイルへ持たないという spsa.md の設計に従い、反復のファイルに保存されたθも信用せずに、連鎖の検査が更新則から再計算した値を使う。 |
| 保存記録を意味の水準でも検査する | 再開では、パラメーターファイルの解析と `validate_settings` を通った実行条件との完全一致を要求するので、保存記録の中身の妥当性は呼び出し側が保証している。`apply` はパラメーターファイルを受け取らないので、`manifest.json` を読み込んだ後に、係数の検査（1つ以上あり、名前に重複がなく、最小値が最大値以下で、開始値が範囲内にあり、摂動幅と学習率が正の有限値であること）を適用し、続いて `validate_settings` をそのまま呼んで（反復数、1反復のペア数、および同時対局数が正で、計数が桁あふれせず、最初と最後の反復の摂動幅と学習率の導出値が有限で正であること）から連鎖の検査へ進む。検査の一部を書き写した別の実装は作らない。この検査を省くと、壊れた記録が更新則の再計算の途中でパニックし得る（[外部入力でパニックしない](../lessons/no-panic-on-external-input.md)）。 |
| 完了したセッションだけを受理する | 反復のファイルが1から総反復数まで欠番なく揃っていることを、連鎖の検査とは別に要求する。連鎖の検査は存在するファイルの適用番号の連続性を確かめるだけで、総反復数に達したことは検査しないからである。 |
| 実行中のセッションを拒否する | `lock_run_directory` で排他ロックを取ってから読む。runnerが動いている実行ディレクトリではロックの取得に失敗し、途中のθを読むことがない。ロックはロックファイルを作成するので厳密な読み取り専用ではないが、`apply` は `manifest.json` と反復のファイルを変更せず、再開時に行う書きかけの一時ファイルの削除も行わない。共有する読み込み処理は一時ファイルを無視し、削除は再開の側に残す。 |
| 書き換えの対象と方法 | 表の宣言を名前で探し、既定値のリテラルだけを置き換える。解析は「書き換え規則」で定める文法に従い、ファイル中にちょうど1つある `parameters!` の呼び出しの内側だけを対象にする。呼び出しの内側で、文書コメントでも宣言でもない行があればエラーとし、複数行に分かれた宣言も受け付けない。黙って読み飛ばすと、コメントの中の宣言に似た行を書き換えて成功と報告する事故が起こり得るからである。宣言の既定値以外の文字と、ほかのすべての行はバイト単位で変えない。ファイルを構造から生成し直す案は、文書コメントと並び順を保てないので採らない。やねうら王のように周辺のコードを目印にして数値を探す案は、目印の保守が要るので採らない。 |
| 棄却する代案：データファイルと`build.rs` | 表をTOMLまたはJSONへ移し、`build.rs` がアクセサ関数と調整用の宣言を生成する構成にすれば、`apply` は既存のパーサ（`toml_edit`など）で値を差し替えるだけになる。しかし、`build.rs` とコード生成の処理が増え（TOMLならパーサの依存も加わり、JSONならコマンド側は既存の `serde_json` で読める）、係数ごとの文書コメント（設計書への典拠）をデータファイルの欄へ移してコード生成でrustdocへ書き出す必要があり、表の構文をrustcがマクロで検査している現状の保証がコード生成へ移る。JSONはコメントを持てない。[調査メモ](../research/spsa-parameter-application.md)で確認したとおり、Hobbes、akimbo、Reckless、Viridithas、およびapeironのいずれも係数の定義をRustソースに置き、自動反映を持つやねうら王、fishutils、apeironの3例はいずれもソース中の定数の行を独自の規則で探して数値を置き換える。本書の方式はこの系譜に従う。 |
| 棄却する代案：パーサ生成器またはパーサコンビネータ | pest、nom、winnow、lalrpopなどで表の文法を定義する案は採らない。対象の文法は入れ子も再帰も持たない1行1宣言であり、`spsa_runner` が6欄のパラメーターファイルとUSIの宣言行を解析している既存の手書きの分割と同じ様式で書ける。現在の依存には正規表現ライブラリも含まれておらず、生成器の追加はクレートの監査、ビルド時間、およびMSRVの確認を増やす。配列の宣言や複数行の宣言を表に加えて文法が育った時点で置き換えを判断する。 |
| 範囲の照合 | セッションの範囲が表の範囲に含まれることを要求し、一致までは求めない。事前確認のセッション（「目的」）で時間切れが出た係数は、その端の値が安全でないことが分かったので、手引きは範囲を狭めてから本調整を始めると定めており、runnerも宣言より狭い範囲を受け付けるからである。丸めた整数は、セッションの範囲と表の範囲の両方に収まることを検査する。 |
| 開始値との一致を要求する | 表の既定値を `f64` に変換した値がセッションの開始値と厳密に等しいことを要求する。候補のコミットは、調整対象のコミットから係数の値だけを変えたものでなければならない（「目的」の第4の誤り）。事前確認のセッションは時間管理の4係数の開始値を表の既定値と変えて実行するので、この検査によって本調整と取り違えても拒否される。runnerは小数の開始値も受け付けるが、`apply` は整数の既定値と厳密に等しい開始値だけを認める。一致しない場合の上書きを許す切替は設けない。必要なら調整対象のコミットからブランチを切り直して `apply` をやり直す。 |
| セッションに含まれない係数 | パラメーターファイルから行を削って調整しなかった係数は、表の値を変えずに「セッションに含まれない」として報告する。これはrunnerの既存の機能に対応する扱いであり、表への係数の追加や削除ではない。セッションにあって表にない係数はエラーとする。 |
| 丸め | `f64::round`（四捨五入、0.5は0から遠い側へ）で整数にする。runnerが終了時に表示する整数と同じ規則である。θは更新則で範囲へ切り詰められているので丸めた整数も範囲に収まるが、`apply` は書き込む前に範囲を検査する。 |
| 書き込みの手順 | 書き換え後のファイルの内容をメモリ上で作り、同じ解析で読み直して各係数の既定値が整数と一致することを確かめてから、同じディレクトリの一時ファイルへ書いて改名で置き換える。検査はすべて置き換えの前に終わるので、失敗したときに表のファイルが変わらないことを保証できる。改名が確定の時点であり、改名の後のディレクトリの同期に失敗した場合は、ファイルが変わらなかったとは報告せず、書き込み後の失敗として報告する。ファイル全体を直接書く案は、書き込みの途中で止まるとコミットしていない変更を失うので採らない。 |
| `--source` は必須 | 表のパスに既定値を持たせない。runnerは固定したworktreeから実行されるので、カレントディレクトリからの相対パスを既定にすると、runnerのworktreeの表を黙って書き換える。 |
| コミットと設計書の改訂は手動 | `apply` はgitを操作しない。コミットメッセージにセッションの実行ディレクトリ名と調整対象のコミットを書き、来歴はgit履歴が持つ。表の文書コメントへ来歴を自動で書き足す案は、コメントが係数を定めた設計書を引いており、その改訂は採用が確定してから行うので採らない。 |
| runnerのSHA-256と作業ツリーの検査をしない | 再開はrunnerのSHA-256の一致を求めるが、`apply` は本来runnerより新しいバイナリで実行する。作業ツリーのコミットが調整対象と一致するかの検査は、gitの状態を読む機構を足すことになるので設けない。`apply` が確かめるのはセッションに含まれる係数の名前、範囲、および開始値の整合だけであり、候補のコミットが調整対象から係数の値だけで異なることは、手引きどおり調整対象のコミットからブランチを切って `git diff` を確認する運用が保証する。 |
| `--dry-run` を設けない | 書き換えの結果は `git diff` で確かめられる。差分の表示だけを行う経路を足すと、検査と書き換えの2つの経路を保守することになる。 |
| 候補のビルドの確認 | `apply` はエンジンをビルドしない。書き換えが調整用ビルドの宣言へ反映されたことは、手引きの手順で `spsa_runner params` を候補の調整用ビルドに対して実行し、既定値の欄が `apply` の出力した整数と一致することで確かめる。 |

## コマンドの契約

```console
spsa_runner apply --run-dir <実行ディレクトリ> --source <params.rsのパス>
```

`--run-dir` は `match_report` と同じく既存の実行ディレクトリを指す。
`apply` は次の順に処理し、いずれかの検査に失敗した場合は表のファイルを変えずに終了コード1で終了する。

1. 実行ディレクトリの排他ロックを取る。
2. `manifest.json` を読む。未知のフィールドは拒否し、「保存記録を意味の水準でも検査する」の検査を適用する。
3. `iterations/` の反復のファイルを読み（一時ファイルは無視する）、反復番号が1から総反復数まで欠番なく揃うことと、連鎖の検査を通ることを確かめ、最終のθを得る。
4. `--source` の表を解析し、セッションの各係数の宣言をちょうど1つ見つける。
5. 各係数について、セッションの範囲が表の範囲に含まれ、表の既定値がセッションの開始値と一致することを確かめる。
6. θを丸めて整数にし、セッションの範囲と表の範囲の両方に収まることを確かめる。
7. 書き換え後の内容をメモリ上で作り、同じ解析で読み直して各係数の既定値が整数と一致することを確かめる。
8. 一時ファイルへ書き、改名で表のファイルを置き換える。

標準出力には、係数ごとに `名前: start=開始値 final=最終値 integer=整数 changed` または `unchanged` を1行で出し、セッションに含まれない表の係数は `not in session` として出す。
最後に、書き換えた係数の数、変わらなかった係数の数、および対象のファイルのパスを1行で出す。

エラーは専用の列挙型で分類し、原因ごとに変種を持つ（[エラーを文字列へ失わない](../lessons/typed-errors-over-strings.md)）。
少なくとも、ロックの取得失敗、実行条件の不正、未完了のセッション、連鎖の検査の失敗、表の解析失敗（呼び出しの個数、認識できない行）、表に見つからない係数、表に複数回現れる係数、範囲の不整合、開始値の不一致、範囲外の整数、および書き換え後の読み直しの不一致を区別する。
実行ディレクトリと表は外部入力なので、パニックせずにエラーへ変換する。

## 書き換え規則

表の解析は次の規則に従う。

1. 前後の空白を除いた内容が `parameters! {` である行がファイル中にちょうど1つあり、その後に最初に現れる、前後の空白を除いた内容が `}` である行が呼び出しを閉じる。開始行が0個または2個以上なら解析失敗とする。字下げの量や開始行と終了行の字下げの一致は要求しない。行末の `\r` は認識時に無視し、書き戻しではそのまま保つ。
2. 呼び出しの内側の各行は、空白だけの行、先頭の空白を除いた部分が `///` で始まる文書コメントの行、または次の文法の宣言の行のいずれかでなければならない。それ以外の行（ブロックコメント、属性、複数行に分かれた宣言を含む）があれば解析失敗とする。
3. 呼び出しの外側の行は解析せず、変更もしない。

宣言の行の文法は次のとおりである。

```text
<空白>* <名前> "(" <識別子> ")" ":" <空白>* <整数> "," <空白>* <整数> "," <空白>* <整数> ";" <空白>*
```

整数は任意の符号を持つ10進のリテラルとし、3つの整数は順に既定値、最小値、最大値である。
書き換えは既定値の整数だけを新しい整数の10進表記で置き換え、行のほかの文字は変えない。
解析器は、`parse_parameters` と `declarations` と同じく標準ライブラリの文字列操作で手書きし、外部の解析ライブラリを使わない（理由は「設計判断」）。
解析はコンパイル済みの `PARAMETERS` ではなくテキストに対して行う。
`PARAMETERS` は調整用ビルドにしかなく、`apply` は通常ビルドの `spsa_runner` から、任意のコミットの表に対して動く必要があるからである。
現行の表は、連続する文書コメントの行を含めてこの規則に一致する。

`cargo fmt` はこの規則を破らない。
rustfmtは、`{}` で区切られたマクロ呼び出しの中身を宣言として整形しないが、字下げの作り直し、行末の空白の除去、および改行コードの変換は行い得る（確認の記録は[調査メモ](../research/spsa-parameter-application.md)の「rustfmtの扱い」）。
規則が字下げの量と一致を要求せず、行末の `\r` を無視し、宣言の行の内容だけを見るのは、これらの変更に影響されないためである。
`apply` が保証するのは書き込んだ時点のバイト列であり、後続の整形による変更は `apply` の契約の外にある。
規則2は、`parameters!` マクロ自体が受け付ける書き方より狭い。
将来、表に規則から外れた書き方の宣言を加えた場合は、`apply` と「検証」の解析テストが解析失敗で検出するので、その時点で規則か表のどちらかを改める。

## 手引きの改訂

docs/guides/spsa.md の「値の採否を判定する」の第1項を、次の内容へ置き換える。
調整対象のコミットからブランチを切り、`spsa_runner apply` を実行し、`git diff` で表の既定値だけが変わったことを確かめ、セッションの実行ディレクトリ名と調整対象のコミットを書いたメッセージで1つのコミットにする。
続いて `spsa_runner params --engine commit:<候補のコミット> --rules engine-default` を実行し、既定値の欄が `apply` の出力した整数と一致することを確かめる。
第2項以降（通常対局の事前確認と、STCとLTCのGSPRT）は変えない。

`apply` が拒否したときの対処は、原因ごとに次のとおり書く。
実行中のセッションはロックの取得に失敗するので、セッションの終了を待つ。
未完了のセッションは、手引きの第5節の手順で再開して完了させる。
表の不一致（見つからない係数、範囲の不整合、開始値の不一致）は、調整対象のコミットからブランチを切り直して `apply` をやり直す。
実行条件の不正と連鎖の検査の失敗は保存記録の破損を意味するので、個別のJSONを編集せずに原因を調べる。

## 検証

フェーズ1の単体テストは、runnerのテストが使う実行ディレクトリの作成手順で作った記録に対して、エンジンを起動せずに行う。

- 3個程度の係数を持つ表の写しと完了済みの実行ディレクトリに `apply` を実行し、既定値のリテラルだけが置き換わり、ほかのすべての行がバイト単位で同じであることを固定する。あわせて、`manifest.json`、反復のファイル、および置いておいた一時ファイルのバイト列が変わらないことを固定する。
- 未完了の検出を連鎖の検査と独立に固定する。反復のファイルが1つもない実行ディレクトリと、総反復数の1つ手前まで揃った実行ディレクトリの両方で、未完了のエラーになることを固定する。連鎖の検査は途中で切れた記録の連続性を確かめるだけなので、この2例がなければ完了の検査を省いても通ってしまう。
- 全反復が揃っているが保存θを書き換えた実行ディレクトリで、連鎖の検査のエラーになることを固定し、`apply` が連鎖の検査を呼ぶことを確かめる。
- `manifest.json` の1反復のペア数を0にした場合と、最小値と最大値を逆にした場合に、実行条件の不正のエラーになることを固定する。
- 名前が表にない場合、名前が表に2回現れる場合、セッションの範囲が表の範囲からはみ出す場合、既定値が開始値と違う場合、呼び出しの内側に宣言に似たブロックコメントの行がある場合、および宣言が2行に分かれている場合に、エラーの分類が期待どおりであり、表のファイルが変わらないことを固定する。
- 開始行より浅い字下げの文書コメントと宣言、開始行と字下げの異なる終了行、行末の空白、および `\r\n` の改行を含む表に対して、解析が成功し、既定値以外のバイト列（`\r` を含む）が保たれることを固定する。
- テスト内でロックを保持した実行ディレクトリに対して、ロックの取得失敗で終了することを固定する。
- セッションに含まれない係数が変わらず、`not in session` として報告されることを固定する。
- 丸めの規則を、小数部が0.5の値と負の値を含む最終値で固定する。
- 実際の `src/search/alphabeta/params.rs` を解析し、解析が成功して全宣言の既定値が最小値以上かつ最大値以下であることを固定する。表に規則から外れた行を書けば、このテストが解析失敗で検出する。

フェーズ2の実セッションでの確認は、自動テストではなく手順として実行し、完了したことと確認日を状態の節に書く。

- 調整用ビルドで反復数と1反復のペア数を小さくした短いセッションを固定深さで実行し、その実行ディレクトリに `apply` を実行して候補のコミットを作る。
- 候補の作業ツリーで `cargo fmt --check` が通り、`cargo build` と `cargo build --features tuning` の両方で通り、候補のコミットに対する `spsa_runner params --engine commit:<候補のコミット> --rules engine-default` の既定値の欄が `apply` の出力した整数と一致することを確かめる。`params` は `commit:` 指定を調整用ビルドでビルドするので、通常ビルドを別に用意する必要はない。
- 同じ実行ディレクトリを、既定値を1つ変えた表に対して実行し、開始値の不一致で拒否されることを確かめる。

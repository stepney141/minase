# SPSAによる探索係数と時間管理係数の調整の設計書

## 先に読む要約

本マイルストーンは、探索と時間管理に埋め込まれた数値係数を、自己対局の勝敗から自動で調整する仕組みをminaseへ導入する。
調整にはSPSA（simultaneous perturbation stochastic approximation、同時摂動確率近似）を使う。
SPSAは、全係数を同時に正負どちらかへ少しずらした2つの設定を対局させ、勝った側の向きへ全係数の中心値を少し動かす操作を、数千回繰り返す最適化手法である。
係数が何個あっても1回の反復に必要な設定は2つだけなので、1局の測定が高価で勝敗のノイズが大きいゲームAIに向き、Stockfishとやねうら王が探索係数の調整に使っている。
minaseの係数は現在すべてソースコード中の定数であり、値は診断用の計測から決めたもので、対局結果から調整したことはない。
本書は3つの部品を定める。
第1は、係数を1つの表に定義し、通常ビルドでは定数のまま、調整用ビルドでだけUSI（将棋系エンジンとGUIの間の通信規約）の`setoption`で変更できるようにするマクロである。
第2は、対局ハーネス`match_runner`の対局実行部を共有して、SPSAの反復を回す新しいコマンド`spsa_runner`である。
第3は採否の手順であり、SPSAが返した値を定数としてコミットし、調整前のコミットとの自己対局をGSPRT（勝敗から強さの差を逐次判定する統計検定、[docs/guides/sprt.md](../guides/sprt.md)）にかけて判定する。
SPSA中の対局結果は採用の根拠にしない。
完了条件は、通常ビルドの探索が1ノードも変わらないことを確認した基盤がmasterへ入り、最初の調整セッションの値についてGSPRTの採否が確定することである。

## 目的

minaseの探索係数は、各段階の設計書が診断から1つずつ決めた値である。
診断とは、固定局面集を探索して、枝刈りが働いた割合（発動率）や、浅く読んだ結果が本来の深さの結果と食い違った割合を数える計測をいう。
これらの指標は棋力そのものではなく棋力の代理であり、対局の勝敗で確かめた値ではない。
診断は係数を1つずつ決めるので、ある係数を変えると別の係数の最適値が動くという相互作用も見ていない。
一方、係数の候補値を1つずつGSPRTにかける方法は、1件のLTC（長時間条件）の判定に数十時間を要する。
20個を超える係数のそれぞれについて複数の候補値を試すと、測定の合計が数か月になるので、この方法は使えない。
[棋力測定の所要時間削減](match-cost-reduction.md)は、この問題への対処としてSPSAを挙げ、別の設計書として起案すると定めていた。
本書がその設計書である。

時間管理の係数も対象に含める。
2026年9月21日の利用者の決定による。
`src/search/mod.rs`の`clock_budget`のコメントも、係数の変更は自己対局で採否を判定すると定めている。

## 適用範囲

本マイルストーンでは、次の作業を行う。

- `src/search/params.rs`を新設し、調整対象の係数を1つの表で定義するマクロと、cargo feature `tuning`を追加する。
- `src/search/mod.rs`と`src/search/correction.rs`の対象係数を、表が生成するアクセサ関数の呼び出しへ置き換える。`src/eval/pst.rs`がPSTの復号時に計算しているdelta pruningの余裕値は、探索側で計算する形へ移す。
- `src/protocol/usi.rs`に、調整用ビルドでだけ働く調整用オプションの宣言と受理を追加する。
- `src/bin/match_runner.rs`の対局実行部を、ライブラリのモジュール`harness`へ移す。別のbinから使うので`pub`とし、`#[doc(hidden)]`を付けて公開APIの文書には載せない。
- 新しいコマンド`src/bin/spsa_runner.rs`を追加する。
- 手引き docs/guides/spsa.md を新設し、最初の調整セッションを実行して、結果の値の採否を判定する。

次の項目は対象外とする。

- 評価関数の重み。PST（駒種と升の組ごとの評価値の表）の27,360個の重みは勾配法の学習が扱い（[docs/guides/pst-training.md](../guides/pst-training.md)）、SPSAの対象にしない。
- 小さな整数の適用条件。`depth >= 3`のような深さの閾値、LMRの減深量の上限3、最善手の安定を判定する反復数4は、1段階の変化が大きく、摂動幅を連続的に縮められないので初回は対象にしない。OpenBenchの手引きはこの種の係数を調整が壊れやすいものとして注意している。
- 構造を決める定数。表の寸法、killer手の数、停止検査の間隔、およびLazy SMPの補助ワーカーの深さ間隔は対象にしない。
- 秒読みの項の係数。理由は「対象の係数」の節に書く。
- 時間切れを防ぐ安全余裕の30 ms。探索の外で生じる遅れは測定機と負荷に依存するので、自己対局の勝敗で調整すると測定機に固有の遅れへ過適合する。
- 複数の測定機へ対局を配る分散実行。

本書の用語は次のとおりである。
**係数**は調整対象の数値、**θ**は全係数の現在の中心値の組をいう。
**反復**はSPSAの更新1回分であり、θから作った2つの設定**θ+**と**θ−**の対局と、その結果によるθの更新からなる。
**セッション**は、1つの実行ディレクトリに対応する調整の実行全体をいう。
cargo featureは、Rustのビルド時にコードの一部を有効または無効にする切り替えである。
**調整用ビルド**は`--features tuning`を付けてビルドしたminaseであり、**通常ビルド**は付けないminaseである。
配布とlishogiのBotに使うのは通常ビルドだけであり、調整用ビルドはセッションの対局にだけ使う。
**調整用オプション**は、調整用ビルドがUSIの`setoption`で受け付ける係数の設定項目をいう。
**ペア**は、同一の開始局面で先後を入れ替えて指す2局をいう。
**STC**は短時間条件`time=10000+100`、**LTC**は長時間条件`time=60000+200`であり、どちらも[docs/guides/sprt.md](../guides/sprt.md)が定める。
`time=10000+100`は、持ち時間10秒に1手ごとの**加算**0.1秒を足す時間制御を表す。
**秒読み**は、持ち時間が尽きた後も1手ごとに使える時間であり、STCとLTCは秒読みを使わない。
**soft**は反復深化の境界で探索を止める目安の時間、**hard**は探索の途中でも打ち切る上限の時間である。
**NPS**は1秒あたりの探索ノード数、**bench**は固定局面集を固定深さで探索するコマンドである。

## 設計判断

| 項目 | 決定 |
|---|---|
| 係数の公開方式 | 係数を`src/search/params.rs`の1つの表に定義し、マクロが係数ごとにアクセサ関数を2通り生成する。通常ビルドの関数は既定値のリテラルを返すだけの`#[inline]`関数であり、調整用ビルドの関数は`static`な`AtomicI32`を読む。Rust製チェスエンジンのHobbesとakimboがこの形を採る。`unsafe`を使わないので、`Cargo.toml`の`unsafe_code = "forbid"`と両立する。Recklessは調整用ビルドで`static mut`を使うので採らない。 |
| 棄却する代案：ソースへの一時パッチ | やねうら王の`tune.py`は、調整の開始時にC++ソースの定数を変数とUSIオプションへ書き換え、終了時に定数へ書き戻す。目的は通常版のソースを調整用の変数で汚さないことである。Rustではマクロとfeatureで同じ目的を達成できるので、周辺のコードを照合してパッチを当てる道具を別に保守する理由がない。 |
| 棄却する代案：常時USIオプション | dlshogiは探索係数を平時からUSIオプションとして公開し、SPSAのスクリプトは`setoption`を送るだけで済む。Viridithasも実行時の構造体に係数を常時保持する。minaseでこの形を採ると、通常ビルドの探索の内側に実行時の読み出しが常駐し、lishogiのBotやGUIに20個を超える調整用オプションが見える。通常ビルドは定数のままとする。 |
| 棄却する代案：外部の調整サーバー | fishtestとOpenBenchはチェス用の対局管理ツールで対局を実行するので、中将棋の規則を判定するminaseの審判層を使えない。更新則だけを借りる。 |
| 係数の表現 | 係数はすべて`i32`とする。小数と粗い単位は、挙動を変えない整数表現へ書き換える。LMRの除数2.0は、100倍した整数の200で持って使用時に100で割り（以下、この表現を百分率と呼ぶ）、歩兵価値の倍率で持つ余裕値は歩兵価値に対する百分率とする（半歩兵単位の`[1, 3, 3]`は`[50, 150, 150]`）。null moveの減深量`2 + depth / 6`は、分母1,200の固定小数点で`(切片 + depth × 傾き) / 1200`と表し、切片2,400と傾き200で現行の式と厳密に一致させる。各式の型と演算の順序は「整数表現」の節で確定する。 |
| 係数を読む時点 | 係数から導く値は、調整用オプションが確定した後、すなわち探索の生成時か使用時に計算する。現行のdelta pruningの余裕値は、minaseがUSIの入力を読む前に埋め込みPSTを復号する時点で`2 × 歩兵価値`として計算され、`OnceLock`に保持される。この計算をアクセサへ置き換えるだけでは、後から届く`setoption`が反映されない。そこで余裕値は探索の生成時に歩兵価値と係数から計算する。フェーズ1では、全係数について、既定値と異なる値が探索または時間予算の計算に実際に反映されることを係数ごとのテストで固定する。 |
| 調整用オプションの名前と受理 | オプション名は`Tune_`に係数名を続けた形とし、型は`spin`、既定値と範囲は表から生成する。範囲外の値と、最初の`go`より後の変更はエラーの情報行を返して拒否する。LMRの減深量表はプロセス内で1回だけ生成されるので、探索を始めた後に除数が変わると表と係数が食い違うからである。ハーネスはエンジンを局ごとに起動し直し、`setoption`を`isready`の前に送るので、この制約の下で表は必ず調整値から生成される。 |
| 調整ループの置き場 | 新しいコマンド`spsa_runner`とする。`match_runner`にSPSAのモードや側ごとの`setoption`の引数を足す案は採らない。`match_runner`は採否を判定する計器であり、採否の測定が係数を注入した状態で実行される余地を、CLIの段階で残さないためである。 |
| 対局実行部の共有 | `match_runner.rs`のうち、エンジンプロセスの起動と通信、1局の進行、1ペアの実行、開始局面の生成、コミットのビルドとキャッシュを、これらが使うプレイヤーの設定と対局記録の型とともに、ライブラリのモジュール`harness`へ移す。`rng`と`stats`と同じく`#[doc(hidden)]`を付けた`pub`モジュールとし、公開APIとは扱わない。`missing_docs`の警告の下にあるので、移す項目には文書コメントを付ける。プレイヤーの設定には、握手の後に送る`setoption`の列を加える。`match_runner`はこの列を常に空で使う。2つのbinが同じファイルを`#[path]`で取り込む案も成立するが、ライブラリに置けば単体テストの実行が1回で済み、`rng`と`stats`の置き方とも揃うので採らない。 |
| 対局の構成 | 各反復で、同じ調整用ビルドのバイナリにθ+とθ−を与えて直接対局させる。1反復は8ペアとし、各ペアは既存のペア構造（同一開始局面の先後入替）をそのまま使う。1反復8ペアはOpenBenchの既定値であり、反復番号を8ペアごとに1つ進める数え方もOpenBenchと同じである。fishtestは反復番号をペアごとに進めるが、総ペア数が同じなら、学習率の総和に結果を掛けた移動量の期待値は両者でほぼ等しい。dlshogiの調整スクリプトは基準エンジンとの対局も併用するが、θ+とθ−の差だけが更新に必要な情報なので採らない。 |
| 更新則 | fishtestとOpenBenchに共通する式を使う（「更新則」の節）。ハイパーパラメーターは両者の既定値に合わせ、α = 0.602、γ = 0.101、A = 反復数の0.1倍、`r_end` = 0.002、`c_end` = 係数の範囲の1/20とする。`c_end`と`r_end`は係数ごとにパラメーターファイルで上書きできる。 |
| 整数への丸め | θは実数で保持し、対局へ渡すときだけ`floor(x + u)`で確率的に丸める。`u`は区間[0, 1)の一様乱数であり、ペアごとに係数ごとに1つ引いて、θ+とθ−に同じ値を使う。θ+とθ−に同じ乱数を使う点はOpenBenchと同じである。OpenBenchは整数の係数の摂動幅に下限0.5も設けるが、確率的な丸めだけで勾配の情報は保たれるので、この下限は採らない。単純な四捨五入では、摂動幅が1未満になった係数でθ+とθ−が同じ整数になり、その係数の勾配の情報が失われる。 |
| 並列実行と更新の順序 | 同時対局数の範囲で複数の反復を並走させ、反復が完了した順にθを更新する。後から発行する反復は、発行の時点のθを使う。fishtestと同じ非同期の更新である。時間制御の対局はもともと完全再現の対象外なので、更新の順序が実行ごとに変わることは新しい制約にならない。 |
| 乱数とシード | 対局のシードは、1つの基本シードの下で「反復番号×1反復のペア数＋ペア番号」を通し番号として派生させる。摂動の符号と丸めの乱数は、基本シードと反復番号から決定的に作る反復ごとの乱数列から引く。対局の通し番号とは重ならない番号の空間から派生させる。乱数が反復番号だけで決まるので、保存する乱数の状態はなく、中断した反復をやり直しても同じ符号と同じ開始局面になる。基本シードを複数使わないので、隣接シードの衝突は起こらない。 |
| 異常の扱い | エンジン異常、時間切れ、および不正着手は、`match_runner`と同じく起こした側の負けとして更新に使う。係数の値が原因の異常は、その向きが悪いという正しい情報だからである。手数上限に達したペアは更新に使わない。件数はセッションの要約に出力し、0でなければ採否の測定へ進む前に原因を調べる。 |
| 保存と再開 | 実行ディレクトリに、実行条件の`manifest.json`と、完了した反復を1反復1ファイルで置く`iterations/`を持つ。`manifest.json`は、調整用ビルドのコミットとSHA-256、パラメーターファイルの内容、ハイパーパラメーター、1反復のペア数、時間制御、規則、シード、同時対局数、測定機、およびrunnerのSHA-256を持つ。反復のファイルは、反復番号k、更新を適用した順番を表す適用番号、摂動の符号、各ペアへ渡した整数値、各局の結果、および更新後のθを持ち、`match_runner`のペア記録と同じく一時ファイルからの改名で原子的に書く。反復番号kは発行の時点で決まり、摂動幅、学習率、対局のシード、および乱数はすべてkから決まる。非同期の実行では完了の順序が発行の順序と入れ替わるので、反復番号と適用番号を区別する。θの現在値を別のファイルへ持たず、反復のファイルだけを正とするので、2つのファイルの書き込みの間で止まって記録とθが食い違うことがない。再開時は`manifest.json`の完全一致を検査し、適用番号が最大のファイルの更新後のθを現在値として、ファイルのない反復番号だけを発行し直す。発行済みで未完了だった反復の対局は捨てる。発行し直す反復は、同じkの摂動幅と乱数を使い、θだけが再開の時点の値になる。総反復数はハイパーパラメーターの式に入るので、再開時に変更できない。 |
| 棋譜の保存 | 異常で終わった局に限り、着手列、各手の実測時間、および時計の再構成に必要な残り時間の列を保存する。全局の着手列は保存しない。SPSAの対局は採否の根拠にならず、監査の対象は異常の原因だけだからである。時間切れの原因は着手列だけでは調べられないので、時計の情報も残す。 |
| パラメーターファイル | 1行が`名前, 開始値, 最小, 最大, c_end, r_end`の6欄であり、fishtestの入力形式と同じである。`spsa_runner`の`params`サブコマンドが、調整用ビルドの握手に現れた`Tune_`オプションから既定のファイルを生成する。エンジンに一覧を出力する専用のコマンドは足さない。セッションの開始時に、ファイルの全係数がエンジンの宣言にあり、範囲が宣言の範囲に収まることを検査する。minaseは未知のオプションを黙って無視するので、この検査がなければ、名前を誤った係数が対局に反映されないまま更新される。 |
| 採否 | SPSAの最終値を四捨五入して表の既定値へ書き込んだコミットを候補とし（書き込みは`spsa_runner apply`が行う。設計は[spsa-apply.md](spsa-apply.md)）、調整対象のコミットを基準として、標準のSTCとLTCのGSPRTで判定する。StockfishとRecklessのコミット記録も、調整値を定数にしてからSTCとLTCのSPRTを通している。候補は全係数の値を1組として扱う。不採用のときに一部の係数だけを選び直して再測定することは、LTCの結果を見た後の主張の追加に当たるので行わない。 |
| 調整の時間制御 | STCで調整する。fishtestの手引きは、短い時間制御は速い近似に、長い時間制御は長時間対局での値のよさに向くと述べる。LTCの処理能力は1時間あたり約150ペアであり、同じペア数の調整にSTCの数倍の時間を要するので、最初のセッションの採否を見てから別に判断する。短時間で調整した値が長時間で通用するかどうかは、採否のLTCが判定する。 |
| 探索係数と時間管理係数の同時調整 | 1つのセッションで同時に調整し、1組の候補として採否を判定する。探索の効率が変われば最適な時間配分も変わるので、両者には相互作用がある。セッションを分ける案は、調整の時間が2倍になるので採らない。不採用の場合に原因の群を特定できない点は受け入れる。 |
| 基盤と値の切り離し | フェーズ1からフェーズ3までの成果は、通常ビルドの挙動を変えない測定基盤なので、セッションの採否と切り離してmasterへ入れる。値が不採用になった場合は、値だけを捨てる。 |

## 対象の係数

最初のセッションの対象は、次の22個である。
表の群の欄は係数が属する探索手法であり、各手法の内容は「依存関係」の節に挙げた各段階の設計書が説明している。
futility pruningは、静的評価に余裕値を足しても探索窓の下限に届かない静かな手を読まずに捨てる枝刈りである。
aspiration windowは、前の反復の評価値の周りの狭い窓で探索を始め、外れたら窓を広げてやり直す手法である。
null move pruningは、手番を渡しても評価値が十分に高い局面を、浅い探索で確かめて打ち切る枝刈りである。
historyは、打ち切りを起こした静かな手の統計であり、手の順序付けとLMRの減深量に使う。
delta pruningは、静止探索（捕獲手だけを読む末端の探索）で、取る駒の価値に余裕値を足しても窓に届かない捕獲手を捨てる枝刈りである。
範囲は、既定値の0倍から2倍をStockfishの`TUNE`の既定に倣って基本とし、0で割る係数、0が無意味な係数、および安全のために上限を抑える係数は個別に定めた。
起案時の点検では、整数表現への書き換えで挙動を保てない係数は見つかっていない。

| 群 | 係数 | 現行値 | 範囲 |
|---|---|---|---|
| LMR（late move reductions、後順位の手の減深） | 対数積を割る除数の百分率 | 200 | 100〜400 |
| LMR | 減深量を増減するhistory値の閾値 | 128 | 0〜512 |
| futility pruning | 残り深さ1、2、3の余裕値の百分率 | 50、150、150 | 各0〜400 |
| SEE pruning（静的交換評価による枝刈り） | 残り深さ1、2、3の余裕値の百分率 | 0、200、0 | 各0〜400 |
| aspiration window | 初期の窓幅の百分率 | 50 | 10〜200 |
| aspiration window | 失敗時の拡大率の百分率 | 200 | 125〜400 |
| null move pruning | 減深量の切片（1,200分率） | 2,400 | 1,200〜4,800 |
| null move pruning | 減深量の傾き（1,200分率） | 200 | 100〜400 |
| history | 全体を半減する上限 | 16,384 | 4,096〜65,536 |
| correction history（静的評価の補正） | 補正値の上限の百分率 | 200 | 50〜400 |
| correction history | 更新の重み（1,024分率） | 32 | 8〜128 |
| 静止探索 | delta pruningの余裕値の百分率 | 200 | 50〜500 |
| 時間管理 | 1局に見込む手数`EXPECTED_PLIES` | 450 | 250〜700 |
| 時間管理 | 残り手数の下限`MIN_MOVES` | 100 | 40〜200 |
| 時間管理 | 加算のうち1手に使う割合の百分率 | 70 | 30〜100 |
| 時間管理 | hardをsoftの何倍までとするかの百分率 | 400 | 150〜800 |
| 時間管理 | hardを残り時間の何%までとするか | 25 | 10〜50 |
| 時間管理 | 次の反復の所要時間を見積もる比の百分率 | 250 | 150〜400 |

百分率で表す余裕値は、埋め込みPSTの歩兵価値に対する割合である。
historyの更新量`depth²`は対象にしない。
更新量、LMRの閾値、および半減の上限の3つは、全体を定数倍しても探索がほぼ変わらないという近似的な冗長性を持つ。
半減が整数の除算なので厳密な不変性ではないが、3つを同時に動かすと同じ効果の向きが複数でき、対象の個数だけが増える。
そこで更新量を固定し、残りの2つを調整する。

時間管理のうち秒読みの項の係数（秒読みの8割を使う割合と、序盤の係数の4と40）は、最初のセッションに含めない。
STCとLTCは秒読みを使わないので、`clock_budget`の秒読みの項は常に0になり、これらの係数をどう変えても探索時間は変わらない。
θ+とθ−の強さに差が生じないので、SPSAの更新は勝敗の偶然の偏りだけでこれらの係数を動かし、値は根拠なく漂うことになる。
秒読みの項を調整するには秒読みつきの時間制御のセッションが別に要るので、実施するかどうかは最初のセッションの結果を見てから判断する。
hardを残り時間の割合で抑える項は、[打ち切り上限は残り時間の割合でも抑える](../lessons/cap-hard-limit-by-remaining-fraction.md)に従って式に残し、範囲の上限を50%とする。

## 整数表現

各係数の式の型と演算の順序を次のとおり確定する。
いずれも既定値で現行の式と一致する。
`p`は歩兵価値を表す。

| 対象 | 式 | 注意 |
|---|---|---|
| LMRの除数 | `f64::from(値) / 100.0`を除数とする。 | 整数の除算を先に行わない。 |
| futility、SEE、初期の窓幅、補正値の上限、delta pruningの余裕値 | `p * 値 / 100` | 乗算を先に行う。`p / 100 * 値`は一致しない。 |
| 窓幅の拡大 | 幅を`i64`で`幅 * 値 / 100`と計算し、その後に`i32`へ飽和させる。 | 現行の`saturating_mul(2)`と一致させるため、乗算の途中で飽和させない。 |
| null moveの減深量 | `(切片 + depth * 傾き) / 1200` | 切片2,400と傾き200で`2 + depth / 6`と厳密に一致する。 |
| correction historyの更新 | `差分 * depth.min(8) * 値 / 1024` | 値32で現行の`/ 32`と一致する。`値 / 1024`を先に計算しない。 |
| 加算の割合、hardの残り時間の割合 | `u128`のまま`increment * 値 / 100`、`remaining * 値 / 100` | 値70と25で現行の`* 7 / 10`と`/ 4`に一致する。 |
| hardとsoftの比 | `soft_raw * 値 / 100` | 値400で現行の`* 4`に一致する。 |
| 次の反復の所要時間の比 | `開始時刻 * 値 <= 上限 * 100`の交差積で比べる。 | 除算による切り捨てを加えない。 |

null moveの切片と傾きは固定小数点で持つが、実際の減深量は整数である。
このため、切片が1,200の倍数をまたぐと、多くの深さで減深量が一斉に1変わる。
SPSAの摂動はこの不連続をまたぐことがあるので、合成目的関数の試験には階段状の応答を持つ係数を1つ含める。

## 更新則

総反復数をN、反復番号をk（1から数える）、係数iの終了時の摂動幅を`c_end_i`とする。

```text
A     = 0.1 × N
c_i,k = c_end_i × N^γ / k^γ
a_i,k = r_end × c_end_i² × (A + N)^α / (A + k)^α
θ+    = clip(θ + c_k ∘ flip)        flip_i は ±1 の一様乱数
θ−    = clip(θ − c_k ∘ flip)
D     = 反復内の全局にわたる（θ+側の勝ち数 − θ+側の負け数）
θ_i  ← clip(θ_i + (a_i,k / c_i,k) × D × flip_i)
```

`flip`は、係数ごとに独立に引いた+1または−1を並べた組であり、反復ごとに引き直す。
`∘`は係数ごとの積を表す。
`clip`は係数ごとの範囲への切り詰めである。
摂動幅は反復の最初に`c_end`の約2.1倍（N = 1,500のとき）から始まり、最後に`c_end`へ縮む。
引き分けと、手数上限で破棄したペアはDに寄与しない。
1反復は8ペアの16局なので、Dは−16から16までの整数である。

## 調整セッションの規模と所要時間

最初のセッションは、総ペア数12,000（1,500反復×8ペア）、時間制御STC、`Threads=1`、`USI_Hash`は既定の256 MB、同時対局数16とする。
所要時間は約32時間と見積もる。
根拠は、[strength-stage8-see-capture-stc](../measurements/strength-stage8-see-capture-stc.md)が同じ測定機の同時対局数16で496ペアに4,697秒を要したことであり、1時間あたり約380ペアになる。
fishtestの既定の60,000局（30,000ペア）では約79時間になる。
総ペア数は開始時に固定し、途中で延長しない。

この規模で期待できる移動量を、更新則から概算する。
係数の範囲の幅をWとすると、1反復の更新量は終了時に`0.0001 × W × D`であり、全反復の学習率を合計すると、Dの期待値が一定の場合の移動量は`0.2226 × W × E[D]`になる。
ある係数を有利な向きへ摂動した側が一定のElo差だけ強いと仮定すると、結果は次のとおりである。

| 有利な摂動によるElo差 | 12,000ペアの期待移動量 | 30,000ペアの期待移動量 |
|---|---|---|
| 1 Elo | 範囲の約1.0% | 範囲の約2.6% |
| 5 Elo | 範囲の約5.1% | 範囲の約12.8% |
| 10 Elo | 範囲の約10.3% | 範囲の約25.6% |

勾配がない係数が勝敗の偶然だけで動く量の標準偏差は、引き分けのない独立な16局を仮定すると、12,000ペアで範囲の約2.4%、30,000ペアで約3.8%である。
実際の値は、ペア内の相関、引き分け、範囲の端での切り詰め、および他の係数との相互作用で変わる。
したがって12,000ペアのセッションは、現行値の近傍で数Elo以上の勾配を持つ係数を動かす規模であり、範囲の全体を探索する規模でも、22個の係数の収束を保証する規模でもない。
最初のセッションはこの規模で実行し、得られた移動量と採否の結果から次のセッションの規模を決める。
θの履歴が終盤に動かないことだけを、収束の証拠として扱わない。

セッションの実行コマンドは次の形とする。

```console
cargo run --release --bin spsa_runner -- \
  --run-dir data/spsa/<セッション名> --seed <シード> \
  --engine commit:<調整対象コミット> --params <パラメーターファイル> \
  --rules engine-default --each time=10000+100 --concurrency 16 \
  --iterations 1500 --pairs-per-iteration 8
```

`--engine`の`commit:`は、`match_runner`と同じ手順で当該コミットを展開し、`--features tuning`を付けてビルドして、通常ビルドとは別のキーでキャッシュする。
セッションは、runnerのコミットを固定したworktreeから実行する。

## 実装フェーズ

### フェーズ1　係数の表とマクロ

`src/search/params.rs`、feature `tuning`、および調整用オプションを実装し、対象の係数をアクセサ関数へ置き換える。
完了条件は次のとおりである。
通常ビルドと、既定値のままの調整用ビルドの両方で、深さ6のbenchの局面ごとのノード数、最善手、および評価値が変更前と一致する。
benchの既定の深さ3では、深さ5から働くaspiration windowの書き換えを検査できないので、深さ6を使う。
null moveの減深量は深さ0から256までの全値で、時間予算の式は丸めの境界を含む入力の格子で、書き換えの前後の値が一致することを単体テストで固定する。
固定深さのbenchは時間管理を通らないからである。
通常ビルドのNPSは、3回の中央値が変更前の99%以上である。
1%の差を判定できるように、測定は性能コアへ固定し、ほかの負荷のない状態で、変更前と変更後を交互に実行する。
調整用ビルドのNPSを同じ方法で測り、通常ビルドに対する比を記録する。
全係数について、既定値と異なる値が計算に反映されることのテストが通る。
通常ビルドの`usi`の応答に`Tune_`オプションが現れない。

### フェーズ2　対局実行部の移設

`match_runner.rs`の対局実行部を`harness`モジュールへ移し、プレイヤーの設定に`setoption`の列を加える。
完了条件は、`match_runner`の既存のテストがすべて通り、固定シードと`depth`制限の`elo`モードの出力（経過時間の行を除く）が移設の前後で一致することである。
`match_runner`のCLIと保存形式は変えない。

### フェーズ3　`spsa_runner`と検証

`spsa_runner`と`params`サブコマンドを実装し、「検証」の節の合成目的関数の試験と煙試験を通す。

### フェーズ4　最初のセッションと採否

段階9の採用構成を取り込んだmasterの先頭を調整対象として、docs/guides/spsa.md を書き、セッションを実行する。
セッションの記録を docs/measurements/ へ置く。
セッションの前に、時間管理の係数を範囲のうち最も長く考える側の端に置いた設定で時間切れが起こらないことを確かめる。
具体的には、hardの残り時間の割合50、hardとsoftの比800、残り手数の下限40、および次の反復の所要時間の比150を開始値とするパラメーターファイルで、13反復（104ペア）の短いセッションを同時対局数16で実行する。
時間切れが1件でも出た場合は、原因を調べて該当の係数の範囲を狭めてから、本番のセッションを始める。
現行の安全余裕30 msは、探索の外の遅れが36 msに達して時間切れになった記録があるとおり、範囲の端での安全を保証しない。

最終値を表の既定値へ書き込んだコミットを作り、採否の前にSTCの条件の煙試験を行う。
合格の条件は時間切れとエンジン異常が0件であることであり、あわせて、総思考時間の調整前に対する比、終局時の残り時間、手数帯ごとの完了深さ、および停止理由の分布を記録する。
時間の使い方が変わること自体は調整の目的に含まれるので、これらの値は合否の条件にせず、採否の結果を解釈するための記録とする。
その後、標準のSTCとLTCで採否を判定する。
採用した場合は、係数を定めている各設計書の値を改訂する。

## 検証

- 更新則の単体テストは、N、k、`c_end`、`r_end`の組に対する`c_k`と`a_k`を、fishtestの`spsa_workflow.py`の式で別に計算した参照値と照合する。
- 確率的な丸めのテストは、多数回の丸めの平均が元の実数に収束することと、θ+とθ−が同じ乱数を使うことを固定する。
- 合成目的関数の試験は、エンジンを起動せずに`spsa_runner`の更新ループだけを検査する。実際の対局では係数の真の最適値が分からず、更新ループが正しく収束するかを確かめられないので、最適値を自分で決めた人工の強さの関数を使う。各係数の最適値が既知の2次関数でEloを定め、θ+とθ−のElo差から勝敗を乱数で生成して、1,500反復の後のθが開始値より最適値へ近いことを複数のシードで確かめる。試験の条件は次のとおり事前に定める。係数は22個とし、うち1個は階段状の応答を持たせる。開始値は最適値から範囲の20%だけ離す。Eloの曲率は、開始値でθ+とθ−の間に係数1個あたり約5 Eloの差が生じる大きさとする。距離は範囲の幅で正規化する。合格の基準は、20本のシードのうち18本以上で、正規化した距離の全係数にわたる平均が開始時より小さくなることとする。この基準が更新則の概算（5 Eloで範囲の約5%の移動、偶然の変動が約2.4%）と整合することを、実装時に1回だけ確かめてから固定する。stats.rsのモンテカルロ検証と同じく、通常のテスト実行から外す。
- 煙試験は、調整用ビルドと少数の反復で、対局が進行し、異常が0件であり、中断と再開の後に反復のファイルが欠番なく揃うことを確かめる。パラメーターファイルに存在しない係数名を書いた場合と、通常ビルドを`--engine`に渡した場合に、開始時の検査がエラーで終了することも確かめる。
- 符号の検査は、対局結果からDと更新量を作る経路に模擬の結果を渡して、決定的に行う。ペアの第1局と第2局で先後が入れ替わっても、θ+の側が常に勝つ模擬の結果ではDが正の最大値になり、各係数が`flip`の向きへ動くことを固定する。θ−の側が常に勝つ結果、引き分けだけの結果、および手数上限で破棄したペアを含む結果も同じく固定する。
- 再開の検査は、完了の順序が発行の順序と逆転した状態、反復のファイルの書き込み途中、および書き込みの直後の3つの時点で強制終了した実行ディレクトリを作り、再開後に更新の二重適用と欠落がないことを確かめる。
- 実エンジンによる向きの診断として、LMRの除数だけを対象にし、開始値を範囲の上端の400に置いた短いセッションを実行して、θの動きを記録する。除数が大きい領域では減深量表がθ+とθ−で同じになり勾配が消えることがあるので、この診断は合否の条件にしない。
- 調整用オプションのテストは、範囲外の値と、最初の`go`より後の変更が拒否されることを固定する。

# NNUE教師生成を探索結果を変えずに速くする設計書

## 先に読む要約

NNUE（着手ごとに差分で更新できる小さなニューラルネット）の教師は、自己対局の各局面を2万ノードで探索して作る。
vast.aiの生成機（AMD EPYC 9654の2基構成、384スレッド）で、現行の生成は試走時の版の約3分の1の速さに落ちており、1億局面に約20時間かかる。
本書は、同じシードから同じ教師ファイルが得られる変更だけで、生成機の時間あたりの記録局面数を現行の2倍へ近づける。
探索結果が変わらないので棋力は落ちず、教師の品質も変わらない。
調査の結論は次のとおりである。
遅い主因はメモリ待ちではなく命令数であり、ノードあたりの命令数が試走時の版の1.87倍になっている。
コンパイラのインライン閾値を上げるだけで命令数が12.5%減り、手生成、王手判定（gives_check）、反復検出、手の順位付けには、同じ結果を安く求める余地が残る。
これとは別に、生成機では本（教師の1ファイル）の終わりに最長の対局を待つ間、計算資源の約11%が遊んでいる。
完了条件は、探索結果の一致を検査で確かめ、生成機で探索速度と記録局面数の比を実測し、段階ゲートの判定を経て利用者が採否を決めることである。

## 目的

2026年11月4日の第1世代の生成は1本（7,500局）に約29分かかり、試走の見積もりの2倍以上になった。
利用者は、強さを損なわずに現在の教師生成を2倍くらいに速くすることを求めた。
先行測定は[単独スレッドの比較](../measurements/adhoc/teacher-single-thread-profile-20261104.md)と[3つの変更の評価](../measurements/adhoc/teacher-nonzero-optimization-20261104.md)であり、後者の改善は7.33%にとどまった。

本書で使う語を次のとおり定める。

- **本**：教師の生成の単位である1ファイル。1本は7,500局である。
- **生成機**：教師の生成のためにvast.aiで借りる計算機。
- **報告ノード**：探索が着手を適用した回数。2万ノードの上限はこれを数える。
- **探索結果の一致**：同じ入力に対して、局面別のノード数、最善手、評価値、および生成した教師ファイルがバイト単位で同じであること。
- **代理環境**：測定機の12本のE-coreで同時12局を動かす測定条件。1スレッドあたりのキャッシュ量が生成機に近く、旧版と現行版の速度比が0.36で、生成機の0.33に近い。

## 適用範囲

対象は次のとおりである。

- ビルド設定（`.cargo/config.toml`）。
- `crates/minase-core/src/movegen/`の合法性判定、王手判定、手生成、利きの逆引き。
- `crates/minase/src/search/alphabeta/`の反復検出、手選択器、静止探索の初期化、SEE（静的交換評価）。
- `crates/minase/src/eval/nnue/accumulator.rs`の差分更新。
- 生成機での本の始め方とNUMAの扱いの提案。スクリプトは[世代反復](nnue-generation-reset.md)の担当なので、本書では測定と提案までとする。

次の事項は対象外とする。

- 探索木を変える変更（探索の係数、表の大きさ、枝刈りの条件）。教師のノード数の変更。
- `unsafe`による先読み（[ADR](../adr/do-not-prefetch-transposition-table-entries.md)）とPGO。いずれも利用者の決定により提案しない。
- 履歴表を疎にする案。読み出しの93%は対局内で既に更新された行と駒種に当たるので速くならない。
- 置換表の縮小。代理環境で16 MiBを2 MiBまで縮めても、ノードあたりのサイクル数は減らなかった。
- mimallocの環境変数。代理環境で`MIMALLOC_PURGE_DELAY=-1`、`MIMALLOC_ALLOW_LARGE_OS_PAGES=1`、`MIMALLOC_ARENA_EAGER_COMMIT=1`の差は0.4%以内で、`MIMALLOC_RESERVE_OS_MEMORY=4GiB`は8%遅くなった。生成機のカーネル時間は全CPU時間の1%未満で、大きなページは常駐メモリの93%に効いている。

## 設計判断

| 判断 | 採る方式 | 棄却した代案と理由 |
|---|---|---|
| 探索結果 | 教師ファイルのバイト一致を保つ変更だけを行う | 探索木を変える案は、固定ノードの棋力を対局で確かめる必要があり、教師の品質の検証に世代単位の時間がかかる。 |
| インライン閾値 | `-C llvm-args=-inline-threshold=1000`を全ビルドに適用する | 閾値400は効果が小さく（サイクル−8.7%）、2500はこれ以上減らない。個別の`#[inline(always)]`は保守の手間が増える。`panic=abort`は差がなかった。 |
| 反復検出（repetition detection） | 対局履歴のキーを探索開始時にビットフィルタへ登録し、一致の可能性があるときだけ従来の線形走査を行う | [線形走査のADR](../adr/check-repetition-by-linear-scan.md)は現行の評価関数と長い履歴での再測定を求めている。現行では全サイクルの5%であり、走査の結果は変えない。`HashSet`は1回の照会が重い。 |
| 王手判定（gives_check） | 動かす駒の遮蔽なしの到達範囲で直接の王手を先に否定し、移動元、経由升、および到達升が王駒の8方向と5×5近傍から外れる手には、ノードで1回求めた既存の利きの有無を使う | ノードごとの全手の前計算は、1ノードで数手しか判定しない場合に損をする。 |
| 合法性の判定 | 特殊駒以外の置換表の手とkiller手は、駒1枚の全手を生成せず、利き、獅子の規則、および成りの選択肢を直接調べる | 結果を2回使い回すだけでは1回あたり約1,000サイクルの費用が残る。 |
| 静かな手の順位付け | 手選択器が1段階で65手を採点して54手を取り出す実態に合わせ、同じ移動元の間で駒ごとの値を使い回し、相手の利きの集計から確保と整列を除き、整列キーを小さくする | 採点を遅らせる案は、子探索中の履歴更新を拾って順序が変わる。 |
| 本の末尾 | 次の本を早めに始めて重ねる案を測定結果とともに世代反復の担当へ提案する | 1本の局数を増やす案は、途中で失う量と検査の単位が変わる。 |

先行実装の調査では、Stockfish（`../stockfish`）のMovePickerが全静かな手を採点してから`partial_insertion_sort`で一部だけを整列し、`Position::gives_check`が直接の王手を`check_squares`で先に判定し、開き王手を`blockers_for_king`で判定していることを確かめる。
本書の王手判定は同じ考え方であり、中将棋では走り駒と2段階移動があるので、線と近傍の判定に置き換える。

## 負荷の内訳

下表は、インライン閾値と3つの小変更を入れた版を、完局までの2対局（2,300万ノード）について、呼び出し元とインライン展開を解決して集計した包含サイクルの割合である。
呼び出し回数は同じ条件で数えた報告ノードあたりの値である。

| 処理 | 包含の割合 | 回数/報告ノード | 主な無駄 |
|---|---:|---:|---|
| 静止探索の全体 | 32.5% | 0.712 | 下の各項を含む。 |
| 利きの逆引き`attackers_to_by` | 9.5% | 1.3以上 | 8方向を毎回調べる。 |
| SEE | 8.1% | 1.266 | 利きの逆引きが大半である。 |
| 静止探索の初期化 | 7.9% | 0.312 | 全自駒の捕獲可能升を毎回求める。 |
| NNUEの出力 | 7.4% | 0.640 | 入力の93%が非零なので疎な計算は効かない。 |
| 置換表の照会 | 6.6% | 1.18 | 大半がキャッシュミスである。 |
| 静かな手の採点 | 6.2% | 4.25 | 手ごとに駒の情報を引き直す。 |
| 静かな手の生成 | 5.8% | 0.092 | 手ごとに獅子と成りの規則を調べる。 |
| 反復検出 | 5.2% | 0.730 | 平均342件の対局履歴を毎回走査する。 |

## 実装フェーズ

### フェーズ1：ビルド設定と既存の3変更

インライン閾値を上げ、[先行の評価](../measurements/adhoc/teacher-nonzero-optimization-20261104.md)の3変更を取り込む。
完了条件は探索結果の一致と全テストの成功であり、終えている。

### フェーズ2：委任する3つの作業

3つの作業は編集するファイルがほぼ分かれるので、それぞれ別のworktreeで並行して委任し、委任元が1つずつ取り込む。

- **作業A（探索の帳簿）**：反復検出のフィルタ、ノードごとの`Vec`確保の除去、NNUEの複写と更新の一本化。
- **作業B（`minase-core`）**：合法性の直接判定、王手判定の高速化、手生成の規則判定の省略、捕獲生成と静止探索の初期化の絞り込み、利きの逆引き。
- **作業C（手選択器）**：駒ごとの値の使い回し、相手の利きの集計の簡素化、整列キーの縮小、killer手の遅延生成。

各作業の完了条件は、探索結果の一致、全テストの成功、および委任元の交互測定で増分が親の幅を超えることである。

### フェーズ3：生成機での確認

利用者の許可を得て、生成機で現行版と候補を同時384局で比べる。
NUMAノードごとの2プロセスと本の重ね方も、同じ機会に測る。

### フェーズ4：段階ゲート

探索結果が同じでも、持ち時間の対局では速度の分だけ強くなるはずなので、[測定の手引き](../guides/sprt.md)に従って候補とmasterのSTCとLTCを実行する。
測定機の混雑に応じて、開始の時期は利用者と決める。

## 検証

委任元と委任先は次を実行する。

- 探索結果の一致：`target/teacher-speedup/verify/verify_identical.py`で、`dev bench --depth 9`の全局面、2通りのシードの教師ファイルのSHA-256、および6通りの規則セットの固定ノード探索を基準版と比べる。
- 全テスト：`cargo test -p minase -p minase-core`、`cargo fmt --check`、`cargo clippy`。
- 高速経路の試験：従来の遅い経路を試験側の参照として残し、乱数対局の局面と全規則セットで一致を確かめる。獅子の捕獲制限、先獅子、および成り権保留は固定例でも試験し、[置き換えの教訓](../lessons/pin-rule-exceptions-when-replacing-generation-with-attacks.md)に従って誤りを入れて失敗することを確かめる。
- 速度：[交互測定の教訓](../lessons/alternate-speed-rounds-against-parent.md)に従い、性能コアでの単独スレッドと代理環境で親と交互に5回測る。

## 完了条件

探索結果の一致を保ったまま、生成機の時間あたりの記録局面数を現行比で測り、段階ゲートの判定が出て、利用者が統合を判断した時点で完了とする。
2倍は目標であり、探索結果を変えずに届かない場合は、達した倍率と残りの差を埋める探索木の変更の候補を示して利用者に判断を求める。

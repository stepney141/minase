# 時間管理の変更の分解測定

## 先に読む要約

本書は、[持ち時間の効率的な使用](time-management-efficiency.md)の最終候補（第0段階から第3段階までを積んだコミット3087d1d）が段階ゲートのSTC（短時間の自己対局による逐次検定。[棋力測定の手引き](../guides/sprt.md)）で`H0`となった結果を受け、どの段階が棋力を下げたかを分けて測るマイルストーンの設計書である。
元の設計書は利用者の決定により段階ごとの測定を行わず最終コミットだけを測ったので、段階ごとの効果は分からない。
本書は、第1段階だけの候補、第1段階から序盤の係数を外した候補、の順にSTCで測り、棄却の原因を第1段階の予算の再定義、序盤の係数、第3段階の係数のいずれかに絞る。
各候補は元のブランチのコミットを組み替えた新しいコミットとして作り、いずれも着手前のコミットee3fd60と比べる。
完了条件は、原因を1つの段階または係数に特定する測定記録が揃い、次に採る候補（または採らない結論）が決まることである。

## 状態

起案。2026年9月18日に起案し、着手日は未定である。
着手には利用者の承認を要する（STC1本あたり同時対局数16で最長約8時間）。
次の一手は、候補D1のコミットの作成である。

## 目的

最終候補の棄却の原因を、第1段階の予算の再定義（hard = targetと途中結果の採用）、序盤の係数w、第3段階の局面適応の係数のいずれかに特定し、時間管理の改善で残せる部分を決める。

## 適用範囲

対象は、[持ち時間の効率的な使用](time-management-efficiency.md)のブランチ`time-management-efficiency`にある各段階のコミットの組み替えと、そのSTC測定である。
探索や評価の新しい変更は含めない。
置換表の2つの修正（作成または消去の後に未使用の置換表の消去を省く0a3a9b3、既定容量の置換表を`isready`で確保する3087d1d）は探索の返す着手を変えないので、すべての候補に含める。

## 依存関係

- [持ち時間の効率的な使用](time-management-efficiency.md)の設計判断と測定記録（[STC](../measurements/time-management-efficiency-stc.md)、[最終診断](../measurements/time-management-efficiency-after.md)）が前提である。
- 採否測定は[docs/guides/sprt.md](../guides/sprt.md)の段階ゲートに従う。

## 設計判断

| 判断 | 内容 |
|---|---|
| 候補の順序 | D1は第1段階だけ（第0段階、第1段階、置換表の2修正）、D2はD1から序盤の係数を外したもの（`w = 1`）とする。D1が`H1`またはLLRが0以上の保留なら原因は第3段階にあり、D1が`H0`ならD2を測って序盤の係数を切り分ける。D2も`H0`なら原因は予算の再定義（hard = targetと途中結果の採用）にある。第3段階だけの候補（第1段階なしで係数を入れる構成）は、第3段階が第1段階のhard中断を前提とするので作らない。 |
| 時間切れの原因の扱い | STCで候補側に出た2件の時間切れは、第3段階のhard（`5·(remaining / moves_to_go + 0.7·increment)`）が残り時間の割合で抑えられず、持ち時間を使い切った後に安全上限−30 msだけで指したことによる（[打ち切り上限は残り時間の割合でも抑える](../lessons/cap-hard-limit-by-remaining-fraction.md)）。D1とD2はhard = target（1手の消費が公平な分担そのもの）なので持ち時間を使い切らず、この経路には入らない。第3段階を再び候補にする場合は、hardに`remaining / 4`の項を戻す修正を前提とし、本書の範囲外で別に起案する。 |
| 序盤の係数を疑う理由 | STCの対局は初形から8〜12手進めた局面で始まり、そこでの係数は0.3〜0.4なので、候補は最初の約14手を基準の3〜4割の予算で読む。序盤の係数は5分＋秒読み10秒のような人間向けの時間制御での消費を絞る目的で入れたものであり、STCの条件では純粋な不利として働き得る。この効果はLTCでも同じ手数に及ぶが、その割合は小さい。 |
| 測定条件 | 各候補を着手前のコミットee3fd60と標準のSTCで比べ、`H1`またはLLRが0以上の保留の候補だけをLTCへ進める。同時対局数は測定機が空いている場合に16とし、`time_forfeits`が1件でも出れば停止して原因を調べる。 |
| コミットの作り方 | D1は`ee3fd60`から`0dd134c`（第0段階）、`551ea76`（第1段階）、`0a3a9b3`（消去の省略）、および`3087d1d`の`isready`の変更だけを順に適用した新しいブランチのコミットとする。D2はD1の上で`clock_budget`の序盤の係数を外す1コミットとする。単体テストの期待値もそれぞれの構成に合わせる。 |

## 実装フェーズ

### フェーズ1　候補D1のコミットと煙試験

D1のブランチを作り、`cargo test`と固定深さのbenchを通し、`time=9000+0,byoyomi=300`の10ペア煙試験で時間切れ0件を確認する。

### フェーズ2　D1のSTC

標準のSTCで判定し、`docs/measurements/time-management-decomposition-d1-stc.md`へ記録する。`H0`ならフェーズ3へ、そうでなければ第3段階が原因と結論してフェーズ4へ進む。

### フェーズ3　候補D2のコミットとSTC

D1から序盤の係数を外したD2を作り、同じ手順で測って`-d2-stc.md`へ記録する。

### フェーズ4　結論と次の起案

原因の段階を特定し、残せる構成があればそのLTCと採用を別に起案する。元の設計書とissue #7へ結論を追記する。

## 検証

- 各候補のbench総ノード数と単体テストの通過。
- 各STCの`time_forfeits`、エンジン異常、拒否着手が0件であること。

## 完了条件

D1（必要ならD2）のSTCの記録が揃い、棄却の原因が1つの段階または係数に特定され、次の起案の有無が決まっていること。

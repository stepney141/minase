# 持ち時間の効率的な使用（issue #7）

## 先に読む要約

本書は、GitHub issue #7「持ち時間制にて思考時間を使いすぎている」を解決し、あわせて時間管理をStockfishとYaneuraOuが持つ構造へ改めるマイルストーンの設計書である。
issueの症状は、持ち時間5分と秒読み10秒の対局で初手に約15秒を使い、その後も同様に長考して持ち時間をすぐ使い切ることである。
minaseの探索は反復深化（深さ1から1ずつ読みを深める外殻）であり、時間管理は1手の標準予算softと打ち切り上限hardの2つの時間で行う（[探索部](search.md)の「時間管理」節）。
原因は、現行の時間管理がsoftを「次の反復を始めてよいかの門」としてしか使わず、門を通った最後の反復が完了するまで打ち切らないことにあり、hardはsoftの4倍に置かれて実際にはほとんど働かないため、1手の思考時間は最後の反復の所要時間で決まってsoftの1倍から2.8倍に散り、秒読み局面では逆に予測の規則（経過時間の2.5倍がhardを超えると次の反復を始めない規則）が働いて秒読みの4割前後しか使えない。
StockfishとYaneuraOuも標準予算と上限の二段構えだが、探索途中で止めても根の各手の結果を保持して完了した手の中の最善手を採り、予算の半分を過ぎたら次の反復の深さを抑え、予算に評価値の下落や最善手の入替などの局面の信号を乗算し、minaseはこの3つの機構を持たない。
本書は、根の探索結果を保持する表を入れた上で、途中結果の採用と予算の再定義（序盤の係数を含む）、深さの抑制、局面適応の係数の3段階を順に実装し、深さの抑制と係数は採否測定の前にbenchで発動を確かめ、最終コミットと着手前のコミットを1組の標準のSTCとLTC（[棋力測定の手引き](../guides/sprt.md)が定める短時間と長時間の自己対局測定）のGSPRT（同手引きの逐次検定）で判定する。
予算式の係数（残り手数の見積り、加算の0.7倍、秒読みの0.8倍、安全余裕30 ms）は探索部の設計書が定めた現行値であり、本書は変えず、序盤の消費を絞る係数を1項だけ加える。
第1段階で各手の思考時間は予算を超えなくなり、序盤の係数により初手は約0.9秒、自分の19手目以降で満額（issueの条件で約9.3秒）になり、秒読み局面は秒読みの8割を使う。
持ち時間が序盤で尽きること自体は、既存エンジンの調査（[秒読みつき時間制御における既存エンジンの持ち時間配分](../research/time-management-byoyomi-survey.md)）で確認した参照実装と同じ配分の帰結として受け入れ、温存する配分は採用しない（毎手予算どおりに使う計算では自分の43手目に尽き、実際の手数は診断で数える）。
秒読みつきの挙動は時計の診断と煙試験で確認してGSPRTは行わず、完了条件は、最終コミットのLTCの採用、issueの条件での初手が予算内に収まること、全手が予算の許容幅内に収まること、および時間切れ0件である。
結果は不採用であった。時計の診断は全項目を満たしたが、最終コミットはSTCで`H0`となり、加算つきの時間制御で候補側に2件の時間切れが出た（[STC](../measurements/time-management-efficiency-stc.md)）。

## 目的

持ち時間制および秒読みつきの時間制御で、1手の思考時間が予算を超えず、秒読みの取りこぼしと着手が確定した局面での消費をなくし、局面の信号に応じて予算を伸縮させる。
issue #7の2つの指摘のうち、初手と各手の長考、秒読みの取りこぼし、および合法手が1つの局面の消費は第1段階で解決し、「深く読むべき時には深く、浅く読めば十分な時にはすぐ返す」柔軟性は第2段階と第3段階で扱う。
最初の数手で秒読み相当の時間を使う消費は、既存エンジンに倣った序盤の係数で絞る（「設計判断」の「序盤の係数」）。
持ち時間が序盤で尽きること自体は参照実装と同じ配分の帰結であり、本書では変えない（「設計判断」の「持ち時間の温存を採用しない理由」）。

## 適用範囲

対象は次のとおりである。

- `src/search/mod.rs`の`clock_budget`、`should_start_next_iteration`、`search_root`、`search_iteration`、`run_main_worker`、`select_worker_outcome`、および根の探索結果を保持する新しい表。
- `src/protocol/usi.rs`の最終`info`の出力条件と、対局中に持ち越す直前の手の評価値。

- `scripts/clock_profile.py`と、削除済みブランチから復元する診断スクリプト（[初形の実測](../measurements/time-management-efficiency-probe.md)の「参考」）。

対象外は次のとおりである。

- 評価関数、根以外の探索の手順（枝刈り、延長、手順前後）、およびLazy SMP（複数のワーカーが1つの置換表を共有して並列に反復深化を行う方式。[Lazy SMP](lazy-smp.md)）のワーカー構成。
- 目標時間の式の既存の係数と残り手数の見積り。序盤の係数の追加は対象である。
- 時計の規則。本書は、持ち時間が残る間は思考時間の全額を持ち時間から引き、尽きた手から秒読みを与える時計（lishogiと対局ハーネスの規則）を前提とし、秒読みを先に消費する方式には対応しない。
- Lishogi-Botの`move_overhead`と受け付ける時間制御の範囲（[lishogi Bot接続](lishogi-bot.md)の運用パラメータ）。
- 秒読みの安全余裕（`0.8·byoyomi`と30 ms）の引き上げ、およびYaneuraOuの秒単位の切り上げ（lishogiの時計はミリ秒単位なので不要）。
- 秒読みの複数回（periods）の扱い。
- 対局ハーネスの保存記録の形式。

## 設計判断

| 判断 | 内容 |
|---|---|
| 原因の特定 | 症状は3つの機構から生じる。第1に、反復継続の判断（`should_start_next_iteration`）は、最善手が安定していなければ「経過時間がsoft未満、かつ経過時間の2.5倍がhard以下」で次の反復を始め、始めた反復は完了まで走る。hardは`4·soft_raw`なのでhard側の条件は拘束せず、soft未満で始めた最後の反復がsoftを超えて完了する。[実測](../measurements/time-management-efficiency-probe.md)では、issueの条件の初手（soft 9,333 ms、hard 37,332 ms）で深さ11が6.8秒に完了して深さ12へ入り、13.4秒でsoft停止した。10分＋30秒の初手（soft 26,613 ms）は45.9秒であった。第2に、秒読み局面ではsoftとhardが一致し、予測の規則が経過時間0.4·hard以降の反復開始を禁じるため、残り0・秒読み10秒で4.1秒、秒読み30秒で13.5秒しか使わない。第3に、探索の途中でhardに達した反復は全体が捨てられる（`search_root`が`None`を返す）ので、hardを予算へ近づけると捨てる計算が増え、候補K1のようにhardを下げるだけでは中央値が予算から遠ざかる。 |
| 参照実装との比較 | Stockfish（`search.cpp`、`timeman.cpp`）とYaneuraOu（`yaneuraou-search.cpp`、`timeman.cpp`）の骨格はminaseと同じ二段構えだが、次の3点が異なる。(a) 根の各手の評価値`rm.score`を手ごとに更新し、根の探索呼び出しが返るたびに`stable_sort`するので、途中で止めても完了した手の結果が順序に反映され、`rootMoves[0]`は完了した手の中の最善になる（最初の手が未完了なら直前反復の順序が保たれる）。minaseは反復全体を捨てる。(b) 反復の完了時に`increaseDepth = elapsed <= totalTime * 0.50`を評価し、予算の半分を過ぎたら`searchAgainCounter`を増やして次の反復の深さを`rootDepth − 3·(searchAgainCounter + 1) / 4`へ抑える。minaseはsoft未満なら全深さの反復を始める。(c) 停止の閾値を`totalTime = optimum × fallingEval × reduction × bestMoveInstability × highBestMoveEffort`と局面の信号の乗算で決め、`elapsed > min(totalTime, maximum)`で止める。minaseの信号は直近4反復の最善手の一致だけである。加えてStockfishは合法手が1つなら`totalTime`を500 msに抑え、YaneuraOuは残り時間が秒読みの1.2倍未満なら残り時間と秒読みの全額を1手に使う。YaneuraOuの予算式は概略で`optimum = minimumTime + (time + inc·MTG + byoyomi·MTG) / MTG`（実装には残り時間による制限と切れ負け時の`max_ratio`の縮小がある）であり、秒読み全額に持ち時間の分担を足すminaseの`target`と同じ構造で、持ち時間を序盤から使う配分は参照実装でも同じである。したがって差は配分の思想ではなく実現の機構にあり、本書は(a)(b)(c)を順に導入する。 |
| 段階の順序 | 第0段階（根の探索結果の保持）は他の全段階の前提で、探索木を変えない再構成とする。第1段階（途中結果の採用と予算の再定義）はissueの症状を直接解決し、上限を予算へ近づける前提を与える。第2段階（深さの抑制）は第1段階のhard中断と代替関係にあるので、第1段階の実装済み構成の上でbenchの事前判定を行う。第3段階（局面適応の係数）は、実現精度が1〜2.8倍に散る現状では係数の効果を判別できないため最後に置く。各段階は1コミットとして順に積み、第2段階は採否測定の前にbenchの事前判定で見送りを決める。第3段階は見送らず、benchで発動しなければ測定へ進まずに原因を調べる。採否測定は段階ごとには行わず、最終コミットと着手前のコミットの1組で行う。第0段階は探索木を変えない再構成なので、採否にかかわらず残す。 |
| 根の探索結果の保持（第0段階） | 根の合法手ごとに、着手、今回の反復の評価値と境界の種別（確定、上界、下界、未探索）、直前の反復の評価値、主変化、および探索に費やしたノード数を保持する表を`run_main_worker`が持ち、`search_root`へ渡す。この段階は記録だけを行い、合法手の列、`order_moves`、および置換表の記録手を先頭に置く現行の順序は変えない。探索木を変えないので、固定深さのbench総ノード数と代表局面ごとの着手、評価値、ノード数が一致することで確認し、採否測定は行わない。直前反復の最善手を表から明示的に先頭へ置く変更は探索の順序を変えるので、第1段階の候補に含める。 |
| 途中結果の採用の条件（第1段階） | aspiration windowsは直前反復の評価値を中心とする窓[α, β]で探索し、外れたら窓を広げて同じ深さを読み直す。根の探索では最初の手を全幅の窓[α, β]で読み、2手目以降はまず零窓（幅1の窓[α, α+1]。`search_move`の`-alpha-1, -alpha`）で読んでαを超えた手だけを全幅の窓で読み直す。第1段階では、根の探索順序を「直前反復の最善手（表から`run_main_worker`が渡す）を先頭に置き、残りを現行の`order_moves`で整列」へ変え、置換表の記録手が直前反復の最善手と異なる場合も直前反復の最善手を先に読む。`search_root`は、hardリミットで中断したとき、中断した窓について次の2条件が成り立てば、その窓で完了した手の中の最善手とその評価値および主変化を「途中結果」として返す。(a) 直前反復の最善手の探索が、零窓で改善を検出した後の全幅の読み直しまで含めて中断した窓で完了している。(b) 完了した手の最善評価値が、中断した窓の入力時の下限（`search_root`の`original_alpha`）を上回る。零窓でαを超えない手の評価値は上界にすぎず最善手を置き換えないが、αを超えた手は全幅で読み直した確定値かβ以上の下界を持つ。保証は「探索の境界値が妥当である限り、採用する手は同じ窓で完了した手に劣らない」ことであり、同点の手や真の優劣は保証しない。前の窓で得たβ以上の下界は使わず、中断した窓の結果だけで判定する。外部停止要求とノード上限による中断には適用せず、従来どおり直前反復の結果を返す。 |
| 途中結果の報告 | 主ワーカーは途中結果があれば最善手、評価値、主変化をそれで置き換え、完了深さは直前反復のまま、停止理由はhardリミットのまま報告する。中断した反復の根の結果は置換表へ保存しない（現行どおり中断時は保存しない）。プロトコル層は、途中結果を採用したすべての手について、採用した着手が直前反復の最善手と同じかどうかによらず`info string partial`を出し、続けて完了深さで最終`info`（`time`は中断時点の経過時間）を出力する。対局ハーネスは`info string stop`以外の`info string`行を無視するので既存の記録形式は変わらないが、`completed_time_ms`の意味は「最後の`info`行の経過時間」になり、途中結果を採用した手では中断時点の時間になる。`scripts/clock_profile.py`がこの時刻との差を「完了反復後に捨てられた計算時間」として表示する箇所は、意味の変更に合わせて「最後の`info`以後の時間」へ改める。着手の変更率は、スクリプトの記録で直前の完了反復の主変化の先頭と最終着手を比べて求める。 |
| ワーカーの選択 | `select_worker_outcome`は現在、完了深さが最大のワーカーを採り、同じ深さなら番号が最小のものを採る。これを`(完了深さ, 途中結果の有無, Reverse(ワーカー番号))`の辞書式順序で最大のものを採る規則に変え、深さdの途中結果を持つ結果は、完了深さd−1だけの結果より優先し、深さdを完了した結果より劣後させる。途中結果がない固定深さの探索では現行と同じ選択になる。補助ワーカーの途中結果は採らない。 |
| 予算の再定義（第1段階） | 1手の目標時間を`target = w·(remaining / moves_to_go + 0.7·increment + 0.8·byoyomi)`とする。wは次の行「序盤の係数」が定める係数で、括弧内は現行の標準予算`soft_raw`と同じ式であり、`moves_to_go = max(100, (450 − ply) / 2)`は残り手数の見積り、0.7と0.8は加算と秒読みのうち1手の予算に組み入れる割合で、値の根拠は[探索部](search.md)の「時間管理」節にある。加算や秒読みのない時間制御では該当の項が0になる。その上で`hard = max(1 ms, min(target, safe_hard))`、`soft = hard`とする。`safe_hard = max(1 ms, remaining + byoyomi − 30 ms)`は、時計が1手に許す最大値（残り時間と秒読みの和）から探索以外の固定費の余裕30 ms（探索部の設計書の値）を引いた安全上限であり、現行のままである。YaneuraOuに倣い、秒読みが正で残り時間が0より大きく秒読みの1.2倍未満の手では`target = safe_hard`とし、残り時間と秒読みを1手で使う（最終押し込み）。残り時間0の手には適用せず、秒読みの8割の規定を保つ。安定時の早期終了で残り時間が正のまま残れば、この規則は再び働く。現行の`4·soft_raw`と`remaining / 4 + 0.8·byoyomi`の項は外す。`4·soft_raw`は難しい局面が後続の手から前借りする係数だが、現行ではsoft未満で始めた最後の反復の所要時間に応じて偶然に前借りが起こっており、局面の信号に基づく前借りは第3段階が係数として導入する。`remaining / 4 + 0.8·byoyomi`は`remaining / moves_to_go ≤ remaining / 100`なので、残り時間が加算の約3.3倍を下回る局面（加算つきの時間制御の終盤）でだけ`0.7·increment`の項を通じて拘束する。この項を外すことは、その局面で上限を`remaining / 4`から`0.7·increment`前後へ引き上げる変更であり（例えば残り200 ms・加算100 msでhardは50 msから70 msへ）、冗長な項の削除ではない。その局面でも加算の払い戻しが`0.7·increment`を上回るので残り時間は`moves_to_go·(0.3·increment − 固定費)`の近傍へ収束し、安全上限`safe_hard`が時間切れを防ぐが、余裕は30 msと4,096ノードごとの時計検査の遅れの差に縮むので、「検証」でhardの超過を測る。 |
| 序盤の係数（第1段階） | 既存エンジンの調査（[秒読みつき時間制御における既存エンジンの持ち時間配分](../research/time-management-byoyomi-survey.md)）では、Apery、技巧、dlshogiが序盤の消費をplyに応じた係数または除数で絞る。理由を明記するのはYaneuraOuのコメント（序盤は定跡で進み、勝負どころではない）だけで、3本は理由を書いていない。本書はこれに倣い、係数`w = min(1, (ply + 4) / 40)`を予算に掛ける。plyは初形を0とする局面の手数で、自分の1手目（ply 0）で0.1、9手目（ply 16）で0.5、19手目（ply 36）以降で1になる。整数演算では予算に`min(40, ply + 4)`を掛けてから40で割る。係数は、残り時間が0より大きく最終押し込みが働かない手にだけ掛け、softとhard（第3段階の拡張後の式を含む）の両方に掛けてから`safe_hard`で抑える。残り時間0の手には掛けない。未使用の秒読みは持ち越せず、節約に利益がないからである。`movetime`だけの探索にも掛けない。時計と`movetime`の併用では、時計の予算にwを掛けてから、現行どおり指定時間との小さい方をsoftとhardのそれぞれで採る。始値0.1はAperyが10手目未満の手の重要度に掛ける係数、長さ40 plyはAperyの立ち上げの長さと同じ値を借りた。Aperyの係数は配分比の分子と分母の両方に入るので予算の0.1倍にはならず、本書は値だけを借りて予算に直接掛ける。中将棋は将棋より長いが、Minaseには定跡がなく初手から探索するので、立ち上げを将棋より長くする根拠はないと判断した。これらは測定で調整した値ではなく設計上の判断値であり、パラメータ違いは追加しない。加算だけの時間制御（STC、LTC）にも掛かるので、序盤の節約分は残り時間として後の手へ配られ、採否測定は係数の効果を含んで判定する。issueの条件では初手のhardが9,333 msから933 msへ、30分＋秒読み40秒では40,000 msから4,000 msへ下がる。棄却した代案は、Aperyのように序盤で秒読み項だけを外す方式である。秒読み項と持ち時間の分担を別に扱う分岐が増える一方、序盤の絞りという効果は係数1つで足りるため採らない。 |

| 深さの抑制（第2段階） | Stockfishの`increaseDepth`と`searchAgainCounter`に倣う。反復番号`root_depth`（毎反復1増える）、実際に探索する深さ`search_depth`、および報告する完了深さ（完了した`search_depth`の最大値）を区別する。各反復の完了時に、まず安定時の早期終了（第2段階まで維持）を判定し、停止しない場合に限り、経過時間がsoftの半分を超えていれば抑制回数kを1増やし、そうでなければkを0に戻す。次の反復は`search_depth = max(1, root_depth − (3·(k + 1)) / 4)`（整数除算）で読む。深さ12の完了直後から抑制が続く場合、`root_depth`は13、14、15、16と増え、`search_depth`は12、12、12、13になる。aspiration windowsの中心は直前に完了した反復の評価値とし、抑制した反復の途中結果の採用は第1段階と同じ条件で行い、反復の完了時に`completed_depth = max(completed_depth, search_depth)`とする（上の例では4回目の抑制した反復の完了で完了深さが12から13へ増える）。停止は、経過時間がsoftを超えた反復の完了時（softリミット）、またはhardの探索中検査（hardリミット）による。第1段階のhard中断との違いは、予算の後半を「次の深さの部分的な探索」に使うか「現在の深さ前後の再探索」に使うかである。読み直しが置換表の即時打ち切りだけで終わって時間を空費する可能性があるので、実装後、採否測定の前に、代表局面（段階6の反復深化の診断と同じ局面と手順）で置換表を局面ごとに空にし、softを完了反復の経過時間の1.2倍に固定して実際に実行される抑制した反復の所要時間を測り、その所要時間を直前の全深さの反復の所要時間で割った比の中央値が0.05未満なら空費と判定してこの段階を見送る（[採否測定の条件で改良が発動することを実装前に確認する](../lessons/measure-feature-activation-before-sprt.md)）。0.05は本書が事前に定める判定値であり、通常の反復が直前の反復の1.5倍以上かかることに対し、その5%未満で終わる読み直しは置換表の照会以外をほとんど行っていないとみなす。見送りの判定は結果を見てから変えない。 |
| 局面適応の係数（第3段階） | Stockfishの`totalTime`に倣う。`soft = max(1 ms, min(target, safe_hard))`は第1段階のまま変えず、`hard = max(1 ms, min(w·(5·(remaining / moves_to_go + 0.7·increment) + 0.8·byoyomi), | 持ち時間の温存を採用しない理由 | lishogiの時計（scalashogiの`Clock.step`）と対局ハーネスの`Clock::update`は、持ち時間が残る間は思考時間の全額を持ち時間から引き、持ち時間が尽きた手とその後の手に秒読みを与え、未使用の秒読みを持ち越さない。自分の手数をN、持ち時間をR、秒読みをB、a = 0.8Bとし、持ち時間が尽きるまで1手にb ≥ aを使い、対局中に尽きる（R / b < N）と仮定する連続近似では、持ち時間はR / b手で尽きて残りのN − R / b手が各aを使うので、総思考時間は`R + (N − R / b)·a`でbが大きいほど増える。さらに1手の価値を思考時間の対数とする仮定（読みの深さが時間の対数に比例するという通常の近似）を置けば、aを超える分の総価値は`(R / b)·ln(b / a)`でb = e·a（issueの条件なら約21.7秒）が最大、b < aでは負になる。尽きない場合（R / b ≥ N）の総価値は`N·ln(b / a)`でやはりbに単調である。このモデルは全局面に同じ対数価値を仮定し、離散的な手数、尽きる手で使える秒読み、各手の上限を含まないので、現行の配分を選ぶ根拠ではなく、温存が有利になる条件（局面の難しさに応じた延長が価値を生むこと）が示されていないことを示すにとどまる。YaneuraOuの予算式も秒読み全額に持ち時間の分担を足して序盤から持ち時間を使う。既存エンジンの調査（[秒読みつき時間制御における既存エンジンの持ち時間配分](../research/time-management-byoyomi-survey.md)）でも、対局全体で温存するエンジンはなく、KataGoは同じ対数モデルから本書より速い消費を最適と導いている。持ち時間優先の時計では秒読みは持ち時間が尽きるまで使えないため、持ち時間が対局全体に上乗せする思考時間は、係数なしの試算で5分＋秒読み10秒なら1局38秒、30分＋秒読み40秒なら240秒にとどまり、持ち時間の大半は秒読みの肩代わりに消える。この帰結は持ち時間優先の時計に固有であり、秒読みを先に消費する時計には当てはまらない（同調査メモの「前提となる時計の規則」）。棄却した代案は、持ち時間が秒読みを十分上回る間は目標時間から秒読み項を外し、残り時間が秒読みに近づいた領域で秒読みの予算へ移る方式である。序盤の消費を直接減らし重要局面へ持ち時間を残せる一方、序盤の到達深さが下がる。利用者の決定により、YaneuraOuと同じく序盤から持ち時間を使う配分を採り、温存は採用しない。棋力上の優劣は未検証のままであり、本書では測定しない。 |
| 採否の判定方法 | 第1段階から第3段階は探索の返す着手を変えるので、標準のSTCとLTCのGSPRTで判定する。利用者の決定により、段階ごとの測定は行わず、第3段階までを積んだ最終コミットと本書の着手前のコミットを1組で比べる。段階ごとの効果は分解できないので、不採用となった場合の分解（第1段階だけのコミットの測定など）は別のマイルストーンとして起案する。各段階のコミットは分解に備えて1段階1コミットのまま保つ。予算の再定義は秒読みのない標準の時間制御でも各手の時間の分布を変える（現行はsoftの1〜2.8倍に散り、第1段階はhardで揃う）ため、標準の測定条件で効果が現れる。配分だけの変更を時計の診断で判定する運用は、探索の返す着手を変えない変更に限るので、本書の変更には適用しない。秒読みつきの挙動は時計の診断と煙試験で確認し、秒読みつきの時間制御のGSPRTは行わない。これで示せるのは秒読み時の時間の挙動と観測範囲での安全性であり、秒読み時の棋力改善ではない。採否測定の後に時間管理を変える修正（安全余裕、時計検査の周期を含む）は中断時点と採用着手を変えるので、測定済みの候補と同一ではなく、修正後のコミットで採否測定をやり直す。 |

## 現行の時間消費

[初形の実測](../measurements/time-management-efficiency-probe.md)では、持ち時間局面の1手がsoftの1.4〜1.7倍、秒読み局面の1手が秒読みの0.41〜0.45であり、停止理由はすべてsoftリミットであった。
削除済みブランチの診断（同記録の「参考」）では、`time=9000+0,byoyomi=300`の10ペア自己対局と5分＋10秒の40手自己対局で、持ち時間局面の思考時間とsoftの比の中央値が0.95〜1.08、90パーセンタイルが2.0〜2.2、最大が2.78、hardによる中断が2〜4%、秒読み局面の比の中央値が0.57〜0.60であり、持ち時間は5分＋10秒で先手28手目と後手36手目に尽きた。
なお、Lishogi-Botは各対局の最初の1手だけ`movetime 1000`を送るので、issueの「初手に約15秒」はlishogi経由ではなく、時計引数を直接送るGUIまたはUSI経由の観測である。

第1段階では、各手の思考時間はhard（issueの条件の初手なら序盤の係数0.1を掛けた933 ms、自分の19手目以降なら9,333 ms前後、残り0・秒読み10秒なら8,000 ms）に4,096ノードごとの時計検査の遅れと着手の出力時間を加えた値を超えない。
第3段階では持ち時間局面のhardが、持ち時間の分担の5倍に秒読みの8割を足して序盤の係数を掛けた値になり、反復の完了時の停止は`total`で決まるので、思考時間は`total`とhardの小さい方の前後で伸縮する。`total`には上限がない（最善手の入替回数の項に上限がない）ので、実際の打ち切り上限は常にhardである。
持ち時間が尽きる手数は、毎手targetをちょうど使う整数計算では、issueの条件で自分の43手目（係数なしなら34手目）、大会で採用例のある30分＋秒読み40秒で58手目（同50手目）であり、実際の値はフェーズ1、3、7の自己対局で数える。

## 診断の指標

診断は、対局ハーネスの保存記録（`think_time_ns`、`evaluation.depth`、`stop_reason`、`completed_time_ms`）と、初形から時計を再現するスクリプトの記録（同じ欄に加えて`info string partial`と`info string forced`の有無、および直前の完了反復の主変化の先頭）から求める。
両側の時計は、各手の思考時間をハーネスの`Clock::update`と同じ規則（思考時間が残り時間と秒読みの和を超えれば時間切れ、そうでなければ残り時間から思考時間を引いて0で止め、加算を足す）で整数ナノ秒で順に再生して再構成し、各手のtargetとhardは着手前の残り時間を整数ミリ秒へ切り捨てた値とplyから対象コミットの式で再計算する。
指標は次の6つとし、持ち時間局面（着手前の残り時間が0より大きい手）と秒読み局面（0の手）に分け、さらに停止理由（hard、安定時の早期終了または`total`によるsoft、合法手1つ）で分けて数える。合法手1つの分類はスクリプトの記録でだけ行い、対局ハーネスの記録ではsoftに含める。

1. 思考時間とhardの比。どの段階でも式から導ける期待は、全手について思考時間がhard + 100 ms以下であることと、hard停止の手の比が1以上であることである。第1段階ではさらに、`safe_hard`が拘束しない手のsoft停止の比が1未満である。100 msは、4,096ノードごとの時計検査の遅れと着手の出力に対する診断上の許容値であり、式からの帰結ではなくフェーズ3の煙試験とフェーズ7の診断で検証する。第3段階では`total`は反復の完了時にだけ検査されるので、`total`の超過（思考時間 − `total`）は反復単位の超過として別に記録し、判定条件にしない。全体の中央値と90パーセンタイルは停止理由の構成に依存するので記録するだけとする。
2. 秒読みの利用率（秒読み局面の思考時間を秒読みで割った値）。どの段階でも式から導ける期待は、hard停止の手が0.8に検査の遅れを加えた値になることである（加算0で`safe_hard`が拘束しない秒読み局面のhardは全段階で`0.8·byoyomi`であり、加算つきの秒読み局面では一般式から計算する）。全体の中央値が現行（フェーズ1の値）より高いことは改善の目標であり、安定時の早期終了や`total`による停止が過半数なら中央値が変わらない場合もあるので、式からは導かず実測で判定する。
3. issueの条件（`btime 300000 wtime 300000 byoyomi 10000`、加算0）の初手の実測思考時間（`go`の送信から`bestmove`の受信まで）。第1段階ではhard 933 ms（係数なしの9,333 msに序盤の係数0.1を掛けた値）に100 msを加えた1,033 ms以下を、実測で検証する許容値として置く。第3段階のhardは`(5·1,333 + 8,000)·0.1 = 1,466 ms`なので許容値は1,566 msとし、あわせて、スクリプトの記録で再計算したhardが、ply 36以降の手で係数なしの式と一致し、それより前の手で係数分だけ小さいことを係数の立ち上がりの確認として記録し、あわせて`total`（スクリプトが`info string`から取る係数の積で再計算する）と実測の関係を記録する。
4. 停止理由の分布（第3段階では`total`による停止と安定時の早期終了を区別できないので、softとして数える）、完了深さが0の手（hardが深さ1の完了前に到来し、探索前に確保した合法手を返した手）の割合、hard停止の手のうち途中結果を採れなかった手の割合、および途中結果が直前反復の最善手と異なる着手を返した割合。完了深さ0の割合が0であることは診断上の判定条件であり、後2者はスクリプトの記録から数える。
5. 持ち時間が尽きる手数の分布（記録するだけとする）。手数上限までに尽きなかった側は、尽きた手数を数えず未枯渇として記録する。
6. 時間切れ、エンジン異常、拒否着手の件数（いずれも0件を要する）、およびhardの超過（思考時間 − hard）の最大値（30 ms未満を要し、ちょうど30 msは不合格とする）。

期待値は起案時に候補の式へ当てて導いた値と、実測で検証する許容値、および改善を期待する統計量に分け、いずれも結果を見てから変えない。

## 実装フェーズ

### フェーズ1　診断基盤の復元と現行の診断

削除済みブランチから診断スクリプト3本と教訓ファイルを復元し、予算の再計算に本書の式（`--budget target`と`--budget total`）と停止理由別の集計を加える。
現行構成どうしを`time=9000+0,byoyomi=300`の10ペア（同時対局数4、約16分）と、issueの条件の先手60手の自己対局（改訂後の予算では持ち時間が自分の43手目に尽きる計算なので、秒読みへの移行まで観測できる手数にする）にかけ、「診断の指標」の6項目を`docs/measurements/time-management-efficiency-diag.md`へ記録する。
完了条件は、指標の記録と、削除済みブランチの診断と同じ基本シードで現行の値が再現することである。

### フェーズ2　根の探索結果の保持（第0段階）

根の探索結果を保持する表を導入し、`search_root`が各手の評価値、境界の種別、主変化、ノード数を表へ書く。
探索の順序と結果は変えないので、固定深さのbench総ノード数が現行と一致することを完了条件とし、採否測定は行わない。

### フェーズ3　途中結果の採用と予算の再定義（第1段階）

`search_root`と`search_iteration`に途中結果の返却を、`run_main_worker`にその採用と直前反復の最善手を表から先頭に置く順序を、`select_worker_outcome`に途中結果を含む順序を、プロトコル層に`info string partial`、`info string forced`、および最終`info`の出力を実装し、`clock_budget`と`should_start_next_iteration`を「設計判断」の式（最終押し込みを含む）へ変える。
合法手が1つの局面の即時停止も同じコミットに含める。
単体テストは、途中結果の採用条件（直前反復の最善手が未完了なら採用しない、全幅の読み直し中の中断は採用しない、最善評価値が`original_alpha`以下なら採用しない、条件を満たせば直前反復と異なる最善手を採用する）、ワーカー選択の順序、代表的な時計の予算値（issueの条件の初手で`soft = hard = 933 ms`、残り300,000 ms・秒読み10,000 ms・ply 36で9,449 ms（`moves_to_go = 207`）、残り0・秒読み10秒で係数を掛けない8,000 ms、STCの初手で11 ms、残り200 ms・加算100 ms・ply 36で70 ms、残り10,000 ms・秒読み10,000 msで係数を掛けない最終押し込みの19,970 ms）、および合法手1つの即時停止と非適用の探索を固定し、D7-TIME群の期待値を更新する。
候補で`time=9000+0,byoyomi=300`の10ペアの煙試験を行い、時間切れ0件、hardの超過の最大値が30 ms未満であることを確認する。超えた場合は時計検査の周期を1,024ノードへ下げて同じ煙試験をやり直し、この変更を候補に含める。1,024ノードでも超える場合は採否測定へ進まず原因を調べる。
issueの条件の先手60手の自己対局を行い、初手の実測思考時間が1,033 ms以下であること（指標3）と完了深さ0の手がないこと（指標4）を確認する。満たさない場合は次の段階へ進まず原因を調べる。
完了条件は、テストの通過、固定深さのbench総ノード数の変化（探索順序を変えるので変わり得る）の記録、煙試験の通過、および初手の確認である。

### フェーズ4　深さの抑制（第2段階）

第1段階の実装済み構成の上に、「設計判断」の深さの抑制を実装する。
実装後、「設計判断」の手順で抑制した反復の所要時間の比をbenchで測り、空費の判定基準に該当すればこの段階を見送ってコミットを外し、該当しなければ残す。
記録は`docs/measurements/time-management-efficiency-stage2-bench.md`へ置く。
完了条件は、見送りまたは採用の判定の記録である。

### フェーズ5　局面適応の係数（第3段階）

benchの事前判定を反映した構成の上に、「設計判断」の4係数、hardの拡張、必要な状態の持ち越し、および係数の積の`info string`出力を実装し、直近4反復の最善手の一致による早期終了を外す。
実装後、代表局面で係数の分布をbenchで記録し、発動の判定基準に該当しなければ採否測定へ進まず、原因を調べて1回だけ定数を見直し、発動を確認してから確定する。
記録は`docs/measurements/time-management-efficiency-stage3-bench.md`へ置く。
完了条件は、発動の確認と定数の確定である。

### フェーズ6　採否測定

第3段階までを積んだ最終コミットと本書の着手前のコミットを、標準のSTC（`time=10000+100`、最大3,000ペア）のGSPRTで比べ、[docs/guides/sprt.md](../guides/sprt.md)の振分け規則（`H1`、または上限到達の判定保留でLLRが0以上ならLTCへ進み、`H0`または負のLLRの判定保留なら不採用）に従う。
LTC（`time=60000+200`）で`H1`かつ異常0件なら採用し、判定保留は同じ実行ディレクトリを`--resume`で延長する。
記録は`docs/measurements/time-management-efficiency-stc.md`と`-ltc.md`へ置く。
不採用の場合は本書を不採用で終え、issue #7へ原因の分析と不採用の結果を報告し、分解の測定は別に起案する。
完了条件は、段階ゲートの判定である。

### フェーズ7　秒読みつきの最終診断と煙試験

採用した構成でフェーズ1と同じ2つの実行を行い、指標の期待値との比較を`docs/measurements/time-management-efficiency-after.md`へ記録する。
あわせて`time=10000+100,byoyomi=200`の10ペア煙試験で`time_forfeits`が0件であることを確認する。
指標1、2、3、4、6のいずれかの判定を満たさない場合は採用を保留して原因を調べ、修正後のコミットで煙試験とフェーズ6の採否測定をやり直す。
完了条件は、指標1、2、3、4、6の判定の達成と、指標5の記録である。

### フェーズ8　文書とissueの更新

[探索部](search.md)の時間管理の節を採用した方式へ書き換え、`clock_budget`、`search_root`、および根の表のrustdocを更新し、[lishogi Bot接続](lishogi-bot.md)の秒読みの余裕に関する記述を本書へのリンクに置き換える。
issue #7へ原因、参照実装との比較、変更、および測定結果を報告して閉じる。
完了条件は、文書の更新とissueの終了である。

## 検証

- 途中結果の採用は、回帰テストを修正を外して失敗させてから採用する（[回帰テストは修正を外して失敗を確認する](../lessons/confirm-regression-test-fails-without-fix.md)）。
- 根の表の導入と第3段階の係数は、固定深さのbench総ノード数で探索木の不変（第0段階）または変化の範囲（第3段階は時間制御でだけ働くので不変）を確認する。
- 時間制御を変えるので、手数上限に近い着手列を1手ずつ与えて、1手あたりの固定費（`position`の処理、探索の準備、および出力にかかる探索以外の時間）とhardの超過の和が安全余裕30 msの内側に収まることを再確認する（[手数に比例する固定費は超長手数の対局で時間切れを起こす](../lessons/per-move-overhead-grows-with-game-length.md)）。残り時間が少ない加算つきの局面（残り200 ms・加算100 ms）、`Threads` 4、および静止探索が長い局面を含める。
- 第2段階と第3段階は、実装直後にbenchで発動または空費を判定し、採否測定は最終コミットで1回だけ行う（[採否測定の条件で改良が発動することを実装前に確認する](../lessons/measure-feature-activation-before-sprt.md)）。
- 採否測定の前に、`time_forfeits`、エンジン異常、および拒否着手が0件であることを確認する。
- フェーズ1の診断は、削除済みブランチの診断と同じ基本シード（20260916）を使い、現行の値が再現することで集計の正しさを確かめる。

## 完了条件

採用で完了する条件は次のとおりである。

- 最終コミットのLTCが`H1`であり、異常が0件である。第2段階の見送りの判定と第3段階の発動の確認が記録されている。
- issueの条件の初手の実測思考時間が1,566 ms以下である。
- 全手の思考時間がhard + 100 ms以下であり、完了深さ0の手がなく、秒読み局面の利用率の中央値がフェーズ1の現行の値より高い。
- 煙試験と診断の全対局で時間切れが0件であり、hardの超過の最大値が30 ms未満である。
- 探索部の設計書、rustdoc、およびissue #7が更新されている。

不採用で完了する条件は、最終コミットがSTCまたはLTCで不採用となり、測定記録とissue #7への報告が残り、分解の測定が別に起案されていることである。この場合、第0段階の再構成だけを残す。

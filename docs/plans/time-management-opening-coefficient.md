# 秒読みの予算に序盤の係数を加える

## 先に読む要約

本書は、GitHub issue #7の主症状（持ち時間5分と秒読み10秒の対局で最初の数手に各10秒以上を使うこと）を、現行の時間管理の機構を変えず、秒読みのない時間制御の挙動も変えずに直すマイルストーンの設計書である。
[持ち時間の効率的な使用](time-management-efficiency.md)と[分解測定](time-management-decomposition.md)で、予算を分担どおりに中断する方式も局面適応の係数で伸縮させる方式も現行の機構に有意に劣ると分かり、現行の機構（予算softを反復の開始の門とし、始めた反復を完了させ、hardを`min(4·soft_raw, remaining / 4 + 0.8·byoyomi, safe_hard)`で抑える方式）が既知の構成の中で最良である。
初手の長考は、issueの条件の予算9.3秒のうち8秒が秒読みの項`0.8·byoyomi`から来ることによる。
本書は、この秒読みの項にだけ序盤の係数`w = min(1, (ply + 4) / 40)`を掛け、持ち時間と加算の分担、hardの式、反復継続の判断は変えない。
秒読みのない時間制御（STC、LTC、lishogiの加算方式の対局。STCとLTCは[棋力測定の手引き](../guides/sprt.md)が定める短時間と長時間の自己対局条件）では式が現行と一致するので、着手と時間は変わらず、棋力測定は不要である。
秒読みつきの時間制御では、利用者の決定に従い時計の診断で採否を判定し、秒読みつきの棋力は測らない。
完了条件は、issueの条件で初手の実測思考時間がhardに100 msを加えた値以下になること、時間切れ0件、固定深さのbench総ノード数と秒読みなしの予算値が現行と一致することである。

## 状態

起案。2026年9月18日に起案し、着手日は未定である。
着手には利用者の承認を要する（実装と診断で約1時間）。
次の一手は、承認を得て実装することである。

## 目的

人間との対局（lishogi経由を含む）で、対局開始直後の数手に秒読み相当の長考を使う挙動をなくし、秒読みのない時間制御の挙動と棋力を式の上で現行と同一に保つ。

## 適用範囲

対象は、`clock_budget`の`soft_raw`における秒読みの項、その単体テストとD7-TIME群の期待値、および診断スクリプト`scripts/clock_budget_stats.py`への本書の式の追加である。
現行の機構（反復継続の判断、hardの式、秒読み局面の予測規則、中断した反復の破棄）は変えない。
持ち時間が序盤で尽きること自体（5分＋10秒で自分の30〜36手目）は、参照実装と同じ配分の帰結として受け入れ、変えない（[持ち時間の効率的な使用](time-management-efficiency.md)の「持ち時間の温存を採用しない理由」）。
Lishogi-Botの設定と受け付ける時間制御の範囲は対象外である。

## 依存関係

- 現行の時間管理の正は[探索部](search.md)の「時間管理」節である。本書の完了時に、同節へ秒読みの項の係数を追記する。
- 置換表の2つの修正（作成または消去の後に未使用の置換表の消去を省く修正と、既定容量の置換表を`isready`で確保する修正）は探索を変えない修正であり、本書の候補の親に含める（分解測定の共通基準B′と同じ構成）。
- 序盤の係数の根拠は[秒読みつき時間制御における既存エンジンの持ち時間配分](../research/time-management-byoyomi-survey.md)にある。Aperyは20手目まで秒読みの項を加えず、本書はそれを連続な係数にしたものである。

## 設計判断

用語は[探索部](search.md)の「時間管理」節に従う。
`remaining`は着手前の残り時間、`increment`は加算、`byoyomi`は秒読み、`moves_to_go = max(100, (450 − ply) / 2)`は残り手数の見積り、`safe_hard = max(1 ms, remaining + byoyomi − 30 ms)`は安全上限である。

| 判断 | 内容 |
|---|---|
| 変更の範囲 | `soft_raw = remaining / moves_to_go + 0.7·increment + 0.8·byoyomi·w`、`w = min(1, (ply + 4) / 40)`とし、整数演算では秒読みの項を`byoyomi·8·min(40, ply + 4) / 400`で求める。hardは現行どおり`max(1 ms, min(4·soft_raw, remaining / 4 + 0.8·byoyomi, safe_hard))`であり、`remaining / 4 + 0.8·byoyomi`の項には係数を掛けない（歯止めは現行のまま）。`soft = min(soft_raw, hard)`。残り時間0の手にも同じ式を使うが、残り時間0の局面は初形から離れているので実用上`w = 1`である。 |
| 秒読みの項にだけ掛ける理由 | 秒読みのない時間制御では`byoyomi = 0`なので式が現行と一致し、着手と時間が変わらない。したがって利用者の制約（人間向けの変更で棋力を落とさない）を測定ではなく式の同一性で満たす。持ち時間の分担にも係数を掛ける案は、分解測定のD1とD2の観測成績が近かったことから加算つきの条件で効果が小さい示唆はあるが、同等性は未検証であり、加算つきの条件の着手を変えるので採らない。 |
| 予算値 | issueの条件（残り300,000 ms、秒読み10,000 ms、加算0）の初手（ply 0）は`soft_raw = 1,333 + 800 = 2,133 ms`、`hard = min(8,532, 83,000, 309,970) = 8,532 ms`。ply 36以降は現行と同じ9,333 ms前後と37,332 ms前後である。30分＋秒読み40秒の初手は`soft_raw = 8,000 + 3,200 = 11,200 ms`、`hard = 44,800 ms`。残り0・秒読み10,000 msは現行と同じ8,000 ms。STC（残り10,000 ms、加算100 ms）の初形は現行と同じ114 msと456 msである。実測時間は現行の機構どおりsoftの1〜2.8倍に散るので、初手の実測は診断で確認する。 |
| 採否の判定 | (a) 秒読みなしの同一性: 単体テストで秒読み0の代表入力の予算値が現行と一致すること、固定深さのbench総ノード数が親と一致すること。(b) 時計の診断: issueの条件の先手60手自己対局で、初手の実測思考時間がhard 8,532 msに100 msを加えた8,632 ms以下、全手でhardの超過が30 ms未満、時間切れ0件。`time=9000+0,byoyomi=300`の10ペア煙試験で時間切れ0件。診断の集計は`scripts/clock_budget_stats.py`に本書の式（`--budget byoyomi-opening`）を加えて行う。(c) 秒読みつきの棋力は、利用者の決定（秒読み配分の候補は時計の診断で採否判定）に従い測定しない。参考値として`time=9000+0,byoyomi=300`の固定200ペアEloを記録してもよいが、採否の根拠にはしない。 |
| lishogiでの挙動 | Lishogi-Botは最初の1手だけ`movetime 1000`を送るので初手には影響しないが、2手目以降は時計で指すので、秒読みつきの対局では係数が2〜19手目の長考を絞る。加算方式の対局では何も変わらない。 |

## 実装フェーズ

### フェーズ1　実装

B′を親に、`soft_raw`の秒読みの項へ係数を掛けるコミットを作る。
単体テスト（issueの条件の初手2,133 msと8,532 ms、ply 36で現行値、残り0・秒読み10,000 msで8,000 ms、STCの初形で114 msと456 ms）とD7-TIME群を更新し、`scripts/clock_budget_stats.py`へ`byoyomi-opening`の式を加える。
固定深さのbench総ノード数が親と一致することを確認する。

### フェーズ2　時計の診断

issueの条件の先手60手自己対局と`time=9000+0,byoyomi=300`の10ペア煙試験で判定(b)を確かめ、`docs/measurements/time-management-opening-coefficient-diag.md`へ記録する。

### フェーズ3　文書の更新

採用なら[探索部](search.md)の時間管理の節と`clock_budget`のrustdocへ係数を追記し、masterへの統合（置換表の2修正を含む）を利用者に提案する。

## 検証

- 秒読み0の代表入力で予算値が現行と一致し、固定深さのbench総ノード数が親と一致すること。
- 診断と煙試験の`time_forfeits`、エンジン異常、拒否着手が0件であること。

## 完了条件

採用で完了する条件は、判定(a)と(b)の通過と、文書の更新である。
不採用で完了する条件は、測定記録が残り、係数の値を変えた再試行を行わないことである。

# 旧式の時間管理に序盤の係数を加える

## 先に読む要約

本書は、GitHub issue #7の主症状（持ち時間5分と秒読み10秒の対局で最初の数手に各10秒以上を使うこと）を、現行の時間管理の機構を変えずに直すマイルストーンの設計書である。
[持ち時間の効率的な使用](time-management-efficiency.md)と[分解測定](time-management-decomposition.md)で、予算を分担どおりに中断する方式も局面適応の係数で伸縮させる方式も現行の機構に有意に劣り、序盤の係数だけは棋力に影響しない（±25 Elo以内で0）と分かった。
本書は、現行の機構（予算softを反復の開始の門とし、始めた反復を完了させ、hardを`min(4·soft_raw, remaining / 4 + 0.8·byoyomi, safe_hard)`で抑える方式）をそのまま保ち、`soft_raw`に序盤の係数`w = min(1, (ply + 4) / 40)`を掛けるだけの変更を行う。
係数は残り時間が正の手にだけ掛け、秒読み局面は変えない。
この変更は探索の返す着手を時間を通じて変えるが、目的は棋力ではなく人間との対局での挙動なので、採否は時計の診断と、STCの条件での固定600ペアEloによる非劣性の確認（95%信頼区間の下限が−25 Elo以上）で判定し、GSPRTの段階ゲートは使わない。
非劣性の確認は[棋力測定の手引き](../guides/sprt.md)にない運用であり、本書の着手前に手引きへ「配分だけの変更の非劣性確認」の節を追加することを利用者に求める。
完了条件は、issueの条件で初手の実測思考時間がhardに100 msを加えた値以下になること、時間切れ0件、および非劣性の確認の通過である。

## 状態

起案。2026年9月18日に起案し、着手日は未定である。
着手には、非劣性の確認を測定手引きへ追加することの承認と、測定の実行（固定600ペアで同時対局数16なら約2時間）の承認を要する。
次の一手は、承認を得て測定手引きの節を追加することである。

## 目的

人間との対局（lishogi経由を含む）で、対局開始直後の数手に秒読み相当の長考を使う挙動をなくし、それ以外の時間の使い方と棋力を現行のまま保つ。

## 適用範囲

対象は`clock_budget`の`soft_raw`の計算と、その単体テストおよびD7-TIME群の期待値である。
現行の機構（反復継続の判断、hardの式、秒読み局面の予測規則、中断した反復の破棄）は変えない。
持ち時間が序盤で尽きること自体（5分＋10秒で自分の30〜36手目）は、参照実装と同じ配分の帰結として受け入れ、変えない（[持ち時間の効率的な使用](time-management-efficiency.md)の「持ち時間の温存を採用しない理由」）。
Lishogi-Botの設定と受け付ける時間制御の範囲は対象外である。

## 依存関係

- 現行の時間管理の正は[探索部](search.md)の「時間管理」節である。本書の完了時に、同節へ序盤の係数を追記する。
- 置換表の2つの修正（作成または消去の後に未使用の置換表の消去を省く修正と、既定容量の置換表を`isready`で確保する修正）は探索を変えない修正であり、分解測定の共通基準B′と同じく候補と比較対象の両方に含める。
- 序盤の係数の根拠は[秒読みつき時間制御における既存エンジンの持ち時間配分](../research/time-management-byoyomi-survey.md)にある。

## 設計判断

| 判断 | 内容 |
|---|---|
| 変更の範囲 | `soft_raw = (remaining / moves_to_go + 0.7·increment + 0.8·byoyomi) · w`（残り時間が正の手）、`w = min(1, (ply + 4) / 40)`、整数演算では`min(40, ply + 4)`を掛けてから40で割る。残り時間0の手は現行どおり`w = 1`。hardは現行の式のまま`soft_raw`から導くので、係数はhardにも及ぶ。issueの条件の初手は`soft_raw = 933 ms`、`hard = 3,732 ms`となり、現行の機構では実測が0.9〜3.7秒に収まる。19手目（ply 36）以降は現行と同じである。30分＋秒読み40秒の初手は`soft_raw = 4,000 ms`、`hard = 16,000 ms`である。 |
| 機構を変えない理由 | 分解測定のD1とD2は、予算を分担そのものにして探索中の中断で止める方式が、現行の反復完了による超過で使っていた時間を約14%使い残し、中断した反復の時間が着手に反映されないために劣ると示した。現行の機構は既知の構成の中で最良であり、本書は機構に触れない。 |
| 採否の判定 | 標準の段階ゲートはH1 = +10 Eloの改善を検出する設計であり、棋力に中立な配分の変更は原理的に通らない。本書の目的は挙動なので、採否は次の2つで判定する。(a) 時計の診断: issueの条件の先手60手自己対局で、初手の実測思考時間がhard 3,732 msに100 msを加えた3,832 ms以下、全手でhardの超過が30 ms未満、時間切れ0件。(b) 非劣性の確認: 候補（B′＋係数）と比較対象（B′）を`time=10000+100`の固定600ペアEloで対局させ、95%信頼区間の下限が−25 Elo以上であること。600ペアの信頼区間の幅は約±19 Eloであり、−25は本書が事前に定める値である。分解測定でD1とD2（係数の有無だけが違う）の度数が一致したことは、この確認が通る事前の根拠である。 |
| 測定手引きへの追加 | 手引きの「機能採否の段階ゲート」は棋力の改善を主張する変更の規則であり、本書の非劣性の確認はそれと別の運用として、「配分だけの変更の非劣性確認」の節を手引きに加える。節の内容は次のとおりである。探索の枝刈りや評価を変えず時間の配分だけを変える候補は、時計の診断で目的の挙動を確認したうえで、STCの条件の固定600ペアEloで95%信頼区間の下限が−25 Elo以上なら採用できる。判定保留や信頼区間の読み替えによる採用は認めず、区間の下限が−25を下回れば不採用とする。棋力の改善を主張する場合は段階ゲートに従う。この追加は利用者の承認を要する。 |
| lishogiでの挙動 | Lishogi-Botは最初の1手だけ`movetime 1000`を送るので初手には影響しないが、2手目以降は時計で指すので、係数は2〜19手目の長考を絞る。lishogiの時計はミリ秒単位で持ち時間優先であり、本書の前提と同じである。 |

## 実装フェーズ

### フェーズ1　測定手引きの追加と実装

承認を得て[docs/guides/sprt.md](../guides/sprt.md)に非劣性確認の節を加える。
B′を親に`soft_raw`へ係数を掛けるコミットを作り、単体テスト（issueの条件の初手933 ms、ply 36で9,449 ms、残り0・秒読み10秒で8,000 ms、最終押し込みは現行どおり）とD7-TIME群を更新する。固定深さのbench総ノード数がB′と一致することを確認する。

### フェーズ2　時計の診断

issueの条件の先手60手自己対局と、`time=9000+0,byoyomi=300`の10ペア煙試験で、判定(a)を確かめて`docs/measurements/time-management-opening-coefficient-diag.md`へ記録する。

### フェーズ3　非劣性の確認

固定600ペアEloで判定(b)を確かめ、`-elo.md`へ記録する。

### フェーズ4　文書の更新

採用なら[探索部](search.md)の時間管理の節と`clock_budget`のrustdocへ係数を追記し、masterへの統合を利用者に提案する。

## 検証

- 固定深さのbench総ノード数がB′と一致すること。
- 診断と固定Eloの`time_forfeits`、エンジン異常、拒否着手が0件であること。

## 完了条件

採用で完了する条件は、判定(a)と(b)の通過と、文書の更新である。
不採用で完了する条件は、測定記録が残り、係数の値を変えた再試行を行わないことである。

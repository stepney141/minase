# USI投了（issue #6）の設計書

## 先に読む要約

本マイルストーンは、minaseが明らかに負けている局面で自ら投了できるようにする（[issue #6](https://github.com/stepney141/minase/issues/6)）。
USI（将棋系エンジンとGUIの間の通信規約）では、エンジンが着手の代わりに`bestmove resign`を返すと投了になる。
対局ハーネス`match_runner`はこの応答を当該局の負けとして受け取り、lishogiのBotブリッジ（Bot APIとUSIエンジンを仲介するプログラム）も投了をAPIへ送る機能を持つが、minaseにはこの応答を出す経路がない。
本書は、探索が停止したときに`bestmove`の根拠として採る最終結果（以下、採用結果）の評価値が、自分の視点で閾値以下のときにUSI層が`bestmove resign`を返す方式を採る。
閾値はUSIオプション`ResignValue`（やねうら王と同じ名前と意味）で与え、探索部は変更しないので、投了しない探索のノード数は変わらない。
閾値の既定値は、保存済みの自己対局記録（約10万局、各着手の評価値と最終結果を含む）へ仮想的な投了条件を当てた[診断](../research/usi-resignation-diagnosis.md)から選ぶ。
診断では、どの閾値でも投了した側が結局は勝つか引き分ける局（以下、誤投了）が0件にはならず、詰みを読み切った報告でも0.03%の局で逆転していたので、既定値は誤投了で放棄する得点の割合と省ける思考時間とを比べて利用者が決める。
棋力測定の対局ハーネス`match_runner`は、両エンジンへ`ResignValue`の無効化を送って対局を規則上の終局まで指させる。投了が測定の勝敗に入ると、相手が先に投了した局面からの勝ち切りの差が測れなくなり、保存記録も完走した対局でなくなるからである。
したがって投了は自己対局の測定に影響せず、GSPRT（勝敗から強さの差を逐次判定する統計検定、[docs/guides/sprt.md](../guides/sprt.md)）による採否判定の対象にならない。
lishogiで投了を有効にするには、Botブリッジのフォークが`bestmove resign`を対局APIの投了へ写す改修が必要であり、これを最後のフェーズに置く。
完了条件は、投了の契約とハーネスの無効化がテストで固定され、既定値が診断の表から確定し、lishogiの公開対局で投了が成立することである。

## 状態

起案。2026年9月23日に起案し、同日に保存記録の診断（フェーズ1）を完了した。
利用者の決定を待つ点は、`ResignValue`の既定値（診断の表からの選択）と、棋力測定では投了を無効化する方針の承認の2点である。
次の一手は、この2点の確定後にUSI層の実装（フェーズ2）へ進むことである。

## 目的

minaseが、USIの`bestmove resign`によって自ら投了できるようにする。
対象は、明らかに負けている局面での投了だけであり、引き分けの提案や勝ちの宣言は扱わない。
投了によって、人間との公開対局とGUIでの対局で、負けが確定した後の無意味な指し続けをなくす。

## 適用範囲

本マイルストーンでは、次の作業を行う。

- `src/protocol/usi.rs`に、USIオプション`ResignValue`の宣言と受理、および`bestmove`送出時の投了判定を実装する。
- `src/harness.rs`のUSIエンジンの起動手順に`setoption name ResignValue value 30000`を加え、棋力測定の対局を規則上の終局まで指させる。[docs/guides/sprt.md](../guides/sprt.md)にこの条件を記す。
- 保存済み対局記録へ仮想的な投了条件を当てる診断スクリプト`scripts/resign_diagnosis.py`を置き、結果を[調査メモ](../research/usi-resignation-diagnosis.md)に残して`ResignValue`の既定値を確定する。
- 挙動とその典拠を先に定めてからテストを書く方式（spec-first、[設計書](spec-first-tests.md)）のマトリクス[D6-USI](spec-first-tests/matrices/d6-protocol.md)へ投了の挙動を追加し、台帳を改訂する。
- [外部対局接続](engine-connectivity.md)の「`bestmove resign`を送出する経路は本マイルストーンには存在せず」の段落と、[lishogi Bot接続](lishogi-bot.md)の対象外の項目「評価値による任意投了」を、採用時に本書への参照へ書き換える。
- フォークstepney141/lishogi-botに`bestmove resign`を対局APIの投了へ写す改修を入れ、`minase-lishogi-bot`の配備環境で投了の通信を確かめる。

次の項目は対象外とする。

- CECP（XBoardプロトコル）の投了。`src/protocol/cecp.rs`は変更しない。CECPでminaseを動かすのは開発用の接続だけであり、HaChuとの比較測定ではminaseはUSI側で動く。
- 対局ハーネスによる評価値の裁定。[早期投了の導入判定](match-early-resignation.md)が扱い、待機中のまま変更しない。ハーネスの裁定は両エンジンの評価値を審判が見て双方に終局を宣言する仕組みであり、本書のエンジン自身の投了とは判断の主体が異なる。
- 引き分けの提案、勝ちの宣言（`bestmove win`）、および`go mate`。
- 教師データ生成`selfplay_gen`。探索部を直接呼ぶので、USI層の投了の影響を受けない。
- 探索部、評価関数、時間管理の変更。投了判定は探索が停止した後に行うので、探索の木、ノード数、および時計の消費を変えない。
- 診断で見つかった、詰みの報告が1手で消える局の原因調査。診断の調査メモに記録し、探索部の課題として別に扱う。

本書の用語は次のとおりである。
**採用結果**は、探索が停止したときに`bestmove`の根拠として採る最終結果であり、最善手、評価値、および完了した深さからなる。Lazy SMPでは最も深い反復を完了したワーカーの結果である。深さ1の反復を完了する前に中断された探索では、採用結果は深さ0と根の静的評価を持ち、この場合は投了判定が成立せず通常の`bestmove`を返す。
**投了閾値**は`ResignValue`の値であり、採用結果の評価値（自分の視点、単位はcp）が−ResignValue以下のときに投了する。
**詰み帯**は、強制的な終局までの手数を含む評価値の範囲であり、絶対値が29,744（`MATE_THRESHOLD`）以上の値をいう。探索が詰み帯を返すのは、王駒の捕獲と第23条の合法手なしを読み切った場合であり、反復は探索内では引き分けの値で扱う。詰み帯の評価値は探索の結果でしか現れず、深さ0の静的評価には現れない。
**誤投了**は、仮想的な投了条件が発火した局で、投了せずに指し続けた実際の対局を発火した側が勝つか引き分けた場合をいう。仮想的に投了していれば、その勝ちまたは引き分けを失っていたことになる。
**評価尺度**は、評価関数の世代ごとに異なる評価値の目盛りをいう。同じcpの値でも、駒の価値を学習し直した世代の間では優劣の程度が一致しないので、既定値の根拠には現行の評価尺度の記録だけを使う。

## 設計判断

| 項目 | 決定 |
|---|---|
| 投了判定の位置 | USI層が`bestmove`を送出する直前で判定する。探索部に投了を表す指し手や結果を持ち込む案（やねうら王は探索の結果に投了の指し手`Move::resign()`を積む）は、指し手型に着手でない値が入ると審判層、ハーネス、および保存記録のすべての経路で特殊値の扱いが必要になるため棄却した。投了はUSIの応答の選択であり、探索結果の解釈として通信層に閉じる。 |
| 判定の入力 | 採用結果の評価値と完了した深さを使い、深さが1以上のときだけ投了する。深さ0の採用結果は根の静的評価であり探索の裏付けがないので、投了せず通常の`bestmove`を返す。 |
| 閾値の与え方 | USIオプション`ResignValue`（`spin`、最小1、最大30000）で与え、評価値が−ResignValue以下なら投了する。名前と意味はやねうら王のオプションに合わせ、GUIの利用者が既知の設定として扱えるようにする。詰み帯の評価値は通常の評価値と同じ比較で扱い、詰みだけの分岐を作らない。詰まされる評価値は−(30,000−N)であり、Nは探索内の距離（王駒の捕獲を採点する時点のply）であって実際の着手数とは一致しない。根で現れる最小値は−29,999なので、29,744では負の詰み帯全体が対象になり、たとえば29,900では距離100以内の詰みだけが対象になり、30,000では投了しない。特別な「無効」の値は設けず、この範囲で無効化できる。 |
| 既定値 | 診断の表（調査メモの「結論」の表）から利用者が確定する。確定までの提案は4,000 cp（現行構成群で放棄する得点の割合0.19%、思考時間の削減7.2%）である。3,000 cpは削減13.4%と引き換えに0.88%の得点を放棄し、5,000 cpは0.06%の放棄で削減4.0%にとどまる。削減時間は測定では使わないので、選定の主眼は放棄する得点の割合と、人間の相手に対して十分に明らかな劣勢で投了することとの釣り合いである。この選定は過去標本に基づく運用上の判断であり、未参照の対局での検証は行わない。確定した値をソースの宣言に書き、本行を確定値へ書き換える。 |
| 連続手数 | 直前の着手の評価値を保持しない単発判定にする。診断では、3,000 cpの誤投了が連続1手の942局に対して連続2手で820局、連続3手で770局であり、連続を要求しても1〜2割しか減らない。一方で連続を数える状態は、通常の対局では毎手`position`が届くので局面の同期と切り離して持つ必要があり、外れた先読みで捨てる結果を数えない例外も要る。減る誤投了がこの費用に見合わないので状態を持たない。 |
| 判定を適用する`bestmove` | 通常の`go`、`ponderhit`後の完了、および`stop`による解放（無限探索と外れた先読みを含む）のすべてで同じ判定を行う。送出点を1つにするためであり、`go infinite`の検討ではGUIが`bestmove`を無視し、外れた先読みの`bestmove`もエンジンは同じ判定で出すが、ハーネス（`discard_bestmove`）とブリッジがともに読み捨てるので、投了を返しても対局には影響しない。保留状態（`AwaitingStop`）は、解放時の判定に必要な採用結果の評価値と深さを保持する。 |
| 出力の形式 | 現行の`info`行の出力を変えず、`info string stop <停止理由>`の後に`bestmove resign`を出力する。予想手は付けない。採用結果の評価値は、主ワーカーの進捗またはより深い補助ワーカーの最終情報として既に`info`行へ出ているので、投了のために再出力しない。 |
| 局面の状態 | 投了を`Engine.game`へ適用しない。`bestmove`が局面を進めない現行の契約（D6-USI-24）と同じであり、終局の状態遷移は`gameover`が担う。審判層の`Game::resign`は使わない。 |
| 採否の判定方法 | 投了は棋力測定の対局では無効化するので、自己対局の勝敗に影響せず、棋力に影響し得る変更をGSPRTで判定する共通方針の対象にならない。採否は、USI層の契約とハーネスの無効化がテストで固定されていること、既定値が診断の表から確定していること、およびlishogiの公開対局で投了が成立することで判定する。投了の有無で自己対局の強さを比べる測定は、投了が期待得点を減らすだけで増やさない（投了した局の得点は0、指し続けた局の得点は0以上）ので行わない。 |
| 診断の対象記録 | `data/matches/`配下の全実行ディレクトリの保存記録を使い、時間切れ、エンジン異常、および手数上限で終わった局を除く。既定値の根拠には、候補と基準の両方が2026年9月8日（序中盤と終盤を補間するPSTを採用し、評価尺度が現行の系統になった日）以降のコミットで、時間制御、規則`engine-default`の現行構成群を使う。この群にも重みの異なる評価モデルの対局が混在するが、閾値に対する誤投了の形は全記録の表と一致するので、モデルごとには分けない。評価尺度が異なる過去の評価関数、固定深さ、および外部エンジンとの対局を含む全記録の表は、この形の確認に使う。 |
| 誤投了の判定 | 発火した側が実際の対局で勝った局と、引き分けた局を誤投了に数える。発火した側が指し続けた後に相手が投了して勝った局も、仮想的な投了で失う勝ちなので誤投了に含める。相手の時間切れや異常で勝った局は、その局ごと除外する。放棄する得点の割合は（勝ち＋0.5×引き分け）÷対象局数とする。この割合は先に発火した側が放棄する得点を局単位で数えた値であり、片側だけが投了を導入したときの得点差ではない。 |
| 棋力測定での無効化 | `match_runner`は、USIエンジンの起動時に`USI_Hash`と同じ手順で`setoption name ResignValue value 30000`を候補と基準の両方へ送る。無条件かつ両側同一の対局条件であり、機能比較のスイッチではない。投了が測定に入ると、基準が先に投了した局で候補が勝ち切れたかどうかを観測できず、勝ち切りの退行が隠れる。また保存記録が完走した対局でなくなり、本書の診断のような事後の分析ができなくなる。オプションを持たない旧コミットは、USIの慣例どおり未知のオプション名を黙って無視するので、コミット対コミットの対称性は保たれる。CECPエンジンには送らない。 |
| lishogiのブリッジ | フォークstepney141/lishogi-botに、採用した結果を着手として送る箇所（`li.make_move`の直前）で`bestmove resign`を分岐し、既存の`li.resign`を呼んで先読みを始めない変更を入れる。外れた先読みの結果はブリッジが既に捨てているので、その経路の`bestmove resign`は投了にならない。上流のlishogi-botは`bestmove`の2語目をそのまま着手として送るので、改修なしでは投了が着手の送信失敗になる。[lishogi Bot接続](lishogi-bot.md)はブリッジの改変を避ける方針だが、[USI先読み](ponder.md)で既にフォークを固定して改修しており、同じ運用に従う。 |

## USI層の契約

`usi`への応答に、`option name ResignValue type spin default <既定値> min 1 max 30000`を1行宣言する。
`setoption name ResignValue value N`は、1以上30000以下の10進整数だけを受理し、値の欠落、非整数、および範囲外は`info string error: ...`を1行返して直前の設定を保持する。
探索中の変更は`Threads`と同じく既存の入力待機列に載せ、次の探索から適用する。

投了の判定は、`bestmove`を送出する各経路で、採用結果の完了した深さが1以上、かつ評価値が−ResignValue以下のときに成立する。
成立した場合の出力は次の順である。

```text
info string stop <停止理由>
bestmove resign
```

`info`行の出力は現行のままであり、`bestmove resign`には予想手を付けない。
成立しない場合の出力も現行のままである。

投了はエンジンの対局状態を変えない。
投了の後にGUIが`gameover`を送れば現行どおり対局を終え、`position`を送れば現行どおり局面を同期する。

## 診断

診断の方法と結果は[調査メモ](../research/usi-resignation-diagnosis.md)が持つ。
本節は、既定値の確定に使う規則だけを定める。

仮想条件は、着手した側の視点へ換算した評価値が閾値以下、深さが1以上、上下界の種別が`exact`の着手を発火とし、時系列で最初の発火でその局を仮想的に終える。
`mated_in`は常に発火、`mate_in`は常に非発火とし、深さ0、欠測、および上下界の評価値は発火させない。
削減時間は、発火した着手より後の両者の思考時間の合計を、対象局の思考時間の合計で割った値である。
閾値の候補は1,500から8,000 cpまでと負の詰み帯全体（29,744に相当）であり、29,744を超える値は診断しない。

既定値は、現行構成群の表から利用者が放棄する得点の割合と削減時間を見て選ぶ。
確定した既定値はソースの宣言と一致させ、以後、閾値の候補を増やしたり結果を見て規則を変えたりしない。
設計判断を変える必要が実装中に見つかった場合は、本書の設計判断を改めたうえで診断を同じスクリプトでやり直し、結果を調査メモに書き直す。

## 実装フェーズ

### フェーズ1　保存記録の診断

診断スクリプトを`scripts/`に置いて実行し、閾値ごとの費用と削減時間を調査メモに残す。
完了条件は、調査メモに全記録と現行構成群の表、除外数、および誤投了の内訳が記録されていることである。

### フェーズ2　USI層の実装

`ResignValue`の宣言と受理、投了判定、および出力を実装し、マトリクスと台帳へ挙動を追加してテストで固定する。
完了条件は、テストが通り、`bench`の深さ6の総ノード数が着手前と一致し（探索部を変えていないことの回帰確認）、外部対局接続とlishogi Bot接続の設計書が現行の実装へ改訂されていることである。

### フェーズ3　棋力測定での無効化

`src/harness.rs`のUSIエンジンの起動手順に`setoption name ResignValue value 30000`を加え、偽のエンジン台本でこの行が候補と基準の両方へ送られることをテストで固定する。
完了条件は、テストが通り、[docs/guides/sprt.md](../guides/sprt.md)に無効化の条件が記され、既存の測定の保存形式が変わっていないことである。

### フェーズ4　lishogiのブリッジ改修と有効化

フォークstepney141/lishogi-botに`bestmove resign`の処理を入れ、偽のエンジンと偽のAPIを使うテストで、通常の探索と的中では投了APIだけを呼び、外れた先読みでは呼ばず、投了後に先読みを始めないことを固定する。
`minase-lishogi-bot`のイメージを更新して、配備環境で投了の通信を確かめる。
完了条件は、公開対局でminaseの投了が対局記録に`resign`として残ることである。

## 検証

- `cargo test`と`cargo clippy --all-targets`が通る。
- 投了の契約（宣言、受理と拒否、深さ0での非投了、詰み帯での投了、閾値での投了、境界値29,744と30,000での挙動、`stop`と`ponderhit`の経路、出力順、局面の不変）をマトリクスの挙動IDに対応するテストで固定する。探索実行中と完了保留中のそれぞれについて、`stop`と`ponderhit`を区別して検証する。
- 投了しない探索の`bench`深さ6の総ノード数が着手前と一致する。
- ハーネスの起動手順が`ResignValue`の無効化を両エンジンへ送ることを、偽のエンジン台本のテストで固定する。
- 詰まされる局面を`position sfen`で与えた`minase --protocol usi`の対話で、`info`行の後に`info string stop`と`bestmove resign`が出ることを確かめる。

## 完了条件

次をすべて満たしたとき、本マイルストーンを完了とする。

- 調査メモに既定値の選定根拠が残り、利用者が確定した既定値がソースの宣言と一致している。
- USI層の契約がテストで固定され、マトリクスと台帳が改訂されている。
- ハーネスの無効化がテストで固定され、docs/guides/sprt.mdに記されている。
- lishogiの公開対局で投了が成立し、ブリッジの改修がフォークに固定されている。
- 外部対局接続、lishogi Bot接続、およびROADMAPの状態表が現行の実装へ改訂されている。

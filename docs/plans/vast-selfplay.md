# vast.aiでの教師生成

## 先に読む要約

本計画では、中将棋の教師データの生成を、vast.aiで借りる計算機（以下、生成機）へ移す。
開発に使っている手元の作業機では、教師生成と棋力測定が計算資源を取り合い、30ファイルの生成に約35時間かかるので、作業機を占有せずに、より短い時間で生成を終えることが目的である。
教師データは、自己対局の各局面に探索の評価値や対局結果を付けた学習用のデータであり、既存の生成コマンド`minase data selfplay generate`が、対局の乱数の種（シード）の連続した範囲1つにつきファイル1本を書く。
vast.aiは、個人や事業者が貸し出す計算機を時間単位で借りられる市場であり、出品はすべてGPU付きの機械だが、CPUは借りたGPUの割合に応じて割り当てられるので、GPUをすべて借りれば機械全体のCPUを使える。
生成機では生成コマンドをシード範囲ごとに順に実行し、完成したファイルを生成機のディスクに置く。
作業機は生成中に10分ごとにファイルを取得し、ヘッダと件数を計画と照合する検査に通ったファイルだけを受け入れ、そのファイルが作業機にあることを完了の記録とする。
生成機が途中で止まった場合は、作業機にないシード範囲だけを新しい生成機へ送って生成し直すので、失うのは最後の取得以後の分だけである。
機種は、AMDのサーバー向けCPUであるEPYCのうちZen 4以降の世代を2基積んだ、物理192コア、384スレッドの機械を条件として選ぶ。
この条件で借りたEPYC 9654の2基構成の機械の試走では、1ファイルを約11分で生成し、30ファイルを約5.5時間、約5.6米ドルで生成できる見込みを得たが、作業機より速いかは、作業機で同じ条件の生成を測ってから判定する。
完了条件は、作業機より速い生成を実際のvast.aiで確認し、生成機が途中で止まっても作業機の検査済みファイルに欠落と重複が起きないことである。

## 状態

状態は起案であり、起案日は2026年10月16日、調達先をvast.aiとする改訂は2026年10月17日である。
実装には未着手であり、作業機にはvastai CLI 1.8.3が入っている。
作業機のAPIキーで`vastai show user`と`vastai show ssh-keys`が通ることを2026年10月17日に確かめ、同じ日に作業機のvast.ai専用の鍵`~/.ssh/id_vastai`の公開鍵をアカウントに登録した。
フェーズ0のうち生成機での測定は2026年10月17日に終え、結果を[試走の記録](../measurements/vast-selfplay/vast-selfplay-trial.md)に書いた。
同時384局で1ファイル653秒（4,206記録局面/秒）であり、同時192局より約10%速かったので、並列度はスレッド数とする。
いま詰まっている点は、作業機で別の学習が動いており、作業機での同じ条件の測定を始められないことである。
次の一手は、作業機の他の処理が止まった時点で、同じコミットとシードの1ファイルを作業機で生成し、作業機より速いことを確かめてフェーズ0を終えることである。

## 目的

作業機（Intel Core Ultra 7 265KF、Pコア8＋Eコア12の20スレッド）では、教師生成と棋力測定が計算資源を取り合い、30ファイルの生成に約35時間かかる。
教師生成をvast.aiの計算機へ移し、作業機より短い時間で生成を終えることが第一の目的である。
費用は、速さの条件を満たす機種のうち最も安いものを選んで抑える。
速度で作業機に劣る機種は、費用が安くても採用しない。

## 適用範囲

対象は、`minase data selfplay generate`による、乱数で開始局面を作る自己対局の教師生成である。
生成機は、`run_id`で識別する1つの実行につき1台とし、1ファイルの生成の中で`--concurrency`によって複数の対局を並列に進める。
生成機のディスクへの保存、作業機への取得と検査、および中断後の再開までを実装対象とする。

探索、教師データ形式MNSD版2、および学習器は変更しない。
対局の途中状態の保存、実戦棋譜からの生成、複数台への作業配布、および学習中の重みの再開は対象外とする。
作業機で追加生成した結果を同じ実行に混ぜる操作も設けない。作業機で続ける場合は、新しいシード範囲の別の実行として手引きどおりに生成する。

## 依存関係

教師データの構造と検査は、[MNSD版2の実装](../../crates/minase/src/training/records.rs)と[生成・検査コマンド](../../crates/minase/src/bin/minase/selfplay_gen/)を使う。
`inspect`はヘッダを表示したうえで全対局を復号するので、ファイルの途中の破損も検出する。
学習器は複数の完成ファイルを入力できるため、ファイルを1つへ連結する必要はない。
生成条件と過去のシード範囲の確認は、[教師生成の手引き](../guides/pst-training.md)に従う。
生成コマンドはヘッダの生成コミットを`git rev-parse HEAD`で取り、作業ツリーに未コミットの変更があれば停止するので、生成機にも固定コミットのGit作業コピーが要る（[生成コミットを固定する教訓](../lessons/pin-generation-binary-to-worktree.md)）。
GitHubのリポジトリ`stepney141/minase`は公開されているので、生成機は認証情報なしにcloneできる。
作業機では、vast.aiのCLI（`vastai`）で生成機の作成、状態の確認、ファイルの取得、停止、および削除を行う。

## 設計判断

|---|---|---|
| 計算機の調達先 | vast.ai。利用枠の申請が要らず、残高を入れれば数分で借りられる。物理192コアの機械が1時間あたり1〜5米ドルで出品されている（2026年10月17日に公開APIで確認）。 | AWSのEC2のc8a.48xlargeは、新規アカウントではvCPU上限の引き上げに審査が要り、AWSは所要時間を公表していない。時間単価は10.35米ドルで、30ファイルの費用は約29米ドルと約2倍になる。RunpodのCPU Podは1台あたり最大32 vCPU（2026年10月16日にAPIで確認）で、作業機の数倍に届かない。 |
| 機種 | Zen 4以降のEPYCを2基積み、384スレッド以上を持つ機械を、GPUをすべて借りる条件で選ぶ。2026年10月17日の候補はEPYC 9654またはEPYC 9B14の2基構成である。単一スレッド性能は作業機のPコアの約0.59倍だが、物理コアが多い。試走では、EPYC 9654の2基構成で1ファイルを約11分で生成した。 | 1基構成の192スレッド機は速度が約半分で、30ファイルの費用も2基構成より安くならない。Zen 2とZen 3のEPYCは単一スレッド性能がさらに低い。vast.aiの自動試験に通っていない機械は選ばない。そうした機械の表示は、未検証を表すunverifiedか、検証の取り消しを表すdeverifiedである。 |
| 購入方式 | オンデマンド。時間単価がすでに安く、中断への対策を足すほどの節約にならない。 | 入札型（interruptible）は、より高い入札が入ると生成機が停止し、生成中のプロセスが終了する。 |
| 保存先 | 生成機のコンテナのディスク。停止しても内容が残り、停止中でも`vastai copy`で作業機へ取得できる。生成機には、vast.aiが生成機ごとに発行し、その生成機の開始、停止、および削除にだけ使えるAPIキー（以下、インスタンス専用のAPIキー）のほかに、認証情報を置かずに済む。 | S3などのクラウドストレージは、送信用の認証情報を、運営者がファイルを読める他人の機械に置くことになる。vast.aiのCloud Syncも、外部ストレージの認証情報を貸し手の機械へ写す。vast.aiのボリュームは作成した物理機械に固定され、作業機へ直接コピーできない。 |
| 完了の記録 | 生成機では、正常終了したファイルを作業用の場所から`teacher/`へ名前の変更で移し、その存在を生成機の中での完了とする。作業機では、取得して検査に通ったファイルの存在を、実行全体の完了とする。 | 生成機の中の記録だけで完了を判断すると、生成機が失われたときに、作業機へ取得していないファイルまで完了と誤る。 |
| 取得の方法 | 作業機が`vastai copy`で生成機の`teacher/`と`logs/`を10分ごとに取得する。生成機が動いていても停止していても同じ方法で取得でき、生成中に取得しておけば、生成機が失われても失うのは最後の取得以後のファイルだけになる。 | SSHを使うrsyncやscpは、生成機のコンテナが動いている間しか使えない。vast.aiの中継を通るSSHは、大きな転送に向かない。 |
| 転送の検査 | 作業機が、取得したファイルを`inspect`で検査し、ヘッダと生成ログを計画と照合する。`vastai copy`が使うrsyncは、転送したファイルを全体の検査和で確かめ、転送中のファイルを一時的な名前で書いて最後に名前を変える（CLI 1.8.3は`--inplace`を付けない）ので、作業機に現れたファイルは転送を終えたものである。 | 生成機でSHA-256の一覧を作り作業機で照合する方式は、rsyncの検査と`inspect`の上に照合を重ねるだけなので設けない。 |
| 再開の単位 | シード範囲1つにつきファイル1本という既存の生成単位をそのままバッチとする。作業機は計画のうち検査済みファイルがない行だけを生成機へ送り、生成機は自分の`teacher/`にある名前を飛ばす。1回の中断で失う計算は、最後の取得以後に完成したファイルと生成中の1ファイルである。 | 対局や探索の途中状態の保存は、保存対象と復元条件を増やすので入れない。 |
| 実行環境 | 生成機のイメージには、Rustの公式Dockerイメージ`rust:<版>-bookworm`を指定する。起動方式には、vast.aiがコンテナにSSHの接続を用意して起動時スクリプトを実行する方式（以下、SSHの起動方式）を使う。ツールチェーンはイメージの版で、Rustの依存はCargo.lockで固定され、イメージにはcurl、git、およびgccも含まれる。生成機は固定コミットをcloneし、`target-cpu=native`でビルドする。 | Ubuntuのイメージにrustupでツールチェーンを入れる方式では、期限での停止に要るcurlもaptで入れることになり、その失敗で停止が予約されない。専用のDockerイメージの作成と配布は、ビルドを1回に減らすための仕組みであり、ビルドが数分で終わる192コア機には要らない。イメージのentrypointで起動する方式では、vast.aiの起動時スクリプトを使えない。 |
| 生成の起動 | vast.aiの起動時スクリプトが、まず期限での停止を予約し、次に作業機が送る開始の印（空ファイル`started`）を待ってから生成を始める。起動時スクリプトはコンテナが起動するたびに動き得るので、再起動の後も同じ経路で生成を続けられる。作成時に指定した環境変数とインスタンス専用のAPIキーも、起動時スクリプトには届く。 | 作業機からSSHで生成を始める方式では、作成時に指定した環境変数がSSHのセッションに既定で届かず、コンテナが再起動すると生成が止まったままになる。 |
| 費用の上限 | 前払い残高は見積もりに余裕を加えた額だけ入れ、自動補充は設定しない。生成機は作成時に指定した期限に、インスタンス専用のAPIキーで自分を停止する。自己停止が失敗した場合は、作業機の`fetch.py`が期限の超過を見て停止を要求する。作業機は全ファイルの検査を終えた時点で生成機を削除し、停止と削除はいずれも生成機の状態を照会して成功を確かめる。 | 期限での自己削除は、作業機へまだ取得していないファイルを消し、取り戻せなくする。残高が0になると生成機は停止するが、ディスクの課金は負の残高として続き、保存したカードへの請求か、猶予期間の後の生成機とデータの削除で精算されるので、残高を上限の代わりにしない。 |
| 生成機の数 | 1つの実行につき生成機は1台とし、同じ実行のラベルを持つ生成機があれば新しい生成機を作らない。 | 2台を同時に動かすと、同じシード範囲を二重に生成し得る。 |

## 機種、費用、および選定条件

### 見積もりの土台

作業機の実測は、[初代NNUEの教師生成](../measurements/nnue-replacement/nnue-replacement-generation.md)の20ファイル（7,500局、1局面20,000ノード、同時12局）に22.87時間かかった記録を使う。
1ファイルあたり1.14時間、30ファイルで約35時間である。
容量は、この記録の旧形式（1局面160バイト）で数えると30ファイルで約14 GBになる。
現行のMNSD版2は1局面の固定部が7バイトなので実際にはこれより小さく、試走では1ファイルが25.1 MB、30ファイルで約0.75 GBだった。

候補の1スレッド性能は、CPUの公開ベンチマークであるPassMarkの単一スレッド評価を、作業機のPコアに対する比として表す。
作業機の値には、同じコアを持つCore Ultra 7 265Kの4,928を使う。
作業機とEPYC 9R45の値は2026年9月8日時点、EPYC 9654とEPYC 9B14の値は2026年10月17日に参照した値である。
EPYC 9654は2,898、EPYC 9B14は2,886であり、比はともに約0.59である。
参考に挙げるAWSのc8a.48xlargeのEPYC 9R45は0.77である。
vast.aiの出品が示すコア数は、1つの物理コアで2つのスレッドを同時に動かすSMTのスレッド数であり、384スレッドの2基構成は物理192コアに当たる。
1物理コアに1局を割り当てると、作業機の同時12局に対して約9.4倍（192×0.59÷12）になる。
SMTで2局目を載せたときの上積みは測っていないので、0〜3割の幅を置いて約9.4〜12.3倍と見積もった。
試走では、SMTの上積みは約11%だったが、384スレッドを同時に動かすと1スレッドあたりの探索速度が単独で動かしたときの約3割に落ち、生成の速さはこの見積もりを下回った（[試走の記録](../measurements/vast-selfplay/vast-selfplay-trial.md)）。
作業機の同時12局にはEコアも含まれるが、すべてPコアで動くとみなして作業機の性能を過大に見積もる。一方、PassMarkの値は1スレッドだけを動かしたときの値であり、GPU向けに組まれた機械で384スレッドを同時に動かしたときの周波数は分からない。以下の倍率はこの両方向の不確かさを持つ推定であり、採否はフェーズ0の実測で決める。

### 候補の比較

価格は、2026年10月17日にvast.aiの公開APIで照会したオンデマンドの出品の例であり、使わないGPUの代金を含む。
出品は貸し手の都合で入れ替わり、価格も変わる。試走の時点で選定条件を満たす最も安い出品は、EPYC 9654の2基構成の1時間1.02米ドルだった。

| 構成 | 物理コア／スレッド | 作業機比 | 30ファイル | 1時間あたりの例 | 30ファイルの費用 |
|---|---|---|---|---|---|
| EPYC 9654または9B14の2基構成 | 192／384 | 約9.4〜12.3倍 | 約2.9〜3.7時間 | 4.00〜4.80米ドル | 約11〜18米ドル |
| EPYC 9654または9B14の1基構成 | 96／192 | 約4.7〜6.1倍 | 約5.7〜7.4時間 | 2.67米ドル | 約15〜20米ドル |
| 参考：AWSのc8a.48xlarge | 192／192 | 約12倍 | 約2.8時間 | 10.35米ドル | 約29米ドル |

同じSMTの上積みを仮定すると、1基構成の30ファイルの費用は、2基構成の1時間4.00米ドルの例より高く、4.80米ドルの例と同程度である。
1基構成は費用が安くならず速度が約半分になるので、2基構成を採る。
ディスク50 GBの保管料は、4時間で0.2米ドル未満である。
作業機への転送料は、貸し手ごとの料金（1 TBあたり4〜40米ドル）で、30ファイルの約0.75 GBなら0.03米ドル以下である。
試走の費用は、作り直した1台目と転送料を含めて約0.54米ドルだった。

### 選定条件

生成機は、`vastai search offers`で次の条件をすべて満たすオンデマンドの出品のうち、1時間あたりの価格が最も安いものとする。
GPUの種類は問わない。

- 出品が機械のGPUのうちどれだけを貸すかを表す`gpu_frac`が1であり、借り手が使えるCPUのスレッド数`cpu_cores_effective`が機械のスレッド数`cpu_cores`と等しい。vast.aiはCPUとメモリを、借りたGPUの割合に応じて割り当てるからである。
- CPUがZen 4以降のEPYCであり、`cpu_cores`が384以上である。
- `verified=true`であり、vast.aiが記録する機械の信頼度`reliability`が0.95以上である。生成機が失われても再開できるので、信頼度は生成機を作り直す手間を減らすための目安である。
- 貸出期限までの日数`duration`が1日以上である。貸出期限に達した生成機は停止し、起動し直せず、48時間後に削除され得るので、生成と取得に要る数時間に余裕を持たせる。
- 外から直接つながるポートの数`direct_port_count`が1以上であり、vast.aiの中継を通らずにSSHで接続できる。
- 送信速度`inet_up`が100 Mbps以上である。30ファイルの約0.75 GBを約1分で作業機へ転送できる。
- `disk_space`が50 GB以上である。

### 実行前の確認

vast.aiは前払い制であり、最低の入金額は5米ドルである。
SSHの公開鍵は、アカウントに登録した後に作った生成機にだけ入るので、生成機を作る前に`vastai create ssh-key`で登録する。
CLI 1.8.3にファイルのパスを渡すと、ファイルの中身ではなくパスの文字列が鍵として登録されるので、`vastai create ssh-key "$(cat ~/.ssh/id_vastai.pub)"`のように公開鍵の中身を渡し、`vastai show ssh-keys`で登録内容を確かめる。
作業機の`scp`、`ssh`、および`vastai copy`には、この鍵`~/.ssh/id_vastai`を指定する。
`vastai create instance`には`--cancel-unavail`を付ける。付けないと、割り当てに失敗したときに停止状態の生成機が作られ、ディスクの課金が続く。

作業機に入れたCLI 1.8.3のソースでは、3つのコマンドの確認と終了コードの挙動が、資料の記述と異なる。
`vastai destroy instance`は確認を求め、端末がなければ中止するので、スクリプトからは`-y`を付けて呼ぶ。
`vastai stop instance`と`vastai destroy instance`は、APIが失敗を返しても終了コード0で終わる経路がある。
`vastai copy`は、内部で実行するrsyncの終了コードを確かめない。
このため、停止と削除の成否は生成機の状態の照会で、取得の成否は作業機にそろったファイルで判断する。

## 生成と保存

### 実行の構成

実行ごとに`run_id`を決め、作業機の`data/vast-selfplay/<run_id>/`に次の配置で置く。`data/`はGitの管理外である。

| パス | 内容 |
|---|---|
| `plan.tsv` | 1行に1ファイル分の`名前`、`シード`、`局数`をタブ区切りで並べる。`名前`は教師ファイルの名前`<名前>.mnsd`に使う。シードはそのファイルの基本シードである。生成コマンドは基本シードと対局番号の和から各対局の乱数の種を作るので、1ファイルは基本シードから局数の分だけ連続した範囲を使う。 |
| `conditions.toml` | 生成コミット、Rustツールチェーンの版、ノード上限、手数上限、置換表容量、ランダム着手、期待する規則コード列、および期待する重みの検査和を、TOMLのキーとして1行ずつ書く。規則は生成コマンドが`engine-default`に固定しており変更できないので、`inspect`の`rule_set`と比べる期待値である。重みの検査和は`inspect`の`network_checksum`（重みファイルのヘッダを除いた本体のSHA-256、16進表記）と比べる期待値であり、作業機で同じコミットのビルドによる短い生成の`inspect`出力から写す。 |
| `received/` | 生成機の`teacher/`を取得した写し。検査の前のファイルを含む。 |
| `teacher/<名前>.mnsd` | 検査に通った教師ファイル。`received/`の同名ファイルへのハードリンクであり、内容を複製しない。存在が実行全体の完了の記録であり、学習にはこのディレクトリのファイルを渡す。 |
| `logs/` | 生成機の`logs/`を取得した写し。 |
| `deadline` | 現在の生成機の停止の期限（UNIX時刻）。`launch.py`が生成機を作るたびに書き、`fetch.py`が自己停止の失敗を見つけるために読む。 |

計画の行はどれも同じ列を持つ表なのでタブ区切りにし、条件は型を持つ値の組なのでTOMLにする。作業機と生成機のスクリプトはPythonで書き、標準ライブラリの`csv`と`tomllib`で読む（統括計画の設計判断の「スクリプトの言語」）。
シードは互いに局数以上離し、過去の生成と重ならないことを手引きの手順で確認する。
`plan.tsv`と`conditions.toml`は実行を始めた後は変更せず、条件を変える場合は新しい`run_id`で別の実行にする。
並列度は生成機のスレッド数とし、期限までの分数は、1ファイル約11分にファイル数を掛けて1.3倍し、ビルドの分として10分を足した値とする（30ファイルで439分）。
1ファイルの局数は7,500のまま変えない。試走では、終わり近くで負荷が下がり始めたのが同時384局で終了の約55秒前（所要時間の約8%）であり、局数を増やして縮められる時間はこれより短い。
並列度と停止の期限は生成機ごとに決める実行時の値なので、計画には含めず、`launch.py`の引数で受け取って生成機の作成時に環境変数として渡す。省略時の既定値は置かず、省略はエラーにする。

### 生成機の起動

`launch.py`は次の順に処理する。

1. 計画全体を読み、名前の一意性と文字種、列数、シードと局数の値の範囲、および`conditions.toml`の必須項目の有無を検査し、不正なら生成機を作らずに止まる。完了は`teacher/<名前>.mnsd`の有無で判定するので、名前が重複すると、先の行で作られたファイルによって、まだ生成していない後の行まで完了とみなされるからである。
2. `vastai show instances`に同じ`run_id`のラベルを持つ生成機があれば、新しい生成機を作らずに止まる。
3. 作業機の`teacher/`に教師ファイルがない行だけを、生成機に送る`plan.tsv`として書き出す。残りの行がなければ止まる。
4. 引数の「期限までの分数」を現在時刻に足して期限のUNIX時刻を求め、作業機の実行ディレクトリの`deadline`に書く。
5. 指定した出品に、`conditions.toml`の版の`rust:<版>-bookworm`のイメージ、SSHの起動方式と直接接続（`--ssh --direct`）、ディスク50 GB、`--cancel-unavail`、ラベル、並列度と期限の環境変数、および起動時スクリプトを指定して`vastai create instance`を実行する。
6. 生成機の状態がAPIの`actual_status`で`running`になるまで待つ。`running`は稼働中、`stopped`は停止、`exited`はコンテナの処理が終わった状態、`offline`は貸し手の機械がvast.aiとの接続を失った状態、`unknown`は状態が分からないことを表す。`running`にならずに`stopped`、`exited`、`offline`、または`unknown`になった場合と、待ち時間の上限を超えた場合は、生成機を削除して止まる。上限は10分とする。試走では、作成から`running`まで、イメージの取得を含めて82秒、取得済みのイメージで23秒だった。
7. `vastai show instance --raw`の`public_ipaddr`と`ports`の`22/tcp`の割り当てからSSHの接続先を求める。`vastai ssh-url`は結果を一時ファイルに保存して使い回すので使わない。待ち時間の上限までに割り当てが得られなければ、生成機を削除して止まる。
8. `scp`で`/workspace/job/`へ`plan.tsv`、`conditions.toml`、および`remote.py`を送り、すべての送信が成功した後に、`ssh`で開始の印となる空ファイル`started`を作る。送信に失敗した場合は、まだ何も生成していないので、生成機を削除して止まる。

起動時スクリプトは、次の順に処理する。

1. `/root`、`/root/.ssh`、および`/root/.ssh/authorized_keys`の所有者をrootにし、権限をそれぞれ700、700、600にする。`rust:<版>-bookworm`のイメージでは、これを直さないとsshdが「bad ownership or modes」として公開鍵の認証を拒んだ。あわせて`/root/.no_auto_tmux`を作る。vast.aiはSSHのログインごとにtmuxを開き、そのままでは非対話のSSHのコマンドが「open terminal failed: not a terminal」で失敗するからである。
2. 期限での停止をバックグラウンドで予約する。期限を過ぎていれば直ちに停止を要求する。停止は、vast.aiが渡す`CONTAINER_ID`とインスタンス専用のAPIキー`CONTAINER_API_KEY`を使い、vast.aiのAPIの`PUT /api/v0/instances/{id}`に`{"state": "stopped"}`をcurlで送って行う。これはCLIの`vastai stop instance`と同じ操作であり、停止してもディスクの内容は残る。1回の要求は60秒で打ち切り、各回の結果を`logs/onstart.log`に書く。APIが4xxの応答で要求を拒んだ場合は、送り直しても変わらないので、そこで諦める。通信の失敗と5xxの応答では1分おきに送り直し、30分で諦める。自己停止が失敗した場合は、`fetch.py`が期限の超過を見て作業機から停止を要求する。
3. `started`が現れるまで待つ。
4. `remote.py`をバックグラウンドで起動し、出力を`logs/remote.log`に追記する。

停止の予約を開始の印より先に置くのは、作業機が送信の途中で止まり`started`が作られなかった場合にも、期限で課金が止まるようにするためである。
コンテナが再起動するたびに同じ期限で予約し直すので、期限は作成時に決めた時刻から動かない。
vast.aiの起動時スクリプトは、SSHとJupyterの起動方式でだけ使え、4,048文字までに限られる。
vast.aiの資料は起動時スクリプトがコンテナの起動時に動くと述べ、初回だけとは述べていないので、再起動のたびに動くものとして扱う。
このため、処理の本体は`remote.py`に置き、`remote.py`は何度起動されても完了済みの行を飛ばすように書く。

### 生成機での手順

生成機のディスクでは、`/workspace/job/`の下に次の配置を使う。

| パス | 内容 |
|---|---|
| `plan.tsv`、`conditions.toml`、`remote.py` | 作業機が送るジョブ一式。`plan.tsv`は作業機の計画のうち未完了の行だけを同じ形式で並べる。 |
| `started` | ジョブ一式の送信が終わったことを示す空ファイル。 |
| `minase/` | 生成コミットのGit作業コピー。 |
| `work/` | 生成中の教師ファイルとログを置く一時ディレクトリ。 |
| `teacher/<名前>.mnsd` | 生成コマンドが正常終了した教師ファイル。存在が生成機の中での完了の記録である。 |
| `logs/` | 行ごとの生成ログ、起動時スクリプトと`remote.py`のログ、および`remote.py`の終了コードを書いた`exit-status`。 |

`remote.py`は次を順に行う。

1. 前回の`exit-status`と`work/`の中身を消す。コンテナの停止や強制終了で途中のファイルが`work/`に残っていても、ここで除かれる。
2. コンテナに許されたCPUの数を示す`nproc`と、CPU時間の上限をログに書く。上限は、cgroup v2なら`/sys/fs/cgroup/cpu.max`、v1なら`/sys/fs/cgroup/cpu/`の`cpu.cfs_quota_us`と`cpu.cfs_period_us`にある。試走の機械はv1であり、上限はCPU約368.6個分だった。vast.aiはコンテナのCPUの制限方式を公表していないので、実際の割り当てを記録に残す。
3. 作業コピーがないか、そのHEADが生成コミットでなければ、作業コピーを作り直してGitHubから生成コミットを取得する。リポジトリの`.cargo/config.toml`にある`target-cpu=native`のまま`cargo build --release --locked --bin minase`を実行する。評価関数の重みは実行ファイルに埋め込まれるので、別に配布しない。再起動の後は、cargoがビルド済みの部分を再ビルドしない。
4. 計画の行ごとに`teacher/<名前>.mnsd`の有無を調べ、あれば飛ばす。
5. なければ、カレントディレクトリを作業コピーにしたまま生成コマンドを実行する。生成コマンドがカレントディレクトリで`git rev-parse HEAD`と`git status`を実行するからである。`--allow-dirty`は付けない。出力とログは、行ごとに新しく作る`work/`の下の一時ディレクトリへ絶対パスで書く。生成コマンドは出力を新規作成でしか開かないが、試行ごとに新しい出力先を使うので、前の試行のファイルと衝突しない。
6. 生成コマンドが終了コード0で終われば、ログを`logs/<名前>.log`へ移し、最後に教師ファイルを`teacher/<名前>.mnsd`へ移す。どちらも同じファイルシステムの中での名前の変更なので、`teacher/`に途中のファイルは現れず、`teacher/`にある教師ファイルには必ずログがある。
7. 生成コマンドが失敗した場合は、ログを`logs/<名前>.failed.log`へ移し、次の行へ進まずに終了する。
8. 終了時に、自分の終了コードを一時ファイルに書いてから`logs/exit-status`へ名前の変更で移す。準備の段階で失敗した場合も同じである。

教師ファイルの内容の検査は、生成機ではなく、信頼できる作業機で`fetch.py`が行う。
生成機の運営者はコンテナのファイルを読み書きできるので、生成機での検査の結果は受け入れの根拠にならないからである。

### 作業機での取得と検査

`fetch.py`は、次の1回分の処理を10分ごとに繰り返す。
`vastai`の各コマンドには上限時間を設け、超えたら失敗として扱う。
1回の`vastai copy`の上限は60分とし、状態の照会と、停止および削除の確認の上限は10分とする。
試走では25.1 MBの1ファイルを12.5秒で取得したので、60分は30ファイルをまとめて取得する場合にも十分な長さである。

1. `vastai show instances --raw`で`run_id`のラベルを持つ生成機を探す。1台もなければ、検査済みのファイルを残したまま、未完了の行を表示して0以外の終了コードで止まる。2台以上あれば、何も操作せずに0以外の終了コードで止まる。
2. 作業機の`logs/exit-status`を消してから、`vastai copy`で生成機の`teacher/`を作業機の`received/`へ、続いて生成機の`logs/`を作業機の`logs/`へ取得する。rsyncは生成機で消えたファイルを作業機から消さないので、先に消しておかないと、前の生成機の終了コードを読んでしまう。
3. 作業機に`exit-status`が届いたか、生成機の`actual_status`が`stopped`、`exited`、`offline`、または`unknown`であれば、生成機の処理は終わっている。処理が一時停止して課金だけが続く`frozen`と、作業機の`deadline`の時刻を過ぎてなお`running`である場合は、生成機を停止してから同じく終わったものとする。この場合は、手順2の取得をもう一度行い、この回を最後の回として以後の手順を進める。教師ファイルの取得とログの取得の間に最後のファイルが完成した場合も、この取得で回収できる。起動中の`loading`と再起動中の`rebooting`は処理の途中なので、最後の回とせずに次の回へ進む。
4. `received/`にあり`teacher/`にないファイルごとに、生成ログがあることを確かめる。ログがまだない場合、最後の回でなければ次の回に回し、最後の回なら検査の失敗とする。
5. ログがそろったファイルに`inspect`を実行し、その終了コード0を確かめる。続いて、ヘッダの`generation_commit`、`rule_set`、`seed`、探索ノード上限の`teacher_search_budget`、および`network_checksum`が、`conditions.toml`と`plan.tsv`に一致することを検査する。生成ログについては、`games_completed`が要求局数と一致し、`nodes`、`max_ply`、`hash_mb`、および`random_moves_max`が`conditions.toml`と一致し、ヘッダの`game_count`と`games_discarded_max_ply`の和が要求局数と一致することを検査する。
6. 検査に通ったファイルは、`received/`の同名ファイルへのハードリンクを`teacher/`に作る。1つでも通らなければ、生成機を停止し、0以外の終了コードで止まる。
7. 計画の全行が`teacher/`にそろえば、`vastai destroy instance <ID> -y`で生成機を削除し、生成機が一覧から消えたことを確かめて、終了コード0で終わる。
8. 最後の回で計画の行が残っていれば、動いている生成機を停止し、残りの名前を表示して0以外の終了コードで止まる。

停止は`vastai stop instance`の後に`intended_status`が`stopped`になり、`actual_status`が`stopped`か`exited`になること（試走では`exited`だった）、削除は`vastai destroy instance`の後に当該のIDが一覧から消えることを、それぞれ上限時間の中で確かめる。
確かめられなければ、生成機のIDと終わっていない操作を表示して、0以外の終了コードで止まる。
APIが作業機からの停止も受け付けない場合、課金を止める手段はvast.aiのコンソールでの操作だけになるので、利用者がその表示を見てコンソールから停止する。
要求した全局が手数上限で破棄された場合も、生成が正常終了し件数の照合が成り立てば、保存局数0の完了ファイルとして扱う。
手数上限で破棄した対局も予約したシード範囲を消費するので、保存局数の不足を理由に同じ実行の局数やシードを増やさない。

### 中断と再開

コンテナが再起動した場合は、起動時スクリプトが期限での停止を予約し直してから再び`remote.py`を起動し、`remote.py`は生成機の`teacher/`にある名前を飛ばして生成を続ける。
コンテナの再起動を自分で行う場合は、`vastai reboot instance`を使う。このコマンドはGPUの割り当てを失わずにコンテナを止めて起動し直す。

期限で停止した場合と生成が失敗した場合は、`fetch.py`が停止した生成機から最後の取得と検査を済ませ、残りの名前を表示して止まる。
この後の削除と作り直しは自動では行わず、利用者がその表示とログを確かめてから、生成機を`vastai destroy instance`で削除し、`launch.py`で別の生成機を作って残りの行を生成させる。
停止した生成機の起動し直しは、その間にGPUが別の借り手に貸されていると始まらないので、再開の手段にしない。
生成の失敗が計画や条件の誤りによる場合は、新しい`run_id`で別の実行にする。

貸し手の機械がオフラインになった場合は、その間の課金は止まるが、生成機のファイルも取得できず、`fetch.py`は残りの名前を表示して止まる。
待つ間の費用はかからないので、急がなければ機械が戻るのを待って`fetch.py`を起動し直す。
急ぐ場合は生成機を削除して別の生成機を作る。作業機へ取得していないファイルは失われ、新しい生成機で生成し直される。

## 操作の入口

スクリプトは`scripts/vast-selfplay/`に置く。
[探索の関数形の見直しの統括計画](search-forms.md)のSPSAのスクリプトと共通する処理（機械の作成と待機、SSHの接続先、起動時スクリプトの権限の修正と自己停止、停止と削除の確認）は、先に実装する側が`scripts/vast/common.py`に置き、後から実装する側はそれを使う。

| 操作 | 内容 |
|---|---|
| `launch.py` | 作業機で実行する。引数は`run_id`、出品のID、並列度、および期限までの分数である。計画を検査し、未完了の行だけを持つ生成機を作り、ジョブ一式を送って生成を始めさせる。起動時スクリプトは、`scripts/vast/onstart.sh`の共通部分に生成の起動行を加えて作る。 |
| `remote.py` | 生成機で、起動時スクリプトから呼ばれる。ビルドの準備、生成、および終了コードの記録を行う。 |
| `fetch.py` | 作業機で実行する。引数は`run_id`である。生成機から10分ごとにファイルとログを取得して検査し、全行がそろえば生成機を削除し、生成機の処理が終わっても行が残るか失敗を見つければ、生成機を停止して止まる。 |

## 実装フェーズ

フェーズ0では、選定条件に合う機械を30分ほど手作業で借りて測る。
30分は、ビルド、並列度を2通りにした1ファイルずつの生成、および取得の測定を合わせた時間である。
測るのは、`minase dev bench`の1スレッドの探索速度、7,500局の1ファイルの生成の所要時間、および記録局面/秒の3つである。
探索速度はNPS（1秒あたりのノード数）で表す。
記録局面/秒は、教師ファイルに書いた局面の数を生成時間で割った値である。
生成は、同時対局数をスレッド数に合わせた場合と物理コア数に合わせた場合の両方で測り、速い方を並列度とする。
あわせて、`rust:<版>-bookworm`のイメージがSSHの起動方式で動くこと、作成から`running`までの所要時間、コンテナの中の`nproc`と`/sys/fs/cgroup/cpu.max`の値、1ファイルの大きさ、および1ファイルを`vastai copy`で作業機へ取得する所要時間を確かめる。
`vastai copy`はコンテナのSSHではなく貸し手の機械のrsyncを通るので、その経路が選定条件の機械で使えることも、ここで確かめる。
作業機では、他の処理を止めた状態で同じ測定を行う。
1ファイルの終わり近くで長い対局だけが残り、ほかのスレッドが空いて待つ時間も測り、無視できない場合は1ファイルの局数を増やす。
同じシード範囲を作業機と生成機で生成して教師ファイルの内容を比べ、差があれば測定記録に残す。
同じ内容になれば、貸し手の機械で生成したファイルを作業機での再生成で抜き取り検査できるが、生成の決定性は本計画の要件ではないので、この比較は完了条件に含めない。
完了条件は、選定条件、並列度、1ファイルの局数、期限までの分数、`launch.py`の待ち時間の上限、および生成1回の費用見積もりが実測に基づいて確定していることである。

フェーズ1では、`launch.py`、`remote.py`、および`fetch.py`を実装し、少ないコアの安い機械を検証用の生成機として借りて、小さい局数の計画で「検証」の全条件を通す。
生成機を作らずに止まるべき条件は、作業機だけで確かめる。
完了条件は、「検証」の全条件を通すことである。

フェーズ2では、`docs/guides/vast-selfplay.md`に準備、起動、取得、費用の確認、および片付けの手順をまとめる。試走の測定はフェーズ0で`docs/measurements/vast-selfplay/vast-selfplay-trial.md`に記録しており、作業機の測定もここに加える。
永続的な仕様を各スクリプトの冒頭の説明へ、設計判断をADRへ移してから本書を凍結する。

## 検証

| 条件 | 期待する結果 |
|---|---|
| 名前が重複する計画、列数の足りない計画、および必須項目の欠けた`conditions.toml`を`launch.py`に与える。 | 生成機を作らずに止まる。 |
| 同じ`run_id`のラベルを持つ生成機があるときに`launch.py`を実行する。 | 新しい生成機を作らずに止まる。 |
| 複数ファイルの計画を中断せず実行し、`fetch.py`で取得する。 | 計画した全ファイルが作業機の`teacher/`に1回ずつ載り、要求局数と保存・破棄局数が整合し、生成機の削除が確かめられて`fetch.py`が終了コード0で終わる。 |
| 生成機の`remote.py`が終わった後に、初めて`fetch.py`を起動する。 | 最後の回の取得で全ファイルとログがそろい、終了コード0で終わる。 |
| `fetch.py`の実行中に、生成中のコンテナを`vastai reboot instance`で再起動する。 | `fetch.py`は`loading`と`rebooting`の状態で止まらずに続く。完成していた行は生成し直されず、中断した行だけが同じシードで生成し直される。`teacher/`に途中のファイルは現れない。 |
| 生成中に生成コマンドを`kill -9`で強制終了し、`fetch.py`が止まった後、生成機を削除して同じ`run_id`で`launch.py`を実行し、`fetch.py`を起動し直す。 | 強制終了した行のファイルは`teacher/`に移されず、`exit-status`に0以外が記録され、`fetch.py`は生成機を停止して止まる。新しい生成機では、作業機に残った前の`exit-status`で止まらずに完走し、強制終了した行が同じシードで生成される。 |
| 全局を手数上限で破棄する設定の行を計画に入れる。 | 保存局数0で、要求局数と破棄局数が一致する完了ファイルとして作業機の`teacher/`に載る。 |
| 作業機の検査に通らないファイルを生成機の`teacher/`に置く。 | `fetch.py`はそのファイルを作業機の`teacher/`に載せず、生成機を停止して0以外の終了コードで止まる。生成機は削除されない。 |
| 存在しない生成コミットを指定して`remote.py`を失敗させる。 | 生成機の`logs/exit-status`に0以外が記録され、`fetch.py`が生成機を停止して0以外の終了コードで止まる。 |
| 期限を短くして生成機を作る。 | 期限に生成機が停止し、停止した生成機から`fetch.py`が`teacher/`と`logs/`を取得できる。 |
| 期限を短くし、生成機の作成後、`started`を作る前に`launch.py`を強制終了する。 | 生成は始まらず、期限に生成機が停止する。 |
| `fetch.py`の実行中に、生成の途中で生成機を削除し、`launch.py`で別の生成機を作って`fetch.py`を起動し直す。 | 最初の`fetch.py`は検査済みのファイルを残して未完了の行を表示し、0以外の終了コードで止まる。新しい生成機では作業機にない行だけが生成され、最後には作業機の`teacher/`が計画の全行を1回ずつ持つ。 |
| 停止の要求が4xxで拒まれるように起動時スクリプトの要求先を変えた生成機を、短い期限で作り、`fetch.py`を動かしておく。 | 起動時スクリプトは4xxの応答で自己停止を諦め、期限の超過を見た`fetch.py`が作業機から生成機を停止し、停止を確かめる。 |
| 停止と削除の権限のないAPIキーで、`fetch.py`に生成機の停止と削除を要求させる。 | 状態の照会で成功を確かめられず、生成機のIDと終わっていない操作を表示して0以外の終了コードで止まる。 |

## 完了条件

フェーズ0の実測で、採用した機種で1ファイルを生成する時間が作業機より短いこと。
生成、作業機への取得と検査、および再開をスクリプトから行え、「検証」の各条件を満たしていること。
試走の時間、費用、および転送量の記録と、同じ操作を再現できる手引きがあること。
仕様と設計判断の移し替えを終え、`docs/ROADMAP.md`の状態を更新して本書を凍結していること。

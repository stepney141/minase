# 提案と議論の索引

本ディレクトリは、minaseの方式についての提案と、その検討の議論を収める。
提案は、[調査メモ](../research/README.md)が確かめた外部の事実や、[監査報告](../audits/)が記したある時点のminaseの診断を根拠に、候補と試す順序を示す。
表題に「調査」を含む文書でも、minaseへの採用の候補や試す順序が主題なら本ディレクトリに置く。

## 提案と設計書の違い

提案は、何を試すかを利用者が選ぶための文書であり、候補、根拠、費用と効果の見込み、および勧める順序を書く。
[設計書](../plans/README.md)は、選んだ候補をどう試し、どの基準で採否を決めるかを定め、その作業を進めるための文書である。
そのため、提案には設計判断、実装フェーズ、完了条件、および作業の状態を書かない。
提案を検討する中で利用者が設計書の起案の前に決めたことは、起案する設計書の「設計判断」の節に書く。
測定による採否は設計書と設計判断の記録（[ADR](../adr/README.md)）に記し、提案は候補の行き先を示すだけにする。

## 提案の書き方

提案の最初の節は「候補の扱い」とし、提案が挙げた候補を1行ずつ並べた表で、それぞれの扱いを示す。
扱いは次の4つのいずれかとする。

| 扱い | 意味と書き方 |
|---|---|
| 未決 | 利用者がまだ判断していない。 |
| 設計書へ | 候補を設計書へ渡した。採否はその設計書が決めるので、設計書へのリンクを添える。 |
| 不採用 | 利用者が行わないと決めた。根拠を記した設計書かADRへのリンクを添え、どちらもなければ決定の日付と理由を1文で書く。 |
| 取り下げ | 前提が成り立たなくなった。前提を失った理由を1文で書く。 |

「候補の扱い」より後の本文は、作成日の時点の分析として書き、後から採否や進捗を書き足さない。
本文を直すのは、根拠の誤りを見つけた場合と、勧めの前提になった事実が変わった場合に限る。
外部の事実のうち、設計書やADRが根拠に引くものは、調査メモとして分けて書く。
1つの提案は1つの主題に絞り、主題の異なる候補は別の提案にする。

## 更新と凍結

候補を設計書へ渡すときは、起案する設計書と同じコミットで「候補の扱い」の表を書き換える。
利用者が候補を不採用と決めたときと、候補の前提が成り立たなくなったときも、その時点で表を書き換える。
「未決」の候補が残る提案は、本ディレクトリの直下に置く。
「未決」の候補がなくなった提案は、[archived/](archived/)へ移して凍結する。
移すときは、その提案の冒頭に短い段落を置いて決着の日付と内容を書き、本書の「未決の候補が残る提案」の表から該当する行を「決着した提案」の表へ移して「決着」の列を埋める。
凍結した提案は書き換えない。
この規則は2026年11月13日に定めた。
それより前に決着した提案は「候補の扱い」の節を持たず、それより前に書いた提案には、設計書の起案の前に決めたことを本文に記したものがある。

本書の表は、作成日（初回のコミット日）の古い順に並べる。

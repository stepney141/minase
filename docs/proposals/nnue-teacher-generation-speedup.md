# NNUE教師生成の高速化候補

本書は、中将棋エンジンminaseの自己対局による教師生成について、探索結果を保って計算費用を減らす候補を示す提案である。
教師生成は、自己対局で得た局面と探索の評価値を、着手に応じて評価を差分更新するニューラルネットワークNNUEの学習用データとして保存する処理を指す。
作成日は2026年11月14日であり、分析の基準はコミット`c1c84466476eb36cf43abc529792469862b8e856`と、[2026年11月13日の教師生成の測定](../measurements/adhoc/nnue-teacher-bottleneck-20261113.md)である。
各候補の改善量は未測定であり、本書の優先順位は、確認された負荷、変更範囲、および追加する処理の費用から判断したものである。

## 候補の扱い

| 候補 | 扱い |
|---|---|
| 攻撃駒の存在判定を早期終了する | 未決 |
| 静かな手の線形評価差分で移動元の計算を共有する | 未決 |
| 同点破りの線形評価差分を必要な手だけに求める | 未決 |
| 置換表の検証キーを詳細な復号より先に照合する | 未決 |
| 生成機のCPUとメモリの配置、および並列数を合わせる | 未決 |

## 測定が示す範囲

ローカルの測定では、対局を進める処理の98.52–98.68%を探索が占め、書き出しは生成全体の経過時間の0.02–0.06%に相当した。
学習済みの幅256のネットを使い、1局面を20,000ノード、1局を最大4,000手、ランダム着手を0手として、完局まで動かした値である。
規則は日本中将棋連盟に準拠する`L0,P0,R1,E0`であり、測定機はIntel Core Ultra 7 265KFだった。
この条件で生成を速めるには、まず探索側の処理を減らす必要がある。

サイクル標本を重複しない区分に分けた主な内訳は次のとおりである。
分母は採取周期で重み付けしたCPUサイクルの標本の合計であり、経過時間や削減可能な時間の割合ではない。

| 処理 | サイクル標本の構成比 |
|---|---:|
| 手生成、利き計算、および盤面のビット集合演算 | 32.1% |
| 手の順位付け、整列、および関連する履歴参照 | 21.8% |
| NNUE評価と累積値更新 | 14.7% |
| 置換表 | 8.8% |

手生成と利き計算を含む区分の32.1%には、攻撃駒の全件列挙が必要な処理も含まれる。
順位付けの21.8%には、履歴表の参照、採点、および整列が含まれるため、整列だけの変更で全体を削れるとは見込めない。
また、[以前の高速化](../measurements/teacher-generation-speedup/teacher-generation-speedup-engine.md)で、利きの逆引き、王手判定の情報共有、採点の共通計算、および部分整列は既に導入されている。
今回の候補は、その後にも残る計算を対象とする。

新しいコード候補が直接変える範囲は、これらの大分類の一部に限られる。
攻撃駒の存在判定で対象となる照会は全サイクル標本の2.27%であり、手の順位付けで使う静かな手の線形評価差分は1.44%だった。
線形評価差分の標本は、上表ではNNUEの区分に含めている。
線形評価差分は、移動元の共通計算と同点破りの2候補が同じ処理を対象にするので、改善量を独立に加算できない。
大きな費用削減を見込むときには、本書の小さな変更だけでなく、後述する既存の手生成の計画と、生成機の料金と処理速度の比較も判断材料になる。

4並列の測定では、終了時にワーカーが不足し、割り当てたCPUを使い切れなかった。
8局の生成が終わる前の約8.0–8.5秒に探索ワーカーが2本だけ残っていた。
CPUの命令処理枠に対するメモリ待ちの指標は、1並列の10.9%から4並列の11.9%への変化だった。
この測定は終了時のワーカー不足を確認したが、数百並列でのメモリ帯域の飽和を判定するものではない。
コードの変更と大規模並列の設定は、根拠の異なる候補として考える。

## コードを変える候補

### 攻撃駒が見つかった時点で存在判定を終える

現在の[王駒への攻撃判定](../../crates/minase/src/search/alphabeta/royal.rs)は、`attackers_to_by`が返す攻撃駒の集合を作ってから、空かどうかを調べる。
王駒は王将、玉将、および太子を指す。
この呼び出しでは攻撃駒が1枚でもあれば足りるので、最初の1枚を見つけた時点で残りの駒種と方向の検査を終える案が考えられる。
対象は結果の存在だけを必要とする照会であり、取り合いの評価のように攻撃駒の集合を使う照会は全件列挙を続ける。

最初に調べる対象としては、現在の盤面をそのまま使う王駒への攻撃判定が扱いやすい。
[利きの逆引き](../../crates/minase-core/src/movegen/control.rs)が扱うのは、駒の動きと遮蔽から決まる疑似利きであり、獅子を取る手の合法性まで一律に判定するものではない。
存在判定もこの契約を保つ必要がある。
攻撃駒が存在しない照会は最後まで調べるため、呼び出し回数だけでなく、真になる割合と早期終了までに調べる量が効果を左右する。

仮想盤面を使う照会へ広げる場合は、盤上を遮る駒と攻撃候補に残す駒を区別する必要がある。
[王手判定](../../crates/minase-core/src/movegen/gives_check.rs)は移動元の駒を攻撃駒の集合から除き、[獅子の足の判定](../../crates/minase-core/src/movegen/lion_capture.rs)は捕獲後に残る相手駒との共通部分を取っている。
足は、獅子が取られたと仮定した盤面で、獅子と同じ側の駒の利きがその升に届くことである。
これらを集合の加工を伴わない存在判定へそのまま置き換えると、取られた駒や移動前の駒を数えるおそれがある。
王駒が2枚残る王手判定も、2枚を1手ですべて取れるかを判定する別の条件なので、一律に置き換えられない。

変更範囲は存在判定の入口とその呼び出し元だが、利きの規則を二重に持つ実装には保守費用が生じる。
集合を作る処理と存在を判定する処理で利きの定義を共有でき、早期終了の節約が追加の分岐を上回るかを確かめたい。
手生成と利き計算を含む区分の32.1%から、この候補の改善率を直接見積もることはできない。
呼び出し元別の追加集計では、現在の盤面を使う王駒への攻撃判定と、王手判定のために着手前の盤面の利きを調べる処理は、合わせて全サイクル標本の1.12%だった。
この2箇所は返された集合を加工しないため、最初に調べる対象になる。
仮想盤面の王手と獅子の足まで広げた対象は2.27%だが、これも削減量ではなく、現在の処理が占める標本の割合である。

### 静かな手の評価差分で移動元の計算を共有する

駒を取らない手を、本書では静かな手と呼ぶ。
現在の[手選択器](../../crates/minase/src/search/alphabeta/ordering.rs)は、履歴などによる第一の採点値、線形評価の差分、および生成順の3つで静かな手の順序を確定する。
[線形評価差分の計算](../../crates/minase/src/eval/nnue/mod.rs)は、駒数から求める係数と、移動元と移動先の重みを使う。
同じ駒を動かす候補では、移動元の特徴番号と重みを共有できる。

この候補は、線形評価差分の値と採点時点を保ち、移動元の特徴番号と重みを駒ごとに1回だけ求める案である。
手選択器は既に移動元ごとの情報をまとめており、その既存のまとまりへ必要な値を加える程度の変更が考えられる。
局面をまたいで保持する表を増やす必要はない。

[機械語の確認](../measurements/adhoc/nnue-teacher-bottleneck-20261113.md#改善候補が対象とする処理の範囲)では、駒数の係数は既にループの外で計算されていた。
したがって、係数の共通化による追加の高速化は見込まない。
一方、移動元の特徴番号の計算と重みの読み出しは各手の処理に残る。
対象は順位付け全体の一部に限られるが、変更範囲が小さく、採点の値を変えずに試しやすい候補である。

### 同点破りの評価差分を必要な手だけに求める

現在の手選択器は、第一の採点値が異なる手にも、同点破りの線形評価差分を計算している。
第一の採点値が同じ手だけをまとめ、その組の中だけで評価差分を求めれば、単独の採点値を持つ手の計算を省ける。
ただし、同点の組を見つける費用と、整列の回数が増える費用が加わる。
同点になる手の割合が高ければ、省ける計算は少ない。

この候補では、第一の採点値を求める時点と、最後に生成順で同点を解く規則を保つ必要がある。
履歴表は子局面の探索中にも更新されるため、次の手を取り出すたびに第一の採点値を求め直す方式は着手順を変え得る。
また、部分整列の境界で同点の組が分断されても、線形評価差分を含む従来の順序を保たなければならない。
共通計算をまとめる候補より処理が複雑になるため、同点の組の大きさと実際に取り出す手の割合を調べた後の候補と考える。

### 置換表のキーの不一致を先に判定する

置換表は、探索済み局面の評価値などを記録して再利用する表である。
現在の[照会処理](../../crates/minase/src/search/alphabeta/tt.rs)は、読み出した記録の予約領域と評価値の種類を検査してから、局面の検証キーを比較する。
キーが違う記録は結果を使わないので、キーの不一致を先に判定すれば、空振りした照会の詳しい復号を省ける可能性がある。

この候補では、読み出した同じ記録を使ってキーを比較し、一致した記録には従来どおりの検証を行う。
表の大きさ、記録の置換規則、および並列探索の読み出し順序の保証は変える必要がない。
測定に使ったバイナリの機械語でも、詳しい復号がキーの比較より前に残っており、順序を変える余地は確認できる。

今回のL3キャッシュのロードミス標本の70.3%は置換表に帰属した。
これはミスの発生箇所の内訳であり、置換表による停止時間の割合ではない。
キーを先に比較しても記録をメモリから読む待ちは残るので、置換表の8.8%を大幅に削れるとは見込まない。
復号関数に帰属したサイクル標本の大半もロード直後の命令に集中しており、復号だけの費用が大きいという根拠にはならなかった。
変更範囲は小さいものの、他のコード候補より優先順位を下げるのがよい。

## 生成機の使い方を変える候補

### CPUとメモリの配置を合わせて並列数を選ぶ

多数のCPUを持つ機械では、CPUとメモリの接続位置によってアクセス時間が変わるNUMA構成を取ることがある。
NUMAは非一様メモリアクセスを意味する。
複数のNUMAノードが見える機械では、CPUの割り当てとメモリの確保先を同じノードへ寄せる候補がある。
並列数の調整は、NUMAノード数によらず全体の生成速度を比べて行う。
メモリの配置は既存のページを自動で移し替えるとは限らないので、起動時の割り当てから比較する必要がある（[Linuxのメモリ配置の説明](https://docs.kernel.org/admin-guide/mm/numa_memory_policy.html)）。

[2026年11月4日の生成機測定](../measurements/nnue-generation-reset/nnue-generation-reset-generator-speed.md)では、AMD EPYC 9654を2基持つ機械で、旧版を2プロセスへ分け、それぞれのCPUをNUMAノードへ固定すると約9%速くなった。
この先例はCPUの固定を比べたもので、メモリの配置方針の指定による改善を測ったものではない。
これは現行版やGoogle Cloudでの改善率を示す値ではないが、配置を比較する根拠にはなる。
同じ記録では並列数を減らすと全体の処理速度も下がっており、1ワーカーの速度だけで並列数を決めることはできない。

置換表は各ワーカー内で確保されるので、CPUの固定だけでも配置が変わる可能性がある。
CPUの固定とメモリの配置方針の指定を分けて比べれば、どちらが効いたかを判別しやすい。
この候補の費用は主に起動方法と測定条件の整備であり、探索の実装を変えずに試せる。
一方、対象機での測定費用と、複数プロセスで対局のシードを重複させない管理が必要になる。
判断に使う値は、保存局面数/秒、常駐メモリ、および同じ局面数を保存するまでの料金である。
時間料金が固定の機械では、並列数を減らしただけでは料金は減らないため、全体の処理速度を含めて比べたい。

## 既存の計画と判断との関係

[合法手生成と利き計算の高速化の第3期](../plans/movegen-speedup-3.md)には、走り駒の集合で空振りする方向を先に除く案がある。
この案は存在判定を早期終了する案と別の手段だが、同じ利き計算を変えるため、両者の改善率を独立とみなして加算できない。
今回の攻撃駒の照会は、全サイクル標本の8.46%が取り合いの評価からの呼び出しに帰属し、存在判定だけの変更ではこの部分を減らせない。
第3期の診断は今回より古いコードと探索条件によるものなので、現行の教師生成でも空振りが多いかを確認する余地がある。
本書では既存計画の候補として参照し、同じ内容を新たな未決候補に重ねて登録しない。

[教師生成の中断と再開](../plans/archived/resumable-nnue-teacher-generation.md)は、複数の対局をまとめた教師ファイル1本の内部を小さな単位で保存して、中断後に再利用する計画である。
同計画は1本7,500局という単位と、本ごとのシードを保つ。
保存の区切りごとに全ワーカーを待ち合わせないことは、末尾待ちを増やさないための重要な前提である。
この計画そのものは、1本の最後に起きるワーカー不足を解消するものではない。

終了時のワーカー不足を減らすために1本の局数を増やす案は、[以前の設計判断](../plans/archived/teacher-generation-speedup.md)で、中断時に失う量と検査の単位が変わるため見送られている。
小さな単位での保存が加われば中断時の損失は減るが、検査の単位と標準レシピの量の定義は変わらないので、今回は候補に戻さない。
生成器は既に、対局を終えたワーカーが次の対局番号を受け取る[動的な割り当て](../../crates/minase/src/bin/minase/selfplay_gen/generate.rs)を行っている。
末尾では新たに配る対局が残らないため、この方式でもワーカーが余る。
[第2世代の生成記録](../measurements/nnue-generation-reset/nnue-generation-reset-gen2-training.md)にある384並列での未使用CPU時間13.25%は、対象機での損失を調べる根拠として扱い、少数並列の損失率へ換算しない。

[NNUEの標準レシピ](../plans/nnue-standard-recipe.md)は生成の規則を`lishogi`へ切り替える計画を含む。
今回の比率は日本中将棋連盟の規則で測った値なので、規則とネットが変われば、候補の働く頻度も測り直す必要がある。
複数の条件を同時に変えた速度差を、この提案のコード変更だけの効果とは扱えない。

過去に見送った方式は今回の候補に戻さない。
実行頻度をコンパイラへ渡すプロファイル誘導最適化と、`unsafe`を要する置換表の先読みは[既存の方針](../plans/archived/teacher-generation-speedup.md)に従い対象外とする。
置換表の縮小とmimallocの環境変数の変更には[不採用の測定](../measurements/teacher-generation-speedup/teacher-generation-speedup-allocator-and-hash.md)があり、複数の本の生成を重ねる改修も[第2世代の記録](../measurements/nnue-generation-reset/nnue-generation-reset-gen2-training.md)で見送られている。
1局面の探索ノード数や履歴表の構成を変える案は教師の内容と質も変えるため、同じ教師を安く作るという本書の候補には含めない。

## 試す順序の提案

新しいコード候補の中では、静かな手の移動元の特徴番号と重みを共有する案を最初に勧める。
繰り返す計算が機械語に残ることを確認でき、採点の値と順序を保ったまま小さく変えられるためである。
次に、攻撃駒の存在判定が真になる割合を調べ、後処理のない照会に限った早期終了を検討する。
同点破りの遅延計算は、移動元の共有後に残る計算と同点の頻度を見てから選び、置換表の照合順序は最後に置くのがよい。
より広い利き計算を対象にする既存の第3期の計画と比べる際は、改善の対象範囲と変更量の双方を判断材料にしたい。

生成機の配置と並列数は、その機械で得る保存局面数/秒を比べる候補である。
コードの改善が終わるまで待つ必要はないが、使う版とネットを固定して比べ、別の機械の値を代用しない。

コードを変える候補を選ぶときには、同じ局面の探索ノード数、最善手、評価値、および教師ファイルを保てることが必要になる。
最終的な費用には保存した教師局面数/秒が直結するが、今回の測定環境では小さな速度差を最適化の効果と判定できない。
以前の高速化で使った命令数とサイクル数も調べ、変更前後を交互に測って、減らせた処理と経過時間の揺れを区別する方法が適している。
具体的な測定条件と採否の手順は、選んだ候補を渡す設計書で定める。

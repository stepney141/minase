# 規則実装の形式検証の実現可能性と検証を強める候補

本書は、minaseの規則実装（crate `minase-core`）が規則書 [chu-shogi.md](../rules/chu-shogi.md) を正しく実装していることを形式検証できるかを検討し、検証を強める候補と試す順序を示す。
形式検証とは、プログラムが仕様を満たすことを、テストの標本ではなく、数学的な証明または全入力の機械的な検査で示すことをいう。
検討は2026年11月25日と26日に行い、対象はmasterのコミット`767c36fe`（`crates/minase-core`の最終変更は`eaf49464`）と、規則書の第17版である。
先行例と道具についての外部の事実は、調査メモ[ゲームの規則実装を形式検証した先行例とRustの検証器の調査](../research/formal-verification-prior-art.md)にある。
検討では、AIエージェントのClaudeとcodexがそれぞれ独立に分析し、互いの主張をコードと資料で確かめた。
以下、コードのパスは`crates/minase-core/src/`からの相対で書く。

本書で使う用語を先に定める。
局面合法手は、1つの局面だけから決まる合法手をいい、`MoveGenerator::generate_moves`が生成する。
対局合法手は、対局が続いている間は、局面合法手から、対局の履歴によって反復規則R2またはR3が禁じる手を除いたものをいい、終局後は空である。`Game::legal_moves`が返す。
合法手生成器の健全性は生成された手がすべて規則上合法であること、完全性は規則上合法な手がすべて生成されることをいう。
信頼の基底は、証明や検査の結論が正しいと言うために、検証されないまま信頼する部分をいう。
審判の層は、反復と終局を裁定する`game/`以下のコードをいう。
ADRは、設計判断を1件ずつ記録した文書であり、[docs/adr/](../adr/README.md)にある。

## 候補の扱い

扱いは、利用者の判断の状況を表す。
「未決」は利用者がまだ判断していないことをいい、本書の勧めとは別である。

| 候補 | 扱い |
|---|---|
| 1. 規則書だけから書いた局面合法手の独立仕様と、本番の合法手生成器との双方向の照合 | 未決 |
| 2. 有限の部品（駒の動きの表、走りの遮蔽、成りの可否、規則コードの受理）の全数検査 | 未決 |
| 3. 着手の適用による状態の遷移、反復の履歴、および終局条件の優先関係を、独立な参照実装と照合する検査 | 未決 |
| 4. 有界モデル検査器Kaniによる記号的な検査 | 未決 |
| 5. 証明支援系Lean 4で書いた規則のモデルについての定理の証明 | 未決 |
| 6. Rustのコードの演繹的な検証（Verus、Creusot、Aeneasなど）によるcrate全体の証明 | 未決 |

## 結論

`minase-core`の全体を、任意の局面と任意の長さの対局について一括で証明する方式（候補6）は、原理的には可能だが勧めない。
理由は3つある。
第1に、規範である規則書は自然言語で書かれているので、証明できるのは実装と形式仕様の一致までであり、形式仕様が規則書に合っていることは人の承認に残る。
規則書は第17版まで改訂が続いており、典拠に明文がない事項を補った補充規定を多く含む。
第2に、本番の反復の判定は、規則上の同一局面を、局面から計算した64ビットのハッシュ値（Zobrist値）の一致で近似している（[ADR](../adr/keep-zobrist-keys-at-64-bits.md)）。
値の衝突がないと仮定しない限り、反復を含む対局全体についての定理は成り立たない。
第3に、演繹的に検証する道具は、変数を可変で捕捉するクロージャ、実行時に構築する表、および`HashMap`に制約があり、本番のコードの書き換えを求める。
先例の証明の行数は、Verusの事例で実装の約3.3倍から13.3倍、Aeneasと証明支援系Leanによる暗号ライブラリの事例で約14倍である。

一方、規則実装を区分に分ければ、強さの異なる保証を現実的な費用で得られる。
入力が有限で小さい部品は、通常のRustのテストで全入力を検査できる。
局面合法手は、規則書だけから書いた独立な仕様と本番の生成結果の一致を、宣言した有限の配置の集合では全数で、それ以外は乱数対局の局面で照合できる。
反復と終局の裁定は、履歴と全手の生成に依存するので、範囲を限った検査と、独立な実装との出力の突き合わせにとどまる。

既存の検証には、固定した局面で合法手の欠落を検出する事例のテストがある。
欠けているのは、独立な仕様が定める局面の集合について、規則の組合せを含む合法手の集合の全体を、健全性と完全性の両方向で照合する検査である。
したがって最初に勧めるのは、証明器の導入ではなく、候補1である。
候補2と候補3をその後に置き、候補4と候補5は、後述する条件が満たされたときに限って勧める。

検討の副産物として、規則書の条文から読みが一意に決まらず、読みによって本番の挙動の正否が変わる箇所が4件見つかった。
条文と本番は一致しているが、典拠に照らして条文を見直す余地のある定義も1件見つかった。
形式仕様は期待値を条文から書くので、4件のうち局面合法手に関わる2件は候補1より前に、残りは候補3より前に、規則書を管理する人が決める必要がある。

## 「正しく実装している」の定義

正しさは、規則書の第17版でminaseが提供すると定めた規則セットごとに、3つの命題に分けて定義する。
連盟式の千日手R0は、規則書に条文があるが実装しないと明記されている（第31条、第33条第4項）ので、対象から外れる。

1. 局面合法手については、整合した局面`p`（盤面の配列、ビットボード、およびZobrist値が互いに矛盾しない`Position`）と任意の着手`m`について、次の2つが同値であることをいう。1つは、`m`が`generate_moves(p)`の出力に含まれることである。もう1つは、規則の下で合法な移動の経路が存在し、その経路を着手の正準形（同じ結果になる複数の経路を1つの表現にまとめた形）へ直したものが`m`であることである。前者から後者が健全性、後者から前者が完全性に当たる。同じ着手が2回出力されないことは別の命題とする。
2. 状態の遷移については、合法手を適用した後の盤、手番、駒の成否、先獅子の記録（直前の着手で獅子以外の駒が獅子を取った升の記録）、および成り権の保留が、参照仕様の遷移と一致することをいう。着手の取り消し（`unmake_move`）で全部の状態が戻ることは追加の実装上の契約であり、往復できても順方向が正しいとは限らない。
3. 対局合法手と裁定については、初期局面から規則に従って到達する履歴について、`Game::legal_moves`が対局合法手の集合に等しく、`Game::play`の後の状態と勝敗が参照仕様と一致し、終局後の着手が拒否されることをいう。

形式検証が保証するのは、本番と形式仕様の一致である。
形式仕様が規則書の意味を正しく写していることは、保証しない。
後者は、定義を短く読みやすく保つこと、定義と条項を対応づけること、典拠にある事例を試験に使うこと、および外部の実装と照合することで支えるしかなく、先行例も同じ種類の手段を使っている。
照合に使える外部の実装は、オンライン対局サイトlishogiの棋譜と、既存の中将棋エンジンHaChuである。

得られる結果の強さは3段階に分かれ、混同しないように区別して表示する。

| 得た結果 | 主張できること |
|---|---|
| 独立に書いたRustの述語と本番の生成器を、明示した有限の局面の集合と全候補で照合した | その集合について、本番が仕様に適合する。列挙の網羅性、比較のコード、およびコンパイラを信頼する。集合の外の局面には及ばない。 |
| Leanで、任意の局面についてモデルの生成器と仕様の同値を証明した | Leanのモデルと仕様が全域で一致する。本番のRustとは標本を突き合わせただけなら、Rustについては標本での適合にとどまる。 |
| 本番のRustの意味と仕様の間の対応まで証明した | 証明に置いた前提の下で、本番が仕様と全域で一致する。 |

## 既存の検証が確かめている範囲

既存の検証は、条文ごとの固定した局面の事例と、乱数対局の局面での健全性の側の必要条件を検査している。
独立な仕様と本番の合法手の集合を、多数の局面で双方向に照合する検査はない。

- 条番号を名前に持つ事例のテストは、期待値を条文から導く（[ADR](../adr/derive-test-expectations-from-normative-documents.md)）。駒の動きのテスト（`movegen/tests/pieces.rs`）は、条文の方向と距離から期待する到達升の集合を作り、生成結果と集合として等しいことを調べるので、その局面では合法手の欠落も検出する。獅子の捕獲規則には、第13条から第16条と第29条の項ごとの固定局面が約40件ある（`movegen/tests/lion_capture.rs`）。
- 乱数対局による性質のテスト（`movegen/tests/properties.rs`の`assert_canonical_invariants`）は、生成された手が満たすべき性質を検査する。検査する性質は、重複がないこと、到達升に自駒がないこと、経由升が始点に隣接すること、および成る手に不成の対があることである。規則上合法な手がすべて生成されることは検査しない。
- 参照実装との照合（同じファイルの`generation_before`と、`game/adjudication/tests/oracle.rs`）は、最適化する前の本番の実装の複製を参照実装に使う。この参照実装は、利きの計算、2段階移動の生成、成りの展開、および獅子の捕獲の判定を本番と共有するので、共有する部分の誤りを検出しない。規則書から独立に書いた合法手の参照実装は、リポジトリにない。
- lishogiの棋譜の再生（`tests/lishogi_replay.rs`）は、実際に指された手を`Game::play`が受理することと、終局の裁定を確かめる。指されなかった合法手の欠落は分からない。
- フィーチャ`invariants`は、着手の適用と取り消しのたびに、局面の整合と、差分で更新したZobrist値と再計算した値の一致を検査する。

perftは、ある局面から指定した深さまでの合法手の列の総数を数え、外部の実装の値と照合する検証の方法である。
perftの手数を基準にしない決定の[ADR](../adr/verify-movegen-without-perft-counts.md)は、その結果として「獅子の規則の相互作用を系統的に網羅する検証は失われ、その代わりを条文ごとの事例テストが担う」と書いている。
候補1は、この系統的な検証を、手数の照合とは別の形で補う。

## 規則実装の区分

規則実装を、入力の大きさと状態の持ち方で区分した。
区分に共通する事実は次のとおりである。

- 局面`Position`は、盤外の番兵を含む192要素の盤面の配列、占有・色別・駒種別のビットボード、手番、先獅子の記録、成り権の保留の集合、および2つのZobrist値（局面の値と、成り権の保留の値）を持ち、大きさは約1.7キロバイトである。意味を持つ状態は盤面、手番、先獅子の記録、および成り権の保留であり、ビットボードとZobrist値はそこから導かれる。
- 1升の駒コードは79通り（空升、および先後それぞれの不成21種と成駒18種）なので、144升の盤面の配列の値は79の144乗、約10の273乗通りある。この数は、駒の枚数の上限と、初期配置から到達できるかどうかを考えない符号化の総数である。
- 着手の生成と適用に使う規則`MoveRules`は576通り、対局全体の規則`Rules`は10,368通りある。
- 利きの表とZobristの乱数表は、初回の呼び出しで実行時に構築する。
- 再帰する関数はない。ループは、定数個の方向と駒種、ビットボードの立っているビット（最大144）、および生成した手の列を回る。対局の長さに比例して伸びるのは、反復の履歴だけである。

判定の列の「全」は、その行の契約の全入力を検査または証明できることをいい、「有界」は、駒数、配置の集合、または履歴の長さを明示した範囲の検査にとどまることをいう。

| 区分と条文 | 主なコード | 入力の大きさ | 判定 |
|---|---|---|---|
| 駒の動きの定義（第9条から第12条） | `attacks/fixed.rs` | 29駒種の固定の移動量、走りの方向、特殊な動きの種別 | 全。条文から独立に書いた表と照合する。 |
| 利きの表の構築（第7条、第9条から第12条） | `attacks/tables.rs`の`AttackTables::build`、`attacks/sliding.rs` | 入力なし。固定の利きが8,064個、利き線が1,152本 | 全。独立な座標の式と照合する。 |

| 駒ごとの利きと、利きの逆引き（第7条、第9条から第12条） | `movegen/control.rs`の`piece_control_with_occupancy`と`attackers_to_by` | 局面、色、升、および仮想の占有 | 駒と升の対に分解すれば全。個々の駒の寄与を合わせる論証が人手で残る。 |

| 獅子の捕獲規則（第13条から第16条、第29条） | `movegen/lion_capture.rs`、`movegen/virtual_board.rs` | 獅子規則12通り、局面、着手。足（獅子が取られたと仮定した盤面で、その升に利く味方の駒）の判定は、遠くの走り駒と、着手の途中の仮想の盤面に依存する | 有界。足の有無を真偽値として与えた判定の組合せは全。 |
| 成りの可否（第17条から第19条、第30条） | `promotion.rs`の`promotion_choice_for` | 筋に依存しないので、色、駒種、成否、始点と終点の段、捕獲、保留、および成り規則48通りで3,207,168通り | 全。 |

| 反復（第24条、第25条、第31条） | `game/repetition/`、`game/referee.rs` | 対局の全履歴。規則上は長さに上限がない（本番は手数を32ビットで数える） | 無条件の一致は主張できない。正確な局面の列に対する履歴の集計（出現の回数、攻撃の連続数）は帰納で証明できる。 |
| 終局の裁定（第8条、第20条から第23条、第32条） | `game/adjudication/` | 局面、規則、履歴、駒枯れの猶予。詰みの判定は、全合法手の仮の適用と、相手が王駒を取れるかの判定を含む | 有界。 |
| 規則コードの組立て（第28条から第33条） | `rules/assembly.rs`の`Rules::from_codes` | 19個のコードの重複のない部分集合で524,288通り | 集合としての受理と組立ては全。同じコードを重ねた列の拒否は別の契約である。 |
| 直前局面の生成（ある局面の1手前になり得る局面の列挙） | `predecessor/` | 局面全体。候補を順方向の合法性の判定で検証する | 健全性は順方向の判定から導かれる。完全性は有界。 |

コードには、最適化した経路と素朴な定義が一致するという補題が、docコメントとADRに文章で書かれ、テストが標本で検査しているものがある。
走りの利きが1升ずつの歩行と一致すること、`attackers_to_by`が駒ごとの利きの逆引きと同値であること、相手の獅子でない駒の升では利きが届くことと合法な捕獲があることが一致すること、および`is_legal_move`が全手の生成に含まれることと同値であることが、その例である。
これらは実装の内部の同値であり、規則書との一致とは別の層にある。

## 候補

### 候補1：局面合法手の独立仕様との双方向の照合

規則書だけを入力にして、テスト専用のRustで局面合法手の述語を書き、本番の`generate_moves`の出力と照合する。
仕様は本番の分岐を写さず、盤を座標と駒の配列、走りを1升ずつの歩行、2段階移動を途中の盤を持つ経路として書く。
審判の層、探索用の捕獲生成、直前局面の生成、ビットボード、およびZobrist値は含めない。
仕様の側が本番の利きの表や獅子の判定を呼ぶと保証を失うので、呼ばない。

照合は双方向に行う。
完全性は、候補の着手をすべて列挙し、独立仕様が合法とした手が本番の出力に入っていることで確かめる。
候補は、自駒のある始点（各対局者の駒が46枚以下の局面で高々46）、経由升なしまたは隣接8升、到達升144、および成否2の組であり、1局面あたり高々119,232件である。
健全性は、本番が出力した全部の手を独立仕様が合法と認めることで確かめる。
本番の出力を候補の範囲で絞らないので、相手の駒を始点とする手や、隣接しない経由升を持つ手があれば検出できる。

局面は2通り用意する。
1つは、獅子、経由升の駒、足になる駒、および遠くの遮蔽の駒を数升に置く配置の集合を宣言し、その全数を検査するものである。
もう1つは、乱数対局の局面を576通りの`MoveRules`で検査する標本である。
後者は規則の設定については全数、局面については標本である。

この候補で確かめるべきことは、一致に加えて、本番へ意図的に入れた誤り（跳びを1つ落とす、足を調べる升を変えるなど）を独立仕様が検出することである。
既存の参照実装は本番と一部を共有するので、その部分の誤りを見逃す。
独立仕様がその誤りを検出できるかが、この候補の価値を決める。

費用は最も小さい。
追加のcrateも本番の変更も要らず、既存の試験と同じ`cargo test`で動く。
独立仕様の行数と、宣言した配置の全数が通常の試験の時間に収まるかは、書いてみないと分からない。
規則書が改訂されたときは、該当する条項の述語だけを直す。

この方法には限界がある。
同じ規則書から書いた2つの実装は、同じ誤読を共有し得る。
別のエージェントや別の言語で書くことは、独立であることの証拠にならない。
2つの実装の出力を突き合わせる価値は、どちらが誤っているかを判定することではなく、2つの読みが食い違う入力を示すことにある。
仕様の側が本番の関数を借りないと書けない条項、または条文から期待値が決まらない条項については、適合を主張しない。

### 候補2：有限の部品の全数検査

入力が有限で小さい部品を、通常のRustのテストで全入力について検査する。
対象は、駒の動きの定義と利きの表（条文から独立に書いた表および座標の式との照合）、走りの遮蔽（245,604件）、成りの可否（3,207,168件）、および規則コードの受理（524,288件）である。

既存の走りのテスト（`attacks/tables.rs`の`article_7_4_5_sliding_control_matches_a_stepwise_walk_with_blockers`）は、空の盤、全升、対角線、1升だけの占有、および乱数の8標本を調べており、全占有ではない。
ビットボードは3つの64ビット整数からなるので、整数の境界をまたぐ特定の配置でだけ誤る実装があり得る。
全数にすると、そのような誤りを標本に頼らずに検出できる。

走りの遮蔽と成りの可否は、入力を縮約してから全数を数えている。
縮約の根拠（線の外の占有に依存しない、筋に依存しない）は人がコードを読んで確かめるので、信頼の基底に残る。
全数の検査が常設の試験に入れられる時間で終わるかは、実時間を測って決める。

### 候補3：遷移、反復の履歴、および終局の優先関係の検査

候補1の仕様は1局面についての述語なので、複数の手にまたがる誤りを検出しない。
たとえば、P2の待機が次の自分の手番で満了しない誤りは、仕様の側に本番の保留のビットを渡す限り見えない。
候補3は次の3つを加える。

- 成り権の保留と先獅子の記録を、短い手順について独立に追い、本番の遷移と比べる。
- 反復の履歴を2通りに作り、対局の再生を使って比べる。1つは、盤、手番、および一時的な状態を直接比べて同一局面を数える参照実装であり、もう1つは本番のZobrist値による履歴である。
- 終局条件が同じ着手で同時に成立する組合せを列挙し、到達できないもの、勝敗が同じもの、および勝敗が変わるものに分類する。

審判の層まで参照実装を書くと、規則の実装を2つ保守することになる。
参照実装が本番の複製に近づいたら、拡張をやめる。

### 候補4：Kaniによる記号的な検査

Kaniでは、検査したい性質をテストに似た関数（ハーネス）として書き、入力を記号的な値（その型が取り得る任意の値を表す値）にする。
Kaniは、RustをCの有界モデル検査器CBMCの入力へ変換し、範囲内の全入力をSATソルバ（論理式を真にする割り当てがあるかを判定するプログラム）で検査する。
ハーネスを`#[cfg(kani)]`で囲めば、本番の関数の本体を変えずに使える。
実現可能性を確かめるために、Kani 0.68.0で成りの可否と走りの遮蔽を実測した（[測定記録](../measurements/adhoc/kani-rules-feasibility-20261126.md)）。

- 成りの可否では、標準規則の`promotion_choice_for`が、第17条から第19条を段の数値で書いた式と一致することを、色、駒種、成否、始点と終点の升、捕獲、および保留の全入力（9,621,504通り）について、検証の時間0.14秒で確かめた。筋を含む全部の升を記号的に扱うので、候補2が人手に残す「筋に依存しない」という縮約の根拠が要らない。参照の式は、成り先の有無を本番の`PieceKind::promoted`から、段の値を本番の`Square::rank`から借りているので、駒種ごとの成り先と座標の復号の正しさは検査していない。
- 走りの遮蔽では、全部の始点、8方向、および有効な144升の全部の占有（2の144乗通り）を記号的に扱い、`sliding_control`が、1升ずつ進んで最初の駒で止まる歩行と一致することを検査した。Kaniを通した実行は、Kaniが呼ぶ検査器CBMCの常駐メモリが14.3 GiBに、その後Kaniの本体の常駐メモリが15.4 GiBに達し、30.9 GiBの機械のメモリを使い切りかけたので、判定を得る前に打ち切った（GiBは2の30乗バイトである）。同じ検査をCBMCで直接実行すると、開始から2分10秒で一致の判定が出て、常駐メモリの最大は9.8 GiBだった。比較した歩行は、1升の移動とビットの設定に本番の`step_square`と`Bitboard::set`を使い、検査した利き線の表も同じ2つの関数で作られるので、この検査は、方向の定義と升のビットへの対応を条文から独立には確かめていない。
- 本番と同じ入口`attack_tables()`で全部の表を構築するハーネスは、CBMCの仮想メモリを17.2 GiBに制限した直接実行で、表の構築を論理式へ展開している途中にメモリが尽きた。上の一致の判定は、利き線の表だけを本番の`build_ray_table`で構築するハーネスによる。

この結果から言えることは3つある。
第1に、表を読まない標準規則の成りの可否は、Kaniで全入力を1秒以内に検査できた。
第2に、表を読む関数にも検査できた例がある。走りの遮蔽は、利き線の表だけを構築する形にしてCBMCを直接実行すれば検査できた。
第3に、利きの表の全体の構築を検査に含めることは、今回のハーネスの構成と17.2 GiBの制限ではできなかった。
利きの逆引きや合法手生成のように多くの表を読む区分へ広げられるかは、試していない。
表の構築を検査から切り離す場合は、切り離した部分が信頼の基底に入る。
局面の全体を記号的に扱う検査も試していない。

Kani 0.68.0には、CBMCが結果を書き出す途中でメモリ不足になると、途中までの結果から検証の成功を報告し得る不具合があり、修正を含む版は出ていない。
メモリを多く使う検査では、CBMCが正常に終了したことと、結果が欠けていないことを確かめる必要がある。
今回の測定で、この不具合による誤った成功は観測していない。

この候補を勧めるのは、候補2の全数検査で縮約の根拠を人手に残したくない関数がある場合である。
標準規則の成りの可否は、単発の確認として済んでいる。
48通りの成り規則へ広げるには、次の節のP2とP3の併用の読みを先に決める必要がある。

### 候補5：Lean 4で書いたモデルの定理

規則のモデルと仕様をLean 4で書けば、任意の局面についての定理を、Leanの核（証明を検査する小さなプログラム）で検査できる。
本将棋ではlean-shogiが、局面合法手の生成器と仕様の同値を証明している。
規則書の無矛盾性と完全性、すなわちどの局面と着手にも合法性と裁定が一意に定まることも、条項を独立な制約として書けば検査の対象にできる。

ただし、Leanで証明できるのはモデルの側の定理である。
本番のRustとは、別プロセスでテキスト（局面を文字列で表す拡張SFENと、着手の表記）を交換して標本を突き合わせることになり、Rustについては標本での適合にとどまる。
認可言語Cedarの先例は、Leanから生成したライブラリをRustから`unsafe`な呼び出しで使うが、`minase-core`は`unsafe`を禁じているので、テキストの交換が現実的である。
この場合、表記の変換のコードが信頼の基底に入る。
規則書が改訂されるたびに、Leanの定義、証明、および本番との突き合わせの3つを直す費用がかかる。

この候補を勧めるのは、次の2つがともに満たされる場合に限る。
1つは、具体的なモデルの側の全称定理（任意の局面についての定理）が必要な成果になり、その証明が規則の広い範囲を必要とすることである。
もう1つは、規則書を管理する人が、代表的な条項のLeanの定義を本番のコードを見ずに読んで承認でき、条文の改訂に合わせて定義を追えることである。
条件が満たされると見込むなら、候補1の仕様を最初からLeanで書くほうが、同じ条文を2度形式化せずに済む。

### 候補6：crate全体の演繹的な検証

Verus、Creusot、またはAeneasで、本番のRustと仕様の対応を証明する。
成功すれば、入力を列挙せずに本番の全域での一致を得られる唯一の方式である。

勧めない理由は結論の節に書いた。
本番のコードには、道具の制約に当たる書き方がある。
変数を可変で捕捉するクロージャ（`movegen/generate.rs`の`generate_piece_quiets`）、多重のループの中の`return`（`game/adjudication/mate.rs`の`stalemate_or_mate`）、実行時に構築する表、および`HashMap`である。
意味を変えない高速化でも証明が壊れ得るが、合法手生成の高速化は現在も計画されている（[第3期の計画](../plans/movegen-speedup-3.md)）。
外部の利用者への保証が必要になったとき、または局所の検査が見逃す同じ種類の不具合が繰り返されたときに、見直す価値がある。
暗号ライブラリSymCryptの検証では、AIエージェントが証明の大半を生成しており、費用は今後下がり得る。

### 勧める順序

1. 次の節の事項のうち、局面合法手に関わる2件の読みを決める。決めない箇所は、検証の対象から外して明記する。
2. 候補1を行い、独立仕様の行数、条文から決まらなかった箇所、照合の時間、および意図的に入れた誤りの検出の結果を得る。
3. 候補2を加える。
4. 反復と終局に関わる読みを決めたうえで、候補1が見逃す種類の誤りを対象に、候補3を必要な範囲で加える。
5. 候補4と候補5は、それぞれの節に書いた条件が満たされたときに検討する。

## 形式仕様を書く前に決める規則書の事項

条文から読みが一意に決まらない箇所が4件ある。
いずれも本番の不具合と断定するものではなく、本番は一方の読みを実装している。
このうち、P2と最奥段の救済の併用、および付け喰いの優先の範囲は、局面合法手を変えるので、候補1の前に決める。
同一局面の条件と終局条件の優先順位は、反復と終局の裁定だけを変えるので、候補3の前に決めれば足りる。
5件目の詰みの定義は、条文と本番が一致しており、典拠に照らして条文を改めるかどうかの問題である。
どの読みが典拠に照らして妥当かは、[規則書の読みが分かれる箇所の読みの候補](rulebook-readings.md)で扱う。

### 同一局面の条件としての先獅子（第24条第1項c）

条文は同一局面の条件を「先獅子による直後の捕獲禁止の有無と対象」と書く。
本番の反復のキーは、非獅子が獅子を取ったという記録の有無と升を含み、取った側に獅子が残っておらず禁止が生じない場合にも、記録のある局面とない局面を区別する。

初期配置から、2つの読みで裁定が変わる手順を構成できる。
座標は、`Square::new`に渡す0から11までの（筋、段）で書く。
段0は先手側の最下段で、段が増える向きが先手の前方であり、筋0はUSIの表記の12筋に当たる。
先手は仲人を(3,4)と(3,5)の間で往復させ、後手は獅子を(6,9)から(6,7)、(6,5)へ進め、6手目に(6,3)の歩兵を取り、8手目に隣接する(5,2)の先手の獅子を取る。
9手目に先手の奔王が(6,2)から(5,2)へ進んで後手の獅子を取ると、双方に獅子がなくなる。
以後、後手の仲人(8,7)から(8,6)、先手の仲人(3,4)から(3,5)、後手の仲人(8,6)から(8,7)、先手の仲人(3,5)から(3,4)の4手を繰り返す。
13手目の後の局面は、9手目の後の局面と盤、手番、および成り権が同じで、先獅子の記録だけがない。

| 反復規則 | 禁止の有無で読む場合 | 本番（記録で読む） |
|---|---|---|
| R2 | 13手目を禁じる | 13手目を受理し、14手目を禁じる |
| R3 | 21手目を禁じる | 21手目を受理し、22手目を禁じる |
| R1 | 21手目で引き分け | 22手目で引き分け |

本番の列は、規則`L0,P0,E1,E2`と各反復規則で、公開APIの`Game::play`を実行した結果である。

### P2の待機と最奥段の救済の併用（第30条）

P2は、敵陣へ入る着手で不成を選んだ駒が、その側の直後の1手番に限り、非捕獲の着手で成れないと定める。
P3は、香車に最奥段で非捕獲による追加の成る機会を与える。
規則書は両者の併用を認めるが、待機中の香車が最奥段へ非捕獲で進むときにどちらが優先するかを書いていない。
本番は成りを選択できるとし、P6があれば強制にする。
保留を付けた局面を組み立てて`generate_moves`を呼び、この挙動を確かめた。

### 付け喰いの優先が及ぶ範囲（第15条第8項、第16条第7項）

対象は、先獅子の禁止が成立している直後の1手で、獅子が第1段階で足のある隣接する相手の獅子を取り、第2段階で隣接しない別の相手の獅子を取る着手である。
条文は「付け喰いは先獅子より優先する」と書くだけで、第1段階で取る獅子への禁止まで解くかを書いていない。
本番は着手全体を禁止から除く。
標準規則で、先獅子の記録を付けた局面を組み立てて`generate_moves`を呼ぶと、隣接する獅子だけを取る手は生成されず、2枚を取る手は生成される。

### 終局条件の優先順位

規則書は、王駒の捕獲、R1、駒枯れまたは裸玉、合法手なし、および詰みが同じ着手で同時に成立する場合の順位を定めていない。
本番はこの順で裁定する。
順位は勝敗を変え得る。
次の表は、駒を置いて構成した局面と履歴で、本番が採った裁定と、それより後の順位の条件も同時に成立していたことを確かめた例である。
1行目は公開APIで実行し、E3を採る場合と採らない場合の裁定を比べた。
2行目から4行目は、審判の層の関数を直接呼ぶ使い捨ての試験で、本番の裁定（`adjudicate_after_move`）と、合法手なしおよび詰みの判定（`stalemate_or_mate`）を、同じ局面と履歴に適用した。
どの局面も駒の枚数は初期配置の枚数以内だが、初期配置から到達できることは確かめていない。

| 同時に成立した条件 | 規則 | 本番の裁定 | 後の順位の条件を先に適用した場合 |
|---|---|---|---|
| 一方が裸玉で負ける条件（E3）と、もう一方に合法手がないこと | E3 | 裸玉の側の負け | 合法手のない側の負け |
| R1が引き分けと裁定する4回目の出現と、手番側の詰み | R1、E1なし | 引き分け | 詰まされた側の負け |
| 駒枯れによる勝ち（E0）と、勝つ側の詰み | E0 | 余分な駒を持つ側の勝ち | その側の負け |
| 死に駒を除いて双方が王駒だけになった引き分けと、R2の禁止による合法手なし | R2とE0、R2とE3 | 引き分け | 手番側の負け |

4行目の手番側には、最奥段で移動不能になった歩兵（死に駒）がある。この歩兵が王駒の移動先の1つを塞ぎ、残りの移動先はどれも既出の局面を再現するので、R2が禁じる。

### 詰みが王手を要件とするか（第21条第3項）

第21条第3項は、詰みを逃れとなる合法手がないことで定義し、最後の王駒が現に王手を受けていることを要件にしていない。
本番もこの定義のとおりに、王手を受けていないが、何を指しても最後の王駒を取られる局面を詰みと裁定する。
上の表の3行目の局面は、駒枯れを採用しないE2では、詰みによる終局になる。
日本中将棋連盟の初心者向けの[規則の解説](https://www.chushogi-renmei.com/kouza/rule.htm)は、詰みを「王手をかけられてしまい、なおかつ他に逃げる場所が無くなってしまった状態」と説明しており、王手を要件に加えるかどうかが論点になる。

## 検討で分かった実装と文書の不整合

- 局面の整合を検査する`Position::validate`は、同じ色の別の駒種のビットボードに余分なビットが立っていても検出しない。駒種別のビットボードの和集合が色別のビットボードに等しいことと、升ごとに正しい駒種のビットがあることしか調べないからである。
- `game/adjudication/mod.rs`の`adjudicate_after_move`のdocコメントは、駒枯れによる勝利と合法手なしまたは詰みが同時に成立する場合に勝者は一致し、優先順位が変えるのは勝因の表示（`WinReason`）だけだと書く。前節の表の3行目はこの記述の反例である。
- ADR [record-lion-trigger-on-move-and-judge-foot-in-movegen](../adr/record-lion-trigger-on-move-and-judge-foot-in-movegen.md)は、先獅子の記録が「次の合法手を変えるので」Zobrist値に含まれると書く。取った側に獅子が残らない場合、記録は合法手を変えない。
- R1の出現回数は、反復のキーごとに8ビットの整数で数える（`game/repetition/r1.rs`）。R1は、同一局面の4回目以降の出現で、可逆手が12手以上続いていれば裁定して対局を終える。同じ局面は一続きの可逆手の中でしか再現しないので、キーの衝突がなければ回数は255に達しないと推論できるが、この不変条件は文章にも試験にもない。

## 既存の決定との関係

勧める順序は、既存の決定と矛盾しない。
perftの手数を期待値にしない決定（[ADR](../adr/verify-movegen-without-perft-counts.md)）は変更せず、期待値を規範文書から導く方針（[ADR](../adr/derive-test-expectations-from-normative-documents.md)）を、事例から述語へ広げる。
対局の履歴を`Position`の外に置く決定（[ADR](../adr/keep-game-history-out-of-position-and-movegen.md)）も変更しない。
着手を検証して適用する`try_make_move`の[ADR](../adr/check-try-make-move-against-all-legal-moves.md)が退けたのは、本番の中に第2の規則判定を置くことである。テスト専用の仕様は本番に入らず、本番との食い違いを誤りの手がかりとして使うので、この決定と矛盾しない。
候補4を常設する場合は、開発版のコンパイラに固定された道具をCIへ足すことになり、[サニタイザとMiriを採らないADR](../adr/do-not-adopt-sanitizers-or-miri.md)と同じ観点（検出できる不具合の種類に対する保守の費用）での判断が要る。

## 議論で意見が分かれた点

- 最初に行う実験について、codexは当初、走りの遮蔽の全数検査（候補2の一部）を挙げた。Claudeは、既存のテストが最も厚い区分であり、結果が方式の選択を変えないと反論した。codexは、最小の費用で保証を1つ得る実験と、方式を選ぶために最も情報を得られる実験を取り違えていたとして、候補1へ改めた。
- 仕様をLeanで先に書くかについて、ClaudeはLeanを先にする根拠（後から移すと同じ条文を2度形式化する）を示した。codexは、Leanで証明できるのはモデルの定理でありRustについては標本での適合のままだとして、Rustを先にする案を維持し、候補5の節の2条件を示した。Claudeはこれに同意した。
- 「相手の獅子でない駒の升では、利きが届くことと合法な捕獲があることが一致する」という補題について、Claudeは、本番の審判の層がすでにこの補題に依存している（[ADR](../adr/judge-non-lion-captures-by-attacks-and-stop-mate-at-the-first-escape-in-the-referee.md)）ので証明の必要が生じているとも読めると考えた。codexは現時点で必須としない。候補1の独立仕様の上で範囲を限って照合できるので、勧める順序は変わらない。
- 候補6の費用について、Claudeは先例の比率から証明を数万行から十数万行と見積もったが、codexは先例の比率をminaseの工数へ換算できないとした。勧めないという結論は同じである。
- Kaniについて、Claudeは、判定が出る前に打ち切った2026年11月25日の実行を根拠に、表を読む区分にはKaniを使わないことを勧めた。codexは、その実行は当時のハーネスの構成を見送る根拠であって、表を読む関数の一般の限界ではないとした。翌日の測定で、走りの遮蔽はCBMCを直接呼べば検証できたので、codexの指摘が正しかった。成りの可否の検査を常設のCIへ入れるかについては、codexが単発の確認にとどめることを勧め、Claudeも同意した。

## 残る不確実性

| 不確実な点 | 決める方法 |
|---|---|
| 独立な局面合法手の仕様が何行になり、条文だけから書けるか | 候補1を行い、本番の関数を借りずに書けた条項と書けなかった条項を記録する。 |
| 宣言した配置の全数と乱数対局の標本が、通常の試験の時間に収まるか | 候補1で実時間を測る。 |
| 独立仕様が、既存の参照実装と本番が共有する部分の誤りを検出できるか | 本番へ意図的に誤りを入れ、検出の有無を記録する。 |
| 独立仕様と本番が同じ誤読を共有していないか | 原理的に排除できない。条項との対応づけ、典拠の事例、lishogiの棋譜、およびHaChuとの照合で減らす。 |
| 反復の裁定を無条件に保証できるか | できない。必要なら、キーが一致したときに局面そのものを照合するなど、本番の設計の変更が要る。 |
| 規則書の4件の読みと、詰みの定義を改めるかどうか | 規則書を管理する人が決める。 |

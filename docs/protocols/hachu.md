# HaChu調査　CECPによる中将棋対局の実装例

## 第1章　調査の範囲

### 第1節　目的と対象

本文書は、プロトコル層マイルストーン（docs/plans/protocol-layer.md）のフェーズ1調査として、中将棋エンジンHaChuのソースコードを調査し、CECP（Chess Engine Communication Protocol）による中将棋対局の実装例を記録する。調査対象は、RULES.mdが典拠［E5］として挙げるGitHubリポジトリddugovic/hachuであり、コミット649ef114dd5fa39d3e1be4112e63ebe2ab3d5d8b（2023年4月23日）を精査した。エンジンのバージョン文字列は0.23である（hachu.h 11行）。以下で行番号を示す引用は、すべてこのコミットのものである。

HaChuはH. G. MullerがC言語で書いたWinBoard用エンジンであり、中将棋のほか小将棋、大将棋、天竺将棋などの変則将棋・変則チェスに対応する。原作者版はhgm.nubati.netのgitwebで公開されており（README.pod 59行）、ddugovic版はそれを複数ファイルへ分割・整理したフォークである。フォークには「Fix setboard command」「Parse setboard side-to-move indicator」などのコミットが含まれるため、以下の記述が原作者版にそのまま当てはまるかどうかは未確認である。

### 第2節　比較する仕様文書

実装との乖離を判定する基準として、次の2つの仕様文書を用いた。CECPの原典であるengine-intf.htmlは、hgm.nubati.net上のパスが404を返したため、GNUプロジェクト掲載版（Mullerによる拡張追記を含む版）を参照した。もう1つは、Mullerが同プロトコルを再整理したnewspecs.htmlである。両文書の詳細な解説は、並行調査のdocs/protocols/cecp.mdが扱う。

## 第2章　起動時の握手とfeature送信

### 第3節　protover応答

HaChuは`protover`受信時に、次のfeature群を送信する（hachu.c 1253〜1267行）。プロトコルバージョン番号の検査は行わず、`protover`の引数を読まない。

```text
feature variants="chu,nocastle,shogi,dai,tenjiku,shatranj,makruk,lion,wa-shogi,werewolf,cashew-shogi,macadamia-shogi"
feature ping=1 setboard=1 colors=0 usermove=1 memory=1 debug=1 sigint=0 sigterm=0
feature myname="HaChu 0.23" highlight=1
feature option="Full analysis PV -check 1"
feature option="Allow repeats -check 0"
feature option="Promote on entry -check 1"
feature option="Okazaki rule -check 0"
feature option="Resign -check 0"
feature option="Contempt -spin 0 -200 200"
feature option="Tsume -combo no /// Sente mates /// Gote mates"
feature done=1
```

variants文字列はvariants[]表（variant.c 383〜402行）から生成され、中将棋は変種名`chu`として先頭に置かれる。`chu`はXBoard 4.8以降が本体側で認識する組み込み変種名であり（［S2］の変種名表）、盤サイズを`12x12+0_`のような接尾辞で宣言する必要はない。`highlight=1`は第7章の升ハイライト機構を有効化し、`colors=0`は旧式の`white`/`black`コマンドを抑止し、`sigint=0 sigterm=0`はGUIからのシグナル送出を抑止する。`feature done=0`による初期化待機は使用しない。

### 第4節　エンジン定義オプション

`option`コマンドの受信処理（hachu.c 1269〜1283行）は、受信した瞬間にグローバル変数を書き換える。次対局から反映するといった遅延（latch）機構はなく、対局中の変更も即座に効く。中将棋の規則に関わるオプションは次の3つであり、RULES.mdの規則コードとの対応は第8章で述べる。

| オプション名 | 型と既定値 | 内容 |
| --- | --- | --- |
| Allow repeats | check、0 | 0で既出局面の再現手を不合法として拒否し、1で合法だが敗着級の評価として回避する。 |
| Promote on entry | check、1 | 1で成りを敵陣に入る手に限定し、0で1手待機後の再成りを認める寛容方式に切り替える。 |
| Okazaki rule | check、0 | 1で先獅子の禁止に足条件（岡崎ルール）を付ける。 |

このほかTsume（詰将棋モード）、Contempt、Full analysis PVがある。Resignはfeatureとして宣言され`option`で受理されるが、変数`resign`を参照するコードが存在せず、機能しない（hachu.c 85行の宣言以外に読み出しがない）。

## 第3章　変種の宣言と初期局面

### 第5節　variantコマンドとsetup送信

`variant NAME`を受信すると、HaChuは名前をvariants[]表と照合してエンジンを初期化し直す（hachu.c 1335〜1374行）。変種`chu`ではGUIへ何も送り返さない。XBoard 4.8が中将棋の初期配置、駒種、成り規則の入力面をGUI側で知っている前提であり、初期局面はエンジン内部のchuArray（variant.c 342〜344行）から設定する。chuArrayの配置は、王将を先手、玉将を後手とし、獅子と奔王を先後で鏡映に置く点も含めて、RULES.md第5条の初期配置と一致することを確認した。

一方、GUIが規則を知らない変種（`shogi`、`wa-shogi`、`werewolf`、`macadamia-shogi`、`cashew-shogi`）では、`setup (PIECETOCHAR) NxM+H_親変種 FEN`と`piece ID ベツァ記法`をGUIへ送信して盤サイズ・駒種・駒の動きを宣言する（hachu.c 1342〜1371行）。この機構は［S2］［S3］が定めるエンジン定義変種の仕組みそのものであり、minaseが将来ローカルルール差をGUIへ伝える際の参考になる。なお変種名`shogi`の実体は、醉象を含み持ち駒のない小将棋であり（hachu.c 1345〜1346行の9x9+0_shogi宣言）、仕様書の変種名表で`shogi`が指す本将棋とは異なるゲームを同名で提供している。

`new`コマンドは仕様上「チェスを指せないエンジンは位置設定を後続のvariantまで遅延する」と定めるが、HaChuは`new`で直ちにV_CHESS（変種名`nocastle`、キャスリングなしのチェス）を初期化する（hachu.c 1331〜1334行）。中将棋で対局する限り、直後の`variant chu`が初期化をやり直すため実害はない。

## 第4章　指し手表記

### 第6節　座標系と基本形式

升の表記は、筋を小文字`a`〜`l`、段を数字`1`〜`12`で表す。生成はtypes.hのFILECHとRANKマクロ（21〜22行）、解析はReadSquare（move.c 67〜75行）が担い、ReadSquareは2桁の段（10〜12）を正しく読み進める。段1が先手（内部色WHITE）側の最下段、段12が後手側の最奥段であり、FENの並びと同じく上（後手側）の段から記述される。10段の盤に限り段を0起算とする仕様上の特例（［S2］）は、12段の中将棋には適用されない。

通常の1段階の指し手は`e2e4`形式の座標対で表す。成りは末尾に`+`を付ける。出力側のMoveToText（move.c 39〜65行）は、変種が将棋系（内部フラグrepDrawsが偽で、マックルック・人狼チェスでない場合）のとき成り文字として`+`を選ぶ（move.c 62行）。入力側のParseMove（move.c 77〜161行）は、座標列の直後の文字が改行でも`=`でもなければ成りとみなす（move.c 126行）。したがって`e2e4+`は成り、`e2e4`と`e2e4=`は不成である。この判定は緩く、`+`以外の任意の文字でも成り扱いになる。本調査が参照した仕様文書（［S2］［S3］）の成り表記の明文は小文字の駒文字接尾辞（`a7a8q`）だけである。ただし、Muller版CECP仕様（cecp.mdの［C2］）の付録Eには、固定の成り先を持つ駒の成り手に成り文字`+`を使う明文がある。したがって`+`自体は仕様に根拠があり、実装慣行にとどまるのは不成の`=`と、改行・`=`以外を全て成り扱いにするHaChuの寛容な判定である。

### 第7節　獅子・角鷹・飛鷲の2段階移動

複数レグの指し手は、方向によって仕様が非対称である。GUIからエンジンへの`usermove`は、レグをコンマで区切った単一文字列で届く（例は`c4d5,d5e4`。［S2］の指し手形式一覧）。エンジンからGUIへの`move`は、レグごとに別の`move`コマンドとし、最終レグ以外の末尾にコンマを付け、成り接尾辞は最終レグにだけ付けられる（［S2］［S3］）。

HaChuの実装はこの両方に従う。受信側のParseMoveは、コンマ区切りの2レグまたは3レグを読み、第2レグの始点が第1レグの終点と一致しなければ不正とする（move.c 84〜112行、一致検査は87行）。第1レグは王将1歩の8方向（獅子犬用の2歩形も許す）に限定され、3レグ移動は直線のみ許す（move.c 101行）。解析結果は内部のray対符号（後述）へ変換され、合法手リストとの照合で最終判定される。送信側は、main関数がMoveToTextをmultiLine=1で呼ぶことで実現する（hachu.c 1225行）。MoveToTextは中間レグを`move e6d6,`のようにコンマ付きの独立した`move`行として先に印字し（move.c 53〜58行）、最終レグを呼び出し元が`move d6e6`として印字する。同じ関数をmultiLine=0で呼ぶと`e6d6,d6e6`という単一文字列になり、これは思考出力のPV、`Hint:`応答、ポンダー照合用文字列に使われる。

具体例を挙げる。e6の獅子がd6の駒を取ってc6へ抜ける2段階捕獲は、受信では`usermove e6d6,d6c6`、送信では`move e6d6,`と`move d6c6`の2行になる。d6の駒を取って元の升へ戻る居喰いは`e6d6,d6e6`である。居喰いを含む捕獲側の2段階手は、捕獲手生成GenCaptsがray対符号で直接生成する（hachu.c 303〜313行、居喰いは307行のsqr+v == x分岐）。

### 第8節　じっとの表記

じっと（隣接升へ出て元の升へ戻る非捕獲2段階手）は、往復の2レグ表記（`e6f6,f6e6`）として綴ること自体は可能だが、HaChuはその綴りを生成も受理もしない。HaChuは、じっとを始点と終点が同じ升のヌルムーブとして符号化し、MoveToTextはこれをCECPのヌルムーブ表記`@@@@`として出力する（move.c 45行）。受信側も、先頭が`@`の入力を「始点と終点が等しい生成済みの手」に一致させる（move.c 132行）。じっとが可能な局面かどうかは手生成側が判定しており、獅子等が合法な1歩非捕獲移動を持つ場合にだけ、この自己升手が手リストへ積まれる（GenNonCapts内のnullMove設定はhachu.c 214行、手リストへの追加は657〜660行）。空升を経由する`e6f6,f6e6`のような明示的な2レグ表記の非捕獲手は生成されないため、この綴りでじっとを入力することはできない。`@@@@`は現行engine-intf.html（［S2］）の指し手形式一覧に記載があるが、それをじっとに転用する対応付けはHaChuの実装判断であり、仕様文書には明文がない。lishogi系がじっとを明示的な2レグ（往復）で綴るのと対照的であり、minaseのCECP側表記設計ではこの差を吸収する必要がある。

### 第9節　内部符号と復号表

参考として内部表現を記す。指し手は32ビット整数で、始点を9ビット左シフトし終点とORした形式である（types.h 23〜37行）。2段階移動は、終点フィールドに定数SPECIAL（400）以上の特殊値を置き、第1レグ方向iと第2レグ方向jの対を`SPECIAL + 8*i + j`で符号化する。復号は3本の変位表epList（第1レグの犠牲升）、ep2List（第2犠牲升）、toList（最終到達升）で行い、これらはInitが起動時に構築する（piece.c 296〜314行）。獅子犬用の3レグ形はSPECIAL+64〜95、キャスリングはSPECIAL+100〜103に割り当てられる。この設計は、指し手の適用時に第1レグの犠牲駒を「経由升の取り」として処理するものであり、minaseのMove型（経由升を明示する形式）とは符号化の方針が異なる。

## 第5章　局面表記

### 第10節　setboardの受理形式

`setboard FEN`を受信すると、HaChuは現在の変種で初期化し直してからSetUp2へFEN文字列を渡す（hachu.c 1375行）。SetUp2（hachu.c 931〜947行）は、最初の空白でFENを切り、空白の直後の1文字が`b`なら後手番、それ以外なら先手番とする（939行）。盤面部と手番以外のフィールド（キャスリング欄、手数カウンタ等）は一切解析されない。仕様のsetboardはFEN全体を送ると定めるので、後続フィールドの無視は実装上の割り切りである。

盤面部の構文はSetUp（board.c 36〜148行）が解析する。チェスFENと同様に、上（後手側の段12）から段ごとに`/`で区切り、大文字を先手、小文字を後手の駒とする。数字は空升の連続を表し、2桁（10〜12）に対応する（board.c 51〜54行）。`.`も1升の空きとして受理する。成駒は駒文字の直前に`+`を置く（board.c 47行）。駒文字の直後の`'`と`!`は文字空間を拡張する装飾接尾辞だが、中将棋の駒表では使われない（board.c 61〜62行）。

### 第11節　中将棋の駒文字

FENの1文字IDから内部駒名への変換表はchuIDs（variant.c 367行）が定める。中将棋で使われる21文字と駒の対応は次のとおりである（大文字＝先手。小文字は後手の同じ駒）。

| 文字 | 駒 | 文字 | 駒 | 文字 | 駒 |
| --- | --- | --- | --- | --- | --- |
| P | 歩兵 | I | 仲人 | L | 香車 |
| A | 反車 | B | 角行 | C | 銅将 |
| S | 銀将 | G | 金将 | F | 猛豹 |
| T | 盲虎 | E | 醉象 | X | 鳳凰 |
| O | 麒麟 | M | 横行 | V | 竪行 |
| R | 飛車 | H | 龍馬 | D | 龍王 |
| Q | 奔王 | N | 獅子 | K | 王将・玉将 |

J、U、W、Y、Zの5文字は未割当である。成駒は`+P`（と金相当の金将）のように基駒への`+`接頭辞で表し、独立の文字を持たない。この表はHaChu側の受理仕様であり、XBoard 4.8本体が中将棋のFENで同じ文字割当を使うことは、本調査では未確認である（cecp.md調査の範囲とする）。

### 第12節　setboardで表現できない状態

SetUp2は、成り遅延の抑制升を保持する変数sup0・sup1・sup2を無条件にABSENTへリセットする（hachu.c 943行）。この変数群は、直前に不成で敵陣へ入った駒の升と、獅子が非獅子に取られた直後であることを示すフラグ（先獅子状態）を運ぶ（第8章参照）。したがって、不成直後の成り権制限や先獅子による捕獲禁止が生きている途中局面は、setboardでは復元できない。CECPのFENにこれらを載せる拡張もHaChuには存在しない。この事実は、minaseが拡張SFENに先獅子状態と成り権状態のフィールドを設ける設計判断（protocol-layer.md）を裏付ける実例である。

## 第6章　対応コマンドの全体像

メインループ（hachu.c 1161〜1381行）とGetLine（1113〜1148行）が処理するコマンドを、機能別に示す。各項は文で補足する。

| 区分 | コマンド |
| --- | --- |
| 握手 | xboard（無視）、protover、option、accepted・rejected（無視） |
| 対局進行 | new、variant、setboard、usermove、go、force、result、quit |
| 手戻し | undo（1手）、remove（2手） |
| 時間・探索制御 | level、st、sd、time、otim（無視）、memory、ping |
| 解析・思考出力 | analyze、exit、.（無視）、hint、easy、hard、post、nopost |
| ハイライト機構 | lift、put、hover（無視） |
| その他 | computer、name（無視）、ics（無視）、book（無視）、random |
| 独自デバッグ | p、f、w、b、l（盤面・利き・駒リストのダンプ） |

`usermove`の受理時は、ParseMoveが返した手をMakeMove2で適用し、非合法なら`Illegal move {理由}`を返す（hachu.c 1314〜1328行）。理由文字列は「Repeats earlier position」「Counterstrike against Lion」「Distant capture of protected Lion」の3種で、不合法理由の記録repeatMoveから引かれる（move.c 151〜153行）。`ping N`には`pong N`を返す（1288行）。`undo`と`remove`は、初期局面から棋譜を再生し直すTakeBack（1093〜1102行）で実装される。`time`は自クロックの残り時間をセンチ秒で受け、`otim`は読み捨てる。`random`は仕様ではトグルだが、HaChuは常にONへ倒す（1295行）。

エンジンからGUIへの出力は、`move`、`pong N`、`Illegal move {理由}`、結果宣言`1-0 {理由}`・`0-1 {理由}`・`1/2-1/2 {理由}`（PrintResult、1104〜1111行）、`Hint: 指し手`、思考出力、`highlight`、`setup`、`piece`、`tellusererror`である。思考出力は`深さ 評価値 時間 ノード数 PV`の形式で、時間は仕様どおりセンチ秒に換算して印字する（810〜814行）。`#`で始まる多数のデバッグ行も無条件に出力され、これは`feature debug=1`の宣言で正当化されている。

## 第7章　升ハイライトによる2段階移動の入力

`feature highlight=1`で有効になる機構は、GUIに規則知識がない変種で、選択中の駒の行き先をエンジンが着色指示するものである（［S2］［S3］）。GUIはユーザーが駒を掴むと`lift 升`を送り、エンジンはHighlight関数（hachu.c 991〜1054行）で合法手リストを走査し、盤面と同形のCOLORFEN文字列を`highlight`コマンドで返す（1053行）。文字は色を表し、Yが空升への移動先、Rが捕獲、Mが成り選択を要する到達、Cが複数レグの中間升である。ユーザーがC升へ駒を置くとGUIは手の入力を完了せず、同じ駒への`lift`を再送し、エンジンは第2レグの行き先だけを改めて着色する（1015〜1034行が`put`で記憶した升からの第2レグ列挙）。これにより、獅子の2段階移動が2回のクリック列として入力される。README.podも、XBoardの行き先表示オプションが無効だと2段階の獅子の手を入力できないと明記する（28〜30行）。ハイライト機構は入力補助であり、合法性の最終判定は`usermove`受理時にエンジン側で行われる。

## 第8章　中将棋規則の実装とRULES.mdの規則コードとの対応

### 第13節　合法性判定の構造

HaChuは、独立した合法手判定器を持たず、深さ1相当の探索（ListMoves、hachu.c 966〜989行）で手リストを生成し、獅子捕獲の禁止則は探索中に該当手をINVALIDへ書き換える形で実装する（731〜750行）。書き換え時に理由コード付きでrepeatMoveへ記録し、ParseMoveの照合失敗時に`Illegal move`の理由文字列として使う。

### 第14節　獅子捕獲の禁止則

探索中の判定（hachu.c 731〜750行）は次の2種を不合法化する。第1に、獅子による獅子の捕獲では、両者が隣接せず、到達升が相手の利きにあり、経由升の犠牲駒の価値が閾値以下の場合を不合法とする（736〜738行）。これはRULES.md第14条（隣接例外付きの獅子対獅子規則）と第16条の付け喰い（価値ある駒を取りながらの捕獲は許す）に相当する。第2に、非獅子で相手獅子を取る手は、直前に相手が同種の獅子捕獲を行った直後（フラグpromoSuppress & PROMOTE）には不合法とする（740〜743行）。判定式は`if(!okazaki || ATTACK(tb.to, stm)) score = -INF;`であり、Okazaki ruleオプションが0なら足の有無を問わず禁止（RULES.mdのL1相当）、1なら利きの条件付きの禁止となる。後者はL0（岡崎ルール）に近い足条件付き方式だが、RULES.mdのL0が定める足（獅子捕獲後の仮想盤面での取り返し可能性であり、裏足を含む。第13条）との厳密な対応は未確認である。この条件式中のATTACKがどちら側の利きをどの盤面で検査しているかの意味論は、本調査ではコードの引用にとどめ、確定していない。RULES.md第29条がHaChuを「“Okazaki rule”を切替オプションとして実装する」と記す内容と整合する。

### 第15節　反復の扱い

反復判定は、手番を含むハッシュ（hashKeyH）を可逆手カウンタの範囲で照合する（hachu.c 707〜726行）。チェス系変種では3回未満でも即引き分け評価だが、中将棋ではAllow repeats=0（既定）のとき、既出局面を再現する手をINVALIDへ書き換えて不合法とする。これは盤面と手番の2回目の再現を禁じる点でRULES.mdのR2（既出局面再現禁止方式）の系統である。ただしR2の同一局面判定は先獅子状態など次の合法手に影響する状態も含む（第24条）ため、HaChuのハッシュ照合との厳密な一致は未確認である。ルート局面で禁じられた手はrepeatMoveに記録され、ユーザーがその手を入力すると`Illegal move {Repeats earlier position}`が返る。Allow repeats=1では、再現手は合法のまま敗着に近い評価値（-INF+8）を受け、相手の連続王手と読める反復は勝ち評価に反転する（717〜722行）。README.podの「repeatsを厳格に禁止するか、他の敗着と同様に回避するだけにするか」という説明（50〜51行）と一致する。

### 第16節　成り規則

成り機会の判定はPromotionFlags（hachu.c 90〜99行）が行う。Promote on entry=1（既定）では、到達升または経由升が敵陣で、かつ始点が敵陣外の手だけに成りを認める。敵陣内での捕獲や敵陣から出る手での再成り（RULES.md第18条2項）は生成されないため、既定設定は日本中将棋連盟規則より狭い。Promote on entry=0では始点か到達升が敵陣なら成りを認め、不成で入域した駒の升をsup0〜sup2で2手分持ち回り、その駒の直後の1手だけ成りを抑制する（GenNonCaptsの抑制は204行、持ち回りはMakeMove2の892〜895行）。これはRULES.md第30条P2（1手待機方式）の系統であり、RULES.mdのP1欄が「HaChuが実装する寛容型の成り規則は1手待機のP2系統」と記す内容をコードで確認できた。また、不成を選んだ歩兵はpromoFlagを最奥段のみに絞り直すため、以後は最奥段でだけ成れる（move.c 144行）。これは第19条1項の歩兵救済と同じ帰結になる。

### 第17節　終局の扱い

HaChuは詰みを宣言せず、合法手探索が手を返さなくなった時点で、相手王駒を実際に取る手があればその手を`move`として出力してから`1-0 {king capture}`のような結果を宣言し、なければ`{resign}`を理由に自分の負けを宣言する（hachu.c 1198〜1214行）。最後の王駒の実捕獲まで指し続けるこの挙動は、RULES.md第32条E1（王駒実捕獲終局）の系統である。醉象の成る太子は王駒として扱われ、王将と太子の両方が残る側は片方を取られても続行する（Search冒頭の王駒判定、479〜512行）。

## 第9章　仕様文書と実装の乖離

調査項目の中心である乖離を列挙する。各項は、仕様（［S2］［S3］）の規定、HaChuの実装、乖離の性質の順で述べる。

1. 不合法手の応答形式が仕様と異なる。仕様は`Illegal move: MOVE`または`Illegal move (REASON): MOVE`とし、問題の指し手を必ず末尾に反響させる。HaChuは`Illegal move {理由}`と出力し、指し手を反響せず、理由を丸括弧でなく波括弧で囲む（hachu.c 1320行）。xboardは「illegal move」の綴り揺れやコロン省略に寛容と明記するが、この波括弧形式と指し手反響の欠落をGUIが正しく処理することは未確認である。
2. setboardのFENを部分的にしか解析しない。仕様はFEN全体の受理を前提とするが、HaChuは盤面部と手番文字だけを読み、以降を無視する（第10節）。加えて成り遅延・先獅子の内部状態を復元しない（第12節）。局面設定の往復同一性は保証されない。
3. 不成の接尾辞`=`は仕様文書に明文がない。本調査が参照した［S2］［S3］には成り接尾辞`+`の明文もないが、`+`はMuller版CECP仕様の付録E（cecp.mdの［C2］）に明文がある。実装慣行にとどまるのは`=`と、改行・`=`以外をすべて成りとみなすHaChuの寛容な入力判定である（第6節）。
4. じっとの`@@@@`転用は実装判断である。`@@@@`自体は仕様のヌルムーブ表記だが、これを中将棋のじっとという合法手に対応付けることは仕様に書かれていない（第8節）。
5. `new`の扱いが仕様の推奨と異なる。チェスを指せないエンジンはvariant受信まで初期化を遅延すべきところ、HaChuは`new`で直ちにキャスリングなしチェスを設定する（第5節）。また変種名`nocastle`を、仕様の変種名表の意味（キャスリング無しシャッフルチェス）と異なる通常配置で使う。
6. 変種名`shogi`で小将棋を提供する。仕様の変種名表では`shogi`は本将棋を指すが、HaChuは同名で醉象付き・持ち駒なしの小将棋を実装し、`setup`で盤面と規則を上書きする（第5節）。
7. `random`はトグルでなく常時ONである（第6節）。また`Resign`オプションは宣言だけで機能しない（第4節）。

なお、複数レグ指し手の送受信形式（受信は単一行コンマ区切り、送信はレグごとの`move`コマンドと非最終レグのコンマ接尾）は、両仕様文書の規定とHaChuの実装が一致しており、乖離はない（第7節）。

## 第10章　minase設計への示唆

本調査から、プロトコル層フェーズ2の設計に対して次の含意が得られる。第1に、CECPの指し手表記は受信と送信で非対称であり、minaseのCECP用Move文字列変換は「コンマ区切り単一文字列の解析」と「レグ分割された複数`move`行の生成」の両方を実装する必要がある。第2に、じっとはCECP側では`@@@@`、lishogi系では明示的な往復レグで表されるため、内部Move型からの写像は表記層ごとに分岐しなければならない。第3に、CECPのsetboardには先獅子状態と成り権状態を運ぶ標準的な方法がなく、HaChuも復元を放棄しているため、拡張SFENをCECP側でも受け渡す独自手段（エンジン定義オプションまたは独自コマンド）を検討する余地がある。第4に、HaChuの規則オプションは即時反映であり、minaseが採るlatch方式（次対局から反映）はHaChuより厳格な設計になるが、CECPの`option`はいつでも届き得るため、拒否でなく受理して保留する応答設計が適合する。第5に、WinBoardでの2段階移動の対話入力にはhighlight機構（`feature highlight=1`とlift/put応答）が事実上必須であり、実GUI接続を行うマイルストーンではこの実装を計画へ含める必要がある。

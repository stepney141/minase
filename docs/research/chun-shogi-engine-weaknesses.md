# Webアプリ「チュン将棋」の思考部がminaseより弱い原因

本書のminaseに関する記述は、2026年11月15日の時点（コミット`53d26bbd`）のものである。

「チュン将棋」（<https://chu.punomo.dev/>）は、ブラウザで動く中将棋の対局アプリであり、CPUの思考部もブラウザのJavaScriptで書かれている。
2026年11月15日に始めた対局では、minaseは持ち時間を相手より大幅に短くしたうえで、アプリの最強のレベル（Lv10）に全勝している。
本書は、アプリが配布しているソースを読み、思考部をNode.jsで動かして、この差がどこから生じるかを調べた記録である。

## 結論

結論は次の5点である。

1. 速度は原因ではない。アプリの思考部はNode.jsで1秒あたり1.46M〜3.90Mノード（NPS）を探索し、同じ機械で対局中のminaseの中央値534k NPSより約3〜7倍速い。対局の14局でminaseが使ったCPU時間はアプリの0.64倍なので、minaseが探索したノード数はアプリの約14%と推定される。
2. 評価関数は、駒の価値、段と中央度に比例する位置の加点、囲いと大駒の位置の加点、および手番の加点の和だけでできている。玉の安全度、駒の利き、駒どうしの関係、および脅威を見る項はなく、SPSAで調整したのはこの線形の評価の係数である。
3. 探索の枝刈りが弱い。late move reduction（LMR）の削減幅は最大2である。手の数による枝刈り（late move pruning、LMP）はない。駒の取り合いの損得を見積もるstatic exchange evaluation（SEE）による枝刈りと、singular extensionもない。深さ10を終えるまでに2.8M〜31Mノードを使い、実効分岐係数は2.3〜4.1である。同じ局面でminaseは深さ20を84k〜729kノードで終える。
4. 静止探索は、2手目以降の駒を取る手のうち、取る駒の価値が取られる駒の価値に200点を足した値より大きい手を読まない。調整後の獅子は2,842点、奔王は1,611点なので、獅子と奔王による取り返しは静止探索の2手目以降でほとんど読まれない。この誤りは、駒を最小限に絞った局面で再現した。
5. アプリは、深い探索の最善手を、浅い読みで選んだ「受けにくい手」へ確率的に差し替える。対局の14局ではアプリの1,512手のうち35手（2.3%）が差し替えられ、minaseの深さ14の評価では元の手より中央値で89点、平均で277点悪かった。

置換表の大きさは主な原因ではない。
置換表を16倍にしても、深さ10を終えるまでのノード数は幾何平均で0.83倍にしか減らなかった。

上の5点がそれぞれ強さの差のどれだけを占めるかは測っていない。

## 思考部の構成

`engine.js`は、規則と探索の実装一式を1つのファクトリ関数（`ChuEngine`）に収め、画面側の規則判定とWorkerの思考で同じコードを使う。
盤は16×16のmailboxであり、局面ごとに全駒の着手を生成する。
探索は反復深化のαβ探索で、principal variation search、置換表、空手枝刈り（null move pruning）、LMR、futility pruning、killer move、history heuristic、および駒を取る手だけの静止探索を持つ。
レベルごとの深さと思考時間の定義は`engine.js:1265-1278`にあり、Lv9とLv10はどちらも1手26秒と設定されている。
ただし画面側の処理（`app.js:648-649`）に1手を10秒までに抑える制限があり、Lv10だけはこの制限を外して26秒まで読む。

## 評価関数

標準流派の評価値は、駒と升ごとの値の表（`engine.js:151-161`）の和に、手番の加点56点（`engine.js:142`、`engine.js:879`）を足したものである。
表の値は、駒の価値に、段に比例する前進の加点と、中央度に比例する加点を足して作る。
標準流派では、この表にさらに2つの作戦の加点を書き込む（`engine.js:183-191`）。
金将、銀将、および銅将を自陣の奥3段の中央寄りに置く加点と、角行と龍馬を自陣の3段より前に出す加点である。

評価に入っていない項目は多い。
玉の安全度、駒の利きの数（mobility）、駒どうしの関係、および取られそうな駒の脅威を見る項はない。
敵玉への近さと自玉の周りの守りを数える動的評価（`engine.js:278-306`）はあるが、攻め型の流派、変則規則専用の流派、および劣勢が続いたときの逆転モード（`cpu_worker.js:10-19`）でしか有効にならない。
重みを学習した動的評価`dynTuned`（`engine.js:845-868`）は、設定`cfg.tuned`を渡したときだけ使われ（`engine.js:126-140`）、どの流派も渡していない。

標準流派の係数は`engine.js:8`の`TUNED`にまとめられ、ソースのコメントによると自己対局のSPSAで300反復調整した結果である。
係数は、駒の種類ごとの価値の倍率28個、6つの駒の群ごとの前進と中央の倍率12個、手番の加点1個、獅子の中央度1個、2つの作戦の強さ2個、および成った駒の価値の割引1個の計45個である。
ソースのコメントによると、最後の割引だけは別の自己対局で決めた値である。
調整後の駒の価値は、歩兵73点、銅将355点、銀将310点、金将523点、龍馬969点、龍王1,168点、奔王1,611点、獅子2,842点である。

一方、minaseの評価関数は、学習した重みを持つNNUEである（`crates/minase/src/eval/nnue/mod.rs`）。

評価の弱さは、対局での両者の評価値の食い違いに表れている。
14局のうち7局では、minaseの評価値が初めて自分に+1000以上になった手の前後で、アプリは自分に+79〜+1416と評価していた。
minaseの手とその直後のアプリの手の組1,449組のうち325組（22%）で、minaseが自分に+300以上、アプリも自分に0以上と評価していた。
2つの評価値は尺度が異なるので数値を直接比べることはできないが、どちらが優勢かの判断が食い違っており、勝ったのはすべてminaseである。
後述の手の差し替えを調べた35局面でも、差し替える前の手を指した局面を、アプリが自分に0以上と見て、minaseがアプリに−300以下（minase自身に+300以上）と見たものが24局面あった。
差し替えはアプリの評価値が−150より大きいときにしか起きないので、この35局面はアプリが劣勢と見ていない局面に偏っている。

## 探索の枝刈り

アプリの探索は、前向きの枝刈りと深さの削減が少ない。
標準の設定で働くものと、その条件は次のとおりである。

| 手法 | アプリの条件 | 場所 |
|---|---|---|
| LMR | 残り深さ3以上、5番目以降の静かな手で1、13番目以降で2を削る | `engine.js:915`、`engine.js:984` |
| futility pruning | 残り深さ2以下、静的評価に200×残り深さを足してもαに届かない静かな手 | `engine.js:921`、`engine.js:973` |
| null move pruning | 残り深さ3以上、削減幅は2（残り深さが6より大きければ3） | `engine.js:922`、`engine.js:948-954` |
| 静止探索のdelta pruning | stand-patに取る駒の価値と250点を足してもαに届かない取り | `engine.js:870`、`engine.js:898` |

reverse futility pruning、内部反復深化、および大きな駒を取る手の延長も実装されているが、既定では使われない（`engine.js:916`、`engine.js:920`）。
LMP、SEEによる枝刈り、history heuristicによる枝刈り、およびsingular extensionはない。
history heuristicの表は着手の移動元と移動先で参照し、βを超えた静かな手に残り深さの2乗を足すだけで、超えなかった手の値を減らす処理はない（`engine.js:994-998`）。

中将棋の局面には多くの合法手があり、上の9局面では70〜131手だった。
枝刈りの弱さがどれだけ深さを縮めるかを見るため、9局面で、深さごとに読み終えるまでの累積ノード数を両者で数えた。
アプリは`engine.js`の写しに反復ごとの報告を足し、時間の上限を60秒に延ばし、最善手が安定したときの早めの停止を外して、深さ10まで読ませた。
minaseは`go depth 20`で読ませ、置換表は256 MBにした。

実効分岐係数は、深さが1増えるごとに累積ノード数が何倍になるかの幾何平均である。
アプリは深さ6から最後に読み終えた深さまで、minaseは深さ10から20までで求めた。
ペア2第1局の90手目のアプリは、時間の上限（60秒）の手前で深さ10を始めなかったので、深さ9の値を載せた。

同じ深さの数字が表す読みの広さは、両者で異なる。
minaseは多くの手を大きく削って読むので、深さの数字が同じでも、最後まで読む手はアプリより少ない。
そのため、深さの数字の比較から棋力の差は導けない。
この表から言えるのは、アプリが深さ10に使うノード数の範囲内で、minaseが9局面すべてで深さ20まで読み終えたことである。

対局でも同じ傾向が見えた。
アプリの手のうち序盤14手を除く1,484手では、1手の思考時間の中央値は20.4秒、到達した深さの中央値は10だった。
minaseの1,519手では、思考時間の中央値は0.08秒、深さの中央値は16だった。
minaseの思考時間は、先読みが当たった手では当たった後に読んだ時間だけを数えているので、計算量の比較には上のCPU時間の比0.636を使う。

## 静止探索の枝刈り

アプリの静止探索は、駒を取る手だけを最大6手先まで読む（`engine.js:870-913`）。
2手目以降の駒を取る手では、取られる駒の価値に200点を足しても取る駒の価値に届かない手を読まない（`engine.js:899`）。
ソースのコメントは、この枝刈りの意図を「安い駒に高い駒で取る手は、取り返される想定で読まない」と説明している。
しかし、この条件は取られる駒に守りがあるかを見ていないので、守りのない駒を大駒で取る手も読まない。

この条件で読まれない取りは、取る駒が大きいほど多い。
獅子（2,842点）は、2手目以降では2,642点未満の駒を取らないので、取れるのは相手の獅子と玉将だけである。
太子の価値は2,500点なので、相手の最後の王駒が太子であれば、2手目以降の獅子はそれも取らない。
奔王（1,611点）は1,411点未満の駒を取らず、飛鷲（1,531点）、奔王、獅子、および王駒しか取らない。
静止探索の駒の取り合いは、手番側が1手目で駒を取り、相手が2手目で取り返す形から始まる。
2手目の取り返しが獅子か奔王なら、静止探索はその取り返しを読まず、1手目の駒を取る手を得と判断する。

この誤りを、駒を最小限に絞った次の局面で確かめた。
後手番で、後手は7fの金将で7gの先手の銀将を取れる。
先手の銀将は7hの駒が守り、後手の金将は8eの銀将が守る。
ほかには、先手の玉将が7l、金将が12l、後手の玉将が6a、金将が1aにある。
7hの駒を獅子にした局面と銅将にした局面の2つで、後手番の静止探索の値から後手のstand-patを引いた差（駒を取る手による評価値の増分）を比べた。

| 7hの駒 | 既定の設定 | 2手目以降の枝刈りを外した設定 |
|---|---:|---:|
| 獅子 | +214 | 0 |
| 銅将 | 0 | 0 |

どちらの局面でも、正しくは、金将で銀将を取ると7hの駒に取り返されて後手は損をするので、静止探索は取らずにstand-patを選び、差は0になる。
既定の設定では、守りが獅子のときだけ、静止探索は獅子の取り返しを読まずに銀将の得と見積もった。
+214は、銀将の310点から後述の手番の差112点を引き、位置の差を加えた値である。
2手目以降の枝刈りを外した設定は、アプリの設定項目`qSlack`に十分大きな値を渡して作った。
獅子は周囲2升の24升に、奔王は8方向の走りで遠くまで利くので、どちらも多くの駒を同時に守りやすい。
そのため、この誤りは通常探索の葉の局面に広く入り込む可能性がある。

minaseの静止探索は、直前の手の到達升で取り返す手をこの種の枝刈りから外し、そのほかの取りはSEEで判定する（`crates/minase/src/search/alphabeta/quiesce.rs`の`quiesce`）。
SEEは取られる駒の守りを数えるので、守りのない駒を大駒で取る手を捨てない。
なお、アプリの静止探索は、手番側の王駒が取られる状態でもstand-patを使う。
minaseも同じ近似を使っており、その理由は[王駒がすべて狙われた局面でも静止探索でstand-patを使う](../adr/use-stand-pat-when-royals-are-attacked.md)に記録されているので、これは両者の差ではない。

手番の加点56点は、静止探索が歩兵を取る判断も歪めている。
stand-patには手番側の加点が入り、駒を取った後の局面には相手の加点が入るので、位置の差を除けば、駒を取る手によるstand-patからの増分は、取った駒の価値から112点を引いたものになる。
歩兵の価値は73点なので、静止探索は守りのない歩兵も取らない。
このため、上の静止探索の誤りを歩兵を取る形で再現しようとしても、守り駒によらず差は出ない。

## 受けにくい手への差し替え

`cpu_worker.js`は、深い探索で選んだ手を、一定の条件で別の手に差し替える（`cpu_worker.js:102-129`、`cpu_worker.js:158-166`）。
アプリの画面はこの機能を「楽しさ成分（受けにくい手）」と呼び、差し替えたときに元の手をメモ欄へ書く（`app.js:687-688`）。
差し替えを試みる条件は、先読みをするレベルであること、変則規則でないこと、8手目以降であること、評価値が−150より大きいこと、および15%の乱数に当たることである。
変則規則を選ばない通常の対局では、`app.js`は規則の設定を渡さない（`app.js:1303`）ので、「変則規則でないこと」という条件は常に満たされる。

差し替える手は、次の手順で選ぶ。
まず、すべての合法手を、1,500ノードを上限とする3手の読みで評価する。
その値が最も良い手から40点以内で、かつ深い探索の評価値から40点以内の手を、上位4手まで候補にする。
各候補について、相手のすべての応手を同じ浅い読みで評価し、相手から見て最善から100点以内の応手（以下、良い応手）の数を数える。
応手が12手以上あり、良い応手の数が6手以下の候補のうち、良い応手が最も少ない手を指す。
40点以内という基準は、深い探索の評価値と、1,500ノードで打ち切る浅い読みの値を比べているので、差し替えた手が深い探索でも40点以内に収まるとは限らない。

14局では、アプリの1,512手のうち35手（2.3%）が差し替えられた。
名目の15%より少ないのは、良い応手の数などの条件を満たさない候補しかなければ元の手を指すからである。
35手それぞれについて、差し替えた手と元の手を指した後の局面を相手番から読ませ、指した側から見た評価値を比べた。

| 判定に使った探索 | 元の手からの評価値の低下の中央値 | 平均 | 100点以上悪い手 | 300点以上悪い手 | 差し替えた手の方が良い手 |
|---|---:|---:|---:|---:|---:|
| minaseの`go depth 14` | 89点 | 277点 | 17手 | 13手 | 7手 |
| アプリの標準流派で5秒 | 77点 | 161点 | 15手 | 7手 | 5手 |

アプリ自身の探索で見ても差し替えた手は元の手より悪く、差し替えは自分の深い探索の結論を捨てていることになる。
差し替えの処理は、浅い読みのために本体と同じ探索器を数百回呼ぶ。
呼ぶたびにkiller moveを消してhistory heuristicの表を4分の1にする（`engine.js:1167-1168`）ので、直後の先読みはこれらの表がほぼ空の状態から始まる。

## 影響の小さい要因

置換表は2^20件で、同じ場所に当たった記録を常に上書きし、静止探索では使わない（`engine.js:766-768`、`engine.js:1005-1006`）。
1手26秒の探索では数千万ノードを訪れるので、置換表はあふれて深い記録が浅い記録に上書きされる。
この影響を見るため、置換表を2^24件にした写しで、上の9局面の累積ノード数を数え直した。
深さ10（1局面は深さ9）を終えるまでのノード数は、局面ごとに元の0.38〜1.33倍であり、幾何平均は0.83倍だった。
置換表を大きくすれば多少は速く深くなるが、上で示した分岐係数の差に比べると小さい。

先読みは、40ミリ秒の探索を繰り返して進める（`cpu_worker.js:8`、`cpu_worker.js:45`）。
1回ごとに反復深化を深さ1からやり直し、killer moveを消してhistory heuristicの表を4分の1にするので、先読みの間はこれらの表がほぼ働かない。
ただし、アプリが先読みの結果をそのまま指した手は、思考時間が0.05秒未満の手として数えると、序盤14手を除く1,484手のうち34手にとどまり、この作りの影響は大きくないと見られる。

そのほかに、強さを少しずつ削る作りが次の4つある。

- 序盤14手では1秒しか読まず、評価値に最大40点のばらつきを加える（`app.js:654-658`）。
- SPSAで調整したのは標準流派だけだが、半分の対局を標準以外の流派で指す（`styles.js:6-13`）。たとえば囲い型は、標準の囲いの加点に、その8倍の加点を重ねる。
- 成れる手では成る手だけを生成し、不成の手を読まない（`engine.js:441`）。
- 同じ局面が3回目になる手も避ける（`app.js:28`）。

これらの影響は測っていない。

## 未検証の事項

結論の5点が強さの差のどれだけを占めるかは測っていない。
測るには、アプリの思考部どうしを、設定を1つずつ変えて対局させる必要がある。
静止探索の枝刈りは`qSlack`の設定で外せ、差し替えは`cpu_worker.js`の確率`TRAP_P`を0にすれば止められる。
評価関数と探索の枝刈りの寄与は、アプリのコードの改造なしには切り分けられない。

速度と深さの測定は、対局と並行して同じ機械で行ったので、NPSの絶対値は機械が空いているときと異なる可能性がある。
ただし、アプリとminaseのNPSはどちらも同じ負荷の下で測っており、約3〜7倍という比はこの条件の比較である。
NPSの比較にminaseの対局中の値を使ったので、両者のNPSは異なる局面の値である。

「評価関数」の節で述べた評価値の食い違いの数値は、尺度の異なる2つの評価値の符号と大きさの組で数えたものであり、どちらの評価が正しいかを局面ごとに確かめてはいない。
食い違いの向きがminaseの全勝という結果と一致することだけを根拠にしている。

## 再現の手順

測定に使ったスクリプトはリポジトリの外に置き、保存していない。
次の手順で同じ測定を組み直せる。

アプリのファイルは、<https://chu.punomo.dev/js/engine.js>などのURLから取得し、上の表のSHA-256と照合する。
`engine.js`は末尾で`module.exports`に`ChuEngine`を渡すので、Node.jsの`require`で読み込める。
局面は`ChuEngine({})`の`reset`を呼んだ状態から、棋譜のUSIの手を`engine.js`の着手の形式に直して`commit`に渡し、再現する。
変換では、USIの升の筋は12から`engine.js`の列番号を引いた値、段の文字は`engine.js`の行番号（0が`a`）に対応する。
経由升を持つ獅子の手は、経由升に相手の駒があれば途中で取る手、空きなら跳ぶ手として符号化する。

速度は`think({ maxDepth: 60, ms: 10000, noise: 0 })`が返すノード数と時間から求めた。
深さごとの累積ノード数は、`engine.js:1231`の`doneDepth = depth;`の直後で深さとノード数を報告するように写しを書き換え、`think`に`nodes: 1e12`と`ms: 60000`を渡して求めた。
`nodes`を渡すと、最善手が安定したときの早めの停止が働かなくなる。
置換表の比較は、写しの`TT_BITS`を20から24に変えて同じ測定を繰り返した。
静止探索の再現は、写しに静止探索の関数を外から呼ぶ口を足し、後手番の局面で`qsearch(-1000000, 1000000, 0, turn, 0)`を呼んで、後手のstand-patと比べた。

差し替えた手は、ラッパーが標準エラーに書く`trap ply=<手数> move=<差し替えた手> base=<元の手>`の行を、対局の記録の同じ手数のアプリの手と照合して特定した。
minaseの判定には、規則`L1,L3,P2,P6,R3,E0,E1`、置換表256 MBで、各局面に`usinewgame`を送ってから`go depth 14`を使った。
アプリの判定には、標準流派の新しい探索器で`think({ maxDepth: 60, ms: 5000, noise: 0 })`を使った。

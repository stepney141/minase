1. 探索の全体構造についての結論は、通常の `#n` が固定した手数上限の下で詰みの存在を判定し、その後に短い解を再探索する、というものである。
    最初から `1, 3, 5, …, n` と上限を増やす反復深化ではなく、全節点を必ず展開する固定深さ全探索でもない。
    攻方は少なくとも1手が詰めばよい OR 節点、受方はすべての応手を詰ませる必要がある AND 節点として処理する。
    攻方の再帰関数は `FUN_1400036d0`、受方の再帰関数は `FUN_1400072e0` であり、互いを呼ぶ。

    探索結果は関数の真偽の返り値ではなく、節点の `+0x18` にある証明数と `+0x1c` にある反証数に記録される。
    以下ではコードの `0x3fffffff` を便宜上の無限大 `I` とする。

    | 証明数 | 反証数 | 意味 |
    | --- | --- | --- |
    | `1` | `1` | 未展開節点の初期値である。 |
    | `0` | `I` | 現在の探索条件で詰みが証明された。 |
    | `I` | `0` | 現在の手数上限では詰まないと判定された。 |
    | `0` | `0` | 指定手順外など、集計から除外する状態である。 |

    深さは節点の `+0x30`、詰みまたは不詰判定までの長さは `+0x32` に保持される。
    詰みの長さは攻方で最小、受方で最大を選び、親へ1手加えて伝播する。
    深さの上限に達しても詰みなら成功とし、詰みでなければ手数不足による不詰とするため、この不詰を無制限の手数での不詰と解釈することはできない。

    | 表示と文字列アドレス | 対応する判定 |
    | --- | --- |
    | 「詰 C」 `0x1400365f8` | 攻方の子局面が王手であり、受方の逃れがないと先に確認できた。 |
    | 「千日手 C」 `0x1400365d8` | 攻方の着手後の局面が経路内の同手番局面と一致したため、その手を削除する。 |
    | 「疑似逃れ（手数不足）C」 `0x140036600` | 攻方の子が手数上限に達し、詰みを確認できなかった。 |
    | 「逃れ（王手なし）C」 `0x140036630` | 攻方で探索対象の手が残らなかった。通常条件では有効な王手がないことに対応する。 |
    | 「逃れ（攻方王詰）E」 `0x140036b40` | 受方の応手によって攻方の王駒に当たりが生じ、攻方の安全な応手が存在しない。 |
    | 「詰* E」 `0x140036af4` | 受方節点自身が手数上限に達し、その局面で詰みを確認した。 |
    | 「逃れ（受手なし）E」 `0x140036b10` | 受方に生成された手がなく、王手かつ詰みという条件も成立しない。 |

    根拠は、統括処理 `FUN_140005300` の C 3067–3118 行、探索開始処理 `FUN_140005460` の 3120–3146 行、攻方の 1577–1860 行、受方の 4351–4641 行である。
    終端の詰み確認は `FUN_1400196e0` の 18006–18038 行、攻方王詰の確認は `FUN_14000db80` の 9151–9182 行にある。
    `#n` の数値をそのまま上限へ代入するのは `FUN_14000a1f0` の 6686–6724 行であり、二重の `#` による順次検索指定を読む分岐とは区別されている。
    確信度は高である。

2. 置換表についての結論は、最善詰用の節点表と、協力系用の不詰局面表を分けて理解する必要がある、というものである。
    最善詰には攻方用と受方用の2表があり、各表は `2^21` 個のバケットを持つ連結リスト方式である。
    バケット番号は攻受のハッシュ値の下位部分を排他的論理和で合わせ、`0x1fffff` でマスクして求める。
    一致条件は攻方の64ビットハッシュ、受方の64ビットハッシュ、深さの3つであり、手番は表の選択により区別する。

    最善詰の節点は64バイトで、主要な内容は次のとおりである。

    | オフセット | 保存内容 |
    | --- | --- |
    | `+0x00`, `+0x08` | 最初の子と次の兄弟へのポインタを保存する。 |
    | `+0x10` | 生成途中では局面へのポインタ、表への登録後はバケット内の連結に使う。 |
    | `+0x18`, `+0x1c` | 証明数と反証数を保存する。 |
    | `+0x20`, `+0x28` | 攻受各64ビットのハッシュ値を保存する。 |
    | `+0x30`, `+0x32`, `+0x34` | 深さ、結果の長さ、状態フラグを保存する。 |
    | `+0x36` | 8バイトの着手情報を保存する。 |

    同一キーが見つかると証明数、反証数、長さ、フラグを再使用する。
    確定結果の更新では、既存の詰みより短い詰み、既存の不詰より長い不詰判定を優先する比較がある。
    木から外した確定節点を保存するリストと、再利用可能な節点のリストを分け、メモリ不足時には枝の整理や保存節点の解放を行う。
    したがって、最善詰の置換方針を単純な参照回数最小方式と呼ぶことはできない。

    「攻方不詰局面（参照回数 %d以下）を再使用します」の結論は、証明済みの不詰情報を読み出す際の通知ではなく、使用頻度の低い保存レコードを回収して新しい局面に使う際の通知、ということである。
    この表のレコードは28バイトで、連結ポインタ8バイト、ハッシュ値2個で16バイト、不詰を確認した残り手数2バイト、参照回数2バイトを持つ。
    同じハッシュ値で、今回の残り手数が保存済みの残り手数以下なら、その局面を探索から除ける。
    参照回数は255まで増加し、保存時の初期値は1である。

    保存領域が不足すると100万件単位で増設し、増設できない場合には参照回数の分布から回収閾値を選ぶ。
    回収対象は参照回数と保存した残り手数の両条件で選び、全体の約40%を目安としている。
    表示は「以下」だが、実際の比較は `参照回数 < 閾値` である。
    残すレコードの参照回数も減らし、古い利用実績の影響を弱める。

    ハッシュは、升、駒種、陣営ごとの乱数を排他的論理和で合成する Zobrist 方式である。
    乱数生成部は624語の状態配列と MT19937 の定数を使うため、Mersenne Twister と同定できる。
    成保留駒は別の駒番号としてハッシュに入り、獅子捕獲には追加の乱数を混ぜ、次の着手で前手分を外す。
    比較時に144升の盤面を再照合する処理はなく、ハッシュ一致に依存する。

    メモリ量は探索用の動的記憶領域の予算に使われる。
    `/XM` では搭載物理メモリから `0x40000000` バイト、すなわち1 GiBを引き、それ以外では空き物理メモリを採る。
    主な増設単位は、節点が10万個×64バイト、局面が1万個×204バイト、協力系の不詰レコードが100万個×28バイトである。
    この予算をすべて1枚の置換表へ割り当てる構造ではない。

    根拠は、最善詰の登録と検索を行う `FUN_140003f20`、`FUN_140007b90`、`FUN_140004ec0`、`FUN_140004f50`、`FUN_140004fe0`、`FUN_1400050e0` の C 1862–1891、4643–4672、2746–2955 行である。
    協力系との分岐と保存領域の確保は `FUN_14000a1f0` の 6900–7112 行、不詰表の検索は `FUN_14000e170` の 9446–9487 行、保存と回収は `FUN_14000e260` の 9489–9645 行にある。
    対応文字列の先頭は C が参照する `0x140037350` で、strings_va.txt は直前の1バイトを含む `0x14003734f` として採録している。
    ハッシュの根拠は `FUN_14000cd20`、`FUN_14000cf90`、`FUN_14000cff0`、`FUN_14000cf10`、`FUN_14000d3e0`、`FUN_140018f50` の C 8481–8522、8605–8690、8574–8603、8826–8862、17681–17717 行である。
    メモリ予算は `FUN_140018060` の 16919–16946 行、割当てと回収は `FUN_140016b70` の 15930–16073 行および `FUN_140017010` の 16102–16162 行にある。
    確信度は高である。

3. 早詰検索についての結論は、最初に得た詰手数を `m` として、`m−2` 手以下で詰むかを再探索する、というものである。
    成功すれば、その探索で得た詰手数へ上限を更新し、再び2手短い上限を試す。
    失敗すれば前の上限と解を復元する。
    `/ENSSM` はこの再探索を省くため、この指定時の最初の解には最短性の確認が付かない。

    「検査深度 %d で変化・早詰を除去」は、得られた解の木を整理する処理である。
    分岐局面で一時的な節点を作り、現在の深さを `d`、検査深度を `k`、現在の全体上限を `N` とすると、上限を `min(d+k, N−2)` に変更して同じ探索器を呼ぶ。
    短い詰みを証明できた枝を置き換え、攻方では短い詰手順、受方では長い抵抗を残すように長さを更新する。
    既定の検査深度は `N−2` であり、設定値がある場合には手番の偶奇を合わせる。
    ハッシュ参照によって結果だけ得られ、木が未展開の箇所も再展開してから手順を整える。

    余詰検索は、採用手順の印が付いた枝をたどり、攻方の分岐で未採用の手を再探索する。
    `/ENSAM` で省略でき、解数上限にも従う。
    追加手数を持つ内部設定が非ゼロなら上限を増やして長手数の余詰も調べるが、この設定の利用者向け指定方法までは確定していない。
    入口には `DAT_1430bc684 <= 根の結果長` という条件もあるため、早詰を発見したすべての場合に余詰検索が無条件で実行されるわけではない。

    根拠は `FUN_1400067c0` の C 3878–4004 行、全体の呼出順を定める `FUN_140005300` の 3091–3115 行、枝の短縮を行う `FUN_140005bb0`、`FUN_140005c50`、`FUN_140005e90` の 3397–3588 行である。
    最短と最長の枝の整理は `FUN_140006120` の 3639–3750 行、未展開箇所の展開は `FUN_1400052b0`、`FUN_140005510`、`FUN_140005690` の 3051–3065、3148–3275 行、余詰検索は `FUN_140006390` と `FUN_1400064a0` の 3752–3876 行にある。
    対応文字列は早詰確認 `0x140036978`、手数付き確認 `0x140036998`、検査深度 `0x140036a00`、余詰確認 `0x140036a50`、探索起点表示 `0x140036a98` である。
    確信度は高であり、追加手数の指定方法だけは未確定である。

4. 探索技法についての結論は、df-pn 系の証明数探索と明示的な手の順序づけがあり、通常の駒得評価に基づく αβ 探索は確認できない、というものである。
    証明数を `pn`、反証数を `dn` とすると、OR 節点では通常 `pn=min(pn_i)`、`dn=sum(dn_i)`、AND 節点では通常 `pn=sum(pn_i)`、`dn=min(dn_i)` を計算する。
    ただし、和が1000万を超える場合には最大の子の値に切り替えるため、教科書的な和を常に保つ実装ではない。

    次に探索する子は、OR では証明数最小、AND では反証数最小を基本として選ぶ。
    同値の場合には反対側の数が大きい子を優先する比較がある。
    OR の子の証明数閾値は `min(親閾値, 次点の証明数+1+選択子の証明数/10)`、反証数閾値は `親閾値+選択子の反証数−親の反証数` である。
    AND では証明数と反証数の役割が逆になる。
    この閾値更新と相互再帰が、df-pn 系と判断する直接の根拠である。

    手の初期順序にも別の処理がある。
    攻方の手は到達升への利きなどから順位を付け、受方の手は駒取り、玉の移動、玉の近傍への移動などを区別する。
    その値を着手の最終バイトの下位4ビットへ置き、昇順に並べ直す。
    利きの一部は障害物を反映しない事前計算の集合なので、これを合法性の最終判定と混同してはならない。

    根拠は、集計関数 `FUN_140004d00`、`FUN_140004d50`、`FUN_140004da0`、`FUN_140004e00` の C 2577–2716 行、子の選択関数 `FUN_1400051e0` と `FUN_140005250` の 2957–3049 行、閾値更新の 1794–1808、4573–4584 行である。
    順位の付与は `FUN_1400096a0` と `FUN_140009730` の 5986–6097 行、並べ替えは `FUN_140009f80` の 6406–6445 行にある。
    「証明数配列領域」 `0x1400370b0` と「反証数配列領域」 `0x1400370c0` は、深さ別の閾値配列の確保と対応する。
    確信度は高であり、αβ の不在は追跡した通常最善詰の探索経路についての結論である。

5. 王手の定義についての結論は、1枚の王駒への当たりをまず検出し、王駒が2枚ある場合には1手で両方を取れるかを追加判定する、というものである。
    攻方から受方への当たりは局面の `+0xb6` の `0x80`、逆向きは `0x40` で表す。
    この当たりフラグだけで、2枚の王駒に対する通常の王手を確定してはいない。

    | 受方の王駒 | 通常条件で攻方に要求する状態 |
    | --- | --- |
    | 0枚 | 通常の開始局面としては入力エラーにする。 |
    | 1枚 | その王駒に当たりがあることを要求する。 |
    | 2枚 | 次の1手で2枚とも取れる配置であることを要求する。 |
    | `!MGY` 指定時 | 少なくとも1枚への当たりを王手として受け付ける。 |

    2枚取りの判定では、王駒同士の隣接と、相手に獅子、成獅子、角鷹、飛鷲があることを調べる。
    獅子の場合は少なくとも一方の王駒への隣接、角鷹と飛鷲の場合は固有の前方2歩の並びを確認する。
    2枚が別々の駒に狙われているだけでは通常の王手にはしない。
    `!MGY` でも、受方の応手後に次の1手で全王駒が消える状態を許すわけではなく、一部の王駒への当たりを残す応手を許す。

    王駒位置の保存先は各陣営2個であり、3枚以上を一般的に数え上げて「全王駒」を判定する構造は確認できない。
    さらに、飛鷲の2枚取り判定には `2 <= 升番号/12 <= 9` という左右両端を一律に除く条件がある。
    推定として、端寄りから盤内へ向かう合法な2枚取りまで王手と認めない場合がある。
    したがって、仕様書の定義を任意の配置で完全に実現しているとまでは結論できない。

    根拠は、王駒と当たりを集める `FUN_140001000` の C 1–114 行、当たり検出の `FUN_14000d1e0`、`FUN_14000d290` の 8710–8824 行、2枚取りを調べる `FUN_1400081f0` の 5096–5208 行である。
    `FUN_140008500` と `FUN_140008600` の 5210–5292 行は、2枚の王駒が即時に全滅する場合に0、それを回避できている場合に1を返す。
    攻方の王手義務は `FUN_140003630` の 1538–1575 行、受方の応手条件は `FUN_140007280` の 4330–4349 行にある。
    `!MGY` は文字列 `0x140036bec` と定数表 `0x1400453b8` に対応し、`DAT_140047c24` の `0x80000000` を設定する。
    受方王駒なしの入力エラーは C 6971–6976 行、文字列 `0x140037008` である。
    確信度は基本分岐について高、3枚以上と飛鷲の境界事例の実動作について中である。

6. 王手放置についての結論は、通常条件では双方の王駒の即時全滅を避ける手だけを探索する、というものである。
    攻方の着手は自分の王駒を守る条件と相手への王手条件を満たす必要があり、受方の着手も自分の王駒を守る条件を満たす必要がある。
    王駒が2枚あるときには、そのうち1枚を当たりにさらす手は残り得る。
    これは、最後の王駒を取られるまで王手放置自体を合法とする規則書第8条の一般対局規則とは異なる。

    「逃れ（攻方王詰）」は、攻方の王駒を実際に取ったという表示ではない。
    受方の応手後に攻方への当たりを検出し、攻方がそれを解消できる着手を持たないと判定した時点で、受方の逃れを証明している。
    攻方に王手を返しながら攻方王を詰ませる応手を、探索上の反証として使う処理である。

    受方が攻方の王駒を取る手そのものは、通常の捕獲として盤上から駒を除く処理に入る。
    しかし、その後も受方自身の王駒の安全確認を通る必要がある。
    追跡した箇所には、「攻方の最後の王駒を取ったので、自分への王手を残していても即勝利」とする分岐はない。
    通常の攻方着手で自王の即時全滅を避ける設計でもあるため、規則書第21条の実捕獲による勝利をこの表示から読み込むべきではない。

    根拠は `FUN_140003630` の C 1546–1572 行、`FUN_140007280` の 4338–4346 行、`FUN_1400072e0` の 4445–4474 行である。
    攻方に安全な応手がないことを調べるのは `FUN_14000db80` の 9151–9182 行と `FUN_14000da40` の 9107–9149 行であり、攻方の次の王手の有無だけを調べているわけではない。
    捕獲の適用は `FUN_1400199f0` の 18161–18205 行にある。
    対応文字列は `0x140036b40`、仕様上の説明はヘルプ15–21行である。
    確信度は高である。

7. 獅子、角鷹、飛鷲の動作についての結論は、直接の移動と、隣接駒を取ってからの追加移動を分けて生成する、というものである。
    着手は駒種、移動元、最終到達升、経由升、到達升で取った駒、経由升で取った駒、フラグ、順位の8バイトで表す。
    経由升が `0x90` なら通常の1段階移動であり、経由升を持つ手では両方の捕獲を記録して盤面から除く。
    獅子の直接移動表は周囲24升を含み、中間の駒を跳び越せる。
    角鷹は前方、飛鷲は前方斜めの専用表を使い、1歩目の捕獲後に直進する手と元へ戻る居喰いを生成する。

    じっとは、調べた通常生成経路では生成されない。
    空の隣接升を見つけてもそこへの直接移動を生成するだけで、元へ戻る2段階目へ進むのは1歩目で相手駒を取った場合である。
    獅子の直接移動表にも原位置を表す差分はない。
    このため、居喰いの実装を根拠として、無捕獲のじっとも実装されていると判断することはできない。

    獅子同士の直接捕獲は、隣接なら足による制限を受けず、非隣接なら相手側の足フラグで制限する。
    足は各駒の利きを盤面上で走査して求め、王駒も足から除外しない。
    走り駒の走査では、途中の相手獅子を越えた先の味方獅子も調べるため、捕獲側獅子が元の升を離れることで通る裏足を考慮している。
    捕獲制限を再帰的に解く方式ではない。
    ただし、足フラグは獅子と成獅子の種類ごとに集約され、同種の獅子が多数ある局面の個体別管理ではない。

    先獅子は、直前に非獅子が獅子を取ったことと、取り返される側の獅子に足があることから判定する。
    この制限を呼ぶのは主に非獅子の捕獲経路であり、隣接する獅子同士の捕獲には同じ制限を適用していない。
    したがって先獅子のこの部分は、規則書の `L0＋L4` に相当すると推定する。
    麒麟が獅子を取って成る場合も、直前の移動駒種は麒麟として残るため、成獅子を無条件に取り返せる `L2` の例外は確認できない。

    付け喰いは、1歩目に歩兵または仲人以外を取った場合、2歩目で足のある獅子を取ることを認める形で現れる。
    一方、1歩目が歩兵または仲人、2歩目が獅子という組合せは、足の有無を調べずに除外している。
    この除外は、規則書第16条が禁止する「歩兵または仲人が唯一の足だった場合」より広く、足のない獅子への2枚取りも除く。

    `/ESSZS` は初形の直前捕獲駒欄を獅子の番号 `0x13` にして、先獅子が成立した直後として扱う。
    通常の奇数手 `#n` で攻方手番なら、コードは受方の足フラグ `0x05` を検査し、「開始図では受方先獅子」と表示する。
    受方手番では攻方の足フラグ `0x0a` を検査する。
    したがって、実装が足を要求するのは保護される直前着手側であり、ヘルプ118–119行の「手番側」という文言とは一致しない。

    根拠は、攻方の特殊移動生成 `FUN_140003260` の C 1381–1508 行、受方の `FUN_140006ec0` の 4172–4300 行、捕獲適用 `FUN_14000ddd0` の 9273–9315 行である。
    駒種ごとにこれらを選ぶ処理は `FUN_1400094f0` の 5907–5984 行にある。
    直接移動の元表はバイナリの獅子 `0x1400461b0`、角鷹 `0x140046888`、飛鷲 `0x140046748` である。
    足は `FUN_14000d1e0`、`FUN_14000d290`、`FUN_140018d50`、`FUN_140018e00` の 8710–8824、17564–17679 行、先獅子は `FUN_1400174a0` と `FUN_140017500` の 16310–16364 行にある。
    付け喰いの制限は1486–1488行、初形の先獅子設定は6947–6967行、対応文字列は `0x140036f78`、`0x140036fa0`、`0x140036fc0`、`0x140036fe8` である。

    足については、通常生成と詰み検査の不整合も残る。
    攻方の詰み検査用 `FUN_14000d6d0` は C 9094 行で `+0xb6` を参照するのに対し、通常生成は1498行で足を持つ `+0xb5` を参照する。
    推定として、攻方王詰の検査で非隣接獅子の捕獲制限を取り落とす場合がある。
    確信度は移動生成と先獅子の分岐について高、規則コードとの対応および個々の不整合が詰み判定へ及ぼす影響について中である。

8. 成りについての結論は、成り権の管理の骨格が `P0` に近いものの、実際の処理全体を `P0` から `P6` のいずれか、またはその単純な組合せと同一視できない、というものである。
    敵陣は各側4段であり、移動元または移動先が敵陣にあることを成りの候補条件とする。
    敵陣で不成を選んだ駒は成保留駒へ変え、以後は原則として捕獲を伴う場合にのみ成りを認める。
    敵陣から出れば保留を解除し、再入陣による成りを可能にする。
    1手待っただけで非捕獲の成り権を回復する `P1` や `P2` の時間管理は確認できない。

    成保留は駒ごとの追加ビットではなく、`0x16` から `0x1d` の予約駒番号を割り当てて表す。
    その駒種記述へ `0x01000000` を付け、`+0x72` に本来の駒番号を保存する。
    初形から敵陣にある未成駒にもこの変換を適用し、「成保留駒です」と通知する。
    したがって、初形にある未成駒がまだ成る機会を使っていなかった、という過去の違いを入力から表す構造ではない。

    最奥段の救済には不整合がある。
    手の生成側は成保留駒の元の番号を読み、歩兵 `1` と香車 `3` なら、最奥段への非捕獲移動でも成りを試す。
    これは `P3` を含める意図を示すと推定できる。
    しかし、着手適用側は元の番号ではなく現在の予約番号を `1` または `3` と比較するため、成保留駒の非捕獲成りはその段階で拒否される。
    歩兵の標準的な最奥段救済もこの経路にかかるので、「P0＋P3 を正しく実装している」とは報告できない。
    この比較は元バイナリの `0x14000de4e`、`0x14000de53` と受方側の `0x140019a6e`、`0x140019a73` でも確認した。

    `P4` の仲人救済を示す比較はなく、`P5` の「保留後の歩兵は最奥段だけで成る」という制限とも一致しない。
    成保留駒は最奥段以外でも捕獲を伴えば成れるためである。
    最善系には一部の駒の不成候補を省く属性 `0x02000000` があり、香車だけでなく反車、盲虎、角行、飛車、龍馬、龍王、酔象にも設定されている。
    協力系ではこの属性を消すため、推定としてこれは成る手を優先して候補を省く探索上の処理であり、最奥段だけに適用する `P6` の規則とは区別すべきである。

    根拠は、成り候補生成 `FUN_140002e80` の C 1242–1314 行と受方側 `FUN_140006b50` の 4042–4115 行、成保留の初期化 `FUN_14000bb00` の 7551–7627 行、予約番号の生成 `FUN_1400175e0` の 16406–16525 行である。
    捕獲成りと保留解除は `FUN_14000ddd0` の 9297–9312 行、受方側は `FUN_1400199f0` の 18185–18203 行にある。
    不成省略属性を協力系で解除するのは `FUN_140017560` の 16366–16389 行である。
    対応文字列は `0x1400371a8`、比較対象は規則書第17–19条および第30条である。
    確信度は成保留の構造と番号比較の不整合について高、実装意図と規則分類について中である。

9. 千日手についての結論は、通常最善詰では探索経路を同手番ごとにさかのぼり、ハッシュが一度一致した段階で攻方の着手を除外する、というものである。
    「経路照合かハッシュか」は二者択一ではなく、経路上の局面ハッシュの組を比較している。
    深さ `d−2, d−4, …` を調べ、既出一致数の閾値として1を渡すため、最初の再出現、すなわち2回目で作動する。

    判定は攻方の子を処理する際に行われ、受方の再帰関数には同じ検査の呼出しがない。
    該当する手を子リストから削除し、攻方のすべての候補が消えれば不詰になる。
    対局全体の千日手勝敗を返すのではなく、攻方の詰み証明に使えない手として扱う。
    4回反復を数える規則書の `R0`、`R1`、`R3` には相当せず、双方へ既出局面再現禁止を課す `R2` とも完全には一致しない。

    協力系には別途、現在の探索経路の局面をバケットへ登録し、復帰時に取り除く方式がある。
    こちらも攻受別の表でハッシュ値を照合し、不詰保存表の照合と同じ入口にまとめている。
    成保留の駒番号と直前の獅子捕獲に由来する追加値がキーへ入る一方、手順全体を置換表のキーへ含める処理はない。
    そのため、経路に依存する反復判定と置換表の再使用の組合せについて、一般的な正当性まではこの静的解析から保証しない。

    先獅子の初形には、ハッシュとの整合について追加の確認点がある。
    初形ハッシュの計算は `/ESSZS` が直前捕獲欄を変更するより前に行われ、その直後の再計算は見当たらない。
    推定として、開始局面と探索中の局面で獅子捕獲の追加値の扱いがずれる可能性がある。

    根拠は、経路照合 `FUN_140004e60` の C 2718–2744 行と、その呼出しおよび手の削除を行う `FUN_1400036d0` の 1641–1653 行である。
    協力系の登録、照合、削除は `FUN_14000e650`、`FUN_14000e170`、`FUN_14000e100` の 9647–9665、9446–9487、9415–9444 行、反対側は `FUN_140019da0` の 18334–18375 行などにある。
    初形ハッシュと先獅子設定の順序は `FUN_14000a1f0` の 6929–6967 行で確認できる。
    対応文字列は「千日手 C」 `0x1400365d8` と「手順中局面構造体配列領域」 `0x140037328` である。
    確信度は通常最善詰の反復処理について高、置換表との相互作用および初形の追加値の影響について中である。

10. 終局条件と盤表現についての結論は、通常最善詰が「指定条件で受方を詰ませられるか」を解くプログラムであり、一般対局の全終局条件を実装したエンジンとは区別される、というものである。
    受方に安全な着手がなく、王手であれば詰みとして扱う。
    王手がなくて受方の手がない場合は、最善詰では逃れとする。
    協力ステイルメイト `H=` では、その状態を別の目標として判定する。
    規則書第23条の「王手の有無を問わず合法手がなければ手番側が負け」という一般規則とは一致しない。

    追跡した最善詰の終端判定には、規則書第22条の駒枯れ、裸玉同士の引き分け、合意による引き分けを裁定する処理は見つからない。
    それらを理由とする勝ちを詰みの代わりに認める根拠もない。
    不詰という探索結果を、そのまま一般対局での引き分けと解釈してはならない。

    盤面は12×12の144升を1バイトずつ並べ、局面構造体の `+0x18` から `+0xa7` に置く。
    升番号は `12×(筋−1)+(段−1)` である。
    駒番号の下位6ビットを駒種、`0x80` を攻方、`0x40` を受方として使い、通常の成駒は元の駒番号に `0x20` を加える。
    空升は0、岩は `0x3e`、穽は `0x3f`、位置が存在しない場合の番兵は `0x90` である。
    移動先リストの終端には別に `0xff` を使う。

    岩と穽はどちらも通常の到達升にできない。
    走り駒の走査では岩で止まり、穽なら走査を続ける。
    獅子などの直接跳躍は経由升を走査しないため、岩の隣を越える跳躍まで壁として止める処理は確認できない。
    仕様書の「岩は通過不可」は、少なくとも走り駒の走査として実装されている。

    根拠は、最善詰の終端処理 `FUN_1400072e0` の C 4399–4418、4430–4434、4491–4502 行、詰み検査 `FUN_1400196e0` の 18006–18038 行、協力ステイルメイト分岐 `FUN_140007c50` の 4904–4923 行である。
    盤面と着手の配置は `FUN_14000dc30` の 9184–9271 行、`FUN_140019860` の 18074–18159 行に現れ、局面の割当てサイズ `0xcc` は `FUN_140017010` の 16136 行で確認できる。
    岩と穽の入力は `FUN_14000a1f0` の 6665–6674 行、走査は `FUN_1400030b0` の 1316–1379 行と `FUN_140006d80` の 4117–4170 行にある。
    対応文字列は「逃れ（受手なし）E」 `0x140036b10`、「岩（着手、通過不可領域）」 `0x1400378b8`、「穽（着手不可、通過可能領域）」 `0x1400378d8` である。
    確信度は盤表現と通常最善詰の終端条件について高、一般対局の終局機能が存在しないという範囲の広い否定について中である。

# 探索ノード数の定義と既存エンジンとの照合

2026年9月19日に、マルチスレッド探索のNPS（1秒あたり探索ノード数）が1,000万を超える値を示す理由を調べ、ノード数の数え方をStockfish、やねうらおう、およびHaChuのソースコードと照合した。
調査の目的は、minaseのNPSが既存の将棋プログラムやチェスプログラムのNPSと同じ量を測っているかを確かめることである。

結論は次の3点である。
第1に、調査時点のminaseは通常探索の末端局面を2回数えており、表示ノード数の約33%が二重計上であった。
第2に、Stockfishとやねうらおうは「探索中に実際の着手を盤面へ適用した回数」をノード数とし、探索ワーカー側の`do_move`ラッパーで数える。
第3に、minaseのノード数を同じ定義へ改めた結果、固定深さの探索結果を変えずに二重計上が消え、1スレッドあたり約240万NPSという値は既存エンジンと同じ定義の数値として比較できるようになった。

ノード数の現行仕様は[探索部の設計書](../plans/search.md)の「ノード数の定義」節が所有し、本書はその根拠を記す。

## 調査時点の数え方と二重計上

調査時点の探索は、`Searcher::enter_node`を`search_root`、`negamax`、`quiesce`の各入口と、最後の王駒を取る手および反復の葉で呼び、呼び出しごとに1ノードを数えていた。
`negamax`は残り深さが0になると同じ局面のまま`quiesce`を呼ぶので、通常探索の末端局面は`negamax`の入口と`quiesce`の入口で合わせて2回数えられる。
この構造は、静止探索を導入したコミットc12d460（2026年8月22日）から続いていた。

二重計上の割合は、`negamax`が残り深さ0で`quiesce`へ渡した回数を数える計測コードを一時的な作業ツリーに入れ、benchを実行して測った。
基準はコミット713745fであり、測定機はIntel Core Ultra 7 265KF（20コア）である。

| 条件 | 表示ノード数 | 二重計上したノード数 | 割合 |
|---|---|---|---|
| 1スレッド、深さ7 | 6,264,253 | 2,035,799 | 32.5% |
| 1スレッド、深さ9 | 36,223,447 | 12,267,201 | 33.9% |
| 16スレッド、深さ7 | 32,710,983 | 10,815,432 | 33.1% |
| 16スレッド、深さ9 | 159,620,242 | 53,769,565 | 33.7% |

割合は深さとスレッド数によらず約33%で安定していた。
盤面へ適用しない王駒捕獲の葉の計上は全体の1%以下であり、表示値を大きく動かす要因は末端局面の二重計上だけであった。
二重計上とは別の問題として、この計測コードは全スレッドが共有する原子カウンタを使ったため、16スレッド、深さ7のNPSが計測コードなしの約2,870万から約2,250万へ下がった（教訓は[lessons/shared-probe-counter-distorts-threads.md](../lessons/shared-probe-counter-distorts-threads.md)）。
上の表の割合は回数の比であり、この歪みの影響を受けない。

## 既存エンジンの数え方

Stockfishとやねうらおうは現行のmasterを2026年9月19日に取得し、HaChuは[RULES.md](../../RULES.md)の［E5］と同じコミットdf26f4aを参照した。
以下の`do_move`は着手を盤面へ適用する関数であり、minaseの`make_move_unchecked`に相当する。
null moveは、枝刈りの判定のために手番だけを相手へ渡す仮想の着手であり、`do_null_move`がこれを適用する。

| 項目 | Stockfish | やねうらおう | HaChu |
|---|---|---|---|
| 数える場所 | 探索ワーカーの`Search::Worker::do_move`で、`pos.do_move`の直前に`++nodes`を行う（`src/search.cpp`） | 探索ワーカーの`YaneuraOuWorker::do_move`で、`pos.do_move`の直前に1を加える（`source/engine/yaneuraou-engine/yaneuraou-search.cpp`） | 通常探索と静止探索を兼ねる`Search`関数の入口で`nodes++`を行う（`hachu.c` 2087行） |
| 静止探索の着手 | 同じラッパーを通るので数える | 同じラッパーを通るので数える | 同じ関数の入口なので数える |
| null move | `do_null_move`は数えない | `do_null_move`は数えない | 子局面の入口で数える |
| 根局面 | 数えない | 数えない | 数える |
| 王を取られる着手 | 非合法手として`do_move`の前に除外するので数えない | 同左 | 王駒捕獲を検出して入口の計数より前に戻るので数えない |
| スレッドの合算 | 全ワーカーの合計（`ThreadPool::nodes_searched`） | 全ワーカーの合計 | 単一スレッド |
| NPSの式 | `nodes * 1000 / 経過ms` | 同左 | 思考出力はノード数と経過時間だけを出し、NPSは受け手が計算する |

どちらの方式でも1局面を数えるのは1回だけであり、調査時点のminaseのような二重計上は起こらない。
ノード数の数え方に業界共通の規格はなく、着手の適用時に数える方式と、探索関数の入口で数える方式が併存する。
両方式の差は根局面とnull move直後の局面の分だけであり、全ノードの大半を静止探索が占める探索では無視できる。
計数を置く場所は版によって異なるが、数える対象は一貫して盤面へ適用した着手である。
Stockfish 16（タグ`sf_16`）とやねうらおうv6.00は、盤面型の`Position::do_move`の中で`thisThread->nodes.fetch_add(1)`を行っていた。
Stockfish 17（タグ`sf_17`）は計数を`search.cpp`の`pos.do_move`の各呼び出し箇所へ移し、両エンジンの現行masterは上の表のとおり探索ワーカーの`do_move`ラッパーで数える。
minaseが探索側で数えるのは、`Position`が合法手生成ライブラリの公開型であり、探索ワーカーのカウンタを持たせられないためである。

Stockfishには、置換表の打ち切り判定の中でラッパーを通さずに`pos.do_move`を呼ぶ箇所が1つあり、この着手は数えられない。
これはStockfish固有の検査であり、minaseに対応する処理はない。

## 採用した定義

minaseのノード数は、探索中に実際の着手を盤面へ適用した回数とする。
数える箇所は、`search_move`が`make_move_unchecked`を呼ぶ直前と、`quiesce`が`make_move_with_captures_unchecked`を呼ぶ直前の2つだけである。
null move、根局面、および盤面へ適用しない最後の王駒を取る手は数えない。
置換表で打ち切られる局面と反復で引き分けになる局面は、着手の適用後に判定するので1ノードとして数える。
この扱いは、上の表のStockfishおよびやねうらおうの各項目と一致する。

`enter_node`は停止条件の検査とノード上限の予約を兼ねたまま、呼び出し位置だけを着手の適用直前へ移した。
探索関数の入口で数える方式のまま`negamax`の深さ0の判定を計数の前へ移す代案でも二重計上は消えるが、参照実装の多数派と定義が一致し、計数点が着手の適用という1種類の出来事に対応する現方式を採った。

## 検証

変更はコミットb221621で行い、`cargo fmt --check`、`cargo clippy --all-targets -- -D warnings`、および`cargo test`の成功を確認した。
benchの深さ7では、全15局面で最善手と評価値が変更前と一致し、総ノード数だけが6,264,253から4,121,971へ減った（34.2%減）。
固定深さの探索木は変わらないので、棋力測定は行っていない。

変更後のbenchのNPSは次のとおりである。
複数スレッドの値は3回反復の中央値である。

| スレッド数 | 深さ | NPS |
|---|---|---|
| 1 | 9 | 約239万 |
| 4 | 8 | 約804万 |
| 8 | 8 | 約1,465万 |
| 16 | 8 | 約2,240万 |

差分更新つきの駒位置評価だけを使い、ノードの大半が捕獲手だけを生成する静止探索である探索としては、1スレッドあたり約240万NPSは異常な値ではない。

## 既存の記録への影響

コミットc12d460からb221621の直前までのminaseが出力したノード数とNPSは、旧定義の値である。
該当するのは、benchの総ノード数とNPS、`nodes=100000`条件の測定記録、設計書に残る1ノードあたりの費用、およびUSIの`info`行である。
これらの記録は完了済みの測定として書き換えず、現行の値と比べるときは、末端局面の割合が同程度なら旧定義の値に約0.66を掛けて換算する。
高速化の設計書が用いたNPSの倍率は、分子と分母が同じ定義なので、末端局面の割合を変えない変更についてはそのまま有効である。

[HaChu対minaseの探索深さとNPSの実測](../measurements/hachu-vs-search-nps.md)は、minaseを約140万〜270万NPS、HaChuを約80万〜95万NPSと記録している。
minaseの値は旧定義であり、約0.66を掛けると約90万〜180万NPSになる。
換算後もHaChuの値を下回らないので、「等時間の差の主因は探索量ではない」という結論は変わらないが、NPSの差は記録が示すほど大きくない。

`go nodes N`の上限は、着手の適用N回を意味するようになった。
同じNでも旧定義より約1.5倍多く探索するので、旧定義の`nodes`条件で取った測定と、現行の`nodes`条件の測定を同じ条件として比べてはならない。
hard limitと停止フラグの確認周期は4096ノードのままであり、実時間では約1.1 msから約1.7 msへ延びた。

# やねうら王の王手判定と合法手生成の使い分けを審判層の裁定へ応用する調査

## 結論

[審判層の裁定が繰り返す合法手生成の削減の設計書](../plans/referee-adjudication-movegen.md)は、対局の審判層`Game::play`が1手ごとに行う4つの判定で合法手生成が繰り返されることを問題にしている。
4つの判定とは、着手の合法性検査、反復規則R1（Lishogi式の4回反復の裁定で、攻撃的着手を続けた側を負けとする）の攻撃的着手の記録、合法手なしの判定、および詰み判定である。
本書は、将棋エンジンのやねうら王が合法手生成を避けて王手と合法性を判定する方法をソースコードで調べ、minaseの審判層へ適用できる考え方を整理した。
やねうら王の方法は、次の3つの原則にまとめられる。

1. 探索の中では合法手の全件生成を行わない。1手の合法性は、全件生成した列との照合ではなく、その1手だけを調べる`pseudo_legal()`と`legal()`で判定する。
2. 「王に利きが当たっているか」は、合法手生成ではなく、対象の升への利きの逆引き`attackers_to`、またはその結果を局面に付随させた`checkersBB`で判定する。
3. 連続王手の千日手は、王手の真偽値を整数のカウンタへ畳み込み、同一局面までの手数と比べて裁定する。

この3つの原則をminaseの審判層に当てはめると、設計書が削減の対象外として残している合法手生成のうち、着手の合法性検査とR1の攻撃的着手の記録の2つを置き換えられる。
どちらも、裁定の結果を変えずに、動かした駒1枚についての着手生成と利きの逆引きで処理できる。
置き換えの根拠は、設計書が王駒1枚の捕獲可能性の判定に使う補題にある。
すなわち、捕獲の制限は獅子を取る手にしか掛からないので、獅子でない駒の升へ疑似利きが届くことと、その駒を取る合法手があることは一致する。
この性質は対象の升ごとに成り立ち、王駒の枚数に依存しない。
同じ補題は、駒枯れの引き分けと裸玉の裁定が使う「いずれかの王駒を取れるか」の判定にも使える。
駒枯れの猶予の判定は、王駒だけになった側の王駒1枚についての着手生成で足りる。
合法手なしの判定と詰み判定については、やねうら王の`is_mated()`も合法手の全件生成を使うので、そのまま適用できる手法はない。
ただし、やねうら王の段階的な生成（MovePicker）と王手回避の生成の考え方から、着手生成を駒単位で逐次実行して最初の逃れる手で打ち切る方式と、王駒の手を先に試す順序が導ける。

設計書の試算（再生1手あたり約10回の合法手生成を約3回へ削減）は、これらを加えると1回未満まで下がる見込みになる。
ただし、本書の見積りは呼出し回数の勘定であり、置き換え後の費用は測定で確かめる必要がある。
設計書へ反映する項目は、測定による確認を前提として「設計書への反映候補」の節に整理した。

やねうら王の王手情報の派生構造（`checkersBB`、`blockersForKing`、`checkSquares`）を局面に付随させる方式、`LONG_EFFECT_LIBRARY`の利き数の差分更新、および1手詰め判定は、審判層の裁定削減には使わない。
理由は「採らない方式」の節で述べる。

## やねうら王の方法

### 1手の合法性は全件生成との照合で判定しない

やねうら王の探索は、合法手の一括生成`MoveList<LEGAL>`または`MoveList<LEGAL_ALL>`を根の候補手の作成にしか使わない（`thread.cpp` 419行から466行）。
`LEGAL`は2段目の歩と香の不成、および角と飛の不成を省き、`LEGAL_ALL`が全合法手を生成する（`movegen.h` 68行から71行）。
minaseの`generate_moves`は不成を省かないので、集合としては`LEGAL_ALL`に対応する。
探索ノードでは`MovePicker`が擬似合法手を段階的に生成する。
王手を受けていなければ捕獲手と非捕獲手（静かな手）を順に生成し、王手を受けていれば最初から王手回避の段階へ入る（`movepick.cpp` 164行、479行から496行、566行から579行、651行から667行）。
生成した手は探索側が1手ずつ`pos.legal(move)`で自殺手を除く（`engine/yaneuraou-engine/yaneuraou-search.cpp` 3496行）。
置換表から得た手の検証も同じであり、Stockfishが`MoveList<LEGAL>(pos).contains()`で行っていた照合を、やねうら王は「pseudo_legalとlegalで十分なのではないか」という注記とともに1手の検査へ置き換えている（同5898行から5900行）。

```cpp
//if (MoveList<LEGAL>(pos).contains(ttData.move))
// ⇨ Stockfishのこのコード、pseudo_legalとlegalで十分なのではないか？
if (pos.pseudo_legal_s<true>(m) && pos.legal(m))
```

`generate<LEGAL>`自体は、王手を受けていれば回避手、さもなくば全擬似合法手を生成してから`pos.legal()`で篩い落とし（`movegen.cpp` 940行から950行）、「かなり重い。ゆえにLEGALは特殊な状況でしか使うべきではない」と注記されている（同938行から939行）。

### 王手の有無は利きの逆引きで判定する

局面に付随する`StateInfo`は、手番側の王に王手をかけている駒の集合`checkersBB`（`position.h` 131行）を持ち、`in_check()`はその非空判定である（同554行）。
`checkersBB`を利きの逆引き`attackers_to`から計算するのは局面の設定時だけであり（`position.cpp` 307行と329行）、`do_move`の中では呼出し側から受け取った真偽値`givesCheck`に従って、真なら前局面の表から差分で求め（同2045行から2070行）、偽なら空集合を設定する（同2085行）。
2077行の`attackers_to`は`#else`側にあり、製品ビルドでは実行されない。
探索は各手について`legal()`の後に`gives_check(move)`を計算して`do_move`へ渡す（`yaneuraou-search.cpp` 3496行、3552行、3867行）。

`gives_check`は、相手玉の升から駒種ごとに逆向きの利きを引いた表`checkSquares`（`position.h` 160行）と、ピンの関係`blockersForKing`（同152行）だけを参照し、利きを再計算しない（`position.cpp` 1244行から1256行）。
この2つの表は差分更新ではなく、`do_move`ごとに`set_check_info`が両側の`blockersForKing`を空にしてから構築し直し、`checkSquares`も計算し直す（同242行から285行、901行から902行）。
差分更新なのは`checkersBB`だけである。
`legal()`も、王の移動では到達升への相手の利きを、玉を除いた占有ビットボードで調べ、それ以外の駒ではピンのビット判定と方向の比較だけを行う（同1577行から1583行）。
王手回避の生成は`checkersBB`から王手駒を取り出し、王手駒の利きが届く升を王の移動先から除き、両王手なら王の移動だけ、1枚なら王手駒の捕獲と合駒の升へ目標を絞る（`movegen.cpp` 492行から551行）。
王の移動先に残る自殺手は生成器では除かず、`legal()`に委ねる（同522行）。

これらはすべて、将棋の合法性が王の安全を含むことを前提にしている。
中将棋では王駒を相手の利きへ移す手も王手の放置も合法なので（RULES.md第8条第3項から第5項）、合法性の判定としては適用できない。
適用できるのは、「王駒に利きが届いているか」を合法手生成ではなく利きの逆引きで判定するという考え方だけである。
minaseの`Position::attackers_to_by`（[control.rs](../../crates/minase-core/src/movegen/control.rs) 65行）は、やねうら王の`attackers_to`に相当する逆引きであり、`Position::gives_check`（[gives_check.rs](../../crates/minase-core/src/movegen/gives_check.rs)）が王駒1枚の場合にこれを使う。

### 連続王手の千日手は整数のカウンタで裁定する

`StateInfo`は、手番側ごとに「何手前から王手を続けているか」を`continuousCheck[COLOR_NB]`（`position.h` 82行）に持つ。
`do_move`は`givesCheck`が真なら着手側の値を2増やし、偽なら0へ戻す（`position.cpp` 1875行から1881行、2085行から2086行）。
千日手の判定は、`previous`の鎖を2手ずつ遡って局面の鍵を比べ、同一局面までの手数`i`が`continuousCheck`以下なら、その区間が連続王手であると判定する（同2125行から2162行）。

```cpp
st->repetition_type = (i <= st->continuousCheck[sideToMove])  ? REPETITION_LOSE
                    : (i <= st->continuousCheck[~sideToMove]) ? REPETITION_WIN
                                                              : REPETITION_DRAW;
```

この判定は直前の同一局面までの区間しか見ないので、3回目以降の出現では、前回の出現で求めた種別と今回の種別が異なれば通常の千日手（引き分け）へ落とす（同2176行から2181行）。
最初の出現からの区間全体の連続王手は、区間ごとの種別の引き継ぎで表している。

minaseの反復規則R1の実装は、同じ構造の「攻撃連続数」`consecutive_attacking_moves`を`R1History`に持ち、最初の同一局面の出現より後の自分の着手数と直接に比べる（[r1.rs](../../crates/minase-core/src/game/repetition/r1.rs)の`r1_repetition_result`）。
区間の扱いは異なるが、カウンタへ入れる真偽値を着手ごとに求める点は同じであり、差は、やねうら王が利きの表から得るのに対し、minaseの`move_was_attacking`（同223行）が合法手の全件生成から得ている点にある。

### 利きの差分更新は既定のビルドで使われない

`LONG_EFFECT_LIBRARY`は、各升の利きの数`board_effect`と走り駒の利きの方角`long_effect`を`do_move`で差分更新し、「ある升に相手の利きがあるか」を1バイトの配列参照にする（`position.h` 601行から605行、`extra/long_effect.h` 198行から305行、`extra/long_effect.cpp` 341行から470行）。
このオプションは既定のNNUEビルドでは無効であり（`config.h` 400行、716行から722行、`Makefile` 33行）、駒得評価の`MATERIAL_LEVEL`が2以上のときと`EVAL_NNUE_HALFKPE9`のときだけ有効になる（`config.h` 413行から416行、716行から720行）。
やねうら王が利きの計算の要否を切り替えている箇所は2つある。
1つはこのビルド時の切替であり、もう1つは探索が計算した`givesCheck`を`do_move`へ渡して、王手のときだけ`checkersBB`の差分計算を行う仕組みである。

1手詰め判定`mate_1ply`は、既定のビルドでも有効であり（`config.h` 368行の`USE_MATE_1PLY`）、通常探索と静止探索が王手を受けていないノードで呼ぶ（`yaneuraou-search.cpp` 2901行から2903行、4766行）。
利きライブラリが無効なので、コンパイルされる実装は利き数を使わない`mate/mate1ply_without_effect.cpp`である。
この関数は、手番側が相手玉を詰ませる手を、王の8近傍の表と駒打ちを軸に探す攻め側の判定である（同48行から51行、720行から731行）。
審判層の詰み判定は「各候補手の後に相手が最後の王駒を取れるか」という受け側の判定であり、持ち駒がなく王駒が2枚になり得る中将棋では表の前提も合わないので、適用しない。
`is_mated()`は`MoveList<LEGAL>(*this).size() == 0`であり（`position.cpp` 1260行から1264行）、合法手の一括生成を使う。
`MoveList`は常に生成対象をバッファへ書き切るので（`movegen.h` 159行から160行、187行）、「1手でも存在するか」を途中で打ち切る入口はやねうら王にはない。

## minaseの審判層への当てはめ

minaseの`Game::play`（[referee.rs](../../crates/minase-core/src/game/referee.rs)）は、1手ごとに次の判定で合法手を生成する。
設計書の「目的」の節が命令数から推定した回数は、合法性検査で1回、R1の記録で1回、合法手なしと詰み判定の冒頭で2回、詰み判定の候補手ごとに2回である。
逃れる手が見つかるまでに試す候補手の数をkとすると合計は4+2k回であり、kの平均は約3である。

### 着手の合法性検査は動かす駒1枚の生成で足りる

`Position::try_make_move_with_undo`（[checked.rs](../../crates/minase-core/src/movegen/checked.rs) 33行から45行）は、全合法手を生成して`contains`で照合する。
一方、`MoveGenerator::is_legal_move`（[movegen/mod.rs](../../crates/minase-core/src/movegen/mod.rs) 114行から139行）は、移動元の駒が手番側の駒であることを確かめてから、その駒1枚の合法手を`generate_piece_moves`で生成して照合する。
`generate_moves`は手番側の全駒について同じ`generate_piece_moves`を呼ぶ和集合である（[generate.rs](../../crates/minase-core/src/movegen/generate.rs) 17行から31行）。
獅子の捕獲制限と成りの展開は駒ごとの生成の中で着手ごとに行われる（[expand.rs](../../crates/minase-core/src/movegen/expand.rs) 25行）ので、全件生成の列に含まれることと`is_legal_move`が真を返すことは構成から一致する。
着手を逆算して前局面の候補を作る`predecessor/reverse.rs`（75行から89行）は、既にこの一致に依存している。

これは、やねうら王が`MoveList<LEGAL>.contains()`を`pseudo_legal_s<true>(m) && legal(m)`へ置き換えた変更（`yaneuraou-search.cpp` 5898行から5900行）と同じ方針である。
合法性の検査自体は省かないので、[MCTSの葉を審判層で裁定するADR](../adr/adjudicate-mcts-leaves-by-the-referee-before-the-repetition-approximation.md)が条件付きで先送りした「合法性の検査を省く軽いAPI」には当たらない。
生成する駒は最大46枚から1枚になるので、設計書の内訳で8.8%を占める合法性検査の生成の費用は、ごくわずかになる。
`is_legal_move`と`generate_moves`の一致を確かめる試験は`crates/minase-core`にないので、置き換えるなら参照試験として加える。

### R1の攻撃的着手の判定は利きの逆引きと動かした駒1枚の捕獲生成で足りる

`move_was_attacking`は、着手側の全合法手を生成し、いずれかの相手の王駒を取る手があるか、または動かした駒（到達升にある駒）に捕獲手があるかを調べる（[r1.rs](../../crates/minase-core/src/game/repetition/r1.rs) 223行から244行）。
設計書は、この判定を候補手では遅延評価にする一方、`record_move`での1回は全件生成のまま残す。
残す理由として設計書が挙げるのは、動かした駒が取れる相手の駒が獅子だけの場合に、獅子を取る手が捕獲制限で不合法になり得て、疑似利きの有無だけでは判定できないことである。
この理由は、2つの条件をまとめて疑似利きで判定する案に対するものであり、条件ごとに別の方法で判定すれば、全件生成なしに正確に判定できる。

第1の条件「相手のいずれかの王駒を取る合法手がある」は、王駒の升ごとに`attackers_to_by(mover, royal, occupied)`が非空かを調べれば足りる。
設計書が王駒1枚の捕獲可能性に使う補題は、対象の升に対して成り立つ。
捕獲の制限（第14条から第16条）は獅子を取る手にしか掛からず（[lion_capture.rs](../../crates/minase-core/src/movegen/lion_capture.rs) 23行から26行は、取る獅子がなければ無条件に真を返す）、王駒は獅子ではない。
獅子が経由升で取る手は移動元へ戻る居喰いが常に生成され（[lion.rs](../../crates/minase-core/src/movegen/lion.rs)の「移動元へ戻る居喰いも含む」）、距離2の升へは中間升の占有を問わず直接跳べる（`lion_jumps`は距離2の升の集合）。
したがって、2段階目で別の駒を取る手が捕獲制限で不合法になっても、王駒だけを取る1段階の着手が必ず残る。
角鷹と飛鷲も同様である（[lion_like.rs](../../crates/minase-core/src/movegen/lion_like.rs)）。
成りの展開は不成と成りの少なくとも一方を出す（[expand.rs](../../crates/minase-core/src/movegen/expand.rs) 33行から38行）。
したがって、王駒が2枚でも「いずれかを取れるか」は升ごとの判定の論理和で求められ、全件生成と一致する。
これは、やねうら王が`continuousCheck`へ入れる真偽値を、合法手生成ではなく`gives_check`の表参照（`checkSquares`と`blockersForKing`）から得ることに相当する。

第2の条件「動かした駒に捕獲手がある」は、到達升の駒1枚について捕獲限定の生成`generate_piece_moves::<true, false>`を行えば、獅子の捕獲制限を含めて全件生成の結果と一致する。
先獅子の状態は`Position`が持つので、他の駒の生成には依存しない。
じっと（隣接升へ進んで同じ着手で元の升へ戻る非捕獲の着手）の到達升は元の升なので、同じ扱いでよい。
捕獲先の駒が獅子でなければ利きの逆引きだけで判定できるが、場合分けを増やすより、駒1枚の生成に統一するほうが単純である。

この置き換えは、`record_move`の1回と、遅延評価の後に残る候補手ごとの判定の両方に効く。
設計書の内訳で37.4%を占める`move_was_attacking`の費用は、遅延評価と合わせて、ごくわずかになる見込みである。
`generate_piece_moves`は`pub(super)`なので、1駒の捕獲生成を`MoveGenerator`の公開の関数として足す必要がある。

### 「いずれかの王駒を取れるか」と駒枯れの猶予の判定も1駒の範囲で足りる

駒枯れの引き分け（第22条第8項）と裸玉の裁定（第32条E3）は、`can_capture_any_royal`（[bare_king.rs](../../crates/minase-core/src/game/adjudication/bare_king.rs) 73行から90行）で、手番を入れ替えた局面の複製から全合法手を生成し、「いずれかの王駒」を取る手を探す。
条文はいずれも「いずれの王駒も」「いずれかの王駒を」と升ごとの条件で書かれているので、前節と同じ升ごとの補題で`attackers_to_by`の論理和へ置き換えられる。
この判定が走るのは、双方が王駒だけになった引き分けの判定と、片側が裸玉で相手が価値ある駒を2枚以上持つ敗北の判定（同27行）であり、設計書の測定の経路では費用を占めないが、同じ補題の適用なので同じ変更で扱える。

駒枯れの猶予（第22条第5項）の判定も合法手生成を使う（[exhaustion.rs](../../crates/minase-core/src/game/adjudication/exhaustion.rs) 101行）。
王駒だけになった側の手番で、余分な駒または相手の最後の王駒を取れるかを調べる判定であり、`candidate_immediate_result`（[adjudication/mod.rs](../../crates/minase-core/src/game/adjudication/mod.rs) 164行）から候補手ごとにも到達する。
余分な駒は獅子であり得るので、升ごとの補題は使えない。
しかし、王駒だけになった側が動かせる駒は王駒1枚だけである（死に駒は動けず、第9項により王将と太子を併せ持つ側は余分な駒を持つ側になる）。
したがって、その王駒1枚についての着手生成で全件生成と一致する。

一方、詰み判定の`can_capture_last_royal`は「残存王駒をすべて1手で取れるか」であり、2枚のときは1手で両方を取る合法手が要るので、設計書のとおり合法手生成を残す。
αβ探索の根の候補手の選別（[root_repetition.rs](../../crates/minase-core/src/game/root_repetition.rs) 69行）にも応手の全件生成があるが、`Game::play`の外の処理なので本書の対象外とする。

### 合法手なしと詰みの判定は駒ごとの生成で打ち切る

やねうら王の`is_mated()`は一括生成であり、ここからそのまま適用できる手法はない。
ただし、MovePickerが必要な手だけを段階的に生成し、βカットで残りを生成しないこと、および王手回避の生成が王の移動と王手駒の捕獲へ候補を絞ることから、次の2つが導ける。

第1に、合法手なしの判定と詰み判定は、どちらも「条件を満たす手が1つ見つかれば終わる」判定である。
合法手なしは最初の合法手で偽が確定し、詰みは最初の逃れる手で偽が確定する。
反復規則R2とR3（既出局面の再現を禁じる規則）では、禁止手を除いた最初の手で判定する。
設計書は両者で1つの合法手列を共有するが、列を全件作ってから走査する必要はない。
駒ごとに生成して候補手を順に試し、逃れる手が見つかった時点で残りの駒の生成を省けば、通常の経路の生成は全件から数駒分へ減る。
逃れる手が見つかるまでに試す候補手の数kは平均で約3なので、最初の数駒で逃れる手が見つかる。
判定の結果は真偽値なので、生成と走査の順序は結果に影響しない。
R2とR3の禁止手の除外、候補手ごとの即時の裁定、および試行ごとの局面の復元は、順序を変えても維持する。

第2に、王駒が攻撃されている局面では、逃れる手は王駒自身の移動、攻撃駒の捕獲、または走り駒の利き線への合駒に偏る。
やねうら王の王手回避の生成はこの3種に候補を限る。
中将棋の詰みの定義（第21条第3項）は、即時の勝ちと引き分けを生じる着手と相手の最後の王駒を先に取る着手も逃れる手に数えるので、候補を3種に限ることはできない。
候補を限らずに、王駒の手と攻撃駒を取る手を先に試す順序にすれば、正確さを保ったままkを減らせる。
`PieceKind::ALL`の順では王将と太子は後方にあるので、順序の変更は生成を呼ぶ側で行う。

駒ごとの生成は、設計書の「合法手列の共有」と両立し、共有した列を作る代わりに、両方の判定が1つの生成の進行を共有する形になる。
やねうら王の`blockersForKing`に相当するピンの表を持てば、「王駒が攻撃されておらず、ピンされていない駒の1段階の静かな手があれば詰みではない」と生成なしに判定することもできる。
しかし、設計書の疑似利きの判定を入れた後は候補手1つの費用が着手の適用と復元と利きの逆引きだけになるので、表を持つ利点は小さい。

### 採らない方式

やねうら王の`checkersBB`を局面に付随させて差分更新し、`checkSquares`と`blockersForKing`を着手ごとに構築する方式は、「王駒に利きが届くか」を配列参照で判定できる利点があるが、minaseでは`attackers_to_by`によって局面から直接に判定できる。
差分更新は`Position`に状態を増やし、獅子と角鷹と飛鷲の2段階移動で経由升が空く場合の更新を要する。
着手ごとの構築は、審判層が1手に1回しか使わない表を毎手作ることになる。
利きの逆引きの費用が測定で問題になるまでは、いずれも採らない。
`LONG_EFFECT_LIBRARY`の利き数も同じ理由で採らず、やねうら王自身も既定のビルドで無効にしている。

王手の放置が合法な中将棋では、王手回避の生成による合法手の絞り込みも、`legal()`によるピンと王の移動先の判定も採れない。
また、`givesCheck`を探索が計算して`do_move`へ渡す方式は、審判層が探索側の申告に依存せずに裁定する責務を持つので採用しない。

## 設計書への反映候補

次の項目は、本書の結論を設計書へ反映する候補であり、採否は設計書の測定で判断する。
設計書は2026年10月28日にこの5件を取り込んだ。
いずれも裁定の結果を変えない置き換えであり、設計書のフェーズ1の参照試験の型で全件生成との一致を確かめられる。

1. 着手の合法性検査を`try_make_move_with_undo`の全件生成から`is_legal_move`の1駒生成へ置き換える。`is_legal_move`と`generate_moves`の一致を確かめる参照試験を加える。
2. `move_was_attacking`を、王駒の升ごとの`attackers_to_by`と到達升の駒1枚の捕獲限定生成へ置き換える。`record_move`と候補手の両方に効く。設計書の「R1の記録の攻撃的着手」の設計判断（全件生成を維持する）を改める。
3. `can_capture_any_royal`を王駒の升ごとの`attackers_to_by`の論理和へ置き換える。
4. 駒枯れの猶予の判定を、王駒だけになった側の王駒1枚についての着手生成へ置き換える。
5. 合法手なしと詰みの判定で共有する合法手列を、駒ごとに生成して最初の逃れる手で打ち切る進行へ改め、王駒の手と攻撃駒を取る手を先に試す。

1から4までを加えると、通常の経路で再生1手あたりに残る全件生成は、合法手なしと詰み判定で共有する1回だけになる。
5を加えると、その1回も数駒分の生成になる。
設計書の「約3回」の見込みは「1回未満」に改まる。
ただし、`attackers_to_by`と1駒の生成の費用は全件生成の46分の1ではなく、置き換え後の探索時間は測定で確かめる。
設計書の完了条件である探索時間の半減の判定方法は変えない。

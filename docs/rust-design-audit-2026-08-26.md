# Rust設計監査報告書

## 監査の目的

本報告書は、minaseのRustコードが、Rustの型システム、所有権、エラー処理、公開API設計を十分に活用しているかを調べた結果である。
全ファイルの初回監査はコミット`6bc33e1`を基準とし、Rust 48ファイル、31,371行を調査した。
報告書の作成中に学習用PST（Piece-Square Table。駒の種類と升ごとの重み表）の実装が追加されたため、コミット`6bc33e1`からコミット`7e13888a8abe1752e9dd2aba4c4a6a16e61d192e`までの差分も追加調査した。
最終的な対象はRust 51ファイル、31,944行である。
2026年8月26日時点のHEAD `8e384a8`は`.gitignore`だけを変更したコミットであり、Rustソースは`7e13888`と同一である。
本文の行番号はこのコミット済みソースを基準とし、未コミットの作業ツリー変更は対象に含めない。

この監査でいう「Rustらしい設計」は、短いコードや特定の書式だけを指さない。
呼び出し側が作ってはならない状態を型で表現できなくし、通常の入力誤りを`Result`で返し、資源の終了処理を所有者の寿命に結び付ける設計を指す。
したがって、コンパイルが通るコードでも、公開APIの利用者が容易にパニックや不整合を起こせる場合は改善対象とした。

本監査ではソースコードを修正していない。
以下の改善案も実装方針の候補であり、API変更や性能変更に着手する前には、影響範囲を設計書で確定する必要がある。

## 用語

本文では、Rustに不慣れな実装者が判断根拠を追えるよう、次の意味で用語を使う。

- **crate**：Rustがコンパイルし、他のコードへ公開する単位を指す。

- **公開API**：別のcrateから呼び出せる型、関数、定数、モジュールを指す。

- **Clippy**：Rustコードにある典型的な誤りや読みにくい表現を検出する静的解析器を指す。

- **不変条件**：値が有効である間、常に満たす必要がある条件を指す。
  たとえば「成駒専用の駒種を未成として盤へ置かない」は駒表現の不変条件である。

- **パニック**：その場の処理だけでなく、通常はスレッドまたはプロセスを中断する異常終了を指す。
  外部入力の誤りは予想可能なので、原則としてパニックではなくエラー値を返す。

- **fallibleなAPI**：失敗を`Result`や`Option`として戻り値に表すAPIを指す。
  呼び出し側は成功と失敗を型に従って処理できる。

- **enum**：取り得る状態を列挙する型を指す。
  複数の`bool`や`Option`で状態を組み立てるより、不可能な組合せを作りにくい。

- **newtype**：既存の数値型などを1フィールドの専用型で包む設計を指す。
  `NonZeroUsize`も同じ目的で使え、0を受け付けないという条件を型で表現できる。

## 重大度

所見は、影響と到達可能性に基づいて3段階に分類した。

- **重大**：外部入力でプロセスを停止できる、公開APIから局面を破壊できる、または終了すべきスレッドが残る問題である。

- **中程度**：直ちに障害を再現していないが、不正状態、保守上の誤り、移植性低下を招きやすい設計である。

- **軽微**：意味は保たれているものの、標準APIや専用型を使う方が意図を明確にできる問題である。

## 監査結果の概要

重大な所見は6群あり、そのうち2件はプロトコル入力だけで実際のパニックを再現した。
残る重大所見は、公開型の定義域と関数の前提が一致しない問題、および探索スレッドの所有権に関する問題である。

一方、コード全体に`clone`、`String`、`Vec`、`unwrap`が無差別に使われているわけではない。
通常設定のClippyは警告なしであり、自作コードには`unsafe`ブロック、外部関数インターフェース、生ポインタ、`transmute`が存在しない。
このため、機械的な書き換えより、公開境界と状態表現を優先して直す必要がある。

## 重大な所見

### 非ASCIIのUSI着手文字列

USI（Universal Shogi Interface）は、将棋GUIとエンジンが文字列で通信するためのプロトコルである。
[USIの升解析](../src/notation/usi.rs#L136)は、バイト列を使って段番号の終端を求めた後、その位置をRust文字列の境界として使う。
UTF-8では1文字が複数バイトになるため、求めた位置が文字境界に一致するとは限らない。

実際に、`--protocol usi --rules engine-default`で起動したminaseへ次の入力を標準入力から与えると、[162行目](../src/notation/usi.rs#L162)で文字列スライスに失敗し、終了コード101でプロセスが停止した。

```text
usi
position startpos moves 1あ
quit
```

```text
thread 'main' panicked at src/notation/usi.rs:162:41:
end byte index 2 is not a char boundary; it is inside 'あ' (bytes 1..4 of string)
```

この入力は合法な着手ではないが、プロトコルの構文エラーとして予想できる入力である。
公開解析器は`UsiError`を返す契約を持つため、ASCIIであることを先に検証するか、`char_indices`で文字境界を追跡する必要がある。

同じ解析器は、[match_runnerの着手検証](../src/bin/match_runner.rs#L1262)が外部エンジンの`bestmove`文字列にも適用する。
解析器のエラー値は当該エンジンの反則負けへ写されるが、パニックは捕捉されないため、非ASCIIの着手表記を出力する相手エンジンは、自分の反則負けではなく測定ハーネス全体を停止させる。

### 置換表サイズのオーバーフロー

[USI](../src/protocol/usi.rs#L592)とCECP（Chess Engine Communication Protocol）の[設定処理](../src/protocol/cecp.rs#L663)は、外部から受け取った置換表サイズについて、0より大きいことだけを検査する。
その値は[TranspositionTable::new](../src/search/tt.rs#L133)または`resize`へ渡され、メビバイト（MiB）からバイトへの変換でオーバーフローするとパニックする。
`new`はrustdocでパニック条件を宣言しているので置換表側の契約は明示されているが、プロトコル層が上限を検査せずに外部入力を渡すため、宣言があっても停止は防げない。

実際に64 bit環境で同様に起動したminaseへ次の入力を与えると、[entry_count](../src/search/tt.rs#L255)の`checked_mul`後に置かれた`expect`でプロセスが停止した。

```text
usi
setoption name USI_Hash value 18446744073709551615
quit
```

```text
thread 'main' panicked at src/search/tt.rs:259:10:
transposition table size overflow
```

設定値の誤りは外部入力の問題なので、置換表の生成とサイズ変更は`Result`を返す必要がある。
プロトコル側も実用的な上限を検査し、利用者へ明示的なエラーを返すべきである。

### 駒コードとSFEN出力の不一致

SFEN（Shogi Forsyth-Edwards Notation）は、将棋の局面を文字列で表す形式である。
[PieceCode::new](../src/core/piece.rs#L247)は、`WhiteHorse`、`Whale`、`FlyingOx`など、成駒としてしか現れない8種類を未成の駒として構築できる。
成駒側の`new_promoted`は駒種を検査して`Option`を返すため、未成側だけが無検査という非対称がある。
[Position::validate](../src/core/position.rs#L577)は盤面集合の整合と駒コードの読取り可能性は検査するが、駒種と成りの整合は検査しないため、この状態を有効な局面として受理する。
公開の[PositionBuilder::put](../src/core/position.rs#L814)も任意の`PieceCode`を受け付けるので、この状態は外部crateから公開APIだけで構築できる。

しかし、[SFEN出力](../src/notation/sfen.rs#L272)は未成の成駒専用種に文字を割り当てておらず、`unreachable!`でパニックする。
`to_sfen`は失敗を返せない`String`戻り値なので、この不一致に出会った時点で停止以外の選択肢がない。
さらに、[訓練データのテスト](../src/eval/training_data.rs#L877)は未成の`WhiteHorse`の符号がバイト表現の往復で保持されることを確認しており、異常値が一時的な構築途中に限定されていない。

直接の原因は、`Position`が受理する`PieceCode`の範囲と、SFENが出力できる駒の範囲が一致しないことである。
盤上駒では基本駒と成駒を区別する型を使い、訓練データに追加の状態が必要なら、その目的に限定した表現へ分離するのが一貫した設計となる。

### 未検証着手と合法手の混在

[Move](../src/core/mv.rs#L10)は、移動元、中間升、移動先、成りフラグをすべて公開している。
したがって、空升からの移動、通常駒の2段階移動、不正な「じっと」など、局面に対して成立しない値を外部crateから作れる。

一方、[Position::captured_squares](../src/core/position.rs#L435)は移動元に駒があることを`expect`し、rustdocにもパニック条件の記載がない。
この`expect`には、公開の[best_move_is_tactical](../src/eval/training_data.rs#L566)を経由しても到達する。
[USIのtext](../src/notation/usi.rs#L57)は合法手生成器が作った着手であることを前提とし、前提を破る値では、じっと形の着手だけがパニックし、それ以外は局面と矛盾したUSI文字列を黙って返す。
いずれも通常名の公開関数なので、利用者は不正値を渡した結果を型から判断できない。

さらに、[make_move_unchecked](../src/core/position.rs#L667)と[unmake_move](../src/core/position.rs#L774)も公開されている。
両者はrustdocで局面破壊の可能性を警告しているが、誤った着手や対応しない`Undo`を渡すと、メモリ安全性は失わないものの、盤面、占有集合、ハッシュ値の対応を静かに壊す可能性がある。

外部入力を表す`MoveSpec`と、特定の局面に対して検証済みの`LegalMove`を分ける設計が候補になる。
少なくとも、uncheckedな更新関数と巻き戻しトークンはcrate内部に限定し、公開境界は`Result`を返す必要がある。

### 探索条件と探索局面の不正状態

[SearchLimits](../src/search/mod.rs#L56)は5個の公開フィールドで探索条件を表す。
この形では、制限が1つもない状態、深さ0、ノード数0、時間0、無期限探索と別の制限の併用を構築できる。
`validate`は深さと「制限が1つ以上あること」だけを検査するため、時間0や競合する条件は残り、無期限探索と併記された他の制限は探索が黙って無視する。
持ち時間を表す`ClockLimits`の公開フィールドにも検証はない。

[SearchSnapshot](../src/search/mod.rs#L108)も全フィールドが公開されている。
局面と規則が一致しない状態、履歴キーが別の対局に属する状態、ルート着手が合法でない状態を構築できるが、探索は内部でuncheckedな局面更新を使う。

[start_search](../src/search/mod.rs#L227)と[search](../src/search/mod.rs#L286)は公開APIであるにもかかわらず、空のルート着手や不正な制限を`assert!`で処理する。
公開入口が`Result<SearchHandle, SearchInputError>`などを返し、検証後の内部関数だけが不変条件を前提にすべきである。

型設計では、無期限探索と制限付き探索をenumで分け、深さや件数には0を表せない型を使う方法がある。
内部APIの時間に標準の`Duration`を使う方法もあるが、プロトコル境界で`_ms`付き整数を使うこと自体は単位が明記されており、直ちに不適切とはいえない。
`SearchSnapshot`は`Game`から作る検証済みコンストラクタを持ち、フィールドを非公開にするのが自然である。

### SearchHandle破棄後の探索スレッド

[SearchHandle](../src/search/mod.rs#L183)はイベント受信端、停止フラグ、`JoinHandle`を所有する。
`JoinHandle`は生成したスレッドの終了を待つための値だが、この型には破棄時の処理がない。

呼び出し側が[SearchHandle::join](../src/search/mod.rs#L204)を呼ばずに値を破棄すると、Rust標準ライブラリはスレッドを切り離す。
停止フラグへアクセスする所有者も失われるため、特に外部停止だけを条件とする探索は運用上終了しない処理になり得る。

所有者を破棄すると停止要求を出し、スレッドを回収する設計が必要である。
`Drop`で`JoinHandle`を取り出すならフィールドを`Option<JoinHandle<_>>`にする方法があるが、破棄時に待つ時間も含めて探索ライフサイクルの契約を先に決める必要がある。

## 中程度の所見

### 学習PST追加後の公開境界

初回監査後に追加された[特徴番号モジュール](../src/eval/features.rs#L1)にも、既存の`PieceCode`設計から派生する公開境界の不一致がある。
[piece_state](../src/eval/features.rs#L34)と[feature_index](../src/eval/features.rs#L44)は公開関数だが、公開定数である`PieceCode::EMPTY`または`PieceCode::WALL`を渡すと`expect`でパニックする。

これらの関数は学習評価関数の内部処理として使われており、外部利用を示すコードは確認できない。
特徴番号モジュールをcrate内部へ狭めるか、空升と番兵を含まない検証済みの盤上駒型を受け取る必要がある。

また、[start_search](../src/search/mod.rs#L227)と[search](../src/search/mod.rs#L286)は、埋め込み重みの検証結果に`expect`を使う。
探索を呼び出す4個のバイナリ（minase、bench、match_runner、selfplay_gen）は起動時に重みを検査して終了するが、ライブラリ利用者は各バイナリの`main`を通らないため、この前提は公開ライブラリでは成立しない。
探索器の構築時に検証済みの`Pst`を渡すか、公開探索APIが重みの検証エラーを返す設計が必要である。

評価器の所有権にも不一致がある。
[Pst::decode](../src/eval/pst.rs#L30)と[eval::evaluate](../src/eval/mod.rs#L13)は呼び出し側が復号した任意の`Pst`を扱えるが、公開探索APIはグローバルな埋め込みPSTだけを内部取得する。
したがって、外部から復号したPSTを実際の探索へ渡す経路がない。
任意のPSTを対応するなら探索コンテキストが`Pst`を所有し、固定評価器だけを対応するなら復号APIの公開範囲を狭める必要がある。

一方、[Pst::decode](../src/eval/pst.rs#L30)は、長さ、識別子、版、特徴数、尺度、文字列、検査和を専用の`Error`で検証する。
外部バイト列を文字列へ潰さず型付きエラーで拒否しており、この部分は公開境界の良い基準として利用できる。

### SetupPositionの公開フィールド

[SetupPosition](../src/notation/sfen.rs#L12)は、局面、直前の獅子捕獲升、次の手数を公開フィールドで保持する。
解析器は手数を1以上9,999以下に制限するが、利用者は0や10,000以上を直接代入できる。
獅子捕獲升と局面の整合も直接構築時には検査されない。

[to_extended_sfen](../src/notation/sfen.rs#L295)はこれらの値を無検証で出力するため、「解析器が受理する値」と「公開型が表現できる値」が一致しない。
フィールドを非公開にし、解析器と同じ規則を使う検証済みコンストラクタを設ける必要がある。

### 文字列へ失われるエラー情報

[RuleCodeのFromStr実装](../src/core/rules.rs#L112)と[parse_rule_set](../src/core/rules.rs#L137)は、エラー型として`String`を使う。
[RejectReason](../src/protocol/engine.rs#L60)も、規則エラーと局面エラーを文字列に変換して保持し、対局ライフサイクルの誤りである「the game has not started」まで`InvalidPosition`へ含める。

文字列だけでは、呼び出し側が「未知の規則コード」「併用できない規則」「対局未開始」を安全に分類できない。
元のエラーを`source`としてたどることもできないため、ログ以外の回復処理が文字列比較に依存する。

規則コード、規則集合、局面、対局ライフサイクルに専用エラー型を設け、表示用文字列への変換はプロトコル出力の直前に限定すべきである。
これはエラーメッセージの互換別名を増やす変更ではなく、原因を型で保持するための境界整理である。

### positionコマンドの黙示的な無視と補完

[USIのposition処理](../src/protocol/usi.rs#L645)は、`startpos`でも`sfen`でもない引数を受け取ると、エラーを出力せずに黙って戻る。
引数がない場合はエラー文字列を返すので、同じ関数の中で誤入力への応答が一貫していない。
この経路でも局面は非同期化されるため、GUIは後続の`go`が失敗するまで`position`の誤りに気付けない。

また、[SFEN欄の解析](../src/protocol/usi.rs#L837)は、第5欄の解析に失敗した場合、その欄が成り権保留欄の形でなければ黙って4欄の解釈を採用し、第6欄以降は常に無視する。
この曖昧さ解決の意図は関数コメントに記録されているが、誤字を含む第5欄が黙って読み飛ばされると、GUIとエンジンが異なる局面を持ったまま対局が進み得る。
外部入力の境界では、解釈できなかった欄を明示的なエラーとして返す方が、黙示的な補完より安全である。

### 探索ワーカーのパニック伝播

[探索チームの回収処理](../src/search/mod.rs#L514)は、補助ワーカーのパニックを`resume_unwind`でそのまま投げ直し、事前に停止フラグを立てない。
補助ワーカーのjoinは主ワーカーの完了後に行われるため、パニックの検出もそこまで遅れる。
主ワーカー自身がパニックした場合は停止フラグを立てる者がなく、`thread::scope`の暗黙のjoinが残る補助ワーカーの終了を待つため、無期限探索では外部からの停止要求が届くまで回収が終わらない可能性がある。

さらに、[start_search](../src/search/mod.rs#L227)が生成するスレッドはパニックを捕捉せず、`Finished`イベントも送られない。
プロトコル層は`join`の失敗を`io::Error`へ写して伝播し、minaseは`bestmove`を返さずに終了コード1で停止する。
探索中の内部バグをセッション全体の喪失として扱うこと自体は設計判断になり得るが、現在はその契約がどこにも文書化されていない。

### 置換表の最善手と検証キーの範囲

[置換表のprobe](../src/search/tt.rs#L173)は、キー検証を含む原子語を`Acquire`で読んだ後、最善手を含む別の原子語を読む。
[store](../src/search/tt.rs#L194)は最善手側を先に書くため、並行する書き込みと重なると、キー検証に合格した古いエントリの評価値へ、別局面の新しい最善手が組み合わさり得る。
`Hit`の文書は「格納されていた最善手」と述べるが、`Threads`が2以上ではこの保証は成立しない。

現在の探索は最善手を手の並べ替えにだけ使い、生成済みの合法手と一致した場合しか効果を持たないため、誤動作には至らない。
ただし、最善手を検証なしで指す・枝刈りに使うといった将来の変更はこの前提を壊すので、「最善手は助言であり照合対象外」という契約を文書化するか、最善手をキー検証の対象へ含める必要がある。

### プロトコル内の探索状態に関する改善候補

[USIの状態](../src/protocol/usi.rs#L26)と[CECPの状態](../src/protocol/cecp.rs#L25)は、置換表を`Option`で保持する。
`None`は「まだ存在しない」と「探索スレッドへ所有権を渡した」の両方を表し、探索開始時には`take().unwrap_or_default()`で欠落を既定表へ置き換える。

非公開の状態機械は重複した探索開始を防いでおり、この二義性による誤動作は再現していない。
ただし、`Idle { table }`と`Searching { handle }`のようなenumで置換表と探索ハンドルを同じ状態機械に含めれば、遷移と所有者を型から追いやすくなる。

CECPには別の重複表現もある。
[force_mode](../src/protocol/cecp.rs#L31)と[engine_side](../src/protocol/cecp.rs#L29)が同じ対局モードを別々に表すため、意味のない組合せを作れる。
現在は非公開の遷移処理が組合せを管理しているが、`Force`と`Playing { engine_side }`のenumにすれば、判定条件を1か所に集約できる。

### 探索セッション処理の共通化候補

[USI](../src/protocol/usi.rs#L213)と[CECP](../src/protocol/cecp.rs#L229)は、探索開始、イベント受信、停止、切断、古いイベントの破棄、スレッドの回収を別々に実装する。
プロトコル固有のコマンドは異なるが、探索スレッドの所有権と終了処理は共通である。

この重複は、片方だけが停止処理やエラー処理を変更する可能性を増やす。
一方、現時点で両実装に同じ不具合があることは確認しておらず、過度な共通化はプロトコル固有の流れを読みにくくする。
共通の`SearchSession`を導入するかは、停止と回収の契約を整理した後に、削減できる重複量と複雑さを比較して判断する必要がある。

### 内部表現の公開範囲に関する改善候補

[Square::raw](../src/core/square.rs#L71)、`raw_index`、`RAW_SQUARE_COUNT`、[Bitboard::words](../src/core/bitboard.rs#L37)、`VALID_WORD`は、番兵付き盤の内部配置を公開している。
[lib.rs](../src/lib.rs#L24)はこれらの型と定数の一部をcrateルートから再公開する。

`from_raw`は値を検査し、`from_words`は番兵ビットを取り除くため、これらの関数だけで不変条件が壊れるわけではない。
ただし、外部利用者が生インデックスや3個の`u64`へ依存すると、盤表現を変更するだけで公開APIの互換性が壊れる。
外部で必要な利用例を確認したうえで、密な座標、イテレータ、集合演算だけを安定APIとして残すか判断する必要がある。

[CapturedPiece](../src/core/mv.rs#L37)もcrateルートから再公開されているが、この型を返す公開関数と公開フィールドは存在せず、値は`Undo`の非公開フィールドにだけ現れる。
名前だけが公開された型は、利用者が必要とする操作が確定するまで内部に置く方がAPIを小さく保てる。

### doc(hidden)モジュールの公開

[lib.rs](../src/lib.rs#L15)は`rng`と`stats`を`#[doc(hidden)] pub mod`としている。
`doc(hidden)`は生成文書から項目を隠すだけであり、外部crateからの利用や互換性契約を無効にはしない。

[src構成の設計書](plans/src-layout.md#rngモジュールは現状維持とする)には、複数のバイナリで共有するために現在の形を維持する決定が記録されている。
したがって、これは意図しない実装ミスではなく、単一crate構成が生む既知の境界漏れである。
外部利用者または公開意思が生じた時点で、ライブラリと実行プログラムのcrate境界を引く必要がある。

### ライブラリとCLIの依存境界

[コマンドラインインターフェース（CLI）](../src/bin/minase.rs#L1)は、端末から実行プログラムへ引数を渡す入口である。
[Cargo.toml](../Cargo.toml#L6)では、`clap`と`mimalloc`が通常依存として宣言されている。
両者の参照は`src/bin/`に限られるが、ライブラリだけをビルドする場合にもコマンドライン解析器とC製アロケータが依存関係へ入る。

既存の[src構成の設計書](plans/src-layout.md#crate構成は単一crateを維持する)は、外部利用者、公開意思、ビルド時間の問題のいずれかをcrate分割の条件としている。
現状では意図的な単一crate設計だが、プロジェクトが外部利用可能なライブラリを目標に含む以上、この条件を定期的に見直す必要がある。

分割前の小さな選択肢として、CLI依存を任意機能にし、各バイナリへ`required-features`を指定する方法がある。
ただし、恒久的な互換層を増やすより、条件が成立した時点でライブラリと製品CLIを明確に分ける方が単純である。

### ホスト固有CPUへの固定

[.cargo/config.toml](../.cargo/config.toml#L2)は、このリポジトリを起点に実行するすべてのビルドへ`-C target-cpu=native`を渡す。
この指定はビルドしたコンピュータの中央処理装置（CPU）が持つ命令を最大限に使うため、生成したバイナリを命令の少ないCPUへコピーすると不正命令で停止し得る。
一方、Cargoのこの設定は起動ディレクトリから解決されるので、minaseを依存として別のディレクトリからビルドする外部crateには波及せず、影響はリポジトリ内で作るバイナリとテストに限られる。

この指定はコミット`4578e2d`（2026年8月1日）でperft実測のために追加されたもので、全ビルドへ常時適用する理由の記録はない。
現在のホストではx86拡張命令セットのAVX2などが有効になっており、通常のテストも同じ条件だけで実行されるため、移植性の退行をローカルで検出できない。
これは「ビルドしたホストでだけ動かす測定用バイナリ」には適するが、対局プログラムのバイナリを他の環境へ配る使い方とは両立しない。

リポジトリ共通設定からホスト固有指定を外し、性能測定時だけ専用コマンドまたは専用プロファイルで有効にする方法がある。
この変更は探索速度と時間管理へ影響し得るため、採否はベンチマークと再現手順を伴って判断する必要がある。

### Rustバージョンとパッケージ契約

[Cargo.toml](../Cargo.toml#L1)はedition 2024を指定するが、必要なRustバージョンを`rust-version`で宣言していない。
実測ではRust 1.87.0による全ターゲットの検査が、未安定のlet chainを理由に10件の`E0658`で失敗し、調査環境のRust 1.98.0では成功した。
let chainはRust 1.88.0で安定化された構文なので、最小対応版は1.88と推定できるが、1.88そのものでの実測は行っていない。

ライブラリ利用者は、どのRustバージョンからビルドできるかをCargoのメタデータから判断できない。
実測した最小対応版を宣言し、その版と現行stableの両方を継続的インテグレーションで検査する必要がある。

さらに、`cargo package --list --allow-dirty`は、description、licenseまたはlicense-file、documentation、homepage、repositoryの欠如を警告した。
公開するならメタデータと配布対象を定め、公開しないなら`publish = false`で意思を明示する必要がある。

### lint方針の適用範囲

[lib.rs](../src/lib.rs#L8)は`unsafe_code`を禁止し、公開項目の文書を警告対象にする。
しかし、crateルート属性は7個のバイナリや統合テストへ継承されないため、リポジトリ全体の方針にはなっていない。

Cargoの`[lints.rust]`と`[lints.clippy]`を使えば、同じ方針を全ターゲットへ適用できる。
`pedantic`と`nursery`を一括で警告にする必要はなく、プロジェクトが守るlintだけを選び、正当な例外には理由を記録する方が実用的である。

厳格なClippy設定では、公開`Result`の`# Errors`不足、公開関数の`# Panics`不足、多数の`#[must_use]`候補を検出した。
これらはすべてを機械的に直す対象ではないが、[Game::play](../src/core/game.rs#L175)、[parse_rule_set](../src/core/rules.rs#L137)、[SearchHandle::join](../src/search/mod.rs#L204)など、公開境界の契約から優先して確認する必要がある。

### 擬似乱数生成器の定義域

[XorShift64::new](../src/rng.rs#L34)は0を受け取ると`assert`でパニックし、`index`は長さ0で剰余演算のパニックを起こす。
さらに、`u64 as usize`は32 bitターゲットで上位32 bitを捨てる。
シードを`NonZeroU64`、長さを`NonZeroUsize`で受ければ、0という不正値を呼び出し前に排除できる。

`next`という名前は`Iterator::next`と紛らわしいが、この命名は理由付きの`#[allow(clippy::should_implement_trait)]`で設計決定として記録済みであり、改名は必須の改善ではない。

### 大きなローカル配列

[レイ表の初期化](../src/core/attacks/sliding.rs#L12)は36 KiB、[history表の初期化](../src/search/mod.rs#L584)は162 KiBの固定長配列をローカル値として作る。
後者は`Box::new`へ渡されるが、配列式の一時値が先にスタックへ置かれる可能性がある。

[Pst::decode](../src/eval/pst.rs#L70)も、約27 KiBの重み配列をローカル変数として初期化する。
復号は通常1回だが、スレッドのスタック容量によっては無視できない大きさである。

スタックは各スレッドに割り当てられる容量が限られるため、大きな一時値は探索ワーカー数の増加時に危険になる。
現状ではスタック枯渇を再現していないので、直接ヒープ上で初期化できる表現へ変える前に、対象環境で使用量を測定する必要がある。

### 引数群と長い実行関数

[探索内部](../src/search/mod.rs#L446)と[match_runner](../src/bin/match_runner.rs#L1283)は、`too_many_arguments`を複数箇所で抑制している。
局面、規則、履歴、ルート着手、共有状態、置換表などの同じ組を複数階層へ渡すため、順序の取り違えと責務の分散を招きやすい。

借用だけを保持する`SearchInput`やワーカー設定型へまとめると、関数が必要とする概念を名前で示せる。
ただし、関連しない値まで巨大な設定型へ集めると別の不明瞭さが生じるため、同じ寿命と同じ責務を持つ値だけをまとめる必要がある。

[match_runnerのmain](../src/bin/match_runner.rs#L1625)は204行あり、コマンドライン検証、エンジン解決、ワーカー制御、結果の順序統合、統計表示を1つの関数で処理する。
設定の検証結果、対局実行、集計と出力を段階ごとの関数へ分ける余地がある。

### バイナリ境界のテスト

`cargo test --all-targets --all-features`では472件のテストが成功したが、[selfplay_gen](../src/bin/selfplay_gen.rs#L1)と[perft](../src/bin/perft.rs#L1)はそれぞれ0件だった。
特に`selfplay_gen`は、ファイル作成、並列処理、パニック捕捉、検査サブコマンドを含む。

固定シードによる小規模生成、生成物の読み戻し、不正ヘッダ、既存ファイル拒否、並列度を変えたときの決定性をバイナリ境界で検査する必要がある。
`perft`には既知局面の深さ別ノード数と、不正なコマンドライン引数の回帰テストが適する。

## 軽微な所見

### 三状態を表すOptionの入れ子

crate内部（`pub(super)`）の[unpack_move](../src/search/tt.rs#L328)は`Option<Option<Move>>`を返す。
外側の`None`が破損、`Some(None)`が着手なし、`Some(Some(move))`が着手ありを表すが、型名だけでは意味を読めない。

この意味は関数の局所文書に書かれており、現在の表現もRustとして正しい。
それでも呼び出し箇所が増えるなら、`Result<Option<Move>, DecodeError>`または`Invalid`、`NoMove`、`Move`を持つ専用enumの方が状態を明示できる。

### 恒久的なlint抑制

リポジトリには`#[allow(...)]`が11箇所あり、内訳は`too_many_arguments`が7箇所、`type_complexity`が2箇所、`large_enum_variant`と`should_implement_trait`が各1箇所である。
このうち`reason`付きで理由を記録しているのは`rng.rs`の1箇所だけであり、`allow`は対象の警告が将来消えても残り続ける。

意図的に残す例外には`#[expect(lint名, reason = "理由")]`を使うと、警告が発生しなくなった時点で不要な抑制を検出できる。
ただし、抑制の置換だけで終わらせず、引数群が独立した概念を表す箇所は先に型へまとめる必要がある。

### 冗長なclone

[random_play](../src/bin/random_play.rs#L411)には、本番コードで確認できた唯一の冗長な`clone`がある。
後続の`fail`は戻らない関数なので、`previous_sfen`の所有権をそのまま渡せる。

この1件以外の`clone`は、局面のスナップショットやスレッドへの所有権移動に目的があり、機械的な削除対象ではない。

### 表示時の一時確保

[RulesのDisplay実装](../src/core/rules.rs#L599)は、表示するたびに`Vec<RuleCode>`を作る。
`RuleCode::ALL`を絞り込みながら`Formatter`へ直接書けば、一時的なヒープ確保を避けられる。

これは現時点で測定済みのボトルネックではない。
変更する場合も性能改善として扱うのではなく、処理を単純にする小規模な整理として判断する必要がある。

### 中点計算の標準API

[stats](../src/stats.rs#L59)は二分法の中点を`(lower + upper) / 2.0`で計算し、[bench](../src/bin/bench.rs#L186)は偶数個標本の中央値を隣接2値の同じ形の平均で計算する。
どちらも標準の`f64::midpoint`が同じ意図をより直接に表し、大きな有限値同士の加算が無限大になる経路も避けられる。
現在の値域でオーバーフローは起きないため、これは意図の明確化にとどまる。

### 開発ビルドの常時最適化

[Cargo.toml](../Cargo.toml#L15)は通常の開発プロファイルにも最適化レベル3を指定する。
探索を伴うテストは速くなる可能性がある一方、コンパイル時間が延び、デバッガでの実行順序がソースと対応しにくくなる。

この設定はコミット`649bbdd`（2026年8月11日）でmimalloc導入・release LTOと同時に追加されたが、コミットメッセージにも設計書にも理由と測定の記録がない。
通常開発、速度が必要な検証、リリースを別プロファイルにするか、現設定が必要なら再現可能な測定値を記録する必要がある。

## 改善の順序

修正は、局所的なlint警告より公開境界から進める必要がある。
同じ不変条件を各呼び出し側で繰り返し検査すると抜けが再発するため、型または1つの検証済みコンストラクタへ集約する。

1. USI文字列と置換表サイズについて、外部入力で再現する2件のパニックをエラー応答へ変更する。

2. `PieceCode`、`Move`、`SearchLimits`、`SearchSnapshot`、`SetupPosition`について、表現できる状態と各関数の前提を一致させる。

3. `SearchHandle`とプロトコル探索状態について、停止、所有権移動、パニック伝播、スレッド回収を1つのライフサイクルとして設計する。

4. 公開エラー型、公開範囲、ライブラリとCLIのcrate境界を整理する。

5. CargoのCPU指定、Rustバージョン、lint、パッケージ情報を整え、複数環境で同じ契約を検査できるようにする。

6. 大きな配列、引数群、長い関数、軽微なClippy所見を個別に処理する。

この順序は、古い挙動を別名や黙示的な既定値で残すことを意図しない。
公開APIを変更する場合は、成立しない状態を新しい型から除き、回復不能な入力には明示的なエラーを返す構造を優先する。

## 検証結果

次の検査は、コミット`8e384a8`をクリーンに取り出した作業木で、すべて成功した。
重大所見に挙げた2件のパニックも、同じ作業木でビルドした実バイナリで再現した。

```text
cargo fmt --all -- --check
cargo check --all-targets --all-features
cargo clippy --all-targets --all-features
cargo test --all-targets --all-features
RUSTDOCFLAGS='-D warnings' cargo doc --no-deps --all-features
cargo tree -d
```

全ターゲットのテスト472件がすべて成功し、通常設定のClippyは警告0件だった。
`cargo tree -d`は重複依存を報告しなかった。

一方、`clippy::pedantic`と`clippy::nursery`を追加した検査では、通常設定では表示されない多数の候補を検出した。
主な分類は、`#[must_use]`候補、値を切り詰め得るキャスト、公開`Result`の`# Errors`不足、符号変換で値が変わり得るキャストである。
固定幅の盤表現、テストコード、内部可視性に由来する低価値な警告も含むため、厳格Clippyの警告数をそのまま修正件数として扱うことはできない。

## 一致を確認した事項

自作コードには`unsafe`ブロック、外部関数インターフェース、生ポインタ、`transmute`、`MaybeUninit`が存在しない。
[lib.rs](../src/lib.rs#L8)はライブラリcrateについて`unsafe_code`を禁止している。

広範な`clone`乱用、無意味な添字ループ、`String`や`Vec`の無差別使用も確認できなかった。
`unwrap`と`expect`の大半はテストコード、または内部で証明された不変条件の表明に使われており、機械的に`Result`へ置き換える対象ではない。

規則型も、相互排他的な選択肢の多くをenumで表している。
そのため、規則の各`bool`を一律に専用型へ変える必要はなく、実際に不正な組合せを表現できる型だけを対象にすべきである。

探索が木の内部で同一局面の再現を一律に引き分けへ近似することは、[探索の設計書](plans/search.md)が採用理由と限界を含めて決定として記録している。
着手後の反復裁定は審判層が規則どおり行うため、本監査ではこの近似を指摘対象としない。

## 未確認の範囲

32 bit、Windows、macOS、WebAssembly向けのクロスビルドは、対象ツールチェーンが調査環境に入っていないため実施していない。
したがって、整数キャストとプラットフォーム固有処理については、静的な指摘を超える動作確認が残る。

Miri、サニタイザ、loom、ファジングによる動的検査も実施していない。
自作の`unsafe`コードがないためMiriの優先度は低いが、文字列解析とプロトコル状態機械にはファジングが有効と考えられる。

`cargo-audit`、`cargo-deny`、`cargo-machete`、`cargo-udeps`は調査環境に導入されていなかった。
このため、依存関係の既知脆弱性、ライセンス整合性、未使用依存は専用ツールで確認していない。

性能変更の採否も本監査の対象外である。
CPU指定、大きな配列、表示時の確保、開発プロファイルを変更する場合は、プロジェクトの測定方針に従って再現手順と実測値を残す必要がある。
